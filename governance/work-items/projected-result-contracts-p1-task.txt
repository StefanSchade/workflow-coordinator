======================================================================
WHAT INSPECTION FOUND: TWO INLINE SEAMS, NOT ONE
======================================================================

The concept document's own section 5 diagram and section 15 "likely
mutation surfaces" describe exactly one inline selection seam,
`vertical.py:300-305`:

  result_contract_version = (
      2 if profile.schema_version == 3
      or phase.convergence_role is not ConvergenceRole.NONE
      else 1
  )

Commission-time source inspection found a SECOND, textually identical
inline copy of this same predicate inside `reducer.py`'s `reduce_result`
(currently around lines 1275-1283), there named `expected_result_version`
and used to fail closed when `result.schema_version != expected_result_version`:

  expected_result_version = (
      2 if profile.schema_version == 3
      or (phase is not None and phase.convergence_role is not ConvergenceRole.NONE)
      else 1
  )

Within one live dispatch both copies read the same in-memory `profile`
object, so today this duplication is not itself a live correctness bug.
It IS, however, a second permanent copy of the exact logic P1's
acceptance criteria require to be replaced, not left standing ("the old
inline selection seam is replaced, not left as parallel logic"). If P1
introduces `select_result_contract(...)` and calls it only from
vertical.py while leaving reducer.py's copy untouched, that is a FAILED
P1: a real seam exists at one call site while a parallel, un-replaced
duplicate survives at another. `reducer.py` and `tests/unit/test_reducer.py`
are therefore authorized, narrowly: replace reducer.py's inline duplicate
predicate with a call to (or a value consistently derived from) the same
selector vertical.py now calls, so there is exactly one selection
computation in the codebase. Do not change any other reducer.py behavior:
Finding authority, convergence-fact derivation, route authority, and every
other `reduce_result` check must be byte-for-byte unchanged in effect.

P1 MUST ESTABLISH
======================================================================

1. A provider-neutral closed result-contract identity, `ResultContractKind`,
   following the repository's `CoordinatorValue` pattern (model.py:30-31,
   e.g. `class ResultContractKind(CoordinatorValue): ...`). At minimum it
   must have one member equivalent to today's generic routing-result
   contract (both v1 and v2 legacy shapes remain reachable through it; P1
   does not collapse the existing v1/v2 axis, it sits alongside/above it).

2. One deterministic selector, conceptually
   `select_result_contract(profile, phase, run) -> ResultContractKind` (or
   the smallest truthful equivalent; exact parameter list is
   implementation's choice as long as it is a pure function of ADMITTED
   facts, never of ambient/mutable state). It must be keyed ONLY by:
     - `Phase.role` (WorkflowRole);
     - whether `Phase.review` is present, and `Phase.review.finding_authority`;
     - `Phase.convergence_role` (ConvergenceRole);
     - the Run's governing contract-version lineage (today:
       `profile.schema_version` / `run.schema_version`, exactly the facts
       already read at both existing inline sites).
   NEVER by hard-coded phase-key strings such as `if phase_key == "review"`.

3. The selector REPLACES, at BOTH existing inline sites (vertical.py AND
   reducer.py; see prior section), the current duplicated computation. No
   dual permanent architecture: no new path running beside an un-replaced
   old one.

4. The selected kind reaches the adapter boundary: `AgentExecutionRequest`
   (adapter.py) must carry the selected kind (a new field, or an
   equivalent carrier) alongside its existing `contract_version`/
   `result_contract` fields, not merely an internal vertical.py-local
   variable the adapter never sees.

5. `codex_adapter.py`'s `CodexCliAdapter.execute` must consult the
   selected kind it was given and must NOT infer workflow semantics from
   `request`'s phase, role, or any phase-name string -- it has none of
   those today and must gain none. It is authorized to add exactly one
   narrow guard: reject (fail closed) a kind it does not support, mirroring
   its existing `request.contract_version not in {1, 2}` check. Its
   existing schema-generation functions (`routing_result_openai_schema`,
   `structured_result_envelope_openai_schema`) are not expected to change
   shape or behavior in P1, only to become reachable through the new seam
   for the one generic kind every current phase selects.

6. Every currently supported phase (every phase in every current
   governance fixture, test profile, and the self-development profiles
   themselves) must select a kind equivalent to today's generic
   RoutingResult/`routing-result-envelope` contract. No phase's dispatched
   schema, parser, or reducer input changes shape in P1.

7. Existing reducer semantics remain unchanged (see prior section: the
   ONLY reducer.py change authorized is replacing the inline duplicate
   predicate with the selector call).

8. Existing provider-visible JSON schema remains semantically equivalent
   (same required keys, same shapes, same v1/v2 branching) for every
   phase.

9. Existing prompt semantics remain unchanged. `prompt.py` is NOT
   authorized for this P1 scope: the selected kind need not be mentioned
   in agent-facing prompt text to satisfy any P1 acceptance criterion
   (the audit requirement in the next section is met by persisting the
   kind on the Hop record, not by prompt text). If implementation
   discovers a genuine reason `prompt.py` must change, escalate
   (requires_human=true, escalation.kind=scope) rather than touch it.

PERSISTENCE / REPLAY REQUIREMENT (resolve explicitly, do not skip)
======================================================================

Current state, confirmed by inspection: `Hop` and `HopSummary` (model.py)
persist NO per-Hop contract/version identity field today.
`AgentExecutionRequest.contract_version` and the parsed
`RoutingResult.schema_version` are used transiently for dispatch and
validation and are never written onto a Hop or Run record. The only
durably persisted version fact today is `Run.schema_version` itself
(1/2/3, a Run-level fact, unrelated to any single Hop's dispatched
contract).

`serialization.py` already establishes the working precedent for adding
exactly this kind of optional, version-gated, backward-compatible Hop
field: `pre_route_anchor_sha256` is present only where available, is
never fabricated for historical data, and required no Run.schema_version
bump or migration (`run_to_json`/`_hop_summary`, see the
`anchor_field`/`run_version == 3` handling). P1 must follow the identical
discipline for the new identity:

  * For NEW P1-created Hops: the exact `ResultContractKind` actually
    selected for dispatch must be durably recorded on that Hop/HopSummary,
    at the same granularity `pre_route_anchor_sha256` already
    demonstrates, so a later inspector or replay never has to re-derive it
    from current (possibly since-edited) profile YAML content.
  * For HISTORICAL Hops/Runs created before P1: they remain readable and
    replayable with NO migration, NO reinterpretation, and NO fabricated
    `ResultContractKind` invented from current configuration. Where no
    such field was ever recorded, none is synthesized; legacy behavior
    (today's version-int-only path) continues to apply to that history
    exactly as it does today.
  * Byte-identical serialization of NEW Runs is NOT required if adding the
    identity requires a new field; byte-identical serialization of
    PRE-EXISTING persisted Runs (`run_to_json` round-trip) IS required and
    must be tested (see test coverage section).
  * `reduce_result`/replay must not re-derive a NEW Hop's persisted kind
    from mutable current profile configuration when a durable per-Hop
    record exists for it; where no persisted identity exists (legacy
    Hops), the existing recompute-from-profile behavior is correct and
    must be preserved unchanged.

Exact field name and placement (a new `Hop`/`HopSummary` field; whether it
extends `contract_version`'s existing role or is a sibling field) is left
to implementation. The binding requirement is that replay semantics are
unambiguous: given the rule above, a reviewer must be able to state, for
any Hop old or new, exactly which contract/version governed it and why,
without guessing.

======================================================================
FAIL-CLOSED BEHAVIOR
======================================================================

If P1 introduces a representable condition where a contract kind is
unsupported, unknown, inconsistent with the carried version, or missing
where new history requires it, the implementation must fail closed BEFORE
any provider invocation (mirroring today's `OpenAIStrictSchemaError`/
`ResultValidationError` paths). Do not invent a fallback to the generic
contract for an unknown NEW kind. Truthful legacy/historical handling is
different and must keep working exactly as today: an old persisted Hop
with no kind recorded is legitimately legacy, not an error condition.

ACCEPTANCE BOUNDARY
======================================================================

P1 may complete only when fresh independent review establishes ALL of:

 1. One permanent provider-neutral ResultContractKind identity exists.
 2. Contract selection is deterministic from admitted semantic facts and
    uses no hard-coded phase-name branching.
 3. BOTH old inline selection copies (vertical.py and reducer.py) are
    replaced by the one selector; neither survives as parallel dead or
    live logic.
 4. The selected contract kind reaches AgentExecutionRequest/the adapter
    boundary.
 5. The adapter does not infer workflow semantics from phase names.
 6. Every currently supported phase still receives the generic current
    contract.
 7. Current provider-visible schema remains equivalent.
 8. Current generic RoutingResult semantic parsing/reduction remains
    equivalent.
 9. New P1-created history durably preserves the actual selected contract
    identity at replay-relevant granularity.
10. Pre-P1 historical Runs remain readable/replayable without migration or
    fabricated current-profile-derived identity.
11. Replay does not re-derive a new Hop's contract identity from mutable
    current profile configuration when a persisted record exists.
12. Missing/unknown/inconsistent new contract identity fails closed where
    applicable.
13. No real provider invocation was required to demonstrate any of this.
14. The full active test suite is green.
15. No P2 strict worker/reviewer result types were introduced.
16. No reducer authority was weakened, narrowed, or bypassed anywhere
    outside the one authorized predicate replacement.
17. No Harness/operator architecture was changed.
18. No unrelated source/test/governance path was modified.

The reviewer must explicitly answer, in the durable review artifact:
  * Is the new seam real, or merely dead indirection around the same
    global constant?
  * Could P2 add genuinely distinct WorkResult/ReviewVerdict projections
    through this seam without replacing P1?
  * Does persisted new history prove which contract was actually
    dispatched?
  * Can historical old Runs still replay truthfully?
  * Is there any path where the adapter or replay layer guesses semantic
    contract kind from phase-name strings?
  * Did implementation accidentally alter current generic provider schema
    or reducer behavior?
  * Did scope creep into P2/P3/P4/P5?

Acceptance means only that P1 infrastructure is sound; it does NOT itself
promote Runtime, authorize P2, or push.
