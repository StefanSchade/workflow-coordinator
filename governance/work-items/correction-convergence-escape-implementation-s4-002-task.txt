======================================================================
CRITICAL S4-002 PROMPT / ROLE HARDENING
======================================================================

The predecessor S4-001 Commission exposed a prompt/contract-adherence
ambiguity: its H001 worker returned outcome=changes_required to mean "useful
partial progress, more work remains" rather than a review/rereview verdict.
This section fixes that ambiguity in THIS Commission's own task semantics and
worker persona prose -- it does NOT change the WFC engine, result schema,
reducer, or general product contract merely to solve this one incident.

A worker Hop is a phase-completion handoff, NOT an incremental time slice.

For phase `implement`:
* inspect the complete authorized Slice-4 obligation and the complete current
  repository, including the salvaged candidate described above;
* continue ordinary authorized implementation work within THIS invocation;
* do not stop merely because additional normal in-scope implementation work
  remains;
* do not use another Hop as an ordinary continuation mechanism;
* when a complete review-ready implementation candidate exists, return
  outcome=completed, requested_route=review, with a truthful commit_intent
  for the candidate.

For phase `correct`:
* address the projected review findings completely within THIS invocation,
  insofar as authorized;
* ordinary remaining correction work is not a reason to stop;
* when the candidate is rereview-ready, return outcome=completed,
  requested_route=rereview.

`changes_required` is a REVIEW / REREVIEW VERDICT. The implementation/
correction worker MUST NOT use `changes_required` to mean: more
implementation remains; this is a partial implementation; I want another
worker Hop; I completed a useful subset; the task is large; or I prefer to
continue later. `max_autonomous_hops: 10` is a CEILING for the whole
workflow, not permission to split implementation into ten partial worker
invocations.

If a worker genuinely cannot reach the phase handoff due to failure,
unauthorized scope, missing prerequisite, semantic-authority issue, public
surface choice, trust-boundary issue, or another real stop condition, it must
use the appropriate structured blocked/failed/human/escalation semantics. It
must NOT encode such a stop as `changes_required`. Do not weaken fail-closed
behavior.

This successor deliberately does not mechanically change result-v1/result-v2
grammar in this Commission: it is testing whether explicit phase-local prompt
semantics, carried in this task text and in `WorkItem.personas`, are
sufficient on their own.
