Produce, and have independently reviewed, ONE design record for the
smallest viable contract that lets a semantically specified, authorized
Commission Intent select a versioned reusable workflow program and
deterministically produce the governing inputs (WorkItem, profile, policy,
task, components) that existing WFC admission already consumes. This is
Workstream 3 of the 2026-10-26 Front Door plan. Design and independent
review only. No production code, no test implementation, no profile
migration, no renderer, no Run of any kind.

Loop: design -> independent_review -> {accept: complete, correction};
correction -> rereview; rereview -> {accept: complete, correction}. Initial
phase: design. No supervisor. No child Run. No nested WFC.

An `accept` disposition at `independent_review` or `rereview` makes the
design artifact this Commission's accepted target design. It does not
itself authorize implementation: a later Commission that builds any part of
this design (a CommissionIntent parser, a renderer, a Direct or Robust
profile) still requires its own separate, explicit maintainer Commission.

======================================================================
WHY THIS DESIGN IS BEING COMMISSIONED
======================================================================

The 2026-10-26 plan deferred P3.5 implementation behind Front Door /
Profile-Commission stabilization. The 2026-10-27 decisions record then
named Direct and Robust as the first reusable-program targets and required
(`DEC-WFC-020`) that Front Door Basic's human and machine interfaces share
one structured, validatable semantic Commission contract with a
deterministic, authority-free projection to governing inputs -- but left the
concrete schema and implementation decomposition explicitly open (its §4).
The accepted profile archaeology supplies the evidence for how much
parameterization surface actually exists: one base WORK/GATE cycle
(occurring once or twice) covers 35 of 36 profiles in the amendment
baseline, phase names carry no engine meaning, and Finding authority,
evidence-failure routing, phase/route structure, and mandatory defensive
review are the recorded counterexamples that must not be treated as safe
parameters. This Commission closes exactly that open schema question, at
the smallest bounded scope that remains exercisable on one real Commission.

======================================================================
REQUIRED DESIGN COVERAGE -- the design artifact must give each a concrete,
implementation-ready answer, not merely acknowledge it
======================================================================

A. Boundary and ownership. Separate, with an explicit ownership table in
   the style of the Commissioning concept §6: immutable program semantics
   (the reusable workflow program itself); Commission-specific task
   bindings (scope, persona, evidence profile, artifact paths); explicit
   authorization (the maintainer act that makes a rendered bundle
   admissible); derived effective permissions (what Level 0 actually
   computes and enforces); and Runtime-owned execution. State where a
   reusable program is stored, how a Commission pins a specific program
   revision so an in-flight or historical Commission's semantics cannot
   silently shift under it, and which Commission-supplied parameters are
   allowed versus structurally forbidden (cite the archaeology's
   counterexamples by name).

B. Commission Intent. Propose a minimal, understandable structured contract
   (field list, types, and at least two realistic worked examples -- one
   Direct, one Robust) usable through both a human-facing interface and a
   machine CLI/file interface, following the Commissioning concept §12's
   canonical/derived split. Distinguish, field by field, which are
   user-provided semantic decisions and which are compiler-derived, and
   describe concretely how an operator inspects the effective rendered
   governing inputs before authorizing PREPARE/LAUNCH (per the
   Commissioning concept §2.2's usability requirement that the operator can
   see which task, which program revision, which authority, and which model
   bindings actually entered execution).

C. Deterministic projection and fail-early validation. Define, precisely
   enough to guide a later implementation, how the compiler produces the
   four existing WFC governing inputs (WorkItem, profile, policy, task;
   components reused unchanged) from a Commission Intent without granting
   authority itself. State explicitly, with a short worked trace against
   `operator.py:_preflight`'s actual checks, why the compiler cannot
   silently weaken process guarantees, enlarge scope, alter mandatory
   reviews, or change Finding-disposition permissions. Address how the
   rendered projection is pinned (git commit, consistent with the
   Commissioning concept §5.1's "git diff is the review seam") and how a
   later launch step confirms the inputs it is about to admit are exactly
   the ones that were validated -- not a file hand-edited afterward without
   re-validation. State that every generated Commission must undergo this
   provider-free validation before any agent invocation, and that an
   invalid configuration must fail at that point, never at or after the
   first Hop.

D. Reusable program compatibility. Use Direct and Robust (`DEC-WFC-022`) as
   the two initial target scenarios. For Robust, state the exact grammar
   element needed to express "no successful Completion may occur without a
   renewed full-breadth review after any correction" -- the 2026-10-26
   plan's own §9 grammar hypothesis does not yet name this edge; name it
   concretely (e.g., as a derived non-removable route constraint) without
   proposing a general-purpose workflow DSL. Preserve, and state how the
   design preserves: professional continuation across separately authorized
   successor Runs (`DEC-WFC-014`, never resume/retry/replay); existing
   same-Run reconciliation; and the salvage/authority separation
   (`DEC-WFC-013`). Identify only the minimal additional program-semantic or
   grammar primitives the Direct/Robust target actually requires beyond
   what the accepted base-pattern-plus-modifiers hypothesis (Commissioning
   concept §9) already describes -- do not invent primitives beyond what
   Direct and Robust concretely need.

E. Concrete proof path. Propose the smallest vertical implementation slice
   (naming the concrete files/functions it would touch, at a level the
   maintainer could commission directly as a future, separate Commission)
   that could be exercised on one real, newly authorized Commission --
   Direct is the more likely first candidate given its simplicity -- without
   migrating any historical profile. Identify the specific program-invariant
   tests (e.g., "a Robust-derived profile always rejects acceptance after
   any correction without an intervening broad gate") and the
   compiler/admission-correctness tests (round-trip: Commission Intent ->
   rendered governing inputs -> `_preflight` acceptance; and a negative case
   per counterexample in A) that slice would need, without writing them.

======================================================================
HARD CONSTRAINTS -- not design questions
======================================================================

Design and independent review only. No production code or test
implementation. No bulk profile migration or historical-compatibility
project. No P3.5 implementation: its general static reachability validator
is deferred beyond the Beta MVP unless a concrete MVP safety requirement
demonstrably makes it unavoidable, and this design must not construct that
case unprompted -- if the design finds itself needing a reachability
validator to make Robust's renewed-review invariant enforceable, name that
dependency explicitly as a flagged open question rather than designing the
validator here. No Level-1 implementation, Front Door Advanced, provider
registry, quota scheduler, or generalized orchestration framework. No
redesign of archive storage or the Claude adapter.

INDEPENDENT_REVIEW (phase `independent_review`)
======================================================================

- Independently and adversarially attempt to falsify the design, with fresh
  context, against every item in Required Design Coverage A-E and every
  Hard Constraint above, and specifically against: whether the trust-
  boundary asymmetry from the Commissioning concept (§5.2: above the
  boundary a requester may add assurance and narrow capability; below it,
  derivation may add assurance and narrow capability, and its additions are
  not removable from above) is actually preserved by the proposed
  Commission Intent fields and compiler behavior; whether any field or
  mechanism would let a Commission Intent silently weaken an existing
  admission predicate (walk `_preflight`, `_admit_a1`, and
  `_admit_evidence_disposition` against the proposal); whether Direct and
  Robust are given concrete, exercisable grammar coverage rather than prose
  aspiration, and whether Robust's renewed-broad-review invariant is
  actually unbypassable in the proposed grammar; whether the proof path in
  E is genuinely minimal and does not quietly require touching an existing
  profile or a kernel file; and whether the design accidentally designs a
  general-purpose workflow DSL, a provider registry, or Front Door Advanced
  despite the Hard Constraints. Reject speculative platform-building even
  where internally consistent.
- Record the review in the required durable artifact
  docs/warm_storage/concepts/workflow_coordinator_front_door_commission_contract_design_2026-10-28_review_001.adoc.
  If requesting correction, assign every blocking requirement a stable
  identifier (`FDC001`, `FDC002`, ... ) naming the underlying design
  requirement/invariant, not merely the single example that most recently
  demonstrated it, and list every open identifier explicitly in the
  artifact.
- If the design is sound, request `route: accept`. If correction is
  needed, record the concrete blocking problem(s) -- each under its stable
  `FDCxxx` identifier -- in the durable review artifact and request
  `route: correction` with `outcome: changes_required` and an empty
  `findings` list -- do not create a WFC Current-Run Finding merely to
  carry an ordinary design defect. Do not invent a shadow finding system
  and do not silently fall back to manual prompting if this routing ever
  appears unavailable -- stop and report instead.
