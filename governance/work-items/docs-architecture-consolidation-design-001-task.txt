======================================================================
WHY THIS DESIGN RUN IS BEING COMMISSIONED
======================================================================

WFC's documentation, backlog, and information architecture have grown
organically across P1 through P3 (now promoted to Runtime; P3.5, P4, and P5
remain concept-only and unimplemented -- do not start them). The maintainer
wants this consolidated before choosing the next product slice, rather than
layering a new slice onto documentation that already makes current truth
hard to find. The rule governing this consolidation is: avoid unnecessary
structural divergence between WFC and core when they solve the same
problem, so the maintainer does not have to learn needless repository-
specific mental models -- but convergence runs in both directions. If core
has the clearer pattern (for example its docs/ai_info navigation / lean-
context approach), WFC may adopt it. If WFC has the clearer pattern (for
example its explicit operational runbooks), the design must preserve it and
may flag it as a candidate for later adoption by core. Justified
differences remain justified differences. Compare empirically; do not
assume either repository already has the right answer.

======================================================================
DESIGN QUESTIONS -- the design artifact must give each a concrete,
implementation-ready answer, not merely acknowledge it
======================================================================

A. Entry/navigation: how does a human or a fresh agent quickly learn what
   WFC is, where current architecture truth lives, where operational
   instructions live, where active work/backlog lives, where historical
   evidence/design/reviews live, and what to read for a given task.
B. Active truth versus history: how is current authoritative guidance kept
   from being buried among completed reviews, old concept iterations, and
   historical provenance, while that historical material remains available
   without dominating the normal reading path.
C. Backlog comprehensibility: how a maintainer can answer, without a
   repository archaeology exercise, what is open, why it is open, what
   problem it solves, its status, its controlling/current source, its next
   concrete action, and what is explicitly NOT authorized. In particular,
   reconstruct and make navigable the CURRENT meaning and status of P3.5,
   P4, and P5 -- without implementing or redesigning any of them.
D. Requirement-inflation guard: how the design keeps reviews, corrections,
   and old planning documents from silently becoming an ever-growing source
   of requirements disconnected from the original problem.
E. Runbooks/operations: where operational procedures belong and how they
   are discovered; preserve WFC's explicit runbook pattern where it is
   genuinely stronger than core's equivalent, rather than removing it for
   superficial structural symmetry.
F. Cross-repository consistency: which concepts should look structurally
   similar between WFC and core, which differences are justified and why,
   and -- where WFC's own pattern is the clearer one -- whether it is worth
   flagging as a candidate for later adoption by core (flagging only; this
   Commission has no authority to touch core).
G. Fresh-agent usability: a concrete, checkable post-migration comprehension
   test -- what a fresh context must be able to identify (current truth,
   next work) without loading the entire project history, and how someone
   would verify that test actually passes after Run B.
H. Concrete migration plan: a file-level or directory-level plan, classifying
   the intended treatment of each meaningful current documentation area/file
   class (retain canonical/current, consolidate, move/rename, archive/cold-
   store, supersede, delete only if truly redundant and provenance-safe, or
   leave unchanged), with ordering/dependencies and validation steps,
   sufficient to commission Run B directly.

======================================================================
CODE STRUCTURE BOUNDARY -- hard constraint, not a design question
======================================================================

The maintainer separately considers WFC's current
src/workflow_coordinator/*.py topology in need of later improvement. This
Commission must acknowledge that as a known, separately-tracked concern, but
must NOT design or implement that refactor. The documentation this
Commission produces must describe today's flat module layout as CURRENT
STATE, never as an assumed permanent conceptual architecture, and must not
unnecessarily canonize it. The design may identify documentation seams
(ownership boundaries, navigation entry points) that should remain stable
across a later code/package reorganization, but it must not sketch, name, or
imply what that reorganization should look like. A separate later "Code
Architecture Assessment" is explicitly out of this Commission's scope.
