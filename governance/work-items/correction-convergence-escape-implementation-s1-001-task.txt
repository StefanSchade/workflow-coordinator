WHAT SLICE 1 ACTUALLY IS -- from the accepted FTR's "Exact later implementation
scope and slicing" section: "Add v3 Finding/Hop records, result v2, exact
v1/v2 compatibility, gate-owned obligation introduction, coverage and total
assessment cross-validation, role-closed blocker creation, and atomic
local-to-concrete successor references, with no routing change." Concretely,
drawing on the accepted FTR's "One blocker ledger, with structured correction
facts" section (as corrected by the accepted D001/D002 review):

1. Extend `Finding` with nullable `correction_obligation` metadata:
   `CorrectionObligation { owner: gate | human, introduced_by_hop: Hop ID }`.
   An ordinary Finding, and every Finding in a legacy Run, has `null`
   metadata and is never silently treated as tracked.

2. Add a result-v2 envelope (schema_version 2, alongside the unchanged
   result-v1 envelope and `RoutingResult` shape) that adds five fields to
   every v2 result, using empty arrays/`null` when inapplicable:
   `coverage_claims`, `convergence_assessments`, `diagnosis`,
   `strategy_revision`, `strategy_assessment`. Implement the first two fully,
   per item 3 below. Because `DiagnosisReport`/`StrategyRevision`/
   `StrategyAssessment` are Slice-4 typed semantics, represent the latter
   three fields in the v2 wire shape as strictly null-only placeholders for
   this slice: the schema must accept `null` and must reject any non-null
   value, with a type you can refine into a real typed union without a wire
   version bump when Slice 4 lands. Do not design their eventual non-null
   shape; that is Slice 4's job.

3. Implement, in the reducer, exactly these rules from the accepted FTR
   (ownership/validation subsections of "One blocker ledger..."):
   * every new open blocking Finding delta in a result-v2 reduction is
     rejected unless the source role is `evaluator`-equivalent (see role
     signal below); an admitted evaluator-created open blocker is always
     atomically tagged `owner: gate`; corrector/other roles cannot create an
     untracked open blocker;
   * ordinary result-v1/profile-v2 Finding creation is completely unchanged;
   * a `corrector`-equivalent phase must submit exactly one coverage claim
     (`finding_id`, `disposition: addressed | blocked | escalation`,
     `evidence_refs`) for every open tracked obligation projected into that
     Hop; unknown, closed, or superseded IDs are rejected; `addressed` never
     mutates Finding state and never takes a complete route;
   * `convergence_assessments` (`finding_id`, `correction_hop_id`,
     `result: closed | carried_new_counterexample | carried_unmet |
     residualized | superseded`, `evidence_refs`) must be total and
     cross-checked against a matching Finding delta in the same result:
     `closed` only with an authorized `resolved` delta, `residualized` only
     with an authorized `residual` delta leaving the Finding non-blocking,
     `superseded` only with an authorized superseding delta and valid
     successor, and both carried values require the Finding to remain open
     and blocking after reduction; `carried_new_counterexample` additionally
     requires a new, previously absent evidence reference;
   * the initial protocol rejects `reopen` authority on these evaluator-role
     phases; existing simple (non-convergence) profiles retain current
     `reopen` behavior unchanged;
   * `NewFindingDelta` gains a nullable `local_ref` field (`N[1-9][0-9]*`,
     unique within the result); an `ExistingFindingDelta` superseding a
     tracked obligation may set `successor_ref` to either a concrete `Fxxx`
     ID or `local:Nxxx`; reduction is atomic and ordered exactly as the
     accepted FTR specifies: validate all deltas/local-reference syntax/
     uniqueness/authority/role rules first (no state change); allocate
     concrete IDs to new deltas in result order and build the local-to-
     concrete map; resolve every local successor reference, rejecting a
     missing reference or a target that is not a same-result open blocking
     tracked obligation; validate the complete prospective Finding graph for
     self-reference and direct/transitive cycles; then apply everything as
     one transaction. Duplicate/unknown local references, references to a
     non-blocking/untracked new Finding, concrete unknown IDs, ID prediction
     inside `local_ref`, and every self/cycle case reject the whole result
     without consuming IDs or changing state. Persisted Findings and Hop
     summaries contain only resolved concrete IDs; `local_ref` is never
     durable identity, and replay never reallocates or reinterprets it.

4. Extend Run/Hop wire to schema version 3: add `Finding.correction_obligation`
   and Hop-summary `coverage_claims`/`convergence_assessments` (only these two
   new Hop-summary fields belong to this slice; `phase`/`requested_route`/
   `route_reason`/diagnosis/strategy/`ConvergenceEscape` belong to later
   slices and must not be added as live fields yet -- see the next paragraph
   for how to keep the wire shape forward-compatible without implementing
   them). Profile schema version 2 and result schema version 1 keep their
   exact current closed shape and behavior, byte-for-byte. The Run parser
   accepts v1, v2 (existing `semantic_stop`/`successor_provenance` shape),
   and the new v3 shape; v1/v2 read-only load/status/replay stays byte-
   preserving and synthesizes no obligation/claim/assessment data. There is
   no in-place v1/v2-to-v3 migration; existing v1-to-v2 persistence transitions
   are unaffected. Only a Run actually carrying v3-shaped state (constructed
   as described below) persists as v3; this slice does not add a real
   mechanism that causes production Runs to become v3, because that
   mechanism is profile-v3 selection (Slice 3). The serializer must omit the
   new nested fields when writing v1 or v2, exactly as it already omits
   v2-only fields when round-tripping v1.
