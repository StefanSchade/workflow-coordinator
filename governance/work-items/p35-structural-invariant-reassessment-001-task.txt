THIS IS A FRESH COMMISSION -- READ BEFORE WRITING ANYTHING
======================================================================

Unlike the predecessor P3.5 design-review lineage
(WI-WFC-P35-FINDING-REACHABILITY-DESIGN-REVIEW, -002, -003), this WorkItem
does not correct or extend the accepted design document itself. It
produces an entirely separate, independent reassessment of whether that
accepted design is the right architecture for Level 0 at all, given the
consequence its own acceptance review recorded: under the accepted rule,
*all 43* currently inventoried schema-v2 self-development profiles are
rejected (43 rejections / 0 acceptances). This is a maintainer-flagged
pending architecture decision
(docs/warm_storage/concepts/workflow_coordinator_level0_mvp_planning_decisions_2026-10-21.adoc
§2), not a request to implement, migrate, or further correct the design.

No outcome is predetermined. The design may be judged exactly right, judged
too strict and narrowable, judged correct but reducible for Level-0, or
judged overbuilt relative to what the runtime completion guard already
provides. Preserving the 43 existing profiles as they stand is not, by
itself, a goal of this Commission; nor is preserving the accepted design as
it stands. Ground every judgment in evidence -- source citations, concrete
counterexamples, actual reducer behavior -- not in preference for either
outcome.

ASSESSMENT (phase `assessment`, first phase of this Run)
======================================================================

Author
docs/warm_storage/concepts/workflow_coordinator_p35_structural_invariant_reassessment_2026-10-25.adoc
as a durable, evidence-based architecture reassessment. At minimum, address
each of the following eight determinations explicitly, each grounded in
cited source and/or a concrete, minimal, worked example -- not merely a
restatement of the design document's or Concept doc's own prose:

 1. The actual failure class P3.5 is intended to prevent. State it
    precisely, distinguishing it from the runtime completion guard's own
    failure class (determination 2) and from general workflow liveness
    (the design's own named non-goal, §4.7/§7 example 8).
 2. What the existing runtime completion guard
    (`_has_open_blocker`/`_apply_route`, reducer.py) already prevents at
    Run time, and precisely what risk, if any, remains uncovered by it once
    a Run is already admitted. Ground this in the guard's actual code path,
    not merely the design document's characterization of it.
 3. Whether P3.5 is a safety invariant (preventing a Run from reaching an
    unsafe/incorrect state), an admission-time liveness/usability check
    (preventing a Run from wasting Hops and provider cost on a structurally
    doomed topology, given §3.4's deliberate exclusion of any `COMPLETE`-
    equivalent state that the *runtime* guard would not itself also already
    stop), or a combination of both -- and what follows for Level-0 MVP
    priority from whichever answer the evidence supports.
 4. Whether the current strict-after disposition rule (a disposer must be
    reachable strictly *after* the opening invocation; an opener's own
    concurrent closing authority never satisfies it, per design §4.5's
    origin-check arm and the H005/H002 counterexamples) is necessary in
    every case the rule currently rejects, or only in some -- distinguish
    these with concrete cases rather than asserting one answer for the rule
    as a whole.
 5. Why all 43 inventoried schema-v2 profiles fail, using at least two
    concrete representative profiles (drawn from actual governance/
    self-development/*.yaml files, named precisely) and the minimal
    counterexample shape each instantiates. Do not rely solely on the
    design document's own §6.1 characterization; verify at least one
    profile's rejection directly against its actual YAML and the §4.3/§4.5
    predicates.
 6. Whether a narrower sound invariant is possible -- one that would admit
    at least some of the 43 currently-rejected profiles without
    reintroducing the exact falsified shape H005/H002 closed (an opener's
    own concurrent authority satisfying the rule, or an undisposed Finding
    silently carried to completion). If no narrower sound invariant is
    possible, say so explicitly and show why, rather than leaving the
    question open by omission.
 7. Whether retaining the current design exactly as accepted, and
    separately commissioning profile migration for some or all of the 43,
    is justified -- weighed explicitly against the cost (43 profiles
    potentially needing migration or schema-v4 adoption) and the benefit
    (what determination 1-4 established is actually at stake).
 8. Whether P3.5 can be reduced for the Level-0 MVP specifically -- e.g.
    narrowed scope, deferred to post-MVP, replaced by a documented operating
    convention, or some other reduction -- without leaving an unacceptable
    defect, where "unacceptable" is judged against determinations 1-4, not
    against convenience alone.

Additionally, and explicitly:

 A. Test the distinction between a reviewer being *authorized* to open a
    blocking Finding (a declared capability: `review.authority: gate` with
    `blocking_policy: blocking_only`, or, in the design's own schema-v4
    proposal, `may_open_findings: true`) and that reviewer *actually opening*
    one in a specific Run's history. State explicitly what each of P3.5 (a
    static, pre-Run, capability-only check) and the runtime completion guard
    (a dynamic, per-Run, actual-history check) can and cannot see about this
    distinction, and what follows for whether a static check can ever fully
    substitute for -- or must instead complement -- the dynamic guard.
 B. For every claim about engine behavior, cite the exact current source
    (file and function/line) rather than the design document's or BUG's own
    citation of it; where you cannot independently verify a cited behavior,
    say so explicitly rather than treating the citation as established by
    its mere presence in an accepted document.
 C. State explicitly whether your reassessment's conclusion is: (i) retain
    the accepted design and commission profile migration separately; (ii)
    narrow the invariant and re-specify it precisely; (iii) reduce or defer
    P3.5 for Level-0 under a stated, bounded operating convention; or (iv)
    some combination, naming exactly which parts of the design each
    component of your conclusion affects. A reassessment that reaches no
    stated conclusion does not satisfy this WorkItem's purpose.
 D. Do not implement anything, migrate any profile, or edit the governing
    concept, the BUG, the backlog, or either existing P3.5 design/review
    document. This phase has no durable-artifact authority and does not
    touch the review artifact.

Before requesting `review`, provide an explicit summary in your assessment
document's own text (not merely in the commit message) stating which of the
four conclusion shapes in item C you reached, and a one-line pointer to the
document section supporting each of the eight determinations above.
