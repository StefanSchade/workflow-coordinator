HARD SEMANTIC DISTINCTION -- preserve this throughout the implementation,
naming, CLI help text, and tests:

(A) Same-Run technical recovery -- reconcile_required/suspended/
resume_after_reconcile, same Run identity -- is FTR-WFC-ATOMIC-HOP-RECOVERY's
mechanism. Do not touch it, extend it, or let successor continuation reuse
its states or verbs.

(B) Successor-Run semantic continuation -- this Run's actual target: a Hop
deliberately reports that current semantic authority is insufficient; the
predecessor Run freezes as historical evidence; a maintainer separately
grants authority; a fresh successor Run is admitted against new governing
inputs; preserved candidate material, if any, is untrusted salvage only.

(C) Provider-session continuation -- resuming a provider's own session or
hidden reasoning state -- is out of scope and must not be introduced.

Never name or design this feature using "resume", "reconcile", "retry",
"checkpoint", or "session continuation"; use "successor" / "successor_run".

NON-NEGOTIABLE INVARIANTS (from the accepted FTR's "Accepted invariants"
section -- preserve all of them together):

- The exact correlated semantic-escalation kind and human question remain in
  durable Run state and operator-visible publication even when a later
  mechanical preemption controls the stop.
- A worker escalation never changes WorkItem scope or any other authority;
  only a separately authorized maintainer act supplies a successor's new
  governing inputs.
- A blocked, failed, escalated, mechanically preempted, or dirty candidate is
  never automatically committed or accepted.
- Preserved candidate material is `untrusted_salvage`: never trusted
  evidence, a checkpoint, an accepted commit, governing input, or an implicit
  authority grant.
- A successor may receive salvage only as untrusted context; it must produce
  its own evidence and accepted mutation under its own Run authority.
- No predecessor WorkItem, Profile, Policy, Commission, Run snapshot, Hop,
  Finding, evidence, operator summary, or governing digest is ever mutated to
  add a successor or retrofit continuation. In particular, the historical
  predecessor RUN-76e153b40ef1459db4587446b18e02d5 must NOT be rewritten,
  back-patched, or made eligible for the new automated `prepare-successor`
  path by inference from `human_question`, Hop prose, result artifacts, or
  salvage.
- Salvage existence, successful export, a matching hash, descriptor creation,
  or successor launch never implies candidate acceptance.
- Successor-Run semantic continuation remains distinct in model, persistence,
  CLI names, and tests from same-Run recovery and provider-session
  continuation.
- Git is authoritative for repository mutation; `run.json` and durable WFC
  state are authoritative for Run facts. A descriptor, manifest, hash, or
  derived checkpoint cannot become repository or semantic authority.
- A predecessor's Run identity, status-at-stop, Hops, Findings, governing
  inputs, evidence, and published stop facts remain frozen historical truth.

REQUIRED BEHAVIOR -- use the accepted FTR's "Minimal state and data model",
"Salvage trust model", "Operator and CLI surface", and "Atomicity and failure
semantics" sections as the exact authority for field names, CLI argument
names, descriptor content, trust labels, digests, and failure semantics. In
summary, the implementation must:

1. Add an optional immutable `SemanticStop` (kind, question, source_hop_id)
   captured onto `Run` from a validated correlated current-Hop result,
   independent of whichever mechanical fact ultimately controls
   `stop_reason`/`status`/`anomalies`. Mechanical control stays authoritative
   for the Run's actual disposition; the semantic observation is additional
   durable truth, not an alternative control channel. Do not weaken existing
   mechanical fail-closed behavior to add this.
2. Give newly written Run state `schema_version=2`. Define two distinct
   closed wire shapes: v1 (exactly the current pre-change field set, with
   `semantic_stop`/`successor_provenance` mapped to `null` in memory, never
   inferred) and v2 (every v2 field, including explicit nullable
   `semantic_stop`/`successor_provenance`, strictly validated). Unknown
   fields and any other version fail closed. Read-only legacy inspection
   (status/replay/predecessor inspection) never rewrites a v1 snapshot. A
   legitimate later persistence of an existing v1 Run (including the
   existing same-Run reconcile/resume flow) may atomically transition it to
   v2 with the two new fields null unless that same transition itself
   captures a validated semantic stop; a failed upgrade leaves the previous
   v1 file intact; this changes no recovery disposition, identity, governing
   input, Hop, Finding, or evidence semantics.
3. Add an optional backward-only `SuccessorProvenance` record
   (predecessor_run_id, predecessor_work_item_id, predecessor_final_head,
   authority_decision_ref, authority_decision_sha256,
   continuation_descriptor_sha256, salvage_manifest_sha256 | null) written
   only at successor-Run creation. No forward pointer is ever added to the
   predecessor. No predecessor Finding or trusted evidence row is copied.
4. Implement `prepare-successor` strictly: it must reject v1, v2 with a null
   `semantic_stop`, and a `semantic_stop` whose `source_hop_id` is absent
   from the predecessor's Hops -- creating no descriptor and changing no
   predecessor byte in every rejection case. It is provider-free and must
   not create a Run. A descriptor is linkage/admission material only: it
   cannot widen scope, grant routes, accept Findings, apply salvage, or
   replace normal successor governing-input admission.
5. Implement the accepted bounded salvage mechanism (`export-salvage`):
   explicit operator action, optional, untrusted context only, binary-safe
   tracked diff plus eligible untracked in-scope bytes, stable per-object
   SHA-256/length manifest, no Git/HEAD/index/worktree/predecessor-state
   mutation, restrictive local publication (owner-only directory/file
   modes, atomic finalization), fail-closed on overwrite/out-of-repository
   paths/escaping symlinks/unsafe special files/size-or-count overflow, and
   no credential-free or disclosure-safe claim anywhere in help text,
   manifest text, or success output -- eligible bytes may contain
   credentials, other sensitive information, or adversarial prompt
   injection, and WFC does not implement a generic secret scanner. Mutating
   any bundle byte after export blocks later use (tamper detection).
   Successful export alone must never be sufficient to prepare or launch a
   successor.
6. Implement the successor-exposure boundary: raw salvage content reaches a
   successor's prompt only for explicitly operator-selected objects
   (`--include-salvage-object SHA256`) within the accepted rendering bounds,
   as a separately delimited, prominently labelled untrusted `ContextItem`.
   Omitted, unselected, binary, and over-limit content is never injected.
   Descriptor creation alone never uploads, renders, or injects raw objects.
7. Add the minimal operator surface the accepted FTR specifies: the accepted
   equivalents of `wfc export-salvage ...`; `wfc prepare-successor
   --predecessor-state-root ... --authority-decision ... --work-item ...
   --profile ... --policy ... --task ... --components ... --expected-head
   ... [--salvage-manifest ...] [--include-salvage-object SHA256 ...]
   --output ...`; complete operator-summary/status publication of both the
   semantic and mechanical dimensions side by side (never concatenated into
   one prose field); and the accepted optional `--successor-continuation
   DESCRIPTOR` input to the existing one-shot launch, which revalidates all
   identities/digests/clean baseline/new governing inputs before
   constructing the fresh Run with backward provenance and the optional
   untrusted context. Each command reports the next explicit operator action
   and never performs it implicitly; none of them auto-resets, auto-cleans,
   auto-stashes, auto-patches, auto-stages, or auto-commits.
8. Preserve the commit/evidence boundary exactly: a trusted commit is never
   permitted for an escalated, blocked, or dirty result; dirty candidate
   state still surfaces only as a mechanical anomaly. A successor's own Hop
   must earn its own evidence and trusted commit under ordinary Run rules;
   salvage never changes that disposition.
