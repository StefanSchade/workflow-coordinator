======================================================================
WHAT P2 MEANS
======================================================================

P2 makes worker-vs-review category mistakes structurally unrepresentable,
not merely rejected after the fact by the reducer. A worker/corrector
invocation selects `WorkResult` (`status: completed | blocked`, plus the
genuinely applicable existing semantic/evidence/effect fields); it MUST NOT
be able to express `changes_required` or any other review-only verdict --
absent from the type and the provider schema. A review/rereview invocation
selects `ReviewVerdict` (`verdict: accept | changes_required`, plus Finding
proposals/updates, evidence, summary); it MUST NOT expose worker-only status
vocabulary. Every phase with `phase.convergence_role is not
ConvergenceRole.NONE` remains on the existing generic `RoutingResult`
contract, untouched by P2. Selection extends the one existing P1 selector,
`select_result_contract(profile, phase, run) -> ResultContractKind`, never a
second mechanism, never a phase-key string branch. The full semantic detail
is already fully specified in
governance/work-items/projected-result-contracts-p2-task.txt and the
original WorkItem's `authority_source`
(governance/work-items/projected-result-contracts-p2.yaml). Read both
completely; their exact wording controls P2's semantic boundary. This task
text does not repeat that specification; it governs what THIS successor Run
must additionally do.

======================================================================
CORRECTED WORKFLOW TOPOLOGY
======================================================================

This Commission uses the existing canonical converging-review shape of
docs/wfc_operator_manual.adoc section 22.4, which the stagnation audit
loaded and simulated successfully against current production mechanics.
The profile for this Commission implements exactly:

  integration [worker]
      role: worker
      review: null
      evidence: []
      routes:
        completed -> independent_review

  independent_review [gate]
      role: independent_reviewer
      review.authority: gate
      review.finding_authority: [resolve]
      evidence: [pytest]
      review.failed_evidence_route: correction
      routes:
        accept             -> complete
        correction/changes_required -> correction

  correction [worker]
      role: worker
      review: null
      evidence: []
      routes:
        completed -> rereview

  rereview [gate]
      role: independent_reviewer
      review.authority: gate
      review.finding_authority: [resolve]
      evidence: [pytest]
      review.failed_evidence_route: correction
      routes:
        accept             -> complete
        correction/changes_required -> correction

Initial phase: integration.

DO NOT put full-suite `pytest` in `integration.evidence` or
`correction.evidence` -- those phases carry `evidence: []`, unless direct
repository inspection shows a genuinely phase-local deterministic check
clearly distinct from global acceptance is warranted; do not invent such a
check merely to populate the field. The complete repository command remains
`python -m pytest -q` with the existing 900-second timeout, and it belongs
as Coordinator-required evidence ONLY on `independent_review` and
`rereview`, because those gates own acceptance/completion.

Both review gates explicitly declare `review.failed_evidence_route:
correction`, naming the existing `correction` goto route, using the exact
schema and nesting the current production loader and reducer accept. This
is load-bearing: a reviewer may semantically return `accept` while trusted
`pytest` later fails, and in that case the reducer must route to
`correction` rather than `complete` or stopping `awaiting_human`.
