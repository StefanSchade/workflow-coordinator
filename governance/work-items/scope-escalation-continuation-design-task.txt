HARD SEMANTIC DISTINCTION -- preserve this throughout:

(A) Same-Run technical recovery -- charged-Hop interruption, suspend/
reconcile/resume, same Run identity -- is tracked separately by
FTR-WFC-ATOMIC-HOP-RECOVERY.adoc. Do not solve (A) merely because it is
adjacent, and do not weaken or redesign it.

(B) Successor-Run semantic continuation -- a Hop deliberately stops because
additional semantic authority is required; the predecessor Run remains
historical evidence; a maintainer may grant new authority; a fresh successor
Run may continue the work; preserved candidate material, if any, remains
untrusted salvage -- is the actual target of this design. Do not introduce
provider-session continuation, and do not invent a generic outer
orchestration layer or Level-1 planner as the solution to this Level-0
operator problem.

NON-NEGOTIABLE INVARIANTS the design must preserve (already recorded by the
BUG; if repository truth shows one needs clarification, clarify it, but do
not silently weaken it):

- Preserve the original semantic escalation / human question in
  operator-visible published state even when a later mechanical preemption
  also applies to the same stop.
- Never auto-widen a WorkItem's authorized scope in response to a worker's
  escalation; a scope grant remains an explicit, separately authorized
  maintainer act.
- Never auto-commit or auto-accept a blocked or dirty candidate.
- Preserve candidate material, when preserved at all, only as explicitly
  non-authoritative salvage -- never as trusted WFC evidence, a checkpoint,
  an accepted commit, or an implicit grant of authority.
- A successor Run may consume salvage only as untrusted context, never as a
  substitute for that Run's own evidence or trusted commit.
- Never mutate a predecessor Run's governing inputs (WorkItem, Profile,
  Policy, Commission) to retrofit continuation.
- Never infer acceptance of a candidate from the mere existence of preserved
  salvage material.
- Predecessor Run identity, state, and evidence remain frozen historical
  truth.
- Keep successor-Run continuation distinct from same-Run technical
  crash/reconcile recovery and from provider-session continuation, in any
  naming or mechanism.
- Git remains authoritative for repository mutation; run.json / durable WFC
  state remain authoritative for Run facts; derived checkpoints must not
  become repository or semantic authority.

REQUIRED DESIGN QUESTIONS -- the design artifact must answer all of these
concretely, not merely acknowledge them:

A. Semantic escalation visibility: how should WFC represent both the
   semantic stop reason/human question and a later mechanical
   preemption/anomaly without one destroying or hiding the other? Determine
   whether current Run/operator-summary fields are sufficient with different
   reduction/publication semantics, or whether an explicit additional
   field/state representation is required.
B. Predecessor disposition: what exact terminal/suspended status should the
   predecessor Run have after a legitimate semantic scope escalation? Do not
   casually reuse technical-recovery semantics if they mean something
   different.
C. Salvage ownership: should WFC itself create/preserve a salvage artifact,
   or should it merely publish enough information for an operator-side
   mechanism to preserve it? Define provenance, trust classification,
   location/ownership, mutation rules, lifecycle, whether hashes are useful,
   and state explicitly that salvage is non-authoritative. Avoid turning
   salvage into a hidden checkpoint or shadow commit.
D. Successor relation: what minimal first-class representation is needed to
   relate predecessor Run -> maintainer authority decision -> successor
   WorkItem/Run without mutating predecessor state? Determine whether WFC
   needs an explicit successor/predecessor reference, continuation
   descriptor, operator command/input, or some smaller mechanism.
E. Successor input: if salvage is supplied to a successor Run, define how it
   is exposed to the worker as untrusted context rather than applied
   repository state or trusted evidence. The successor must still begin from
   a clean, known Git baseline and produce its own accepted mutations.
F. Operator surface: determine the smallest useful operator/CLI workflow.
   Assess, without adopting them merely because they are convenient names,
   whether a future shape resembling `wfc status` / `wfc prepare-successor`
   or `wfc continue-as-successor` is justified, or whether a smaller
   primitive is sufficient.
G. Atomicity/failure behavior: specify what happens if salvage preservation
   itself fails, if the repository cannot be restored cleanly, if successor
   preparation fails, or if governing authority is not granted. Fail closed
   in every case.
H. Exact implementation scope: finish with an exact proposed set of
   production/test/docs paths for the later implementation WorkItem. Do not
   leave the later implementation agent to rediscover its scope.
