# Qualify whether a nested Claude Code CLI invocation runs reliably inside WFC's own outer bwrap namespace

Investigate, by small reproducible local experiments against the
already-implemented, accepted `src/workflow_coordinator/execution_boundary.py`
primitive (including its `/tmp/s` external scratch bind-mount), whether
and under which conditions a Claude Code CLI invocation -- itself
activating its own nested sandbox -- runs reliably inside a WFC-owned
outer bubblewrap namespace, with agent-launched Bash commands able to
use the external scratch while the rest of WFC's filesystem boundaries
remain intact.

This is an explicitly bounded technical investigation, not a general
provider integration. Do not wire this module, the external scratch
bind, or any nested-sandbox accommodation into `claude_adapter.py`,
`codex_adapter.py`, `operator.py`, or `scripts/wfc_op.py`. Do not design
or implement the eventual Claude-adapter / WFC scratch-allocator
integration; identify its requirements only, as output of this
investigation, for a later, separately authorized Commission.

### Required semantics and bounds (fail closed on every one)

- No credential, token, private key, or authentication file may be
  copied into any untrusted scratch location used by an experiment.
- No experiment may grant blanket access to `$HOME`, provider
  configuration, or network access merely to make a test pass; any
  visibility an experiment genuinely needs must be the narrowest
  concrete grant that experiment requires, explicitly justified in the
  report.
- No experiment may disable, bypass, or weaken any sandbox or
  permission mechanism (WFC's own `execution_boundary.py`, the Claude
  CLI's own sandbox/permission layer, or the host's).
- `enableWeakerNestedSandbox` (or an equivalent weaker-nested-sandbox
  setting) must never be enabled automatically, by default, or as an
  unreviewed workaround; if a real nested invocation's own sandbox
  initialization appears to require it, that requirement -- and what
  security guarantee it would actually change -- must be reported as a
  finding, not silently applied.
- No host security policy change, no administrator/root action, and no
  additional system package installation.
- No change to the regular provider dispatch path (`operator.py`,
  either adapter, `scripts/wfc_op.py`).
- A real, authenticated nested `claude` CLI invocation is in scope only
  to the extent it can be performed safely using already-available,
  lawfully-held authentication under the bounds above. If it cannot be
  performed within these bounds, record that as a valid, explicit
  negative finding -- do not route around the constraint, and do not
  substitute a fake-provider run and present it as a live qualification.

### Required investigation

Using real `bwrap` processes and synthetic repositories/fixtures (a
fake/stub provider only where it isolates a specific mechanism cheaply,
never as a substitute for a real nested Claude invocation's own
reporting), investigate and report, for each: a mechanically verified
finding (with the exact command/test that demonstrated it), a
retraction of any earlier-session hypothesis this investigation
disproves, or an explicitly unresolved open question -- never blurring
the three:

1. Whether nested user/mount namespaces (a `bwrap` invocation running
   inside a process that is itself already confined by an outer
   `bwrap` namespace) function on this host at all, and under which
   preconditions.
2. The minimal mounts and process preconditions the Claude CLI needs to
   start and operate at all inside such a nested namespace.
3. Whether `AF_UNIX` socket paths the Claude CLI constructs remain
   within the kernel's `sun_path` length limit when nested one level
   deeper than the existing non-nested short-`TMPDIR` mechanism assumes.
4. Whether `/tmp/s` (the external scratch bind-mount) is actually
   reachable, writable, and correctly scoped for the relevant child
   processes (the outer boundary's own process, and any process Claude
   itself launches inside its own nested sandbox).
5. What effect the outer WFC boundary has on Claude's own sandbox
   initialization -- does it initialize normally, degrade gracefully, or
   fail outright, and with what observable symptom in each case.
6. Whether `enableWeakerNestedSandbox` or an equivalent accommodation is
   actually required for Claude's nested sandbox to initialize under
   the outer boundary, and if so, precisely which security guarantee
   that setting changes (state this as a finding to evaluate, not an
   action to take).
7. What this investigation's findings imply as concrete requirements
   for a later, separately authorized Commission that would wire the
   WFC scratch allocator and the Claude adapter together.

A test or probe that only inspects a generated command line or argv
without actually running a real sandboxed subprocess and observing real
behavior does not satisfy any claim above; host-filesystem or
process-observable verification is required wherever a claim depends on
it, exactly as the prior external-scratch Commission required for its
own isolation claims.
