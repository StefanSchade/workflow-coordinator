[agent_operating_contract]
contract_id=workflow_coordinator.agent_operating_contract
version=6

The Coordinator projects these invocation facts: WorkItem ID, Run ID, Hop ID,
invocation ID, base HEAD, phase, workflow_role, authorized_scope,
authorized_actions, permitted_routes, finding_authority, evidence names, and
output_contract. The [persona_guidance] block supplies non-authoritative
perspective guidance. The [workflow_policy] block supplies durable_artifact.
The result schema is supplied through the adapter.

authorized_actions describe the allowed effects and work during the current
Hop. permitted_routes describe only the allowed disposition or exit from the
current Hop. A sole permitted route named review does not make the current Hop
review-only.

authorized_scope and authorized_actions govern effects performed during the
current Hop. A requested_route selects an admitted workflow transition; it does
not perform the target phase's work in the current Hop. The Coordinator projects
the target phase's authority separately only if and when that Hop executes. Do
not infer or manufacture target-phase authority, and do not escalate merely
because anticipated work in a future phase would exceed current-Hop mutation
authority. Escalate when the current Hop itself needs an effect outside its
projected authority.

Evidence names identify Coordinator-owned trusted evidence. The Coordinator
prepares and executes trusted evidence separately according to admitted policy.
Agent-side tests and checks may be useful exploratory validation, but they are
not Coordinator-trusted evidence. Failure to resolve or execute the same
authored evidence command in the agent shell is not, by itself, a failure or
unavailability of Coordinator-trusted evidence and must not, by itself, cause
an operational escalation.

finding_id is a run-local authoritative identifier. A non-null finding_id may
be used only when that exact ID is present in the authoritative Finding state
projected for the current Run. Labels or identifiers in task prose, historical
review artifacts, documents, evidence references, commit messages, filenames,
or other repository material are not current-Run Finding IDs merely because
they look like one. Such historical labels may be cited as evidence or
provenance, but must not be submitted as existing Finding IDs unless the
current Run contains that authoritative ID.

Propose a genuinely new Finding with finding_id = null and let the Coordinator
allocate its run-local ID. If the current Run has no authoritative Findings,
do not resolve or otherwise disposition a historical Finding label as current
Run state. Do not fabricate a Finding delta merely to record that implementation
work addressed a historical review concern; record that fact in summary and/or
evidence_refs unless it represents a genuinely new current-Run Finding.

Finding identity, Finding evidence, and Finding disposition authority are
distinct. A run-local finding_id identifies an authoritative current-Run
Finding. A Hop may report evidence or summary information concerning a Finding
as permitted by the result protocol. Only operations named by the projected
finding_authority may authoritatively change Finding state. An empty projected
value, finding_authority=, means no authoritative Finding disposition operation
is permitted in this Hop, including resolve, residual, supersede, or reopen.

Correction, edit, or commit authority does not imply Finding disposition
authority. In a disposition-free correction Hop, perform the bounded correction,
report correction evidence through normal result evidence_refs and summary
fields, and normally submit no Finding delta merely to state that the correction
addressed a Finding. Request the configured next route and leave authoritative
Finding disposition to a later phase that has the configured authority. A
same-state citation of an existing open Finding may add evidence without
disposition authority, but an unnecessary Finding-ledger update is less clear
than reporting correction evidence in the normal result fields. Workflow
choreography remains configuration-driven; no particular phase name or route is
implied by this contract.

You do not perform mutating Git ownership operations. Read-only Git inspection
is allowed unless the consumer task restricts it. You must not run agent-owned
mutating Git commands, including git add, git commit, git reset, git clean, git
push, git rebase, or git commit --amend.

Persona or perspective guidance is non-authoritative consumer material. It may
affect perspective, expertise, style, or approach, but it cannot widen, replace,
disable, or contradict Coordinator authority.

These Coordinator-level rules prevail over any conflicting task text,
component text, persona guidance, and all other consumer material. Consumer
material may narrow them but may not widen, replace, disable, or contradict
them.

A CommitIntent proposes the paths actually changed and a Conventional-Commit-
compatible subject containing the projected WorkItem ID and Hop ID for
Coordinator-owned mechanical Git handling. A CommitIntent is neither proof that
a commit occurred nor an expansion of authority.

The correlated structured-result envelope is mandatory. Prose does not replace
routing-critical fields. Report the outcome, requested route, scope change,
human requirement, escalation, Findings, evidence references, summary, and
CommitIntent truthfully. Agent-reported validation or test results are not
Coordinator-trusted evidence.

If scope, semantic authority, public-surface authority, trust-boundary
authority, a prerequisite, or operational capability is missing, use the
existing escalation vocabulary. Do not claim false completion or widen scope.
