# P2 planning: compact plan for the documentation consolidation

PLANNING Commission P2: produce a COMPACT, executable plan for the documentation consolidation of this repository; it changes nothing but the plan document and its two review artifacts. Read first: docs/backlog/ROADMAP-POST-BETA-TO-RELEASE-BRIEF.adoc section 5, docs/backlog/FTR-WFC-DOCUMENTATION-CURATION.adoc (earlier curation results C1-C4 and the retained-shim handoff), docs/README.adoc, the Operator Manual and Developer Guide entry points, scripts/wfc_doc_catalog.py, and the docs tree itself; the P1 plan docs/backlog/postbeta_plan_p1_adr_and_hardening.adoc only for its dependency statements (it is planning input, not authority). Verify every count, path and consumer against the repository. MAINTAINER PRINCIPLES (binding, 2026-11-21): historical CONTENT is kept but historical documentation SURFACES are not conserved for their own sake. An old document path has no entitlement to exist merely because it was used before. Create NO redirect files, stub documents, compatibility shims or parallel documentation trees just to keep historical paths alive. The distinction: immutable Run evidence (the archived Runs in the sibling Evidence repository), archived artifacts and their provenance stay intact; ordinary development, concept and project documentation MAY be restructured, moved, consolidated and, where a canonical presentation exists, replaced. Relevant historical content must stay FINDABLE, not necessarily under its former path. Active internal references are updated when things move; historical evidence is not rewritten retroactively for that. Old paths are supported only where a concrete, still-valid compatibility requirement exists, never as a precaution. A SEPARATE FOCUS is navigability through the directory structure: docs/warm_storage holds about 151 largely flat concept documents (about 45 Beta review artifacts, 32 workflow documents and many more), and docs/ has loose root files, including the five small root shims named in the curation record. A large flat set is hard to open up even with search. Propose a comprehensible thematic structure with suitable subdirectories, meaningful names and a FEW useful entry points, so that a reader can place content from the directory tree alone. Prefer a simple, stable taxonomy over a new metadata, index or governance system; use the existing documentation tools and the existing catalog where sensible. SUCCESS CRITERION for the whole P2 is not maximal preservation of historical file structure but a clearly smaller, more consistent and more navigable CURRENT documentation surface with the relevant information and evidence preserved. DELIVER docs/backlog/postbeta_plan_p2_documentation_consolidation.adoc with: (1) a verified inventory (counts per area, the flat warm_storage set grouped by theme, the root files and shims, and the active consumers of each path that would move: documents, Asciidoctor includes, source and tests, the catalog, scripts and the sibling Evidence repository's ledger links, which you may only describe, not edit); (2) the rules separating immutable evidence from restructurable documentation, applied to the real artifact classes (review artifacts, concept documents, runbooks, backlog records, cold storage, the five root shims); (3) the target taxonomy for docs/warm_storage and for the loose root files, with a compact old-to-new mapping by group (a per-file table only where a group cannot be expressed by a rule); (4) the shim retirement list with each shim's real consumers and what updates them; (5) the link, include and catalog impact and the CHECKABLE verification for each package (Asciidoctor render of the entry points and assembled books, the catalog `generate` and `check`, a link check that names the command and expected result, a grep proving no live reference to a removed path remains outside immutable evidence); (6) the list of deliberately abandoned historical paths to report, instead of recreating them; (7) the execution packages as small Commissions, each with exact scope (directories where a restructure legitimately spans one), a Hop budget with reasoning, dependencies, checkable acceptance, and non-goals, in a sensible order (note that moves are renames; the trusted commit now accepts same-content renames after hardening H3, and an installed Runtime must contain it); (8) the few decisions only the maintainer can take, each with a recommendation. PROPORTION (maintainer principle): the plan must be compact (about 500 lines at most; it should read as an operating plan, not a report), must not restate the P1 plan or the brief, and must introduce no new metadata system, register or governance process; every proposed package and criterion earns its place by a concrete benefit, and a package whose cost exceeds its benefit is listed as rejected with the reason. Do not repeat the mistake of the P1 plan (over 2,300 lines and three correction cycles over citations): cite only what a decision rests on, and verify each citation. A Worker never reports any Finding operation (resolve, residual or any other delta); only the independent reviewer opens and resolves Findings. The CommitIntent names every changed leaf individually, never directories; no agent Git writes.

## Acceptance

The plan renders with Asciidoctor, stays within about 500 lines, and every count, path and consumer it cites was verified against the repository; it contains the inventory, the evidence versus restructurable rules, the taxonomy with the mapping, the shim retirement list, the checkable verification per package, the list of deliberately abandoned paths, the execution packages with exact scope, budgets, dependencies, acceptance and non-goals, rejected packages with reasons, and the maintainer decisions with recommendations; it proposes no redirect, stub, shim, parallel tree or new metadata system; no file other than the plan and its two review artifacts changed; independently accepted with no blocking Findings and Coordinator task-check passed.

## Withheld authority

No change to any document other than the plan and its review artifacts; no move, rename or deletion; no change under src/, tests/, governance/ or project_memory/, and none to the sibling Evidence repository; no tag, release, push, merge, rebase or Runtime promotion; no decision taken on the maintainer's behalf.

## Default escalation

Escalate a real scope or authority conflict, a decision only the maintainer can take, or a plan that cannot be kept compact without dropping a needed package; incomplete work alone is not blocked.
