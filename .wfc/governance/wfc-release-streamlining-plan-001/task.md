# Release architecture and executable implementation plan for streamlining the WFC release before Beta 2

GOAL. Produce the release architecture and an executable implementation plan for streamlining WFC's release process before Beta 2, as accepted FTRs plus one prioritized plan. This Commission implements NO product code and changes NO workflow, script, Makefile, test, pyproject or version; it plans. Shift left: the independent review is deliberately heavy on architecture, complexity, economics, reuse of existing mechanisms and real feasibility of each slice, so that the implementation Commissions that follow need few correction loops.

BINDING WORKING BASIS. `docs/warm_storage/post-beta-planning/wfc_release_process_comparison_fable_2026-11-23.adoc` (verbatim copy of an independent, non-authorizing Fable analysis; read the whole document, in particular the WFC as-is chapters, the comparison, the target operating model, `Recommendations for workflow-coordinator (WFC)` W1-W10, the roadmap and the open decisions). Everything about `core` (spreadsheet-handling) is out of scope: use it only as comparison context; produce no core FTR.

KNOWN STALENESS OF THE BASIS (verified by the Level-1 operator; check and extend it yourself, do not just trust it). The analysis was made at WFC `baab49e`, the commit carrying local tag `v0.1.0b1`; `main` is now 100+ commits later. Since then `.github/` and the `Makefile` are unchanged, but `pyproject.toml` (skill package data) and `scripts/wfc_dist_audit.py` (skill files in the allow-list) changed, and the Agent Skill (tag-pinned URLs checked against `VERSION` by `tests/unit/test_agent_skill_content.py`), chapter 9 of the Operator Manual with tutorials (`test_consumer_tutorial_pages.py`) and release-note text were added. So the version-bearing surface that W2 would have to cover is larger than the analysis lists (README links, `SKILL.md`, `references/*.md`, chapter 9 pages, several test literals in `test_release_tooling.py`, `test_bp1_identity.py`, `test_agent_skill_content.py` and others). Publication state of `v0.1.0b1` (pushed? tag run executed? PyPI/TestPyPI state, GitHub Environment rules, Trusted Publisher entries) is NOT verifiable from the repository: treat it as an explicitly marked external assumption and never invent it; make plan steps conditional on it where they depend on it.

DO.
1. Analyse the Fable concept: its comparison perspectives, architecture decisions (target operating model), recommendations W1-W10 and open decisions. For EACH recommendation record, against the repository as it is now (read: `.github/workflows/release.yml`, `Makefile`, `pyproject.toml`, `scripts/wfc_release_check.py`, `scripts/wfc_dist_audit.py`, `docs/developer_guide/ch04_release_management.adoc`, `docs/release_notes/release_notes.adoc`, `docs/backlog/postbeta_plan_p3_release_engineering.adoc`, the Operator Manual chapters 3, 5, 6, 9, 10, `docs/backlog/_open.adoc`, `docs/backlog/ROADMAP-POST-BETA-TO-RELEASE-BRIEF.adoc`, the tests that pin release behavior, and the Agent Skill sources): confirmed / partly outdated / already implemented / refuted, with file:line evidence, and a decision: adopt, adapt, defer, reject, with a reason that weighs real recurring effort against complexity and risk (economic adequacy; no machinery without a concrete recurring cost it removes). Identify what is ALREADY implemented or decided and avoid repeating it (P3 decisions and gates, E0-E3 one-time work, the existing release-check and dist-audit).
2. Reconcile with Beta-2 goals and the current state: read the Beta-2/post-beta roadmap sources in the repository (`docs/backlog/_open.adoc`, ROADMAP brief, release notes `planned` entry) and state what Beta 2 must contain for the release process. Do not decide anything the P3 decisions or the maintainer already decided; where the Fable concept reverses a recorded decision (W3: consumer smoke before vs after the tag), present it as an open MAINTAINER DECISION with both options, costs and your recommendation, not as a settled design.
3. Produce the plan document `docs/backlog/beta2_release_streamlining_plan.adoc` (follow the style of `docs/backlog/postbeta_plan_p3_release_engineering.adoc` and `docs/ai_info/doc_conventions.adoc`): the target release architecture for WFC in a compact form; the slice list with, per slice: purpose, exact scope (repository paths; note that `.github/workflows/release.yml` is NOT in the `.wfc/config.yaml` scope ceiling, so any slice that changes it needs a maintainer-decided temporary ceiling entry, as the earlier E3 slice had; say which slices are affected), dependencies, what can run in parallel (state a dependency graph and at most three parallel lanes that do not touch the same files), risks, test strategy (this repository's own: `python -m pytest -q` with the offline bundle, release tooling tests, doc render and catalog checks; WFC is stack-agnostic, but this plan is for this repository), concrete verifiable acceptance criteria, the recommended WFC profile and execution binding with the reason (standard: Sonnet worker and Sonnet reviewer; demanding: Sonnet worker and Opus reviewer; architectural: Opus and Opus; `simple@v1` where a slice is truly small), an estimate of Hop budget as an upper limit, and the Front Door docs-sync impact; the prioritized order; the explicit separation of what an autonomous Level-1 operator may do (prepare, implement and integrate locally on `main`) from what needs a human decision (any push, tag, TestPyPI/PyPI publication, GitHub Environment/Trusted Publisher/secret/branch-or-tag-protection settings, changing `.wfc/config.yaml`, Runtime promotion, accepting W3, and the release approval itself); open maintainer decisions with your recommendation; and what is deliberately NOT done and why (keep unchanged what the product justifies).
4. Produce one FTR per implementation slice as `docs/backlog/FTR-WFC-RELEASE-<SLICE-NAME>.adoc`, following the existing FTR structure (read `docs/backlog/README.adoc` and two existing FTRs such as `FTR-WFC-AGENT-SKILL-DISTRIBUTION.adoc` and `FTR-WFC-LIFECYCLE-ROTATION.adoc`): type, status (planned, nothing authorized or accepted), scope, decisions, acceptance, test strategy, dependencies, withheld authority. Group the Fable recommendations into the smallest set of slices that are independently commissionable and each realistic within one Run; do not create a slice per recommendation by reflex and do not merge unrelated risk. Slices that implement part of the plan may be marked conditional on a maintainer decision.
5. Update `docs/backlog/_open.adoc` with the new cards (follow the existing entries and ordering rules) and make `postbeta_plan_p3_release_engineering.adoc` point to the new plan with the smallest possible status edit (do not restate it, do not change its decisions).
6. Write one compact planning record `docs/warm_storage/post-beta-planning/wfc_release_streamlining_planning_record.adoc`: the claim-by-claim table of step 1, the staleness findings, the design decisions with reasons and rejected alternatives, the impact matrix (CLI/Front Door, Agent Skill, tutorials, release documentation, CI) applying the Front Door docs-sync convention (`docs/developer_guide/ch03_engineering_conventions.adoc`, section `frontdoor-docs-sync`), and the checks you ran and could not run.

CONSTRAINTS. Do not invent facts about GitHub, PyPI, TestPyPI or remote repositories: mark every such statement as an external assumption. Do not add any new governance layer, gate, agent role or program; use existing WFC programs and Phase Execution Bindings only. Every path you cite must exist. Every FTR statement about current behavior must be verified against the files. Historical material under `docs/cold_storage/` and `docs/warm_storage/` other than the new files is immutable.

ENVIRONMENT: the Coordinator's task-check runs the full required suite (`python -m pytest -q`) after your Hop with verified offline inputs; your sandbox may lack them, so do not claim full-suite counts you did not measure. Documentation checks you can run: strict render `asciidoctor --safe-mode=safe -a assembled -o /dev/null --failure-level=WARN <file>` must print nothing for each changed .adoc; `python3 scripts/wfc_doc_catalog.py generate` then `check` must not report more unresolved links or Project Memory misses than before your change (note the baseline first); catalog output is generated and must not be left as a stray file.

COMMIT MECHANICS (binding): no git command that writes (no add, mv, rm, reset, stash, commit); the index stays untouched; `commit_intent.paths` is a JSON array with exactly one plain repository-relative path per element (every new, modified or deleted leaf individually; no sentence, count, glob or directory); derive it from `git status --short -uall` and compare the counts before you finish. Leave no stray file behind. Never put untracked /dev/null-like wrapper entries into the CommitIntent. A Worker never reports any Finding operation; only the independent reviewer opens and resolves Findings.

REVIEW FOCUS (independent reviewer, whole candidate, by your own execution; architecture first): is each adopted change justified by a concrete recurring cost, or is it machinery for its own sake; does it reuse what exists (release-check, dist-audit, release.yml jobs, the P3 decisions) instead of duplicating it; is the staleness analysis complete and correct against the repository (verify the claims yourself, including the version-bearing surface and the unchanged workflow); is each slice really commissionable (scope paths exist and are inside the scope ceiling or the ceiling issue is stated, acceptance verifiable, size plausible for one Run, no hidden coupling between supposedly parallel slices); are the dependencies and parallel lanes sound; are the human decisions (publication, credentials, external settings, config changes, W3) cleanly separated from autonomous work; are all statements about external state marked as assumptions; are the FTRs consistent with the plan, `_open.adoc` and the existing backlog conventions; does nothing authorize or imply a push, tag or publication.

## Acceptance

The plan document, one FTR per slice, the `_open.adoc` cards, the minimal pointer in the P3 plan and the planning record exist and are consistent; every Fable recommendation W1-W10 has a verified disposition with evidence; the staleness of the basis is analysed against the current repository; slices are independently commissionable with exact scope (the scope-ceiling issue for workflow changes stated), dependencies, parallel lanes, risks, test strategy, verifiable acceptance, recommended profile and binding with reasons, and Hop upper limits; human decisions and external assumptions are explicit and separated from autonomous work; the Front Door docs-sync impact is recorded; no product code, workflow, script, Makefile, test, pyproject, version or .wfc/governance change; strict render of every changed .adoc prints nothing; the doc catalog check shows no additional unresolved links; the full required suite and quality gates pass; the independent whole-candidate review accepted with no blocking Finding; CommitIntent array has one plain path per element; Coordinator task-check passed.

## Withheld authority

No product code, test, workflow, script, Makefile, pyproject, version-literal, .wfc/ or governance/ change; no push, tag, release, publication, TestPyPI/PyPI action, GitHub setting or credential; no Runtime promotion or installation; no new governance layer, program or role; no invented external facts; no weakening or skipping of tests; no edit of existing historical records; no self-acceptance.

## Default escalation

Escalate a decision that the P3 decisions or the maintainer own and that blocks planning, a needed file outside the scope, and missing required evidence. Present maintainer decisions with options and a recommendation instead of deciding them. Do not silently substitute models. Incomplete work alone is not blocked.
