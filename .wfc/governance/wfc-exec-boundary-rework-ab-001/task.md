# Rework AB: trustworthy started signal, per-invocation provider channel, authentication-mount contract and fail-closed file-scope refusal for the Execution Boundary

GOAL. Rework AB of the Execution Boundary Slice A ("Execution Lifecycle Integrity" and "Boundary Contract Alignment"): fix findings F1, F2, F3 and F5 of the independent Opus implementation review (`docs/warm_storage/post-beta-planning/wfc_execution_boundary_slice_a_opus_implementation_review.adoc`, read sections 2, 2a and the probes first; F15 follows from F2). Slice A (contract `docs/backlog/FTR-WFC-EXECUTION-BOUNDARY-DISPATCH-INTEGRATION.adoc`) is implemented and integrated; this Commission changes only what F1, F2, F3 and F5 require. The four findings are deliberately one Commission because all of them change `src/workflow_coordinator/operator.py` (and the launcher/boundary seam beside it), and the reviewers must be able to judge the combined change to `operator.py` as a whole. It is NOT a redesign: the architecture the contract specified stays.

THE DEFECTS (verified in the review; re-verify them yourself by reading the code). F3 and F5 are described after F1/F2 below.
F1. The boundary-started marker, the only input to the started-versus-not-started classification of a boundary-selected provider invocation, is a file (`.wfc-boundary-started`, `execution_launcher.py` around `boundary_started_marker` and `prepare_bubblewrap`) created by a `sh -c ': > "$1"; shift; exec "$@"'` wrapper inside a directory (the provider channel on the Codex path, the external scratch on the Claude path) that is bind-mounted writable into the view. The confined agent can unlink it (a provider that did run is classified "boundary failed before the provider started") and cannot be told apart from a stale one.
F2. The provider channel is `<run_root>/provider-channel`, one directory per checkout (`operator.py` near the `channel_dir = run_root / "provider-channel"` line and `slice4.py` near line 324), not per invocation as the contract section on the provider channel specifies. A marker (or any file) from Hop N therefore survives into Hop N+1, so a bubblewrap setup failure in a later Hop is classified as a started provider. F15 (the archive reads three fixed file names from an agent-writable channel that persists across Hops, `frontdoor/archive.py`) is the archive-side consequence.

F3. The provider-authentication mount (`WFC_BOUNDARY_AUTHENTICATION_PATH`, `execution_boundary.py` `readable_host_paths` validation, `operator.py` preflight) accepts any existing host file or directory that is absolute, canonical, disjoint from the repository, system roots, channel, scratch and other mounts and outside the generated system view; the contract's rule "no blanket `$HOME` bind, and no bind of a whole provider configuration directory when a single file suffices" is not enforced and not stated in the Operator Manual; the companion test `test_readable_host_path_cannot_substitute_an_arbitrary_host_path` has a name that claims a property its body does not prove.
F5. A writable scope entry that does not exist yet is pre-created as a DIRECTORY (contract mount rule 1), except for the phase's declared durable artifacts. A worker-phase `authorized_scope` entry naming a precise, not-yet-existing FILE therefore gets a directory at that path and the Commission cannot run under the boundary, without being refused by name.

MAINTAINER DISPOSITION (binding; 2026-11-26).
F1: model the asymmetric authority as lean as technically possible: the launcher side can establish the started state, the agent can never take it back. Preferred: a unidirectional pipe with the Coordinator as the receiver and owner of the authoritative state. No additional service and no unnecessary infrastructure. The file descriptor must not be inherited by the provider. The exact semantics of the signal must be documented.
F2: change the resource model to a Hop-specific (per-invocation) provider channel. NO symptomatic clean-up of individual markers between Hops. Lifetime and identity of the provider channel correspond to the invocation, not the checkout.
F3: accept the existing implementation in principle. The choice of the authentication mount is the OPERATOR's responsibility. WFC enforces the security boundary the operator set against the agent; it does not protect the operator from the operator's own authorization decisions. Implement NO additional path restrictions. Correct the contract `docs/backlog/FTR-WFC-EXECUTION-BOUNDARY-DISPATCH-INTEGRATION.adoc` accordingly: narrow credential mounts are an operating recommendation, not a technically enforced invariant. Document in the Operator Manual that the authentication mount is an explicit extension of the read authority. Correct the misleading test name (and make its docstring state exactly what the body proves). Make sure the agent can neither directly nor indirectly configure or extend the mount itself: trace and test every channel by which the mount source could be influenced from inside a Run (environment inherited by or settable from the agent, repository content, Commission or request content, files in the writable grants or channel) and show that none exists; state the result in the review artifact. If a channel exists, close it and say so.
F5: fail closed with a NAMED preflight refusal. NO implicit widening of the authorized scope to the nearest existing directory, and no directory created where a file may have been authorized. Define the exact rule (which absent writable entries are refused, for which phases, and how a declared durable artifact is treated); prefer the narrowest rule that never creates a directory where a file was authorized; if no sound discriminator between an absent file and an absent directory exists, refuse every absent worker-phase writable entry that is not a declared durable artifact and say so plainly in the contract and the Operator Manual. The refusal must be a named boundary-preflight classification with an actionable message that says how to make the Commission runnable (declare the path as an artifact or create the file in the base). The long-term problem (creating new files in a precise file scope must eventually work under the boundary) is recorded as the backlog item `docs/backlog/FTR-WFC-EXECUTION-BOUNDARY-FILE-SCOPE-CREATION.adoc`; do not design or implement it here, and refer to it from the contract text you change.

CANDIDATE FOR THE SIGNAL (verified by the Level-1 operator on this host, bubblewrap 0.11.0, kernel 6.12; you cannot run `bwrap` in your Hop sandbox, so rely on these facts and make the Coordinator task-check, which runs with real `bwrap`, prove your tests): `bwrap --json-status-fd FD` writes JSON documents to FD from the OUTER bwrap process. Observed: (a) on success: `{"child-pid": N, "mnt-namespace": M}` then `{"exit-code": 0}`; (b) when mount setup fails (for example a nonexistent bind source): only the `child-pid` document, no `exit-code` document, bwrap exits 1 with its message on stderr; (c) when the command cannot be exec'd (nonexistent executable): only the `child-pid` document, exit 1; (d) command exits 3: `child-pid` then `{"exit-code": 3}`; (e) inside the sandbox the status fd is NOT open (writing to it fails with "Bad file descriptor"), so the agent cannot forge or withdraw it. Therefore `child-pid` alone does NOT prove the provider started (it is emitted even when setup fails); the `exit-code` document is emitted only when the wrapped command was actually executed and has exited, so "an `exit-code` document was received" is a candidate for "the provider process was started". Evaluate this against the contract's classification needs, in particular: what the Coordinator must conclude when bwrap is killed by the timeout/kill sequence (N13) before any `exit-code` document, and when the provider is killed; the `--info-fd` variant (earlier information, same non-forgeability) as an alternative; how the Coordinator opens the pipe (`os.pipe`, `pass_fds` to the bwrap process only, the read end closed in the child, the write end closed in the Coordinator right after spawn, no deadlock on a full pipe, a bounded read); whether this makes the `sh -c` marker wrapper unnecessary (then remove it and its tests rather than leaving dead code). If you find the candidate insufficient, choose the leanest sound alternative that meets the disposition (no agent-writable state in the decision) and justify it in the review artifact; do not add a service or a daemon. The signal semantics (what each observation proves and does not prove, including the kill case) go into the contract `docs/backlog/FTR-WFC-EXECUTION-BOUNDARY-DISPATCH-INTEGRATION.adoc` and the operator-facing boundary documentation.

The channel directory is created fresh for each provider invocation (identity: the invocation, for example `<run_root>/provider-channel/<invocation id>`), must not pre-exist (refuse if it does), is never reused by a later invocation, and its lifetime ends with the invocation (decide cleanly where it is archived and where it is removed; the archive must read the per-invocation files, with the glob/depth adapted, and the review artifact must say which names in an agent-writable channel are agent-reachable and therefore not trusted: F15). Keep the contract's other channel rules (the Run state directory is never mounted; read-only for the Claude shape, writable for the Codex shape; no new mount kind).
