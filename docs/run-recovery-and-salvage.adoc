= WFC Run recovery and maintainer salvage

This is the generic maintainer/operator contract for deciding what happens
after a Run or Hop does not cleanly complete. It is not a new recovery
mechanism, not a CLI manual, and does not itself authorize a Run, a
successor Commission, or a Runtime promotion.

The central invariant:

`Salvage preserves work, not authority.`

A useful second formulation, where it fits without restating the first: a
maintainer's own knowledge of what happened may be revised as evidence
accumulates, but the historical Run record itself is never rewritten.

== Four outcomes

A Run or Hop that does not cleanly complete resolves into exactly one of
four maintainer-chosen outcomes. None is automatic; the Coordinator derives
at most the bounded facts that make an outcome eligible, never the choice
itself.

[cols="1,3,3",options="header"]
|===
|Outcome |Use when |Key properties

|1. Same-Run reconcile/resume
|The existing accepted reconcile/resume predicates in
link:backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[`FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`]
allow it: same checkout identity, reconciled current HEAD verified and
stable/clean, unchanged governing truth, and no unresolved reconcile
anomaly.
|Same Run, same governing truth; the stopped Hop stays charged; no
retroactive repair of it; no automatic replay; explicit maintainer action.
This document does not implement or widen that mechanism.

|2. Maintainer salvage + fresh successor Run
|Useful bounded candidate work exists but the predecessor Hop/Run cannot or
should not continue under the same authority/truth -- e.g. dirty candidate
plus `reconcile_required` whose anomaly blocks resume, or changed
governing/Runtime/contract truth.
|The original Run remains frozen historical truth. The candidate is
preserved as explicitly non-authoritative Git history. A separately
authorized successor inspects it fresh. See "Canonical salvage procedure"
below.

|3. Forensic preservation only
|The dirty worktree has unauthorized/out-of-scope mutations, unexplained
untracked files, mixed provenance, an ambiguous baseline, or any inability
to prove the candidate is actually what the Run left behind.
|Do not create an ordinary salvage commit, which would overstate
provenance. Preserve the material externally (a patch is appropriate here),
stop, classify the state, and require explicit maintainer judgment.

|4. Discard
|The candidate has no preservation value.
|Preserve the historical Run evidence needed for audit, then discard the
candidate. Do not impose salvage ceremony on worthless WIP.
|===

== Canonical salvage procedure (outcome 2)

=== Freeze before mutation

Before changing repository history:

* verify exact current HEAD and the expected baseline/parent;
* capture `git status --porcelain=v1 --untracked-files=all`;
* establish the exact modified path set and compare it against the
  predecessor WorkItem's authorized scope;
* capture `git diff --stat` and a full binary-safe diff, and compute its
  SHA-256;
* run `git diff --check`.

Dirty agent-produced code is not run merely to make salvage appear valid.
Tests are useful evidence only if they were already trusted Run evidence.

=== Archive predecessor truth before Git salvage

Where a mechanical Run archive exists, archive the stopped Run -- saying
exactly what happened (uncertain Hop, absent candidate/trusted commit, dirty
tracked state, `reconcile_required`) -- before changing Development HEAD.
Never mutate the historical Run to point at the later salvage commit; the
salvage commit is a later, separate maintainer event.

=== Preserve exact WIP in Git

If provenance/scope checks pass, stage exactly the frozen candidate paths
and commit them without content repair, under an explicitly
non-authoritative subject such as `wip(...): preserve interrupted
<WorkItem/Hop> candidate`. The commit body identifies the source Attempt,
Run, Hop, baseline HEAD, why normal Hop authority was not established, and
that the commit is maintainer-owned preservation only. The commit may
represent a known-red or incomplete state -- a salvage commit is
history/provenance, not an accepted executable baseline, so it is never
cleaned up to look green.

=== Verify exact preservation

Reproduce the diff from the original baseline to the salvage commit and
compare its digest against the frozen precommit diff. The invariant:

`salvage commit delta == frozen dirty candidate delta`

Stop and investigate on any mismatch.

=== Fresh successor Commission

A successor is separately commissioned; predecessor governing inputs are
never mutated to retrofit continuation. The successor's execution starting
point may contain the salvage commit, but

`execution starting point != assurance baseline`

The successor task states that every salvaged line is unverified candidate
material, free to be kept, altered, removed, or replaced within the
successor's own newly authorized scope. Preservation is never required for
its own sake; the successor worker owns every retained line through fresh
inspection and its own trusted Hop result.

=== Independent review after salvage

The fresh reviewer evaluates the complete resulting product against the
real assurance baseline, including salvaged ancestry -- never merely the
latest correction, the successor's delta, or the delta after the salvage
commit. Salvage ancestry grants no correctness credit.

=== Patch role

For a coherent, attributable, entirely in-scope candidate intentionally
carried into the next Run, the Git salvage commit is the primary handoff
mechanism; a patch may still be retained as forensic backup or a recovery
aid, but does not become a third competing truth source. For ambiguous or
out-of-scope states (outcome 3), external patch/forensic preservation is
preferable precisely because an ordinary salvage commit would overstate
provenance. Git remains the durable work/provenance trail.

== Authority statement

A salvage commit IS: durable Git provenance, exact (or explicitly
classified) preservation of candidate work, and input a later separately
authorized worker may inspect.

A salvage commit IS NOT: a retroactive successful predecessor Hop, a trusted
WFC commit, a reconstructed candidate result, trusted evidence, review,
acceptance, Finding disposition, a scope grant, Runtime promotion, or
authorization for a successor Run.

Semantic acceptance/reuse of candidate material as trusted Hop output is
never authorized. That is a different statement from explicit maintainer
preservation of the exact same material as non-authoritative Git history,
which is the established practice this document canonicalizes. The two do
not contradict each other.

== Non-automation boundary

This procedure is maintainer-owned throughout. WFC does not automatically
decide candidate value, create salvage commits, widen scope, commission
successors, resume stopped Runs, or select between same-Run resume and a
fresh successor. Those remain explicit maintainer acts; future product
automation would require separate design, review, and authority, none of
which this document creates.

== Relation to adjacent mechanisms

* link:backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[`FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`]
  defines same-Run reconcile/resume (outcome 1) and its own narrower,
  evidence-gated same-Hop-retry question. It is a different mechanism from
  maintainer salvage and is not restated or widened here.
* link:backlog/BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc[`BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc`]
  records a distinct, adjacent case -- a mid-Hop scope escalation leaving
  useful uncommitted work -- and the separately implemented `export-salvage`
  / `prepare-successor` operator mechanism it commissioned. That mechanism
  packages predecessor candidate material as an explicitly untrusted,
  content-addressed bundle for a successor checkout; it is a different,
  already-productized tool for a different triggering scenario, not the
  Git-commit-based procedure documented here, and this document neither
  restates nor supersedes it.
* Runtime promotion (see
  link:self-development.adoc[self-development.adoc]) is independent of both:
  a salvage or WIP commit on Development `main` is never promoted merely
  because it is on `main`.
