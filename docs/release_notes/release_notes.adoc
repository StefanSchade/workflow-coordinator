== 0.1.0b2 -- planned

Adds one packaged, provider-neutral
https://agentskills.io/specification[Agent Skill] (named `wfc`) inside the
wheel, installed with an explicit `wfc skill install (claude|codex)`, and
read back with `wfc skill status`/`wfc skill show`. It describes how a fresh
agent session orchestrates an installed WFC from outside (Level 1): a
distillation of the
link:../operator_manual/ch10_level1_orchestration/_chapter.adoc#level1-orchestration[Level-1
orchestration] chapter, which stays the normative owner. Installation is
local and explicit: `pip install` writes nothing outside the environment,
and `wfc skill install` never writes to `CLAUDE.md`, `AGENTS.md`,
`.gitignore`, host settings or permission files, and never commits.

This is not yet qualified with fresh agents: no fresh-context,
explicit-invocation qualification run against either supported host has been
performed. No release date is set for this cycle.

Adds a disposable consumer demo kit (`examples/consumer-demo/`) and, in the
Operator Manual's consumer-quickstart chapter, a chapter overview and three
progressive tutorials built on it -- a documentation change, a program
change with a test and an independent review, and two stops. Every
tutorial rehearses offline with a scripted, no-model stand-in for the
provider before showing the live command pattern; none claims a live
provider Run was performed or qualifies any model.

Provider-reported token usage (input/output/cache/reasoning figures, never
a price) is captured per invocation when the adapter's provider reports it,
and projected into `audit.json` (per Hop, plus Run-wide totals, per-role
and per-model aggregates with an explicit lower-bound marker) and into
`wfc report`; a missing figure stays unknown, never estimated or
zero-filled. `usage_not_reported` remains the limit exactly when no
invocation captured any usable figure; `usage_partially_reported` names an
incomplete capture instead of pretending completeness.

== 0.1.0b1 -- (released)

Workflow Coordinator (WFC) is a bounded, repository-native engine for
serial agent workflows with explicit Git, evidence, authority and
human-stop boundaries. It installs as the `wfc` command-line tool
(`python3 -m pip install 'workflow-coordinator==0.1.0b1'` from PyPI, or
`python3 -m pip install .` from a source checkout) and operates a single, independently reviewed
WorkItem against an authorized Commission: `init`, `plan`, `run --yes`,
`status`, `report` and archive, all against the executing repository's own
Git history. Real provider execution always requires separate consumer
authority and is never implied by installation.

This beta's practical qualification is as a coordinator for
*software-development* workflows: its own development and the consumer
quickstart both exercise a Git repository with a committed check command as
trusted evidence. The product's task-level mechanics make no assumption
beyond a Git repository, repository-relative scopes and an evidence command
given as plain argv; non-software use is not excluded, but only the
software-development path is qualified for this release. This
domain-neutral core is an enabling component of a longer-term "Agentic
Anything Factory" direction -- a strategic target image, not a capability
this release delivers.

Qualification of this release candidate (the evidence is recorded in the
link:../developer_guide/ch04_release_management.adoc[release-management
chapter]): the GitHub-hosted workflow ran the whole required test suite, lint,
build, distribution audit, an install-and-identity smoke from the built wheel
and the strict documentation render on a hosted Linux runner (run 9 of
2026-11-23, accepted by the maintainer); an informational job installed the
same wheel on CPython 3.10, 3.11 and 3.12 and ran a provider-free test
selection, which is a compatibility smoke and not a qualification of those
interpreters. Two minimal consumer smoke runs, one per supported adapter
(Claude and Codex), drove the installed wheel through authorization, a worker,
an independent review by a different model, the trusted commit and evidence
archival on a separate consumer repository. They demonstrate that the chain
works for one trivial documentation task; they are not a qualification of any
consumer change or of non-trivial work.

Known limitations of this beta (see the
link:../operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#beta-limitations[consumer
quickstart's full list] for detail):

* WFC does not supervise a launched provider process; an unresolved launch
  is classified `uncertain_launch` and is never treated as safe to relaunch.
* Every role in a Run shares one adapter and one provider executable; mixing
  adapters within a Run is not supported.
* A Commission declares exactly one trusted `task-check` command (at most
  900 seconds), used both as the pre-launch baseline probe and as
  `task-check` evidence; there is no separate per-phase or per-Hop command.
* The working tree must be completely clean at launch, and every scope path
  must sit at or beneath a path already named in `--scope-ceiling`.
* There is no `wfc continue`; a stopped Run is recovered manually from a
  non-authoritative preservation commit, inspected from scratch by a fresh
  successor Commission.
* One Run per checkout: an already-authorized checkout refuses every later
  `wfc run` until lifecycle rotation is decided, even after a terminal,
  archived Run.
* The archived `audit.json` always reports `usage_not_reported`; token usage
  is not measured.
* WFC never pushes either the payload or the Evidence repository; every
  commit it makes stays local.
* Trusted commits (the Commission commit, candidate preservation and the
  bounded path commit) refuse outright whenever any effective
  `filter.*.clean`/`filter.*.process` Git configuration is visible to them,
  including Git LFS; a repository that needs such a filter cannot currently
  use WFC's trusted commits. This is a deliberately conservative current
  limit, not a bug, and not advice to remove such filters from a repository
  that functionally needs them.

Qualified platform for this release: CPython 3.13 on Linux x86-64 (the
offline-input profile's one qualified host). The package declares Python
3.10 or newer, but no other interpreter, architecture or OS is qualified by
this repository's own development; ARM64 is an intended target, not a
qualified one today. An installed, authenticated Claude or Codex CLI is a
prerequisite for using the matching adapter, not itself a qualification of
that adapter/model combination for this release.

WFC began as tooling inside the `spreadsheet-handling` repository and was
later extracted into this standalone project; its kernel stayed generic
enough for foreign-domain work, demonstrated by a September 2026
Latin-course dogfood in another repository. That history is a limited
feasibility demonstration, not a qualification of this product for
non-software use.
