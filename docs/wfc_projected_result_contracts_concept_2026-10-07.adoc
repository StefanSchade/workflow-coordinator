== 1. Purpose

Define a provider-neutral, phase-/role-projected semantic result contract so
a WFC agent invocation can only emit the result vocabulary its current
phase actually owns. The reducer already enforces statefully that a result
is *authorized*; this work makes a class of results *inexpressible* before
authority is even checked, removing recurring mechanical preemption of
otherwise-useful agent work. Sequenced into small permanent slices (P1-P5,
section 17) with Runtime promotion points between them (section 18).

P1 (section 16) is now implemented, independently assured by a fresh
successor Run, archived, semantically curated, and promoted to Runtime. From
here, this document's remaining job is to govern P2 onward -- including two
lessons P1 dogfooding surfaced that the original draft did not anticipate:
a composition-level authority-conformance gap (section 11) and a model-owned
versus Coordinator-owned mechanics gap in commit rendering (section 12).
Neither changes what P1 already shipped; both sharpen what comes next.

== 2. Empirical problem statement

Three reproductions, already recorded in
`docs/backlog/BUG-WFC-PHASE-COMPLETION-CONTRACT-OPAQUENESS.adoc`, motivate
this concept; that record offers them as evidence toward the deferred FTR's
activation criterion, which this document treats as satisfied.

*S4-001, worker-phase contract mismatch* (`WI-WFC-CORRECTION-CONVERGENCE-
ESCAPE-IMPLEMENTATION-S4-001`, Run `RUN-3efc7eb2aa374263a2b12954213642f1`,
Hop H001, `role: worker`). The worker did useful partial implementation but
returned `outcome: changes_required` -- a review-style disposition the
`worker` phase does not produce when completing -- made no commit, and left
the worktree dirty. The Coordinator mechanically preempted it; the useful
partial work survived only as non-authoritative salvage, and a fresh
successor Run (S4-002) had to begin. `Outcome.CHANGES_REQUIRED` is one value
of the single `Outcome` enum shared by every phase's `RoutingResult.outcome`
(`model.py:138-142`, `:388-404`); nothing in today's schema
(`codex_adapter.py:141-142`) keys its admissible members to the dispatching
phase's role.

*Existing-Finding invariant restatement*
(`docs/backlog/BUG-WFC-IMMUTABLE-FINDING-ECHO.adoc`, Latin Story-2 dogfood,
Run `RUN-b57dcdacecb142239cb80a45015da0bf`, Hop H004, `independent_reviewer`
rereview). H004 correctly judged Finding F001 resolved, but its
finding-delta supplied an `invariant` string that paraphrased -- rather than
reproduced byte-for-byte -- F001's Coordinator-owned original text;
`reducer.py` correctly rejected it. The judgment was correct; only the
unconstrained-string projection of Coordinator-owned state caused the stop.
(A different, textually similar identifier, `S4-004` Hop `H006` in
`FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE_implementation_review_001.adoc`, is an
unrelated replay budget-preemption finding; this document cites the Latin
incident, not that one.)

This instance is *already structurally fixed*, and is this concept's working
precedent (section 5, section 10): `FindingDeltaValue` (`model.py:310`) now
splits into `NewFindingDelta` (`:297-308`, carries `invariant`/`blocking`,
agent-authored) and `ExistingFindingDelta` (`:286-295`, carries only
`finding_id`/`proposed_state`/`evidence_refs`/`successor_ref`/
`new_material_evidence` -- no `invariant`, no `blocking`). The Codex/OpenAI
projection (`codex_adapter.py:105-135`) emits an `anyOf` of two disjoint
strict schemas matching that split, so the wire contract no longer offers an
`invariant`-replacement slot for an existing Finding, and `reducer.py`
dispatches on `isinstance(delta, ExistingFindingDelta)` (`:598`, `:715`), not
a string discriminator.

*S3-002, Finding-authority mismatch.* H003 rereview correctly judged three
Findings resolved but could not express it because
`rereview.review.finding_authority` was `[]` -- an authority *projection*
gap, tracked separately in
`docs/backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc`. At the
time of the original draft this was cited only as evidence of the shared
pattern. P1's own self-development lineage then reproduced the identical
failure shape against itself: predecessor Run
`RUN-157080a2fa7b44de8429aa9b8fba53ab`'s H002 independent review opened
Run-native blocking Finding F001; H003 corrected it; H004's fresh rereview
independently judged F001 satisfied and requested `accept`, but
`rereview.review.finding_authority` was `[]`, identical to
`independent_review`'s own, so H004 had no operation able to transition F001
out of `open` -- the reducer correctly refused `accept -> complete` and the
Run terminated `awaiting_human`. The successor P1-Assurance-Closure
Commission's only available fix was a local, per-profile workaround: granting
`finding_authority: [resolve]` to both its `independent_review` and
`rereview` phases (`governance/self-development/projected-result-contracts-
p1-assurance-closure-profile.yaml`). This is why this document now treats
the pattern as the concrete motivating case for the new P3.5
Commission/authority-conformance slice (section 11), still not a P1-P3
target: P1 did not just observe this failure class in an unrelated lineage
(S3-002), it suffered it directly, and closed it only ad hoc, per
Commission, not architecturally.

*Common property:* in each case the agent's semantic judgment was sound; a
different independently-expressed surface of the generic envelope (an
untyped shared `outcome` enum, an unconstrained `invariant` string, an
unprojected authority gate) let a locally plausible result become globally
inadmissible, caught only by mechanical preemption. The fix is to stop
offering the inadmissible shape, not to weaken any check.

== 3. Design principles

* *Generic inside, specific at the agent boundary* -- the reducer/domain
  layer may keep internal generic representations (`FindingDeltaValue`
  already is one); the contract projected for one invocation must be
  role/phase-specific.
* *Semantics from the model, mechanics from the Coordinator* -- the model
  emits only the degrees of freedom it owns; deterministic mechanics are
  derived where already true, or later made so (section 12).
* *Structural invalidity unrepresentable; stateful invalidity rejected* --
  parse/schema boundaries make a class of shapes impossible to construct;
  the reducer alone decides whether a structurally valid result is
  permitted here, now, by this history.
* *Declarative derivation, no hardcoded phase names* -- already required by
  the deferred FTR ("designs such as `if phase == "correct":
  forbid_resolve()` are explicitly rejected"); selection keys off admitted
  configuration (`WorkflowRole`, `ReviewDescriptor` presence,
  `finding_authority`, `ConvergenceRole`), the same facts
  `vertical.py:300-305` and `prompt.py` already read declaratively.
* *Defense in depth, three layers, never collapsed* -- prompt projection
  tells the model what it may do; the phase-scoped schema makes a locally
  invalid action hard or impossible to emit; the reducer remains
  authoritative regardless. This document does not touch reducer authority.

These five principles are unchanged by this revision and govern the new
P3.5 slice (section 11) exactly as they governed P1-P3: P3.5 adds a sixth
kind of check -- whether individually valid phase capabilities *compose*
into a completable workflow -- without weakening or duplicating any of the
five.

== 4. Structural vs. stateful validity

[source,text]
----
STRUCTURAL (parse/schema)              STATEFUL (reducer)
"Can a worker emit changes_required    "Does F001 exist? Does this
 at all?" -- NO, type has no field      authority have permission to
"Can an existing-Finding delta carry    resolve/reopen it? Is the
 a replacement invariant?" -- NO,       transition legal given history?
 field absent from that variant         Is evidence sufficient?" --
                                         reducer decides, always
----

A review schema may structurally permit `finding_id` + `disposition` +
`evidence_refs`; the reducer still decides whether that Finding exists,
whether this phase has authority over it, whether the transition is legal,
and whether evidence is sufficient. Projected contracts narrow vocabulary;
they never narrow or replace reducer authority. `ExistingFindingDelta` is
the live proof: removing `invariant` from the type removed rewriting from
the realm of possibility, while every reducer check on what the type still
*can* carry is untouched.

A third category sits beside these two and is distinct from both: whether a
*Commission/profile's declared capabilities, taken together across phases*,
can ever reach a completable state at all. This is not per-invocation
structural validity (it is not about what one result type can express) and
it is not per-decision stateful validity (it does not depend on any
particular Run's history). It is static composition validity over a
workflow graph, knowable from the Commission/profile alone, before any Run
exists. Section 11 names this the P3.5 slice.

== 5. Current architecture seam

[source,text]
----
Phase (role, convergence_role, review.finding_authority) -- model.py:225
    v
vertical.py:300-305 -- result_contract_version = 2 if
    profile.schema_version == 3 or phase.convergence_role is not NONE
    else 1  <- declarative selector, but coarse: one axis, never role
    v
prompt.py:assemble_prompt (:149) -- already phase-derived, no names
    v
AgentExecutionRequest(..., ROUTING_RESULT_ENVELOPE_CONTRACT,
    contract_version=...) (adapter.py:39-51) -- result_contract is
    ALWAYS the one constant; only the version int varies
    v
CodexCliAdapter.execute (codex_adapter.py:269-270) -- ONE schema
    per version, covering every phase/role
    v
provider -> adapter.validated_result (:104) ->
    serialization.routing_result_from_data (:1151) -- ONE parser,
    version-gated, not role-gated
    v
RoutingResult (model.py:388) -- one shape, superset of every phase
    v

    ExistingFindingDelta) (:598, :715)
----

Three facts mattered for P1, and remain true as the seam P2-P5 build on.
First, the selection mechanism already existed, narrowly:
`vertical.py:300-305` was a real declarative fact-to-variant selector; P1
generalized its *shape*, not its content (section 16). Second, the identity-
versioning discipline already existed and already survived replay:
`RoutingResult.schema_version`, `AgentExecutionRequest.contract_version`,
and `Run.schema_version` (1/2/3) are persisted facts, checked for
consistency (`adapter.py:117-121`), and `serialization.run_to_json`
(`:1239`) already drops fields a historical version never had. Third, the
one working precedent for a role-aware disjoint projection is
`ExistingFindingDelta`/`NewFindingDelta` (section 2) -- a real `anyOf` of two
disjoint strict schemas, serialized/parsed/reduced without a string
discriminator. P1 scaled this from one field family to the whole
per-invocation contract-selection seam; P2-P3 scale it further to the result
types themselves.

== 6. Target projected-contract architecture

[source,text]
----
admitted Profile + Phase + Run facts
    v
SELECTION (P1, COMPLETE) -- deterministic function of the facts,
    never a phase-name switch -- returns a ResultContractKind
    v
semantic result TYPE (WorkResult | ReviewVerdict | RoutingResult)
    -- "parse, don't validate": invalid combinations for THIS kind
    cannot be constructed from provider output at all
    v
adapter projection (existing seam) -- kind -> provider schema,
    exactly as routing_result_openai_schema already does
    v
provider invocation (unchanged) -> kind-specific parse -> reducer
    (UNCHANGED)
----

Selection and the `ResultContractKind` identity were the only new permanent
concepts P1 introduced; every stage below the semantic-type line already
existed in some form. P2-P5 change what flows through the existing pipe,
not its stages.

== 7. Contract ownership

Profile/domain layer defines semantics -- `WorkflowProfile`/`Phase` already
carries every fact selection needs; no new ontology. The orchestration layer
(`vertical.py`, at its existing `result_contract_version` call site) owns
invoking selection once per Hop. The provider adapter receives an
already-selected kind and never infers semantics from phase names, exactly
as it already only knows how to render a given `contract_version` today.
The reducer never participates in selection; it consumes whichever semantic
type the kind produced, unchanged.

== 8. Worker / corrector direction

Illustrative only, not implemented here:

[source,text]
----
WorkResult:
    status: completed | blocked
    summary, evidence_refs, claimed_commits
    commit_intent: CommitIntent | null
    escalation: Escalation | null   (only if this phase owns escalation)
----

No `changes_required` branch exists on this type -- absent from the type,
not merely forbidden by a reducer check. S4-001 becomes structurally
impossible: a worker cannot emit a review-style disposition because
`WorkResult` has no field that could hold one. Whether `findings` belongs
on `WorkResult` for worker-role phases that today create new Findings in
some profiles is an open P2 question (section 22). `commit_intent`'s own
shape is reassessed in section 12; nothing there changes this section's
illustrative sketch of *which* result families exist.

== 9. Review / rereview direction

[source,text]
----
ReviewVerdict:
    verdict: accept | changes_required
    finding_updates: [ExistingFindingUpdate | NewFindingAuthoring]
    evidence_refs, summary
----

`changes_required` exists only on this family's type. The S4-001 category
mistake is eliminated at both ends: a worker cannot emit it, and a
reviewer's authority to emit it is visible in the type it was given, not
inferred from prose a prompt already constructs per phase but today's
single shared `Outcome` enum does not mirror at the schema level.

== 10. Finding projection direction

The slice with a working precedent already in production (section 2,
section 4); P3's job is to generalize, not invent. `NewFindingAuthoring`
(P3 name for today's `NewFindingDelta`) carries `invariant`/`blocking`/
`proposed_state`/`evidence_refs`/`successor_ref?`, unchanged, because
new-Finding authorship is genuinely agent-owned. `ExistingFindingUpdate`
(P3 name for today's `ExistingFindingDelta`) carries `finding_id`/
`disposition`/`evidence_refs`/`new_material_evidence?`/`successor_ref?`,
unchanged; immutable trusted fields (`invariant`, `blocking`, origin hop)
are never re-authored by the model, because the reducer already sources
them from Coordinator-held `Finding` state (`model.py:408-419`), never from
the delta. P3's actual work is confirming this is the general pattern P2's
`finding_updates` field should embed, and auditing whether any other field
named a "related echo" in the accepted `WI-WFC-GENERATIVE-ECHO-AUDIT-001`
assessment needs the same treatment once P2's per-family types exist to
host it.

P3 owns *what the model may author about a Finding*: a brand-new invariant
and blocking judgment for a Finding that does not yet exist, or a
disposition proposal plus evidence for one that does. P3 does not own, and
must never re-introduce, authorship of trusted immutable Finding facts
(`invariant`, `blocking`, origin Hop) once a Finding exists -- those remain
sourced from Coordinator-held state, exactly as `ExistingFindingDelta`
already demonstrates. Whether a *phase* is even permitted to disposition a
Finding at all is a different, composition-level question: that is P3.5
(section 11), not P3. P3 generalizes *what a result can say*; P3.5 checks
*whether the phases that can say it were ever granted the authority to make
it stick*.

== 11. New slice: Commission / authority conformance (P3.5)

*Purpose:* mechanically reject internally inconsistent Commission/Profile
workflow graphs before any provider invocation. This is a different failure
class from projected result typing (sections 8-10). Projected result typing
constrains what *one* agent invocation can express. Commission/authority
conformance constrains whether the *individually valid* capabilities
declared across a workflow's phases *compose* into a workflow that can ever
mechanically complete. A phase can be perfectly well-formed in isolation --
a legal `ReviewDescriptor`, a legal `finding_authority` tuple, legal
`routes` -- and the graph those phases form can still be unreachable to
`complete` for any agent, however sound its judgment.

*Concrete motivating failure, first instance*
(`docs/backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc`,
discovered via `WI-WFC-CORRECTION-CONVERGENCE-ESCAPE-IMPLEMENTATION-S3-002`):
an `independent_review` gate opened blocking Findings `F001`/`F002`/`F003`;
`correction` ran and fixed the underlying defects but, correctly, asserted
no Finding disposition (`correct` has no review descriptor and no
disposition authority of its own); `rereview` -- a gate whose own stated
purpose was "fresh independent disposition of the corrected implementation"
-- judged all three corrections sufficient and requested `accept`, but could
not resolve any of the three Findings because the profile commissioned it
with `finding_authority: []`. The Run correctly, truthfully stopped
`awaiting_human` with three open blocking Findings, rather than silently
completing or fabricating authority. The admission test for that profile,
`tests/architecture/test_self_development_governance.py::
test_correction_convergence_escape_implementation_s3_002_bundle_passes_
production_preflight`, explicitly asserted the empty-authority tuple -- the
contradiction was authored and admitted deliberately, not an oversight that
slipped past review. The BUG record further notes this same empty-authority
convention was latent across every predecessor self-development profile in
the lineage (S1-001 through S2-003), never exercised only because no prior
reviewer in that lineage had populated a Run-native blocking Finding.

*Concrete motivating failure, second instance -- P1 itself* (section 2):
predecessor Run `RUN-157080a2fa7b44de8429aa9b8fba53ab` -- the Run that
implemented this very P1 slice -- reproduced the identical shape against its
own self-development Commission. H002 independent review opened Run-native
blocking Finding F001; H003 corrected it; H004's fresh, independent rereview
judged the correction satisfactory and requested `accept`, but
`rereview.review.finding_authority` was `[]`, identical to
`independent_review`'s own, so it had no operation able to close F001. The
Run correctly stopped `awaiting_human` rather than completing. The only
available remedy was local and ad hoc: the successor P1-Assurance-Closure
Commission's profile
(`governance/self-development/projected-result-contracts-p1-assurance-
closure-profile.yaml`) grants `finding_authority: [resolve]` to both its
`independent_review` and `rereview` phases, fixing this one Commission, not
the pattern. Two independent lineages hitting the identical shape -- one of
them the very work that produced this concept -- is why this slice is added
now as permanent architecture rather than left as a sequence of one-off
per-Commission authority grants: the failure is structural to how
Commission/profile authority is authored, not an isolated incident.

*Target property (ordered reachability, not path membership):* for every
phase `P_open` capable of producing a new, open, blocking Finding (any
phase with a `review` descriptor whose `authority`/`blocking_policy`
admit opening one), and for every forward path from `P_open` that may
reach a `complete`/`accept`-gated route while that Finding can remain
open, some phase *strictly reachable after `P_open` on that same forward
path* -- not `P_open` itself, unless a route loops back to it and a later
invocation of that same phase occurs after the Finding was opened -- must
possess the Finding operation needed to dispose of it before completion.
Authority located only at or before `P_open` does not satisfy this:
`reducer.py:1413-1423` computes `permitted_operations` from the
*currently executing* Hop's phase alone, so `P_open`'s own authority is
already spent by the time a later Hop on the same forward path needs to
close the Finding it opened. This is a static ordered-reachability
condition over the existing declarative `Phase.routes`/
`finding_authority` facts -- a suffix-of-path check relative to where the
Finding becomes open, not set membership over the whole path -- not an
addition of temporal logic or a generic model checker. For example, in

[source,text]
----
independent_review
    -> correction
    -> rereview
    -> accept -> complete
----

if `independent_review` can produce an open blocking Finding and
`correction` does not itself own Finding disposition, then a phase
*after* `independent_review` on the forward path -- here, `rereview` --
must hold sufficient `finding_authority` (at minimum `resolve`) to close
the corrected Finding before `accept -> complete` is reachable. Granting
`resolve` to `independent_review` itself instead of (or in addition to)
`rereview` does NOT satisfy this property: `independent_review` is the
opening phase, already executed by the time disposition is needed, and
this topology does not route back to it. A Commission that cannot satisfy
the ordered property for some reachable state should fail a trusted
preflight check -- `INVALID COMMISSION / PROFILE` -- before provider
invocation, agent cost, semantic work, or the creation of a doomed Run.

*Boundary (ties to section 4):* this is a third validity category,
distinct from both existing ones. It is *statically knowable* from the
Commission/profile alone -- reachable phase topology, phase routes, declared
`finding_authority`, declared gate `authority`, completion requirements --
and so belongs at trusted preflight, before a Run exists. It is explicitly
*not* a replacement for reducer authority: whether a *specific* Finding, in
a *specific* Run's history, may legally be resolved by a *specific* Hop
remains entirely the reducer's stateful decision (section 4's right-hand
column), unchanged. P3.5 only rejects graphs that could never have reached
a legal completion regardless of any Run's actual history; it never
second-guesses a reducer decision about one that could.

*Explicit non-overstatement:* this is not full formal verification of
workflow semantics, and must not grow into one. It is the smallest useful
static conformance check expressible over the declarative facts the engine
already admits (`Phase.role`, `Phase.review`, `Phase.review.finding_authority`,
`Phase.routes`, `ReviewAuthority`, `ConvergenceRole`) -- the same facts
`vertical.py:300-305`, P1's `select_result_contract`, and `prompt.py`
already read declaratively. No new workflow DSL, ontology, or generic
compiler is implied or desired.

*Where this belongs (open, not decided here):* the engine already has a
structurally analogous precedent -- `operator.py:265`'s `_preflight`
already performs trusted, mechanical, pre-Run cross-document consistency
checks (repository identity, `WorkItem.personas` vs. profile roles,
execution-binding roles vs. profile roles) before any Commission is
authorized to run. Whether the new conformance check belongs inside profile
parsing (`serialization._review`/`workflow_profile_from_yaml`), as a
separate conformance pass over an already-parsed `WorkflowProfile`, or as an
addition to this existing `_preflight`/Harness-WFC-preflight boundary is left
to P3.5 implementation after source inspection; this document does not
prematurely choose among them.

*Non-goals for this slice* (restated from the governing task): no
Commission-conformance implementation is authorized here; no new workflow
DSL, ontology, plugin system, provider registry, outer orchestration layer,
hierarchical escalation system, or generic compiler; no closure of
`BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY` itself (that BUG's own
follow-up directions -- profile audit, admission-test strengthening,
least-privilege authority grants, a regression fixture -- remain its own
record's scope; P3.5 is the permanent engine-level generalization of the
same invariant, not that BUG's closure).

== 12. Coordinator-owned effects / mechanics (P4, sharpened)

Assessed only, not committed to implementation here. The governing question
for every candidate field is the same throughout:

[source,text]
----
Which fields express genuine model-owned semantic degrees of freedom, and
which merely restate facts or mechanics already deterministically known by
the Coordinator?
----

This is a different failure class again from both projected result typing
(sections 8-10) and Commission/authority conformance (section 11).
Projected result typing constrains what an individual agent invocation can
express. Commission/authority conformance constrains whether individually
valid phase capabilities compose into a mechanically completable workflow.
Coordinator-owned effects removes model-authored *restatement* of mechanics
the Coordinator already knows deterministically -- a field can be perfectly
well-typed and the workflow perfectly completable, and still ask the model
to re-derive, in prose, a fact the Coordinator could have computed exactly.

*New concrete P4 direction: canonical commit intent.* Today's
`CommitIntent` (`model.py:320-328`) carries `paths: tuple[str, ...]` and
`subject: str`, and the model supplies the complete subject string, free
form. `git_facts.py:386-395`'s `commit_subject_error` already *validates*
that string as a postcondition -- one non-empty line, Conventional-Commit
shape (`_CONVENTIONAL_SUBJECT`), and containing both the WorkItem id and the
Hop id as literal tokens -- and `git_facts.py:738` passes `intent.subject`
directly to `git commit -m`. This produced a materially more readable Git
log than older subjects did, but the correctness of WorkItem identity, Hop
identity, punctuation, Conventional-Commit shape, and formatting currently
depends on the model reproducing all of it correctly, with the Coordinator
only checking afterward that it did. That is restatement-then-validation of
facts the Coordinator already holds (`work_item_id`, `hop_id`), not
authorship of a fact only the model could know.

Illustrative direction only, not normative syntax:

[source,text]
----
commit_intent:
    paths: [...]
    kind: docs
    summary: "record independent assurance review"
----

with the Coordinator -- not the model -- owning `work_item_id`, `hop_id`,
canonical punctuation/format, and final subject rendering, deterministically
producing exactly the shape `commit_subject_error` already polices, e.g.:

[source,text]
----
docs(WI-WFC-PROJECTED-RESULT-CONTRACTS-P1-ASSURANCE-CLOSURE):
record independent assurance review H001
----

Field naming above (`kind`, `summary`) is illustrative, not normative; P4
implementation fixes exact syntax after source inspection, not this
revision.

*Is `kind` (docs/test/chore/feat/fix) mechanical or semantic?* Not a
simplistic single answer. `docs`/`test`/`chore` may often be mechanically
inferable from the classes of paths actually mutated (a commit touching only
`docs/**` is unlikely to be anything but `docs`). `feat` versus `fix` more
often expresses a genuine semantic judgment about the nature of a change
that path classification alone cannot always recover. P4 implementation
must make this distinction explicit rather than forcing one rule for every
`kind` value; some commits' `kind` may be Coordinator-inferred, others may
remain model-declared, and the two need not be resolved identically.

*Other P4 candidates, reassessed but not decided:*

`requested_route`:: often derivable from a typed semantic verdict/status
plus `Phase.routes`, once P2 supplies a total per-family mapping. Not
decided here.

`requires_human`:: potentially derivable from `escalation is not None` plus
phase/human-gate facts, rather than an independently model-settable boolean.
Not decided here.

`claimed_commits`:: the Coordinator already observes actual Git facts
independently; whether this field remains semantically useful once observed
facts exist, or is merely generative echo, needs determination -- not
decided here.

Durable-artifact completion bookkeeping:: likely Coordinator-owned
mechanical truth already, but must stay aligned with
`BUG-WFC-PHASE-COMPLETION-CONTRACT-OPAQUENESS.adoc` rather than be redesigned
independently of it here.

`summary`:: likely remains model-authored semantic explanation unless
evidence surfaces otherwise -- the one candidate most clearly on the
"genuinely model-owned" side of the governing question.

The same principle governs every candidate above and the CommitIntent split:
do not ask the model to restate a deterministic Coordinator fact merely
because today's schema happens to offer it a slot to restate it in.

== 13. Provider-neutral projection boundary

The semantic result type is provider-neutral by construction, an ordinary
dataclass like today's `RoutingResult`. The seam from semantic type to wire
dialect already exists and already isolates this concern:
`codex_adapter.py`'s module docstring states it "owns Codex argv/process
behavior and the OpenAI Structured Outputs dialect... neither parses nor
accepts a semantic RoutingResult," and `routing_result_openai_schema`/
`assert_openai_strict_schema` (`:60-96`, `:100`) are today's concrete
instance. P1 did not relocate this seam, only made it receive a *selected*
kind instead of always the one generic type. A future Claude adapter would
implement its own `<kind> -> schema` function beside this one; neither
adapter infers semantics from phase names. Any P4 CommitIntent-rendering
change (section 12) stays entirely on the Coordinator side of this boundary:
whichever provider is dispatched to, it still only ever supplies the
model-owned fields, never the rendered subject. Full capability-registry
cleanup is P5, assessed only if still needed after P1-P4.

== 14. Replay / persistence implications

Replay must never validate a historical Hop against a contract other than
the one actually used, and must never infer contract identity from mutable
current configuration. Section 5 already shows the working answer for the
coarser existing axis: `Run.schema_version`, `RoutingResult.schema_version`,
and `AgentExecutionRequest.contract_version` are persisted per-invocation
facts, not re-derived from current profile YAML, and `run_to_json` branches
on the *persisted* version. P1 generalized this discipline to a
`ResultContractKind` identity persisted as a sibling pair alongside version
on `Hop`/`HopSummary` (`model.py:449-450`, `:502-503`): a complete recorded
pair governs replay, an incomplete or unsupported pair fails closed before
trust, and historical Runs with no recorded pair fall back to the shared
selector/version seam truthfully. A historical Run recorded under today's
generic contract stays valid forever under its own recorded kind, no
migration, no re-validation of existing Runs. The same discipline must
extend to whatever P2 adds (new `ResultContractKind` members) and to any P4
CommitIntent rendering change: a historical Hop's persisted `commit_intent`
and the actual rendered subject it produced must remain replayable exactly
as recorded, never re-rendered at replay time from a possibly-since-changed
rendering rule.

== 15. Prompt implications

`prompt.py:assemble_prompt` already derives its text entirely from `Phase`
facts (role, routes, authorized_scope/actions, evidence, finding_authority
-- `:116-147`), with no phase-name branching. P1 did not need to change
this; P2 must keep it synchronized with its strict types, so a worker's
prompt never describes a `changes_required` option its `WorkResult` type
cannot carry. Because `assemble_prompt` already receives `phase` and
`contract_version`, threading the selected kind through the same call was
additive, and any P4 CommitIntent field split (section 12) must likewise
keep the prompt's description of what the model may supply synchronized
with what the rendered type can actually carry.

== 17. P2-P5 sequencing

implementation slice after this revision. P3, Finding authority types
(section 10): generalizes the already-working `NewFindingDelta`/

`BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY`'s failure class. P4,
Coordinator-owned effects (section 12): assessed and sharpened here around
canonical CommitIntent rendering, may be a larger refactor, does not block
P2/P3/P3.5 shipping. P5, provider projection/capabilities cleanup (section
13): only if still needed after P1-P4.

Each slice is permanent architecture; none is a parallel v1/v2 result
system requiring later removal. The three non-P1 failure classes this
roadmap now separately names are genuinely distinct and must stay visible as
distinct, not collapsed into one "result contract" story: projected result
typing (P2/P3) constrains what *one* agent invocation can express;
Commission/authority conformance (P3.5) constrains whether individually
valid phase capabilities *compose* into a workflow that can mechanically
complete; Coordinator-owned effects (P4) removes model-authored

== 19. Testing strategy

P1 (realized; implemented and reviewed, not re-specified here): deterministic
selection tests, adapter-reachability tests, replay/history tests, and a
fail-closed path for an unsupported projection -- all present in the
reviewed candidate (`FTR-WFC-PROJECTED-RESULT-CONTRACTS_implementation_review_002.adoc`),
exercised provider-free.

P2 (not designed here): worker schema cannot represent review-only outcomes
and vice versa at the type level, not a runtime check; provider
schema-generation tests per family; reducer remains the stateful authority.

P3 (not designed here): `ExistingFindingUpdate` cannot carry `invariant`
(already true today; P3 generalizes this to the per-family types);
`NewFindingAuthoring` still requires full authored fields; authority/state
tests stay in the reducer.

P3.5 (not designed here, sketched only): fixture Commission/profile pairs
covering both a known-good topology (sufficient `finding_authority`,
correctly *ordered* per section 11's ordered-reachability property, on
the forward path after any phase that can open a blocking Finding) and a
known-bad one modeled directly on the S3-002 shape (section 11), asserting
the trusted preflight check accepts the former and rejects the latter with
`INVALID COMMISSION / PROFILE` before any provider call.

"Every currently accepted self-development Commission/profile must
continue to pass" is not one undifferentiated promise. P3.5 must hold
four distinct compatibility promises apart and must not conflate them:

. *Historical artifact remains parseable* -- unaffected; P3.5 is a
  preflight-time check over profile YAML, never the historical-Run
  parsing path.
. *Historical Run remains truthfully replayable* -- unaffected; section
  14's replay discipline is per-Hop persisted-identity based, and P3.5
  runs before a Run exists, not during replay.
. *Old profile remains usable as a regression fixture* -- preserved, but
  the fixture's *assertion* changes: the profile document stays and keeps
  exercising exactly the shape P3.5 exists to catch.
. *Profile remains admissible for a NEW launch under current preflight* --
  intentionally and deliberately revoked by P3.5 for any profile whose
  topology matches the structurally invalid shape (a gate phase capable
  of opening a blocking Finding, a non-disposing correction phase, and a
  rereview gate with `finding_authority: []`, routing to `complete`).

P3.5 MUST preserve promises 1-3 for every existing profile. P3.5 MUST
revoke promise 4 for any profile matching the invalid shape above --
explicitly including the eight self-development profile lineages
`correction-convergence-escape-implementation-{s1-001,s1-002,s1-003,
s2-001,s2-002,s2-003,s3-001,s3-002}-profile.yaml`, whose
`tests/architecture/test_self_development_governance.py`
`..._bundle_passes_production_preflight` assertions are expected to flip
to an equivalent `..._bundle_fails_production_preflight` assertion as
part of P3.5's own bounded implementation. This is not a regression: it
is the intended behavioral effect of shipping P3.5 at all. Every other
currently accepted Commission/profile, whose topology does not match this
shape, must continue to pass unchanged.

P4 (not designed here, sketched only): canonical-rendering tests proving the
Coordinator-rendered commit subject matches exactly what
`commit_subject_error` already requires, for every `kind`/path-class
combination; a property that model-supplied prose can never influence the
rendered WorkItem/Hop identity or punctuation, only the semantic fields it
is given.
