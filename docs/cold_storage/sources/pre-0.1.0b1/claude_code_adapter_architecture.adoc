== 1. What this document is, and is not

It explains how WFC's `claude_cli` adapter actually invokes the Claude Code
CLI today -- including its child-process environment, its write-permission
grant, and its short-`TMPDIR`-symlink/external-scratch mechanism -- why each
took the shape it did, what authenticated live qualification has and has not
observed, and the current, precise status of WFC's own (separate)
`execution_boundary.py` primitive. It is not a competing architecture
proposal: the accepted design remains
link:../../../warm_storage/concepts/workflow_coordinator_claude_code_adapter_design_2026-11-01.adoc[the
Claude Code adapter design] and its reviews. The controlling defect/feature-
status records are
link:../../../backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc[the
write-permission BUG] (open; see §7) and
link:../../../backlog/BUG-WFC-CLAUDE-ADAPTER-SHORT-TMPDIR-RESOURCE-EXHAUSTION.adoc[the
short-`TMPDIR` BUG] (resolved by separate maintainer acceptance 2026-11-10;
see §7). This document cites and summarizes those sources, their review
trails, and the Evidence repository's `project_memory/run_ledger.adoc` for
durable Technical Model reference; it does not restate their full content,
and the Hop-by-Hop chronology of any cited Run lives in the ledger, not here.

== 2. As-implemented: how WFC invokes Claude Code noninteractively

`src/workflow_coordinator/claude_adapter.py`'s `ClaudeCliAdapter` is WFC's
only `claude_cli` execution-port implementation (selected by
`operator.py::_execution_adapter`).

`argv()` (`claude_adapter.py:137-146`) builds, as a tuple passed without a
shell: `-p --output-format json --json-schema <schema>` for structured
output, `--model`/`--effort` from the role binding, `--restricted
--safe-mode --strict-mcp-config --tools Read,Glob,Grep,Edit,Write,Bash` for
the closed tool surface, `--settings <generated-file>
--permission-mode acceptEdits --permission-prompts none
--no-session-persistence`, and the task prompt as the final positional
argument. This shape is unchanged since the write-permission correction in
§3's provenance.

`_settings(request, external_scratch_dir)` (`claude_adapter.py:148-169`)
generates a settings file with: `sandbox.enabled: true`,
`failIfUnavailable: true`, `allowUnsandboxedCommands: false`;
`filesystem.denyRead: ["~/"]`, `filesystem.allowRead` set to *two* entries --
the resolved repository path and the resolved per-invocation external scratch
directory (§5) -- and, new since the short-`TMPDIR` correction,
`filesystem.allowWrite` set to that same single scratch directory;
`network.allowedDomains: []`; and `permissions.allow: ["Edit", "Write"]`,
`deny: ["WebFetch", "WebSearch"]`, `blockReadsOutsideWorkingDirectories: true`.
The settings schema's `allowWrite` field, absent in every prior revision of
this adapter, exists today *only* to grant that one resolved scratch path; it
is not a general write-scope mechanism, and no other grant populates it.

`execute()` (`claude_adapter.py:208-285`) derives the short symlink path and
the real external scratch directory (§5), writes the schema and settings
files, builds the child environment from an explicit allowlist (§3) with the
`TMPDIR`/`TMP`/`TEMP` triplet set to the short symlink path, and launches the
subprocess with `cwd=request.repository.resolve()` (`:251`) -- the same
resolved path used as the sandbox's first `allowRead` entry, so there is a
single source of truth for "the repository" rather than two independently
maintained paths.

== 3. Child-process environment: explicit allowlist

The child environment is built as an explicit, minimal allowlist
(`claude_adapter.py:239-244`): only `PATH`, `HOME`, `USER`, `LANG`
(`_ENVIRONMENT_NAMES`, `:33`), plus whatever operator-configured
`extra_environment_names` the adapter was constructed with, are copied from
the orchestrating process's own environment -- each only if actually present
-- and the `TMPDIR`/`TMP`/`TEMP` triplet is then set unconditionally to the
per-invocation short symlink path. No other variable reaches the child by any
path. `__post_init__` (`:124-135`) validates `extra_environment_names`
eagerly: a name must be a bare `[A-Za-z_][A-Za-z0-9_]*` identifier, must not
start with `CLAUDE_CODE_`, and must not be `TMPDIR`, `TMP`, or `TEMP` --
construction itself raises `ValueError` otherwise. The operator-facing
extension point is `WFC_CLAUDE_EXTRA_ENV_NAMES`, a comma-separated list of
*names* read once at construction (`_extra_environment_names()`, `:36-39`);
it can only ever widen which already-ambient variable *names* are copied, by
value, at launch time -- never raw `key=value` pairs, never a scope grant.

This replaces an earlier mechanism, now fully superseded in production code:
through `WI-WFC-CLAUDE-ADAPTER-WRITE-PERMISSIONS-004`, the child environment
was `{**os.environ, "CLAUDE_CODE_SUBPROCESS_ENV_SCRUB": "1"}` -- a full copy
of the orchestrating process's own environment, plus a variable that made the
installed CLI apply its own all-subprocess scrubbing. Setting that variable
had a documented side effect: the CLI itself reported, in both the original
diagnosis and the §8.1 live qualification, that `--permission-mode
acceptEdits` is overridden back to the CLI's default permission mode whenever
scrubbing is active. Under default mode, `--permission-prompts none` denies,
rather than asks approval for, any tool call that would otherwise prompt. The
first write-permission correction candidate added only
`permissions.allow: ["Edit"]`; independent broad review
(`5d46d67fe938ec127e4abf6ec1086aabed1530dc`) found, by reading the installed
CLI's own embedded source, that `Edit` and `Write` are parsed and matched as
distinct tool names with no family relationship, so a bare `Edit` rule never
covered `Write`. The correction (`4eb69d9c038110f9885c05612927535c725a21e6`)
widened the rule to `["Edit", "Write"]` -- which is why both names are still
listed explicitly today, independent of the scrubbing mechanism that
originally made the gap visible. This tool-name-matching behavior is
implementation-specific to the installed Claude Code CLI (`2.1.270`'s own
embedded source), not a documented public contract.

`WI-WFC-CLAUDE-ADAPTER-ENVIRONMENT-ALLOWLIST-001`
(`464aefe3d3438bc66b110725de68def316238ffa`) then replaced the
`{**os.environ, ...}` construction with today's explicit allowlist, and
stopped setting `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` at all, in any form --
removing both the scrub-induced permission-mode override and the
full-environment copy in the same change. One consequence, confirmed by
`__post_init__`'s own validation rather than merely by convention: a
`CLAUDE_CODE_*`-prefixed variable from the orchestrating process's own
environment (for example `CLAUDE_CODE_SESSION_ID`, relevant to a nested
dispatch; see §8.1) can no longer reach the child by any path, including
through the extra-names extension point, which rejects any such name outright
at construction time. §9 records this as resolving, structurally, an open
question §8's live qualification had raised against the pre-allowlist
mechanism.
link:../../../warm_storage/concepts/workflow_coordinator_claude_adapter_environment_allowlist_2026-11-07_broad_review.adoc[Broad
review] and
link:../../../warm_storage/concepts/workflow_coordinator_claude_adapter_environment_allowlist_2026-11-07_focused_review.adoc[focused
review] record the implementation review trail; see §7 for this WorkItem's
own acceptance disposition, which differs from an ordinary completed Run.

== 4. Repository boundary, `--restricted`, sandbox settings, and Bash

`--restricted` confines the file tools (`Edit`/`Write`/`Read`-family) to
the working directory and removes code-running tools unless `--tools`
names them explicitly; `_TOOLS` (`claude_adapter.py:32`) names `Bash`
alongside the file tools, so Bash remains available to the worker -- this
is not a general Bash grant layered on top of the closed profile, it is the
accepted design's own minimum built-in surface (see the design document,
link:../../../warm_storage/concepts/workflow_coordinator_claude_code_adapter_design_2026-11-01.adoc[§
"Permissions and filesystem"]). The adapter never widens this: no
`--add-dir`, no `excludedCommands`, no `--dangerously-skip-permissions` or
`bypassPermissions` mode, no second working directory outside the
single, narrowly-scoped scratch grant §5 describes.

`Edit`/`Write` confinement to the repository root rests on `--restricted`'s
own working-directory confinement plus the explicit `permissions.allow`
rule; the settings-level `filesystem.allowWrite` field exists only for the
one external scratch path (§5), never as a general write-scope list for the
repository itself. This absence of a repository-scoped `allowWrite` was
recorded as an open, unexcluded alternative hypothesis throughout the
original write-permission bug record and every review Hop in that lineage;
§8.1 records what the live qualification established about it, and that
finding is unaffected by the later scratch-specific grant, which names a
disjoint path.

The accepted design already distinguishes Bash's own sandbox coverage from
file-tool confinement rather than treating them as one uniform boundary:
"Claude documents that its Bash sandbox covers shell commands and their
children, while file tools, hooks, MCP, and other processes can run outside
it" (design document, same section). `sandbox.enabled`/`failIfUnavailable`
require Claude's own Bash sandbox and forbid an unsandboxed retry;
`allowUnsandboxedCommands: false` removes the fallback path. §8.1 records a
live observation consistent with that distinction.

== 5. Short-`TMPDIR` symlink and external scratch provisioning

This section documents the mechanism
link:../../../backlog/BUG-WFC-CLAUDE-ADAPTER-SHORT-TMPDIR-RESOURCE-EXHAUSTION.adoc[the
controlling BUG record] commissioned and `WI-WFC-CLAUDE-ADAPTER-TMPDIR-SCRATCH-PROVISIONING-001`
implemented, as actually coded in `claude_adapter.py` today -- not only the
design intent that motivated it.

=== 5.1 Why Claude Code needs a short socket path

Claude Code derives its own per-session IPC directory from `TMPDIR` (keyed
by uid, the launch cwd with `/` replaced by `-`, and a session UUID) and
binds `AF_UNIX` sockets inside it for the Bash tool's sandbox bridge.
`AF_UNIX` socket paths are capped at 108 bytes (`sockaddr_un.sun_path`); a
long, human-readable, Attempt-scoped `TMPDIR` -- exactly what WFC's own
launch already exports for other purposes -- reliably pushes the derived
path past that kernel limit, failing the sandbox bridge even for a trivial
command. `_SHORT_TMP_ROOT = Path("/tmp")` (`:49`) exists to give the
subprocess a short, invocation-scoped `TMPDIR` instead of inheriting the long
one.

=== 5.2 Why an entirely `/tmp`-rooted scratch is separately problematic

A short *path* for socket purposes and a large-capacity, Attempt-isolated
*filesystem* for bulk material are two different needs that a naive fix can
conflate onto one `TMPDIR` value. Placing all of a Hop's scratch material --
including whatever an agent's own exploratory test runs materialize -- under
the short root risks exhausting the host's (often `tmpfs`-backed, inode- or
byte-limited) `/tmp`, which is exactly the resource-exhaustion incident
(1,048,576/1,048,576 inodes) the controlling BUG record discovered. The
short root therefore needs to remain genuinely short, in bytes, without
becoming the actual destination for bulk content.

=== 5.3 The mechanism: short symlink, real scratch directory

`execute()` resolves two distinct paths per invocation before launch
(`:221-230`):

* `_short_subprocess_tmp_dir()` (`:178-182`) -- `_SHORT_TMP_ROOT /
  "wfc-claude-<token>"`, the short path the subprocess will see as `TMPDIR`.
* `_external_scratch_dir()` (`:184-188`) -- `_external_scratch_root() /
  "wfc-claude-<token>"` (§5.4), the real, large-capacity directory that path
  actually points at.

`<token>` is `_invocation_token()` (`:171-176`), the first 16 hex characters
of `sha256(run_id/hop_id/invocation_id)` -- deterministic per invocation, so
two concurrent invocations (distinct run/Hop/invocation identity) can never
derive the same pair of paths. `execute()` creates the real directory first
(`real_dir.mkdir(parents=True, mode=0o700)` then an explicit
`real_dir.chmod(0o700)`, `:227-228`), resolves it, and only then symlinks the
short path onto it (`tmp_dir.symlink_to(real_dir, target_is_directory=True)`,
`:230`) -- so the short path is never anything but a symlink to an
already-existing, correctly-permissioned real target.

=== 5.4 Choosing the real scratch root, and the collision fallback

`_external_scratch_root()` (`:61-77`) takes the first non-empty ambient
`TMPDIR`, `TMP`, or `TEMP` -- the same large-capacity, Attempt-isolated
scratch WFC's own launch already exports ahead of this adapter shortening it
for the subprocess (FD-08's own Harness-level relocation; `scripts/wfc_op.py`'s
`create_attempt_scratch()`/`_scratch_environment()`) -- or, absent all three,
`tempfile.gettempdir()`. If that resolved root equals `_SHORT_TMP_ROOT`
itself -- the stock Ubuntu/WSL default with none of those variables set, or
an operator explicitly setting `TMPDIR=/tmp` -- the adapter does *not* use
it: it falls back to `_WFC_FALLBACK_SCRATCH_ROOT`, `Path.home() /
".wfc-claude-scratch"` (`:58`), an unprivileged, WFC-owned default mirroring
`create_attempt_scratch()`'s own unprivileged `~/wfc-scratch` convention.
This guard exists because, unguarded, the degenerate case would make the
short symlink and its own real target the same path -- the exact finding
(`F001`) an independent broad review raised against the first implementation
candidate (`3102b65`), and which the correction (`48bb0c4`) closed. No branch
of this function requires a privileged host action; it works, as the
ordinary case, on a stock host with no WFC launcher present, degrading to
the unprivileged home-rooted fallback rather than silently placing bulk
material back on the `tmpfs` this mechanism exists to protect.

=== 5.5 `TMPDIR`/`TMP`/`TEMP` and the paths actually used

All three variables are always set identically, to the short symlink path
(`environment.update(TMPDIR=str(tmp_dir), TMP=str(tmp_dir),
TEMP=str(tmp_dir))`, `:244`) -- never to the real scratch directory
directly, and never inherited from the orchestrating process's own ambient
values (§3). A process that only consults `$TMPDIR` (or `TMP`/`TEMP`) sees a
short path; the kernel transparently follows the symlink at `bind()` time
for `AF_UNIX`, which does not canonicalize the path first, so the 108-byte
limit is evaluated against the short string, not the real target's (longer)
resolved path. This was live-qualified directly against the real,
unmodified adapter before implementation (see §8.1 and the controlling BUG
record's own 2026-11-07/08 follow-ups).

=== 5.6 Sandbox grant scoped to the real resolved target

`_settings()` (§2) names the real, resolved external scratch directory --
never the symlink, never an ancestor, never WFC's own whole Attempt scratch
root -- in both `filesystem.allowRead` (appended after the repository) and
as the sole `filesystem.allowWrite` entry. `denyRead: ["~/"]`,
`blockReadsOutsideWorkingDirectories: true`, `network.allowedDomains: []`,
and the `permissions.allow`/`deny` rules are all unchanged by this
mechanism. The grant is per-invocation: a fresh token, and therefore a fresh
pair of paths and a fresh grant, is derived every time `execute()` runs.

=== 5.7 Lifecycle and cleanup

Before creating either path, `_supersede_or_reject_leftover()` (`:80-93`) is
called for both the real directory and the short symlink (`:223-224`): it
`lstat()`s the candidate path, and if something already exists there, clears
it only when owned by the current effective uid (a directory via `rmtree`,
anything else via `unlink`) -- raising `ClaudeCliError` and leaving the
leftover untouched otherwise. This makes a repeated dispatch of the *same*
invocation identity (for example after an unclean prior shutdown)
deterministic without ever adopting or silently reusing a path this process
did not itself create.

On every exit path -- success, a local launch failure wrapped into
`ClaudeCliError`, or a timeout (including the `SIGTERM`-then-`SIGKILL`
escalation, `:260-267`) -- the `finally` block (`:268-276`) calls
`_remove_scratch_path()` (`:96-107`) independently for the symlink and the
real directory. That helper dispatches on `is_symlink()` (so a symlink is
`unlink()`ed rather than handed to `rmtree`, which silently no-ops on a
symlink) and swallows `OSError`, so a failure removing one target can never
suppress the other removal or mask an exception already in flight from the
`try` block above. Neither the short symlink nor the real scratch directory
is expected to survive past the invocation that created it.

=== 5.8 Error handling and known limits

A failure creating the real directory, or a `FileExistsError` from
`symlink_to()` (for example a sticky-`/tmp` third party racing the same
short, predictable `wfc-claude-<token>` name between supersession and
creation), is wrapped into `ClaudeCliError`
(`:255-256`) rather than escaping as a raw `OSError`; the worst case for a
same-user leftover is deterministic supersession, and for a different-uid or
raced leftover is a clear, named-path denial of that one invocation, not
privilege escalation or silent misdirection. Independent review of the
accepted correction (`48bb0c4`) recorded several residual, explicitly
non-blocking observations that remain accurate limits today, not
blocking defects: `tempfile.gettempdir()` could in principle still resolve
to the current working directory (the repository checkout) if `/tmp`,
`/var/tmp`, and `/usr/tmp` were all unwritable -- judged non-blocking because
ordinary WFC dispatch always exports `TMPDIR` and the targeted host classes
(Ubuntu/WSL, typical corporate hosts) have a writable `/tmp`; the fallback
root's own *parent* directory (`~`) is created with the ambient umask, not an
explicit `0o700`, unlike the scratch directory itself; and an ambient
`TMPDIR` that is itself a subdirectory *under* `/tmp` (rather than `/tmp`
exactly) satisfies the coincidence guard while still placing bulk material on
that `tmpfs` -- inherent to trusting WFC's own exported convention, not a
defect this mechanism was scoped to close.

== 6. Division of protections: provider-owned vs. WFC-owned

Three layers, kept distinct per `docs/self-development.adoc`'s
Commission-authoring section and `docs/architecture.md`'s generalized
containment disclaimer (both from `36089fb`):

. *Provider file-tool permission* -- the explicit `Edit`/`Write` allow
  rule (§3, §4). Provider-owned, not Coordinator-verified (`DEC-WFC-009`).
. *Provider execution isolation* -- the CLI's own sandbox (`--restricted`,
  the generated `sandbox.*` settings including the scratch-scoped
  `allowWrite` of §5.6, and whatever temp/scratch exceptions the CLI's own
  sandbox profile grants by design; §8.1 records a live instance of the
  latter). Also provider-owned, not Coordinator-verified.
. *WFC's trusted post-Hop Git/scope observation* -- Coordinator-owned and
  authoritative. This is what actually determines whether a candidate
  mutation becomes an accepted WFC commit, independent of what the
  provider's own permission or sandbox layer did or did not prevent, and it
  is WFC's own primary, actually-enforced protection goal: controlled,
  reviewed acceptance of repository mutations -- not a general host- or
  OS-level isolation guarantee.

No provider permission or sandbox setting described in this document is an
OS-level isolation guarantee WFC has verified. Per `docs/architecture.md`
(`36089fb`): "WFC V1 provides neither hostile-code containment nor host
isolation; restricting agent writes is primarily an operational safeguard
against accidental damage, not a security perimeter." The Claude adapter's
closed profile is, in that same sense, "a transitional operational
safeguard -- useful, not discarded without reason, but provider-owned and
not Coordinator-verified."

=== 6.1 Status of WFC's own execution boundary (`execution_boundary.py`)

A separate, WFC-owned primitive exists, independent of the Claude adapter
described above: `src/workflow_coordinator/execution_boundary.py`, an opt-in
Linux filesystem/namespace boundary built on `bwrap` (bubblewrap). It is
*implemented and tested* -- `validate()`/`build_argv()`/`run()` construct and
exercise a real `bwrap` invocation with a read-only `/usr`/`/bin`/`/sbin`/
`/lib`/`/lib64` view, a protected, remounted-read-only `.git`, a private
`/tmp` scratch, and one explicitly validated, caller-designated external
scratch bind-mount at a fixed destination (`EXTERNAL_SCRATCH_DESTINATION =
/tmp/s`) -- not a proposal or a future idea. Its own test suite
(`tests/integration/test_execution_boundary_bwrap.py`,
`tests/unit/test_execution_boundary_config.py`,
`tests/integration/test_nested_claude_bwrap_qualification.py`) is 26 tests,
all passing as of `6c88e47`, including real host-filesystem-verified `bwrap`
subprocess behavior (not argv inspection alone) and a confirmed, syscall-level
`AF_UNIX` bind succeeding through the external scratch mount (§7's
provenance table; corrected 2026-11-10 in `e495b04` after an unaccepted,
never-independently-reviewed qualification Hop had asserted the opposite).

This primitive is, as of this writing, *not* wired into the regular provider
dispatch path: `claude_adapter.py` and `codex_adapter.py` do not construct or
invoke it, and `operator.py` does not route any Hop's execution through it.
Its own authorizing record,
link:../../../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[FTR-WFC-EXECUTION-TRUST-BOUNDARIES],
explicitly scopes each of its narrow 2026-11-06/2026-11-08 implementation
slices to the primitive itself, repeatedly stating that none of them
authorizes wiring the module, or the external scratch mount, into
`claude_adapter.py`, `codex_adapter.py`, or `operator.py` -- the broader
provider-integration question (which the 2026-11-08 nested-Claude-in-bubblewrap
qualification investigation probed, finding an unresolved `/proc` precondition
for a second, nested `bwrap` layer) remains separately deferred. So: the
primitive is real, tested, and available; its integration into live Hop
dispatch is a distinct, not-yet-authorized step. WFC's layer-3 post-Hop
Git/scope observation (above) remains the actually-enforced protection for
every Hop dispatched today, regardless of `execution_boundary.py`'s own
readiness.

Whatever VM or host boundary currently limits the operational blast radius
of running any of this is independent of, and does not by itself establish,
repository-root isolation *inside* that VM; for a Hop dispatched through the
Claude adapter today, Claude's own sandbox (§4, §5.6) is the only mechanism
attempting the latter, and §8.1 records a live data point about where that
mechanism's boundary actually sits for one tool (Bash) under one observed
condition (a nested invocation).

== 9. Residual security-model distinctions and deferred work

The three-layer split in §6 holds with §8.1's observation folded in under
layer 2 (provider execution isolation): a session-scoped scratchpad write is
provider sandbox behavior, not a WFC-verified control, and it does not
change what layer 3 (WFC's own post-Hop Git/scope observation) actually
enforces for acceptance into a trusted commit.

The specific mechanism §8.1 flagged -- inherited `CLAUDE_CODE_*` session
variables reaching a nested child -- is resolved as of `464aefe` (§3):
`__post_init__`'s validation makes it structurally impossible for any
`CLAUDE_CODE_*`-prefixed name to reach the child environment, through the
fixed allowlist or through the operator extension point, regardless of what
the orchestrating process's own environment contains. This closes the
specific propagation path; it is not a claim that Claude's own scratchpad
exception (if it still applies under the current allowlist) has been
re-examined, nor a general statement about nested-session isolation beyond
that one variable family.

Provider-specific sandbox behavior -- Claude's own `bwrap`/scratchpad
mechanics -- remains something WFC has not verified and should not become a
foundational WFC security assumption. §6.1 records `execution_boundary.py`'s
actual, current status precisely: implemented, tested, and available as a
primitive, but not wired into any provider-dispatch path today, and the
broader provider-integration and execution-trust-boundary architecture
remains deferred under
link:../../../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[FTR-WFC-EXECUTION-TRUST-BOUNDARIES]'s
own standing authorization scope.

Finally: §8.1 does not establish that Claude's sandbox is broken. The
observed Bash behavior there is consistent with a documented product
feature (a session-scoped scratchpad write allowance) evaluated against a
stricter-than-documented WFC objective (repository-root-only containment),
not with an absent or defective isolation mechanism.
