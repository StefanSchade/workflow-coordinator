=== R2-001 -- The asserted reference-repository identity is factually wrong

Invariant:: Focused Invariant A -- repository naming must make the design
understandable outside this maintainer's exact filesystem layout.

Disposition:: *BLOCKING.*

The new NOTE (design lines 23--35) states: "That repository's own name is
Spreadsheet Memory", and "`spreadsheet-handling` names the broader
multi-repository activity/workspace, not the reference repository itself."

Repository evidence contradicts both claims.  In the reference checkout
`/home/stefan/repos/spreadsheet-handling/core`:

* `git remote -v` resolves `origin` to
  `git@github.com:StefanSchade/spreadsheet-handling.git`;
* `pyproject.toml` declares `name = "spreadsheet-handling"`;
* `README.md` titles the project "Spreadsheet Handling", and its install
  instruction is `pip install spreadsheet-handling`.

A case-insensitive search for `spreadsheet.memory` across the reference
repository's `*.adoc`, `*.md`, `*.toml`, `*.json`, and `*.cfg` files returns no
match, and the same search across this repository returns no match outside the
design under review.  No directory matching `*memor*` exists at depth two under
`/home/stefan/repos`.  The portable identity "spreadsheet-memory" therefore does
not exist in evidence; the reference repository's portable identity *is*
`spreadsheet-handling`, which is also -- coincidentally and confusingly -- the
name of the local parent workspace directory that holds many unrelated
checkouts.

This repository's own established convention for naming that reference is
`core`, not "Spreadsheet Memory".  `project_memory/README.adoc` line 8 models
this memory on "`spreadsheet-handling/core`'s `project_memory`", and line 21
documents a `core:`/`wfc:` `commit_refs` prefix that "disambiguates which
repository a referenced commit belongs to".  Canonical
`concern_events.json` uses that live convention in three events
(`SIG-ACT-WFC-CONCEPTION`, `SIG-ACT-WFC-FIRST-CONSUMER-RUN`,
`SIG-ACT-WFC-RELKEY-S3B-CONVERGENCE`) across ten `core:` commit references.
The NOTE's claim that "core" is merely "a local checkout/directory name in this
development environment, not that repository's portable identity" therefore
also reads as deprecating a documented and in-use canonical Project Memory
repository disambiguator.

Risk:: Concrete and migration-relevant, not cosmetic.  §1's scope boundary now
reads "or change Spreadsheet Memory, Project Memory, Runtime, governance"
(design line 19).  A future Run B cannot resolve "Spreadsheet Memory" to any
real repository, and the NOTE additionally instructs that reader that
`spreadsheet-handling` is *not* the reference repository -- so the one true
identifier is explicitly ruled out.  A reader following the design would
mis-identify the very repository the boundary exists to protect, and the §2
comparison citations ("Spreadsheet Memory's `docs/ai_info/_ai_info.adoc`",
`docs/backlog/_ftrs_open.adoc`) become unlocatable by repository identity even
though both files genuinely exist in that checkout.  The correction thus fails
its own stated purpose: it does separate checkout path from identity, but
assigns the wrong identity, leaving the record *less* portable than the
"Core" shorthand it replaced.

For the record, the prompt's question of whether the slug `spreadsheet-memory`
should additionally be stated explicitly is answered *no*: stating it would
harden the error rather than remove ambiguity.

Smallest sufficient correction:: Replace the identity assertion in the NOTE with
the evidenced identity, and keep the genuinely useful path/identity separation
the correction introduced.  One sufficient form:

* the reference repository's portable identity is `spreadsheet-handling`
  (GitHub `StefanSchade/spreadsheet-handling`, distributed as
  `spreadsheet-handling`), display name "Spreadsheet Handling";
* `/home/stefan/repos/spreadsheet-handling/core` is its current local checkout
  path in the maintainer's environment, where the parent directory name
  coincides with the repository name without denoting it, and `core` is the
  local checkout directory name;
* `core` additionally remains this repository's canonical Project Memory
  `commit_refs` prefix for that repository per `project_memory/README.adoc`,
  and that convention is unchanged by this design.

The context-sensitive body renames may then either revert to the previously
unambiguous "Core" shorthand, now that the NOTE defines it, or use the
evidenced name; either resolves the finding, and no further cosmetic renaming
is required.

No regression was found in the rename's mechanical execution: all ten semantic
"Core" occurrences in the baseline became "Spreadsheet Memory", while
`docs/imported/core-incubator/**` (design lines 396 and 552),
`FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc` (line 434), the
literal checkout path, and all other identifiers and artifact names are intact.
The defect is the asserted identity itself, not the edit's blast radius.

=== R2-002 -- The terminal lifecycle move is timed after independent acceptance

Invariant:: Focused Invariant C -- no completed migration plan remains active
warm sediment, and simultaneously no repository mutation required by the
migration occurs outside the independently reviewed/accepted Run-B candidate
unless an existing explicit maintainer-owned mechanism authorizes it.

Disposition:: *BLOCKING.*

The semantic goal is correct and should be retained.  The defect is mechanical
timing and attribution.  The new §6.1 paragraph (design lines 508--525) states:
"Once Run B is independently accepted -- implemented, validated, and reviewed
-- ... At that point a current pointer must move this design itself from
`docs/warm_storage/concepts/` to `docs/cold_storage/concepts/history/`".  §8
repeats the same trigger: "Once Run B is independently accepted, this
acceptance boundary itself expires".

Three concrete problems follow.

*No actor or authority.* "A current pointer must move this design itself"
names no agent; a pointer cannot relocate a file.  No Run-B phase, hop, or
maintainer step is assigned the action, so a future Run B cannot determine
whether the move is inside or outside its own scope.

*The trigger is unsatisfiable inside the reviewed candidate.* Because the
condition is Run B's own independent acceptance, Run B cannot perform the move
within the candidate that gets accepted.  The reviewer therefore accepts a
topology in which the completed migration plan is still warm, and the final
topology is reached only by a later, unreviewed mutation.  This contrasts with
the adjacent, sound construction two paragraphs earlier, which moves "this
design's review record *after* this Run accepts the design" -- there the
condition is already satisfied when Run B executes, so the move sits inside
Run B's candidate.

*It contradicts the same section's retention instruction.* §6.1's warm-concepts
list expressly directs Run B to "Retain in `docs/warm_storage/concepts/` the
unresolved/current direction records: ... and this consolidation design", and §7
validation requires "each live warm item has a current discovery path".  Run B's
accepted candidate must therefore keep this design warm *and* linked from current
navigation, while the new paragraph declares that at the instant of that same
acceptance the design must already be cold and that "no current document may
continue presenting this migration plan as active direction after that
acceptance".  The accepted candidate is non-compliant with the design's own
anti-sediment requirement at the moment it is accepted.

Risk:: Either the move never happens -- leaving exactly the permanent warm
sediment this correction was written to prevent -- or it happens as an
unreviewed post-acceptance commit.  The second outcome is materially broader
than a bare disposition record: because §7 requires a current discovery path
for every live warm item, relocating this design also requires editing the
current navigation surfaces that link it (the new `docs/ai_info/_ai_info.adoc`
route and the active manifest) so the link becomes labelled provenance.  Those
are content changes to current navigation documents that the independent
reviewer validated, performed after validation.

On the question of whether an existing mechanism already authorizes this:
`docs/self-development.adoc` does establish that "Review and lifecycle-closure
commits may legitimately exist on Development/`main` after the accepted
implementation commit.  That is expected shape, not drift", and that such
commits "record acceptance and disposition".  A maintainer-owned closure commit
is therefore a real candidate authority.  But the design neither invokes that
mechanism nor names the maintainer as the actor, and the required inbound-link
rewrites exceed the "records acceptance and disposition" shape that passage
describes.  The existing mechanism does not, as the wording stands, make the
current text correct.  §4's own supersession rule also points the other way:
it moves a predecessor to cold storage when "the replacement declares
supersession", and the replacement here -- the migrated topology -- exists at
the end of Run B's migration, inside the candidate.

Smallest sufficient correction:: Flip the trigger from Run B's acceptance to Run
B's migration completion, so the terminal move is Run B's own final migration
step and the reviewer accepts the actual final topology. Specifically:

* condition the move on the migration being complete and validated, not on its
  acceptance, and assign it to Run B explicitly as its last ordered step;
* remove this design from §6.1's warm-retention list, or qualify that entry as
  "warm until Run B's terminal step relocates it", so the retention instruction
  and the lifecycle rule agree;
* state that after the move the plan remains the controlling migration plan for
  any Run-B correction or rereview hop at its cold path, loaded from Run B's
  Commission as the current pointer, so a correction cycle keeps it
  discoverable and usable;
* keep §8's expiry statement, retriggered on the same completion condition.

Alternatively, if the maintainer prefers the move to remain post-acceptance,
the sufficient correction is to attribute it explicitly to the maintainer-owned
lifecycle-closure commit of `docs/self-development.adoc` and to state that the
accompanying inbound-link relabelling is part of that closure commit.  Either
form resolves `R2-002`; the first is smaller and keeps the whole mutation inside
the independently reviewed candidate.

`project_memory/README.adoc` documents `make memory-roundtrip-check` as the

requirement that every remapped `source_path` resolve to its intended migrated

additional ceremony.

The ordered-execution amendment -- applying the §6.2 exception immediately after
each move rather than deferring it -- is a sound sequencing choice and raises no
finding.
