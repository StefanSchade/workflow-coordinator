== 4. The actual Hop algorithm

Reconstructed from production source (`vertical.py::run_one_hop` and
`reducer.py::reduce_result`), not from task prose or expectation. The
load-bearing ordering is:

[source,text]
----
semantic result
    -> CommitIntent admission
    -> Coordinator-owned trusted commit
    -> trusted evidence
    -> route application
----

Numbered flow, sufficient to make the later diagnosis legible:

. *Phase and result-contract selection.* The selector reads only declarative
  facts -- phase role, whether a `review` descriptor exists, its
  `finding_authority`, `convergence_role`, and the profile/Run schema versions.
  A convergence phase maps to the generic contract; a `worker` phase with
  `review: null` maps to `WORK_RESULT`; an `independent_reviewer` phase with a
  review descriptor maps to `REVIEW_VERDICT`.
. *Git preflight* (repository identity and expected HEAD). Failure means the
  invocation never starts and no Hop budget is charged.
. *Prompt construction*, carrying the selected contract kind/version, the
  family-specific vocabulary (`status=completed|blocked` for a worker,
  `verdict=accept|changes_required` for a review gate), and the phase's
  required evidence *names*.
. *Provider/agent invocation.*
. *Structured-result validation* -- envelope field set, schema version,
  dispatch correlation, then the family-specific strict parser. Field
  validation is strict in both directions: unknown fields and missing fields
  are both rejected. A validation failure is recovered as an uncertain
  dispatch, never replayed.
. *CommitIntent admission, before Git is touched.* A non-null CommitIntent is
  permitted only when the result outcome is `completed` (or a gate's
  `changes_required` review-artifact commit), *and* scope is unchanged, *and*
  `requires_human` is false, *and* `escalation` is null -- and only when the
  phase grants both the `edit` and `commit` workflow effects.
. *Coordinator-owned trusted commit*, only if admitted. The agent never runs a
  Git command; `CommitIntent` is a proposal to trusted Coordinator handling,
  never proof that a commit occurred.
. *Delta observation* if no commit was made, then post-acceptance anomaly
  detection (commit-subject identity, required durable artifacts).
. *Trusted evidence execution* -- the phase's required evidence commands are
  prepared and executed by the Coordinator *here*, after the result and after
  any commit.
. *Post-evidence repository re-observation* (HEAD drift, worktree
  cleanliness), contributing repository anomalies.
. *Evidence classification* into `pass`, clean `fail`, and `error`/`not_run`.
. *Budget charge* and Hop recording.
. *Route reduction*, then checkpoint persistence.

Inside reduction, mechanical preemption strictly precedes all route, Finding,
and scope authority. A correlated semantic stop is captured as *observation
only* and cannot hide a controlling mechanical fact. Evidence disposition is
then resolved as follows:

`pass`:: permits ordinary reduction of the requested route.

clean `fail`:: a trusted negative observation. If -- and only if -- the current
phase is a *gate* review declaring a `failed_evidence_route` that names an
existing `goto` route, that route *replaces* the agent's requested route.
Otherwise the Run stops `awaiting_human` with
`required_evidence_failed_without_route`.

`error` / `not_run`:: a hard mechanical stop, preempting even the semantic
result.

Three durable insights follow, and are the reason the later diagnosis holds:

* *Trusted evidence runs AFTER the candidate result and after the trusted
  commit.* An agent therefore cannot have proven it at result time; the fact
  does not yet exist when the result is authored.
* *Trusted evidence may override the agent's requested route* -- including
  overriding a reviewer's `accept`. The audit confirmed this against existing
  production tests, in which a gate requests `accept`, evidence fails, and the
  applied route is the declared correction route.
* *Agent self-tests are never trusted evidence.* They are agent-attributed
  diagnostics only.


== 5. Worker completion is not acceptance

Worker `status: completed` means approximately:

[source,text]
----
my bounded work/candidate for this phase is ready, and I request this
declared route
----

It does *not* mean:

[source,text]
----
I have already proven that every Coordinator-required acceptance criterion,
including all downstream trusted evidence, is satisfied
----

The second reading is not merely undesirable; it is unsatisfiable. Required
evidence executes after the result is parsed (section 4), so no agent can
truthfully assert its outcome at authoring time. Worse, `completed` is itself
the *precondition* for the candidate to be published at all: a worker that
downgrades to `blocked` in order to be "honest" about a red downstream gate
destroys its own trusted-commit path and leaves its work uncommitted.

Five concepts must be kept separate:

[cols="1,1,3",options="header"]
|===
|Concept |Owner |Meaning

|Worker completion
|agent (semantic)
|Bounded work ready; declared route requested. Gates CommitIntent admission.

|Trusted commit
|Coordinator
|One bounded local commit materialized from an admitted CommitIntent.
Publication, not acceptance.

|Trusted evidence
|Coordinator
|Independent post-commit mechanical observation: `pass`, clean `fail`, or
`error`.

|Review acceptance
|gate phase (semantic)
|`verdict: accept` from a phase with sufficient Finding disposition authority.

|Run completion
|reducer
|A `complete`-effect route actually applied, with no open blocking Finding and
required evidence not failing.
|===

All five must align for a Run to complete. *No single one implies any other.*

Conflating worker completion with trusted acceptance was a decisive
commissioning mistake in this lineage (finding `P2-STAG-03`), and it is the
direct cause of the current Run's stop shape (section 8).


== 6. Root causes, ranked

Primary causes -- these three jointly and sufficiently explain the stagnation:

. *Required full-suite evidence placed on the worker phases.* Both
  `integration` and `correction` select the full-repository `pytest` command as
  Coordinator-required evidence. The only mechanism able to absorb a clean
  evidence failure, `failed_evidence_route`, lives on the review descriptor and
  is validated as *gate-only*; a `worker` phase with `review: null` therefore
  *structurally cannot* declare one. Every worker Hop was consequently an
  accidental one-shot acceptance gate, and any red suite at a worker Hop could
  only terminate the Run. This alone accounts for both predecessor Runs.
  (`P2-STAG-01`)

. *The review gates omit `failed_evidence_route` as well.* Verified
  programmatically: no phase in the current profile declares one. So even once
  a reviewer Hop were reached, a red suite would terminate the Run rather than
  route to `correction`. The profile *advertises* a convergence topology it
  cannot *exercise* from an evidence failure. (`P2-STAG-02`)

. *Agent-facing "definition of done" prose.* The Commission told the worker
  that the complete `python -m pytest -q` command is its acceptance boundary,
  that it should run that exact command itself before reporting `completed`,
  that a narrower check is insufficient, and that it should escalate
  (`requires_human=true`, `escalation.kind=scope`) otherwise. This made
  full-suite success a *prerequisite* for worker `completed`, which contradicts
  the reviewed, Coordinator-owned agent operating contract -- that contract
  states agent-side tests are not Coordinator-trusted evidence and that
  inability to resolve or execute an authored evidence command in the agent
  shell "must not, by itself, cause an operational escalation." The worker
  obeyed the prose over the contract. (`P2-STAG-03`)

Secondary and non-causes -- real, but not the reason the loop never ran:

[start=4]
. *Stale pre-P2 fixtures.* Genuine migration debt: eight tests in
  `tests/unit/test_slice4b_git_authority.py` (addressed by the dirty salvage
  patch, three changed lines) plus the two `tests/unit/test_wfc_op.py` fakes
  (two changed lines, still outstanding). Five changed lines in total.
  (`P2-STAG-04`)

. *One narrow agent error.* The current worker's diagnosis of
  `tests/unit/test_wfc_op.py` as a network / build-isolation blocker is
  falsified as an explanation of the trusted repository failure (section 7).
  (`P2-STAG-05`)

. *Environment was not the cause of the trusted failure.* The nested PREPARE
  completes and builds both virtual environments; the recorded preflight seam
  is `ok`. The audit reproduced this.

. *Core limitations noted, but not P2 blockers.* Two genuine observations,
  neither blocking: `failed_evidence_route` is structurally unavailable to
  non-gate phases; and a trusted observation's retained summary is only its
  exit status, with the command's output body omitted (hashed, not retained),
  so a subsequent correction Hop learns *that* required evidence failed but not
  *which* tests failed. Neither needs to change for P2 to complete.

Primary and secondary causes must not be blurred. In particular, the fixture
debt was never large enough to explain three lost Runs; the topology was.

== 10. Recommended P2 profile shape

The audit loaded the following shape through the *current* production profile
loader and simulated its reduction against *current* production mechanics.

[source,text]
----
integration [worker]
    role: worker
    review: null
    evidence: []                      # or only truly worker-local mechanics
    routes:
      independent_review -> goto independent_review

independent_review [gate]
    role: independent_reviewer
    evidence: [pytest]
    review.failed_evidence_route: correction
    routes:
      accept     -> complete
      correction -> goto correction

correction [worker]
    role: worker
    review: null
    evidence: []
    routes:
      rereview -> goto rereview

rereview [gate]
    role: independent_reviewer
    evidence: [pytest]
    review.failed_evidence_route: correction
    routes:
      accept     -> complete
      correction -> goto correction
----

The current loader *admitted* this shape unchanged, and the simulated
reduction produced exactly the intended convergence behaviour:

[source,text]
----
worker completed  (no worker evidence)        -> independent_review   (ready)
reviewer accept   + trusted pytest fail       -> correction           (ready)
correction completed                          -> rereview             (ready)
rereview accept   + trusted pytest fail       -> correction           (ready, loops)
rereview accept   + trusted pytest pass       -> COMPLETED
----

For contrast, the same simulation against the *current* profile reproduced the
predecessor stop exactly: worker `completed` with a failing suite yielded no
route and `required_evidence_failed_without_route`.

Properties established:

* An imperfect candidate *can* be committed and handed to independent review,
  because the worker phase carries no required evidence to fail.
* It remains *impossible to complete P2 while the full suite is red*, because
  both `complete` routes sit on gates carrying the full-suite evidence.
* A reviewer's semantic `accept` is *deterministically overridden* by a clean
  trusted evidence failure, routing to `correction`.
* `rereview` can repeat the same evidence gate after correction, producing a
  genuine multi-Hop autonomous correction loop.
* Non-convergence remains bounded by the existing autonomous Hop budget, which
  terminates with the ordinary budget-exhaustion stop rather than looping
  indefinitely.
* Worker phases may still run the suite *themselves, diagnostically*;
  `phase.evidence` governs only what the *Coordinator* requires.

[IMPORTANT]
====
*NO Core change is needed for immediate P2 completion.*

The pinned P1 Runtime `9e49458de12e79dae4d8827a60f7cd39d18b4c80` already
supports the needed failed-evidence routing in both its profile validation and
its reducer. The recommended shape is therefore executable under the *currently
pinned* Runtime, with no Runtime promotion and no engine change.

Recommending this shape is not authorizing it. Adopting it requires a separate,
explicitly authorized successor Commission.
====

One caveat to carry into any such Commission: because a trusted observation
retains only its exit status, a correction Hop is told *that* required evidence
failed, together with the prior requested and applied routes, but not *which*
tests failed. It should be instructed to re-run the suite itself to localize.


== 11. Review breadth and incremental worker fixes

A conceptual concern worth settling durably: *it is legitimate for a worker or
correction Hop to correct only a bounded subset of known problems and still
hand the resulting candidate to review.*

The distinction that matters is between the *mutation surface* of the latest
Hop and the *review surface* handed to the gate. These are independent. A
worker that changed one or two fixture files still produces, and commits into,
the *complete current candidate*; the gate reviews that candidate, not merely
the latest diff.

* *The first independent P2 review should be broad.* It should inspect the
  entire accumulated P2 candidate -- the original strict result-family
  implementation plus every subsequent integration correction -- even though
  the immediately preceding worker Hop may have touched only one or two fixture
  files. Adversarial discovery belongs there, because no independent review of
  this candidate has ever executed.
* *Subsequent rereview should narrow*, to: known current-Run Findings; the
  corresponding corrections; direct regressions from those corrections; and the
  required trusted evidence. A genuinely new MATERIAL defect supported by
  concrete new material evidence may still escape that bounded surface; an
  unrelated newly noticed MINOR observation should not automatically reset
  convergence.

This is consistent with the existing manual guidance that fresh reviewer
context and broad review breadth are independent axes.

The practical consequence is that the mistaken premise behind the current
Commission's prose -- that a worker must drive the full suite green before
review is useful -- is false. Review is useful on an imperfect candidate, and
the gate's own trusted evidence is what prevents an imperfect candidate from
being *completed*.


== 12. Corrected agent-facing evidence semantics

The conceptual replacement for the mistaken "the worker must prove the full
definition of done before `completed`" framing. Recorded as recommended
conceptual wording; adopting it is a separate authorized act.

What the current wording got *right*, and should be kept: naming which trusted
evidence the Coordinator will later execute; encouraging the worker to run the
same or useful diagnostics where permitted; stating that the worker's own
checks are agent-attributed rather than trusted; and letting the worker use
test failures to improve its candidate.

What must be removed: making full-suite success a *prerequisite* for
`completed`; treating a narrower agent-side check as a failure to establish
acceptance; and directing the worker to escalate when the suite is not green.

Recommended conceptual wording:

[source,text]
----
Trusted evidence. The Coordinator independently executes
`python -m pytest -q` as required evidence ON THE REVIEW GATES. It runs
AFTER your result is validated and after any Coordinator-owned commit, and
it is the authority on acceptance. Your own test runs never are.

You are encouraged to run `python -m pytest -q` yourself to find and fix
more of the remaining integration debt within your authorized scope. Treat
its output as diagnostic input to improve your candidate, not as a gate you
must clear. If your sandbox cannot execute it, say so in `summary` and
proceed: per the agent operating contract, inability to run evidence in your
own shell is NOT grounds for escalation.

Report `status=completed` when your bounded work for this phase is coherent
and ready for review, together with a CommitIntent for exactly what you
changed. A still-red downstream suite is NOT a reason to report `completed`
falsely, NOR a reason to report `blocked`: the gate's trusted evidence will
observe it and the Coordinator will route to correction.

Reserve `status=blocked` for when THIS Hop itself needs authority, scope, or
a capability it does not have -- never for a downstream gate that is not yet
green.
----

*No Definition-of-Done schema is recommended.* The required content is prose
guidance plus correct evidence placement. Introducing a schema here would add
mechanism where authoring discipline and documentation suffice.


== 13. Commission robustness finding

Recorded separately from the immediate P2 repair, because it is a broader
authoring problem and must not be allowed to block P2.

Multiple independently authored P2 successor Commissions were syntactically
valid, accepted by the current production loaders, accepted by current
preflight, and sensible on prose inspection -- yet each configured required
evidence such that a routine negative acceptance signal terminated the entire
Run instead of using the declared correction topology.

Two verified observations frame why this recurred:

* *`failed_evidence_route` is absent from the Operator Manual.* The mechanism
  appears zero times in `docs/wfc_operator_manual.adoc` -- the artifact a
  Commission author, human or LLM, actually reads -- despite having shipped and
  being exercised by production tests.
* *Profile survey:* of the 30 self-development profile lineages in
  `governance/self-development/`, *29 declare no `failed_evidence_route` at
  all.* The single exception declares it on its first review gate but *not* on
  the later gate that actually owns `accept -> complete`, so it does not
  establish a robust general authoring convention either.

This is the same latency shape already documented elsewhere in this repository
for empty gate `finding_authority`: a convention absent across an entire
lineage, never exercised only because the triggering condition had never
occurred. P2 is simply the first lineage in which required evidence actually
went red.

=== What is, and is not, statically provable

*The current configuration is not necessarily logically invalid.* With a green
suite, the current P2 profile completes correctly; and a reviewer can still
route a semantic `changes_required` to `correction` regardless of evidence. An
author may also *intentionally* want:

[source,text]
----
semantic changes_required -> correction
evidence failure          -> human escalation
----

rather than routing evidence failure to correction. A generic preflight rule
must therefore *not* silently assume that evidence failure means correction.

The real weakness is narrower and is the finding worth persisting:

[source,text]
----
The evidence-failure disposition is IMPLICIT, and is therefore easy to omit
by accident. Omission silently converts a route-bearing phase into a
one-shot acceptance gate.
----

Observed harm from that implicitness is concrete, not imaginable: three
repeated fresh Runs, lost autonomous continuity, repeated operator
intervention, duplicate Commission authoring, useful model work made
expensive, and a first independent P2 review never reached. (`P2-STAG-06`)


== 14. Deterministic admission candidate

Recorded as a *candidate direction only*. This artifact authorizes no Core,
schema, or preflight change, and does not implement the rule below.

Preferred direction from the audit:

[source,text]
----
Required evidence on a route-bearing phase should eventually require an
EXPLICIT evidence-failure disposition.
----

Possible dispositions could include a declared `goto` correction route, or an
explicit escalation/human-stop declaration. *The key property is EXPLICITNESS,
not always routing to correction* -- the legitimate "evidence failure escalates
to a human" workflow of section 13 must remain fully expressible, merely
stated rather than defaulted into.

Why this direction is attractive:

* *Deterministic* -- decidable from already-admitted declarative facts
  (phase routes, review descriptor, declared evidence), with no Run history and
  no new workflow DSL, ontology, or model checker.
* *Visible before provider invocation* -- it fails fast, before agent cost,
  semantic work, or the creation of a doomed Run.
* *Preserves legitimate human-stop workflows* -- it narrows nothing that is
  currently expressible; it only requires the choice to be authored.
* *Makes omission difficult or impossible* rather than silently defaulted.
* Matches the project principle *structural invalidity made unrepresentable;
  stateful invalidity rejected by trusted logic.* Whether a *specific* route in
  a *specific* Run's history may legally apply remains entirely the reducer's
  stateful decision, unchanged.

Admission boundary, if it is ever pursued:

*PREPARE, implemented in the pinned Runtime's `_preflight()`* -- not the
Harness reimplementing Runtime semantics. The existing preflight already
performs trusted, mechanical, pre-Run cross-document consistency checks before
any Commission is authorized to run, and it executes before STATE creation and
before any provider invocation. The Harness must continue delegating semantic
admission to the pinned Runtime, so that Runtime-pinned replay semantics are
preserved.

A lifecycle consequence worth recording: because such a check would live in the
Runtime, it binds only Runs prepared under a Runtime containing it. Historical
configurations stay replayable; new unsafe ones are denied. *It therefore
cannot help the current P2 lineage* -- which is precisely why the documentation
fix and the profile fix must come first, and why immediate P2 completion must
not be blocked on it.

Smallest-mechanism discipline: the rule's stop condition is that it rejects
*only* the missing-declaration shape, never a declared one; never inspects Run
history; never second-guesses a reducer decision; and never grows toward
general workflow verification.


== 15. Relation to P3.5

The audit's conclusion is deliberately nuanced.

*Same broad family.* Both concern a workflow that advertises progression or
convergence while the declared capabilities or dispositions required to
actually exercise that path are absent. Both are statically knowable from the
WorkItem, WorkflowProfile, and RepositoryPolicy alone. Both belong at a trusted
preflight seam with new-launch-only enforcement.

*Not the same predicate.* P3.5 addresses a stronger reachability/authority
unsoundness: a phase can open a blocking Finding and no strictly later phase on
the forward path possesses the operation needed to dispose of it, so the graph
could never have reached a legal completion regardless of any Run's history.
The evidence-failure disposition problem is weaker: it is an *explicitness and
hazard* issue, because the workflow may still succeed perfectly well when
evidence is green.

Recommendation: *share the seam, not the rule.* Both can share:

* the trusted PREPARE / pinned-Runtime preflight seam;
* the new-launch-only lifecycle, preserving historical replayability;
* the discipline of deciding only over deterministic static facts the engine
  already admits.

Without forcing a weaker hazard predicate and a stronger unreachability proof
into one rule. Unification should not be forced where the semantics differ.
Whether this is folded into P3.5's scope or kept as an earlier independent
guardrail is a separate decision this artifact does not make.

== 17. Model quality conclusion

Assessed from concrete evidence only; neither defending nor blaming the model
generically.

*This episode does NOT show that WFC requires frontier models for basic
operation.*

Observed GPT-5.6 Terra contributions across the three Runs:

* produced coherent P2 Core work -- the strict worker/review result-family
  candidate, in which this audit found no implementation defect;
* corrected several stale integration fixtures in the first successor Run;
* corrected Slice4B correctly, minimally, and completely for its file
  (section 9);
* made *one* real diagnostic error -- the falsified `test_wfc_op`
  network/build-isolation explanation (section 7).

Strands that must be attributed elsewhere: Commission authoring, profile
topology, and trusted-evidence placement were the primary causes (section 6);
Commission prose was decisive for the current Run's stop shape; admission
weakness is a Core/documentation gap; and the environment was not a cause.

The honest reading is that *the system made ordinary model mistakes unusually
expensive.* Each Run permitted exactly one Hop before a routine negative
acceptance signal terminated it, so every ordinary mistake cost a whole Run, a
fresh Commission, and operator intervention, instead of being absorbed by the
correction loop the profile claimed to have.

The one genuine model error was itself partly induced: the Commission demanded
full-suite proof from an agent whose sandbox cannot perform the networked
install that the nested fixture requires, then pointed it at a scope
escalation. Under the same Commission, a stronger model would have faced the
same forced choice between a false `completed` and a self-defeating `blocked`.

*The honest test of model adequacy has not yet occurred*, because the first
genuine independent P2 review has never executed.
