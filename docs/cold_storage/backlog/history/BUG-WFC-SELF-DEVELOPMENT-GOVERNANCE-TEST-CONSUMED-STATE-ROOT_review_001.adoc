default -- there is no code path that seeds a new `Run`'s findings from a

referenced only as historical/advisory context in the new task file and the
WorkItem's `authority_source` field -- never as a resumable identifier, never
wired into any test fixture, WorkItem mapping, or Coordinator code path. No
governance text, fixture, or Coordinator behavior imports or resumes
Attempt-5 state.

== 4. Durable-artifact mapping -- inspected, not assumed

The WorkItem YAML maps only:

[source,yaml]
----
durable_artifacts:
  review:
    - docs/backlog/wfc_reviews/WI-WFC-DEVELOPER-ERGONOMICS-REVIEW-004/review.adoc
----

There is no `rereview` entry. I traced this against
`src/workflow_coordinator/operator.py:255-282` (`_preflight`, unmodified by
this candidate), the branch taken whenever `work_item.durable_artifacts is not
None` (true here):

[source,python]
----
for phase_key, phase_value in profile.phases.items():
    paths = durable_artifacts.get(phase_key, ())
    if phase_value.durable_artifact is DurableArtifact.REQUIRED and not paths:
        raise OperatorPreflightError(...)
    if phase_value.durable_artifact is DurableArtifact.NONE and paths:
        raise OperatorPreflightError(...)
    if any(not _within_scope(path, work_scope)
           or not _within_scope(path, normalized_phase_scopes[phase_key])
           for path in paths):
        raise OperatorPreflightError(...)
----

This loop iterates *every declared phase in the shared profile*, not only
phases reachable from `work_item.initial_phase`. `standalone-development-profile.yaml`
declares `review.durable_artifact: required` and `rereview.durable_artifact:
none` (unmodified). Consequently:

* `phase_key = "review"`: `paths` is the one mapped WI-004 path (non-empty);
  `REQUIRED` + non-empty is satisfied; the path is within both `work_scope`
  and `review`'s `authorized_scope` (`docs/backlog/wfc_reviews`) -- passes.
* `phase_key = "rereview"`: `paths = durable_artifacts.get("rereview", ())`
  is empty (no `rereview` key in the mapping); `NONE` + empty is satisfied --
  passes.

Given the profile's actual topology (`review -> correct -> rereview ->
{accept, correct}`, with nothing routing back into `review` or `investigate`),
a Run whose `initial_phase` is `rereview` can never transition into `review`
for the remainder of its lifetime: `correct` only routes to `rereview`, and
`rereview` only routes to `accept` or `correct`. The mapped `review` artifact
path is therefore mechanically dead for this specific Run's execution.

Disposition: *(A) correct, harmless mapping* -- not stale or misleading
governance. Reasoning:

. `_preflight()`'s structural check validates the WorkItem's
  `durable_artifacts` mapping against *every* phase the shared profile
  declares, because the same profile file is reused across all
  developer-ergonomics attempts with different `initial_phase` values
  (Attempt 4/5 start at `review`; Attempt 6 starts at `rereview`). The
  validator performs no reachability analysis from `initial_phase`; it cannot
  distinguish "phase declared but unreachable from this WorkItem's start" from
  "phase declared and reachable." Supplying the `review` mapping is therefore
  a mandatory, harmless artifact of reusing this general-purpose profile, not
  something specific to or newly introduced by this candidate (the mapping
  mechanism and this exact validation loop are unmodified `operator.py` code
  predating this commit).
. The mapped path is a fresh, WI-004-scoped name
  (`WI-WFC-DEVELOPER-ERGONOMICS-REVIEW-004/review.adoc`), consistent with the
  precedent already recorded in
  `docs/backlog/BUG-WFC-PROFILE-DURABLE-ARTIFACT-INSTANCE-COUPLING.adoc`
  (durable-artifact names must be per-instance, never reused across attempts).
  It does not collide with, alias, or reinterpret any other attempt's review
  artifact.
. Because `review` is unreachable from `rereview` under the current topology,
  no Hop in Attempt 6 will ever be authorized under `review`'s
  `authorized_scope`/`authorized_actions`, so the mapping creates no authority
  ambiguity, no spurious write requirement, and no preflight inconsistency at
  runtime -- it is validated once, at admission, and then never referenced
  again by the Run.
. This is not a defect introduced by the candidate: the candidate does not
  modify `operator.py`, the profile, or the policy. It is an existing,
  general property of how a shared profile's structural validation composes
  with a non-initial-reachable phase, correctly and harmlessly triggered by
  Attempt-6's `rereview`-first WorkItem.

I record this only as INFO, not a finding requiring correction: a future
profile change that made phase-reachability-aware validation possible could
simplify this, but nothing in this candidate requires or motivates that, and
the task text explicitly forbids broadening profile/policy scope.
