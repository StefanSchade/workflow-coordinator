== 1. Interpreter identity semantics

`ExecutableResolution` (`src/workflow_coordinator/evidence.py:42-46`) declares
both fields the candidate compares:

[source,python]
----
@dataclass(frozen=True)
class ExecutableResolution:
    invocation_path: str
    canonical_path: str
    stat_fingerprint: StatFingerprint
----

`resolve_executable` (`evidence.py:109-140`) populates them from the same PATH
search:

[source,python]
----

    invocation_path=candidate,
    canonical_path=os.path.realpath(candidate),

`invocation_path` is the literal PATH-selected spelling (whatever alias the
authored argv[0] happened to resolve through, relative to the repository-root
PATH-selection rule); `canonical_path` is that same selection's
`os.path.realpath` result -- i.e. the actual filesystem target after following
every symlink. This pair is not new: `git log -p --follow -- evidence.py`
shows both fields present since `b67def9` ("implement carve-out A2 evidence
commands"), long before this fix, and `canonical_path` is already surfaced
through production's own evidence plan (`operator.py:475-476`,
`_prepared_evidence_plan`) and persisted (`persistence.py:40-41`). The
candidate therefore reuses an existing, already-load-bearing production
resolver surface; it does not invent a parallel test-only definition of
identity.

The corrected assertion in
`test_current_self_development_bundle_passes_production_preflight`
(`tests/architecture/test_self_development_governance.py:218-224`) is:

[source,python]

assert prepared.admission_resolution.invocation_path == str(Path(sys.executable).parent / "python")

This is a materially stronger proof than "the values happen to be equal": it

== 2. Symlink / alias correctness

`canonical_path = os.path.realpath(candidate)` is the right level of identity
for this invariant, and no material inode/copy/symlink distinction makes it
incorrect:

* The alias in question (`python` vs `python3` inside one venv's `bin/`) is a
  pure symlink chain to one underlying regular file. `realpath` is defined to
  fully resolve symlink chains to their final target, so it is neither
  under-resolving (it does not stop at the first symlink hop -- it would
  correctly collapse `python -> python3 -> /usr/bin/python3` even if the chain
  were one hop longer) nor over-resolving beyond what the invariant needs (it
  does not compare file *content*, hashes, version strings, or inode/device
  numbers -- see below for why that would be the wrong, stronger
  requirement).
* `resolve_executable` separately computes `stat_fingerprint`
  (`st_dev`/`st_ino`/`st_mode`/`st_size`/`st_mtime_ns`,
  `evidence.py:96-106`) and exposes it on `ExecutableResolution`, but the
  candidate does not use inode-level fingerprint equality for this test. That
  is the correct choice: the trusted-evidence contract this BUG concerns is
  "the policy-authored command resolves to the same intended interpreter
  binary," which is exactly what a resolved-path identity captures. Requiring
  inode/device equality in addition would be a *stronger* invariant than the
  contract promises (it would, for example, incorrectly fail if the
  Development environment's `python3` were ever replaced via
  hardlink-breaking reinstall between admission and observation, which the
  BUG does not concern) -- the review brief's instruction not to invent a
  stronger identity requirement without justification is respected.
* `realpath` resolving "too aggressively" would only be a concern if two
  *conceptually distinct* interpreters could collapse to one canonical path.
  That cannot happen here: `realpath` only follows symlinks/normalizes a
  single path's own chain; it never merges two independently-selected
  candidate paths that happen to be hardlinks to the same inode without a
  symlink relationship (hardlinks are not traversed or collapsed by
  `realpath` at all). The venv's actual `python`/`python3` pair is a symlink
  chain, not independent hardlinks, so this is the exact case `realpath` is
  designed to collapse correctly.
* `realpath` resolving "insufficiently" would mean two spellings that should
  be identical are reported as different. That is not observed: both
  `.venv/bin/python` and `.venv/bin/python3` realpath to the same
  `/usr/bin/python3` target on this host, matching the assertion.

No stronger or different identity definition is warranted; the diff does not
invent one.

== 3. Negative regression

`test_production_preflight_identifies_different_python_interpreter_identity`
(`test_self_development_governance.py:227-249`):

[source,python]
----
alternate_bin = tmp_path / "alternate-bin"
alternate_bin.mkdir()
alternate_python = alternate_bin / "python"
shutil.copy2(sys.executable, alternate_python)

monkeypatch.setenv(
    "PATH",
    os.pathsep.join((str(alternate_bin), os.environ["PATH"])),
)
...
result = _preflight(_preflight_args(repository, expected_head, state_root))
prepared = result[13]["pytest"]

assert prepared.admission_resolution.canonical_path == str(alternate_python.resolve())
assert prepared.admission_resolution.canonical_path != str(Path(sys.executable).resolve())
----

Findings:

. This is not tautological. `shutil.copy2` follows `sys.executable`'s own
  symlink chain and copies the underlying *bytes* of the real interpreter
  binary into a brand-new regular file at a distinct path
  (`alternate_bin/python`), not a symlink and not a hardlink. The copy is
  therefore byte-identical in content to the real interpreter yet a genuinely
  different filesystem object at a genuinely different canonical path. The
  test asserts the two `canonical_path` values differ -- proving
  canonicalization discriminates by resolved *path identity*, not by file
  content, executable format, or "is this also a working CPython
  interpreter." A content-based or basename-based identity definition would
  have wrongly treated `alternate_python` as the same interpreter; this test
  would fail against such a (weaker/wrong) implementation, so it is not
  vacuous.
. `alternate_bin` is prepended ahead of the venv's own `bin/` on `PATH`
  (`preflight_python_path`'s fixture PATH is still present later in the same
  variable, per the `os.pathsep.join((str(alternate_bin),
  os.environ["PATH"]))` construction), so `resolve_executable`'s PATH-ordered
  search (`evidence.py:125-132`, first match wins) deterministically selects
  `alternate_bin/python` and not the venv's `python`. This is not an
  incidental filesystem detail; it is the exact mechanism
  (`resolve_executable`'s documented first-match PATH semantics) that the
  admission resolver uses in production, so the test exercises the real
  selection path, not a hand-rolled stand-in.
. The test does not assert or require that production preflight *reject* or
  raise on this mismatch. It only asserts the two `canonical_path` values are
  observably different. This is the correct scope: nothing in
  `RepositoryPolicy`, `_preflight`, or `prepare_evidence_commands` promises to
  compare the resolved trusted-evidence interpreter against `sys.executable`
  of the *test process* -- that comparison is a property the architecture
  test itself checks (to prove the policy's `python` and the suite's own
  running interpreter are the same one), not a runtime admission guarantee
  the system makes about arbitrary PATH contents. Asserting a rejection here
  would incorrectly require production behavior the system does not offer;
  the candidate correctly avoids that overreach, matching the review brief's
  instruction on this point.
. `shutil.copy2` preserves the executable permission bits, and I confirmed
  `_fingerprint` (`evidence.py:96-106`, `S_ISREG` + `os.access(X_OK)`) accepts
  the copy without needing any special-casing in the test -- no unstated
  production leniency is being relied on.

Conclusion: the negative test meaningfully exercises the intended identity
boundary (canonical *path* identity, not content or name) without asserting
production behavior the system does not promise.
