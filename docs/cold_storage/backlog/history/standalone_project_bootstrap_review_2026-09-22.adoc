== 3. Findings

=== 3.1 IMPORTANT

==== I-1 -- Review-phase mutation authority and the implementation/review path split is an unclosed authority decision

Category:: B -- missing authority decision
Changes:: plan only; no architecture change

Observation:: `+_check_action_coherence+` (`+serialization.py+`:500) makes
`edit` and `commit` an inseparable pair and *forces both* on any phase declaring
`durable_artifact: required`. `+_preflight+` (`+operator.py+`:251) requires every
phase `authorized_scope` to lie inside `WorkItem.scope`. The committed fixture
`+tests/fixtures/slice5b_non_dmc.yaml+` already realizes the exact
implement -> review -> correct -> rereview shape the plan proposes, and resolves
this question explicitly: its `review` phase is `durable_artifact: required`
with `authorized_actions: [edit, commit, review]` and `authorized_scope:
[review/report.md]`, while its `rereview` phase is `durable_artifact: none` with
`authorized_actions: [review]`.
+
Plan section 7.2 names only implementation payload areas -- `Makefile`, the
Ruff-only portion of `+pyproject.toml+`, a snapshot-script area, the
package-boundary guard, and narrowly related developer docs and tests. It never
says whether the review phases produce a durable artifact, and never names a
review-artifact path or requires it to be disjoint from the implementation
paths.

Why it matters:: Whether the first-dogfood review phases hold `edit` and
`commit` is decided entirely by that unstated choice, and if they do hold them,
their `authorized_scope` must be a review-artifact path disjoint from every
implementation payload path -- otherwise an independent review phase silently
acquires edit authority over the implementation it is reviewing. That is a
mutation-authority boundary, which is precisely the class of decision the
planning and review gate exists to settle. It is not a least-authority detail
that a bounded implementation step can fill without an architectural choice.
+
A second mechanical consequence follows. If any phase other than the initial
phase is `durable_artifact: required`, `+_preflight+` rejects the legacy
`+--durable-artifact+` argv route outright ("legacy durable-artifact input
cannot satisfy later required phase"). The WorkItem must then carry a pinned
`durable_artifacts` mapping. Choosing a required review artifact therefore also
forces the pinned-mapping route, which is consistent with the plan's
pinned-governing-input thesis but is nowhere stated.

Smallest correction:: In section 7.2, state (a) whether the review and rereview
phases carry `durable_artifact: required` -- and therefore `edit` and `commit` --
or `none` and therefore `[review]` alone; and (b) if required, that the
review-artifact path is a distinct path disjoint from every implementation
payload path, and that the WorkItem supplies it through the pinned
`durable_artifacts` mapping rather than the legacy argv.

==== I-2 -- Section 7.3's coherence properties are not all reachable from a pure production function, and the current wording invites a test-only reimplementation of path algebra

Category:: C -- unnecessary complexity risk (duplicate policy engine)
Changes:: plan only; no architecture change

Observation:: The five properties section 7.3 asks the guard to prove are split
across two production sites with very different preconditions.
+
`+_admit_a1+` (`+operator.py+`:102) is pure, already imported by
`+tests/unit/test_a1_admission.py+`, and covers A1 path shape, governing inputs
inside `policy.governance_paths`, bidirectional phase-scope/governance
non-overlap, `WorkItem.scope` inside the ceiling, and both Hop ceilings.
`+_selected_evidence_names+` and `+_selected_ids+` are pure and importable and
cover the evidence-reference and component-manifest properties.
+
Two properties have no such route. Phase `authorized_actions` inside
`policy.actions`, and phase scope inside `WorkItem.scope`, exist only inside
`+_preflight+` (`+operator.py+`:244-251), which additionally demands a real
clean Git repository at an exact forty-character HEAD and a non-existent state
root. And "phase scopes do not exceed the policy ceiling" has *no* production
expression at all without a WorkItem, because production enforces it only
transitively as phase inside WorkItem inside ceiling. Slice B2 commits no
WorkItem, and `+_admit_a1+` takes one as an argument.

Why it matters:: An implementer asked to prove those properties, with no
WorkItem available and no pure function that expresses them, will most
plausibly write local prefix logic -- a second implementation of
`+_within_scope+` and of the ceiling relation. That is the duplicate policy
engine this review is required to flag. Drift between it and production
admission produces a guard that passes while real admission fails, or the
reverse, which is worse than having no guard.

Smallest correction:: State in section 7.3 that the guard imports and calls
`+_admit_a1+`, `+_selected_evidence_names+`, `+_selected_ids+`,
`+_within_scope+` and `+a1_path_shape+` from the package rather than restating
any rule; that the two properties with no pure production expression are
asserted on top of the imported `+_within_scope+` plus a plain set difference;
and that no path-prefix, domination, action or evidence rule is written
independently in test code.
+
One further project-specific assertion is worth naming there, because
production admission genuinely cannot express it: `+_admit_a1+` checks phase
scope against `governance_paths` and `WorkItem.scope` against the ceiling, but
never checks the *ceiling itself* against `governance_paths`. The binding
protection remains the phase-level non-overlap rule, so no agent can reach
governance regardless; asserting that the committed ceiling also excludes
`governance` is a cheap, honestly project-specific guard.

==== I-3 -- The plan forbids installing into the runtime clone but never states a non-mutating way to execute it

Category:: B -- missing operational decision under a hard invariant
Changes:: plan only; no architecture change

Observation:: Section 2.4 forbids the bootstrap to "install into" the runtime
clone, and the section 13 validation contract forbids any "runtime clone
worktree ... change". The runtime clone is currently pristine: `git status
--porcelain -uall --ignored` is empty and its top level holds no `build/` or
`+*.egg-info/+`. The development clone, by contrast, carries ignored `build/`
and `+src/workflow_coordinator.egg-info/+` -- direct local evidence that
building or installing in place writes derived output into a clone's worktree.
Neither Workflow Coordinator clone has a `.venv`, while all seven sibling
projects under `~/repos/spreadsheet-handling/` do.

Why it matters:: The dogfood requires actually running the runtime Workflow
Coordinator. The two most natural ways to obtain it -- an editable install from
the runtime clone, or a build inside it -- both write into the runtime worktree
and would break the plan's own non-mutation invariant on first use. The plan
assigns `+docs/self-development.adoc+` "invocation/topology/promotion guidance"
but sets no acceptance criterion that the method it names leaves the runtime
worktree byte-identical.

Smallest correction:: Add one Slice B2 acceptance criterion: the
self-development guide names a concrete runtime invocation that writes nothing
into the runtime clone worktree -- for example a virtual environment outside
both clones, a non-editable install, or running the operator module with the
runtime `src` on `PYTHONPATH` -- and records that ignored derived output inside
the runtime clone still counts as a runtime worktree change under section 13.

==== I-4 -- No runnable provider-free test invocation exists in this environment, yet both B2 acceptance and the committed policy's only evidence command presuppose one

Category:: A -- plan contradiction against observed facts
Changes:: plan only; no architecture change

Observation:: In this environment `python` does not resolve; `python3` resolves
to `/usr/bin/python3` and has no `pytest` module; `pytest` does not resolve; and
neither Workflow Coordinator clone has a virtual environment. `+README.md+`
instructs `python -m pip install .` and `python -m pytest`, neither of which
resolves here. Policy evidence commands are resolved at admission by
`+prepare_evidence_commands+` against a captured PATH taken from the repository
root (`+evidence.py+`:114-125), so an evidence command of `["python", "-m",
"pytest"]` -- the obvious transcription of the README -- fails admission.
+
Slice B2 acceptance requires the "full current pytest suite", and section 7.1
commits "the provider-free existing test command" as the policy's initial
evidence command.

Why it matters:: This falsifies the plan's stated endpoint. Bootstrap would
complete and declare that standalone Workflow Coordinator is ready for its first
dogfood WorkItem, while the first Run would exit 2 at preflight before any Hop.
The failure is safe -- it fails closed, before the provider-capable boundary --
but it is discovered at exactly the wrong moment.

Smallest correction:: Record the concrete environment prerequisite in Slice B2
-- a virtual environment outside both clones with the `dev` extra installed, or
an explicitly named resolvable interpreter -- and extend the section 7.3 guard
to run the committed evidence commands through the production
`+prepare_evidence_commands+` resolver, so an unresolvable `argv[0]` fails at
guard time rather than at first dogfood.

== 4. Dispositions on the specific review questions

=== 4.1 Current-authority classification

Sufficient, subject to M-1. One current index plus the existing directory NOTICE
is enough. No historical document could still be mistaken for current authority
once the index exists. The only contradictory current authority found is the
pair of closed enumerations in M-1, which the bootstrap itself creates and can
retire in the same slice. No duplicated authority between README, architecture,
Project Memory and backlog is inherent in the proposed split; the role table in
section 3.1 is a genuine partition. No unnecessary historical curation is
proposed.

=== 4.2 Project Memory

The one file with five sections is enough for fresh-context agents, and nothing
proposed for it is really architecture, backlog or Run evidence -- the ownership
table in section 4.3 draws that line correctly. The accepted-transition refresh
rule has a clear owner: the maintainer, who accepts the transition and whose
WorkItem must name the path before any Run may touch it. An agent cannot widen
its authority through Project Memory (see M-3 for the reasoning and the residual
narrative-only risk). No schema, generator, validator or archive machinery is
required now, and importing Core's Project Memory machinery would be
unjustified. Project Memory minimalism survives falsification.

=== 4.3 Two-clone self-hosting and the push/promotion boundary

The invariant holds and the plan creates no implicit route around it. The review
specifically looked for runtime mutation, runtime ref movement, automatic
runtime update, worktree sharing, development Workflow Coordinator executing
itself before promotion, GitHub push, and promotion by the engine or an agent.
None is present, and the topology on disk already matches the claim: two
physically separate object stores, the runtime detached at the accepted commit
with its push URL disabled, and no worktree sharing.

The one gap is operational rather than architectural and is recorded as I-3: the
plan forbids installing into the runtime clone without saying how to run it
instead.

The maintainer-owned boundary -- local accepted state, then maintainer push,
then optional maintainer runtime promotion -- reads as intentional design, not
missing automation, and should not be automated.

=== 4.4 Self-development governance

The bootstrap gives the engine and the agent no way to author or widen the
authority under which they operate. The intended ownership in section 6.2 is
enforced mechanically, not merely asserted (see W-3). The reusable five-file set
authorizes no Run by itself, because the operator requires a WorkItem and a task
that the maintainer authors separately. No generalized policy or profile
framework is introduced.

=== 4.6 Fixed profile scope consequence

The plan's refusal to invent templating, inheritance or a generalized profile
abstraction is correct and should be upheld. The engine supports what the plan
needs without any new abstraction, and the committed fixture proves it.

The proposed first profile can serve implement -> review -> correct -> rereview
without granting review phases mutation authority they do not need, on one
condition: a review phase that produces no durable artifact declares
`authorized_actions: [review]` with `durable_artifact: none` and receives
neither `edit` nor `commit`, while a review phase that does produce one is
forced to hold both and must therefore be scoped to a review-artifact path
disjoint from the implementation paths. That exact separation *is* needed, and
stating it is the substance of I-1.

Governance paths are excluded, and this is enforced rather than conventional.
Future WorkItem scope does not have to become artificially broad, because
nothing forces profile reuse. A one-purpose first-dogfood profile is
straightforwardly simpler than adding a profile abstraction now.

=== 4.7 Governance coherence test

The risk of creating a second implementation of admission semantics is real and
is the subject of I-2. The preferred property -- production parsers, the actual
pure admission function, no test-local copy of `+_within_scope+`, path algebra,
or action and evidence rules -- is achievable for most of the intended
assertions but not all, and the plan's current "where possible" hedge is too
weak to prevent the bad outcome. The plan needs stronger wording here before
implementation.

=== 4.8 First dogfood payload

Developer ergonomics is the right first real payload. It is genuinely useful,
bounded, free of new engine architecture, and realistic for the current
Codex/Terra-medium binding, subject to I-4's environment prerequisite and M-2's
one-correction-cycle budget.

The bootstrap does not accidentally implement any of it. The one adjacency worth
closing is M-5, the `+__package__+` guard, which Slice B2's new architecture test
sits next to.

=== 4.9 Bootstrap slicing

Two slices are fine. B1 establishes what authority means; B2 commits executable
governance that depends on B1's vocabulary. That is a real dependency, so the
split is not gratuitous, and B1's "recommended, not mandatory" separate review
correctly avoids lifecycle ceremony for a slice that changes only documentation.

No additional gate is warranted. The review specifically asked whether a gate is
missing between authority definition and executable governance, and no concrete
failure was identified that a third slice or an extra mandatory gate would
prevent. Adding one would be process for its own sake.

=== 4.10 Security and unattended-execution truthfulness

Truthful, subject to M-6. The plan states that the adapter *requests*
`approval=never` rather than that it achieves anything, correctly calls that
setting necessary but not sufficient, makes no effective containment claim,
defines unattended execution as the absence of an interactive approval route,
and keeps the OS boundary in LATER and evidence-driven. The bootstrap promises
no sandbox it does not provide.

=== 4.11 Implementation non-scope

Confirmed excluded, with one exception. Every item in the review brief's
non-scope list is excluded by section 12 or by the slice non-scope lists, and no
accidental implementation requirement for any of them was found. The exception
is the `+__package__+` guard, recorded as M-5.
