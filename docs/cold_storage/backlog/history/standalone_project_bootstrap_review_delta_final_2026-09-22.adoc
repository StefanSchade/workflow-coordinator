== 3. I-4R -- CLOSED

=== 3.1 The launch contract

Section 6.1.1 now states one explicit ordered `PATH`:

[source,text]
----
<development/evidence-env>/bin:<runtime-env>/bin:<remaining trusted base PATH>
----

and separates executable *selection* from executable *resolution*: Runtime N is
invoked by the absolute path `<runtime-env>/bin/wfc`, while the ordered `PATH`
decides what `python` means inside that process. The two requirements the parent
review found unreconciled -- runtime `bin` on `PATH`, development/evidence `bin`
first -- are now reconciled by making runtime selection independent of `PATH`
entirely. The plan says so explicitly: "The runtime environment's `bin` need not
be first because the Runtime-N WFC executable is selected independently of
`PATH`."

=== 3.3 One property the plan under-claims

Execution is stronger than the plan asserts, in the plan's favour.
`+PRODUCTION_EVIDENCE_RUNNER.observe+` (`+evidence.py+`:244-260) re-resolves
`+authored_argv[0]+` against the *stored* snapshot and then executes
`+(resolution.invocation_path, *authored_argv[1:])+` -- an absolute interpreter
path -- with `+env=command.environment.values+`. The evidence child process
therefore receives the captured launch environment verbatim and performs no
fresh OS-level `PATH` lookup of its own. Admission-time resolution and
execution-time resolution cannot diverge. The plan does not need to say this; it
is recorded here because it removes the last plausible route by which a correctly
admitted `python` could still execute as a different interpreter.

== 8. INFO / WATCH

W-4 -- The development `wfc` is shadowed by ordering, and that is safe::
Because the development/evidence environment installs the repository with its
`dev` extra, its `bin` contains a `wfc` console script for the *development*
tree, and that `bin` is now first on the launch `PATH`. Any bare `wfc` lookup in
that environment would therefore select development WFC N+1 rather than runtime
WFC N. This is not a defect: the correction's absolute-path rule is precisely
what neutralizes it, and a search of Runtime N's `src/` found no code path that
resolves or re-executes `wfc` by name. The plan's two remaining bare
`+wfc run --bundle <dir>+` mentions are a deferred CLI-design evaluation inside
explicit non-scope, not launch instructions. The property to preserve in the
NEXT 2 documentation is that the launch command is written as an absolute path,
never as a bare name inside an activated environment.

W-5 -- Runtime identity remains procedural, as previously accepted::
W-3 of the parent review noted that the engine performs no self-identification
check, so "runtime N never executes the development package" rests on the launch
procedure. That remains true, and the delta improves it: the B2 proof now
confirms that "the Runtime-N Python import come[s] from the dedicated
non-editable installation prepared from the verified export of accepted Runtime
N", which converts a recorded intention into a checked fact at acceptance time,
even though it is still not enforced per Run. This stays NEXT 2 documentation
work rather than bootstrap work.
