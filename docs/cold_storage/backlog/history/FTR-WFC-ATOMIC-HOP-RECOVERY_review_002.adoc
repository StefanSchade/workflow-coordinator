`vertical.run_one_hop` after `validated_result` succeeds
(`vertical.py:176-189,289`).

No regression: the four distinctions are used consistently in the decision
summary, the charging rules, the budget section, and the R2 gate.

== 2. New findings

=== N-M1 (MINOR) -- the quiescence conjunct is hedged into vacuity inside the machine-derived list

Section A requires "predecessor process termination and absence of a concurrent
Attempt, but only to the degree the execution boundary can actually observe
them." Read literally, a boundary that observes nothing satisfies this conjunct
vacuously, which is the one shape a fail-closed conjunctive predicate must not
have.

The revision's intent is clearly honesty rather than permissiveness, and the
rest of the document supplies the correct rule: section B lists escaped
descendant processes as an uncovered residual risk, and R2 is told to "retain
conservative charging for every ambiguous or ineligible case." The defect is
local placement. The unobservable remainder belongs in section B, and section A
should say that an Attempt whose termination cannot be established is
*ineligible* for retry. This must not survive into an actual R2 predicate
design; it is not a decision blocker now, because R2 is deferred and separately
gated.

=== N-M2 (MINOR) -- a current-truth fact relevant to R1's disposition vocabulary was dropped

The original FTR recorded that "a valid correlated candidate is currently
processed even when transport return code or timeout flags are non-success,
because the vertical acceptance path does not gate candidate validation on
those transport flags." That sentence is gone from the revision, and nothing
replaces it.

It remains true (`codex_adapter.py:181` reads the last-message file
unconditionally after a timeout kill; `vertical.py:176` gates only on
`candidate_result is None`), and it bears directly on R1's proposed disposition
set `not_started | candidate_validated | discarded | uncertain` and on the
search for a "stable structured transient signal": a timed-out invocation may
still be candidate-bearing, so `timed_out` and a non-zero return code are not
by themselves transient markers. Restoring one sentence to "Current repository
facts" would prevent an implementer from assuming otherwise.

=== N-M3 (MINOR) -- the `Priority::` line is the only text that reads as a scheduling commitment

The header reads `Priority:: small recovery MVP; later work is evidence-gated`.
Every other relevant passage is correctly permissive -- "may implement R1.5
first, stop there, and return project effort to spreadsheet-handling/DMC work",
"R2 is not presumed to follow", and the non-goal "implementation approval
through this architecture record". A reader scanning only the header could take
the MVP as scheduled rather than as the recommended shape *if* recovery work is
undertaken. One qualifier, for example "small recovery MVP if pursued", removes
the ambiguity.

=== N-I1 (INFO) -- `operator-plan.json` already publishes a declared `retry` fact

`operator.py:692` writes `"retry": False` into the operator plan, and
`tests/unit/test_operator.py:231` asserts it. The FTR does not mention this
surface. It is consistent with the revision: R1.5 performs no replay, so
`retry: False` stays truthful. R2 would be the first change to make it false,
so that field is a small, already-published place where the P5 supersession the
FTR defers would become visible. Worth knowing when R2 is designed; nothing to
correct now.

=== N-I2 (INFO) -- R1.5's coverage is bounded by the anomaly gate, which the FTR does not state

`resume_after_reconcile` refuses any Run whose `anomalies` tuple is non-empty
(`reducer.py:565-566`), and `recover_uncertain` appends observed Git anomalies
to the recovered Run (`slice4.py:192-193`). No seam clears anomalies. A future
R1.5 entrypoint therefore resumes only the *clean* interruption -- which is
precisely the motivating quota case -- while an interruption that left dirty or
out-of-scope repository state is not resumable and must be dispositioned some
other way, most plausibly as a fresh successor Run.

This is correct fail-closed behavior and does not weaken the FTR's argument,
but the R1.5 description would be sharper for naming the boundary rather than
leaving a designer to discover it.

== 3. MVP and overengineering check

*Yes.* The revised FTR supports the bounded project decision:

  "Implement, if desired, a small explicit reconcile/resume CLI/operator path;
   otherwise return to WFC generalization and DMC work. Do not treat R1/R2/R3
   as mandatory follow-on implementation."

The supporting text is explicit rather than inferred:

* "Smallest useful implementation slice" states that "The practical MVP may
  implement R1.5 first, stop there, and return project effort to
  spreadsheet-handling/DMC work. R1 may proceed independently when its
  observability value warrants it. R2 is not presumed to follow."
* R1.5 is stated to be independent of R1 and "substantially smaller than R2",
  which this review verified against the seams.
* R2 is conditional on measured evidence and on containment work that is
  explicitly not designed here.
* R3 "remain[s] deferred and evidence-driven. Neither blocks a practical
  recovery MVP."
* The non-goals list ends with "implementation approval through this
  architecture record", and the decision summary states the FTR "does not
  approve an implementation or supersede current semantics."
* The closing sentence makes the do-nothing path the default: "Until those
  questions are answered by evidence and a separately reviewed change, explicit
  reconcile/resume and fresh successor Runs are the practical recovery
  mechanisms, and current charging semantics remain authoritative."

No text creates an implementation obligation. The `Priority::` header line
(N-M3) is the only phrase a reader could misread as scheduling, and it is a
one-word fix that does not affect the decision.

Nothing in the revision reintroduces platform scope. Watchdog policy, outer
loop, elevated privilege, provider-session persistence, scratch, and
generalized process-restart recovery are all non-goals, and the
`permitted_recovery_actions` seam is bounded to derived permission with an
explicit prohibition on selection and initiation.
