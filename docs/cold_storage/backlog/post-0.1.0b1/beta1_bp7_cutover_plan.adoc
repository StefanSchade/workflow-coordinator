Updated:: 2026-11-20
Owns:: A concrete, source-grounded implementation plan for
link:../../../backlog/beta1_productization.adoc#bp7[the epic's BP7] and
link:../../../backlog/beta1_execution_plan.adoc[the execution plan]'s BP7 Commission
(`wfc-beta1-bp7-self-development-cutover-001`): gap analysis against the

link:../../../backlog/beta1_execution_plan.adoc#decision-gates[the execution plan's decision
table]. It does not set or prepare the `0.1.0b1` tag, and treats Beta-epic
closure and the tag as distinct, per
link:../../../backlog/beta1_execution_plan.adoc#closure-versus-tag[closure versus tag].

[[config-recommendation]]
== 2. Deployment-configuration binding recommendation

=== What `resolve_evidence` already supports (verified, not assumed)

`frontdoor/config.py:253-287 resolve_evidence(config, repository_root,
environ)`:

* Absent an `evidence` block: `raw="local"`, destination
  `<XDG_DATA_HOME or ~/.local/share>/wfc/evidence/<repository_name>` --
  always under the consumer's data home, never a product-chosen absolute
  path baked into committed config.
* An explicit `evidence.repository` string is resolved *relative to
  `repository_root`* when not already absolute, "including one that escapes
  it with `..`, as self-development does" (the function's own docstring,
  verified against its code: `Path(os.path.normpath(repository_root /
  candidate))`). `repository_root` is always the actual payload repository
  `wfc run`/`resume` was invoked against (`inputs.repository`, passed through
  unchanged to `postrun.run_pending_postrun` at `frontdoor/lifecycle.py:902`
  and into `resolve_evidence` at `frontdoor/postrun.py:197`) -- never a copy,
  scratch clone, or the engine's own state root.
* `raw` is one of `local`/`commit`/`discard` (`EVIDENCE_RAW_CHOICES`,
  `config.py:26`), independent of destination.

This means `evidence.repository: ../workflow-coordinator-run-evidence` with
`raw: commit`, written into a *relative* path in committed config, already
resolves correctly today with **no additive product change** -- provided
`wfc run`/`resume` is always invoked against the real, canonical Development
checkout that actually has that sibling directory one level up (see
<<risks>> for why this is a real operational precondition, not a config
limitation).

`wfc init` (`frontdoor/init.py`) never commits the Consumer Config
(`"wfc init never commits it"`, `init.py:212`) and, given an
`--evidence-repository` pointing at the existing sibling, calls
`ensure_evidence_repository` (`init.py:93-123`), which returns `"reused"`
without writing anything when the path already exists, is a Git repository
root, and has an `archive/` directory -- exactly the sibling's current shape.
So nothing about adopting the existing Evidence repository requires any
write to it; `wfc init --no-evidence-repository` can skip even that read-only
check if the Commission authoring the config prefers to touch nothing
outside the Development repository.

=== Options evaluated

[cols="2,4,3",options="header"]
|===
|Option |What it encodes / what breaks elsewhere |Verdict

|(a) Versioned relative config committed in the repository
(`.wfc/config.yaml`, `evidence.repository: ../workflow-coordinator-run-evidence`)
|Encodes "the Evidence repository is always exactly one directory above
wherever this Development checkout is cloned." No absolute `$HOME` path is
ever written. It breaks the moment a machine keeps the Development checkout
and its Evidence sibling in a different relative arrangement -- but that
arrangement is already today's long-standing self-development convention
(every manual chapter and `scripts/wfc_op.py` invocation already assumes a
sibling clone), not a new assumption this plan introduces.
|*Recommended.*

|(b) Local/untracked override (a second, gitignored config file layered over
or instead of the committed one)
|Would encode an absolute, machine-specific Evidence path outside the
committed history -- exactly what a genuinely multi-machine consumer might
want, but self-development has exactly one real deployment (the
maintainer's own machine, one canonical checkout). *No such layering
mechanism exists today*: `--config` (`frontdoor/plan.py:279-293`,
`frontdoor/lifecycle.py:953-961`) names exactly one file, read once; nothing
in `config.py`/`lifecycle.py`/`plan.py` merges a second config source.
Building it would be an additive product change this plan does not need to
request.
|*Not recommended for this need.* Leave as a possible future
general-consumer feature, not a BP7 requirement.

|(c) Combination (versioned base + untracked override)
|Same additive-code objection as (b), plus two sources of truth for one
small, single-deployment value -- directly against "no second archive path
beside the product function."
|*Not recommended.*
|===

=== Recommendation

Commit `.wfc/config.yaml` at the Development repository root (schema and
keys exactly as accepted in `frontdoor/config.py:consumer_config_from_yaml`):

[source,yaml]
----
schema_version: 1
repository_name: workflow-coordinator
governance_dir: .wfc/governance
work_item_scope_ceiling:
  - src
  - tests
  - scripts
  - docs
max_autonomous_hops: 10
default_execution: {}        # filled per <<open-decisions>> item 3
evidence:
  repository: ../workflow-coordinator-run-evidence
  raw: commit
----

`work_item_scope_ceiling` reuses the existing, already-precedented
`repository-standard@v1` constant literal (`commissioning.py:333`:
`("src", "tests", "scripts", "docs")`), not an invented list; it bounds every
future compiled Commission's `scope`, each of which can and normally should
be much narrower. No currently-identified BP7 retirement work (removing
`scripts/wfc_op.py`, the v1 compile path, and the literal `_repository_
standard_record` check in `commissioning.py`) falls outside this ceiling;
nothing currently in the tree requires touching `governance/` itself (no
concrete "quarantined file" exists anywhere under `src/`, `tests/`,
`scripts/`, or `governance/` as of this Hop -- verified by search -- so this
plan does not invent one; the retirement Commission should re-check for one
when it starts). Nothing is deselected by default today either: `pytest`'s
`addopts` carry no `-m` deselection (`pyproject.toml:38 addopts = "-q"`); what
does exist, and is not a quarantined file in the sense the second-pass
migration review meant, is the registered `historical_governance` marker
(`pyproject.toml:43`) and the small
`tests/architecture/test_historical_governance_parse.py` smoke check that
already replaced an earlier, much larger bundle test -- both of which keep
passing after retirement because `governance/self-development/` is retained
as frozen historical input, per the epic's own "no retroactive rewrite"
rule; C5's acceptance should cite these two by name rather than only the
general "without any quarantined file" phrasing it inherits from the
execution plan.

No additive product change is needed for the Evidence binding itself. One
additive *input* (not a code change) is required regardless of which config
option is chosen: a new, committed `repository_policy` guidance document,
because `compile_commission` always requires `ConsumerRequest.guidance`
(see <<gap-analysis>>). Authoring its content is a real decision, not a
bounded one; see <<open-decisions>>, item 2. Likewise, `default_execution`'s
concrete adapter/model/reasoning values are the maintainer's choice, not
this plan's; see <<open-decisions>>, item 3.

[[archive-equivalence]]
== 3. Archive equivalence

"Archive-equivalence evidence" (execution plan BP7 acceptance) means: for a
real self-hosted `wfc run`, the automatic BP6c postrun archive
(`postrun.run_pending_postrun` -> `archive.archive_run`,
`frontdoor/postrun.py:167-230`, `frontdoor/archive.py:981-1170`) produces a
destination under `archive/<domain>/<workstream>/<attempt_id>` (or
`archive/unclassified/<attempt_id>`) in the existing sibling Evidence
repository that is verified, field by field, against what
`scripts/archive_run.py`/`scripts/wfc-archive-run` would have produced for
the same STATE/OPS facts.

Facts that must match (verified already true of the port, not assumed):

* *File set.* `RUN_ROOT_ALLOW`/`CHECKOUT_ALLOW`/`OPS_ROOT_ALLOW`
  (`archive.py:86-120`) are the Harness allow-lists, copied verbatim.
* *Manifest shape.* A freshly written `manifest.json` is byte-compatible
  with the legacy one apart from `archived_at`
  (`archive.py`'s own module docstring, cross-checked against
  `_manifests_match_ignoring_archived_at`, `archive.py:856-875`, which
  strips exactly that one field before comparing).
* *Destination shape.* `destination_for` (`archive.py:746-749`) reproduces
  the existing `archive/<domain>/<workstream>/<attempt_id>` /
  `archive/unclassified/<attempt_id>` layout the sibling repository already
  uses.
* *Commit mechanics.* Both use the one Coordinator-owned bounded commit
  primitive (`git_facts.bounded_path_commit`); the subject
  (`evidence: archive <attempt>`) is unchanged.

Acceptable, documented differences (name these in the acceptance record so a
reviewer does not mistake either for a defect):

* *Commit body.* The legacy wrapper wrote a rich identity/file-count
  narrative into the commit body; the bounded primitive commits a bare
  subject with no body, so the same narrative is printed to stdout as a
  report instead (`archive.py` module docstring). Acceptable: the facts move,
  they are not lost.
* *Attempt-identity derivation.* The product derives the Attempt id
  deterministically from `repository_name` + the engine's own `run_id`
  (`postrun.py:86-100 _attempt_identity`), explicitly *never* from the engine
  state root's directory name; the postrun path passes that explicit value
  through `validate_explicit_attempt_identity` (`archive.py:567`), which
  `archive_run` uses whenever an explicit `attempt_identity` is supplied
  (`archive.py:1021`). The Harness instead uses whatever string the operator
  chose at `prepare --attempt`, validated by `validate_attempt`
  (`scripts/wfc_op.py:176-198`), which names both roots (`ops_root`/
  `state_root`, `scripts/wfc_op.py:201-206`), is consumed at
  `scripts/wfc_op.py:778`, and is recorded as `attempt_id=` by
  `write_preparation_pins` (`scripts/wfc_op.py:569-582`); the legacy archiver
  then re-derives the same string from the state root's own basename. The
  product retains that identical basename-derivation logic as its own
  `derive_attempt_id` (`archive.py:545`), for byte-identical legacy behaviour
  when no explicit identity is given (`archive.py:1008-1022`), but the
  product lifecycle itself never calls it that way -- `postrun` always
  supplies the explicit, Run-derived identity instead. The two proof Runs
  will therefore carry differently *shaped* Attempt identifiers (e.g.
  `workflow-coordinator-<run-id>` versus a hand-chosen
  `wfc-<slug>-<date>-<n>`); this is an acceptable, already-decided difference
  in identity derivation, not an equivalence failure.
* *Sanitized audit/report.* `audit.json` (BP6a/BP6b) is a genuinely new
  artifact beside the manifest, already independently accepted; its presence
  is an addition, not a compatibility requirement the legacy archive needs to
  match.

How equivalence is demonstrated without a second archive path: this
repository already contains the comparison, committed and passing --
`tests/unit/test_archive_equivalence.py`'s
`test_old_and_new_archivers_produce_identical_manifests_for_the_same_real_run`
(lines 154-191) runs the frozen legacy wrapper (`tests/fixtures/bp5/legacy/
wfc-archive-run`, hash-pinned in `setUp`, lines 147-152) and
`frontdoor.archive.archive_run` end to end, each against its own disposable
*copy* of the same retained Run's STATE/OPS facts
(`tests/fixtures/bp5/real_run/`, provenance in
`tests/fixtures/bp5/PROVENANCE.txt`), into two throwaway Git Evidence
repositories, and asserts the two resulting `manifest.json` files are equal
once `archived_at` is stripped -- a stronger check than comparing extracted
facts alone, since it exercises both archivers' full file-copy and commit
paths, not just `archive.py:454 extract_facts`/`archive.py:621 run_identity`
in isolation. It never invokes `scripts/wfc_op.py archive` a second time
against the real Evidence repository for the same proof Run; doing so would
create a second archive path beside the product function, which the
maintainer specification explicitly forbids. Sub-Commission C1b (see
<<sequence>>) generalizes this already-accepted BP5 module so the same
disposable-copy, two-archiver comparison can be pointed at each proof Run's
own retained facts, rather than building a new comparison from nothing.

The curated `workflow-coordinator-run-evidence/project_memory/
run_ledger.adoc` stays exactly as described in
link:../../../operator_manual/ch04_evidence/02_archive.adoc#semantic-ledger[the
manual's semantic-ledger section]: maintainer-owned, commonly LLM-assisted,
performed separately against the already-archived mechanical facts, never
automated by either path. BP7 adds two ordinary ledger entries, one per proof
Run, following the existing convention; this plan does not change ledger
curation.

[[sequence]]
== 4. Sequence and sub-Commissions

Decomposition of the single BP7 Commission the execution plan already names
(`wfc-beta1-bp7-self-development-cutover-001`) into independently testable
steps. Every step before "C5 retirement" still executes through the
*existing* self-development route (`scripts/wfc_op.py`), per the epic's own
convention that "only BP7 switches self-development itself onto the new
path" -- the retirement Commission is the one that finally performs that

[[risks]]
== 5. Risks and bootstrap

*Runtime N executing Development N+1.* Unchanged in principle by the
cutover: `ch05_self_development/01_topology_budget.adoc`'s invariant
("Accepted Runtime WFC N ... never mutates itself") still normatively
applies. But DG-5 removes the Harness's *fresh-export-per-Attempt* step
(`export_runtime`, `scripts/wfc_op.py:400-424`), which is exactly what
guaranteed Runtime stayed frozen even while Development's own working tree
was being edited by the same self-development Run. The product's
`_default_engine_command` (`frontdoor/lifecycle.py:77-93`) simply finds
`wfc` next to the running interpreter or on `PATH`. *If that resolves to an
editable install of the very Development checkout under modification*, a
Hop editing `src/workflow_coordinator/...` could change the behavior of a
still-running or later Hop before any maintainer promotion -- a real
bootstrap hazard DG-5 introduces by removing the export step, not by
removing the underlying freeze requirement. Mitigation (a precondition, not
a code change this plan performs): before Proof Run 1, the maintainer
installs the accepted Runtime commit into a separate, non-editable
environment (a wheel or `pip install` of a `git archive` export of that
exact commit, prepared once per promotion rather than fresh per Attempt --
the same shape `export_runtime` already used, just promotion-scoped instead
of Attempt-scoped) and ensures *that* installation, not the live Development
checkout's own environment, is what `_default_engine_command` actually finds
first.

*Rollback.* Forward-only by default, consistent with
link:../../../operator_manual/ch06_recovery/01_outcomes.adoc[the existing recovery
contract]'s central invariant ("the historical Run record itself is never
rewritten"). If either proof Run fails to complete or archive cleanly, there
is no BP7-specific rollback mechanism to build: the response is the existing
four-outcome recovery procedure (same-Run reconcile, maintainer salvage plus
a fresh successor, forensic preservation, or discard), and a fresh proof-Run
attempt is separately authorized. The old Harness path remains intact and
regular throughout -- nothing is removed until C5, which does not start
until both proofs succeed.

*Retained legacy path during the proof Runs.* Both paths coexist
deliberately (the second-pass review's own migration "Bridges" table marks
this temporary-until-cutover). Procedural rule for the proof Runs: each
proof Run commits through *exactly one* archive path -- its own automatic
BP6c postrun archive. It must never also be archived a second time through
`wfc_op.py archive` for the same Attempt; doing so would create two
different Attempt identities for the same work and violate "no second
archive path beside the product function."

*Scratch/inode hygiene.* As found in <<gap-analysis>>, the product has no
scratch allocator at all. Under DG-5 this becomes the consumer-provided
environment's responsibility; `ch05_self_development`'s existing "Temporary
storage before test-heavy Runs" guidance (space/inode checks, keeping
`TMPDIR` off the small `/tmp` tmpfs) remains necessary after cutover and must
not be silently dropped -- C5's manual edit should cross-reference it as
still-binding operator discipline, not retire it.

*Preconditions before Proof Run 1 starts:*

. BP1-BP6 Runtime-promoted by the maintainer.
. C1 (config + guidance) and C1b (equivalence harness) independently
  accepted.
. A separate, non-editable Runtime-N environment installed and verified
  first-found by `_default_engine_command` (the bootstrap mitigation above).
. `TMPDIR`/scratch prepared per the existing ch05 guidance (unchanged by
  this plan).
. The real sibling Evidence repository confirmed reachable at
  `../workflow-coordinator-run-evidence` relative to the actual Development
  checkout being used -- not a scratch clone lacking that sibling.
. That sibling Evidence repository's own root `.gitignore` confirmed not to
  exclude `audit.json` at the Attempt's destination: every raw retention mode
  commits it, and `archive._assert_audit_path_not_ignored`
  (`frontdoor/archive.py:254-267`) refuses the whole archive before any write
  if a pattern (for example a broad `*.json`) excludes it; `raw: commit`'s own
  raw files (`manifest.json`, `run/**`, `ops/**`) are separately re-included
  by a per-Attempt `.gitignore` the archiver writes into the Attempt's own
  destination (`_ATTEMPT_COMMIT_GITIGNORE`, `archive.py:165-171`, written at
  `archive.py:1229`), which cannot by itself fix an `audit.json` exclusion

  precondition to verify on the actual deployment, not assumed clear here.
