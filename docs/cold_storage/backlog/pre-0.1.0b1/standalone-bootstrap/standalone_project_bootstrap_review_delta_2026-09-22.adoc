== 3. Findings

=== 3.1 IMPORTANT

==== I-4R -- Evidence resolution is proven in the wrong process environment, and section 7.3 claims a proof the test cannot deliver

Category:: A -- plan contradiction against observed behavior
Closes:: incompletely; I-4 residue
Changes:: plan only; no architecture change

Exact correction text:: Section 6.1.2: "Its `bin` directory is placed first on
the Coordinator's captured `PATH`". Section 6.1.1: "puts that environment's
`bin` directory on `PATH`". Section 7.3: "The architecture test proves that the
selected evidence executable resolves in the captured Coordinator environment."
Slice B2 acceptance: "from the development root, the exact committed evidence
argv resolves and completes successfully."

Problem:: `+snapshot_environment+` (`+evidence.py+`:84) captures `+os.environ+`
of the *running Coordinator process*, and `+resolve_executable+`
(`+evidence.py+`:125-136) returns the first `PATH` entry that yields an
executable regular file. The environment that decides which `python` runs
evidence is therefore the one the runtime-launched Coordinator inherits.
+
Neither proof the correction schedules observes that environment. The
architecture test captures the pytest process environment; the B2 evidence run
captures a shell in the development/evidence environment; `wfc --help` is run
separately "from the external runtime environment". Section 7.3's sentence is
consequently not true as written -- the test proves resolution in the test
runner's environment, not in the Coordinator's.
+
The two environment requirements are also unreconciled. Section 6.1.1 puts the
runtime environment's `bin` on `PATH`; a virtual environment's `bin` always
contains `python`, and the runtime install is a plain non-editable install of
the runtime export, so it carries no `dev` extra and no `pytest`
(`+pyproject.toml+` defines `dev = ["build>=1.2", "pytest>=8.2"]`). Section
6.1.2 requires the development/evidence `bin` to be *first*. Ordinary virtual
environment activation prepends the activated environment's `bin`, so the
natural way to launch runtime `wfc` places the runtime `bin` ahead of the
development/evidence `bin`. The plan states both requirements and never says how
a single launch satisfies them together, and sets no acceptance criterion on the
one `PATH` the Coordinator will actually capture.

Consequence:: Under that ordering, admission still succeeds, because the runtime
environment does provide a resolvable `python`. The failure surfaces later:
evidence is observed at `+vertical.py+`:254, *after* `+adapter.execute+` at
`+vertical.py+`:172, which is past the provider-capable boundary. The first
dogfood Hop therefore spends a real provider invocation and then fails
`python -m pytest -q` on a missing `pytest` module, exiting 1. I-4's objection
was that bootstrap would declare readiness while the first Run failed at
precisely the wrong moment; this residue preserves that failure and moves it from
exit 2 before any provider to exit 1 after one, which is worse-positioned rather
than closed.

Smallest bounded repair:: Two edits, both plan-only.
+
. Replace section 7.3's claim with the truthful one: the architecture test proves
  the committed argv resolves *in the environment that runs the test suite*.
. Add one Slice B2 acceptance criterion binding the single launch `PATH` the
  Coordinator captures: the development/evidence `bin` precedes the runtime
  `bin` on it; the runtime `wfc` is invoked by its absolute path within the
  runtime environment rather than by `PATH` lookup; and under that exact `PATH`,
  `+prepare_evidence_commands+` resolves `python` to the development/evidence
  interpreter. Record the captured `PATH` order as B2 evidence, still without
  committing a machine-specific absolute path.

=== 3.2 MINOR

==== M-7 -- The governance architecture test becomes environment-dependent, and the plan does not say so

Category:: D -- documentation clarity

Section 7.3 routes the primary proof through production `+_preflight+`, which
calls `+prepare_evidence_commands+` and therefore resolves `python` against the
test process `PATH`. On this host `python` does not resolve at all: `python3` is
`/usr/bin/python3` with no `pytest` module, and neither Workflow Coordinator
clone has a virtual environment. The new guard consequently fails for purely
environmental reasons whenever the suite is launched other than from the
development/evidence environment -- for example by `python3 -m pytest`.

This is a deliberate and correct consequence of closing I-4 by real resolution
rather than by assertion, and failing closed is the right direction. It is worth
stating so that the failure is read as a missing environment rather than as a
broken governance bundle.

Smallest correction:: One sentence in section 7.3 or Slice B2 recording that the
governance architecture test requires the development/evidence environment,
so the full suite is run through the committed `python -m pytest -q` argv.

==== M-8 -- Two of the four required Make targets cannot be verified inside the first Run

Category:: A -- plan contradiction, small

Section 8.1 requires "a small Makefile with `make test`, `make lint`,
`make format-check`, and `make check`". Section 7.1 now fixes the policy at
exactly one evidence command, `python -m pytest -q`, and the development/evidence
environment is prepared from the `dev` extra before the Run. That extra is
`build` and `pytest` only; Ruff is absent. The agent may add Ruff configuration,
because `+pyproject.toml+` is in scope, but a dependency added during the Run is
not installed into an environment prepared before it, and no evidence command
exercises lint or format.

The authority boundary is unaffected -- this cannot widen scope, and it fails
closed. The gap is truthfulness: two of the four required targets will be
authored unverified, and the first dogfood's empirical record (section 8.3)
should not read that as success.

Smallest correction:: Either pre-provision Ruff in the development/evidence
environment alongside the `dev` extra, or state in section 8.1 that lint and
format-check targets are authored but not executed within the first Run and are
verified by the maintainer at acceptance.

== 7. Four-Hop semantics

The ceiling is coherent and the plan states the actual behavior truthfully.

`+COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS+` is 5 and `hop_limit` comes from
`WorkItem.max_autonomous_hops` (`+model.py+`:400), which `+_admit_a1+` caps at
both the hard maximum and the policy maximum. With both set to 4, the sequence
investigate H001 -> review H002 -> correct H003 -> rereview H004 fits exactly.

* Only one correction and re-review cycle is possible: a second cycle would need
  H005 and H006.
* Acceptance completes in four Hops. At rereview the `accept` route has effect
  `complete`, which is neither `goto` nor supervisor, so `invocation_needed` is
  false and the Run completes at H004.
* A rereview finding cannot cause an unauthorized autonomous H005. The `correct`
  route is `goto`, `hop_used` equals `hop_limit`, and `+reducer.py+`:425 stops
  the Run as `AWAITING_HUMAN_BUDGET`.

The plan's own sentence -- "A finding at the final re-review stops for the
maintainer rather than starting a second cycle" -- is mechanically exact. Its
explicit refusal of the engine's nominal fifth spare Hop is a deliberate
least-authority choice and is correctly not disturbed here.

The committed fixture `+tests/fixtures/slice5b_non_dmc.yaml+` already realizes
this shape with `max_autonomous_hops: 4` in both WorkItem and policy, the same
four phases with the same durable-artifact modes and action sets, the same
`durable_artifacts` mapping of `review`, and the same route set including
`accept: {effect: complete}` and `correct: {effect: goto}`. Slice B2 is
transcription, not design.
