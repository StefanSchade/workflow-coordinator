= `simple@v1` Level-0 architecture design (2026-10-31)
:toc:
:toclevels: 2
:sectnums:

Status:: *Design for a separately authorized implementation only.*
Scope:: One deliberately small vertical slice: a closed `simple@v1` programme.
Implementation authority:: None. This document neither changes a programme nor
authorizes a Runtime, schema, test, governance, or Commission change.
Source baseline:: Development `e49de08dc21139b4e93636681af2d694341eadd6`.

The 2026-10-31 capability decision makes `simple` an MVP requirement, but does
not make it an alias for `direct` or `robust`.  Capability (`simple`), programme
revision (`simple@v1`), representation schema, and Runtime Git revision remain
four independent dimensions (capability decision record §5).  This design does
not promote P3.5, change either existing programme, or introduce a general
workflow/evidence framework.

== 1. Requirements and explicit non-goals

`simple@v1` has exactly one Worker provider invocation in ordinary execution.
The Worker performs its own task/self-check in that one invocation.  Afterwards
the Coordinator may perform deterministic mechanics, including trusted evidence
commands; those subprocesses are not agent invocations.  There is no independent
reviewer, verification Worker dispatch, correction loop, retry, or continuation
inside the Run.  A success assertion is only an untrusted proposal: Coordinator
Git/scope/commit checks and mandatory evidence decide whether completion is
allowed.

The programme must fail closed for an invalid/failed result, dirty or
out-of-scope change, untrusted-commit failure, evidence error/failure, missing
provider result, infrastructure interruption, or escalation.  Human authority
or a separately authorized successor may address a stopped Run; it is not a
second Simple invocation.

Non-goals are a workflow DSL, catalogue/capability registry, evidence pipeline,
P3.5 implementation, profile migration, Runtime promotion, changes to
`direct@v1`/`robust@v1`, and a claim of generic historical compatibility.  The
Level-0 planning record and active-work manifest identify `simple` as NEXT/MVP
scope, not implemented work; that ordering and the Claude/token MVP items are
unchanged.

== 2. Current-code assessment with source references

The following references were independently checked at the stated baseline;
they are observations, not reused P3.5 line citations.

* Commission parsing presently rejects Simple twice: `commission_intent_from_yaml`
  has only Direct and Robust persona pairs at
  `src/workflow_coordinator/commissioning.py:177-209`; `_load_sources` has only
  their catalogue/template/component entries and rejects every other pair at
  `:318-352`.  Rendering projects programme roles, evidence and scope slots at
  `:367-425`, and labels the rendered WorkItem with programme id/revision at
  `:433-440`.  There is therefore no Simple catalogue/template/Intent persona
  binding today.
* The compiler's current selected-component provenance is narrower than runtime
  prompt selection.  `render_commission` collects only each phase's
  `components.role` at `commissioning.py:442-446`, then derives both pinned
  source digests and `selected_components` manifest records from that truncated
  mapping (`:448-460`).  In contrast, operator `_selected_ids` selects role,
  modifier, *and* repository-policy components (`operator.py:107-112`) and
  preflight loads those IDs from expected HEAD (`:437-446`).  The Front Door
  only byte-compares the component-manifest plus entries the renderer supplied
  (`commissioning.py:513-518`).  A Simple-only modifier would therefore be
  dispatched without a pinned-source byte comparison unless the renderer's
  existing traversal is completed.
* Preflight pins a clean expected HEAD and parses all governing inputs at
  `operator.py:281-323`; it checks exact role/binding agreement, actions and
  phase scope containment at `:324-367`, A1 governance/scope/hop relations at
  `:138-201`, evidence-command definitions at `:204-218`, and prepares command
  identities at `:451-467`.  `_prepared_evidence_plan` records command digest,
  timeout, resolved executable/stat fingerprint and PATH digest at `:598-626`.
* The current admission obstacle is precise: `_admit_evidence_disposition`
  rejects every evidence-bearing phase unless it has a `gate` review and a
  `failed_evidence_route` (`operator.py:123-135`).  It does *not* otherwise
  require a second phase.  Direct happens to have `implement -> verification`
  and Robust has review/correction phases because their closed records declare
  them, not because `new_run` or `record_hop` requires two Hops
  (`model.py:854-883`, `:886-914`).
* `select_result_contract` presently selects `WORK_RESULT` for every Worker
  with no review, `REVIEW_VERDICT` only for an independent reviewer with a
  review, and generic routing otherwise (`model.py:654-702`).  That is not
  sufficient as-is: `WorkStatus` admits only `completed` and `blocked`
  (`model.py:145-148`), and the strict Work-result projection repeats that
  two-value enum (`codex_adapter.py:294-301`; `serialization.py:1315-1317`).
  In contrast the existing generic routing contract admits `Outcome.FAILED`
  (`codex_adapter.py:105-109, :199`; `serialization.py:1214-1266`) and the
  reducer already makes it a terminal human stop before routes or Findings
  (`reducer.py:1660-1663`).  Existing route effects already include `complete`,
  `await_human`, and `stop` (`model.py:118-123`); `_apply_route` completes only
  when no blocking Finding remains (`reducer.py:1152-1188`).  Thus a new status
  or terminal primitive is unnecessary, but Simple needs a deliberately
  selected existing result family.
* The current vertical path already schedules evidence at the desired boundary:
  it dispatches and validates the one agent result (`vertical.py:284-341`),
  applies the trusted commit/scope boundary (`:342-413`), invokes evidence for
  the *current phase* (`:414-424`), checks that evidence did not alter HEAD or
  worktree (`:425-445`), then records/reduces the Hop (`:519-563`).  The serial
  driver invokes `run_real_one_hop` once per dispatched Hop
  (`operator.py:815-910`).  Thus evidence subprocess count must not be confused
  with agent-invocation count.  There is one required transport correction:
  after `adapter.execute`, current `run_one_hop` validates a present candidate
  without first making `AgentExecutionOutcome.returncode` or `timed_out`
  controlling (`vertical.py:324-341`), and records those fields only later in
  a staged attempt (`:499-500`).  `run_real_one_hop` already routes an
  `ExecutionResultValidationError` to `recover_uncertain`, which charges an
  uncertain dispatch and retains its marker rather than retrying
  (`slice4.py:332-354, :390-399`); the operator's local diagnostic records
  return code, timeout, candidate presence and tails as untrusted operational
  telemetry (`operator.py:686-720`).
* Reduction makes mechanical facts controlling: errors preempt to
  `awaiting_human` (`reducer.py:1621-1658`); a Worker `FAILED` also stops
  (`:1660-1666`); unknown route and inappropriate changes-required are stopped
  (`:1679-1692`).  Required evidence failure is routed before completion; absent
  a legal gate failure route it stops `required_evidence_failed_without_route`
  (`:1742-1757`).  Hop ceiling enforcement occurs before a route needing another
  invocation (`:1806-1835`), while `Run.hop_remaining` is defined at
  `model.py:649-651` and preflight applies the hard ceiling at
  `operator.py:193-200`/`:368-371`.

== 3. Proposed Simple programme and finite execution lifecycle

The future immutable catalogue record is `governance/workflow-programs/simple/v1.yaml`.
It has `roles: [worker]`, one `task-check-v1` evidence profile mapping only to
`[task-check]`, no durable artifacts, scope slot `S`, and one `implement`
phase:

[source,yaml]
----
role: worker
components: {role: [worker], modifiers: [simple-self-check], repository_policy: []}
durable_artifact: none
scope: S
authorized_actions: [edit, commit]
human_gates: []
evidence: E
review: null
routes: {accept: {effect: complete}}
----

`E` is always `[task-check]`; Simple v1 deliberately has no `none` profile.
`simple-self-check` is a new immutable manifest component at
`governance/self-development/prompts/simple-self-check.txt`.  Its closed text
instructs the Worker to perform the task's bounded self-check *before it emits
its sole result*, and to report a discovered task failure as `outcome: failed`
or an authority/dependency issue as `blocked`/escalation.  It does not declare
evidence passed, grant authority, or alter the shared `worker` component.
Consequently the instruction is programme-declared behavior selected and
source-pinned with the Simple programme, rather than optional maintainer task
prose.  That requires the narrow renderer correction specified in §7: the
render manifest must record every selected component category, not merely role
components.  Direct and Robust continue to select only `worker`.

The Simple terminal-worker shape deliberately selects the existing generic
`structured_result_v1` (not `work-result_v1`): `outcome` is `completed`,
`blocked`, or `failed`; the strict route enum permits only `accept`.  A
`changes_required` generic result remains mechanically stopped because a
review-less phase cannot take that outcome (`reducer.py:1687-1691`), so it is
not a hidden correction route.  Only `completed` may request `accept`.  The
finite lifecycle is:

`PREPARE/admit -> dispatch Worker once -> trusted commit/scope observation ->
trusted evidence -> reduce -> COMPLETED | AWAITING_HUMAN | RECONCILE_REQUIRED`.

No `goto` exists in this programme.  A human stop is terminal for autonomous
Simple execution, rather than an instruction to dispatch the Worker again.

== 4. Exact one-invocation contract

Set `max_autonomous_hops: 1` in every Simple Intent and retain the normal
hard/policy ceiling.  The operator dispatch loop counts provider calls through
accepted Hops; a Simple run must record exactly H001 and no H002.  The Worker
is required by the selected Simple-only component to self-check before
submitting its one result, but that self-check is not trusted evidence and
cannot make a failed Coordinator observation pass.

Terminal outcome mapping reuses existing states:

* Valid Worker completion, trusted commit/scope checks, and all evidence pass:
  `accept -> COMPLETE`.
* Worker `blocked`, `failed`, escalation, or `requires_human`: existing
  `AWAITING_HUMAN` stop (`result_blocked`, `result_failed`, or mechanical human
  authority preemption).  `failed` is a correlated generic-routing result, so
  it is distinct from blocked and reaches the existing `result_failed` guard.
* Invalid result, commit/scope/Git/governing identity fault: existing mechanical
  preemption to `AWAITING_HUMAN`.  A missing result or nonzero/timed-out
  provider transport before semantic acceptance becomes
  `RECONCILE_REQUIRED` through existing uncertain-dispatch recovery, never a
  completed Hop.
* Evidence fail/error/not-run: `AWAITING_HUMAN`, never `COMPLETE`.
* Provider interruption/no validated candidate: preserve the current uncertain
  dispatch/recovery outcome, not a fabricated completed Hop.

Pre-dispatch preflight refusal has no Run/Hop and therefore no terminal Simple
Run; this differs from post-dispatch faults, which retain the charged H001 for
diagnosis.  The `DispatchMarker` and recovered `uncertain_dispatch` Hop are the
durable recovery record; the best-effort local diagnostic is explicitly
untrusted and is not qualifying evidence.  No recovery branch dispatches a
replacement Worker for this Run.

== 5. Trusted evidence scheduling and failure behavior

Three alternatives were assessed.

A. Add a new post-Worker Coordinator evidence operation.  This could express
the boundary explicitly but duplicates `vertical.run_one_hop`'s existing
post-agent/pre-reduction observation, requires new persistence/recovery
correlation rules, and risks creating a second orchestration subsystem.

B. Reuse that existing seam for a review-less terminal Worker phase.  Evidence
already executes after the agent and before reduction, with prepared command
identity and execution evidence/provenance.  Its sole incompatibility is the
over-broad preflight gate requirement above.

C. Admit only a no-evidence Simple MVP.  It avoids code but contradicts the
binding requirement that mandatory Coordinator validation/evidence remain and
does not demonstrate failure behavior for a real required check.

*Recommendation: B.*  Make one narrow, backward-compatible change to
`_admit_evidence_disposition`: continue to admit the present gate-with-failure-
route pattern unchanged, and additionally admit an evidence-bearing phase only
when it is the closed review-less Simple Worker terminal shape defined below.
For this shape, evidence failure deliberately takes the current reducer's
fail-closed `required_evidence_failed_without_route` human stop rather than a
correction route.  The compiler's exact Simple template supplies the stronger
one-phase/`accept` shape; the admission predicate prevents an arbitrary
evidence-bearing looping worker phase.  No new evidence type, runner, command
format, or non-agent phase is added.

This uses the current generic result technical schema rather than widening the
immutable Work-result v1 enum for every existing review-less Worker.  A small
shared selector predicate must therefore select generic routing only for the
closed Simple shape: a one-phase profile; Worker; no review; exactly
`[simple-self-check]` modifiers and `[task-check]` evidence; no convergence;
and exactly one route, `accept: complete` (no target, question, or supervisor).
`_admit_evidence_disposition` must use the same predicate (or a shared helper)
before applying the terminal exception.  The closed compiler template is the
authority that supplies this shape; the predicate prevents the exception
becoming a generic loop or an arbitrary evidence-bearing Worker mechanism.  The
existing `MechanicalFacts.required_evidence_*` path decides after the evidence
observation.  This has better recovery/provenance than a new hook because the
staged execution-evidence record already includes required command identities
and observations (`vertical.py:446-518`).

== 6. Findings and terminal-state semantics

FD-08 was not a reducer failure.  Its H002 opened F001; H004 requested accept
but Direct's gate had `finding_authority: []`, so completion correctly stopped
with `completion_blocked_by_open_blocking_findings` (BUG record
§“FD-08”, especially lines 177-205).  A gate's disposition operations are
independent of gate authority.

Source inspection also establishes that lack of a review descriptor does *not*
forbid creation.  `_finding_operation(None, OPEN)` is `None`
(`reducer.py:470-486`), and legacy v1 processing allocates/records a new
Finding without calling `_may_dispose` when that operation is `None`
(`:566-618`).  `reduce_result` gives a review-less Worker `AGENT` authority
and no disposition operations (`:1693-1721`), while `_may_dispose` permits
only HUMAN or gate-listed operations (`:489-498`).

Therefore Simple v1 permits a Worker to create a Run-native Finding, but only
with constrained terminal semantics: it must report `blocked`/human escalation
when its self-check identifies an issue; a blocking Finding also independently
prevents `complete` (`:1145-1174`).  It cannot repair, review, or dispose it in
another Simple Hop.  Human authority decides disposition or launches a new
Commission; the successor cannot mutate the predecessor ledger.  This prevents
the FD-08 silent-acceptance shape without pretending that a no-review phase
cannot create Findings.  A non-blocking Finding may be recorded with a completed
run; it is not an open *blocking* governance dead end.  P3.5's explicit
creation capability and reachability check remain deferred, not prerequisites.

== 7. Required minimal schema/compiler/operator/reducer changes, if any

No profile/Run/result technical-schema bump, new `RunStatus`, route effect,
evidence serialization, or reducer change is required for this slice.  The
existing generic result schema is selected for Simple rather than altering
`WORK_RESULT` v1.  The future implementation changes are:

* add the immutable Simple catalogue record and its literal in-memory template,
  including `simple-self-check` as its sole modifier;
* add that Simple-only prompt file and its component-manifest entry.  In the
  existing `render_commission` selected-component comprehension
  (`commissioning.py:442-460`), replace the role-only traversal with the
  deterministic first-reference-ordered traversal of `role`, `modifiers`, then
  `repository_policy` for every phase.  The existing digest and
  `sources.selected_components` generation must consume that complete set.
  Consequently the already-existing `verify_render_manifest` pinned-blob loop
  (`:513-518`) byte-compares the Simple modifier too.  This is a bounded
  completion of an existing provenance path, not a second manifest, pinning
  system, or Front Door mechanism;
* add `("simple", "v1")` with `{worker}` to the two closed mappings in
  `commissioning.py`, allowing exactly one Worker persona and no artifacts;
* render the same schema-v2 profile/WorkItem/manifest shape and existing
  programme provenance labels; and
* add one shared closed-terminal-worker predicate: `model.select_result_contract`
  uses it to select existing generic routing for Simple's outcome-bearing
  result, and `_admit_evidence_disposition` uses it to admit evidence without a
  review gate.  All other present selector branches remain unchanged;
* immediately after `adapter.execute` in `vertical.run_one_hop`, reject a
  nonzero `returncode` or `timed_out` before candidate parsing, trusted commit,
  evidence, `record_hop`, or reduction, by raising
  `ExecutionResultValidationError(outcome, ...)`.  Existing
  `slice4.run_real_one_hop` then takes its no-replay `recover_uncertain` path;
  no new recovery state or evidence schema is introduced; and
* add focused commissioning/model/adapter/vertical/slice4/operator tests.

The strict provider schema, `adapter.validated_result`, and existing generic
parser/reducer already represent `failed`; the selector change makes those
seams apply to Simple.  The reducer's existing failure, evidence-failure, and
completion-blocker guards then enforce the semantics.  Direct and Robust
catalogue literals, component selections, mappings, and runtime behavior are
unchanged.

== 8. Comparison of alternatives and rationale for the chosen design

The recommendation is smallest because it uses the existing trusted command
preparation, execution, post-evidence Git check, Hop evidence record, reduction,
and terminal statuses.  A new post-Hop operation would need an atomic boundary
and recovery/provenance design; a synthetic second verification phase violates
the product contract; a gate descriptor on the sole phase would retain
unnecessary review semantics; and no-evidence Simple does not meet the stated
assurance goal.  The narrow admission relaxation is auditable, applies only to
a terminal Worker evidence shape, and leaves both established programme
revisions intact.

For the failure-result gap, widening `WorkStatus` would touch the strict
Work-result schema and silently change the ordinary review-less Worker contract
used by existing programmes.  Adding a new Simple-specific result family would
add model, strict-schema, parser, serialization and replay surface solely to
name an already represented outcome.  Selecting existing generic routing for
one closed shape is smaller and version-honest: no technical schema changes,
and the Worker receives the same family that already strictly encodes
`Outcome.FAILED`.

For transport, accepting a candidate then checking its transport would allow
commits/evidence to run after a failed provider process.  The chosen early
guard instead reuses the current uncertain-dispatch marker/reconciliation
boundary.  It is intentionally not a Worker failure: the semantic candidate is
untrusted because the provider transport did not complete cleanly.

== 9. Trust-boundary and provenance preservation

The Worker never chooses evidence argv, timeout, executable identity, policy,
route map, or programme revision.  Intent pins the programme/policy/component
source commits; `_load_sources` requires byte-equivalent literal programmes
(`commissioning.py:331-350`).  The renderer correction in §7 makes its
source-digest and selected-component records cover role, modifier, and
repository-policy inputs, matching `_selected_ids` (`operator.py:107-112`).
The Front Door then rerenders pinned sources, byte-compares the bundle, and
byte-compares every selected component to the Intent's component source object
(`commissioning.py:490-518`) before canonical preflight.  Normal preflight
retains clean HEAD, policy scope, governing input, role/binding and action
checks.

At execution the Coordinator owns provider-transport acceptance before any
candidate is acted upon, trusted commit landing and allowed-path validation
(`vertical.py:342-407`), evidence command execution and post-check repository
observation (`:414-445`), and reduction.  A Worker self-check, summary, or
evidence reference remains agent-attributed information, not proof that the
Coordinator command passed.  After the bounded compiler correction, the
selected Simple-only prompt is included in the complete manifest source-digest
set and pinned/rechecked by Front Door through the existing loop; the execution
record retains adapter, executable/model/reasoning binding and required-evidence
identity, preserving both executable and source provenance.

== 10. Focused test and real dogfood acceptance plan

The implementation WorkItem should add focused unit/integration tests that:

* render/admit Simple with one Worker, one phase, `task-check`, no artifact,
  `max_autonomous_hops: 1`; reject extra persona/artifact, `none` evidence,
  modified route/evidence/action/Finding authority, a missing/altered
  `simple-self-check` component-manifest source or selected-component digest,
  or nonliteral programme.  In particular, construct a pinned component
  manifest whose modifier bytes differ at expected HEAD from
  `components_ref.source_commit`; Front Door must reject it before operator
  dispatch.  Assert that all role/modifier/repository-policy selected entries
  are rendered and byte-checked, while Direct and Robust manifests remain
  byte-identical because their latter two lists are empty;
  assert the rendered prompt includes that component while Direct and Robust
  projections do not change;
* instrument the adapter and evidence runner separately: exactly one adapter
  invocation, while one Coordinator evidence subprocess is expected;
* complete only when a valid Worker result, trusted in-scope commit, clean
  post-evidence repository, and passing evidence are all present;
* assert the Simple dispatch projects generic `structured_result_v1`, accepts a
  correlated `outcome: failed`, and reaches existing `result_failed` without a
  second invocation; assert `blocked` and escalation remain separately
  represented and `changes_required` cannot route a review-less Worker;
* prove failing/error/not-run evidence cannot apply `accept`, scope-exceeding
  changes/commit intent cannot complete, and an evidence-bearing Worker with a
  `goto`, supervisor, human-route, extra route, missing Simple-only modifier,
  or non-`accept` terminal profile is preflight-rejected;
* inject both a nonzero-with-valid-correlated-candidate and a
  timeout-with-valid-correlated-candidate transport outcome.  In each case
  assert no trusted commit/evidence/reduction-to-complete occurs, exactly one
  provider call is charged, the dispatch marker/recovered uncertain Hop remains,
  and diagnostics record the transport fact; also retain missing-result and
  launch/interruption coverage;
* prove a Worker-created blocking Finding stops completion/human-escalates and
  is never silently terminally accepted; and
* retain Direct and Robust render/preflight and their existing execution tests
  unchanged as regressions, including programme/pin and executable provenance.

First dogfood is one small real maintenance change with a bounded source/test
scope and its actual task check, not a fixture that merely returns success.  Its
acceptance record must show one provider invocation versus the separate command
count, source commit/digests, binding/executable identity, commit/scope facts,
and the trusted evidence observation.

== 12. Unresolved decisions requiring maintainer authority

* Whether Simple v1's sole mandatory evidence should be the current
  repository-standard `task-check` only, as recommended, or whether a later
  immutable Simple revision should define another closed evidence profile.
* Whether non-blocking Worker-created Findings should be prohibited in a future
  Simple revision.  Prohibiting them truthfully requires an explicit creation
  capability/result restriction and is not silently supplied by this design.
* Whether the narrow terminal-worker evidence admission remains an acceptable
  shared Runtime rule after real dogfood.  It must not be broadened into a
  generic post-phase pipeline without separate authority.
* The capability/revision/schema/Runtime compatibility declaration and
  retirement policy remain the separately recorded future Front Door work; this
  design records all four dimensions but does not create that mechanism.
