== What this is not

No reproducing test exists and no actual incident has been observed. This
record is a source-inspected possibility, independently confirmed by direct
reading of the current code at the stated Development commit, not an
empirical defect report. It does not characterize the existing
`recover_uncertain`/uncertain-dispatch recovery mechanism, `DEC-WFC-013`, or
the fail-closed `reconcile_required` outcome as defective; that mechanism is
sound for the case it currently covers (no candidate present). This record is
narrowly about the case where a candidate *is* present despite failed
provider transport.

This record does not characterize a Worker-reported task failure
(`outcome: failed` in a correlated, valid structured result) as a defect of
any kind. That is working as intended and is a distinct code path from the
one described here. The defect under investigation is specifically that the
Coordinator does not yet distinguish "the provider process itself did not
complete cleanly" from "the provider process completed and returned a
semantically valid result" before deciding whether that result's meaning
matters.

== Observed current behavior (source-inspected)

`src/workflow_coordinator/vertical.py`'s `run_one_hop` calls
`adapter.execute(...)` and binds the full `AgentExecutionOutcome` to
`outcome` (`vertical.py:324-329`). It then branches only on
`outcome.candidate_result`:

[source,python]
----
outcome = adapter.execute(AgentExecutionRequest(...))
if outcome.candidate_result is None:
    raise ExecutionResultValidationError(outcome, "agent execution produced no candidate structured result")
try:
    result = validated_result(
        outcome.candidate_result, invocation, selected_result_contract_version, selected_result_contract,
    )
except ResultValidationError as error:
    raise ExecutionResultValidationError(outcome, str(error)) from error
----

(`vertical.py:324-341`). `AgentExecutionOutcome` (`adapter.py:61-73`) carries
`candidate_result: str | None`, `returncode: int | None`, and
`timed_out: bool` as independent fields. Nothing between `adapter.execute`
returning and `validated_result` being invoked reads `outcome.returncode` or
`outcome.timed_out`. If a provider process exits nonzero, or times out, but
still emits a syntactically valid, schema-conformant structured result on its
output channel before terminating, `outcome.candidate_result` is non-`None`
and `validated_result` succeeds. Parsing then proceeds into the trusted
commit/scope boundary (`vertical.py:342-413`), Coordinator evidence
(`:414-424`), the post-evidence repository check (`:425-445`), and reduction
(`:519-563`) exactly as if provider transport had completed normally.

Both `outcome.returncode` and `outcome.timed_out` are read later, but only
for untrusted operational diagnostics: `operator.py`'s `_summary` (around
`:999-1002`) and `_best_effort_failure_summary` (around `:1044-1047`) each
fold them into a `provider` dict as best-effort telemetry (consistent with
the existing propagation gap described in
`BUG-WFC-OPERATOR-DIAGNOSTIC-PROPAGATION.adoc`), not as a controlling input
to whether the candidate is acted upon.

`slice4.py`'s `run_real_one_hop` already has a no-replay recovery path for
exactly the case this record is concerned with keeping distinct: catching
`ExecutionResultValidationError` and calling `recover_uncertain(error.outcome, str(error))`
(`slice4.py:390`), which retains the charged dispatch via
`recover_uncertain_dispatch` and does not dispatch a replacement Worker
(`slice4.py:332-354`). That recovery path is only reached today when
`candidate_result is None` or fails schema validation -- not when a
nonzero-exit or timed-out transport still yields a validator-passing
candidate.

== Why this is undesirable

A provider process that exits nonzero or times out has not demonstrated that
it completed its invocation cleanly. Treating any syntactically valid output
it happened to emit as an authoritative semantic result conflates two
distinct facts that the current data model already keeps separate
(`AgentExecutionOutcome.returncode`/`timed_out` vs. `candidate_result`): that
the provider *transport* completed, and that the provider *produced a
result*. A result correlated with failed transport should not be trusted
merely because it parses -- the process's own abnormal exit means the
Coordinator has no basis for confidence that the output is complete, was not
truncated or interleaved with a crash, or reflects the provider's actual
final state. This is distinct from, and must not be confused with, a Worker
that completes cleanly and *reports* `outcome: failed` -- that is a
correlated, trusted-transport result and must continue to be accepted and
routed normally.

This is a general shared-execution-invariant gap in the current vertical
Hop boundary -- it is not specific to any one programme capability -- but it
is surfaced here because the accepted `simple@v1` design (§4, §8) explicitly
requires it as a precondition: Simple's exactly-one-invocation contract
depends on failed provider transport never completing a Hop, since there is
no independent reviewer able to catch a wrongly-accepted candidate
afterward.

== Proposed correction (not authorized by this record)

Add an early guard immediately after `adapter.execute` returns in
`vertical.run_one_hop`, before `outcome.candidate_result` is read or
`validated_result` is called: if `outcome.returncode` is truthy and nonzero,
or `outcome.timed_out` is `True`, raise the existing
`ExecutionResultValidationError(outcome, ...)` unconditionally, regardless of
whether `outcome.candidate_result` is present. This reuses the existing
exception type and the existing no-replay `recover_uncertain` path in
`slice4.run_real_one_hop` (`slice4.py:386-390`) without introducing a new
recovery state, retry mechanism, evidence schema, or Worker-failure
taxonomy. The dispatch marker and recovered `uncertain_dispatch` Hop remain
the durable recovery record, exactly as they are today for the
already-handled missing-candidate case; only the guard's trigger condition
widens.

This preserves the existing boundary completely: no trusted commit, no
Coordinator evidence subprocess, and no `record_hop`/reduction may run for a
Hop whose provider transport did not complete cleanly, matching the
"provider-transport acceptance before any candidate is acted upon" invariant
already stated for the Coordinator in
`docs/warm_storage/concepts/workflow_coordinator_simple_v1_architecture_design_2026-10-31.adoc`
§9.

== Required negative tests (not yet written)

A correction commission must add, at minimum:

* a nonzero-`returncode`-with-valid-correlated-candidate case: assert no
  trusted commit, no evidence subprocess, and no reduction to a completed Hop
  occurs; assert exactly one provider call is charged; assert the dispatch
  marker and recovered `uncertain_dispatch` Hop remain; assert the local
  diagnostic still records the transport fact.
* a `timed_out=True`-with-valid-correlated-candidate case with the same
  assertions.
* a regression proving the existing missing-candidate and
  schema-invalid-candidate paths are unchanged.
* a regression proving a clean-transport (`returncode == 0`,
  `timed_out is False`) candidate with a correlated `outcome: failed` result
  is still accepted as a valid, routable Worker result (i.e., the guard must
  not be confused with, or substitute for, ordinary Worker-failure handling).
