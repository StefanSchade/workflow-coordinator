== 1. Root-cause fit

The BUG's root-cause classification is that
`structured_result_envelope_openai_schema()` projected `run_id`/`hop_id`/
`invocation_id` as unconstrained `{"type": "string"}`, asking the model to
regenerate Coordinator-owned deterministic identity as free text. The
candidate's only behavioral change is to that projection: each identity
field now projects as `{"type": "string", "enum": [<dispatched value>]}` via
a local `dispatched()` helper. Nothing else in the generative surface
(`result`, `routing_result_openai_schema()`, `schema_version`) is touched.
This is a narrow, exact fit to the classified defect -- it does not touch
semantic result content, `validated_result()`, or Hop/reducer mechanics.

== 2. Invocation-specific schema

Confirmed directly in `codex_adapter.py:125-146`:

* `run_id`, `hop_id`, `invocation_id` are each `dispatched(invocation.<field>)`
  = `{"type": "string", "enum": [value]}` -- exact dispatched value, explicit
  `type: "string"` retained (not dropped in favor of a bare `const`, which
  would fall outside `_STRICT_KEYS`).
* `structured_result_envelope_openai_schema()` now requires an `invocation:
  Invocation` positional argument; calling it with no arguments raises
  `TypeError` (verified interactively and exercised by
  `test_identity_projection_is_invocation_specific_with_no_unconstrained_fallback`).
  There is no optional/default parameter and no production call site passes
  `None` or omits it -- the only production call is
  `CodexCliAdapter.execute()` -> `structured_result_envelope_openai_schema(request.invocation)`
  (`codex_adapter.py:184`), and `grep` confirms this is the only non-test
  call site in `src/`.
* The projection is genuinely invocation-specific: two different
  `Invocation`s produce different one-element enums for all three fields
  (`test_identity_projection_is_invocation_specific_with_no_unconstrained_fallback`),
  and `test_execute_writes_the_schema_derived_from_the_exact_dispatched_invocation`
  proves the schema **written to disk** by `execute()` matches the schema
  built directly from the same `Invocation` passed into
  `AgentExecutionRequest`.

== 3. Provider-neutral authority preservation

`adapter.validated_result()` is absent from the diff; independent inspection
of the current file (`src/workflow_coordinator/adapter.py:103-119`) shows it
is byte-identical in effect to the BUG's cited pre-fix line numbers: it still
parses JSON, checks the exact envelope key set, checks `schema_version == 1`,
and compares `(envelope["run_id"], envelope["hop_id"],
envelope["invocation_id"])` against `(expected.run_id, expected.hop_id,
expected.invocation_id)` by tuple equality, raising `ResultValidationError`
on any mismatch.

`CodexCliAdapter.execute()` (`codex_adapter.py:164-199`) writes the
invocation-specific schema, runs the subprocess, and returns
`AgentExecutionOutcome(candidate, ...)` where `candidate = result.read_text(...)
or None` -- the raw file content, unmodified. There is no code path in
`execute()` that parses, rewrites, or touches the JSON body of the returned
result before construction of `AgentExecutionOutcome`. This is independently
proven, not just inspected: `test_execute_never_repairs_a_divergent_returned_identity`
drives a fake executable that writes an envelope with the exact historical
`"run_id": "RUN-WIRED,"` trailing-comma defect, asserts
`outcome.candidate_result` still contains the divergent value verbatim, and
then asserts `validated_result(outcome.candidate_result, invocation)` still
raises `ResultValidationError` with `"does not correlate"`. This directly
demonstrates the rejected Option B tautology is not present: correlation
enforcement still lives solely in `validated_result()`, and a schema-side
narrowing does not, and structurally cannot, cause the adapter to
self-assert correlation.

== 4. Strict-schema compatibility

`assert_openai_strict_schema()` and `_STRICT_KEYS` in `codex_adapter.py` are
unchanged by the diff. `_STRICT_KEYS` already includes `"enum"` (it is used
pre-existingly for `schema_version`, `Outcome`, `FindingState`, and
`ESCALATION_KINDS`), so `{"type": "string", "enum": [value]}` is squarely
inside the pre-existing accepted subset -- no validator change was needed or
made. `test_invocation_specific_identity_projection_stays_inside_the_strict_subset`
exercises `assert_openai_strict_schema()` directly against the new
invocation-specific schema (positive case) and against a mutated copy with
`type` deleted from `run_id` (negative case, still walks and rejects
correctly). This is deterministic/offline conformance evidence only, as the
BUG record anticipates; no real-provider (Codex CLI / OpenAI) acceptance was
tested or is claimed, and the BUG's acceptance criteria do not require it
for this implementation review.

== Potential point inspected, not a defect

The invocation-specific schema is written to the same
`structured-result.schema.json` filename under `result_directory`
(`= checkout_state_root(state_root, association)`, i.e. per-checkout, not
per-Hop-history) on every `execute()` call, exactly as it was before this
fix -- this commit changes schema *content*, not the artifact pathname or
retention scheme. Per the review brief, this is not broadened into a
schema-retention/audit redesign, as no concrete correctness or authority
defect follows from it: `validated_result()` never reads that file, only the
freshly dispatched Codex process does, and each `execute()` call overwrites
it with the schema for its own current `Invocation` immediately before
launching that same process. INFO/WATCH only, not BLOCKING/IMPORTANT/MINOR.
