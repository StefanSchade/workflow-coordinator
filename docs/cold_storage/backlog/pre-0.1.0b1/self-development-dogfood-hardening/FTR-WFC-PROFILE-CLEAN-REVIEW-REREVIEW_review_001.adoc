== 2. Four-eyes invariant

Confirmed mechanically, not only from YAML:

* *Clean initial review cannot complete directly.* `phases.review.routes`
  contains only `rereview` and `correct` -- no `accept` key exists. In
  `reduce_result`, an agent requesting `accept` from `review` resolves
  `route = phase.routes.get("accept")` to `None`, which the reducer rejects
  as `mechanical_preemption:unknown_route:accept` and stops for human
  attention (`reducer.py:356-363`). There is no code path by which `review`
  can reach `RunStatus.COMPLETED`.
* *Clean initial review must go to rereview.* The only routes out of `review`
  are `rereview` (goto) and `correct` (goto); a clean review's only
  non-defect exit is `rereview`.
* *Rereview remains independent.* `rereview.role` is `independent_reviewer`
  (same as `review`), and `review.context` is required to equal `"fresh"` for
  every review phase -- `serialization._review` raises
  `ValidationError` if `context != "fresh"` (`serialization.py:441-442`); this
  is the only supported value in Slice 1, so it cannot be weakened per-phase.
  `vertical.py:286` records each Hop's review context as `"fresh"`
  unconditionally. Rereview therefore gets the same independent-context
  guarantee as the original review, not a reuse of the first reviewer's
  context.
* *Initial review with a defect can still go to correction.* `review ->
  correct` is retained unchanged.
* *Correction must still go to rereview.* `phases.correct.routes` still
  contains only `rereview`.
* *Rereview may accept or return to correction.* `phases.rereview.routes`
  still contains exactly `accept` (complete) and `correct` (goto), unchanged
  from revision 2.

Both required semantic paths are therefore live and exclusive:
`review -> rereview -> accept` (clean) and
`review -> correct -> rereview -> accept|correct` (defect found), and
`review -> accept` is unreachable by construction of the routes mapping, not
merely by convention.

== 4. Historical-attempt test semantics

Inspected `_materialize_bundle`
(`tests/architecture/test_self_development_governance.py:104-124`): for every
governing path it writes `_current_text(path)`, i.e. the *live* file content
at `PROJECT_ROOT`, into a synthetic one-commit repository, unless a test
supplies an explicit `replacements` override (only
`test_work_item_mapping_cannot_enlarge_review_phase_authority` does). The
`ATTEMPT_4`..`ATTEMPT_7_GOVERNING_PATHS` tuples each pair one per-attempt,
frozen WorkItem/task file (e.g.
`governance/work-items/developer-ergonomics-review-002.yaml`, itself untouched
by this candidate) with the *same, shared* profile/policy/components/prompt
paths used by every other test in the module -- always the current live
files.

This is Possibility A. These tests do not attempt to reconstruct or replay
historical Attempt truth: `_materialize_bundle` has no facility to pin a
historical profile snapshot, and it always resolves the shared paths (indices
1-3 of each `*_GOVERNING_PATHS` tuple) to whatever the profile/policy/
components currently are. The test names read literally --
`test_attempt_N_bundle_passes_production_preflight` -- and that is exactly
what each proves: that the named historical WorkItem definition, combined
with the *current* governing profile/policy bundle, still passes *current*
production preflight. Updating the expected `profile.revision` from `"2"` to
`"3"` in these five tests is therefore the correct action, not a
falsification of history: it keeps the assertions truthful to what
`_materialize_bundle` actually constructs.

This is also an established convention, not a pattern newly introduced by the
candidate. Commit `0e85a751b76cdeb2a78f1ddc55141b9656c8a814`
(`governance: raise self-development hop ceiling to five`) previously applied
the identical edit shape -- splitting a combined
`profile.revision == policy.revision == "2"` assertion and bumping
`policy.revision` to `"3"` -- across this same set of tests (current,
continuation, attempt_4, attempt_5) when `repository-policy.yaml` last
changed. The candidate is the second application of that precedent, this time
for the profile revision.

Classification: acceptable architecture-test convention, not a defect. The
one residual observation (INFO, non-blocking) is naming clarity: a reader
unfamiliar with `_materialize_bundle` could misread "attempt_N" as implying
exact historical replay of admitted governance, when it actually asserts
present-day compatibility of a historical WorkItem shape against the live
bundle. A future docstring on `_materialize_bundle` or a module-level comment
stating this explicitly would remove the ambiguity; it is not required for
this candidate's correctness and no such change should be bundled into this
governance edit.

Frozen historical archive docs (`docs/backlog/first_wfc_on_wfc_dogfood_attempt_*.adoc`)
and the per-attempt WorkItem/task files themselves are unchanged by this
candidate, consistent with "historical docs and frozen Run state must remain
