== 1. Workflow role migration

*Complete and correctly bounded.*

`WorkflowRole` (`model.py:85-90`) is a `CoordinatorValue` string enum with
exactly `worker` and `independent_reviewer`. `Phase.role` is typed
`WorkflowRole` (`model.py:166`) and `workflow_profile_from_yaml()` admits it
through `_enum()` (`serialization.py:644-646`), so any other value is rejected at
the input boundary. Probed directly: `developer`, `observer`, `prepare`, and
`verify` all fail with `must be one of: worker, independent_reviewer`, which is
also the parametrized assertion at `tests/unit/test_serialization.py:313`.

*Role names grant no authority.* `reducer.py` imports neither `Phase` nor
`WorkItem` nor `WorkflowRole`, and a search of the module for `role`, `persona`,
`model`, `reasoning`, `adapter`, `provider`, `worker`, or `reviewer` returns only
the `from .model import (` line. Authority remains in `ReviewDescriptor`,
`authorized_scope`, `authorized_actions`, `routes`, and `finding_authority`, none
of which is cross-checked against a role name.

*Reducer behavior is independent of role names.* The only reducer change in the
entire diff is the profile schema literal at `reducer.py:62`
(`profile.schema_version != 1` becomes `!= 2`).
`tests/unit/test_reducer.py:370` adds a direct proof: two profiles differing only
in `Phase.role` produce equal `reduce_result()` output, and the `reduce_result`
signature is asserted disjoint from
`{persona, adapter, provider, model, reasoning, subject_domain}`.

*`Hop.role` and `HopSummary.role` remain open trace strings.* Both are still
`str` (`model.py:250,288`). `vertical.py:286` records `phase.role.value`, so
ordinary agent Hops carry the resolved workflow-role value while the string type
stays open.

*Coordinator-authored values remain representable.* `persistence.py:140` still
writes `role="uncertain_dispatch"` into a recovery Hop, and
`tests/unit/test_serialization.py:427` pins that this survives `compact()`. The
value is never admitted in a profile and is never used for persona or binding
selection.

*No live `developer` workflow role or role component remains.* A search for
`role: developer`, `[developer]`, and `prompts/developer` across `governance/`,
`src/`, and `tests/` returns nothing, and a case-insensitive search of `src/` for
`developer`, `pytest`, or `code reviewer` returns nothing at all. The only
surviving `developer` strings in governance are `developer-ergonomics` WorkItem
IDs, file names, and the `standalone-developer-ergonomics` profile ID -- exactly
the software-subject names migration step 10 requires be left intact.

*No dangerous half-migration.* The migration is version-gated rather than
aliased. `_migrated_version()` (`serialization.py:180-188`) rejects a
`schema_version` below the expected value with an explicit migration message and
rejects anything above it outright, for both WorkItem (expected 2) and profile
(expected 2). Probed: WorkItem `schema_version: 1` is refused with "migration to
schema_version 2 is required". No code path reinterprets an old document under
the new version.

== 2. Persona model and admission

*Correct, strict, and mechanically inert.*

Shape validation lives in `_persona()` / `_personas()`
(`serialization.py:326-352`); cross-input completeness lives in `_preflight()`
(`operator.py:253-275`), which is the placement review 001 recommended in F-N4.

Probed directly against `work_item_from_yaml()`:

|===
|Input |Result

|missing `personas` key |rejected, `WorkItem is missing fields: personas`
|`personas: {}` |rejected, `must not be empty`
|unknown role `architect` |rejected, `must be one of: worker, independent_reviewer`
|`developer` role key |rejected, same message

*Exact profile-role coverage.* `_preflight()` compares `set(work_item.personas)`
against `{phase.role for phase in profile.phases.values()}` for set equality and
reports missing and unknown roles separately. Three operator-level tests
(`tests/unit/test_operator.py:1053,1072,1087`) prove rejection happens before the
fake provider executable is ever launched, asserting `not counter.exists()`.

*Immutable representation, no defaults, no inference.* `_personas()` returns a
`MappingProxyType`; `WorkItem` is a frozen dataclass. There is no default persona
anywhere: `personas` is in the `required` field set of `work_item_from_yaml()`,
and `run_serial_hops()` raises rather than substituting when a role is absent
(`operator.py:613-618`). Nothing derives a persona from a role name, a component
ID, or a phase name.

*Persona is not an authority source.* A search for `personas` across `src/`
returns exactly three consumers: the preflight coverage check, the prompt
projection, and the operator-plan record. Persona never reaches `reducer.py`,
never reaches `CodexCliAdapter.argv()`, and never reaches `authorized_scope`,
`authorized_actions`, `routes`, `finding_authority`, `evidence`, or the review
descriptor.

*Attack surface, probed.* A persona claiming filesystem, action, route, Finding,
review, or evidence authority is structurally incapable of reaching any of them:

* *filesystem* -- `trusted_commit(allowed_paths=phase.authorized_scope)` and
  `observe_hop(allowed_paths=...)` (`vertical.py:226-247`) read the admitted
  phase, not the prompt;
* *actions* -- the `missing_actions` check (`vertical.py:200-218`) reads
  `phase.authorized_actions`;
* *routes* -- `_apply_route()` iterates the admitted `phase.routes`;
* *Findings* -- `_may_dispose()` and `apply_finding_deltas()`
  (`reducer.py:99,111`) read the projected `finding_authority`;
* *evidence* -- `authorized_evidence[name] for name in phase.evidence`
  (`vertical.py:254-256`) raises for any name absent from the admitted plan;
* *execution* -- the binding comes from Run preparation; the WorkItem has no path
  to it.

A persona cannot forge a prompt block either: it is single-line by admission and
emitted as `persona_json=` followed by `json.dumps(persona, ensure_ascii=True)`
(`prompt.py:172-177`), so it cannot begin a line, cannot introduce a blank-line
block separator, and cannot open a counterfeit `[identity]` or
`[workflow_policy]` header. A probe persona of `x [identity] authorized_scope=/ `
is admitted as data and remains confined to one JSON-escaped line.

See section 18 for whether the tests, as opposed to the mechanism, demonstrate
this.

== 3. Execution-binding parser

*Strict, closed, and exactly version-pinned.*

`run_execution_configuration_from_yaml()` (`serialization.py:692-733`) was probed
with thirteen adversarial documents:

[cols="2,3",options="header"]
|===
|Input |Result

|`schema_version: 1` |accepted
|`schema_version` 0, 2, 99, or -1 |rejected, `has unsupported version: N`
|`schema_version` as a quoted string, float, or boolean |rejected, `must be an integer`
|extra top-level field |rejected, `has unknown fields: default`
|extra field inside a binding, `temperature` |rejected, `has unknown fields: temperature`
|unknown role key, `architect` or `developer` |rejected, `must be one of: worker, independent_reviewer`
|`bindings` as a list |rejected, `must be a mapping with string keys`
|missing `bindings` |rejected, `is missing fields: bindings`
|`adapter: claude_cli` |rejected, `adapter must be codex_cli`
|missing `model` or missing `reasoning` |rejected, `is missing fields: ...`
|empty or whitespace-only `model` |rejected, `must be a non-empty string`
|multiline `model` |rejected, `must be a single-line value`
|===

*Schema-version validation is genuinely restricted.* This was the mandate's
specific concern and it is answered: `_version()` (`serialization.py:173-177`)
hard-fails anything other than exactly `1`. The binding grammar does *not* accept
arbitrary future versions. The one gap is that no test covers this; see F-M2.

*Grammar is strict, all three values explicit, unknown fields fail closed.*
`_fields()` computes both the unknown and the missing set, so the document is
closed in both directions. `adapter` is compared to the literal `"codex_cli"`,
with a second defence-in-depth check before adapter construction
(`operator.py:630-633`). That is two hard-coded string comparisons, not a
registry.

*Exact profile-role coverage is enforced.* `_preflight()`
(`operator.py:276-288`) applies the same set-equality rule as for personas, with
separate missing and unknown reporting, and two operator tests prove
pre-dispatch rejection in both directions.

*Mapping is genuinely immutable.* Probed: `RunExecutionConfiguration` and
`ExecutionBinding` are both `frozen=True`; `bindings` is a `mappingproxy`;
attribute assignment raises `FrozenInstanceError`, item assignment and `clear()`
raise `AttributeError`, and the nested `ExecutionBinding` values are frozen
dataclasses of plain strings, so immutability is total through the nesting. The
underlying dict is a function local with no escaping reference. See F-N5 for the
one caveat.

*No hidden model or reasoning fallback survives on the production operator
path.* `CodexCliAdapter` no longer has dataclass defaults; see section 8.

== 4. Parse-once binding invariant

*Proven, both structurally and behaviorally.*

The chain is:

. `_preflight()` resolves `args.execution_bindings`, reads it once
  (`operator.py:232-238`), and parses it once inside the single admission `try`
  block (`operator.py:248`);
. the resulting `RunExecutionConfiguration` is returned from `_preflight()` and
  held by `main()`;
. `main()` passes that object to `run_serial_hops()` (`operator.py:828`);
. the Hop loop indexes `execution_configuration.bindings[workflow_role]`
  (`operator.py:626`) and never touches a path.

*The source cannot be re-read between Hops* because `run_serial_hops()` has no
parameter carrying the path and never imports a reader. The property is
structural, not merely conventional.

*Mutation after H001 cannot alter H002* is proved behaviorally.
`test_dmc_and_latin_consumers_use_distinct_role_bindings_in_one_serial_run`
(`tests/unit/test_operator.py`) rewrites the binding file through the `progress`
callback after H001 to `changed-worker` / `changed-reviewer` / `low`, then
asserts H002 still uses `reviewer-model` / `high` and still records those values
in evidence.

*Parse-once is proved on the production entry point.*
`test_main_runs_supported_n2_path_with_fake_local_executable` monkeypatches
`operator.run_execution_configuration_from_yaml` with a counting wrapper and
asserts `len(parse_calls) == 1` across a completed two-Hop `main()` Run. That is
a direct test of the invariant rather than a restatement of the implementation.

*Python immutability is sufficient here*, including nested values, as probed in
section 3. No Run-level binding digest is required, and none is demanded: the
candidate does not permit drift.

== 5. Same object -> adapter + evidence

*Satisfied. This is the candidate's strongest mechanical contribution.*

Tracing one production Hop (`operator.py:610-650`):

----
phase_key        = run.phase                       # captured before the Hop
workflow_role    = profile.phases[phase_key].role
resolved_binding = execution_configuration.bindings[workflow_role]
execution_adapter = CodexCliAdapter(run_root,
                        model=resolved_binding.model,
                        reasoning_effort=resolved_binding.reasoning,
                        executable=executable)
binding          = _binding_evidence(resolved_binding, executable=executable)
----

`_binding_evidence()` (`operator.py:493-501`) reads only `binding.adapter`,
`binding.model`, `binding.reasoning`, and the same `executable` local that was
passed to the constructor. The prior `_execution_binding()` helper, which
reconstructed a throwaway `CodexCliAdapter(Path("."))` to describe defaults, is
deleted. Evidence is therefore never reconstructed from adapter defaults, from
the role name, from provider self-report, or from the current external source.

*No divergence exists between configured and recorded binding.* Both derive from
the same `ExecutionBinding` instance in the same loop iteration, and
`tests/unit/test_operator.py:383` pins `_binding_evidence` to project only the
explicit resolved value.

*Multi-Hop transitions are correct.* `phase_key`, `workflow_role`, `persona`, and
`binding` are captured before `run_real_one_hop()` and passed to
`_execution_evidence()` after `run = hop_run.run` has advanced the phase
(`operator.py:676-681`). The evidence row therefore describes the Hop that
produced the outcome, not the next phase. The two-Hop consumer test asserts the
ordered sequences `["worker", "independent_reviewer"]`,
`["worker-model", "reviewer-model"]`, and `["medium", "high"]`, which would fail
if the capture had been taken after the transition.

== 8. Codex adapter

*Correct. The silent Terra/medium fallback is genuinely gone.*

`CodexCliAdapter` (`codex_adapter.py:136-157`) now declares `model` and
`reasoning_effort` as required fields ahead of `executable`, and validates both
in `__post_init__`. Probed:

* `CodexCliAdapter(path)` raises `TypeError: missing 1 required positional
  argument` -- there is no default to fall back to;
* an empty `model` or `reasoning_effort` raises `ValueError: ... must be explicit
  and non-empty`;
* `model=None` raises the same;
* a multiline or NUL-bearing `reasoning_effort` raises `... must be a single-line
  value`.

`argv()` projects the values as `--model <model>` and
`-c model_reasoning_effort="<reasoning>"`. Timeout handling,
`start_new_session=True`, the `os.killpg` SIGTERM-then-SIGKILL escalation,
bounded stdout and stderr capture, and the `AgentExecutionOutcome` shape are
identical to the baseline. `AgentExecutionRequest` is unchanged and remains
provider-neutral -- it carries no model, reasoning, or provider field.

*No argv injection is possible.* A deliberately hostile `reasoning_effort` ending
in a quote followed by `--sandbox danger-full-access` and a comment marker was
probed: it lands as a single argv element because `subprocess.Popen` is given a
tuple with no shell, and the existing `--sandbox workspace-write` pair at indices
8 and 9 is unaffected. A hostile `model` value is positionally consumed by
`--model` for the same reason. This is worth stating explicitly because the value
is now human-authored rather than hard-coded.

*Reasoning validation is bounded to shape, not to a provider vocabulary,* which
is correct for the accepted MVP -- the FTR forbids a capability registry. The
consequence is recorded as F-M1: it is a fail-closed, fail-late, diagnosable
error rather than a fail-open one.

== 12. Prompt composition

*Order and semantics are exactly as specified.*

`assemble_prompt()` (`prompt.py:128-200`) emits, in order: the `[identity]`
header, the complete Agent Operating Contract, the full selected-component loop
over `_selected_ids()` (role, then modifiers, then repository policy), then
`[persona_guidance]`, then `[workflow_policy]`, then `[task]`, then each
`[context]` item, then the optional `[diff]`, then `[result_output_contract]`.
This matches the accepted precedence list and resolves review 001's F-M3 exactly:
the persona block is appended *after* the component loop, so no loop surgery was
needed and all repository-policy component text stays ahead of non-authoritative
persona guidance.

*`workflow_role` is projected from the admitted current Phase.* `_header()` emits
`workflow_role={phase.role.value}` immediately after `phase=`
(`prompt.py:123`), and `phase` is `profile.phases[run.phase]` resolved inside
`run_one_hop()` (`vertical.py:157`) -- the same phase whose role drove persona and
binding selection in `run_serial_hops()`.

*Persona comes from the admitted WorkItem mapping* and is threaded as a required
keyword through `run_serial_hops` to `run_real_one_hop` to `run_one_hop` to
`assemble_prompt`. None of those parameters has a default, so no caller can
silently omit it.

*Persona is JSON/data encoded as intended*: `persona_json=` followed by
`json.dumps(persona, ensure_ascii=True)`, under `source=work_item` and
`authority=none`, both Coordinator-emitted.

*Component IDs remain independent from workflow roles.* `_selected_ids()` returns
the explicit `role_components`, `modifier_components`, and
`repository_policy_components` lists; nothing resolves a component from
`Phase.role`. Production still demonstrates the decoupling: the profile assigns
`role: independent_reviewer` while selecting component `reviewer`.

*Persona cannot replace or suppress authoritative blocks.* It is appended as its
own block after all components; it cannot omit, truncate, or reorder anything,
and cannot forge a block header (section 2).

*No prompt-bound regression from persona size accounting.* Persona bytes are
deliberately not added to `used`, so the component and context omission
thresholds behave exactly as before. The worst case is a prompt at most 512 bytes
larger plus fixed block framing, against a `CONTEXT_LIMIT_BYTES` of 196,608. The
existing bound tests in `test_slice3_vertical.py` still pass unchanged apart from
the new keyword.

== Findings

=== F-M1 (MINOR) -- an unusable model or reasoning value is discovered only at provider dispatch, and costs a charged Hop

`_execution_value()` (`serialization.py:334-339`) and
`CodexCliAdapter.__post_init__` validate that `model` and `reasoning` are
non-empty, single-line, and NUL-free, but not that they name anything the provider
accepts. That is correct for the MVP -- the FTR forbids a capability registry --
but the failure mode is newly reachable, because these values were previously
hard-coded constants and are now human-authored per Run.

Traced: a typo in the reasoning value is admitted by preflight, reaches the `-c
model_reasoning_effort=` argument, and the Codex CLI exits non-zero with no
candidate result. `run_one_hop()` then raises `ExecutionResultValidationError`,
`run_real_one_hop()` routes it to `recover_uncertain(error.outcome)`
(`slice4.py:224-225`), the Hop is charged, and the Run lands in
`RECONCILE_REQUIRED` needing human reconciliation.

This is fail-closed, not fail-open: no default is substituted, no widened
authority results, and the evidence row *is* written with the exact resolved
model, reasoning, return code, and stderr tail, so the cause is diagnosable from
`execution-evidence.json`. But the classification is misleading -- a configuration
typo presents as an uncertain provider dispatch -- and it costs one of at most
five Hops on a first real DMC Run.

No registry is requested. If anything is done, the cheapest options are a
pre-dispatch smoke of the admitted binding through the existing
`codex_adapter_smoke` surface, or a note in the DMC Run-preparation procedure. Not
a promotion blocker.

=== F-M2 (MINOR) -- exact binding-schema-version rejection is implemented but untested

`run_execution_configuration_from_yaml()` uses `_version()`
(`serialization.py:717-720`), which hard-fails anything other than `1`. This was
verified behaviorally: 0, 2, 99, -1, a quoted string, a float, and a boolean are
all rejected. The behavior is correct and the mandate's concern is answered.

However, `test_execution_binding_parser_rejects_unsupported_or_incomplete_bindings`
parametrizes four cases -- unknown adapter, missing `model`, missing `reasoning`,
empty `model` -- and no case for `schema_version`. Every other strictness dimension
of the grammar is covered, which makes the omission conspicuous rather than
systematic.

The consequence is narrow but real: `_version()` is a shared helper also used by
the component manifest grammar. A future change that swapped it for a laxer
validator, or that introduced binding schema v2 by relaxing rather than migrating,
would not be caught by any test. One parametrize entry closes it.

=== F-M3 (MINOR) -- the self-development profile was materially changed without bumping its `revision`

`governance/self-development/standalone-development-profile.yaml` keeps
`revision: "3"` while its content changed substantively: `schema_version` 1 to 2,
two phases from `role: developer` to `role: worker`, and the selected role
component from `developer` to `worker`.

The repository has an established convention of bumping this field on every
substantive profile edit -- `53d0109` created revision 1, `0ba506c` moved to 2,
`cb41c8b` moved to 3 -- and revision 3 is already cited in frozen documentation as
the developer-role content
(`FTR-WFC-PROFILE-CLEAN-REVIEW-REREVIEW_review_001.adoc:15`: "Standalone-developer-ergonomics
profile revision 3 correctly ...").

There is no runtime defect. `run.profile_revision` is pinned per Run from the
profile actually read at the pinned Git revision, the content digest is in
`governing_inputs` and re-verified between Hops, and no live Run state exists. But
`persistence.py:176` projects Run identity as
`f"{run.profile_id}@{run.profile_revision}"`, so
`standalone-developer-ergonomics@3` now denotes two materially different profiles
across the repository's evidence, which degrades exactly the reconstruction path
the checkpoint projection exists to serve.

`tests/architecture/test_self_development_governance.py:185` asserts
`profile.revision == "3"`, so the test encodes the omission rather than catching
it.

Cheapest now: bump to `"4"` and update that assertion, folded into the promotion
commit. It is free there and becomes progressively less free once the first DMC
Run publishes more evidence at `@3`. Not a promotion blocker.

=== F-N1 (INFO) -- `execution_configuration` is optional while `personas` is required, and an injected adapter silently ignores a supplied configuration

In `run_serial_hops()` (`operator.py:556-568`), `personas` is a required keyword
while `execution_configuration` defaults to `None`. When `adapter` is injected,
the `execution_configuration` branch is skipped entirely, so a caller passing both
gets the injected adapter and a `local` evidence row with null model and reasoning,
without a diagnostic.

No production caller can reach this: `main()` never passes `adapter`, and the
`adapter is None and execution_configuration is None` guard already fails closed.
`tests/unit/test_slice5b.py:494` deliberately passes both, which is the pattern
that would need adjusting if the seam were tightened.

Recorded only so that a future library consumer of `run_serial_hops()` is not
surprised. Making the two parameters mutually exclusive would be a one-line
improvement; it is not required by the accepted record.

=== F-N2 (INFO) -- persona shape admits NUL and ANSI control characters, while execution values do not

`_execution_value()` rejects NUL explicitly; `_persona()` does not. Probed: a
persona containing a NUL byte, and one containing an ANSI escape sequence, are
both admitted, because `str.splitlines()` does not treat NUL or ESC as line
boundaries. `_string()` also returns the value unstripped, so a persona of
`"  dev  "` is admitted verbatim; the same is true of `model`.

The impact is cosmetic. `json.dumps(..., ensure_ascii=True)` escapes both to
`\uXXXX` sequences, so the persona still cannot break out of its single line or
forge a block header, and nothing mechanical depends on the content. Recorded as a
hygiene inconsistency between two adjacent validators added in the same change.

=== F-N3 (INFO) -- the persona attack test asserts prompt text for the Finding-authority claim rather than exercising it

Covered in section 18. The attack persona claims "approve your own Findings", and
the test asserts that the projected `finding_authority` is empty; it does not
submit a Finding delta under that persona.

No duplicate test is demanded, because persona provably never enters
`apply_finding_deltas()`'s input set and three existing tests
(`test_reducer.py:64,172`, `test_slice5b.py:1313`) prove the disposition boundary
independently. Recorded so a later reader does not mistake the prompt assertion
for the whole proof.

=== F-N4 (INFO) -- accepted non-semantic software-culture residue remains in engine-owned text

Contract v6 retains "Agent-side tests and checks", "record that implementation",
"Agent-reported validation or test results", and "public-surface authority";
`ESCALATION_KINDS` (`serialization.py:87-94`) retains `public_surface`.

This is review 001's F-M5 and F-N5, which the accepted FTR then disclosed and
declared non-semantic, making neutralization permitted rather than required. No

passes. Correctly not treated as a defect; recorded only to confirm the residue

already being revised.

=== F-N5 (INFO) -- `mappingproxy` immutability has the usual Python escape hatch

Reaching the underlying dictionary through `gc.get_referents()` and mutating it
was probed and succeeds. This is a property of every `mappingproxy` in CPython,
not of this design, and no production code holds or can obtain a reference to the
backing dictionary: it is a function local in
`run_execution_configuration_from_yaml()` whose only escaping handle is the proxy.

Recorded for completeness because the mandate asked whether Python immutability is
sufficient. It is, for every realistic drift path; a determined in-process caller
using `gc` is outside the threat model the accepted MVP addresses, and hardening it
would require copying into a frozen structure for no practical gain.

=== F-N6 (INFO) -- `proof_harness.py` cannot exercise a Run's actual binding

Classified in section 6 as a legitimate harness-owned binding (option A), not a
remaining hard-coded production binding. One consequence is worth noting: unlike
`codex_adapter_smoke.py`, the proof harness does not expose `--model` or
`--reasoning-effort`, so Terra and medium are fixed at the call site
(`proof_harness.py:223`). A proof run therefore cannot pre-validate the model a

That capability already exists in the smoke CLI, which is the correct surface for

are not later mistaken for the fallback the FTR removed -- they are now explicit
arguments of a fixture that also hard-codes its own WorkItem, profile, policy,
task, and repository.

=== F-N7 (INFO) -- promotion must move the Runtime and the governance bundle together

The clean no-alias migration the FTR mandated has the intended consequence that
the two sides are not interoperable. The currently promoted Runtime at
`workflow-coordinator-runtime` is at `CONTRACT_VERSION = 5` and requires
`profile.schema_version == 1`, so it will reject this repository's migrated
governance bundle; and the candidate Runtime rejects any un-migrated profile or
WorkItem through `_migrated_version()`.

This is correct behavior, explicitly chosen over a silent alias, and it fails
closed with an explicit migration message in both directions. Recorded because it
makes promotion an atomic operation: the Runtime export and the governance bundle
must be advanced in the same step, and no partially promoted state can execute.
The FTR's pre-implementation guard -- confirm no externally stored non-frozen Run
is intended for resumption -- was verified to still hold: this repository contains
no `run.json`, `checkpoint.json`, or `operator-plan.json`, and state roots are
external by construction.

== Summary

Nothing in this review requires correction before Runtime promotion. The three
MINOR findings are a diagnosability note (F-M1), one missing parametrize entry
(F-M2), and one governance-hygiene omission (F-M3). Only F-M3 is meaningfully
cheaper to fix now than later, and it has no runtime effect.

*Strongest positive.* The same-object adapter-and-evidence path. The previous
`_execution_binding()` built a throwaway `CodexCliAdapter(Path("."))` to describe
defaults while `slice4.py` independently built the real adapter, so the recorded
binding agreed with the invoked binding only because both read the same dataclass
constants. The candidate deletes that split: one `ExecutionBinding` instance
supplies the constructor arguments and the evidence projection in the same loop
iteration, and the dataclass defaults that made the coincidence possible are gone.
Combined with parse-once immutability and the pre-dispatch plan, the Run's
configured binding and its recorded binding cannot diverge.

*Strongest concern.* F-M1: the model and reasoning values are now human-authored
per Run but are validated only for shape, so an unusable value is discovered by
the provider rather than by preflight, charges a Hop, and presents as an uncertain
dispatch. This is fail-closed and diagnosable from the evidence row, and the
accepted record explicitly forbids the capability registry that would eliminate
it, so it is an operational note rather than a defect.

The candidate is suitable for promotion as the next WFC Runtime and for the first
real DMC consumer Run, subject to F-N7's requirement that the Runtime and the
migrated governance bundle be promoted together.

This implementation review invoked no WFC and no provider, mutated no Runtime, Run
state, governance, profile, policy, production code, test, or remote, and changed
no file other than this review artifact.
