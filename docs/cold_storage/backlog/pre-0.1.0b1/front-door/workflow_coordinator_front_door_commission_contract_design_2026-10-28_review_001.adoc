== 1. Disposition

Outcome:: `changes_required`
Route:: `correction`

The proposal gets the central boundary right: the Intent is a request, the
compiler is deterministic and authority-free, the rendered existing inputs
remain visible, and current Level-0 admission and separate maintainer
authorization remain controlling.  It also avoids a general workflow DSL and
states Robust's essential gate-to-gate renewal shape.  It is not yet an
implementation-ready contract, however.  The exact-render pin cannot work as
written, and the two supposedly closed initial programs still leave semantic
constants unresolved.

Open blocking identifiers:: `FDC001`, `FDC002`.

No WFC Current-Run Finding is created for these ordinary design defects.

== 3. Blocking requirements

=== FDC001 -- PREPARE must re-prove the exact pinned projection without a self-referential manifest

Invariant:: The Front Door path must prove, before PREPARE succeeds and before
any provider invocation, that the five inputs about to be admitted are the
byte-exact deterministic projection of the pinned Intent and pinned selected
sources.  The proof must remain bound to the exact clean bundle commit through
LAUNCH.  A digest list authored in the same mutable render transaction is not
by itself that proof.

The design says the resulting bundle commit is named in the render manifest
(section 3, immediately after the field table), then says the Intent, manifest,
and governing bundle are committed together and that a PREPARE wrapper compares
"the manifest's commit" and its digests with that committed tree (section 4.3).
A tracked file cannot contain the identity of the Git commit that contains that
file: inserting or changing the identity changes the commit.  More importantly,
checking only manifest-listed digests proves consistency with that list, not
equivalence to the Intent; a hand edit and a matching manifest edit can remain
self-consistent without any rerender check.  The earlier standalone
`commission render --check` invocation is not mechanically tied to PREPARE.

Current PREPARE already supplies the useful lower half of the solution:
`_preflight` requires the live clean HEAD to equal `expected_head`, reads all
five governing inputs and selected components from that tree object, and the
existing launch envelope later refuses pin or launch-artifact drift.  The
design must make the Commission-Intent path's PREPARE step itself rerun a
byte-for-byte projection-equivalence check from the Intent plus the pinned
program/policy/component sources at that same observed HEAD before delegating
to canonical `_preflight`, or specify an equally concrete non-self-referential
attestation bound to that HEAD.  The manifest may record source identities and
content digests; it must not claim to contain its own commit identity.  The
ordinary hand-authored PREPARE path may remain independent, as the candidate
already requires.

Evidence:: Candidate sections 3 (post-table pin statement), 4.1, 4.2, and 4.3;
`src/workflow_coordinator/operator.py::_preflight`; `scripts/wfc_op.py`'s
canonical preflight seam and prepared launch artifacts; operator manual
sections 7--8.

=== FDC002 -- Direct-v1 and Robust-v1 must be fully closed, executable program records

Invariant:: Selecting `direct@v1` or `robust@v1` must determine every process
guarantee which the Intent is forbidden to author.  The design must give the
finite literal program semantics needed to render each existing profile,
rather than deferring a required target behavior to a later program design.

For Direct, the design currently says only "one bounded worker phase" with
"fixed routes" and no gate evidence; it neither names the route key/effect nor
the exact phase actions/artifact behavior.  More seriously, it defers
task-specific deterministic checks to prose or a later Direct revision.  That
does not satisfy `DEC-WFC-022`'s Direct target: no independent LLM review, but
whatever deterministic checks the task actually needs.  Under current
admission, Coordinator-required evidence on a worker/non-gate phase is
rejected, so supporting checked Direct work requires an explicit bounded
design choice (for example, a closed verification-gate shape that does not
become independent semantic review), not postponement.  If `direct@v1`
intentionally supports only `evidence_profile: none`, it is not the selected
Direct target and cannot serve as the advertised proof of that target without
the design saying what narrower program it proves instead.

For Robust, the route diagram captures renewal, breadth, and the evidence
failure path, but the record never fixes the gate `finding_authority` values
needed for `focused_review` to close Findings before returning to
`broad_review`.  It likewise leaves the literal action/artifact semantics and
complete route keys/effects to a future catalogue entry.  These are exactly
the archaeology counterexamples the design correctly forbids in an Intent;
therefore they must be stated as program constants here.  At minimum the
corrected record must enumerate, for both programs, phase role, components,
artifact requirement, scope-binding rule, actions, evidence placement,
review descriptor (including Finding authority and failed-evidence route), and
all route keys/effects.  A compact literal table is sufficient and remains a
closed two-program grammar, not a DSL.

Robust's renewed-broad-review invariant itself is sound if those constants are
fixed: every post-`correct` successful path is
`focused_review -> broad_review -> COMPLETE`, and `context: fresh` makes the
re-entered broad gate a fresh pass.  No general P3.5 reachability validator is
required for a finite exact-template equality check.

Evidence:: Candidate sections 3.1, 3.2, 5.1, and 5.2; Front Door MVP decisions
section 2.4; `src/workflow_coordinator/operator.py::_admit_evidence_disposition`;
operator manual sections 22.3--22.4; archaeology sections A, D, and E.

== 5. Trust-boundary and scope conclusions

The Intent exposes no phase graph, actions, Finding authority, evidence argv,
failure route, component selection, model, adapter, or switch removing required
review.  Requested scope and hop limits can only narrow; program/policy
derivation may add assurance and narrow capability; and an Intent cannot remove
those additions.  Current role/persona equality, policy-action containment,
A1/governance/scope containment, artifact mapping, evidence-definition, and
gate/failure-disposition predicates all still execute in `_preflight`.  No
existing admission predicate is weakened.

The design does not implement or design P3.5, Front Door Advanced, Level 1, a
provider registry, a quota scheduler, archive storage, the Claude adapter, a
general workflow DSL, production code, tests, profiles, migrations, or a Run.
Its future proof slice does not require modifying an existing profile or a
kernel file.  The design artifact remains a single record and includes both
required rejected alternatives and an explicit open-question list.
