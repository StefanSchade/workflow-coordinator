=== Open: must the whole required suite run on a hosted runner? (C6, MD-5)

*Status: accepted by the maintainer for 0.1.0b1 on 2026-11-23, see the <<md5-maintainer-acceptance,acceptance record>>; the text below is the investigation record as it stood before the acceptance.* The earlier recommendation -- a subset on the runner -- is
*not* accepted. Target: the whole required suite, on a qualified hosted
environment, as a binding gate (G2), if technically possible.

Setup requirements (fact [1]):: `WFC_TEST_INPUTS`/`WFC_TEST_PROFILE` set to a
bundle verified byte-for-byte; `check_host` compares implementation, Python
minor, machine, system, SOABI, seed pip exactly and glibc as a floor; 12
pinned wheels; an editable WFC install; real bubblewrap userns, Git without
a clean/process filter, GNU make, PEP-517 isolation. Four conditional skips
fire on the Operator's reference host (three opt-in live-provider, one
internal probe); three further conditional skip sites exist suite-wide and
must be asserted *not* to fire on the runner -- `make` and `git` present,
`governance/self-development` checked out -- not silently relied upon.
Reproducible on a GitHub runner? (fact [2]):: Not yet proven, but plausible:
route R-A, now implemented as `.github/workflows/release.yml`'s `check` job
(link:../../../../developer_guide/ch04_release_management.adoc#release-ci[chapter
4's CI workflow section]), uses `ubuntu-24.04` (pinned label) plus `setup-python`
pinned to the exact patch `3.13.5`, a `sudo sysctl` relaxing unprivileged
userns for bwrap, a step-scoped neutralization of the runner's git-lfs
filter (not WFC's own filter-refusal test), the normal `fetch`+`exec` flow,
then the unmodified suite. The route was exercised on 2026-11-23 in seven hosted
attempts (see the <<md5-hosted-run-record,hosted-run record>>); the
step-scoped neutralization of the git-lfs filter turned out to be insufficient
and was replaced by removing the runner's system-level filter entries.
A second host profile's closure review? (fact [3]):: Re-verified against the
profile: the 12 wheel pins are checked only by filename, size, SHA-256,
metadata and wheel tag (manylinux/`py3-none`/`cp313` plus a glibc floor) --
none depends on the CPython build, so the pins would not change. The
build-dependent part is `seed_pip_version` (`ensurepip.version()`), which
Debian patches to a bundled pip distinct from upstream; other host fields
are generic. A second profile's review therefore reduces to a byte-equality
diff of `wheels` plus a review of the build-specific `host` fields -- never
a full dependency re-audit.
What cannot run at all? (fact [4]):: Nothing by design -- the four skips
above are opt-in or internal, and the three further sites are host- and
checkout-dependent conditions to verify, never silently widened or assumed.

*Still unknown, needing a hosted run:* (a) the runner's actual seed pip
version for CPython 3.13.5 on `ubuntu-24.04`; (b) bwrap userns after the
`sysctl`; (c) whether the runner's Git carries a git-lfs filter and the
neutralization suffices; (d) that `fetch` reaches `files.pythonhosted.org`;
(e) whether a second profile is wanted if the pip version differs.

*Cheapest evidence:* the first hosted run of the E3 workflow
(link:../../../../developer_guide/ch04_release_management.adoc#release-ci[chapter
4's CI workflow section]) on `main` answers (a)-(d).

*Escalation rule:* a real, reproducible blocker is documented with the
failing log and escalated -- a digest-pinned container, a documented partial
gate, or otherwise -- to the maintainer; MD-5 is not loosened and G2 is not
narrowed without that decision.

===== Release-candidate artifact of run #9, verified by the Operator

The maintainer transferred `release-dist.zip` of run #9 to the Operator's
machine on 2026-11-23. Checked there: the archive's SHA-256 equals the API
digest recorded above (`3f7bc459697838aba0fa1a76de366387636b53af9bd72f504a376f639b9eba77`);
it holds exactly `SHA256SUMS.txt`, the wheel and the sdist, with no unsafe entry
names; extracted into its own directory, `sha256sum -c SHA256SUMS.txt` passes
(wheel `fa166bd2fa9573daca609ce6d0b7a6ede4ac42acc8dc8864da2af83b7673cb2d`, sdist
`bfcb2e1ca59f6dd0a4cddf8cd5b59715d01984671f13a8f4f437d2c19ceb1d61`). The wheel
metadata names `workflow-coordinator` `0.1.0b1`, `Requires-Python >=3.10`,
`Requires-Dist PyYAML>=6`, license MIT; the sdist's `PKG-INFO` says `0.1.0b1`.

*What proves the origin and what does not.* The wheel itself carries no commit
identifier (`source_commit` is `null` by design). The link to commit `23b9a3b`
rests on the run data (the artifact's workflow-run head SHA is `23b9a3b`, and
its digest equals the transferred archive) and on a member-by-member
comparison with a local rebuild from `git archive 23b9a3b` (all 44 wheel
members byte-identical; the wheel container bytes differ, which is expected
because a rebuild's byte identity is not claimed). Installed into a clean,
RC-only virtual environment from this wheel (not from a checkout; the
installation records the wheel's SHA-256 as its source), `wfc --version
--json` reports version `0.1.0b1`, `source_commit` `null` and implementation
tree digest `7106c1bb81b86ebc2d602756b58ea01472a4584073978b8abdfe12125f8b2231`;
the four packaged resources match the reported digests; the `wfc` commands
`init`, `plan`, `run`, `resume`, `status`, `report` and `audit` answer
`--help`.

Run date:: 2026-11-23 (attempts #1 to #7 per the maintainer's account; run
number 9 as recorded above).
Disposition:: *Proposed for the maintainer, not decided by the Operator:* on
the maintainer's account of #1 to #7 and the primary evidence of run #9, route
R-A (a native `ubuntu-24.04` runner with `setup-python` 3.13.5, offline
bundle, the whole unmodified required suite) is feasible without a subset, a
container or a weakened test, with the setup corrections listed above, and
the amended workflow (commit-SHA pinned actions, the informational
`python-compat` matrix, the tag-only release preflight) ran green on `main`.
What remains for the maintainer: (1) read the job log of run #9 (or attach it)
to replace the inferences (a), (b) and (d) by the actual lines; (2) decide
whether this evidence settles MD-5 and what G2 becomes; (3) the tag-mode path
(preflight, publication chain) has not been exercised by a hosted run, which
is expected before the tag. (The maintainer has since decided; see the
acceptance record below.)
