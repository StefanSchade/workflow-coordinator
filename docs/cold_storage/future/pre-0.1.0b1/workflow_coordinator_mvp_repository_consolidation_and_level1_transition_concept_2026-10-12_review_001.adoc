== 1. Review verdict

*CHANGES REQUIRED.*

The central plan shape survives. The proposed order -- finish the current
capability line, make Level 0 consumable through an authority-free Front Door,
make the repository legible, declare a Level-0 product milestone, learn from a
first bounded Level-1 consumer, and only then consolidate the kernel before

as the preferred near-term planning hypothesis. All of them are bounded
amendments to this concept. None requires redesigning WFC, inventing a
mechanism, abandoning the Front Door, or replacing the roadmap.

The concept is ready for a bounded amendment of the same kind the Commissioning
concept received at `009aed3`.

=== 2.2 The thesis in one paragraph

The concept is right that the project's next bottleneck is not the Run/Hop
kernel but the specification, authoring, and discoverability machinery around
it, and right that this is first-class engineering work rather than cleanup. It
is right to put consumability and legibility before Level-1 construction, and
right to defer the kernel refactor until a consumer exists above it. Its three
systematic weaknesses are: it is written entirely without citations, so none of
its load-bearing claims can be traced (F-M1); it flattens the recorded
disposition of several roadmap items it schedules as required (F-M2); and it
treats a public release as part of a milestone definition rather than as a
separately gated consequence of one (F-B1).

== 4. Findings

=== F-B1 -- The MVP definition binds an irreversible public release to an unaccepted surface with no declared public API

Severity:: *BLOCKING*

Claim under review::
§3.2: "The Level-0 MVP boundary should coincide with the first deliberate public
package publication of `workflow-coordinator` to PyPI", with §6's
eleven-item pre-publication checklist and §11's `A8 package/release hardening`
-> `A9 publish MVP to PyPI`.

Evidence::
* `pyproject.toml` declares `wfc = "workflow_coordinator.operator:main"`. That
  callable dispatches `export-salvage` and `prepare-successor`
  (`operator.py:227,1610-1613`). Their lineage's last independent rereview
  returned *CHANGES REQUIRED* with carried requirement `R1A` open across three
  cycles, and no correction attempt followed
  (`FTR-WFC-SCOPE-ESCALATION-CONTINUATION_implementation_review_004.adoc`;
  `CONC-WFC-ATOMIC-HOP-RECOVERY-WIRING`). Publication would therefore ship an
  independently unaccepted operator surface as part of the product's only
  console entry point.
* The package declares no public API: `__init__.py` carries one docstring
  describing it as *"Repository-local mechanics"*, `__all__` occurs once in
  ~10,600 lines, and the distribution is a flat namespace of 15 top-level
  modules. Publication makes `workflow_coordinator.reducer`,
  `.serialization`, `.vertical`, `.slice4` and the rest a de-facto import
  surface.
* §8.3 proposes to reorganize exactly that layout into an `Execution Kernel`
  plus isolated `Policy / Domain Services`. Phase C therefore intends to
  restructure what Phase A would have published.
* §6's checklist contains no item for independent-acceptance status of
  published behavior, no declared-public-API item, and no decision about
  `scripts/wfc_op.py`, which is the documented current operator path and lies
  outside the package.
* No test builds, installs, or runs `wfc`;
  `test_package_boundaries.py:101-105` covers `python -m
  workflow_coordinator.<module> --help` only.

Why it matters::
PyPI is the only step in Phase A that is externally irreversible and visible to
people who will never read this repository. Making it part of the *definition*
of the MVP converts a release decision into a milestone criterion, which is
precisely backwards: the concept's own §3.2 rationale ("a forcing function for
product boundaries") argues for doing the boundary work, not for binding the
milestone to the publication event. As written, following A8-A9 would publish
commands a gate refused, freeze a pre-refactor import surface as a public
contract, and do so while the package's own docstring says it is
repository-local.

Required disposition::
Three bounded amendments.

. Reclassify publication as a *release milestone immediately after* the Level-0
  MVP declaration, not as a hard MVP criterion. Keep the forcing-function
  benefit by moving the boundary work (A8) inside the MVP and leaving A9
  outside it.
. Add to §6 and to §12's `Packaging` question: every command reachable from a
  published entry point must be independently accepted, or explicitly excluded
  from the published surface; name `R1A` as the concrete instance.
. Add an explicit published-surface decision to A8: what the supported public
  surface is (recommended, and consistent with current evidence: the `wfc` CLI
  only, with the Python module layout documented as internal and unstable under
  0.x), a replacement for the "Repository-local mechanics" docstring, a test
  that installs the distribution and exercises the declared `wfc` entry point,
  and a decision on whether Harness v0 ships, stays out, or is replaced by
  package-side equivalents.

=== F-M3 -- The MVP consumer-face criterion is not satisfiable by the Front Door scope the plan commits to

Severity:: MATERIAL

Claim under review::
§3.1 `Consumer face`: "A stable, provider-free Front Door exists that *prevents
consumers from directly hand-assembling the full raw Commission protocol* for
ordinary use", and "The second property is required before serious Level-1
work."

Evidence::
* §4.3 commits definitely to Steps 1-2 only. Step 1 populates the existing
  Components seam; Step 2 adds an authoring-time validator. Neither prevents
  hand-assembly -- a validator refuses incoherent hand-authored Commissions
  earlier, which is a different and more modest claim.
* The only mechanism that could satisfy §3.1 as worded is Step 3
  (`CommissionIntent` + deterministic renderer), and §4.3 states: "This concept
  does not require `CommissionIntent` to exist if Components plus validation
  already remove most of the measured friction."
* The strong reading of "prevents" conflicts with accepted direction. The
  amended Commissioning concept §5.3 requires that "admission must not depend on
  this one convenience authoring tool, so a hand-authored Commission must remain
  admissible."
* §12 states the same criterion far more weakly and satisfiably: "Can a consumer
  construct ordinary valid work without directly mastering every raw Commission
  invariant?" §3.1 and §12 therefore disagree about what the MVP requires.

Why it matters::
The MVP boundary is the concept's central object. As written, a reader must
either build the conditional Step 3 unconditionally to satisfy §3.1, or
conclude the MVP is unreachable, or -- worst -- pursue making hand-authored
Commissions inadmissible, which accepted direction rejects. The answer to review
question A is therefore: yes, a two-faced MVP is coherent and the repository
supports it, but *not with this wording of the second face*.

Required disposition::
Replace §3.1's `Consumer face` with the satisfiable form already present in
§12, expressed against measured friction rather than prevention. Suggested
shape, to be stated in the concept's own words: ordinary Commission authoring
does not require re-deriving mechanical invariants; deterministic authoring
errors are refused before PREPARE reserves an attempt identity; and the measured
authoring friction baseline (F-M6) has fallen. State explicitly that
hand-authored Commissions remain admissible, citing the amended Commissioning
concept §5.3. Soften "is required before serious Level-1 work" to the planning
claim it is.

=== F-M4 -- §4.2 places one trusted activity and one conditional activity inside the Front Door

Severity:: MATERIAL

Claim under review::
§4.2's diagram listing the Front Door's content as "semantic authoring /
Components resolution / provider-free validation / deterministic projection /
no authority".

Evidence::
* *Components resolution.* At HEAD, component content is loaded from the pinned
  revision and digest-recorded inside Level-0 admission
  (`operator.py:443`, `_pinned_text(repository, args.expected_head, path,
  context=f"component {component_id}")`, with digest re-verification at
  `:475`). The Commissioning review independently reproduced this: components
  are "selected in declared order, loaded from the pinned revision,
  digest-recorded". Naming "Components resolution" as Front Door content is
  ambiguous between *selecting which components a Commission references*
  (requesting-side, correct) and *resolving component content and digests*
  (trusted admission, currently Level 0). The second reading moves a pinning
  activity across the trust boundary.
* *Deterministic projection.* §4.2 lists it as definitional Front Door content,
  while §4.3 Step 3 makes it conditional and possibly unnecessary. The diagram
  that defines the Front Door therefore asserts more than the plan commits to.

Why it matters::
This is the only place in the concept where trusted derivation leaks into the
Front Door, and it is in the diagram a reader will treat as the definition.
Everything else about the classification is correct: §4.2 states "no authority",
"This is a concern and adapter surface, not a new architectural level", and
§13 rejects "a new architectural Level 0.5". The leak is narrow and the fix is a
wording change, but left in place it is exactly how an authority-free adapter
acquires a trusted responsibility by diagram.

Required disposition::
Rename the first item to "Components *selection* / authoring" and add one
sentence: digest-pinned component loading, digest recording, and

== 6. Required explicit reviews

=== 6.1 Front Door versus the trust boundary

The classification is correct in substance and the concept gets the hard part
right: authority-free, requesting-side, an adapter and concern rather than a
level, consistent with the Commissioning review's conclusion that "a
deterministic compiler is best understood as authority-free tooling or a library
used by the requesting side, not as an independently trust-bearing runtime
service", and with its finding that no evidence supports "an independently
deployed/stateful service or new architectural level".

Two qualifications. First, the one place trusted derivation leaks in is §4.2's
"Components resolution" (F-M4): component loading and digest recording happen
inside Level-0 admission at `expected_head` today. Second, the concept never
takes a position on package placement, where the amended Commissioning concept
§5.3 does: "plausibly inside the WFC distribution as an explicitly
non-authoritative tool, in the relationship `scripts/wfc_op.py` and `make
memory-export` already have. It must not link into `src/workflow_coordinator/`
admission or reducer paths". That is also where F-M5's reuse question bites,
and where F-B1's published-surface decision applies. The concept should state
the placement question as open and bounded by that constraint, rather than
leaving it unaddressed while scheduling the work.

=== 6.2 Project Memory role

Appropriate. §5.6 assigns Project Memory a compact-semantic-index role,
explicitly declines to duplicate architecture records, and authorizes no new
projection format. Nothing in the concept turns it into execution authority;
§12's `Memory` question asks for accuracy, not authority, which is the right
test. The current four tables demonstrably do this job well -- every fact in the
review brief was independently confirmable from them, which is the strongest
available evidence that the design works. Only F-m4's bounding sentence is
requested.

=== 6.3 Repository discoverability plan

The diagnosis is right and under-stated (F-M7); the remedy needs anchoring to
repair-plus-generate rather than addition (F-M7), and the FTR/bug projection
needs two status axes rather than one prose line (F-M8). The acceptance
criterion in §5.7 is the right one and is already a standing test recorded in
Project Memory; it should be cited rather than appearing invented. The friction
record §11's questions 10 and 11 ask for exactly this and should be cited as the
work's origin.

=== 6.4 PyPI milestone

Publication is technically plausible: dependencies are correct and complete,
imports are relocatable and guarded, resources are pinned by digest, and
`python -m` seams work from an unrelated working directory. What is not mature
is the *boundary*: no declared public API, a flat 15-module namespace, an
`__init__` docstring describing the package as repository-local, no classifiers,
no test of the declared entry point, an unaccepted command inside that entry
point, and a Phase C that intends to restructure the published layout.

Answering the brief's question directly: publication should be a *release
milestone immediately after the MVP*, not a hard MVP criterion. PyPI does
function usefully as a product-boundary forcing function, but the forcing
function is the boundary work (A8), which belongs inside the MVP; the publication
event is the one irreversible, outward-facing step in Phase A and should be
separately gated behind it. A 0.x version plus an explicit statement that the
CLI is the only supported surface preserves nearly all of the discipline at a
fraction of the commitment.

=== 6.5 L1-before-refactor sequencing

Sound, and corroborated (I-3). A first bounded L1 does supply evidence a
bottom-up refactor cannot: which L0 details leak through the Front Door, which
escalations recur, what L1 can decide deterministically. No current kernel
problem is a blocker to a bounded L1 consumer; the one candidate
(`BUG-WFC-PHASE-COMPLETION-CONTRACT-OPAQUENESS`) is addressed by Front Door
scope, not by refactoring. The distinction the brief asks for is therefore:
`operator.py` breadth, `vertical.py`/`slice4.py` naming, and
`serialization.py` size are ordinary deferred debt under an explicit WATCH;
nothing in the repository is an actual blocker. The only correction needed is
F-M9's -- stop proposing a competing decomposition in advance of the evidence
the phase exists to gather.

=== 6.6 Kernel-preservation principle

Useful, and worth keeping. "New Level-0 policy/derivation capabilities live
behind narrow typed interfaces and do not require cross-cutting modification of
the established Run/Hop execution kernel unless the kernel abstraction itself is
proven insufficient" is a good discipline, consistent with the existing
boundaries-to-preserve list and with
`FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW`'s refusal to "design one workflow
stage per privilege aspect".

The concept does overclaim the eventual shape. §8.3 pre-names five services and
a specific `ExecutionRequest -> ExecutionConstraints` interaction; §8.5 proposes
a slice-wide characterization/architecture-test activity against an existing
"do not create a broad architecture-test project" direction. Both are F-M9.
§8.5's "No feature piggybacking" rule and §8.1's rationale are good and should
stand unchanged.

=== 6.7 Future authority/secret probes

Both probes are well chosen and grounded in existing records --
`FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW` for privileged Git escalation and
`FTR-WFC-EXECUTION-TRUST-BOUNDARIES` plus `CONC-WFC-EXECUTION-TRUST-BOUNDARY`
for protected-context execution. They are the right kind of probe: they exercise
a cross-cutting concern that the refactor claims to isolate, and neither is made
an MVP requirement (§9: "These are not MVP requirements"; §13 defers both
explicitly). This review confirms they must not become current requirements: no
current authority record requires either, and the trust-boundary concern's
posture is `not_now_revisit_on_concrete_need`.

The single correction is F-M10: the protected-context probe's pass condition
must include the recorded execution-binding pinning precondition, or the probe
can pass with the gap it exists to detect still open.
