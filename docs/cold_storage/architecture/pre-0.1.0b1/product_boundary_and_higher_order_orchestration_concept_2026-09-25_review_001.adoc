== 1. Verdict

*B -- SOUND DIRECTION, MATERIAL CORRECTIONS REQUIRED BEFORE PRODUCT-SCOPE
REALIGNMENT.*

The responsibility split is materially sound: WFC should remain a generic,
bounded, repository-native governed executor, while long-lived goal custody,
work discovery, replanning, semantic parent/child relationships, programme
maintenance, and closure remain outside the WFC product. The DMC evidence does
support different lifetime, knowledge, and closure semantics at the two
levels. Nothing found requires WFC to understand DMC, Epic, Family, Cycle,
Slice, or LangGraph vocabulary.

The concept is nevertheless unsafe as a direct basis for a fundamental README
or product-security rewrite. Its strongest trust claim assumes the very
boundary it needs to establish: a Higher Loop described as untrusted can run as
the same OS user with ordinary repository, command, credential, filesystem,
and network access. It can bypass WFC entirely. WFC never sees that act, so no
WorkItem, policy ceiling, expected HEAD, evidence command, review gate, or
reducer rule can stop it. The concept records future containment of the agent
invoked *by* WFC, but does not record the separate requirement to contain the
caller or to put WFC behind a protected broker/service/identity boundary.

There is also a narrower current-truth defect inside Level 0. Source still
admits the legacy observed-commit path (`claimed_commits` with no
`CommitIntent`), and the current provider boundary is not Coordinator-owned
containment. A hostile agent can therefore attempt direct Git mutation; an
in-scope, correctly named, correctly claimed direct commit is not rejected by
the current vertical path. The concept's repeated current claim that the
Coordinator alone mutates Git is stronger than executable truth.

Finding counts:

* BLOCKING: 1;
* IMPORTANT: 5;
* MINOR: 2; and
* INFO / WATCH: 5.

No finding rejects the central product direction. The BLOCKING classification
means only that the direction must not yet be promoted into a security/product
promise without the bounded conceptual corrections in section 8.

== 3. Review method

For each major claim, this review classified it as current fact, future
requirement, hypothesis, or open question, and asked:

. Which current authority or executable mechanism supports it?
. Which code path or accepted record narrows or contradicts it?
. Can a hostile or merely mistaken Level-1 caller cross the boundary without
  WFC observing the act?
. Can the governed agent itself cross it before post-effect observation?
. Does safety depend on voluntary prompt compliance or social operator
  discipline?
. Is an existing WFC responsibility moved to Level 1, or Level-1 semantic
  responsibility moved into WFC?
. Does the proposal introduce generic machinery before the DMC evidence needs
  it?
. What authority and persistence facts become unavoidable at the proposed
  boundary?

The review prefers concrete attack traces over abstract discomfort. It does
not count explicit, correctly classified future work as a defect merely
because it is unimplemented.

== 4. Findings

=== F-B1 -- BLOCKING -- An untrusted Higher Loop can bypass WFC completely; the concept lacks a protected caller/executor boundary

Concept location / claim:: Sections 1, 7, 8.5, 11.2, 11.5, 18, and Design
Principles 3--6. Level 1 is described as semi-trusted or compromised, may
request but not grant authority, may not perform trusted effects, and depends
on trusted Level 0 for effects and evidence. The product formulation is
"Bring your own orchestration; WFC supplies governed execution."

Current evidence:: `wfc` is an ordinary one-shot console process. The caller
supplies a repository path and governing paths. `operator.py` checks those
inputs only after it is invoked. `CodexCliAdapter` starts a child process under
the same ambient OS identity and merely requests provider-owned
`--sandbox workspace-write`. `architecture.md`, Project Memory, and
`self-development.adoc` explicitly deny any Coordinator-owned or verified
host/environment containment claim. Nothing launches an external Higher Loop
under a reduced OS identity, makes the target checkout read-only to it, or
forces mutations/commands/network/secrets through WFC.

Concrete attack:: A LangGraph node or other orchestrator running as the same
user executes:

[source,python]
----
open("src/foo.py", "w").write(payload)
----

and then invokes `git add`, `git commit`, an external command, a network
client, or a credential-reading API directly. It can likewise edit governance
or policy, move `HEAD`, create a commit containing a newly authored WorkItem,
or read sibling repositories and prior Run state. It need never invoke WFC.

Why safeguards do not catch it:: Scope domination, expected-HEAD checks,
governing digests, trusted evidence, route/Finding rules, and post-Hop Git
observation exist only inside an invoked WFC Run. They have no observation or
interposition point over an external process that acts directly. A later WFC
call may notice a changed HEAD, but that is evidence that the bypass already
happened, not prevention; the caller may simply never make the later call.
Prompting Level 1 to behave cannot turn this into a security boundary.

Smallest conceptual correction:: Add a distinct hard precondition beside F1:
an untrusted programmatic orchestrator must not possess ambient authority to
bypass Level 0. Before the product direction can carry a security claim, one
of the following (or an equivalent protected invocation boundary) must be
true: the Higher Loop runs in a restricted containment domain; the target
repository is not writable by it; repository mutation uses a distinct OS
identity; WFC is a separately privileged broker/service/process; or all
relevant filesystem, Git, command, secret, and network effects are mediated by
a protected boundary. State explicitly that this is separate from containment
of the worker invoked by WFC.

Direction impact:: This correction does not change the product split. It
makes "orchestrator -> WFC" a real trust boundary rather than a voluntary call
convention. Until then, the product sentence is a future integration direction
for trusted/cooperative callers, not a defensible security promise to
untrusted callers.

=== F-I1 -- IMPORTANT -- "Coordinator alone mutates Git" is not current executable truth against a hostile agent

Concept location / claim:: Section 5 item 6 says the Coordinator alone mutates
Git and agents own no Git; sections 11.2, 21.1, and the product-security
summary rely on "Coordinator-sole Git authority" as a present safeguard.

Current evidence:: Agent Operating Contract v6 prohibits agent-owned mutating
Git and current real DMC Runs use `CommitIntent` plus `trusted_commit()`.
However, `RoutingResult` still contains `claimed_commits`. When
`commit_intent is None`, `vertical.run_one_hop()` calls `observe_hop()` over
whatever commits appeared. `observe_hop()` can accept matching
`claimed_commits`; `delta.claim_mismatch` is not consulted by the vertical
reduction path; this path supplies no `max_commits=1`; and phase
`edit`/`commit` action checks occur only on the `CommitIntent` path.
`tests/unit/test_slice4.py` deliberately demonstrates that a provider process
can directly run `git add` and `git commit`; the test exercises uncertain
recovery after a later injected observation failure, but the direct mutation
itself is real. No Coordinator-owned sandbox prevents it.

Concrete attack:: A hostile worker changes an in-scope file, runs `git add`
and `git commit` itself with a subject containing the WorkItem/Hop tokens, and
returns the new commit in `claimed_commits` with `commit_intent: null`. If the
worktree is clean, changed paths are in scope, ancestry is linear, and the
subject passes, the current ordinary observation path has no rule declaring
the direct commit unauthorized. It can do this even though the prompt says not
to; the no-`CommitIntent` path does not test the phase's commit authority.

Why safeguards do not catch it:: Out-of-scope paths, dirty state, bad
ancestry, and bad subjects are observed and can stop the Run. Those checks
bound some results after mutation; they do not prove that the Coordinator was
the mutator. Provider sandboxing is expressly outside current trusted claims.

Smallest conceptual correction:: Replace the current-fact wording with the
truth: WFC has a narrow Coordinator-owned trusted-commit mechanism used by
current governed flows, and prompt-level prohibition of agent Git, but does
not yet mechanically prove Coordinator-sole Git mutation against a hostile
worker. Treat retirement/rejection of the legacy direct-commit path plus a
verified execution boundary as prerequisites for the stronger product claim.
Do not silently weaken the desired invariant.

Direction impact:: Sharpening only. Trusted Git remains correctly assigned to
Level 0; the present implementation assurance is narrower than the concept
states.

=== F-I2 -- IMPORTANT -- Level-1 durable state mixes authority, semantic facts, and operational continuity without a terminating authority root

Concept location / claim:: Sections 10.2, 11.6, 12, and 14.2. The concept
distinguishes the orchestration engine from a deterministic mutation kernel,
calls checkpoints operational continuity, lists Git/accepted artifacts/
"curated Level-1 domain state" as semantic truth, and persists goal,
authority envelope, closure criteria, accepted plan, open obligations,
supersession, relationships, and maintenance obligations. It says closure
criteria change only by explicit durable plan revision.

Current evidence:: The accepted execution-trust FTR requires effective
authority to resolve from inputs fixed or admitted independently of and before
the requester could influence them. Current WFC persistence is deliberately
not authority: checkpoint routes are re-derived from the admitted profile.
The concept imports that insight but does not finish it for Level 1. No source
or transition owner is named for Epic creation, plan-revision acceptance,
obligation deletion, child acceptance, supersession, authority-envelope
change, or Epic closure. "Curated" and "accepted" are adjectives, not
mechanical provenance.

Concrete attack:: The ordinary LangGraph transition code updates its durable
state to widen the Epic goal, replace the authority envelope, delete an
inconvenient obligation, mark a child accepted without a WFC result, supersede
unfinished work, or revise closure criteria to match the current state. On
restart it loads that state and reports a clean frontier. A small deterministic
schema validator can prove the mutation is well-formed while still accepting
the unauthorized semantic change.

Why safeguards do not catch it:: Repository-anchor revalidation proves only
what repository HEAD is. It does not prove the authority of an Epic goal or
the completeness of an obligation ledger. A reducer of
`WorkGraph + authorized Event -> WorkGraph'` is safe only if "authorized
Event" has a provenance and grant rule outside the engine that benefits from
the event. WFC Run evidence can prove a child result, but the concept does not
require Level 1 to bind `CHILD_ACCEPTED`, supersession, or closure to that
evidence.

Smallest conceptual correction:: Define three explicit classes:

. protected/admitted Epic authority: identity, goal, maximum authority
  envelope, closure criteria, and who may approve each kind of revision;
. append-only or equivalently audit-preserving semantic ledger: plan revisions,
  obligations, relationships, supersession, maintenance and closure events,
  each with evidence/provenance and transition authority; and
. disposable/rebuildable operational checkpoint: node position, caches, and
  other engine continuity.

The engine may propose events. A deterministic kernel may validate them. The
facts that widen authority, erase obligations, accept child evidence, revise
closure, or close the Epic must originate from a protected authority root or
from mechanically verified WFC evidence under a pre-authorized rule. Restart
must reconstruct/reconcile from the protected specification and semantic
ledger, never regenerate either from a model call.

Direction impact:: No change to the product split. This supplies the missing
authority model that makes `resume != replan` and "restart is semantically
invisible" enforceable rather than aspirational.

=== F-I3 -- IMPORTANT -- The first-MVP F1 escape hatch is procedural, not mechanically proven

Concept location / claim:: Sections 11.5, 19, and 21.2. The concept correctly
calls F1 a hard precondition for automated governing-input materialization,
then permits the first loop to stop for "a human act of authorship" or select
among bundles a human already authored and committed.

Current evidence:: `WorkItem.authority_source` is unverified prose.
`operator._pinned_text()` proves only that inputs are tracked at the selected
commit; A1 proves structural/path domination; digests prove within-Run
stability. The authority index adds an explicit *maintainer authorization per
real Run* as an operational rule, but the CLI has no authenticated approval
object or protected provenance check. The accepted trust-boundaries FTR is
stronger than "human-authored": it permits a human/maintainer root *or a
separately governed authority source* whose provenance is mechanically
protected, and it does not require one human act per future WorkItem when a
bounded envelope has already been independently admitted.

Concrete attack:: Level 1 writes and commits a bundle, fills
`authority_source` with "maintainer-prepared", and invokes the one-shot CLI at
the resulting HEAD. Alternatively it copies a pre-authored bundle and changes
the task or expected anchor. Current admission cannot distinguish those acts
from a maintainer-prepared bundle if the caller already has repository and
process authority.

Why safeguards do not catch it:: F2 ceilings bound how far a bundle can go;
they do not establish who authorized it. A LangGraph human interrupt is only a
pause unless the subsequent approval and launch occur through a protected
identity/path. Git authorship is not a sufficient root, and the Coordinator's
own commit can carry the maintainer's configured Git identity.

Smallest conceptual correction:: State that the proposed first MVP is safe
only as a *procedurally supervised* tool: it may recommend/select and prepare a
request, but must stop before materialization and launch so that an external,
independently trusted operator authors or approves the exact immutable bundle
and invokes WFC. Do not describe that as mechanical F1 closure. Also preserve
the more general future option: a protected authority source may pre-authorize
a bounded family/envelope of future WorkItems; a maintainer act per WorkItem is
not an architectural invariant.

Direction impact:: No product-direction change. It narrows the first MVP and
aligns the concept with the accepted FTR's actual provenance rule.

=== F-I4 -- IMPORTANT -- The non-self-similarity argument is too absolute and conflicts with governed Level-1 effects

Concept location / claim:: Sections 1, 8.1, and 8.5 say the two levels are not
recursively self-similar, that a bounded-admission abstraction has "nothing to
offer" Level 1, and that *any* design making Level 1 an instance of Level 0
puts programme intelligence inside the security boundary. Sections 6 and 14.1
simultaneously require Level-1 maintenance mutations to execute through
bounded Level-0 WorkItems.

Current evidence:: DMC proves that an Epic lifetime is not one WFC Run: its
size, branches, supersession, return points, and closure emerge over time.
That supports separate lifecycle semantics and separate product ownership. It
does not prove that bounded *operations on Level-1 state* cannot use WFC. WFC
can govern opaque plan-ledger, closure-record, or maintenance-file mutations
without understanding DMC. The imported composable concept also correctly
observed that automated preparation may itself be governed execution.

Concrete failure:: A designer reads the absolute rule as forbidding WFC from
governing plan revisions or the Level-1 semantic ledger, so the semi-trusted
orchestrator edits them directly. It then deletes an obligation or changes
closure criteria outside any bounded review. The opposite design -- Level 1
remains external and owns the semantics, while a bounded opaque ledger edit is
submitted to WFC -- does not put LangGraph or DMC logic in the WFC reducer.

Why safeguards do not catch it:: The concept's maintenance exception already
admits the compositional case but does not repair the universal statements.
The absolute wording may therefore move a security-sensitive effect to the
wrong side of the boundary.

Smallest conceptual correction:: Preserve the strong product rule but narrow
the proof: *the long-lived Level-1 lifecycle is not representable as one
Level-0 Run, and WFC must not own Level-1 planning semantics or topology.* Add
that individual Level-1 effects, including preparation, ledger maintenance,
or closure artifacts, may themselves be bounded governed WFC executions when
that is useful. Reusing the governed-execution primitive is not the same as
putting the orchestration engine inside WFC.

Direction impact:: This sharpens rather than reverses the Level-0/Level-1
split. The products remain separate and the dependency remains
`orchestrator -> WFC`.

=== F-I5 -- IMPORTANT -- Current resource/security/assurance enforcement is narrower than the three-axis model

Concept location / claim:: Sections 11.1--11.3 and 22 separate profile,
security/capability policy, and assurance floor; the worked example rejects an
`execute -> complete` profile over `.github/workflows/release.yml`; section
21.1 titles the current gap as containment.

Current evidence:: Section 11.2's caution correctly labels the *pipeline* as
future, but the later summaries can still be read as though only containment
is missing. Current `RepositoryPolicy` has repository scope, governance paths,
WorkItem path ceiling, Hop ceiling, actions, and evidence commands. It has no
resource classes, capability/data classifications, profile allowlist,
security floor, or assurance floor. Preflight checks phase actions against
policy actions and scopes against ceilings; it does not infer mandatory
independent review from `.github`, release tooling, generated executable
configuration, mixed resources, or deferred effects. Both cited security
FTRs are proposed/deferred, not implemented mechanisms.

Concrete attack:: A committed/admitted policy ceiling includes
`.github/workflows/release.yml` and actions `edit, commit`; a committed simple
profile has one worker phase and a complete route. Current preflight can admit
that combination. The same is true for an innocuous-looking source generator
that emits a later-executed hook or build configuration: path scope and the
requested action do not classify the deferred execution effect. A mixed
WorkItem has no current rule computing the strongest applicable assurance
floor.

Why safeguards do not catch it:: Current checks prove requested values fit
explicit ceilings; they do not derive missing controls from resource/effect
classification. Human authorship of the current bundle is the present
assurance, not a generic WFC rule.

Smallest conceptual correction:: In the current/future correction and roadmap
implications, state explicitly that *resource/effect classification, security-
floor derivation, assurance-floor derivation, and profile compatibility are
all future*, not merely OS containment. Retain the three-axis invariant and
the fail-closed worked example as future design. Do not describe either FTR as
supplying a current mechanism.

Direction impact:: No direction change. It prevents the product description
from advertising a control that the current schema and preflight do not
contain.

=== F-M1 -- MINOR -- Parent/child suspension is reducer semantics, not a current end-to-end operator capability

Concept location / claim:: Section 13.2 says Level 0 "already owns" suspension
and return mechanics through `suspend_for_prerequisite`, `child_run_id`,
`suspension_head`, and `prerequisite_return` reconciliation.

The corrected responsibility split is right. These fields and pure functions
exist and have replay/unit coverage. Production `operator.py`, however, is
one-shot: it rejects an existing state root and has no entrypoint calling
`authorize_prerequisite()`, `require_reconcile(reason="prerequisite_return")`,
or `resume_after_reconcile()`. The atomic-hop recovery FTR records the same
operator gap for reconcile/resume generally. The smallest correction is to
say Level 0 *models and tests* these mechanics, while production operator
wiring and outer child dispatch are not current capabilities. This affects
truthful current-state wording, not the ownership boundary.

=== F-M2 -- MINOR -- The design-principles summary weakens the cross-Run policy invariant

Concept location / claim:: Section 11.4 states the strong invariant that
policy is trusted input and not ordinary output of the agent it governs,
including an unresolved cross-Run representation. Design Principle 13 narrows
this to policy not being mutable "within the execution it governs."

That summary wording reintroduces the exact F1 laundering channel the body
correctly discusses: an agent may not change this Run's policy but could
author the next Run's policy. Replace the summary with the full provenance
rule: effective governing inputs must be independently rooted and fixed before
the requester can influence them; agent output does not become authority by
commit, reference, or passage through another component.

=== F-W1 -- INFO / WATCH -- Graph-primary / stack-projection is a justified hypothesis, not an MVP requirement

RELKEY's Slice-1 fan-out, cross-branch supersession of C3-S2, the independent
3a/3b branches, and obligations surviving the discovering WorkItem show that
a literal single stack is insufficient as the semantic model. Deletion
Authority also proves the usefulness of a return projection. The concept
correctly labels graph-primary as HYPOTHESIS and leaves explicit graph versus
structured plan OPEN. For the first MVP, a small versioned structure with
stable IDs, dependencies, supersession, open obligations, and return anchors
is enough; no generic node registry, graph DSL, or generic Epic framework is
earned.

=== F-W2 -- INFO / WATCH -- Reducer logic is correctly reinterpreted, conditional on F-I2

The concept correctly retains the Level-0 reducer and separates durable state
from controlled mutation. A small deterministic Level-1 mutation/admission
kernel is plausible, but schema determinism alone does not grant authority.
F-I2's protected event provenance must precede any claim that the kernel is an
authority mechanism. There is no basis to abandon the reducer insight or to
build a second general workflow engine now.

=== F-W3 -- INFO / WATCH -- LangGraph is replaceable infrastructure and is not needed to validate the boundary

The dependency direction is sound: WFC must not require LangGraph in its core,
package, runtime semantics, or governance contracts. An alternate
orchestrator can call the same future WFC interface without WFC changes.
LangGraph's routing/checkpoint/interrupt facilities are plausible conveniences
for Level 1, but its checkpoint and human interrupt must not become authority.
The first advisory MVP may be small enough that a structured state file and
ordinary control code are simpler. This review neither adopts nor rejects
LangGraph.

=== F-W4 -- INFO / WATCH -- Deferred execution is correctly identified; the future classifier must follow effects and provenance, not filenames alone

The concept does not reduce policy to a path allow-list. It names actions,
data/capability classification, Git hooks, CI, packaging, test discovery,
build/deploy configuration, and the trusted-service confused-deputy problem.
"Strongest applicable requirement wins or split" is the correct composition
rule. Future design still has to classify a harmless-looking source generator
whose output becomes executable configuration, and agent-authored artifacts
later consumed by trusted services. That is an open implementation/design
question, not a defect in the stated boundary.

=== F-W5 -- INFO / WATCH -- WFC generality survives, but current substrate and assurance limits must remain visible

No DMC/Epic/LangGraph vocabulary occurs in the deterministic core or current
governance. The role/persona/binding implementation and neutral tests support
documentation, TypeScript, Rust, and other repository subjects without core
changes. Current WFC remains Git/repository-native and Codex-CLI-specific in
its production adapter; infrastructure/deployment repositories expose the
unimplemented assurance/containment work most sharply. This is a truthful
substrate constraint, not evidence that WFC should become a general security
platform.

| Future requirement, not current fact (F-I5).

| C: `implement -> review`, release/deployment tooling
| Admit only if containment, capability, evidence, and assurance floors all
match the resource/effects.
| Review occurs because the supplied profile requests it, not because Level 0
derives it from the target.
| Topology and assurance are separate in the concept, not yet in the schema.

| D: ordinary-looking source produces a dangerous deferred artifact
| Classify the indirect effect and trusted consumer; containment now is
insufficient without later review/least-authority execution.
| No derived-effect classifier exists.
| Concept handles the threat correctly; future policy must be semantic and
provenance-aware (F-W4).

| E: one WorkItem spans ordinary and high-risk resources
| Strongest applicable floor wins or split the item.
| No resource-class join exists; only explicit path/action ceilings apply.
| Correct future invariant, not current enforcement.
|===

== 6. Boundary assessments

=== 6.1 Level 0 versus Level 1

The materially sound split is by *responsibility and lifetime*, not by a ban on
composition:

* Level 0 admits and executes one bounded request under immutable Run truth,
  owns effect/evidence mechanics, and converges or stops.
* Level 1 owns long-lived semantic identity, work discovery, planning,
  dependencies, supersession, maintenance, and evidence-based closure across
  many Runs and repository states.

Long-lived goals with unknown size, discovery, prerequisites, branches,
suspension/continuation, replanning, maintenance, closure, and many-Run
persistence all remain Level 1. Level 0 may still govern an individual edit to
Level-1 durable artifacts without knowing their DMC meaning.

=== 6.2 Parent/child split

The section 13.2 correction is architecturally right. Level 0 owns the generic
Run-local suspension/return-anchor semantics; Level 1 owns the semantic work
relationship that may span multiple Runs and outlive any one parent Run.
Deletion Authority proves why a child cannot be represented only by
`child_run_id`: it was an independently evolving body of work. RELKEY proves
why return means reconsider under current truth, not replay a stale parent
action. The only correction is current-capability precision (F-M1).

=== 6.3 Epic size, planning, and closure

`Epic = goal + authority envelope + closure criteria` is a useful HYPOTHESIS.
It handles both a three-task Epic and the open DMC programme without assuming
task count, nesting depth, fixed upfront decomposition, replanning after every
child, or no replanning. "No scheduled child" is correctly rejected as
closure; FK Cycle 2's accepted negative result is good evidence. Closure
criteria are rightly first-class, but F-I2 must define who may revise or
accept them and how restart preserves them.

=== 6.4 Graph, stack, and reducer

A graph-shaped semantic model is justified by current evidence, while generic
graph infrastructure is not. A stack is a useful current-path/return
projection. Reducer logic remains authoritative at Level 0 and is plausibly
reused as a small Level-1 event-admission kernel only after protected event
authority is defined. Persistence never becomes authority merely by being
durable.

=== 6.5 Containment

Containment of the governed worker and construction of the effective execution
envelope belong on Level 0's side. The concept accurately denies that WFC
currently owns or verifies such containment and does not claim `bwrap` exists.
Policy weakening by the worker must remain impossible, and an untrusted caller
must never select `sandbox=false`. F-B1 adds the omitted second boundary:
containment/mediation of the external orchestrator itself. F-I1 additionally
narrows the present Git guarantee until worker containment and the legacy
direct-commit path are resolved.

=== 6.6 Product generality

The proposal successfully keeps DMC planning out of WFC. Existing LangGraph
applications, CI drivers, other agent frameworks, and different language or
documentation repositories can all be callers in principle. The invariant is
an orchestration-neutral request/result contract admitted by WFC, not a
LangGraph API. Conversely, WFC should derive only the execution controls it
must enforce; it should not become a project planner, universal DLP engine,
classification ontology, credential platform, or general-purpose security
operating system.

== 7. Explicit answers to the required questions

. *Is the Level-0 / Level-1 split materially sound?* *Yes*, as a
  responsibility/product/lifetime split. Level 1 must remain external and WFC
  must not understand its domain semantics. The absolute claim that Level-0
  governed execution has "nothing to offer" bounded Level-1 effects must be
  corrected (F-I4).

. *Is "Bring your own orchestration; WFC supplies governed execution"
  defensible under the current security model?* *Only as a future product
  direction, or today for a trusted/cooperative caller under external operator
  discipline.* It is not a security claim for untrusted programmatic callers
  until caller mediation/containment, F1 provenance, worker containment, and
  resource/assurance derivation are resolved.

. *Can an untrusted Higher Loop currently bypass WFC? Is the omission
  blocking?* *Yes.* With ordinary same-user access it can directly modify the
  checkout/governance, move Git, run tools, read secrets/sibling files, and use
  network. The omission is *BLOCKING for promoting this concept into a
  product-security boundary or README promise*, but it is a bounded missing
  prerequisite rather than evidence against the product split itself.

. *Is F1 represented strongly enough?* The diagnosis and invariant are strong,
  and policy ceilings are not confused with provenance. The first-MVP remedy
  is not mechanically strong enough: "human-authored" is not a verifiable
  property today (F-I3). Preserve the protected non-human authority-root option
  and do not require a maintainer act per WorkItem as a universal rule.

. *Are workflow topology, capability/security, and assurance floor genuinely
  separated?* *Yes conceptually.* Current WFC does not yet implement the latter
  two as derived axes; supplied policy/profile configuration and human
  authorship provide today's control (F-I5).

. *Is the future resource/security-policy concept robust against indirect and
  deferred execution?* *Directionally yes.* It explicitly rejects path-only
  reasoning, names confused-deputy/deferred effects, and applies the strongest
  floor or split rule. Actual classification must follow generated/deferred
  effects and trusted consumers, not filenames alone (F-W4).

. *Is containment on the correct side without overstatement?* Worker execution
  containment is correctly a future Level-0 duty and current provider-owned
  sandboxing is accurately disclaimed. The concept omits caller/orchestrator
  containment or protected brokerage (F-B1), and present Coordinator-sole Git
  wording is overstated (F-I1).

. *Is Level-1 persistence sufficiently explicit about authority versus
  operational state?* *No.* Checkpoint versus repository truth is a good start,
  but goal/envelope/closure/obligation/acceptance/supersession authority lacks
  a protected root and event provenance (F-I2).

. *Is graph-primary / stack-projection justified?* *Yes as a HYPOTHESIS.* Real
  branches, supersession, obligations, and return addresses falsify a lone
  stack. They do not justify a generic graph framework for the MVP.

. *Is reducer logic correctly reinterpreted?* *Yes, conditionally.* Durable
  persistence and deterministic mutation admission are correctly separated;
  the Level-1 kernel becomes an authority mechanism only after F-I2 defines
  authorized-event provenance.

. *Is LangGraph replaceable infrastructure rather than product authority?*
  *Yes.* WFC has and should retain no LangGraph dependency. Checkpoints,
  interrupts, and routing remain conveniences, never authority. No adoption is
  authorized or needed to accept the product boundary.

. *Can the first DMC Higher-Loop MVP remain small?* *Yes, only if narrowed.*
  The minimum useful subset is deterministic repository/state reconciliation,
  a small versioned obligation/dependency/return record, next-action
  recommendation or selection from already prepared candidates, WFC-result
  ingestion, maintenance/closure checks, and an external human stop before
  governing-input approval and launch. Untrusted automatic materialization and
  invocation pull in F-B1/F-I2/F-I3/F-I5 and are not a small first MVP.

. *Does the concept require WFC to understand DMC/Epic semantics?* *No.* DMC
  vocabulary remains outside `src/`, current neutral tests prove subject
  generality, and opaque bounded Level-1 artifact mutations do not change that.

. *What must be corrected before a fundamental README/product rewrite?* Apply
  all six items in section 8. No implementation, LangGraph adoption, FTR
  promotion, or backlog change follows from this review.

== 8. Exact conceptual corrections required before README/product-scope realignment

. Add the missing protected caller/executor boundary as a hard prerequisite
  parallel to F1. Distinguish containment of Level 1 from containment of the
  worker invoked by Level 0.
. Recast the BYO-orchestration sentence as current only for trusted/cooperative
  callers under external operator control; present untrusted programmatic
  orchestration as future until that boundary and F1 are mechanical.
. Correct present Git wording: current WFC provides a trusted-commit path but
  does not prove Coordinator-sole Git mutation against a hostile worker while
  provider containment is unverified and the legacy `claimed_commits` path is
  admitted.
. Define protected Epic authority, an audit-preserving semantic event/obligation
  ledger with transition provenance, and disposable operational checkpoints;
  bind child acceptance/closure/supersession to protected authority or verified
  WFC evidence.
. Preserve F1's broader authority-root rule. Mark "human-authored bundle" as a
  procedural first-MVP stop, not mechanical provenance, and allow a separately
  protected source to pre-authorize a bounded family without a human act for
  every item.
. Narrow the non-self-similarity absolute: the Level-1 lifecycle is not one WFC
  Run and WFC owns no planning semantics, but bounded Level-1 effects may use
  WFC. Explicitly classify resource/effect security-floor, assurance-floor,
  and profile-compatibility derivation as future alongside containment, and
  describe prerequisite suspension as modeled/tested but not operator-wired.

These corrections sharpen the product direction; none moves DMC/Epic semantics
into WFC, makes LangGraph authoritative, or authorizes implementation.

== 9. First Higher-Loop MVP assessment

The proposed full illustrative flow is small in diagram form but crosses four
unsolved trust seams if treated as unattended automation: authority-rooted
Epic state, governing-input provenance, caller mediation, and current
resource/assurance derivation. It remains realistically small only as a
supervised continuation assistant.

Minimum value-bearing slice:

[source,text]
----
load protected Epic specification + semantic ledger
reconcile repository anchor and already-accepted WFC results
compute eligible/open obligations deterministically
recommend one next bounded action, or select one exact pre-prepared bundle
pause for independent maintainer approval/authorship and WFC launch
ingest the immutable WFC result deterministically
append evidence-linked obligation/maintenance/closure state
----

For the current RELKEY evidence, this can retain Slice-1 -> (2, 3a, 3b) -> 4,
the C3-S2 supersession, failed-Run dispositions, lifecycle alignment, and
closure obligations without a generic Epic framework. LangGraph may or may not
reduce application code; it is not required to obtain this first value.

Explicitly deferred from the MVP: automatic governing-input materialization;
unattended WFC launch; a generic graph schema; a plugin system; an
orchestration DSL; a node registry; multi-repository mutation; parallel
children; model/provider routing; generic privilege/resource taxonomy; and a
second workflow engine.

== 13. Final statement

The proposed product boundary survives adversarial review as a working
direction, but not yet as a security boundary for untrusted BYO orchestration.
WFC should remain a bounded governed executor and Level 1 should remain an
external semantic orchestrator. Before that sentence drives the README or
roadmap, the concept must name the protected caller boundary, terminate
Level-1 authority mechanically, stop treating procedural human authorship as
F1 proof, qualify current trusted-Git and resource/assurance claims, and soften
the false universal ban on using governed execution for bounded Level-1
effects. Those are material corrections, not a new product design.
