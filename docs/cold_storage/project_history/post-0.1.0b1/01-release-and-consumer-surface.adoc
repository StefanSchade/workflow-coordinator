=== The 0.1.0b1 release and the consumer-surface sprint (23--24 November 2026)

This chapter distinguishes *direct evidence* (Git, the repository's review and
backlog records, the archived Runs, and for the release the public GitHub and
package-index data read by the Operator on 24 November), *reconstruction* (a
sequence assembled from those sources) and *interpretation*. Acceptance below
means independent acceptance at Run level; it is not product closure, Runtime
promotion or a release. The operational detail of every Run is in the Run
Ledger of the sibling Evidence repository (entry of `c68caed`); it is
referenced here, not repeated. Times are Git author times in CET unless marked
UTC. Cut-off: Development `main` at `39e5a84`.

==== The release (23 November)

*Direct evidence.* The release notes were frozen in `7e4fbcc`; the maintainer's
acceptances of MD-5 (`a72a6e5`) and of the consumer qualification G7 (`baab49e`)
are recorded in the developer guide. The annotated tag `v0.1.0b1` points at
`baab49e` (tagger time 16:33 CET). The hosted workflow ran on that commit twice:
run 10 for the `main` push (ID `45198972182`) and run 11 for the tag push (ID `45206570404`), both
`success`. In run 11 the `check` job, the three informational compatibility
jobs, `publish-testpypi`, `publish-pypi` and `release` all concluded `success`,
in that order. The package index data show `workflow-coordinator 0.1.0b1` on
TestPyPI (upload 15:46 UTC) and on PyPI (upload 15:52 UTC) with identical
digests (wheel `edb85eeb5561dde7976e7c27a9523ce735317dc048eec5ec1d15763f8e9e0418`,
sdist `e5c75796c7219e6f178029f12726aedd3505f7f25284015a81e985dea85e99af`), and
a GitHub Release `v0.1.0b1` published at 15:53 UTC with the same two files.
All 44 members of the published wheel are byte-identical to those of the
release-candidate wheel that Q1-A and Q1-B had used; the wheel containers
differ, because the tag run built its own artifact.

*Not visible in the data read.* The approval of the `pypi` environment (G8) is
the maintainer's act; the public data show only that `publish-pypi` ran about
six minutes after `publish-testpypi`. The GitHub Release is not flagged as a
pre-release although the version is a beta. Neither point is interpreted here.

==== Level-1 orchestration, parallelism and the recovery from the usage limit

*Direct evidence.* One Level-1 Claude Code session wrote the Commissions,
previewed them with `wfc plan`, launched the Runs in separate Git worktrees,
verified each accepted result itself (lint, the full suite, build and artifact
audit, and for the kit and the skill a run against a built or the released
wheel) and integrated by fast-forward or `--no-ff` merge. Its commits of this
sprint carry the trailer `Claude Fable 5.2`, those up to the release
`Claude Sonnet 5.5`; the Workers ran on `claude-sonnet-5` and the reviewers on
`claude-opus-5` throughout. Up to three Runs were active at the same time
(Tutorials S1, Demo Workspace S2 and Agent Skill S1 from 22:07 on 23 November);
later pairs ran side by side (the two first continuations around midnight;
the Demo S2 continuation and Agent Skill S2 after 03:13).

*Direct evidence.* At about 22:52 on 23 November the three concurrent Runs
stopped `reconcile_required` within a minute of each other, each at a provider dispatch that was interrupted
after its dispatch marker; the retained engine state of one names the
provider's usage limit, and the Level-1 session reached the same limit at that
time. WFC stopped and archived the three Runs; it did not resume or repair
them. After the limit reset, the Level-1 operator continued each slice by a
freshly authorized *review-first continuation* Commission off the stopped
branch in a new worktree: a Worker Hop that verified the existing candidate
against every acceptance criterion and corrected only demonstrated defects,
followed by a whole-slice independent review. The stopped Runs were not
declared successful afterwards. At the maintainer's request no further
Commission was started until the weekly usage renewal at 03:00; the two
continuations already running were left to finish, and later starts were
staggered with at most two Runs in parallel.

*Interpretation.* The recovery was the operator's work on WFC's retained state
and evidence, by the documented procedure; it is not an autonomous recovery
capability of the product. The parallelism again sat at the orchestration
level and in worktree isolation, as on 23 November (chapter 13).

==== What the independent reviews found

*Direct evidence, from the review records and the Runs' Finding ledgers.*

* Agent Skill S1: the packaged skill text stated facts about the CLI that are
  false, among them about what consumes a checkout's lifecycle, with an
  incomplete account elsewhere; corrected in `2310d37`.
* Agent Skill S2: `make check` did not pass, because lines added to a
  format-checked file failed the format check; and a test of the installer
  could write outside its temporary home when `CLAUDE_CONFIG_DIR` was inherited
  from the environment; both corrected (`f0f3f7b`, `15daaaf`). No real agent
  configuration directory was found written.
* Demo Workspace S2: `rehearse.py` did not answer an unresolvable `wfc`
  executable with return code 2 before creating anything; corrected in
  `2fa7c61` and confirmed by the continuation.
* Tutorials S1: the new link rule's own example was itself a dead in-page
  reference; corrected in `1875ab3`.
* Tutorials S2 and S3: the live command sequence of the tutorials could not be
  followed as printed; a "What was verified" section claimed commands that
  had not been executed for the page; one statement about where `--yes`
  appears was untrue; and Tutorial 2 said the two roles may use different
  adapters, which a Run does not support; corrected in `40bb1ce` and `fe8ea28`.

Demo Workspace S1 was accepted at the first review with six non-blocking
observations, three of which S2 took up.

==== Effectiveness, cost and what remains open

*Demonstrated.* The parallel, operator-driven procedure delivered seven
authorized slices, each independently reviewed and integrated, in about
eleven hours of wall time including a forced interruption, and it absorbed
that interruption without losing work or weakening an acceptance.

*Not demonstrated.* Whether this was efficient compared with a sequential
execution is open. The interruption cost three additional continuation Runs
(2, 7 and 2 Hops); a high concurrent model consumption is not by itself
evidence of worse overall efficiency, and no token or cost figure was
collected (WFC reports no usage in this version). No productivity or cost
figure is derived here.

*An open diagnostic gap.* One launch (Tutorials S1, first attempt, about 21:25 on 23 November) was
refused before any provider started because the baseline probe, the full
suite, failed once while a second suite started at the same time. The suite
passed when re-run alone in the same worktree, and the failing test could not
be identified, because the probe's output is not retained. This is recorded
as a missing diagnostic, not as a demonstrated concurrency defect and not as
a failure of the evidence architecture.

*An unexplained hosted result.* The maintainer pushed `main` at `3379a03` on
24 November; the hosted run 12 (ID `45345678011`, 07:08 UTC) concluded
`failure` in the step `Required test suite`. The Operator could not read the
log, found the suite green on that commit locally, also under an imitation of
the runner's Git and temporary-directory set-up, and does not know the cause
or whether it is related to the refused baseline probe.

Development `main` is at `39e5a84`, eleven commits ahead of the pushed
`3379a03`; nothing was pushed, tagged or published by the Operator. Development
