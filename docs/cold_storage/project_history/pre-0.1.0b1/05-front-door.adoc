=== P3.5 Finding reachability: design review (19.10.2026–20.10.2026)

Commits: `2735e98`, `eac9dfc`, `6075417`, `11759b0`, `8fc44ee`, `4f9598f`, `04c784c`, `6807d56`, `b3dbbd9`.

Backlog (related):: link:../../backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc[BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY]

A Finding records an issue that can block completion; disposition is an authorized treatment such as `resolve`, `residual` or `supersede`. The practical problem: if a review phase opens a blocking Finding and no later reachable phase may handle it, a Run can stop only after spending Hops. P3.5 sought to identify this configuration statically, without a provider, during preflight.

The design examined the phase graph and required paths to a completion or equivalent checkpoint to pass a later phase with suitable disposition authority. That did not guarantee a Run would reach that phase: the check proved neither termination nor completion within the Hop budget. Several corrections exhausted the review budget; only a focused successor accepted the design. P3.5 as a whole was not implemented.

=== P3.5: structural invariant reassessment (21.10.2026–25.10.2026)

Commits: `194bfcc`, `2391d80`, `ecb8f51`, `079b508`, `cbc59ef`, `65720a6`, `165de29`, `fab606e`.

After MVP planning, an independent reassessment asked what additional protection the accepted static check offered beyond the existing runtime rule: the reducer already prevents completion with an open blocking Finding. The review observed that a reachable authorized phase alone does not prove the agent will select it or resolve the issue.

The accepted reassessment recommended deferring the P3.5 package for Level 0 while retaining the existing completion guard. It was a recommendation for maintainer disposition and did not erase the earlier design acceptance.

=== P3.5: requirements archaeology (26.10.2026)

Commits: `1cb5b4f`, `0de42a5`, `8196bbe`, `27622fd`, `b3988d0`, `e5af5c8`, `b6d2937`, `4da394a`, `8c07595`.

The second reassessment examined the original requirement: must *at least one* authorized disposition path exist, or must *every* possible completion path first pass such a phase? A profile with a correction loop and a direct completion branch distinguishes the claims; the existing runtime guard would prevent direct completion with an open Finding.

Following an uncertain provider exit and a fresh attempt, the accepted review recommended escalating this semantic ambiguity to the maintainer; Front Door and the Profile/Commission boundary moved up in priority. The later maintainer decision `DEC-WFC-018` selected the narrower existential authority- and state-aware reachability predicate; implementation remained deferred. See the link:../backlog/pre-0.1.0b1/p35-commission-authority-conformance/README.adoc[P3.5 archive] for the comparison.
