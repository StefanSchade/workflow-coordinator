=== From sequenced Commissions to two-level orchestration (18–20 November 2026)

This is a historical retrospective. It states what the Git history, the review
artifacts and the sibling `workflow-coordinator-run-evidence` repository show;
it is not a product requirement, an authorization or a measure of productivity.

==== Before: an externally sequenced series

Through 17 November, self-development (chapter 10) ran as a series of single
Commissions. The maintainer sequenced them one by one: authoring or approving
each Commission, preparing and launching the Run, reading the review
artifacts, deciding on follow-up Commissions, archiving the Evidence and
handling every stop and recovery step. WFC enforced authority inside one Run;
everything between Runs was manual operator work.

==== The new division of labour

On 19 November the maintainer asked a Claude Code session (Sonnet, "Level 1")
to act as WFC Operator for the Beta-1 productization series, after reading the
Operator Manual, and widened that authority stepwise on the same day: commit,
launch, Runtime promotion if needed and start the following Commissions, with
the limit set by what the plan allows. Push was not granted.

* *Level 1 (the Operator agent)* decomposed packages (for example BP4 into BP4a
  and BP4b, BP6 into BP6a/BP6b/BP6c), authored and rendered Commissions,
  ran `commission check`, `prepare` and `launch`, monitored Runs, interpreted
  review outcomes and stops, organized corrections and successor Runs,
  archived Evidence and applied the scratch-cleanup rule.
* *Level 0 (WFC)* enforced the authorized boundaries mechanically: Commission
  pins and scope, one Run per checkout, Coordinator-owned commits, the
  Coordinator `task-check`, Finding authority, the Hop ceiling and the stop
  states. Level 1 could not and did not override these.
* *Reviewers and Workers* inside each Run were separate fresh agent
  invocations (Sonnet Worker, Opus reviewer).
* *The maintainer* kept the decisions: DG-3 (Variant B supervision basis),
  DG-1 (token usage as fast-follow), the BP4a/BP4b split approvals, product
  acceptances and every disposition of a stopped Run.

Two stops are part of the record and are not to be read as successes. BP4b
reached its Hop ceiling because five review cycles worked through one class of
edge case (non-UTF-8 bytes in Git paths and filter names) one Git boundary at a
time; the review's acceptance and the Hop ceiling coincided, and the maintainer
accepted the candidate in a separate decision. BP6b stopped on the reducer's
Finding-authority rule and was continued only by a separately authorized fresh
successor Run, the same pattern as the BP5 recovery recorded in chapter 11.

The same two days also produced operating rules that Level 1 recorded in the
repository: a documented stance that scratch directories are released after a
verified archive (`baea36c`, generalized in `b5d12fc` after a root-filesystem
inode exhaustion traced to retained per-Attempt scratch), forward-only
handling of stops (preserve, archive, disposition, fresh successor) and the
BP4a/BP4b/BP6 package boundaries recorded in the Epic.

==== BP6c as a worked case

BP6c shows the division of labour on a single decision. The first Run
(Commission `ccf86fa`, Evidence `75acb72`) stopped mechanically after one Hop:
the Worker had found that every Run of a consumer would archive under the
directory name `engine-state` and, lacking authority to change the design,
escalated instead of committing. WFC stopped fail-closed (`awaiting_human`);
Level 1 archived the stop truthfully and preserved the uncommitted candidate as
non-authoritative salvage (`07ac532`) without discarding anything.

The maintainer then made exactly one architecture decision: the archive
identity derives from the Run identity, with idempotency and a regression test
of two Runs in one Evidence repository. Everything after that was organized by
Level 1 under the established procedure: a successor Commission (`0c5d8da`)
with the decision, the salvage and the fixture-adaptation rule written into
its authority, then the Run itself. That Run used nine Hops with several
independent reviews (`a0aec9e`, `21ad91c`, `492effc`, `f62602b`), corrections
(`213fb08`, `bf499b9`) and a final accepting broad review (`2e2635e`); Evidence
`7a3b6fa`. The successor never retroactively completed the stopped Run.

For the human work this is the change in a small scale: the maintainer did not
steer individual Hops, review rounds or archive steps; the maintainer decided one
question that was theirs. The Runtime promotion that followed was authorized in
one statement and executed by Level 1 under the maintainer-owned runbook.

==== A Level-1 mistake and its recovery (BP7 C1b)

On 20 November the first C1b Run needed a fixture built from an archived Run in
the sibling Evidence repository. Level 1 had not staged that input where a Worker
sandbox can read it. The Worker stopped correctly (`blocked`), invented nothing,
recorded exactly what was missing in its provenance file and left a coherent
partial candidate. Recovery stayed controlled: archive of the stopped Run
(Evidence `a5031af`), a non-authoritative salvage ref (`acb5561`), a targeted
stash of exactly the three working files after maintainer approval, staging of the
input under an ignored `build/` path and a successor Run (`RUN-c158a62359d84731836f65b0efd8c532`,
Commission `e2e43de`) that verified the staged copy independently against its manifest
digests and completed in two Hops. Earlier the same day, a planning Run had also
stopped because Level 1 launched it without the offline-input wrapper that the
Coordinator's task-check needs; the plan itself had been accepted by an independent
review and was taken over by a separate maintainer decision.

==== Limits of the autonomy

* There was no Level-1 intervention inside a running WFC Run. Level 1 acted
  between Runs; within a Run, Workers, reviewers and the Coordinator acted
  under Level 0 authority.
* Substantive decisions and significant authorizations stayed with the
  maintainer: supervision basis, scope of each decision gate, acceptances of
  stopped Runs, dispositions, the Runtime-promotion and push boundaries.
* Level 1 made its own mistakes and the maintainer corrected them, for
  example by rejecting a proposal to discard a Run without consultation and by
  correcting a crash-matrix case that equated a free lock and absent state with
  "no launch".
* Recurring misunderstandings about Finding authority and about the review
  economy (how many Hops an edge-case class may consume) remain improvement
  potential; the Hop ceiling for BP4b and the preemption for BP6b are
  instances.
* An integrated autonomous multi-Commission product function does not follow
  from this. The orchestration was done by a conversational agent using the
  existing Harness and manual; it is not a feature of WFC.

==== BP7: the cutover to the product itself (20/21 November)

BP7 is the case in which the product replaced the tool that had built it. After the
maintainer's decisions (cutover before the tag; the old Harness stays until two real
archived Runs through the product Front Door), Level 1 drove the sequence without
further per-step approvals. Two small real tasks served as proofs: an error-message
improvement in `evidence.py` (`RUN-25295d0d0d3b40d9b8069e0f143ba3a3`, 8 Hops, two
blocking reviews corrected on the way) and a documentation reconciliation of four
accepted BUG records (`RUN-3e19e853f30246199b938856e3f145c7`, 5 Hops). Each was
archived by the product's own lifecycle into the sibling Evidence repository, and a
frozen legacy archiver produced identical file hashes on a disposable copy. The
retirement Commission (`RUN-3d46d38115a843fb8699bb713d01da30`, 5 Hops) then removed
the legacy Harness, its tests and the v1 compile path and moved the manual to the
product commands; it ran through the product Front Door itself.

Things that did not go smoothly are part of the record. A background monitor that
checked liveness with `pgrep -f` matched its own command line and kept running after
the Run had ended; the maintainer noticed, and Level 1 verified from the lifecycle
classification instead. The product allows one lifecycle per checkout, so the second
proof and the retirement needed fresh worktrees; this gap had already been recorded
in the BP4a review and became a backlog item after the maintainer asked about the
intended target picture. Level 1 also had to widen the retirement scope beyond the
plan's file list after searching for live references, and verified the result itself
rather than relying on the Run's review alone.

For the human role this meant that, during BP7, the maintainer decided a handful of
architecture questions (DG-4/DG-5, BP6c Option 1, the three open BP7 decisions, the
choice of the second proof task) and asked clarifying questions about target
architecture, while Hops, Runs, archives and documentation upkeep were done by
Level 1 and the Runs' own agents. This is an observation about this series, not a
measure of productivity.

==== What changed for the human work

The maintainer's activity shifted from dispatching single agent steps toward
requirements, architecture decisions and acceptances: for example selecting the
DG-3 supervision variant, deciding DG-1, deciding whether to accept a
budget-stopped candidate or to run an independent successor, and specifying
the BP7 deployment constraints (state, OPS, scratch and Evidence target stay
separate; the existing Evidence repository stays authoritative). Manual
orchestration of the Runs themselves was largely taken over by Level 1.

==== Evidence and limits of this account

The record can be followed in `git log` (the Commission, candidate, correction
and review commits above), in the review artifacts under
`docs/warm_storage/concepts/wfc_beta1_*`, in the Epic and execution plan, and
in the sibling `workflow-coordinator-run-evidence` repository (archive commits
and `project_memory/run_ledger.adoc`). The 1,000th commit on the reachable
history is `5465890` (20 November 2026, BP6b H005); it is a milestone of the
repository, not a productivity figure. This account makes no claim about time
saved, cost, economics or statistical reliability from one pair of days, and the
Runs listed are not a sample.
