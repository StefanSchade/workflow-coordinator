=== Release preparation and hosted qualification (21--23 November 2026)

This chapter distinguishes *direct evidence* (Git, repository records and
reviews), *reconstruction* (a sequence assembled from those sources or the
maintainer's staged hosted-CI account), and *interpretation*. Run acceptance is
not publication, final release approval or product closure.

==== Seven hosted runs and the lint baseline (23 November)

The following is a *reconstruction* from `HOSTED_CI_FACTS.txt`, the maintainer's
staged account dated 23 November, checked against the workflow and each named
Git correction. The hosted run identities and logs are not repository artifacts,
so the numbered outcomes are not presented as independently reproduced locally.

. Run 1 exposed 17 repository-wide Ruff F-rule findings. L1
  (`RUN-d7572589ade84b74a067ef946efd7a90`, five Hops) removed them in `64945b0`
  without weakening the gate; its record correction and final review were
  accepted at `0266348`.
. Runs 2--4 exposed runner setup assumptions around Git identity and pytest
  temporary directories. The successive workflow corrections were `d2f90cd`,
  `1afd551` and `96d173f`.
. Run 5 reached trusted-commit tests and exposed Git-LFS filters inherited from
  `/etc/gitconfig`; `d3998ba` neutralized those runner filters for the test.
. Run 6 exposed the missing Bubblewrap executable; `aeb11ad` installed it in
  the test environment.
. Run 7 passed lint, the required tests, build, distribution and documentation
  checks. Release preflight alone refused because the 0.1.0b1 release-notes
  section remains `planned`. That is the designed pre-release barrier, not a
  product defect.

*Interpretation.* The sequence qualified increasingly deep layers of the hosted
environment: first static lint, then isolated Git identity/temp behavior,
trusted-commit configuration and finally the OS sandbox dependency. The staged
account supports "technically largely qualified"; it does not itself close the
maintainer-owned MD-5 decision or authorize release.

Together four Runs and 22 Hops, all `completed` with an accepting independent
final review. From the Commission commits to the Evidence archive commits,
DOC-A ran from 10:37 to 11:49, DOC-D from 11:01 to 11:24, DOC-B from 11:07 to
12:45 and DOC-C from 12:53 to 13:17. DOC-A, DOC-B and DOC-D were therefore
active together between about 11:07 and 11:24, and DOC-A and DOC-B overlapped
until 11:49. DOC-C was commissioned only after DOC-B was integrated, on the
consolidated state, because it links the results of A and B and edits the
shared indexes.

*Direct evidence.* The file scopes of A, B and D were largely disjoint
(quickstart and developer guide; a new manual chapter; the project history).
Run commits were integrated without rewriting: D by fast-forward when `main`
had not yet moved, then DOC-A (`d7ca0d8`), the separately made Q1 check
correction (`1dcdb94`) and DOC-B (`681cb7b`) as `--no-ff` merges because `main`
had advanced in the meantime, and DOC-C by fast-forward. The three historical
reports were copied byte-for-byte by the Operator into DOC-D's worktree before
the Run (commit `32b6d52`), so that no model had to transcribe them. The
Run logs show no collision in the shared Evidence repository; all four
archives are present.

*Direct evidence.* DOC-D ran its worker and its independent reviewer through
the Codex adapter (`gpt-5.6-sol` and `gpt-5.6-terra`) while Claude-adapter Runs
were active. Codex-adapter Runs are not new (the archive records `codex_cli`
Runs with `gpt-6.1-*` models on 18 November, for example BP1 and BP8); what is
new is a Codex Run executing alongside Claude Runs under one Level-1 operator.
It again shows a worker and a reviewer of different models inside one Codex
Run. It does not show that two adapters can be mixed inside one Run, which WFC
does not support (one adapter per Run), and it is not the Q1-B qualification.

*Reconstruction.* Before, the Level-1 operator chained WFC Runs mostly one
after another, each with its own lifecycle, review and archive (chapter 12 and
the earlier sections of this chapter); the Operator's working rule was one Run
at a time with read-only preparation beside it. This account does not claim
that no two Runs ever overlapped in time, only that none had been deliberately
steered as parallel work before. On 23 November one Level-1 session started three
independent Level-0 Runs in separate worktrees, monitored them together,
let each archive on its own, verified each result independently, integrated
them one by one and then started the Run that depended on them. The mix of
adapters occurred between Runs, not inside one.

*Interpretation, with limits.* The parallelism sits at the orchestration level
and in the worktree isolation that WFC already required (one authorized
lifecycle per checkout); the Hops of each Run stayed sequential, and no new
parallel mechanism entered the WFC core. The observation is that disjoint
scopes, separate worktrees and a human-or-agent integration order were enough
for this case. It is not evidence of general safety under concurrency: no
explicit cross-Run lock was found in the archive code beyond Git's own
locking, so a collision of two archives in the same second was possible and is
not excluded; it is not evidence of scalability,
and it supports no statement about throughput, cost or economic superiority,
for which no figures were collected (WFC reports no token usage in this Beta).

*Reconstruction.* One correction of the same morning is easy to miss: while
preparing Q1, the Operator found that the maintainer's first Q1 check
commands asserted that the not-yet-existing smoke file exists, which the
mandatory baseline probe of `wfc run` would have refused. The maintainer
accepted the finding; the checks were made baseline-compatible and a separate
post-run verification was added (commit `2486b70`, merged as `1dcdb94`). Q1 was
not run.

*Current position after the offensive.* DOC-A to DOC-D are accepted at Run level
and integrated locally. The release is still technically largely qualified but
*not published and not finally released*: no tag, no push by the Operator, the
release notes still say `planned`, MD-5 is open until the maintainer records
the hosted-run evidence, and Q1-A and Q1-B have not run.
