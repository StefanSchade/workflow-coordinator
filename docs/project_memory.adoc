== 1. Why WFC exists

WFC's provenance is the Core `spreadsheet-handling` FK/reference-helper Domain
Maintainer Contract (DMC) pilot (2026-08-21 through 2026-08-25, Cycle 0/Cycle
1, 60+ commits). That pilot did not show semantic decisions are mechanical; it
showed that getting one bounded decision through implementation and
independent review repeated a mechanical human dispatch loop -- agent works,
human verifies Git state, human packages evidence, human selects the next
role/context and pastes the next bounded prompt, repeat. The recurring burden
was coordination overhead, not a claim that automation should replace
maintainer semantic authority. See
`docs/spreadsheet_handling_adoption_note_2026-09-25.adoc` for the fuller
reconstructed chronology and
`docs/imported/core-incubator/agent_workflow_coordinator_concept_2026-08-25.adoc`
for the originating hypothesis paper.

That 2026-08-25 paper's key refinements, still load-bearing:

* not a deterministic coordinator with probabilistic work steps, but a
  *policy-bounded agentic coordinator running on deterministic execution
  mechanics* -- deterministic Git/evidence mechanics; policy-bounded supervisor
  judgment choosing only among admitted routes; semantic/strategic authority
  reserved to humans;
* Git is authority over agent self-report;
* bounded autonomous-Hop budgets (`max_autonomous_hops = N`, `N: 1 -> 2 -> 5 ->
  10 -> higher only for proven routine paths`) as a safety/observability
  checkpoint, not a review-iteration count;
* "Project Memory remembers what matters; the Coordinator records what
  happened" -- this file is deliberately not per-Hop state.

== 3. Current architecture / mental model

Verified against current `src/workflow_coordinator/` source, `governance/`,
and `docs/architecture.md`, which remains the authoritative architecture
record (not duplicated here):

[source,text]
----
Policy       determines Authority
Profile      determines Flow
WorkItem     determines bounded task/scope
Coordinator  executes the admitted flow deterministically
Agent        performs the bounded semantic work inside a Hop
----

Phase and route are distinct: a Hop's `authorized_scope`/`authorized_actions`
govern only the *current* phase; `requested_route` selects a transition, it
never performs or pre-authorizes the target phase's work. Runtime N operates
on a separate Development N+1 clone and never mutates itself
(`docs/self-development.adoc`); promotion and push remain maintainer-owned,
never automatic. The package-owned Agent Operating Contract is currently
version 6 (`src/workflow_coordinator/resources/agent_operating_contract_v6.txt`),
loaded through `importlib.resources` and not consumer-selectable. Workflow
role, persona, and execution binding are separated, with a closed role
vocabulary and bindings treated as Run-preparation input rather than authority
(`FTR-WFC-ROLE-PERSONA-EXECUTION-BINDING`, implemented `ec397b6`, minors closed
`9b98c99`).

*Autonomous-Hop ceiling (current, `dcb1da0` / accepted `9fc478b`,
2026-09-26/27).* `COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS` is 20
(`src/workflow_coordinator/model.py`), raised from a historical value of 5.
The independently enforced relationship is unchanged:

[source,text]
----
WorkItem.max_autonomous_hops <= RepositoryPolicy.max_autonomous_hops
                              <= Coordinator hard ceiling (20)
----

each link checked independently at RepositoryPolicy parsing, WorkItem
admission, operator preflight, and the serial-Hop driver. Raising the ceiling
did *not* widen any configured policy or WorkItem: this repository's own
self-development `governance/self-development/repository-policy.yaml` keeps
`max_autonomous_hops: 5`. The change only decouples the product ceiling from
the old coincidentally-equal value of 5 -- it does not mean ordinary WorkItems
receive 20 Hops.

*Product boundary (current, closed 2026-09-25/26: concept `4e2d6ae`, review
`bd6d38f`, correction `519f803`, delta re-review `ea6c4af`, findings closed
`4767309`).* WFC is *Level 0*: generic governed bounded execution -- given an
admissible request against one repository, execute it safely and produce a
trusted, auditable result. It is explicitly not a project planner and must not
understand DMC/Epic/Family/Cycle/Slice vocabulary. *Level 1*, the "Higher
Loop" that decides what bounded work should exist next (goal custody, work
discovery, replanning, cross-session persistence, closure judgement), is a
different problem class -- unpinned and discovery-driven where Level 0 is
pinned and fully knowable at admission -- and lives outside the WFC product.
"Bring your own orchestration; WFC supplies governed execution." The concept
also names WFC's current threat model precisely: it defends against *agentic
self-escalation* (an autonomous or model-driven path must have no alternate
route around Level 0 for governed effects), not against authorized humans or
administrators (explicitly out of scope, no technical-prevention claim). A
*supervised* caller's residual ambient capability is an accepted, named
deployment residual today, not a containment claim; no current
Coordinator-owned or Coordinator-verified OS/environment containment boundary
is claimed, and provider sandbox modes (e.g. Codex `--sandbox workspace-write`)
are provider-owned behavior, not Coordinator-trusted.

== 4. What WFC-on-WFC dogfooding actually exposed

The first WFC-on-WFC self-development WorkItem (`WI-WFC-DEVELOPER-ERGONOMICS-*`)
ran across seven numbered attempts (2026-09-22 through 2026-09-24, full record
under `docs/backlog/first_wfc_on_wfc_dogfood_attempt_*.adoc` and
`docs/backlog/wfc_reviews/`). Execution against a real repository exposed real
defects that static design and review had not eliminated. None required a
Runtime or Core change beyond the fixing commit itself; each was independently
reviewed before closure. These are RESOLVED HISTORICAL DEFECTS, not current
behavior:

* *Attempt 1* (`RUN-63312f78`) stopped fail-closed: the agent conflated its
  sole permitted exit route with its current authority, and misread its own
  shell's missing bare `python` as a trusted-evidence failure. Fixed by
  Agent Operating Contract V2 (`f196c90`): separates `authorized_actions` from
  `permitted_routes`; states agent-side checks are exploratory, not trusted
  evidence.
* *Attempt 2* (`RUN-b4477109`) completed H001 (`fd7ab86`), then the agent tried
  to resolve a historical review-document label (`M-5`) as if it were a
  run-local Finding ID; the reducer correctly rejected it
  (`unknown Finding ID`). Fixed by Contract V3 (`be6b3dc`: run-local Finding
  identity), itself re-reviewed and corrected once (`c6e3f24`, removing a
  duplicate-contract-file regression) before acceptance.
* *Profile durable-artifact instance coupling* (2026-09-22, not a numbered
  attempt): the self-development profile hard-coded one review-artifact
  filename, so a fresh continuation Run could not get a fresh artifact;
  `_preflight` failed closed correctly. Fixed by a dedicated namespace,
  `docs/backlog/wfc_reviews/` (`0ba506c`, accepted `2b08a59`): the namespace,
  not the per-WorkItem mapping, is the real write ceiling.
* *Attempt 3* (`RUN-5733283c`) found a real Finding (`make lint`/`make check`
  unusable), corrected it, but then tried to resolve that Finding from the
  `correct` phase, which holds no disposition authority -- **the
  Finding-authority prompt-projection defect**: the reducer always enforced
  disposition authority correctly; the contract simply never told the agent
  what authority it currently held. Fixed by Contract V4 (`e57796c`: an
  unconditional `finding_authority=<ops>` header), accepted `8ae4444`.
* *Attempt 4* (`RUN-71187374`) reproduced a real evidence gap (bare `python`
  absent by default) but escalated for scope it did not currently hold,
  conflating "the next phase will need this scope" with "this Hop needs it
  now" -- **BUG-WFC-CURRENT-HOP-FUTURE-PHASE-AUTHORITY**. Fixed by Contract V5
  (`d875026`: current-Hop authority is distinct from future route-target
  authority), accepted `7bc54cf`.
* *Attempt 5* (`RUN-8919d170`) reproduced the same bare-`python` Finding
  correctly this time (V5 fixed the prior escalation confusion), corrected it
  (`b069f98`, `PYTHON ?= python3`), then hit a permanent architecture test that
  had encoded a one-time pre-launch fact (a concrete state-root path does not
  yet exist) as a permanent invariant, so it broke once the Run legitimately
  created that path -- a test lifecycle defect, not Coordinator semantics.
  Fixed by `daf06db`, accepted `2304e9f`.
* *Attempt 6* (`WI-...-REVIEW-004`) exposed a second test-only defect: a
  permanent test compared literal executable-path spelling instead of
  canonical (realpath) interpreter identity, spuriously rejecting a legitimate
  `python` -> `python3` alias. Fixed by `a9edf0c` (compares
  `ExecutableResolution.canonical_path`), accepted `ea4c253`.
* *Preflight ambient-PATH defect* (discovered during Attempt-3 preparation,
  test-only): architecture tests invoking the real `_preflight()` accidentally
  depended on ambient shell `PATH` exposing bare `python`, unrelated to
  production semantics. Fixed by `981286f`.
* *Attempt 7* (`RUN-85da1df0`) completed in exactly one Hop
  (`rereview -> accept -> completed`), no Findings, clean worktree -- closing
  the developer-ergonomics dogfood workstream. A deferred profile optimization
  (letting a clean `review` route directly to `rereview`) was deliberately not
  implemented here; it remains recorded future work.

Architectural lesson that recurs across these: the Coordinator's deterministic
enforcement (reducer-side authority, fail-closed evidence, Finding-identity
checks) was correct in every case; every defect was in what the Agent
Operating Contract truthfully *projected* to the agent about its own current
authority. Successful dogfooding increases confidence in the paths it
exercised; it does not prove arbitrary autonomous execution safe or correct.

== 5. Real cross-repository evidence: the DMC-RELKEY-C0 family against Core

WFC's first real (non-self-development) consumer use is the `DMC-RELKEY-C0`
Relation-Key Identity family in the sibling `core` repository. Slice 1 was the
first real Core DMC consumer Run, `RUN-a9f9d68c` (WorkItem `DMC-RELKEY-C0-S1`,
2026-09-25): H001 implemented cleanly and Coordinator-trusted evidence passed;
H002's independent review found no semantic or scope defect but opened one
blocking Finding because the governing Core task required a commit-trailer
format `CommitIntent` could not express -- a capability gap, not a WFC defect,
recorded and deferred as `FTR-WFC-COMMIT-INTENT-BODY`. Slices 2 and 3a were
subsequently implemented and independently accepted (their acceptance reviews
are cited as governing components of later Slice-3b work).

=== 5.1 The 2026-09-27 Slice-3b run (`DMC-RELKEY-C0-S3B`)

This is the most important recent maturity milestone. An autonomous WFC
Runtime run executed WorkItem `DMC-RELKEY-C0-S3B` against Core baseline
`8c703ca462542f98c72dee5e963ccfdf80b681b5`, using Runtime commit
`dcb1da0403e0af430a883288f61e593162ee9e47`, hop budget 6, state root
`~/wfc-runs/dmc-relkey-c0-s3b-20260927-01`. Before crossing the provider
boundary, executable resolution and baseline trusted-evidence commands were
checked and the real Runtime `_preflight()` passed provider-free with the
state root absent. Per `operator-summary.json`: `run_status: completed`,
`hop_used: 4` of 6, `final_head` equal to `current_head`, `worktree_clean:
true`.

The Hop sequence (Hop is not the same unit as commit -- four Hops produced
three commits):

[cols="1,3,3",options="header"]
|===
|Hop |Outcome |Commit

|H001 (implement)
|`completed`
|`e905e3ce` -- `feat(DMC-RELKEY-C0-S3B): delegate reference graph identity`

|H002 (review)
|`changes_required`
|`64be8738` -- `docs(DMC-RELKEY-C0-S3B): record review` (the review artifact
itself)

|H003 (correct)
|`completed`
|`cad877c2` -- `fix(DMC-RELKEY-C0-S3B): preserve DateTime key precision`

|H004 (rereview)
|`completed`
|none -- final acceptance produced no new commit
|===

The review at H002 was not ceremonial. It found one real BLOCKING semantic
defect (`B1`): the new reference/graph relation-membership paths built keys
through row iteration that silently converted object-dtype
`numpy.datetime64[ps]` cells to nanosecond `pandas.Timestamp` before calling
the shared relation-key-identity owner, so two distinct picosecond DateTime
values could collide into the same identity -- violating the accepted
full-precision DateTime identity rule. H003 corrected this by obtaining
relation-identity components from a carrier-preserving row traversal before
calling the owner, and H004's independent rereview accepted the corrected
state.

*Evidentiary significance (verbatim characterization for this record).* This
run is empirical evidence, from one meaningful end-to-end execution, that the
Coordinator can: maintain durable Run/Hop state; transition deterministically
between configured phases and routes; preserve review Findings across Hops;
route a failed review into bounded correction and correction back into fresh
rereview; distinguish Hop state from Git commit count; execute trusted
evidence; and converge to a clean, accepted repository state in a real
consumer repository without a human acting as prompt dispatcher between Hops.
It does *not* establish general correctness, general safety, production
readiness, arbitrary-task autonomy, that every route or failure mode has been
exercised, or that human governance -- authorization, Runtime promotion, and
push all remain maintainer-owned -- is no longer required.
