== What WFC does today

This section is the present-capability baseline for everything below. Treat a
numbered section's claim as draft intent wherever it goes beyond this.

A maintainer authors a Commission Intent, has it deterministically rendered into
governing inputs, reviews and commits them, then prepares, inspects and
authorizes one Run that executes a fixed workflow program over an admitted,
bounded repository scope. Concretely, as implemented:

Three closed workflow programs:: `simple@v1`, `direct@v1` and `robust@v1`
(`governance/workflow-programs/*/v1.yaml`). `simple@v1` is one Worker
invocation with an in-invocation self-check and no independent reviewer.
`direct@v1` is a Worker followed by a deterministic verification phase (which
disposes `task-check` only, with no semantic review authority) and a correction
loop. `robust@v1` adds an independent adversarial reviewer with a broad review,
a correction/focused-review loop, and a structurally guaranteed renewed broad
review as the only path to completion. `commissioning.py` recognizes exactly
these three programs and rejects any other, comparing each pinned record
against an in-source literal template.

Deterministic Commission rendering:: The Front Door (`commissioning.py`)
substitutes only declared slots -- scope, durable-artifact paths, the selected
evidence profile -- so ordinary Commission authoring cannot rewrite phases,
routes, review descriptors or guarantees. This is the implemented answer to the
authoring-friction and silent-process-drift problem described in Section 5.

Enforced authority composition:: The repository Policy is an independent
ceiling; admission (`operator.py:_preflight`, `_admit_a1`) composes Policy,
WorkItem and Profile and fails closed on any violation, including any attempt
to place a mutation scope inside governance paths. Governing inputs are read
from a pinned commit and digested.

Projected result contracts (P1--P3):: Each invocation receives a closed,
phase-projected result schema, so a Worker literally has no field able to hold
a review verdict, a route outside the phase's permitted set is unrepresentable,
and a new Finding's `finding_id` is typed `null` so an invented identity cannot
be authored as new (one asserted as existing fails closed at reduction). See the
link:../technical_model/workflow_program_architecture.adoc#implemented-p1-p3[Technical
Model] for the mechanism and the explicit P3.5/P4/P5 boundary.

Independent review with Finding lifecycle:: Findings have Coordinator-allocated
identity and a gated lifecycle; a Run cannot complete while any Finding is open
and blocking. Disposition authority is per-phase and separate from the ability
to do work -- `robust@v1`'s reviews may `resolve`, `direct@v1`'s gate may
disposition nothing.

Coordinator-owned effects:: Exactly one trusted Git write surface
(`git_facts.py:trusted_commit`), validating subject form and WorkItem/Hop
identity tokens and requiring the changed-worktree set to equal the proposed
paths exactly within authorized scope. Evidence commands are Coordinator-run
(`task-check` is `python -m pytest -q` under the standard policy basis) and
re-validated against what was prepared; an agent's own checks are never trusted
evidence. A program's declared evidence profiles fix what a Run owes:
`robust@v1` and `simple@v1` always require `task-check`, while `direct@v1` also
permits a `none` profile.

Two provider adapters:: The implemented `codex_cli` and `claude_cli` adapters
behind one provider-neutral port, bound per workflow role, with one adapter per
Run.

Self-development topology:: An accepted Runtime WFC N operates on a Development
WFC N+1 checkout and never mutates itself. The maintainer alone owns any push
and any later Runtime promotion.

What is *not* implemented today, despite appearing as intent below: a program
catalogue, packaging or admission mechanism; typed program parameterization;
consumer-supplied programs; elevated-privilege workflows with compulsory
defensive review (UC-04); protected-context or local-inference phases (UC-05);
any Level-1 orchestration layer; and any Coordinator-owned execution-isolation
boundary. Current acceptance and qualification standing for the implemented
pieces lives in link:../backlog/_open.adoc[the active-work manifest], not here.

== 1. Product vision and origin

WFC originated directly out of developing the `spreadsheet-handling` library.
That project already practiced high-quality software development with LLM
agents, independent reviews, and many iterative steps -- but the maintainer
had to manually commission each agent, collect results, organize reviews, and
trigger correction loops by hand.

*The original product idea was to progressively automate that manual
dispatch work without losing the development quality already achieved.*

The approach is deliberately bottom-up:

* Start by automating a single agent hop.
* Then automate recurring workflow sequences.
* Current focus: a controlled, deterministic review-and-correction cycle for
  one development activity (see Section 4).
* Long-term vision: orchestrate progressively larger development work with
  growing autonomy.

Overarching project planning or fully autonomous product development is
*not* the current implementation focus (see Section 3's non-goals and
Section 9's deliberately unresolved Level-1 question).

=== 1.1 Development practices WFC exists to preserve

Alongside automation itself, WFC was from the outset about carrying forward
the practices that plausibly contributed most to `spreadsheet-handling`'s
quality:

Context management:: A project's memory lives in the repository, not in a
volatile chat -- decisions and reasoning are documented, the resulting corpus
is made discoverable/indexed, and "cold" information is deliberately
forgotten by archiving it to cold storage. The original purpose was improving
LLM working conditions and context quality, not auditability for its own
sake (that follows separately, below).

Small, clearly bounded steps:: Development proceeds in bounded hops with
defined tasks and checkable results.

Structured commissioning:: Precise tasks, change scope, relevant documents,
roles/personas, and explicit result/review expectations. Parts of this
practice are recognizable today in the Workflow Coordinator's prompt
construction and in the history of `vertical.py`.

Independent review and iterative correction:: Quality assurance is part of
the automated development process itself, not merely a final check appended
at the end.

Traceability and auditability:: This need also grew out of practical
experience with `spreadsheet-handling`: the maintainer needs an overview of
which work was commissioned, executed, reviewed, accepted, or deferred.

These practices are a deliberate methodological starting point for WFC, not a
claim that they are proven causes of `spreadsheet-handling`'s quality.

=== 1.2 Extension toward security capability

Context management and tight authorization of change scope led to the
insight that the same mechanisms could, in principle, also serve more
demanding security requirements. Examples under consideration:

* Hiding confidential content from model calls that are not correspondingly
  authorized, potentially via controlled filesystem views.
* Protecting critical areas -- for example Git hooks or security-relevant
  infrastructure files -- from ordinary write operations.
* Allowing a targeted authorization extension for such changes that then
  triggers a mandatory defensive security review
  (`FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW`).
* Documenting the information and action scope actually granted, so it
  remains traceable.

The bubblewrap-based execution-boundary work grew out of this line of
thinking and has been explored experimentally.

*Important:* This document distinguishes existing technical building blocks,
already-integrated functionality, and future product capability strictly by
what the repository currently shows -- see link:../architecture.md[architecture]
for the normative statement. In particular, the existence of a bubblewrap
primitive must not be read as claiming complete isolation of all provider calls.
`execution_boundary.py` exists and its own docstring says it is not an authority
resolver and not a replacement for post-Hop scope checks; it is not wired into
provider dispatch. Architecture states plainly that "WFC V1 provides neither
hostile-code containment nor host isolation" and that no current
Coordinator-owned or Coordinator-verified OS/environment containment boundary is
claimed for any consumer repository. The authoritative enforcement of a phase's
authorized scope is the Coordinator's own post-Hop Git observation.

== 2. Formal goal catalog

A small number of stably referenceable product goals, intended to be cited
by ID (`GOAL-WFC-NNN`) from other documents and records rather than
restated. These are product goals, not use cases -- Section 6's use cases
remain the place that concretizes them; this catalog does not duplicate or
replace that catalog.

GOAL-WFC-001 -- Automate high-quality development work (primary goal)::
Progressively reduce the maintainer's manual dispatch, review-organizing, and
correction-triggering burden for LLM-agent development work, without
reducing the development quality already achieved without automation. This
is the primary goal; all other goals below serve it and are not independent
maximization targets.

GOAL-WFC-002 -- Preserve the proven development practices:: Carry forward
context management, bounded hops, structured commissioning, independent
review with iterative correction, and traceability/auditability as the
methodological basis for automated development (Section 1.1), adapting their
mechanics as needed rather than discarding them for automation's sake.

GOAL-WFC-003 -- Provide scoped security capability in service of the primary
goal:: Where development work requires it, protect confidential content and
critical surfaces through authorized elevation and mandatory defensive
review (Section 1.2), without this becoming an independent, open-ended
security-hardening program (see Section 3's non-goals).

GOAL-WFC-004 -- Preserve agent capability and productivity:: Keep ordinary
agent capability -- including public internet access for research,
documentation, dependency management, and experimentation -- as unrestricted
as reasonably possible; justify every additional restriction against its
cost to development quality and productivity rather than applying it by
default (Section 3).

== 3. Design principles and non-goals

=== 3.1 Design principles

* Ordinary agent capabilities should remain as unrestricted as possible.
* Restrictions must be weighed against their effect on development quality
  and productivity, not applied as a default stance.
* Public internet access for research, documentation, dependency management,
  and experimentation is an important agent capability. The current restriction
  to an empty allowed-domain list and denied `WebFetch`/`WebSearch` tools is
  implemented now in `src/workflow_coordinator/claude_adapter.py` (the
  generated settings file's `sandbox.network.allowedDomains: []` and
  `permissions.deny`); the
  link:../cold_storage/sources/pre-0.1.0b1/claude_code_adapter_architecture.adoc[adapter snapshot]
  is dated provenance for how it got there, not the current source of truth.
  This restriction is a functional gap to investigate for Beta 1, not a
  deliberate target state;
  link:../backlog/FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY.adoc[the public-internet
  capability record] owns it, and the ordinary-access decision is settled while
  settings, profiles and enforcement are not.
* Additional security restrictions should generally be justified by the
  deployment context and the operator's own decisions. A later
  Commission-driven configuration of such restrictions is conceivable but not
  committed.
* The integrity of WFC's own orchestration, authorization, state management,
  and trusted operations remains non-negotiable regardless of the above.

=== 3.2 Explicit non-goals

WFC does *not* aim to build, without concrete need, a fully self-contained,
watertight isolation layer that assumes zero trust in Codex's, Claude Code's,
or their runtime's own security mechanisms. In particular, full additional
provider isolation and a WFC-owned credential broker are *not* current
general product requirements; such requirements can be reconsidered later if
a concrete security need arises. Existing sandbox research findings are
preserved regardless (`docs/architecture.md`'s
`FTR-WFC-EXECUTION-TRUST-BOUNDARIES` pointer).

This is a product-level, long-term non-goal about security scope. It is
distinct from Section 10's near-term implementation non-goals for the
current increment (no universal workflow DSL, no expanded orchestrator
kernel, etc.) and from Section 9's deliberately unresolved question about a
possible Level-1 orchestration layer -- neither of those is decided by this
section, and this section does not decide them either.

== 4. Current development focus

The present, concrete development focus is UC-01/UC-02/UC-03 below: a
controlled, deterministic review-and-correction cycle for one development
activity -- independent review, focused re-review of known Findings, fresh
broad review, and recognizing/escaping non-converging correction loops. This
is the bottom-up step currently being built and dogfooded.

Its implemented core is `robust@v1`: implement, broad review, correct, focused
review, renewed broad review, with completion reachable only from
`broad_review.accept`. `robust@v1` has independent acceptance;
`direct@v1`'s implementation acceptance reconciliation is still outstanding;
the convergence-escape Slices 1--4 are implemented and independently accepted
while Slice-5/6 evidence has not run. Consult
link:../backlog/_open.adoc[the active-work manifest] for the exact current
standing rather than reading a status into this section.

This is explicitly *not* the same as the long-term vision in Section 1 of
orchestrating progressively larger development work with growing autonomy.
Capabilities described elsewhere in this document as candidate, planned, or
architectural (for example Section 8's governance/program-variant material,
UC-04's elevated-privilege workflow, or UC-05's protected-context workflow)
are future direction, not claims about the current increment's scope.

== 5. User-facing purpose

A maintainer commissions a bounded task, chooses a suitable reusable workflow program, authorizes the task and its limits, and starts a Run. The workflow program specifies the process; the Commission must not accidentally redefine it through copied YAML. The interpreter carries out the declared process and enforces its contracts. Independent assessment, repair, evidence, human stops, and auditability remain first-class features.

The near-term product problem is Commission authoring friction and unexpected differences in workflow programs; it is not a demand for a generalized workflow platform or a redesign of the already working reducer.

Workflow flexibility is an intended capability, not an accident to eliminate. The product goal is to preserve the ability to define specialized processes *without* letting ordinary Commission authoring silently rewrite process guarantees, generate incompatible one-offs, or make every Run expensive to reason about.

== 6. Candidate workflow programs and test scenarios

The examples are *scenarios to preserve and analyze*, not a claim that each is
already a supported, distinct reusable YAML program. Each scenario carries its
own current-evidence note; three of the six have an implemented program and
three do not.

=== UC-01 -- Standard review loop

Approximate logical flow (loops omitted):

[source,text]
----
Implement -> Independent Review -> Correct -> Focused Rereview -> Complete
----

Requirements:

* The reviewer can raise blocking issues.
* An authorized later phase can disposition outstanding Findings.
* A clean outcome can complete without performing a needless correction.
* A failed review can return for correction and rereview, possibly repeatedly.
* A Run cannot complete with an open blocking Finding.

Known current evidence:: Implemented as `robust@v1`, whose closed record is
reused by every Commission that selects it; the per-Commission profile file is
now a deterministic rendering of that one program rather than a hand-copied
process. `robust@v1` has independent acceptance and a completed dogfood.
`direct@v1` implements the narrower verification-plus-correction variant and
its acceptance reconciliation remains outstanding. The requirement that "an
authorized later phase can disposition outstanding Findings" is satisfied by
`robust@v1`'s reviews (`finding_authority: [resolve]`) but *not* by
`direct@v1`'s gate, which declares none -- the known defect owned by
link:../backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc[the gate
Finding-authority BUG]. The completion guard against open blocking Findings is
implemented.

=== UC-02 -- Staged adversarial review with economical correction loop

[source,text]
----
Implement (economical model)
  -> Broad adversarial review (frontier model)
  -> Correct / focused rereview loop (economical model[s])
  -> Fresh broad adversarial review (frontier model)
  -> Complete, or return to correction / further review
----

The inexpensive focused rereview checks disposition of the *known* Finding set. The later broad review is a *new* attempt to discover missed issues and may therefore open new Findings. A final broad review must not be characterized as a phase from which no new issues can emerge.

Model choices (e.g., Terra High/Medium and Sol High) are illustrative commercial bindings, not the definition of the workflow program. Model selection, role separation, independence and cost accounting are separate concerns.

Known current evidence:: `robust@v1` implements the *topology* of this scenario,
including the renewed fresh broad review as the sole completion path. The
*economical* part is not yet expressible: execution bindings
(`RunExecutionConfiguration`) select adapter, model and reasoning effort per
*workflow role*, and `robust@v1`'s broad and focused reviews are both the
`independent_reviewer` role, so they cannot be bound to different models.
`operator.py:_preflight` additionally requires one adapter across all roles.
Per-phase or per-review-breadth binding is the concrete granularity gap; no
design is selected.

Open historical question:: Did a similar final review appear or disappear in historical Commissions due to copied/modified profiles rather than a deliberate product version change? Verify against profile history and the Run Ledger. This question concerns the legacy hand-authored profiles under `governance/self-development/`; the three closed programs are no longer subject to that drift.

=== UC-03 -- Convergence-failure escape

[source,text]
----
Correction <-> Rereview (repeated without progress)
  -> Diagnose recurring failure / root cause
  -> Revise strategy
  -> Authorized strategy review / resume
----

A new attack example need not imply an entirely new conceptual Finding. It may show that a narrow fix repaired one manifestation without addressing the common underlying invariant. The workflow must be able to recognize stagnation and change abstraction level instead of merely iterating the same response.

Existing evidence:: link:../backlog/FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE.adoc[the convergence-escape FTR] and accepted implementation Slices 1--4 establish substantial runtime work: `model.py` carries the closed `ConvergenceRole`, `ConvergenceProtocol`, diagnosis/strategy vocabularies and typed convergence records, `reducer.py` derives convergence facts from trusted qualification evidence and substitutes a reserved escape route at the goalpost, and profile `schema_version: 3` requires a convergence configuration. No *catalogue* program uses it: all three closed programs render profile `schema_version: 2` with no convergence role, so this path is exercised by fixtures and tests rather than by a reusable dogfooded program. Slice-5 R1A-history dogfood and Slice-6 foreign-domain falsification have not run. Check phase/route/result semantics against code and fixtures before claiming end-to-end product availability.

=== UC-04 -- Elevated-privilege work and compulsory defensive review

[source,text]
----
Ordinary work -> Explicitly authorized elevation -> Privileged work
  -> Mandatory defensive security review -> Ordinary continuation / completion
----

Sensitive surfaces include CI/CD scripts, Git hooks, tooling executed at another trust level and selected critical tests. Ordinary agents may be prevented from modifying them through OS-level controls; an elevated step requires authorization outside the mere choice of a phase. Once an elevated change occurs, no successful completion path may bypass the defensive review. This is a legitimate all-successful-path assurance condition, unlike a demand that every Finding-bearing route pass a later fixer.

Source:: link:../backlog/FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW.adoc[the elevated-privilege record]; not a deployed capability. Nothing in the current programs, phase model or admission expresses privilege elevation, and no implemented mechanism makes a later phase compulsory on every successful path.

=== UC-05 -- Protected context / local inference

A data-sensitive assignment may require a phase whose model executes only within an approved environment, possibly self-hosted inference. Protected sources must not be leaked to providers or artifacts outside their trust boundary. Trust is enforced by execution and information-access controls, not simply by declaring `trusted_model` in YAML. Working-tree Git access and derived content/export paths require explicit analysis; hiding directories by mounts alone is insufficient.

Status:: Candidate architectural use case. No claim that such a product workflow or full containment exists today. Today's phase model has no protected-context or information-flow concept at all, and per-role execution bindings carry no trust attribute; `execution_boundary.py`'s mount primitives are unintegrated. link:../research/README.adoc[The research register] owns the open R1/R3 questions.

=== UC-06 -- Simple task

[source,text]
----
Work -> Complete
----

A bounded single-agent task with no mandatory independent review, for cases in which WFC becomes the ordinary controlled gateway to LLM execution. This is a different workflow guarantee, not an invitation for a Commission to disable a required review in UC-01 or UC-04.

Known current evidence:: Implemented as `simple@v1`, which has independent
acceptance, Runtime promotion and a clean first dogfood. It is a genuinely
separate program, not a weakened `robust@v1`: `model.py:is_closed_terminal_worker_shape`
recognizes its exact shape -- one phase, no review, the `simple-self-check`
modifier, `task-check` evidence, a single `accept` route with `effect: complete`
and no `goto` -- so a second Hop is structurally unreachable from the program
alone. That recognition is also the only reason its phase is exempt from the
rule that a phase with required evidence must be a gate review.

== 7. Cross-cutting functional requirements

These are requirements, stated as requirements. Several are already satisfied by
current behavior and two are not; the parenthetical notes say which, so the list
is not read as a delivery claim.

* A Commission specifies its task, scope, authorization and the reusable program to execute.
* Programs define mandatory phase relationships and safety/quality obligations; different Commissions can reuse the same reviewed program.
* Program choice and runtime execution remain pinned and reproducible for an existing Run.
* No silent elevation of action or information-access authority via a YAML setting.
* Incorrect or inconsistent agent results are rejected/stopped rather than repaired into a new semantic answer by the reducer. (Satisfied; the narrow *mechanical* substitutions that do exist -- the declared `failed_evidence_route` on required-evidence failure, and the reserved convergence escape route at a derived goalpost -- are enumerated in link:../semantic_model/workflow_execution_semantics.adoc#phase-versus-route[the Semantic Model].)
* Strongly prefer a pre-dispatch bounded result contract when it can make invalid outputs unrepresentable; retain trusted post-result checks for state-dependent conditions. (Satisfied by P1--P3 plus the reducer's stateful checks.)
* Preserve independent review and the distinction between focused disposition of known Findings and a new broad search for new Findings. (Satisfied structurally by `robust@v1`: both reviews are `context: fresh` and only `broad_review.accept` can complete.)
* A Run with open blocking Findings must not advance irreversibly into a no-repair branch. A clean-only branch must be guarded by proven cleanliness. (*Partly unmet.* Completion is guarded; entry into a no-repair branch by `goto` is not. This is the P3.5 question -- see link:../semantic_model/workflow_execution_semantics.adoc#p35-problem[the Semantic Model] and link:../backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc[the gate Finding-authority BUG].)
* Keep user-visible diagnostic and recovery cost reasonable; no unsafe automatic retry of an uncertain provider execution. (No automatic retry exists. Several diagnostic-quality defects remain open in link:../backlog/_open.adoc[the active-work manifest].)
* WFC provides and propagates its documented execution environment while
  consumers configure their own tools. Arbitrary tools can ignore temporary
  variables, hard-code paths or change subprocess environments, so placement
  for all toolchains cannot be promised. This does not exempt WFC from its
  documented execution or sandbox responsibilities; self-development makes
  the WFC repository a consumer of its Runtime. This discussion record is
  not itself an accepted Runtime contract.

== 8. Governance, program variants and future deployment scenarios

Functional requirements to investigate, not yet a product feature or syntax:

* *Known standard program:* A Commission can select a reviewed, immutable program revision, supplying only declared task-specific bindings; it cannot remove required reviews or guards.
* *Bounded variation:* A program may expose narrowly typed and reviewed configuration parameters, such as accepted model/cost/budget classes. The allowed parameter space must preserve the program's claimed guarantees. A parameter that changes phase topology may instead require a distinct program revision or variant.
* *Special-purpose program:* A maintainer or authorized higher-level caller can propose a new declarative workflow as a separate artifact. Creating/proposing it must never constitute admission, authorization or permission to execute it.
* *Deployment policy:* A future installation may expose only an approved catalogue (for example, a regulated-development pack) or permit independently approved consumer programs. Package installation/availability and permission for a particular Commission/Run remain separate decisions.
* *Guarantee preservation:* Governance-required process guarantees are mandatory floors. A Commission's configuration cannot weaken them; an explicitly exceptional program would require a separately authorized exception path, not a boolean override.
* *Auditability:* Pin the exact program revision, effective bindings and applicable governance rules for each Run, including experimental/one-off programs.

The words "standard", "parameterized" and "custom" describe prospective authoring/admission classes. **They are not currently implemented WFC operating modes.** A future workflow pack should initially be treated as a declarative package/manifest, *not* a permission to load third-party Python into the trusted interpreter.

Current standing of these six items:: *Known standard program* and *guarantee
preservation* are substantively satisfied for the three closed programs: a
Commission selects a pinned `(program_id, revision)` whose record must equal an
in-source literal template, and an Intent has no write path to phases, routes or
review descriptors. *Auditability* is partly satisfied: the WorkItem records
`program_id`, `program_revision` and `program_source_commit` as profile labels,
the Run pins profile and policy identity/revision, and the render manifest
digests every source -- but effective per-Run binding audit and
experimental-program pinning are not generalized. *Bounded variation*,
*special-purpose program* and *deployment policy* are entirely uninvestigated:
there is no parameter type system, no admission decision procedure for a
consumer-supplied program, and no catalogue or packaging mechanism. The
evidence-profile selection is the only variation point that exists, and it is a
closed enumeration inside each program record.

== 9. Level 1 deliberately unresolved

The maintainer considered recursive, self-similar WFC reducer loops: a review loop inside a backlog-selection loop inside higher-level project preparation. Later work suggested the outer orchestration may be categorically different and could use, for example, LangGraph. Both remain hypotheses. No commitment is made to recursive WFC, LangGraph, program-authoring by Level 1, or a specific integration API. The only current boundary requirement is that any future caller must not silently weaken Level-0 workflow guarantees or confer execution authority by creating a Commission.

== 10. Product non-goals for this step

No immediate universal workflow DSL, profile migration, expanded orchestrator kernel, speculative Level-1 planner, or rollout of all six example programs. First verify the profile corpus, implement one reusable real-life program, and measure reduced Commission authoring burden.

These non-goals still hold. The middle step has since happened: three reusable
programs exist and are used by current Commissions, and no legacy profile
migration was required for that. The *measurement* of reduced authoring burden
has not been done, and no DSL, kernel expansion or Level-1 planner was built.
