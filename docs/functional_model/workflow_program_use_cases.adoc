=== Platform portability and consumer stack neutrality -- draft continuation

Standing:: *WORKING DRAFT / DISCUSSION RECORD*: the following is functional
product intent, not implementation, qualification, an accepted technical
contract or a guarantee of product capability. It continues
<<_3_1_design_principles,Section 3.1's design principles>>,
<<_uc_01standard_review_loop,UC-01>> and <<_uc_06simple_task,UC-06>>,
and <<_7_cross_cutting_functional_requirements,Section 7's cross-cutting
requirements>>. It does not replace Section 7's execution-environment wording
or change existing responsibility, authorization or sandbox boundaries. The
Technical Model retains ownership of implemented mechanisms.

* WFC should be portable across expressly supported host platforms, including
  Linux x86-64 and ARM64. Product qualification should explicitly identify
  supported operating systems, Python versions, CPU architectures and
  provider/adapter combinations; ARM64 does not mean every ARM system is
  supported.
* A consumer project should not be required to use Python, pip, venv, a
  particular CPU architecture, build system or package manager. WFC's own
  runtime prerequisites are separate from requirements on the consumer project.
* On a supported host, WFC should orchestrate authorized tools supplied by the
  host or consumer, including architecture-specific compilers, libraries, test
  tools and hardware interfaces. WFC should not generally install those tools,
  manage their dependencies or make them compatible with the platform. This
  intent preserves Section 7's documented execution and sandbox responsibilities
  and its limitations on arbitrary toolchains.

Scenario:: On an ARM64 Linux mini-workstation, the host supplies WFC, its
execution environment, and ARM-native build/test or hardware tools; the user
authorizes the commands. Ordinary workflows, review where selected, and the
applicable authority and evidence mechanisms should be usable without requiring
the consumer project to use x86 or Python. Availability of the agent CLI and
provider adapter and actual ARM qualification are independent prerequisites,
not assumed facts. This scenario does not require automatic distribution of
Commissions across hosts.

Qualification discussion:: Primary WFC self-development may continue on Linux
x86-64 with Python 3.13. ARM64 qualification may use a different supported
Python, for example Python 3.11 on Debian 12; this is an example subject to
qualification, not a compatibility claim. The current declared Python
`>=3.10` remains unchanged; the final product matrix and exact minimum version
are separate product decisions.

The link:{model-docs}/backlog/beta1_productization.adoc[Beta-1 plan] retains
its user-provided environment direction; this continuation does not claim its
BP product functions are delivered. See also the
link:{model-docs}/warm_storage/concepts/wfc_beta1_product_boundary_review_second_pass.adoc[Beta-1 boundary review]
for the proposed user-provided, probed environment.
