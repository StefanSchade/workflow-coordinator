== What WFC does today

This section is the present-capability baseline for everything below. Treat a
numbered section's claim as draft intent wherever it goes beyond this.

A maintainer authors a Commission Intent, has it deterministically rendered into
governing inputs, reviews and commits them, then prepares, inspects and
authorizes one Run that executes a fixed workflow program over an admitted,
bounded repository scope. Concretely, as implemented:

Three closed workflow programs:: `simple@v1`, `direct@v1` and `robust@v1`
(`governance/workflow-programs/*/v1.yaml`). `simple@v1` is one Worker
invocation with an in-invocation self-check and no independent reviewer.
`direct@v1` is a Worker followed by a deterministic verification phase (which
disposes `task-check` only, with no semantic review authority) and a correction
loop. `robust@v1` adds an independent adversarial reviewer with a broad review,
a correction/focused-review loop, and a structurally guaranteed renewed broad
review as the only path to completion. `commissioning.py` recognizes exactly
these three programs and rejects any other, comparing each pinned record
against an in-source literal template.

Deterministic Commission rendering:: The Front Door (`commissioning.py`)
substitutes only declared slots -- scope, durable-artifact paths, the selected
evidence profile -- so ordinary Commission authoring cannot rewrite phases,
routes, review descriptors or guarantees. This is the implemented answer to the
authoring-friction and silent-process-drift problem described in Section 5.

Enforced authority composition:: The repository Policy is an independent
ceiling; admission (`operator.py:_preflight`, `_admit_a1`) composes Policy,
WorkItem and Profile and fails closed on any violation, including any attempt
to place a mutation scope inside governance paths. Governing inputs are read
from a pinned commit and digested.

Projected result contracts (P1--P3):: Each invocation receives a closed,
phase-projected result schema, so a Worker literally has no field able to hold
a review verdict, a route outside the phase's permitted set is unrepresentable,
and a new Finding's `finding_id` is typed `null` so an invented identity cannot
be authored as new (one asserted as existing fails closed at reduction). See the
link:{model-docs}/technical_model/workflow_program_architecture.adoc#implemented-p1-p3[Technical
Model] for the mechanism and the explicit P3.5/P4/P5 boundary.

Independent review with Finding lifecycle:: Findings have Coordinator-allocated
identity and a gated lifecycle; a Run cannot complete while any Finding is open
and blocking. Disposition authority is per-phase and separate from the ability
to do work -- `robust@v1`'s reviews may `resolve`, `direct@v1`'s gate may
disposition nothing.

Coordinator-owned effects:: Exactly one trusted Git write surface
(`git_facts.py:trusted_commit`), validating subject form and WorkItem/Hop
identity tokens and requiring the changed-worktree set to equal the proposed
paths exactly within authorized scope. Evidence commands are Coordinator-run
(`task-check` is `python -m pytest -q` under the standard policy basis) and
re-validated against what was prepared; an agent's own checks are never trusted
evidence. A program's declared evidence profiles fix what a Run owes:
`robust@v1` and `simple@v1` always require `task-check`, while `direct@v1` also
permits a `none` profile.

Two provider adapters:: The implemented `codex_cli` and `claude_cli` adapters
behind one provider-neutral port, bound per workflow role, with one adapter per
Run.

Self-development topology:: An accepted Runtime WFC N operates on a Development
WFC N+1 checkout and never mutates itself. The maintainer alone owns any push
and any later Runtime promotion.

What is *not* implemented today, despite appearing as intent below: a program
catalogue, packaging or admission mechanism; typed program parameterization;
consumer-supplied programs; elevated-privilege workflows with compulsory
defensive review (UC-04); protected-context or local-inference phases (UC-05);
any Level-1 orchestration layer; and any Coordinator-owned execution-isolation
boundary. Current acceptance and qualification standing for the implemented
pieces lives in link:{model-docs}/backlog/_open.adoc[the active-work manifest], not here.
