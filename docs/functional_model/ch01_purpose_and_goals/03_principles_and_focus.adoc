== 3. Design principles and non-goals

=== 3.1 Design principles

* Ordinary agent capabilities should remain as unrestricted as possible.
* Restrictions must be weighed against their effect on development quality
  and productivity, not applied as a default stance.
* Public internet access for research, documentation, dependency management,
  and experimentation is an important agent capability. The current restriction
  to an empty allowed-domain list and denied `WebFetch`/`WebSearch` tools is
  implemented now in `src/workflow_coordinator/claude_adapter.py` (the
  generated settings file's `sandbox.network.allowedDomains: []` and
  `permissions.deny`); the
  link:{model-docs}/cold_storage/sources/pre-0.1.0b1/claude_code_adapter_architecture.adoc[adapter snapshot]
  is dated provenance for how it got there, not the current source of truth.
  This restriction is a functional gap to investigate for Beta 1, not a
  deliberate target state;
  link:{model-docs}/backlog/FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY.adoc[the public-internet
  capability record] owns it, and the ordinary-access decision is settled while
  settings, profiles and enforcement are not.
* Additional security restrictions should generally be justified by the
  deployment context and the operator's own decisions. A later
  Commission-driven configuration of such restrictions is conceivable but not
  committed.
* The integrity of WFC's own orchestration, authorization, state management,
  and trusted operations remains non-negotiable regardless of the above.

=== 3.2 Explicit non-goals

WFC does *not* aim to build, without concrete need, a fully self-contained,
watertight isolation layer that assumes zero trust in Codex's, Claude Code's,
or their runtime's own security mechanisms. In particular, full additional
provider isolation and a WFC-owned credential broker are *not* current
general product requirements; such requirements can be reconsidered later if
a concrete security need arises. Existing sandbox research findings are
preserved regardless (`docs/architecture.md`'s
`FTR-WFC-EXECUTION-TRUST-BOUNDARIES` pointer).

This is a product-level, long-term non-goal about security scope. It is
distinct from Section 10's near-term implementation non-goals for the
current increment (no universal workflow DSL, no expanded orchestrator
kernel, etc.) and from Section 9's deliberately unresolved question about a
possible Level-1 orchestration layer -- neither of those is decided by this
section, and this section does not decide them either.

== 4. Current development focus

The present, concrete development focus is UC-01/UC-02/UC-03 below: a
controlled, deterministic review-and-correction cycle for one development
activity -- independent review, focused re-review of known Findings, fresh
broad review, and recognizing/escaping non-converging correction loops. This
is the bottom-up step currently being built and dogfooded.

Its implemented core is `robust@v1`: implement, broad review, correct, focused
review, renewed broad review, with completion reachable only from
`broad_review.accept`. `robust@v1` has independent acceptance;
`direct@v1`'s implementation acceptance reconciliation is still outstanding;
the convergence-escape Slices 1--4 are implemented and independently accepted
while Slice-5/6 evidence has not run. Consult
link:{model-docs}/backlog/_open.adoc[the active-work manifest] for the exact current
standing rather than reading a status into this section.

This is explicitly *not* the same as the long-term vision in Section 1 of
orchestrating progressively larger development work with growing autonomy.
Capabilities described elsewhere in this document as candidate, planned, or
architectural (for example Section 8's governance/program-variant material,
UC-04's elevated-privilege workflow, or UC-05's protected-context workflow)
are future direction, not claims about the current increment's scope.

== 5. User-facing purpose

A maintainer commissions a bounded task, chooses a suitable reusable workflow program, authorizes the task and its limits, and starts a Run. The workflow program specifies the process; the Commission must not accidentally redefine it through copied YAML. The interpreter carries out the declared process and enforces its contracts. Independent assessment, repair, evidence, human stops, and auditability remain first-class features.

The near-term product problem is Commission authoring friction and unexpected differences in workflow programs; it is not a demand for a generalized workflow platform or a redesign of the already working reducer.

Workflow flexibility is an intended capability, not an accident to eliminate. The product goal is to preserve the ability to define specialized processes *without* letting ordinary Commission authoring silently rewrite process guarantees, generate incompatible one-offs, or make every Run expensive to reason about.
