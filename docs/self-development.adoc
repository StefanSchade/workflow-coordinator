= WFC self-development

This guide records the operational Runtime-N / Development-N+1 contract. It is
not a general CLI manual and does not authorize a Run.

== Topology and preparation

Accepted Runtime WFC N operates on the separate Development WFC N+1 clone and
never mutates itself. The clones have separate Git directories and object
stores. Export the exact accepted runtime commit into temporary storage outside
both clones, then install that export non-editably into an external runtime
virtual environment. Create a second external development/evidence virtual
environment with ordinary `python3 -m venv` and install the current development
repository's `dev` extra. Keep exports, build/install scratch, caches, package
metadata, virtual environments, and each new Run state root outside both
clones.

The single launch environment is:

[source,text]
----
PATH=<development/evidence-env>/bin:<runtime-env>/bin:<remaining trusted base PATH>
----

Select Runtime N independently of `PATH` by invoking the absolute
`<runtime-env>/bin/wfc`; never use bare `wfc`. Verify that absolute executable
with `--help`, and verify through production `snapshot_environment()` and
`prepare_evidence_commands()` that the ordered `PATH` is captured and the
policy command `python -m pytest -q` resolves to the development/evidence
interpreter. Supply the development clone to `--repository`, its exact full
HEAD to `--expected-head`, and a new external path to `--state-root`. The
WorkItem's per-phase artifact mapping is authoritative; do not pass the legacy
`--durable-artifact` option.

== Ownership and promotion

The maintainer owns the RepositoryPolicy, profile, WorkItem, task, scope,
acceptance, push, and any later runtime promotion. WFC coordinates only the
committed envelope and may create only its authorized local commits. The
maintainer separately reviews and accepts a result, may push it, and may later
promote a runtime. Promotion is never automatic.

The committed developer-ergonomics WorkItem is a separate future first dogfood
Run. Bootstrap B2 validates it provider-free but does not execute it. The
current adapter's `--sandbox workspace-write` request remains provider-owned
behavior; it is not trusted Coordinator-owned containment of the host or
environment.
