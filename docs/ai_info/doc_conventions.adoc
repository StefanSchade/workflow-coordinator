Updated::   2026-11-05
Owns::      How to write and classify WFC documentation -- the Maturity/Authority metadata model, the writing conventions, and modular-chapter mechanics. Does not own feature implementation status or Run execution authority.

One page. No approval requirement, no governance framework beyond what
follows. This is Batch 1 of
link:../warm_storage/concepts/wfc_documentation_consolidation_plan.adoc[the
documentation consolidation plan] (its §2, §3); it restates the plan's
already-worked-out model rather than defining a new one.

*Runtime-authority fact, stated once:* neither `Maturity::` nor
`Authority::` grants WFC runtime execution authority. An actual Run,
provider invocation, Runtime promotion, or repository mutation is
authorized only by an explicitly committed Commission/WorkItem/Profile/
Policy -- never by a document's own metadata or prose. No other WFC
document needs to repeat this.

== 1. Three concepts, kept distinct

Only the first two are document metadata; the third never is.

[cols="1,3",options="header"]
|===
|Concept |Where it lives

|*Document maturity* -- lifecycle of the document artifact
|`Maturity::` in the document header

|*Document authority* -- standing of its content
|`Authority::` in the document header

|*Feature implementation progress* -- property of a feature or defect
|The controlling `+FTR-*+`/`+BUG-*+` record, never a document header (§1.6)
|===

=== 1.1 `Maturity::` vocabulary

[cols="1,3",options="header"]
|===
|Value |Meaning

|`draft`
|Being written or substantially incomplete; may change without notice.

|`in-review`
|Content complete and submitted for independent review; not yet dispositioned.

|`stable`
|Maintained and expected to stay current. Says nothing about whether the
content is normative.

|`superseded`
|The *document* is no longer maintained; retained as evidence. Belongs in
`cold_storage/`.
|===

=== 1.2 `Authority::` vocabulary

[cols="1,3",options="header"]
|===
|Value |Meaning

|`historical`
|Content describes a past state, retained as provenance. Distinct from
`Maturity:: superseded`: a maintained document may contain historical
content (§1.4).

|`informative`
|Explains, navigates, or summarizes; defers to a named owner for every
contract it touches.

|`exploratory`
|Concept, hypothesis, or discussion record. Not adopted; nothing may be
built on it without separate adoption.

|`accepted-design`
|Independently reviewed and accepted as the design to implement. Acceptance
is neither implementation nor a currently applicable contract.

|`normative`
|Currently applicable: states a contract or invariant that current behavior
and current work must respect.
|===

=== 1.3 Relationship fields

Used only when they apply, to preserve a distinction a single state value
would destroy:

* `Supersedes::` / `Superseded-by::` -- document-level replacement.
* `Superseded-in-part-by::` -- a named decision or record overrides one
  point while the rest of the document stands (§1.4).
* `Governing-records::` -- already used by several WFC documents; keep it.

=== 1.4 Mixed documents: section-level overrides

A document is sometimes only partly current. Resolve that at section
granularity with the same two fields -- no new governance model, no
document split:

* Give the whole document the weaker, document-level default so nothing in
  it is read as a contract by accident (for example `Authority::
  exploratory`), and mark only the superseded point with
  `Superseded-in-part-by::` naming the overriding decision.
* Mark only the dated/delivered sections with a one-line section-level
  `Authority:: historical`; everything else keeps the document default.

Two worked instances already exist in
link:../warm_storage/concepts/wfc_documentation_consolidation_plan.adoc[the
consolidation plan]'s §2.3 (a design accepted after its own stale `Status::`
line was written) and §2.4 (a mixed delivered/forward-looking contract
document) -- read those before classifying a similarly mixed document
rather than re-deriving the pattern from scratch.

=== 1.5 Mechanical placement

The metadata block must be separated from the title (and any `:attr:`
entries) by a blank line. Without the blank line, AsciiDoc parses the
document-header position and silently renders `Maturity:: stable` as the
author line and the next two lines as revision fields instead of a
description list.

[source,asciidoc]
----
= <Title>
:toc:

Maturity::  stable
Authority:: normative
Updated::   2026-11-05
Owns::      <the durable facts this document is canonical for, one line>
----

=== 1.6 Status stays at the controlling source

Feature status and its evidence belong to the controlling `+FTR-*+`/
`+BUG-*+` record, never to a document header. WFC development is
incremental -- slices are partially implemented, interrupted, resumed,
revised -- and the record is where slice-level dispositions already live;
`docs/backlog/_open.adoc` stays the planning and navigation overview, which
links onward rather than restating.

Current documentation *may* state facts about implemented behavior where
needed for comprehension -- the technical model's "As-is: confirmed from
current source" is a legitimate, permanent example of this. What a
document must not carry is a *redundant status declaration* that duplicates
a controlling record and will silently go stale.

=== 1.7 Chapter source files: standalone and assembled rendering

A chapter file must be legible on its own but must not inject a second
metadata block into an assembled guide. Wrap the chapter's own header in a
preprocessor conditional that the guide entry document switches off:

[source,asciidoc]
----
\ifndef::assembled[]
= WFC Operator Guide -- Run Preparation

Maturity::  stable
Authority:: normative
Updated::   2026-11-05
Owns::      Deterministic Run-preparation mechanics.
\endif::[]

== Run preparation
...
----

*Verified with asciidoctor (2026-11-05):* the blank line between the title
and `Maturity::` inside the guard is required by §1.5 and is easy to drop
precisely because the `ifndef::assembled[]` line sits directly above the
title. Omitting it reproduces §1.5's failure exactly: both this chapter's
standalone render and an assembled render that includes it silently lose
`Maturity`/`Authority` into the author/revision lines instead of a
description list.

The entry document sets `:assembled:` before its `include::` directives.
Reading the chapter alone shows its own title and metadata; reading the
assembled guide shows the guide's metadata once, not once per chapter. A
chapter declares `Maturity`/`Authority` only where it *differs* from the
guide's -- otherwise it carries just an `Owns::` line naming the facts it
owns.

Backlog records, review artifacts, and `cold_storage/` keep their own
existing schemas; this model applies to documentation only.

== 2. Writing conventions

. *Declare maturity and authority* using §1. Four header lines, no prose
  status paragraph, and the blank-line placement rule of §1.5.
. *State the runtime-authority fact once*, in `docs/README.adoc` (and
  restated once above, since this document is itself read standalone). No
  other document carries a non-authorization disclaimer.
. *One canonical home per durable fact.* State it once, in the document
  whose `Owns::` line claims it. Elsewhere, link and give the conclusion in
  one sentence -- never restate the procedure.
. *Keep document metadata out of issue lifecycle.* Feature status, slice
  dispositions, and review evidence stay in the controlling record under its
  own schema (§1.6).
. *Current documents stand alone.* A reader must understand current
  behavior without reconstructing history. Cite an archived record for
  provenance only after stating the conclusion in the document's own words.
. *Proportionate detail.* Concise and token-efficient but human-readable:
  concrete commands, small YAML fragments, worked examples where they
  prevent a misreading; no example that restates a procedure another
  document owns. No length targets.
. *Structure for selective retrieval.* Prefer a central entry document with
  chapter includes over a monolith, so one chapter can be loaded alone.
  Meaningful headings; one `=` title; sections from `==`; chapter files
  `==`-rooted per §1.7.
. *Mechanics.* AsciiDoc for new documents. No date in a filename unless the
  document *is* a record of that date's event.
. *Apply prospectively* -- to new documents and current documents expected
  to outlive the MVP. `cold_storage/` and `imported/` are not migration
  targets; a historical document is read as evidence, not corrected to this
  model.

A WFC document does *not* require: a dedicated approval workflow before
publication; a function/file/section length or readability metric; a
repeated non-authorization disclaimer once §1's runtime-authority fact is
stated centrally; or a review artifact for a routine content edit that
changes no contract (routine edits still get the review artifacts their
owning WorkItem/Profile requires). Proportionality -- stating "not
applicable" plainly rather than hiding a touched contract -- is preferred
over forcing every document through the same checklist.

== 3. Reference Readability and Local Human Readability

WFC already adopts these two principles from Core's Domain Maintainer
Contract for *code* maintenance
(link:../warm_storage/concepts/wfc_documentation_consolidation_plan.adoc[consolidation
plan] §7). The same two definitions apply to documentation text, unchanged:

=== 3.1 Reference Readability

Permanent documentation must state its meaning *without requiring an FTR
ID, review finding, obsolete version name, or Git history lookup*.
Historical identifiers may remain as optional provenance when the
surrounding meaning stands independently of them. A document that only
makes sense by cross-referencing a review finding or a superseded slice
label fails this, regardless of its `Maturity`/`Authority` fields -- metadata
correctness does not substitute for readable prose. (Live counter-example,
not a documentation file but the same failure mode: `operator.py:214`'s
user-facing refusal message names a historical slice label a reader cannot
resolve without archaeology.)

=== 3.2 Local Human Readability

For a document a reader actually opens, that reader should be able to
reconstruct current meaning, scope, and important non-local reasons without
avoidable archaeology through other documents, backlog records, or Git
history. This is bounded reconstruction inside a sound documentation
structure (§2 point 7), not a mandate to inline everything: §1.3's
cross-reference fields and §2 point 3's "state it once, link elsewhere" rule
remain correct. It creates no length, section-count, or link-count metric.

== 4. Scope

Applies to current WFC documentation only. `cold_storage/`, `imported/`,
`provenance/` keep their existing curation and are not migration targets
(§2 point 9). Backlog records (`+FTR-*+`/`+BUG-*+`/`_open.adoc`), review
artifacts, and governance artifacts under `governance/` keep their own
existing schemas (§1 and §1.7); this document does not alter them. This
convention does not itself migrate any existing document's header --
link:../warm_storage/concepts/wfc_documentation_consolidation_plan.adoc[the
consolidation plan]'s Batch 3 does that, one document at a time, using the
inventory in its appendix.
