== Make standing clear where it matters

Identify binding current contracts, explanatory guidance, unadopted concepts
and historical material in the text where a reader could confuse them.
Label historical or proposed sections in mixed documents at the section itself.
An accepted design is a design to implement, not proof of implementation or
an automatically applicable current contract. Execution authority comes from
the admitted governing inputs described in the index, not document labels.

No uniform metadata block or parallel index classification is required:

* `Authority::` can clarify standing when the introduction does not. Existing
  `normative`, `informative`, `exploratory`, `historical` and `accepted-design`
  labels express the distinctions above; they do not grant execution authority.
* `Owns::` is useful when a document's canonical subject would otherwise be
  ambiguous. A clear title or introduction usually suffices.
* `Maturity::` is optional; use it only when a draft or review condition
  matters to the reader. Maintaining `stable` everywhere adds no useful fact.
* `Updated::` is useful for a dated snapshot or verification with a stated
  scope. Git records ordinary edits; no date refresh is required for each edit.
* For supersession, link the replacement and identify the affected rule or
  section. Plain text suffices; existing `Supersedes::`, `Superseded-by::`,
  `Superseded-in-part-by::` or `Governing-records::` fields may do that job.
  No paired fields or duplicate index entry are required.

These rules replace the link:../warm_storage/concepts/wfc_documentation_consolidation_plan.adoc[earlier mandatory metadata model]
and its central classification maintenance. Existing headers need no bulk migration; old
consolidation inventories and reviews describe their own work, not an ongoing
header-update obligation.

== Update documentation with behavior

Distill active durable knowledge into the appropriate current models and
operational documents; preserve inactive reasoning and provenance in cold
storage. Archival does not judge validity. See
link:../research/context_sculpting_and_knowledge_lifecycle.adoc[context sculpting and the knowledge lifecycle].

When implementation changes documented behavior, the implementer updates the
affected canonical documents in the same WorkItem, within authorized scope.
Operating commands, usage, preparation, evidence handling or recovery changes
particularly require checking the link:../operator_manual/operator_manual.adoc[Operator Manual]
and updating affected sections. Link to the owning procedure elsewhere.
If there is no documentation impact, no artificial document edit or separate
form is needed.

If a necessary update is outside scope, the implementer names the document,
required correction and reason in the work result or handoff to the responsible
maintainer, who arranges the scoped follow-up. Do not expand agent scope.
Feature implementation, independent acceptance and product closure are recorded
at their actual milestones as described in link:../backlog/README.adoc[backlog upkeep];
none follows automatically from editing documentation.

== Write for direct use

* Keep one canonical home per durable fact or procedure; link to it elsewhere.
  The index provides navigation, not a second copy of headers or issue status.
* Explain current meaning, scope and important reasons locally. A reader should
  not need an FTR ID, review finding or Git archaeology to understand the text.
  Historical references can supply optional provenance after the conclusion.
* Use concrete commands and small examples when they prevent misunderstanding.
  Use meaningful headings and proportionate detail; no length metrics.
* Use AsciiDoc for new documentation. Date filenames only for dated records.
  Check affected relative links and fragments, including inbound links when
  headings or paths change. Render changed pages and relevant assemblies.

== AsciiDoc mechanics

Use one `=` document title and sections starting at `==`. Leave a blank line
between the title/attributes and body text or description-list metadata;
otherwise AsciiDoc can interpret metadata as author/revision information.
For modular guides, guard a chapter's standalone title and optional metadata:

[source,asciidoc]
----
\ifndef::assembled[]
= Run preparation

A standalone introduction, if needed.
\endif::[]

== Run preparation
...
----

The entry sets `:assembled:` before its `include::` directives. Follow the
existing guide's `leveloffset` arrangement; check both standalone and assembled
rendering. Keep any section-specific authority or historical warning outside
the guard so it remains visible in the assembly.

== Scope

Apply these rules when creating or maintaining current documentation. Backlog,
review and governance artifacts retain their own schemas and configured
Coordinator/review requirements. Routine documentation changes need no additional
approval process or review artifact beyond those requirements. Historical
Commissions, accepted reviews and archived sources remain unchanged.
