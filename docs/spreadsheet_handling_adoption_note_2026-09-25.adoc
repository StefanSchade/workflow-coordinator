== Reading this note

This is deliberately a short reconstruction, not a new DMC procedure, FTR,
roadmap, traceability system, or architecture design.  It is intended to
prevent several weeks of WFC work from obscuring the empirical context that
created WFC's first use case.

The factual bases are Git and the governing/review artifacts in the
read-only sibling repository at `../core`, verified at
`ad91eeb067752ae4773f86927071dd6c3aaf8621`.  Project Memory is useful
orientation, but is not the basis for a disputed historical claim.  The
standalone WFC baseline consulted for this note was
`9b98c99575ffe6f13065ae1855932bc13c219adf`.

Paths below are relative to the spreadsheet-handling parent unless stated
otherwise.  Historical review artifacts explain evidence and decisions; they
are not silently promoted to present behavioral authority.

== The bounded DMC was retained

The August DMC formation and promotion sequence is visible in
`fefe7f41` (design), `5b6398bc` (revision), `73c990fe`, `68c64ea5`, and
`8b45d2ae` (review/finding closure), `7e8c49cb` (promotion), and
`3eee351f` (promotion verification).  The promoted contract remains at
`core/docs/developer_guide/ch06_code_conventions/05_domain_maintainer_contract.adoc`.

Its basic unit is broad-but-bounded Domain hardening: understand the selected
area's semantics, authority, compatibility, state, consumers, tests, and
documentation sufficiently to make a safe local decision.  A family is the
normal, pragmatic divide-and-conquer scope where semantic and metadata
locality make it useful.  It was never asserted to be the only possible
scope.  The contract expressly also permits a bounded capability, shared
primitive whose stewardship changes, cross-cutting Domain service, boundary,
or material handoff.

Accordingly, the following is an important correction to a tempting but false
history: September's cross-family finding did *not* abandon family-by-family
DMC hardening, and Relation-Key Identity did *not* replace the family model.
A family cycle can expose a semantic fact whose real ownership is wider than
that family.  The proper response can be one bounded shared-primitive
investigation, followed by an explicit return to the originating family/cycle.
Later family or cross-family census/hardening can complement one another.
The DMC current-state assessment explicitly concludes that this is a scope
selection limitation, not a reason to revise DMC.

== Why the first pilot pointed to WFC

The DMC pilot did not show that semantic decisions are mechanical.  It showed
that getting a bounded decision through implementation and independent review
repeated a mechanical human dispatch loop:

[source,text]
----
bounded prompt -> agent work -> Git verification/evidence packaging
  -> choose next role/context -> independent review
  -> bounded correction and re-review, or a human gate -> repeat
----

`core/docs/warm_storage/concepts/agent_workflow_coordinator_concept_2026-08-25.adoc`
records the distinction precisely: the recurring burden was packaging and
hand-off between turns, not substituting automation for maintainer semantic
authority.  The contemporary Cycle-1 handoff commit `c4b844a2` additionally
records that the 60+ small reviewed commits became difficult to navigate by
subject alone.

That is the provenance of WFC's intentionally narrow inner loop.  Current
WFC executes one already-admitted WorkItem through worker, independent review,
bounded correction/re-review, acceptance, or a human stop.  It does not decide
which semantic work exists.  DMC and a human (or a future separately designed
higher-order process) remain responsible for that steering.

=== Git identity is helpful but not a new subsystem

The historical guidance at `c4b844a2` added a non-binding recommendation:
future DMC work should expose stable family/cycle/work-item macro identity in
Git where practical, through a subject tag or trailers such as
`DMC-Family`, `DMC-Cycle`, `DMC-Work-Item`, and `DMC-Phase`.  It neither
rewrites history nor adds a validator.

For future real WFC DMC use, preserve the same division:

* Git is factual repository authority: commits, ancestry, changed paths, and
  current tree truth.
* WFC Run/Hop evidence is operational genealogy: what was admitted, attempted,
  reviewed, corrected, and stopped under a particular bounded execution.
* Project Memory is durable semantic orientation after appropriate human
  curation; it is not per-Hop state and does not grant Run authority.

Visible macro identity in Git should make the first two easier to reconcile;
it should not become a fourth authority or a traceability product.

== The deletion-authority return was a real subroutine

The clearest empirical precedent is
`core/docs/cold_storage/reviews/topic_reviews/fk_helper_reviews/dmc_hardening/deletion_authority/sequence_summary.adoc`.
The H5 FK/Lookup provenance-handoff slice found that a physical helper column
could be materialized by Lookup while FK cleanup believed it owned the same
name.  Requested or durable-policy identity was insufficient authority to
delete a physical artifact.  Because this required research, design, several
runtime slices, integration review, documentation closure, and finding
correction, it was extracted from ordinary Cycle-1 work.

It behaved like a bounded subroutine:

[source,text]
----
DMC hardening
  -> FK/reference-helper family, Cycle 1
       -> H5 provenance-handoff slice
            -> deletion-authority child investigation
               -> closed after integrated evidence and documentation
       -> return to the exact interrupted Cycle-1 point
----

The child did not become a new family or silently advance Cycle 1.  Its
sequence summary says both that it was a required nested question and that it
returned to the exact H5 point.  Cycle 1 then continued through F-002 and the
Cell Codec handoff and closed at `f4698c8f`.  This is concrete evidence for a
conceptual return address, not evidence that WFC already has a general return
stack.

synonymous with code churn.  `312f712c`, its independent review `deb1ba22`,

== What Relation-Key Identity discovered

The September current-state audit found a single high-risk semantic fact with
four independent current interpreters: FK helper materialization, FK helper
validation, Lookup enrichment, and declarative reference/graph validation.
They were not merely different implementations of an accepted shared rule;
there was no accepted relation-key owner at all.

The reproduced examples in
`core/docs/warm_storage/global_reviews/relation_key_identity_dmc_cycle0_assessment_2026-09-18.adoc`
show why this matters:

[cols="2,4",options="header"]
|===
| Example | Current disagreement observed

| `" 1 "` versus `"1"`
| FK and Lookup materialization miss, while FK validation trims and reports
  a misleading helper-value mismatch rather than an unresolved key.

| `1` versus `"1"`
| FK and reference/graph stringification resolve it; Lookup's inferred-dtype
  merge raises a raw pandas `ValueError`.

| `1.0` versus `1`
| FK misses and reports unresolved; Lookup resolves under pandas numeric
  behavior.

| `True` versus `1`
| Current Lookup/pandas mechanics can collapse them despite Boolean and
  Number being distinct admitted scalar categories.

| `None` versus `None`, or `""` versus `""`
| Validators treat Missing as non-identity or skip it under caller policy,
  while FK/Lookup producer paths can match blank or null target rows.
|===

The accepted bounded answer is not a universal scalar normalizer or generic
equality framework.  It introduces a narrowly owned Domain relation-key
primitive and leaves carrier representation, scalar admission, display,
generic tuple uniqueness, and caller-specific reporting policy separate.
Supported principles are:

* Missing never participates in relation-key identity; a permitted absent
  source may still be skipped by its caller, but it does not match a Missing
  target.
* String identity is exact payload: no trimming, and non-empty whitespace is
  eligible.
* Identity is category-sensitive: String `"1"` differs from Number `1`, and
  Boolean `True` differs from Number `1`.
* Number identity is exact represented numeric value, rather than
  stringification, pandas coercion, or NumPy weak-scalar promotion; therefore
  `1` and `1.0` agree when their exact values agree.
* Equality and the hashable key identity must agree, so maps, sets, duplicate
  checks, and merge-style consumers do not receive incompatible answers.

This explanation intentionally omits the accepted design's detailed Date and
DateTime bases and implementation traps.  Those are bounded Cycle-0 design
evidence, not new WFC requirements.

=== How it fits the existing FK program

Relation-Key Identity is a shared-primitive DMC scope whose stewardship changes,
not a renamed FK family.  It covers the maintained FK, Lookup, declarative
reference, and graph consumers because an FK-only decision would unilaterally
choose equality for the other owners.  It also carries the useful part of
C3-S2's `"nan"` obligation into the FK migration slice; it does not claim that
C3-S2 was implemented.

The accepted dependency shape is:

[source,text]
----
                    +--> Slice 2: FK --------+
                    |                         |
Slice 1: owner/tests +--> Slice 3a: Lookup ----+--> Slice 4: docs
                    |                         |
                    +--> Slice 3b: Ref/Graph -+
----

Review 002
(`core/docs/warm_storage/global_reviews/relation_key_identity_dmc_cycle0_assessment_2026-09-18_review_002.adoc`,
commit `397d4cf6`) gives Verdict A: the Cycle-0 review loop is closed; Slice 1
may later be authorized; implementation has not started.  It also retains
generic `unique_edges` and `unique_reference` tuple identity as a separate,
undecided follow-up rather than smuggling it into this scope.

== Current conceptual return stack

This is a semantic-navigation representation, not a WFC data model:

[source,text]
----
DMC hardening program
  -> FK/reference-helper family
       -> Cycle 3: partly complete
          (C3-S1 accepted; C3-S2 ready but unauthorized)
       -> relation-key identity: bounded shared-primitive child scope
          (Cycle 0 review closed; Slice 1 candidate, not authorized)
       -> return address: FK/reference-helper family/cycle context,
          reconciled against accepted repository truth after the child closes
----

The deletion-authority precedent establishes the desired discipline: close the
bounded child, record its outcome, then re-enter/reconcile the parent rather
than assuming the old next action still applies.  Relation-Key work must not
silently become “the new DMC program” or cause the family sequence to vanish.
The exact parent resumption decision remains human/DMC steering, especially
because the September assessment redirects the cross-owner key question away
from a one-sided FK Cycle-3 decision.

== Adoption lesson for standalone WFC

The next experiment should be empirical and deliberately small: run several
real, bounded DMC WorkItems through the standalone inner loop before designing
a higher-order loop.  Observe hop duration, review findings, correction and
rereview behavior, provider behavior, commit genealogy, operator ergonomics,
and the points at which a human still supplies semantic steering.

The likely first consumer identity is *proposed*, not durable truth yet:
`DMC-RELKEY-C0-S1`.  Its conceptual scope is the accepted Relation-Key Slice
1: introduce the bounded private semantic owner and its contract tests before
any consumer migration.  Naming it here neither creates the WorkItem nor
authorizes its implementation, a Run, or a provider invocation.

This order matters.  WFC's current inner loop has evidence for converging one
admitted item.  It does not yet have sufficient real DMC operational evidence
to justify abstracting a family/workstream dispatcher around it.

=== A future outer loop is a signal, not a feature

The deletion-authority return and the Relation-Key parent context suggest what
a future higher-order mechanism may eventually need to model explicitly:

[source,text]
----
parent WorkItem
  -> bounded child issue discovered
  -> suspend parent with explicit return address
  -> admit and execute child WorkItem
  -> close child against accepted repository truth
  -> reconcile and resume the parent, or stop for human steering
----

The imported WFC concept evidence calls this explicit bounded parent/child
orchestration: distinct identities, scope/budget/evidence per child, visible
child outcome, and no implicit authority increase.  It is an adoption signal
and design input only.  This note does not design, authorize, or implement an
outer loop, automatic WorkItem materialization, child dispatch, or parent
resumption.

It is also distinct from provider retry and recovery.  Recovery concerns a
failed or uncertain Attempt of an already-admitted current Hop: a possible
same-Hop retry, reconcile/resume of the same Run, or a fresh successor Run
under changed governing truth.  Parent/child orchestration concerns a new
semantic bounded problem with its own authority and return address.  A retry
does not discover, admit, close, or return from a child DMC scope.

`docs/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc` is consistent with that
separation: it explicitly excludes a generic outer loop, makes recovery
permission mechanically derived rather than policy-selected, and defers
same-Hop retry until evidence justifies it.
