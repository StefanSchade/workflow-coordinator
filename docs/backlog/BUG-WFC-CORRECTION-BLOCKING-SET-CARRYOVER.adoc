== What this is not

* This is not about whether the Scope-Escalation-Continuation mechanism's
  acceptance-matrix *content* is itself correct or sufficient. That is
  `BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP`'s own open concern and is
  unaffected by this record.
* This is not a Finding-authority or reducer-enforcement defect. Every
  `independent_reviewer` Hop discussed below used only its `rereview`-phase
  authority as designed, and the reducer's fail-closed acceptance gate was
  never bypassed.
* This is not a claim that any individual reviewer Hop was wrong to block, or
  that any individual worker Hop's correction was itself defective. Each
  correction Hop (H001/H003/H005/H007 across both Runs, see below) made a
  real, verifiable fix for the specific defect group its immediately
  preceding review had just raised, confirmed by the next review.
* This is not a crash, uncertain dispatch, or mechanical preemption. Every Hop
  examined here ended in an ordinary `completed` or `changes_required`
  outcome with a clean, fully committed worktree.
* This record does not yet claim a specific mechanism (prompt composition,
  context projection, Finding/blocking carry-forward, or the correction
  contract) as the proven cause. See "Hypotheses to investigate" below.

named requirement -- completion of the mandatory FTR acceptance matrix -- was
raised as an explicit blocking item at *every single review Hop*, and
survived six intervening correction Hops unaddressed, even though each of
those corrections resolved the other, narrower defects the same review had
raised alongside it.

=== The pattern

Across the two Runs combined, the identically-named blocking requirement
("the mandatory acceptance matrix is absent/incomplete") was raised at seven
consecutive independent-review Hops in a row (Run 001 H002, H004, H006; Run
002 H002, H004, H006, H008), separated by six intervening correction Hops (Run
001 H003, H005; Run 002 H001, H003, H005, H007). Every one of those six
correction Hops produced a real, independently confirmed fix for *other*,
narrower defect groups the immediately preceding review had also raised
alongside the acceptance-matrix item -- but none of them made the
acceptance-matrix item itself materially smaller, even though it had already
been an explicit, named, written-down requirement since the very first review
that raised it. Both Runs stopped at `autonomous_hop_budget_exhausted` with
this already-known requirement as the decisive remaining obstacle.

=== Requirement identity versus requirement-closure convergence (Runs 003-004)

Runs 001-003 provide evidence of a *requirement carryover/identity* problem:
the same substantive blocking concern survived across reviews, but under a
new name and number at nearly every Hop that restated it (B5 -> R4 -> H006-R4
in Run 001; H002-R3 -> H004-R2 -> H006-R2 -> H008-R1 in Run 002; H002-R1 ->
H004-R1/R2 -> H006-R1/R2/R3 in Run 003). A reader following only Hop-local
identifiers could not tell, without re-reading full review prose each time,
whether a newly numbered item was the same long-open obligation or a
genuinely new one.

Run 004 deliberately tested a narrower, task-level intervention: stable,
explicitly named identifiers (`R1A`, `R1B`, `R2`, `R3`) that both the worker
and each fresh independent reviewer were required to re-evaluate and restate
*by the same name* at every Hop, rather than inventing a fresh label when
re-describing an existing concern. That experiment materially changed the
observed carryover behavior:

* `R1B`, `R2`, and `R3` remained explicitly addressed under their stable
  identities through H002, H004, and H006; they did not silently disappear
  from review prose and later re-emerge renamed, the way comparable concerns
  had in Runs 001-003.
* `R1A` remained explicitly the *same* open carried requirement throughout --
  named `R1A` at H002, H004, and H006 alike, never renumbered.
* Each worker correction (H003, H005) demonstrably closed the concrete R1A
  counterexample the immediately preceding reviewer had raised, confirmed by
  the next review.
* Each fresh independent reviewer nevertheless found a progressively deeper
  counterexample to the same broad R1A invariant -- a final artifact can be
  validly published while the command still reports failure -- moving from a
  post-publication canonicalization call (H002), to fallible success-output
  printing (H004), to a deferred stdout-buffer flush raising
  `BrokenPipeError` at interpreter shutdown (H006).
* Run 004 exhausted its 6/6 autonomous Hop budget at H006 with R1A, and only
  R1A, still open.

This distinguishes two different phenomena that the original Run 001/002
evidence alone could not separate:

. *Requirement identity/carryover loss* -- a still-open concern becomes
  harder to track because it is restated under a new name or number each
  cycle, independent of whether the underlying work is actually converging.
. *Failure of repeated local correction to close a broader invariant* -- even
  with requirement identity held constant and explicitly tracked, successive
  narrow corrections each closed only the specific counterexample most
  recently demonstrated, without closing the invariant the counterexamples
  were instances of.

Run 004 provides positive, but non-conclusive, evidence that stable
identifiers and explicit per-identifier completion/carry-forward discipline
measurably improve problem (1): three requirements that would plausibly have
been vulnerable to renaming under the Run 001-003 pattern instead stayed
visibly, continuously tracked and closed. One Run exercising three
correction/rereview cycles does not establish that stable identifiers are a
general or sufficient fix for (1), and this record makes no such claim.

Run 004 does *not* resolve problem (2). R1A's successive counterexamples
show that repeated adversarial review plus local correction can keep
producing real, substantive fixes without ever closing the broader invariant
those fixes are instances of, and the Run exhausted its entire autonomous Hop
budget in exactly that state. This record does not establish *why* --
whether the invariant itself was under-specified, whether the worker's
fixes were locally scoped by construction, whether exhaustive success-path
fault injection simply needs more than three correction/rereview cycles, or
some other cause. No root cause for R1A's non-convergence is established or
claimed here, and this BUG is not thereby fixed: closing R1A itself is a
separate, later, still-unauthorized act, and the pattern this record
documents -- a correction loop that keeps making real local progress without
reaching its reviewer's acceptance -- remains open regardless of R1A's
eventual disposition. Problem (2) is what motivates a generic,
domain-neutral correction-loop convergence-escape mechanism, commissioned as
a design-only Run below.

== Hypotheses to investigate (not established root causes)

The following are candidate explanations, offered to guide future
investigation. None of them is confirmed by this record, and none should be
treated as an accepted diagnosis:

* *Correction scope framing*: a correction Hop may be implicitly treating "fix
  what the latest reviewer counterexample demonstrated" as its completion
  obligation, rather than "close every currently open named blocker,
  including ones carried over from earlier reviews."
* *Prompt composition / context projection*: the correction Hop's prompt may
  under-emphasize, truncate, or fail to foreground the full accumulated
  blocking set relative to the most recent review's newest, most concrete
  counterexamples.
* *Finding/blocking carry-forward*: the mechanism by which a still-open,
  previously-raised blocking item is represented to a later correction Hop
  (versus a newly discovered one) may not clearly distinguish "already known,
  still open" from "new this cycle" in a way that shapes what the corrector
  treats as its job.
* *Correction-contract ambiguity*: the operating contract governing a
  `correct` Hop may not state an explicit obligation to address the complete
  current blocking set before requesting `rereview`, as opposed to addressing
  only the defects a correction was most directly prompted by.

The guiding hypothesis this record exists to test, stated carefully:

____
A correction Hop may optimize for the most recent reviewer counterexample
instead of treating the complete authoritative set of known blocking
requirements as its completion obligation before requesting rereview.
____

== Desired future behavior (not authorized here)

Any future correction to this gap must preserve the following properties;
none of them is a commissioned design and none authorizes implementation:

* A correction Hop must be able to obtain or reconstruct the complete current
  authoritative set of open blocking requirements, not only the most recently
  demonstrated counterexample.
* Before a correction Hop requests `rereview`, it must be possible to
  determine, for every already-known blocking item, whether it was closed,
  remains open, or was dispositioned differently in light of new evidence --
  this is a traceability property, not a new autonomous disposition authority.
* New reviewer findings must remain fully possible and are not something this
  record wants constrained; the goal is complete carry-forward of what is
  already known to be blocking, not narrower review.
* Any solution must not weaken existing Finding authority or independent
  reviewer authority. The reducer's fail-closed acceptance boundary and the
  reviewer's sole authority to accept or continue blocking a candidate must
  remain exactly as they are.
* Any solution must not invent a numerical "all findings counted, therefore
  done" heuristic if that would conflict with the existing evaluator/optimizer
  convergence architecture (`FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc` and the
  self-development `correct -> rereview -> {accept, correct}` topology); the
  independent reviewer's substantive judgment of sufficiency, not a count,
  remains the acceptance authority.

== Commission: WI-WFC-CORRECTION-CONVERGENCE-ESCAPE-DESIGN-001

Run, `WI-WFC-CORRECTION-CONVERGENCE-ESCAPE-DESIGN-001`, to produce and have
independently reviewed an implementation-ready architectural design for a
generic, domain-neutral correction-loop convergence-escape mechanism. The
commissioned subject is problem (2) above -- the observed failure of

== Lifecycle

This BUG is *open*. It documents an observed empirical pattern across four
WFC self-development Runs: Runs 001-003 show a requirement carryover/
identity problem, and Run 004 shows that stable per-requirement identifiers
materially help that specific problem while leaving a distinct problem --
repeated local correction failing to close a broader invariant (R1A) -- open
under its own stable identity through 6/6 Hops. This record does not declare
either problem fixed. In particular, it does not declare this BUG fixed, and
it does not claim a proven root cause for R1A's non-convergence: R1A's
successive counterexamples are documented as empirical observation, and the
question of why the invariant kept yielding new counterexamples is
explicitly left open above and is not answered by this record.

The maintainer has separately authorized a bounded design-only commission,
`WI-WFC-CORRECTION-CONVERGENCE-ESCAPE-DESIGN-001` (see "Commission:
WI-WFC-CORRECTION-CONVERGENCE-ESCAPE-DESIGN-001" above), to produce and have
independently reviewed an implementation-ready, domain-neutral design for a
generic correction-loop convergence-escape mechanism addressing the second
problem. That design Run's independent reviewer is the sole authority that
may accept or continue blocking the design; its eventual `accept`
disposition -- if and when it occurs -- will mean that
`docs/backlog/FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE.adoc` becomes the
accepted architectural/design authority for this mechanism, without any
further separate maintainer design-acceptance act, exactly as independent
review acceptance already did for the accepted
`docs/backlog/FTR-WFC-SCOPE-ESCALATION-CONTINUATION.adoc`. Accepted
architecture is nonetheless not implementation authority: that acceptance
will not by itself implement anything, will not by itself close this BUG,
will not by itself close `BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP` or
resolve R1A, and will not promote `workflow-coordinator-runtime` or
authorize any further Run -- a later implementation Run still requires its
own separate, explicit maintainer Commission. Closing this BUG requires a
separate, later maintainer decision after a
mechanism is actually implemented, independently reviewed, and shown to work
against real evidence, which may include R1A as a dogfood case. No
correction to the convergence-escape problem itself has been commissioned;

Finding and independent-reviewer authority exactly as they stand today, and
