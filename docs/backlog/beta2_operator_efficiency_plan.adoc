[[target]]
== The target picture

The operating model does not change. A Level-1 operator still authors one
bounded Commission at a time, previews it, launches one Run per fresh
checkout, reads the classification and integrates what an independent review
accepted. This plan removes mechanics and recoverable mistakes from that loop
and adds no stage, gate class, agent role, program or governance layer.

Six states of the operator's own loop, and what each costs today:

[cols="1,3,2",options="header"]
|===
|State |What it is, and today's cost |Where it lives

|*1 Prepare the checkout*
|A fresh worktree at a *fresh path*, its own venv with an editable install,
the verified offline bundle in the environment, a scratch `TMPDIR` outside
the worktree, and -- until <<o3,O3>> -- a second committed config file that
must never be integrated. All manual; five friction entries; each omission
costs a refused probe and the checkout's single lifecycle.
|<<o4,O4>> (new command), <<o1,O1>> (the recipe)

|*2 Author the Commission*
|A task document, scope, program, personas, Hop budget and one evidence
command. The judgement is irreducible; the mechanics are not: the operator
writes a build script and a shell wrapper per Commission for a Consumer
Request `wfc plan` already assembles and discards.
|<<o5,O5>>, <<o1,O1>>

|*3 Choose the deterministic gate*
|One evidence argv, freely chosen. The highest-leverage decision in the
system and the one with no guidance: omitting lint cost ten Hops and two
Opus Broad Reviews for one unused import.
|<<o1,O1>> (the rule), <<o6,O6>> (the docs half of the gate)

|*4 Launch*
|`wfc plan`, then `wfc run --yes`. Three refusals arrive late or incomplete
and each one spends the checkout: a config path checked only after
authorization, an `--executable` never compared with its adapter, and a
probe refusal that discards the output it captured.
|<<o2,O2>>

|*5 Read the stop*
|Classifications are documented and accurate. Two things the operator needed
are not in the shipped texts: `wfc resume`'s actual scope, and that
`prepare-successor --authority-decision` is the answer channel for an
`awaiting_human` semantic stop.
|<<o1,O1>>

|*6 Verify and integrate*
|Unchanged, and deliberately so. Independent verification before
integration, and the reviewer's sole Finding authority, are the safeguards
this plan is built to protect rather than to cheapen.
|no slice
|===

What is *deliberately absent* from the target picture, each with the
recurring cost it leaves in place: a list of evidence commands, an in-place
Hop-budget raise, Worker-only closure of a mechanical Finding, a non-default
phase entry, mechanical CommitIntent enumeration and checkout reuse. All six
are category B; <<decisions>> and <<not-done>> state why none is proposed.

[[slices]]
== The slices

Six slices. They group the analysis's eight candidates into six because
`C7` and `C8` are category B and carry no slice at all. Each slice is
independently commissionable, independently useful and sized for one Run.

*Authority class* is the analysis's A/B classification. Every slice below is
*class A*: none changes a trust or authority boundary. That is a property of
the proposed cut, not a coincidence -- the class-B candidates were
deliberately left out of it.

*Program and model recommendation* follows the shift-left rule: the strongest
model where the work is design judgement or a completeness argument over a
list, a cheaper one where the work is mechanical and a deterministic gate
decides. The repository's committed default is already Sonnet worker and Opus
reviewer; where a slice says *default*, it asks for that and not for an
exception.

*Evidence command.* Every slice names a single argv that runs the
repository's own deterministic gates, which is the direct remedy for friction
entry 18. For code slices that is `make check` (`lint format-check test`,
`Makefile:28`). Two preconditions the operator must satisfy before launching,
both of them existing practice: the verified offline input bundle must be in
the launching environment, because the suite has reached 896.96 seconds
without it against a 900-second kernel hard cap (`model.py:27`), and the
exact command must be run by hand in the fresh checkout first, because a
refused probe spends the checkout. Documentation slices name <<o6,O6>>'s
aggregate target instead, which is why O6 is first.

Record:: link:FTR-WFC-UNUSED-ROLE-DEFAULT-TOLERANCE.adoc[FTR-WFC-UNUSED-ROLE-DEFAULT-TOLERANCE]
(analysis `C1`; friction entries 1 and 21).
Purpose:: `simple@v1` cannot run in a repository whose committed config
carries a `robust@v1` reviewer default (`frontdoor/config.py:257-262`), so
every `simple@v1` Commission needs a second committed config file that must
never be integrated -- and editing the committed one instead breaks an
exact-equality test and fails the baseline probe, which is friction entry 21
in full. This slice removes the artifact and the failure mode together.
Exact scope:: `frontdoor/config.py`, `frontdoor/plan.py` (to print the
ignored defaults), their unit tests, and the Agent Skill and manual
paragraphs <<o1,O1>> wrote as *planned*. Inside the ceiling.
Dependencies:: <<o1,O1>> accepted *and integrated* (it carries the
second-config paragraph this slice retires). <<d2,D2>> decided. No dependency
on <<o2,O2>>, <<o4,O4>> or <<o5,O5>>.
Risks:: (a) The refusal is the only mechanical signal that a committed role
default is inert, so removing it could let a consumer read an
`independent_reviewer` default as evidence that review happens when the
selected program performs none. Mitigated by printing the ignored defaults in
`wfc plan`, which makes inertness visible rather than silent, and by the fact
that an unknown role *name* is still refused when the config is parsed
(`frontdoor/config.py:204-206`). (b) Over-reach into the override check.
Mitigated by the acceptance criterion that an unused `--execution-override`
is still refused: an override is a per-Commission intent that cannot take
effect, a config default is a standing repository fact.
Evidence command:: `make check`.
Acceptance (verifiable):: `simple@v1` resolves against the committed
repository config unchanged, with no second config file and no edit to
`.wfc/config.yaml`. An unused `--execution-override` is still refused with
its existing message. `wfc plan` names every role default the selected
program ignores. `tests/unit/test_self_development_consumer_config.py` is
green and unchanged. The skill and manual no longer instruct the operator to
create a second config file.
Program and model:: *default* -- `robust@v1`, Sonnet worker, Opus reviewer.
The implementation is a handful of lines, but it *narrows a fail-closed
check*, and that is precisely where an independent reviewer earns its cost.
Hop budget (upper limit):: 6.
Authority class:: A, with the named safeguard consideration above. It changes
no admission authority: the set of roles a program resolves
(`frontdoor/config.py:269-274`) is unchanged, and an unused default is
already inert there.
Qualification and review path:: `robust@v1`'s own broad review, focused on
the safeguard question; `make check`; a reviewer check that the override
refusal is intact.
Front Door docs-sync:: Applies. A refusal disappears and `wfc plan`'s output
gains a line, so the skill's setup reference and the quickstart are checked
in this slice and the paragraphs <<o1,O1>> wrote as planned are retired here.

=== O2 — Pre-launch refusals that are complete and early

Record:: link:BUG-WFC-PRELAUNCH-REFUSAL-ERGONOMICS.adoc[BUG-WFC-PRELAUNCH-REFUSAL-ERGONOMICS]
(analysis `C2`; friction entries 2, 14 and 21).
Purpose:: Three refusals around `wfc run`'s first three steps arrive late or
omit the fact the operator needs, and each one spends the checkout's single
lifecycle -- a fresh worktree, a fresh venv and a fresh multi-minute probe
every time. These were three of the four lifecycle losses of the session.
Exact scope:: `frontdoor/plan.py`, `frontdoor/lifecycle.py` (steps 1-3 only:
authorization, pre-launch, probe) and their unit tests. Inside the ceiling.
No kernel change, no new classification, no change to the probe's own
semantics.
Dependencies:: <<o1,O1>> accepted *and integrated* (it carries the
`--executable` rule this slice retires). Sequenced after <<o3,O3>> in
<<ownership,the one lane>>, with no content dependency on it.
Risks:: (a) The adapter-mismatch refusal is *new*, and a false positive would
block a legitimate provider wrapper. Mitigated by refusing only an
unambiguous cross-adapter mismatch -- the resolved basename is the *other*
adapter's known binary -- and never refusing an unrecognized name or an
explicit path. (b) Printing captured command output in a refusal must not
blur the trusted/untrusted split. Mitigated by reusing the existing bounded
limit and untrusted labelling of the in-Hop path (`evidence.py:25`,
`:243-260`) and by persisting nothing as evidence. (c) Moving the config-path
check earlier must not change which inputs are *admissible*, only when the
refusal happens.
Evidence command:: `make check`.
Acceptance (verifiable):: `wfc plan` refuses a `--config` that is absolute or
not A1-normalized, with a named message, before any lifecycle exists; the
same input in `wfc run` is refused before authorization rather than as
`inconsistent` after the Commission commit. A `claude_cli` envelope launched
with `--executable codex` (or the reverse) is refused by name before dispatch;
an explicit path and an unrecognized basename are not refused. A failing
baseline probe's refusal carries a bounded, explicitly untrusted tail of the
output `subprocess.run` already captured, beside the exit code. The
`refused_probe`, `refused_prelaunch` and `refused_drift` classifications and
their exit codes are unchanged, and no admissible input becomes inadmissible.
Program and model:: *default* -- `robust@v1`, Sonnet worker, Opus reviewer.
Three small changes in a fail-closed launch path, one of which adds a
refusal; the authoring is routine and the boundary reasoning is not.
Hop budget (upper limit):: 8.
Authority class:: A. (a) and (c) move or extend diagnostics only; (b)
narrows rather than widens.
Qualification and review path:: `robust@v1`'s own broad review; `make check`
with one new test per refusal; a reviewer check that no classification or
exit code moved and that the printed tail is labelled untrusted.
Front Door docs-sync:: Applies in full -- diagnostics and a new refusal
cause. The classifications do not change, so the skill's stop table should
need no edit; the `--executable` rule <<o1,O1>> wrote as planned is retired
here.

=== O4 — One deterministic Run-checkout preparation step

Record:: link:FTR-WFC-RUN-CHECKOUT-PREPARATION.adoc[FTR-WFC-RUN-CHECKOUT-PREPARATION]
(analysis `C3`; friction entries 4, 6, 12, 17 and 20).
Purpose:: The widest-footprint friction in the session. Every Run needs a
fresh checkout *at a fresh path* (`frontdoor/journal.py:75-89`), its own venv
with an editable install, the verified bundle in the environment and a
`TMPDIR` outside the worktree; all of it is manual and each omission costs a
refused probe and the checkout. AD-5 names exactly this as the preferred way
to reduce the friction: "automated worktree or branch creation and controlled
cleanup at the Front Door, not a looser kernel invariant".
Exact scope (variant A, prepare only — recommended):: a new Front Door
command under `src/workflow_coordinator/frontdoor/`, `frontdoor/cli.py`, unit
tests, and the skill and manual paragraphs <<o1,O1>> wrote as *planned*. It
creates a worktree at a fresh path and a sibling scratch directory, and
drives consumer-specific environment preparation from a declared, committed
hook rather than hard-coding WFC's own offline bundle. Inside the ceiling.
Exact scope (variant B, prepare and clean up):: variant A plus removal of a
checkout and scratch directory the command itself created, recorded so that
removal can refuse anything else. Pending <<d4,D4>>.
Dependencies:: <<o1,O1>> accepted *and integrated*; <<d4,D4>> decided for the
variant. Last in the one lane. No dependency on <<o2,O2>>, <<o3,O3>> or
<<o5,O5>>.
Risks:: (a) Scope creep into checkout *reuse*, which is
link:FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]'s
category-B subject behind AD-5's five entry conditions. Mitigated by the
acceptance criterion that the command refuses any path whose checkout digest
already carries a journal -- it makes a fresh checkout cheap, it never makes
a spent one reusable. (b) A Front Door command that writes outside the
repository is a new kind of effect. Mitigated in variant A by writing only
inside the checkout and scratch directory it creates. (c) Variant B is
*destructive*, and the Agent Skill already withholds discarding anything the
session did not itself create (`SKILL.md:50`, `:57`) -- which is why the
variant is a maintainer decision and not a default. (d) WFC's own offline
bundle is not a generic consumer need; hard-coding it would make a
self-development detail part of the product surface.
Evidence command:: `make check`.
Acceptance (verifiable):: The command creates a usable checkout at a fresh
path and refuses a path whose checkout already has a lifecycle, by name. A
prepared checkout passes an unmodified baseline probe that an unprepared one
fails. The one-Run-per-checkout invariant is asserted unchanged, and no
journal, lifecycle or archive behaviour is touched. Nothing outside the
created checkout and scratch directory is written. For variant B only:
removal refuses any path the command did not record as its own, and never
touches the Evidence repository.
Program and model:: *architectural* -- `robust@v1`, Opus worker and Opus
reviewer. A new Front Door surface that sits directly against a load-bearing
kernel invariant, and in variant B performs a destructive action; the design
reasoning is the work.
Hop budget (upper limit):: 10 for variant A; 8 for a later cleanup slice if
the maintainer splits it.
Authority class:: A *while it honours the one-Run-per-checkout invariant*,
which its acceptance asserts. Reuse would be B and is excluded.
Qualification and review path:: `robust@v1`'s own broad review, focused on
the invariant and on what the command may remove; `make check`; and a
rehearsal in a scratch clone before the first real use, which is a maintainer
or operator step and *not* slice acceptance.
Front Door docs-sync:: Applies in full -- a new command and a changed
operating flow. The skill's `setup.md`, chapter 9 and chapter 10's worked
sequence are checked in this slice, and the manual-recipe paragraphs
<<o1,O1>> wrote as planned are retired here.

Two lanes, and only two. <<o6,O6>> touches no document <<o1,O1>> touches, so
it can run alongside anything; everything else is one lane for the reason the
release-streamlining plan already established for chapter 4 -- *the file is
the unit of conflict, not the section*, and four slices cannot hold

one maintainer launching one Run at a time.

If only one slice is ever commissioned, commission *O1*. It is the only
remedy for the eight friction entries whose cause is operator knowledge, it
changes no behaviour, and the four code slices are small enough that their
absence costs the operator a documented workaround rather than a wrong

[[autonomy]]
== What an autonomous Level-1 operator may do, and what it may not

May, autonomously — prepare, implement and integrate locally on `main`::
Author and launch the Commissions for <<o6,O6>>, <<o1,O1>>, <<o3,O3>> and
<<o2,O2>> within their stated scopes once the maintainer has decided the cut;
prepare each Run's fresh checkout, scratch directory and environment, and run
the exact evidence command by hand before launching; run `make check`, the
strict render and the doc-catalog check locally; integrate accepted
candidates into local `main`; and record Run id, Hops used and Evidence
commit in the controlling record and `_open.adoc` as
link:README.adoc[backlog upkeep] describes.

Needs a human decision, always::
* Every decision in <<decisions>>, and the <<cut,cut>> itself.
* Commissioning <<o5,O5>> or <<o4,O4>> at all: each is gated on a decision
  (<<d1,D1>>, <<d4,D4>>) that chooses which surface it implements.
* Any widening of a slice's stated scope, program or Hop budget, including
  after a stop.
* Any `git push`, tag, publication, external setting or `.wfc/config.yaml`
  change. No slice in this plan needs a temporary scope-ceiling entry --
  deliberately, since every scope above is inside the committed ceiling.
* Runtime promotion, `wfc skill install`, or any change of the installed WFC
  version -- which is also what makes <<o1,O1>>'s shipped text reach a
  consumer.
* Judging a stop's disposition, and opening or resolving any Finding. Only
  the independent reviewer does the latter.

[[decisions]]
== Open maintainer decisions

Seven. Each states its options, its cost and a recommendation. *None is
decided here*, and the recommendations are advice, not a default that takes
effect by silence.

[[d1]]
D1 — Does request emission get its own surface, or a flag on `wfc plan`?::
`wfc plan` is documented as writing nothing -- in the source
(`frontdoor/plan.py:1-16`, `:222-225`), the manual and the skill -- and
<<o5,O5>> needs to write one file. Not a trust boundary; a stated contract.
+
*Option A — a flag on `wfc plan`* (`--emit-request PATH`). Smallest change;
one code path; the no-flag behaviour stays byte-identical. Cost: the
"entirely read-only" sentence becomes "read-only unless you ask it to
write", which is a weaker thing to promise about a preview command.
+
*Option B — a separate subcommand* (`wfc request`), sharing
`consumer_request_from_plan_inputs` with `plan`. Cost: a second surface that
takes the same dozen arguments, and one more subcommand for the skill to
describe.
+
*Option C — no emission.* The operator keeps writing a script per Commission.
+
*Recommendation: Option B.* `wfc plan`'s write-nothing promise is load-bearing
for how the operator reasons about previewing an unauthorized Commission, and
it is repeated in three shipped texts; keeping it absolute is worth one extra
subcommand. Option A is a reasonable second choice if the argument duplication
is judged the larger cost.

[[d2]]
D2 — Are unused *config* role defaults tolerated?::
*Option A — tolerate config defaults, keep refusing CLI overrides*, and have
`wfc plan` print the ignored defaults. *Option B — keep today's refusal* and
document the second-config pattern permanently. *Option C — tolerate both.*
+
*Recommendation: Option A.* It removes a per-Commission committed artifact and
the never-integrate hazard, and it removes friction entry 21's whole failure
mode; the asymmetry is principled -- an override is a per-Commission intent
that cannot take effect, a config default is a standing repository fact
several programs share. Option C is rejected: an override that cannot take
effect is a genuine operator error and should stay refused. The residual risk
of Option A, stated plainly, is a consumer reading a committed reviewer
default as evidence that review happens; printing the ignored defaults is the
mitigation, not a cure.

[[d3]]
D3 — Does the documentation render join `make check`?::
*Option A — a separate `docs-render` target plus an opt-in aggregate* that
documentation Commissions name as their one evidence command. *Option B —
make `docs-render` a prerequisite of `check`.* *Option C — extend the release
workflow's G5 list instead.*
+
*Recommendation: Option A.* Option B would make the repository's own gate, and
therefore every Commission's mandatory baseline probe, fail on a host without
Ruby -- a cost paid by every Run to catch a defect in some. Option C needs a
maintainer-granted temporary ceiling entry for a file outside the ceiling, for
a gate a Make target provides without one; it also leaves local Runs
ungated, which is where the defect was introduced.

[[d4]]
D4 — Does the preparation command also clean up?::
*Option A — prepare only* (<<o4,O4>> variant A). *Option B — prepare and
remove what it created* (variant B).
+
*Recommendation: Option A for Beta 2, Option B considered afterwards on the
evidence of A's use.* Removal is destructive, and the skill already withholds
discarding anything the session did not create; AD-5 does name "controlled
cleanup" as part of the preferred direction, so Option B is the eventual
target rather than a rejected idea. Taking A first means the command's
recording of what it created -- which is what makes a safe removal possible
at all -- is in place and exercised before anything is removed.

[[d5]]
D5 — Is the 900-second evidence hard cap raised or made configurable?::
Category B: `COORDINATOR_HARD_MAX_EVIDENCE_TIMEOUT_SECONDS = 900`
(`model.py:27`) is a kernel limit enforced on every Consumer Request
(`frontdoor/request.py:81`). It binds the lint-inclusive evidence command
<<o1,O1>> recommends: the plain suite has reached 896.96 seconds on this
repository without the verified bundle, and 171 seconds with it.
+
*Option A — leave it.* *Option B — make it configurable below a higher hard
ceiling.*
+
*Recommendation: Option A.* The cap is doing a real job as a stall detector --
link:BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[the open timeout BUG] exists
because a gate ran to that limit with no retained output -- and the measured
fix for the duration is the prepared environment, not a longer limit. Revisit
only if `make check` is measured to exceed it on the qualified profile *with*
the bundle in place, which <<unverified-dep>> records as unmeasured.

[[d6]]
D6 — Is the evidence-command *list* adopted or deferred?::
Category B. The kernel already models several named evidence commands
(`model.py:232`) and the accepted programs already declare an evidence list
(`commissioning.py:140`, `:155`), but adopting it means changing the Consumer
Request schema *and* the accepted program literals -- and `model.py:699`
requires `phase.evidence == ("task-check",)` exactly for the terminal
Worker shape that `select_result_contract` uses, so extending `simple@v1`'s
list changes which result contract its sole phase is admitted under.
+
*Recommendation: defer*, recorded as
link:FTR-WFC-EVIDENCE-COMMAND-SEQUENCE.adoc[FTR-WFC-EVIDENCE-COMMAND-SEQUENCE]
with the coupling named, and take the benefit now through <<o1,O1>>'s rule
plus `make check`, which already gives ordered, fail-fast lint-then-test at
the cost of one conflated exit code. A design investigation first (Hop budget
10) if the maintainer wants it opened; the accepted `robust@v1` program is out
of bounds regardless.

[[d7]]
D7 — Is the economy of continuing a stopped Run addressed?::
Category B on three counts: a budget raise changes an admitted WorkItem's
governing truth against the recorded rule that used Hops are never reset;
Worker-only closure of a "mechanical" Finding moves disposition away from the
independent reviewer; a lighter answer channel re-opens what truth a
continuation admits.
+
*Recommendation: defer*, recorded as
link:FTR-WFC-STOPPED-RUN-CONTINUATION-ECONOMY.adoc[FTR-WFC-STOPPED-RUN-CONTINUATION-ECONOMY].
The erosion to weigh is that "a deterministic check failing with no behaviour
change" is not mechanically distinguishable from "a blocking Finding the
Worker would rather close itself". The interim remedy prevents the case
instead of cheapening its repair: <<o1,O1>>'s gate rule would have caught the
observed residue at the first Hop, and its budget guidance covers the
retire-heavy shape. Measured recurrence so far: once.

[[not-done]]
== Deliberately not done, and why

Each with the recurring cost it leaves in place.

* *A list of evidence commands* (<<d6,D6>>). Leaves lint, format and tests
  behind one conflated exit code. Not done because it reaches the accepted
  program literals and, through `model.py:699`, result-contract selection.
  Recorded.
* *An in-place Hop-budget raise, and Worker-only closure of a mechanical
  Finding* (<<d7,D7>>). Leaves a successor Commission with its own review
  chain as the price of a one-import residue. Not done because the first
  changes admitted governing truth and the second moves Finding disposition
  away from the independent reviewer. Recorded.
* *A non-default phase entry for a successor Run.* Leaves a verification
  Commission entering at `implement` as the substitute. Not done because AD-6
  defers it deliberately, its substitute demonstrably works, and nothing in
  the 21 entries shows a Run that needed it. The analysis adds that entering
  at a review phase also interacts with durable-artifact admission
  (`operator.py:561-576`), so it is not the cosmetic renderer change it
  resembles.
* *Mechanical CommitIntent enumeration.* Leaves a probabilistic model
  reproducing a long deterministic list.
  link:FTR-WFC-COMMIT-INTENT-ENUMERATION.adoc[Its record] already holds the
  question, three alternatives, a nine-case regression inventory and success
  criteria; a new record would duplicate it, and no entry in this session is
  a cardinality failure. The analysis adds one adverse fact about the
  *current* mitigation rather than the mechanism, as a dated pointer there.
* *Checkout reuse after a terminal lifecycle.* Leaves one fresh checkout per
  Run. Not done because AD-5 decided it stays for Beta and set five entry
  conditions; <<o4,O4>> is deliberately the complement, making a fresh
  checkout cheap rather than a spent one reusable.
* *A lock for concurrent Evidence archiving.* Leaves the operator serializing
  archiving. Not done because the behaviour is already fail-closed
  (`frontdoor/archive.py:805-820`), the recurrence is one decision per
  parallel pair, and a lock beside a Run's archive step is a new failure mode
  for a documented contract's price.
* *Relaxing the scope-ceiling pin test.* Leaves the ceiling entry and the
  test expectation as one coordinated edit. Not done because the pin is the
  only mechanical guard that a ceiling widening is noticed.
* *A shipped default evidence command.* Leaves the choice with the operator,
  guided by <<o1,O1>>'s rule. Not done because the command must be the
  consumer's own committed gate, which WFC cannot inspect at install time.
* *Any new governance layer, gate class, agent role, program or Phase
  Execution Binding; any temporary scope-ceiling entry; any push, tag,
  publication, external setting or Runtime promotion.* Not in any slice, by
  construction.
