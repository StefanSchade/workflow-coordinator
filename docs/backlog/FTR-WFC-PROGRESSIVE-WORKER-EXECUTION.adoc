== Observed product boundary

`robust@v1` expects a complete first implementation candidate from the Worker
in one `implement` Hop. The Worker reports `completed` (route `broad_review`)
or `blocked`; the later phases (`broad_review`, `correct`, `focused_review`)
are for independent review and correction of a candidate, not for arbitrary
partial implementation. There is no sanctioned way for a Worker to hand over
a plan or a finished part of the work and have a following Worker Hop
continue it before review begins.

This is a limit of the current workflow contract, not a demonstrated WFC bug.

== Evidence

* Two real Runs ended after one Hop with the Terra Worker
  (`codex_cli:gpt-6.1-terra:high`) returning `blocked` and no change:
  `wfc-operator-manual-consolidation-001` (Run
  `RUN-deb3a4f3765346c6ae247488c5efddae`) and
  `wfc-operator-manual-structure-migration-002` (Run
  `RUN-278851ab5c704354a1c4f089d27cd8cd`, a reduced-scope Commission). Both
  Coordinator stops (`awaiting_human`) were contract-conformant: `blocked`
  carries no CommitIntent and the reducer escalates it.
* Synthetic replays outside WFC, in disposable clones, with the prompt
  reconstructed through `assemble_prompt` from the real Run inputs: Terra
  returned `blocked` without any change in 3 of 3 replays; Sol
  (`gpt-6.1-sol:high`) returned `completed` with extensive changes in 2 of 2
  replays, including the reduced-scope task. The Sol results were checked
  formally (CommitIntent equals the changed files, scope, rendering) but not
  reviewed for content quality.
* The concrete internal cause of the Terra behavior remains unexplained. The
  evidence does not isolate the prompt, the sandbox, the task size or missing
  readable inputs as the cause; the model is the remaining observed
  difference. The replays are small samples.

== Idea (hypothesis only)

A Worker could alternatively report one of:

* `planned` -- an executable plan, delivered as a concrete, structured
  handoff for a following Worker Hop;
* `progress` -- a verifiable part of the work already done, plus one
  determinate next step;
* `completed` -- the full candidate; only this leads to independent review.

`planned` would need a concrete structured handoff, not prose intent.
`progress` would need checkable work and a definite next step, so that a
reported state can be told apart from an early stop.

== Open questions this record deliberately does not resolve

* Dynamic result contracts and routes: today the schema's status and
  `requested_route` enums are fixed per phase.
* Plan persistence: where a plan lives, who may change it, and how it is
  bound to the Commission's scope and acceptance criteria.
* Intermediate commits: whether partial progress is committed, and how that
  fits CommitIntent admission, which presently admits a commit only for
  `completed`.
* Recovery: how an interrupted or rejected progress Hop is resumed.
* Evidence of progress: how the Coordinator distinguishes real progress from
  a stall or an early stop.
* Convergence and Hop budget: how a sequence of `planned`/`progress` Hops is
  bounded, and how it interacts with the existing Hop limit.
* Scope boundaries: whether successive Hops may widen or must keep the
  admitted scope.
* Review independence: how the independent review stays independent of a
  multi-Hop implementation history.

== Non-goals (for this record)

This record does not propose a Result schema, a workflow topology or
programme, a release, or an implementation date, and it does not change the
`robust@v1` contract. It also does not claim that `robust@v1` is defective.
It exists to preserve the observation and the idea against loss.

== Practical consequence today

Until something like this exists, a task for `robust@v1` has to fit one
complete Worker candidate. Binding scope is reduced rather than result
semantics weakened, and Worker model choice has been observed to matter in
practice.

== Deferred priority and revisit trigger

Explicitly deferred. Revisit only with recurring concrete evidence beyond the
two Runs and small replay set above, and only after cheaper measures (task
reduction, Worker binding, a clearer statement in the Worker role component of
when `blocked` is legitimate) have been tried and shown insufficient.
