== Thesis

Public internet access -- for research, documentation lookup, dependency
downloads, public APIs, and experimentation -- is a regular capability of
an ordinary development agent, not a privilege requiring case-by-case
justification. WFC must not withhold it through a blanket restriction
merely because that restriction is easy to apply by default.

== Decision

The November 9 Maintainer decision stands: for ordinary WFC operation,
restricting public internet requires justification weighed against its cost
to development quality and productivity. This holds provider-neutrally for
Codex and Claude Code. See
link:../functional_model/workflow_program_use_cases.adoc[Functional Model],
`GOAL-WFC-004` and §3.1. Blanket deny plus approval for each ordinary request
would replace that decision and is not the proposed direction.

[[direction]]
== Bounded direction and alternatives (planning recommendations)

Prefer the smallest provider-supported configuration changes that allow
ordinary noninteractive public access while preserving existing filesystem,
credential, result-validation and Coordinator boundaries. For Codex, evaluate
an explicit workspace-write network override rather than abandoning the
sandbox. For Claude, reconcile tool selection, permissions and Bash network
configuration together; no single deny-list edit is sufficient to cover all
three. Select exact syntax against the chosen CLI's documented/offline
interface before implementation acceptance; current docs alone do not qualify it.

Alternatives assessed:

* Relying only on ambient provider/user defaults avoids a WFC override, but
  does not remove Claude's authored restrictions and leaves Codex behavior
  dependent on unpinned effective configuration. It is insufficient as a
  portable capability claim.
* Provider-supported explicit configuration is the preferred first direction.
  It can correct WFC defaults without new Commission schemas, per-task
  profiles, maintained domain allowlists, proxies or sidecars. A provider
  may internally use a proxy or domain-setting syntax; using its supported
  interface is not a decision to build WFC egress infrastructure.
* A WFC-owned proxy, firewall or outer network mechanism is justified only by
  a concrete unmet capability/protection need and evidence that provider
  configuration cannot meet it. None is established here. Host restrictions
  must be reported to their owner, not bypassed. Blanket deny with per-request
  permissions, full-access mode and disabling provider sandboxing are not
  ordinary-access solutions consistent with the accepted boundaries.

Context-specific constraints remain possible under the existing trust-boundary
FTR's “Independent elevation semantics” and “Information flow and derived
output”. Resolve an independently governed authority envelope and compatible
execution/information boundary before exposing protected context; the worker
cannot grant itself visibility, broader egress or declassification. For public
or bounded ordinary work, no new per-request approval is implied. A concrete
sensitive workload may justify narrower egress or a different execution binding,
without making that restriction the ordinary default. This plan adds no DLP,
classification lattice, information-flow engine, credential broker or governance
layer. Provider credential protection remains sufficient for ordinary product
scope by the trust-boundary FTR's November 9 decision; that is a scope decision,
not proof of absolute credential security.
