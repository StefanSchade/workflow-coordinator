== Verdict

*MATERIAL_REVISION_REQUIRED.*

The decomposition is right. Separating workflow function from domain persona
from execution binding is the correct cut, the closed two-role vocabulary is an
appropriate MVP restriction rather than a premature framework, and the
record's current-state reconstruction is accurate in every load-bearing
particular this review could test. Nothing here is a reason to reject the
direction, and nothing here asks for a registry, router, inheritance, plugin
system, or CLI redesign.

Three architectural decisions must nevertheless be settled in the record before
implementation. Each is cheap -- a versioned contract revision, one seam
sentence, one corrected mechanism claim -- but each is a decision, not a
detail, and each is materially harder to retrofit than to state now.

. The record's central safety claim rests on an Agent Operating Contract
  precedence clause that does not actually cover persona text, and the proposed
  prompt changes require a contract revision the record never mentions (F-I1).
. Keying both persona and execution binding by workflow role quietly removes
  the design freedom that the deferred elevated-privilege concept needs, and
  creates pressure toward exactly the third workflow role this record forbids
  (F-I2).
. `operator-plan.json` is described as "the Run pin". It is write-only in
  production; nothing reads it. The pin is process-local immutability, and the
  distinction becomes load-bearing the moment a resume path exists (F-I3).

Finding counts: BLOCKING 0, IMPORTANT 3, MINOR 5, INFO 7.

== 1. Current-state accuracy

The reconstruction is accurate. Each claim below was verified independently.

*`developer` has no hidden semantic meaning.* `grep -rn developer src/` returns
nothing. `Phase.role` is an unconstrained `str` (`model.py:141`) accepted by
`_string()` (`serialization.py:596`), copied into `Hop` (`vertical.py:286`),
persisted on `HopSummary` (`model.py:245,263`), and projected into checkpoints
(`persistence.py:195`). `reducer.py` imports neither `Phase` nor `WorkItem` and
contains no `role` reference at all. The `developer` meaning is exactly
configuration plus one prompt file: `standalone-development-profile.yaml:6,51`
assigns the role, `components.yaml:3` maps the component to
`prompts/developer.txt`, and that file says "Implement the bounded task within
the current phase scope." The record's characterization is exact.

*Phase/component role representation.* As described. Note the profile already
uses component ID `reviewer` under role `independent_reviewer`
(`standalone-development-profile.yaml:25-27`): component IDs and role names are
already decoupled in production, which the record does not observe (see F-M4).

*Codex adapter selection.* `slice4.py:177`, `execution_port = adapter or
CodexCliAdapter(run_root, executable=executable)`, with the injected value
reserved for tests. `run_serial_hops()` threads one optional `adapter` through
every Hop (`operator.py:512`), so there is no role-sensitive selection today.
`--executable` (`operator.py:199`) is the executable only. Accurate.

*Model and reasoning defaults.* `CodexCliAdapter` dataclass defaults
`model="gpt-5.6-terra"` and `reasoning_effort="medium"`
(`codex_adapter.py:140-143`), projected as `--model` and
`-c model_reasoning_effort=` in `argv()`. `codex_adapter_smoke.py:217-218`
duplicates both defaults on its own argparse surface; `operator.py` exposes
neither. Accurate.

*Evidence recording.* `_execution_binding()` (`operator.py:450-459`) introspects
or reconstructs an adapter purely to describe it; `_execution_evidence()`
(`operator.py:493`) merges that dict into the per-attempt row, published as
`execution-evidence.json` schema 2. The described duplication is real and
slightly worse than stated: on the production path `adapter is None`, so
`_execution_binding` builds `CodexCliAdapter(Path("."))` while `slice4.py:177`
independently builds `CodexCliAdapter(run_root, ...)`. Two objects, agreeing
only because they share dataclass defaults. The record's insistence that
evidence be emitted from the same object that instantiates the adapter is
correct and is the single best mechanical improvement in the proposal.

*Operator plan.* `operator.py:685-698` writes `operator-plan.json` before
`register_checkout()` and before any dispatch, carrying inputs, pinned
revision, component digests, durable artifacts, `executable`,
`timeout_seconds`, `max_autonomous_hops`, `retry`, contract provenance,
`governing_inputs`, and the prepared evidence plan -- and no model or
reasoning. Accurate. Its authority status is weaker than the record implies;
see F-I3.

*Contradicting assumptions.* None found. `run.json` is written pre-dispatch
(`slice4.py:174`) before `dispatch.json` and before adapter construction, so
current phase is durably recoverable, which is what the proposed reconstruction
argument needs.

Two material gaps in the migration inventory and one overstatement about the
operating contract are recorded as F-M1 and F-M5.

== 2. Workflow role model

*`worker` and `independent_reviewer` are workflow function, not expertise.*
Correct, and the record's stated reason -- that the closed vocabulary exists
precisely to stop `software architect` or `Latin lector` being smuggled into
topology -- is the right justification.

Adversarial checks, all passing against current code:

* *Reducer semantics do not depend on the literal names.* `reducer.py` never
  reads `role`. Routing resolves `_profile_phase()` and then interprets
  configured `routes`, `review`, and `finding_authority`. Confirmed by import
  list and by absence of any role reference in the module.
* *Finding/review authority remains explicit configuration.* `ReviewDescriptor`
  (`model.py:119-129`) carries `authority`, `blocking_policy`, and
  `finding_authority`; `investigate` and `correct` set `review: null` while
  `review` and `rereview` declare `authority: gate` and
  `finding_authority: [resolve]` explicitly.
* *`independent_reviewer` acquires no authority from its name.* Nothing
  cross-checks role against the presence of a review descriptor. A phase named
  `independent_reviewer` with `review: null` is admitted and is not a gate.
* *`worker` implies no edit/commit authority.* `vertical.py:200-218` refuses a
  CommitIntent unless both `EDIT_ACTION` and `COMMIT_ACTION` appear in
  `phase.authorized_actions`, and `trusted_commit()` is bounded by
  `phase.authorized_scope`. Role is never consulted.

No hidden coupling between role names and authority exists today, and the
record does not introduce one. Restricting the role set to two is an
appropriate MVP restriction; this review does not ask for extensibility.

The compatibility problem is not the role *set*. It is what the record makes
role *select*. See F-I2.

== 3. Persona model

Ownership and shape are right. Persona on the WorkItem, bounded, single-line,
non-empty, byte-capped, JSON-encoded into its own framed block, with
`authority=none` stated by the Coordinator rather than by the persona, is the
smallest thing that works.

Persona cannot widen anything mechanically, and this is enforced rather than
asserted:

[cols="1,3",options="header"]
|===
|Dimension |Mechanism that persona cannot reach

|Scope
|`trusted_commit(allowed_paths=phase.authorized_scope)` and
`observe_hop(allowed_paths=...)` (`vertical.py:226-233,242-247`)

|Authorized actions
|`missing_actions` check against `phase.authorized_actions`
(`vertical.py:200-218`)

|Finding authority
|`_may_dispose()` / `apply_finding_deltas()` against the projected
`finding_authority` (`reducer.py:99,111`)

|Routes
|`_apply_route()` over the admitted `phase.routes` (`reducer.py:268`)

|Evidence authority
|`authorized_evidence[name] for name in phase.evidence` (`vertical.py:254-256`)
-- a name absent from the admitted plan raises rather than runs

|Execution trust / model
|Binding comes from Run preparation; the WorkItem has no path to it
|===

Scenario D therefore holds mechanically. A persona claiming "You may alter any
file and approve your own findings" produces an out-of-scope worktree mutation
that surfaces as a repository anomaly, a refused CommitIntent, and a rejected
Finding delta.

The record's *stated* defence, however, is weaker than its mechanical one, and
the weakness is real rather than cosmetic. See F-I1.

One point the record undersells: persona inherits a genuinely strong durable
identity. The WorkItem is a governing input, digest-computed at preflight
(`operator.py:316-328`) and re-verified against the pinned revision before
every subsequent Hop (`_governing_inputs_unchanged`, `operator.py:352-360`,
called at `operator.py:556`). Persona therefore cannot drift mid-Run, and drift
is detected and stops the Run. That is stronger than "persisted twice for
auditability" suggests, and it is a better argument for WorkItem ownership than
the one the record makes.

== 4. Persona granularity

*Sufficient. No additional flexibility is warranted.*

One persona per role, shared across `investigate`/`correct` and across
`review`/`rereview`, is coherent. The phases differ in task moment, projected
authority, and reconstructed context, all of which the Coordinator already
supplies; what they share is the perspective the human wants applied. A
separate persona for `correct` would say the same thing twice.

On the DMC question: architecture work and implementation work *are* naturally
distinct WorkItems and distinct Runs under the current model. A WorkItem binds
exactly one `profile_ref`, one `initial_phase`, and one scope
(`model.py:86-97`), and `new_run()` (`model.py:373`) derives the Run from it.
Scenarios A and B in the record are already written as separate Runs with
separate personas and separate bindings. No near-term scenario requires two
different worker personas inside one Run.

No registry, inheritance, stack, or phase-level persona configuration is
needed, and this review does not ask for the deferred phase-override mechanism
to be built. The record's "do not build that mechanism before such a case
exists" is the correct disposition.

== 5. Latin / non-development test

*Genuinely supported at the engine level, with one honest residue.*

Separating generic engine issues from consumer configuration:

*Consumer configuration, correctly out of scope.* `role: developer`, the
`developer` component, `evidence: [pytest]`, the software-shaped
`authorized_scope` lists, and every `developer-ergonomics` WorkItem live in
`governance/self-development/` and `governance/work-items/`. A Latin consumer
supplies its own. None of this is engine semantics.

*Engine, and genuinely neutral.* The reducer knows Outcomes, routes, Findings,
review authority, and mechanical facts -- no domain vocabulary. Phase names are
never branched on. `serialization.py` validates shapes, not subjects.
`_CONVENTIONAL_SUBJECT` (`git_facts.py:64`) is
`^[a-z][a-z0-9-]*(?:\([^)]+\))?!?: `, an open lowercase type token rather than
a closed `feat|fix|docs` list, so `lectio(unit3): WI-LATIN-001 H002 ...` is
admitted. Git as substrate is accepted per the review mandate.

*Engine, and residually software-flavoured.* Two items, neither blocking:

* The package-owned Agent Operating Contract
  (`resources/agent_operating_contract_v5.txt`) says "implementation work",
  "Agent-side tests and checks", and "public-surface authority". It is injected
  into every prompt and hash-pinned at `prompt.py:20`.
* `ESCALATION_KINDS` (`serialization.py:83-90`) includes `public_surface`, a
  software-API notion in a closed engine-owned enum projected into the provider
  schema (`codex_adapter.py:103`).

Neither carries semantics: no reducer path, route, or authority depends on
them, and a Latin Run that never escalates `public_surface` is unaffected. But
acceptance scenario C states that "the engine requires no `developer`, `code
reviewer`, `pytest`, source-code, or implementation meaning", and the contract
text is engine-owned and does contain implementation and test vocabulary. That
is an overstatement of an otherwise correct conclusion (F-M5), and it lands in
the same place as F-I1: the contract needs a revision anyway.

Conclusion: engine semantics are domain-neutral. The Latin scenario is
supported. Nothing in the candidate blocks it.

== 6. Execution binding model

*The smallest coherent design, with one silent-fallback path to close.*

Verified against current seams:

* *Different models per role.* Achievable. `run_serial_hops()` already holds
  `run.phase`, `profile`, and `checkout_state_root(state_root, association)`,
  so it can resolve role, look up the binding, and construct the adapter per
  Hop rather than threading one.
* *One binding per Hop.* The lookup `phase -> role -> binding` is total once
  the role vocabulary is closed and preflight requires one binding per declared
  role. Total and checkable is precisely what closing the vocabulary buys.
* *No reducer effect.* Confirmed: the binding never reaches `reduce_result()`.
* *No automatic routing implied.* Correct. The mapping is an exact lookup; no
  fallback chain, score, or price appears anywhere in the record.
* *Unsupported adapters fail closed.* The record specifies preflight rejection
  of unknown adapters, roles, and fields before dispatch. Correct as designed.
* *Defaults cannot override the admitted binding.* Only partly. The record
  requires `model` and `reasoning` to be explicit and validated, but
  `CodexCliAdapter` keeps dataclass defaults (`codex_adapter.py:140-143`), so
  a construction path that omits either field silently yields Terra/medium
  rather than failing. Acceptance criterion 6 depends on that not happening.
  See F-M2.

No multi-provider support is requested by this review. Codex-only is the right
MVP boundary and the record's refusal to build a registry is correct.

== 7. Binding ownership and pinning

This is where the record's wording outruns its mechanism.

*What actually makes a binding authoritative today.* Nothing durable.
`operator-plan.json` is written once (`operator.py:698`) and never read: the
only readers in the entire repository are two test assertions
(`tests/unit/test_operator.py:229,323`). There is no production code path that
loads it. Authority over the binding is therefore held by the in-process
immutable object, and `operator-plan.json` is its durable *evidence*.

*Is that sufficient for the MVP?* Yes -- for a precise reason the record does
not give. WFC has no cross-process re-dispatch path. `main()` is one-shot;
`recover_uncertain_dispatch()` (`persistence.py:112`) is called in-process by
`slice4.py`, charges the interrupted Hop, and drives the Run to
`RECONCILE_REQUIRED`; no operator entry point resumes an existing Run. Because
no later process ever re-derives a binding, no later Hop can observe a changed
plan, and mid-Run model change is mechanically impossible rather than merely
discouraged -- provided the configuration source is parsed exactly once at
preflight into an immutable object and never re-read. The record asserts the
property but never names the mechanism that produces it. See F-I3.

*Does the Run model need a binding identity or digest?* *No.* `run.json` is the
semantic Run snapshot consumed by the deterministic core; absorbing a provider
binding into it would put shell configuration into core state for no mechanical
gain, and the core FTR's fourth load-bearing boundary warns against persisted
convenience fields becoming independent truth. The plan already carries the
complete mapping, so a digest would be derivable rather than new information.
The record's decision to keep both new facts out of `run.json` is correct and
should be preserved.

*Composition with Atomic-Hop-Recovery.* That record requires R2 to establish
"unchanged ... relevant execution binding identities" before any same-Hop
retry. The candidate satisfies this today by reconstruction: pre-dispatch
`run.json` gives the phase, the pinned profile gives the role, the plan gives
the binding. Sound. But R1.5 -- the small explicit reconcile/resume operator
path that the recovery record calls a practical MVP -- would be a *second
process re-dispatching an existing Run*, and at that moment the plan must stop
being evidence and start being read, compared, and enforced. The candidate
should say so conditionally now, because it costs one sentence now and a
redesign later.

There is also an asymmetry worth naming. Persona is a repository-tracked
governing input, digest-checked between Hops. The binding arrives on the argv
channel, like `--executable` and `--timeout-seconds`, which an earlier imported
review already recorded as "recorded in `operator-plan.json` but neither pinned
nor drift-checked". That is the correct home for it -- binding must vary per
Run and must not become repository policy -- but the record should state that
the two inputs have deliberately different admission strength rather than
implying both are "pinned" in the same sense.

== 8. Evidence and reproducibility

All six questions are answerable under the proposal.

[cols="2,3",options="header"]
|===
|Question |Answered from

|Which workflow role executed?
|`Hop.role` (already recorded) plus the proposed per-Hop evidence field

|Which persona was projected?
|Pinned WorkItem at the pinned revision, plus the resolved value/digest in the
Hop evidence row

|Which adapter, model, reasoning ran?
|The per-Hop evidence row, emitted from the object that built the adapter

|Was that the binding admitted for this Run?
|Cross-reference: plan mapping, plus phase from `run.json`, plus role from the

The configured/actual distinction is handled correctly, and handled in the only
way that is safe: the persisted evidence is emitted from the resolved binding
object rather than from anything the adapter reports back. The adapter cannot
redefine Coordinator policy by reporting different values because it is never
asked. This closes the existing `_execution_binding` reconstruction split and
is the proposal's strongest mechanical contribution.

The residual gap -- no evidence row when `recover_uncertain(None)` fires,
because `_execution_evidence` is appended only when an outcome exists
(`operator.py:584-596`) -- is correctly identified, correctly attributed to the
Atomic-Hop-Recovery record, and correctly argued not to block DMC, since the
pre-dispatch plan, `run.json`, and dispatch marker still identify the prepared
binding.

Persona durable identity is already provided by WorkItem ownership, more
strongly than the record claims (section 3). No separate persona identity
mechanism is needed.

== 10. Schema and governance ownership

Ownership matches semantics:

* *Profile* owns workflow topology and authority shape, and `Phase.role` is the
  right home for a value the profile alone declares.
* *WorkItem* owns persona: task-varying, human-prepared, already digest-pinned
  and drift-checked as a governing input.
* *Run preparation* owns the binding: Run-varying, authority-free, and
  deliberately not repository policy.

No accidental authority implication arises. Neither persona nor model appears
in any authority predicate, and the record states the negative explicitly for
both. The converse requirement -- that configuration which must stay stable
through the Run has durable authoritative identity -- holds for persona and is
satisfied for the binding only through the process-local argument of F-I3.

One altitude observation, not a demand: adding `personas` to `WorkItem` places
presentation data in `model.py`, the deterministic core. The core FTR already
qualifies that `model.py` "includes repository policy, Git heads and commit
intent, evidence observations, and durable-state records" and is not
infrastructure-agnostic, so this is consistent with the accepted shape. No
change requested (F-N3).

== 11. Prompt semantics

The `[persona_guidance]` boundary is well designed. `source=work_item`,
`authority=none`, and a JSON-encoded single-line value are Coordinator-emitted
framing that the persona cannot forge, and the bound plus JSON encoding
mechanically prevents a persona from opening a counterfeit block header. That
is a genuinely better framing than existing prompt components receive:
`assemble_prompt()` appends `component.content` raw, with no delimiter at all
(`prompt.py:167`).

Two problems.

*The precedence list does not match the assembly it must be built on.* The
record places persona "after the Agent Operating Contract and generic role
component" and lists "persona guidance" before "workflow policy and
task/component content". But `assemble_prompt()` emits *all* selected
components -- role, then modifiers, then repository policy -- in one loop
(`_selected_ids`, `prompt.py:109-111`; loop at `prompt.py:156-168`) before
`[workflow_policy]` and `[task]`. Placing persona immediately after the role
component would split that loop and put persona *ahead of* repository-policy
component text, which is closer to authority than persona is. See F-M3.

*The authority argument names a clause that does not cover persona.* This is
the material one. See F-I1.

No general prompt-template framework is needed, and the record correctly does
not propose one.

== 12. Functional core / effect shell

Clean. Against the core FTR's load-bearing boundaries:

* No provider or model name reaches `reducer.py`; the record forbids it
  explicitly and acceptance criterion 13 tests for it.
* No persona-aware route logic; routes remain configured `Route` records.
* No filesystem or provider effect enters `model.py` or `reducer.py`. A
  `WorkflowRole` enum is a value type of the kind `model.py` already holds
  (`Outcome`, `RunStatus`, `DurableArtifact`, `FindingState`).
* No domain-specific workflow branches. Closing the role vocabulary reduces the
  chance of one by making expertise labels unavailable as topology.

Binding resolution, persona projection, and adapter construction all land in
`operator.py` / `slice4.py` / `prompt.py` -- the shell. The record's
architecture-debt assessment ("the work will touch broad `operator.py`
orchestration, but it does not justify a service-layer or package-reorganization
project") is accurate and matches the core FTR's WATCH disposition. Nothing here
forces architectural debt the record understates.

== 13. Security compatibility

Compatible, and the deferred architecture is not reopened here.

The record does not confuse model choice with trust: the binding grants no
scope, action, route, information, or Finding authority; persona grants nothing;
and the closing paragraph states the one-directional rule -- a future binding
may carry trust facts, a phase or Run may declare requirements, checks fail
closed before dispatch, and an eligible binding "may never expand workflow
authority". That is the correct seam, correctly one-directional, correctly
unimplemented.

The one compatibility defect is structural rather than semantic: the extension
seam is reserved on the binding *value* but not on the binding *key*. A future
trust requirement is a property of a phase, and a role-keyed map cannot express
two differently-trusted phases of the same workflow function. See F-I2.

== 14. CLI and higher loop

*Deferral is sound.* The human higher loop already works exactly as the record
assumes: WorkItems are hand-authored YAML in `governance/work-items/`, and the
operator passes `--work-item`, `--profile`, `--policy`, `--components`,
`--task`, `--expected-head`, `--executable`, `--timeout-seconds`
(`operator.py:186-199`). Adding personas is a WorkItem edit. Adding bindings is
one more argument of the same shape.

Postponing ergonomic CLI work until real DMC usage is the right call, and it is
consistent with the backlog's own `NEXT` item ("Narrow CLI UX evaluation based
on dogfood evidence"). Evidence should drive that, not anticipation.

== 15. Implementation slicing

Slice 1 is close to the correct minimum. Testing it against "what is the
smallest implementation that lets us run a real DMC WorkItem with separate
worker/reviewer models and a domain persona?":

*Necessary and present.* Closing and migrating the role vocabulary (without it
the role-keyed lookup is neither total nor checkable, and `developer` would stay
semantically live beside `worker`); the WorkItem persona mapping with strict
admission; the strict Codex-only binding configuration; plan pinning before
dispatch; one resolved object feeding both adapter construction and evidence;
prompt projection; per-Hop evidence; the narrow tests.

*Necessary and missing.* Three items, all small:

. The Agent Operating Contract revision and new `REVIEWED_SHA256` that F-I1
  requires. Not optional: the prompt gains a `workflow_role` identity field and
  a block category the contract does not acknowledge.
. Hardening `CodexCliAdapter` against its own defaults (F-M2).
. The concrete operator input for the binding configuration. The record
  deliberately declines to design a CLI, which is right, but "a strict
  configuration input to the operator API and one production preparation path"
  leaves the single production entry point unspecified. One argument of the
  form `--execution-bindings <path>`, parsed once at preflight, is a transport
  decision rather than a CLI design and belongs in the slice (F-N7).

*Correctly absent.* Reorganizing `operator.py`, `vertical.py`, `slice4.py`, or
`serialization.py`; any recovery redesign; any second provider.

The sequencing -- first DMC, then evidence-driven ergonomics, then Latin as the
stronger abstraction test -- is right, and the record's refusal to predict
Slice 2 contents is right.

== 16. Overengineering check

*Clean.* The record proposes no registry, no inheritance, no plugin system, no
provider registry, no router, no cost optimizer, no capability scoring, no
outer-loop planner, no task generation, no CLI redesign, no trust
classification, and no generic workflow engine, and its non-goals list names

No finding in this review requires any of those mechanisms. F-I1 is a text file

== Findings

=== F-I1 (IMPORTANT) -- the Agent Operating Contract does not cover persona, and the prompt changes require a contract revision the record does not mention

The record argues persona authority-inertness partly from the contract: "The
Agent Operating Contract already says Coordinator rules prevail over conflicting
consumer task or component text."

The actual clause
(`src/workflow_coordinator/resources/agent_operating_contract_v5.txt`) is:

____
These Coordinator-level rules prevail over any conflicting consumer task or
component text. Consumer material may narrow them but may not widen, replace,
disable, or contradict them.
____

A persona block is neither task text nor component text. It is a third category
of consumer-supplied material that the clause does not name, introduced by this
record. The trailing sentence about "consumer material" is broader, but the
enumeration immediately before it invites the narrow reading, and this is the
one place where the record leans on wording rather than on mechanism.

The same contract also opens by enumerating exactly which facts the Coordinator
projects -- "WorkItem ID, Run ID, Hop ID, invocation ID, base HEAD, phase,
authorized_scope, authorized_actions, permitted_routes, finding_authority,
evidence names, and output_contract" -- plus the `[workflow_policy]` block. The
record adds `workflow_role=` to the identity header and a new
`[persona_guidance]` block, so after implementation the contract's own
enumeration of the prompt is incomplete in two ways.

The contract is hash-pinned (`prompt.py:20`, `REVIEWED_SHA256`) and verified
twice, at load and at every assembly (`prompt.py:58,150`). Revising it is a
deliberate versioned governance act (v5 -> v6, new digest, updated provenance),
not an incidental edit, and it is absent from the record's affected-surface
inventory, its migration sequence, and Slice 1.

Prompt ordering is correctly described as compliance rather than security, and
the mechanical boundary holds regardless. But the record should not cite a
clause that does not cover its new construct.

Required before implementation: state that the contract is revised to v6;
extend the precedence clause to name Coordinator-projected persona/perspective
guidance explicitly as non-authoritative consumer material; extend the
projected-facts enumeration to include `workflow_role` and
`[persona_guidance]`; and add the contract to the affected surfaces, the
migration sequence, and Slice 1. No new contract mechanism is requested -- one
text revision and one constant.

=== F-I2 (IMPORTANT) -- keying both persona and binding by workflow role forecloses the elevated-privilege design space and creates pressure toward a third role

The record separates three concepts and then makes two of them functions of the
third:

----
workflow role -> persona
workflow role -> execution binding
----

For the two near-term consumers this is exactly right, and this review does not
ask for it to change in the MVP.

The problem is compatibility with `FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW`,
which the mandate requires be kept possible.

*The two-role set itself is fine.* Elevated-privilege work can remain
`role: worker` with different admitted `authorized_scope` / `authorized_actions`
and, later, a different execution boundary; mandatory defensive review can
remain `role: independent_reviewer` with its own review descriptor,
`finding_authority`, and route topology. Current `routes` are per-phase and
explicit, so `elevated_work -> defensive_review` with no bypass route is
expressible today. No third workflow *function* is mechanically necessary. The
record's claim on that point survives.

*The binding key is not fine.* Both the elevated-privilege record and the
execution-trust record anticipate that elevated or protected work needs a
different execution boundary: "The Workflow Coordinator should know the
authority granted to a phase and the selected execution boundary should enforce
it"; "delegate that subproblem to a bounded execution binding compatible with
the information"; and the open question "Do elevated phases require a distinct
provider or model policy?".

Under a role-keyed map, two `worker` phases in one Run necessarily share one
binding and one persona. An ordinary worker phase and an elevated worker phase
in the same Run cannot be bound differently. The designer then faces exactly
two options: declare a third workflow role such as `elevated_worker` -- the
outcome this record forbids and the mandate asks about -- or re-key the map.
The candidate does not make a third role necessary today, but it builds the
gradient that produces one.

The deeper point is that the record's own decomposition argues against its key.
Workflow function answers "what does this phase do in the workflow"; execution
binding answers "under what execution configuration and, later, what trust
boundary does it run". Those are independent questions, and the MVP happens to
have a one-to-one mapping between them. Encoding a coincidence as the schema is
what makes the future case awkward.

Required before implementation: state in the record that the binding map is
keyed by workflow role *as an explicit MVP simplification*, that the general key
is the phase's execution-binding selector which defaults to its workflow role,
and that a future elevated or protected phase needing a distinct binding must be
able to declare that selector without introducing a third workflow role. Same
sentence for persona.

No mechanism is requested now: no selector field, no per-phase configuration, no
trust fields. One recorded sentence, so the future concept is not designed into
a corner. The migration is additive if stated and a schema fight if not.

=== F-I3 (IMPORTANT) -- `operator-plan.json` is described as the Run pin but is write-only; the real mechanism is process-local immutability

The record states: "The complete mapping is pinned before the first dispatch and
cannot change during the Run", "That persisted plan is the Run pin", and "A
model/reasoning change after Run creation requires a new explicitly prepared
Run ... it is never an implicit mid-Run switch."

The conclusions are true today. The stated mechanism is not.

`operator-plan.json` is written at `operator.py:698` and read by nothing in
production. The only readers in the repository are `tests/unit/test_operator.py`
at lines 229 and 323. A file that is never read cannot pin anything; it is
durable evidence of a decision made elsewhere.

What actually prevents mid-Run change is that WFC is one-shot and single-process:
`main()` prepares, dispatches serially, and exits; there is no operator entry
point that loads an existing Run and re-dispatches it. If the binding
configuration is parsed once during `_preflight()` into an immutable object and
that object is the sole source for every Hop's adapter construction, mid-Run
change is mechanically impossible. If instead the implementation re-reads the
configuration file per Hop -- which nothing in the record forbids -- the
property silently disappears, because unlike the WorkItem the binding file is
not a governing input and gets no `_governing_inputs_unchanged` drift check
(`operator.py:352-360,556`).

This also determines how the design composes with Atomic-Hop-Recovery. Today
the composition works by reconstruction: pre-dispatch `run.json`
(`slice4.py:174`) gives the phase, the pinned profile gives the role, the plan
gives the binding. But that record's R1.5 -- the small explicit reconcile/resume
operator path it calls a practical MVP -- would be a second process
re-dispatching an existing Run. At that point the plan must become an input that
is read, compared, and enforced, and a resume that cannot reproduce the
originally admitted binding must refuse rather than re-derive one from current
configuration.

Required before implementation: state that the binding configuration is parsed
exactly once at preflight into an immutable object, that this object is the sole
source for adapter construction and evidence, and that the source is never
re-read during the Run; describe `operator-plan.json` as the durable record of
that admitted object rather than as the enforcing pin; and state the conditional
that any future resume path must read the recorded binding and fail closed
rather than re-derive one.

No duplicative persistence is requested. No Run-level digest is requested; the
plan already carries the full mapping and `run.json` should stay free of it.

=== F-M1 (MINOR) -- the migration inventory misses two live phase-role labels and does not state that `Hop.role` stays open

The record lists the open role labels to normalize as `implementer`, `reviewer`,
`observer`, `investigator`, `corrector`, and `independent_rereviewer`. Two more
live *phase* roles exist and will fail admission under a closed enum:
`role: prepare` and `role: verify` in the two-Hop operator fixture
(`tests/unit/test_operator.py:613,623`).

Separately, `tests/architecture/test_replays.py` passes Hop-role labels
`"delta reviewer"`, `"routing supervisor"`, `"independent reviewer"`,
`"formal reviewer"`, and `"corrector"` (lines 60, 95, 100, 104, 167, 173, 187,
193). These are `Hop.role` values, not phase roles. They stay legal only if
`Hop.role` remains an open `str` -- which the record implicitly requires anyway,
since `persistence.py:140` records the synthetic `uncertain_dispatch` label
there. The record handles `uncertain_dispatch` but never states the general rule.

Suggested: add `prepare` and `verify` to the normalization list, and state
explicitly that `WorkflowRole` constrains `Phase.role` only, while `Hop.role`
remains an open recorded string so coordinator-authored trace labels stay
representable.

=== F-M2 (MINOR) -- `CodexCliAdapter` dataclass defaults are a silent fallback under the new binding

`codex_adapter.py:140-143` gives `model` and `reasoning_effort` dataclass
defaults of `"gpt-5.6-terra"` and `"medium"`. Under the new design, a
construction path that omits either field silently produces those values instead
of failing, and the resulting evidence row would truthfully record a binding the
human never admitted.

Preflight validation is the primary control and the record specifies it. But
acceptance criterion 6 ("an unknown adapter or incomplete binding fails before
dispatch") deserves defense in depth at the boundary that actually builds the
argv.

Suggested: make `model` and `reasoning_effort` required constructor arguments
so an incomplete binding is a construction error rather than a silent Terra/medium
invocation. `codex_adapter_smoke.py:99-100,217-218` keeps its own argparse
defaults and is unaffected as a separate surface.

=== F-M3 (MINOR) -- the stated prompt precedence does not match `assemble_prompt()`'s block order

The record places persona "after the Agent Operating Contract and generic role
component" and orders "persona guidance" before "workflow policy and
task/component content".

`assemble_prompt()` emits all selected components in one loop in the order role,
modifiers, repository policy (`_selected_ids`, `prompt.py:109-111`; loop at
`prompt.py:156-168`), then `[workflow_policy]`, then `[task]`, then `[context]`,
then optional `[diff]`, then `[result_output_contract]`. Placing persona
immediately after the role component requires splitting that loop and places
persona ahead of repository-policy component text, which is closer to authority
than persona is.

Suggested: place `[persona_guidance]` after the complete component loop and
before `[workflow_policy]`, and restate the precedence list to match -- identity,
contract, all selected components (role, modifiers, repository policy), persona
guidance, workflow policy, task, context, diff, result contract. One insertion
point, no loop surgery.

=== F-M4 (MINOR) -- migration step 3 re-couples component ID to role name, against existing evidence that they are independent

The profile assigns `role: independent_reviewer` while selecting component
`reviewer` (`standalone-development-profile.yaml:25-27`). Component IDs and role
names are already decoupled in production, and the record itself relies on that
decoupling when it argues that prompt presentation is a separate concern from
workflow function.

Migration step 3 renames the `developer` component to `worker` and
`prompts/developer.txt` to `prompts/worker.txt`, which re-couples the two for
one role while leaving the other decoupled -- an inconsistency a later reader
will try to "fix" in the wrong direction.

Suggested: keep the rename (the old name must go), but state that the match
between component ID and role name is incidental, that component IDs are free
consumer identifiers, and that nothing resolves a component from a role name.
Acceptance criterion 2 already forbids only `developer`, so `reviewer` may
correctly stay as it is.

=== F-M5 (MINOR) -- the Latin neutrality claim overstates the engine-owned contract text

Acceptance scenario C states the engine "requires no `developer`, `code
reviewer`, `pytest`, source-code, or implementation meaning". The package-owned
Agent Operating Contract is engine-owned and contains "implementation work",
"Agent-side tests and checks", "Agent-reported validation or test results", and
"public-surface authority"; `ESCALATION_KINDS` (`serialization.py:83-90`)
contains `public_surface`.

None of this carries semantics -- no reducer path, route, or authority depends on
any of it, and the conclusion that engine semantics are domain-neutral is
correct. But the claim as written is falsifiable by reading one engine-owned
resource.

Suggested: narrow the claim to engine *semantics* and note the residual
software-culture vocabulary in the contract text and escalation enum as accepted,
non-semantic residue. Since F-I1 already requires a v6 contract revision, the
wording could be generalized opportunistically ("checks and validation" for
"tests"); this is not required and should not expand the slice.

=== F-N2 (INFO) -- persona and binding have deliberately different admission strength; say so

Persona rides the WorkItem, a repository-tracked governing input, digest-computed

This asymmetry is correct -- binding must vary per Run and must not become

=== F-N6 (INFO) -- no Run-level binding digest is required

Answering the mandate's question directly: none. The plan carries the complete
mapping, so a digest would be derived rather than new; `run.json` is the semantic
core snapshot and should not absorb shell configuration; and there is no
cross-process re-dispatch path for a digest to guard. The record's decision to

Should Atomic-Hop-Recovery R1.5 ever introduce resume, a binding digest in the

=== F-N7 (INFO) -- name the production transport for the binding configuration

Slice 1 requires "a strict Run execution configuration" and the record declines
to design a CLI, which is right. But `main()` is the only production preparation
path, and it is argparse-driven (`operator.py:186-199`). One argument of the
existing shape -- `--execution-bindings <path>`, resolved and parsed once in
`_preflight()` -- is a transport decision rather than a CLI design, and naming it
removes the only ambiguity in an otherwise precise slice. Whether a later
ergonomic surface uses a preset, a default location, or something else remains
open, as the record says, provided it produces the same admitted immutable
object.

== Summary of required revisions

Before implementation, the record should:

. acknowledge the Agent Operating Contract as an affected surface, revise it to
  v6 with a new `REVIEWED_SHA256`, extend its precedence clause to name persona
  guidance, extend its projected-facts enumeration to cover `workflow_role` and
  `[persona_guidance]`, and add this to the migration sequence and Slice 1
  (F-I1);
. state that role is the MVP binding/persona key by explicit simplification, and
  that a future elevated or protected phase must be able to declare a distinct
  execution-binding selector without a third workflow role (F-I2);
. state the parse-once immutability invariant, describe `operator-plan.json` as
  the durable record rather than the enforcing pin, and record the conditional
  obligation on any future resume path (F-I3).

The five MINOR findings are cheap corrections of inventory, defaults, ordering,
and two overstated claims. The seven INFO observations may be adopted or left
standing; none changes a disposition.

== Final statement

Commit `3a172c42d92bd55e00e9d96a5ae1c28b1b7069b8` establishes the right
decomposition. Workflow function, domain persona, and execution binding are
genuinely independent concerns, the record separates them correctly, keeps all
three out of the deterministic core, and refuses every framework it could have
reached for. The current-state reconstruction is accurate. The persona-authority
attack fails mechanically. The Latin scenario is supported by engine semantics
rather than by assertion. The no-alias migration is right for a project with no
live Run state. The single best mechanical contribution is requiring that
execution evidence be emitted from the same resolved object that instantiates
the adapter, which closes a real existing duplication in `_execution_binding`.

The strongest remaining concern is F-I2: the record separates three concepts and
then keys two of them by the third, encoding an MVP coincidence as schema and
building pressure toward the third workflow role it explicitly forbids. It costs
one sentence now.

This review made no WFC, provider, Runtime, Run-state, governance, profile,
policy, test, or remote mutation, and changed no file other than this review
artifact.
