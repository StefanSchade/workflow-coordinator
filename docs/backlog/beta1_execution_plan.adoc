=== What the 2026-11-18 decisions already settle

* *Program set:* `simple@v1` and `robust@v1` only; `direct@v1` withheld
  (closes the second-pass review's Q7).
* *Guidance binding:* consumer guidance is a binding into the frozen
  `repository_policy` slot, not a program revision (closes Q2).
* *Bindings separate from the Commission:* the readiness review's C1 is
  adopted -- model/adapter/reasoning selection is execution configuration,
  never part of the committed Commission (closes Q4: no).
* *Unattended lifecycle is the normal case:* one confirmation, `--yes`
  first-class, no prompt from authorization through archive (closes Q1,
  adopts C2).
* *`wfc plan` runs no project command; the probe follows authorization*
  (adopts C3's placement, not its every mechanism).
* *Evidence default:* a separate Git-backed Evidence repository with a
  sanitized audit projection and a local-raw option is preferred (answers
  Q3's default; exact retention/projection fields remain open, see
  <<decision-gates>>).
* *Preservation is a requirement, recovery is not:* automatic,
  non-authoritative candidate preservation on a regular stop is required;
  full crash supervision is not. This is addressed below as a bounded
  version of C5 that does *not* depend on C4.

[[preservation-gate-status]]
* *That "required" settles the feature's scope, not its `0.1.0b1` gate
  status, and this plan does not silently pick the stricter reading:*
  `_open.adoc` (the sole priority/readiness authority this plan names at
  <<basis>>) classifies automatic candidate preservation as "a Beta-1
  *candidate*, with design/acceptance still open" -- a readiness
  classification the epic's "requirement" language above does not itself
  override. This plan follows the epic for BP4's own *scope*
  (`preserve_candidate` is built as part of BP4, per the bounded
  recommendation below), but whether a failed or incomplete
  preserved-candidate-ref case actually blocks the `0.1.0b1` tag is a
  separate question `_open.adoc` leaves open. DG-6 below gives the
  maintainer that gate-status choice explicitly, before BP4 starts, rather
  than this plan resolving it through BP4's acceptance wording alone.
* *No mandatory comprehensive supervisor/subreaper:* the readiness review's
  C4 (host process, subreaper, six-case classifier, `wfc stop`) and its
  "mandatory BP4a dependency" are *superseded for Beta 1*. BP4 below is
  therefore R2's original controller, corrected by C1–C3, not R3's BP4a/BP4b
  split.
* *Continuation stays manual in Beta 1:* C6 and `wfc continue` (RP1) are a
  fast-follow, not a Beta-1 package; no lineage block, no adoption command
  and no new review-entry phase are commissioned here.
* *Claude:* operationally proven in successful Runs; exactly one targeted
  qualification remains open (a positive new-directory write and WFC
  candidate acceptance under the current Runtime). The former negative
  (preventive-isolation) criterion is superseded. This plan does not invent
  a second Claude qualification; see BP9 below.
* *Execution-boundary integration* (provider-independent preventive
  isolation) is explicitly post Beta 1 and is not a BP1–BP9 deliverable.

=== Access verified versus inaccessible

This checkout contains the Development repository only. The "sibling
`workflow-coordinator-run-evidence` archiver" the task names is a *separate*
Git repository (the Evidence repository); it is not present in this sandbox.
What was actually inspected: `scripts/wfc_op.py`'s `cmd_archive` (lines
1149–1234) and `_invoke_canonical_archive`, which is a thin, deterministic
wrapper that runs `<evidence>/scripts/wfc-archive-run <state> <evidence>
[--dry-run]` and parses its own printed report lines; and the second-pass
review's citation of that repository's `scripts/archive_run.py`,
`scripts/wfc-archive-run`, `tests/test_archive_helpers.py` and
`tests/test_wfc_archive_run.py` (61 tests) as the archiver's actual
implementation and conformance suite. Neither file's contents nor the cited
tests could be read from here. BP5 below states this as a concrete
prerequisite for its own implementer -- who needs that repository checked
out locally, exactly as `scripts/wfc_op.py`'s own tests already require it
operationally -- not as a gap this plan papers over.

[[conventions]]
== Commission-authoring convention used below

Each entry recommends the content of a future Commission's `task.md`,
`profile.yaml` and `work-item.yaml`; it is not one. Stable IDs follow
`wfc-beta1-<bp>-<slug>-001`, matching the lower-case, hyphenated style of
existing `governance/commissions/*` directories. "Predecessor" means the
Commission whose *independent acceptance* (review plus passing Coordinator
`task-check`) is the actual prerequisite, per link:README.adoc[the backlog
upkeep convention] -- not merely its Hop having run. All Commissions below
execute, as every current BUG/FTR correction does, through the *existing*
self-development route (`scripts/wfc_op.py` and the current governance
profiles); BP1–BP6, BP8 and BP9 build the replacement without yet using it.
Only BP7 switches self-development itself onto the new path.

=== BP5 -- `wfc-beta1-bp5-archive-port-001`

Goal/deliverable:: The canonical archiver as an installed, byte-compatible,
retry-safe `wfc archive` capability, ported from the Evidence repository's
own implementation rather than reimplemented.
Modules/paths:: `frontdoor/archive.py`; `wfc archive`; staging and atomic
placement; idempotent retry; the narrowed cleanliness rule the second-pass
review specifies.
Excluded scope:: No projection/retention design (BP6); no change to the
Evidence repository's own `scripts/archive_run.py` or
`scripts/wfc-archive-run`, which remain the source of truth this port must
match.
Prerequisites/predecessors:: `wfc-beta1-bp1-packaging-identity-001` accepted
is sufficient to *start* -- porting the 61 Evidence-repository tests,
staging and the equivalence test can proceed in parallel with BP2a/BP2b/BP3.
But per `_open.adoc` ("BP5 archive port can start from BP1; its commit
wiring needs BP3's primitive"), the epic's identical dependency line, and
the second-pass review's own port step 3 ("Port the wrapper's probes and
commit to Python on `bounded_path_commit`"), this Commission's *own*
acceptance -- the copy-to-commit retry producing exactly one commit --
cannot close until `wfc-beta1-bp3-init-plan-commit-001` is independently
accepted, since that is where `git_facts.bounded_path_commit` is built. BP5
therefore starts alongside BP2a/BP2b/BP3 but finishes after BP3.
Controlling BUG/FTR:: None dedicated -- the epic states explicitly that
"no separate active BUG/FTR owns this port; do not create a duplicate
issue."
Acceptance:: An equivalence test passes on a real retained Run: archiving
the same STATE root with the old `scripts/wfc_op.py cmd_archive` path and
with the new module into two temporary Evidence repositories produces
identical `copied_files` digests and facts (ignoring `archived_at`). A
retry after a kill between copy and commit produces exactly one commit with
identical content; a second archive of the same attempt is a no-op.
Tests/evidence:: The ported Evidence-repository conformance tests (61 per
the second-pass review's count) now driving the new module, plus the
equivalence and retry tests above.
Risks:: *A semantic change smuggled into the port* is the named risk in
the second-pass review; the equivalence test is the guard, not code review
alone. *Operational prerequisite:* this Commission's implementer needs the
`workflow-coordinator-run-evidence` repository checked out locally to port
and run its tests -- confirm that access is actually available before
authorizing this Commission; if it is not, this Commission stops on that
concrete prerequisite rather than silently porting a smaller, invented test
set.
Decision gates:: None.

=== BP4 -- `wfc-beta1-bp4-lifecycle-controller-001`

Goal/deliverable:: `wfc run` from authorized request to terminal Run,
restartable at every step but launch, ending at `terminal` with no archive
yet (BP6 wires archive in). Adopts C1 (two-digest authorization over
Commission and envelope), C2 (unattended normal case, `--yes`,
pre-authorization checks) and C3's placement (probe runs once, after
authorization, on the clean baseline). Does *not* include the readiness
review's C4 host/subreaper/six-case classifier or `wfc stop`, which the
epic supersedes as mandatory for Beta 1; does not include C6/lineage.
Modules/paths:: `frontdoor/lifecycle.py`, `frontdoor/envelope.py`; `run`,
`resume`, `status`; journal and step functions; engine subprocess launch,
lock and detachment exactly as today (no new host process); same-repository
refusal; active-lifecycle pointer; `git_facts.preserve_candidate`
(bounded version of C5, below).
Excluded scope:: Any supervising host process, subreaper, or completion
record beyond what the engine and its existing lock already provide; any
`wfc stop` command; any lineage block, `--continues` or `wfc continue`.
Prerequisites/predecessors:: `wfc-beta1-bp3-init-plan-commit-001` accepted.
Controlling BUG/FTR:: link:BUG-WFC-OPERATOR-PREPARE-EXECUTABLE-VALIDATION.adoc[Executable
validation before `PREPARED`]; link:BUG-WFC-EVIDENCE-COMMAND-RESOLUTION-DIAGNOSTICS.adoc[executable-resolution
diagnostics]; link:BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[timeout
diagnostics] (all three are usability candidates folded into this
Commission's acceptance, not independently re-opened); link:FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[same-Run
recovery] (explicitly *not* in scope; this Commission classifies an
interruption, it does not resume the interrupted Run itself).
Bounded technical recommendation for preservation without C4:: Capture a
candidate only when the engine's own lock is free and the journal shows
either a clean terminal summary or an interruption at a recorded step
boundary -- the same facts R2's original design already classifies as
"interrupted" -- *without* claiming the host's `attested` quiescence the
readiness review introduces. Label the preservation record's quiescence
source `unattested` in this case. This matches the epic's own instruction
("practical preservation without full recovery") and must be stated in the
Operator Manual's recovery chapter as an explicit limitation at the point
of implementation: a provider process that outlives the engine could still
be writing when the candidate is captured; Beta 1 does not detect this.
Acceptance:: The second-pass review's acceptance scenario up to the
terminal state passes in a neutral fixture with a fake provider, including
a refusal-before-launch case and an engine-killed-mid-Hop case that ends
`interrupted` with a preserved candidate ref and an untouched working tree;
no `pip` invocation occurs anywhere in the path; a scripted non-terminal
`--yes` Run reaches a terminal state with no further prompt.
Tests/evidence:: A completed Run and an `awaiting_human` Run with the fake
provider; a crash-injection matrix killing the controller after each step
boundary, asserting `resume` reaches the same end state with exactly one
Commission commit and exactly one engine launch; a changed package identity
or provider binary between authorization and launch is refused; the
preservation predicates (quiescence-as-defined-above, HEAD match, clean
index, paths within phase scope, no clean/filter config, size cap, two
stable tree passes) tested individually against fixture STATE directories.
Risks:: Process supervision is the least certain part of this plan even in
its reduced form; a provider process may outlive the engine and keep
writing (stated as a limitation above, not solved here). Attempt names
must carry a project slug so two projects cannot collide under one home
directory.
Decision gates:: See <<decision-gates>>, DG-3 (preservation disposition)
and DG-6 (preservation's release-gate status) should be confirmed before
this Commission starts.

=== BP9 -- `wfc-beta1-bp9-beta-gate-001`

Goal/deliverable:: Evidence that an external user who has not read the
Operator Manual can install, configure, plan, run unattended, inspect and

Modules/paths:: A permanent end-to-end acceptance test with the fake

Excluded scope:: No new product mechanism; this Commission consumes BP1–BP6

(post Beta 1, per the FTR).
Prerequisites/predecessors:: `wfc-beta1-bp6-audit-report-001` accepted.
Controlling BUG/FTR:: link:BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc[the
Claude write-permission BUG] -- this Commission is where the *one* remaining

Acceptance:: A person who has not read the Operator Manual completes the

parts and one live Run per supported adapter (Codex, then the Claude
qualification above) from an installed wheel.
Tests/evidence:: The permanent fake-provider acceptance test; the local
integration scenario (install, `init`, `plan`, `run --yes` through archive
and report, one deliberate failure case from the second-pass review's

[[sequencing]]
== Critical path, parallel work and integration points

[source,text]
----
BP1 --> BP2a --> BP2b --> BP3 --+--> BP4 --+--> BP6 --> BP9 --> 0.1.0b1
  \                              \         |
   +---> BP5 (port/tests start) --+-> BP5 (commit, finishes) --+
BP8 (parallel, independent, no predecessor)
BP7 (after BP6 acceptance + maintainer Runtime promotion; before or after the tag, per DG-4)
----

Critical path: BP1, BP2a, BP2b, BP3, BP4, BP6, BP9. BP5 is off the critical
path in the sense that its port, staging and equivalence-test work can run
the whole time BP2–BP3 are built; but BP5's own acceptance (the
copy-to-commit retry) needs BP3 accepted first, so BP5 cannot *close*
before BP3 does. BP8 is independent from the start. BP7 is deliberately
last and gated on a maintainer action (Runtime promotion), not on any agent
Hop.

Integration points that actually matter: BP2b is where the compiler and
`admit_parsed` meet (BP1+BP2a feed it); BP3's commit primitive
(`git_facts.bounded_path_commit`) is the only write path BP4's lifecycle,
BP5's archive-commit step and BP6's archive/report all reuse, so a defect
found there blocks three downstream packages at once, not two; BP4 and BP5
meet only at BP6, where archive is first wired into the lifecycle -- until
then they are independent of *each other* (though both depend on BP3) and
should be reviewed independently.

Real release gates (block `0.1.0b1`): BP1–BP6, BP8, BP9 as specified above,
including the one Claude positive qualification -- see
<<preservation-gate-status>> for the one open gate-status question within
that list. Explicit post-Beta items, not gates: BP7's exact timing
(candidate before the tag, acceptable after); `wfc continue`/RP1 and C6's
lineage block; same-Run reconcile (`FTR-WFC-ATOMIC-HOP-RECOVERY`);
`direct@v1`; dynamic routing or mixed adapters in one Run; execution-boundary
integration and qualification (`FTR-WFC-EXECUTION-TRUST-BOUNDARIES`);
macOS/Windows support; any host subreaper beyond this plan's bounded
preservation recommendation.

*Disposition -- public-internet investigation (explicit, per the epic's BP9
entry):* `FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY` is a separate, already
substantially advanced track -- `_open.adoc` records independently accepted
and maintainer-promoted Codex P1/P3 and Claude P2-002/curl qualifications --
that progresses on its own FTR, outside this plan's Commissions. It is
provider/agent network capability, not a BP1–BP9 product deliverable, and is
not a `0.1.0b1` release gate; `_open.adoc` (the sole readiness authority)
still classifies it "planned" overall, and that status is unchanged by this
plan. BP9's live per-adapter qualification Runs use whatever network
capability is promoted at the time; BP9 does not re-open or re-decide this
FTR's own remaining investigation.

[[batches]]
== Batches

Each batch is sequential work a maintainer can authorize together; no batch
grants new authority, and nothing in it auto-promotes a Runtime or pushes.
"Autonomous-continuation condition" means: every Commission in the batch
reaches independent broad-review acceptance with no open blocking Finding,
and Coordinator `task-check` passes. If that holds, the next batch may be
authorized without a further maintainer decision beyond the ordinary
per-Commission authorization. "Stop" means a point where only the maintainer
can proceed.

[[release]]
== Release acceptance and definition of done

Three distinct milestones apply to every Commission above, per
link:README.adoc[the backlog upkeep convention], and must not be conflated:

. *Implementation acceptance* -- the implementer's own candidate, with
  local checks passing, is not yet acceptance.
. *Independent acceptance* -- the configured independent review accepts
  with no open blocking Finding, and Coordinator `task-check` passes. This
  is recorded per Commission, in `_open.adoc` and the controlling BUG/FTR,
  exactly as every other accepted correction already is.
. *Product closure* -- the maintainer records closure only when remaining
  product obligations (qualification, integration, Runtime promotion where
  required) are met. Independent acceptance of BP1–BP6, BP8 and BP9 does
  not by itself close the Beta-1 epic.

Definition of done for `0.1.0b1`:

* BP1–BP6, BP8 and BP9 each independently accepted per the acceptance
  criteria above, with Coordinator-trusted evidence for every accepting
  Run.
* Each accepted Run archived (via the existing `scripts/wfc_op.py
  cmd_archive` path, since BP5/BP6 do not yet exist for their own
  predecessors) into the Evidence repository, consistent with current
  practice for every other accepted BUG/FTR correction.
* BP9's full acceptance scenario passing end to end, including the one
  live Claude qualification this plan does not duplicate or invent further.
* DG-1 through DG-6 resolved, with their resolutions recorded in the epic
  (`beta1_productization.adoc`) by the maintainer, not silently assumed by
  an implementer.
* The maintainer's separate product-closure record for the epic, per the
  upkeep convention above; an accepted Commission's independent review is
  not that record.
* BP7 completed either before or after the tag per DG-4; its timing does
  not block the tag itself if deferred, per the epic's own classification
  of BP7 as "candidate before tag / later if deferred."

Explicitly *not* required for `0.1.0b1`, consistent with the epic's current
decisions: `wfc continue`/RP1 and C6's lineage mechanism; same-Run reconcile
(`FTR-WFC-ATOMIC-HOP-RECOVERY`); execution-boundary integration and
qualification (`FTR-WFC-EXECUTION-TRUST-BOUNDARIES`); a second Claude
qualification beyond the one named in BP9; macOS or Windows support; dynamic
routing or mixed adapters in one Run; any comprehensive host
supervisor/subreaper.

[[limits]]
== Limits of this plan

This plan was built by reading the repository and the named reviews, not by
running the suite or any live provider; Coordinator `task-check` for *this*
WorkItem is a separate, Coordinator-owned step, not performed here. The
Evidence repository's own implementation and tests were not directly
readable from this sandbox, as stated in <<basis>>; BP5's prerequisite is
stated rather than assumed satisfied. The preservation recommendation under
BP4 (DG-3) is this plan's own bounded technical judgment, not a settled
maintainer decision; it should be confirmed, not silently executed, before
BP4 is authorized. Batches group Commissions for authorization convenience;
they do not change any Commission's own authorized scope or finding
authority, and no batch boundary is itself a review or acceptance event.
