recorded in `workflow-coordinator-run-evidence/project_memory/run_ledger.adoc`
("Latin Story-2, attempt 03 -- bounded scope grant exercised successfully,

== Exact failed invariant

Any finding-delta that references an existing `finding_id` must reproduce
that Finding's `invariant` exactly, byte-for-byte, whether or not the
proposed disposition changes the Finding's state. The reducer enforces this
unconditionally, before considering `proposed_state`, `blocking`, or any
other field of the delta (`reducer.py:189-190`). H004's delta did not: the
underlying linguistic judgment that F001 was resolved was correct, but the
resupplied `invariant` text was not the original string.

== Why the current fail-closed behavior is correct

This is not a bug in the reducer's existing-Finding protection. An agent must
not be able to rewrite the semantic identity of an existing Finding merely by
referencing its `finding_id` -- that is exactly the invariant
`reducer.py:189-190` exists to enforce, and this BUG does not propose
weakening it. Rejecting a non-exact match and refusing to apply any
disposition before that match succeeds is the intended fail-closed behavior,
consistent with the same general design posture documented for the
correlation-identity case.

== Root-cause classification (established facts only)

`FindingDelta.invariant` is a required `str` field
(`src/workflow_coordinator/model.py:196`), and the Codex/OpenAI structured-
result schema projects it as an unconstrained `{"type": "string"}`
(`src/workflow_coordinator/codex_adapter.py:95`). There is no schema-level
distinction between a finding-delta that creates a new Finding (where the
model is the sole author of `invariant`, and free-form generation is
semantically correct) and a finding-delta that references an existing
`finding_id` (where the Coordinator already holds the authoritative
`invariant` in Run state, and any independent regeneration is redundant with,
and in this Attempt diverged from, that already-known value). The shape
observed:

----
Coordinator already owns immutable Finding.invariant
    ->
projected to the model as a free-form string field
    ->
model must emit the value again to reference the Finding
    ->
free-form generation
    ->
reducer checks exact equality against Coordinator-held state
    ->
harmless paraphrase (same semantic conclusion) causes fail-closed stop
----

This resembles the closed correlation-identity defect's shape structurally
(Coordinator-owned identity -> generative re-emission -> a small textual
divergence -> exact-match validation failure), but this BUG does not itself
assert they share a root cause, a schema location, or an implementation fix.
That question -- and whether either is representative of a broader family, or
each is an isolated case -- was the open investigation question this record
commissioned; it has since been answered by the accepted architecture
assessment (see "Architecture assessment: completed and accepted" below),
not decided by this paragraph.

== Relationship to the broader generative-echo question

This BUG's narrow, established fact is: an existing Finding's `invariant` is
Coordinator-owned immutable state that the current provider-facing result
contract nonetheless asks the model to regenerate as free-form text, and the
reducer's independent exact-match check is correct to reject a divergent
regeneration. Whether this is one isolated defect or a member of a small
coherent family of similarly-shaped fields elsewhere in the result contract
(existing Finding blocking state, successor_ref, proposed Finding
disposition, evidence_refs, and the likely-false-positive candidates
`requested_route`, `proposed_state`, `escalation`, `evidence_refs`,
`CommitIntent`, `claimed_commits`, `summary`) was an open architecture
question. It was commissioned to a bounded WFC self-development Run,
`WI-WFC-GENERATIVE-ECHO-AUDIT-001`, whose durable product is an independently
reviewed architecture-assessment artifact at
`docs/backlog/wfc_reviews/WI-WFC-GENERATIVE-ECHO-AUDIT-001/review.adoc`. That
Run has now completed and its assessment has been independently accepted;
see "Architecture assessment: completed and accepted" below. Acceptance does
not itself imply the correction is implemented, and no finding raised in the
assessment became a BUG merely by being raised there -- see "Authorized
correction scope" for exactly what is, and is not, authorized by that
acceptance.

The accepted assessment's conclusions, taken as now-established for the
purpose of this BUG:

* Correlation identity (`run_id`/`hop_id`/`invocation_id`) is the
  already-fixed member of the same small design family as this BUG
  (`docs/backlog/BUG-WFC-GENERATIVE-CORRELATION-IDENTITY.adoc`); the two are
  members of one design family but not one implementation defect, and do
  not share a fix location.
* For an existing Finding referenced by `finding_id`:
** `invariant` regeneration is the primary remaining generative-echo defect
   (the observed H004 failure and the correction's central target).
** `blocking` regeneration for a same-state citation, and for anything other
   than the authorized `open -> residual` downgrade, is a related
   conditional echo.
** A same-state `successor_ref` restatement requirement is a related echo;
   an active-supersession `successor_ref` remains genuinely agent-owned and
   must remain required and validated there.
* `finding_id` itself remains necessary reference/identity selection, not a
  generative-echo defect.
* `proposed_state`, `evidence_refs` (both existing-Finding and result-level),
  `requested_route`, `escalation`, `CommitIntent`, `claimed_commits`,
  `summary`, and the other candidates falsified in the assessment are not
  material generative-echo defects and are not authorized as correction
  targets by this acceptance.
* New-Finding semantics (`finding_id = null`) are unchanged: `invariant`,
  `blocking`, evidence, and any successor remain genuinely agent-authored
  output and must remain required and validated as such.
* The existing atomic Finding-delta reduction, authority checks, exact
  correlation validation, and fail-closed behavior described in "Why the
  current fail-closed behavior is correct" above must remain intact; this
  acceptance does not weaken them.

=== Why the shared self-development governance could not carry this correction

`governance/work-items/*.yaml` plus its paired `*-task.txt` (the mechanism
that commissioned `WI-WFC-GENERATIVE-ECHO-AUDIT-001` above) commissions a WFC
self-development Run under
`governance/self-development/repository-policy.yaml` and
`governance/self-development/standalone-development-profile.yaml`. Every
phase of that profile's `authorized_scope`, and the policy's
`work_item_scope_ceiling`, is fixed to developer-ergonomics files
(`Makefile`, `README.md`, `pyproject.toml`, `scripts/wfc_snapshot.py`,
`tests/unit/test_wfc_snapshot.py`,
`tests/architecture/test_package_boundaries.py`) plus
`docs/backlog/wfc_reviews` for review/rereview phases. `src` is explicitly
excluded: `operator.py`'s preflight rejects any `WorkItem.scope` exceeding
the ceiling, and `tests/architecture/test_self_development_governance.py`
itself asserts `not _within_scope("src", policy.work_item_scope_ceiling)`. A
`governance/work-items/*.yaml` naming any file under "Authorized source
files" above would therefore fail WFC's own preflight against *that shared*
policy before a Run could even start.

This still matches the closed sibling precedent in one respect: the accepted
correlation-identity fix
(`docs/backlog/BUG-WFC-GENERATIVE-CORRELATION-IDENTITY.adoc`, commit
`a390ac23b42f69112af8f4c81cd171795920873a`) was never issued as a
`governance/work-items/*.yaml` WorkItem against the shared developer-
ergonomics governance either; it was implemented directly. Extending
`governance/self-development/repository-policy.yaml`'s
`work_item_scope_ceiling` (and the shared profile's per-phase
`authorized_scope`) to admit `src` for WFC self-hosted implementation Runs in
general remains a distinct, separately-decidable future direction; this
record neither proposes nor authorizes that extension. See "Execution
mechanism" below for what this record now authorizes instead.
