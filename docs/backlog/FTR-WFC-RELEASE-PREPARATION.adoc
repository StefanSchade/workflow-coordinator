37 edit sites (1 + 1 + 1 + 12 + 6 + 6 + 1 + 4 + 5) in *thirteen* distinct
files, against the four version-bearing files the basis names. Two gaps matter
more than the count:

. *`pyproject.toml` and `implementation_identity.VERSION` can disagree and
  the whole required suite stays green.* Only a hosted CI run catches it.
. *`README.md` can keep links to the previous tag and `release-check`
  passes.* Beta 2 would publish a README pointing at `v0.1.0b1`.

Two claims about this surface do *not* hold and are deliberately excluded:

* `tests/unit/test_release_tooling.py` contains ten `0.1.0b1` literals, but
  its module docstring and `_write_baseline` show them to be a *synthetic*
  fixture version used to build throwaway repositories and in-memory
  archives. The constant is internally consistent and must *not* be bumped.
* `scripts/wfc_doc_catalog.py:762`, `:875` and a large number of `.adoc`
  references name the cold-storage path prefix `pre-0.1.0b1`, which is a
  directory name, not a version pin. A naive search for the version string
  therefore matches far more lines than the surface does, most of them in
  historical records; the enumerated table above, not a grep, is the surface.

== Chosen direction

One new read-write script, `scripts/wfc_release_prepare.py`, behind
`make release-prepare VERSION=<v>`, that owns the enumerated surface; plus two
cheap mechanical guards so the surface cannot drift silently.

* *A script, not a documented procedure*, because the recurring cost is the
  completeness of a list of thirteen files, which is exactly what a human
  forgets and a list in code does not.
* *The only writing release tool.* `release-check` and `dist-audit` stay
  read-only and network-free; this tool writes, once, explicitly, to
  enumerated paths only, and commits nothing.
* *The surface list is data, not prose*, so the guard test and the script
  read the same list.
* *No version bump in this slice.* The tool is added and proven on a scratch
  copy; the real bump is a separate, maintainer-instructed invocation.

[[scope]]

. `scripts/wfc_release_prepare.py` (new): the surface list, the rewrite, the
  idempotence, the refusals.
. `scripts/wfc_release_check.py`: extend `check_readme_links` so a

  `dist-audit`.

. `tests/architecture/test_consumer_tutorial_pages.py`: one line, only if
  <<d2>> is decided as recommended.
. `docs/developer_guide/ch04_release_management.adoc`: the three line groups

Every path is inside `.wfc/config.yaml`'s `work_item_scope_ceiling`. No
temporary ceiling entry is needed.

== Non-goals

* No version bump, tag, push, release or publication.
* No change to `pyproject.toml`, `implementation_identity.py`, `README.md`,
  the Agent Skill texts or the chapter 9 pages. The tool *can* write them; the
  slice does not.
* No Git operation of any kind inside the tool: no `add`, no `commit`, no
  branch. It leaves ordinary working-tree changes for review with `git diff`,
  the way `make memory-import` already does.
* No network access, no subprocess other than none at all.
* No new dependency; standard library only, like both existing release tools.
* No change to the C2 allow-list, the offline-input profile or its digests.
* No reversal of C1's deliberate test literal at
  `test_bp1_identity.py:41` -- see <<d1>>.
* No release-notes *authoring*: the tool freezes the heading of an existing
  section and refuses when the section is missing.
* No chapter-4 work beyond the three line groups of <<ch04>>: no restatement
  of the contract, no gate added or removed, no record moved, no edit to the
  recovery table or the CI section.

[[design]]
== Design

=== The surface list

One module-level table, each entry a path plus the rule by which the version
appears in it. Three rules suffice for the thirteen files:

[cols="1,3",options="header"]
|===
|Rule |Meaning

|`version_literal`
|An exact assignment: `version = "<v>"` in `pyproject.toml`,
`VERSION = "<v>"` in `implementation_identity.py`, the quoted literal in
`test_bp1_identity.py`.
|`tag_pinned_url`
|Every `https://github.com/StefanSchade/workflow-coordinator/blob/v<x>/`
occurrence, rewritten to the new tag. The path after the tag is not touched.
|`install_pin`
|`workflow-coordinator==<v>` and the prose version mentions beside it, in
`README.md:24`, `:26`, `references/setup.md:30` and
`01_quickstart.adoc:120`, `:126`, `:130`, `:133`.
|===

`release_notes.adoc` is handled separately: the heading
`== <new> -- planned` becomes `== <new> -- (released)`.

=== Refusals

The tool exits non-zero and writes nothing when: the given version is not a
valid PEP 440 version; the release-notes file has no section for it; that
section is already `(released)`; a file in the list is missing; or a
`version_literal` site does not match its expected pattern exactly once. A
partial write is never left behind -- every file is rewritten only after all
of them parse.

=== Idempotence

Running the tool twice with the same version produces no second change. This
is the property the guard test can check cheaply and the one a release
operator relies on after an interrupted preparation.

=== The two guards

`tests/unit/test_release_version_surface.py`, against this checkout:

. `pyproject.toml`'s `project.version` equals
  `implementation_identity.VERSION`. This is the gap the required suite
  cannot see today.
. Every `blob/v<x>/` URL in `README.md` names that same version. The Agent
  Skill files already have this guard
  (`tests/unit/test_agent_skill_content.py:237`); `README.md` does not.

Both must *fail* if a single site is left behind -- demonstrated by a
negative case on a copied tree, not asserted.

== Acceptance criteria

AC-1:: `make release-prepare VERSION=<v>` run on a scratch copy of the
checkout changes exactly the enumerated sites and no other byte, verified by
`git diff --stat` against the expected file list.
AC-2:: A second invocation with the same version changes nothing.
AC-3:: The tool refuses, with a named reason and exit 1, for each case in
<<design>>'s refusal list, and leaves the tree untouched in each.
AC-4:: `scripts/wfc_release_check.py` fails when a `README.md`
`blob/v<x>/` link names a version other than the released one, and passes
unchanged on the tree as it is today (`0.1.0b1` everywhere).
AC-5:: `tests/unit/test_release_version_surface.py`'s two guards pass on this
checkout and are each shown to fail on a copied tree with one site reverted.
AC-6:: No version literal anywhere in the repository changes as part of the
slice; `git diff` touches only the files in <<scope>>.
AC-7:: The tool makes no network call and runs no subprocess; standard
library only.
AC-8:: `python -m pytest -q` is green with the offline bundle, `make lint`
and `make format-check` pass.
AC-9:: Chapter 4 is left true of the repository as integrated: its runbook
names `make release-prepare` as an existing step, and the G1 row, the step-1
enumeration and the runbook's preflight sentence name the tag-pinned README
assertion `release-check` now makes. No other line of the chapter differs --
`git diff` on that file shows only the three line groups of <<ch04>>. Strict
render of the chapter prints nothing and
`python3 scripts/wfc_doc_catalog.py generate` then `check` reports no
additional unresolved link or Project Memory miss against the count taken
before the slice starts.

[[tests]]
== Required tests

In `tests/unit/test_release_tooling.py`, synthetic trees in the module's
existing style:

* each refusal of <<design>>, asserting the message and that no file changed;
* a full happy-path rewrite over a miniature surface, asserting the exact
  resulting bytes;
* idempotence;
* the extended `check_readme_links`: passes on a matching tag, fails on a
  stale one, still fails on a repository-relative link.

In `tests/unit/test_release_version_surface.py`, against this checkout:

* `pyproject.toml` version equals `implementation_identity.VERSION`;
* every `README.md` `blob/v<x>/` URL names that version;
* a negative case per guard on a copied tree.

Unchanged and expected to stay green: `test_agent_skill_content.py`,
`test_bp1_identity.py`, `test_offline_distribution.py`,
`test_consumer_tutorial_pages.py` (modulo <<d2>>).

No new test for the chapter-4 edit of <<ch04>>. A test asserting the chapter's
prose would restate prose, which P3 already rejected for the
workflow-versus-gates case; the strict render, the catalog comparison of AC-9
and the independent review reading the chapter against the tool stand in for
it -- the same arrangement
link:FTR-WFC-RELEASE-PIPELINE-ROBUSTNESS.adoc[R3] makes for its own chapter
lines.

== Risks

R-1 An incomplete surface list ships a stale link:: the whole value of the
slice is the list. _Mitigation:_ the two guards, which fail on exactly that;
and the enumerated table under <<problem>>, derived by search and
cross-checked against each test that pins a version.
R-2 A writing release tool is new in this repository:: every other release
tool is read-only and network-free. _Mitigation:_ one explicit invocation, an
enumerated path list, all-or-nothing writing, no Git operation, and
`release-check` left read-only.
R-3 A re-pin that claims an unrepeated verification:: the chapter 9 tutorial
lines. _Mitigation:_ <<d2>>, left undecided rather than assumed.
