== 1. Purpose and intended outcome

WFC should leave the Beta-1 development phase as a *bounded, installable, documented, versioned, independently reviewed agentic development product*, rather than remain a powerful but self-development-specific tool.

The planned sequence is:

. Complete and accept/disposition the *existing* Beta-1 epic (including the applicable BP7/BP8/BP9 gates).
. Record an ADR reassessing open workflow generality versus closed, versioned workflow programmes.
. Conduct a bounded *hardening and stabilization offensive*, selected from evidence and the existing backlog.
. Consolidate and slim the active documentation, including warm storage and temporary compatibility shims.
. Prepare and qualify the release: distribution, CI/CD, user documentation, release notes, optional version-pinned published HTML, runbooks and recovery procedures.
. As the final pre-release qualification, perform a real end-to-end development WorkItem in `spreadsheet-handling` using the intended WFC product installation and public Front Door, then decide on release authorization.

The last two steps are separate gates: *release engineering readiness* is not proof of *real consumer usefulness*.

This is a planning direction, not permission to automatically execute the entire sequence. Package selection, scopes, Commission authorization, architecture changes, public publishing and release decisions retain their existing authority requirements.

== 2. Historical rationale: why the target is changing

=== 2.1 Origin and recovery of the original consumer use case

WFC began as tooling in `spreadsheet-handling` and was later extracted into a standalone repository. Its kernel was sufficiently generic to perform foreign-domain work; the September 2026 Latin-course (`latein`) dogfood provides historical evidence of work and trusted commits in another repository. The old Run's later contract/Finding problem must not be misrepresented as a fully completed Run.

Subsequent Front-Door productization and self-development introduced requirements and paths specialized for WFC's own development environment. The final `spreadsheet-handling` qualification is therefore *a return to the original consumer*, not WFC's first contact with a different repository.

The release must demonstrate that later self-development specialization has not destroyed the original repository- and domain-independent product capability. This is different from supporting arbitrary user-defined workflows.

=== 2.2 Evolution of Level-1 orchestration

An earlier architectural possibility was to implement Level 1 on the same reducer/phase mechanism as Level 0. A higher-order workflow might have phases for planning, task choice and execution; its execution phase could commission a new Level-0 Run. That possibility increased the apparent value of a universal, user-configurable workflow engine.

In current self-development practice, Level 1 is instead external orchestration (presently Sonnet): it decomposes packages, commissions and launches Runs, monitors results, archives evidence, cleans up eligible scratch resources, and arranges successor Runs. Level 0 WFC executes *one admitted, bounded WorkItem* with deterministic authority checks and independent review.

This has worked across successive commissions in the November 19/20 Beta work, while still requiring Maintainer decisions at genuine authorization or acceptance boundaries. It is an observed operating model, not yet a claim that WFC ships a general multi-commission Level-1 product.

Crucial boundary: *no ad hoc Level-1 intervention inside a live WFC Run is part of the design*. Strategy can change between Runs/Commissions. The reducer is not a semantic repair service.

=== 2.3 Why stronger result contracts are justified

Historical dogfood and recent BP6b execution have shown recurring cases of schema-valid but *phase-authority-invalid* agent outputs, notably unauthorized Finding dispositions. WFC correctly fails closed, but repeated mechanical stops consume hops and human attention. This demonstrates a gap between broad expressible result shapes and the permitted actions of a specific programme phase.

The prior FTR `docs/backlog/FTR-WFC-PHASE-SCOPED-RESULT-SCHEMA.adoc` explicitly captured this issue in September and deferred implementation pending recurring evidence. The present assessment should re-evaluate that trigger from real Runs, not assume the feature is already authorized.

Two factors therefore shift the trade-off in the same direction:

* *Lower benefit* of consumer-supplied, arbitrary workflow topology now that Level 1 is orchestrated outside the Level-0 reducer.
* *Higher demonstrated cost* of overly broad agent contracts that rely on prompt compliance to avoid structurally expressible but unauthorized operations.

This is not a conclusion that the original generic design was mistaken under its original assumptions; the assumptions and evidence changed.

== 3. Proposed architecture decision: decide before hardening

=== 3.1 ADR subject

Working title:: `ADR: Closed, Versioned Workflow Programmes on a Generic Execution Kernel`
Alternative title:: `ADR: Reassessment of Workflow Generality and Agent Result Contracts`

The ADR should make a real choice, documenting alternatives and consequences; it must not silently treat this brief as an already accepted ADR.

=== 3.2 Alternatives to analyze

[cols="1,3,3",options="header"]
|===
|Alternative |Benefit |Cost / risk
|A: Consumer-configurable workflow engine |Arbitrary consumer-defined phases, routes, authority and topology |Open-ended contract space; more challenging schema and security assurance; large compatibility commitment
|B: Entirely hard-coded programmes |Strong local typing and straightforward phase semantics |Potential duplication of execution, recovery, evidence and reducer mechanisms
|C: Closed, versioned programmes on generic kernel |Bounded, testable product contract with reusable enforcement machinery |Two internal abstractions; deliberate new-release work for new programmes
|===

*Preferred direction for ADR review:* C.

=== 3.3 Proposed decision and boundaries

* A consumer selects a *supported, product-owned programme/revision*, such as the currently supported subset of `simple@v1` and `robust@v1`; do not silently assert acceptance of other catalogue entries (`direct@v1` has had an explicit unresolved support question).
* Consumer configuration supplies permitted task inputs, scope and execution parameters; it does *not* define arbitrary executable phases, route graphs, Finding authorities or agent-result schemas.
* New programme families or incompatible result contracts require product code, evidence, tests, independent review and a versioned release.
* The kernel may remain data-driven and generic internally. *Declarative implementation does not imply an open public DSL.*
* Results may be programme-specific and role-specific, with phase authority narrowing the currently available shape. The programme defines roles and contract families; the admitted phase selects the active contract and capabilities.
* Prompts and schema narrowing prevent routine mistakes; the reducer remains the *authoritative fail-closed boundary*, also against malformed or forged output.
* Existing accepted programmes and in-flight pinned Commissions must not silently change contract or behavior; decide compatibility/versioning explicitly.
* Inventory older, unused profiles and templates. Decide whether each is supported, internal test material or removable debt. Do not remove solely because current self-development does not exercise it.

A future structured decision-analysis programme (alternatives, criteria, independent assessments, dissent and synthesis) is an example of *release-managed extensibility*, not a mandate to implement it now. Its own backlog record remains deferred.

=== 3.4 ADR acceptance

An accepted ADR must state the rejected alternative, the public configuration boundary, the generic kernel's retained purpose, compatibility policy, implications for `FTR-WFC-PHASE-SCOPED-RESULT-SCHEMA`, and the revisit trigger for opening workflow topology to consumers.

*Gate:* No large-scale result-schema refactoring before this decision is accepted.

== 4. Hardening offensive: bounded, evidence-led

=== 4.1 Start with one assessment Commission

Review `docs/backlog/_open.adoc`, `docs/backlog/beta1_productization.adoc`, relevant BUG/FTRs, recent review artifacts and terminal Run evidence. Produce a candidate plan with explicit inclusions, exclusions, dependency order, acceptance cases, impact on accepted programme contracts and estimated Commission boundaries.

Distinguish *observed recurring operational friction* from speculative extensibility or one-off incidents. Do not reopen completed work solely because its historic review remains available.

=== 4.2 Priority candidates to assess (not pre-authorized)

. *Phase-/programme-scoped structured result schemas.* Restrict permitted routes, Finding operations and authority-shaped fields before the agent replies. Cover worker, correction and reviewer differences under the ADR's chosen programme model; retain negative reducer tests.
. *Agent contract and Commission-template coherence.* Remove conflicting or redundant instructions; ensure schema, projected authority, route vocabulary and examples agree. Address the observed BP6b worker attempt to resolve a Finding without creating a new hidden permission.
. *Review-cycle and correction ergonomics.* Examine repeated newly opened Findings in the same technical family and repeated correction failures, distinguishing independent discoveries from true non-convergence. Avoid inserting an unplanned interactive Level-1 control channel into live Runs.
. *Legacy profile/template and adapter debt.* Identify unreachable or unowned profiles, compatibility shims and unused variants; remove only after proving no accepted programme, fixture, history tooling or legitimate consumer depends on them.
. *Security and operational findings that have concrete reproductions.* Prioritize actual escaped errors, privacy false refusals, isolation failures or misleading success over abstract hardening. For example, BP6b's documented short OS-user-name substring collision (`ci`, `ops`) is a relevant input for assessment; confirm whether it was already resolved by the eventual Beta baseline.

The assessment may find other higher-priority candidates; this list does not mandate their execution.

=== 4.3 Scope discipline and exit criteria

Plan a small number of focused technical changes (initial hypothesis: 2–3 substantive topics, not an open-ended rewrite). Each must have an independently verifiable failure or contract goal, mutation-sensitive tests where appropriate, reviewed migration of any serialized contract and explicit non-goals.

Do not soften reducer authority, auto-correct unauthorized agent intent, rewrite the generic kernel without demonstrated need, or imply that reducing agent invalid-output frequency eliminates correctness or security review.

*Gate:* The selected changes have passing authoritative checks and independent review; recurring historical failure cases are reproduced as either prevented or safely refused; unsupported promises are not added to the product surface.

== 5. Documentation consolidation: current versus historical knowledge

=== 5.1 Objective

Reduce active-context noise and navigational indirection while preserving historical provenance and the ability to understand how the product evolved.

Existing homes have distinct responsibilities:

* Operator Manual: supported operation, commissioning, run/status, evidence and recovery.
* Developer Guide: maintenance, code navigation, tests and release procedures.
* Architecture / functional / technical models: present design and boundary explanations.
* Backlog / ADRs: current unresolved decisions and accepted architectural rationale.
* Warm Storage: material awaiting assessment or retirement, not a permanent dumping ground.
* Cold Storage / Project History: retained historical artifacts and provenance, not current operating authority.

Honor the current documentation authority index and conventions; do not create another competing navigation tree.

=== 5.2 Shim retirement policy

Previous C4 curation retained temporary source-path/anchor bridges for 25 retired paths and retained five root compatibility shims for real consumers. They are transitional, not an indefinite promise.

* A deleted file's historical content and original commit ancestry remain recoverable with Git. *Git provenance is sufficient for history but not for live links/includes.*
* A shim may be removed when all *current authoritative consumers* (Asciidoctor includes, docs links, scripts, CI, packaging, active guidance and required tooling) are either migrated or explicitly retired.
* Do not rewrite historical review records to make their old links appear current. If a history reader requires navigation, supply an index or provenance note at the historical destination, not a permanent active shim for every prior path.
* Distinguish real product/file compatibility from mere convenience for a deprecated document location.
* Where the current trusted-commit mechanism or other mechanical path-ownership rule complicates deletion, record and handle that boundary explicitly instead of either circumventing it or keeping all shims forever.

=== 5.3 Proposed work packages and checks

. Inventory active versus warm/cold docs and shim classes; sample link consumers rather than automatically importing all old documents into the new plan.
. Move genuinely historical warm documents to appropriate cold destinations; distill any still-current guidance to one authoritative home before retiring the original.
. Retarget active includes, anchors, relative links, search/navigation entries and build scripts. Remove shims proven unnecessary; explicitly list retained exceptions with their active consumer and removal trigger.
. Validate AsciiDoc build, documentation navigation and relevant architecture/governance tests; inspect shipped distributions for accidental inclusion of archived documentation.

*Gate:* A small, coherent current documentation surface; no broken current authoritative references; historical evidence retained; no shim retained merely because its filename once existed.

== 6. Release engineering and publishing readiness

=== 6.1 Reference implementation: spreadsheet-handling

Treat `spreadsheet-handling` as a *reference and improvement candidate*, not a specification to clone. Inspect its actual current implementations and release history at execution time, including:

* `.github/workflows/release.yml` for test/build/publish orchestration and credential boundaries;
* `tools/release_check.sh`, `tools/pages_publish_check.sh` and release runbook for preflight and publication verification;
* `pyproject.toml` / build metadata and versioning (including possible `setuptools-scm` patterns);
* User Guide, release notes and generated AsciiDoc/HTML documentation;
* version-specific published HTML and stable `latest` convenience navigation.

Deviate where WFC's threat model, installed CLI, distribution needs or operational model differ, or where the reference has a demonstrable weakness.

=== 6.2 Decide release contract before wiring CI

Explicit Maintainer decisions are required for:

* distribution destination: PyPI, private index, GitHub Releases or staged combination;
* public/private repository and documentation visibility;
* first release version/tag form, version derivation and supported Python/platform matrix;
* which guides and release notes are publicly shipped;
* whether a separate GitHub Pages publishing repository is warranted (preferred for long-lived immutable published docs, subject to assessed cost);
* release secrets/permissions, provenance/signing policy and human confirmation before irreversible publication.

No assumption in this brief authorizes public PyPI publishing or creation/configuration of new remote repositories.

=== 6.3 Distribution artifacts and content discipline

* Build a wheel and a source distribution from a tagged candidate; install the wheel in a fresh environment outside the WFC source checkout.
* Keep packaged code/resources, license and build metadata sufficient for a reproducible build. The sdist must be intentionally scoped; inspect the *actual archive contents*.
* Do *not* repeat `spreadsheet-handling`'s over-inclusive source-release documentation problem. In particular, `docs/warm_storage`, `docs/cold_storage`, historical Commissions, run artifacts, Evidence and developer scratch are not presumed necessary for the installed package or sdist.
* Verify required product resources remain available and identity-pinned after installation; overzealous sdist slimming must not break the build or installed CLI.
* Run installed-package command tests from an unrelated working directory; verify `wfc --help`, version/identity and documented entry points.

=== 6.4 CI/CD and release gates

Recommended staged pipeline (final exact design subject to release decision):

. Read-only release preflight: clean/tagged HEAD, expected branch and remote, version consistency, no unexpected artifacts.
. Complete authoritative product/architecture/CLI tests, including build/install isolation and relevant security negative tests.
. Build wheel and sdist; inventory both file lists; inspect metadata, dependency resolution and distribution completeness.
. Install the actual built artifacts in fresh consumer-like environments and exercise basic public CLI workflows.
. Build user documentation and release notes; fail on unresolved current links/includes or missing published assets.
. On an explicitly authorized release tag, publish package artifacts with minimal privileges and a documented retry/failure model.
. Optionally publish immutable version-pinned HTML from the same tag; update `latest` separately; verify final contents and URLs after publication.

Document how pipeline failure before/after package publish and before/after docs publish is detected and recovered. Avoid silently changing an immutable published version. Separate CI permissions for testing, package publishing and Pages publishing; never embed deploy credentials or private paths in distributed assets.

=== 6.5 User documentation and runbooks

At minimum deliver and verify:

* a new-user quickstart from installation through init/config/plan/authorized run/status/report/archive;
* a supported-programme catalogue and clear workflow/role limitations;
* provider setup and privilege boundaries; permissions and safe Git expectations;
* a reliable operator runbook for routine Runs, stopped/ambiguous Runs, evidence handling, scratch retention/cleanup and recovery;
* explicit Evidence retention semantics (`local`, `commit`, `discard`), including what Git tracks, what it does not back up, and the no-remote/no-push contract;
* release notes for the shipped version: what changed, user-visible compatibility, known limitations and supported setup;
* a release operator runbook: preflight, tagging, package/docs publish, verification, partial-failure recovery and maintainer authorization;
* documentation build/check commands suitable for CI and local rehearsal.

If published HTML exists, use immutable paths such as `versions/<tag>/...` and treat `latest` only as an alias. Frozen documentation for a release should not silently link to future `latest` content for version-specific operational claims.

=== 6.6 Release qualification exit criteria

A candidate is release-engineering-ready only when fresh build/install, the documented CLI, full required checks, distribution-content audit, documentation build, tag/version checks and a *rehearsed* release runbook all pass. A green test job alone is insufficient.

== 7. Final consumer qualification: return to spreadsheet-handling

=== 7.1 What this test proves

The final pre-release task should be a real, narrowly scoped implementation or bugfix in `spreadsheet-handling`, performed by the intended *released-product path* of WFC, not by the old self-development Harness or an editable WFC checkout.

This is a *return-to-origin regression and integration gate*: the product must still work on the repository where WFC began as tooling, notwithstanding intervening extraction and Front-Door specialization. It is *not* WFC's first foreign-repository test, nor a proof of universal repository independence from one success.

=== 7.2 Keep it separate from BP9

BP9 already requires neutral, non-Python fixtures and installed-wheel qualification with supported adapters. Those release-matrix cases must be completed and retained independently.

The `spreadsheet-handling` task adds a *real project-development* demonstration: a bounded change with actual tests, independent review, correction if needed, and an end-to-end evidence trail. The two gates are complementary and neither substitutes for the other.

=== 7.3 Proposed acceptance setup

. Install the intended WFC release candidate as a built artifact in an isolated environment; record exact version and implementation identity.
. Prepare `spreadsheet-handling` using the supported Front Door, its current legitimate consumer configuration and a pinned clean Git baseline. Avoid internal WFC-only paths and incidental sibling checkout assumptions.
. Authorize one genuine, suitably small WorkItem, with explicit scope, check command, programme revision and role bindings; use a real model/provider for worker and independent reviewer.
. Exercise admission/plan/launch/status/report/archive through the installed product path, including the selected Evidence retention configuration.
. Require a real repository modification and test evidence. Preserve distinct review and correction responsibility; do not manufacture a green result by weakening gates.
. Verify original repository outside the authorized scope was not mutated, Git writes were bounded, runtime/evidence locations were explicit and archive facts correspond to the real Run outcome.
. Compare with the project's own tests/CI; record release-candidate version, WFC evidence, commit IDs, review disposition and limitations.
. After success or safe, truthful stop, have the Maintainer explicitly disposition the result. A failed Run may give valuable evidence but does not silently satisfy the positive release gate.

The specific `spreadsheet-handling` WorkItem should be selected close to execution time: a genuine need, low blast radius, meaningful regression assertion, and no contrived dummy change solely to make the demo green.

=== 7.4 Final release gate

The release decision uses both the BP9 neutral qualification and the `spreadsheet-handling` real-WorkItem evidence, together with the complete package/docs/publishing gates. It remains a Maintainer authorization. A release tag must not be inferred from a local green test or an agent assertion.

== 9. Authority, evidence and change-control invariants

* Existing Beta work and in-flight Runs take precedence. Do not intervene in live Level-0 Runs or change an active Run's authority, budget or semantics from this planning record.
* New Commissions require explicit admission and appropriate authorization; a strategic roadmap does not grant Git, provider, filesystem, network or publishing authority.
* Keep Level-1 orchestration external unless a future, separately authorized product decision changes that boundary.
* Maintain the reducer's fail-closed security/authority checks, independent review and truthful Run classification.
* Preserve historical Evidence and decisions; a successor Run is not a retroactive successful completion of a prior stopped Run. Mechanical archive and curated semantic Run ledger are separate.
* Keep state root, OPS, scratch and Evidence repository distinct. An Evidence destination is not an engine state root. XDG default and the existing self-development sibling Evidence repository are *alternative configured destinations*, not successive stages.
* For self-development the current intended retained Evidence target is `../workflow-coordinator-run-evidence` (relative to the Development repo), with `raw: commit`, subject to the actual BP7 cutover configuration decision; do not silently create a second XDG archive or embed a maintainer HOME path as a product default.
* `wfc init`/`wfc archive` making local Git commits is not a remote push. Existing BP6b guarantees state no remote/push; any external backup, sync or publication needs a distinct authorization and design.
* Distinguish agent exploratory checks, Coordinator-trusted checks, independent review and Maintainer acceptance. Avoid claiming completed Runs, accepted product changes or released artifacts from commit count alone.
* Do not publish private run logs, credentials, home paths or raw Evidence through release packages or public documentation.

== 10. Completion definition and open decisions

The programme is complete when:

* the ADR is accepted, with resulting contract/public-config boundaries clear;
* selected hardening changes are independently reviewed and have authentic regression evidence;
* current documentation is navigable, historical documentation has explicit homes, and temporary shims have been retired or justified;
* built WFC distributions install independently, contain intentional files and expose the documented CLI;
* CI/CD, release notes, user/operator documentation, (if chosen) pinned published docs and release runbooks have reproducible evidence;
* BP9's neutral external qualification and the final real `spreadsheet-handling` WorkItem both satisfy their separate gates;
* a Maintainer explicitly authorizes the first release and the release procedure records the resulting tag, package and documentation publication outcomes.

The planning agent must bring open decisions to the Maintainer before treating them as settled: ADR acceptance; support/versioning of catalogue entries including `direct@v1`; exact hardening shortlist; any retained shims with real current consumers; public/private destination and credential setup; documentation Pages repository; release version/tag; and final production publish authorization.
