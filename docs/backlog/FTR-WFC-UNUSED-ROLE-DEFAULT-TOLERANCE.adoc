== Maintainer decision (2026-11-26)

D2, *Option A*: unused repository-config role defaults are tolerated and shown explicitly; unused explicit CLI overrides are still refused. Slice link:beta2_operator_efficiency_plan.adoc#o3[O3].


== Design (2026-11-26, WI-WFC-BETA2-O3O2-001)

*Rule.* `frontdoor.config.resolve_execution` no longer raises when
`config.default_execution` names a role the selected program's phases do not
use; it still raises, unchanged, when an explicit `--execution-override`
names such a role (`CommissionError`, "execution overrides name roles the
selected program does not use"). The tolerated role names are collected,
sorted, and returned as a new field on the existing result
(`ExecutionEnvelope.ignored_default_roles: tuple[str, ...]`, defaulting to
`()` so every pre-existing construction of that frozen dataclass stays
valid). `wfc plan`'s preview prints that list on its own line, always --
empty as `(none)`, non-empty by name -- so a committed `independent_reviewer`
default resolved against `simple@v1` is visible, never silent.

*What stays refused.* An unused `--execution-override` (unchanged message
and refusal). An unknown role *name* anywhere in `default_execution` is still
refused where the config is parsed, before resolution ever runs
(`consumer_config_from_yaml`'s `WorkflowRole(role_name)` call); this slice
touches only `resolve_execution`'s widening check, not that parse-time check.

*What is newly tolerated.* A syntactically valid role name in
`default_execution` that the selected program's phases do not require.

*Safeguard preserved.* The risk this record names is a consumer reading a
committed `independent_reviewer` default as evidence that review happens
when the selected program performs none. Three facts bound it, as the
Problem section already argues, and this design keeps all three: the
*program* selection (not the config) decides whether review happens and is
already explicit in `wfc plan`'s own output; an unknown role name is still
refused at parse time, so tolerance only ever reaches a valid role the
program simply does not execute; and the required `wfc plan` line replaces
the refusal with a stated fact rather than with silence, which is the actual
mitigation, not a convenience -- hence it is unconditional, not shown only
when the list is non-empty.

*Alternatives rejected.* (i) Tolerate both unused defaults and unused
overrides -- rejected per D2 Option A: an override that cannot take effect is
a per-Commission intent and a genuine operator error, unlike a standing
repository fact several programs legitimately share. (ii) Make the `wfc
plan` line advisory (print it only when the list is non-empty) -- rejected;
printing `(none)` on every preview is what keeps the line itself from
becoming an inattention risk ("no line" silently meaning either "nothing
ignored" or "an older `wfc plan` build").

== Problem

`resolve_execution` refuses a Consumer Config whose `default_execution` names
a role the selected program does not use:

----
execution config defaults name roles the selected program does not use: ...
----

(`frontdoor/config.py:257-262`). A repository configured for `robust@v1`
carries an `independent_reviewer` default, so `simple@v1` is refused in it --
by `wfc plan` first, so the operator never reaches a launch.

Two consequences, both observed:

. Every `simple@v1` Commission needs a *second* Consumer Config file, without
  the reviewer default, committed in the run worktree only and never
  integrated (friction entry 1). `verify_commission` reads the config from
  the Git tree at the authorized head (`frontdoor/verify.py:71`), so it must
  be committed; hence a worktree-local commit per Commission whose only
  property is that it must not travel.
. Editing the committed `.wfc/config.yaml` instead -- the obvious shortcut --
  breaks `tests/unit/test_self_development_consumer_config.py:51-60`, which
  pins the `default_execution` mapping exactly, `independent_reviewer`
  included. That made a full-suite baseline probe fail before any provider
  ran, consuming the checkout's single lifecycle (friction entry 21). The
  earlier `simple@v1` Runs of that day used a documentation-only evidence
  command and never ran the test, which hid the coupling.

The refusal is not technically necessary for the resolution itself: only
`required_roles` are ever resolved into bindings
(`frontdoor/config.py:269-274`), so an unused default is already inert
downstream.

== Direction (not a chosen design)

Tolerate an unused role *default* and keep refusing an unused
`--execution-override`. The asymmetry is the point: an override is a
per-Commission *intent* the operator typed for this Run and which cannot take
effect, so refusing it reports a real operator error
(`frontdoor/config.py:252-256`); a `default_execution` entry is a standing
repository *fact* that several programs legitimately share.

To keep the inertness visible rather than silent, `wfc plan` should name the
role defaults the selected program ignores, in the preview the operator reads
before authorizing.

== The safeguard this touches, stated plainly

The refusal is today the only mechanical signal that a committed role default
has no effect. Without it, a consumer could read an `independent_reviewer`
default in a committed config as evidence that review happens, when the
selected program performs none.

Three facts bound that risk without dismissing it: the *program* selection,
not the config, decides whether review happens and is already explicit in
`wfc plan`'s output and in the Commission; an unknown role *name* is still
refused when the config is parsed (`frontdoor/config.py:204-206`), so this
check only ever fires on a valid role the program does not use; and the
proposed `wfc plan` line replaces a refusal with a statement rather than with
silence. The residual risk is a consumer who reads the config and not the
plan output.

== Open decisions

* link:beta2_operator_efficiency_plan.adoc#d2[D2] -- tolerate config defaults
  while still refusing overrides (the plan's recommendation), keep today's
  refusal and document the second-config pattern permanently, or tolerate
  both. Tolerating both is argued against in the plan: an override that
  cannot take effect is a genuine operator error.
* Whether the `wfc plan` line is required or advisory. The plan's acceptance
  treats it as required, because it is the mitigation rather than a
  convenience.

== Implementation note (2026-11-26, WI-WFC-BETA2-O3O2-001)

Implemented exactly as the Design section above states.
`frontdoor.config.resolve_execution` (`frontdoor/config.py`) no longer
refuses an unused `default_execution` role; it collects the ignored role
names onto a new `ExecutionEnvelope.ignored_default_roles` field (default
`()`, so every existing construction stays valid), and `wfc plan`
(`frontdoor/plan.py`) prints them on an unconditional preview line. An
unused `--execution-override` is still refused, unchanged. An unknown role
*name* in `default_execution` is still refused at parse time, unchanged.
`tests/unit/test_self_development_consumer_config.py` is green and
unchanged; `tests/unit/test_consumer_compiler.py` and
`tests/unit/test_frontdoor_init_plan.py` carry the new coverage (the
tolerance, the preview line with and without an ignored default, and the
unchanged override/unknown-role refusals). The skill
(`references/setup.md`) and the Operator Manual
(`ch09_consumer_quickstart/01_quickstart.adoc`,
`ch03_running/01_preparation.adoc`) no longer instruct a second Consumer
Config file; `docs/backlog/FTR-WFC-LEVEL1-OPERATOR-GUIDANCE.adoc`'s entry
1/21 row is marked retired.
