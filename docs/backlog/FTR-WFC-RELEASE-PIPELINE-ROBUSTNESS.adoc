[[problem]]
== Problem

Three small, independent defects in `.github/workflows/release.yml`, each
verified against the file at `0f50ad2`, plus one *decision* the basis raises
that this record presents rather than takes. The file is byte-identical to the
version the independent basis of 2026-11-23 read.

W1 -- `release` is not re-runnable:: `:371` calls `gh release create`, which
fails when the release already exists. After a partial success -- the release
created but an asset upload interrupted -- the job cannot be re-run. R2's
corrected recovery table therefore states "re-run the failed jobs" with an
explicit exception for this one job while this slice is still planned; this
slice removes the behaviour and the exception together, and that exception is
the only line of R2's chapter whose truth this slice changes.
W4 -- the checksum file is built and then not attached:: `:169-178` writes
`dist/SHA256SUMS.txt` and echoes it into the job summary. `publish-testpypi`
and `publish-pypi` verify it and then `rm` it (`:307-312`, `:341-346`). The
`release` job attaches only `dist/*.whl dist/*.tar.gz` (`:371-374`), so the
one place a downloader could use the checksums -- the GitHub Release -- does
not get them. Inside the artifact it describes, the file detects corruption,
not tampering; attached to the Release, it is a usable record.
W5 -- the facts the maintainer approves on were inferred, not read:: Chapter
4's hosted-run record states for four of five open items that they are
*Operator inferences*, because job logs were not retrievable
(`ch04_release_management.adoc:485-495`, `:518-529`): the runner's seed pip
version, whether the `sysctl` for `bwrap` was needed, the pytest pass and
skip counts, and whether the offline-input fetch reached its index. Each is a
single line the job already has and does not print. Today's summary carries
only the artifact SHA-256 (`:169-178`) and `python-compat`'s coverage note
(`:284-291`).
W7 -- an advertised-interpreter gap, *not* a defect and *not* decided here::
`publish-testpypi` needs only `check` (`:293-295`), so a red `python-compat`
does not stop publication, while `pyproject.toml:17-20` advertises CPython
3.10 to 3.13 and only CPython 3.13 on Linux x86-64 is qualified. That is the
*recorded maintainer decision of 2026-11-23* -- `:188-195` ("no release gate
(no job waits for it; it reports the compatibility facts for the
maintainer)"), `ch04_release_management.adoc:164-168` ("not a prerequisite of
any publishing job") and `:566` ("the informational `python-compat` matrix")
-- and `ch04:243`'s gate-class sentence is scoped to the enumerated gates
G1-G8 (`ch04:267-274`), which do not include this job. There is therefore no
contradiction in the chapter to correct. Closing the gap by gating the job
would *reverse* that decision, so it is maintainer decision
link:beta2_release_streamlining_plan.adoc#d6[D6] (Option A gate it, Option B
drop the 3.10-3.12 classifiers, Option C leave both). Only the one-line

[[design]]
== Design

=== W1 -- an idempotent `release` job

Replace the single `gh release create` with: `gh release view "$tag"` to
decide, then `gh release create` when it is absent or `gh release upload
--clobber` when it is present. The job keeps `contents: write` as its only
elevated permission and keeps reading the already-published tag and the
downloaded artifact; it creates nothing else.

An absent release and a failed `gh release view` for another reason (network,
authentication) must be distinguished -- a non-zero exit is not by itself
"absent". The step inspects the failure rather than assuming.

=== W4 -- attach the checksums

`release` attaches `dist/SHA256SUMS.txt` beside the wheel and the sdist. The
two publishing jobs continue to `rm` it before uploading to an index --
nothing about the upload payload changes.

=== W5 -- decision facts in the job summary

The `check` job writes one block to `$GITHUB_STEP_SUMMARY`:

* interpreter version and the seed pip version
  (`python3 -c "import ensurepip; print(ensurepip.version())"`), which is the
  exact field `check_host` compares and the one unknown (a) of the chapter's
  hosted-run record;
* `bwrap --version` -- unknown (b);
* the pytest pass and skip counts, from the summary line the suite already
  prints;
* artifact names, byte sizes and SHA-256 -- extending the block that exists;
* `implementation_tree_sha256`, read from `wfc --version --json` in the
  existing C3 clean-venv step (`:130-144`), so the candidate's identity is
  printed rather than reconstructed;
* the `dist-audit` result line.

Every value is already produced inside the job. Nothing new is computed and
no step's exit status changes. This block is what the maintainer reads at the
`pypi` pause.

=== W7 -- conditional: `python-compat` as a prerequisite (only under D6 Option A)

*This part of the slice is conditional on maintainer decision
link:beta2_release_streamlining_plan.adoc#d6[D6] and must not be executed
without it*, because it reverses the recorded 2026-11-23 decision that the
job is informational.

If and only if the maintainer takes Option A: add `python-compat` to
`publish-testpypi`'s `needs`. One line; no run-time cost, because the job
already runs on every trigger after `check`. A red compatibility job then
stops the publication chain, and the advertised classifiers are backed by
something that can stop a release.

If D6 is undecided, or taken as Option B (drop the 3.10-3.12 classifiers --
a `pyproject.toml` change outside this slice's scope) or Option C (leave
both), the workflow's `needs:` graph stays exactly as it is and this slice is
commissioned, executed and accepted on W1, W4 and W5 alone. A Worker must not
read the plan's *recommendation* of Option A as the decision itself.

== Risks

R-1 This is the publication chain:: the highest-consequence file in the
repository, and *[X]* the tag-mode path has never run on a hosted runner
(`ch04_release_management.adoc:570`). _Mitigation:_ every change is either
additive (summary lines, one attached file) or a one-line `needs:` edit; none
alters the artifact, the upload payload, the Environments or the OIDC path. A
branch-push run exercises `check`, `python-compat` and the whole summary block
without touching publication.
R-2 Under D6 Option A, gating `python-compat` can block a release for a
compatibility smoke:: by design, and that is why the decision is the
maintainer's and not this plan's. The sharper edge: the 3.10-3.12 matrix jobs
install from the ordinary index rather than the offline bundle
(`ch04_release_management.adoc:168-172`), so an upstream dependency change can
redden a release for a reason outside the repository. _Mitigation:_ the job
has run green (run #9, three matrix jobs) *[X]*; the alternative of narrowing
the classifiers stays available as a separate one-line change; and if D6 is
not taken, this slice simply omits the line.
R-3 `gh release view` masking a real error:: treating any non-zero exit as
"absent" would turn an authentication failure into a `create` attempt.
_Mitigation:_ AC-1's explicit two-branch requirement.
R-4 A summary step that fails the job:: a diagnostic must never be the reason
a release stops. _Mitigation:_ the block is assembled from values the job
already has; any step that could fail on a missing value is written so that
it reports the absence instead of exiting non-zero.
