[[design]]
== Design

=== W1 -- an idempotent `release` job

Replace the single `gh release create` with: `gh release view "$tag"` to
decide, then `gh release create` when it is absent or `gh release upload
--clobber` when it is present. The job keeps `contents: write` as its only
elevated permission and keeps reading the already-published tag and the
downloaded artifact; it creates nothing else.

An absent release and a failed `gh release view` for another reason (network,
authentication) must be distinguished -- a non-zero exit is not by itself
"absent". The step inspects the failure rather than assuming.

=== W4 -- attach the checksums

`release` attaches `dist/SHA256SUMS.txt` beside the wheel and the sdist. The
two publishing jobs continue to `rm` it before uploading to an index --
nothing about the upload payload changes.

=== W5 -- decision facts in the job summary

The `check` job writes one block to `$GITHUB_STEP_SUMMARY`:

* interpreter version and the seed pip version
  (`python3 -c "import ensurepip; print(ensurepip.version())"`), which is the
  exact field `check_host` compares and the one unknown (a) of the chapter's
  hosted-run record;
* `bwrap --version` -- unknown (b);
* the pytest pass and skip counts, from the summary line the suite already
  prints;
* artifact names, byte sizes and SHA-256 -- extending the block that exists;
* `implementation_tree_sha256`, read from `wfc --version --json` in the
  existing C3 clean-venv step (`:130-144`), so the candidate's identity is
  printed rather than reconstructed;
* the `dist-audit` result line.

Every value is already produced inside the job. Nothing new is computed and
no step's exit status changes. This block is what the maintainer reads at the
`pypi` pause.

=== W7 -- no design, because the slice does not implement it

Nothing is designed here, by decision of the plan and not by omission. The
`needs:` graph is left as it is, and so is every `python-compat` line in the
workflow and in chapter 4. The reasoning is in <<w7>> and in
link:beta2_release_streamlining_plan.adoc#d6-slices[the plan]: Option A
reverses the recorded 2026-11-23 decision and its documentation consequence
reaches the gate list, so the change belongs to the maintainer who takes the
decision, together with the chapter lines it outdates.

A Worker executing this slice must therefore not add the `needs:` line even if
D6 has meanwhile been decided as Option A: that would be the maintainer's
change arriving inside a slice whose scope excludes the chapter lines it makes
untrue. If the maintainer wants the slice to carry it after all, that is a
scope decision taken when the slice is commissioned, and it has to extend the
slice's chapter-4 scope and <<ac8,AC-8>> at the same time. A Worker never
reads the plan's *recommendation* -- which is Option C -- as a decision
either.

== Risks

R-1 This is the publication chain:: the highest-consequence file in the
repository, and *[X]* the tag-mode path has never run on a hosted runner
(`ch04_release_management.adoc:570`). _Mitigation:_ every change is either
additive (summary lines, one attached file) or a one-line `needs:` edit; none
alters the artifact, the upload payload, the Environments or the OIDC path. A
branch-push run exercises `check`, `python-compat` and the whole summary block
without touching publication.
R-2 A Worker adds the `needs:` line anyway:: the plan discusses D6 at length
and the one-line edit sits in the file this slice is allowed to change, so the
temptation is real -- and taking it would leave chapter 4 asserting that a job
which can stop the publication chain cannot (`ch04:165`, `:566`), in a slice
whose scope excludes those lines. _Mitigation:_ the Not-authorized line, the
`needs:` non-goal, <<ac5,AC-5>>'s byte-identical requirement, and the
commissioning note that states D6's standing explicitly. The underlying cost
of Option A is recorded where the decision is, not here: the 3.10-3.12 matrix
jobs install from the ordinary index rather than the offline bundle
(`ch04_release_management.adoc:168-172`), so an upstream dependency change
could redden a release for a reason outside the repository.
R-3 `gh release view` masking a real error:: treating any non-zero exit as
"absent" would turn an authentication failure into a `create` attempt.
_Mitigation:_ AC-1's explicit two-branch requirement.
R-4 A summary step that fails the job:: a diagnostic must never be the reason
a release stops. _Mitigation:_ the block is assembled from values the job
already has; any step that could fail on a missing value is written so that
it reports the absence instead of exiting non-zero.
