== Problem and practical benefit

The three reference models are single files of 523, 580 and 705 lines:
link:../functional_model/workflow_program_use_cases.adoc[Functional],
link:../semantic_model/workflow_execution_semantics.adoc[Semantic] and
link:../technical_model/workflow_program_architecture.adoc[Technical]. After the completed
link:../cold_storage/backlog/post-0.1.0b1/FTR-WFC-DOCUMENTATION-CURATION.adoc[curation packages] they hold distilled present knowledge
next to labelled drafts and proposals. That is the right content but an awkward shape:

* A reader or agent who needs one mechanism, one scenario family or one proposal must load the
  whole file, including the part whose standing differs from the part they need.
* Concurrent work on one model (for example a Semantic correction and a P3.5 proposal edit)
  collides in one file; a Commission scope names a whole file even for a one-section change.
* The Technical Model has no single place that answers "which component owns what" and "what
  happens, in what order, between components". Today that knowledge is spread over the layer table,
  the admission, projection and reduction subsections and `architecture.md`.

The practical benefit is navigability and bounded edits, not new content: the same text, anchors,
numbers and authority labels, organized like the already-delivered
link:../operator_manual/operator_manual.adoc[Operator Manual], plus two genuinely new, source-verified
Technical Model views.

This record supersedes, for this purpose only, the C2-time planning allocation in the curation record
("Small Semantic and Technical Models stay single files", "expand into subject chapters only when
growth makes independent reading useful"). That sentence was a planning-time allocation, not an
accepted constraint; the Maintainer has since asked for modular models. The curation record, its C1–C4
outcomes and acceptance evidence stay unchanged.

== Target structure

Principle: the models' existing `==` sections (numbered or anchored) are already the chapter-level units, so
the conversion keeps every existing heading level, title text, number and anchor. Directories group
contiguous sections in the original order; `_chapter.adoc` is an assembly file with a guarded standalone
title and no new visible heading, so the assembled page keeps the same sections and table of contents.
This deliberately differs from the manual, whose chapter files add a chapter-level `==` heading and include
sections at `leveloffset=+1`; adding such headings here would re-level every numbered section. Here a
chapter's section files are included at the same net level (entry `:leveloffset: -1`, chapter include
`+1`, section include none), except where a chapter heading already exists (Semantic `[[proposals]]`, Technical `[[current]]`) or is new
(Technical `[[architecture-views]]`): that heading is written inline in `_chapter.adoc` and its section files
are included at `+1`. As in the manual, section files are `==`-rooted so each renders standalone without a
level warning; text therefore moves unchanged except for heading-marker depth, and rendered output is the
equivalence test. The implementation
Hop verifies this arrangement before bulk work (<<wp-m1>>). Use `link:` for cross-file references as the
manual does, unless a spike shows `xref:file#id[]` resolves internally in the assembled render and in
every standalone file; the default is the manual's practice.

A file is justified when a section is an independently readable unit, is cited as one, or exceeds roughly
40 lines. Small connective sections stay inline in `_chapter.adoc` or in a neighbour; several short
sibling sections may share a file. The layouts below are the proposal; an implementer may merge but should
not split further without a reason recorded in the work result.

Checks are performed by the Worker and independently repeated by the reviewer against the repository, not the
Worker summary; the Coordinator `task-check` stays separate.

. *Entry paths and IDs.* The three entry files exist at their current paths and render as one page each.
  The set of rendered `id` values of the assembled Functional and Semantic entries equals the baseline set;
  for the Technical Model it equals the baseline set plus exactly the new `architecture-views`,
  `_component_view`, `_runtime_view` and the identifiers created inside them (listed in the work result).

  baseline text after whitespace normalization (a section-by-section comparison of the rendered HTML of the

== Mechanical versus human judgment

* Mechanical: moving text, building includes, retargeting seven references, baseline/after `id` and
  rendered-text comparison, link and fragment existence, module-inventory completeness, import-edge listing.
* Judgment: the two standing-label alignments, chapter grouping decisions within the stated rule, the wording
  of the new views, and which exceptions to the layer picture are worth naming. The independent reviewer
  checks these; no Maintainer decision is needed before M1.

Default adopted here: keep existing heading levels (no manual-style chapter headings). A Maintainer who prefers
chapter headings must say so before authorization, since it re-levels every numbered section.
