= FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES -- Preserve the Architectural Core

Type:: future technical record
Status:: proposed direction to preserve / structural consolidation WATCH /
documentation only; no implementation or refactoring authorized
Priority:: preserve during real feature work; do not open a cleanup program
Date:: 2026-09-24
Recorded now:: Before workflow-role and execution-binding generalization and new
consumer use, preserve the boundaries and name consciously deferred debt.

== Decision

The standalone Workflow Coordinator does not need a fundamental redesign.
Preserve approximately this existing shape:

----
deterministic semantic core
    model.py
    reducer.py

controlled-effect shell
    operator and orchestration
    provider adapters and prompt construction
    Git observation and trusted mutation
    evidence preparation and execution
    persistence and recovery
    filesystem and process interaction
----

This directs feature work; it does not permit package reorganization. Next,
generalize roles/personas/execution bindings separately, exercise real
consumers, and improve ergonomics only from observed use.

== Repository evidence and qualifications

`model.py` has immutable records, enums, and deterministic state operations.
`reducer.py` imports only `dataclasses.replace` and those model types. It has no
provider, Git, filesystem, process, persistence, network, clock, or environment access.

The core is deterministic, but not infrastructure-agnostic. `model.py` includes
repository policy, Git heads and commit intent, evidence observations, dispatch
markers, and durable-state records. Preserve effect freedom and deterministic
semantics, not a claim that the model has no effect-shaped vocabulary.

The shell spans `operator.py`, `vertical.py`, `slice4.py`, `adapter.py`,
`codex_adapter.py`, `prompt.py`, `git_facts.py`, `evidence.py`, `persistence.py`,
and `serialization.py`. `vertical.py` composes a Hop's effects and reduction;
`slice4.py` adds real dispatch, checkout association, durable markers, recovery,
and checkpointing.

`persistence.py` is broader than a passive serializer: it owns atomic writes,
projections, and conservative uncertain-dispatch recovery using deterministic
model/reducer operations. It does not define topology or route authority;
checkpoint routes are re-derived from the admitted profile and Run rather than
accepted from the stored projection.

== Load-bearing boundaries to preserve

. Reducer and domain semantics remain deterministic and effect-free. Effects
  may prepare inputs to a reduction or materialize its consequences; they do
  not occur inside reduction.
. Workflow topology and authority remain declarative. Current production
  routing resolves the Run's phase from `WorkflowProfile`, then interprets
  configured routes, route effects, review authority, Finding authority, and
  limits. It does not branch on phase names such as `review`, `correct`, or
  `rereview`.
. Git and Evidence facts are observed or prepared in the shell. The reducer
  consumes admitted `MechanicalFacts` summaries and the candidate
  `RoutingResult`; it does not run Git, execute evidence, or manufacture those
  observations.
. Durable Run state and checkpoints represent or project Coordinator state.
  Recovery may conservatively reconstruct state through core operations, but
  persisted convenience fields must not become an independent source of
  workflow, route, Finding, or authority truth.
. Adapters execute a provider and return execution observations or a candidate
  structured result. Parsing and schema validation at that boundary are
  permitted; Coordinator policy, authority, routing, trusted Git mutation, and
  authoritative Finding transitions remain outside adapters.
. Prompt components, role presentation, provider/model selection, and future
  persona/execution binding remain shell concerns. They must not become
  semantic route predicates in the reducer.
. A consumer's subject area must not require deterministic-core changes merely
  because it is software, spreadsheets, Latin instruction, or another domain.
  Repository/Git assumptions are current execution-substrate constraints, not
  a declaration that WFC is inherently a software-development coordinator.

== Domain generality

Workflow function is not domain persona. A `worker` may be a software
architect/senior developer or a Latin course designer. An `independent
reviewer` may be an adversarial architecture/code reviewer or a Latin
editor/lector.

These are examples, not a binding design. Phase role and components are
configured strings, while provider/model choice stays out of the reducer. A
later concept may generalize bindings without making subject identity a routing
rule; this FTR introduces neither that design nor a generic workflow engine.

== Deferred structural debt: WATCH

=== `operator.py`

`operator.py` combines CLI parsing/reporting, admission/preflight, Run and plan
preparation, context reconstruction, serial Hop orchestration, evidence
handling, and durable summaries. Breadth alone does not authorize extraction.

Decompose only when concrete pressure shows a useful seam: two responsibilities
evolve independently; unrelated setup dominates tests; a feature repeatedly
crosses internal seams; or extraction simplifies the next concrete feature.
Do not add service classes/interfaces merely for layering aesthetics.

=== `vertical.py` and `slice4.py`

These names and compositions retain incremental Slice-3/Slice-4 history.
Do not rename, merge, or consolidate them now. When substantive work naturally
touches these seams, they should either acquire stable domain-oriented
responsibilities and names or be absorbed into better-named orchestration
components. Historical naming alone is not a refactoring reason.

=== `serialization.py`

`serialization.py` centralizes strict validation and conversion for YAML/JSON
manifests, Work Items, policy, profiles, routing results, Run snapshots, and
dispatch markers. Size alone is not a reason to split it.

Revisit only if substantially independent external grammars or configuration
families accumulate and begin changing for independent reasons. Any later
separation should follow those observed change boundaries rather than a target
file size.

== Architecture-test direction

Do not create a broad architecture-test project. When a real feature touches a
load-bearing boundary, add the cheapest narrow guard that protects it. Useful
directions include guards that:

* keep reducer imports and execution free of I/O, provider, network, and
  process effects;
* keep topology and phase transitions declarative rather than phase-name
  branches;
* prove Git/Evidence facts enter reduction as observations rather than being
  created there;
* prevent persistence or checkpoint projections from becoming authority;
* prevent adapters from bypassing Coordinator policy, route, Git, or Finding
  authority; and
* keep domain persona and provider/model binding out of semantic routing.

No tests are authorized or changed by this record.

== Explicit non-goals

This FTR is not authority for:

* splitting `operator.py` now;
* renaming or merging `vertical.py` or `slice4.py` now;
* splitting `serialization.py` now;
* introducing a generic workflow engine;
* adding DDD/application/domain layers for symmetry;
* adding ABCs or interfaces for every component;
* redesigning the Run/Hop/Finding state model;
* building new architecture-test infrastructure; or
* changing production code, tests, governance, policy, profiles, Runtime,
  Run state, or remotes.

== Revisit triggers

Revisit the relevant boundary, without making it mandatory roadmap work, when:

* a real consumer exposes a subject-domain assumption in core semantics;
* role/persona/model/provider binding work would otherwise cross the
  core/effect boundary;
* a module gains responsibilities that demonstrably change independently;
* testing a feature requires substantial unrelated orchestration setup;
* historical slice structure obstructs a concrete feature;
* serialization accumulates independently evolving grammar families; or
* observed consumer use reveals a narrow architecture guard or CLI pain worth
  addressing.

Until one of those pressures is concrete, preserve the boundaries, record the
debt, and continue with consumer work.
