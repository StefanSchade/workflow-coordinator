== H002-R1 -- Publication failure can still leave a consumable artifact

`_discard_export_bundle()` correctly attempts to unlink `manifest.json` before
fallible tree cleanup. If that unlink itself fails, however, it raises while
leaving the already published, parser-consumable manifest in place. The direct
injected-permission probe reproduced exactly that state. This is the explicit
manifest-removal failure that H006-R2 required the correction to cover, and it
still violates the rule that a reported export failure publishes no valid
manifest.

Descriptor publication has the analogous failure shape. After
`_rename_no_replace()` succeeds, `_write_descriptor_no_clobber()` executes a
fallible temporary-path cleanup in `finally`; an injected cleanup error makes
the operation report failure while the final descriptor remains consumable.
`_prepare_successor()` also computes the printed digest by rereading the
already published output without any invalidation path if that readback fails.
Thus preparation can report failure after publication without removing or
invalidating the descriptor.

The new tests cover successful manifest removal followed by failed tree cleanup
and a descriptor rename failure before publication. They do not inject the
manifest-removal failure, descriptor post-publication cleanup/readback failure,
or the required write/permission/verification/finalization combinations at
both public command boundaries.

Required correction: structure each artifact publication so every fallible
verification and cleanup step either occurs before the atomic no-clobber
publication or can atomically invalidate the published artifact without first
depending on the operation being injected to fail. A reported failure must
leave no parser-consumable manifest or descriptor. Add public-boundary tests
for existing entries, races, and injected write, rename, permission,
verification, invalidation/removal, and cleanup failures for both artifact
types, asserting exact filesystem effects.

== H002-R2 -- Launch does not revalidate the predecessor/successor repository relationship

Preparation now correctly compares the selected successor checkout's Git
common-store identity with the predecessor checkout. Launch revalidates the
selected successor path, HEAD, cleanliness, governing digests, descriptor
digest, and predecessor `run.json`, but it no longer compares the launch
checkout's repository-store identity with the repository reread from the
predecessor checkout association. The equality check removed to allow separate
worktrees was not replaced with the common-store check used during preparation.

Consequently a changed predecessor checkout association after preparation can
point at another or unavailable repository while leaving the digested
`run.json` unchanged; a no-salvage launch can still pass
`_validated_successor_descriptor()` and reach the provider-capable boundary.
The descriptor does not carry a predecessor repository identity that closes
this gap. This fails the H006-R3 requirement that preparation and launch both
revalidate a separately selected checkout of the same repository.

The added wrong-repository and wrong-HEAD assertions exercise preparation only.
They do not exercise launch-time repository/HEAD/source-association changes or
assert absence of provider-capable effects for those launch rejections.

Required correction: persist an integrity-bound predecessor repository identity
in the descriptor and, at launch, compare the independently reread predecessor
repository identity with the selected successor checkout using the same
worktree-aware identity rule. Reject changed/unavailable predecessor
association, wrong successor repository, and wrong successor HEAD before state
root creation, checkout registration, adapter construction, or provider
execution. Add positive different-worktree and negative launch-time cases.

== H002-R3 -- The mandatory acceptance matrix remains materially incomplete

The H001 correction adds one successful tracked-binary/different-worktree
lifecycle test, dangling-symlink checks, two helper-level no-clobber tests, one
best-effort cleanup test, and one descriptor pre-publication rename-failure
test. That does not complete H006-R4 or the accepted FTR's mandatory matrix.
Still absent are, among other explicit requirements:

* strict malformed/missing non-null version-2 `SemanticStop` and
  `SuccessorProvenance` cases;
* byte-identical read-only legacy status, replay, and predecessor inspection;
  a version-1 reconcile/resume transition; and an injected failed version-1 to
  version-2 persistence upgrade preserving the exact legacy bytes;
* complete layered-stop serialization/replay plus rejection of another Hop and
  both same-Run recovery APIs;
* the named historical version-1/no-back-patch case;
* one successful full public export/prepare/launch lifecycle proving
  predecessor `run.json`, summary, governing inputs, and evidence remain
  byte-identical; backward-only provenance and distinct Run identity; and no
  inherited scope, authority, Finding, evidence, or accepted commit;
* public export containment for out-of-scope paths, untracked binary/text,
  special files, object-count/per-object/aggregate limits, all tree modes,
  stable identities, tampering between every boundary, sensitive-content
  wording, and selected/unselected/over-limit rendering;
* public preparation and launch mutation cases for predecessor, authority,
  governing input, descriptor, manifest, and selected object content;
* a no-salvage successor launch; and
* a successor that independently earns an authorized mutation through its own
  evidence and trusted commit, plus ordinary evidence-failure and invalid
  `CommitIntent` rejection under successor provenance.

Several present assertions are helper-only even though H006-R4 expressly
requires public/operator boundaries for lifecycle and failure-effect claims.
The green suite therefore proves the newly added narrow paths, not the complete
commissioned acceptance basis.

Required correction: implement the remaining accepted FTR matrix within the
already authorized six ordinary test paths. Use public/operator boundaries for
lifecycle, pre-provider, immutability, and publication-effect claims; helper
tests may supplement but not replace those assertions.
