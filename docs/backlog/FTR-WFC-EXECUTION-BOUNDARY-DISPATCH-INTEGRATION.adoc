[[what]]
== What Slice A is

Slice A connects the already implemented, already reviewed Bubblewrap
primitive `src/workflow_coordinator/execution_boundary.py` to the live
provider dispatch path, through *one provider-neutral seam* used by both
adapters, so that a dispatched agent process can write only where the
Coordinator has authorized it to write and can reach neither `.git` nor the
Git object database.

It is deliberately the *integrity* slice of the three maintainer goals
recorded in the umbrella record. Confidentiality (hiding), per-phase
visibility profiles, elevated privilege and network containment are not in it.

[[a-seam]]
== (a) Integration architecture: one provider-neutral launcher seam

=== The seam

A new module `src/workflow_coordinator/execution_launcher.py` holds one pure
transformation with a single entry point, two implementations of it, and the
Coordinator-side derivation of the value they consume (<<a-carrier>>):

----
@dataclass(frozen=True)
class BoundaryGrant:         # Coordinator-computed per invocation; see <<a-carrier>>
    mode: str                                  # "direct" | "bubblewrap"
    repository: Path                           # canonical, symlink-free
    writable_repository_paths: tuple[str, ...]  # repository-relative, normalized
    readable_host_paths: tuple[Path, ...]       # outside the repository
    writable_host_paths: tuple[Path, ...]       # outside the repository
    provider_channel: Path
    external_scratch: Path | None

@dataclass(frozen=True)
class LaunchPlan:            # the grant, plus what the adapter itself builds
    grant: BoundaryGrant
    argv: tuple[str, ...]
    cwd: Path | None
    environment: Mapping[str, str] | None     # None = inherit, as Codex does today

@dataclass(frozen=True)
class PreparedLaunch:        # what the adapter passes to Popen
    argv: tuple[str, ...]
    cwd: Path | None
    environment: Mapping[str, str] | None
    boundary: str            # "direct" | "bubblewrap"

def prepare(plan: LaunchPlan) -> PreparedLaunch: ...   # dispatches on plan.grant.mode
def prepare_direct(plan: LaunchPlan) -> PreparedLaunch: ...
def prepare_bubblewrap(plan: LaunchPlan) -> PreparedLaunch: ...
----

`prepare_direct` returns the plan's own `argv`, `cwd` and `environment`
unchanged, so an unisolated invocation is byte-identical to today's. It reads
*nothing* from the grant, which is why an adapter constructed without one
behaves exactly as it does today. `prepare_bubblewrap` validates the view
through `execution_boundary.validate()` and returns `build_argv(...) + argv`,
`cwd=None` (the view sets the child's directory with `--chdir`) and the
plan's `environment` unchanged.

`prepare` is the single entry point both adapters call, and it selects the
implementation from `plan.grant.mode` alone; an unrecognised mode is a
refusal, never a direct launch. The adapters therefore cannot select the
boundary, accidentally or otherwise -- which is what makes "no silent
fallback" (<<enablement>>) a structural property of the seam rather than a
rule each adapter has to remember.

=== Why this shape

* *Nothing about process handling moves.* Each adapter keeps its own
  `subprocess.Popen` call, its own `stdin`/`stdout`/`stderr` wiring, its own
  `text=True`, its own `start_new_session=True`, its own `communicate(timeout=
  ...)` and its own `SIGTERM` / three seconds / `SIGKILL` process-group
  sequence. The kill sequence is therefore not duplicated, not re-derived and
  not re-qualified.
* *The transformation is pure.* It can be unit-tested exhaustively without a
  namespace, which matters because an agent sandbox cannot necessarily create
  the namespace a `bwrap` sandbox needs (see the planning record's limits
  section).
* *One seam, not two copies.* Both adapters call the same function; a future
  non-Bubblewrap boundary is a third `prepare_*`, selected by a closed name,
  exactly as `operator._execution_adapter` selects an adapter today "without a
  registry or fallback".
* *`execution_boundary.py` keeps its documented contract.* It remains a view
  validator and argv builder that takes already-authorized grants; it gains no
  process, environment or authority responsibility.

[[a-carrier]]
=== How the grant reaches the launcher

The grant is the security content of this slice, so the surface that carries
it is an architecture decision and is taken here rather than left to the
implementation Run.

*What exists today.* Nothing carries it. `AgentExecutionRequest` carries
`invocation`, `prompt`, `repository`, `result_contract`, `timeout_seconds`,
`contract_version`, `result_contract_kind`, `permitted_routes` and
`finding_authority` and nothing else (`adapter.py:44-69`); there is no field
for a filesystem view, a grant set or a boundary mode. The two CLI adapters
are constructed from an `ExecutionBinding` with only `result_directory`,
`model`, `reasoning_effort` and `executable` (`operator.py:86-98`, `:977-980`;
`claude_adapter.py:191-194`, whose only further field is the defaulted
environment allowlist at `:195`; `codex_adapter.py:393-396`), and
`slice4.run_real_one_hop` default-constructs a `CodexCliAdapter` the same way
when no adapter was injected (`slice4.py:321-326`).

*Decision: the construction axis, not the port.* The Coordinator computes one
frozen `BoundaryGrant` per invocation and passes it to the CLI adapter's
constructor as one optional parameter, `boundary: BoundaryGrant | None =
None`, where `None` means today's unisolated behaviour. The
provider-neutral port is *unchanged*: `AgentExecutionRequest`,
`AgentExecutionOutcome` and `AgentExecutionPort.execute` gain no field
(`adapter.py:44-97`).

Four reasons, in order of weight:

. *A port field would be silently ignorable, which is the shape decision (e)
  forbids.* The port has four implementations under `src/`
  (`adapter.py:105`, `:115`, `claude_adapter.py:284`,
  `codex_adapter.py:417`), and two of them --
  `FakeAdapter` and `SubprocessAdapter` (`adapter.py:100-125`) -- cannot
  honour a filesystem view at all. A request field saying "confine yourself to
  these paths" that some callees ignore is a fallback to unisolated execution
  by construction. On the chosen axis, only an adapter that can honour a grant
  can be handed one, so an ignored grant is not expressible.
. *The port models semantic dispatch facts; the boundary is an execution-
  environment fact.* Every field of `AgentExecutionRequest` is something the
  prompt or the result contract depends on. The execution environment is
  already modelled on the other axis -- the admitted binding, the result
  directory and the executable are constructor arguments -- and the grant
  belongs with them.
. *The boundary mode already arrives on that axis.* Decision (e) puts the
  closed `boundary` key on the Run execution envelope, i.e. on
  `RunExecutionConfiguration` (`model.py:180-192`;
  `serialization.py:1004-1043`, whose `_fields` call at `:1013` must gain
  `optional={"boundary"}` for the key to be accepted at all). `operator.py`
  holds that object exactly where it resolves the binding and constructs the
  adapter (`:966-980`). Carrying the mode and the grant on two different
  surfaces would split one decision in two.
. *Blast radius.* The port is shared by `FakeAdapter`, `SubprocessAdapter`,
  every adapter conformance test and the proof harness; none of them changes.

*Consequences, stated so the implementation Run inherits no open question:*

. *Both construction sites use one derivation function.* The grant is derived
  once, Coordinator-side, by a single function that takes the repository, the
  executing phase, the provider channel directory, the scratch root, the
  authentication path and the selected mode, and returns the normalized grant
  (<<mounts>>). `operator._execution_adapter` (`:86-98`) gains the grant as a
  parameter and its caller computes it; the inputs are all in hand at that
  call site, which already holds `profile`, `phase_key` (`:958`),
  `workflow_role` (`:959`), the resolved binding (`:972`) and `run_root`
  (`:977`). The derivation lives in the launcher module, not in either
  adapter, so a per-adapter copy cannot drift.
. *The second construction path stays explicitly unisolated, and that is not a
  fallback.* `slice4.run_real_one_hop` gains the same optional grant
  parameter, forwarded to its default `CodexCliAdapter` construction
  (`slice4.py:172`, `:321-326`). Its only in-tree caller that relies on the
  default is the Codex proof harness (`proof_harness.py:215-225`), which does
  not pass one and therefore keeps running unisolated exactly as today. This
  is a non-change for a path that never requested a boundary, not a silent
  downgrade of one that did: if a caller passes a `bubblewrap` grant, that
  path honours it or refuses by name, and a `bubblewrap` mode is never
  satisfied by constructing an adapter without a grant.
. *The audit field cannot diverge from the dispatch.* The `boundary` field of
  decision (d)'s mode visibility is projected from the same grant the adapter
  was constructed with, in `_binding_evidence` (`operator.py:677-685`, called
  at `:981`), so there is one source for what ran and what was recorded. The
  injected-adapter branch (`:984-989`) projects `direct`, which is what it is.
. *Slice B's extension point is now named on both sides.* Slice B requires
  that "the profile that the Slice A launcher consumes should be a value the
  Coordinator computes"
  (link:FTR-WFC-EXECUTION-BOUNDARY-PHASE-PROFILES.adoc[Slice B], target
  architecture item 6). `BoundaryGrant` is that value: a later richer
  profile changes the derivation function and the grant's contents without
  changing the port, the seam or either adapter.

*Rejected: boundary fields on `AgentExecutionRequest`.* It would put the grant
where `vertical.run_one_hop` builds the request (`vertical.py:303`, `:332-339`),
which also holds the phase, and it would need no change to either adapter
constructor. It is rejected for reason 1 above: the same field would reach two
adapters that cannot act on it, and fail-closed behaviour would then depend on
a check in each implementation rather than on who can be handed a grant at
all.

[[a-lifecycle]]
=== Who owns the pre-create and post-Hop removal lifecycle

The same Coordinator frame that computes the grant. Materialising an absent
authorized directory target (<<mounts>>) and removing it afterwards are two
ends of one bracket around the Hop, and the adapter can own neither end: its
`execute()` returns before the Hop's post-Hop observation and candidate
acceptance (`vertical.py:400-422`), so an adapter-side removal would run too
early, and an adapter that creates and deletes host directories is no longer a
transport.

Concretely, in `operator.py`'s per-Hop loop body: compute the grant, create
the absent directory targets, construct the adapter with the grant (`:978`),
call `run_real_one_hop` (`:1007-1023`), and after it returns (`:1024`) --
which is after the post-Hop observation inside it -- remove the directories it
created that are still empty. The bracket must also run when the Hop raises,
so it is a `finally`-shaped bracket and a removal failure must not displace an
exception already in flight. The agent never creates and never removes a
grant path, and nothing is created outside the repository. Ordering is stated
for clarity rather than for safety: Git does not track empty directories, so
a still-empty pre-created directory is invisible to the post-Hop delta either
way.

=== What flows through it

[cols="2,5",options="header"]
|===
|Element |Treatment

|argv
|Prefixed, never rewritten. Every absolute path an adapter embeds stays valid
because the repository is mounted at its own path (<<mounts>>).

|cwd
|`--chdir <repository>` inside the view reproduces the Claude adapter's
`cwd=request.repository.resolve()`. Codex passes `--cd <repository>` in argv
and needs no cwd either way.

|environment
|Passed through unchanged. Bubblewrap does not clear the environment unless
asked, and Slice A does not ask: the Claude adapter's allowlist -- four fixed
names plus any name the operator lists in `WFC_CLAUDE_EXTRA_ENV_NAMES`
(`claude_adapter.py:41`, `:44-47`, `:316-319`) -- plus its `TMPDIR` override, and the
Codex adapter's inherited environment, both keep exactly today's meaning. This
is a deliberate non-change; see <<residual>>.

|stdin, stdout, stderr
|Unchanged. `bwrap` passes its own standard streams to the child, so Codex's
prompt-on-stdin and both adapters' piped output keep working. The streams are
the adapter's `Popen` arguments and never appear in the plan.

|timeout, signals, process group
|Unchanged in the adapters. The boundary *improves* this case without being
asked to: `--die-with-parent` is already generated, and with `--unshare-pid`
the `bwrap` process is PID 1 of the sandbox, so every descendant dies with it
rather than surviving as an orphan. The adapters' group signals reach `bwrap`,
which is the process they started.

|result and candidate
|Unchanged in contract. Claude's candidate is still parsed from the wrapper
JSON on stdout; Codex's is still read from the result file the provider wrote.
What changes is only *where* that file lives: in the per-invocation provider
channel directory rather than in the Coordinator's Run state directory, so
that the narrow writable bind the Codex path needs cannot reach Run state or
audit records (<<channel>>).

|scratch
|Unchanged in the Claude adapter: it still creates the invocation-scoped real
directory and the short `/tmp/wfc-claude-<token>` symlink, and still removes
both in its `finally` block. Inside the view the real directory is bound at
the fixed short destination `/tmp/s` and the adapter's `TMPDIR` for the child
is that destination. The host-side symlink remains for the unisolated path.

|usage
|Unchanged. Usage is parsed from the provider's own transport output and is
independent of the boundary.
|===

[[git]]
== (b) Git worktrees, the `.git` view, and what the agent does not need

=== The problem, mechanically confirmed

`execution_boundary.validate()` requires the repository to contain a real,
non-symlink `.git` *directory*. In a linked Git worktree `.git` is a regular
file containing `gitdir: <path>`, and both the per-worktree gitdir and the
common Git directory lie outside the checkout. The primitive therefore refuses
exactly the checkout shape WFC self-development and the documented
one-worktree-per-Run operating pattern actually use. This was reproduced
against this repository's own checkout and against a synthetic
`git worktree add` checkout (planning record, E1 and E2).

=== The decided view

. `validate()` accepts a checkout whose `.git` is *either* a real directory
  *or* a regular file. A symlink at `.git` stays refused in both cases.
. When `.git` is a directory, it is masked as today:
  `--tmpfs <repository>/.git --remount-ro <repository>/.git`.
. When `.git` is a file, a tmpfs cannot be mounted over it. It is masked with
  an *empty, read-only regular file* using bubblewrap's `--ro-bind-data FD
  DEST` (present in `bwrap` 0.11.0 on this host). The implementation
  Commission must confirm by a real `bwrap` run that the result is an empty,
  unwritable regular file and that `git -C <repository> rev-parse` inside the
  view fails; if `--ro-bind-data` turns out unsuitable, `--bind-data` followed
  by `--remount-ro`, or an equivalent that produces an empty unwritable file,
  is admissible. Reaching the real gitdir is not.
. Neither the per-worktree gitdir nor the common Git directory is mounted, in
  any mode. They are already known to the Coordinator from the checkout
  association, which records `canonical_path`, `git_dir` and `common_dir` and
  revalidates them every Hop; the boundary uses those values only to *assert
  that they are not inside the view*, never to mount them.
. The result is a view in which no Git repository metadata, no refs, no index,
  no hooks, no configuration and no object database exist.

=== What the agent does not need

Git is not a capability of an ordinary WFC agent. Every Git write is
Coordinator-owned: the agent reports a CommitIntent and the Coordinator's
trusted commit lands it after the agent has exited, with inherited `GIT_*`
variables stripped, `core.hooksPath` forced to `/dev/null` and `--no-verify`.
An agent that cannot run `git` loses no authorized capability.

It does lose *convenience*: `git log`, `git diff` and `git status` are
ordinary agent habits. Slice A accepts that cost and states it. The prompt and
task text already describe the base HEAD and the authorized scope; a worker
does not need Git to do authorized work. If experience shows a real need, a
read-only Git *service* is a Slice B topic, not a Slice A mount.

=== What the provider CLIs need from Git -- an open qualification question

This is *not* established and Slice A must not assume it away.

* It is *assumed*, on the evidence that `claude --version` completed inside an
  experimentally `/proc`-enabled outer boundary that contained no Git at all,
  that neither CLI requires Git for startup or for producing a structured
  result.
* It is *known* that both CLIs expose a `Bash` tool, and that Claude's tool
  list includes it. A session that chooses to run `git` inside the view will
  see it fail. The qualification must observe what the CLI then does: report
  the failure in its transcript (acceptable), retry in a loop (acceptable but
  wasteful), or abort the invocation (a finding that needs a decision).
* If a live run shows a provider CLI genuinely cannot operate without Git, the
  stop rule (<<stop>>) applies: record it as a blocking Finding with options,
  do not paper over it by mounting the object database.

[[mounts]]
== (c) The mount model

=== Repository view and path identity

The repository is mounted *read-only at its own canonical absolute path*, not
at `/repo`. Both adapters embed the resolved absolute repository path in argv
(`--cd`, `cwd=`) and the Claude settings embed it in `allowRead` while relying
on `blockReadsOutsideWorkingDirectories`; translating paths would mean
rewriting argv, the generated settings, diagnostics and the scratch logic, and
would make the settings file describe a filesystem that does not exist inside
the view. `validate()`'s destination rule and the tests asserting `/repo`
destinations change accordingly; `/repo` stays available for a caller that
asks for it explicitly.

=== Writable grants and the Commission-scope versus phase-scope relation

The writable grant set for an invocation is derived from
`phase.authorized_scope` of the *executing phase*, and from nothing else.

[cols="2,5",options="header"]
|===
|Phase kind |What is mounted writable

|Worker phase (`implement`, `correct` in `robust@v1`)
|Every entry of `phase.authorized_scope`. Under `robust@v1` that slot resolves
to the *complete* Commission Intent scope, which in practice includes the
reviewer-artifact paths. Slice A mounts exactly that and claims exactly that.

|Reviewer phase (`broad_review`, `focused_review`)
|Only that phase's own `durable_artifacts[artifact_key]` paths, because that
is what its `authorized_scope` resolves to -- but at *directory* granularity
whenever the artifact does not yet exist, which is the normal case. See the
qualification immediately below; do not read this row as a phase-isolation
guarantee.

|Any phase
|Nothing else. No write outside the repository except the private `/tmp`, the
external scratch and -- on the Codex path -- the per-invocation provider
channel directory (<<channel>>).
|===

What this is *not*: it is not phase-specific isolation of worker deliverables
from reviewer artifacts, and Slice A must never be described that way. The
guarantee is "no write outside the Commission scope for this phase", which for
a worker phase equals "no write outside the Commission scope".

The reviewer side needs the same care, because the narrower scope slot invites
a stronger claim than the mechanism supports. A reviewer phase's grant is
narrower than a worker phase's, and that asymmetry is real; but it is *not* a
guarantee that a reviewer cannot write a worker deliverable, for a reason that
follows from Slice A's own rule below: a durable review artifact does not
exist when the phase that must create it starts -- that is what makes it the
phase's deliverable -- so the file-shaped not-yet-existing case applies, and
the grant becomes the artifact's nearest existing ancestor *directory*. Where
that directory also holds other records, the reviewer can write them.

This Commission's own data is the illustration rather than an edge case: the
`broad_review` phase's single scope entry is the then-nonexistent
`docs/warm_storage/post-beta-planning/wfc_execution_boundary_broad_review.adoc`
(`.wfc/governance/wfc-exec-boundary-ftr-001/profile.yaml:60-61`), so the grant
would have been the whole `docs/warm_storage/post-beta-planning/` directory --
which holds this slice's own planning record. The honest statement is
therefore: *a reviewer phase is confined to the directories containing its own
authorized artifacts, not to those artifacts.* This is residual risk 3 in
<<residual>>, reached through the reviewer path; Slice A states it rather than
fixing it, because narrowing it is a change to the scope data or to the
artifact layout, and both belong to
link:FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[the phase write-scope
record] and
link:FTR-WFC-EXECUTION-BOUNDARY-PHASE-PROFILES.adoc[Slice B]. The post-Hop
candidate-scope check remains the control that catches an actual out-of-scope
write, exactly as today.

Normalization, required before mounting: `authorized_scope` entries are
canonical relative paths with no globs and no `..`, but nothing deduplicates
nested entries, and `validate()` refuses overlapping destinations. The
launcher therefore drops any entry contained in another, sorts the remainder,
and refuses a scope list that cannot be normalized to a disjoint set.

=== Not-yet-existing authorized targets

A bind source must already exist; a writable `Mount` naming an absent path is
refused (planning record, E3). This is the mechanism behind the
link:BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc[Claude
write-permission] case, where the authorized `docs/developer_guide/` did not
exist at launch.

. For an authorized entry that does not exist and whose shape is a
  *directory* (no file extension is not a reliable signal, so: any entry that
  does not exist is treated as a directory unless the Commission says
  otherwise), the Coordinator creates it, mode `0o700`, before validation, and
  removes it after the Hop *if it is still empty*. Git does not track empty
  directories, so this is invisible to the post-Hop delta and to the
  clean-worktree assertions.
. For an authorized entry that names a not-yet-existing *file*, no empty file
  is created, because an untracked empty file would be visible to the post-Hop
  observation. Instead the nearest existing ancestor directory is mounted
  writable. This *overgrants* to that directory, and Slice A states it as a
  residual prevention gap (<<residual>>); the post-Hop scope check still
  refuses anything outside scope.
. Pre-creation is a Coordinator act, performed before `validate()` by the
  per-Hop dispatch frame that computes the grant and brackets the Hop
  (<<a-lifecycle>>), never by the agent or the adapter, and never outside the
  repository.

=== Symlinks, hardlinks and mount overlaps

Unchanged from the reviewed primitive, and relied upon rather than
re-invented: a writable grant whose tree contains a non-directory inode with
more than one link is refused before launch and again at `build_argv`;
symlink targets resolve inside the view, so a symlink pointing out of the
repository resolves to nothing; `..` in a destination is refused; overlapping
destinations are refused; only regular files and directories may be bound. The
existing integration tests already exercise the hardlink, symlink-metadata and
`..` escape cases against a real `bwrap`.

host content under `$HOME` is reachable other than the designated mounts

which is a live-qualification question (L6).

write, and no guarantee in <<guarantees>> depends on it -- but two things
follow. First, a child can create files at in-view paths that have no host
backing, which a test asserting "the write attempt fails" would get wrong
(N11). Second, an uncapped root tmpfs is a cheaper target for scratch abuse
than the size-capped `/tmp` (N12). The installed build documents
`--remount-ro DEST` as non-recursive, so appending `--remount-ro /` after the
mount arguments should leave the writable binds, the private `/tmp` and the
external scratch untouched. No Hop of this planning Commission could enter a
sandbox to verify that (planning record, limits), so it is an *assumption*:
Layer 1 must measure both the pre-change writability and the post-change
behaviour of every writable grant, and if `--remount-ro /` is recursive or
refuses, the implementation Run reports it and the in-view-only writability
stays a stated residual rather than being papered over.
|===

Process flags in the generated view, for completeness, since they belong to
the same decision: `--die-with-parent` (unchanged), `--unshare-pid` with
`--proc /proc` (above), and `--new-session`, which detaches the sandbox from
the operator's controlling terminal so a child cannot push input back into it.
All three are part of the view Slice A establishes, not optional extras.
`--as-pid-1` must *not* be used: the die-with-parent and
no-leftover-descendant properties depend on bwrap itself remaining PID 1 of
the new PID namespace and reaping orphans there.

[[channel]]
=== The provider channel is separated from the Run state directory

*The fact that forces this decision.* Both adapters are handed one directory
as `result_directory`, and that directory is the Coordinator's own Run state
directory, not a channel: `operator.py:977-980` constructs the adapter with
`result_directory=run_root`, where `run_root =
checkout_state_root(state_root, association)` is `<state_root>/checkouts/<checkout_id>`
(`slice4.py:135-136`). That same directory holds the Coordinator's
authoritative Run state and audit records -- `run.json` (`operator.py:919`,
`slice4.py:319`), `checkpoint.json` (`operator.py:926`), the dispatch marker
`dispatch.json` (`slice4.py:182`, `:320`), `execution-evidence.json`
(`operator.py:885`, `slice4.py:183`) and `usage.json` (`operator.py:841`) --
and they are already present *during* dispatch, because `slice4.py:319-325`
writes the run snapshot and the dispatch marker immediately before
constructing the adapter. They are read back as trusted state afterwards
(`frontdoor/lifecycle.py:709`, `:716`; `frontdoor/archive.py:487-495`). Only
`checkout-association.json` lies one level up (`slice4.py:100`).

Mounting that directory would therefore hand the agent read access to the Run
snapshot and every prior Hop's evidence, and -- on the Codex path, which needs
a writable mount -- write access to the dispatch marker on which this slice's
own not-started/started classification depends, and to the very
`execution-evidence.json` that is supposed to record whether the agent was
isolated (<<provider>>). An agent-writable record of the agent's own
confinement is not an audit trail, and it would contradict the guarantees in
<<guarantees>>. Today only Codex's own `--sandbox workspace-write` keeps that
directory out of reach; since this slice's premise is that the provider
sandbox is not the authoritative boundary, the WFC boundary must not be the
weaker of the two.

*Decision.* The three provider channel files move into a dedicated
per-invocation channel directory under the Run state directory -- for example
`<run_root>/provider-channel/` -- and it is the *channel directory*, never the
Run state directory, that is passed to the adapter and mounted:

[cols="3,2,4",options="header"]
|===
|File |Direction |Mount consequence

|`claude-closed-settings.json` (`claude_adapter.py:308`)
|Coordinator writes before launch; the Claude child reads it by the path in
`--settings` (`claude_adapter.py:217`)
|The Claude path needs the channel directory *read-only* and nothing more. The
result schema is passed to Claude inline as a serialized string
(`claude_adapter.py:214`, `:325`), so Claude never reads a schema file.

|`structured-result.schema.json` (`claude_adapter.py:307`, `:314`;
`codex_adapter.py:433`)
|Both adapters write it before launch; only the Codex child reads it, via
`--output-schema` (`codex_adapter.py:414`)
|Read access on the Codex path; on the Claude path the file lives in the
channel but is never read by the child.

|`result-message.json` (`codex_adapter.py:434`, pre-created empty at `:443`)
|The Codex child writes it via `--output-last-message`
(`codex_adapter.py:414`); the Coordinator reads it back at `:461`
|The Codex path needs the channel directory *read-write*. Because the mount
point is the directory and not the file, a provider that replaces the file by
rename still works.
|===

All three are Coordinator-written before launch, so a bind source always
exists and no pre-creation mechanism beyond the existing writes is needed.

*Rejected alternative:* binding the three files individually at their present
paths inside the Run state directory. It is equally narrow in what it exposes
(bind destinations materialise only their parent chain, so the Run state
directory would appear in the view containing nothing but the three bound
files) and it would require no relocation. It is rejected because a file bind
mount cannot be replaced by `rename()` -- an in-place replacement of the
result file by the Codex CLI would fail with `EBUSY` -- and whether
`--output-last-message` writes in place or renames over the target is an
unverified property of a third-party CLI. The directory form does not depend
on it. Should the relocation turn out to be the more expensive change, this
alternative may be revisited, but then only together with a Layer-1 test that
actually exercises a rename over the bound path.

*Consequences the implementation Commission must carry, and must not
discover late:*

. `operator.py:979` and `slice4.py:321-322` pass the channel directory, which
  the Coordinator creates before dispatch; `claude_adapter.py:191` and
  `codex_adapter.py:393` keep one directory field, now a channel rather than
  the Run state root.
. The archive plan copies allowlisted checkout files at *one* level only
  (`CHECKOUT_ALLOW` globbed against `checkout_dir`,
  `frontdoor/archive.py:96-103`, `:377`, `:402`). Moving
  `result-message.json` and `structured-result.schema.json` into a
  subdirectory removes them from the archive unless the archive is extended to
  the channel subdirectory. The existing depth-one patterns must be kept so
  that recorded historical runs (`tests/fixtures/bp5`, `tests/fixtures/bp7`)
  still archive unchanged, and a test must cover both shapes.
. Tests that assert the present location move with it:
  `tests/unit/test_slice4.py:218`, `:440`, `:496`,
  `tests/unit/test_codex_adapter_smoke.py:83-84`, and the adapter conformance
  tests that build the paths from their own `tmp_path`
  (`tests/unit/test_claude_adapter_conformance.py:66`, `:188`, `:335`, `:448`;
  `tests/unit/test_codex_adapter_conformance.py:141`, `:212`, `:281`, `:425`,
  `:441`, `:515`, `:562`). `codex_adapter_smoke.py:121-175` already uses a
  dedicated `result` directory and shows the shape is workable.
. The relocation is a change to Coordinator-owned state layout and belongs to
  step 1 of <<decomposition>>, before the seam. It changes no result contract
  and no envelope.
. Residual, stated plainly: on the Codex path the agent can still overwrite
  its own schema and result file inside the channel. That is already true
  today and is why `validated_result` correlates the envelope's identity
  against the dispatch (`adapter.py:142-145`). What the separation buys is
  that the Run snapshot, the dispatch marker, the usage record and the
  execution evidence are outside the mount entirely.

[[provider-reachability]]
=== The provider executable must be reachable inside the view

*Precondition, stated positively:* for an invocation with the boundary
selected, the provider executable and everything it loads at runtime -- its
own install tree, its bundled JavaScript or runtime files, and the interpreter
named in its shebang -- must resolve to paths that exist inside the view, which
in Slice A means under `/usr` or the four `/bin`-family links.

*Why this must be decided here and not left to the implementation Run.* On the
host designated for the live qualification this precondition does not hold
today: neither CLI is present at a view-visible path (`/usr/bin/claude`,
`/usr/local/bin/claude`, `/usr/bin/codex` and `/usr/local/bin/codex` do not
exist, while `/usr/bin/bwrap`, `/usr/bin/node`, `/usr/bin/env`, `/usr/bin/sh`
and `/usr/bin/python3` do), and `PATH` resolves provider tooling through two
`$HOME`-local entries that are deliberately not mounted (planning record, E6).
Preflight check 5 would therefore refuse *every* isolated invocation on that
host. The refusal is the correct direction, but without a stated remedy the
whole Layer-2 qualification -- which gates every preventive-isolation claim in
every document (<<qualification>>) -- would have no performable precondition.

*Decision: option (a), an operator-side prerequisite.* The provider CLI is
installed, by the operator, at a view-visible path (for example under
`/usr/local/bin` with its runtime likewise under `/usr`), and that is recorded
as a precondition of enablement (<<enablement>>) and of the live layer
(<<qualification>>). This adds no mount kind, no code path and nothing to
<<outside-sources>>.

*Option (b), considered and not taken:* a fourth designated, individually
validated read-only external mount kind for the provider install tree. It
would make a `$HOME`-local or version-manager-managed install usable, which is
a real operational convenience, but it extends the enumeration the maintainer
is being asked to authorize (planning record, M7) and it binds a directory
whose contents the operator did not enumerate. It is therefore *not* taken by
this record and *not* available to the implementation Commission on its own
judgement: if the maintainer prefers it, that is an addition to M7 and the
mount kind is implemented with the same separate-named-parameter discipline as
the other three. If neither option is in place when the Commission reaches
Layer 1 or the maintainer reaches Layer 2, the stop rule (<<stop>>) applies --
an unreachable provider is never a reason to widen the view ad hoc.

*Where the Layer-1 fake provider lives.* Layer 1 dispatches a fake provider
through the real path, so the same precondition applies to it. The fake
provider executable is placed *inside the synthetic repository the test builds
under its own `tmp_path`*, which the boundary mounts read-only at its own
absolute path, and its shebang names `/usr/bin/env python3` or `/bin/sh` --
both view-visible. This keeps Layer 1 independent of any host provider install
and offline, and it places no artifact in the WFC repository itself. Three
consequences for the ported fixtures, all cheap but none automatic:

* The executable must be *committed in the synthetic repository's baseline
  commit*, as `PROOF.md` already is (`tests/unit/test_slice4.py:54-63`),
  because an untracked executable would show up in the Coordinator's post-Hop
  observation of that repository as an unauthorized change.
* Today's fake providers are written into `tmp_path` *outside* the repository
  (`tests/unit/test_slice4.py:73`), which the boundary does not mount. Those
  fixtures stay valid for the unisolated path; the boundary-selected variants
  need the in-repository placement.
* Some fixtures write side files into `tmp_path` as well (`:1059`, `:1112`).
  Under the boundary those paths are not writable, so such a fixture must
  write into the channel directory or the scratch instead.
* One existing fake provider runs `git add`, `git commit` and `git rev-parse`
  inside the repository to produce the commit its test then observes
  (`tests/unit/test_slice4.py:1114-1116`). That shape *cannot* be ported to a
  boundary-selected variant: under the decided `.git` view the object database
  and the index are not there (<<git>>), so Git inside the sandbox fails by
  design. A boundary variant of that scenario must have the fake provider
  leave worktree mutation only and let the Coordinator's trusted commit
  produce the commit, which is the normal worker shape anyway. Stated here so
  the implementation Run reads a decided consequence rather than debugging a
  confusing fixture failure.

[[outside-sources]]
=== Outside-repository sources: which rule each category passes through

The 2026-11-08 authorization fences `validate()`'s repository-only bind-source
rule (`source.relative_to(repository)`, `execution_boundary.py:124-127`) and
permits exactly *one* designated exception, today's external scratch root
(`:139-156`). Slice A requires more than one outside-repository path, so it
must say per category which mechanism carries it and how far the fence moves.
Nothing here is left to the implementation Run's judgement.

[cols="3,2,5",options="header"]
|===
|Category |Mechanism |Consequence for the fence

|`/usr`, the `/bin`-family links, `--dev /dev`, `--proc /proc`
|Generated inside `build_argv` (`execution_boundary.py:166-172`); not `Mount`
values at all
|None. These never reach the `Mount` loop and are unaffected by the
bind-source rule, today or in Slice A.

|The private `--tmpfs /tmp`
|A caller-supplied `Mount` of mode `SCRATCH` with *no source*, handled by its
own branch (`execution_boundary.py:117-119`) before the bind-source branch is
reached
|None, and unchanged: it has no source to check. Slice A adds only a `--size`
cap to it.

|The narrow `/etc` set
|*Generated system-view entries,* in the same place and the same form as
`/usr`: fixed absolute host paths, identical for every invocation on a host,
read-only, individually enumerated in code, never caller-supplied
|Formally outside the fenced rule, because they are not caller-designated
`Mount` values. Slice A does *not* rely on that technicality: it is a real
widening of the generated view and the umbrella record names it as such.

|The per-invocation provider channel directory (<<channel>>) -- *not* the Run
state directory that contains it
|*A designated, individually validated external mount kind:* a new named
parameter beside `external_scratch`, with its own checks modelled on
`:139-156` -- must exist, must be a directory, must be disjoint from the
repository, from every system root and from every other mount source, its
destination must not overlap another, and a writable grant still runs the
hardlink-alias walk. One additional check belongs to this kind so that passing
`run_root` by mistake cannot satisfy it: the source directory must contain no
entry named `run.json`, `checkpoint.json`, `dispatch.json`,
`execution-evidence.json` or `usage.json` (<<channel>>)
|*Second* designated exception. The generic rule for undesignated
caller-supplied mounts is unchanged.

|The provider authentication location
|*A designated, individually validated external mount kind* of the same form,

proves necessary
|*Third* designated exception. It cannot be a generated system-view entry: its

|Anything else outside the repository
|None
|Refused by the unchanged generic rule. No new caller-supplied path kind, no
pattern, no allowlist, no configuration that could add one.
|===

Four consequences the implementation Run must act on:

. Each designated kind is a *separate named parameter with its own validation*,
  never a general relaxation of `source.relative_to(repository)` and never a
  shared "external mounts" list. Negative case N16 proves that an arbitrary
  host path is still refused through every one of them.
. Every designated destination must be rejected if it lands *inside the
  generated system view*. Today's overlapping-destination check compares
  caller-supplied destinations only with one another
  (`execution_boundary.py:114-116`) and never with `/usr` or the
  `/bin`-family paths, so overmounting a system path is not currently refused
  by anything. Slice A adds that check rather than assuming it exists; see
  also <<provider-reachability>>, where this is the reason an install cannot
  simply be bound into `/usr/local/bin`.
. The widening from one designated exception to three, plus the enumerated
  `/etc` entries, *exceeds the 2026-11-08 authorization's own fence*. It is
  recorded as an open maintainer decision (planning record, M7) and the
  umbrella record's supersession marker names all three categories. The
  implementation Commission does not take this widening on its own judgement;
  the maintainer takes it when commissioning. If it is not taken, the stop rule
  (<<stop>>) applies rather than a quietly reduced boundary.
. The `/etc` set and the authentication path are both *live-qualification
  outputs* (L6). Until L6 has run, the sets written in this record are
  assumptions, and the implementation must add only what L6 observed.

=== The credential-exposure consequence, stated explicitly

The boundary must expose the provider's own authentication to the provider
process and nothing more. Four rules, all of which the 2026-11-08
investigations established the need for:

. No blanket `$HOME` bind, and no bind of a whole provider configuration
  directory when a single file suffices.
. No credential file, token, key or authentication material is ever copied
  into the repository, the external scratch or any agent-writable path.
. No token is injected through an environment variable merely to make a test
  pass.
. The authentication location is mounted *read-only*, and the fact that the
  provider's own tool layer can still read what the provider process can read
  is accepted by the 2026-11-09 product-scope decision and must be restated,
  not quietly relied upon: WFC treats the provider application's own
  mechanisms as sufficient to protect that provider's own authentication from
  agent-driven tools. Slice A does not weaken that and does not improve it.

Which path this is, for each provider, is a *live qualification output*, not an
assumption of this record. The implementation must fail closed when the
required path is not configured: an opt-in boundary that silently omits the
authentication mount would turn every isolated Run into an authentication
failure.

[[provider]]
== (d) Provider configuration inside the boundary

=== The rule

Provider configuration may become more permissive *only* on an invocation for
which the WFC boundary was actually validated and entered. The value that
selected the boundary and the value that selects the provider profile are the
same value, computed in the same call. There is no global setting, no
environment variable and no configuration file that can make a provider
profile permissive on an unisolated run.

=== How an operator can tell which mode a Run used

Three places, all already existing surfaces:

. The per-Hop binding evidence gains one field, `boundary`, with the closed
  values `direct` and `bubblewrap`, projected beside `adapter`, `executable`,
  `model` and `reasoning`.
. The audit projection's closed field allowlist and its per-binding field set
  gain the same field, so `wfc audit` and `wfc report` show it. A Run whose
  projection carries no `boundary` field is, unambiguously, a Run from before
  this slice.
. The Run's own persisted state carries it, so recovery and `wfc resume`
  cannot silently resume an isolated Run unisolated: a resumed Hop must use
  the same boundary mode, and a mismatch is a refusal by name.

A provider profile that differs because the boundary was in force must be
derivable from that field plus the committed adapter code. The generated
Claude settings file already persists in the provider channel directory
(<<channel>>) for the invocation's lifetime; Slice A does not add a second
copy of it to the evidence. Note that `execution-evidence.json`, which carries
the new `boundary` field, stays in the Run state directory and is therefore
outside the view -- an agent cannot read or alter the record of its own
confinement.

[[enablement]]
== (e) Enablement, preflight, error classification and fail-closed semantics

=== Selection

Opt-in, per Run, through the execution envelope; absent means today's
behaviour exactly.

* `run_execution_configuration_from_yaml` gains one *optional* top-level key,
  `boundary`, with the closed values `direct` and `bubblewrap`, defaulting to
  `direct`. Its vocabulary is closed, so the key must be added explicitly;
  adding it as optional keeps every existing envelope, Run, archived Commission
  and test valid.
* `consumer_config_from_yaml` gains the same optional key so a repository can
  state its default. `.wfc/config.yaml` is outside this repository's scope
  ceiling, so the implementation Commission adds the schema and the
  documentation; editing this repository's own config to switch the boundary on
  is a maintainer act.
* Per-adapter and per-phase selection are *not* offered. A security property
  that depends on which model a phase is bound to is a trap, and per-phase
  boundaries are Slice B's subject.
* Default-on is *not* decided here. It is an open maintainer decision
  (planning record, M1), to be taken after the exit criteria in
  <<qualification>> are met for both adapters.

Rationale for opt-in over default-on: default-on changes the behaviour of
every existing Run, configuration and test at the same moment as introducing
the mechanism, and makes the first observed failure mode "my Run stopped
working" rather than "my Run is isolated". Migration path: opt-in, then the
maintainer's own use on this repository, then the qualification record, then a
separate maintainer decision about the default.

Host prerequisites for selecting `bubblewrap`, which the operator must satisfy
and which the documentation step of <<decomposition>> must state in the
Operator Manual: `bwrap` installed, unprivileged user namespaces usable, a
configured provider authentication location, and the provider CLI with its
runtime installed at a view-visible path (<<provider-reachability>>). None of
them is satisfied silently and none is worked around by the implementation;
each unmet prerequisite is a named preflight refusal.

=== Preflight, before any provider dispatch

Each check fails with a named `OperatorPreflightError`-class refusal that
identifies the missing piece. All of them run only when the boundary is
selected.

. `bwrap` resolves to an executable file.
. An unprivileged user namespace can actually be created: one
  `bwrap ... -- /bin/true` probe. This is not redundant with check 1 -- on
  this very development machine, inside a nested sandbox,
  `/proc/sys/user/max_user_namespaces` reads `0` and the probe fails while the
  binary is present.
. The repository is a canonical, symlink-free, existing directory whose `.git`
  is a directory or a regular file, not a symlink.
. The provider channel directory and the external scratch root exist, are
  directories, and are disjoint from the repository and from each other; and
  the channel directory contains none of the Coordinator state file names
  listed in <<channel>>, so that a Run state directory passed by mistake is
  refused rather than mounted.
. The provider executable resolves to a path that exists *inside the view*.
  A provider installed under `$HOME` -- and this host's `PATH` contains two
  such entries -- is not reachable from a view that mounts only `/usr` and the
  four `/bin`-family links, and must be refused by name before dispatch
  rather than discovered as a confusing exec failure. The refusal must name
  the operator-side remedy stated in <<provider-reachability>>: install the
  CLI and its runtime at a view-visible path. Note that the check can only
  establish that the executable *itself* resolves inside the view; whether
  everything it loads at runtime does is a Layer-2 observation (L1, L6), not a
  preflight property.
. The authentication mount required for the selected adapter is configured and
  exists.
. The normalized writable grant set is disjoint and every entry is inside the
  repository.
. Every path the adapter writes into a provider's own generated configuration
  names a location that exists *inside the view*. For Claude this is
  `sandbox.filesystem.allowRead`/`allowWrite`
  (`claude_adapter.py:231-232`) and `TMPDIR`; a settings file that describes a
  filesystem the child cannot see is a silent denial, which is the failure
  mode this check exists to turn into a named refusal.

=== Error classification

* Every preflight failure, and every `BoundaryConfigurationError`, is
  *not-started*: it proves the execution port was not entered. Both adapters'
  own error types already subclass `ExecutionNotStartedError`, and a new
  boundary error must join that hierarchy so the existing dispatch-marker
  cleanup and re-raise path applies unchanged.
* A `bwrap` process that starts and then exits before the provider command is
  *also* not-started, and is distinguishable: `bwrap` writes its own
  diagnostic to stderr and exits non-zero without the provider having run. The
  implementation must classify it by `bwrap`'s own exit path, not by guessing
  from output text. The existing asymmetry in which `CodexCliError` is wrapped
  into `Slice4Error` while `ClaudeCliError` takes the generic
  `ExecutionNotStartedError` branch must be made consistent for the new error
  rather than copied.
* A provider that starts inside the boundary and then fails is *started*, and
  reaches the existing `ExecutionResultValidationError` path with its
  transport outcome. Nothing changes here.

=== No silent fallback

If the boundary was selected and cannot be established, the invocation is
refused. There is no retry without the boundary, no degraded mode, no
"boundary unavailable, continuing" diagnostic, and no configuration that makes
such a fallback possible. A test must prove this by making the boundary
unestablishable and asserting a refusal rather than an unisolated dispatch.

=== Timeout, kill and cleanup

Unchanged in the adapters, with one gained property: `--die-with-parent`
combined with `--unshare-pid` means the sandbox's whole process tree dies with
the `bwrap` process the adapter started, so a descendant that leaves its
process group no longer survives. Scratch cleanup stays in the Claude
adapter's `finally` block; the pre-created empty authorized directories are
removed, if still empty, by the Coordinator dispatch frame that created them,
after the Hop returns and after its post-Hop observation (<<a-lifecycle>>) --
not by the adapter, which has returned by then. A cleanup failure must
not suppress an exception already in flight, as the existing scratch-removal
helpers already ensure.

[[qualification]]
== (g) Qualification plan

Three layers. None of them may be substituted for another, and a positive
claim may never stand in for a missing layer.

=== Layer 1: deterministic tests through the real dispatch path

Offline, network-free, no provider credentials, fake providers. These are the
implementation Commission's own deliverable and part of the required suite.
The fake provider executable lives inside the synthetic repository each test
builds, for the reason and with the consequences stated in
<<provider-reachability>>; no Layer-1 case depends on a provider CLI being
installed on the host.

Positive cases:

. A worker-shaped invocation dispatched through the real
  `vertical.run_one_hop` path with a fake provider executable, with the
  boundary selected, writes a file inside the authorized scope and the
  Coordinator accepts the candidate.
. The same for an authorized target *directory that did not exist* at launch.
. A reviewer-shaped invocation writes its own durable artifact, and writes
  nothing *outside the directory that artifact lives in*. The assertion must be
  phrased that way and not as "nothing else": a reviewer artifact does not
  exist when its phase starts, so its grant is the artifact's parent directory
  (<<mounts>>, residual risk 3). A test asserting artifact-level confinement
  would assert a property the boundary does not have. The companion assertion
  is that a write *outside* that directory is prevented.
. The provider channel works in both directions: the fake Claude-shaped
  provider reads the generated settings file from a read-only channel mount,
  and the fake Codex-shaped provider writes the result file -- in place and,
  separately, by rename over it -- that the Coordinator then reads back
  (<<channel>>). The rename variant is what justifies the directory-level
  mount over per-file binds.
. A linked Git worktree validates and dispatches successfully.
. An unisolated invocation produces a byte-identical argv, cwd and environment
  to today's, proving `prepare_direct` is a true identity.

Negative cases, each attempting the forbidden access *through the real
dispatch path with a real `bwrap`*, and each asserting both that the attempt
failed and that the host-side target is unchanged:

[cols="1,6",options="header"]
|===
|# |Attempt

|N1
|Write to a repository path outside the authorized grant.

|N2
|Write inside `.git` -- a new file, an existing file, a hook, the index.

|N3
|Read `.git`, a ref, the index, or an object by path, in both the
`.git`-directory and the `.git`-file worktree shape.

|N4
|Reach the Git object database through the per-worktree gitdir path and

worktree.

|N5
|Escape through a symlink inside a writable grant that points outside the

|N6
|Escape through `..` from a writable destination.

|N7
|Escape through a hardlink alias created before launch (already covered by
the existing tests; re-asserted through the dispatch path) and through one the
sandbox tries to create itself.

|N8
|Create a new mount, or a new user namespace that re-mounts a host path, from
inside the sandbox.

|N9
|Create a file at a repository path the Commission did not authorize, when
that path's parent *is* authorized and when it is not.

|N10
|Read the operator's `$HOME` beyond the materialised ancestor chain of the

|N11
|From the Codex-shaped path, with the provider channel directory bound

|N12

remaining the namespace's PID 1 and reaping orphans there (<<mounts>>).

|N14
|Boundary selected but unestablishable: assert a named not-started refusal and
assert that no provider process was started at all -- no silent fallback.

|N15
|A scope list that cannot be normalized to a disjoint set is refused before

|N16
|Pass an arbitrary host path through *each* of the designated external mount

and assert that each is refused by its own named check, including that a Run

kinds did not become a general loosening of the repository-only bind-source
rule (<<outside-sources>>). The same case asserts that an undesignated
caller-supplied `Mount` with an outside-repository source is still refused.
|===

=== Layer 2: live qualification with real authenticated providers

Required before any preventive-isolation claim is made in any document. It is
*not* a Commission deliverable: an agent Hop on this host cannot start `bwrap`
at all (planning record, limits). The maintainer or Level-1 operator performs
it outside a Commission, against a disposable repository, with a stated
minimal invocation budget.

*Stated precondition, which does not hold on the qualification host today.*
L1 to L6 all begin by starting a real provider CLI inside the boundary, so
each of them requires the provider executable and its runtime to be reachable
in the view (<<provider-reachability>>). On the host designated for this
qualification neither CLI is at a view-visible path at the time of writing, so
preflight check 5 would refuse every isolated invocation and none of L1 to L6
could start. Preparing the host -- installing the CLI and its runtime
view-visibly -- is therefore the first step of the live layer, and if it is not
done the honest outcome is "L1 to L6 not performed, precondition unmet", never
a substitute claim.

[cols="1,4,4",options="header"]
|===
|# |Check |What it proves

|L1
|`claude` starts inside the boundary and completes one minimal authenticated
`-p` invocation returning a valid structured result, with
`sandbox.failIfUnavailable: true` unchanged and
`enableWeakerNestedSandbox` unset.
|That the outer boundary and the provider's own nested sandbox coexist. A

relax the provider.

|L2

|That the nested sandbox's own bridge, including its `AF_UNIX` socket under

|L3

|The Codex path and the provider channel's writable mount end to end, with the

|L4

|The positive case the
link:BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc[Claude

|L5
|For each provider: an instructed write outside the authorized scope, and an

|That the boundary, not the provider, is what prevents it -- the negative case

|L6

|That the exposed set is the necessary set rather than a guess. The `$HOME`

be necessary; if it is, that is a Finding with options under <<stop>> and a

|L7
|The boundary mode appears in the Run's audit projection and report.
|Operator-visible auditability.
|===

Authentication handling for the live layer: the maintainer's existing,
lawfully-held provider authentication is used *in place*, mounted read-only at
its own path into the view. Nothing is copied, printed, committed, or placed
in the repository or the scratch. No `$HOME` is granted. If a check cannot be
performed within those bounds, that is a valid reported outcome. A missing or
impossible live qualification is reported as missing; it is never replaced by
a deterministic-test result, an argv inspection or a positive claim.

=== Exit criteria

. Layer 1 complete, in the required suite, passing under the Coordinator's
  task-check, with every N-case asserting host-side non-effect, and with the
  sandbox-root measurement N12 requires recorded either way.
. Layer 2's L1 to L7 performed and recorded, or each unperformed check named
  with its reason.
. A qualification record exists that states, per claim, which layer
  established it.
. Only then may any document say WFC preventively enforces a phase's
  authorized scope, and only for invocations with the boundary in force.

[[stop]]
== (i) Stop rule for the implementation Run

If any requirement in this record cannot be realised as specified, the
implementation Run must end with a blocking Finding or an honest stop. It must
not lower the security claim to make the work fit.

Specifically, the Run must stop or open a Finding rather than:

* mount the Git object database, the gitdir or the common Git directory to
  make a provider or a convenience work;
* mount `$HOME`, a whole provider configuration directory, or `/etc`
  wholesale;
* mount the Coordinator's Run state directory, or any directory containing
  `run.json`, `checkpoint.json`, `dispatch.json`, `execution-evidence.json` or
  `usage.json`, in place of the provider channel (<<channel>>);
* widen the view in order to reach a provider installed outside it, instead of
  refusing and naming the prerequisite (<<provider-reachability>>);
* disable, weaken or default-away a provider sandbox or permission mechanism,
  including `enableWeakerNestedSandbox` and `failIfUnavailable: false`;
* make the repository view writable beyond the normalized authorized grant;
* introduce any fallback to unisolated execution, including a diagnostic-only
  one;
* carry the grant or the boundary mode on a surface an adapter can ignore, or
  construct an adapter without a grant while a `bubblewrap` mode was selected
  for that invocation (<<a-carrier>>);
* settle the sandbox-root writability question by assumption in either
  direction instead of measuring it, or drop the measurement because the
  host-side guarantee holds anyway (<<mounts>>, the sandbox root row);
* relax, skip or make conditional the post-Hop candidate-scope check, the
  clean-worktree assertions or trusted Git's refusals;
* weaken or delete an existing test to make a change pass;
* describe a deterministic fake-provider result as a live qualification; or
* claim preventive isolation while any exit criterion is unmet.

A requirement that turns out to be unrealisable is recorded as an open
decision with options and a recommendation, for the maintainer.

[[decomposition]]
== (j) Decomposition, scope, budget and documentation impact

=== One Commission, five ordered internal steps

Recommendation: *one* implementation Commission, not two. Splitting would
leave an intermediate integrated state in which the boundary is half-wired,
which is the condition the maintainer's intent exists to end, and `robust@v1`
already provides an independent review at every cycle. The ordered steps below
are review checkpoints inside that Run, not separate Commissions:

. *Provider channel separation.* Move the three provider channel files out of
  the Run state directory into the per-invocation channel directory, adjust
  `operator.py`, `slice4.py` and both adapters' directory field, extend the
  archive plan to the channel subdirectory while keeping its existing
  depth-one patterns, and move the tests that assert the old location --
  exactly as <<channel>> specifies. This comes *first*: it changes no boundary
  behaviour, is independently reviewable, and the mount model depends on it.
. *Boundary view.* `execution_boundary.py`: the `.git`-file worktree case,
  path-identity mounting, the two new designated external mount kinds (the
  provider channel and the provider authentication location, each a separate
  validated parameter with its own checks),
  the enumerated `/etc` entries in the generated system view, `--proc` /
  `--unshare-pid` / `--new-session` (and not `--as-pid-1`), the `/tmp`
  size cap, and the measured decision about `--remount-ro /` for the sandbox
  root (<<mounts>>) -- classified exactly as <<outside-sources>> requires, and subject
  to the open maintainer decision named there. Unit and integration tests,
  including every negative case reachable at this level.
. *Launcher seam and its carrier.* `execution_launcher.py` with
  `BoundaryGrant`, `LaunchPlan`, the single `prepare` entry point,
  `prepare_direct`, `prepare_bubblewrap` and the Coordinator-side grant
  derivation; the `boundary` constructor parameter on both CLI adapters; the
  forwarded optional parameter on `slice4.run_real_one_hop`; both adapters
  calling the seam instead of building `Popen` arguments inline. The
  provider-neutral port is not touched (<<a-carrier>>). Byte-identity tests
  for the direct path, and a test that an unrecognised mode refuses.
. *Enablement, lifecycle and evidence.* The optional `boundary` key in both
  configuration schemas, preflight, error classification, the pre-create and
  post-Hop removal bracket in the dispatch frame (<<a-lifecycle>>), the
  persisted Run state, the binding evidence and the audit projection, resume
  consistency. Negative cases N14 and N15.
. *Documentation reconciliation.* The stale-statement list below.

If the Run exhausts its Hop budget, step 5 is the only step that may be
carried by a successor Commission: it changes no security property. Step 1 is
mechanical -- a relocation plus an archive-plan extension plus test moves --
and is costed inside the budget below rather than as a Hop of its own.

[[residual]]
== (h, continued) Residual risks, honestly stated

. *Mutable-source assumption.* The primitive's own docstring already says it:
  sources must remain stable between validation and execution. `build_argv`
  revalidates, which narrows the window but does not close it. An actor who
  can change the mount tree concurrently with validation is out of the threat
  model.
. *Hardlink and TOCTOU limits of the validator.* The `st_nlink != 1` defence
  is a point-in-time check over the writable tree. It is effective against an
  alias that exists at validation time and is re-checked at launch; it is not
  a proof against a concurrent creator, and it is a full-tree walk whose cost
  grows with the grant.
. *File-shaped not-yet-existing scope entries overgrant* to the nearest
  existing ancestor directory (<<mounts>>). Prevention gap, not acceptance
  gap. Its most important instance is the *reviewer* phase: a durable review
  artifact never exists when its phase starts, so every reviewer grant is a
  directory grant, and this is exactly why the reviewer-side asymmetry in
  <<mounts>> is stated as confinement to a directory rather than to an
  artifact. A cheaper mitigation exists -- one directory per artifact, or
  pre-created placeholder files that the post-Hop observation tolerates -- but
  choosing one is a change to the artifact layout or to the scope data, and
  Slice A deliberately leaves it to
  link:FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[the phase write-scope
  record] rather than inventing a mechanism here.
. *Worker-phase grants are Commission-wide.* Stated in <<guarantees>>; the
  cause is the program's scope slot, not the boundary.
. *`/proc` exposure.* `--unshare-pid --proc /proc` still exposes host-global
  procfs entries whose sensitivity is unassessed. Named, not resolved.
. *No network statement.* The sandbox shares the host network namespace. An
  agent with network access can transmit anything it can read; the effective
  control is what is readable at all, which is Slice B.
. *Codex inherits the Coordinator's whole environment* inside the boundary,
  exactly as outside it. Any token-bearing variable in the Coordinator's
  environment is visible to the Codex process. Slice A deliberately does not
  change this, because narrowing it risks breaking Codex authentication and
  needs its own qualification. It is a real residual exposure and belongs on
  the follow-up list, not in a guarantee.
. *The provider's own tool layer sees what the provider process sees.* Inside
  the boundary this includes the narrowly mounted authentication path. This is
  the condition the 2026-11-09 product-scope decision accepts; Slice A
  restates rather than resolves it.
. *Nested user namespaces are not always available.* Observed on this very
  host inside a nested sandbox. Where the provider's own sandbox cannot
  initialize and `failIfUnavailable` is `true`, the invocation refuses. That
  is the correct failure direction, and it is a usability risk the
  qualification must measure rather than a security risk.
. *The provider channel stays writable on the Codex path.* The agent can
  overwrite its own result file and its own schema inside the channel
  directory, exactly as today; `validated_result`'s identity correlation
  (`adapter.py:142-145`) is what makes that harmless. What the separation in
  <<channel>> buys is that the Run snapshot, the dispatch marker, the usage
  record and the execution evidence are outside the view altogether. A
  narrower per-file grant was rejected for a stated mechanical reason, not
  overlooked.
. *The boundary depends on an operator-prepared host.* A view-visible provider
  install (<<provider-reachability>>) is a prerequisite the operator must
  satisfy, and on the current qualification host it is not satisfied. The
  failure direction is a refusal, so this is an availability cost rather than
  a security gap -- but it is the reason an unprepared host cannot produce any
  isolation claim at all.
. *The boundary can be off.* Opt-in means most Runs will not have it until the
  maintainer changes the default. Every claim is conditional on the recorded
  boundary mode for that Run.
. *In-view writability that reaches no host path is not yet measured.* bwrap's
  own base tmpfs, including the directories it materialises to carry bind
  destinations, is presumably writable for the child (<<mounts>>, the sandbox
  root row). No host guarantee depends on it, and Slice A intends
  `--remount-ro /` to close it, but whether that works as documented could not
  be tested by any Hop of the planning Commission. Until Layer 1 measures it,
  this is an explicitly marked assumption rather than a property, and it is
  the reason N11 asserts host-side identity rather than the failure of the
  write attempt.

== Non-goals

This slice does not: design or implement network policy or egress control;
design or depend on an MCP sidecar or any other service; hide any repository
area from an agent; introduce per-phase visibility or capability profiles;
implement privilege elevation or defensive-review topology; confine evidence
commands; narrow worker-phase `authorized_scope`; change the accepted
`robust@v1` program; introduce a credential broker; replace a provider
sandbox; claim hostile-code containment; or add a governance layer, program,
gate or role.
