== Problem and motivation

WFC `0.1.0b1` installs from PyPI and its CLI is qualified with both provider
adapters. Installing it does not tell a new Level-1 agent how to operate it:
the wheel contains no documentation, and the procedure lives in the
link:../operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#consumer-quickstart[consumer
quickstart] and
link:../operator_manual/ch10_level1_orchestration/_chapter.adoc#level1-orchestration[Level-1
orchestration], which an agent in an unfamiliar repository never sees.
Self-hosting worked because the operator carried that knowledge in standing
instructions and earlier sessions.

Target: a fresh Claude Code or Codex agent discovers the WFC operating
procedure, knows when it applies, and operates an installed WFC correctly in
an unfamiliar repository, with one extra command from the human and no
recurring upkeep beyond keeping the skill text true.

== Chosen direction

Ship one provider-neutral https://agentskills.io/specification[Agent Skill]
inside the wheel and install it with an explicit command, `wfc skill
install`, into the chosen host's skill directory.

* *In the wheel*, because the skill must describe exactly the CLI the agent
  will drive, must work offline, and should not need a second release
  channel.
* *An explicit command*, because a wheel has no install hook and an implicit
  write into agent configuration is excluded; and because the host path
  table, conflict handling and the dirty-tree warning are what a documented
  `cp -r` gets wrong.
* *One skill, two destinations*, because the two hosts share no skill
  directory.
* *Bound by content*: the installer copies the packaged bytes unchanged and
  records their digests; freshness is a byte comparison with the executing
  package.
* *User scope by default*, because `wfc run` refuses a dirty tree and an
  untracked skill directory in the consumer repository is one.

[[non-goals]]
== Non-goals

* No general skill or plugin manager: no registry, no third-party skills, no
  `update` or `uninstall` command, no host auto-detection, no all-hosts
  status.
* No change to the deterministic core, the reducer, the adapters, admission,
  the Trusted Commit or any existing subcommand's behaviour or output.
* No delegation mechanism of any kind: no file, flag or record by which
  authority is granted to an agent (<<authorization>>).
* No write to `CLAUDE.md`, `AGENTS.md`, `.gitignore`, host settings or
  permission files, and no Git commit by this command.
* No Claude Code plugin, marketplace manifest or Codex `agents/openai.yaml`.
* No conversion of the Operator Manual into the wheel and no generated
  skill text.
* No version bump: `pyproject.toml` and `implementation_identity.VERSION`
  stay as they are; the bump belongs to the release.
* No new dependency.

`agent_skill/` is a data directory beside `resources/`, without an
`+__init__.py+`, declared like `resources/roles/`. It is separate because
`resources/` holds the four digest-pinned execution inputs and the skill is
not one: the skill files are not added to
`implementation_identity.RESOURCE_DIGESTS`. They are covered by
`implementation_tree_sha256`, which already hashes the whole package
directory; that digest therefore changes with S1, and a test that pins it or
a file count is updated knowingly, not worked around.

[[skill-content]]
=== Skill content contract

Frontmatter, exactly these keys:

[source,yaml]
----
name: wfc
description: >-
  Operate an installed WFC (workflow-coordinator, the `wfc` CLI): turn a
  development task into a bounded, human-authorized Commission, preview it
  with `wfc plan`, launch and monitor one Run, and read stops, reviews and
  Evidence. Use when the user asks to use WFC, workflow-coordinator, a
  Commission or a `wfc` command, or asks for a governed, independently
  reviewed change in a repository that has `.wfc/config.yaml`. Not for
  ordinary edits the user did not ask to route through WFC. Not for use
  inside a WFC Worker or Reviewer Hop.
license: MIT
compatibility: Requires the workflow-coordinator package (`wfc` on PATH), Git and Python 3.10+.
----

The wording may be improved; the last sentence of the description, the
exclusion of Worker and Reviewer Hops, must stay in the description
(<<level0>>).

`SKILL.md` body, in this order, at most 300 lines, with the first three
sections inside the first 80 lines:

. *What this is.* An operating guide for the session that orchestrates WFC
  from outside (Level 1). It grants no authority; WFC's runtime enforcement
  decides what is allowed whatever this text says; the human's instructions
  may narrow these defaults and nothing here widens them. A WFC Worker or
  Reviewer does not use it.
. *Authorization.* The rules of <<authorization>>, stated as rules, with the
  always-human list.
. *Preflight.* The three steps of <<preflight>>.
. *When WFC fits, and when it does not.*
. *The loop.* Repository readiness; Commission draft; `wfc plan` preview;
  the authorization check; fresh worktree, request outside the repository,
  `wfc run --yes`; `wfc status` and the rule "read `CLASSIFICATION`, not the
  exit code"; on `completed`, `wfc report` and independent verification; on
  anything else, the stops reference and the human.
. *Never.* Edit in-scope files directly once the task is routed through
  WFC; commit inside a Run's checkout; edit `.wfc/` state or Evidence; open
  or resolve a Finding; relaunch in a used checkout; run an unrecognized
  `wfc` subcommand; install or upgrade WFC or this skill unasked.
. *Where exact facts come from.* `--help` of each subcommand (there is no
  top-level `wfc --help`), the `wfc plan` output, `wfc status`, `wfc report`,
  and the tag-pinned manual URLs.

Rules for all four files:

* Markdown only. No `scripts/`, no `assets/`, no `agents/`, no executable
  bit, no host substitution or injection syntax (`$ARGUMENTS`,
  `${CLAUDE_SKILL_DIR}`, `!`-prefixed command blocks), no host tool names.
* No frontmatter key beyond `name`, `description`, `license`,
  `compatibility`, `metadata`. In particular no `allowed-tools`.
* Each reference at most 200 lines, linked from `SKILL.md` by relative path,
  one level deep, and opening with the Operator Manual section it distils.
* Documentation links are absolute and pinned to the tag of the package
  version, `https://github.com/StefanSchade/workflow-coordinator/blob/v<VERSION>/docs/...`,
  as the README's are. They change with the version at release time; the
  drift guard makes that a knowing change.
* The Operator Manual owns every procedure. Where the skill and the manual or
  the CLI disagree, the skill is wrong.

[[authorization]]
=== Authorization and existing delegations

The skill must describe WFC's authority model as it is implemented and
practised, neither looser nor stricter. It introduces no approval step of
its own.

What is implemented: `wfc run` confirms two digests, the Commission's and
the execution envelope's, once per checkout. `--yes` conveys that
confirmation for a non-interactive caller; without it and without a
terminal the launch is refused (`refused_unauthorized`). The manual calls
this confirmation the maintainer's explicit authorization to launch
(link:../operator_manual/ch03_running/01_preparation.adoc[preparation
contract]). WFC does not check on whose word `--yes` was passed. The
committed `.wfc/config.yaml` bounds every scope by its scope ceiling. The
request's `authority_source` is carried into the Commission.

What is practised (link:../operator_manual/ch10_level1_orchestration/01_operating_pattern.adoc#level1-human-decisions[chapter
10]): the human decides a new Commission's scope, authority, program and Hop
budget "for the first time"; Level 1 continues on its own when "launching a
Commission whose scope, program and Hop budget the human has already
approved for this package".

The skill states the following, and the acceptance scenarios test them:

[horizontal]
AU-1 -- Authority facts:: Of a Commission: its scope, its program, its Hop
budget, and any execution binding that differs from the committed
`default_execution`. The human decides them. Passing `--yes` asserts that
the human has; WFC does not verify the assertion.
AU-2 -- Initial authorization:: An authority fact the human has not yet
decided. The agent proposes a value, shows the `wfc plan` projection, and
asks once, for the undecided facts only.
AU-3 -- Existing delegation:: A decision the human has already made: in the
task instruction, in a standing instruction for the repository or session,
or by approving a decomposition into packages. It covers a launch when every
authority fact that `wfc plan` projects lies within it: scope equal to or
inside the approved paths, the approved program, a Hop budget not above the
approved one, bindings as approved or as committed. A covered launch
proceeds with `--yes` without a further approval turn; the agent reports
the digests and what it launched.
AU-4 -- Narrow reading:: Ambiguity is not delegation: ask. The scope
ceiling is a bound, not an approval of a particular Commission. An
instruction to carry out a task through WFC is an instruction to launch it
once its authority facts are decided, unless the human reserved the go.
AU-5 -- Never delegated by a launch:: Resolving a stop; widening scope or
budget, also after a stop; a push, tag, publication or configuration
change; changing the installed WFC version; discarding a branch, worktree,
stash or preserved ref. These need the human each time, as chapter 10 lists
them.
AU-6 -- The record:: `authority_source` names truthfully who authorized the
Commission and by which instruction.
AU-7 -- The reserved go:: When the human keeps the launch decision, the
agent prepares everything and hands over the exact `wfc run` command for an
interactive terminal, or waits for the instruction to launch.

WFC has no delegation object, file or flag, and this record adds none. The
skill teaches recognition of a decision that exists; it does not create a
way to grant one.

=== Command interface

[source,text]
----
wfc skill install (claude|codex) [--scope user|project] [--repository PATH]
                                 [--skills-dir DIR] [--dry-run] [--force]
wfc skill status  (claude|codex) [--scope user|project] [--repository PATH]
                                 [--skills-dir DIR] [--json]
wfc skill show [FILE] [--list]
----

`--help` on `wfc skill` and on each subcommand prints usage and returns 0.
A bare `wfc skill`, a missing host and an unknown subcommand print usage and
return 2. None of these falls through to the legacy operator entry point.

Destination (the skill directory is always named `wfc`):

[cols="1,3,3",options="header"]
|===
|Host |`--scope user` (default) |`--scope project`

|`claude`
|`$CLAUDE_CONFIG_DIR/skills/wfc` when that variable is set, otherwise
`$HOME/.claude/skills/wfc`
|`<top-level>/.claude/skills/wfc`

|`codex`
|`$HOME/.agents/skills/wfc`
|`<top-level>/.agents/skills/wfc`
|===

`<top-level>` is the Git top-level of `--repository` (default `.`).
`--skills-dir DIR` replaces the skills root and addresses `DIR/wfc`; it is
the route for a relocated configuration or another Agent Skills host, and it
excludes `--scope`.

[[states]]
=== Installed state and install semantics

An *installation* is one destination directory: one host at one scope, or
`DIR/wfc`. The installer writes the packaged files byte-for-byte and one
marker, `.wfc-skill.json`, containing `schema` (1), `wfc_version` and
`files` (a SHA-256 per relative path). No timestamp, so equal inputs give
equal bytes.

[cols="1,3,3",options="header"]
|===
|State |Definition |`install` does

|`absent` |No destination directory. |Creates it.
|`current` |Installed files equal the packaged files. |Nothing; returns 0.
|`stale` |Files equal their own marker and differ from the package. |Replaces
the directory: the copy is untouched and WFC's own.
|`modified` |Files differ from both the marker and the package. |Refuses,
return 3, listing the differing files. `--force` replaces the directory.
|`foreign` |A directory without a valid marker that is not `current`.
|As `modified`.
|===

* A destination that is a symbolic link is refused (return 2) with or
  without `--force`; it is never followed or replaced.
* `--scope project` outside a Git work tree is refused (return 2).
* The new directory is staged in the parent of the skills root, never inside
  the skills root (a staged copy there would be discovered as a second
  skill), and renamed into place; on replacement the old directory is
  removed immediately before the rename. A failure leaves the old
  installation, the new one or none, never a partial one.
* `--dry-run` prints the detected state and the planned action, writes
  nothing, and returns what the real call would return.
* Output follows the Front Door's existing voice: `STATE:`, `INSTALLED:` (or
  `WOULD INSTALL:`), `WFC VERSION:`, `INVOKE:` (`/wfc` for `claude`, `$wfc`
  for `codex`) and `NOTHING ELSE WAS CHANGED`. Project scope adds `NEXT
  EXPLICIT ACTION:` -- commit the directory yourself; `wfc skill install`
  never commits, and an uncommitted copy makes `wfc run` refuse the tree.
* Return codes: 0 done or nothing to do; 2 usage or environment error; 3
  conflict.

`wfc skill show` prints one packaged file to standard output (default
`SKILL.md`); `FILE` must equal a packaged relative path; `--list` prints the
paths with their digests. Removing the directory that `status` prints is the
uninstall.

[[status]]
=== Status semantics

`wfc skill status` answers one question for one host: in which state is each
installation of that host. It is read-only.

* The host is required. Only that host's destinations are evaluated; the
  other host is neither read nor reported. There is no mode that covers both
  hosts.
* Every installation has exactly one state from <<states>>. States are never
  combined into an overall state.
* Which installations are reported:
** with `--scope`: exactly that one;
** with `--skills-dir`: exactly `DIR/wfc`;
** with neither: the user-scope installation, and the project-scope one when
   `--repository` (default `.`) is inside a Git work tree. Outside one, the
   project installation is omitted; that is not an error.
* `absent` is an ordinary state. The command returns 0 whenever it could
  evaluate, whatever the states; the state is read from the output.
* Text output, one block per installation, then one line for the package:
+
[source,text]
----
HOST: claude
SCOPE: user
PATH: /home/user/.claude/skills/wfc
STATE: current
INSTALLED VERSION: 0.1.0b2

PACKAGED VERSION: 0.1.0b2
----
+
`INSTALLED VERSION` is the marker's `wfc_version`, or `-` without a valid
marker.
* `--json` prints one object with the same facts:
+
[source,json]
----
{"host": "claude", "packaged_version": "0.1.0b2",
 "installations": [{"scope": "user", "path": "/home/user/.claude/skills/wfc",
                    "state": "current", "installed_version": "0.1.0b2"}]}
----
+
`scope` is `user`, `project` or `custom` (for `--skills-dir`);
`installed_version` is `null` without a valid marker.

An installation is *usable as it is* exactly when its state is `current`.

[[preflight]]
=== The skill's preflight

. `wfc --version --json`. If it fails, WFC is not installed in this shell:
  stop and tell the human.
. `wfc skill status <host>`, where the host is `claude` in Claude Code and
  `codex` in Codex. If the command fails, the installed WFC predates this
  skill: stop and tell the human. The other host is not checked; its state
  is irrelevant to this session.
. Take the installation whose `PATH` is the directory this `SKILL.md` was
  loaded from. `current`: proceed. Any other state: read `wfc skill show`
  and follow that text for this session, and tell the human to re-run
  `wfc skill install <host>` for that scope. If the agent cannot tell which
  installation it was loaded from: proceed when every reported installation
  that is not `absent` is `current`; otherwise use `wfc skill show`.

Under another Agent Skills host the second step is `wfc skill status claude
--skills-dir <parent of the skill directory>`; the host name then only
selects the invocation hint.

[[level0]]
=== Level 0 does not use the skill

Level 1 is the session that orchestrates WFC from outside; Level 0 is WFC
executing one Commission, with Worker and Reviewer sessions that WFC starts
through its adapters. The skill is for Level 1 only.

Observed (2026-11-23, no provider contacted):

* A Claude role session, started with the adapter's `--restricted
  --safe-mode`, lists neither personal nor project skills.
* A Codex role session, started with the adapter's exact arguments, receives
  the name, the description and the file path of every user-level and
  repository-level skill in its prompt, and not the body of `SKILL.md`. A
  user-installed `wfc` skill is therefore one catalogue line in every Codex
  Worker and Reviewer prompt.

Not observed: any role agent loading the skill or acting on it. WFC's
enforcement does not rest on the role agent's restraint; a second `wfc run`
in a checkout that has a lifecycle is refused (`refused_active_lifecycle`).

Decision (D5):

* No adapter change and no `agents/openai.yaml`. Visibility of one line is
  demonstrated, harm is not, and a Codex role session inherits every user
  and repository skill, of which this is the only one written to exclude
  that reader.
* Because a role session sees the description and nothing else, the
  exclusion sentence lives in the description, and a content test asserts
  it (<<tests>>). The body repeats it in its first section.
* Residual question, recorded in <<residual>>: whether a role agent ever
  loads the skill. The Codex qualification has the duty to look (<<s3>>).

== Security invariants

[horizontal]
SI-1:: `pip install` writes nothing outside the environment. Agent
configuration changes only through an explicit `wfc skill install`.
SI-2:: The skill grants no host permission: portable frontmatter only, no
`allowed-tools`, no hook, no settings or permission file.
SI-3:: Installation copies inert text. It executes nothing from the skill,
opens no network connection and installs no dependency.
SI-4:: `wfc skill` never starts, resumes or authorizes a Run, never imports
the engine, and never reads or writes `.wfc/`, the journal or Evidence.
SI-5:: A consumer repository is written only under `--scope project`, only
at the one destination directory, and is never committed, staged or
otherwise altered.
SI-6:: Nothing existing is overwritten without `--force`, except an
unmodified copy that WFC installed itself.
SI-7:: Only user-writable paths are targets; no privilege is needed or
requested; admin skill locations are never written.
SI-8:: Nothing depends on a WFC checkout: all content comes from the
installed package.
SI-9:: The skill text claims no authority, states that WFC's runtime
enforcement prevails, and describes authorization exactly as
<<authorization>> does: no approval step that WFC's contract does not
require, no delegation that the human did not give.
SI-10:: The core does not depend on the skill: no module outside
`frontdoor/cli.py` imports `frontdoor/skill.py`.
SI-11:: Status for one host never depends on the other host's
installations.

== Acceptance criteria

For S1 and S2:

[horizontal]
AC-1:: A wheel built from the tree contains exactly the four skill files in
addition to today's content, and `make dist-audit` passes.
AC-2:: In a clean environment, from a directory outside the checkout,
`wfc skill show` prints the packaged `SKILL.md` and `wfc skill install` works
for both hosts into a temporary home.
AC-3:: The states and install semantics of <<states>> hold for both hosts and
both scopes, including idempotence, `--dry-run`, `--force` and the symbolic
link refusal.
AC-4:: The status semantics of <<status>> hold: one host per call, one state
per installation, no aggregate, `absent` not an error; a missing, stale or
modified installation of one host leaves the reported state of the other
host's installation unchanged.
AC-5:: SI-1 to SI-11 are each covered by a test or, for SI-9, by review of
the text against <<authorization>>.
AC-6:: Every `wfc` subcommand and flag named in the skill is accepted by the
CLI of the same tree; every classification named exists in
`frontdoor/lifecycle.py`'s `EXIT_CODES`; every documentation URL is pinned to
`implementation_identity.VERSION` and resolves to a file in the tree.
AC-7:: The skill text contains the statements AU-1 to AU-7, the preflight of
<<preflight>> and the exclusion of <<level0>>; the description carries the
exclusion sentence.
AC-8:: `make check` passes; apart from the artifact-audit expectations no
existing test is changed in meaning, and no existing subcommand's output
changes.
