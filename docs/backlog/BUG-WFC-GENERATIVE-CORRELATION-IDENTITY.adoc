== Exact failed invariant

The structured-result envelope must correlate exactly, byte for byte, to the
dispatched `(run_id, hop_id, invocation_id)` before its `result` payload may
be treated as the Hop's semantic outcome. It did not: `hop_id` and
`invocation_id` matched exactly; `run_id` carried one trailing byte the
dispatched value does not have. The envelope therefore failed correlation as
a whole, and no partial or majority-field acceptance occurred.

== Why the current fail-closed behavior is correct

This is not a bug in `validated_result()`, the reducer, or Hop accounting.
Rejecting on a non-exact match, refusing to apply any Git/evidence trust
before correlation succeeds, and charging the attempt as an uncertain Hop
under `reconcile_required` rather than silently discarding or retrying it are
exactly the documented invariants:

* `WFC-AUTO-02` (`docs/imported/core-incubator/FTR-AGENT-WORKFLOW-COORDINATOR-P5.adoc:504-511`):
  once the atomic dispatch marker exists, acceptance that cannot be disproved
  is conservatively charged as one Hop and never replayed.
* `WFC-AUTO-03` (ibid.:513-516): V1 has no hidden retry.
* `WFC-AUTO-05` (ibid.:523-526): resume requires explicit maintainer action
  and verified current HEAD/clean state; used Hops never reset.
* `docs/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc` (accepted architecture-
  convergence input, not superseded by this BUG): "Invocation correlation
  already prevents stale predecessor result content from being silently
  consumed as the successor result: validation checks
  `run_id`/`hop_id`/`invocation_id`" (line ~360); "a semantic failure must not
  become retryable merely because another model invocation might produce a
  better answer... [a] malformed or uncorrelated output... is likewise not
  reclassified as a transient interruption" (lines 113-117).

None of the rejected approaches enumerated by the maintainer (punctuation
trimming, whitespace/punctuation normalization, prefix matching, fuzzy
matching, accepting on two-of-three field agreement, trusting return code 0,
trusting in-scope repository changes, editing the persisted failed result, or
silent retry) is compatible with these invariants, and this BUG does not
propose any of them. `validated_result(raw, expected_invocation)` is correct
today and must remain the exact-match, provider-neutral, fail-closed
correlation authority.

== Root-cause classification

`src/workflow_coordinator/codex_adapter.py` builds the Codex-specific OpenAI
Structured Outputs projection of the envelope
(`structured_result_envelope_openai_schema()`, lines 124-134). Its
`run_id`, `hop_id`, and `invocation_id` properties are each projected as
unconstrained `{"type": "string"}` (lines 130-131). The function takes no
`Invocation` argument and `CodexCliAdapter.execute()` calls it with none
(line 172), even though `execute()` already receives `request:
AgentExecutionRequest`, whose `request.invocation` carries the exact
dispatched `run_id`/`hop_id`/`invocation_id`
(`src/workflow_coordinator/adapter.py:32-35, 46`) before the provider is ever
invoked.

The Coordinator therefore asks the model to *regenerate*, as free-form text,
three values it already knows exactly and will later require to match
byte-for-byte. That is a category error:

----
correlation identity is Coordinator-owned deterministic data,
not semantic content requiring model generation.
----

`hop_id` and `invocation_id` were reproduced correctly in this Attempt;
`run_id` was not. Nothing in the current schema, prompt, or provider contract
makes exact reproduction of an opaque, already-known identifier structurally
necessary -- the model is free to emit any string in that slot, and on this
occasion it emitted one extra trailing byte.

This preserves, and does not blur, the existing architectural distinction:

* provider-specific structured-output projection remains
  `codex_adapter.py`'s concern;
* provider-neutral `validated_result()` remains the sole semantic
  correlation authority and needs no behavior change.

Semantic acceptance is not being moved into Codex-specific code by this
classification; only the *shape of what the model is asked to produce* in
that code is implicated.

== Likely bounded correction (investigated, not implemented)

Options considered:

A. **Invocation-specific exact-value schema projection.** Thread
   `request.invocation` into `structured_result_envelope_openai_schema()` and
   constrain `run_id`, `hop_id`, `invocation_id` each to a one-element
   `enum` of the exact dispatched value (the same JSON Schema construct
   already used for `schema_version` and other closed vocabularies in this
   file, e.g. lines 96, 113, 130). The model is no longer free to emit an
   arbitrary string in those three slots; the returned envelope still
   contains them, and `validated_result()` still performs its own,
   independent, byte-exact comparison against `expected` -- unchanged.

B. **Adapter wrapping/injecting correlation IDs after provider output.**
   Have `CodexCliAdapter.execute()` overwrite or splice
   `run_id`/`hop_id`/`invocation_id` into the candidate JSON after the
   process returns, before returning `AgentExecutionOutcome`. Rejected: this
   makes the downstream `validated_result()` correlation check tautological
   for the Codex adapter -- it would always pass by construction, because the
   adapter, not the provider, would be the one asserting correlation. It also
   destroys the diagnostic signal used in this very Attempt (a divergent
   returned identity is evidence about *provider/schema-conformance
   behavior*, and silently repairing it before validation would erase that
   signal for every future Attempt). It would make provider-conformance
   drift invisible instead of visible.

C. **Prompt-only reinforcement.** Strengthen the prompt's wording asking the
   model to reproduce the IDs exactly. Rejected as insufficient on its own:
   this Attempt's prompt-equivalent instruction (see
   `codex_adapter_smoke.py:_prompt()`, "Use these exact correlation IDs...")
   already states the requirement in the closely related smoke path, and nothing
   in the repository's own architecture treats natural-language reinforcement
   as a substitute for structural narrowing where a schema construct is
   available (compare the accepted precedent in
   `docs/backlog/FTR-WFC-PHASE-SCOPED-RESULT-SCHEMA.adoc`: "schema narrowing is
   usability and error prevention"). Prompt wording may still be worth
   revisiting, but not as the sole or primary correction.

D. **Tolerant/normalized validation.** Explicitly rejected per the
   maintainer's non-scope list and per `FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`'s
   own conservative-charging rationale; would weaken the exact-match
   invariant this BUG exists to preserve.

Option A is the likely correction: it best preserves the current trust
model because it changes only what the model is asked (and structurally
permitted) to produce, not what `validated_result()` independently checks.
Under A, the provider-facing schema is itself derived from the same
dispatched `Invocation` that `expected` is built from, so the schema-side
and `expected`-side values are not conceptually unrelated -- narrowing the
schema is precisely how the Coordinator's already-known value reaches the
provider. What matters is that `validated_result()` remains the
provider-neutral semantic correlation boundary and independently
re-enforces exact equality on whatever the returned envelope actually
contains, regardless of how the provider-facing schema was derived or how
narrowly it constrained the model; it does not trust or skip that check
merely because the schema was narrowed, and it would equally reject a
Codex response that, despite the enum constraint, still returned a
divergent value. Under B, by contrast, the adapter itself -- not the
provider -- would be the one asserting correlation by construction,
collapsing that independent check into a tautology for the Codex adapter,
which is exactly the outcome to avoid.

Whether an invocation-specific schema is regenerated per Hop (schema and
result-message paths are already per-`result_directory`, so this appears
mechanically straightforward) is an implementation detail for later review,
not decided here.

== Non-scope

This BUG does not authorize changes to:

* `adapter.validated_result()` or its exact-match semantics;
* the reducer or its fail-closed authorization boundary;
* Git reconciliation, Run-state semantics, or Hop accounting;
* automatic retry or generic recovery redesign (see
  `docs/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`, which remains the
  separate, evidence-gated authority for recovery/retry policy);
* a new provider abstraction or adapter registry;
* the phase-scoped result schema direction (see Relationship below);
* Level-1/outer-loop orchestration;
* any Latin-domain code, data, or content;
* Project Memory tooling or curation.

If the correction can be shipped without changing
`adapter.validated_result()` at all -- which option A implies -- that is a
desirable boundary for the eventual implementation to preserve, subject to
repository truth at implementation time.

== Relationship to FTR-WFC-PHASE-SCOPED-RESULT-SCHEMA

That FTR concerns narrowing the *semantic result capabilities* admitted by
phase/profile (permitted routes, Finding-disposition authority, escalation
surface, commit-intent capability) so that a phase-authority-invalid but
schema-valid output becomes harder to express. It is deferred pending
materially recurring schema-valid/phase-authority-invalid failures.

This BUG is narrower and orthogonal: the three fields at issue
(`run_id`/`hop_id`/`invocation_id`) are not semantic result content at all --
they are Coordinator-owned dispatch identity that exists prior to, and
independent of, any phase/profile authority question. Narrowing them to
their exact dispatched value is not "phase-scoped result schema" in that
FTR's sense, has a single occurrence with a concrete, already-observed
provider divergence (not merely a theoretical concern), and does not depend
on the FTR's activation criterion. This BUG is not merged into that FTR, and
resolving this BUG does not on its own satisfy or advance the FTR's
activation criterion.

== Frozen-attempt / future-runtime boundary

This BUG does *not* itself authorize repair, resumption, or continuation of
`RUN-39f7984a68ff4de68c3e039971451b88`. That Run's `reconcile_required`
state, its charged uncertain H001, and its dirty tracked state are valid
fail-closed historical evidence and must not be mutated, repaired in place,
normalized, or reinterpreted. No automatic retry is authorized by this
record.

This is not a categorical prohibition on same-Run reconcile/resume as a WFC
mechanism. Explicit same-Run reconcile/resume remains a valid recovery
mechanism in general, per `FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`'s accepted R1.5
direction and the existing `reducer.resume_after_reconcile()` seam, wherever
the accepted recovery predicates permit it: it preserves Run-local Findings,
phase, and pinned governing truth for a fresh subsequent Hop, and it never
normalizes, repairs, rewrites, or semantically accepts the malformed,
uncorrelated H001 candidate itself. A future corrected Runtime does not
retroactively make that H001 result trustworthy, whether or not the Run is
later resumed.

Concretely, `RUN-39f7984a68ff4de68c3e039971451b88` currently carries
`anomalies=["dirty tracked state"]` (`operator-summary.json`), and
`reducer.resume_after_reconcile()` raises `"reconcile anomalies must be
resolved before resume"` whenever `run.anomalies` is non-empty
(`src/workflow_coordinator/reducer.py:565-566`). This concrete state is
therefore not presently resumable through that seam as recorded -- the
mechanism is not unavailable in general, but this Run's own anomaly does not
currently satisfy the seam's precondition. Where Runtime, contract,
governing truth, or other admitted system truth instead changes -- for
example once this BUG's correction ships and a Runtime is promoted -- a
fresh successor Run is the appropriate continuation mechanism, rather than
resuming a Run pinned to superseded truth.

Preserve the distinction between:

* safe recovery of existing WFC authority (explicit same-Run reconcile/resume
  of an eligible, anomaly-free Run, preserving Findings/phase/governing
  truth, once the accepted predicates are satisfied);
* salvage of an invalid candidate (never authorized: the H001 result is
  never normalized, repaired, or semantically accepted, however the Run is
  eventually disposed);
* a fresh successor Run (appropriate once governing/Runtime/contract truth
  changes; does not implicitly inherit Run-local Findings); and
* same-Hop/provider-session replay (not this BUG's subject; a separately
  evidence-gated, deferred R2 concern per `FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`).

The final disposition of the frozen Latin attempt -- reconcile/resume once
otherwise eligible, or a fresh successor WorkItem/Run -- remains an explicit
maintainer decision, not something this BUG record decides or authorizes.

Three separate decisions must not be conflated:

. fixing future structured-result projection (this BUG, once implemented and
  independently reviewed);
. deciding separately, as a maintainer-owned action, how to dispose of the
  frozen failed Run (e.g. explicit reconcile/resume of the same Run per
  `FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`'s R1.5 direction, or a fresh successor
  Run/WorkItem); and
. promoting an accepted WFC Runtime, which must occur before any fixed
  behavior may govern a fresh Latin Run.

A future runtime correction does not retroactively make the malformed
`RUN-39f7984a68ff4de68c3e039971451b88` H001 candidate trustworthy, and does
not by itself make that Run resumable -- its `dirty tracked state` anomaly
would still need to be independently addressed under
`resume_after_reconcile()`'s existing precondition. Only a fresh
continuation WorkItem and fresh Run, dispatched under a promoted, corrected
Runtime, may be considered -- and only after explicit maintainer
authorization.

== Acceptance criteria for a future implementation

* The exact dispatched `run_id`, `hop_id`, and `invocation_id` constrain the
  provider-visible structured-output schema for that invocation (e.g. via a
  one-element `enum` per field, threaded from `request.invocation`).
* The model is no longer free to emit arbitrary values for those three
  fields.
* The schema remains valid under
  `assert_openai_strict_schema()` / the currently supported Codex/OpenAI
  strict Structured Outputs subset.
* `adapter.validated_result()` still independently rejects a deliberately
  uncorrelated envelope; its exact-match comparison is unchanged.
* No normalization, trimming, or fuzzy acceptance is introduced anywhere in
  the correlation path.
* Malformed/uncorrelated `FakeAdapter`/fake-adapter results continue to fail
  closed in tests.
* Hop accounting (`record_hop`, `recover_uncertain_dispatch`) and
  reconciliation behavior (`reducer.resume_after_reconcile`,
  `RunStatus.RECONCILE_REQUIRED`) remain unchanged.
* Existing adapter conformance tests
  (`tests/unit/test_codex_adapter_conformance.py`) and the full WFC test
  suite pass; new conformance tests cover the invocation-specific
  enum-constrained projection.
* A bounded real-adapter smoke (`codex_adapter_smoke.py`) may be required
  only after implementation review and explicit maintainer authorization; it
  is not authorized by this BUG record.
* A Runtime promotion is required before the fixed behavior may govern a
  fresh Latin Run; this BUG record does not authorize that promotion.
