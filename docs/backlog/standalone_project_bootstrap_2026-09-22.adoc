== 1. Purpose and bounded decision

The accepted standalone repository is independently installable and tested, but
its current project-control surface is intentionally only a README, a short
architecture overview, and imported provenance. The smallest useful next step
is to make current authority, near-term work, standalone memory, and
self-development authority explicit before Workflow Coordinator (WFC) operates
on its own development clone.

This plan proposes exactly two bootstrap implementation slices:

. establish a small current authority/backlog/Project Memory surface; and
. commit the minimum self-development governance and self-hosting guidance,
  validate it without a provider, and close bootstrap readiness.

The bootstrap deliberately does not deliver developer tooling or product
features. Standalone developer ergonomics is reserved as the first useful,
bounded WFC-on-WFC payload.

=== 2.3 Current execution facts that documentation must preserve

Inspection of the current implementation establishes these facts:

* The operator takes separate committed WorkItem, WorkflowProfile,
  RepositoryPolicy, component-manifest, task, and selected prompt-component
  paths. Their content is read from the exact expected HEAD and digested before
  dispatch.
* `WorkItem.repository` is a logical identity admitted against policy scope.
  `--repository` is the filesystem path to the operated Git top level. They are
  intentionally different concepts.
* The one-shot `--state-root` must not already exist and must be physically
  disjoint from the operated repository in both nesting directions.
* A new operator invocation creates a new Run. The current CLI does not expose
  retry/resume of a prior Run; internal reconciliation primitives are not a
  public resume workflow.
* Policy-authored evidence commands are trusted Coordinator execution, not
  arbitrary agent shell authority. They are prepared at admission, resolved
  again at execution, run with `shell=False` from the repository root, and
  inherit a captured environment.
* `--executable` replaces the executable used by the concrete
  `CodexCliAdapter`. It is therefore a Codex-CLI-compatible executable seam, not
  a generic provider selector.
* That adapter currently requests `--ask-for-approval never`,
  `--sandbox workspace-write`, model `gpt-5.6-terra`, and reasoning effort
  `medium`.
* Operator exit `0` means the Run completed and the repository ended clean;
  exit `1` means a provider-capable attempt did not meet that condition or
  failed after the provider-capable boundary; exit `2` means usage or local
  preflight failure before that boundary. The Run status and written summary
  remain the more precise result.
* The Coordinator may create bounded ordinary local commits when admitted
  inputs authorize both edit and commit. It has no push or runtime-promotion
  authority.

These statements belong in the proposed Getting Started/CLI/boundary
documentation dogfood, not as a large expansion of this bootstrap.

A maintainer, fresh coding agent, or independent reviewer can begin at the root

== 4. Lightweight standalone Project Memory

=== 4.1 Minimum shape now

Create one human-readable file: `docs/project_memory.adoc`. Do not create a
directory taxonomy, YAML schema, generator, archive, ledger, validator, or
snapshot machinery.

The file has a date and accepted-HEAD anchor followed by five stable headings:

. *Current state* -- what is working and the most recent accepted transition.
. *Accepted decisions* -- compact decisions still relevant to current work.
. *Active work* -- at most the current bootstrap/WorkItem and its state.
. *Durable constraints* -- boundaries future work must preserve, including
  authority ownership, separate clones, external state roots, provider limits,
  no autonomous push/promotion, and known deferred security work.
. *History and evidence pointers* -- links to the carve-out manifest, commit map,
  imported-history NOTICE, and relevant current artifacts rather than copied
  pre-split prose.

Git history is the history of this single current snapshot. No separate event
log is needed.

=== 4.2 Normal refresh rule

Refresh Project Memory only at an accepted state transition: bootstrap
acceptance, WorkItem acceptance, a durable architecture decision, backlog
promotion/demotion with lasting consequences, or runtime promotion. The same
ordinary commit that accepts that transition should update the affected current
summary. A WFC Run may propose a refresh only when its maintainer-authored
WorkItem explicitly includes that path; it cannot silently expand its own
authority.

During active work, transient Run evidence remains under the external state
root. Project Memory records the accepted outcome and useful measurements, not
provider transcripts, every Hop, or generated prose wholesale.

=== 4.3 Content ownership boundaries

[cols="2,5",options="header"]
|===
|Surface |Belongs here

|Project Memory
|Current state, accepted decisions, active accepted work, durable constraints,
and links needed by a fresh-context agent.

|Backlog
|Priority/disposition, desired outcome, ordering, and candidate work that is not
yet authorized.

|Architecture
|Stable system responsibilities, trust boundaries, and invariants that code and
governance must preserve.

|WorkItem/task
|Exact authorized payload, scope, workflow, and completion request for one Run.

|External Run state
|Invocation evidence, checkpoints, summaries, observations, and transient
recovery facts.

|Imported history/provenance
|Pre-split rationale, old reviews, old lifecycle state, and commit lineage.
|===

=== 4.4 Deliberately deferred memory machinery

Defer machine schemas, automated refresh, semantic extraction, multiple memory
files, lifecycle taxonomies, cold/warm storage, generated indexes, snapshot
integration, memory-specific CI, and an agent-owned memory updater. Add one only
after repeated dogfood shows a concrete failure that the single file cannot
handle.

== 6. Self-hosting and promotion invariants

=== 6.1 Runtime N operates on development N+1

The invariant is:

[source,text]
----
accepted Runtime WFC N  --operates on-->  Development WFC N+1
accepted Runtime WFC N  --never mutates--> Runtime WFC N
----

The runtime executable, package/resources, Git metadata, environment, state, and
remote configuration are execution authority. They are never payload paths.
The development clone is the only repository supplied through `--repository`
for WFC self-development. The external state root is outside both clones and is
new per Run.

==== 6.1.1 Runtime execution environment

Runtime N is launched from a dedicated virtual environment outside both clones.
The maintainer creates that environment from a temporary export of the exact
accepted runtime commit, installs the export non-editably, and verifies at
least `wfc --help` provider-free. The launch contract records the runtime commit
and puts that environment's `bin` directory on `PATH`; it never executes the
development package. Preparing or replacing this environment is an explicit
maintainer/bootstrap operation, not automatic runtime promotion. The external
Run state root is separate from the runtime environment as well as both clones.

==== 6.1.2 Development/evidence environment

A second, separate development/evidence virtual environment supplies the
development checkout's trusted evidence tools. It is prepared outside both
clones with ordinary `python3 -m venv` and `pip` using the repository's `dev`
extra (an exported exact development tree may be used to avoid derived output
in the checkout). Its `bin` directory is placed first on the Coordinator's
captured `PATH`, so the portable evidence argv `python -m pytest -q` resolves
mechanically from the repository root. This environment is not runtime N and
does not change which WFC installation coordinates the Run. Neither environment
introduces a dependency manager or repository-local environment framework.

Do not use `git worktree` as the primary model. Separate clones and object stores
prevent payload commits or ref movement from implicitly changing runtime
authority.

=== 6.2 Role ownership

[cols="2,5",options="header"]
|===
|Owner |Authority

|Maintainer
|Authors/accepts RepositoryPolicy, WorkItem, task, scope, profile selection, and
promotion; decides whether a local result is accepted; performs push and
optional runtime promotion; may stop at any time.

|WFC runtime
|Deterministically admits pinned governing inputs, coordinates only declared
routes/Hops, executes trusted admitted evidence, records external Run state, and
creates bounded local payload commits when authorized.

|Semantic agent
|Inspects and edits only the authorized development payload and returns the
required structured result. It cannot grant itself paths, Hops, policy,
governance changes, push, promotion, or runtime mutation.
|===

=== 6.3 Push and runtime promotion

The steady-state trust transition is:

[source,text]
----
WFC-created local development commits
        -> maintainer review and acceptance
        -> maintainer push (optional)
        -> maintainer runtime promotion (optional and separate)
----

WFC or its agent may inspect, edit admitted payload paths, run admitted evidence,
and produce the existing bounded local commits. They may not push to GitHub,
change runtime refs/remotes/configuration/environment, copy development HEAD into
runtime, or decide that a version it just produced may execute itself. The
runtime clone's disabled push URL is an existing local safeguard; documentation
records it but bootstrap does not manage or test-write that configuration.

=== 6.4 Unattended execution boundary

A genuinely unattended Run has no interactive approval route. The current
adapter's `approval=never` setting is necessary behavior, not a sufficient
security boundary. Its requested `--sandbox workspace-write` mode is also
provider-owned inner behavior; the Coordinator does not establish or verify it
as an OS/environment boundary. Long-term enforcement must be Coordinator-owned
or Coordinator-verifiable rather than an accumulation of provider approval or
sandbox modes and prompt rules. The likely experiment is an OS-level
`bwrap`/equivalent boundary that limits reachable and mutable surfaces while
Coordinator-owned Git/evidence authority remains outside. Bootstrap records
this invariant and limitation only; it neither claims containment nor
implements a sandbox.

== 7. Minimum committed self-development governance

=== 7.1 Proposed committed files

Bootstrap Slice B2 adds only this consumer-style governing bundle, using
existing schema and engine behavior:

[source,text]
----
governance/
  self-development/
    repository-policy.yaml
    standalone-development-profile.yaml
    components.yaml
    prompts/
      developer.txt
      reviewer.txt
  work-items/
    developer-ergonomics.yaml
    developer-ergonomics-task.txt
----

The policy uses logical repository identity `workflow-coordinator`, governance
root `governance`, exactly the payload ceiling in section 7.2, Hop ceiling `4`,
the existing `edit`/`commit`/`review` actions, and one provider-free evidence
command whose argv is `python -m pytest -q`. It grants no push, runtime, remote,
arbitrary shell, or provider-selection capability. Four Hops are required by
the fixed convergence sequence; although the engine hard maximum is five, this
profile permits only four: the engine's nominal fifth spare Hop is deliberately
not granted. The first dogfood therefore permits only one correction and
re-review cycle. A finding at the final re-review stops for the maintainer
rather than starting a second cycle.

The profile is one finite investigate -> independent review -> correct -> fresh
re-review workflow, using only the existing route/review model demonstrated by
the consumer-neutral fixture. Its routes are investigate -> review, review ->
correct, correct -> rereview, and rereview -> complete on acceptance or ->
correct when findings remain (where the four-Hop budget forces a safe stop).
The two short selected role components serve the developer/corrector and
reviewer/rereviewer respectively. They do not duplicate the package-owned
operating contract or introduce a prompt framework. No additional policy
prompt component is needed; the manifest pins exactly the two selected role
components through the current mechanism.

The WorkItem and task are part of B2 so production preflight can validate the
actual first-dogfood envelope before any provider invocation. They are committed
as maintainer-authorized `NEXT` work, select this profile, carry the exact scope
and per-phase durable-artifact mapping below, and are invoked later with the
exact accepted development HEAD. Their presence does not start a Run. This
authority comes from maintainer/bootstrap acceptance; neither WFC nor its agent
may author, widen, or replace the policy, profile, WorkItem, or task under which
it operates.

=== 7.2 Smallest decision forced by fixed profile scopes

Current profiles contain concrete `authorized_scope` paths, and admission
requires every phase scope to fit inside the WorkItem. A universal development
profile would therefore require every WorkItem to carry a broad fixed scope.
Bootstrap must not invent templating or a new policy abstraction to hide this
fact.

The one-purpose profile and WorkItem use this exact implementation payload set:

* `Makefile`;
* `README.md`;
* `pyproject.toml`;
* `scripts/wfc_snapshot.py`;
* `tests/unit/test_wfc_snapshot.py`; and
* `tests/architecture/test_package_boundaries.py`.

The policy ceiling and WorkItem scope contain exactly those paths plus the
dedicated review artifact
`docs/backlog/first_wfc_on_wfc_dogfood_review.adoc`. Generated snapshots are
evidence/output, not committed payload. `src/`, `governance/`,
`docs/project_memory.adoc`, runtime paths, remotes, every other documentation or
test path, and all other repository paths are outside the first-dogfood
authority. This closes the trust boundary in the plan; B2 may transcribe these
values but may not broaden them to make the profile reusable.

The phase authority is exact:

* `investigate` may use `edit` and `commit` only on the six implementation
  paths. Its durable-artifact mode is `optional`.
* `review` uses `review`, `edit`, and `commit` only because its durable artifact
  is `required`. Its sole `authorized_scope` and sole mapped artifact are
  `docs/backlog/first_wfc_on_wfc_dogfood_review.adoc`; it has no implementation
  mutation authority. It may inspect the committed implementation delta, as in
  the accepted convergence mechanics.
* `correct` may use `edit` and `commit` only on the six implementation paths.
  Its durable-artifact mode is `optional`, and it must not mutate the review
  artifact.
* `rereview` has only `review`, has `durable_artifact: none`, and receives no
  `edit` or `commit` authority. Its `authorized_scope` is the review-artifact
  path, matching the existing accepted observation-only convergence shape.

The WorkItem uses the modern per-phase `durable_artifacts` mapping to map the
review phase to the dedicated review artifact. It supplies no legacy
`--durable-artifact` argument. This is mandatory because a non-initial required
artifact cannot be satisfied through that legacy argv route.

The invariant is explicit: *review-artifact mutation authority is not
implementation mutation authority*. The review path is disjoint from every
implementation path; the implementation phases cannot mutate it, and the
review phase cannot mutate implementation payload. The rereviewer observes and
disposes findings without mutating either set.

After dogfood, either reuse that exact profile for similarly scoped work or make
one explicit profile revision/new bounded profile. Do not add variables,
inheritance, a registry, or a general profile framework during bootstrap.

=== 7.3 Coherence checks without a provider

Add one small architecture test,
`tests/architecture/test_self_development_governance.py`. The primary proof
must materialize a clean
disposable Git repository at an exact forty-character HEAD containing the
concrete governing bundle, then call the production parser and `_preflight`
path with that actual WorkItem, profile, policy, manifest, task, and a new
external state-root path. This exercises production governing-input admission,
phase-scope containment, action domination, WorkItem ceiling and Hop rules,
component/evidence reference coherence, the per-phase durable-artifact mapping,
and `prepare_evidence_commands` resolution. It stops before operator dispatch
and invokes no real or fake AI provider.

The test must not reimplement `_within_scope`, A1 path algebra, phase/WorkItem
containment, ceiling rules, action domination, evidence-reference coherence,
Hop limits, or governing-input admission. Focused properties owned by pure
production seams may call `_admit_a1`, `_selected_evidence_names`,
`_selected_ids`, `_within_scope`, or `a1_path_shape` directly, but the complete
bundle proof uses production `_preflight`; no admission rule is copied into
test-only code. Project-specific assertions are limited to facts production
admission cannot express, notably that the committed policy ceiling itself
excludes `governance` and that push, runtime-clone mutation, and automatic
promotion authority are absent. Even those assertions reuse production path
semantics where paths are compared.

The architecture test proves that the selected evidence executable resolves in
the captured Coordinator environment. B2 validation then runs the exact
committed `python -m pytest -q` argv once, provider-free, from the development
repository using the prepared development/evidence environment. It is not run
recursively from inside the architecture test. Bootstrap cannot claim readiness
unless both production preflight and that actual evidence execution succeed.
*No duplicate policy engine* is an acceptance criterion.

== 8. First WFC-on-WFC dogfood WorkItem

The first WorkItem is *standalone developer ergonomics*. Slice B2 commits its
exact governing bundle as maintainer-authorized `NEXT` work and validates it
through production preflight, but does not execute its Run. After independent
bootstrap acceptance, the next maintainer action can therefore be the actual
WFC Run rather than another authority-design exercise. The payload is useful
and bounded enough for the current Codex/Terra-medium execution binding and its
single correction-cycle budget.

=== 8.1 Payload

The exact six implementation paths in section 7.2 may deliver only:

* a small Makefile with `make test`, `make lint`, `make format-check`, and
  `make check`;
* `make build` only when current packaging and local use justify it;
* Ruff/dev-tool configuration in `pyproject.toml` only as needed;
* small repository snapshot tooling and `make snapshot` /
  `make snapshot-multi`;
* an architecture guard closing the accepted post-carve-out `__package__`
  MINOR, after reading the exact accepted review evidence; and
* narrowly related development documentation and tests.

The dedicated review-artifact path is the seventh and only other WorkItem path;
it is not implementation payload. The WorkItem does not modify runtime WFC N,
change engine architecture, add a provider, create a CLI command, update
Project Memory, or widen its own governance.

=== 8.2 Snapshot contract

The WorkItem must inspect the actual spreadsheet-handling/Core snapshot
implementation and adapt only useful behavior. Future standalone snapshots
must have line numbers, a table of contents, an included repository tree, and
semantic condensation into fewer/larger useful files rather than many tiny
files. Every filename must be clearly WFC-prefixed so Core and WFC snapshots can
coexist in one analysis context, conceptually:

* `wfc_project_memory...`
* `wfc_repo_infrastructure...`
* `wfc_src_and_tests...`

The bootstrap does not decide exact groups, file formats, or single-versus-multi
partitioning. Those are implementation facts for the dogfood WorkItem.

=== 8.3 Empirical record

At acceptance, the maintainer records a short dogfood result in Project Memory
and updates backlog disposition. Use existing external Run evidence plus a
compact human summary; do not add telemetry machinery. Capture where practical:

* maintainer interventions and why;
* findings and correction/re-review hops;
* inconvenient setup/CLI steps;
* failed or non-unattended behavior;
* useful versus missing evidence;
