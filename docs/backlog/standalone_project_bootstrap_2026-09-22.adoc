== 1. Purpose and bounded decision

The accepted standalone repository is independently installable and tested, but
its current project-control surface is intentionally only a README, a short
architecture overview, and imported provenance. The smallest useful next step
is to make current authority, near-term work, standalone memory, and
self-development authority explicit before Workflow Coordinator (WFC) operates
on its own development clone.

This plan proposes exactly two bootstrap implementation slices:

. establish a small current authority/backlog/Project Memory surface; and
. commit the minimum self-development governance and self-hosting guidance,
  validate it without a provider, and close bootstrap readiness.

The bootstrap deliberately does not deliver developer tooling or product
features. Standalone developer ergonomics is reserved as the first useful,
bounded WFC-on-WFC payload.

=== 2.3 Current execution facts that documentation must preserve

Inspection of the current implementation establishes these facts:

* The operator takes separate committed WorkItem, WorkflowProfile,
  RepositoryPolicy, component-manifest, task, and selected prompt-component
  paths. Their content is read from the exact expected HEAD and digested before
  dispatch.
* `WorkItem.repository` is a logical identity admitted against policy scope.
  `--repository` is the filesystem path to the operated Git top level. They are
  intentionally different concepts.
* The one-shot `--state-root` must not already exist and must be physically
  disjoint from the operated repository in both nesting directions.
* A new operator invocation creates a new Run. The current CLI does not expose
  retry/resume of a prior Run; internal reconciliation primitives are not a
  public resume workflow.
* Policy-authored evidence commands are trusted Coordinator execution, not
  arbitrary agent shell authority. They are prepared at admission, resolved
  again at execution, run with `shell=False` from the repository root, and
  inherit a captured environment.
* `--executable` replaces the executable used by the concrete
  `CodexCliAdapter`. It is therefore a Codex-CLI-compatible executable seam, not
  a generic provider selector.
* That adapter currently requests `--ask-for-approval never`,
  `--sandbox workspace-write`, model `gpt-5.6-terra`, and reasoning effort
  `medium`.
* Operator exit `0` means the Run completed and the repository ended clean;
  exit `1` means a provider-capable attempt did not meet that condition or
  failed after the provider-capable boundary; exit `2` means usage or local
  preflight failure before that boundary. The Run status and written summary
  remain the more precise result.
* The Coordinator may create bounded ordinary local commits when admitted
  inputs authorize both edit and commit. It has no push or runtime-promotion
  authority.

These statements belong in the proposed Getting Started/CLI/boundary
documentation dogfood, not as a large expansion of this bootstrap.

== 3. Proposed current-authority model

=== 3.1 One explicit index, not historical re-curation

Add `docs/README.adoc` as the small current documentation/authority index and
link it from the root README. The index will classify paths by role and point to
the existing imported-history NOTICE and provenance manifest. It will not move,
rewrite, relabel one-by-one, or duplicate the imported documents.

After bootstrap, the intended current surface is:

[cols="2,3,5",options="header"]
|===
|Path/area |Authority role |Content boundary

|`README.md`
|Current entry point
|What WFC is, supported installation/development basics, and links to the
current authority index. It does not become a full CLI manual in bootstrap.

|`docs/README.adoc`
|Current authority index
|Classifies current docs, executable authority, governing inputs, provenance,
historical material, backlog, and Project Memory for fresh readers.

|`docs/architecture.md`
|Current stable architecture
|Product boundary and durable invariants, including self-development roles and
the two-clone/runtime-promotion trust boundary. It does not absorb backlog or

|`docs/project_memory.adoc`
|Current standalone state summary
|Split-forward state, accepted decisions, active work, and durable future
constraints. It records no pre-split narrative already available in provenance.

|`docs/backlog/README.adoc`
|Current small roadmap
|NOW/NEXT/LATER/WATCH/DROP-SUPERSEDED dispositions and links to active plans or
WorkItems. It does not restate architecture.

|`governance/self-development/`
|Committed executable self-development envelope
|Maintainer-owned policy, one bounded profile, component manifest, and selected
prompt components. A committed WorkItem and task add item-specific authority;
these reusable files alone authorize no Run.

|`governance/work-items/`
|Per-item maintainer authorization
|Future committed WorkItem/task pairs. The bootstrap creates no first dogfood

|Executable/package behavior
|Current implementation. Documentation cannot claim behavior contradicted by
the executable implementation.

|`tests/`
|Executable verification and guards
|Tests verify current contracts; a historical test name or marker does not make

|`docs/provenance/`
|Extraction lineage
|Traceability only.

|`docs/imported/core-incubator/`
|Historical evidence
|Never current standalone product, backlog, WorkItem, or promotion authority.
|===

When these roles appear to conflict, executable behavior must be described
truthfully; architecture changes require explicit current acceptance; Project
Memory summarizes accepted state but does not override architecture or grant
authority; backlog expresses intent but does not authorize execution; only a
maintainer-approved committed WorkItem within committed policy/profile ceilings
authorizes a self-development Run.

=== 3.2 Why this is sufficient

A maintainer, fresh coding agent, or independent reviewer can begin at the root
README, follow one current index, and see both the active surfaces and the hard
historical boundary. Adding per-document banners or moving the 660-KiB imported
corpus would add churn without resolving more ambiguity than the existing
directory NOTICE plus the new index.

== 4. Lightweight standalone Project Memory

=== 4.1 Minimum shape now

Create one human-readable file: `docs/project_memory.adoc`. Do not create a
directory taxonomy, YAML schema, generator, archive, ledger, validator, or
snapshot machinery.

The file has a date and accepted-HEAD anchor followed by five stable headings:

. *Current state* -- what is working and the most recent accepted transition.
. *Accepted decisions* -- compact decisions still relevant to current work.
. *Active work* -- at most the current bootstrap/WorkItem and its state.
. *Durable constraints* -- boundaries future work must preserve, including
  authority ownership, separate clones, external state roots, provider limits,
  no autonomous push/promotion, and known deferred security work.
. *History and evidence pointers* -- links to the carve-out manifest, commit map,
  imported-history NOTICE, and relevant current artifacts rather than copied
  pre-split prose.

Git history is the history of this single current snapshot. No separate event
log is needed.

=== 4.2 Normal refresh rule

Refresh Project Memory only at an accepted state transition: bootstrap
acceptance, WorkItem acceptance, a durable architecture decision, backlog
promotion/demotion with lasting consequences, or runtime promotion. The same
ordinary commit that accepts that transition should update the affected current
summary. A WFC Run may propose a refresh only when its maintainer-authored
WorkItem explicitly includes that path; it cannot silently expand its own
authority.

During active work, transient Run evidence remains under the external state
root. Project Memory records the accepted outcome and useful measurements, not
provider transcripts, every Hop, or generated prose wholesale.

=== 4.3 Content ownership boundaries

[cols="2,5",options="header"]
|===
|Surface |Belongs here

|Project Memory
|Current state, accepted decisions, active accepted work, durable constraints,
and links needed by a fresh-context agent.

|Backlog
|Priority/disposition, desired outcome, ordering, and candidate work that is not
yet authorized.

|Architecture
|Stable system responsibilities, trust boundaries, and invariants that code and
governance must preserve.

|WorkItem/task
|Exact authorized payload, scope, workflow, and completion request for one Run.

|External Run state
|Invocation evidence, checkpoints, summaries, observations, and transient
recovery facts.

|Imported history/provenance
|Pre-split rationale, old reviews, old lifecycle state, and commit lineage.
|===

=== 4.4 Deliberately deferred memory machinery

Defer machine schemas, automated refresh, semantic extraction, multiple memory
files, lifecycle taxonomies, cold/warm storage, generated indexes, snapshot
integration, memory-specific CI, and an agent-owned memory updater. Add one only
after repeated dogfood shows a concrete failure that the single file cannot
handle.

== 6. Self-hosting and promotion invariants

=== 6.1 Runtime N operates on development N+1

The invariant is:

[source,text]
----
accepted Runtime WFC N  --operates on-->  Development WFC N+1
accepted Runtime WFC N  --never mutates--> Runtime WFC N
----

The runtime executable, package/resources, Git metadata, environment, state, and
remote configuration are execution authority. They are never payload paths.
The development clone is the only repository supplied through `--repository`
for WFC self-development. The external state root is outside both clones and is
new per Run.

Do not use `git worktree` as the primary model. Separate clones and object stores
prevent payload commits or ref movement from implicitly changing runtime
authority.

=== 6.2 Role ownership

[cols="2,5",options="header"]
|===
|Owner |Authority

|Maintainer
|Authors/accepts RepositoryPolicy, WorkItem, task, scope, profile selection, and
promotion; decides whether a local result is accepted; performs push and
optional runtime promotion; may stop at any time.

|WFC runtime
|Deterministically admits pinned governing inputs, coordinates only declared
routes/Hops, executes trusted admitted evidence, records external Run state, and
creates bounded local payload commits when authorized.

|Semantic agent
|Inspects and edits only the authorized development payload and returns the
required structured result. It cannot grant itself paths, Hops, policy,
governance changes, push, promotion, or runtime mutation.
|===

=== 6.3 Push and runtime promotion

The steady-state trust transition is:

[source,text]
----
WFC-created local development commits
        -> maintainer review and acceptance
        -> maintainer push (optional)
        -> maintainer runtime promotion (optional and separate)
----

WFC or its agent may inspect, edit admitted payload paths, run admitted evidence,
and produce the existing bounded local commits. They may not push to GitHub,
change runtime refs/remotes/configuration/environment, copy development HEAD into
runtime, or decide that a version it just produced may execute itself. The
runtime clone's disabled push URL is an existing local safeguard; documentation
records it but bootstrap does not manage or test-write that configuration.

=== 6.4 Unattended execution boundary

A genuinely unattended Run has no interactive approval route. The current
adapter's `approval=never` setting is necessary behavior, not a sufficient
security boundary. Long-term enforcement must be Coordinator-owned and
verifiable rather than an accumulation of provider approval modes or prompt
rules. The likely experiment is an OS-level `bwrap`/equivalent boundary that
limits reachable and mutable surfaces while Coordinator-owned Git/evidence
authority remains outside. Bootstrap records this invariant and limitation only;
it neither claims containment nor implements a sandbox.

== 7. Minimum committed self-development governance

=== 7.1 Proposed committed files

Bootstrap Slice 2 should add only this consumer-style set, using existing schema
and engine behavior:

[source,text]
----
governance/
  self-development/
    repository-policy.yaml
    standalone-development-profile.yaml
    components.yaml
    prompts/
      developer.txt
      reviewer.txt
----

The policy supplies a standalone logical repository identity, a `governance`
input root, an explicit payload ceiling, a small Hop ceiling, the existing
`edit`/`commit`/`review` actions, and only evidence commands needed by the first
dogfood (initially the provider-free existing test command). It grants no push,
runtime, remote, shell, or provider-selection capability.

The profile is one finite implement -> independent review -> correct -> fresh
re-review workflow, using only the existing route/review model. The two short
prompt components clarify role-specific work; they do not duplicate the
package-owned operating contract or introduce a prompt framework. The component
manifest pins them through the current manifest mechanism.

No WorkItem or task is included in this reusable set. For each Run, the
maintainer separately authors and commits a concrete pair under
`governance/work-items/`, selects the accepted profile, names exact payload
paths, and pins the expected development HEAD. The WFC/agent must not author the
policy or unrestricted WorkItem under which it will operate.

=== 7.2 Smallest decision forced by fixed profile scopes

Current profiles contain concrete `authorized_scope` paths, and admission
requires every phase scope to fit inside the WorkItem. A universal development
profile would therefore require every WorkItem to carry a broad fixed scope.
Bootstrap must not invent templating or a new policy abstraction to hide this
fact.

The small decision is to make the single profile reusable for the bounded first
developer-ergonomics workflow and its correction/re-review Hops, with the exact
least-authority path set finalized by the maintainer during Slice 2. Likely
payload areas are `Makefile`, the Ruff-only portion of `pyproject.toml`, one
small snapshot-script area, the existing package-boundary guard, and narrowly
related developer docs/tests. `src/`, `governance/`, runtime paths, remotes, and
unrelated docs/tests remain outside unless a concrete need is independently
authorized.

After dogfood, either reuse that exact profile for similarly scoped work or make
one explicit profile revision/new bounded profile. Do not add variables,
inheritance, a registry, or a general profile framework during bootstrap.

=== 7.3 Coherence checks without a provider

Add at most one small architecture test,
`tests/architecture/test_self_development_governance.py`, or an equivalently
small existing-test extension. It should:

* load policy, profile, and component manifest through production parsers;
* prove all selected component paths are tracked and represented by the
  manifest;
* prove governance inputs sit under policy governance paths;
* prove phase scopes do not overlap governance and do not exceed the policy
  ceiling;
* prove the profile selects only policy-permitted actions/evidence; and
* assert that push, runtime-clone paths, and automatic promotion are absent from
  the committed authority surface.

This is schema/authority validation only. It must not call the operator's
provider-capable path or invoke a real/fake AI provider.

== 8. First WFC-on-WFC dogfood WorkItem

The first post-bootstrap maintainer-authored WorkItem is *standalone developer
ergonomics*. It is deliberately useful and bounded enough for the current
Codex/Terra-medium execution binding.

=== 8.1 Payload

The WorkItem may authorize only the paths needed to deliver:

* a small Makefile with `make test`, `make lint`, `make format-check`, and
  `make check`;
* `make build` only when current packaging and local use justify it;
* Ruff/dev-tool configuration in `pyproject.toml` only as needed;
* small repository snapshot tooling and `make snapshot` /
  `make snapshot-multi`;
* an architecture guard closing the accepted post-carve-out `__package__`
  MINOR, after reading the exact accepted review evidence; and
* narrowly related development documentation and tests.

The WorkItem does not modify runtime WFC N, change engine architecture, add a
provider, create a CLI command, or widen its own governance.

=== 8.2 Snapshot contract

The WorkItem must inspect the actual spreadsheet-handling/Core snapshot
implementation and adapt only useful behavior. Future standalone snapshots
must have line numbers, a table of contents, an included repository tree, and
semantic condensation into fewer/larger useful files rather than many tiny
files. Every filename must be clearly WFC-prefixed so Core and WFC snapshots can
coexist in one analysis context, conceptually:

* `wfc_project_memory...`
* `wfc_repo_infrastructure...`
* `wfc_src_and_tests...`

The bootstrap does not decide exact groups, file formats, or single-versus-multi
partitioning. Those are implementation facts for the dogfood WorkItem.

=== 8.3 Empirical record

At acceptance, the maintainer records a short dogfood result in Project Memory
and updates backlog disposition. Use existing external Run evidence plus a
compact human summary; do not add telemetry machinery. Capture where practical:

* maintainer interventions and why;
* findings and correction/re-review hops;
* inconvenient setup/CLI steps;
* failed or non-unattended behavior;
* useful versus missing evidence;
* elapsed execution time; and
* model usage when the existing provider exposes it reliably.

These observations decide later priorities; they do not automatically authorize
features.

== 9. Subsequent dogfood order

=== 9.1 Second: fresh-reader adoption

Use the first Run's setup friction to author Getting Started, CLI reference, and
a minimal working example. The documentation must explicitly explain:

* `--executable` is Codex-CLI-compatible, not a provider selector;
* logical `WorkItem.repository` versus filesystem `--repository`;
* why the state root is new, external, and disjoint;
* pinned governing inputs, including all selected prompt components;
* a new Run versus absent retry/resume CLI behavior;
* the trusted Coordinator boundary for policy-authored evidence commands; and
* current Run-status and process-exit-code semantics.

=== 9.2 Third: narrow CLI UX v1 decision

Evaluate whether `wfc run --bundle <dir>` materially removes repeated argument
friction. Consider validation or status commands only when they expose existing
engine facts without new semantics. Reject any design that becomes another
workflow engine, a TUI, an outer loop, implicit resume, automatic WorkItem
authorship, or promotion automation.

=== 9.3 Fourth: unattended proof and environment boundary

Reproduce unattended behavior explicitly, including failure cases, before
selecting a boundary mechanism. Separate these questions:

. Does the Run ever seek interactive approval?
. What can the agent process reach/read/mutate?
. What trusted Git/evidence operations remain outside the agent boundary?
. What facts can the Coordinator verify and record?

Only then decide whether and how to use `bwrap` or an equivalent.

=== 9.4 Fifth: capability priority from evidence

Use accumulated dogfood to decide whether resumability (former 5C), another
provider/model control, or some different observed pain is next. No imported
slice sequence wins by default.

== 10. Bootstrap implementation slices

Purpose:: Establish one obvious split-forward project-control surface without

Exact likely files/areas::

* update `README.md` with the current-index entry point;
* update `docs/architecture.md` only with stable standalone authority and

* add `docs/README.adoc`;
* add `docs/backlog/README.adoc`; and
* add the single `docs/project_memory.adoc`.

Authority/invariant established:: Current versus provenance versus history is

Acceptance criteria::

* A fresh reader can identify every authority class from README -> one index.
* Project Memory contains only split-forward current state and provenance links.
* Backlog uses only the five dispositions in section 5 and preserves their

* Imported documents, provenance records, source, tests, package metadata, Core,

* All new/changed AsciiDoc renders at warning failure level; Markdown links and

Tests/checks:: `asciidoctor --failure-level WARN` for changed AsciiDoc;

Non-scope:: Governance YAML/profile implementation, WorkItem authoring,

Independent review:: Recommended as part of the consolidated bootstrap review;

=== Slice B2 -- bounded self-development authority and readiness

Purpose:: Commit the smallest consumer-style authority needed for a maintainer
to author the first dogfood WorkItem, document how the existing runtime clone is
used, and prove governance coherence without dispatch.

Exact likely files/areas::

* add the five-file set under `governance/self-development/` from section 7.1;
* add `docs/self-development.adoc` with invocation/topology/promotion guidance;
* add or extend one architecture test under `tests/architecture/` for section
  7.3; and
* refresh `docs/project_memory.adoc` and `docs/backlog/README.adoc` in the same
  accepted commit to record bootstrap completion and NEXT 1.

Authority/invariant established:: Maintainer owns governing inputs, policy scope,
WorkItem/task, push, and promotion; WFC coordinates only the committed envelope;
the agent cannot edit governance or runtime; accepted runtime N operates on
development N+1; first dogfood is ready to be authorized but is not yet begun.

Acceptance criteria::

* Production parsers accept policy/profile/manifest and selected component paths.
* Policy governance roots, ceiling, actions, evidence commands, and Hop limit
  are explicit and minimal.
* The one profile has finite current routes, fresh independent review, and a
  least-authority first-dogfood path set.
* No committed WorkItem claims blanket authority and no file grants push,
  runtime mutation, provider selection, hidden retry/resume, or automatic
  promotion.
* The self-development guide uses the existing runtime clone as execution
  authority, the development clone as payload, and an external new state root.
* All tests and document renders pass without provider invocation.
* After required independent acceptance and any corrective commit, the endpoint
  statement is true: *standalone WFC is ready for its first WFC-on-WFC dogfood
  WorkItem*.

Tests/checks:: Focused governance architecture test; full current pytest suite;
`asciidoctor --failure-level WARN`; `python -m build` only if already available
and useful for regression confidence; `git diff --check`; path-scope review; and
read-only confirmation that runtime HEAD/configuration did not change. Do not
run the operator or any provider-capable smoke path.

Non-scope:: The first WorkItem/task and its payload; Makefile; Ruff; formatting;
snapshots; CLI redesign; sandbox implementation; old 5C/resumability; provider
abstraction; second adapter; TUI; parallel or multi-agent execution; multi-repo
orchestration; automatic push/promotion; broad historical cleanup.

Independent review:: *Required.* Review the combined B1+B2 result adversarially,
including authority ceilings, profile fixed-scope consequences, two-clone
non-self-mutation, absence of push/promotion paths, and truthful limitations.
Resolve blocking findings by ordinary corrective commit before declaring
readiness. The review is not itself a WFC-on-WFC Run unless separately
authorized after bootstrap.
