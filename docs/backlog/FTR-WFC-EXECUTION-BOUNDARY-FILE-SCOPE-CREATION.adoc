== Problem

Slice A's boundary view mounts a Commission's writable scope as bind mounts of
*existing* host paths. A scope entry that names a file that does not exist
yet cannot be bound. The implementation pre-creates absent writable entries
as directories (the contract's mount rule 1) unless the phase declares the
path as a durable artifact (the reviewer shape). A worker phase whose
`authorized_scope` names a precise, not-yet-existing file therefore gets a
directory at that path, and the Commission cannot do its work under the
boundary.

*Interim decision (maintainer, 2026-11-26):* fail closed. The boundary refuses
such a Commission with a named preflight refusal. It never widens the
authorized scope to the nearest existing ancestor directory, and it never
creates a directory where a file was authorized.

== Why this is only an interim answer

Creating new files inside a precise file scope is a legitimate and regularly
needed use of the Commission model: new documents, new test modules, new
review artifacts. Long term the Execution Boundary must not reduce what a
Commission can express. A boundary that can only run Commissions whose files
already exist makes the boundary a reason to widen scopes, which is the wrong
incentive and weakens the integrity goal it exists for.

== Direction (not a design)

Requirements any later design has to meet:

. A worker can create exactly the files the scope names, and nothing next to
  them, without the view exposing a writable directory wider than the
  authorization.
. The creation is bounded by the same post-Hop scope check and trusted Git
  that bound every other change; no new trust is placed in the agent.
. The behaviour is the same for both provider adapters and does not depend on
  the provider's own sandbox.
. A Commission that declares file scope keeps working unchanged outside the
  boundary.

Mechanisms to evaluate then, without a preference recorded here: the
Coordinator creating empty placeholder files for each named path before the
Hop and removing the unchanged ones after it; binding the writable parent
directory and rejecting, after the Hop, every change outside the named files
(a deliberate, documented over-grant of visibility and mutation until the
post-Hop check, which weakens the preventive claim and therefore needs an
explicit maintainer decision); and a view-construction primitive that
supports a file-creation grant directly, if the platform offers one.

== Open decisions

. Whether a post-Hop-only enforcement of "no other file in the parent" is
  acceptable for any scope, or whether creation must be preventively
  confined.
. How an absent file placeholder interacts with Git-visible state and the
  trusted commit mechanics.
. Whether this belongs to Slice B's per-phase profile design or stands alone
  before it.
