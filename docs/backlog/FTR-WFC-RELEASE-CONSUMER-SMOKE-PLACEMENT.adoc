[[problem]]
== Problem

Beta 1's consumer qualification Q1 ran in under two minutes per Run. Its
preparation and its record did not.

From chapter 4's own account:

* the candidate was the wheel of hosted run #9, which needed an
  *authenticated* artifact download, was transferred by the maintainer to the
  Operator's machine, verified there, and compared *member by member* with a
  local rebuild from `git archive`, because the wheel carries no commit
  identifier (`source_commit` is `null` by design)
  (`ch04_release_management.adoc:531-556`); a rebuild's byte-identity is not
  claimed, and the container bytes are expected to differ (`:546-549`, and
  `:251-254` for the same reason stated as a gate condition);
* the Runs used `spreadsheet-handling` as the consumer, in one fresh worktree
  and branch each, and those branches and worktrees are kept as
  consumer-side artifacts (`ch04_release_management.adoc:293-296`,
  `:330-332`).

Verified directly against this repository:

* the Q1 post-run verifier is *not* in the repository -- `git ls-files
  scripts/` lists seven scripts and `q1_postrun_verify.py`, which chapter 4
  reports as having run (`:315`), is not among them -- so Beta 2 cannot
  repeat Q1 from the repository alone.

Stated by the independent basis and not independently re-verified here
(primary run evidence is not in the repository): that the tag run rebuilds, so
the tag build is "equivalent by argument, not identical by construction"
rather than the published bytes being the qualified bytes
(`wfc_release_process_comparison_fable_2026-11-23.adoc:310-312`); that the Q1
request files and verifier lived under `~/wfc-runtime-env/` (`:306-309`); and
that recording the results took documentation commits between the green run
and the tag (`:307-309`). The first of these is consistent with chapter 4's
own statement that the `check` job re-runs on the tag
(`ch04_release_management.adoc:255-257`).

The independent basis proposes moving the smoke into the `pypi` approval
pause: install the version from TestPyPI and run the smoke on the bytes PyPI
will receive. That removes the shuttle, the rebuild comparison and the
pre-tag evidence commits, and gives the TestPyPI stage a recurring purpose.

It also *reverses a recorded maintainer decision*. The P3 plan states, at its
recorded Q1 decisions of 2026-11-23: "Q1 stays before the tag; confirmed
again and finally"
(`postbeta_plan_p3_release_engineering.adoc:507-510`). Nothing in this record
pre-empts that. D1 is the maintainer's.

[[already]]
== What already exists and must not be duplicated

The basis suggests letting the smoke "create a throwaway repository, as the
quickstart example already does". That machinery is in the repository and
accepted at Run level:

* `examples/consumer-demo/make_workspace.py` creates a separate, disposable
  consumer repository with its own Evidence repository and ready-made
  requests; `examples/consumer-demo/rehearse.py` and `scripted_provider.py`
  rehearse complete Runs offline with a scripted stand-in for the provider.
  Slices S1 and S2 are implemented and independently accepted
  (`_open.adoc`'s consumer-demo-workspace entry).
* That record's *own* slice S3 is "one step after the existing
  clean-environment install smoke in the `check` job of
  `.github/workflows/release.yml`, and one sentence in the gate table" of
  chapter 4, requiring its decision D2
  (`FTR-WFC-CONSUMER-DEMO-WORKSPACE.adoc:558-562`, `:572-575`).

So the *offline* installed-wheel rehearsal in CI is already designed and owned
elsewhere. This slice is only about the *real-provider* smoke -- the one that
needs a provider credential and therefore cannot run inside a hosted job that
holds no secret. The two records must be reconciled before either is
commissioned, and this slice must *reuse* the kit rather than add a second
disposable-repository mechanism (see
link:beta2_release_streamlining_plan.adoc#d5[the plan's decision D5]).

[[ceiling]]
== The scope-ceiling constraint

Both variants change `.github/workflows/release.yml`, which is *not* in
`.wfc/config.yaml`'s `work_item_scope_ceiling`. A maintainer-decided
*temporary, file-exact* entry is required, as for the earlier E3 slice
(`_open.adoc`'s E3 card) and as for
link:FTR-WFC-RELEASE-PIPELINE-ROBUSTNESS.adoc[R3]. Changing
`.wfc/config.yaml` is a maintainer action; no Worker or Level-1 operator may
make it.

[[variants]]
== The two variants

Exactly one is implemented, after D1.

[[variant-a]]
=== Variant A -- the smoke runs in the approval pause

Shape:: Tag first. `publish-testpypi` uploads. While the run waits at the
`pypi` Environment, the Operator runs one repository-kept script that
installs the version *from TestPyPI* into a clean environment, creates a
disposable consumer repository with the existing demo kit, runs the two
real-provider smoke Runs (one per adapter) and prints a short result. The
maintainer reads it and approves or rejects. The result goes into the GitHub
Release text, not into `docs/`.
Scope:: `scripts/wfc_release_smoke.py` *or* an added entry point under
`examples/consumer-demo/` (the reconciliation of <<already>> decides which);
`.github/workflows/release.yml` (the summary line that tells the approver
what to run and on which version);
`docs/developer_guide/ch04_release_management.adoc` (the sequence, G7's
placement, the recovery consequence).
What it buys:: The smoke tests the bytes PyPI will receive. No authenticated
artifact download, no manual transfer, no member-by-member rebuild
comparison, no pre-tag evidence commits, no second `check` run on `main` as a
prerequisite. The real-provider check before PyPI -- a justified WFC
requirement -- is preserved.
What it costs:: A failed smoke spends a beta number, because the tag and the
TestPyPI version are already gone. For a `bN` line that is cheap; for a
non-beta version it is not. It also requires the Operator to be available,
authenticated and willing to act *while a hosted run is paused*, which is a
new operational coupling.
What it must not do:: Store a provider credential in CI; run a provider call
from a hosted job; make the approval conditional on anything automatic;
weaken G7's disposition, which stays the maintainer's.

[[variant-b]]
=== Variant B -- the smoke stays before the tag

Shape:: Nothing about the recorded decision changes. The *manual* part of the
identity argument is replaced by a mechanical one: `implementation_tree_sha256`
is printed in the job summary of both runs (R3 already adds it), and the tag
run asserts equality with the candidate's recorded value. The
member-by-member rebuild comparison is then unnecessary.
Scope:: `.github/workflows/release.yml` (one assertion step reading a
maintainer-supplied expected value, or a recorded comparison in the summary)
and `docs/developer_guide/ch04_release_management.adoc` (the sequence and
G7's evidence). Optionally the repository-kept smoke tooling, which is useful
under either variant and is the part of the basis's W3 that does not depend
on D1.
What it buys:: Most of Variant A's value for one assertion. The "equivalent
by argument" gap becomes "equal by measurement". The out-of-repository tooling
problem is solved independently of where the smoke runs.
What it costs:: The artifact shuttle and the pre-tag recording remain, in a
reduced form: the candidate still has to be downloaded and installed, and the
result still has to be recorded somewhere before the tag.
What it must not do:: Treat the digest equality as a substitute for G7's
disposition, or as proof that the two builds are byte-identical -- the wheel
*container* bytes are expected to differ, as chapter 4 already states
(`:546-549`). The digest covers the implementation tree, not the archive.

=== The part common to both

The smoke tooling itself -- the request files and the read-only post-run
verifier that lived under the Operator's home directory for Beta 1 -- belongs
in the repository under either variant, so that Beta 2's qualification can be
repeated from the repository alone. Implementing only that, and leaving the
placement question open, is a legitimate reduced form of this slice if D1
stays undecided.

== Non-goals

* No decision on D1, D5 or the demo-workspace record's D2.
* No consumer qualification Run, and no authorization for one. G7 stays the
  maintainer's disposition; a truthful stop stays a valid outcome.
* No provider credential in CI, no provider call from a hosted job, no new
  secret, no new third-party action, no new permission.
* No second disposable-repository mechanism. The existing demo kit is reused.
* No change to the TestPyPI stage's existence (the plan's D2), the build-once
  rule, the artifact hand-over or the C2 allow-list.
* No automatic gate that could approve or block a publication without the
  maintainer. The `pypi` Environment approval stays the single human
  authorization.
* No edit to the recorded Q1 result or the recorded G7 acceptance; after R2
  those live in cold storage and are historical.

== Acceptance criteria

Per the chosen variant. In both:

AC-1:: The manual member-by-member artifact comparison is no longer required
by the documented sequence, and chapter 4 says what replaced it.
AC-2:: The smoke's request files and its read-only post-run verifier are in
the repository, so the qualification can be prepared without any file outside
it.
AC-3:: Nothing in the slice performs, schedules, authorizes or implies a
push, tag, publication, provider call or credential creation. Verified by
reading every added command.
AC-4:: No repository secret, no new third-party action and no new permission
appears in `.github/workflows/release.yml`; the pinned action SHAs are
unchanged.
AC-5:: `python -m pytest -q` is green with the offline bundle; the smoke
script's own refusals are unit-tested on synthetic inputs, with no provider
and no network.
AC-6:: Strict render prints nothing for the changed chapter; the doc-catalog
check adds no unresolved link.
AC-7:: Variant A additionally: the script refuses to run unless the version
it is asked for is actually installed from the index it names, and the
printed result distinguishes "smoke passed", "smoke failed" and "smoke not
run" -- a missing result is never read as a pass.
AC-8:: Variant B additionally: the assertion fails when the two
`implementation_tree_sha256` values differ, and its failure message says that
a differing digest means a different implementation tree, not a different
archive.

[[tests]]
== Required tests

* The smoke script's argument handling, its refusals and its result
  formatting, on synthetic inputs, with no provider and no network.
* Variant A: a negative case proving that an absent or empty result is not
  reported as a pass.
* Variant B: a negative case for the digest assertion.
* No test asserts the workflow's prose or the gate table; P3 rejected that
  class of test and the reason still holds.

The live smoke itself is never slice acceptance. It is a maintainer-released
activity with its own gate (G7), exactly as Beta 1's Q1 was.

== Risks

R-1 Variant A spends a beta number on a failed smoke:: and does so after the
tag and the TestPyPI version are already gone. _Mitigation:_ none available
-- it is the cost of the variant, and it is why D1 is the maintainer's.
R-2 Variant A couples a hosted run's pause to a human being available and
authenticated:: a paused deployment is not free: it holds a concurrency slot
and an approval decision open. _Mitigation:_ the script is one command and
Beta 1's two Runs took under two minutes each; but the preparation did not,
and that is the real risk.
R-3 Duplicating the demo-workspace record's S3:: two records describing an
installed-wheel step in the same job. _Mitigation:_ <<already>>'s
reconciliation, required *before* either is commissioned.
R-4 A digest read as a byte-identity claim:: Variant B. _Mitigation:_ AC-8's
failure message and chapter 4's existing statement that the container bytes
differ by design.
R-5 Provider availability and model support:: Beta 1's Q1-B depended on a
specific Codex worker/reviewer combination, and the P3 plan required an
unsupported model to be *recorded as such and not silently replaced*
(`:442-449`). _Mitigation:_ carry that rule into the script's result
vocabulary.
