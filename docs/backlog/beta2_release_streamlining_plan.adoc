== What this plan cannot know

Nothing about GitHub, PyPI or TestPyPI is verifiable from this repository.

*[X]* and is an *external assumption*, never a fact:

  tag locally (`git tag -l`) and shows that its commit `baab49e` is an
  ancestor of the last-fetched `refs/remotes/origin/main`; neither tells
  whether the tag *ref* reached the remote.
* *[X]* Whether the tag-mode run of the workflow ever executed, and how it
  ended. Chapter 4 records that it had not
  (`ch04_release_management.adoc:570`) and nothing later contradicts that in
  the repository.
* *[X]* Whether `0.1.0b1` is on PyPI or TestPyPI, and whether either upload
  carries attestations.
* *[X]* Whether the Trusted Publisher entries, the `testpypi` and `pypi`
  Environments and the `pypi` required-reviewer rule exist as ES-1 and ES-2
  describe them.

  and the deprecation timeline of the Node runtime the pinned artifact

[[architecture]]
== The target release architecture for WFC

The architecture does not change. WFC already implements the shape the basis
proposes — one `release.yml`, build once, audited artifact, clean-venv
install, an Environment approval before the irreversible step, release notes
frozen before the tag, zero repository secrets, every action SHA-pinned. This
plan closes three gaps in it and removes recurring manual work; it adds no
stage, no gate class, no agent role, no program and no governance layer.

|===

|One release-preparation commit on `main`: the version set everywhere it is

release-notes heading frozen. Today this is hand editing across thirteen
files; <<r1,R1>> makes it one command and one commit.

Recovery rules, correcting the one state chapter 4 currently gets wrong
(<<r2,R2>>, W1):

[cols="2,3",options="header"]
|===
|State |Action

|Failed before any upload |Fix on `main`, delete the tag, tag again.
|TestPyPI upload succeeded, a later step failed |Transient failure: re-run
the failed jobs. Content change: the next version. *Never* delete and re-tag
— TestPyPI refuses a second upload of the version and `publish-pypi` needs
`publish-testpypi`, so a corrected tag cannot pass.
|PyPI upload succeeded, a later job failed |Re-run the failed jobs. Never
re-tag.
|Wrong content on PyPI |Yank; release the next version.
|===

*Exception, for as long as <<r3,R3>> is only planned:* "re-run the failed
jobs" holds for every job *except* `release`. If that job already created the
GitHub Release, a re-run fails — `release.yml:371-374` calls `gh release
create` with no pre-check and no `--clobber`. Until R3 integrates, attach the
missing assets by hand. Two different things are therefore wrong today and
are corrected in different slices: the documented rule for the TestPyPI-spent
state (<<r2,R2>>, documentation only) and the `release` job's non-idempotence
(<<r3,R3>>, workflow). R2 writes the exception above into the chapter rather
than claiming the pipeline is already re-runnable, and R3 strikes it when the
behaviour changes. Because publication uses stored bytes, no state needs a
rebuild — that part *is* already true of the implementation
(`release.yml:180-186`, `:302-312`, `:336-346`).

[[ceiling]]
== The scope-ceiling constraint

`.wfc/config.yaml`'s `work_item_scope_ceiling` is `src`, `tests`, `scripts`,
`docs`, `README.md`, `pyproject.toml`, `Makefile`, `examples/consumer-demo`.
`.github/` is *not* in it, and `.wfc/config.yaml` is itself outside every
WorkItem scope.

* <<r1,R1>> and <<r2,R2>> are entirely inside the ceiling and need no change
  to it.
* <<r3,R3>> and <<r4,R4>> change `.github/workflows/release.yml` and
  therefore need a *maintainer-decided temporary, file-exact ceiling entry*,
  exactly as the earlier E3 slice had (`_open.adoc`'s E3 card: the temporary
  entry `f4d575b` was added for E3 and removed again after integration).
  Granting
  it is a maintainer action; neither this plan nor a Worker may make it.

[[slices]]
== The slices

Four slices. W1–W10 group into these and not into ten, because the recurring
cost they remove falls into four places: the preparation commit, the release
chapter, the pipeline's own robustness, and the placement of the consumer
smoke. Each slice is independently commissionable, independently useful, and
sized for one Run. <<r4,R4>> is conditional on <<d1,D1>>; the other three are
unconditional. Of the two decisions that would reverse a recorded maintainer
decision, <<d1,D1>> determines *which variant* R4 implements, while <<d6,D6>>
is carried by no slice at all (<<d6-slices>>).

The repository's own default execution binding (`.wfc/config.yaml`) is
already Sonnet worker and Opus reviewer — the *demanding* profile. Where a
slice says "demanding", it is asking for the default, not for an exception.

[[ch04-ownership]]
=== One lane, because every slice owns the chapter lines it makes true

Chapter 4 is the single owning document for the release contract, and the
repository's rule is that
link:{backlog-docs}/developer_guide/ch03_engineering_conventions.adoc[the
owning documentation is maintained when behaviour changes]. <<r2,R2>> writes
the chapter first and names R1's and R3's work as *planned*, the way E1 named
E2's and E3's tooling. The rule then says who retires each "planned": the
slice that makes it real, in the same slice, because that is the moment the
chapter would otherwise become untrue.

[cols="2,3,1",options="header"]
|===
|Chapter statement whose truth a later slice changes |Where |Retired or
corrected by

|The preparation command `make release-prepare` in the runbook
|Runbook, prepare step
|<<r1,R1>>
|What `release-check` asserts (today without the tag-pinned README assertion,
`ch04:267` and `:369`) — outdated by R1's extension of the tool, not written
as planned
|G1 row and runbook preflight
|<<r1,R1>>
|The `release` job is idempotent, so "re-run the failed jobs" needs no
exception
|Recovery table
|<<r3,R3>>
|`SHA256SUMS.txt` is attached to the GitHub Release
|CI section and runbook publish step
|<<r3,R3>>
|The `check` job writes the decision facts to the job summary
|CI section
|<<r3,R3>>
|===

Five rows, and the table is complete *because* no slice of this plan changes
anything else the chapter asserts. The one candidate for a sixth row is kept
out deliberately: making `python-compat` a prerequisite of `publish-testpypi`
would outdate `ch04:165` and `:566` and reach the gate list, so that change is
not in any slice at all but is maintainer decision <<d6,D6>>, whose
documentation consequence travels with the maintainer's own change
(<<d6-slices>>). The rule is the same one either way — whoever changes the
behaviour maintains the owning documentation — and it is the reason the
decision is not carried as a conditional branch inside <<r3,R3>>.

Because both R1 and R3 end in a chapter-4 edit, and *the file is the unit of
conflict, not the section*, they cannot be in flight at the same time: one
lane, not two. This is a deliberate change from an earlier draft of this plan,
which kept chapter 4 out of R1 and R3 entirely to buy a second lane. That
version left the chapter stating five existing things as planned after its own
prioritized order had run — including a prepare command the operator is told
to use — and pinned the defect with acceptance criteria that forbade repair.
The schedule gain is near-zero here (one maintainer, one Commission at a time)
and the price was an untrue runbook, so the lane is given up and not the
chapter's truth.

What remains true, and is what a reader needs: R1 and R3 are independent in
*content* — neither consumes the other's product, neither reads the other's
file (`scripts/`, `Makefile`, `tests/` on one side,
`.github/workflows/release.yml` on the other), and the maintainer may
commission them in either order after R2. Only their chapter-4 edits are
mutually exclusive in time. R4 re-enters chapter 4 for the smoke sequence and
is likewise sequenced after R3.

The *semantic* coupling behind the first retirement, stated so it is not
rediscovered: one row of R2's recovery table only becomes unconditionally true
once R3 integrates (the `release` job's non-idempotence,
`release.yml:371-374`). R2 therefore writes that row with an explicit "while
R3 is planned" exception, and R3 removes the exception in the same slice that
removes the behaviour.

If only one slice is ever commissioned, commission R2: it corrects a recovery
rule that would make the first real failure start at a dead end, and it costs
no behaviour change at all.

[[autonomy]]
== What an autonomous Level-1 operator may do, and what it may not

May, autonomously — prepare, implement and integrate locally on `main`::
Author and launch the Commissions for R1, R2 and R3 within their stated
scopes; run the required suite, the strict render, the doc-catalog check,
`make release-check` (read-only), `make build` and `make dist-audit` locally;
integrate accepted candidates into local `main`; record implementation,
acceptance and Run evidence in the controlling records and `_open.adoc` as
link:README.adoc[backlog upkeep] describes; run `make release-prepare` once
R1 exists, on the maintainer's instruction, producing an ordinary local
commit.

Needs a human decision, always::
* Any `git push`, of a branch or of `main`.
* Creating or pushing any tag.
* Any TestPyPI or PyPI action, including a re-run of a publishing job.
* Any GitHub web-interface setting: Environments, required reviewers, Trusted
  Publisher entries, secrets, branch or tag protection, Actions enablement.
* Changing `.wfc/config.yaml`, including the temporary scope-ceiling entry
  R3 and R4 need.
* Runtime promotion or installation of any WFC version.
* Accepting <<d1,D1>> (W3) or <<d6,D6>> (W7) — both would reverse a recorded
  maintainer decision — and any other decision in <<decisions>>. For D6, also
  *executing* it: the one-line `needs:` edit of Option A or the classifier
  line of Option B, together with the chapter-4 lines each of them outdates,
  is maintainer work and belongs to no slice (<<d6-slices>>).
* The release approval itself (G8) and the release decision.
* Resolving a new action pin, which needs network access the agent
  environment may not have, and must never be an invented SHA.

The separation is not new; it is ES-1 to ES-6 and G7/G8 of the P3 plan,
restated here only so that each slice can be read on its own.

[[d1]]
D1 — Does the real-provider consumer smoke move after the tag? (W3):: The P3
plan records, at its §(c), that "Q1 stays before the tag; confirmed again and
finally". The basis proposes the opposite.
+
*Option A — move it into the `pypi` approval pause.* The smoke runs on the
version installed from TestPyPI, i.e. on the bytes PyPI will receive. Removes
the authenticated artifact download, the manual transfer, the rebuild
comparison and the pre-tag evidence commits; gives TestPyPI a recurring
purpose. Cost: a failed smoke spends a beta number, and the Operator must be
able to run a provider-authenticated script while a hosted run waits.
+
*Option B — keep it before the tag.* Nothing about the recorded decision
changes. The manual comparison is replaced by printing
`implementation_tree_sha256` in both runs' summaries and asserting equality
in the tag run, which <<r3,R3>> already makes available. Cost: the artifact
shuttle and the pre-tag evidence commits remain, in a reduced form.
+
*Recommendation: Option B for Beta 2, Option A considered again for the first
non-beta release.* Option A's benefit is real but its cost lands exactly
where Beta 2 is weakest — the tag-mode path has never run *[X]*, so Beta 2
would exercise an untested publication chain *and* a relocated qualification
in the same release. Option B takes most of Option A's value (the identity
argument becomes mechanical) for one assertion, and reverses no decision.

[[d2]]
D2 — Is the TestPyPI stage permanent?:: Its Beta-1 value — proving the OIDC
wiring and metadata acceptance — is spent once. Under <<d1,D1>> Option A it
gains a recurring purpose; under Option B it does not, and it still burns a
version number on any later failure. *Recommendation: keep it for Beta 2 and
revisit after two clean releases.* It is one job, it has never cost anything
observable *[X]*, and removing it while the tag path is unproven removes a
rehearsal exactly when a rehearsal is worth most.

[[d3]]
D3 — Lockfile, Dependabot, or manual SHA pins? (W6):: *Recommendation: keep
manual SHA pins; add neither mechanism now.* WFC pins five actions. The
documented resolution procedure already exists
(`ch04_release_management.adoc:216-218`). A Dependabot stream is a recurring
triage obligation for a single maintainer that plausibly exceeds the two or
three manual resolutions a year it would replace, and the lockfile's
availability is *[X]*. The one concrete pending item — the Node-runtime
deprecation warning of the two artifact actions (`:515`) — is a single
one-time pin bump, and it needs `git ls-remote`, so it is an Operator or
maintainer step, not an FTR slice. Revisit if a security advisory against a
pinned action ever arrives.

[[d4]]
D4 — Are the chapter 9 "What was verified" version literals records or pins?::
`tests/architecture/test_consumer_tutorial_pages.py:180` requires the literal
`0.1.0b1` in each tutorial's "What was verified" section, and the pages say
"On the installed `wfc` 0.1.0b1". Either reading is defensible: the sentence
records the version a rehearsal was verified against (historical, stays), or
it tells a reader which version the page describes (a pin, re-pinned every
release). The answer decides whether five tutorial lines and one test literal
belong in <<r1,R1>>'s surface list. *Recommendation: treat them as records
and leave them.* Re-pinning them would claim a verification that was not
repeated. The test literal should then be changed to assert *a* version is
named, not that it is the current one — a one-line change inside <<r1,R1>>.

[[d5]]
D5 — The consumer for the smoke (W10):: `core` (as Beta 1 used, leaving two
branches and worktrees there) or a disposable repository.
*Recommendation: the disposable repository, reusing
`examples/consumer-demo/make_workspace.py`, which already creates one with
its own Evidence repository and four ready requests.* This is not new work;
it is an accepted, integrated kit. The decision overlaps the demo-workspace
record's own D2 and should be taken once, there or here, not twice.

[[d6]]
D6 — Does `python-compat` become a gate, or do the classifiers go? (W7):: The
job is informational *by decision*, not by oversight: `release.yml:188-195`
records "maintainer decision of 2026-11-23 ... no release gate (no job waits
for it; it reports the compatibility facts for the maintainer)",
`ch04_release_management.adoc:164-168` that it is "not a prerequisite of any
publishing job", and `:566` calls it "the informational `python-compat`
matrix". (`ch04:243`'s "every gate is release-blocking" is scoped to the
enumerated gates G1-G8 at `:267-274`, which do not list it, so the chapter
does not contradict itself.) What remains true is the gap the basis names:
`pyproject.toml:17-20` advertises CPython 3.10-3.13 while only CPython 3.13
on Linux x86-64 is qualified, and a red compatibility job stops nothing.
Changing either side reverses or completes a maintainer decision, so the
choice is the maintainer's. *No slice of this plan carries either change*;
see <<d6-slices>> below for why.
+
*Option A — gate it.* Add `python-compat` to the `needs:` of
`publish-testpypi` (one line, no run-time cost: the job already runs on every
trigger, after `check`). The advertised interpreters then cannot regress
unnoticed. Costs, all of them: a compatibility failure on an interpreter that
is *not* the qualified profile blocks a release; the 3.10-3.12 jobs install
from the ordinary index rather than the offline bundle, so an upstream
dependency can turn the release red for a reason outside the repository; and
the change does not end in `release.yml`. It makes `ch04:165` ("not a
prerequisite of any publishing job"), `:566` ("the informational
`python-compat` matrix") and the workflow's own comment
(`release.yml:188-195`: "no release gate (no job waits for it)") false, and it
puts something that can stop a release *outside* the gate list G1-G8 — so
either that list gains an entry or the chapter has to say that a
release-blocking prerequisite is deliberately not a numbered gate. The gate
list and the G namespace are P3's decided contract: <<r2,R2>> is explicitly
forbidden to extend them and <<r3,R3>> does not own them.
+
*Option B — drop the 3.10-3.12 classifiers.* The one-line change the E1 card
already names as available (`_open.adoc:158`); `requires-python = ">=3.10"`
stays, so nothing about installability changes. The advertised surface then
matches the qualified profile and the informational job keeps its decided
role. Costs: the package stops advertising interpreters it very likely
supports; the job's results become purely informational with nothing depending
on them; and `ch04:167` ("`requires-python` ... and the classifiers are
unchanged") and the same workflow comment have to be brought up to date.
No gate and no contract item moves.
+
*Option C — leave both as they are* and record the gap as accepted, as the
2026-11-23 decision already does. Nothing changes anywhere.
+
*Recommendation: Option C for Beta 2, with Option A reconsidered for the first
non-beta release, once the tag path has actually run.* The gap is a
correctness question, not a recurring cost: nothing manual repeats because of
it. Once <<r3,R3>> lands, `python-compat`'s result is among the facts the
maintainer reads at the `pypi` pause, so a compatibility regression is visible
without being release-blocking — which is most of Option A's value for none of
its price. Against Option A now: it reverses a decision taken on 2026-11-23
with the same facts in view, it lands that reversal in the release where the
tag path has never run *[X]*, its failure mode is an index-side dependency
change reddening a release, and its documentation consequence reaches the gate
list. There is also no precedent to lean on: P3 excluded a matrix from this
release altogether — E3's non-goals say "no ... Python or architecture matrix"
(`postbeta_plan_p3_release_engineering.adoc:332-334`) and "a Python/OS matrix"
is in its *Not in this release* list (`:615`) — and the matrix that exists at
all exists because the maintainer added it on 2026-11-23 *as an informational
job and explicitly not as a gate* (`_open.adoc:181`). Option A would therefore
do what neither P3 nor that decision did. Option B is the
honest alternative if the maintainer would rather shrink
the advertisement than enforce it; it reverses nothing, touches no gate, and
stays available as a one-line change at any time.
+
[[d6-slices]]
*What this means for the slices.* <<r3,R3>> contains no `needs:` edit and no
`python-compat` change at all — not even a conditional one — and <<r2,R2>>
describes the job as the files describe it when R2 runs (today: informational,
gating nothing). If the maintainer takes Option A or Option B, it is *their*
change, and the chapter-4 lines named above travel with it, exactly as the
pending action-pin bump of <<d3,D3>> is a maintainer or Operator step rather
than an FTR slice. The reason is this plan's own rule that whoever changes the
behaviour maintains the owning documentation (<<ch04-ownership>>): here the
behaviour change is a decision reversal in the maintainer's hands, and its
documentation consequence reaches a contract list no slice of this plan may
touch. Carried as a conditional branch inside R3, it would land a chapter that
denies that a job which can stop the publication chain can.

[[not-done]]
== Deliberately not done, and why

Keep unchanged what the product justifies. The following are *not* proposed,
each with the recurring cost it does not remove:

* *A post-publication verification job (W9).* It would replace two cheap
  manual page checks and add a job after the irreversible step whose natural
  failure mode — index propagation delay — produces an alarming red run that
  means nothing. Revisit if releases become frequent.
* *A `MANIFEST.in` (the basis's C6, for `core`).* WFC's sdist is already
  exactly scoped and the exact allow-list audit enforces it mechanically
  (`ch04_release_management.adoc:68-72`, `scripts/wfc_dist_audit.py`). A
  second control against the same failure buys nothing.
* *Removing the TestPyPI stage*, *published HTML or a Pages repository*, *a
  Python or architecture matrix as a gate*, *signing or provenance beyond the
  publish action's defaults*, *a second qualified profile*. All are P3
  decisions or P3 non-goals; none is reopened here. The one borderline case —
  gating the informational matrix the maintainer added after P3 — is *routed*
  to the maintainer as <<d6,D6>>, with Option C recommended, and is in no
  slice.
* *Any new governance layer, gate class, label namespace, agent role,
  program or Phase Execution Binding.* The existing programs `robust@v1` and
  `simple@v1` and the existing bindings carry every slice.
* *A test that asserts the workflow matches the documented gates.* P3
  rejected it, for the reason that it would parse YAML to restate prose; that
  reason still holds.
* *Making tests read the version from `pyproject.toml` (part of W2).* C1
  names the literal at `tests/architecture/test_bp1_identity.py:41`
  deliberately, "so a future bump touches it knowingly". <<r1,R1>> keeps the
  literal and adds a consistency guard instead, which closes the real gap
  (nothing local today compares `pyproject.toml` with
  `implementation_identity.VERSION`) without reversing a decided contract.
* *Any version bump, push, tag, publication or external setting.* Not in any
  slice, by construction.
