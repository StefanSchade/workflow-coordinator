== What this plan cannot know

Nothing about GitHub, PyPI or TestPyPI is verifiable from this repository.

*[X]* and is an *external assumption*, never a fact:

* *[X]* Whether the local tag `v0.1.0b1` was pushed. The repository shows the
  tag locally (`git tag -l`) and shows that its commit `baab49e` is an
  ancestor of the last-fetched `refs/remotes/origin/main`; neither tells
  whether the tag *ref* reached the remote.
* *[X]* Whether the tag-mode run of the workflow ever executed, and how it
  ended. Chapter 4 records that it had not
  (`ch04_release_management.adoc:570`) and nothing later contradicts that in
  the repository.
* *[X]* Whether `0.1.0b1` is on PyPI or TestPyPI, and whether either upload
  carries attestations.
* *[X]* Whether the Trusted Publisher entries, the `testpypi` and `pypi`
  Environments and the `pypi` required-reviewer rule exist as ES-1 and ES-2
  describe them.
* *[X]* The availability and shape of GitHub's workflow dependency lockfile,
  and the deprecation timeline of the Node runtime the pinned artifact
  actions use. The repository records only that run #9 warned about it
  (`ch04_release_management.adoc:515`).

Every slice below is written so that it can be prepared, implemented and
integrated *locally* without resolving any of these. Where a step depends on
one, the dependency is named and the step is conditional.

[[architecture]]
== The target release architecture for WFC

The architecture does not change. WFC already implements the shape the basis
proposes — one `release.yml`, build once, audited artifact, clean-venv
install, an Environment approval before the irreversible step, release notes
frozen before the tag, zero repository secrets, every action SHA-pinned. This
plan closes three gaps in it and removes recurring manual work; it adds no
stage, no gate class, no agent role, no program and no governance layer.

Recovery rules, correcting the one state chapter 4 currently gets wrong
(<<r2,R2>>, W1):

[cols="2,3",options="header"]
|===
|State |Action

|Failed before any upload |Fix on `main`, delete the tag, tag again.
|TestPyPI upload succeeded, a later step failed |Transient failure: re-run
the failed jobs. Content change: the next version. *Never* delete and re-tag
— TestPyPI refuses a second upload of the version and `publish-pypi` needs
`publish-testpypi`, so a corrected tag cannot pass.
|PyPI upload succeeded, a later job failed |Re-run the failed jobs. Never
re-tag.
|Wrong content on PyPI |Yank; release the next version.
|===

Because publication uses stored bytes, "re-run the failed jobs" is safe in
every state and no state needs a rebuild. This is already true of the
implementation; only the documented rule is wrong.

[[ceiling]]
== The scope-ceiling constraint

`.wfc/config.yaml`'s `work_item_scope_ceiling` is `src`, `tests`, `scripts`,
`docs`, `README.md`, `pyproject.toml`, `Makefile`, `examples/consumer-demo`.
`.github/` is *not* in it, and `.wfc/config.yaml` is itself outside every
WorkItem scope.

* <<r1,R1>> and <<r2,R2>> are entirely inside the ceiling and need no change
  to it.
* <<r3,R3>> and <<r4,R4>> change `.github/workflows/release.yml` and
  therefore need a *maintainer-decided temporary, file-exact ceiling entry*,
  exactly as the earlier E3 slice had (`_open.adoc`'s E3 card: the temporary
  entry `f4d575b` was added for E3 and removed again after integration).
  Granting
  it is a maintainer action; neither this plan nor a Worker may make it.

[[slices]]
== The slices

Four slices. W1–W10 group into these and not into ten, because the recurring
cost they remove falls into four places: the preparation commit, the release
chapter, the pipeline's own robustness, and the placement of the consumer
smoke. Each slice is independently commissionable, independently useful, and
sized for one Run. <<r4,R4>> is conditional on <<d1,D1>>.

The repository's own default execution binding (`.wfc/config.yaml`) is
already Sonnet worker and Opus reviewer — the *demanding* profile. Where a
slice says "demanding", it is asking for the default, not for an exception.

[[autonomy]]
== What an autonomous Level-1 operator may do, and what it may not

May, autonomously — prepare, implement and integrate locally on `main`::
Author and launch the Commissions for R1, R2 and R3 within their stated
scopes; run the required suite, the strict render, the doc-catalog check,
`make release-check` (read-only), `make build` and `make dist-audit` locally;
integrate accepted candidates into local `main`; record implementation,
acceptance and Run evidence in the controlling records and `_open.adoc` as
link:README.adoc[backlog upkeep] describes; run `make release-prepare` once
R1 exists, on the maintainer's instruction, producing an ordinary local
commit.

Needs a human decision, always::
* Any `git push`, of a branch or of `main`.
* Creating or pushing any tag.
* Any TestPyPI or PyPI action, including a re-run of a publishing job.
* Any GitHub web-interface setting: Environments, required reviewers, Trusted
  Publisher entries, secrets, branch or tag protection, Actions enablement.
* Changing `.wfc/config.yaml`, including the temporary scope-ceiling entry
  R3 and R4 need.
* Runtime promotion or installation of any WFC version.
* Accepting <<d1,D1>> (W3), and any other decision in <<decisions>>.
* The release approval itself (G8) and the release decision.
* Resolving a new action pin, which needs network access the agent
  environment may not have, and must never be an invented SHA.

The separation is not new; it is ES-1 to ES-6 and G7/G8 of the P3 plan,
restated here only so that each slice can be read on its own.

[[decisions]]
== Open maintainer decisions

[[d1]]
D1 — Does the real-provider consumer smoke move after the tag? (W3):: The P3
plan records, at its §(c), that "Q1 stays before the tag; confirmed again and
finally". The basis proposes the opposite.
+
*Option A — move it into the `pypi` approval pause.* The smoke runs on the
version installed from TestPyPI, i.e. on the bytes PyPI will receive. Removes
the authenticated artifact download, the manual transfer, the rebuild
comparison and the pre-tag evidence commits; gives TestPyPI a recurring
purpose. Cost: a failed smoke spends a beta number, and the Operator must be
able to run a provider-authenticated script while a hosted run waits.
+
*Option B — keep it before the tag.* Nothing about the recorded decision
changes. The manual comparison is replaced by printing
`implementation_tree_sha256` in both runs' summaries and asserting equality
in the tag run, which <<r3,R3>> already makes available. Cost: the artifact
shuttle and the pre-tag evidence commits remain, in a reduced form.
+
*Recommendation: Option B for Beta 2, Option A considered again for the first
non-beta release.* Option A's benefit is real but its cost lands exactly
where Beta 2 is weakest — the tag-mode path has never run *[X]*, so Beta 2
would exercise an untested publication chain *and* a relocated qualification
in the same release. Option B takes most of Option A's value (the identity
argument becomes mechanical) for one assertion, and reverses no decision.

[[d2]]
D2 — Is the TestPyPI stage permanent?:: Its Beta-1 value — proving the OIDC
wiring and metadata acceptance — is spent once. Under <<d1,D1>> Option A it
gains a recurring purpose; under Option B it does not, and it still burns a
version number on any later failure. *Recommendation: keep it for Beta 2 and
revisit after two clean releases.* It is one job, it has never cost anything
observable *[X]*, and removing it while the tag path is unproven removes a
rehearsal exactly when a rehearsal is worth most.

[[d3]]
D3 — Lockfile, Dependabot, or manual SHA pins? (W6):: *Recommendation: keep
manual SHA pins; add neither mechanism now.* WFC pins five actions. The
documented resolution procedure already exists
(`ch04_release_management.adoc:216-218`). A Dependabot stream is a recurring
triage obligation for a single maintainer that plausibly exceeds the two or
three manual resolutions a year it would replace, and the lockfile's
availability is *[X]*. The one concrete pending item — the Node-runtime
deprecation warning of the two artifact actions (`:515`) — is a single
one-time pin bump, and it needs `git ls-remote`, so it is an Operator or
maintainer step, not an FTR slice. Revisit if a security advisory against a
pinned action ever arrives.

[[d4]]
D4 — Are the chapter 9 "What was verified" version literals records or pins?::
`tests/architecture/test_consumer_tutorial_pages.py:180` requires the literal
`0.1.0b1` in each tutorial's "What was verified" section, and the pages say
"On the installed `wfc` 0.1.0b1". Either reading is defensible: the sentence
records the version a rehearsal was verified against (historical, stays), or
it tells a reader which version the page describes (a pin, re-pinned every
release). The answer decides whether five tutorial lines and one test literal
belong in <<r1,R1>>'s surface list. *Recommendation: treat them as records
and leave them.* Re-pinning them would claim a verification that was not
repeated. The test literal should then be changed to assert *a* version is
named, not that it is the current one — a one-line change inside <<r1,R1>>.

* *Any version bump, push, tag, publication or external setting.* Not in any
