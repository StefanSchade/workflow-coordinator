== Observed behavior

`commissioning.render_commission` (`src/workflow_coordinator/commissioning.py`,
around lines 367-440) derives each profile phase's `authorized_scope` from
its program-declared scope slot: a worker-role slot (`"S"`) resolves to the
*complete* `Intent.scope` -- every path the Commission touches, including
both durable reviewer-artifact paths -- while a reviewer/durable-artifact
slot resolves only to that phase's own specific
`durable_artifacts[artifact_key]` paths.

Directly confirmed in the committed rendered
`governance/commissions/wfc-doc-authority-index-001/profile.yaml`: both
worker phases (`implement`, `correct`) list `authorized_scope` as
`[docs/README.adoc, <broad_review artifact path>, <focused_review artifact
path>]` -- the complete Commission Intent scope -- while each reviewer
phase (`broad_review`, `focused_review`) lists `authorized_scope` limited to
only its own single durable-artifact path.

Worker role/task instructions (persona text, the task's `withheld_authority`,
etc.) prohibit a worker from rewriting reviewer-authored durable artifacts,
and no such violation occurred in this accepted Run -- no worker-phase
mutation of a reviewer artifact was attempted or needed. The gap observed
here is purely in the declarative scope data: technical path-level write
separation between "the worker's own deliverable paths" and "the reviewer's
durable-artifact paths" is not mechanically enforced for worker phases the
way it already is for reviewer phases. The boundary is currently
instructional only, not a mechanical `authorized_scope` boundary, for the
worker side.

== Desired direction (not committed)

Investigate whether a future program version could narrow worker-phase
`authorized_scope` to exclude paths that are exclusively a different
phase's required durable artifact, while preserving the worker's ability to
read/reference them where legitimately needed -- as a defense-in-depth
mechanical boundary alongside the existing instructional prohibition. Any
such design should be assessed against `FTR-WFC-EXECUTION-TRUST-BOUNDARIES`
(the broader mutation/visibility/execution trust-dimension framework, of
which this is one concrete, narrower candidate instance) and
`FTR-WFC-PHASE-SCOPED-RESULT-SCHEMA` (a structurally similar "narrow by
phase-declared configuration" pattern, there applied to result shape rather
than write scope).
