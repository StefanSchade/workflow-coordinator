== Update: sandbox reproduction and current limits (2026-11-12)

A maintainer-requested, separate agent-side full pytest diagnostic reproduced
this class of failure in a network-restricted sandbox. The module-scoped
`prepared` fixture called the real Harness `prepare`; its Runtime export's
`pip install` attempted to resolve the isolated build dependency
`setuptools>=68` at the package index. The captured test output showed
repeated DNS failures (`Name or service not known`) for `/simple/setuptools/`,
then `No matching distribution found for setuptools>=68`, surfaced as a
Harness refusal. Fixture-dependent tests consequently errored. Other tests
also failed in that diagnostic, but the complete output was not retained and
their individual causes have not been established here. This is an observed
sandbox diagnostic, not Coordinator-trusted evidence; it used the prepared
Development interpreter but different sandbox, PATH, temporary-directory and
pytest-cache conditions. No claim is made that every offline configuration
fails: a sufficiently provisioned local source/cache and pip configuration may
satisfy resolution without an external index.

Beyond `prepared`, `test_wfc_op.py` has a separate real `completed_run`
fixture and individual drift, pinned-preflight, frozen-PATH, shell-quoting
and optional real-wrapper tests that invoke real preparation. Both Runtime
and Development environment builders install into fresh venvs. Some early
refusal tests stop before installation, and other scratch tests monkeypatch
the environment builders; not every `prepare` call reaches pip. Development's
`[dev]` dependencies can require resolution too. No external-index request is
required if all needed candidates are available through the configured local
sources; ordinary local Git clones alone do not make the nested installs
offline-independent.

The later FTR05 review Run `RUN-4ffabb5371c04888b997569a22c63233` had a
Coordinator-owned `task-check` timeout after 900 seconds, but persisted no
command output. Its execution was outside the diagnostic agent sandbox, so
network/DNS or pip retries are *possible*, not established causes. See
link:BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[the separate timeout-diagnostics BUG].
The earlier observations and hypotheses below are retained as historical
context; assertions that the offline fixture failure had not been reproduced
are superseded by this update. The sandbox reproduction does not establish
that the Coordinator timeout had the same cause.

== What is verified (test implementation and dependency facts)

`tests/unit/test_wfc_op.py`'s module-scoped `prepared` fixture
(`tests/unit/test_wfc_op.py:265-289`) makes "one full, real `prepare` call"
and is reused read-only by every LAUNCH test in that file. `prepare`
(`scripts/wfc_op.py::cmd_prepare`) calls both
`prepare_runtime_environment` (`scripts/wfc_op.py:373-389`) and
`prepare_development_environment` (`scripts/wfc_op.py:391-406`) --
`cmd_prepare`, around lines 741-742. Each of these builds a fresh venv
(`build_venv`, `scripts/wfc_op.py:334-339`) and then runs `pip install`
against a local source tree (`pip_install`, `scripts/wfc_op.py:341-345):
the Runtime path installs a `git archive` export of the pinned Runtime
commit; the Development path installs the live Development checkout with
its `[dev]` extra (`build>=1.2`, `pytest>=8.2`, `ruff>=0.6`).

`pyproject.toml` (`[build-system]`) declares `requires = ["setuptools>=68"]`
with `build-backend = "setuptools.build_meta"` and no `[tool.setuptools]`
override disabling build isolation. A plain `pip install <local path>`
against this project therefore uses pip's default PEP 517 build-isolation
behavior: pip provisions an ephemeral build environment and resolves/
installs `setuptools>=68` into it before building the wheel, independently
of the target venv `pip_install` installs into. This is a nested
installation step inside an already-nested `prepare` call: `prepare` ->
`pip install` -> PEP 517 build isolation -> resolve `setuptools`.

A cached artifact and offline dependency resolution are not the same
condition. An already-cached `setuptools` wheel only satisfies the
installation step once a specific version has already been resolved; pip's
default resolution for an unpinned range such as `setuptools>=68`
ordinarily still performs an index lookup to pick a candidate version,
independently of whether a matching wheel already sits in the local wheel
cache (ordinarily under the host's unprivileged account, not necessarily
shared with or reachable from an agent's sandboxed shell). That index
lookup is what actually needs the network -- it is avoided only if pip is
told to skip it (e.g. `--no-index`/`--find-links` against a local-only
source) or if a prior, still-fresh query of the same index is itself served
from pip's separate HTTP response cache -- and is not avoided merely
because a usable wheel happens to already be cached locally. No code in
this repository pins, vendors, or stages a local `setuptools` wheel, nor
configures an index-lookup bypass, for this path.

== Earlier report and observations (historical)

This record's Discovery context is the newly added Worker/Reviewer
role-prompt guidance on offline agent execution (Part A of this same
maintenance task). That guidance exists because the first real Simple
dogfood, `RUN-e28bd75fe52f4118b3b33a0f1f944c62`, reports exactly this class
of observation: its Worker-attributed structured result records an
unsuccessful agent-local full-suite diagnostic implicating `setuptools`
availability. That report is the Worker's own agent-side observation, not
an independently reproduced root cause for this exact nested-`prepare`/
`prepared`-fixture mechanism -- no diagnostic transcript tying the failure
specifically to the PEP 517 build-isolation step above has been reproduced
-- and it is distinct from that same Run's Coordinator-owned `task-check`,
which executed separately and passed (see "Coordinator-trusted evidence"
below). This record documents the class of problem that report and the new
prompt guidance anticipate for this specific nested-`prepare` path; it does
not itself attach a fresh, reproduced failure transcript from an
intentionally offline agent shell for this exact fixture.

A probe run in the current (networked) interactive session -- `python3 -m
venv` followed by `pip install --no-input <this project's path>` -- *did
not* fail: pip reported `Installing build dependencies: ... finished with
status 'done'` and completed the install, because this session's shell has
outbound network access (confirmed separately via a direct HTTPS request to
`pypi.org`) and/or a cached index response that made the version-resolution
index lookup unnecessary. That result does not confirm or disprove this
record's hypothesis; it only establishes that reproducing the failure
requires a shell that can perform neither the index lookup nor fall back to
an already-cached equivalent of it, which this session is not.

== Earlier hypothesis (now reproduced in the sandbox case above)

That an intentionally offline agent shell (no network, no relevant local
`pip` cache entry) running `tests/unit/test_wfc_op.py`'s `prepared` fixture
(or any other nested-`prepare` test) will have `pip_install` fail at the
PEP 517 build-isolation step with a network-resolution error for
`setuptools`, surfaced through `HarnessRefusal(f"pip install {target!r}
into {env_dir} failed: ...")` (`scripts/wfc_op.py:344-345`). This has not
yet been reproduced under a genuinely offline agent shell as part of this
record; it is recorded as the mechanism most directly supported by the
verified facts above, not as an observed transcript.

== Important historical caution -- do not generalize

Earlier forensic work on a separate, unrelated Run failure already
established that a general "setuptools / network" explanation was *not* the
cause of that other incident. This record does not reopen, cite as
precedent, or rely on that prior diagnosis; it treats the nested-`prepare`
offline-installation mechanism described above as its own, independently
reasoned and independently-to-be-reproduced hypothesis. Conversely, that
prior diagnosis being inapplicable there does not mean sandbox-local
dependency installation can never fail independently elsewhere -- the two
incidents are not shown to share a cause, and must not be treated as
interchangeable.

== Earlier pre-beta classification (historical)

Coordinator-owned trusted evidence does not route through an agent's own
shell; the agent-shell network restriction alone does not establish its
network conditions. The later Coordinator timeout remains unexplained (see
the update above). The gap recorded here is about
agent-side exploratory/diagnostic test execution specifically -- a worker or
reviewer wanting to run `tests/unit/test_wfc_op.py` locally inside a
sandboxed, offline invocation -- not about any currently authorized
Simple or Robust execution path. It is recorded now, ahead of PyPI Beta
hardening, because the new offline-execution role-prompt guidance (Part A)
means agents are now expected to notice and report exactly this class of
limitation rather than silently fail or silently skip meaningful packaging
validation.

== Candidate approaches (options, not a predetermined solution)

The following are recorded as possibilities for a future, separately
authorized investigation to weigh against each other; none is selected,
scoped, or authorized by this record:

* A locally staged/vendored compatible `setuptools` wheel (and any other
  currently-PyPI-resolved build dependency) made available to `pip_install`
  via `--find-links` or an equivalent offline-first resolution path, so
  `prepare`'s nested installs never need the network for build dependencies
  already satisfiable from the repository or a prepared cache.
* A dedicated, explicitly offline-fixture variant of the `prepared` fixture
  (or a new, narrower fixture) that either pre-warms the two venvs' build
  dependencies from a controlled local source before any sandboxed test run,
  or is skipped with an explicit, actionable reason under a detected-offline
  condition rather than failing opaquely.
* Recording, and gating on, whether a compatible `setuptools` wheel is
  already present in the executing environment's `pip` cache before
  attempting the nested installs, to turn a late PEP 517 failure into an
  earlier, clearer diagnostic.

Any of these must preserve meaningful packaging validation (a real `pip
install` against this project's `pyproject.toml` and `setuptools.build_meta`
backend) rather than merely suppressing or bypassing the installation step.
