== 2. F-I2 -- independent selection axes

*RESOLVED.*

The revision does not merely add a caveat to a role-keyed schema. It states the
general model first, then derives the MVP inputs from it as an explicitly
temporary projection. That is the right order, and it is what makes the
remaining role-keyed YAML safe.

*The three axes are conceptually independent.* The Decision section now leads
with the general model (line 33):

----
phase -> workflow role
      -> persona selection
      -> execution-binding selection
----

followed by "For the immediate DMC MVP only, both selection keys default to the
workflow role ... This is a deliberately narrow projection of the general model,
not a permanent identity between role, persona, and binding, and it adds no
selector fields now." The per-Hop lookup block was rewritten to name the MVP
selectors as selectors rather than as role itself.

*Role-keyed maps are labelled MVP projection only.* Both subsection headings
were renamed to "... role-keyed for the MVP". The persona mapping is
"intentionally only the MVP projection"; the binding representation "is the MVP
default, not the general key". The former general claim -- role "may influence
only these MVP shell concerns" -- became "role supplies the default selection
key", followed by "That default is not a general derivation rule. A future
phase may select a different persona or binding while remaining `worker`;
workflow role continues to describe function rather than expertise, model
strength, or execution trust." That last clause also answers review 001's
security-compatibility point directly: model strength is explicitly denied
equivalence to trust, at the level of the role concept itself.

*Selector fields are not schema-committed.* "This record does not add or
schema-commit persona-selector or execution-binding-selector fields" (line 293);
"Until then, selector equals workflow role by definition of the MVP projection";
a new non-goal, "persona-selector or execution-binding-selector schema in the
MVP" (line 694); Slice 1's "without selector fields"; and an acceptance
criterion requiring the default to "introduce no selector fields". Four
independent statements, all restrictive. An implementer cannot read "MVP
persona selector" as an instruction to build a selector indirection.

*Future `role = worker` phases may differ.* The new subsection "Independent
selection axes and future compatibility" (line 262) enumerates the four
configurations that must remain reachable -- two personas under `worker`
(`frontend_developer`, `backend_developer`) and two bindings under `worker`
(`ordinary_worker`, `elevated_local`) -- and concludes "Thus future phases may
share `role = worker` while selecting different personas or execution
bindings." These are illustrative values inside a preservation requirement, not
a proposed vocabulary.

*No third workflow role for elevated work.* "Elevated or protected execution
does not require `frontend_worker`, `backend_worker`, `elevated_worker`, or any
third workflow role", restated as an acceptance criterion.

*Defensive review stays `independent_reviewer`.* "Mandatory defensive review
remains `role = independent_reviewer`; its gate status, scope, routes, and
Finding authority still come only from admitted phase/profile configuration."
This is consistent with the mechanism review 001 verified: `ReviewDescriptor`
fields, `authorized_scope`, `authorized_actions`, and configured `routes` are
the only authority sources, and nothing cross-checks them against a role name.
A new non-goal, "elevated-privilege execution or defensive-review
implementation" (line 702), keeps the deferred design out of this record while
its compatibility is preserved.

*Does this fully resolve the original concern?* Yes. Review 001's objection was
that an MVP coincidence was being encoded as permanent schema, so that a future
elevated phase would face a choice between a third role and a schema fight. Both
horns are now removed. The serialized input remains role-keyed, which is
correct and minimal, but the record establishes that the key is a projection,
that adding a selector is a later additive slice, and that the two-role
vocabulary survives it. The extension-seam paragraph was correspondingly
generalized: a future phase "may declare requirements and select a compatible
binding without changing its workflow role", still one-directional, still
fail-closed, still adding no fields now.

The record now says what it means, and what it means is compatible with the
deferred concept.

*The stability mechanism is named.* "Stability comes from parse-once

*No Run-level digest required.* "No Run-level binding digest is required for

*Future resume must reconstruct, verify, and fail closed.* "Any future

*No recovery implementation leaked.* Confirmed. The paragraph states an

The asymmetry review 001 asked to be named is also stated, in the ownership
section: "persona is a pinned/rechecked governing input; binding is a
parse-once immutable Run-preparation object whose durable plan projection is
evidence, not an input reread by the current process."

=== N-N1 (INFO) -- the contract loader's literal filename is not named among the provenance constants

The affected-surfaces list and the v6 subsection name `CONTRACT_VERSION`,
`RESOURCE`, and the reviewed SHA-256 (`prompt.py:18,19,20`).
`load_agent_operating_contract()` additionally hard-codes the filename as a
string literal, independent of `RESOURCE`:
`resources.files(__package__) / "resources" / "agent_operating_contract_v5.txt"`
(`prompt.py:54`). A v6 revision must update that literal too.

This fails closed if missed -- loading the v5 file against a v6
`REVIEWED_SHA256` raises `CoordinatorResourceError` at both the load and
assembly checks -- so it is an implementation note rather than a requirement on
the record. Recorded so the implementer does not discover it only from a test
failure.

=== N-N2 (INFO) -- the production transport for the binding configuration is still unnamed

Review 001's F-N7 stands unchanged and was not made worse. The record still
specifies "a strict configuration input to the operator API and one production
preparation path" without naming the concrete argument, while `main()` remains
the sole production entry point and is argparse-driven. One argument of the
existing shape, resolved and parsed once in `_preflight()`, remains the obvious
minimal transport. This is a transport detail, not a CLI design, and the
record's refusal to design a CLI is still correct.

=== N-N3 (INFO) -- one acceptance criterion constrains the record rather than the implementation

"The MVP persona and binding selectors default to workflow role and introduce no
selector fields; the record and implementation do not make that default a
permanent conceptual identity." The first clause is mechanically testable; the
second, as applied to "the record", is a property of this FTR rather than of the
implementation it accepts. Harmless, and the intent is clear. Noted only for
tidiness.
