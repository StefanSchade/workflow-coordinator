== Problem

. The README's "Run a small demo" link opens
  `docs/operator_manual/ch09_consumer_quickstart/02_first_run_example.adoc`
  on GitHub, which renders that file on its own. The page refers to its
  neighbour with in-page anchors that exist only in the assembled manual:
  eight of its references lead nowhere, among them prerequisites, install
  and limitations. The same defect occurs twice in
  `ch10_level1_orchestration/02_worked_sequence.adoc`, and once in
  `ch10_level1_orchestration/_chapter.adoc`, where the target is reachable
  only if the viewer expands includes. The documentation gate renders only
  the assembled books and does not see any of this.
. There is one example, a documentation change with a single role. It shows
  no test, no independent review, no Finding and no stop, and it states that
  `wfc run` was not executed for it.
. The three kinds of reader -- someone finding out what WFC does, someone
  attempting a first Run, and a coding agent operating WFC -- start from one
  undifferentiated list.

== Expected user-visible outcome

* Every page the README links to reads correctly when opened on GitHub at
  the release tag.
* A newcomer finds, from the README, one overview page with a map of the
  demo workspace and three tutorials of rising difficulty. Each can be
  rehearsed offline in seconds and then run live, and each says exactly
  which of its outputs come from a rehearsal, which from a real provider
  Run, and which were not executed.
* The pages never present a rehearsal as evidence of what a model does.

== Decided design direction and rationale

* *Repair the publication surface that exists.* GitHub at the release tag
  is the decided documentation surface (release contract C5). Making it
  read correctly needs a link rule and a guard, not a rendering pipeline.
* *Three tutorials, not a catalogue.* One exists; two add what it cannot
  show. A fourth, on Level-1 orchestration, waits for the Agent Skill.
* *Tutorials live in the Operator Manual, chapter 9.* The manual already
  owns operating procedures, the chapter is rendered by the documentation
  gate, and tutorial text links to the owning sections for every rule
  instead of restating it.
* *Quoted files cannot drift.* Whatever a page quotes from the kit is
  compared byte for byte with the kit by a test.
* *Two modes, never mixed.* Rehearsal output and live output appear in
  separate, labelled sections.

== Scope

. The link rule and its guard for all Operator Manual sources; the eleven
  repairs it requires today.
. `README.md`: the "Where to start" list by audience.
. Chapter 9: one overview leaf, the revised first example as Tutorial 1,
  two new tutorial leaves; the chapter file's include list and introduction.
. The quote guard.
. Pointers: the command index in
  `docs/operator_manual/ch08_examples/02_command_flow.adoc`, the entry for
  chapter 9 in `docs/README.adoc`, a `-- planned` release-notes entry.

== Non-goals

* No published HTML, Pages repository, slide deck, screenshot or recording.
* No rewrite of the quickstart's installation, prerequisite or limitation
  sections, and no change to any normative section of the manual.
* No Level-1 or Agent Skill tutorial; no change to chapter 10 beyond the
  three link repairs.
* No new command, script or package change; the kit is the companion
  record's subject.
* No claim of provider or model qualification.

== Design

[[link-rule]]
=== The link rule and its guard

Rule, to be added to `docs/ai_info/doc_conventions.adoc` under "AsciiDoc
mechanics" in two sentences: in a file that is also read on its own, the
`+<<anchor>>+` form may refer only to an anchor defined in the same file; a
reference to another file uses the existing `link:` form with the target
file and fragment, which works both standalone and in the assembly.

Repairs today, all of the same shape:

[cols="3,2,4",options="header"]
|===
|File |Dead anchors (occurrences) |Replace with a link to

|`ch09_consumer_quickstart/02_first_run_example.adoc`
|`consumer-quickstart`, `quickstart-prerequisites`, `quickstart-install`,
`quickstart-request`, `beta-limitations` (8)
|`{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#<anchor>`

|`ch10_level1_orchestration/02_worked_sequence.adoc`
|`level1-loop` (2)
|`{operator-docs}/operator_manual/ch10_level1_orchestration/01_operating_pattern.adoc#level1-loop`

|`ch10_level1_orchestration/_chapter.adoc`
|`level1-what-is-this` (1)
|`{operator-docs}/operator_manual/ch10_level1_orchestration/01_operating_pattern.adoc#level1-what-is-this`
|===

Each replacement is written with the `link:` macro and keeps or supplies a
link text (for the fourth anchor, for example, "writing a request"). This
is the form the manual already uses between chapters; the `operator-docs`
attribute is defined in every leaf's standalone header and by the assembly.

Guard, `tests/architecture/test_manual_standalone_links.py`, in the
required suite, pure Python, no Asciidoctor needed: for every `*.adoc` under
`docs/operator_manual/`, outside delimited `----` and `....` blocks, every
`+<<target>>+` or `+<<target,text>>+` must name an anchor defined in the
same file as `+[[target]]+` or `+[#target]+`. The failure message lists
file, line and target. The assembled manual
(`docs/operator_manual/operator_manual.adoc`) is exempt as the one file
never read standalone. Shell here-documents (`+<<'EOF'+`) occur only inside
code blocks and are skipped with them.

=== `00_overview.adoc`

Anchor `consumer-overview`. At most one screen before the first command.
Content, in order:

. Two sentences on what a Run is, linking to the orientation chapter.
. The two commands that create the demo workspace and rehearse Tutorial 2.
. The workspace map, as a literal block, and the table below it:
+
[source,text]
----
~/wfc-demo/                       the demo workspace; not a Git repository
├── greeter/                      (1) the repository being modified
│   ├── checks/check.sh           (4) the one trusted check
│   ├── docs/reviews/             (4) review artefacts, written by the reviewer
│   └── .wfc/
│       ├── config.yaml           (3) scope ceiling, Hop ceiling, Evidence location
│       └── governance/
│           ├── repository-policy.md
│           └── <commission-id>/  (2) the Commission, committed by `wfc run`
├── greeter-run-<name>/           one worktree of greeter per Run; (5) its Git log
├── greeter-evidence/             (6) the Evidence repository
├── requests/                     (2) task documents and Consumer Requests
└── rehearsal-home/               (6) lifecycle state of rehearsals
----
+
[cols="1,3,5",options="header"]
|===
|No. |What |Rule to remember

|1 |The repository being modified |One fresh worktree per Run; a checkout
holds one lifecycle.
|2 |Commission and authorized scope |Written outside the repository,
previewed by `wfc plan`, committed only by `wfc run` after authorization.
|3 |Execution configuration and provider bindings |Adapter, model and
reasoning are chosen per Run and are not part of the Commission.
|4 |Checks and review artefacts |The check runs before launch and after
each Hop; review artefacts are scope paths like any other.
|5 |Trusted commits |Made by the Coordinator from the declared paths, never
by the provider.
|6 |Run state and archived Evidence |Outside the repository; the archive is
its own Git repository; nothing is ever pushed.
|===
+
Each row links to the owning manual section.
. *Rehearsal and live Run*, a short section stating the difference once: a
  rehearsal calls no model, costs nothing and always ends the same way; it
  demonstrates WFC's control flow, authority boundaries and evidence, and
  nothing about model quality. A live Run needs an installed, authenticated
  provider CLI, costs usage and may end differently. The archived record of
  a rehearsal names the model `rehearsal-no-model`.
. The tutorial table: name, what it adds, program, rehearsal scenario.

[[page-contract]]
=== The tutorial page contract

Each tutorial has these sections, in this order and with these headings:

. *Goal* -- one paragraph, and what this tutorial adds to the previous one.
. *The task* -- the task document and the Consumer Request, quoted from the
  kit (<<quote-guard>>), with two or three remarks on the fields that
  matter here.
. *Rehearse it* -- the `rehearse.py` command and its real, abridged output.
. *What to look at* -- three to five inspection commands with the expected
  result and one sentence each on what it proves.
. *Run it live* -- the commands for a fresh worktree with the reader's own
  provider (pattern below), and *what may differ* from the rehearsal.
. *What was verified* -- which commands were executed for this page, with
  which WFC version, and which were not. Rehearsal output is real output.
  A live transcript appears only if a live Run was actually performed and
  recorded (<<decisions>>, D2); otherwise the section says so.
. *Next* -- one link forward, and links into the manual for the mechanics.

Live pattern, identical in all three apart from names:

[source,shell]
----
cd ~/wfc-demo
git -C greeter worktree add ../greeter-live-t1 -b live/t1 main
cd greeter-live-t1
wfc plan ../requests/t1-hello-page.task.md --repository . ...   # read-only preview
wfc run --repository . --request ../requests/t1-hello-page.request.yaml \
  --executable claude \
  --execution-override worker.adapter=claude_cli \
  --execution-override worker.model=<your model> \
  --execution-override worker.reasoning=medium
----

The page shows the complete `wfc plan` command with the request's fields.
The live `wfc run` is shown *without* `--yes`, so the reader answers the
authorization prompt; the Codex variant (`--executable codex`,
`codex_cli`) is given once, in Tutorial 1. For `robust@v1` the three
overrides are repeated for `independent_reviewer`.

=== Tutorial 1 -- a documentation change (`02_first_run_example.adoc`)

The existing page, kept as the place where each step is explained, with
these changes: a short note at the top that the kit builds this layout
with one command; the repository it describes becomes the kit's
`greeter` (same idea, now with the small program and test, so the page
describes exactly what `make_workspace.py` creates); the task and request
are `t1-hello-page`; a rehearsal section with real output; the link
repairs. Its explanatory sections "Plan, authorization, run, and archived
evidence" and "Why the check must pass before and after" stay, with their
anchors.

=== Tutorial 2 -- a program change with a test and an independent review

Anchor `tutorial-program-change`; scenario and request `t2-farewell`. It
adds four things and says so:

. *A realistic check.* The check runs the unit tests. It must pass before
  the task (the new test does not exist yet, the old ones pass) and after.
  A boxed warning records the observed trap: a check that leaves any new
  file which Git does not ignore -- Python bytecode is the usual one --
  makes the baseline probe refuse the Run before any provider starts, and
  the refusal consumes the checkout's lifecycle. The demo repository
  ignores `+__pycache__/+` for that reason.
. *A scope of several paths*, and why `robust@v1` puts the two review
  artefacts into the scope.
. *Two roles.* Worker and independent reviewer, bound separately.
. *The review loop.* The rehearsal shows a blocking Finding opened by the
  broad review, the correction, the focused review that resolves it and the
  renewed broad review that accepts.

"What to look at" includes: the six commits and their subjects; that the
reviewer's Hops changed only review artefacts; `wfc report` showing "5 of 6
hops" and no open Finding; the Finding's two Hops in `audit.json`.

"What may differ" states plainly that a live reviewer may accept at once
(two Hops, as both recorded consumer smokes did), raise a different
Finding, or stop, and that none of these is a malfunction.

=== Tutorial 3 -- stops and the human decision

Anchor `tutorial-stops`. Two rehearsals, both without any model:

. *A refusal before launch* (`t3-probe-refusal`): the check cannot run;
  `wfc run` prints that the baseline probe failed and that no provider
  ran, and exits 23. Nothing was committed or archived. Lesson: a refusal
  is cheap, but the checkout's lifecycle is spent; the retry happens in a
  new worktree after fixing the cause.
. *A stop that waits for a human* (`t3-scope-stop`): the task demands a
  change outside its scope; the Worker stops; the Run ends
  `CLASSIFICATION: awaiting_human` with exit code 10. Lesson: read the
  classification, not the exit code; the report names the stop reason and
  the next choice; the Commission commit exists and no payload commit does.

Then one section, *What the human decides*, without inventing procedure:
for this case the correct decision is a new Commission whose scope includes
`docs/notes.adoc`, in a fresh worktree; the page gives that one command
sequence and links to
link:../operator_manual/ch06_recovery/01_outcomes.adoc[recovery outcomes]
for stops that leave work behind and to
link:../operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal
states] for every classification.

"Run it live" for the scope stop says that a real Worker is expected to
stop but may instead complete the in-scope part; either way the scope
enforcement holds, and the page shows how to check that nothing outside the
scope changed.

[[quote-guard]]
=== Quote guard

A page quotes a kit file only in a listing block immediately preceded by a
comment line of the form `// kit: <path relative to examples/consumer-demo>`.
`tests/architecture/test_tutorial_kit_quotes.py` finds each such block under
`docs/operator_manual/ch09_consumer_quickstart/` and asserts that its
content equals the named file byte for byte, apart from one trailing
newline. A missing file fails. At least the three task documents and the
three request templates are quoted this way.

== Security and authority invariants

[horizontal]
SI-1:: No page instructs the reader to pass `--yes` to a live `wfc run`.
`--yes` appears only inside `rehearse.py`.
SI-2:: No page presents rehearsal output as a provider result; every
rehearsal transcript sits under a heading containing "Rehearse".
SI-3:: No page states or implies that a model, an adapter or a subscription
is qualified, sufficient or free. Cost statements link to the existing
cost section of chapter 10.
SI-4:: No page tells the reader to push, tag, edit `.wfc/` state, edit the
Evidence repository, commit inside a Run's worktree, or resolve a stop by
editing files in place.
SI-5:: Tutorials state no rule of their own: every "must" is followed by a
link to the manual section that owns it.
SI-6:: Every live command operates inside the demo workspace.

== Acceptance criteria

[horizontal]
AC-1:: The link guard passes over all Operator Manual sources and fails,
in a test of the guard itself, on a file with a cross-file `+<<anchor>>+`.
AC-2:: Rendered standalone with `asciidoctor --safe-mode=safe`, each leaf
of chapters 9 and 10 has no in-page link to an id that the rendered page
does not contain.
AC-3:: The documentation gate command of the release workflow exits 0 with
no output.
AC-4:: `python3 scripts/wfc_release_check.py` reports no
repository-relative README link.
AC-5:: The quote guard passes and covers at least six blocks.
AC-6:: Every `rehearse.py` transcript in the pages is reproduced by running
the same command against the working tree: classification, exit code, Hop
count and commit subjects match.
AC-7:: Each tutorial has the seven sections of <<page-contract>>; its
"What was verified" section names the WFC version and distinguishes
executed from not executed.
AC-8:: SI-1 to SI-6 hold; SI-1 and SI-2 are checked by a test over the
chapter's sources (`--yes` occurs in no shell block of the chapter;
every block that contains `REHEARSAL` lies in a section whose heading
contains "Rehearse").
AC-9:: Every anchor that existed in `01_quickstart.adoc` and
`02_first_run_example.adoc` before the change still exists.

== Practical tests

Automated, required suite: the link guard and its self-test (AC-1), the
quote guard (AC-5), the wording checks (AC-8), the anchor inventory (AC-9,
a fixed list in the test).

Run by the implementer and recorded in the work result: AC-2 (a
twenty-line script over the rendered HTML), AC-3, AC-4, AC-6.

live, once per adapter, in a fresh demo workspace, with the installed
release candidate; classification, Hop count and the Evidence commit are
recorded in the page's "What was verified" section. A truthful stop is a
valid result and is recorded as one.
