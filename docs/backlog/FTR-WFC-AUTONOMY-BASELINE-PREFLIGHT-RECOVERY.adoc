= FTR-WFC-AUTONOMY-BASELINE-PREFLIGHT-RECOVERY -- Baseline preflight and deterministic recovery

Status:: Open; the rules question is settled by `WI-WFC-LEVEL1-AUTONOMY-002`
(<<settled>>); the technical items below remain open and unimplemented.

== Observation

During the phase-specific execution bindings Commission, the Level-1 operator
launched an authorized Run without the `WFC_TEST_INPUTS` and `WFC_TEST_PROFILE`
environment variables required by the repository's offline test contract. The
baseline probe failed before any provider Hop; `wfc status` reported
`not_launched`. The installed WFC skill required a human decision before
resolving the stop even though the required test inputs and their verification
procedure were determinable from the repository contract. The maintainer then
authorized verification of the offline inputs and resumption of the existing
Run without changing its request, bindings, or baseline requirement.
A second probe with verified inputs exited 1 and left a test-generated
`.claude/skills/wfc/` in the checkout; the runtime reported the exit code
but did not retain the captured test output in its diagnostic. A scratch
directory outside the checkout and the same verified inputs allowed the
unchanged full baseline to pass. The exact failing assertion of the second
probe is unconfirmed.

== Investigation

* How can a Level-1 operator identify and prepare required test inputs before
  starting a Run, while respecting the repository's verification contract?
* Can explicitly defined, safe preflight corrections be made autonomously, and
  under what precise preconditions?
* Should a failed baseline surface or preserve its captured diagnostic output,
  and should status distinguish a failed probe from an unattempted launch?
* How should deterministic preflight correction be distinguished from genuine
  reconciliation, changed authority, or decisions requiring a human?
* What evidence must record the initial failure, verified inputs, unchanged
  authorization, corrective action, and resulting baseline outcome?

Any future proposal must preserve Human Authorization and the trusted baseline;
this item grants no authority to weaken either. It does not commission an
implementation or change the current phase-bindings feature scope.

[[settled]]
== Settled by WI-WFC-LEVEL1-AUTONOMY-002 (2026-11-24)

The rules question this item raised -- "can explicitly defined, safe
preflight corrections be made autonomously, and under what precise
preconditions?" -- is answered at the documentation layer: preparing,
verifying and correcting the declared evidence/baseline command's own
environment (offline inputs, `TMPDIR` placement) is ordinary preparation
within an already-delegated mandate, and a probe that fails for a
correctable reason may be corrected and retried in a fresh checkout,
without a separate human decision each time. This is now stated as a
binding rule, not merely implied, in
link:../operator_manual/ch10_level1_orchestration/01_operating_pattern.adoc[Operator
Manual chapter 10] (prerequisites, the standing-instructions template and
the stop-classification table), the packaged skill's
`src/workflow_coordinator/agent_skill/wfc/SKILL.md` `Authorization`/`The
loop` sections and its `references/stops-and-evidence.md` and
`references/commission.md`, and `FTR-WFC-AGENT-SKILL-DISTRIBUTION.adoc`'s
AU-5. No WFC execution semantics changed: the baseline probe, `refused_probe`
and the one-lifecycle-per-checkout rule are exactly as before; what changed
is which decisions the Level-1 operator may make on its own before asking.
The first attempt at this rule change, `WI-WFC-LEVEL1-AUTONOMY-001`, was
stopped by its Hop timeout and established nothing authoritative; its
preserved, non-authoritative candidate was reviewed, corrected and carried
to completion by this WorkItem, which is the one that actually settles the
question recorded here.

What remains open, not settled here, and not implemented: no change to WFC
source, the reducer, admission or the CLI's observable behavior; and in
particular the technical items this record's `Investigation` section raised
and did not resolve:

* a refused baseline probe's persistent diagnostic log or captured output is
  not retained today -- an operator repeating a corrected probe still cannot
  inspect the first probe's own failure output after the fact;
* `wfc status`/`wfc run` do not distinguish a failed probe from a launch
  that was never attempted (both can currently read as `not_launched` or a
  bare `refused_probe` without the prior attempt's own detail);
* no executable self-development preflight check exists that verifies the
  offline test-input bundle and `TMPDIR` placement *before* `wfc run` is
  invoked, beyond the existing manual Developer Guide procedure;
* a test run can leave a test-generated `.claude/skills/wfc/` directory in
  the checkout that Git does not ignore; this is an observed cleanliness gap
  in the test/skill-installation tooling, not a rule question, and is
  recorded here for a future implementation Commission to pick up.

None of the above is authorized or implemented by this record or by
`WI-WFC-LEVEL1-AUTONOMY-002`; each remains a candidate for a separately
commissioned implementation package.
