Type:: future technical record -- Front Door lifecycle capability gap
Status:: proposed / backlog; not part of Beta-1 BP7 or BP9
Current controlling source:: This record; see link:_open.adoc[the active-work manifest] for its current card.
Next action:: Decide the lifecycle model in the workflow-genericity ADR before any implementation; a Commission only after that decision.

== ADR decision for this record (2026-11-21)

link:../technical_model/ch04_target_and_alternatives/03_adr_closed_versioned_workflow_programs.adoc#adr-ad5[AD-5
of the ADR on closed, versioned workflow programs] answers the lifecycle question
this record requires to be decided first: *one Run per canonical checkout stays
for now and is stated as the Beta contract*, with the strong, simple invariant --
one checkout hosts one Run, so archive lookup stays unambiguous -- recorded as its
benefit. Controlled rotation is deferred to a later lifecycle revision, and the
five design constraints below are its entry conditions.

The ADR also records how the operational friction is preferably reduced: by
automated worktree or branch creation and controlled cleanup at the Front Door,
not by loosening the kernel invariant. The decision authorizes no Commission, and
this record's `Status::` line is the maintainer's and is unchanged here.

== Pointer: the automation half of AD-5's remedy now has its own record (2026-11-26)

AD-5's named preferred remedy -- automated worktree creation and controlled
cleanup at the Front Door -- is now recorded separately as
link:FTR-WFC-RUN-CHECKOUT-PREPARATION.adoc[FTR-WFC-RUN-CHECKOUT-PREPARATION],

== Observation

`wfc run` is effectively once per canonical checkout, forever. In
`frontdoor/lifecycle.py` (`_advance`) any `authorized` record in the checkout's
journal makes every later `wfc run` fail with `refused_active_lifecycle`
(exit 26), also long after a `classified` terminal record and a verified
archive. The classification name says "active" but the check is "present". This
is not the concurrency guard: concurrent engines on one checkout are prevented
by the separate ownership lock.

The rule was recorded as finding P12 of the BP4a independent review
(link:../warm_storage/beta1-productization/wfc_beta1_bp4a_lifecycle_controller_001_broad_review.adoc[BP4a broad review]):
consistent with that task and fail-closed, but undocumented, with no documented
path to start another Run on the same checkout. The BP6c review relies on it
(link:../warm_storage/beta1-productization/wfc_beta1_bp6c_lifecycle_archive_wiring_002_broad_review.adoc[BP6c broad review]):
the unscoped per-checkout archive lookup cannot mask a second Run only because
one checkout hosts one Run.

Recurrence: BP7 Proof Run 2 could not start in the checkout that had hosted
Proof Run 1 and was run in a fresh sibling worktree.

== Target picture (maintainer, 2026-11-20)

One checkout per active Run, any number of sequential Hops inside it, and
controlled reuse after completion. Hops inside one Run already work; reuse
after completion does not.

== Design constraints for any later solution

* Rotation only from a terminal, archived and Evidence-verified lifecycle on a
  clean checkout at the expected head.
* The previous journal is set aside, not deleted.
* `uncertain_launch` and unresolved `launch_intent` are never rotated away.
* Archive lookup must stay unambiguous per Run once a checkout can host more
  than one Run (the BP6c reliance above).
* The ownership lock stays; this record is not about concurrency.

== Interim guidance

Until decided: one fresh checkout (clone or worktree, same relative Evidence
location) per Run. State this in the operator documentation at cutover.
