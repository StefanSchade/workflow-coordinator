== Problem

A Level-1 operator session gets its operating knowledge from the shipped
Agent Skill (`src/workflow_coordinator/agent_skill/wfc/`) and the Operator
Manual. Across one long session, eighteen recorded friction entries traced
back to something those texts do not say, say in a superseded form, or say
wrongly. Two examples establish the shape:

* *A capability that exists and is invisible.* `wfc resume` covered only the
  mechanical durable-artifact anomaly class (`reducer.py:487-500`,
  `frontdoor/lifecycle.py:871-875`, as of the session this records; O10B
  added a second class on 2026-11-27, see the note below) and therefore
  correctly refused an operational `awaiting_human` stop. The productized answer channel for such
  a stop is `prepare-successor --authority-decision`
  (`operator.py:324-342`), eligible because an escalation of any kind --
  `operational` included -- freezes the semantic stop its gate requires
  (`reducer.py:1753-1759`, gate at `operator.py:1688`). The skill describes
  neither `prepare-successor` nor `export-salvage`, lists "Run a `wfc`
  subcommand this skill does not describe" under *Never* (`SKILL.md:131`) and
  warns that an unrecognized bare subcommand falls through to a legacy entry
  point (`SKILL.md:136-137`); the manual shows the command only as
  `python -m workflow_coordinator.operator prepare-successor`
  (`ch06_recovery/02_successors.adoc:130-131`). The operator could not reach
  a channel it was told not to look for.
* *A statement that is wrong.*
  `ch03_running/01_preparation.adoc:315-317` groups `--request` with
  `--guidance-path` and `--scope` as "repository-relative to
  `--repository`". `wfc run` reads `--request` as a plain filesystem path
  (`frontdoor/lifecycle.py:287`), and the skill already states this correctly
  (`references/commission.md:45`). Three arguments with three distinct path
  contracts -- `--scope`/`--guidance-path` repository-relative,
  `--config` repository-relative *and* committed (enforced at
  `frontdoor/verify.py:71`), `--request` a free filesystem path -- are
  documented as one. That conflation is the shape of friction entry 2, where
  a Consumer Config placed outside the repository was accepted by `wfc plan`
  and refused only after authorization, consuming the checkout.

== Direction

One Commission that writes the missing and corrected statements into the
Agent Skill references and Operator Manual chapters 2, 3, 6, 9 and 10. The
plan's link:beta2_operator_efficiency_plan.adoc#o1[O1 acceptance section]
enumerates every item with the friction entry it answers and the `path:line`
that makes it true; the load-bearing ones are the evidence-command rule (the
command must run the repository's own gates, with friction entry 18 as the
worked example of what a deterministic gate must prevent), the 900-second
evidence cap and its coupling to the prepared environment, the
`prepare-successor` channel above, the per-checkout environment recipe with
the shared-editable-install hazard, and the correction quoted above.

This record is also the *specification* for five later Front Door slices.
Five of its statements describe a workaround that those slices remove, so
they are written as *planned* beside the slice that retires each; see
link:beta2_operator_efficiency_plan.adoc#ownership[the ownership table].

== Open decisions

None of its own. Its content depends on no undecided question; the five
*planned* statements depend on the decisions of the slices that retire them
(link:beta2_operator_efficiency_plan.adoc#decisions[D1, D2, D4 and D7a]), and
the text stands unchanged whichever way those go -- it describes today's
behaviour either way.

One judgement, recorded rather than decided: the shipped texts reach a
consumer only through a Runtime promotion and `wfc skill install`, which are
maintainer actions. An accepted candidate therefore improves the repository's
texts immediately and the installed operator experience only on promotion.

== Design (2026-11-27, slice SK -- consolidating the shipped skill)

Slice SK (`WI-WFC-BETA2-SK-001`,
link:beta2_operator_efficiency_plan.adoc#sk[the plan's slice SK]) restructures
the four shipped skill files this record filled. It is a design slice, so the
design is stated here before the code; the full item-by-item inventory,
measurement and old-to-new authority mapping is
link:../warm_storage/post-beta-planning/wfc_skill_consolidation_inventory.adoc[the
skill consolidation inventory]. The problem is not the word count: the four
files mix general operator rules, Runtime contracts, WFC-self-development
experience and historical workarounds that slices O1-O10 have since
automated.

=== SK-1: the shipped file set stays exactly four files

*Decided:* `SKILL.md` plus `references/setup.md`,
`references/commission.md`, `references/stops-and-evidence.md`. Content is
redistributed inside that set; nothing is added to it.

*Rejected:* a fifth packaged reference (`references/operator-notes.md` or
`references/troubleshooting.md`). The packaged set is pinned in three places
outside this slice's scope -- the C2 wheel/sdist allow-list in
`scripts/wfc_dist_audit.py` (`WHEEL_SKILL_FILES`), the enumerated
version-bearing surface in `scripts/wfc_release_prepare.py` (`surface()`), and
`tests/architecture/test_offline_distribution.py`, which asserts that exactly
those four names appear under `agent_skill/` in a built wheel. A fifth file
would ship unaudited or refuse the audit, and correcting that needs a change
to `scripts/`, which this Commission does not have. *Property preserved:* the
distribution allow-list stays the single enumeration of what the package ships.
*Recorded as a separate candidate*, not done here: if a later slice wants a
fifth reference, the allow-list, the release surface and the release-management
chapter move with it in the same slice.

=== SK-2: consumer operator notes are a file convention, not a mechanism

*Decided:* one documented repository-relative path, `docs/operator-notes.md`.
A consumer repository may commit it; the skill tells the Level-1 operator to
read it *when it exists*, from the *committed* starting state of the checkout
the Run begins from (`git show BASE_REF:docs/operator-notes.md`), after a
cheap existence check that is never a mandatory step. It carries Level-1
operating notes only, is not the Commission's `guidance.path` (which is the
Worker's committed policy document, read by the Runtime at a pinned commit),
and confers no authority whatever: it cannot grant a delegation, widen a
scope, approve a launch or modify a rule of the skill. WFC's own
`docs/operator-notes.md` is the convention's first user.

*Rejected:* (a) a runtime realisation -- a config key, a CLI subcommand or a
projection into the Commission. It is withheld here, and it would add a trust
surface for something that needs none: the operator reads the file itself, as
it reads any document. (b) A directory (`docs/operator-notes/`): it needs an
index file and a traversal rule, and buys nothing for a single page. (c) A
repository-name check in the skill ("is this WFC?"), excluded by the order and
wrong in principle -- the repository declares its own notes by committing the
file. (d) `.wfc/operator-notes.md`: outside the committed scope ceiling, so a
normal Commission could not write it.

*Markdown, not AsciiDoc,* deviating from
link:../ai_info/doc_conventions.adoc[the documentation conventions'] "use
AsciiDoc for new documentation": this file's reader is an agent already
reading the Markdown skill, and the convention must hold for consumer
repositories with no AsciiDoc toolchain. The deviation is deliberate, bounded
to this one convention, and recorded here.

*Properties preserved:* reading from committed history, not the working tree
or a Run candidate, fixes *which* notes a Run is operated by -- the same rule
the Runtime already applies to `guidance.path` and to the `prepare-checkout`
hook. And because the notes confer no authority, a consumer that commits them
cannot widen what the skill's Authorization section withholds.

NOTE: this paragraph originally claimed that the read anchor "keeps a Run's
own output from becoming operator instructions in the next Run". That is
over-strong and was corrected by slice SKC2 (<<design-skc2>>); the guarantee
that actually holds is narrower.

=== SK-3: Level 0 and Level 1, and the multi-Run correction

*Decided:* `SKILL.md` states both levels once, in `What this is`: Level 0 (the
Runtime) executes exactly one Commission per Run and takes no portfolio
decision; Level 1 interprets the human's order, chooses the tasks and
Commission shapes, authors and monitors Runs, and may run several Runs one
after another under one delegation. `When WFC fits, and when it does not`
loses the claim that "chaining several Commissions automatically" does not fit
WFC: that is a true Level-0 fact stated as a false Level-1 limit. Parallel
execution stays what it already is in the manual and the archive code --
sequential by default, parallel only where the human's delegation covers it,
never two lifecycles in one checkout, and never two archive steps at once
(`frontdoor/archive.py` refuses the second rather than corrupting anything).

*No authority boundary moves:* every item of the Authorization section's
`Never delegated by a launch` list, and the always-ask list beneath it, is

=== SKC2-1: one placeholder convention -- an UPPER_CASE word

*The defect, precisely.* A placeholder in angle brackets inside a block a
reader is meant to paste is *valid* shell: `bash -n` exits `0` for every one
of the blocks concerned, verified here. What the shell does with
`git show <base-ref>:docs/operator-notes.md` is read `<base-ref` as an input
redirection and `>:docs/operator-notes.md` as an output redirection, so a
literal execution fails with "No such file" or creates a stray file. The
defect is therefore executability, not syntax, and the two have to be
distinguished in both the convention and the test.

*Decided:* inside any block or inline command presented as runnable, a value
the reader supplies is an `UPPER_CASE` word, quoted only where the real value
contains spaces. `SKILL.md` (*Where exact facts come from*) states it once,
for the whole skill, in one sentence that names the stronger property: a
runnable block must *run as written* once each placeholder is replaced, which
is more than being valid shell. A block that cannot meet that is fenced as
`text` and introduced as a fragment.

*Why this form, over the alternatives:*

* *It is already the installed CLI's own convention.* `wfc request --help`
  prints `--output PATH`, `--evidence-argv TOKEN`, `--evidence-command NAME`,
  `--durable-artifact PHASE=PATH`, `--execution-override ROLE.FIELD=VALUE`.
  The skill already used that form in prose for argument names, so the choice
  unifies two conventions rather than introducing a third.
* *It is shell-inert:* no redirection, no glob, no brace expansion, and no
  parameter expansion (a bare upper-case word is just a word). Pasted
  literally it fails cleanly and informatively -- `git show BASE_REF:...`
  reports an unknown revision -- instead of writing a file.
* *It costs no lines.* The shipped files sit at their line caps (`setup.md`
  199 of 200 before this slice), so a convention that adds a line per
  placeholder was not affordable.
* *Rejected -- a shell variable introduced by a preceding line*
  (`base_ref=HEAD` then `git show "$base_ref:..."`). Strictly the most
  executable form, and kept where a block already had such a variable
  (`ch08_examples` now uses its own `$COMMISSION` in `--scope`). Rejected as
  the general convention: it adds a line per placeholder, and a `wfc plan`
  example with eight placeholders would double in length.
* *Rejected -- quoting the angle brackets* (`"<your model>"`). It removes the
  redirection but keeps two notations in one text, and reads as a literal
  value rather than a placeholder.

*Scope of the correction, and the line that was drawn.* Every block presented
as runnable was corrected: the shipped skill's Markdown `shell` fences, the
Operator Manual's `[source,shell]` blocks, and `docs/operator-notes.md`.
Inside the shipped skill the convention was additionally applied to its
non-shell fences and to inline command and argument placeholders, so the
artifact an agent copies from states and follows one convention throughout.
*Left unchanged, deliberately:* angle-bracket placeholders in the Operator
Manual's prose, tables, directory trees, output transcripts and `yaml`/`json`
blocks. They are not pasted into a shell, carry no redirection hazard, and
`<...>` is the ordinary typographic notation for a path or ref shape in
prose; rewriting the manual's prose notation would be a large change with no
executability benefit. The manual's rule is therefore statable: an
`UPPER_CASE` word inside a runnable block, `<...>` in prose.

*Two findings the correction turned up, beyond the four locations forwarded:*

. `ch04_evidence/02_archive.adoc` and `ch06_recovery/01_outcomes.adoc`
  presented *usage synopses* as `[source,shell]`: `[--dry-run]`,
  `[--raw-retention {local,commit,discard}]` and a bare `[--preview]` line
  are glob and brace-expansion syntax, not arguments. The archive synopsis is
  now a `text` block labelled as a synopsis; the `[--preview]` line is gone
  and the prose already carried the fact.
. Three `ch09_consumer_quickstart` tutorial blocks were not merely
  non-executable but *syntactically invalid*: the apostrophe in
  `--guidance-commit <the kit's guidance commit>` opens a single quote that
  never closes, and `bash -n` fails on all three. This is the one part of the
  defect class a token-level check cannot see, and the reason the weaker
  `bash -n` line was kept rather than dropped.

*Safety properties preserved:* none is touched. No Runtime, CLI, schema or
authority-model change; no new runtime function, configuration option or
approval level. The independent reviewer's sole Finding authority, the
trusted-commit boundary, fail-closed admission and one Run per checkout are
untouched; this slice is documentation and tests.

=== SKC2-2: what the notes read anchor does and does not guarantee

*The claim that was wrong.* Several places stated, in substance, that *a Run
cannot write the notes the next Run is operated by*. It does not hold.
`docs/operator-notes.md` sits under `docs`, which is inside the committed
scope ceiling, so a Commission may scope the file; this very slice's
authorized scope includes it. Run A's Worker may change it, the trusted
commit records the change, and once it is reviewed and integrated it is part
of the committed base Run B starts from, where Level 1 reads it for Run B.

*The guarantee that holds, and is now stated instead:* the notes are read
from a *specific committed base state* -- `git show BASE_REF:...`, never a
working tree and never a Run's candidate. That is a *reproducibility and
integrity* property of the bytes read: the same base ref always yields the
same notes, and neither an uncommitted working-tree edit nor a Run still in
flight can influence the notes selected for a given Run.

*Reproducibility is not trustworthiness,* and the corrected text says so
explicitly rather than letting the reader infer it: a committed file is not
thereby human-authored, and not thereby individually checked by the
maintainer. Committing fixes *which* bytes are read, not *whether they are
any good*.

*Unchanged:* the notes confer no authority, are subordinate to the skill's
general operator rules, are not the Commission's `guidance.path`, and a note
the installed CLI contradicts is merely stale.

*Added as an operating recommendation only, never as a mechanism:* a change
to the notes inside a Run's scope should go through that Run's ordinary
independent review, and a maintainer who does not want a Worker to edit the
notes keeps the file out of Worker scopes. No runtime function, configuration
option or approval level was introduced, and none is needed for either.
