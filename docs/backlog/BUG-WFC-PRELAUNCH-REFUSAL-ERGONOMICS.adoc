== Design (2026-11-26, WI-WFC-BETA2-O3O2-001)

*(a) Config path shape, moved earlier.* The A1-normalized, repository-
relative shape check (`commissioning._path`, the same one `verify_commission`
already applies when re-reading `--config` from Git history) now also runs
where `--config` is first read as a plain filesystem argument: in `wfc
plan`'s `main()`, before the file is opened at all; in `wfc run`'s
`_authorize()`, as its very first statement -- before either config/request
read, before `inputs.confirm()` is called, before the checkout lock, and
before any journal record. A shape failure there raises the same
`CommissionError` message ("... must be an A1-normalized repository-relative
path"); for `wfc run` this reaches `cmd_run`'s existing generic exception
handler unchanged, which reports classification `refused_prelaunch` for a
`CommissionError` with no `.classification` of its own -- no new
classification is introduced. *Not refused*: anything that already passes
this shape check -- the check only moves earlier, so nothing admissible
today becomes inadmissible. The post-commit re-check in
`verify_commission` is left exactly as it is (defense in depth against a
config path whose *content*, not shape, differs from what was authorized);
the only behaviour removed is a shape-only mismatch surfacing as a late,
misleading `inconsistent`.

*(b) An unambiguous cross-adapter `--executable` mismatch, refused before
dispatch.* `_do_prelaunch` already resolves `--executable` to a concrete
path. After that resolution, and only when the raw CLI value was a *bare*
name (no path separator, not absolute -- an explicit path is never touched
by this check), its basename is compared against the two adapters' own known
binary names (`codex` for `codex_cli`, `claude` for `claude_cli`, both
already literal defaults elsewhere in this module and the adapters
themselves). The envelope's single adapter is already pinned and available
from the cached `envelope.yaml` at this point (`resolve_execution` already
refuses a mixed-adapter envelope, so there is exactly one to read). A
refusal fires only when the resolved basename equals the *other* adapter's
known binary -- an unambiguous, exact name collision -- with classification
`refused_prelaunch`, before any provider dispatch. *Not refused*: an
explicit path, regardless of basename (a legitimate wrapper may be named
anything and live anywhere); a bare name that is neither known binary (an
unrecognized wrapper name on `PATH`). This is a genuinely new refusal,
scoped as narrowly as the record's own mitigation: no unambiguous-mismatch
false positive is possible because the only two names it ever compares
against are the product's own two adapters' own default binary names.

*(c) The probe refusal carries a bounded, labelled-untrusted tail.*
`_do_probe` already captures stdout/stderr (`subprocess.run(...,
capture_output=True)`). On a non-zero exit, the refusal message now appends
the last `evidence.UNTRUSTED_DIAGNOSTIC_CAPTURE_LIMIT_BYTES` (16384) bytes of
each stream, decoded leniently and explicitly labelled "untrusted" in the
printed text -- the same limit the in-Hop evidence path already uses
(`evidence.py:25`), reused rather than re-chosen. Nothing is written to disk
or to any journal/evidence record; the bytes already exist only in this
process's memory for the duration of raising the one exception, exactly as
today's exit-code-only message does. *Unchanged*: the probe's own semantics
(still exit-code-based, still strictly before any provider runs), the
`refused_probe` classification and exit code, and the trusted/untrusted
split -- no probe byte is ever persisted as, or presented as, evidence.

== Problem

`wfc run` authorizes at most one lifecycle per canonical checkout
(`frontdoor/journal.py:75-89`), so any refusal raised at or after
authorization costs the operator a whole new checkout. Three refusals in the
first three steps are avoidably expensive.

=== (a) The Consumer Config path contract is checked only after authorization

`wfc plan` accepts an absolute `--config` and reads it straight from the
filesystem (`frontdoor/plan.py:271-272`). The actual contract -- an
A1-normalized, repository-relative, *committed* path -- is enforced where the
config is re-read from the Git tree (`frontdoor/verify.py:71`, raising
`commissioning.py:107-108`), which happens at step 5, after the lifecycle is
authorized and the Commission is committed. The operator sees
`post-commit verification failed: Consumer Config must be an A1-normalized
repository-relative path` with classification `inconsistent`
(`frontdoor/lifecycle.py:586-592`) -- a classification whose documented
disposition is a maintainer judgement, not "correct the input and retry".
Friction entry 2.

=== (b) `--executable` is never compared with the adapter it must match

`--executable` defaults to `codex` unconditionally (`frontdoor/lifecycle.py:79`,
`:1206`) and is validated only for PATH resolvability (`:342-348`) and then
for being an executable regular file (`:354-359`). The expected provider is
already known at exactly that point: the resolved envelope is required to use
a single adapter, precisely because the executable is one scalar
(`frontdoor/config.py:294-295`). Nothing compares the two. A `claude_cli`
binding launched without `--executable` resolved `codex`, the first Hop
exited 2, the Run ended `reconcile_required` and the checkout was spent, with
no candidate and no damage. Friction entry 14.

=== (c) The baseline-probe refusal discards the output it captured

`_do_probe` runs the evidence command with `capture_output=True`
(`frontdoor/lifecycle.py:417-419`) and, on a non-zero exit, prints the exit
code alone (`:426-430`). The captured stdout and stderr are dropped. Two
comparisons inside the product show how far behind this is: the *mutation*
branch of the same function names the changed paths (`:431-436`), and the
in-Hop evidence path retains a bounded, explicitly untrusted stdout/stderr
tail (`evidence.py:243-260`, `:305`). The operator had to reproduce the
command by hand with the Coordinator's environment -- about six minutes -- to
learn which test failed. Friction entry 21.

This is *not* covered by the existing diagnostics records:
link:BUG-WFC-EVIDENCE-FAILURE-DIAGNOSTICS.adoc[failure diagnostics],
link:BUG-WFC-EVIDENCE-COMMAND-RESOLUTION-DIAGNOSTICS.adoc[command resolution]
and link:BUG-WFC-OPERATOR-DIAGNOSTIC-PROPAGATION.adoc[operator diagnostic
propagation] all concern the in-Hop A2 evidence path or provider transport,
and link:BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[timeout diagnostics]
concerns the in-Hop timeout branch (`evidence.py:347-363`). The baseline
probe is a separate code path (`frontdoor/lifecycle.py:406-437`).

== Direction (not a chosen design)

(a) Check the path shape where the input is first read, so `wfc plan` refuses
it and `wfc run` refuses it before authorization. This moves an existing
refusal earlier and must widen nothing.

(b) Refuse an *unambiguous* cross-adapter mismatch before dispatch, by name:
the resolved basename is the other adapter's known provider binary. Never
refuse an unrecognized basename and never refuse an explicit path -- a
legitimate wrapper must stay launchable.

(c) Include a bounded, explicitly untrusted tail of the already-captured
output in the refusal, reusing the in-Hop path's existing limit and labelling
(`evidence.py:25`, 16384 bytes). Persist nothing as evidence; this is printed
diagnostics, not an observation.

== Risks and the boundary this must not blur

* (b) is a *new* refusal. The failure mode to avoid is a false positive
  blocking a legitimate provider wrapper, which is why it fires only on an
  unambiguous mismatch.
* (c) prints command output in a refusal. It must carry the same bounded
  limit and the same untrusted labelling the in-Hop path uses. A tail printed
  as though it were trusted evidence would be a real regression of the
  trusted/untrusted split, which
  link:BUG-WFC-EVIDENCE-FAILURE-DIAGNOSTICS.adoc[the failure-diagnostics
  record] established deliberately.
* (a) must change *when* the refusal happens and not *what* is admissible.

== Open decisions

None required. The three changes are independent and each could be taken
alone; the plan groups them because they share one code region, one slice and
one qualification. If the maintainer wants the smallest possible step, (c) is
the cheapest and highest-value of the three.

== Implementation note (2026-11-26, WI-WFC-BETA2-O3O2-001)

Implemented exactly as the Design section above states, all three in
`frontdoor/lifecycle.py`. (a) `_authorize` checks `commissioning._path` on
`inputs.config_path` as its first statement; `frontdoor/plan.py`'s `main`
checks the same shape on `--config` before opening the file. (b)
`_do_prelaunch` calls the new `_refuse_cross_adapter_executable_mismatch`
after resolving the executable, comparing a bare name's resolved basename
against `_ADAPTER_KNOWN_BASENAME`; an explicit path is exempted before any
comparison. (c) `_do_probe`'s non-zero-exit refusal appends
`_bounded_untrusted_tail`, which reuses
`evidence.UNTRUSTED_DIAGNOSTIC_CAPTURE_LIMIT_BYTES`. All three refusals
report classification `refused_prelaunch`/`refused_probe` as designed; no
classification or exit code moved. New tests cover each refusal and each
named non-refusal (an explicit path, an unrecognized bare name, the still-
admissible config path shapes) in `tests/unit/test_lifecycle_controller.py`
and `tests/unit/test_frontdoor_init_plan.py`. The skill
(`references/setup.md`, `references/commission.md`) and the Operator Manual
(`ch03_running/01_preparation.adoc`, `ch09_consumer_quickstart/01_quickstart.adoc`)
no longer describe the executable mismatch as undetected; entry 14's row in
`docs/backlog/FTR-WFC-LEVEL1-OPERATOR-GUIDANCE.adoc` is marked retired.
