== Finding-semantics audit

V3 adds exactly two paragraphs (1045 bytes) and the version line. Each required
semantic was checked against the text.

* *Run-local and authoritative.* "finding_id is a run-local authoritative
  identifier." Present and unqualified.
* *Non-null denotes an existing current-Run Finding.* "A non-null finding_id
  may be used only when that exact ID is present in the authoritative Finding
  state projected for the current Run."
* *Repository material is not an ID.* Task prose, historical review artifacts,
  documents, evidence references, commit messages, filenames, and "other
  repository material" are enumerated and excluded -- "are not current-Run
  Finding IDs merely because they look like one." The enumeration covers every
  channel named in the review brief.
* *Historical labels remain citable.* "Such historical labels may be cited as
  evidence or provenance, but must not be submitted as existing Finding IDs
  unless the current Run contains that authoritative ID." Provenance is
  preserved rather than suppressed.
* *New Findings use null.* "Propose a genuinely new Finding with
  finding_id = null and let the Coordinator allocate its run-local ID."
* *Empty Finding state.* "If the current Run has no authoritative Findings, do
  not resolve or otherwise disposition a historical Finding label as current
  Run state." This is the exact Attempt-2 configuration.
* *Addressing a historical concern needs no delta.* "Do not fabricate a Finding
  delta merely to record that implementation work addressed a historical review
  concern; record that fact in summary and/or evidence_refs unless it
  represents a genuinely new current-Run Finding." This is the operative steer
  for the actual Attempt-2 trigger, and `summary` and `evidence_refs` are real
  top-level `ROUTING_RESULT_REQUIRED_KEYS`, so the sentence names the true
  schema and invents nothing.

Ambiguity checks, all negative:

* Historical label versus existing Finding is distinguished explicitly, twice.
* No implication that the agent may allocate an ID; allocation is attributed to
  the Coordinator in the same sentence that introduces `null`.
* Legitimate new-Finding creation is not discouraged; it is stated
  affirmatively and the "do not fabricate" sentence carries an explicit
  "unless it represents a genuinely new current-Run Finding" carve-out.
* Repository evidence is not converted into Run state; the direction of the
  text is strictly the opposite.
* No second or shadow Finding model: no new field, state, authority, or
  vocabulary is introduced. Every term used already exists in `model.py` and
  `serialization.py`.

== Compatibility with actual reducer semantics

The reducer was read independently (`src/workflow_coordinator/reducer.py:111-258`)
and then exercised directly against production code, with no provider and no
test-helper reimplementation:

[source,text]
----
null      + open      (AGENT): OK       -> allocated ['F001']
null      + resolved  (AGENT): REJECTED -> agent cannot create Finding F001 as resolved
"M-5"     + resolved  (AGENT): REJECTED -> unknown Finding ID: M-5
----

* `delta.finding_id is None` -> `_next_finding_id` allocates the next free
  `F%03d` from current-Run Findings. The contract's "let the Coordinator
  allocate its run-local ID" is literally true.
* non-null unknown -> `ReductionError("unknown Finding ID: ...")`, wrapped by
  `reduce_result` into
  `mechanical_preemption:invalid_finding_delta:...` -- the exact archived stop
  reason. Verified to reject even under `FindingAuthority.GATE` with
  `permitted_gate_operations=("resolve",)`, so no authority level can accept a
  historical label.

The candidate altered neither path. V3 is not more restrictive than the reducer
anywhere: its non-null rule is exactly the reducer's `by_id` membership test,
and its new-Finding rule is exactly the `finding_id is None` branch. Authorized
lifecycle transitions (`resolve`, `residual`, `supersede`, `reopen`) are
untouched and unmentioned, so no transition was narrowed by prose.

The contract's phrase "projected for the current Run" is truthful:
`operator._reconstructed_context` emits one `finding=<id>|state=...|
ledger_authority=coordinator` line per authoritative Finding, plus
`finding_authority=...` when the Phase carries a review descriptor, and that
context is passed on every Hop of the operator loop. With `findings: []` in

=== IMPORTANT 1 -- undeclared reversal of the one-current-contract model

The immediately preceding independent review
(`first_wfc_on_wfc_dogfood_correction_review_2026-09-22.adoc`, verdict A)
accepted V2 partly on these grounds, quoted:

____
Exactly one contract resource exists in the tree and in a pristine export.
____

____
Deleting the V1 package resource is consistent with the accepted one-current-
contract product model: runtime selects exactly one contract by construction,
and no accepted authority requires a consumer-visible V1. Retaining V1 bytes in
the package would have created a second selectable artifact with no selector --
strictly worse.
____

That review further recorded as INFO/WATCH that a wheel built from a dirty tree
shipped both V1 and V2 and instructed the maintainer to export from a clean
tree so that promotion would carry only the current contract.

The candidate makes the state that was previously a hygiene defect the intended
design: a clean export now ships two contracts, and the guard that expressed
the invariant was edited from `== ["...v2.txt"]` to `== ["...v2.txt",
"...v3.txt"]`. Nothing in the commit message, the contract, the tests, or the
docs declares or re-justifies the reversal.

This is not a runtime-correctness defect. The loader names V3 literally,
digest-pins it, and `assemble_prompt` reasserts the digest, so V2 is inert and
unselectable and any mismatch fails closed. It is refused because:

* it silently reverses an explicitly accepted product-model decision, applying
  the prior review's own "strictly worse" reasoning in reverse without argument;
* the reversal is effected by weakening the guard that protected it, which is
  the test-quality pattern this review is charged with catching;
* it establishes unbounded accumulation -- V4 would ship three contracts;
* nothing in the V3 *design* depends on shipping V2. Only one *test* does, and
  the previously accepted alternative works: this review verified mechanically
  that removing the 1045-byte insertion from V3 and downgrading the prologue
  reproduces V2 at exactly `c5f36578...`.

=== MINOR 1 -- new-Finding state authority is unstated

Demonstrated against the production reducer: at `investigate` the Phase has
`review: null`, so `reduce_result` selects `FindingAuthority.AGENT` with no
permitted operations, and `_finding_operation(None, RESOLVED)` requires
`resolve`. An agent that correctly adopts `finding_id = null` but keeps
Attempt 2's `proposed_state: resolved` therefore stops at H001 with
`mechanical_preemption:invalid_finding_delta:agent cannot create Finding F001
as resolved` -- a near-identical dogfood outcome.

V3 says "Propose a genuinely new Finding with finding_id = null" without
constraining the proposed state. It is not *more* restrictive than the reducer;
it is silent where the reducer is strict.

Gating judgement: *not gating on its own.* The operative sentence -- "Do not
fabricate a Finding delta merely to record that implementation work addressed a
historical review concern; record that fact in summary and/or evidence_refs" --
matches the actual Attempt-2 trigger exactly, and a compliant agent emits no
delta at all. Reaching the failure requires the agent to override that explicit
instruction. It also fails closed. Every identity requirement enumerated for
this correction is met without it, so treating it as gating would be expanding
the acceptance criteria after the fact.

It is nevertheless recommended for inclusion because the commit must be reopened
for I1 regardless, and the fix is one clause.

=== MINOR 2 -- Finding state is projected outside the enumerated facts

V3's first paragraph enumerates what the Coordinator projects and stops at
`output_contract`. The new paragraph then depends on "the authoritative Finding
state projected for the current Run". That state is in fact projected, but as
`[context]` lines from `operator._reconstructed_context`, not in the
`[identity]` header the enumeration describes. An agent reading the enumeration
as exhaustive could conclude Finding state is never projected and that the
non-null branch is therefore unreachable.

Gating judgement: *not gating.* The claim is true, the projection is real on
every Hop, and the failure mode is over-caution rather than an invalid delta.
