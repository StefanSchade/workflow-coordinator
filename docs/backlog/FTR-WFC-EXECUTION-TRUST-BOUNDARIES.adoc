== Thesis

Agent visibility, mutation authority, and execution authority are distinct
trust dimensions and must not be conflated. Ordinary repository path scope is
necessary but is not sufficient to model all of them, especially where an
agent-authored artifact can later execute in a more trusted context.

== Trust dimensions

Visibility / read authority:: What repository source, data, and contextual
information an agent may observe. This includes protected source, datasets,
credentials, and any surrounding context from which sensitive information can
be inferred.

Mutation / write authority:: Which files, paths, metadata, Git-adjacent
surfaces, or other state an agent may modify. Repository/path mutation scope
is an important current boundary, but it describes only this dimension.

Execution authority:: Which agent-influenced code or configuration may later
execute, and under which trust context. This dimension includes the authority
of the later process, its readable data, credentials, filesystem, and network
access.

== Independent elevation semantics

Visibility/read elevation and mutation/execution elevation are independent.
A pure visibility elevation is controlled primarily by selecting a compatible
technical information boundary *before* protected information is exposed. The
ordinary worker must not be able to widen its own visibility, and prompt
instructions are semantic guidance rather than containment. Protected paths or
data must instead be absent, sealed, or otherwise technically inaccessible to
an incompatible execution boundary. A later review cannot undo disclosure to
an unauthorized provider or execution boundary.

Agents may request additional visibility or capability, but they do not create
authority. Every effective widening of visibility, mutation authority,
execution authority, network capability, or execution-boundary trust must stay
within an authority envelope ultimately rooted in human/maintainer-derived
authority or in a separately governed authority source whose provenance is
mechanically protected from the requesting and delegating components. Policy,
a WorkItem, execution configuration, or equivalent governed input carries
authority only when its provenance is mechanically distinguishable from
agent-produced output. Being committed, tracked, pinned at `HEAD`, structurally
valid, or admitted by ordinary repository checks is not by itself proof that an
input is an authority root.

For a requesting Hop or component, the effective envelope must be resolved
only from authority-bearing inputs fixed or admitted independently of and
before that requester could author or influence them. Assertions by the
requesting worker, a delegating peer, the receiving worker, or their generated
artifacts do not become authority merely by being referenced, committed, or
passed onward. A higher loop may select or delegate within the resolved
envelope, and an agent may delegate only authority it was explicitly granted;
neither may invent or widen the envelope. Once authoritatively admitted under
this provenance rule, that envelope supports automation without a new human act
per Hop; widening it requires new authority from its protected root. Requesting
authority is not granting it, and selecting within authority is not widening
it.

The compatible worker receives only the visibility needed for its task, with
network, egress, and credentials bounded consistently with the information's
sensitivity. This rule may protect proprietary source code,
business-confidential information or trade secrets, sensitive datasets,
credentials, realistic protected test or staging data, and context from which
protected information may be inferred. It does not imply that all such
information has one classification or define a complete classification scheme.

A pure protected-read elevation does not by itself require the mandatory
defensive-review workflow. If a phase receives mutation or execution authority
over a surface classified by the admitted authority envelope as requiring
elevated handling, the explicit elevated-privilege workflow and mandatory
defensive review described by
`FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW` apply. The trigger is that
governed classification of the authority or surface crossed, not the worker's
claim about whether its change can influence something trusted. The worker
cannot waive review; any exemption must come from the governing authority that
classified or granted the elevation. When work needs both protected visibility
and such mutation/execution authority, both controls apply. Network capability
is not intrinsically assigned to either route; its controls depend on the
governed authority dimensions and execution boundary granted.

== Information flow and derived output

Information authority has both an ingress predicate governing who may receive
protected context and an egress predicate governing where information derived
from that context may flow. Selecting a protected, local, or self-hosted
execution binding authorizes only its bounded input visibility; it does not
authorize arbitrary output to return to a less-trusted or cloud boundary.

Derived output retains at least the combined protection requirements of the
protected sources provided to the execution until an explicit, independently
authorized declassification permits disclosure to a lower-trust sink.
Declassification authority must come from the admitted human/policy-owned
envelope; the producing agent cannot self-declassify. Summarizing, paraphrasing,
transforming, regenerating, logging, committing, or copying information is not
itself declassification.

Relevant sinks include model prompts and context, summaries and Findings,
generated files, review artifacts, logs, diagnostics and scratch space,
Run/checkpoint/evidence state, commit subjects and messages, and other
Coordinator-owned durable output. Future implementation may use labels and
authority comparison, but this rule defines no classification lattice, schema,
content scanner, DLP engine, or taint-tracking mechanism.

== Indirect-execution threat model

A restricted agent can remain dangerous even when direct protected-data access
is forbidden. It may modify an indirect-execution surface such as Git hooks,
CI configuration, test discovery/configuration, `conftest.py`, Makefiles,
build hooks, packaging hooks, Docker/container build or runtime configuration,
or scripts later run by a trusted maintainer or service.

For example, an agent that cannot directly access protected data can write a
test, build step, or hook that exfiltrates it. A later trusted test/build
service executes that artifact with protected data, credentials, filesystem
access, or network access. The service then becomes a confused deputy. Path
scope alone does not express this trust transition.

== Candidate design direction (not an accepted implementation)

Potential mechanisms to investigate include Linux namespace/sandboxing such as
`bwrap`; exposing only the filesystem paths required by an execution; making
protected or unneeded paths unavailable rather than merely prohibited;
constraining writable paths separately from readable paths; constraining Git
metadata and indirect-execution-sensitive surfaces; no ambient credentials;
restricted network/egress where required; and separate execution environments
for agent-authored code. Trusted test/build services are distinct boundaries
and should use fixed entry points and the least authority practical. `bwrap` is
one candidate Linux mechanism, not a required implementation.

There must be *no automatic unlock*. When a task genuinely requires mutation
of an execution-sensitive surface, the agent must explicitly escalate, an
authority within the admitted envelope must authorize the widened capability,
and that run must be distinguishable from ordinary sandboxed runs. The governed
classification of the granted mutation/execution authority determines whether
the mandatory defensive-review pattern in the elevated-privilege FTR applies;
the worker's consequence assessment does not. A protected-read requirement
instead needs an authorized, compatible information boundary before
disclosure; it does not authorize the ordinary worker to reveal or mount the
protected context for itself.

Candidate, non-final event vocabulary is:

----
requires_protected_read
requires_execution_surface_mutation
requires_network
requires_trusted_test_context
----

This record neither implements nor schema-commits that vocabulary.

== Trusted test-service boundary

A trusted test service must not become a confused deputy. Where applicable,
prefer a fixed trusted harness, no network egress, no credentials, protected
data mounted only when required, a bounded filesystem, and execution of
agent-authored tests/code with the least authority necessary. If agent-authored
code must run against protected context, treat it as a distinct trust
transition rather than ordinary test execution.

== Deployment implication

A cloud-hosted worker can often perform generic work against public or bounded
context without receiving protected source or data. If it reports that a
subproblem requires protected context, a future higher loop or human operator
may make the authority/policy decision and delegate that subproblem to a
bounded execution binding compatible with the information, such as a local or
self-hosted model. Output may return to the ordinary workflow only under the
information-egress and declassification rule above. Local/self-hosted execution
is one possible boundary, not a provider-specific rule. This records an
architectural implication only; it does not design an outer-loop planner,
automatic model router, provider selection algorithm, or new workflow profile.

== Relationship to existing WFC boundaries

This extends rather than replaces declarative phase authority, repository/path
mutation scope, Coordinator-owned Git mutation, trusted evidence, and
independent review. The additional concern is indirect execution and explicit
trust transitions; it does not replace repository policy, prompt/contract
authority, or review.

== Non-goals

This FTR does not:

* mandate `bwrap` specifically;
* implement sandboxing;
* define a complete information-classification taxonomy or delegation/router
  architecture;
* replace repository policy, prompt/contract authority, or review;
* guarantee protection against all malicious code;
* define a complete secret-management system; or
* require all development to be self-hosted.

== Deferred priority and revisit trigger

No immediate implementation is authorized. Revisit this backlog record when
protected-data workflows, untrusted-agent containment, trusted test services,
