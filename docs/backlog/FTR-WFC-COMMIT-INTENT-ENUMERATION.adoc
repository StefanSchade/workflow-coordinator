== Three classes of failure (for the record; not a design decision)

The maintainer's report and the verified anchors above distinguish three
different classes, which a later investigation must keep separate rather than
treat as one defect:

. *Commissioning problems* -- D3-001 (an incomplete consumer-scope search
  before commissioning). D4-001 is explicitly *not* a defect of this kind, or
  of any kind: it was a correct escalation on a genuine content-versus-links
  tradeoff that a machine-enumerated path list could not have resolved either.
. *Tool-contract problems* -- D3-002 (`git mv` versus `trusted_commit()`'s
  unchanged-index precondition). This is a Commission-authoring and
  Worker-instruction problem, not a `CommitIntent` enumeration problem.
. *CommitIntent ergonomics* -- D3-003 (one missing pair) and D3-004 (a prose
  element instead of a path list). These are the cases where a probabilistic
  language model was asked to reproduce a long, deterministic enumeration of
  changed paths completely and exactly, and did not.

Only the third class is this record's actual hardening candidate. The first
two are addressed, to the extent they are addressed at all, by better
commissioning and clearer Worker instructions (already captured in the
Operator Manual section cited above), not by a `CommitIntent` mechanism
change.

== Central question

How can the deterministic enumeration of the actually changed paths be
separated from the Worker's semantic commit intent, without weakening any
existing trusted-commit invariant?

This is the maintainer's report's own central question in substance (see
`INCIDENT_REPORT.txt` section 11, phrased there as keeping semantic commit
authority with the Worker while leaving the purely mechanical enumeration to
the Coordinator or a deterministic helper). It is recorded here as a question
for a later, separately authorized investigation, not as an architecture
decision.

== What a later design investigation must cover (questions and constraints -- not chosen architecture)

A future investigation, itself a separate, independently reviewed package,
must at minimum address:

Three sets that must not be silently equated::
`authorized_scope` (what the Commission permits), the actually observed
changes (what Git reports as mutated), and the Worker's explicit `CommitIntent`
(what the Worker says it wants committed). Equating any two of these without
an explicit, checked correspondence is exactly the kind of "real contract
change, not a purely mechanical simplification" the report itself warns
against (`INCIDENT_REPORT.txt` section 8, Stage 2).

Alternatives to compare, with their security consequences, not a chosen design::
. A read-only diagnostic helper only -- derives a canonical path list from
  the real Git state for the Worker/Operator to compare against its own
  intent, but changes no authorization semantics and commits nothing itself.
. Coordinator-computed enumeration with an explicit Worker confirmation --
  a deterministically generated, validated commit manifest that the Worker
  must explicitly confirm before the trusted commit, as one possible solution
  among several (`INCIDENT_REPORT.txt` section 8, Stage 2); whether
  confirmation is required, and what it protects against, is an open design
  question, not settled here.
. No mechanism change, better commissioning only -- the already-accepted
  Operator Manual mitigation (`71da86e`) continues as the sole mitigation;
  this reduces but, as observed, does not remove the underlying cardinality
  problem.
+
Each alternative must be compared against the others on what it actually
changes about who can cause what to be committed, not only on ergonomics.

Byte-faithful Git path handling::
NUL-delimited porcelain output, `--no-renames` (or equivalent explicit,
non-heuristic handling) for any new deterministic enumeration, and no
reliance on Git's rename heuristic as an authorization-relevant fact.

Rename semantics (both halves)::
Any new enumeration mechanism must name both the old and new path of a
rename explicitly, consistent with the existing fix in `cf183a3` (reviewed
`98ac012`) and the still-open
link:BUG-WFC-TRUSTED-COMMIT-RENAME-RECONCILIATION.adoc[rename-reconciliation BUG],
which records that this fix reduces but does not remove rename-shaped
staged-path hazards elsewhere in the codebase.

State changes between observation and commit::
Any enumeration computed before the trusted commit must be rechecked against
the repository's actual state immediately before the commit is made; a
stale observation must never be trusted as current.

Preservation of every existing fail-closed property::
scope refusal, the unchanged-index precondition, the requirement that intent
equal the observed change set exactly, HEAD and repository-cleanliness
expectations, never committing everything in a worktree regardless of intent,
and no loosening of the existing scope boundary. None of these may be
weakened by a future change that only targets enumeration ergonomics.

Relation to the open directory-path BUG::
link:BUG-WFC-COMMIT-INTENT-DIRECTORY-PATH-RECONCILIATION.adoc[the directory-shaped
`CommitIntent` BUG] already records two undecided options for a related but
distinct problem (directory-shaped intent entries, not long leaf-exact
enumerations). A later investigation of this record's question must
reconcile with, not duplicate or silently preempt, that BUG's open choice
between its Option 1 (require leaf-exact paths explicitly) and Option 2
(Coordinator-side directory expansion).

The investigation itself is a later, separately authorized package that must
be independently reviewed; this record decides, schedules and authorizes
none of it.

== Regression inventory for the investigation (test cases, not implementation)

A later investigation's test inventory, adapted from the maintainer's report
(`INCIDENT_REPORT.txt` section 9), over a synthetic Git checkout of
150-300 files. Expected behaviour stays fail-closed in every case except the
first; a faulty intent must never be accepted merely because the overall
change looks plausible.

[cols="1,3,2", options="header"]
|===
|Case |Description |Expected

|A |150 pure renames with a complete, correct `CommitIntent` |commit succeeds (positive control)
|B |one old/new path pair missing from the intent |fail-closed refusal
|C |an extra, unchanged path listed in the intent |fail-closed refusal (no matching worktree mutation)
|D |`git mv` (or any other pre-staging) changed the index beforehand |fail-closed refusal (unchanged-index precondition)
|E |a link/reference consumer outside the authorized scope |fail-closed scope refusal
|F |`commit_intent.paths` holds a prose element instead of a path |fail-closed refusal
|G |file names with spaces, Unicode and unusual filesystem bytes |correct byte-faithful handling; no silent mis-enumeration
|H |the number of actually changed paths differs from the expected/declared count |fail-closed refusal
|I |two consecutive Git observations of the same state differ |rechecked and refused, never committed on a stale observation
|===

== Measurable success criteria for the investigation

Examples the investigation should use to judge any later change against the
status quo, not a current measurement:

* Runs, Hops and operator interventions needed per many-file Commission
  (D3 needed five Runs across the four stopped attempts plus the accepted
  one; D4 needed two Runs), before and after any future change, on a
  comparably-shaped many-file Commission.
* Refusals per path count (whether the fail-closed refusal rate correlates
  with `CommitIntent` cardinality, as it appears to today), before and after.
* No regression on the invariants in the "preservation of every existing
  fail-closed property" constraint above, measured by the regression
  inventory, before and after.

== Not recommended

Taken directly from the maintainer's report (`INCIDENT_REPORT.txt`
section 10), as the hardening candidate's own boundaries, not as this
record's independent conclusion:

* No general loosening of Git authorization.
* No automatic commit of all worktree changes.
* No abolition of the scope boundary.
* No new permanent governance structure for rare mass-file operations.
* No extensive architecture change immediately before the first public
  release.
