= FTR-WFC-PHASE-EXECUTION-BINDINGS -- Phase-specific execution bindings

Work item:: `WI-WFC-PHASE-EXECUTION-BINDINGS-001`
Status:: Implementation submitted for independent review. Integration remains an operator decision.

== Decision

Keep role execution defaults and role CLI overrides. Apply optional Consumer
Config `phase_execution` entries last, field by field, against the selected
program's executing phase keys. Pin the full effective map for the Run and
select from it by the current Hop's phase. The
link:../operator_manual/ch03_running/01_preparation.adoc#execution-bindings[Operator Manual]
owns syntax, precedence and validation.

=== Compatibility and limits

Without phase overrides, the role-keyed version-1 envelope keeps its bytes
and digest for the same bindings. With overrides, version 2 records the
complete phase map. Both forms use one adapter and one scalar executable.
The profile continues to supply roles, personas, review authority and phase
scope. Provider selection grants no workflow authority.

Mixed adapters would require a future design that explicitly binds executable
identity to each adapter, admits the corresponding provider capabilities and
sandbox settings, and defines how those pins are evidenced and checked on
recovery. Distinct models within one adapter meet this WorkItem's need.

== Acceptance and evidence

Preview, admission and execution must agree on every effective phase binding.
Test the field merge, missing fields, unknown or unreachable phases, malformed
values and mixed effective adapters. Exercise `robust@v1` through distinct
models for its two independent review phases, and compare provider arguments,
the envelope digest and archived evidence. Confirm pinning through drift,
resume and reconciliation. See the regression tests in
link:../../tests/unit/test_consumer_compiler.py[resolution],
link:../../tests/unit/test_operator_admit_parsed.py[admission],
