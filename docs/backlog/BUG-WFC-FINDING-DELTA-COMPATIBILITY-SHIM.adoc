== Observed current behavior

`src/workflow_coordinator/model.py:220-255` retains an internal
`FindingDelta(...)` compatibility constructor/helper alongside the two
explicit model forms it was meant to be superseded by:

[source,python]
----
def FindingDelta(
    finding_id: str | None,
    proposed_state: FindingState,
    evidence_refs: tuple[str, ...],
    invariant: str | None = None,
    blocking: bool | None = None,
    successor_ref: str | None = None,
    new_material_evidence: bool = False,
) -> FindingDeltaValue:
    ...
    if finding_id is not None:
        return ExistingFindingDelta(
            finding_id=finding_id,
            proposed_state=proposed_state,
            evidence_refs=evidence_refs,
            successor_ref=successor_ref,
            new_material_evidence=new_material_evidence,
        )
    ...
----

For a non-`None` `finding_id` (an existing Finding), the function accepts
`invariant` and `blocking` arguments and silently drops them while
constructing an `ExistingFindingDelta`, whose type deliberately has no such
fields. No exception, warning, or assertion is raised; the caller's
`invariant`/`blocking` values are accepted syntactically and discarded
semantically.

This is exercised today by at least one internal caller. The test fixture
helper `delta(...)` in `tests/support.py:178-196` unconditionally passes
`invariant` and `blocking` (with defaults `"The accepted invariant must
hold."` / `True`) to `FindingDelta(...)` regardless of whether `finding_id`
is `None`:

[source,python]
----
def delta(
    finding_id: str | None,
    state: str,
    *,
    invariant: str = "The accepted invariant must hold.",
    blocking: bool = True,
    ...
) -> FindingDelta:
    return FindingDelta(
        finding_id=finding_id,
        invariant=invariant,
        blocking=blocking,
        proposed_state=FindingState(state),
        evidence_refs=(evidence,),
        successor_ref=successor_ref,
        new_material_evidence=new_material,
    )
----

`grep -rn "FindingDelta(" tests/` shows this fixture is the only remaining
internal caller of the compatibility constructor with an existing
`finding_id` in the test suite (44 call sites across the unit and
architecture tests route through it); production code
(`src/workflow_coordinator/serialization.py:749-792`) already constructs
`ExistingFindingDelta` / `NewFindingDelta` directly and does not call
`FindingDelta(...)`.

== Why it is undesirable

`ExistingFindingDelta` was deliberately given no `invariant` or `blocking`
fields so that only the Coordinator ledger can own those values for an
existing Finding -- that is the exact invariant
`WI-WFC-IMMUTABLE-FINDING-ECHO-FIX-002` H003 restored at the model level.
`FindingDelta(...)` re-opens a narrower version of the same shape of problem
one layer down: it lets an internal caller *express* a semantically
impossible combination -- "this is an existing Finding, and also here are new
invariant/blocking values for it" -- and then normalizes that expression away
rather than rejecting it. A caller (today, a test fixture; potentially a
future internal helper) can write code that looks like it is proposing new
invariant/blocking content for an existing Finding, and the compatibility
constructor will accept that call and quietly produce a value that carries
none of it. This is a silent-discard / fail-open construction path, which is
the same class of property the completed correction eliminated at the
reducer and wire boundary, just not yet at this internal construction
boundary.

== Desired future correction (not authorized here)

Internal callers should use the explicit semantic form they mean --
`ExistingFindingDelta` for an existing Finding, `NewFindingDelta` for a new
one -- rather than routing through a compatibility constructor whose API
admits a semantically impossible combination and silently discards the
inapplicable arguments. A future bounded correction will likely:

* remove the `FindingDelta(...)` compatibility constructor/helper from
  `src/workflow_coordinator/model.py`; and
* migrate its remaining internal callers and tests (at minimum
  `tests/support.py`'s `delta(...)` fixture and its call sites) to construct
  `ExistingFindingDelta` or `NewFindingDelta` directly, rather than retaining
  the shim merely to avoid updating them.

Any such correction must preserve the already-correct wire/parser/schema
boundary (`src/workflow_coordinator/serialization.py`) and reducer-owned
existing-Finding invariant/blocking authority semantics
(`src/workflow_coordinator/reducer.py`) exactly as
`WI-WFC-IMMUTABLE-FINDING-ECHO-FIX-002` left them; this record does not
propose changing either.
