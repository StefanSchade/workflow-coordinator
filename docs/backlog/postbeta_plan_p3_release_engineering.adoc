== 3. Release-contract decisions

[[c1]]C1 — Versioning scheme and the tag:: Static `version`, tag `v<version>`,
preflight asserting `tag == "v" + version`. *Decided (<<md2,MD-2>>): publish
`0.1.0b1`, not a bump* — the version the built artifacts and
`test_bp1_identity.py:41` already assert; no `b2` appears anywhere in this plan.
[[c2]]C2 — What an artifact contains, and must not:: Wheel: the
`workflow_coordinator` package (`.py` files plus exactly the four reviewed
resource texts) and `*.dist-info`. Sdist: `pyproject.toml`, `setup.cfg`
(setuptools writes it into the archive; no such file is tracked, so the entry is
not a mistake), `PKG-INFO`, `README.md`, `LICENSE`, `src/**`. Forbidden by name
in both: `docs/`, `tests/`, `governance/`, `project_memory/`, `.wfc/`,
`scripts/`, `requirements/`, `tmp/`, `build/`, any `*.ods`, any Evidence or Run
artifact. Fail on anything *unlisted*, not only on the forbidden list, so a new
top-level directory cannot leak in silently.
[[c3]]C3 — The install check from a clean environment:: Install the *built
artifact* into a fresh venv and run `wfc --help` and `wfc --version --json`
from a directory *outside* the checkout, asserting the reported version equals
the tag and `source_commit` is `null`. The suite already proves the mechanism,
so the release adds only the outside working directory and that assertion.
[[c4]]C4 — Release notes:: Preflight fails when the tag has no matching section
or its heading still says `planned`. Content for the first release: what
changed since Beta, the limitations the consumer quickstart already enumerates,
and the one qualified platform profile.
[[c5]]C5 — Version-pinned documentation:: *Decided: publish no HTML for
`0.1.0b1`* (<<md4,MD-4>>, deferred not rejected). Link documentation from
`README.md` by absolute, tag-pinned repository URL, keep the strict render as a
gate, revisit Pages when a second consumer exists. The repository is already
public (<<md3,MD-3>>), so these tag-pinned links already work for a consumer;
no reopening of <<c2>> is needed on that account.
[[c6]]C6 — What runs on a hosted runner:: *Open, tracks <<md5,MD-5>>.* Target:
the whole required suite, not a subset, on a pinned `ubuntu-24.04` runner via
route R-A; everything else in `check` (build, `dist-audit`, <<c3>>, <<g5>>)
runs regardless. Until a hosted run proves R-A green, the qualified host and
the Operator's result stay the binding gate; see <<md5,MD-5>> for the facts
and <<g2,G2>> for the gate.
[[c7]]C7 — Distribution destination:: *Decided (<<md1,MD-1>>): TestPyPI, then
PyPI, both through a Trusted Publisher with no stored token, plus a GitHub
Release carrying the same two artifacts.* TestPyPI is a real upload (a
*rehearsal*, not `--dry-run`): see <<g6,G6>> for why, and <<gates>> for where
it sits relative to tagging and <<q1,Q1>>.

=== E0 — The flaky preservation test

Scope:: `tests/unit/test_candidate_preservation.py`; `git_facts.py` only if a
product defect is proven, not only a racy fixture.

way `python -m pytest -q` is green.

== 6. Final consumer qualification

A separate package with its own gate: *not* the BP9 neutral installed-wheel
qualification and *not* release-engineering readiness. E1–E3 and <<gates>> can
be green while Q1 fails, which is the point of keeping them apart.

[[q1]]
=== Q1 — One real WorkItem in `spreadsheet-handling`

Subject (<<md6,MD-6>>, decided):: The DMC resumption review's ingress-fidelity
defect, its R1: `JSONBackend.read_multi`'s `pd.read_json(dtype="string")` lets
pandas infer a numeric column's dtype before string conversion, so one value's
JSON rendering depends on the other values sharing its column (observed
identically on pandas 3.0.2 and 2.3.3). A real, bounded bugfix with a real
regression assertion, not a contrived demo. If not practical close to execution
time, an explicitly labelled smoke test with a small real repository change
(for example adding one AsciiDoc file) is the fallback — *not equal to a
successful bugfix qualification*; the record states exactly what was proven,
and if the release acceptance criteria would have to change because of that
substitution, this is escalated to the maintainer explicitly rather than
decided here.
Prerequisites:: A release candidate built from the qualified pre-tag commit on
`main` (<<gates>>) and installed *from the artifact* into an isolated
environment, never an editable checkout of this repository; <<ext,ES-6>> for
access, provider CLI and check command; a *fresh* checkout, because one
authorized lifecycle per checkout is the Beta contract (ADR AD-5) and a reused
checkout refuses every later `wfc run`.
Scope of the Run:: One bounded change in R1's area of the *consumer*
repository, with a real test assertion. No WFC repository change belongs to
Q1; defects it reveals become their own records.
Acceptance:: The Run reaches a terminal state through the installed product
path — `init`, `plan`, `run --yes`, `status`, `report`, archive — with the
Commission and execution-envelope digests re-derived; the consumer repository
carries a real modification inside the authorized scope and nothing outside it;
its own check command is the trusted evidence and passes; the independent
review is real and dispositions itself; archive facts match the actual
outcome; and the record names the candidate version, the implementation tree
digest and the provider models.
Stop rules:: Stop and report, never repair, when the pre-launch baseline probe
refuses (`refused_probe`, exit 23 — it consumes the checkout's one lifecycle, so
retry needs a fresh checkout); the check command exceeds the 900-second evidence
cap; WFC refuses the commit over a clean or process filter; or the Run stops
`awaiting_human`. A truthful stop is a *valid*, dispositioned outcome
(<<gates,G7>>): neither a failure to work around nor silent satisfaction of the
gate.
Explicitly not acceptance:: a passing fake-provider test, a green consumer CI
run alone, or a change contrived to produce a green Run.

[[gates]]
== 7. Gates, risks, and what is not in this release

Release sequence, each step gated by the named gate:

. Push the release commit to `main` (<<ext,ES-3>>); `check` runs — <<g1>>,
  <<g2>>, <<g3>>, <<g4>>, <<g5>>.
. With `check` green, the maintainer gives <<q1,Q1>> that commit's build
  artifact (downloaded, or rebuilt identically — the build is static-version
  and reproducible) and authorizes the Run — <<g7>> on completion.
. Only once Q1 is accepted does the maintainer push the tag (<<ext,ES-4>>);
  `check` re-runs in tag mode, re-proving everything against the tagged commit.
. `publish-testpypi` runs unattended — <<g6>>.
. The pipeline waits at the `pypi` environment's required-reviewer gate —
  <<g8>>; approval is never inferred from a green job.
. `publish-pypi`, then `release`, run after approval; the maintainer verifies
  the index page and the Release (<<ext,ES-5>>).

*Why Q1 sits before the tag.* Q1 is the least automated, highest-uncertainty
gate, while a tag by itself spends nothing; TestPyPI/PyPI steps on an
*already-pushed* tag would each spend a version number if Q1 then failed.
Running Q1 pre-tag means a Q1 failure costs only a delayed tag. *The single
point the maintainer must confirm:* that Q1 against a pre-tag build —
self-reporting the same static version, `source_commit` null, exactly as every
wheel/sdist install already does — stands in for "the release candidate,"
rather than requiring Q1 on an already-tagged artifact at the cost of an
abandoned tag or a deliberate deletion.

Every gate is release-blocking; there is no advisory class. Each is named as
*gate — owner — verification evidence*.

[[g1]]G1 Preflight clean — Operator and CI:: topology (branch mode or tag

[[g2]]G2 Required suite green — Operator now, CI once <<md5,MD-5>> is settled
feasible:: `python -m pytest -q` with the two env vars set and zero flake

[[g4]]G4 Clean-environment install and CLI identity — CI and Operator::

[[g5]]G5 Documentation renders strictly — CI::
`asciidoctor --safe-mode=safe -a assembled -o /dev/null --failure-level=WARN`

[[g6]]G6 TestPyPI rehearsal, not a dry run — CI and Operator:: `publish-testpypi`

[[g8]]G8 Release authorized — Maintainer:: the `pypi` environment's

*Risks.*

R-1 MD-5's feasibility is not yet proven:: route R-A depends on `sysctl`/userns
and git-lfs neutralization behaving on `ubuntu-24.04`; unverified items named
in <<md5,MD-5>>. *Mitigation:* the first hosted branch run (<<ext,ES-3>>) is
the cheapest evidence; MD-5's escalation rule governs a real blocker.
R-2 Static version drifts from the tag:: `test_bp1_identity.py:41` asserts the
literal `0.1.0b1`. *Mitigation:* G1, plus that literal named in C1's/E1's
checklists.
R-3 Publication is irreversible, and a tag or TestPyPI version can be spent on
a failed step:: PyPI refuses to re-upload a version; name availability is not
checkable from a Run. *Mitigation:* <<ext,ES-1>> early; Q1 before tagging
keeps the tag cheap to delay; PyPI additionally needs reviewer approval.
R-4 The flaky preservation test could make a "green" suite non-deterministic::
observed 1 of 6 single-file runs, 2 of 40 in the reproduction. *Mitigation:*
<<e0,E0>> resolves this before any result is trusted as <<g2>> evidence.
R-5 Q1's environment refuses the Run:: filter config, the 900-second cap, or
one lifecycle per checkout. *Mitigation:* <<ext,ES-6>> measured first; Q1's
stop rules make each a reportable outcome.
R-6 Correction cycles consume the budget:: 10 of 32 archived Runs stopped
`awaiting_human`. *Mitigation:* budgets (including <<e0,E0>>) include one
correction cycle; a second needs a successor Commission.

*Not in this release.* Published HTML, a Pages repository, a `latest` alias and
their immutability machinery (deferred past `0.1.0b1` per <<md4,MD-4>>, not
rejected); any second repository; signing or provenance attestation; a Python
or OS matrix; ARM64 or a second qualified profile; conda, Homebrew or a private
index; Dependabot configuration; documentation inside the artifacts; automation
beyond the single workflow; a new workflow program or kernel change (ADR AD-1
makes that release work of its own); lifecycle rotation (AD-5).

*Rejected packages.*

A separate README-link tool and bake procedure:: The reference needs a
substitution procedure because its URLs are versioned; WFC's rule is one
assertion inside `release-check`.
A test asserting the workflow matches the documented gates:: Parsing YAML to
restate prose, while missing the only interesting failure — a gate that passes
while proving nothing.
A release-automation Commission:: Tagging and publishing are <<ext,ES-4>> and
<<ext,ES-5>> by design; automating the irreversible step removes the human stop
that matters.

[[decisions]]
== 8. Decisions the maintainer has taken, and the one still open

[[md1]]MD-1 — Distribution destination (<<c7>>), *decided*:: TestPyPI, PyPI and a
GitHub Release, through a GitHub Actions release pipeline. WFC follows
`spreadsheet-handling`'s release flow, tools and operation as closely as
possible; every deviation in section 2's table has a named technical reason.
Both PyPI and TestPyPI use OIDC Trusted Publishing; no long-lived token.
`spreadsheet-handling`'s SSH secrets (`WFC_READ_DEPLOY_KEY`, `DOCS_DEPLOY_KEY`)
answer needs WFC does not have and are *not* adopted.
[[md2]]MD-2 — The first published version (<<c1>>), *decided*:: `0.1.0b1`, tag
`v0.1.0b1`, no bump. `pyproject.toml` already says `0.1.0b1`; the tag-equals-
version assertion and the test literal at `test_bp1_identity.py:41` are named
facts, not independently re-derived.
[[md3]]MD-3 — Repository visibility, *decided*:: `StefanSchade/workflow-coordinator`
is already public and its history is judged clean by the maintainer; no further
disclosure review, no visibility change. This corrects every earlier
conditional statement in this plan that assumed otherwise, including the
reference's read-only deploy key (which answered a need WFC does not have,
regardless of visibility) and the earlier private-repository branch of <<c5>>.
[[md4]]MD-4 — Version-pinned documentation publishing (<<c5>>), *decided*::
Deferred for `0.1.0b1`, *not* permanently rejected. GitHub-hosted documentation
with version-bound links suffices now; `spreadsheet-handling`'s Pages solution
is a possible model for a later extension, once a second consumer exists.
[[md5]]MD-5 — Must the whole required suite run on a hosted runner? (<<c6>>),
*open*:: The earlier recommendation (a subset on the runner) is *not* accepted.
Target: the whole required suite, on a qualified hosted environment, as a
binding gate if technically possible.

[1] Setup requirements:: `WFC_TEST_INPUTS`/`WFC_TEST_PROFILE` set to a bundle
verified byte-for-byte (`tests/conftest.py:101-121`); `check_host` compares
implementation, Python minor, machine, system, SOABI, seed pip exactly and
glibc as a floor (`wfc_test_inputs.py:162-176`, re-verified); 12 pinned
wheels; an editable WFC install (without it, two tests fail with "No module
named workflow_coordinator"); real bubblewrap userns, Git without a
clean/process filter, GNU make, PEP-517 isolation. Exactly four conditional
skips exist suite-wide (three opt-in live-provider, one internal probe);
nothing else is ever skipped.
[2] Reproducible on a GitHub runner?:: Not yet proven, but plausible: route
R-A is `ubuntu-24.04` (pinned label) plus `setup-python` pinned to the exact
patch `3.13.5`, a `sudo sysctl` relaxing unprivileged-userns for bwrap, a
step-scoped neutralization of the runner's git-lfs filter (not WFC's own
filter-refusal test), the normal `fetch`+`exec` flow, then the unmodified
suite.
[3] A second host profile's closure review?:: Re-verified against the
profile and `wfc_test_inputs.py`: the 12 wheel pins are checked only by
filename, size, SHA-256, metadata and wheel *tag* (manylinux/`py3-none`/
`cp313` plus a glibc floor) — none depends on the CPython build, so the pins
would not change. The build-dependent part is `seed_pip_version`
(`ensurepip.version()`), which Debian patches to a bundled pip distinct from
upstream's; other host fields are generic. So a second profile's review
reduces to a byte-equality diff of `wheels` plus a review of `host`'s
build-specific fields, not a full dependency re-audit.
[4] What cannot run at all?:: Nothing by design; the four skips are opt-in or
internal, not host-related, and none may be silently widened.

*Still unknown, needing a hosted run:* (a) the runner's actual seed pip
version for CPython 3.13.5 on `ubuntu-24.04`; (b) bwrap userns after the
`sysctl`; (c) whether the runner's Git carries a git-lfs filter and the
neutralization suffices; (d) that `fetch` reaches `files.pythonhosted.org`;
(e) whether a second profile is wanted if the pip version differs.
*Cheapest evidence:* the first hosted run of <<e3,E3>>'s workflow on a branch
(<<ext,ES-3>>) answers (a)–(d). *Escalation rule:* a real, reproducible
blocker is documented with the failing log and escalated — route R-B
(digest-pinned container), a documented partial gate, or otherwise — to the
maintainer; MD-5 is not loosened and <<g2,G2>> not narrowed without that
decision.

[[md6]]MD-6 — Consumer qualification subject (<<q0>>, <<q1>>), *decided*:: Q0
does not run; Q1 takes the DMC resumption review's ingress-fidelity defect (its
R1) directly as its subject, with an explicitly labelled smoke test as the
fallback if that is not practical close to execution time — a fallback that is
not equal to a successful bugfix qualification, and that, if it would change
the release acceptance criteria, is escalated to the maintainer rather than
decided here.
