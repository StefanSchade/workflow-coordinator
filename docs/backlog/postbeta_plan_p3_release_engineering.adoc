== 3. Release-contract decisions

[[c1]]C1 — Versioning scheme and the tag:: Static `version`, tag `v<version>`,
preflight asserting `tag == "v" + version`; the published version itself is
decided at <<md2,MD-2>> and no `b2` appears anywhere in this plan.
[[c2]]C2 — What an artifact contains, and must not:: Wheel: the
`workflow_coordinator` package (`.py` files plus exactly the four reviewed
resource texts) and `*.dist-info`. Sdist: `pyproject.toml`, `setup.cfg`
(setuptools writes it in; untracked, so not a mistake), `PKG-INFO`,
`README.md`, `LICENSE`, `src/**`. Forbidden by name in both: `docs/`, `tests/`,
`governance/`, `project_memory/`, `.wfc/`, `scripts/`, `requirements/`, `tmp/`,
`build/`, any `*.ods`, any Evidence or Run artifact. Fail on anything
*unlisted*, not only the forbidden list, so a new top-level directory cannot
leak in silently.
[[c3]]C3 — The install check from a clean environment:: Install the *built
artifact* into a fresh venv and run `wfc --help` and `wfc --version --json`
from a directory *outside* the checkout, asserting the reported version equals
the tag and `source_commit` is `null`. The suite already proves the mechanism;
the release adds only the outside working directory and assertion.
[[c4]]C4 — Release notes:: Preflight fails when the tag has no matching
section or its heading still says `planned`. Content: what changed since
Beta, the quickstart's limitations, and the one qualified platform profile.
[[c5]]C5 — Version-pinned documentation:: No HTML for `0.1.0b1` (<<md4,MD-4>>).
Link documentation from `README.md` by absolute, tag-pinned repository URL —
these links work since the repository is public (<<md3,MD-3>>) — keep the
strict render as a gate; no reopening of <<c2>> on that account.
[[c6]]C6 — What runs on a hosted runner:: *Open* — see <<md5,MD-5>> for the
target, facts and escalation rule, and <<g2,G2>> for the gate; everything else
in `check` (build, `dist-audit`, <<c3>>, <<g5>>) runs regardless.
[[c7]]C7 — Distribution destination:: *Decided* — see <<md1,MD-1>>. TestPyPI is
a real upload (a *rehearsal*, not `--dry-run`): see <<g6,G6>> for why, and
<<gates>> for where it sits relative to tagging and <<q1,Q1>>.

Four Commissions, each `robust@v1` with worker plus independent review,

Runs: 126 Hops, 18 `completed`, 10 `awaiting_human`, 3 `reconcile_required`,
1 budget-exhausted, 31 `correct` — one correction cycle is the norm.
<<e0,E0>> is independent of E1–E3, completing (either way) before any suite

[[e0]]
=== E0 — The flaky preservation test

Scope:: `tests/unit/test_candidate_preservation.py`; `git_facts.py` only if a
product defect is proven, not only a racy fixture.
Model:: Sonnet worker, Opus reviewer (heavy-task rule) — whether
`preserve_candidate` can mis-report a real change needs adversarial reasoning
about Git's racy-stat protection against the function's throwaway copied index
(`_isolated_index_copy`), not routine authorship.
Hop budget:: 8 — reproduce the flake deterministically (control timestamps
explicitly rather than wall-clock luck, as `MD5_flake_repro.py` already narrows
it to same-size same-second edits), diagnose defect-vs-fixture before touching
source, then fix or harden with a regression/negative test; the diagnosis is
the hard part, so one correction cycle is budgeted.
Dependencies:: None.
Acceptance:: The record states, with reproduced evidence, whether a second-call
`git status` read can return `not_needed` for an actually-changed file outside
this test's narrow two-rapid-calls pattern. If yes: a fix plus a regression
test failing before and passing after. If no: the fixture is corrected so 100
repeated single-file runs show zero failures, with the reason recorded. Either
way `python -m pytest -q` is green.
Non-goals:: No change to trusted-commit/preservation authority for any other
caller; no behavior change outside the one function investigated.

== 6. Final consumer qualification

A separate package with its own gate: *not* the BP9 neutral installed-wheel
qualification, *not* release-engineering readiness. E1–E3 and <<gates>> can be
green while Q1 fails — that is the point of keeping them apart. As of
2026-11-23 (<<md6,MD-6>>), Q1 is conducted as a *consumer smoke
qualification*, not a bugfix qualification; see <<q1>> for its current
subject and limitation, and <<q1-open>> for the maintainer decisions this
change leaves open.

[[q1]]
=== Q1 — Consumer smoke qualification in `spreadsheet-handling`

Subject (<<md6,MD-6>>, revised 2026-11-23):: A deliberately *minimal consumer
smoke qualification*: a real WFC Run, through the installed
release-candidate distribution, creates one new, small AsciiDoc file in a
suitable documentation directory of the `spreadsheet-handling` repository.
The target directory, file name and check command are *not yet decided* —
see <<q1-open,Decisions the maintainer must take or confirm>> (b). This
replaces the DMC resumption review's ingress-fidelity defect (R1) as Q1's
conduct; R1 itself is postponed, not abandoned — see
<<q1-postponed,Postponed after the release>> below.
Prerequisites:: A release candidate built from the qualified pre-tag commit on
`main` (<<gates>>), installed *from the artifact* — never an editable checkout
— into an isolated environment; <<ext,ES-6>> for access, CLI and check command;
a *fresh* checkout, since one authorized lifecycle per checkout (ADR AD-5)
means a reused one refuses every later `wfc run`.
Scope of the Run:: Exactly one new AsciiDoc leaf, in a directory still to be
chosen (<<q1-open>> (b)), strictly inside the authorized scope granted to the
Run, and nothing outside it. No WFC repository change belongs to Q1; defects
it reveals become their own records.
Acceptance:: The Run reaches a terminal state through the installed product
path — `init`, `plan`, `run --yes`, `status`, `report`, archive — with the
Commission and execution-envelope digests re-derived; the consumer repository
carries the one new AsciiDoc leaf inside the authorized scope and nothing
outside it; its own check command is the trusted evidence and passes; the
independent review is real and dispositions itself; archive facts match the
actual outcome; and the record names the candidate version, the
implementation tree digest and the provider models.
Stop rules:: Stop and report, never repair, when the pre-launch baseline probe
refuses (`refused_probe`, exit 23 — consumes the lifecycle, retry needs a
fresh checkout); the check command exceeds the 900-second evidence cap; WFC
refuses the commit over a clean/process filter; or the Run stops
`awaiting_human` — each a *valid* outcome (<<gates,G7>>), never worked around.
Explicitly not acceptance:: a passing fake-provider test, a green consumer CI
run alone, or a change contrived to produce a green Run. *Above all:* Q1 is
presented explicitly and only as a consumer *smoke* qualification — it
demonstrates the installed release-candidate distribution, the actual
authorization boundaries, Worker execution, an independent review, a Trusted
Commit and evidence/archival. It is *not* proof of a successful substantive
bugfix qualification and carries no claim about substantive (fachliche)
bugfix capability.
[[q1-postponed]]
Postponed after the release:: The DMC resumption review's ingress-fidelity
defect, R1: `JSONBackend.read_multi` calls `pd.read_json(dtype="string")`,
which lets pandas infer a numeric column's dtype before string conversion, so
one value's JSON rendering depends on the other values sharing its column
(observed identically on pandas 3.0.2 and 2.3.3), is *postponed to after this
release* (<<md6,MD-6>>, 2026-11-23). It is a follow-up for
`spreadsheet-handling` itself to pick up, not a WFC release item; nothing
here schedules it.

== 7. Gates, risks, and what is not in this release

Release sequence, each step gated by the named gate:

. Push the release commit to `main` (<<ext,ES-3>>); `check` runs — <<g1,G1>>,
  <<g2,G2>>, <<g3,G3>>, <<g4,G4>>, <<g5,G5>>.
. With `check` green, the maintainer gives <<q1,Q1>> the downloaded `check`
  artifact — a rebuild's byte-identity is unverified, so the checked artifact
  itself is used, not a re-derived one — and authorizes the Run — <<g7,G7>> on
  completion.
. Only once Q1 is accepted *and* <<ext,ES-2>>'s pre-tag confirmation of the
  `pypi` environment is in hand does the maintainer push the tag (<<ext,ES-4>>);
  `check` re-runs in tag mode, re-proving everything against the tagged commit.
. `publish-testpypi` runs unattended — <<g6>>.
. The pipeline waits at the `pypi` environment's required-reviewer gate —
  <<g8>>; approval is never inferred from a green job.
. `publish-pypi`, then `release`, run after approval; the maintainer verifies
  the index page and the Release (<<ext,ES-5>>).

*Why Q1 sits before the tag.* Q1 is the least automated, highest-uncertainty
gate; a tag alone spends nothing, but TestPyPI/PyPI on an already-pushed tag
would each spend a version number if Q1 then failed, so pre-tag Q1 costs only
a delayed tag. *The single point the maintainer must confirm:* a pre-tag
build — same static version, `source_commit` null, exactly as any wheel/sdist
install — stands in for "the release candidate," against the alternative cost
of an abandoned tag or a deliberate deletion.

Every gate is release-blocking; there is no advisory class. Each is named as
*gate — owner — verification evidence*.

[[g1]]G1 Preflight clean — Operator and CI:: topology (branch mode or tag
mode), tag-equals-version, notes frozen, README links absolute; `make
release-check` (plus `TAG=v<version>` in tag mode) exit 0, in both <<e2,E2>>
checkout modes.
[[g2]]G2 Required suite green — Operator now, CI once <<md5,MD-5>> is settled feasible:: `python
-m pytest -q` with the two env vars set and zero flake (<<e0,E0>>); host and
profile recorded. A hosted-runner result stays MD-5 evidence, not the binding
gate, until a hosted run proves route R-A green.
[[g3]]G3 Both artifacts contain exactly the allow-list — CI and Operator:: `make
dist-audit` exit 0 on the sdist and on the wheel.
[[g4]]G4 Clean-environment install and CLI identity — CI and Operator:: fresh-venv
wheel install outside the checkout, `wfc --help`, and `wfc --version --json`
reporting the tag's version.
[[g5]]G5 Documentation renders strictly — CI:: `asciidoctor --safe-mode=safe -a
assembled -o /dev/null --failure-level=WARN` over the assembled books: exit 0,
no output.
[[g6]]G6 TestPyPI rehearsal, not a dry run — CI and Operator:: `publish-testpypi`
uploads the real checked artifact; only a real upload proves the Trusted
Publisher OIDC wiring, the index's metadata acceptance and an installable
result, none of which `--dry-run` proves. Cost: the consumed, non-reusable
TestPyPI version — accepted, since it is only a rehearsal index.
[[g7]]G7 Consumer qualification dispositioned — Maintainer:: the Q1 archive and
the review disposition; a truthful stop (<<q1>>) is itself a valid outcome.
[[g8]]G8 Release authorized — Maintainer:: the `pypi` environment's
required-reviewer rule — a repository setting only the maintainer can create,
confirmed before the tag (<<ext,ES-2>>) and exercised at <<ext,ES-5>> —
mechanically enforces the wait; approval is never inferred from a green job.

*Risks.* MD-5's feasibility risk, the flaky-test risk, and the
budget-consumption risk are each already owned above (<<md5,MD-5>>, <<e0,E0>>,
the §5 budget paragraph) and are not restated here.

R-1 Static version drifts from the tag:: `test_bp1_identity.py:41` asserts the
literal `0.1.0b1`. *Mitigation:* G1, plus that literal named in C1's/E1's
checklists.
R-2 Publication is irreversible; a tag or a TestPyPI version can be spent on a failed step:: PyPI
refuses to re-upload a version. *Mitigation:* <<ext,ES-1>> early; Q1 before
tagging keeps the tag cheap to delay; PyPI needs reviewer approval too.
R-3 Q1's environment refuses the Run:: filter config, the 900-second cap, or
one lifecycle per checkout. *Mitigation:* <<ext,ES-6>> measured first; Q1's
stop rules make each a reportable outcome.

*Not in this release.* Published HTML, a Pages repository and a `latest`
alias (deferred, not rejected, per <<md4,MD-4>>); a second repository;
signing or provenance attestation; a Python/OS matrix; ARM64 or a second
qualified profile; conda, Homebrew or a private index; Dependabot
configuration; documentation inside the artifacts; automation beyond the
single workflow; a new workflow program (ADR AD-1); lifecycle rotation
(AD-5).

*Rejected packages.* A separate README-link tool and bake procedure
(unnecessary — the reference needs it only because its URLs are versioned;
WFC's rule is one `release-check` assertion); a test asserting the workflow
matches the documented gates (would parse YAML to restate prose, missing a
gate that passes while proving nothing); a release-automation Commission
(unnecessary — tagging and publishing are <<ext,ES-4>> and <<ext,ES-5>> by
design, and automating the irreversible step removes the human stop).

[[decisions]]
== 8. Decisions the maintainer has taken, and the one still open

[[md1]]MD-1 — Distribution destination (<<c7>>), *decided*:: TestPyPI, PyPI and
a GitHub Release, through a GitHub Actions release pipeline, following the
`spreadsheet-handling` release flow, tools and operation as closely as
possible — each deviation in section 2's table named with a technical reason.
Both PyPI and TestPyPI use OIDC Trusted Publishing; no long-lived token. The
`spreadsheet-handling` SSH secrets (`WFC_READ_DEPLOY_KEY`, `DOCS_DEPLOY_KEY`)
answer needs WFC does not have and are *not* adopted.
[[md2]]MD-2 — The first published version (<<c1>>), *decided*:: `0.1.0b1`, tag
`v0.1.0b1`, no bump. `pyproject.toml` already says `0.1.0b1`; the tag-equals-
version assertion and the test literal at `test_bp1_identity.py:41` are named
facts, not independently re-derived.
[[md3]]MD-3 — Repository visibility, *decided*:: `StefanSchade/workflow-coordinator`
is already public, its history judged clean; no further disclosure review, no
visibility change. This corrects every earlier conditional statement that
assumed otherwise, including the earlier private-repository branch of <<c5>>;
the reference's read-only deploy key answered a need WFC does not have
regardless of visibility.
[[md4]]MD-4 — Version-pinned documentation publishing (<<c5>>), *decided*:: Deferred
for `0.1.0b1`, *not* permanently rejected. GitHub-hosted documentation with
version-bound links suffices now; the `spreadsheet-handling` Pages solution is
a possible model for a later extension, once a second consumer exists.
[[md5]]MD-5 — Must the whole required suite run on a hosted runner? (<<c6>>), *open*:: The
earlier recommendation (a subset on the runner) is *not* accepted. Target: the
whole required suite, on a qualified hosted environment, as a binding gate if
technically possible.

[1] Setup requirements:: `WFC_TEST_INPUTS`/`WFC_TEST_PROFILE` set to a bundle
verified byte-for-byte (`tests/conftest.py:101-121`); `check_host` compares
implementation, Python minor, machine, system, SOABI, seed pip exactly and
glibc as a floor (`wfc_test_inputs.py:162-176`, re-verified); 12 pinned
wheels; an editable WFC install, required by one package-boundary test's
import check; real bubblewrap userns, Git without a clean/process filter,
GNU make, PEP-517 isolation. Four conditional skips fire on the Operator's
reference host (three opt-in live-provider, one internal probe); three
further conditional skip sites exist suite-wide (`test_memory_workbook.py:54`,
`:55`; `test_historical_governance_parse.py:13`) and must be asserted *not* to
fire on the runner — `make` and `git` present, `governance/self-development`
checked out — not silently relied upon.
[2] Reproducible on a GitHub runner?:: Not yet proven, but plausible: route
R-A is `ubuntu-24.04` (pinned label) plus `setup-python` pinned to the exact
patch `3.13.5`, a `sudo sysctl` relaxing unprivileged-userns for bwrap, a
step-scoped neutralization of the runner's git-lfs filter (not WFC's own
filter-refusal test), the normal `fetch`+`exec` flow, then the unmodified
suite.
[3] A second host profile's closure review?:: Re-verified against the
profile and `wfc_test_inputs.py`: the 12 wheel pins are checked only by
filename, size, SHA-256, metadata and wheel *tag* (manylinux/`py3-none`/
`cp313` plus a glibc floor) — none depends on the CPython build, so the pins
would not change. The build-dependent part is `seed_pip_version`
(`ensurepip.version()`), which Debian patches to a bundled pip distinct from
upstream; other host fields are generic. So a second profile's review reduces
to a byte-equality diff of `wheels` plus a review of the build-specific
fields in `host` — never a full dependency re-audit.
[4] What cannot run at all?:: Nothing by design — the reference host's four
skips are opt-in or internal, and [1]'s three further sites are host- and
checkout-dependent conditions to verify, never silently widened or assumed.

*Still unknown, needing a hosted run:* (a) the runner's actual seed pip version
for CPython 3.13.5 on `ubuntu-24.04`; (b) bwrap userns after the `sysctl`; (c)
whether the runner's Git carries a git-lfs filter and the neutralization
suffices; (d) that `fetch` reaches `files.pythonhosted.org`; (e) whether a
second profile is wanted if the pip version differs. *Cheapest evidence:* the
first hosted run of <<e3,E3>>'s workflow on `main` (<<ext,ES-3>>) answers
(a)–(d). *Escalation rule:* a real, reproducible blocker is documented with the
failing log and escalated — route R-B (digest-pinned container), a documented
partial gate, or otherwise — to the maintainer; MD-5 is not loosened and
<<g2,G2>> not narrowed without that decision.
