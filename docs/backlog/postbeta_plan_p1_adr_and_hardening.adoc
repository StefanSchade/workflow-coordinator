. *The brief is a dated input, not a baseline.* Statements in it are reconciled
  in <<reconciliation>> and labelled `current`, `narrowed`, `contradicted` or
  `obsolete`. No brief statement is rewritten, and the brief file is untouched.

  importable in the planning agent's sandbox (`No module named pytest`), so
  every acceptance criterion below is expressed as a command plus its expected
  result for a later Coordinator-trusted run, never as an agent-observed pass.
  `asciidoctor` is available and was used to check this document's own
  rendering. The staged input digest was verified with `sha256sum`.

[[ad5]]
=== AD-5 The lifecycle model: one Run per checkout

Question:: Is "one `wfc run` per canonical checkout, forever" part of the
product contract, or does controlled rotation after a terminal, archived,
Evidence-verified lifecycle belong to a later lifecycle revision?
Options:: (a) contract: one Run per checkout, documented, with
clone-or-worktree as the supported pattern; (b) add controlled rotation now;
(c) defer rotation to a named later revision while documenting (a) as the Beta
contract.
Evidence:: `frontdoor/lifecycle.py:741-752` refuses `refused_active_lifecycle`
(exit 26, `:125`) on any `authorized` journal record, regardless of a terminal
classification and verified archive -- "the classification name says 'active'
but the check is 'present'", in the FTR's own words.
`FTR-WFC-LIFECYCLE-ROTATION:6` requires this ADR to decide it. Recurrence: once
(BP7 Proof Run 2). The BP6c review relies on one-Run-per-checkout for
unambiguous archive lookup, so rotation is a real design task, not a flag.
Consequences:: (b) requires the archive lookup to become Run-scoped, which the
BP6c review currently relies on *not* being, so it is larger than it looks.
(a)/(c) keep the documented workaround, which every post-Beta Commission above
already assumes (each runs in a fresh worktree).
Recommendation:: *(c)*. State (a) as the `0.1.0b1` contract and record the
FTR's five design constraints as the entry conditions for a later revision.
Who decides:: The maintainer.
Blocks:: `FTR-WFC-LIFECYCLE-ROTATION`.

[[ad6]]
=== AD-6 Program entry at a phase other than `implement`

Question:: May a Commission enter a selected program at a phase other than
`implement`, and if so, how is the entry constrained?
Options:: (a) no: `implement`-only remains the product contract; (b) yes, via
an explicit request field constrained to phases the selected program declares
*and* that can reach a terminal route; (c) yes, derived from the request's
shape.
Evidence:: `commissioning.py:367` hard-codes `"initial_phase": "implement"`.
The engine permits other entries and two archived Beta Runs used `broad_review`
as the entry, both 1 Hop, both completed -- but both through the Harness
deleted by `41f0d52`. `FTR-WFC-FRONT-DOOR-PHASE-ENTRY-CONTINUATION` (`:6-8`,
`:84-99`) records the gap and proposes a validated `initial_phase` Intent field
as a starting point only, admitting it "only under a separately authorized
Commission". The adoption state is on the `_open.adoc` card (`:567-571`):
neither a free initial-phase field nor the derived broad-review entry is
adopted, and entry/assurance decisions and successor tests precede
implementation.
Consequences:: Under (a) the recorded `Next action::` of
`BUG-WFC-PYTEST-TEMP-RESOURCE-EXHAUSTION` cannot be performed by any
Commission, and neither can an independent re-review of an existing candidate;
the maintainer would have to do both outside WFC, which weakens the
self-development claim the product rests on. (c) is the "derived broad-review
entry" the `_open.adoc` card declines to adopt. (b) is bounded: two negative
tests (undeclared phase; unreachable phase)
make it safe, and `verify_commission` already re-admits the rendered bundle.
Recommendation:: *(b)*, with both negative constraints mandatory. This is the
one capability the post-Beta plan needs and currently lacks.
Who decides:: The maintainer.
Blocks:: H4; RW1; any later review-only Commission.
