== Observed behavior

Every one of the five `task-check` trusted evidence observations in that Run
(Hops H002/H004/H006/H008/H010) persisted an identical exit classification
(`status="fail"`, `exit_code=1`), identical `stdout_byte_count=3119`, an
empty `stderr`, and `stdout_body_omitted=true` with `artifact_ref=null` --
but five different `stdout_sha256` digests. The digests prove the five runs'
actual output differed; nothing durable records *how*. A correction Hop
receiving only this record cannot localize the failure without re-running
`task-check` itself.

This is implemented exactly as designed: `evidence.py:188-233`
(`_stream_facts`/`_observation`) reduces any captured `stdout`/`stderr`
bytes to `(byte_count, sha256, body_omitted)` and hard-codes
`artifact_ref=None` (`evidence.py:213`); `ProductionEvidenceRunner.observe`'s
`"fail"` branch (`evidence.py:316-326`) has the real captured bytes in hand
at the moment it calls `_observation`, and discards them immediately
afterward. `model.py:757,771-776` carry the corresponding `Observation`
fields; `persistence.py:54,76` and `serialization.py:1680,1706` project and
parse them unchanged. None of this is a defect in that code -- it is doing
exactly what WFC-EVID-08 requires.

== Why this is a diagnostics gap, not an A2-contract defect

WFC-EVID-08 (originating in the non-authoritative
`docs/cold_storage/sources/pre-0.1.0b1/core-incubator/FTR-AGENT-WORKFLOW-COORDINATOR-P5.adoc:771-780`,
restated as current fact in `docs/wfc_operator_manual.adoc:785-803`, §16)
requires: "No stdout or stderr body shall be durable A2 evidence... the
durable summary shall be generated only from Coordinator outcome facts and
shall not copy command output," uniformly across pass/fail/error. §16 itself
already names the consequence as "a known limitation of the current evidence
persistence, not something redesigned here" -- i.e. this record documents
exactly the gap the operator manual already flags as unaddressed, now with
concrete Run evidence of its cost (a 10-Hop budget exhausted partly on
correction cycles against evidence nobody could read).

This record does not propose weakening, removing, or reinterpreting
WFC-EVID-08, the A2 trusted-evidence/untrusted-telemetry boundary
(`DEC-WFC-006`), or any existing digest/body-omission field. The desired
correction is a second, explicitly untrusted channel alongside the
unchanged trusted `Observation`, not a change to it.

== Desired direction (commissioned)

A bounded, explicitly untrusted diagnostic capture, populated only when a
trusted A2 evidence observation's status is not `"pass"` (i.e. the `"fail"`
branch, `evidence.py:316-326`, where real bytes already exist in-process):
at most a 16 KiB tail of each of `stdout`/`stderr`, with truncation
metadata (at minimum, whether truncation occurred and the original byte
count -- the existing `stdout_byte_count`/`stderr_byte_count` fields already
carry the latter, so this likely does not need to be repeated). The existing
trusted `stdout_byte_count`/`stdout_sha256`/`stdout_body_omitted` fields (and
their `stderr` counterparts) must remain byte-for-byte unchanged in value and
meaning; the new capture must not be written into `Observation.artifact_ref`
or any other existing A2-contract field, and must be identifiable by a
reviewer as diagnostic/untrusted rather than trusted A2 evidence. Never
capture anything on a `"pass"` status. Where the diagnostic content is
stored, and exactly how it is referenced from the trusted record without
becoming part of it, is an implementation decision for the commissioned
WorkItem, not fixed by this record.

Handling expectations the implementation must still satisfy: the captured
tail can contain paths or environment-dependent detail, so it must be
treated with the same sensitivity as other untrusted telemetry, never copied
into a trusted record, and never widened into a general log. Extending the
Git-backed evidence archive's own allow-list (`scripts/archive_run.py`, in
the separate `workflow-coordinator-run-evidence` repository) to recognize
and retain this new, small artifact type is a necessary follow-up but is
explicitly out of this WorkItem's scope -- it lives in a different
repository that no self-development Run operates on.
