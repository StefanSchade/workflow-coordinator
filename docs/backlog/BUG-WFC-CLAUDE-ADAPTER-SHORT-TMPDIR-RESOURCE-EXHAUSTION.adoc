== What happened

`/tmp`, a `tmpfs`, reached **1,048,576 / 1,048,576 inodes (100%)** during
Hop H002 of `WI-WFC-EVIDENCE-FAILURE-DIAGNOSTICS-001`, almost entirely
(530,457 files) under three `pytest-of-stefan` session directories
(`pytest-10`, `pytest-11`, and their `pytest-current` symlink target), each
around 265,000 files. Every `Bash` tool call in the *interactive*
maintainer-operator session (separate from the Run itself) began failing
with `ENOSPC: no space left on device` for several minutes. The Run's own
trusted `task-check` evidence was unaffected (it executes in the
Harness-built `dev-env`, not under the agent's `TMPDIR`), and the Run
completed normally at Hop 2 with no anomaly recorded. The `pytest-of-stefan`
material was removed afterward as a one-off operational cleanup, after
confirming no process still referenced it.

The independent reviewer's own broad-review artifact for the same Hop
independently reports the same symptom from inside the Run itself: denied
`pypi.org:443` egress for real venv installs, and "exhaustion of the
sandbox temporary filesystem; repeat runs could not complete once that
filesystem filled, and redirecting or clearing it was not permitted" --
correctly classified there as an agent-local environmental limitation, not
a candidate defect
(`docs/warm_storage/concepts/workflow_coordinator_evidence_failure_diagnostics_2026-11-07_broad_review.adoc`).

== Why it happened

The Claude adapter gives the Claude CLI subprocess a short, invocation-
scoped `TMPDIR` rooted at the ambient system `/tmp`
(`src/workflow_coordinator/claude_adapter.py:39-47`,
`_SHORT_TMP_ROOT = Path("/tmp")`; `_short_subprocess_tmp_dir()` at
`:110-116`; applied at `:149,166`). That exists because Claude Code derives
its Bash-tool sandbox's `AF_UNIX` IPC-bridge socket path from `TMPDIR`, and
`sockaddr_un.sun_path` is capped at 108 bytes; a long, human-readable,
Attempt-scoped `TMPDIR` reliably breaks sandbox initialization (fixed by
commit `4776fd0`).

Bash-tool commands the Claude CLI launches during a Hop inherit that same
short, `/tmp`-rooted `TMPDIR` unless a command sets its own. During H002,
the agent's own exploratory validation ran `pytest` via the Bash tool;
`pytest`'s temporary-directory machinery honors inherited `TMPDIR`, so its
session/fixture material -- including fixtures in
`tests/unit/test_wfc_op.py` that materialize real exported repository trees
and `pip`-installed virtual environments -- landed on the small host
`/tmp` `tmpfs` instead of the Attempt's own large-filesystem scratch
(`$HOME/wfc-scratch/<attempt>`, established by FD-08,
`WI-WFC-FD08-ATTEMPT-SCRATCH-001`). FD-08 moved the *Harness*'s own
`TMPDIR`/`TMP`/`TEMP` away from `/tmp` for an earlier, distinct incident
(`docs/cold_storage/backlog/pre-0.1.0b1/infrastructure-and-incidents/2026-10-28_tmpfs_exhaustion.adoc`);
the socket-path fix (`4776fd0`), solving a narrower, locally correct
problem, reintroduced a `/tmp` dependency one level deeper, inside the
Claude adapter's own subprocess environment, without revisiting that.

`FTR-WFC-SELF-DEVELOPMENT-EXECUTION-INTEGRATION-DEBT.adoc` already named
this exact tension as an open, unconfirmed evaluation question ("Should a
provider adapter's own short-lived, short-path temp-directory need be
requested from a Harness-owned allocator... rather than each adapter
hardcoding `/tmp` independently?"); this is the first confirmed incident
realizing it.

`BUG-WFC-PYTEST-TEMP-RESOURCE-EXHAUSTION` documents a prior `/tmp`
exhaustion with the same symptom shape (607,722/1,048,576 inodes, also
concentrated in `pytest-of-stefan`) but explicitly declines to attribute a
cause. This record is narrower: it identifies one concrete, sufficient
causal path -- the Claude adapter's short `TMPDIR` inherited by
agent-launched test processes -- without claiming it is the only
contributor to that record's own, still-open question. The two are kept
separate rather than merged.

== Required product behavior

WFC must be able to give a provider subprocess (today, the Claude CLI) a
short temporary path for socket/IPC purposes without that short path also
becoming the destination for unrelated, potentially large volumes of
temporary material the subprocess or its own child processes (such as an
agent-launched `pytest` run) may create. The two needs -- a short *path*
(bytes, for `sun_path`) and a large-capacity, Attempt-isolated *filesystem*
(for bulk material) -- are presently conflated onto one `TMPDIR` value and
should not be. The functional requirement is short socket paths; today's
`_SHORT_TMP_ROOT = Path("/tmp")` is one implementation of that, not a
constraint a correction must preserve as-is.

**Portability:** a correction should assume as little as possible about the
host environment, and in particular should not need, as the ordinary case,
a privileged or administrative host change (a system-wide `/tmp` resize, an
administrator-installed symlink, a mount performed outside WFC's own
process tree). It needs to work, without such a precondition, at minimum on
Ubuntu under WSL and in restrictive corporate environments where the
operator cannot assume elevated host privileges.

== Candidate directions (open hypotheses, nothing selected)

* Point `pytest` fixture/session material at the existing Attempt scratch
  root (FD-08) via `PYTEST_DEBUG_TEMPROOT`, possibly reinforced by explicit
  worker-prompt instruction not to rely on ambient `/tmp` for exploratory
  test runs. **Follow-up (see below): live-qualified and now the preferred
  direction, combined with a scoped `sandbox.filesystem.allowRead`/
  `allowWrite` grant** -- the propagation question is answered (yes), and
  so is the further sandbox-reachability question that answering it
  exposed. Still only a `pytest`-fixture-specific measure; see "Residual
  scope not covered" below.
* An explicit `--basetemp` convention, including the known risks of nested
  or parallel `pytest` invocations sharing or colliding over one fixed
  `--basetemp` path. Not re-examined this round; superseded in priority by
  the `PYTEST_DEBUG_TEMPROOT` direction above, not ruled out.
* A short symlink (or similar short indirection) under `/tmp` pointing at
  the real Attempt scratch root. **Second follow-up (2026-11-08, see
  below): live-qualified and confirmed to work** -- the Claude sandbox's
  own socket-path resolution does *not* re-canonicalize `TMPDIR` before
  constructing IPC paths, so the 108-byte limit is not re-violated, and
  (combined with the same scoped `allowRead`/`allowWrite` grant as the
  first follow-up) ordinary tools that only consult `$TMPDIR` itself --
  not only `pytest` via `PYTEST_DEBUG_TEMPROOT` -- were shown to land their
  output in the real external scratch. Broader in principle than the
  `PYTEST_DEBUG_TEMPROOT` direction above; see "Residual scope not
  covered" below for what still limits it.
* A bind mount inside a WFC-owned bubblewrap namespace, where available --
  not to be assumed available, since an unprivileged mount namespace is
  itself a host capability some environments may not grant. Not
  re-examined; superseded in priority by the symlink direction above once
  it was confirmed to work, not ruled out.

Each trades off differently against the portability requirement above. The
first two directions are now each demonstrated (follow-ups below) to
satisfy it for their respective scope (`pytest` fixtures specifically;
anything that consults `$TMPDIR` directly, more generally) -- see "Residual
scope not covered" for what remains uncovered by either.

== Follow-up live qualification (2026-11-07, maintainer-run)

Two rounds of direct live qualification against the real, unmodified
`ClaudeCliAdapter.execute()` (Claude CLI `2.1.270`), each run outside any
WFC Run/Commission/Runtime, against a disposable repository outside every
WFC checkout -- methodologically the same kind of direct maintainer-run
qualification already used in
link:../technical_model/claude_code_adapter_architecture.adoc[the Claude
Code adapter architecture document] §7. No production source was changed;
only the settings payload `ClaudeCliAdapter._settings()` normally generates
was temporarily substituted, for the experiment only, in a throwaway driver
script.

**Round 1 -- does `PYTEST_DEBUG_TEMPROOT` reach the agent-launched `pytest`,
under the closed profile exactly as shipped?** Yes. Set via the existing
`WFC_CLAUDE_EXTRA_ENV_NAMES` mechanism (no adapter change needed; `TMPDIR`
itself remains reserved and short, per `claude_adapter.py:68-70`), the
variable reached the Bash-tool-launched `pytest` process every time. With
the redirect target left under `$HOME` (the unmodified closed profile,
`denyRead: ["~/"]`, no corresponding `allowRead`), `pytest` itself failed --
`rootdir.mkdir(mode=0o700, exist_ok=True)` (`_pytest/tmpdir.py`, no
`parents=True`) raised `FileNotFoundError`, because the redirected path's
*parent* was invisible inside the sandboxed child's own filesystem view,
even though it demonstrably existed on the host. A control run with the
same mechanism, only pointed at a path inside the repository's own working
tree (already sandbox-visible), passed end to end (`1 passed`), isolating
the cause to sandbox filesystem-visibility specifically, not to the
propagation or redirection mechanism.

**Round 2 -- can a scoped `sandbox.filesystem.allowRead`/`allowWrite` grant
fix exactly that, without widening anything else?** The installed CLI binary
(`2.1.270`) documents, in its own embedded help/error strings (not public
docs), independent `sandbox.filesystem.allowRead`/`denyRead`/`allowWrite`/
`denyWrite` keys ("Paths allowed for writing" / "Paths denied for writing
(takes precedence over allowWrite)"), and treats
`permissions.blockReadsOutsideWorkingDirectories` as a separate, prior gate
whose own documented remedy is exactly `sandbox.filesystem.allowRead`
("Sandboxed commands lose your home directory... until you re-open paths
with sandbox.filesystem.allowRead"). Two live tests used a settings payload
identical to the shipped one except `allowRead` and `allowWrite` each also
named exactly one dedicated, explicitly-untrusted scratch subpath (not
`wfc-scratch` itself, not any Attempt or Evidence directory) -- `denyRead:
["~/"]`, `sandbox.enabled`, `failIfUnavailable`, `allowUnsandboxedCommands:
false`, `network.allowedDomains: []`, and
`permissions.blockReadsOutsideWorkingDirectories: true` all left unchanged:

* *Positive:* `PYTEST_DEBUG_TEMPROOT` pointed at the one allow-listed
  subpath. Fixture material was verifiably created there (confirmed by
  direct host-side filesystem inspection after the run, not only the
  worker's own report), with no material appearing under host `/tmp`.
* *Negative control:* the same profile, instructed to read the allow-listed
  path's own parent directory and an unrelated home-directory file, was
  blocked outright by `permissions.blockReadsOutsideWorkingDirectories`
  before any sandboxed execution of the command, producing no output at
  all -- confirmed by host-side inspection of the (empty) redirected-output
  files, which also caught and corrected an inaccurate self-report from an
  earlier, not-independently-verified sub-run that had claimed the read
  succeeded. The rest of the home directory stayed unreadable and the
  sandbox stayed enabled and enforcing throughout both rounds (the positive
  case could not have passed otherwise: a failed sandbox init fails closed
  under `failIfUnavailable: true`).

**Conclusion of the follow-up:** a scoped `sandbox.filesystem.allowRead` +
`allowWrite` grant, limited to one dedicated untrusted scratch subpath, combined
with `PYTEST_DEBUG_TEMPROOT` via the existing `WFC_CLAUDE_EXTRA_ENV_NAMES`
mechanism, was at this point the maintainer's preferred correction
direction -- demonstrated to coexist with the existing short-`TMPDIR` fix,
and to leave `denyRead`, `blockReadsOutsideWorkingDirectories`, and the
sandbox's own enablement otherwise intact. The symlink direction was
re-examined in a second follow-up below and also confirmed working, more
generally; the bubblewrap-mount direction was not re-examined and is not
ruled out.

**Residual scope not covered by this first follow-up alone:** the adapter's
existing short, `/tmp`-rooted `TMPDIR`/`TMP`/`TEMP` (`claude_adapter.py:149,
166`) is untouched by the `PYTEST_DEBUG_TEMPROOT` direction and continues to
be inherited by `pip`, Python's own `tempfile` module, and any other child
process that does not specifically consult `PYTEST_DEBUG_TEMPROOT` --
confirmed by reading `_pytest/tmpdir.py` itself, which uses that variable
only for its own `tmp_path`/`tmp_path_factory` basetemp, never for
`tempfile.gettempdir()`. The second follow-up below addresses this general
case directly, by redirecting `TMPDIR` itself rather than a pytest-specific
variable; see its own "what remains uncovered" note.

== Second follow-up: short symlink to external scratch (2026-11-08,
maintainer-run)

Same direct-live-qualification methodology as the first follow-up (real,
unmodified `ClaudeCliAdapter.execute()`, Claude CLI `2.1.270`, disposable
repository, no production source changed; only `_settings()` and
`_short_subprocess_tmp_dir()` temporarily substituted in a throwaway driver
script for the experiment). Goal: redirect `TMPDIR` itself -- not a
pytest-specific variable -- to the external scratch, so ordinary tools
(`pip`, `tempfile`, anything else that only consults `$TMPDIR`) benefit too,
not only `pytest`.

**Mechanism confirmed working:** a short symlink under `/tmp` (e.g.
`/tmp/wfc-sym-<token>`) whose target is a dedicated untrusted subpath of the
external scratch, combined with the same scoped `sandbox.filesystem.
allowRead`/`allowWrite` grant (naming the real target, not the symlink) used
in the first follow-up. Host-side inspection after the run found Claude's
*own* internal session artifacts -- `srt-mux-<pid>-0.sock`, `cc-socks/`,
`bash-edit-diff/` -- physically created inside the real external target
through the symlink, with short filenames throughout. This directly answers
the open question the original "Candidate directions" entry raised: Claude's
own socket-path construction uses the given `TMPDIR` string as-is and relies
on the kernel to follow the symlink transparently at `bind()` time; it does
not canonicalize/resolve the path first, so the 108-byte `sun_path` limit is
not re-violated even though the real resolved path is well over 150 bytes.

**False alarm, retracted:** an initial round of agent-launched `touch`/
`mkdir`/`python3` commands against `$TMPDIR` were denied with "no approval
surface," inconsistently across repeated rounds, including -- in later
narrowing-down rounds -- even under the adapter's completely default,
unmodified `TMPDIR` handling (no symlink, no monkeypatch of any kind). A
dedicated control round refuted the hypotheses this had initially suggested
(a `TMPDIR`-write-specific guard, or a denial that cascades through the
rest of a session): the very first command of that control round, a plain
repository-local write never touching `$TMPDIR` at all, was *also* denied.
**No `TMPDIR`-specific approval layer and no session-wide cascade exist; both
are retracted, not merely downgraded to an open caveat.**

The actual, narrower variable isolated: every probe command across this
investigation happened to use a `; echo "EXIT=$?"` exit-code-capture idiom
for diagnostic purposes. Removing it (no `$?`, no semicolon-chaining) let
`touch`, `mkdir`, and `python3 --version` against `$TMPDIR` succeed
immediately, repeatably, under both the default adapter and the
symlink-plus-scoped-grant configuration -- confirmed by host-side
inspection of files actually landing in the real external target, not only
the worker's own report. This is reported as an observation about the
concrete Bash-command authorization behavior encountered in *these specific
test sessions*, under the Claude CLI version and conditions in use at the
time -- not a demonstrated general rule that `;` or `$?` are always denied,
and no claim is made about the underlying mechanism or whether it
reproduces under other conditions.

**Central positive result:** with that test-harness artifact removed,
both Claude's own internal Unix-domain sockets (see above) and
agent-launched `touch`/`mkdir` commands were confirmed working through the
short symlink, writing verifiably into the real external scratch target --
the symlink direction itself is demonstrated working, cleanly, with nothing
outstanding against it from this investigation.

**A separate, narrower, unrelated observation:** a `python3 -c "<multi-line
script that performs actual file I/O, e.g. tempfile creation>"` invocation
was still denied even after removing `$?` and semicolon-chaining, while
`python3 --version` (no inline code execution) succeeded every time. This
looks like its own Bash-command-content heuristic -- plausibly treating
inline-interpreted code that performs file writes with more caution than
simple file utilities or no-execution flags -- distinct from the `$?`-idiom
artifact above and from everything else this BUG is about. **It does not
refute or block the symlink direction**: it was never shown to depend on
`TMPDIR`, the symlink, or the scoped sandbox grant, and the same
`python3 -c` shape was not specifically re-tested outside the symlink
configuration to compare. Not characterized further here (would need its
own bounded investigation); noted only so a future correction attempt is
not surprised by it and does not mis-attribute it to `TMPDIR`/sandbox-grant
mechanics.

**What a later correction still needs to determine, for either direction:**
a concrete way to provision the one dedicated untrusted scratch subpath
both follow-ups grant access to, owned by WFC rather than hardcoded to the
FD-08 self-development Attempt-scratch path (`$HOME/wfc-scratch/<attempt>`)
specifically -- so that a future non-self-development WFC use of this same
adapter has an equivalent grantable path, not only this particular
development-time environment. Also still open: the symlink's own lifecycle
(`shutil.rmtree(tmp_dir, ignore_errors=True)` in `claude_adapter.py`'s
`finally` block is a confirmed no-op on a symlink -- neither the symlink nor
its real target get removed -- so the short symlink itself would accumulate
under `/tmp` across invocations unless a correction adds its own cleanup;
the real scratch target is not at risk from this specific gap either way).
Neither is yet selected; no implementation follows from this record.
