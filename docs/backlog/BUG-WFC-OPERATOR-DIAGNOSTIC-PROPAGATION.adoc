== What this is not

This record does not characterize the Runtime/Hop/Evidence authority model,
the fail-closed `reconcile_required` outcome itself, or `DEC-WFC-013`'s
"salvage preserves work, not authority" principle as defective. A failed
provider invocation correctly produces an uncertain Hop and a Run that stops
for explicit maintainer resume; that mechanism is sound and is not touched
by this record. This record is narrowly about what diagnostic information
survives into durable, inspectable operator state once that stop happens.

This record does not establish, and does not authorize anyone to assert, a
provider-side root cause for either cited incident. The actual cause of the
Codex CLI `exit 1` / no-candidate failures below is unknown and out of
scope; only the *propagation gap* that prevented investigating it is in
scope.

== Observed current behavior

Two real Run Attempts ended `reconcile_required` after an agent CLI
invocation returned a nonzero exit code with no structured candidate
result, and in both cases the maintainer could not determine more than
"some invocation failed" from durable local state:

* `wfc-p35-requirements-archaeology-reassessment-001-2026-10-26-01`
  (`workflow-coordinator-run-evidence/archive/unclassified/...`), invocation
  `INV-9e55b2d0931943c69e84fa710a24e091`, `returncode=1`, `timed_out=false`,
  `candidate_result_present=false`.
* `wfc-front-door-contract-design-001-20261028-01`
  (`workflow-coordinator-run-evidence/archive/unclassified/...`), Hop H003,
  invocation `INV-4e0c0e5c4d3343eb9b519df54eeea7c4`, same shape.

Direct inspection of both archived `run/operator-summary.json` files and
their matching `run/checkouts/<uuid>/execution-evidence.json` files shows
exactly why: the per-Hop legacy evidence row does carry `returncode` and
`timed_out`, but every other diagnostic fact the transport layer already
captured is absent, and the top-level `operator-summary.json["provider"]`
field is simply `null` in both incidents.

Three concrete code-level facts, confirmed by direct inspection, explain
this:

. `src/workflow_coordinator/codex_adapter.py`'s `CodexCliAdapter.execute()`
  already captures bounded `stdout`/`stderr` (`_bounded()`, 16,384-character
  tail) and a short adapter-owned `diagnostics` tuple (e.g. `"Codex CLI
  exited 1"`) onto `AgentExecutionOutcome`
  (`src/workflow_coordinator/codex_adapter.py:404-408`). Capture is not the
  gap.
. `src/workflow_coordinator/operator.py` builds the only three
  operator-visible/persisted records of a Hop's provider facts --
  `_legacy_execution_evidence()` (`operator.py:629-662`), `_summary()`'s
  `provider` dict (`operator.py:905-908`), and
  `_best_effort_failure_summary()`'s `provider` dict
  (`operator.py:947-950`) -- and each pulls only `outcome.returncode`,
  `outcome.timed_out`, and `outcome.candidate_result is not None`.
  `outcome.stdout`, `outcome.stderr`, and `outcome.diagnostics` are read
  nowhere in `operator.py`; they are discarded at exactly these three
  sites. (This is the same gap FD-04 §8.2 already names from static
  inspection; this record adds the two live-incident confirmations and the
  two further wiring defects below, found while tracing why
  `operator-summary.json["provider"]` was `null` rather than merely
  thin.)
. Two further, more specific wiring defects compound the above for exactly
  the documented incident shape (a `reconcile_required` stop reached by
  ordinary return from `run_serial_hops()`, not by an exception):
  .. `operator.py`'s real CLI entry point calls
     `_summary(repository, final_run, None, ...)` with a hardcoded `None`
     third argument (`operator.py:1706`) on every normal-completion path --
     including `reconcile_required` -- even though the real captured
     `AgentExecutionOutcome` for the failing invocation is already available
     in-memory as `latest_outcome` (via the `remember_progress` callback,
     `operator.py:1679-1683`). This is why `provider` is unconditionally
     `null` in both archived incidents even though the legacy per-Hop
     evidence row already has `returncode`/`timed_out`.
  .. A semantic structured-result validation failure
     (`ExecutionResultValidationError`, raised by
     `src/workflow_coordinator/vertical.py` when the candidate result is
     absent or fails schema validation) carries its specific validation
     message as the exception's own `str()`, but
     `src/workflow_coordinator/slice4.py`'s catch site
     (`except ExecutionResultValidationError as error: return
     recover_uncertain(error.outcome)`, `slice4.py:386`) keeps only
     `error.outcome` and discards `str(error)`. `RealHopRun`
     (`slice4.py:56-63`) has no field to carry it. This means requirement
     (2) below -- distinguishing "no candidate" from "candidate present but
     invalid" -- is not determinable from `outcome` alone for the
     structured-result-validation case, independent of the stdout/stderr
     propagation gap.

== Why it is undesirable

A maintainer inspecting a `reconcile_required` Run after the terminal
session that launched it has ended has no durable way to tell, from local
Run state alone:

* which known execution-failure class occurred (nonzero exit vs. timeout
  vs. missing candidate vs. structured-result validation error vs. some
  other local pre-launch failure already surfaced as `operator_error`);
* the actual exit code (present in the legacy evidence row, but not in the
  top-level summary `provider` field that both incidents' operators
  actually consulted first); or
* any bounded diagnostic text the provider process itself already emitted
  on `stdout`/`stderr`, which the adapter already captured and bounded but
  which never reaches any durable record.

This is exactly the gap recorded as FD-04 in
`workflow_coordinator_front_door_priority_and_profile_commission_boundary_plan_2026-10-26.adoc`
§§7-8, which explicitly defers the design to "a separately authorized
design Commission" (§8.2) and explicitly declines to authorize any
`codex_adapter.py`/`operator.py` change itself (§9). This record is that
authorization, bounded to propagation only.

== Desired correction (commissioned below, not separately re-litigated here)

Propagate the already-captured, already-bounded transport diagnostics from
`AgentExecutionOutcome` (and the discarded structured-result validation
message) into durable, operator-visible, correctly-correlated records,
while preserving the trusted-evidence/untrusted-telemetry boundary
(`DEC-WFC-006`) and keeping any newly-exposed raw provider output out of the
normal Git Evidence archive's fixed copy allow-list
(`workflow-coordinator-run-evidence/scripts/archive_run.py`'s
`CHECKOUT_ALLOW`/`RUN_ROOT_ALLOW`, which already does not, and must
continue to not, name any new diagnostic artifact this correction adds).
No automatic retry, recovery, or same-Run resume; no provider-side
root-cause classification; no new adapter framework.

== Non-scope

This record does not authorize:

* any claim about why either cited provider invocation actually failed;
* any change to `src/workflow_coordinator/codex_adapter.py` (the capture
  and bounding mechanism there is already correct and sufficient; see
  Evidence/provenance below) or to its argv/sandbox/provider-selection
  behavior;
* any change to `src/workflow_coordinator/vertical.py`, `reducer.py`,
  `model.py`, or any Run/Hop/Finding/Evidence trust/authority semantics;
* any automatic retry, recovery, or successor-Run mechanism (`DEC-WFC-013`
  and `DEC-WFC-014` govern those unchanged);
* any change to `workflow-coordinator-run-evidence` (including its archive
  allow-lists) or to any Front Door material;
* a generalized provider-error taxonomy beyond the known local execution
  outcomes the adapter already distinguishes (`returncode`, `timed_out`,
  `candidate_result_present`, structured-result validation failure);
* a WorkItem, profile, policy, or WFC Run of any kind; or
* a push.
