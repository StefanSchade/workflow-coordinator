== Code navigation and debugging

The package is flat under link:../../src/workflow_coordinator/[src/workflow_coordinator/].
Start with `model.py` for values, `serialization.py` and
`structured_result_schema.py` for input/result validation, and `reducer.py` for
state and route decisions. `prompt.py` assembles dispatch context. `operator.py`
handles admission and serial execution; `vertical.py:run_one_hop` connects
preflight, dispatch, validation, Git observation, evidence and reduction.
`adapter.py` defines the provider port, with `codex_adapter.py` and
`claude_adapter.py` implementing it. `git_facts.py`, `evidence.py` and
`persistence.py` handle observations, evidence and durable state;
`commissioning.py` renders and checks Commission inputs. `git_facts.py`
also defines `bounded_path_commit`, a narrower sibling of `trusted_commit`
for Coordinator-owned callers acting outside a Hop (`frontdoor.init`,
`frontdoor.archive`): it only ever commits exact, newly created leaf files,
refusing modification or deletion of an already-tracked path and any
directory-shaped intent. `frontdoor/init.py` and `frontdoor/plan.py`
implement the installed, consumer-facing `wfc init`/`wfc plan` commands on
top of the BP2b compiler (`frontdoor/request.py`, `frontdoor/config.py`,
`commissioning.compile_commission`); `wfc plan` is deliberately read-only,
calling `compile_commission`/`resolve_execution` directly rather than
`frontdoor/verify.py`'s admission path. `frontdoor/archive.py` implements
the installed `wfc archive`, ported from the Evidence repository's own
`scripts/archive_run.py`/`scripts/wfc-archive-run` (allow-lists, source
isolation, digest-verified copy and fact extraction unchanged; staging,
atomic placement and idempotent retry are new); it commits through
`bounded_path_commit`, never a raw `git add`/`git commit`. `frontdoor/lifecycle.py`
implements the installed `wfc run`/`resume`/`status` BP4a lifecycle controller,
a thin driver above the unchanged engine: it authorizes one Commission plus
execution-envelope digest pair, runs the one-shot baseline probe, commits the
Commission through `bounded_path_commit`, launches the real engine via the
installed `wfc` script (never `operator.py` directly, and never a changed
engine), and classifies the result from persisted engine facts only
(`run.json`, `checkpoint.json`, `operator-summary.json`,
`checkout-association.json`, `operator-plan.json`), never from process exit
code or summary-file existence alone. `frontdoor/journal.py` provides the
durable, append-only, fsync-framed lifecycle journal under
`$XDG_STATE_HOME/wfc` and the per-checkout ownership `flock` (acquired before
any lifecycle effect, inherited by the launched engine via `pass_fds`); see
link:../warm_storage/beta1-productization/wfc_beta1_bp4a_lifecycle_controller_001_limitations.adoc[the
BP4a limitations record] for what the lock does and does not prove.
`git_facts.py` also defines `preserve_candidate` (BP4b): an additive capture
seam used only by `frontdoor/preservation.py`, which glues it to BP4a's
`classified` journal record and ownership lock and is itself called by
`frontdoor/lifecycle.py`'s `run`/`resume` entry points right after
classification (never by `status`, which only reads the `ext.preservation.*`
facts it wrote). It builds the candidate tree from a private temporary
index -- the registered index is never read as truth or modified -- and
publishes it, if anything changed in authorized scope, as one create-only
`refs/wfc/preserved/<run_id>/<n>` ref; see
link:../warm_storage/beta1-productization/wfc_beta1_bp4b_candidate_preservation_001_limitations.adoc[the
BP4b limitations record] for what that capture does and does not prove.
`frontdoor/audit.py` implements the installed `wfc audit` (BP6a): a pure,
read-only, default-deny projection of an already archived Attempt directory
into `audit.json` (`wfc.audit/1`), built field by field from an explicit
allow-list over `manifest.json`, `run/operator-plan.json`,
`run/operator-summary.json`, `run/checkouts/<id>/run.json` and
`run/checkouts/<id>/execution-evidence.json` -- never a copy-and-scrub of any
source object. A final privacy guard refuses to produce output (naming only
the offending JSON path, never the value) if any string value is an absolute
path, a caller-supplied private string, or a Git remote URL; `wfc report`
(`frontdoor/report.py`) renders the consolidated result from that projection
alone. Neither module writes to, reads Git state from, or re-verifies the raw
archive; see
link:../warm_storage/beta1-productization/wfc_beta1_bp6a_audit_projection_001_limitations.adoc[the
BP6a limitations record] for what the projection does and does not establish.
BP6b adds the optional `evidence` block to `frontdoor/config.py`
(`resolve_evidence`: an explicit `repository` resolved against the payload
root, or a default under `<data home>/wfc/evidence/<repository_name>`, plus
`raw: local|commit|discard`); `frontdoor/init.py` creates or adopts the
Evidence repository (`archive/`, a managed content-glob `.gitignore` block,
one bootstrap commit under the `git_facts` trusted policy duplicated locally
since no HEAD yet exists for `bounded_path_commit` to anchor on) after
writing the Consumer Config, exactly as before. `frontdoor/archive.py`'s
`raw_retention` keyword (`None` is the unchanged BP5 path) projects
`audit.json` from the verified staged copy and places/commits it per mode:
`local` keeps raw files on disk but commits only `audit.json` (raw paths
excluded by the managed `.gitignore`, checked for coverage before any write);
`commit` also commits `manifest.json`/`run/`/`ops/`, re-included past the
managed block by one per-Attempt negation `.gitignore` leaf (Git cannot
re-include a path under a trailing-slash-excluded directory, which is why
the managed block uses `run/**`/`ops/**`, not `run/`/`ops/`); `discard` never
places a raw file at the destination at all, so every resume/no-op check
reprojects `audit.json` from an ephemeral, deterministically-timestamped
manifest rather than comparing bytes on disk. See
link:../warm_storage/beta1-productization/wfc_beta1_bp6b_evidence_retention_001_limitations.adoc[the
BP6b limitations record] for what each retention mode keeps and what it does
not.
`frontdoor/postrun.py` (BP6c) is the additive post-classification step
`frontdoor/lifecycle.py`'s `run`/`resume` entry points call right after
`classified` and BP4b's own preservation step (never from `status`, which
only reads the `ext.archive.*` facts it wrote): it resolves the Evidence
settings from the checkout's cached Consumer Config, derives an explicit
Attempt identity from that config's `repository_name` and the `classified`
record's Run id (never from the engine state root's own directory name,
which BP4a always names `engine-state`), archives from the engine state
root through `frontdoor/archive.py`'s `archive_run` (passing that identity
and a `lifecycle` mapping of the BP4a classification and the latest BP4b
preservation fact, so both land in the same commit as `audit.json`), and
renders the consolidated report from the placed `audit.json`. A missing
Evidence repository is an honest, non-failing `ext.archive.skipped`; any
other refusal is `ext.archive.refused` with the additive, documented
`frontdoor.lifecycle.ARCHIVE_FAILED_EXIT_CODE` -- never one of BP4a's own,
unchanged `EXIT_CODES` values, and never a `LifecycleResult.classification`.
`frontdoor/archive.py`'s `resolve_ops_dir` now recognizes OPS evidence only
by the conventional `execution-bindings.yaml` leaf name, so the installed
lifecycle's own differently-named, per-checkout cached envelope file is
never mistaken for a missing OPS directory. See
link:../warm_storage/beta1-productization/wfc_beta1_bp6c_lifecycle_archive_wiring_002_limitations.adoc[the
BP6c limitations record] for what this step proves and does not.
The
link:{developer-docs}/technical_model/workflow_program_architecture.adoc#_one_hop_end_to_end[Technical Model's Hop path]
provides a more detailed map.

Role and modifier prompt texts live in
link:../../src/workflow_coordinator/resources/roles/[src/workflow_coordinator/resources/roles/],
the single live source: `prompt.py` and `commissioning.py` read only those
bytes, digest-pinned in `implementation_identity.RESOURCE_DIGESTS`. The
same-named files under `governance/self-development/prompts/` are frozen
historical copies that nothing reads; `reviewer.txt` there intentionally
differs from the live reviewer text since that text gained the simplicity and
maintainability review goals. To change a role text, edit the package
resource and update its `RESOURCE_DIGESTS` entry from the final bytes --
editing the frozen copy has no effect.

link:../../tests/unit/[tests/unit/] exercises individual behavior and seams, including
reducer and persistence; `tests/architecture/` checks boundaries and replay or
governance properties; `tests/integration/` exercises selected external
boundaries. These are orientations, not exclusive categories. Search for the
function, contract, or marker under change and inspect nearby fixtures such as
`tests/support.py` before choosing a focused test.

`tests/unit/test_archive_equivalence.py` is the archive-equivalence
comparison (see
link:{developer-docs}/cold_storage/backlog/post-0.1.0b1/beta1_bp7_cutover_plan.adoc#archive-equivalence[the
cutover plan's archive-equivalence definition]): for each `FixtureCase` in
its `FIXTURE_CASES` tuple, it runs the frozen legacy archiver
(`tests/fixtures/bp5/legacy/`, shared by every case) and the installed
`frontdoor.archive.archive_run` end to end against their own disposable copy
of one retained Run's STATE/OPS facts, and asserts the two resulting
`manifest.json` files are equal once `archived_at` is stripped. It reads only
committed, hash-pinned, disposable fixture copies under `tests/fixtures/`,
never the live sibling Evidence repository, and never invokes `wfc archive`
a second time against a real Run -- that would be a second archive path
beside the product function. To add a further proof
Run's fixture: commit a verbatim copy of that Run's already-archived
`run/`/`ops/` facts under a new `tests/fixtures/<name>/real_run/`, following
the collision and relocation rules `tests/fixtures/bp5/PROVENANCE.txt` (and
`tests/fixtures/bp7/PROVENANCE.txt`) document (write a matching
`tests/fixtures/<name>/PROVENANCE.txt`), then add one `FixtureCase` naming
that directory and its Attempt id to `FIXTURE_CASES`; the existing comparison
runs against it unmodified.

=== Investigating a Run

Start with the reported Run and Hop identity and persisted observations, not a
provider's account alone. The manual's
link:{developer-docs}/operator_manual/ch03_running/02_launch_status.adoc[status explanation]
describes source precedence and missing or inconsistent facts. At the state
root, `operator-plan.json` and `operator-summary.json` capture admission and
outcome; `checkouts/<id>/run.json` is the Run snapshot,
`checkpoint.json` is a digest-bound projection, and
`execution-evidence.json` contains evidence rows. Per-invocation diagnostics
may exist when a transport outcome has no accepted result. Compare the phase,
stop reason, Hop facts and evidence to the relevant path in `vertical.py`,
`reducer.py`, `evidence.py` or the adapter. A provider result is a candidate;
Coordinator observations and evidence are separate facts. Diagnostic output is
not itself trusted evidence.

Use a small fixture or existing test to reproduce a suspected behavior; do not
rewrite persisted Run state to make a diagnosis. For operator actions and
recovery, follow the link:{developer-docs}/operator_manual/ch07_diagnostics/_chapter.adoc[manual diagnostics]
and link:{developer-docs}/operator_manual/ch06_recovery/_chapter.adoc[recovery guidance].
