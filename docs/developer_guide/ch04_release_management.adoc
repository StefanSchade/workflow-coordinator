[[release-management]]
== Release management

WFC has one release line: beta pre-releases on `0.1.0bN`, published to PyPI
through a GitHub Actions pipeline, following the sibling
`spreadsheet-handling` repository's release flow and tooling shape as
closely as WFC's own threat model and distribution needs allow. This chapter
records the *decided contract* -- what a release must be true of -- not only
an implementation report. `scripts/wfc_release_check.py` and
`scripts/wfc_dist_audit.py`, run through the `release-check` and `dist-audit`
Make targets, exist and implement this contract (E2).
`.github/workflows/release.yml` *implements this contract* (E3, <<release-ci>>
below). MD-5
(link:../cold_storage/backlog/pre-0.1.0b1/release-engineering/wfc_release_md5_investigation_record.adoc#md5-open[the
investigation]) was accepted by the maintainer for 0.1.0b1 on 2026-11-23 on
the basis of hosted run #9
(link:../cold_storage/backlog/pre-0.1.0b1/release-engineering/wfc_release_md5_investigation_record.adoc#md5-maintainer-acceptance[the
acceptance record]); the acceptance did not by itself rewrite gate G2's
wording -- <<release-gates,the gate table below>> now states it in the
accepted form -- and the gates can still be run by hand if needed.

[[release-contract]]
=== The release contract

C1 -- Versioning and the tag:: The package version is *static* in
`pyproject.toml` (plain `setuptools`, no `setuptools-scm`); the first
published version is `0.1.0b1`, tag `v0.1.0b1`, no bump. Preflight asserts
`tag == "v" + version`. The test literal at
`tests/architecture/test_bp1_identity.py:41` (`first['version'] ==
'0.1.0b1'`) names the version explicitly so a future bump touches it
knowingly.
C2 -- Artifact content allow-list:: Both built artifacts are audited against
an *exact* allow-list; the audit fails on anything *unlisted*, not only on
the forbidden names below, so a new top-level directory cannot leak in
silently.
+
[cols="1,3",options="header"]
|===
|Artifact |Allowed contents
|Wheel |The `workflow_coordinator` package (`.py` files plus exactly the
four reviewed resource texts: `agent_operating_contract_v6.txt`,
`roles/reviewer.txt`, `roles/simple-self-check.txt`, `roles/worker.txt`, and
exactly the four agent-skill texts: `agent_skill/wfc/SKILL.md`,
`agent_skill/wfc/references/setup.md`,
`agent_skill/wfc/references/commission.md`,
`agent_skill/wfc/references/stops-and-evidence.md`) and `*.dist-info`.
|Sdist |`pyproject.toml`, `setup.cfg` (setuptools writes it in; untracked, not
a mistake), `PKG-INFO`, `README.md`, `LICENSE`, `src/**`.
|===
+
Forbidden by name in both, in addition to anything simply unlisted:
`docs/`, `tests/`, `governance/`, `project_memory/`, `.wfc/`, `scripts/`,
`requirements/`, `tmp/`, `build/`, any `*.ods`, any Evidence or Run artifact.
Already true without a `MANIFEST.in`: the measured sdist is 49 files /
830,282 bytes and the wheel 44 files / 822,648 bytes, with no docs, tests,
governance, `.wfc/` or Project Memory content -- now enforced mechanically
by `wfc_dist_audit.py` (E2), called by `make dist-audit` and by
`tests/architecture/test_offline_distribution.py`.
C3 -- Clean-environment install check:: Install the *built artifact* (not an
editable checkout) into a fresh venv and run `wfc --help` and `wfc --version
--json` from a directory *outside* the checkout. Assert the reported
version equals the tag and `source_commit` is `null`. The suite already
proves the underlying mechanism (`tests/architecture/test_bp1_identity.py`);
the release adds only the outside working directory and the assertion.
C4 -- Release notes:: Preflight fails when the tag has no matching section in
`docs/release_notes/release_notes.adoc`, or that section's heading still
says `-- planned`. Content: what changed since Beta, the consumer
quickstart's limitations, and the one qualified platform profile.
C5 -- Version-pinned documentation:: No HTML is published for `0.1.0b1`
(MD-4, *decided*: deferred, not rejected -- GitHub-hosted documentation with
version-bound links suffices now; a Pages-style solution is a possible
later extension once a second consumer exists). `README.md` *must* link
documentation only by *absolute, tag-pinned* repository URL
(`blob/<tag>/docs/...`); no repository-relative documentation link may
appear in `README.md`. This is workable because
`StefanSchade/workflow-coordinator` is already public and judged clean
(MD-3, *decided*; this corrects every earlier conditional statement that
assumed otherwise), and it is enforced mechanically by
`wfc_release_check.py`'s README-link check (E2, G1). The strict AsciiDoctor
render (G5, <<release-gates>>) stays a gate regardless; this does not
reopen C2.
C6 -- What runs on a hosted runner:: *MD-5 accepted by the maintainer for
0.1.0b1 on 2026-11-23*
(link:../cold_storage/backlog/pre-0.1.0b1/release-engineering/wfc_release_md5_investigation_record.adoc#md5-maintainer-acceptance[acceptance
record]). The workflow (<<release-ci>>) implements route R-A. See
link:../cold_storage/backlog/pre-0.1.0b1/release-engineering/wfc_release_md5_investigation_record.adoc#md5-open[the
investigation record] for the still-unknown items and the escalation rule,
and <<release-gates>> for G2.
C7 -- Distribution destination:: *Decided* (MD-1 below): TestPyPI, then PyPI,
then a GitHub Release, through the GitHub Actions pipeline at
`.github/workflows/release.yml` (<<release-ci>>, E3).

[[decided-maintainer-points]]
=== MD-1 and G8, decided

MD-1 -- Distribution destination:: TestPyPI, PyPI and a GitHub Release,
through a GitHub Actions release pipeline, following the
`spreadsheet-handling` flow as closely as possible. Both PyPI and TestPyPI
use *OIDC Trusted Publishing*: no long-lived token is stored as a repository
secret anywhere in this pipeline. TestPyPI is a *real upload* -- a
rehearsal, not `--dry-run` (G6 below) -- because only a real upload proves
the Trusted Publisher OIDC wiring, the index's metadata acceptance and an
installable result.
G8 -- Release authorized (maintainer):: A GitHub Environment named `pypi`
with a *required-reviewer* rule naming the maintainer gates the
`publish-pypi` job. This is an improvement over the reference, which
auto-publishes on every tag push. The setting is created by the maintainer
(external to this repository), confirmed before the first tag, and
exercised when the maintainer approves the pending deployment. Approval is
*never* inferred from a green job.

[[release-ci]]
=== The CI workflow (E3)

`.github/workflows/release.yml` exists and implements the contract above. It
has two triggers -- `push` to `main` and `push` of tags matching `v*` -- and a
top-level `permissions: contents: read`; no step references a repository
secret anywhere in the file. Five jobs:

* `check` (both triggers, no elevated permissions beyond the top-level
  `contents: read`): checks out full history (`fetch-depth: 0`) and
  additionally fetches `origin/main` (needed for the tag-mode reachability
  check, independently of C1's static version); pins the runner to
  `ubuntu-24.04` and `setup-python` to the exact patch `3.13.5` (MD-5 route
  R-A); relaxes unprivileged user namespaces for bubblewrap via `sudo
  sysctl` and installs `bubblewrap` (the hosted runner lacked it, attempt #6);
  in the required-suite step provides the Git identity through
  `$XDG_CONFIG_HOME/git/config` (WFC strips inherited `GIT_*` variables from
  trusted Git calls, so an identity given by those variables would be
  invisible), keeps `TMPDIR` outside the checkout, and removes the *runner's
  system-level* `filter.lfs.clean`/`filter.lfs.process` entries (attempt #5;
  this is a statement about the ephemeral hosted runner, not advice for
  users, and WFC's own filter-refusal test and rule stay unchanged and are
  part of the unmodified suite run in that same step); fetches the
  offline test-input bundle (`scripts/wfc_test_inputs.py fetch`) and installs
  WFC's dev extras from it (`... exec -- python3 -m pip install -e '.[dev]'`,
  link:ch01_development.adoc#offline-test-inputs[offline test inputs]); runs
  `make lint`, `make format-check`, and the unmodified
  required suite (`... exec -- python3 -m pytest -q`); builds once (`...
  exec -- python3 -m build`); runs `make dist-audit` (C2, G3); runs the C3/G4
  clean-environment install-and-identity smoke from a directory outside the
  checkout; runs the G5 strict documentation render; runs the mandatory `make
  release-check TAG=$\{GITHUB_REF_NAME}` (tag mode, G1) for release-tag events
  only -- the preflight refuses a `planned` release-notes section, which is the
  normal state of an ordinary `main` push during a development cycle, so it
  runs at the tag instead of starving the artifact upload and `python-compat`
  on every push; branch mode of the tool remains the maintainer's local
  pre-tag check; a refused preflight on a tag stops the publication chain,
  because it precedes the upload and `publish-testpypi` needs `check`; records
  the two artifacts' SHA-256 in the job summary and uploads `dist/` as a workflow artifact.
  Nothing downstream rebuilds it. The summary also carries the
  maintainer's full decision facts -- interpreter and seed pip version,
  `bwrap --version`, the pytest pass/skip counts, artifact names, sizes and
  SHA-256, `implementation_tree_sha256`, and the `dist-audit` result -- in
  both branch-push and tag-push runs, since `check` runs on both triggers.
* `python-compat` (both triggers, `needs: check`, no elevated permissions,
  matrix CPython 3.10, 3.11 and 3.12 on `ubuntu-24.04`): the maintainer's
  small compatibility job of 2026-11-23, made release gate *G9* by
  maintainer decision D6 (2026-11-25, Option A,
  link:../backlog/beta2_release_streamlining_plan.adoc#d6[the Beta-2
  release-streamlining plan]): `publish-testpypi`'s `needs:` now includes
  this job (the workflow's own comment above the job records the same
  fact), so a red `python-compat` blocks publication the same way G1-G8
  block their own step. The advertised CPython 3.10-3.13 interpreters stay
  unchanged. Accepted risk (maintainer, 2026-11-25): the 3.10-3.12 jobs
  below install from the ordinary index, not the offline bundle `check`
  uses, so an index-side or upstream change on one of them can turn a
  release red for a reason outside this repository; the response is a
  re-run of the failed jobs (<<recovery>>'s "Failed before any upload" row
  -- nothing has been uploaded yet), never a re-tag. Dropping the 3.10-3.12
  classifiers later, to remove the gap instead of accepting it, is a
  separate maintainer-level change (the classifier, the matrix entry and,
  if wanted, `requires-python`).
  `requires-python = ">=3.10"` and the classifiers are unchanged; the only
  fully qualified profile stays CPython 3.13 on Linux x86-64 in `check`.
  This job downloads the `release-dist` artifact that `check` built once,
  re-verifies its SHA-256, installs the wheel into a clean virtual environment
  with ordinary index dependencies (PyYAML and pytest; the 3.13-specific
  offline bundle is *not* reused), verifies the installed metadata version,
  the packaged resources (SHA-256 against `wfc --version --json`) and the CLI
  identity (`wfc --help`, `wfc --version --json`, version equal to
  `pyproject.toml`, `source_commit` null), and runs eleven provider-free
  test modules against the *installed* wheel (`-o pythonpath=.` replaces the
  repository's `src` entry; `--wfc-partial`, the repository's explicit marker
  for a deliberately partial run). It does *not* cover the full required
  suite, bubblewrap, build isolation or real providers, and is neither
  qualification of those interpreters -- it is gate G9, not qualification --
  nor a statement about upstream security support (CPython 3.10 has reached
  upstream end of life).
  The development tooling is not part of this contract: for example
  `scripts/wfc_release_check.py` and some test modules import `tomllib`
  (CPython 3.11 and newer), so the *full* development suite does not run
  unmodified on 3.10. Debian 12 with CPython 3.11 on ARM64 is a future
  qualification target, not a Beta-1 requirement.
* `publish-testpypi` (tags only, `needs: check` and `python-compat` (G9),
  environment `testpypi`, job permissions `contents: read` and `id-token:
  write`): downloads the checked
  artifact unchanged, re-verifies its recorded SHA-256, then uploads it to
  TestPyPI through OIDC (`pypa/gh-action-pypi-publish`) -- a real upload
  (G6), not `--dry-run`.
* `publish-pypi` (tags only, `needs: publish-testpypi`, environment `pypi`,
  same job permissions): the `pypi` Environment's required-reviewer rule
  (G8) is a repository setting only the maintainer can create -- external to
  this file, confirmed before the first tag (ES-2) and exercised at approval
  time (ES-5); it is *not* created or simulated by this workflow. The same
  unchanged artifact is re-verified and uploaded to PyPI through OIDC the
  same way.
* `release` (tags only, `needs: publish-pypi`, job permissions `contents:
  write` only): downloads the same artifact and uses the preinstalled `gh`
  CLI to create the GitHub Release from the tag if none exists for it yet,
  or to re-upload the assets with `--clobber` if one already does -- `gh
  release view` decides which branch runs, and a failure of that step for a
  reason other than an absent release stops the job rather than being
  treated as absence -- attaching the wheel, the sdist and
  `SHA256SUMS.txt`, with a short fixed-body release note pointing at the
  tag-pinned `docs/release_notes/release_notes.adoc` (C4's adoc section is
  not converted to the release body; linking it avoids a lossy adoc-to-
  Markdown conversion). The job is idempotent (<<recovery,the recovery
  table>>).

Every third-party action is pinned to a full commit SHA with the release
named in a trailing comment (resolved on 2026-11-23 with `git ls-remote`
against the upstream repositories; the pinned commit is the one the previously
used mutable reference pointed to, so nothing was upgraded):
`actions/checkout` `d23441a` (v6.1.0), `actions/setup-python` `ece7cb0`
(v6.3.0), `actions/upload-artifact` `ea165f8` (v4.6.2),
`actions/download-artifact` `d3f86a1` (v4.3.0) and
`pypa/gh-action-pypi-publish` `7245906` (v1.14.3, the commit of its
`release/v1` branch). Newer major versions of these actions exist and were
deliberately not adopted. To change a version, resolve the new tag to its
commit (`git ls-remote --tags <repo> <tag> <tag>^{}`, using the peeled commit
for an annotated tag) and change SHA and comment together.

[[dependabot]]
`.github/dependabot.yml` (maintainer decision D3, 2026-11-25) opens pull
requests for new versions of the pinned actions above. It is scoped to the
`github-actions` ecosystem only, directory `/`, with a weekly schedule and a
seven-day cooldown so a newly released version is not proposed immediately.
It groups the actions that run *only* in the unprivileged `check` and
`python-compat` jobs (today `actions/checkout`, `actions/setup-python`,
`actions/upload-artifact`) into one named group, restricted to minor and
patch updates, separately from a second named group covering every action
that runs in `publish-testpypi`, `publish-pypi` or `release` (today
`actions/download-artifact` -- which also runs inside `python-compat`, and is
therefore *not* in the check-only group -- and `pypa/gh-action-pypi-publish`).
The group name is the identifiable mechanism: it appears in each pull
request's title and branch name, and a repository rule or workflow the
maintainer owns can match on it. Grouping by itself enables nothing --
*auto-merge is a GitHub repository setting the maintainer configures
separately, and no file in this repository enables it*; it is recommended
only after the first manually reviewed Dependabot run, and then only for the
check-only group. Publish-path action updates are always reviewed by hand.
Residual risk (maintainer-stated, D3): an action in the `check` job still
influences the bytes later published (it builds and uploads the release
candidate), so auto-merge there is *lower* risk, not none; the human `pypi`
approval (G8) and the audited, hash-listed artifact bound it.

*Maintainer follow-up:*
link:../backlog/postbeta_plan_p3_release_engineering.adoc#ext[ES-1 through
ES-6] (the Trusted Publisher registration, repository and Environment
settings, the first hosted `main` run, the tag, approval and publication,
and Q1's consumer-repository access) remain the maintainer's external
actions; nothing in this file performs or simulates any of them. Q1 itself
is, as of 2026-11-23 (MD-6), conducted as a consumer *smoke* qualification,
not a bugfix qualification -- it demonstrates the installed-artifact Run
path, the authorization boundaries, an independent review and
evidence/archival, but makes no claim of a successful substantive bugfix
qualification. Q1 consists of two separate minimal Runs on the same installed
release-candidate distribution in the consumer repository, each in its own
fresh worktree: Q1-A (Claude adapter) and Q1-B (Codex adapter), reported
separately; it starts only after the hosted CI run is green and the
release-candidate artifact is available. Its target files, baseline-compatible check commands (the check must pass on the clean
tree because the pre-launch baseline probe refuses a Run otherwise), a separate read-only
post-run verification and the limitation are fixed, and the formerly open points decided, in
link:../backlog/postbeta_plan_p3_release_engineering.adoc#q1[the plan's Q1] and
link:../backlog/postbeta_plan_p3_release_engineering.adoc#q1-open[its recorded
maintainer decisions of 2026-11-23].

[[release-gates]]
=== Release sequence and gates

Every gate is release-blocking; there is no advisory class, *scoped to the
enumerated gates G1-G9 below*. `python-compat` (<<release-ci>>) is gate *G9*
(maintainer decision D6, 2026-11-25, Option A,
link:../backlog/beta2_release_streamlining_plan.adoc#d6[the Beta-2
release-streamlining plan]): it blocks `publish-testpypi` the same way
G1-G8 block their own step. Each step below names the gate(s) guarding it.

. Push the release commit to `main`; the `check` job (<<release-ci>>) runs --
  *G1* preflight clean (topology, tag-equals-version, notes frozen, README
  links absolute and tag-pinned), *G2* required suite green, *G3* both artifacts contain
  exactly the C2 allow-list, *G4* clean-environment install and CLI identity
  (C3), *G5* documentation renders strictly. Once `check` is green,
  `python-compat` runs against the same artifact -- *G9* every advertised
  3.10-3.12 interpreter installs the built wheel and passes the
  provider-free smoke.
. With `check` green, the maintainer gives the Q1 consumer *smoke*
  qualification Runs (Q1-A and Q1-B) the downloaded `check` artifact unchanged (a rebuild's
  byte-identity is unverified) and authorizes them -- *G7* consumer
  qualification dispositioned, on completion of both.
. Only once Q1 is accepted *and* the `pypi` environment's pre-tag
  confirmation is in hand does the maintainer push the tag; `check` re-runs
  in tag mode, re-proving everything against the tagged commit.
. `publish-testpypi` runs unattended, now only once both `check` and
  `python-compat` are green (*G1*-*G5* and *G9*) -- *G6* TestPyPI rehearsal.
. The pipeline waits at the `pypi` environment's required-reviewer gate --
  *G8*, above.
. `publish-pypi`, then `release`, run after approval; the maintainer verifies
  the PyPI index page and the GitHub Release.

[[release-runbook]]
=== Release runbook

*Prepare.* `make release-prepare VERSION=<v>` (R1, `scripts/wfc_release_prepare.py`)
sets the version everywhere it is version-bearing and freezes the
release-notes heading in one commit (C1, C4).

*Preflight.* Before tagging: working tree clean, on `main`, local `main` in
sync with `origin/main`; `tag == "v" + version`; `docs/release_notes/release_notes.adoc`
has a matching, non-`planned` section for the tag; README links are absolute
and tag-pinned. `make release-check` (E2, `scripts/wfc_release_check.py`)
automates this read-only, network-free check. It reads
`git symbolic-ref -q HEAD` to select its mode: an attached HEAD is *branch
mode* (pre-tag) and additionally asserts branch identity, a clean tree and
sync with `origin/main`; a detached HEAD is *tag mode*
(`make release-check TAG=v<version>`) and instead asserts that the
checked-out commit is reachable from `origin/main`. Both modes assert
tag-equals-version, frozen release notes and absolute, tag-pinned README
links.

*Tag.* Create `v<version>` from the qualified commit on `main` only after
Q1 (consumer smoke qualification) is accepted and the `pypi` environment's
pre-tag confirmation is in hand (<<release-gates>>). Do not tag an
unqualified commit "to look at it" -- a pushed tag spends a TestPyPI
version even if the publish then fails.

*Publish.* `publish-testpypi` runs unattended on the tag (G6); `publish-pypi`
waits for the `pypi` environment's required-reviewer approval (G8), then
runs; `release` creates the GitHub Release from the same tag, or re-uploads
with `--clobber` if one already exists for it, attaching the same three
files the `check` job already built, audited and checksummed: the wheel,
the sdist and `SHA256SUMS.txt`. No job rebuilds the artifact after `check`.

*Approve.* The `pypi` environment's required-reviewer approval (G8) *is* the
release authorization; GitHub records who approved and when. Approval is
never inferred from a green job (<<decided-maintainer-points>>).

*Verify.* After `publish-pypi`: the PyPI project page shows the new version.
After `release`: the GitHub Release shows the same version and artifacts.

[[recovery]]
*Recovery.*

[cols="2,3",options="header"]
|===
|State |Action

|Failed before any upload |Fix on `main`, delete the tag, tag again.
|TestPyPI upload succeeded, a later step failed |Transient failure: re-run
the failed jobs. Content change: the next version. Never delete and re-tag:
TestPyPI refuses a second upload of the version and `publish-pypi` needs
`publish-testpypi`, so a corrected tag cannot pass.
|PyPI upload succeeded, a later job failed |Re-run the failed jobs. Never
re-tag.
|Wrong content on PyPI |Yank; release the next version.
|===

* *Already true of the implementation:* no state needs a rebuild, because
  every publishing job re-runs against the artifact `check` built once
  (<<release-ci>>).

*Not* adopted as the fix for the TestPyPI-spent state above: `skip-existing`
on the TestPyPI upload. It would let the rehearsal silently keep the old
file, which defeats G6's reason for being a real upload (MD-1).
