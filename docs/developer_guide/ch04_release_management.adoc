[[release-management]]
== Release management

WFC has one release line: beta pre-releases on `0.1.0bN`, published to PyPI
through a GitHub Actions pipeline, following the sibling
`spreadsheet-handling` repository's release flow and tooling shape as
closely as WFC's own threat model and distribution needs allow. This chapter
records the *decided contract* -- what a release must be true of -- not only
an implementation report. `scripts/wfc_release_check.py` and
`scripts/wfc_dist_audit.py`, run through the `release-check` and `dist-audit`
Make targets, exist and implement this contract (E2).
`.github/workflows/release.yml` *implements this contract* (E3, <<release-ci>>
below). Until a hosted run of that workflow proves route R-A green
(<<md5-open>>), the whole-required-suite gate (G2) on a hosted runner remains
evidence towards MD-5, not yet the binding mechanism, and the hosted-runner
gates can still be run by hand if needed.

[[release-contract]]
=== The release contract

C1 -- Versioning and the tag:: The package version is *static* in
`pyproject.toml` (plain `setuptools`, no `setuptools-scm`); the first
published version is `0.1.0b1`, tag `v0.1.0b1`, no bump. Preflight asserts
`tag == "v" + version`. The test literal at
`tests/architecture/test_bp1_identity.py:41` (`first['version'] ==
'0.1.0b1'`) names the version explicitly so a future bump touches it
knowingly.
C2 -- Artifact content allow-list:: Both built artifacts are audited against
an *exact* allow-list; the audit fails on anything *unlisted*, not only on
the forbidden names below, so a new top-level directory cannot leak in
silently.
+
[cols="1,3",options="header"]
|===
|Artifact |Allowed contents
|Wheel |The `workflow_coordinator` package (`.py` files plus exactly the
four reviewed resource texts: `agent_operating_contract_v6.txt`,
`roles/reviewer.txt`, `roles/simple-self-check.txt`, `roles/worker.txt`) and
`*.dist-info`.
|Sdist |`pyproject.toml`, `setup.cfg` (setuptools writes it in; untracked, not
a mistake), `PKG-INFO`, `README.md`, `LICENSE`, `src/**`.
|===
+
Forbidden by name in both, in addition to anything simply unlisted:
`docs/`, `tests/`, `governance/`, `project_memory/`, `.wfc/`, `scripts/`,
`requirements/`, `tmp/`, `build/`, any `*.ods`, any Evidence or Run artifact.
Already true without a `MANIFEST.in`: the measured sdist is 49 files /
830,282 bytes and the wheel 44 files / 822,648 bytes, with no docs, tests,
governance, `.wfc/` or Project Memory content -- now enforced mechanically
by `wfc_dist_audit.py` (E2), called by `make dist-audit` and by
`tests/architecture/test_offline_distribution.py`.
C3 -- Clean-environment install check:: Install the *built artifact* (not an
editable checkout) into a fresh venv and run `wfc --help` and `wfc --version
--json` from a directory *outside* the checkout. Assert the reported
version equals the tag and `source_commit` is `null`. The suite already
proves the underlying mechanism (`tests/architecture/test_bp1_identity.py`);
the release adds only the outside working directory and the assertion.
C4 -- Release notes:: Preflight fails when the tag has no matching section in
`docs/release_notes/release_notes.adoc`, or that section's heading still
says `-- planned`. Content: what changed since Beta, the consumer
quickstart's limitations, and the one qualified platform profile.
C5 -- Version-pinned documentation:: No HTML is published for `0.1.0b1`
(MD-4, *decided*: deferred, not rejected -- GitHub-hosted documentation with
version-bound links suffices now; a Pages-style solution is a possible
later extension once a second consumer exists). `README.md` *must* link
documentation only by *absolute, tag-pinned* repository URL
(`blob/<tag>/docs/...`); no repository-relative documentation link may
appear in `README.md`. This is workable because
`StefanSchade/workflow-coordinator` is already public and judged clean
(MD-3, *decided*; this corrects every earlier conditional statement that
assumed otherwise), and it is enforced mechanically by
`wfc_release_check.py`'s README-link check (E2, G1). The strict AsciiDoctor
render (G5, <<release-gates>>) stays a gate regardless; this does not
reopen C2.
C6 -- What runs on a hosted runner:: *Open.* The workflow (<<release-ci>>)
implements route R-A as evidence towards MD-5, not as its disposition. See
<<md5-open>> below for the investigation, the still-unknown items and the
escalation rule, and <<release-gates>> for G2.
C7 -- Distribution destination:: *Decided* (MD-1 below): TestPyPI, then PyPI,
then a GitHub Release, through the GitHub Actions pipeline at
`.github/workflows/release.yml` (<<release-ci>>, E3).

[[decided-maintainer-points]]
=== MD-1 and G8, decided

MD-1 -- Distribution destination:: TestPyPI, PyPI and a GitHub Release,
through a GitHub Actions release pipeline, following the
`spreadsheet-handling` flow as closely as possible. Both PyPI and TestPyPI
use *OIDC Trusted Publishing*: no long-lived token is stored as a repository
secret anywhere in this pipeline. TestPyPI is a *real upload* -- a
rehearsal, not `--dry-run` (G6 below) -- because only a real upload proves
the Trusted Publisher OIDC wiring, the index's metadata acceptance and an
installable result.
G8 -- Release authorized (maintainer):: A GitHub Environment named `pypi`
with a *required-reviewer* rule naming the maintainer gates the
`publish-pypi` job. This is an improvement over the reference, which
auto-publishes on every tag push. The setting is created by the maintainer
(external to this repository), confirmed before the first tag, and
exercised when the maintainer approves the pending deployment. Approval is
*never* inferred from a green job.

[[release-ci]]
=== The CI workflow (E3)

`.github/workflows/release.yml` exists and implements the contract above. It
has two triggers -- `push` to `main` and `push` of tags matching `v*` -- and a
top-level `permissions: contents: read`; no step references a repository
secret anywhere in the file. Four jobs:

* `check` (both triggers, no elevated permissions beyond the top-level
  `contents: read`): checks out full history (`fetch-depth: 0`) and
  additionally fetches `origin/main` (needed for the tag-mode reachability
  check, independently of C1's static version); pins the runner to
  `ubuntu-24.04` and `setup-python` to the exact patch `3.13.5` (MD-5 route
  R-A); relaxes unprivileged user namespaces for bubblewrap via `sudo
  sysctl`; neutralizes the runner's system git-lfs filter only for the
  required-suite step's own `env:` (step-scoped, never a persistent `git
  config --global`, and never a weakening of WFC's own filter-refusal test,
  which is part of the unmodified suite run in that same step); fetches the
  offline test-input bundle (`scripts/wfc_test_inputs.py fetch`) and installs
  WFC's dev extras from it (`... exec -- python3 -m pip install -e '.[dev]'`,
  link:ch01_development.adoc#offline-test-inputs[offline test inputs]); runs
  `make lint`, `make format-check`, and the unmodified
  required suite (`... exec -- python3 -m pytest -q`); builds once (`...
  exec -- python3 -m build`); runs `make dist-audit` (C2, G3); runs the C3/G4
  clean-environment install-and-identity smoke from a directory outside the
  checkout; runs the G5 strict documentation render; runs `make
  release-check` in branch mode on a `main` push and in tag mode
  (`TAG=$\{GITHUB_REF_NAME}`) on a tag push (G1); records the two artifacts'
  SHA-256 in the job summary and uploads `dist/` as a workflow artifact.
  Nothing downstream rebuilds it.
* `publish-testpypi` (tags only, `needs: check`, environment `testpypi`, job
  permissions `contents: read` and `id-token: write`): downloads the checked
  artifact unchanged, re-verifies its recorded SHA-256, then uploads it to
  TestPyPI through OIDC (`pypa/gh-action-pypi-publish`) -- a real upload
  (G6), not `--dry-run`.
* `publish-pypi` (tags only, `needs: publish-testpypi`, environment `pypi`,
  same job permissions): the `pypi` Environment's required-reviewer rule
  (G8) is a repository setting only the maintainer can create -- external to
  this file, confirmed before the first tag (ES-2) and exercised at approval
  time (ES-5); it is *not* created or simulated by this workflow. The same
  unchanged artifact is re-verified and uploaded to PyPI through OIDC the
  same way.
* `release` (tags only, `needs: publish-pypi`, job permissions `contents:
  write` only): downloads the same artifact and uses the preinstalled `gh`
  CLI to create the GitHub Release from the tag, attaching exactly the two
  artifact files, with a short fixed-body release note pointing at the
  tag-pinned `docs/release_notes/release_notes.adoc` (C4's adoc section is
  not converted to the release body; linking it avoids a lossy adoc-to-
  Markdown conversion).

Action versions are pinned to a version tag (`actions/checkout@v6`,
`actions/setup-python@v6`, `actions/upload-artifact@v4`,
`actions/download-artifact@v4`, `pypa/gh-action-pypi-publish@release/v1`),
not a commit SHA -- authoring this file had no network access to verify
SHAs. *Maintainer follow-up:* pin every action to a reviewed commit SHA.
*Maintainer follow-up:*
link:../backlog/postbeta_plan_p3_release_engineering.adoc#ext[ES-1 through
ES-6] (the Trusted Publisher registration, repository and Environment
settings, the first hosted `main` run, the tag, approval and publication,
and Q1's consumer-repository access) remain the maintainer's external
actions; nothing in this file performs or simulates any of them. Q1 itself
is, as of 2026-11-23 (MD-6), conducted as a consumer *smoke* qualification,
not a bugfix qualification -- it demonstrates the installed-artifact Run
path, the authorization boundaries, an independent review and
evidence/archival, but makes no claim of a successful substantive bugfix
qualification. Q1 consists of two separate minimal Runs on the same installed
release-candidate distribution in the consumer repository, each in its own
fresh worktree: Q1-A (Claude adapter) and Q1-B (Codex adapter), reported
separately; it starts only after the hosted CI run is green and the
release-candidate artifact is available. Its target files, check commands and
limitation are fixed, and the formerly open points decided, in
link:../backlog/postbeta_plan_p3_release_engineering.adoc#q1[the plan's Q1] and
link:../backlog/postbeta_plan_p3_release_engineering.adoc#q1-open[its recorded
maintainer decisions of 2026-11-23].

[[release-gates]]
=== Release sequence and gates

Every gate is release-blocking; there is no advisory class. Each step below
names the gate(s) guarding it.

. Push the release commit to `main`; the `check` job (<<release-ci>>) runs --
  *G1* preflight clean (topology, tag-equals-version, notes frozen, README
  links absolute), *G2* required suite green, *G3* both artifacts contain
  exactly the C2 allow-list, *G4* clean-environment install and CLI identity
  (C3), *G5* documentation renders strictly.
. With `check` green, the maintainer gives the Q1 consumer *smoke*
  qualification Runs (Q1-A and Q1-B) the downloaded `check` artifact unchanged (a rebuild's
  byte-identity is unverified) and authorizes them -- *G7* consumer
  qualification dispositioned, on completion of both.
. Only once Q1 is accepted *and* the `pypi` environment's pre-tag
  confirmation is in hand does the maintainer push the tag; `check` re-runs
  in tag mode, re-proving everything against the tagged commit.
. `publish-testpypi` runs unattended -- *G6* TestPyPI rehearsal.
. The pipeline waits at the `pypi` environment's required-reviewer gate --
  *G8*, above.
. `publish-pypi`, then `release`, run after approval; the maintainer verifies
  the PyPI index page and the GitHub Release.

[cols="1,3,2",options="header"]
|===
|Gate |What it verifies |Owner
|G1 |Topology, tag-equals-version, notes frozen, README links absolute. |Operator and CI
|G2 |`python -m pytest -q`, zero flake, host and profile recorded. Operator-run now; CI once MD-5 is settled feasible. |Operator now, CI later
|G3 |Both artifacts contain exactly the C2 allow-list. |CI and Operator
|G4 |Fresh-venv install outside the checkout; `wfc --help`; `wfc --version --json` reports the tag's version. |CI and Operator
|G5 |`asciidoctor --safe-mode=safe -a assembled -o /dev/null --failure-level=WARN` over the assembled books: exit 0, no output. |CI
|G6 |`publish-testpypi` uploads the real checked artifact via OIDC. |CI and Operator
|G7 |The Q1-A and Q1-B archives and their independent review dispositions, reported separately; a truthful stop is itself a valid outcome. |Maintainer
|G8 |The `pypi` environment's required-reviewer approval. |Maintainer
|===

[[release-runbook]]
=== Release runbook

*Preflight.* Before tagging: working tree clean, on `main`, local `main` in
sync with `origin/main`; `tag == "v" + version`; `docs/release_notes/release_notes.adoc`
has a matching, non-`planned` section for the tag; README links are absolute
and tag-pinned. `make release-check` (E2, `scripts/wfc_release_check.py`)
automates this read-only, network-free check. It reads
`git symbolic-ref -q HEAD` to select its mode: an attached HEAD is *branch
mode* (pre-tag) and additionally asserts branch identity, a clean tree and
sync with `origin/main`; a detached HEAD is *tag mode*
(`make release-check TAG=v<version>`) and instead asserts that the
checked-out commit is reachable from `origin/main`. Both modes assert
tag-equals-version, frozen release notes and absolute README links.

*Tag.* Create `v<version>` from the qualified commit on `main` only after
Q1 (consumer smoke qualification) is accepted and the `pypi` environment's
pre-tag confirmation is in hand (<<release-gates>>). Do not tag an
unqualified commit "to look at it" -- a pushed tag spends a TestPyPI
version even if the publish then fails.

*Publish.* `publish-testpypi` runs unattended on the tag (G6); `publish-pypi`
waits for the `pypi` environment's required-reviewer approval (G8), then
runs; `release` creates the GitHub Release from the same tag, attaching the
same two artifact files the `check` job already built and audited. No job
rebuilds the artifact after `check`.

*Verify.* After `publish-pypi`: the PyPI project page shows the new version.
After `release`: the GitHub Release shows the same version and artifacts.

*Partial-failure recovery.* PyPI refuses to re-upload an already-published
version, so once `publish-pypi` succeeds the version is irreversible;
do not retag. If a step before `publish-pypi` fails (tag pushed, `check`
or `publish-testpypi` red), delete the remote and local tag, fix the
problem, and re-tag from a corrected commit -- no artifact has reached an
index yet. If `publish-pypi` succeeds but `release` fails, re-run `release`
alone; it only reads the already-published tag and artifacts.

*A published version is never retagged.* Once `publish-pypi` has succeeded,
fix forward with the next version; PyPI's own refusal to re-upload makes
this a hard rule, not a style preference.

[[md5-open]]
=== Open: must the whole required suite run on a hosted runner? (C6, MD-5)

*Status: open.* The earlier recommendation -- a subset on the runner -- is
*not* accepted. Target: the whole required suite, on a qualified hosted
environment, as a binding gate (G2), if technically possible.

Setup requirements (fact [1]):: `WFC_TEST_INPUTS`/`WFC_TEST_PROFILE` set to a
bundle verified byte-for-byte; `check_host` compares implementation, Python
minor, machine, system, SOABI, seed pip exactly and glibc as a floor; 12
pinned wheels; an editable WFC install; real bubblewrap userns, Git without
a clean/process filter, GNU make, PEP-517 isolation. Four conditional skips
fire on the Operator's reference host (three opt-in live-provider, one
internal probe); three further conditional skip sites exist suite-wide and
must be asserted *not* to fire on the runner -- `make` and `git` present,
`governance/self-development` checked out -- not silently relied upon.
Reproducible on a GitHub runner? (fact [2]):: Not yet proven, but plausible:
route R-A, now implemented as `.github/workflows/release.yml`'s `check` job
(<<release-ci>>), uses `ubuntu-24.04` (pinned label) plus `setup-python`
pinned to the exact patch `3.13.5`, a `sudo sysctl` relaxing unprivileged
userns for bwrap, a step-scoped neutralization of the runner's git-lfs
filter (not WFC's own filter-refusal test), the normal `fetch`+`exec` flow,
then the unmodified suite. No hosted run of this workflow has happened yet;
this is still the unexercised route, not a hosted-run result.
A second host profile's closure review? (fact [3]):: Re-verified against the
profile: the 12 wheel pins are checked only by filename, size, SHA-256,
metadata and wheel tag (manylinux/`py3-none`/`cp313` plus a glibc floor) --
none depends on the CPython build, so the pins would not change. The
build-dependent part is `seed_pip_version` (`ensurepip.version()`), which
Debian patches to a bundled pip distinct from upstream; other host fields
are generic. A second profile's review therefore reduces to a byte-equality
diff of `wheels` plus a review of the build-specific `host` fields -- never
a full dependency re-audit.
What cannot run at all? (fact [4]):: Nothing by design -- the four skips
above are opt-in or internal, and the three further sites are host- and
checkout-dependent conditions to verify, never silently widened or assumed.

*Still unknown, needing a hosted run:* (a) the runner's actual seed pip
version for CPython 3.13.5 on `ubuntu-24.04`; (b) bwrap userns after the
`sysctl`; (c) whether the runner's Git carries a git-lfs filter and the
neutralization suffices; (d) that `fetch` reaches `files.pythonhosted.org`;
(e) whether a second profile is wanted if the pip version differs.

*Cheapest evidence:* the first hosted run of the E3 workflow
(<<release-ci>>) on `main` answers (a)-(d).

*Escalation rule:* a real, reproducible blocker is documented with the
failing log and escalated -- a digest-pinned container, a documented partial
gate, or otherwise -- to the maintainer; MD-5 is not loosened and G2 is not
narrowed without that decision.
