[[run-preparation]]
== Run preparation

This is the generic WFC operator contract for preparing and launching a Run
once a semantic commission has been reviewed and committed. It is not a
general CLI manual and does not authorize a Run.

It applies uniformly across every WFC-operated repository -- WFC
self-development, Core as a consumer repository, Latin as a foreign-domain
consumer, and any future consumer -- and does not assume any particular
target repository's topology. A repository's own documentation may specialize
this contract (for example, WFC self-development's separate Runtime/target
clones and promotion rules in link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc[self-development specialization]),
but ordinary Run-preparation mechanics are defined once, here.

This anchors an existing operating practice against a recurring operator
mistake: after a semantic WorkItem commission has been reviewed and committed,
the next step -- preparing a Run for launch -- keeps getting reframed as
another LLM/agent task. It is not. This document is not a new CLI design, a
new orchestration feature, or a Project Memory entry; it documents an
already-established procedure precisely enough that it stops being
rediscovered or accidentally changed.

=== What preparation is, and is not

Preparation follows the reviewed, committed Commission (WorkItem, Profile,
RepositoryPolicy, Components and Task). The boundaries and sequence below
own the generic procedure; the product-Front-Door subsection supplies the concrete
command and its self-development substrate distinction.

[[three-boundaries]]
== Three boundaries

Run preparation crosses three distinct boundaries. Keep them separate:

Commission commit::
  Semantic authority is fixed. The WorkItem, profile, RepositoryPolicy, task,
  and any commission-scoped governance are reviewed and committed. Later
  execution-binding selection may choose how authorized work is executed, but
  cannot widen that authority.

`launch.sh` execution::
  Only the maintainer's explicit execution of `launch.sh` enters the
  provider-capable execution path and may cross the provider boundary. A
  launched WFC process may perform preflight, materialize Run/state, and
  register the checkout, and still fail on a mechanical condition before ever
  reaching a provider.

First real provider invocation::
  The provider boundary itself is crossed only when WFC actually dispatches
  the first real provider invocation. A Run may begin to materialize and
  still fail before that boundary is reached.

Executing `launch.sh` does not itself cross the provider boundary; do not
conflate the second boundary with the third.

[[deterministic-preparation]]
== Ordinary preparation is deterministic, not a Hop

Once the repository-backed semantic commission has been committed, ordinary
Run preparation is deterministic maintainer/operator mechanics: selecting
already-known exact commits, creating fresh OPS directories, exporting pinned
commits, creating virtual environments, installing frozen exports, writing
already-selected execution bindings, assembling `PATH`, running provider-free
preflight, and writing `launch.sh`.

It is not another semantic agent Hop. It does not require an LLM to decide or
author the next steps. An LLM may be used when the preparation procedure
itself is being designed, changed, debugged, or reviewed -- that is not part
of normal execution of the established procedure.

[[ops-and-state]]
== OPS root versus state root

Select a fresh, initially absent OPS root and a fresh state root.

The OPS root is then created and populated by deterministic preparation: it
comes to contain the Runtime export/environment, the target/evidence
export/environment, `execution-bindings.yaml`, preparation logs, and
`launch.sh`.

The state root must remain absent throughout preparation. Its freshness is a
WFC launch precondition (the `--state-root` argument), not a preparation side
effect, and it is not the same requirement as the OPS root's initial absence.

[[canonical-sequence]]
== Canonical sequence

After the repository-backed commission has been reviewed and committed,
semantic preparation is complete. From this point until launch, Run
preparation is deterministic maintainer/operator mechanics; it is not an
agent Hop and does not require an LLM to decide or author the next steps.

. Pin exact target and Runtime commits.
. Require clean target and Runtime checkouts.
. Select a fresh, initially absent OPS root and a fresh state root; the state
  root must remain absent throughout preparation.
. Confirm the Runtime's documented implementation identity (its recorded
  version/digest, verifiable with `wfc --version`/`--json`) matches the
  accepted record; per DG-5, WFC does not export, build, or otherwise
  provision a fresh per-Attempt Runtime environment -- that identity must
  already be installed into a consumer-provided environment.
. Confirm the consumer-provided environment the Run will actually execute in
  has been independently prepared and is WFC-probed (the pinned target
  baseline's dependencies installed, the evidence command's interpreter
  resolvable); per DG-5, WFC does not provision project-specific
  environments in general.
. Write `execution-bindings.yaml` from maintainer-selected role bindings.
. Construct and inspect the controlled `PATH`.
. Run provider-free readiness/preflight checks.
. Materialize deterministic `launch.sh`.
. Stop.

Do not commission another LLM merely to perform steps 1-9. Only the
maintainer's explicit execution of `launch.sh` enters the provider-capable
execution path and may cross the provider boundary; the provider boundary
itself is crossed only when WFC actually dispatches the first real provider
invocation.

A repository specializing this contract may add its own preconditions on top
of this sequence (for example, WFC self-development's requirement that the
Runtime checkout satisfy a detached / push-disabled invariant); such additions
narrow, and never replace, the sequence above.

[[target-export-rule]]
== Target export rule

Current preparation practice strengthens the older separate-evidence-
environment rule by deriving that environment from a `git archive`/export of
the exact pinned target baseline commit, not merely installing from an
ambient checkout. Older material that does not spell this out is not thereby
wrong; it simply predates this stronger, now-preferred form of the same
separate-evidence-environment rule.

[[illustrative-shape]]
== Illustrative shape

The following is illustrative, not a second launcher implementation. It shows
the shape of the reusable preparation pattern, not a specific commission's
values.

[source,shell]
----
TARGET=...           # repository this Run operates on -- e.g. a fresh
                      # self-development checkout, or a consumer
                      # repository such as Core or Latin
RUNTIME=...            # the accepted Runtime identity's installed `wfc`
TARGET_HEAD=...        # exact pinned target commit

# exact HEAD / cleanliness checks against $TARGET_HEAD

"$RUNTIME" --version --json   # confirm the installed implementation identity
                               # matches the accepted record (step 4); WFC
                               # provisions nothing here

# confirm the consumer-provided environment is already prepared and
# WFC-probed: dependencies installed, the evidence command's interpreter
# resolvable (step 5); WFC provisions no project-specific environment

# write execution bindings from maintainer-selected role bindings

# assemble and verify the controlled PATH/executable resolution the Run will use

# provider-free readiness/preflight against the committed Commission

# materialize the deterministic launch record and stop; only the
# maintainer's explicit, separate confirmation enters the provider-capable
# execution path
----

On the current product Front Door, this generic shape is what `wfc init`
(Consumer Config), `wfc plan` (a read-only preview: project the Commission
and resolve the execution envelope without writing or launching) and
`wfc run --request ... --yes` (authorize, then launch, with its own
pre-launch checks and probe) perform together; see
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-topology[self-development's current specialization]
for the concrete commands.

[[harness-preparation]]
== Today's mechanism: the product Front Door

Authority:: informative

The generic sequence above remains the contract. Per DG-4/DG-5
(link:{operator-docs}/backlog/beta1_bp7_cutover_plan.adoc[BP7 retirement
cutover plan]), the former `scripts/wfc_op.py` Harness is retired: both proof
Runs are independently accepted with archive-equivalence recorded, and the
installed `wfc` console command (`wfc init`/`plan`/`run`/`resume`/`status`/
`audit`/`report`/`archive`) is now the regular, and only, self-development
path. There is no separate `prepare`/`launch` split and no per-Attempt
OPS/STATE export step: `wfc run` performs authorization, pre-launch checks,
a baseline probe, the Commission commit, re-verification, and engine launch
together, each step journaled write-ahead under the canonical checkout's own
state directory (`journal.state_home()/checkouts/<checkout-id>`).

=== Self-development specialization, in one line

Read the normative
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc[topology and Hop-budget guidance]
and link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc[promotion runbook]
before running a first Run, including the one-fresh-checkout-per-Run
discipline at
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation].

*Distinguish source identity from evidence substrate.* The accepted Runtime
identity is whatever `wfc` the maintainer has installed into a
non-editable environment per the bootstrap mitigation in the cutover plan's
risk section -- WFC itself no longer exports or builds that environment per
Attempt (DG-5). The Development checkout the Run actually operates on keeps
its full Git context (it is the evidence substrate `wfc run` commits
against and `wfc archive` later reads facts from); it is never replaced by a
stripped `git archive` export.

`wfc run` derives the exact repository HEAD and cleanliness requirement from
the live checkout itself (`--repository`, default the current directory) --
there is no separate `--expected-head` to pin by hand. It refuses outright if
a lifecycle is already authorized for this checkout (`refused_active_lifecycle`)
or if the engine state root already exists; see
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation]
for why that means one fresh checkout per Run today. Execution bindings come
from the Consumer Config's `default_execution` plus any
`--execution-override ROLE.FIELD=VALUE`, with no automatic model/provider
choice.

Provider-free preflight is `frontdoor.verify.verify_commission`, run as part
of `wfc run`/`resume` before the engine ever launches: it re-compiles the
Commission from the just-committed materials and re-verifies them against
the repository at the authorized HEAD before invoking the same admission
semantics the engine's own preflight uses. It allocates no Run, invokes no
provider. Journal records (`authorized`, `prelaunch`, `probe`, `commit`,
`verify`, `launched`, `classified`) are the current equivalent of the old
`preparation-pins.txt`/`harness-prepared.json` facts; `wfc status` projects
them. Drift is a named refusal, never a guess.

The product Front Door has no scratch allocator of its own (per the
link:{operator-docs}/backlog/beta1_bp7_cutover_plan.adoc#gap-analysis[cutover
plan's gap analysis], there was never a ported equivalent). The existing ch05
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-temporary-storage[temporary-storage/inode guidance]
remains necessary, unchanged by this cutover, and is now entirely the
consumer-provided environment's own responsibility: prepare and verify
`TMPDIR`/scratch space and inodes yourself before a test-heavy Run, the same
way as before, just without a Harness step that did it for you.

[[selfdev-offline-inputs]]
=== Offline inputs for WFC self-development

The WFC Development repository's required test suite now verifies a reviewed
third-party input bundle before tests and nested isolated builds. The
link:{operator-docs}/developer_guide/ch01_development.adoc#offline-test-inputs[Developer Guide]
owns the profile, `fetch`/`verify`/`exec` commands, staging, diagnostics and
qualification limits. This is WFC's own development tooling, not a requirement
on a consumer repository or a change to generic preparation authority.

Supply verified inputs to the `wfc run`/`resume` process environment; the
engine inherits it from the launching process, not from any frozen
Harness-written `launch.sh`. For a separate Coordinator `task-check`, that
same environment must carry the selected `WFC_TEST_INPUTS` and
`WFC_TEST_PROFILE`. The Guide shows using the verifier's `exec` around the
command; it verifies before and after and supplies the controlled pip settings.
The provider's own shell may have different read access and environment
filtering, so do not infer its access from a host check. A no-index setting
alone does not establish network isolation. Keep existing scratch, scope and
sandbox rules; the tool grants no new access.

=== The command

The paths and role/model values below are illustrative maintainer inputs,
not authorization to execute. `wfc plan` previews a Consumer Request read-only
before authorizing it with `wfc run`:

[source,shell]
----
wfc plan governance/work-items/<work-item-slug>-task.txt \
  --commission-id     <work-item-slug>-001 \
  --work-item-id      WI-<WORK-ITEM-SLUG>-001 \
  --authority-source  "Maintainer authorizes the stated bounded task." \
  --program           robust@v1 \
  --persona           worker="Bounded worker persona." \
  --persona           independent_reviewer="Independent adversarial reviewer persona." \
  --evidence-argv     python --evidence-argv -m --evidence-argv pytest --evidence-argv -q \
  --durable-artifact  broad_review=docs/backlog/<work-item-slug>_broad_review.adoc \
  --durable-artifact  focused_review=docs/backlog/<work-item-slug>_focused_review.adoc \
  --guidance-path     .wfc/governance/repository-policy.md \
  --scope src --scope tests --scope docs/backlog/<work-item-slug>.adoc

wfc run \
  --request governance/work-items/<work-item-slug>-request.yaml \
  --execution-override worker.adapter=<adapter> --execution-override worker.model=<model> \
  --yes
----

`--guidance-path` and `--scope` (on `plan`) and `--request` (on `run`, an
already-authored Consumer Request YAML, not a free-form task file) are
repository-relative to `--repository` (default the current directory).
`wfc plan` is entirely read-only: it never writes a Commission, invokes a
provider, or touches Git; author the Consumer Request YAML it would compile
once its preview looks right, then pass that file to `--request`. `wfc run`
prints the Commission digest and execution-envelope digest before
authorizing (`--yes` accepts non-interactively; an interactive terminal
without `--yes` prompts `y`/`N`). The canonical preflight (now
`frontdoor.verify.verify_commission`) requires personas to match the
program's roles exactly; `--execution-override` fields are `adapter`/
`model`/`reasoning`, never a project/path value.

For an adapter executable, verify the absolute path on this host with
`which codex` or `which claude`; do not assume a fixed location. The
Consumer Config's `default_execution` (`.wfc/config.yaml`) supplies a
default per role; `--execution-override` narrows or replaces one field of
it for a single `plan`/`run` invocation only, never the committed default.

=== Expected result

[source,text]
----
CLASSIFICATION: completed
MESSAGE: classified: completed
RUN ID: RUN-<...>
RUN STATUS: completed
END HEAD: <commit sha>
----

If `wfc run` refuses, read the printed classification and message and
consult link:{operator-docs}/operator_manual/ch07_diagnostics/01_troubleshooting.adoc#troubleshooting[troubleshooting].
Never hand-edit the checkout's journal or engine-state directory; a
refused or interrupted authorization attempt is resolved by `wfc resume`
(continuing) or by preparing a fresh checkout per
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation],
never by editing persisted facts. Continue to
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#launch[launch and monitoring];
archiving happens automatically, per
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#archive[ARCHIVE].

[[recovery-relation]]
== Relation to Run recovery and salvage

This document owns deterministic preparation and launch through `wfc run`/
`resume`. It does not cover what happens when a Run or Hop later fails to
cleanly complete; that maintainer procedure -- same-Run reconcile/resume,
maintainer salvage plus a fresh successor Run, forensic preservation, or
discard -- is owned separately by
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[Run recovery and maintainer salvage].

[[future-ux]]
== Relation to future UX

The product Front Door (`wfc init`/`plan`/`run`/`resume`) is the current
implementation of this deterministic preparation contract, already
collapsed into a small set of commands rather than a maintainer-assembled
shell procedure. Remaining UX gaps -- a scratch allocator, controlled
checkout reuse after a terminal lifecycle
(link:{operator-docs}/backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]),
and the bootstrap mitigation for a non-editable Runtime install -- are named
gaps, not silently absorbed ones; any future change here should preserve the
same pinning, freshness, Runtime freeze, evidence-environment, preflight,
and explicit provider-boundary semantics.
