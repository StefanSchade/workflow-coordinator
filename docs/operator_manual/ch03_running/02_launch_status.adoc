[[launch]]
== LAUNCH

[source,shell]
----
wfc run --request path/to/request.yaml --yes
wfc resume
----

`wfc run` authorizes and launches a lifecycle against the canonical checkout
derived from `--repository` (default the current directory): it compiles and
digests the Commission and execution envelope once, requires explicit
confirmation (interactive `y`, or `--yes` for a non-interactive caller),
re-derives both digests immediately before authorizing to refuse a race
between approval and a later edit, acquires the checkout's ownership lock,
and only then runs the pre-launch checks, baseline probe, Commission commit,
`frontdoor.verify.verify_commission`, and engine launch, each step journaled
write-ahead. `wfc resume` continues an already-authorized checkout purely
from journal and filesystem facts -- it never re-prompts and never
recommits; use it after an interrupted controller, not to start a new
lifecycle. It never resumes the engine's own Run/Hop/session for any other
classification, with one narrow, regular exception: a `reconcile_required`
or `awaiting_human` Run whose own recorded facts satisfy the mechanical-
recovery predicate -- see the normative
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#mechanical-recovery[mechanical recovery section]
of the recovery chapter.
There, `wfc resume` re-verifies that predicate against the live Run and
checkout, and only on success moves the identical Run back to `READY` and
continues its Hop loop; every predicate failure refuses by name
(`refused_not_recoverable`) and changes nothing.

For WFC self-development tests using the offline profile, select the verified
bundle explicitly in this launch process as well as in preparation; see the
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#selfdev-offline-inputs[offline-input guidance].

Each Hop the launched engine runs is bounded by a per-Hop timeout -- a CAP
meant only to end a genuinely hung provider invocation, never a budget for
ordinary work; a normal Hop should practically never reach it. Precedence:
`wfc run --hop-timeout-seconds`, then the `hop_timeout_seconds` key in
`.wfc/config.yaml` (see
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-init[`wfc
init` and configuration]), then the built-in default of 14400 seconds (4
hours). The resolved value is fixed at authorization and recorded for the
Run; `wfc resume` continues with that same recorded value, never re-resolving it.

Launching enters the provider-capable execution path. It does not itself
cross the provider boundary: the first real provider dispatch does.
Preflight, Run/state materialization or checkout registration can fail
before any provider invocation. See the normative
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#three-boundaries[three-boundary contract].

Engine state is materialized under the checkout's own `engine-state`
directory only once the pinned engine's own process actually starts the Run;
Hops then execute until a terminal state. `wfc run`/`resume` may run for a
long time before returning, and print `CLASSIFICATION: <name>` followed by
`MESSAGE: ...` and, when applicable, `RUN ID:`, `RUN STATUS:`, `END HEAD:`,
`STATE ROOT:` and `CHECKOUT STATE ROOT:`. The process exit code encodes the
classification (`0` for `completed`, `10` for `awaiting_human`, and so on,
through `refused_*`/`inconsistent`/`uncertain_launch` codes for mechanical
refusals, including `refused_not_recoverable` -- the regular, authorized
`wfc resume` mechanical-recovery predicate declined, naming which element
failed; see the recovery chapter's
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#mechanical-recovery[mechanical recovery section]).
*A non-zero exit code does not by itself mean provider or engine
failure* -- `awaiting_human` and other legitimate terminal states produce one
too (see terminal states below). Always inspect the printed classification
and `wfc status`, never the exit code alone.

[[status]]
== STATUS

[source,shell]
----
wfc status
----

Strictly read-only; never creates, mutates, retries, reconciles, or launches
anything. Safe and useful from a second shell while a Run executes in the
first. It always exits `0` unless there is no lifecycle at all to report
(`no_lifecycle`, exit `1`): an absent or not-yet-authorized lifecycle is a
fact, not a command failure.

`wfc status` classifies the canonical checkout's journal and filesystem facts
purely from persisted records -- it never invokes the engine's own `wfc
status` (which would be engine-version-coupled). It prints the same
`CLASSIFICATION`/`MESSAGE`/`RUN ID`/`RUN STATUS`/`END HEAD`/`STATE ROOT`/
`CHECKOUT STATE ROOT` fields `wfc run`/`resume` print, plus, when present, a
`PRESERVATION:` block (BP4b candidate-preservation status), an `ARCHIVE:`
block (BP6c postrun archive status, with `outcome`, `commit`,
`destination_relative`, `retention`, and on failure `reason_code`/`reason`)
and one `BUDGET EXTENSION <n>:` block per recorded maintainer Hop-budget
extension of this checkout's Run (amount, ceiling before and after, Hops
used at the grant, time, and the authority statement with its digest; see
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#budget-extension[the
budget-extension contract]).

Classifications distinguish `no_lifecycle` (nothing recorded yet),
`authorized`/`lifecycle_active` (authorized but not yet launched or still
running), `engine_active` (the engine, or its launcher, still holds the
ownership lock), `engine_exited_before_state` (no provider dispatch
recorded), `uncertain_launch` (an unresolved launch intent -- per DG-3
Variant B this is never treated as safe to relaunch), `inconsistent`
(contradictory engine/journal facts), and the terminal engine outcomes
(`completed`, `awaiting_human`, `awaiting_human_budget`,
`reconcile_required`, `stopped`, `interrupted`) plus the `refused_*`
mechanical-refusal classifications. `RUN_RECORDED`-equivalent terminal
classifications do not themselves mean success -- inspect `RUN STATUS` and
the terminal-states guidance below.

Illustrative projection shape (not a literal transcript):

[source,text]
----
CLASSIFICATION: awaiting_human
MESSAGE: classified: awaiting_human
RUN ID: RUN-157080a2fa7b44de8429aa9b8fba53ab
RUN STATUS: awaiting_human
END HEAD: 84fba1653738214bc49d0eabfeefeb4deb03023f
STATE ROOT: /home/<user>/.local/state/wfc/checkouts/<checkout-id>/engine-state
CHECKOUT STATE ROOT: /home/<user>/.local/state/wfc/checkouts/<checkout-id>/engine-state/checkouts/<run-checkout-id>
----

[[terminal-states]]
== Terminal states and awaiting_human

`awaiting_human` is *not* synonymous with provider failure, implementation
failure, or failed review. It means the current Run's authority/mechanics
cannot legally continue -- the trusted reducer correctly refused rather than
fabricate or assume authority it does not have.

`wfc status` reports only the lifecycle classification and run status shown
above; `stop_reason`, `human_question_present`, `hops_used`/`hop_limit`,
`anomaly_count` and the rest of the sanitized Run facts are projected
separately, after archive, via `wfc audit <attempt-dir>` (or automatically by
the BP6c postrun step) and rendered by `wfc report <source>`. When a Run
stops `awaiting_human`, inspect in order: the reported `stop_reason`; whether
`human_question_present`; open Findings and which phase, if any, holds
`finding_authority` over them; the last recorded phase/result; any anomalies;
durable review artifacts the Run references. This is correct fail-closed
behavior, not a malfunction.

`awaiting_human_budget` is the one terminal state with its own in-place
continuation: on an explicit maintainer instruction, `wfc extend-budget`
raises that Run's own Hop ceiling by a recorded amount and continues it (see
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#budget-extension[the
budget-extension contract] for the command, its bounds and every refusal).
It is never an operator's or an agent's own decision.

For the next maintainer decision, use the normative
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[recovery and salvage contract]
and the existing
link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc[successor-continuation runbook]
§§3–4. Preserve the stopped Run's truth; a successor needs separate authority.
For mechanical archiving, use
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#archive[ARCHIVE].
