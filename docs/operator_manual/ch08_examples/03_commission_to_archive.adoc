[[commission-to-archive]]
== Commission-to-archive walkthrough

This example follows a small task from authored Consumer Request to
publication, completion checks and mechanical archive, then separates the
maintainer's remaining decisions, entirely through the product Front Door
(`wfc init`/`plan`/`run`/`status`/`archive`). Per the BP7 retirement cutover
(link:{operator-docs}/backlog/beta1_bp7_cutover_plan.adoc[cutover plan]),
this replaces the historical Direct-v1/Harness walkthrough that preceded it;
no earlier historical Attempt or Commission is replayed here.

*Evidence boundary.* The committed Consumer Request records intended
authority and configuration; the implementation commit proves its subject
and changed bytes; a worker's own result-file account is not a trusted tool
transcript. The commands below illustrate the *current* CLI and expected
transitions, not a transcript of any specific real Run. All angle-bracket
values are illustrative placeholders requiring separately selected real
values. Validation here used source, help and read-only Git inspection;
no Run was performed to produce this chapter.

=== 1. Define the task, scope, authority and Consumer Request

The maintainer authors a bounded task document (`# title` / body /
Acceptance / Withheld authority / Default escalation) and a Consumer
Request under
link:{operator-docs}/operator_manual/ch02_commissioning/01_authority.adoc[Commission authority and admission]
and
link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#direct-v1-quickstart[Commission authoring].
This illustration authorizes one bounded `simple@v1` worker invocation:
read a fixture, edit it, and write a results file; scope is a single
illustrative documentation subtree; governance changes, other
repositories and ungranted Git operations are withheld.

=== 2. Select the program and its inputs

`simple@v1` needs `task-check-v1`'s `task-check` evidence and no durable
artifacts; `robust@v1` additionally needs `broad_review`/`focused_review`
durable artifacts and an `independent_reviewer` persona. This illustration
uses `simple@v1`: `max_autonomous_hops: 1`, one `implement` worker phase,
`review: null`, and an `accept` route with effect `complete` -- no
independent review or correction phase. Every governing input the compiler
uses (role/modifier/guidance component texts, the `simple@v1`/`robust@v1`
literal program templates) is package-owned or the consumer's own committed
guidance file; there is no separate per-Commission source-commit pin to
select, unlike the retired Direct-v1 path.

=== 3. Preview the Commission, read-only

From the Development repository root, preview the Consumer Request/Config
projection before writing anything:

[source,shell]
----
COMMISSION='<new-commission-id>'
TASK="governance/work-items/$COMMISSION-task.txt"

wfc plan "$TASK" \
  --commission-id     "$COMMISSION" \
  --work-item-id      "WI-<WORK-ITEM-SLUG>" \
  --authority-source  "Maintainer authorizes the stated bounded task." \
  --program           simple@v1 \
  --persona           worker="Bounded worker persona." \
  --evidence-argv     python --evidence-argv -m --evidence-argv pytest --evidence-argv -q \
  --guidance-path     .wfc/governance/repository-policy.md \
  --scope docs/qualification/<new-commission-id>
----

`wfc plan` prints the projected Commission digest and resolved execution
envelope; it writes nothing, admits no Run, and invokes no provider.
Inspect the preview: scope, personas, evidence argv, and the resolved
execution envelope must express the intended task.

=== 4. Author and commit the Consumer Request, then authorize

Once the preview looks right, author the equivalent Consumer Request YAML
(`schema_version`, `commission_id`, `work_item_id`, `authority_source`,
`program`, `task`, `scope`, `personas`, `evidence`, `max_autonomous_hops`,
`durable_artifacts`, `guidance`) and commit it -- this commit is distinct
from the later worker implementation commit:

[source,shell]
----
REQUEST="governance/work-items/$COMMISSION-request.yaml"
git add "$REQUEST"
git commit -m "chore: author $COMMISSION Consumer Request"

wfc run --request "$REQUEST" --yes
----

`wfc run` compiles and digests the Commission and execution envelope,
requires confirmation, re-derives both digests immediately before
authorizing (refusing a race against a later edit), commits the compiled
Commission bundle under `.wfc/governance/$COMMISSION/` itself, then calls
`frontdoor.verify.verify_commission` -- canonical provider-free preflight --
before ever launching the engine. There is no separate render-then-commit-
then-check sequence: authorization, admission and launch are one command.

=== 5. Confirm Runtime identity and environment preconditions

Before running, confirm the accepted Runtime identity is what will actually
execute (per DG-5, WFC itself provisions no per-Attempt environment -- see
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-topology[Topology and preparation]):

[source,shell]
----
EXECUTABLE='<absolute-claude-or-codex-executable>'
"$EXECUTABLE" --version   # or: which codex / which claude
wfc --version --json      # the installed Runtime identity wfc run will use
----

Also confirm the consumer-provided environment is already prepared: the
pinned target baseline's dependencies installed, and scratch/`TMPDIR`
resolved outside `/tmp` per
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-temporary-storage[temporary-storage guidance].
Execution bindings (`worker=<adapter>:<model>:<reasoning>`) were already
supplied via the Consumer Config's `default_execution` or an
`--execution-override` on the `wfc run` call in step 4; no separate
role-binding file is written.

=== 6. Recognize the provider boundary

`wfc run` (step 4) already performed authorization, pre-launch checks, the
baseline probe, the Commission commit, verification and engine launch in
one call; there is no separate PREPARE/LAUNCH split to perform here. Only
the first real provider dispatch inside that call crosses the provider
boundary -- preflight, Commission commit or checkout registration can still
fail before it is reached; see
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#three-boundaries[the three boundaries].
Executable availability alone is not proof of authentication, model support
or effective tool permissions.

=== 7. Inspect status, the Hop and Coordinator-owned publication

Use `status` from a second shell while execution runs, or afterward:

[source,shell]
----
wfc status
git show --format=fuller --stat <implementation-commit>
----

The first command reads the checkout's persisted lifecycle/preservation/
archive facts; the second inspects the Hop's actual implementation commit.
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#status[STATUS]
owns classification, Run id/status, Hop counts (via `wfc audit`/`report`
after archive), final HEAD and anomalies. Correlate Run, Hop, invocation and
HEAD rather than inferring success from a process exit code.

An illustrative CommitIntent shape (not a literal transcript):

[source,json]
----
{
  "paths": [
    "docs/qualification/<new-commission-id>/fixture.txt",
    "docs/qualification/<new-commission-id>/results.txt"
  ],
  "subject": "feat(<commission>): WI-<WORK-ITEM-SLUG> H001 bounded worker edit"
}
----

Git verifies those bytes and publication; the worker's own account does not
independently prove the tool sequence. Under
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#commit-intent-admission[CommitIntent admission],
the worker proposes exact leaves and subject; the Coordinator validates and
commits. An intent alone proves no commit; publication alone proves no
acceptance.

=== 8. Distinguish trusted evidence, review and actual completion

This illustration's `task-check` evidence is `python -m pytest -q`. Current
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#trusted-hop-order[trusted ordering]
is result, commit admission, Coordinator commit, required evidence, then
route reduction. Worker self-checks and result-file claims are not trusted
evidence; consult persisted observations (via `wfc audit`/`wfc report` once
archived) for actual classifications.

`simple@v1` has no independent review phase: its sole worker can request
`accept`; actual completion requires the reducer to apply the `complete`
effect with the required evidence and no open blocking Finding or
controlling anomaly. `robust@v1` instead requires independent
review/correction and fresh broad review under
link:{operator-docs}/operator_manual/ch02_commissioning/03_review.adoc[review mechanics];
that review is separate from trusted evidence and from Run completion.
Check the reported `RUN STATUS`, not merely a worker's own claim of
completion. For stops, use
link:{operator-docs}/operator_manual/ch07_diagnostics/02_failure_modes.adoc[failure diagnosis]
and link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[recovery outcomes],
then the separately authorized
link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc[successor procedure]
if needed. Preserve the predecessor's actual outcome.

=== 9. Mechanical archive of a terminal Run

Archiving is automatic: once the Run reaches a `classified` terminal
record, `wfc run`/`resume`'s own BP6c postrun step archives it -- there is
no separate dry-run-then-real-archive sequence to invoke by hand. Confirm
it with:

[source,shell]
----
wfc status   # ARCHIVE: result / outcome: archived, plus destination_relative
----

If a Run predates this wiring, or the automatic step was skipped/refused,
direct invocation remains available per
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#installed-archive[direct `wfc archive`]
(optionally `--dry-run` first) -- never a second time against a Run already
archived automatically. Inspect the reported destination, Evidence commit
and retained manifest; keep engine-state, mechanical archive and semantic
ledger distinct. For this illustration,
`archive/<classification>/<attempt>/manifest.json` is a placeholder only;
no archive path, output, digest or commit is established by this chapter.

=== 10. Curate meaning, consider Runtime promotion, and push separately

After an archive exists, the maintainer may separately curate the
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#semantic-ledger[semantic ledger]
against those mechanical facts, recording outcome, bindings, commits,
relationships and lessons; the product does not automate that judgment.
link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#runtime-promotion[Runtime promotion]
is another explicit maintainer decision selecting an independently accepted
executable identity; an illustrative smoke commit does not establish a new
accepted Runtime. Push is independently authorized and never implied by
publication, completion, archive, curation or promotion. The
link:{operator-docs}/operator_manual/ch08_examples/01_worked_reference.adoc#worked-reference[older stopped case]
remains a distinct historical illustration with its own recorded outcome,
from before this cutover.
