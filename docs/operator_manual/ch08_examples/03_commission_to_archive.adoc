[[commission-to-archive]]
== Commission-to-archive walkthrough

This example follows a small task from authored intent to publication,
completion checks and mechanical archive, then separates the maintainer's
remaining decisions. Its historical basis is Attempt
`wfc-claude-haiku-live-smoke-20261110-03`, Commission
`wfc-claude-haiku-live-smoke-003`, WorkItem
`WI-WFC-CLAUDE-HAIKU-LIVE-SMOKE-003` and Development commit
`aac9ae5c7ad9cfe740c6ee310f07d362d8ae9933`.

*Evidence boundary.* The committed Commission records intended authority
and configuration; the implementation commit proves its subject and changed
bytes. The results file contains the worker's account of tool success, not
a trusted tool transcript. These sources do not establish the historical
Run ID, preparation pins, role/model binding, provider version, full output,
trusted evidence outcome, terminal status or archive location/commit.
The commands below illustrate the *current* CLI and expected transitions,
not a transcript or instructions to replay this historical Commission.
All angle-bracket values are illustrative placeholders requiring separately
selected real values. Validation here used source, help and read-only Git
inspection; preparation, execution and archive were not performed.

=== 1. Define the task, scope, authority and Intent

The historical
link:{operator-docs}/../governance/commissions/wfc-claude-haiku-live-smoke-003/intent.yaml[Intent]
authorizes one authenticated Claude Haiku worker invocation: read a fixture,
edit its second line, write a nested results file, and run the single Bash
command `pwd`. Scope is `docs/qualification/claude-haiku-20261110`;
governance changes, other repositories and worker Git operations are withheld.
The task names the exact two output leaves and subject shown in step 8.
This is historical authority, not this documentation Commission's intent.
For a new task, the maintainer authors its own bounded Intent under
link:{operator-docs}/operator_manual/ch02_commissioning/01_authority.adoc[Commission authority and admission]
and link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#direct-v1-quickstart[Commission authoring].

=== 3. Render and inspect the governing artifacts

From a Development source checkout, this is the illustrative render shape
for a *new*, separately authorized Commission, not the historical directory:

[source,shell]
----
COMMISSION='<new-commission-id>'
OUT_DIR="governance/commissions/$COMMISSION"
INTENT="$OUT_DIR/intent.yaml"
python3 scripts/wfc_op.py commission render \
  --intent "$INTENT" --out-dir "$OUT_DIR" --check
----

Rendering writes five outputs; `--check` prints the provenance-labelled
report and does not perform admission. Inspect the authored Intent and all
five outputs, as illustrated by the historical
link:{operator-docs}/../governance/commissions/wfc-claude-haiku-live-smoke-003/task.md[task],
link:{operator-docs}/../governance/commissions/wfc-claude-haiku-live-smoke-003/work-item.yaml[WorkItem],
link:{operator-docs}/../governance/commissions/wfc-claude-haiku-live-smoke-003/profile.yaml[profile],
link:{operator-docs}/../governance/commissions/wfc-claude-haiku-live-smoke-003/policy.yaml[policy]
and manifest: scope, actions, phase routes, evidence argv, selected components,
digests and source pins must express the intended task. Rendering is a
non-authoritative projection, not a Run or provider invocation.

=== 4. Commit the Commission separately, then check admission

The maintainer separately reviews and commits the Intent and rendered bundle
before preparation, following the
link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#direct-v1-quickstart[owning commit/check procedure].
That Commission commit is distinct from the later worker implementation
commit. With a clean Development checkout at its full 40-character bundle
HEAD, the illustrative provider-free check is:

[source,shell]
----
BUNDLE_HEAD='<full-40-character-committed-bundle-head>'
python3 scripts/wfc_op.py commission check \
  --intent "$INTENT" --out-dir "$OUT_DIR" \
  --repository "$PWD" --expected-head "$BUNDLE_HEAD"
----

The current checker compares committed rendered bytes with pinned-source
re-rendering, verifies reused components, then calls canonical provider-free
preflight. Passing does not launch or prove task execution. The actual
historical bundle HEAD and check output are not asserted here.

=== 5. Prepare with execution pins and explicit role bindings

Under the
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#harness-preparation[preparation owner],
the maintainer selects clean Development, accepted Runtime and Evidence
checkouts and a fresh Attempt. Harness records their exact HEADs; there are
no separate HEAD flags. Runtime must be detached with push disabled.
This illustrative current invocation assumes a newly authored single-worker
profile; paths, model, effort and timeout are selected inputs, not recovered
historical values:

[source,shell]
----
ATTEMPT='<new-attempt-id>'
DEVELOPMENT='<absolute-development-checkout>'
RUNTIME='<absolute-runtime-checkout>'
EVIDENCE='<absolute-evidence-checkout>'
CLAUDE_EXECUTABLE='<absolute-claude-executable>'
MODEL='<maintainer-selected-model>'
EFFORT='<supported-effort>'
TIMEOUT_SECONDS='<positive-number>'
python3 scripts/wfc_op.py prepare \
  --attempt "$ATTEMPT" \
  --development "$DEVELOPMENT" --runtime "$RUNTIME" --evidence "$EVIDENCE" \
  --work-item "$OUT_DIR/work-item.yaml" --profile "$OUT_DIR/profile.yaml" \
  --policy "$OUT_DIR/policy.yaml" \
  --components governance/self-development/components.yaml \
  --task "$OUT_DIR/task.md" --executable "$CLAUDE_EXECUTABLE" \
  --timeout-seconds "$TIMEOUT_SECONDS" \
  --role-binding "worker=claude_cli:$MODEL:$EFFORT"
----

Bindings cover the selected profile's roles explicitly; no reviewer is
invented for historical `simple@v1`. A different program with a reviewer
requires that role's binding too. Harness exports/installs pinned Runtime
and builds its separate evidence environment from live pinned Development;
provider-free preflight resolves evidence executables without running tests.
It creates OPS and private scratch, freezes controlled PATH/temp settings
and launch artifacts, revalidates pins, and stops without creating STATE.
Historical environment paths and successful installation are unproven here.

=== 6. Inspect PREPARED / NOT LAUNCHED

On successful current preparation, the expected declaration is
`PREPARED / NOT LAUNCHED`; read-only inspection uses:

[source,shell]
----
python3 scripts/wfc_op.py status "$ATTEMPT" --json
----

Expect lifecycle `PREPARED_NOT_LAUNCHED` and absent STATE, not a Run ID or
completion claim. Inspect `preparation-pins.txt`, `harness-prepared.json`,
`execution-bindings.yaml` and `launch.sh` in the recorded OPS location:
verify all three repository pins, governing paths, role bindings, executable,
scratch and controlled environment. OPS existing does not mean execution
started. This is the maintainer's explicit go/no-go point; see
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#three-boundaries[the three boundaries].

=== 7. Launch and recognize the provider boundary

With separate maintainer launch authorization, the illustrative command is:

[source,shell]
----
python3 scripts/wfc_op.py launch "$ATTEMPT"
----

link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#launch[LAUNCH]
revalidates pins, cleanliness and launch-artifact digests before executing
the frozen launcher. That enters a provider-capable path; only the first
real dispatch crosses the provider boundary. Preflight/state/checkout
registration can fail earlier. Executable availability is not proof of
authentication, model support or effective tool permissions; historical
CLI version and exact binding are not inferred from the task title.

=== 8. Inspect status, the Hop and Coordinator-owned publication

Use `status` from a second shell while execution runs, or afterward:

[source,shell]
----
python3 scripts/wfc_op.py status "$ATTEMPT"
git show --format=fuller --stat aac9ae5c
----

The first command reads the chosen Attempt's persisted facts; the second
inspects the fixed historical commit, not that new Attempt's output.
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#status[STATUS]
owns identity agreement, lifecycle, Hop counts, phase, stop reason,
anomalies, final HEAD and cleanliness. Correlate Attempt, Run, H001,
invocation and HEAD rather than inferring success from a process exit code.

The following is the *historical* two-field CommitIntent representation
matching `aac9ae5c`'s exact subject and both changed leaves, not this

The commit changes the fixture's second line to `Initial state: verified

link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#commit-intent-admission[CommitIntent admission],
the worker proposes exact leaves and subject; the Coordinator validates and

=== 9. Distinguish trusted evidence, review and actual completion

The historical policy configures `task-check` as `python -m pytest -q`
with a 900-second timeout. Current
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#trusted-hop-order[trusted ordering]
is result, commit admission, Coordinator commit, required evidence, then
route reduction. Worker self-checks and result-file claims are not trusted
evidence. Consult persisted observations for actual classifications; no
historical test pass or complete Run is established by `aac9ae5c` alone.

Historical `simple@v1` has no independent review phase. Its sole worker
can request `accept`; actual completion requires the reducer to apply the
`complete` effect with the required evidence and no open blocking Finding
or controlling anomaly. A different selected program may require independent
review/correction and fresh broad review under
link:{operator-docs}/operator_manual/ch02_commissioning/03_review.adoc[review mechanics];
that review is separate from trusted evidence and from Run completion.
Check persisted `run_status`, not merely worker `completed` or `RUN_RECORDED`.
For stops, use
link:{operator-docs}/operator_manual/ch07_diagnostics/02_failure_modes.adoc[failure diagnosis]
and link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[recovery outcomes],
then the separately authorized
link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc[successor procedure]
if needed. Preserve the predecessor's actual outcome.

=== 10. Mechanically archive a terminal Run

Once persisted facts establish a terminal Run, the maintainer follows
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#archive[ARCHIVE]:

[source,shell]
----
python3 scripts/wfc_op.py archive "$ATTEMPT" --dry-run
python3 scripts/wfc_op.py archive "$ATTEMPT"
----

Current Harness derives STATE/Evidence from preparation facts and delegates
to Evidence's canonical `scripts/wfc-archive-run`: the default invocation
performs a canonical dry-run followed by the real archive. The wrapper owns
copying, hashing, manifest and archive commit; Harness does not interpret
the Run as successful. A stopped terminal Run can also be archived.
Inspect the reported destination and Evidence commit and retained manifest;
keep STATE, mechanical archive and semantic ledger distinct.

For this smoke Attempt, `archive/<classification>/<attempt>/manifest.json`
and `<archive-evidence-commit>` are *illustrative placeholders only*.
No archive path, output, digest or commit is established by the local
Commission or implementation commit. Do not infer an archive from `aac9ae5c`.

=== 11. Curate meaning, consider Runtime promotion, and push separately

After an archive exists, the maintainer may separately curate the
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#semantic-ledger[semantic ledger]
against those mechanical facts, recording outcome, bindings, commits,
relationships and lessons. Harness does not automate that judgment.
link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#runtime-promotion[Runtime promotion]
is another explicit maintainer decision selecting an independently accepted
executable identity; a fixture-only smoke commit does not establish a new
accepted Runtime. Push is independently authorized and never implied by
publication, completion, archive, curation or promotion. No historical
curation, promotion or push is claimed here. The
link:{operator-docs}/operator_manual/ch08_examples/01_worked_reference.adoc#worked-reference[older stopped case]
remains a distinct historical illustration with its recorded outcome.
