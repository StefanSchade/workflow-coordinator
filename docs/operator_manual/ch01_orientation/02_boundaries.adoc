[[harness-limits]]
== What Harness v0 intentionally does not do

Harness v0 does not: choose the next WorkItem; estimate task difficulty;
choose semantic execution strategy; decompose tasks; author implementation
plans or Commissions; decide which model to use semantically (it only
records the maintainer's explicit `--role-binding`); curate the semantic
ledger; promote Runtime; push; repair failed Runs; reinterpret terminal Run
state.

These belong to maintainer decisions or a possible future higher
orchestration layer (link:{operator-docs}/operator_manual/ch01_orientation/02_boundaries.adoc#future-orchestration[future higher orchestration]):

[source,text]
----
higher orchestration / planning / curation   (not designed here)
    -> Commission / execution choice          (maintainer-owned)
    -> Harness v0 deterministic mechanics      (this manual)
    -> WFC Run                                 (WFC-owned semantic execution)
----

[[future-orchestration]]
== Relation to future higher orchestration

A future upper layer may perform non-deterministic activities such as
authorized backlog/task picking, difficulty/risk estimation, model/profile
selection, task decomposition, implementation planning, Commission
authoring, invocation of Harness/WFC Runs, or semantic archive/ledger
curation -- some delegating to reviewed WFC workflows, others using
deliberately lightweight "do this once" profiles. This is an architectural
observation, not an integrated WFC product capability. On 17 November 2026 an
external operator sequenced separately authorized Commissions, checked their
outcomes and archived them; WFC did not itself select or run that series as a
multi-Commission program. Harness v0 remains the deterministic execution
boundary underneath external orchestration or a possible future integrated layer.

[[consumer-tool-environment]]
== Consumer tools and temporary storage

WFC provides and propagates its documented execution environment; consumers
configure their own tools. Tools may ignore temporary-directory variables,
hard-code paths, or alter subprocess environments, so WFC cannot guarantee
placement for every consumer toolchain. This does not reduce WFC's documented
execution or sandbox responsibilities. In self-development the WFC repository
is itself a consumer of its Runtime. Separately, an opt-in Coordinator-owned
Linux filesystem boundary now exists (`boundary: bubblewrap`), wired into
both adapters' provider dispatch; it defaults to off, confines the
filesystem dimension only, and is distinct from the orchestration-layer
boundaries this chapter describes -- see
link:{operator-docs}/backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[the
Execution Boundary record] for its guarantees and standing. When selected,
its private `/tmp` tmpfs is capped at 256 MiB per invocation (a scratch-abuse
bound, stated here rather than left implicit), and it requires an
operator-configured provider authentication location
(`WFC_BOUNDARY_AUTHENTICATION_PATH`) and the provider CLI installed at a
view-visible path; each unmet prerequisite is a named preflight refusal,
never a silent fallback to unisolated dispatch.
