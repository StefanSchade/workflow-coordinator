[[purpose-and-audience]]
== Purpose and audience

The operator manual reading path is for a maintainer returning months
later, with no memory of the surrounding concept papers or chat history,
to operate a WFC self-development Run: run it, check on it, inspect its
automatic archive, and correctly interpret a stop.

It is not another architecture concept (the
link:{operator-docs}/cold_storage/backlog/pre-0.1.0b1/operator-harness-v0/wfc_operator_harness_v0_concept_2026-10-06.adoc[historical Harness v0 concept],
`docs/warm_storage/projected-result-contracts/wfc_projected_result_contracts_concept_2026-10-07.adoc`), not a
restatement of the generic deterministic-preparation contract
(`docs/operator_manual/ch03_running/01_preparation.adoc`), not a restatement of the Runtime-N/
Development-N+1 topology and promotion runbook
(`docs/operator_manual/ch05_self_development/`), and not a restatement of the four
maintainer-chosen recovery outcomes (`docs/operator_manual/ch06_recovery/01_outcomes.adoc`).
Where this manual overlaps one of those, the dedicated document is
authoritative; this manual summarizes only enough to operate correctly and
links there for rationale.

[[mental-model]]
== Five-minute mental model

[source,text]
----
COMMISSION / GOVERNING INPUTS
    = What may this Run do?
      (a Consumer Request: task, scope, program, personas, evidence,
       durable artifacts, guidance -- reviewed and committed before
       `wfc run` ever authorizes it)

EXECUTION ENVELOPE
    = Which adapter/model/reasoning configuration performs each role?
      (the Consumer Config's default_execution, optionally narrowed by
       --execution-override; resolved separately from the Commission bytes)

CHECKOUT
    = The canonical identity of the Development repository `wfc run`
      operates on (resolved Git top-level + common directory).
      Owns the journal, ownership lock, cached Commission materials and
      engine-state. Lives at $XDG_STATE_HOME/wfc/checkouts/<checkout-id>.

ENGINE-STATE
    = WFC-owned persisted Run state, inside the checkout directory above.
      Created only when `wfc run`/`resume` actually launches the engine.

EVIDENCE
    = Durable archived evidence derived from the Run after execution.
      Today: the sibling workflow-coordinator-run-evidence repository.

RUNTIME
    = The accepted WFC implementation used to execute Runs.
      Separate from Development; promoted only by explicit maintainer
      action; never "latest main".
----

Two distinctions matter most operationally:

* *Authorized vs. launched* -- `wfc run` authorizes (digests confirmed,
  ownership lock acquired, journal record written) before it ever launches
  the engine; a dead or interrupted controller can leave a checkout
  authorized but not yet launched, or launched but not yet classified.
  `wfc status` reports exactly which; `wfc resume` continues from there --
  it never starts a second lifecycle in the same checkout (see
  link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation]).
* *Commission authority vs. execution choice* -- the Consumer Request's
  scope/program/personas/evidence/durable artifacts is *what may happen*;
  the resolved execution envelope is *which concrete adapter/model/
  reasoning performs it*. A Commission may stay semantically identical
  while its execution bindings differ, if separately authorized.

[[repositories-and-trust-boundaries]]
== Repositories and trust boundaries

[cols="1,3,2",options="header"]
|===
|Repository |Role |Mutability from the product Front Door

|`workflow-coordinator` (Development)
|Evolving candidate implementation and Commission inputs; also the
checkout `wfc run` operates on for self-development.
|`wfc run`/`resume` read it (verify HEAD, require clean) and commit the
compiled Commission bundle into it; the pinned *Runtime's* installed `wfc`
executes against it.

|`workflow-coordinator-runtime` (Runtime)
|The accepted WFC implementation that executes Runs. Per DG-5, a
non-editable installed environment built once per promotion, not a
per-Attempt export; its source clone stays detached, clean,
`remote.origin.pushurl=DISABLED`.
|Never mutated by `wfc run`/`resume` or by a Run. Changed only by explicit
maintainer promotion
(link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc[Runtime promotion]).

|`workflow-coordinator-run-evidence` (Evidence)
|Durable mechanical archive plus the curated semantic run ledger.
|Never mutated by `wfc plan`/`status`. `wfc run`/`resume`'s own postrun step
(or direct `wfc archive`) commits into it.
|===

The installed `wfc` console command (`wfc init`/`plan`/`run`/`resume`/
`status`/`audit`/`report`/`archive`) is the deterministic mechanical layer
that operates across all three. It owns none of their semantic content.

[[attempt-ops-state]]
== Checkout and engine-state identity

[source,text]
----
checkout_id = sha256(resolved git toplevel + resolved git common dir)

$XDG_STATE_HOME/wfc/checkouts/<checkout_id>/
    journal                  # append-only lifecycle facts
    lock                      # per-checkout ownership lock
    commission/               # cached Commission/Config/envelope materials
    engine-state/             # created only once the engine actually launches
----

This identity is deterministic and derived purely from Git facts -- no
registry, database, or maintainer-chosen name: a symlinked working tree and
a linked worktree sharing one object store resolve to the *same*
`checkout_id`, while two genuinely distinct checkouts never collide. There
is no separate "prepared but not yet launched" directory distinct from the
checkout itself: `wfc status` distinguishes an authorized-but-not-launched
checkout from one whose `engine-state` already exists purely from journal
facts (see
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#status[STATUS]).
Per
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation],
use one fresh checkout per Run today.
