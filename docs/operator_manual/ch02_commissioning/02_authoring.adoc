[[normal-workflow]]
== Normal operator workflow

[source,text]
----
author / accept concept or task intent
    -> wfc init                        [once per repository; Consumer Config]
    -> author Consumer Request (task, scope, program, personas, evidence,
                                 durable artifacts, guidance)
    -> wfc plan                        [read-only preview; no write, no provider]
    -> commit Consumer Request
    -> wfc run --request ... [--yes]   [authorize, then launch the lifecycle]
    -> wfc resume                      [continue an interrupted controller only]
    -> wfc status                      [read-only, any time, any shell]
    -> terminal Run state              [WFC-owned semantic/mechanical fact]
    -> automatic archive (BP6c postrun step; `wfc archive` also directly invokable)
    -> semantic ledger curation        [maintainer/LLM-assisted judgment,
                                         never automated by the product]
    -> Runtime promotion, separately, if accepted
    -> push, separately, if authorized
----

[cols="2,3",options="header"]
|===
|Step |Nature

|Commission authoring/commit |Semantic -- maintainer-owned, reviewed
|`wfc plan` |Deterministic, read-only preview
(link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[preparation contract]),
plus one provider-free preflight-equivalent projection that refuses rather
than decides
|`wfc run` authorization digests |Maintainer decision point: go or don't go
(`--yes`, or an interactive `y`/`N`)
|`wfc run`/`resume` launch |Mechanics up to starting the Run; Hops themselves
are WFC-owned semantic execution, not controller mechanics
|`wfc status` |Deterministic, read-only projection
|Interpreting a terminal state |Semantic -- maintainer judgment
(link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal states]
and link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc[successors])
|`wfc archive` (automatic or direct) |Deterministic mechanics
|Ledger curation |Semantic -- maintainer/LLM-assisted, never product-automated
|Runtime promotion / push |Explicit maintainer action, never automatic
|===

Trusted publication, evidence and acceptance follow the ordering in
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#trusted-hop-order[trusted evidence, worker completion and correction routing].
The link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc[self-development contract]
retains the specialization and Runtime-promotion procedure.

[[direct-v1-quickstart]]
=== Consumer Request quickstart

The product compiler supports `robust@v1` and `simple@v1`; `direct@v1` is
deliberately withheld from it (self-development's historical Direct-v1 path
is retired). In `simple@v1` a sole Worker self-checks and the Coordinator
runs the selected required `task-check`; there is no independent
review/correction loop. `robust@v1` instead includes fresh independent
review and, when warranted, correction and renewed broad review. Both use
the same admitted authority, phase scope, Coordinator-owned commit and
configured evidence boundaries. Choose the program and bindings under the
Maintainer's existing authorization; a single instruction may authorize the
sequence in advance.

`wfc plan` is a closed-program, *non-authoritative* preview: it turns a
task document plus CLI-supplied fields into the exact Consumer
Request/Config shapes, then previews the Commission bytes and the
separately resolved execution envelope -- it neither writes a Commission,
admits a Run, nor invokes a provider. From the Development repository root:

[source,shell]
----
COMMISSION=example-robust-v1-001

wfc plan governance/work-items/$COMMISSION-task.txt \
  --commission-id    "$COMMISSION" \
  --work-item-id      WI-EXAMPLE-ROBUST-V1-001 \
  --authority-source  "Maintainer authorizes the stated bounded task." \
  --program           robust@v1 \
  --persona           worker="Bounded worker persona." \
  --persona           independent_reviewer="Independent adversarial reviewer persona." \
  --evidence-argv     python --evidence-argv -m --evidence-argv pytest --evidence-argv -q \
  --durable-artifact  broad_review=docs/backlog/${COMMISSION}_broad_review.adoc \
  --durable-artifact  focused_review=docs/backlog/${COMMISSION}_focused_review.adoc \
  --guidance-path     .wfc/governance/repository-policy.md \
  --scope src --scope tests
----

There is no durable binding left behind by this preview: it prints the
projected Commission digest and resolved execution envelope for inspection,
not a written bundle. Once the preview looks right, author the equivalent
Consumer Request YAML (`schema_version`, `commission_id`, `work_item_id`,
`authority_source`, `program`, `task`, `scope`, `personas`, `evidence`,
`max_autonomous_hops`, `durable_artifacts`, `guidance`) and commit it:

[source,shell]
----
git add governance/work-items/$COMMISSION-request.yaml
git commit -m "chore: author $COMMISSION Consumer Request"
----

Then authorize and launch:

[source,shell]
----
wfc run --request governance/work-items/$COMMISSION-request.yaml --yes
----

`wfc run` compiles and digests the Commission and execution envelope,
requires confirmation (`--yes`, or an interactive prompt), re-derives both
digests immediately before authorizing to refuse a race against a later
edit, commits the compiled Commission bundle under `.wfc/governance/
$COMMISSION/` itself (there is no separate commit-then-check step), then
calls `frontdoor.verify.verify_commission` -- the current equivalent of
canonical provider-free preflight -- before ever launching the engine. It is
therefore the single admission-and-authorization step, not merely an
authorization to execute later
(link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[preparation contract]
and link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#launch[LAUNCH]).

[[hop-budget]]
== max_autonomous_hops

*This is a safety ceiling, not an estimate of expected Run length.* It is
the single most commonly misapplied piece of operator judgment here.

`max_autonomous_hops` is a WorkItem field, capped by the repository policy's
own ceiling and a hard Coordinator maximum. At Run creation it becomes
`Run.hop_limit`; `status` reports it alongside `hop_used`.

Common mistake: expecting a task to need implementation, review,
correction, and rereview -- maybe 2-4 Hops normally -- and concluding
`max_autonomous_hops` should therefore be 4. That does not follow. The same
task may legitimately need an additional review/correction cycle if a fresh
reviewer finds another real Finding; a too-tight ceiling then converts
healthy convergence into an unnecessary `awaiting_human` stop. Conversely,
an excessively high ceiling enlarges cost and autonomous blast radius if
agents genuinely fail to converge.

Choose the value as a *bounded worst-case safety ceiling* against repeated
symptom treatment, review/correction oscillation, an agent failing to
recognize a legitimate stop condition, or other genuine convergence
failures -- not as an *expected Hop count*. The probability of a convergence
defect does not shrink merely because the task seems easy; a "simple" task
does not justify an artificially tiny ceiling.

For the current bounded self-development workflow, `8` -- the value used in
the link:{operator-docs}/wfc_operator_manual.adoc#_19_worked_example[worked example],
which recorded 4 Hops with 4 unused -- is a reasonable illustration of this
principle, not a universal recommendation.
Set the value per WorkItem from this reasoning, not by copying `8`.

For the provisional self-development recommendation, see the
link:{operator-docs}/self-development.adoc#_commission_hop_budget_max_autonomous_hops[self-development Hop-budget guidance];
its task-specific constraints and applicable ceilings still govern.
