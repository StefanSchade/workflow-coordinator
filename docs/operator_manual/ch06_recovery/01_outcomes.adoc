This is the generic maintainer/operator contract for deciding what happens
after a Run or Hop does not cleanly complete. It is not a new recovery
mechanism, not a CLI manual, and does not itself authorize a Run, a
successor Commission, or a Runtime promotion.

The central invariant:

`Salvage preserves work, not authority.`

A useful second formulation, where it fits without restating the first: a
maintainer's own knowledge of what happened may be revised as evidence
accumulates, but the historical Run record itself is never rewritten.

[[recovery-outcomes]]
== Four outcomes

A Run or Hop that does not cleanly complete resolves into exactly one of
four maintainer-chosen outcomes. None is automatic; the Coordinator derives
at most the bounded facts that make an outcome eligible, never the choice
itself.

[cols="1,3,3",options="header"]
|===
|Outcome |Use when |Key properties

|1. Same-Run reconcile/resume
|The existing accepted reconcile/resume predicates in
link:{operator-docs}/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[`FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`]
allow it: same checkout identity, reconciled current HEAD verified and
stable/clean, unchanged governing truth, and no unresolved reconcile
anomaly.
|Same Run, same governing truth; the stopped Hop stays charged; no
retroactive repair of it; no automatic replay; explicit maintainer action.
This document does not implement or widen that mechanism. `wfc resume`
drives it for the two classes <<mechanical-recovery>> and
<<quiescent-interruption>> name, and `wfc resume --preview` says which, if
either, applies without changing anything.

|2. Maintainer salvage + fresh successor Run
|Useful bounded candidate work exists but the predecessor Hop/Run cannot or
should not continue under the same authority/truth -- e.g. dirty candidate
plus `reconcile_required` whose anomaly blocks resume, or changed
governing/Runtime/contract truth.
|The original Run remains frozen historical truth. The candidate is
preserved as explicitly non-authoritative Git history. A separately
authorized successor inspects it fresh. See "Canonical salvage procedure"
below.

|3. Forensic preservation only
|The dirty worktree has unauthorized/out-of-scope mutations, unexplained
untracked files, mixed provenance, an ambiguous baseline, or any inability
to prove the candidate is actually what the Run left behind.
|Do not create an ordinary salvage commit, which would overstate
provenance. Preserve the material externally (a patch is appropriate here),
stop, classify the state, and require explicit maintainer judgment.

|4. Discard
|The candidate has no preservation value.
|Preserve the historical Run evidence needed for audit, then discard the
candidate. Do not impose salvage ceremony on worthless WIP.
|===

Same-Run resume is exposed by `wfc resume` for exactly *two* mechanically
decidable classes, and is otherwise a library capability only. The reducer's
`resume_after_reconcile` requires `reconcile_required`, a still-resolving
phase, no anomalies, current HEAD equal to the reconciled Run HEAD, and used
Hops no greater than the limit; it returns the same Run to `ready` without
erasing the charged Hop. The two classes `wfc resume` drives it for are
<<mechanical-recovery,the durable-artifact anomaly>> (`reconcile_reason`
`mechanical_recoverable`) and <<quiescent-interruption,the proven-quiescent
post-dispatch interruption>> (`reconcile_reason` `interruption`). For
`prerequisite_return`, and for an `interruption` that does not satisfy the
quiescence predicate, it remains a capability without a production resume
path: those Runs take one of the four outcomes above. Outside those two
classes `wfc resume` continues an already-authorized lifecycle controller
from journal/filesystem facts only, never the engine's own Run/Hop/session.

`wfc resume --preview` states which of the two, if either, applies -- the
class, what was proven or which element would refuse, and what the resume
would then do -- and changes nothing at all: no ownership lock, no Run,
checkpoint or marker write, no journal record, no launch. Run it before
`wfc resume` on any stop you have not seen before.

[[mechanical-recovery]]
=== Mechanical recovery (`reconcile_reason: mechanical_recoverable`)

The first of the two narrow, bounded, already-implemented exceptions to the
paragraph above, of the same shape as `frontdoor.preservation`'s automatic
candidate commit (see "Non-automation boundary" below): a purely mechanical,
consistent, post-acceptance stop is not a decision for a human to make, so
`wfc resume` does expose same-Run resume for it, through the regular,
authorized `wfc resume` command -- no manual state edit, no separate CLI.

The predicate (status-agnostic; it decides eligibility identically for a
Run freshly classified `reconcile_required` and for an already archived,
terminal `awaiting_human` Run stopped before this predicate existed):
`stop_reason` begins with `mechanical_preemption:`; no semantic stop; no
open human question; no open blocking Finding; at least one recorded Hop;
and the anomaly is exactly one of the post-acceptance durable-artifact
class (`required durable artifact has no declared path` / `...has no
CommitIntent` / `...is not named by the CommitIntent` / `...was not
changed in the trusted commit` / `...is absent or not a regular Git-tracked
file at end HEAD`). A WFC-GIT-08 malformed-commit-subject anomaly is
deliberately *not* in this class (a distinct, un-reviewed authorship
defect, not a consistent post-acceptance fact).

`wfc resume` re-verifies this predicate against the *live* Run and
checkout before acting: exact current HEAD, a clean worktree with resolved
submodules, at least one unused autonomous Hop remaining against the
Run's own `hop_limit`, unchanged Commission/execution-envelope identity
against the original lifecycle authorization, an unchanged package
implementation identity (a Run authorized under an earlier implementation
refuses by name; that is deliberate, and recovery adds no digest-migration
path), a pure re-verification of
the reconcile/resume reduction itself, and that the continuation engine
is actually resolvable and executable. Every predicate element, live or
recorded, is checked -- and the checkout's ownership lock is taken -- before
any mutation at all; a failure at any of them refuses by name
(`refused_not_recoverable`) and changes nothing -- no journal mutation, no
Run mutation, no archive attempt. A mechanical stop recorded on the Run's
last authorized Hop refuses by name
(`no autonomous Hop budget remains for a continuation`): there is no
further Hop left for the engine to drive, so recovery must not rewrite the
Run to `ready` only to leave it stopped again with its honest diagnosis
erased and no remaining documented path forward; the Run keeps its
`reconcile_required`/`awaiting_human` record and stop reason, and
authorizing additional Hop budget for it is a separate, explicit
maintainer decision outside this mechanism (and `wfc extend-budget`,
<<budget-extension>>, does not cover it either: that command requires an
`awaiting_human_budget` stop. Slice O10B evaluated this shape on 2026-11-27
and deliberately did *not* ship it -- zero recorded occurrences against a
real widening of the budget-extension authority surface -- so both refusals
stay honest and the only exit is a successor Commission; the reason and the
trigger are in
link:{operator-docs}/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc#design[the
recovery record's Design section]). On success it appends new
journal records only (never rewrites or deletes one), moves the identical
Run to `ready` at its unchanged phase with the stopped Hop still charged
and the Hop budget unchanged, and continues the engine's own Hop loop to a
further terminal classification, itself recorded as a further `classified`
journal record. Recovery never itself accepts the Run: the continuation
still needs its own normal accepting route, exactly like any other Hop.

The continuation engine resolving at the pre-mutation check and then
failing to actually spawn -- the ordinary real-world cause is a stale
console script whose absolute shebang interpreter has since been removed
or replaced, which `os.path.isfile`/`os.access` alone cannot detect -- no
longer leaves the Run rewritten to `ready` with no process driving it: the
launch failure rolls the Run and checkpoint back to their pre-recovery
state and appends a `mechanical_recovery_rolled_back` record (the journal
stays append-only; nothing already written is rewritten or deleted), then
refuses by name (`refused_not_recoverable`) exactly like any other
predicate failure, and a later `wfc resume` recovers the identical Run once
the engine is fixed.

One narrow residual window remains, distinct from "a predicate element
failed" and not covered by the no-mutation guarantee above: a controller
killed between the `mechanical_recovery_resumed` journal record and the
continuation's own further `classified` record has no `uncertain_launch`-
equivalent re-entry of its own, unlike the original launch path. This
leaves the Run in the same unresumable shape mechanical recovery exists to
remove, reachable only by an external kill in that exact window, not by
any predicate-level mistake or an ordinary launch failure; a maintainer
who finds a Run in this shape must treat it as outcome 2 ("Maintainer
salvage + fresh successor Run") above.

The already-archived predecessor attempt (manifest, `audit.json`, raw
files, its own Evidence commit) is never rewritten, moved, or overwritten.
A recovered continuation's own archive uses a distinct, collision-free
destination (an ordinal `-recovery-<n>` suffix on the same Attempt
identity) and refuses outright, never overwrites, an existing but
unrelated destination. `wfc status`/`wfc report` read the journal's
further `classified` record and the distinct archive destination, so the
recovery history is visible, never hidden behind the predecessor's own
facts.

For example, after an uncertain Hop leaves useful, entirely in-scope dirty
work and `reconcile_required` with an anomaly that prevents same-Run
resume, the maintainer may choose outcome 2 if exact provenance can be
proved. Freeze and preserve it under the canonical salvage procedure
below; ambiguous provenance instead requires outcome 3. For the subsequent
maintainer decision and separately authorized continuation, follow the
existing successor runbook's
link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc#_3_core_invariants[§3 Core invariants]
and link:{operator-docs}/operator_manual/ch06_recovery/02_successors.adoc#_4_current_manual_procedure[§4 Current manual procedure].
That walkthrough is informative and subordinate to this normative section,
including exact preservation and fresh assurance; its worked case (§2)
and captured experience (§6) are illustrative background. Its links through
the legacy recovery path lead back here.

[[quiescent-interruption]]
=== Quiescent-interruption recovery (`reconcile_reason: interruption`)

The second bounded exception, and the one the operator meets after a provider
timeout or crash. An invocation interrupted *after* its dispatch marker
existed is charged conservatively as an uncertain Hop and the Run lands in
`reconcile_required`: its acceptance cannot be disproved, so it is never
replayed and the Hop is never refunded. Where the Coordinator can prove from
its own records that the interrupted invocation left *nothing* behind,
`wfc resume` continues the identical Run at its unchanged phase with the next
Hop. The decisions, the five stop classes that deliberately keep refusing and
the honest limits are in
link:{operator-docs}/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc#design[the
record's `Design` section]; this section is the normative operator contract.

The predicate over the persisted Run (`reconcile_required` with
`reconcile_reason: interruption` is its scope gate; a Run outside it is not
refused but simply not this class): the stop reason is the explicit-resume
one and no question of the Run's own is open; no semantic stop; no recorded
repository anomaly at all; and the Run's last Hop is the Coordinator's own
charged uncertain Hop -- role `uncertain_dispatch`, outcome `uncertain`,
attributed to the Coordinator, with no applied route, no Finding delta, no
evidence reference, *no commit*, no HEAD movement while it ran or since, and
no published staged qualification attempt. An open blocking Finding does
*not* block it: the Run's phase, Findings and pinned governing truth are
exactly what a same-Run resume exists to preserve, resume changes no Finding
state, and disposition stays the independent reviewer's.

`wfc resume` then re-verifies the live facts before acting, in the same
pre-mutation order as mechanical recovery above: exact current HEAD, a clean
worktree with resolved submodules, at least one unused Hop against the Run's
own `hop_limit`, unchanged Commission/execution-envelope identity, unchanged
package implementation identity, a dispatch marker that correlates *exactly*
with the charged uncertain Hop (one that does not is refused, never silently
retired), the pure reconcile/resume re-verification, a resolvable continuation
engine, and the checkout's ownership lock -- which is also how the predecessor
controller is established not to be live. Every failure refuses by name
(`refused_not_recoverable`) and changes nothing at all.

On success, and only then, one effect is new: the already-reconciled
predecessor dispatch marker is *retired*, after the resumed Run snapshot and
its checkpoint are durable and before any later dispatch is permitted.
Without that the engine would re-enter its stale-marker branch and
re-reconcile the same uncertain Hop forever. Retiring it enables no replay --
the interrupted Hop's id stays in history, so the next dispatch takes the
following sequence with a fresh invocation identity -- and loses nothing,
because the predicate proved no staged evidence refers to it. A continuation
launch that then fails restores the Run, the checkpoint *and* the marker to
their exact pre-recovery bytes, records the rollback and refuses by name.

What this does *not* do, by design: it does not adopt, reset or clean an
uncommitted candidate (an interruption that left one is refused by name -- the
candidate is salvage material and a maintainer judgement, outcomes 2 to 4
above); it does not diagnose or change the *cause* of the interruption, so an
environmental cause that persists will interrupt the next Hop too, charged and
bounded by the Hop budget; it never resumes automatically; and it charges
nothing for itself.

`wfc status`, `wfc run` and `wfc resume` print one `RECOVERY <n>:` block per
recovery actually performed on this checkout (class, Run, phase, the
interrupted Hop, the Hops charged at the resume and what was proven), read
from the checkout's own append-only journal; a rolled-back attempt is not
reported as a recovery, while its journal records remain as its trace. The
archived `audit.json` carries the Run's `reconcile_reason` from a closed set,
and `wfc report` uses it to name `wfc resume --preview` for this class instead
of the generic "reconcile the Run's conflicting state".

[[budget-extension]]
=== Recorded maintainer Hop-budget extension (`wfc extend-budget`)

The second bounded, already-implemented in-place continuation, and the only
one that *requires* a human decision rather than replacing one: a Run that
stopped `awaiting_human_budget` (`stop_reason=autonomous_hop_budget_exhausted`)
can be continued on an explicit, recorded maintainer authority, without a
successor Commission and without its own new review chain. The decisions,
the rejected alternatives and the honest limits are in
link:{operator-docs}/backlog/FTR-WFC-STOPPED-RUN-CONTINUATION-ECONOMY.adoc#design[the
record's `Design` section]; this section is the normative operator contract.

[source,shell]
----
wfc extend-budget --additional-hops 3 \
  --authority "Maintainer instruction of <date> in this session: <the instruction>" \
  [--preview]
----

Both value arguments are required: no default amount, no default statement.
Before any mutation -- and as the whole of `--preview`, which takes no lock
and changes nothing -- the command prints one confirmation block naming the
Run id, the WorkItem, the phase, the Hops used of the current ceiling, the
admitted and current ceiling, the requested amount, the resulting ceiling,
both bounds with this Run's consumption of them, the policy ceiling, and the
authority statement with its SHA-256.

*What is recorded.* The Run keeps `hop_limit` as its one enforced effective
ceiling and gains an append-only `budget_extensions` entry stating who/what
authorised the grant, when, how much, and against which Run state (status,
stop reason, used Hops and end HEAD at the grant). The admitted
`WorkItem.max_autonomous_hops`, the compiled Commission files and the
Commission digest are *never rewritten* -- the digest is re-verified
unchanged before anything is recorded, so the original admission stays
verifiable and the ceiling admission judged stays reconstructible from the
Run as `hop_limit` minus the recorded grants.

*What it never does.* Reset or refund a charged Hop (`WFC-AUTO-05`; a Run
whose used Hops fell below a recorded grant's own charge is refused on the
wire, so this is a persistence invariant, not a convention); change Hop
charging; change Finding authority. Nothing on the path reads, writes, opens
or closes a Finding. An *open blocking Finding does not block an
extension* -- continuing the Run's own review/correction chain is the only
thing that may dispose of it, and only the independent reviewer ever does.

*The bounds*, all enforced before any effect: at most *four Hops per call*
(one `robust@v1` correction cycle is three Hops -- Worker correction, focused
review, renewed broad review -- plus one further Worker Hop; more in one step
is new work and belongs in a Commission authored as one); in total at most
*half the admitted ceiling, rounded up*, computed from the Run's own record
so repeated small grants cannot creep past it; and never above the admitted
repository policy's `max_autonomous_hops` (re-derived from this checkout's
cached, digest-verified Commission, never from the live `.wfc/config.yaml`)
nor above the hard Coordinator maximum of 64.

*Every refusal is named and changes nothing at all* (classification
`refused_budget_extension`, exit `34`): any classification other than
`awaiting_human_budget`; a Run that is not actually out of budget, whose
stop reason is not the exhausted budget, or that carries a frozen semantic
stop (that Run needs the human's answer, and where eligible the
`prepare-successor` channel, not more budget); an amount outside any bound;
an empty authority statement, one shorter than 40 characters once whitespace
is collapsed, or a bare authorisation gesture (`yes`, `--yes`, `approved`)
in place of a statement of the instruction; a moved HEAD; a worktree that is
not clean with resolved submodules; a changed Commission or execution-envelope
identity; a changed provider or absent engine executable; an already-active
lifecycle in this checkout. A continuation engine that resolves and then
fails to spawn rolls the Run and checkpoint back to their pre-extension
state and records `budget_extension_rolled_back`; the grant and its rollback
both stay in the append-only journal, and because the grant is no longer in
the Run it consumes none of the total bound.

*Visibility.* `wfc status` prints a `BUDGET EXTENSION <n>:` block per grant;
`wfc report` renders a `budget ext` line per grant and, for a budget stop,
names this command as the next human choice; `audit.json` carries the grants
*structurally* -- amount, ceilings, used Hops, time and the statement's
SHA-256, deliberately not its free text, because the sanitized projection is
default-deny and must not let a free-text sentence decide whether a Run is
archivable; the archived raw `run.json` carries the verbatim statement, which
the digest ties to the projection. A continuation attempt's own archive uses
the same distinct, collision-free `-recovery-<n>` destination mechanism as a
mechanically recovered continuation.

*What this cannot enforce, stated plainly.* Nothing at this CLI can
distinguish a human-instructed extension from an invented one: whoever can
run `wfc` can pass both arguments, and a Level-1 operator is itself an agent
that already passes `--yes` for launches. Technical prevention is impossible
at this surface and is not claimed. The controls are the recorded authority
statement (a false one is a durable, attributable false claim in the record
the maintainer reads), the Agent Skill rule that an agent never extends a
budget without the maintainer's explicit instruction in the current session
and says so in its report, the visibility above, and the bounds, which make
the worst case finite and small rather than open-ended.

*What stays separate.* `wfc resume` gains nothing: a budget stop still falls
through to its unchanged no-op, and a mechanically recoverable stop with no
Hop left still refuses by name (`no autonomous Hop budget remains for a
continuation`). `prepare-successor` stays categorically ineligible for a
budget stop. Extending a Run that is *both* budget-exhausted and
mechanically recoverable is deliberately not wired here; it belongs to
link:{operator-docs}/backlog/beta2_operator_efficiency_plan.adoc#o10[Beta-2
slice O10].

== Canonical salvage procedure (outcome 2)

=== Freeze before mutation

Before changing repository history:

* verify exact current HEAD and the expected baseline/parent;
* capture `git status --porcelain=v1 --untracked-files=all`;
* establish the exact modified path set and compare it against the
  predecessor WorkItem's authorized scope;
* capture `git diff --stat` and a full binary-safe diff, and compute its
  SHA-256;
* run `git diff --check`.

Dirty agent-produced code is not run merely to make salvage appear valid.
Tests are useful evidence only if they were already trusted Run evidence.

=== Archive predecessor truth before Git salvage

Where a mechanical Run archive exists, archive the stopped Run -- saying
exactly what happened (uncertain Hop, absent candidate/trusted commit, dirty
tracked state, `reconcile_required`) -- before changing Development HEAD.
Never mutate the historical Run to point at the later salvage commit; the
salvage commit is a later, separate maintainer event.

=== Preserve exact WIP in Git

If provenance/scope checks pass, stage exactly the frozen candidate paths
and commit them without content repair, under an explicitly
non-authoritative subject such as `wip(...): preserve interrupted
<WorkItem/Hop> candidate`. The commit body identifies the source Attempt,
Run, Hop, baseline HEAD, why normal Hop authority was not established, and
that the commit is maintainer-owned preservation only. The commit may
represent a known-red or incomplete state -- a salvage commit is
history/provenance, not an accepted executable baseline, so it is never
cleaned up to look green.

=== Verify exact preservation

Reproduce the diff from the original baseline to the salvage commit and
compare its digest against the frozen precommit diff. The invariant:

`salvage commit delta == frozen dirty candidate delta`

Stop and investigate on any mismatch.

=== Fresh successor Commission

A successor is separately commissioned; predecessor governing inputs are
never mutated to retrofit continuation. The successor's execution starting
point may contain the salvage commit, but

`execution starting point != assurance baseline`

The successor task states that every salvaged line is unverified candidate
material, free to be kept, altered, removed, or replaced within the
successor's own newly authorized scope. Preservation is never required for
its own sake; the successor worker owns every retained line through fresh
inspection and its own trusted Hop result.

Do not rewrite or "repair" historical terminal Run state. If additional
authorized work is genuinely needed, the continuation decision is:

[source,text]
----
archive the original Run truthfully
    -> curate the ledger, if convention requires it
    -> make a fresh maintainer decision
    -> create a separately authorized successor Commission / Attempt
----

A successor may reference predecessor evidence but must never fabricate a
different historical outcome for it. This applies both to an unclean
Run/Hop and to a Run that completed with an authority gap; see
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal states and awaiting_human]
for that distinction.

=== Independent review after salvage

The fresh reviewer evaluates the complete resulting product against the
real assurance baseline, including salvaged ancestry -- never merely the
latest correction, the successor's delta, or the delta after the salvage
commit. Salvage ancestry grants no correctness credit.

=== Patch role

For a coherent, attributable, entirely in-scope candidate intentionally
carried into the next Run, the Git salvage commit is the primary handoff
mechanism; a patch may still be retained as forensic backup or a recovery
aid, but does not become a third competing truth source. For ambiguous or
out-of-scope states (outcome 3), external patch/forensic preservation is
preferable precisely because an ordinary salvage commit would overstate
provenance. Git remains the durable work/provenance trail.

== Authority statement

A salvage commit IS: durable Git provenance, exact (or explicitly
classified) preservation of candidate work, and input a later separately
authorized worker may inspect.

A salvage commit IS NOT: a retroactive successful predecessor Hop, a trusted
WFC commit, a reconstructed candidate result, trusted evidence, review,
acceptance, Finding disposition, a scope grant, Runtime promotion, or
authorization for a successor Run.

Semantic acceptance/reuse of candidate material as trusted Hop output is
never authorized. That is a different statement from explicit maintainer
preservation of the exact same material as non-authoritative Git history,
which is the established practice this document canonicalizes. The two do
not contradict each other.

== Non-automation boundary

This procedure is maintainer-owned throughout. WFC does not automatically
decide candidate value, widen scope, commission successors, resume stopped
Runs, or select between same-Run resume and a fresh successor. Those remain
explicit maintainer acts; future product automation would require separate
design, review, and authority, none of which this document creates. The
recorded Hop-budget extension (<<budget-extension>>) is not an exception to
this: it is a *command for* an explicit maintainer decision, never an
automatic one, and it records the authority it was given.

One bounded, already-implemented exception to "WFC does not ... create
salvage commits": `frontdoor.preservation` creates an automatic,
non-authoritative candidate commit on a fixed set of stop classifications
(`interrupted`, `awaiting_human`, `awaiting_human_budget`,
`reconcile_required`, `stopped`), wired into `wfc run`/`resume`'s own
postrun step. Its own module docstring is explicit that this "does not
replace the manual salvage/successor procedure" above; it grants no
adoption, acceptance, scope widening, Finding transfer or review credit, and
the outcome-2 canonical salvage procedure in this document remains the
maintainer's own distinct act, whether or not an automatic candidate commit
already exists for the same stop.

== Relation to adjacent mechanisms

* link:{operator-docs}/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[`FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`]
  defines same-Run reconcile/resume (outcome 1) and its own narrower,
  evidence-gated same-Hop-retry question. It is a different mechanism from
  maintainer salvage and is not restated or widened here.
* link:{operator-docs}/backlog/BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc[`BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc`]
  records a distinct, adjacent case -- a mid-Hop scope escalation leaving
  useful uncommitted work -- and the separately implemented `export-salvage`
  / `prepare-successor` operator mechanism it commissioned. That mechanism
  packages predecessor candidate material as an explicitly untrusted,
  content-addressed bundle for a successor checkout; it is a different,
  already-productized tool for a different triggering scenario, not the
  Git-commit-based procedure documented here, and this document neither
  restates nor supersedes it.
* Runtime promotion (see
  link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc[Runtime promotion]) is independent of both:
  a salvage or WIP commit on Development `main` is never promoted merely
  because it is on `main`.

The productized `prepare-successor` path requires a schema-v2 predecessor
in `awaiting_human`, a frozen semantic stop naming an existing source Hop,
and a Run snapshot matching its already-published checkpoint identity.
It also admits a clean successor checkout at an exact baseline under newly
pinned governing inputs and an explicit maintainer authority decision.
`reconcile_required` and `awaiting_human_budget` do not satisfy predecessor
eligibility: `prepare-successor` is not a repair for those states, and this
is unchanged by <<budget-extension>>, which continues the *same* Run in
place instead of admitting a successor. An
`export-salvage` bundle alone grants neither that eligibility nor authority
and does not turn the manual Git-preservation path into automated recovery.
