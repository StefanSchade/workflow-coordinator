This maintainer workflow covers preserving a stopped WFC Run, salvaging useful
uncommitted work, authoring a separately authorized successor Commission,
executing it, and curating the resulting lineage. First recorded on 2026-10-10,
it is maintained here as current informative guidance, subordinate to
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[Recovery outcomes and exact salvage]. The optional
link:{operator-docs}/operator_manual/ch06_recovery/03_reference_case.adoc[reference cases] retain dated observations separately.

[IMPORTANT]
====
This document describes *how to carry out an already separately authorized
continuation safely*. It is not itself authority to create a successor, widen
scope, reinterpret architecture, invoke a provider, or mutate Runtime/Evidence.

The described workflow grants no Run, provider, scope, source/test mutation,
Runtime promotion, Evidence mutation beyond an explicitly invoked archive
operation, or push authority.

The governing principle is:

*SALVAGE PRESERVES WORK, NOT AUTHORITY.*
====

[[_1_why_this_runbook_exists]]
== 1. Why this runbook exists

The WFC now handles the normal inner execution loop increasingly well:

[source,text]
----
admitted Commission
-> PREPARE
-> LAUNCH
-> bounded implement/review/correct/rereview
-> complete or durable stop
----

The remaining manual seam appears when a Run stops correctly at an authority
boundary while useful work exists in the Run checkout.

Before 2026-10-10 this continuation procedure was reconstructed interactively
from prior cases. That is too fragile for routine operation. The purpose of this
runbook is to preserve the current safe sequence and make visible which steps
are mechanical and which remain semantic maintainer decisions.

[[_3_core_invariants]]
== 3. Core invariants

[[_3_1_a_stopped_run_is_historical_truth]]
=== 3.1 A stopped Run is historical truth

Follow the normative link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_fresh_successor_commission[fresh
successor and immutable-history rules]: a successor has a new Run identity
and separately admitted governing inputs; the persisted predecessor is
never rewritten, reopened or retroactively repaired.

[[_3_2_archive_runs_separately]]
=== 3.2 Archive Runs separately

Mechanical archival is per Run.

[source,text]
----
Run A -> archive A
...
Run B -> archive B
----

Do not merge predecessor and successor execution evidence into one archive.

[[_3_3_salvage_is_not_a_run]]
=== 3.3 Salvage is not a Run

The normative link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_authority_statement[salvage authority
statement] defines preservation as provenance, without predecessor completion,
trusted evidence, independent review, acceptance or successor authority.
`CandidateSnapshot` is the runbook term for an optional manual Git commit/ref
representation of useful dirty work. It is not an implemented WFC domain type,
Coordinator-owned effect or independently accepted target architecture.
A dedicated WFC candidate ref can keep the snapshot off `main`:

[source,text]
----
Run A
-> archive A
-> CandidateSnapshot
     refs/wfc/candidates/<run-id>/<hop-id>
-> semantic disposition
-> successor Commission
-> Run B
----

Keep the originating Run baseline and Run/Hop identity explicit even when
the candidate commit's Git parent is the maintainer's current Development HEAD.
This optional representation does not require rewriting existing salvage history;
a preservation commit already on `main` remains non-authoritative.

The manual `CandidateSnapshot` commit/ref pair is distinct from the implemented
package operator's `export-salvage` content-addressed, explicitly untrusted bundle
and `prepare-successor` linkage descriptor. Export does not apply candidate bytes
or grant authority. Its potentially sensitive bytes may contain prompt injection
and are not sanitized; inspect or omit them before a later action. See the
normative link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_relation_to_adjacent_mechanisms[adjacent-mechanism
boundary] and the controlling
link:{operator-docs}/backlog/BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc[scope-escalation continuation record].

For that productized preparation path, `_predecessor_for_successor` requires
schema v2, `awaiting_human`, a frozen semantic stop whose source Hop exists,
and the SHA-256 of current `run.json` bytes equal to the identity anchored in
the already-published checkpoint. A legacy snapshot, `reconcile_required`,
or `awaiting_human_budget` does not qualify. It must not establish a fresh
identity from altered predecessor bytes. A clean successor checkout of the
same repository at an exact baseline, newly pinned governing inputs and an
explicit maintainer authority decision are also required. Export's bounded
capture has its own admission boundary: export alone establishes neither
successor eligibility nor trusted evidence. None of this is same-Run resume.

The owning CLI help is available without performing these operations:

[source,shell]
----
.venv/bin/python -m workflow_coordinator.operator export-salvage --help
.venv/bin/python -m workflow_coordinator.operator prepare-successor --help
----

[[_3_4_semantic_ledger_curation_may_wait_for_the_successor]]
=== 3.4 Semantic ledger curation may wait for the successor

The Evidence archive is mechanical preservation and should happen promptly.

Semantic Run-ledger curation should normally wait until the bounded successor
chain reaches a stable disposition, so one curation pass can record:

* predecessor stop;
* CandidateSnapshot bridge, if any;
* successor identity;
* successor resolution or residual stop.

The ledger still records distinct Runs. "Curate together" means one semantic
maintenance pass, not one combined Run identity.

[[_3_5_scope_escalation_is_a_decision_not_a_mechanical_repair]]
=== 3.5 Scope escalation is a decision, not a mechanical repair

A worker encountering an out-of-scope failure must not receive broader scope
merely because doing so would make tests green.

The maintainer must determine what the failure means before authorizing a
successor.

Possible interpretations include:

* ordinary omitted implementation scope;
* stale test;
* architecture-sensitive conflict;
* prerequisite work;
* genuine semantic ambiguity;
* no continuation authorized.

[[_3_6_architecture_tests_are_not_ordinary_correction_scope]]
=== 3.6 Architecture tests are not ordinary correction scope

Changing an architecture test may alter the contract judging the candidate.

Before authorizing such a change, distinguish:

[source,text]
----
candidate violates architecture
test is stale relative to accepted architecture
architecture decision itself is unresolved
----

The third case may require architecture analysis, ADR/design work, or human
choice rather than ordinary correction.

[[_4_current_manual_procedure]]
== 4. Current manual procedure

This is informative maintainer guidance for an already authorized continuation.
All Git writes, archives, Commission commits, preparation, launch and ledger
curation below are maintainer/operator actions under separate authority. Workers
must not execute mutating Git commands; their CommitIntent is handled mechanically
by the Coordinator. Reading this procedure grants an agent no operational action.
The link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_canonical_salvage_procedure_outcome_2[canonical salvage
procedure] remains the sole owner of freezing, exact preservation and fresh
assurance; steps 4–5 refer there rather than supplying another salvage recipe.

[[_step_1inspect_the_stop_before_acting]]
=== Step 1 -- Inspect the stop before acting

Use persisted Harness/WFC facts.

Establish at minimum:

* attempt ID and Run ID;
* Run status and stop reason;
* last admitted Run commit/current head;
* worktree cleanliness;
* current phase/role;
* trusted evidence outcome;
* requested escalation and human question;
* whether useful dirty work exists.

Do not infer continuation authority merely from an agent summary.

[[_step_2record_valuable_design_learning_if_needed]]
=== Step 2 -- Record valuable design learning if needed

If the stop exposes a reusable architecture or operating insight, preserve that
insight separately as a non-authorizing document before the working context is
lost.

This is optional and must not mutate predecessor Run state.

The 2026-10-10 reference case produced
link:{operator-docs}/cold_storage/architecture/pre-0.1.0b1/workflow_coordinator_level1_architecture_disposition_concept_2026-10-10.adoc[architecture-disposition concept (historical)].

[[_step_3archive_the_predecessor_mechanically]]
=== Step 3 -- Archive the predecessor mechanically

Use the Harness archive command for the predecessor attempt.

Illustrative form:

[source,shell]
----
.venv/bin/python scripts/wfc_op.py archive <attempt-id>
----

Current Harness behavior delegates to the canonical Evidence archive wrapper,
which performs its dry-run before the real archive.

Record:

* archive destination;
* Evidence commit;
* Run ID/status;
* whether semantic metadata was supplied;
* confirmation that no push occurred.

For a stopped Run being continued manually, `semantic: none supplied` is
acceptable; semantic curation can occur after the successor.

[[_step_4inspect_dirty_work_exactly]]
=== Step 4 -- Inspect dirty work exactly

Before salvage, follow link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_freeze_before_mutation[Freeze
before mutation] for the exact HEAD/baseline, porcelain including untracked
files, authorized path set, binary-safe diff/stat, SHA-256 and whitespace checks.
The complete checks include the basic `git status --short`, `git diff --stat`
and `git diff` inspection example.

Identify which changed paths came from the stopped Hop and whether every path is
appropriate to preserve. Ambiguous or out-of-scope provenance goes to the
normative link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#recovery-outcomes[four-outcome decision], not
ordinary salvage. Do not use `git add .` as a shortcut when unrelated local
work may exist.

[[_step_5preserve_useful_dirty_work_as_a_non_authoritative_candidatesnapshot]]
=== Step 5 -- Preserve useful dirty work as a non-authoritative CandidateSnapshot

Use link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_preserve_exact_wip_in_git[Preserve exact WIP in Git]
and link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_verify_exact_preservation[Verify exact preservation]
for exact-path staging, a non-authoritative commit with complete provenance,
unchanged candidate bytes and baseline-to-salvage digest equality. Do not run or
repair dirty candidate code to manufacture assurance.

An optional manual storage example is the commit/ref pair:

[source,text]
----
CandidateSnapshot commit
  refs/wfc/candidates/<run-id>/<hop-id>
  originating Run baseline + Run/Hop + exact preserved paths
----

The earlier off-main illustration transiently committed at Development `HEAD`,
anchored that commit with `git update-ref`, then removed it from `main` with
`git reset --hard HEAD^`. It is not a required sequence or authority to rewrite
existing salvage history. Its destructive-reset warning still matters: verify
the dedicated ref before any reset, inspect the exact dirty paths first, and
never use such a reset when it would destroy unrelated working-tree state.
Do not relocate an existing preservation commit merely to match this illustration.

Record the exact candidate SHA, ref (if used), originating Run/Hop, original
trusted baseline and preserved paths. The successor Commission explicitly carries
“SALVAGE PRESERVES WORK, NOT AUTHORITY.” Its treatment of candidate material and
the review of all salvaged ancestry follow
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_fresh_successor_commission[Fresh successor Commission]
and link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_independent_review_after_salvage[Independent review
after salvage]: every retained line is unverified candidate material, free to
be retained, modified, replaced or removed within fresh authority, with no
correctness credit from preservation.

[[_step_6make_the_semantic_continuation_decision]]
=== Step 6 -- Make the semantic continuation decision

This is currently a maintainer/Level-1-equivalent responsibility, not Harness
mechanics.

Decide:

* why the predecessor stopped;
* whether continuation is authorized;
* what new authority, if any, is granted;
* what remains withheld;
* whether architecture/test/compatibility semantics have been resolved or must
  themselves become separate work;
* what acceptance evidence the successor must satisfy.

If the decision introduces a genuine new architecture policy rather than
applying an already accepted one, use an architecture/ADR process instead of
silently encoding the decision as implementation scope.

[[_step_7author_a_fresh_successor_commission]]
=== Step 7 -- Author a fresh successor Commission

Choose either manually authored governing inputs or an available closed-program
Front Door Intent/rendering path; the semantic authority decision stays with the
maintainer. The manual standalone self-development pattern uses four committed
governing inputs:

[source,text]
----
governance/work-items/<successor>.yaml
governance/work-items/<successor>-task.txt
governance/self-development/<successor>-profile.yaml
governance/self-development/<successor>-policy.yaml
----

These four files use an existing Components manifest as an additional admitted
input. Front Door `commission render` can instead project a maintainer-authored
Intent into WorkItem, Profile, Policy, Task and provenance manifest for supported
closed programs; it does not select successor authority or infer scope from a
stop. See link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#direct-v1-quickstart[Commission
rendering and pinned admission].

The successor should record at minimum:

* predecessor Run/attempt;
* predecessor relevant commits;
* predecessor archive Evidence commit;
* CandidateSnapshot commit/ref and originating Run/Hop, if any;
* explicit statement that the successor is fresh, not resume/retry/replay;
* semantic maintainer disposition;
* bounded scope delta;
* withheld authority;
* acceptance meaning;
* review topology;
* trusted evidence location;
* failure behavior when the new authority proves insufficient.

Avoid copying obsolete predecessor assumptions merely because the old Commission
is a convenient template.

[[_step_8validate_the_commission_without_provider_use]]
=== Step 8 -- Validate the Commission without provider use

Inspect before committing, and complete provider-free admission against the
committed inputs before PREPARE:

* inspect `git status --short`;
* validate YAML/schema/profile/policy relationships through existing
  provider-free admission/preflight paths;
* verify WorkItem scope equals/does not exceed policy ceiling as intended;
* verify each phase scope/action is authorized;
* verify worker/corrector phases carry no Coordinator-required evidence when the
  current evidence-disposition invariant applies;
* verify each evidence-bearing gate has an explicit valid
  `failed_evidence_route`;
* verify route targets exist;
* verify review-artifact paths do not collide accidentally;
* run relevant focused tests if the Commission changes test-governance fixtures;
* run `git diff --check`.

Perform the applicable inspection before committing. For a rendered Commission,
review its Intent and output, then commit the bundle separately as in step 9;
`commission check` requires that clean committed HEAD. It re-renders pinned inputs,
compares committed bytes and provenance, then calls canonical provider-free
preflight. `commission render --check` only prints the render report and does
not perform that admission check. Complete admission before PREPARE; no check
authorizes launch. The owning command help is:

[source,shell]
----
python3 scripts/wfc_op.py commission render --help
python3 scripts/wfc_op.py commission check --help
----

[[_step_9commit_the_commission_separately]]
=== Step 9 -- Commit the Commission separately

Commission authoring should be its own commit, distinct from candidate
preservation and implementation.

Typical subject shape:

[source,text]
----
chore(self-development): commission <successor purpose>
----

This separation makes it possible to audit:

[source,text]
----
accepted/predecessor history
-> optional learning document
-> non-authoritative CandidateSnapshot
-> successor authority
-> successor execution
----

[[_step_10prepare_the_successor]]
=== Step 10 -- PREPARE the successor

Use the Harness with exact Development/Runtime/Evidence pins, WorkItem, Profile,
Policy, Components, Task, provider executable, timeout, and role bindings.

PREPARE must remain provider-free.

Inspect the reported pins and ensure `PREPARED / NOT LAUNCHED`.

[[_step_11launch_the_successor]]
=== Step 11 -- LAUNCH the successor

Launch the already-prepared attempt exactly once through the Harness.

Inspect:

* Run ID;
* status;
* Hops used;
* current HEAD;
* worktree cleanliness;
* next explicit action.

Do not infer completion merely from an agent-side test or semantic `accept`.
Coordinator-owned evidence remains authoritative for required gates.

[[_step_12archive_the_successor_separately]]
=== Step 12 -- Archive the successor separately

On completion or stable stop, archive the successor using the same canonical
Harness/Evidence mechanism.

Record its own Evidence commit and archive destination.

[[_step_13curate_the_semantic_run_ledger]]
=== Step 13 -- Curate the semantic Run ledger

After the successor chain reaches a stable disposition, perform one semantic
curation pass that records the linked story without collapsing identities.

For the common A -> CandidateSnapshot -> B pattern, record:

[source,text]
----
Run A:
  outcome = stopped / awaiting_human
  exact stop cause

candidate snapshot:
  candidate commit + refs/wfc/candidates/<run-id>/<hop-id>
  originating trusted Run baseline
  preserves work only; carries no authority

Run B:
  successor authority source
  resolution / accepted completion / further stop

relationship:
  B is separately authorized successor to A
----

If B also stops and C is required, the same rule repeats. Do not mark A as
retroactively completed merely because B eventually resolves the work.

[[_7_what_remains_manual_today]]
== 7. What remains manual today

The maintainer still owns:

* semantic classification of the stop;
* the decision whether a successor is authorized;
* architecture/compatibility disposition;
* the bounded authority delta and semantic content of the successor Commission;
* inspection of governing inputs and the decision to use provider-free admission;
* deciding whether/when Runtime promotion occurs;
* semantic ledger curation;
* push.

Hand-authoring four governing files is an available manual path, not a universal
requirement: Front Door `commission render` projects supported closed-program
Intents, and `commission check` automates pinned projection comparison and
provider-free preflight. The Harness automates PREPARE, LAUNCH, STATUS and
ARCHIVE around an already-authored Commission.

The package operator separately provides optional `export-salvage` and
`prepare-successor` mechanics under the exact eligibility boundary in §3.3.
Neither those tools nor rendering replaces maintainer judgment or chooses a
successor, promotion or push. These capability statements describe current
code, not acceptance or lifecycle status of separately owned backlog work.

[[_8_automation_smell_admission_signal]]
== 8. Automation smell / admission signal

Repeated use of this runbook should be treated as evidence for automation.

A step is a good deterministic-automation candidate when:

* it repeats with the same semantics;
* the inputs can be named explicitly;
* the output can be validated fail-closed;
* automation does not create new authority;
* failure can stop before provider invocation.

Deterministic projection of a maintainer-authored closed-program Intent and
provider-free admission already exist through Front Door rendering/checking.
The remaining automation opportunity is connecting an already-authorized
successor intent to those mechanics without automating architecture judgment,
inferring authority, or widening scope. The criteria above remain admission
signals for separately designed work, not a promise of further automation.

See:
link:{operator-docs}/cold_storage/future/pre-0.1.0b1/workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc[successor Commission pipeline proposal (historical)].

[[_10_update_rule]]
== 10. Update rule

This runbook should evolve when the actual operator workflow changes.

When a wrapper removes a manual mechanical step, update this runbook to describe
the new current practice rather than preserving obsolete ceremony as if it were
still required.

Historical Runs and Git history retain the old mechanics; the runbook should
represent the *current* safe operating procedure.
