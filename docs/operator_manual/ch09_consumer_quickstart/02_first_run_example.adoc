[[consumer-quickstart-first-run-example]]
== Tutorial 1 -- a documentation change

This is the first of
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/00_overview.adoc#consumer-overview-tutorials[three
tutorials]. Read the
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-prerequisites[prerequisites]
and
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-install[install]
sections first. The demo kit (`examples/consumer-demo/` in this repository)
builds the whole layout below with one command; this page names exactly
which of its commands were actually executed to verify it, and which were
not.

[[consumer-quickstart-first-run-example-goal]]
=== Goal

This tutorial walks through one complete bounded task, from a freshly built
demo workspace to an archived Run, naming the plan/authorization/run/
archived-evidence distinction that every Run shares. It uses `simple@v1`:
one Worker role and no review phase -- Tutorial 2 adds the second.

[[first-run-layout]]
One command, `make_workspace.py`, creates three siblings outside any Git
work tree: `greeter/` (the repository being modified), `greeter-evidence/`
(its Evidence repository) and `requests/` (rendered task documents and
Consumer Requests). See the
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/00_overview.adoc#consumer-overview-workspace-map[overview's
workspace map] for the complete picture, including the worktree and
rehearsal-only directories this tutorial does not yet need.

[[first-run-repository]]
Inside `greeter/`: `greeter/core.py` (a tiny `greet()` function),
`tests/test_core.py` (its unit test), `docs/notes.adoc` (one AsciiDoc page)
and `checks/check.sh` -- the one trusted check, which runs the unit tests
and then asserts that every AsciiDoc file under `docs/` starts with a
level-0 title. A `.gitignore` excludes `+__pycache__/+` so running the check
never leaves the tree unclean (Tutorial 2 explains why that matters).

[[first-run-init]]
`make_workspace.py` also runs `wfc init` for you, with
`--scope-ceiling greeter --scope-ceiling tests --scope-ceiling docs`, and
commits the resulting `.wfc/config.yaml`. See
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-init[`wfc
init` and configuration] for what this step means on your own repository,
where you run it yourself.

[[consumer-quickstart-first-run-example-task]]
=== The task

[[first-run-task]]
The kit renders `requests/t1-hello-page.task.md` and
`requests/t1-hello-page.request.yaml` from these templates, substituting
the guidance commit:

// kit: requests/t1-hello-page.task.md
[source,markdown]
----
# Hello page

Create `docs/hello.adoc` whose first line is `= Hello`, followed by one sentence.

## Acceptance

The task-check passes and `docs/hello.adoc` exists with first line `= Hello`, followed by one sentence.

## Withheld authority

No change outside `docs/hello.adoc`.

## Default escalation

Stop and ask if the task cannot be completed inside the authorized scope.
----

[[first-run-request]]
// kit: requests/t1-hello-page.request.yaml
[source,yaml]
----
schema_version: 1
commission_id: t1-hello-page-001
work_item_id: WI-T1-HELLO-PAGE-001
authority_source: The workspace owner authorizes this bounded demo task.
program:
  id: simple
  revision: v1
task:
  title: Hello page
  body: >-
    Create `docs/hello.adoc` whose first line is `= Hello`, followed by one
    sentence.
  acceptance: >-
    The task-check passes and `docs/hello.adoc` exists with first line
    `= Hello`, followed by one sentence.
  withheld_authority: No change outside `docs/hello.adoc`.
  escalation_default: Stop and ask if the task cannot be completed inside the authorized scope.
scope:
  - docs/hello.adoc
personas:
  worker: Implement exactly the authorized scope; stop and escalate rather than guess beyond it.
evidence:
  argv: [sh, checks/check.sh]
  timeout_seconds: 300
max_autonomous_hops: 3
durable_artifacts: {}
guidance:
  path: .wfc/governance/repository-policy.md
  source_commit: '{{GUIDANCE_COMMIT}}'
----

`scope` names exactly one file; `evidence.argv` is the check command shown
above, run both as the pre-launch baseline probe and as the Commission's
`task-check`; `{{GUIDANCE_COMMIT}}` is substituted by the kit with the
commit that added `.wfc/governance/repository-policy.md`, resolved the same
way `wfc plan --guidance-path` resolves it on your own repository (see
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-request[writing
a request]).

[[consumer-quickstart-first-run-example-look-at]]
=== What to look at

[[first-run-status]]
After a rehearsal, `rehearse.py` itself prints these (also real output,
abridged):

* `git -C greeter-run-t1-hello-page log --format='%h %an %s'` -- two new
  commits on top of the seeded tree: the Commission commit
  (`feat(commission): commission t1-hello-page-001 ...`) and the payload
  commit (`docs: WI-T1-HELLO-PAGE-001 H001 add the hello page`). Proves the
  Commission and the change are two separate, Coordinator-made commits.
* `wfc report <archived attempt dir>` -- prints the same
  `outcome`/`commits`/`evidence`/`findings`/archive summary shown above.
  Proves the archived record matches what `wfc run` itself reported.
* `HOME=<rehearsal-home> wfc status --repository greeter-run-t1-hello-page`
  -- prints `CLASSIFICATION: completed` again, read-only. Proves `wfc
  status` is safe to run repeatedly after a Run has finished.
* `python3 -m greeter Ada` inside the worktree -- unaffected by this
  tutorial's change, since the task touched only `docs/hello.adoc`; proves
  the scope stayed exactly where the Commission said it would.

[[consumer-quickstart-first-run-example-run]]
=== Run it live

[[first-run-run]]
For a live Run, use your own fresh worktree of the kit's `greeter`, never
the rehearsal worktree above:

[source,shell]
----
cd ~/wfc-demo
git -C greeter worktree add ../greeter-live-t1 -b live/t1 main
cd ../greeter-live-t1
wfc plan ../requests/t1-hello-page.task.md --repository . --scope docs/hello.adoc \
  --commission-id t1-hello-page-001 --work-item-id WI-T1-HELLO-PAGE-001 \
  --authority-source "The workspace owner authorizes this bounded demo task." \
  --program simple@v1 \
  --persona worker="Implement exactly the authorized scope; stop and escalate rather than guess beyond it." \
  --evidence-argv sh --evidence-argv checks/check.sh --evidence-timeout 300 \
  --max-autonomous-hops 3 \
  --guidance-path .wfc/governance/repository-policy.md --guidance-commit <the kit's guidance commit>   # read-only preview
wfc run --repository . --request ../requests/t1-hello-page.request.yaml \
  --executable claude \
  --execution-override worker.adapter=claude_cli \
  --execution-override worker.model=<your model> \
  --execution-override worker.reasoning=medium
----

For `codex_cli`, pass `--executable codex` and
`--execution-override worker.adapter=codex_cli` instead; every other
tutorial in this chapter gives only the `claude_cli` form and expects you to
make the same substitution. The live `wfc run` above is shown *without*
`--yes`, so you answer the authorization prompt yourself; `rehearse.py`
is the only place `--yes` appears in this chapter.

[[first-run-concepts]]
==== Plan, authorization, run, and archived evidence

Four distinct things happen, or were prepared, above; keep them separate:

Plan (read-only preview):: `wfc plan` writes nothing, runs no project
command, and never touches Git. It only projects the Commission bytes and
resolves the execution envelope it *would* compile.

Authorization (the human's explicit act):: Nothing is authorized merely by
having been previewed. `wfc run` requires explicit confirmation -- an
interactive `y`, or `rehearse.py`'s own `--yes` for its scripted,
non-interactive rehearsal -- immediately before it acquires the checkout's
ownership lock and starts mutating anything.

Run (the controlled lifecycle):: Once authorized, `wfc run` performs, in
order, a one-shot baseline probe, the Commission commit, re-verification,
engine launch, and however many Hops the Worker needs -- `simple@v1` has a
single Worker role and no review phase; `robust@v1` in Tutorial 2 adds one.

Archived evidence (the separate Evidence repository):: `greeter-evidence/`
is a distinct, remote-less Git repository that a terminal Run's facts are
archived into; it is never `greeter/` itself, and WFC never pushes either
one.

[[first-run-why-before-and-after]]
==== Why the check must pass before and after

`wfc run` executes the declared evidence command -- here, `sh
checks/check.sh` -- *before* any provider starts, as a mandatory baseline
probe against today's already-clean tree; a non-zero exit, an unresolvable
executable, a timeout, or any tree mutation there refuses the whole Run
before launch (classification `refused_probe`, exit code `23`) and still
consumes this checkout's one lifecycle; see
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc#quickstart-request[writing
a request] (Tutorial 3 rehearses exactly this).
The identical command is also the Commission's declared `task-check`
evidence, run again later to judge the actual result. `checks/check.sh`
runs the existing unit tests (true before and after this task, since the
task never touches `greeter/core.py`) and then asserts that every AsciiDoc
file under `docs/` starts with a level-0 title -- true now, on
`docs/notes.adoc` alone, and still true once `docs/hello.adoc` exists
alongside it.
