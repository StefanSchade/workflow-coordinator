[[consumer-quickstart]]
== Consumer quickstart

This is for someone who has *not* read the rest of this manual and is
applying WFC to their own, unrelated repository -- not WFC's own
development. It covers only installation through one inspected, archived
Run. For anything beyond that, follow the links below into the full manual.
See the
link:{operator-docs}/operator_manual/ch09_consumer_quickstart/00_overview.adoc#consumer-overview[chapter
overview] first for a map of the demo workspace and the three tutorials
this quickstart leads into.

[[quickstart-prerequisites]]
=== Prerequisites

* Git, and a completely clean working tree -- `wfc run` refuses a dirty tree.
* Python 3.10 or newer, to run `wfc` itself. Your own project's build and
  test tools are *yours* to install; WFC provisions nothing project-specific.
* An already-installed, already-authenticated provider CLI for the adapter
  you intend to use: `codex` for `codex_cli`, or `claude` for `claude_cli`.
  Confirm it resolves with `which codex` or `which claude`.
* A single check command of your own, already committed, that exits `0` on
  today's clean tree without changing anything -- `wfc run` executes it
  verbatim as a mandatory pre-launch baseline probe (see
  <<quickstart-request>>).
* A Git identity (`user.name`/`user.email`) visible in your effective Git
  *configuration* -- never only via `GIT_AUTHOR_*`/`GIT_COMMITTER_*`/
  `GIT_CONFIG_GLOBAL` environment variables -- and no configured
  `filter.*.clean`/`filter.*.process` (including Git LFS) reachable from this
  repository. See <<quickstart-git-identity-and-filters>> below for why and
  how to check.
* *Linux only:* `bwrap` (bubblewrap) is *not* required for ordinary
  `wfc init`/`plan`/`run` use with the Claude or Codex adapters while the
  optional execution boundary stays off (the default); see
  <<quickstart-bwrap-and-platform>>.
* `TMPDIR` (or the platform default temp location) pointing *outside* this
  repository's working tree for your own tooling's temporary files; a
  temporary base inside the repository can itself make the tree look dirty
  to `wfc run`'s clean-tree check.

[[quickstart-git-identity-and-filters]]
=== Git identity and filters

WFC's trusted Git operations -- the Commission commit, candidate
preservation, and `wfc run`'s bounded path commit -- strip every inherited
`GIT_*` environment variable before running Git, precisely so that an
agent-controlled process environment cannot smuggle in a different commit
identity or routing than the one your own Git configuration establishes. One
practical consequence: if you only ever set identity through
`GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_NAME`/
`GIT_COMMITTER_EMAIL` or `GIT_CONFIG_GLOBAL` environment variables rather than
Git configuration itself, that identity becomes invisible to these trusted
commits and Git falls back to its own defaults (or fails if none exist). Set
`user.name`/`user.email` in a configuration file Git actually reads instead
-- your normal global (`~/.gitconfig`) or system config, or, if `HOME`
changes between processes (for example an isolated test or CI environment),
a stable `$XDG_CONFIG_HOME/git/config`.

The same trusted operations also refuse outright whenever any effective
`filter.*.clean` or `filter.*.process` Git configuration is visible to them
-- including Git LFS's `filter.lfs.clean`/`filter.lfs.process` -- even if the
specific commit at hand would never have invoked that filter. This is a
deliberately conservative current product limit, not a bug: a worktree
`.gitattributes` entry can select a configured filter that the trusted-commit
path has no way to safely vet, so it refuses the whole class instead.
Diagnose it read-only before relying on trusted commits in a given
repository:

[source,shell]
----
git config --show-origin --get-regexp '^filter\..*\.(clean|process)$'
----

Any output means a repository that needs that filter cannot currently use
WFC's trusted commits. This is *not* advice to strip Git LFS or other filter
configuration from your own repositories in general -- those filters can be
functionally necessary for your project; it only means this specific
repository cannot combine them with WFC today. A follow-up backlog record
tracking relaxing this is planned.

[[quickstart-bwrap-and-platform]]
=== Bubblewrap and qualified platform

Installing the `workflow-coordinator` package never installs `bwrap`
(bubblewrap), and `bwrap` is *not* required for ordinary consumer use while
the optional execution boundary (`boundary: direct`, the default in the
execution envelope and in `.wfc/config.yaml`) stays off: `wfc init`, `wfc
plan`, and `wfc run` with either the Claude or the Codex adapter invoke the
configured provider CLI directly and do not themselves sandbox it with
`bwrap`. Setting `boundary: bubblewrap` opts a Run into the Coordinator-owned
Linux filesystem boundary (see
link:{operator-docs}/operator_manual/ch01_orientation/02_boundaries.adoc[orientation]);
it then requires `bwrap`, working unprivileged user namespaces, a configured
provider authentication location (`WFC_BOUNDARY_AUTHENTICATION_PATH`), and
the provider CLI installed at a view-visible path (for example under
`/usr/local/bin`), each checked by a named preflight refusal rather than a
silent fallback to unisolated dispatch. `bwrap` is also exercised by WFC's
own development test suite (see
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc[self-development
topology]) and by the host preparation `.github/workflows/release.yml` uses
for WFC's own hosted CI. If you do work with WFC's own source (see the
link:{operator-docs}/developer_guide/ch01_development.adoc[Developer Guide]),
note that installing the package alone does not guarantee working
unprivileged user namespaces on your host; the hosted CI runner needed an
explicit kernel setting to enable them for `bwrap` (see that workflow file).
No document claims preventive isolation for any invocation until the
boundary's qualification exit criteria are met
(`FTR-WFC-EXECUTION-BOUNDARY-DISPATCH-INTEGRATION.adoc`); the live
qualification layer is not part of this package's own test suite.

Separately, the package declares Python 3.10 or newer, but the only profile
this repository's own development has qualified today is CPython 3.13 on
Linux x86-64; ARM64 is an intended target, not a qualified one (see
<<beta-limitations>>). An installed, authenticated `claude` or `codex`
executable is a prerequisite, not a qualification: it has its own sandbox
and permission behavior that WFC does not document beyond what its adapters
configure, and an installed provider CLI is not by itself a fully qualified
adapter/model combination for this release.

[[quickstart-install]]
=== Install

Once 0.1.0b1 is published to PyPI, this is the primary path:

[source,shell]
----
python3 -m venv ~/.venvs/wfc
source ~/.venvs/wfc/bin/activate
python3 -m pip install 'workflow-coordinator==0.1.0b1'
wfc --version --json
----

The exact `==0.1.0b1` pin installs this pre-release deliberately -- a plain
`pip install workflow-coordinator` does not install a pre-release by
default. `--version --json` reports the executing package's implementation
identity; for a wheel install from PyPI this reports `"version": "0.1.0b1"`
and `"source_commit": null` -- a wheel is not a Git checkout, so there is no
commit to report. This paragraph describes the state once that publication
has happened; it does not claim it has happened yet. There is no top-level
`wfc --help`: a bare `wfc` subcommand token WFC does not recognize falls
through to an internal, unrelated legacy entry point, so do not run it.
Each subcommand documented below accepts its own `--help` instead, for
example `wfc init --help` (see <<quickstart-init>>).

Installing from a release artifact (sdist or wheel) or a source checkout
remains the secondary path, for example before publication or when working
from a local build:

[source,shell]
----
python3 -m venv .venv
source .venv/bin/activate
pip install /path/to/workflow-coordinator
wfc --version --json
----

There is no separate build step WFC performs for you either way. This
plain, non-editable install -- the same as installing a built sdist or
wheel -- reports `"source_commit": null`, exactly like the PyPI wheel
install above; only an *editable* install run directly against a clean,
unmodified checkout (`pip install -e /path/to/workflow-coordinator`)
reports that checkout's current commit SHA as `source_commit`, and only
for as long as the tree stays at that exact commit.

[[quickstart-skill]]
=== Install the agent skill

If an agent session (for example Claude Code or Codex) will operate WFC on
your behalf, install the packaged Agent Skill into that host's own skill
directory once, from the same environment the agent runs in:

[source,shell]
----
wfc skill install claude
wfc skill install codex
----

This writes only the one skill directory named (user scope by default) and
nothing else -- no project file, no host settings or permission file, and no
Git commit. Once installed, the supported entry is an explicit invocation at
the start of a message: `/wfc` in Claude Code, `$wfc` in Codex. `wfc skill
status <host>` reports whether an installation is current, and `wfc skill
show` prints the skill text itself; see
link:{operator-docs}/operator_manual/ch10_level1_orchestration/_chapter.adoc#level1-orchestration[Level-1
orchestration] for what the skill distills and what it does not grant.

[[quickstart-init]]
=== `wfc init` and configuration

From your repository root:

[source,shell]
----
wfc init --repository . --scope-ceiling src --evidence-repository ../wfc-evidence
----

This writes `.wfc/config.yaml` (never commits it) and creates or adopts the
named Evidence repository -- a separate, remote-less Git repository. Edit
`.wfc/config.yaml` yourself to add a `default_execution` binding for each
role you will use, for example:

[source,yaml]
----
default_execution:
  worker:
    adapter: codex_cli
    model: <your model>
    reasoning: medium
----

`adapter` must be `codex_cli` or `claude_cli`; no other value is accepted.
Then commit the file yourself:

[source,shell]
----
git add .wfc/config.yaml
git commit -m "chore: add wfc configuration"
----

`--scope-ceiling` is repeatable and names every path a future task's scope
may touch. A ceiling path covers only itself and its own descendants; list a
root-level file (for example `go.mod`) individually -- it is never implied by
a sibling directory.

`.wfc/config.yaml` also accepts an optional top-level `hop_timeout_seconds`
key (a positive number of seconds) that becomes this repository's default
per-Hop timeout -- a CAP meant only to end a genuinely hung provider
invocation, never a budget for ordinary work. `wfc run --hop-timeout-seconds`
overrides it for one invocation; absent both the flag and the key, the
built-in default is 14400 seconds (4 hours).

A committed `default_execution` naming a role your chosen program does not
use (for example an `independent_reviewer` default kept for `robust@v1`
Commissions, in a repository that also runs `simple@v1`) is tolerated, not
refused -- `simple@v1` resolves against the same committed
`.wfc/config.yaml` unchanged, with no second config file. `wfc plan` names
every ignored default in its preview, so the tolerance stays visible rather
than silent. An unused `--execution-override` is still refused: it is a
per-Commission intent that cannot take effect, unlike a standing repository
default.

[[quickstart-prepare-checkout]]
=== One prepared checkout per Run

`wfc run` authorizes at most one lifecycle per canonical checkout, so each
Run needs a checkout at a *fresh path*, a scratch directory outside the
repository, and whatever environment your own check command needs. One
command prepares all three and removes nothing:

[source,shell]
----
wfc prepare-checkout --repository . --path ../myproject-run1 --branch work/run1
source ../myproject-run1-scratch/launch-env.sh
----

It creates the worktree at `--path` on the new `--branch` (from `--base-ref`,
default the current `HEAD`), a sibling `<path>-scratch` directory with a
`tmp/` subdirectory for `TMPDIR`, and `<scratch>/launch-env.sh`, which
exports that `TMPDIR` and anything your preparation hook declared. Source it
before `wfc plan`/`wfc request`/`wfc run`: the baseline probe and every Hop's
check inherit the launching process's environment. The command runs no
`plan`/`run`, authorizes nothing, and writes nothing outside the two
directories it creates (besides Git's own worktree administration and the new
branch ref). It refuses -- by name, and before creating what it can avoid
creating -- an existing path, a missing parent, a path inside any working tree
of the repository (a sibling checkout included: creating anything in one would
dirty that tree and refuse the next Hop of a Run living in it),
a scratch directory inside the checkout, a dirty base, an existing branch, a
`--base-ref` that is not a commit, and a path whose checkout identity already
carries a lifecycle. It never removes a worktree, branch or directory, and
never makes a spent checkout reusable.

If your check command needs a prepared environment (a virtual environment, a
tool on `PATH`, declared inputs), put that in a *preparation hook*: an
executable committed in your repository, declared either by the optional
one-line `checkout_preparation_hook: <path>` key of `.wfc/config.yaml` or by
`--hook <path>` on the command line (`--no-hook` skips it). WFC reads the
declaration and the hook from the commit named by `--base-ref`, never from
the working tree; it passes the checkout path, the scratch path and the base
commit, and exports the bounded `NAME=VALUE` lines the hook prints on stdout
(diagnostics go to stderr), composing `PATH` itself from the hook's
`WFC_PREPARE_PATH_PREPEND`. Understand before you declare one: *a committed
hook is code you approved by committing it*, and it runs on your host with
your privileges before any Run. The full contract and the complete refusal
list are in
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#prepare-checkout-hook[chapter
3].

[[quickstart-request]]
=== Writing a request

`wfc plan` and `wfc run` read your guidance file from Git history at a
pinned commit, never from the working tree, so it must already exist and be
committed before you plan. From your repository root:

[source,shell]
----
mkdir -p .wfc/governance
cat > .wfc/governance/repository-policy.md <<'EOF'
Keep changes small, scoped, and reviewed before they land.
EOF
git add .wfc/governance/repository-policy.md
git commit -m "chore: add repository-policy guidance"
----

Write the task document itself *outside* the repository -- for example in a
sibling scratch directory -- so the repository tree stays completely clean
through the `wfc run` step below. `wfc run` refuses to launch against a
dirty tree, and an untracked file anywhere inside the repository counts as
dirty:

[source,shell]
----
mkdir -p ../wfc-scratch
cat > ../wfc-scratch/task.md <<'EOF'
# Add JSON output to the list command

Add a --json flag that prints the same rows as JSON.

## Acceptance
task-check passes

## Withheld authority
none beyond scope

## Default escalation
stop on ambiguity
EOF
----

`wfc run` below executes the check commands you declare, verbatim and in the
order you declare them, as a mandatory pre-launch baseline probe before it
ever starts a provider: each must already exist, already be committed, exit
`0` when run from the repository root on today's clean tree, and leave the
tree and `HEAD` unchanged. A non-zero exit, an unresolvable executable, a
timeout, or any tree mutation refuses the whole Run before launch
(classification `refused_probe`, exit code 23), names the command it came
from, and still consumes this checkout's one lifecycle -- prepare a fresh
checkout to retry. The same sequence is also the Commission's declared
evidence (see Limitations below); declare the cheap gates first, so a lint
error costs a lint run rather than a test suite. This walkthrough declares
one placeholder command for brevity; replace it with your project's real
gates -- lint first, then the test suite -- before relying on this for
anything but the walkthrough:

[source,shell]
----
mkdir -p checks
cat > checks/check.sh <<'EOF'
#!/bin/sh
# Replace with your project's real check command.
exit 0
EOF
chmod +x checks/check.sh
git add checks/check.sh
git commit -m "chore: add task-check probe script"
----

[[quickstart-plan]]
=== `wfc plan` preview

[source,shell]
----
wfc plan ../wfc-scratch/task.md --repository . --scope src \
  --commission-id add-json-output-001 --work-item-id WI-ADD-JSON-OUTPUT-001 \
  --authority-source "Repository owner authorizes this bounded task." \
  --program simple@v1 \
  --persona worker="Bounded worker persona; implement the requested change within scope." \
  --evidence-argv sh --evidence-argv checks/check.sh \
  --guidance-path .wfc/governance/repository-policy.md \
  --execution-override worker.adapter=codex_cli --execution-override worker.model=<model>
----

`wfc plan` is entirely read-only: it writes nothing, runs no project command,
and never touches Git; `--evidence-argv sh --evidence-argv checks/check.sh`
is not executed here -- it only names the check script you committed above,
which `wfc run` below will actually run. With no `--evidence-command NAME`
flag these tokens declare the one-command sequence named `task-check`; add
`--evidence-command NAME` before a command's own `--evidence-argv`/
`--evidence-timeout` flags to declare further, ordered gates (for example
`--evidence-command lint --evidence-argv make --evidence-argv lint` before
the `task-check` group). It prints the Commission bytes and
execution envelope it *would* compile. `--guidance-path` defaults to
resolving at the
repository's current HEAD, which the `repository-policy.md` commit above
already satisfies. Once the preview looks right, emit the equivalent
Consumer Request YAML with `wfc request`: the same fields and flags as
`wfc plan` above, plus an explicit `--output`:

[source,shell]
----
wfc request ../wfc-scratch/task.md --repository . --scope src \
  --commission-id add-json-output-001 --work-item-id WI-ADD-JSON-OUTPUT-001 \
  --authority-source "Repository owner authorizes this bounded task." \
  --program simple@v1 \
  --persona worker="Bounded worker persona; implement the requested change within scope." \
  --evidence-argv sh --evidence-argv checks/check.sh \
  --guidance-path .wfc/governance/repository-policy.md \
  --execution-override worker.adapter=codex_cli --execution-override worker.model=<model> \
  --output ../wfc-scratch/request.yaml
----

`wfc request` prints the identical projected digests `wfc plan` just
printed -- the same shared request-construction path, so the two can never
drift apart on what a given input set projects -- and writes the exact
Consumer Request YAML those digests were computed from to `--output`.
Refuses an already-existing `--output` file (`--force` to overwrite anyway)
and, by default, an `--output` path inside this repository's own worktree
(`--allow-inside-repository` to allow it anyway): an emitted, uncommitted
file inside the tree would dirty exactly the clean tree `wfc run` requires,
so the scratch directory above needs no flag at all. Nothing here is
authorized: no project command, provider call, Commission write or Git
mutation; `wfc run` below still re-reads the file from `--request` by plain
filesystem path, re-parses it under the closed schema and re-digests it,
exactly as it would a hand-authored file -- the emitted bytes grant no
authority of their own. `wfc report`, below, resolves its own `--repository`
differently: see <<quickstart-status>>.

[[quickstart-run]]
=== Unattended `wfc run --yes`

[source,shell]
----
wfc run --repository . --request ../wfc-scratch/request.yaml \
  --execution-override worker.adapter=codex_cli --execution-override worker.model=<model> \
  --yes
----

`--yes` authorizes without an interactive prompt -- what an unattended/CI
caller uses. Pass `--executable claude` for a `claude_cli` configuration; the
executable must match the configured adapter, and a Run uses exactly one
adapter throughout. WFC refuses an unambiguous cross-adapter mismatch before
dispatch (a bare `--executable` name resolving to the *other* adapter's own
known binary), but never an explicit path or an unrecognized bare name --
get the executable right regardless of this narrow safety net.
`--hop-timeout-seconds SECONDS` overrides, for this
invocation only, the per-Hop CAP described in <<quickstart-init>>; absent
the flag, `.wfc/config.yaml`'s `hop_timeout_seconds` applies, then the
built-in 14400-second default. `wfc run` re-derives and prints the Commission and
execution-envelope digests, requires the clean tree, runs your check command
as the baseline probe described in <<quickstart-request>> (refusing before
any provider starts if that fails), commits the Commission, re-verifies it,
launches the engine, waits, and prints `CLASSIFICATION:`/`MESSAGE:`/
`RUN ID:`/`RUN STATUS:`/`END HEAD:`. *A non-zero exit code does not by itself
mean failure* once the Run has actually launched -- `awaiting_human` and
other legitimate stops exit non-zero too; always read the printed
classification. A probe refusal is different: it happens before launch, is
classified `refused_probe` (exit code 23), prints a bounded, untrusted tail
of the check command's own captured stdout/stderr beside the exit code, and
still consumes this checkout's one lifecycle. See
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#launch[LAUNCH]
for the full mechanics.

[[quickstart-status]]
=== `wfc status` / `audit` / `report`

[source,shell]
----
wfc status --repository .
wfc report --repository .
----

`wfc status` is read-only and safe from a second shell while a Run is in
progress. Archiving happens automatically once the Run reaches a terminal
state; `wfc run` itself prints the exact destination path to use, and every
Run from this walkthrough archives under `archive/unclassified/` since
nothing here sets a domain/workstream. `wfc report --repository .` resolves
the Evidence location from `.wfc/config.yaml` and renders the one archived
Attempt found there -- this `--repository` names the *consumer* repository,
not the Evidence repository, and the command refuses by name if nothing has
archived yet or if more than one Attempt has; after a second Run, name the
Attempt directly instead: `wfc report
<evidence-repo>/archive/unclassified/<attempt-id>/audit.json`. `wfc audit
<attempt-dir>` is only for reproducing or re-deriving `audit.json` directly.
See link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#status[STATUS]
and the link:{operator-docs}/operator_manual/ch04_evidence/_chapter.adoc#evidence[evidence chapter].

[[quickstart-evidence-location]]
=== Where Evidence lands

Absent `--evidence-repository`/an `evidence:` block in `.wfc/config.yaml`,
Evidence lands at `<XDG_DATA_HOME, or ~/.local/share>/wfc/evidence/<repository
name>`. Raw-file retention is `local` by default; pass `--evidence-raw` on
`wfc init` (or set `evidence.raw`) to choose `commit` or `discard` instead. WFC
never pushes this, or any, repository -- there is no remote and no push code
path.

[[quickstart-next]]
=== What next

Prepare *one fresh checkout per Run*: a checkout that has already authorized
one lifecycle refuses every later `wfc run`, even long after a terminal,
archived Run, until
link:{operator-docs}/backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]
is decided. For a stopped Run, a failure diagnosis, or anything past this
quickstart, continue into the full
link:{operator-docs}/operator_manual/operator_manual.adoc[Operator Manual].

[[beta-limitations]]
== Limitations of this Beta

* *Execution boundary is opt-in and not preventive-isolation-qualified.* The
  Coordinator-owned Linux filesystem boundary (<<quickstart-bwrap-and-platform>>)
  defaults to off (`boundary: direct`); enabling it (`boundary: bubblewrap`)
  confines the filesystem dimension only -- no network, confidentiality,
  privilege or hostile-code claim is made -- and no document may describe
  WFC as preventively enforcing a phase's scope until that record's
  qualification exit criteria (Layer 1 and Layer 2) are met for the Run in
  question. The post-Hop Git/scope observation remains the authoritative
  acceptance control either way.
* *Crash and surviving-provider behavior.* Per decision DG-3 Variant B, WFC
  does not supervise a launched engine process. An unresolved launch is
  classified `uncertain_launch` and is never treated as safe to relaunch;
  `wfc resume` never relaunches an engine -- it only continues an
  already-authorized controller from journal and filesystem facts. See
  link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal states]
  and
  link:{operator-docs}/operator_manual/ch07_diagnostics/01_troubleshooting.adoc#troubleshooting[troubleshooting].
* *One adapter per Run.* Every role in a Run shares the same adapter and the
  same provider executable; mixing adapters within one Run is not supported.
* *One evidence sequence, the same for every gated phase.* A Commission
  declares an ordered sequence of named trusted commands -- one or more, each
  with a timeout of at most 900 seconds, which is a per-command cap -- and it
  cannot vary them per phase or per Hop: every phase the program declares as
  gated runs the identical, complete sequence. The commands run in the
  declared order and stop at the first one that does not pass, and the
  identical sequence also runs, before any `task-check` is ever reached, as a
  mandatory pre-launch baseline probe (see <<quickstart-request>>); a
  non-zero exit, an unresolvable executable, a timeout, or any tree mutation
  there refuses the whole Run before any provider starts and names the
  command it came from.
* *Clean-tree and scope-ceiling rules.* The working tree must be completely
  clean at launch, and every scope path must equal, or sit strictly beneath,
  a path already named in `.wfc/config.yaml`'s `--scope-ceiling`; a
  root-level file must be listed individually.
* *Incomplete recovery conveniences.* There is no `wfc continue`. A stopped
  Run is recovered manually: frozen work-in-progress is preserved as an
  explicitly non-authoritative Git commit, then a freshly authorized
  successor Commission inspects it from scratch -- see
  link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[recovery outcomes].
  An automatic candidate-preservation commit may already exist for some
  stops; it grants no acceptance, scope or authority and does not replace
  that manual procedure.
* *One lifecycle per checkout.* Until
  link:{operator-docs}/backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]
  is decided, prepare a fresh checkout for every Run.
* *Token usage is captured only as far as the provider reports it.* When an
  adapter's provider reports token figures (input, output, cache, reasoning)
  for an invocation, `audit.json` records them per Hop and as Run-wide
  totals, per-role and per-model aggregates (with an explicit marker when a
  total is only a lower bound), and `wfc report` shows them; a figure the
  provider never reports stays unknown, never guessed or shown as zero.
  There is no monetary/price figure. `limits` still carries
  `usage_not_reported` when no invocation of the Run captured any usable
  figure, and `usage_partially_reported` when capture was incomplete.
* *Qualified platform, only as far as this repository records it.* The
  package declares Python 3.10 or newer; the only profile this repository's
  own development actually qualifies today is CPython 3.13 on Linux x86-64.
  ARM64 is an intended target, not a qualified one. Host OS, CPU and each
  provider adapter require their own separate qualification.
* *WFC never pushes.* Neither the payload repository nor the Evidence
  repository is ever pushed by any WFC code path; every commit WFC makes
  stays local.

Live qualification of each supported provider adapter, from an installed
wheel, is performed and recorded by the maintainer. This document does not
claim it, and a passing fake-provider test -- including the one exercising
this same scenario in `tests/integration/test_beta_e2e_fake_provider.py` --
does not substitute for it.
