[[troubleshooting]]
== Troubleshooting

For candidate rejection, Worker criteria, semantic and mechanical stops,
provider permissions/compatibility, missing transcripts and scratch-space
failures, use the
link:{operator-docs}/operator_manual/ch07_diagnostics/02_failure_modes.adoc#failure-modes[failure-mode diagnosis].
That section links the owning acceptance and recovery procedures.

[cols="2,3",options="header"]
|===
|Symptom |What to do

|`python: command not found`
|A plain host's base `PATH` may provide `python3` without `python`. Use
`python3 scripts/wfc_op.py ...` for the source-checkout Harness. The
configured Evidence command does use bare `python`: the policy's argv is
`python -m pytest -q`. Harness prepends the Development/evidence and Runtime
virtual-environment bins to its controlled `PATH` and verifies `python3`
resolves to the Development/evidence interpreter. Do not replace the
configured Evidence command or infer its availability from the host's base
`PATH`; inspect the prepared environment and pinned policy.

|`prepare` refuses
|Read the named mismatch and inspect that specific pin/cleanliness/
Runtime-invariant/Evidence/preflight fact. Never hand-edit OPS or
preparation records; re-run `prepare` against a corrected input.

|STATE absent right after `prepare`
|Expected and required -- `prepare` must prove it created no Run.

|STATE already exists before `launch`
|`launch` fails closed rather than reusing/overwriting it. Choose a new
`--attempt` and `prepare` again; never delete an existing STATE to "retry"
without a deliberate, separate maintainer decision.

|`stop_reason: required_evidence_failed_without_route`
a|The phase's required evidence cleanly failed and no gate on it could
absorb that failure (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing]). Ask, in order:

. Which phase owned the failed evidence?
. Is this evidence really phase-local, or is it acceptance evidence that
  belongs on a review gate?
. Is the phase a gate capable of declaring `review.failed_evidence_route`
  (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing])?
. If evidence failure is intended to be correctable, is an explicit `goto`
  failure route declared?
. If human intervention is intended here, is that a deliberate Commission
  choice, or an accidental omission?

This is not something to resume or override from the operator side --
correct the Commission (profile and/or task prose) and prepare a fresh
Attempt (see link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_fresh_successor_commission[fresh successor Commission]).

|===

Most "problems" here are this system correctly refusing or correctly
stopping, not a defect to work around.
