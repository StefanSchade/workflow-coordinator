[[troubleshooting]]
== Troubleshooting

[cols="2,3",options="header"]
|===
|Symptom |What to do

|`python: command not found`
|A plain host's base `PATH` may provide `python3` without `python`. Use
`python3 scripts/wfc_op.py ...` for the source-checkout Harness. The
configured Evidence command does use bare `python`: the policy's argv is
`python -m pytest -q`. Harness prepends the Development/evidence and Runtime
virtual-environment bins to its controlled `PATH` and verifies `python3`
resolves to the Development/evidence interpreter. Do not replace the
configured Evidence command or infer its availability from the host's base
`PATH`; inspect the prepared environment and pinned policy.

|`prepare` refuses
|Read the named mismatch and inspect that specific pin/cleanliness/
Runtime-invariant/Evidence/preflight fact. Never hand-edit OPS or
preparation records; re-run `prepare` against a corrected input.

|STATE absent right after `prepare`
|Expected and required -- `prepare` must prove it created no Run.

|STATE already exists before `launch`
|`launch` fails closed rather than reusing/overwriting it. Choose a new
`--attempt` and `prepare` again; never delete an existing STATE to "retry"
without a deliberate, separate maintainer decision.

|`launch` returns non-zero, `status` shows `awaiting_human`
|Not by itself evidence of provider/Harness failure. Inspect `status` and
see link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal-state interpretation].

|Development/Runtime/Evidence unexpectedly dirty
|Investigate the cause before anything else; never manually override
cleanliness/trust checks.

|Run looks semantically accepted but is not `completed`
|Check which phase holds `finding_authority` over any open blocking Finding
and the recorded `stop_reason` -- a correct rereview with no disposition
authority is expected to stop `awaiting_human`, not complete (see link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal-state interpretation]).

|`stop_reason: required_evidence_failed_without_route`
a|The phase's required evidence cleanly failed and no gate on it could
absorb that failure (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing]). Ask, in order:

. Which phase owned the failed evidence?
. Is this evidence really phase-local, or is it acceptance evidence that
  belongs on a review gate?
. Is the phase a gate capable of declaring `review.failed_evidence_route`
  (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing])?
. If evidence failure is intended to be correctable, is an explicit `goto`
  failure route declared?
. If human intervention is intended here, is that a deliberate Commission
  choice, or an accidental omission?

This is not something to resume or override from the operator side --
correct the Commission (profile and/or task prose) and prepare a fresh
Attempt (see link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_fresh_successor_commission[fresh successor Commission]).

|`operator_error` names `[Errno 28] No space left on device` against a
`/tmp/wfc-observe-index-*` path, Run ends `reconcile_required`
a|*2026-10-29 operational note:* observed once, on 2026-10-28, when the host's
`/tmp` tmpfs filled completely (unrelated `pytest` temporary-file
accumulation, not a Commission or Coordinator defect); see
link:{operator-docs}/cold_storage/backlog/pre-0.1.0b1/infrastructure-and-incidents/2026-10-28_tmpfs_exhaustion.adoc[the incident
report] for the full facts. `observe_repository()`
(`src/workflow_coordinator/git_facts.py`) copies `.git/index` to a temp path
using Python's `tempfile.mkstemp` for a read-only Git observation with
`GIT_INDEX_FILE` pointing at the copy and optional index locks disabled.
The temporary directory follows the process's temporary-directory settings;
it is not hard-coded to `/tmp`. In that incident `/tmp` had no space, the
copy failed and the Hop was charged `uncertain_dispatch`.
As a preliminary measure the maintainer remounted `/tmp` at 12 GiB; this is
operational mitigation, not a fix, and does not change
link:{operator-docs}/operator_manual/ch03_running/02_launch_status.adoc#terminal-states[terminal-state interpretation]
or the normative
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#recovery-outcomes[reconcile/resume boundaries].
Treat it like any other `reconcile_required` stop, and additionally check
free space on the actual temporary filesystem (`df -h /tmp` for that
incident) if it recurs.
A durable scratch-space management requirement (FD-08) motivated by this
incident is tracked separately in
link:{operator-docs}/warm_storage/concepts/workflow_coordinator_front_door_priority_and_profile_commission_boundary_plan_2026-10-26.adoc[the
Front Door priority and Profile/Commission boundary plan] §9. Harness `prepare`
uses a private per-Attempt scratch directory; select its parent with
`--scratch-root ABSOLUTE_DIRECTORY` (default `$HOME/wfc-scratch`). Harness
sets `TMPDIR`, `TMP` and `TEMP` to that directory during preparation and in
the prepared launcher. Check the recorded scratch path and its filesystem
for a prepared Run; do not assume the old `/tmp` mitigation applies.
|===

Most "problems" here are this system correctly refusing or correctly
stopping, not a defect to work around.
