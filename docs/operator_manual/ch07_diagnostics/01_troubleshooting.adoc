[[troubleshooting]]
== Troubleshooting

For candidate rejection, Worker criteria, semantic and mechanical stops,
provider permissions/compatibility, missing transcripts and scratch-space
failures, use the
link:{operator-docs}/operator_manual/ch07_diagnostics/02_failure_modes.adoc#failure-modes[failure-mode diagnosis].
That section links the owning acceptance and recovery procedures.

[cols="2,3",options="header"]
|===
|Symptom |What to do

|`python: command not found`
|A plain host's base `PATH` may provide `python3` without `python`. The
configured Evidence command does use bare `python`: the policy's argv is
`python -m pytest -q`. Per DG-5, WFC itself no longer assembles a controlled
`PATH` for you -- the consumer-provided environment the `wfc run`/`resume`
process inherits must already resolve `python` to the intended interpreter.
Do not replace the configured Evidence command or infer its availability
from the host's base `PATH`; inspect the actual environment that process
ran in.

|Missing, incompatible or modified offline test inputs
|For WFC self-development, verify the selected bundle and host profile; do not
substitute a partial test or online fallback for the required suite. Supply
the verified inputs to the `wfc run`/`resume` process environment and check
the actual provider's allowed read paths. The link:{operator-docs}/developer_guide/ch01_development.adoc#offline-test-inputs[Developer Guide]
lists setup and actionable errors. No-index is not proof of network denial.

|`wfc run` refuses (`refused_prelaunch`/`refused_drift`/`refused_identity_changed`/`refused_probe`)
|Read the printed classification and message and inspect that specific
pin/cleanliness/Runtime-identity/evidence/preflight fact. Never hand-edit
the checkout's journal or engine-state directory; correct the input, then
either `wfc resume` (if a lifecycle was already authorized) or prepare a
fresh checkout and `wfc run` again.

|`wfc run` refuses `refused_active_lifecycle`
|At most one lifecycle is authorized per canonical checkout, even long after
a terminal, archived Run (see
link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation]).
This is not a defect to work around by deleting journal state; prepare a
fresh checkout for the next Run.

|`wfc status` reports `uncertain_launch`
|Per DG-3 Variant B, an unresolved launch intent is never treated as safe to
relaunch. Do not `wfc resume` expecting it to relaunch a second engine; a
free ownership lock does not by itself mean it is safe to try again. Apply
the normative link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc[recovery outcomes]
contract.

|`stop_reason: required_evidence_failed_without_route`
a|The phase's required evidence cleanly failed and no gate on it could
absorb that failure (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing]). Ask, in order:

. Which phase owned the failed evidence?
. Is this evidence really phase-local, or is it acceptance evidence that
  belongs on a review gate?
. Is the phase a gate capable of declaring `review.failed_evidence_route`
  (see link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#failed-evidence-route[failed-evidence routing])?
. If evidence failure is intended to be correctable, is an explicit `goto`
  failure route declared?
. If human intervention is intended here, is that a deliberate Commission
  choice, or an accidental omission?

This is not something to resume or override from the operator side --
correct the Commission (profile and/or task prose) and prepare a fresh
Attempt (see link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#_fresh_successor_commission[fresh successor Commission]).

|===

Most "problems" here are this system correctly refusing or correctly
stopping, not a defect to work around.
