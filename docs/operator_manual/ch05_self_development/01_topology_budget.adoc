[[self-development-topology]]
== Topology and preparation

This is the normative self-development specialization of
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[generic Run preparation].
Here the WFC Operator and WFC Developer roles coincide in one maintainer;
this is a special case, not the generic consumer path.

Accepted Runtime WFC N operates on the separate Development WFC N+1 checkout
and never mutates itself. Runs never mutate the Runtime identity; only
explicit maintainer promotion changes it. Per DG-5
(link:{operator-docs}/backlog/beta1_bp7_cutover_plan.adoc[BP7 retirement
cutover plan]), WFC itself no longer exports or builds a fresh per-Attempt
Runtime environment: the maintainer installs the accepted Runtime commit
once per promotion into a separate, non-editable environment (a wheel or
`pip install` of a `git archive` export of that exact commit), and ensures
that installation, not any live Development checkout's own environment, is
what the Run actually invokes. The Development checkout the Run operates on
keeps its full Git context -- it is the evidence substrate `wfc run` commits
against, never replaced by a stripped export. Keep build/install scratch,
caches, package metadata, virtual environments, and each new Run's
engine-state outside the Development checkout itself.

The sibling `workflow-coordinator-run-evidence` repository holds the durable
archive and curated semantic run ledger
(link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc[archive and ledger guidance]).

The self-development Consumer Config (`.wfc/config.yaml`) and its guidance
document (`.wfc/governance/repository-policy.md`) are committed at the
Development repository root. The config's `evidence` block names that same
sibling Evidence repository (`raw: commit`). Self-development runs through
the product Front Door (`wfc init`/`plan`/`request`/`prepare-checkout`/`run`/
`resume`/`status`/`audit`/`report`/`archive`) against this config, per the
BP7 retirement cutover; the
old Harness (`scripts/wfc_op.py`) is retired.

Per <<self-development-checkout-rotation>> below, each Run uses a fresh
checkout (clone or worktree) at the same relative Evidence location, until
link:{operator-docs}/backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[controlled checkout reuse] is decided.

Select the accepted Runtime N implementation independently of ambient
`PATH` drift by invoking its absolute installed `wfc` (next to the
interpreter that implementation was installed into), never a bare `wfc`
that could resolve to an unrelated or editable install; see
link:{operator-docs}/backlog/beta1_bp7_cutover_plan.adoc#risks[the BP7 cutover plan's bootstrap mitigation]
for why this matters once preparation no longer exports a fresh,
non-editable Runtime copy per Attempt. Verify that absolute executable with
`--version`/`--help` before relying on it. Supply the Development clone to
`--repository` (default the current directory); `wfc run`/`resume` derive
and verify the repository's own expected HEAD and cleanliness from Git
facts, so there is no separate `--expected-head`/`--state-root` to pass by
hand. The compiled WorkItem's per-phase `authorized_scope` is authoritative,
exactly as the Consumer Request's `durable_artifacts` mapping declares it;
there is no legacy `--durable-artifact` override on the product path.

[[self-development-checkout-rotation]]
=== One fresh checkout per Run

`wfc run` authorizes at most one lifecycle per canonical checkout, for as
long as any record of it remains in that checkout's journal -- including
long after a terminal, archived and Evidence-verified Run
(`frontdoor/lifecycle.py`'s `_advance`, classification
`refused_active_lifecycle`). Until
link:{operator-docs}/backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]
is decided, this is not a bug to work around locally: prepare one fresh
checkout (a `git clone` or `git worktree`, sharing the same Git object
store either way) per self-development Run, with the Evidence repository at
the same relative sibling location the committed `.wfc/config.yaml` names.
Do not attempt to relaunch a second Run inside a checkout that already
authorized one, even if that Run completed cleanly. Preparing that fresh
checkout, its scratch directory and its launch environment is one command,
`wfc prepare-checkout`
(link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc#prepare-checkout[preparing
the fresh checkout]), which refuses a path whose checkout identity already
carries a lifecycle rather than spending one on the discovery -- and which
removes nothing.
Remove the checkout again after integration, see <<self-development-checkout-cleanup>>.

[[self-development-preparation]]
== Run preparation

Ordinary Run preparation -- pinning commits, confirming the Runtime identity
and the consumer-provided environment, writing execution bindings, running
provider-free preflight, and launching -- follows the generic deterministic
contract in
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[Run preparation]. That section defines the three
boundaries (commission commit, launch, first real provider invocation), the
canonical preparation sequence (amended at steps 4/5 per DG-5), and the
product-Front-Door commands (`wfc init`/`plan`/`run`/`resume`); none of it is
restated here. In particular, ordinary preparation is deterministic operator
mechanics, not another semantic LLM/agent Hop.

Self-development specializes that generic contract:

* The Development checkout is both the repository `wfc run` operates on and
  the WFC source tree whose own behavior a self-development Commission may
  change (see Topology and preparation above); per
  link:{operator-docs}/operator_manual/ch05_self_development/01_topology_budget.adoc#self-development-checkout-rotation[checkout rotation],
  use one fresh checkout per Run.
* The separately promoted Runtime N clone must stay clean, detached and
  push-disabled (see
  link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#promotion-preconditions[promotion preconditions]);
  the non-editable Runtime environment a Run actually invokes is exported
  from that clone once per promotion, never rebuilt per Attempt and never
  the live Development checkout's own editable install.
* Promotion of a Runtime commit remains maintainer-owned and never automatic
  (see Ownership and promotion below and the
  link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#runtime-promotion[Runtime promotion runbook]).

[[self-development-temporary-storage]]
=== Temporary storage before test-heavy Runs

*Before running a self-development Run*, ensure the scratch directory the
pytest evidence command will actually use resolves outside the `/tmp` tree.
This is a requirement of the WFC consumer repository, not a general Runtime
restriction on every payload. Per DG-5, WFC provisions no scratch directory
of its own (<<self-development-preparation>> above); choose and prepare one
yourself -- for example, a `TMPDIR` under a dedicated directory outside
`/tmp` -- before invoking `wfc run`/`resume`, and export it into that same
process's environment. A `/tmp/...` selection remains unsuitable no matter
how it was prepared. Check the resolved filesystem, available space and
inodes before launching.

Before a large self-development Run, check both space and inodes on `/tmp`
and on the filesystem containing the chosen scratch path:

[source,shell]
----
df -h /tmp "$SCRATCH"
df -i /tmp "$SCRATCH"
printf 'TMPDIR=%s\n' "${TMPDIR:-<unset>}"
----

Use an external scratch directory on a filesystem with sufficient space and
inodes; set `TMPDIR` (or `TMP`/`TEMP`) to it in the shell that invokes
`wfc run`/`resume`. Verify the actual `TMPDIR`, `TMP` and `TEMP` in the
relevant execution context: the value you export reaches the engine process
only because it is inherited, not because anything freezes or re-exports it
on your behalf. Coordinator-owned evidence snapshots the Coordinator's
environment. The Codex adapter passes its inherited environment to the Codex
subprocess; later agent commands may change it. The Claude adapter instead
uses a short `/tmp` symlink to invocation-specific backing storage under the
ambient scratch root, with a fallback in standalone use. Check the resolved
location when it matters.

For this repository, ordinary `python -m pytest -q` places pytest-owned
temporary paths under `wfc-pytest` in the first nonempty `TMPDIR`, `TMP`, or
`TEMP`, if supplied and suitable; otherwise it uses the ignored `<development checkout>/tmp/pytest`
directory. The supplied directory must exist outside `/tmp`; an unsuitable
selection fails rather than falling back silently. A supplied path inside the
checkout must be under its ignored `tmp/` directory. Pytest creates numbered
per-session bases under `pytest-of-<user>` and applies its own retention and
locking. Use `python -m pytest -v` to see the actual base in the header;
failures also show fixture paths. Explicit `--basetemp` and
`PYTEST_DEBUG_TEMPROOT` retain pytest's own semantics; in particular pytest
resets an explicit `--basetemp`. Check space and inodes on the actual chosen
filesystem. Interrupted runs may leave material; inspect ownership and active
use before removing specific stale paths. Never blanket-delete `/tmp` or another
process's data.

This policy covers pytest-owned fixtures, not direct `tempfile` use or
external tools, which can choose different locations. The ignored checkout
default is a test scratch exception to the external-cache guidance above;
use supplied external scratch during self-development when available. See
link:{operator-docs}/backlog/BUG-WFC-PYTEST-TEMP-RESOURCE-EXHAUSTION.adoc[the pytest temporary-resource BUG].

[[self-development-scratch-cleanup]]
=== Scratch cleanup after archival

This specializes the generic
link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc#release-resources-after-archive[release of held resources after archive]
for self-development. The product Front Door has no scratch allocator of
its own (<<self-development-temporary-storage>> above); the scratch
directory a Run used (for example, a `TMPDIR` the operator pointed at a
per-checkout path before invoking `wfc run`) is entirely the
consumer-provided environment's own responsibility to create *and* to
remove. After every self-development Run, the Operator removes that Run's
own scratch directory once both conditions hold:

. The automatic BP6c postrun archive succeeded: `wfc status` prints
  `ARCHIVE: result` with `outcome: archived` (or `resumed_commit`/`no_op`
  for an already-archived retry), not `ARCHIVE: skipped` or
  `ARCHIVE: refused`.
. The persistent Evidence demonstrably exists: the archive commit is in the
  Evidence repository and `archive/<classification>/<attempt>/manifest.json`
  is present there with the Run's recorded identity.

[source,shell]
----
wfc status   # confirm ARCHIVE: result / outcome: archived, and note the destination
MANIFEST="$(ls "$EVIDENCE"/archive/*/<attempt>/manifest.json)"   # Evidence present
git -C "$EVIDENCE" log -1 --format=%h -- "${MANIFEST#"$EVIDENCE"/}"  # committed
rm -rf -- "$SCRATCH"   # the operator's own chosen scratch directory for this Run
----

A Run stopped with open recovery need (`awaiting_human`, `reconcile_required`
or another state without a recorded
link:{operator-docs}/operator_manual/ch06_recovery/01_outcomes.adoc#recovery-outcomes[recovery disposition])
keeps its scratch. After the disposition is documented and the stopped Run is
archived successfully, the same cleanup applies.

Scope: only that Run's own scratch directory. Never a shared scratch parent,
another Run's scratch, the checkout's own engine-state, the Evidence
repository or a directory whose Run cannot be established; never while its
launch process or a provider process is alive. Scratch is ephemeral,
untrusted execution material, not Run evidence (see
link:{operator-docs}/operator_manual/ch07_diagnostics/02_failure_modes.adoc#scratch-diagnosis[scratch diagnosis]);
diagnosis that needs it precedes cleanup.

[[self-development-checkout-cleanup]]
=== Checkout cleanup after integration

<<self-development-checkout-rotation>> means every Run leaves a checkout
(worktree or clone) and a local branch behind. They are not Run evidence: the
Evidence repository holds that. The Operator removes a Run's checkout and its
local branch once all of the following hold:

. The Run's archive succeeded and the Evidence demonstrably exists (the same
  two conditions as for <<self-development-scratch-cleanup>>).
. The Run's result is integrated or its disposition is recorded. A completed
  Run's branch tip is an ancestor of `main`
  (`git merge-base --is-ancestor <branch> main`). A stopped Run has a
  documented disposition (maintainer decision, successor or acceptance) and any
  uncommitted work in its checkout is retained as a preserved ref
  (`refs/wfc/preserved/<run-id>/<n>`), with the working tree verified
  identical to it (`git -C <checkout> diff <ref>` prints nothing).
. No launch or provider process runs in it.

[source,shell]
----
git merge-base --is-ancestor <branch> main        # completed Run: integrated
git -C <checkout> diff <preserved-ref>            # stopped Run: nothing differs
git worktree remove <checkout>                    # --force only for the verified stopped-Run case
git branch -d <branch>                            # -D only if the tip is reachable from a preserved ref
----

Never remove the main checkout, a checkout the maintainer keeps for their own
work, a preserved ref, a salvage branch, a stash or the Evidence repository,
and never a checkout whose Run is not archived or whose result is neither
integrated nor dispositioned. Preserved refs and stashes stay until the
maintainer disposes of them. The Run's small journal under the state home stays
as retained state; this rule does not clean it. The rule is Operator
housekeeping only and changes nothing in the one-lifecycle-per-checkout
invariant.

[[self-development-hop-budget]]
=== Commission Hop budget (`max_autonomous_hops`)

Commission preparation has repeatedly conflated two different numbers: how
many Hops a task is *expected* to need, and the *authorized ceiling*
(`max_autonomous_hops`). When another invocation is required and that
ceiling is exhausted, the Run stops `awaiting_human_budget` with
`stop_reason=autonomous_hop_budget_exhausted`. This is distinct from
`awaiting_human` and does not imply automatic continuation or successor
eligibility. Setting the ceiling equal to the expected count has repeatedly
produced unnecessarily tight budgets of four or six Hops.

A Run that completes at Hop 4 consumes four Hops whether the authorized
ceiling was 6, 20, or 64 -- unused authorized Hops carry no provider
execution cost. The two failure directions are therefore asymmetric: a
generous ceiling only costs something if the extra Hops are actually spent
on unproductive iteration, whereas a tight ceiling reliably stops a
still-converging Run and forces a fresh commissioning/preparation cycle.
Across WFC dogfooding to date, premature exhaustion has occurred
repeatedly; no comparable case of a generous ceiling producing a long run
of useless extra Hops has been observed. That is evidence from experience
so far, not a guarantee, and not a license to pick a ceiling without
reason.

For an ordinary iterative implementation/review/correction Commission,
prefer a generous provisional ceiling of roughly *10 Hops*, even when the
happy-path expectation is four or six. Set a lower ceiling only for a
concrete reason to restrict iteration, not merely because that is what the
happy path is expected to take. This is a provisional default, not a new
hard requirement: an applicable authority ceiling, a task-specific
constraint, or an explicit maintainer decision still governs. The current
hard Coordinator ceiling is `64`; making that ceiling configurable is a
future improvement, not implemented here. See
link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#hop-budget[general Hop-budget mechanics] for the field's full mechanics and
`Run.hop_limit` reporting.

Successful completion and review acceptance remain the normal termination
mechanisms; budget exhaustion is a protective stop, not a desired outcome.

[[self-development-ownership]]
== Ownership and promotion

The maintainer owns the RepositoryPolicy, profile, WorkItem, task, scope,
acceptance, push, and any later runtime promotion. WFC coordinates only the
committed envelope and may create only its authorized local commits. The
maintainer separately reviews and accepts a result, may push it, and may later
promote a runtime. Promotion is never automatic.

Provider-free bootstrap validation (including Bootstrap B2's validation of
the committed developer-ergonomics WorkItem) does not execute that
WorkItem's separate dogfood Run. The Codex adapter's
`--sandbox workspace-write` request remains provider-owned
behavior; it is not trusted Coordinator-owned containment of the host or
environment.

[[self-development-enforcement]]
== Commission authoring: Runtime authority, Development payload, and enforcement layer

A self-development Commission must distinguish three things that are easy to
conflate precisely because Development N+1's payload is WFC's own
provider-adapter code:

* *Executing authority* -- the sandbox/permission behavior of whichever
  adapter (Codex, Claude) executes *this* Hop under Runtime N, including
  whether the Run's own execution envelope selected the opt-in Coordinator-owned
  filesystem boundary (`boundary: bubblewrap`) for it. That behavior governs
  only this Hop's own execution; it is never the subject a WorkItem's task
  describes changing.
* *Payload requirements* -- what the WorkItem's target code (for example,
  `claude_adapter.py`'s generated settings) must do for a *future* invocation
  of the provider it configures. A Commission whose payload is "correct the
  Claude adapter" must not be read, by its author or by an executing agent,
  as a statement about the Runtime process currently executing the
  correction.
* *Future architectural intent* -- a planned but unimplemented mechanism (for
  example, confidentiality or per-phase visibility profiles atop the
  existing filesystem boundary; see
  link:{operator-docs}/backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[FTR-WFC-EXECUTION-TRUST-BOUNDARIES])
  is never a current requirement a WorkItem may cite as already governing.

A security requirement stated in a WorkItem, task, or governing backlog
record must name which layer is expected to enforce it: the provider's own
sandbox/permission request (operational, provider-owned, not
Coordinator-verified -- `DEC-WFC-009`), or WFC's own deterministic post-Hop
Git/scope observation (Coordinator-owned, authoritative). A requirement that
does not say which layer enforces it is incomplete; the Commission author
must resolve that before committing the Commission, not leave it for the
Worker or an independent reviewer to guess.

Experimental implementation within a Commission's granted authority is the
ordinary default, not an exception requiring restatement in every task: a
Worker may choose, try, and justify a bounded technical approach from the
evidence actually available, record residual uncertainty about it, and
proceed -- this is not itself a missing-authority escalation. State an
explicit exception in the Mandate only when a genuine ambiguity or withheld
prerequisite actually applies -- for example, when the Commission's own
`withheld_authority` denies the one means that would otherwise resolve a
necessary precondition. See
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#acceptance-anti-patterns[Commission-authoring anti-patterns] and
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#commission-preflight[semantic Commission-preflight checklist] for the
anti-pattern and the short preflight check this guards against; worked case:
`docs/backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc`,
Attempts `wfc-claude-adapter-write-permissions-001/-002/-003`, each of which
stopped at Hop 1 with zero candidate on a variant of the same unresolved
demand.
