[[self-development-topology]]
== Topology and preparation

This is the normative self-development specialization of
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[generic Run preparation].
Here the WFC Operator and WFC Developer roles coincide in one maintainer;
this is a special case, not the generic consumer path.

Accepted Runtime WFC N operates on the separate Development WFC N+1 clone and
never mutates itself. Harness and Runs never mutate that Runtime checkout;
only explicit maintainer promotion changes it. The clones have separate Git
directories and object stores. Export the exact accepted runtime commit into temporary storage outside
both clones, then install that export non-editably into an external runtime
virtual environment. Create a second external development/evidence virtual
environment with ordinary `python3 -m venv` and install the current development
repository's `dev` extra from the live pinned Development checkout, not
from an archived target export (the evidence substrate must retain Git
context). Keep exports, build/install scratch, caches, package metadata,
virtual environments, and each new Run state root outside both clones.

The sibling `workflow-coordinator-run-evidence` repository holds the durable
archive and curated semantic run ledger
(link:{operator-docs}/operator_manual/ch04_evidence/02_archive.adoc[archive and ledger guidance]).

The single launch environment is:

[source,text]
----
PATH=<development/evidence-env>/bin:<runtime-env>/bin:<remaining trusted base PATH>
----

Select Runtime N independently of `PATH` by invoking the absolute
`<runtime-env>/bin/wfc`; never use bare `wfc`. Verify that absolute executable
with `--help`, and verify through production `snapshot_environment()` and
`prepare_evidence_commands()` that the ordered `PATH` is captured and the
policy command `python -m pytest -q` resolves to the development/evidence
interpreter. Supply the development clone to `--repository`, its exact full
HEAD to `--expected-head`, and a new external path to `--state-root`. The
WorkItem's per-phase artifact mapping is authoritative; do not pass the legacy
`--durable-artifact` option. Harness freezes this controlled `PATH` as a
literal value in `launch.sh`, so later ambient shell changes do not replace
the environment admitted by preflight.

[[self-development-preparation]]
== Run preparation

Ordinary Run preparation -- pinning commits, materializing the OPS/state
roots, exporting Runtime and preparing the target evidence environment, writing
`execution-bindings.yaml`, assembling `PATH`, running provider-free preflight,
and writing `launch.sh` -- follows the generic deterministic contract in
link:{operator-docs}/operator_manual/ch03_running/01_preparation.adoc[Run preparation]. That section defines the three
boundaries (commission commit, `launch.sh` execution, first real provider
invocation), the canonical preparation sequence, the OPS-root/state-root
distinction, and the illustrative shell shape; none of it is restated here.
In particular, ordinary preparation is deterministic operator mechanics, not
another semantic LLM/agent Hop.

Self-development specializes that generic contract:

* `TARGET` is the Development N+1 clone; `RUNTIME` is the separately promoted
  Runtime N clone (see Topology and preparation above).
* The Runtime checkout must additionally stay clean, detached and
  push-disabled (see
  link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#promotion-preconditions[promotion preconditions]).
* Promotion of a Runtime commit remains maintainer-owned and never automatic
  (see Ownership and promotion below and the
  link:{operator-docs}/operator_manual/ch05_self_development/02_promotion.adoc#runtime-promotion[Runtime promotion runbook]).

[[self-development-hop-budget]]
=== Commission Hop budget (`max_autonomous_hops`)

Commission preparation has repeatedly conflated two different numbers: how
many Hops a task is *expected* to need, and the *authorized ceiling*
(`max_autonomous_hops`) the Run may spend before an unfinished Run stops
`awaiting_human`. Setting the ceiling equal to the expected count has
repeatedly produced unnecessarily tight budgets of four or six Hops.

A Run that completes at Hop 4 consumes four Hops whether the authorized
ceiling was 6, 10, or 20 -- unused authorized Hops carry no provider
execution cost. The two failure directions are therefore asymmetric: a
generous ceiling only costs something if the extra Hops are actually spent
on unproductive iteration, whereas a tight ceiling reliably stops a
still-converging Run and forces a fresh commissioning/preparation cycle.
Across WFC dogfooding to date, premature exhaustion has occurred
repeatedly; no comparable case of a generous ceiling producing a long run
of useless extra Hops has been observed. That is evidence from experience
so far, not a guarantee, and not a license to pick a ceiling without
reason.

For an ordinary iterative implementation/review/correction Commission,
prefer a generous provisional ceiling of roughly *10 Hops*, even when the
happy-path expectation is four or six. Set a lower ceiling only for a
concrete reason to restrict iteration, not merely because that is what the
happy path is expected to take. This is a provisional default, not a new
hard requirement: an applicable authority ceiling, a task-specific
constraint, or an explicit maintainer decision still governs. The current
hard Coordinator ceiling is `20`; making that ceiling configurable is a
future improvement, not implemented here. See
link:{operator-docs}/operator_manual/ch02_commissioning/02_authoring.adoc#hop-budget[general Hop-budget mechanics] for the field's full mechanics and
`Run.hop_limit` reporting.

Successful completion and review acceptance remain the normal termination
mechanisms; budget exhaustion is a protective stop, not a desired outcome.

[[self-development-ownership]]
== Ownership and promotion

The maintainer owns the RepositoryPolicy, profile, WorkItem, task, scope,
acceptance, push, and any later runtime promotion. WFC coordinates only the
committed envelope and may create only its authorized local commits. The
maintainer separately reviews and accepts a result, may push it, and may later
promote a runtime. Promotion is never automatic.

Provider-free bootstrap validation (including Bootstrap B2's validation of
the committed developer-ergonomics WorkItem) does not execute that
WorkItem's separate dogfood Run. The Codex adapter's
`--sandbox workspace-write` request remains provider-owned
behavior; it is not trusted Coordinator-owned containment of the host or
environment.

[[self-development-enforcement]]
== Commission authoring: Runtime authority, Development payload, and enforcement layer

A self-development Commission must distinguish three things that are easy to
conflate precisely because Development N+1's payload is WFC's own
provider-adapter code:

* *Executing authority* -- the sandbox/permission behavior of whichever
  adapter (Codex, Claude) executes *this* Hop under Runtime N. That behavior
  governs only this Hop's own execution; it is never the subject a WorkItem's
  task describes changing.
* *Payload requirements* -- what the WorkItem's target code (for example,
  `claude_adapter.py`'s generated settings) must do for a *future* invocation
  of the provider it configures. A Commission whose payload is "correct the
  Claude adapter" must not be read, by its author or by an executing agent,
  as a statement about the Runtime process currently executing the
  correction.
* *Future architectural intent* -- a planned but unimplemented mechanism (for
  example, a WFC-owned bubblewrap execution layer; see
  link:{operator-docs}/backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[FTR-WFC-EXECUTION-TRUST-BOUNDARIES])
  is never a current requirement a WorkItem may cite as already governing.

A security requirement stated in a WorkItem, task, or governing backlog
record must name which layer is expected to enforce it: the provider's own
sandbox/permission request (operational, provider-owned, not
Coordinator-verified -- `DEC-WFC-009`), or WFC's own deterministic post-Hop
Git/scope observation (Coordinator-owned, authoritative). A requirement that
does not say which layer enforces it is incomplete; the Commission author
must resolve that before committing the Commission, not leave it for the
Worker or an independent reviewer to guess.

Experimental implementation within a Commission's granted authority is the
ordinary default, not an exception requiring restatement in every task: a
Worker may choose, try, and justify a bounded technical approach from the
evidence actually available, record residual uncertainty about it, and
proceed -- this is not itself a missing-authority escalation. State an
explicit exception in the Mandate only when a genuine ambiguity or withheld
prerequisite actually applies -- for example, when the Commission's own
`withheld_authority` denies the one means that would otherwise resolve a
necessary precondition. See
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#acceptance-anti-patterns[Commission-authoring anti-patterns] and
link:{operator-docs}/operator_manual/ch04_evidence/01_acceptance.adoc#commission-preflight[semantic Commission-preflight checklist] for the
anti-pattern and the short preflight check this guards against; worked case:
`docs/backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc`,
Attempts `wfc-claude-adapter-write-permissions-001/-002/-003`, each of which
stopped at Hop 1 with zero candidate on a variant of the same unresolved
demand.
