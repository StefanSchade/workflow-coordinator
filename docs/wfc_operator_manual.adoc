== 1. Purpose and audience

This is the document a maintainer should open months from now, with no
memory of the surrounding concept papers or chat history, to actually
operate a WFC self-development Run: prepare it, launch it, check on it,
archive it, and correctly interpret a stop.

It is not another architecture concept (the
link:cold_storage/backlog/pre-0.1.0b1/operator-harness-v0/wfc_operator_harness_v0_concept_2026-10-06.adoc[historical Harness v0 concept],
`docs/wfc_projected_result_contracts_concept_2026-10-07.adoc`), not a
restatement of the generic deterministic-preparation contract
(`docs/run-preparation.adoc`), not a restatement of the Runtime-N/
Development-N+1 topology and promotion runbook
(`docs/self-development.adoc`), and not a restatement of the four
maintainer-chosen recovery outcomes (`docs/run-recovery-and-salvage.adoc`).
Where this manual overlaps one of those, the dedicated document is
authoritative; this manual summarizes only enough to operate correctly and
links there for rationale.

== 2. Five-minute mental model

[source,text]
----
COMMISSION / GOVERNING INPUTS
    = What may this Run do?
      (WorkItem, Profile, RepositoryPolicy, Components, Task -- reviewed
       and committed before any mechanics begin)

EXECUTION BINDINGS
    = Which adapter/model/reasoning configuration performs each role?
      (--role-binding, written to execution-bindings.yaml)

ATTEMPT
    = The identity of one concrete prepared execution attempt.
      (a name; deterministically maps to OPS and STATE paths)

OPS
    = Harness-owned prepared execution envelope.
      Pins identities/environment/bindings/launch mechanics.
      Created by PREPARE. Lives at ~/wfc-ops/<attempt>.

STATE
    = WFC-owned persisted Run state.
      Created only when LAUNCH actually starts a Run.
      Lives at ~/wfc-state/<attempt>.

EVIDENCE
    = Durable archived evidence derived from the Run after execution.
      Today: the sibling workflow-coordinator-run-evidence repository.

RUNTIME
    = The accepted WFC implementation used to execute Runs.
      Separate from Development; promoted only by explicit maintainer
      action; never "latest main".
----

Two distinctions matter most operationally:

* *OPS vs. STATE* -- OPS is Harness's own prepared envelope and exists the
  moment `prepare` succeeds. STATE is WFC's own Run state and must *not*
  exist yet at that point; it is created only when `launch` actually starts
  a Run. Confusing "prepared" with "launched" is the most common misreading
  of this system.
* *Commission authority vs. execution choice* -- WorkItem/Profile/Policy/
  Components/Task is *what may happen*; `--role-binding` is *which concrete
  adapter/model/reasoning performs it*. A Commission may stay semantically
  identical while its execution bindings differ, if separately authorized
  (section 4).

== 3. Repositories and trust boundaries

[cols="1,3,2",options="header"]
|===
|Repository |Role |Mutability from Harness

|`workflow-coordinator` (Development)
|Evolving candidate implementation and Commission inputs.
|Harness only reads it (pins HEAD, requires clean); `launch` invokes the
pinned *Runtime's* executable against it.

|`workflow-coordinator-runtime` (Runtime)
|The accepted WFC implementation that executes Runs. Detached, clean,
`remote.origin.pushurl=DISABLED`.
|Never mutated by Harness or a Run. Changed only by explicit maintainer
promotion (section 15).

|`workflow-coordinator-run-evidence` (Evidence)
|Durable mechanical archive plus the curated semantic run ledger.
|Never mutated by `prepare`/`launch`/`status`. `archive` delegates to its

|===

Harness v0 (`scripts/wfc_op.py`, living in Development, outside the
`workflow_coordinator` package) is the deterministic mechanical layer that
operates across all three. It owns none of their semantic content.

== 4. Inputs and ownership/lifetime

Two kinds of input are easy to conflate:

*WFC / Commission authority* (what may happen; reviewed and committed before
mechanics begin): WorkItem, Profile, RepositoryPolicy, Components, Task.

*Provider/execution choice* (how authorized work is concretely performed):
`--executable`, each `--role-binding`'s adapter/model/reasoning.

The concrete model binding is intentionally *not* the semantic authority of
the WorkItem itself. A Commission may remain semantically the same while its
execution bindings differ, if separately authorized -- rerunning an
identical Commission under a different model for cost/availability reasons
is an execution-choice decision, not a re-commissioning.

[cols="2,2,3,2",options="header"]
|===
|Input |Owner |Lifetime |Kind

|`--development` / `--runtime` / `--evidence`
|Maintainer (repo identity)
|Path long-lived; HEAD pinned per Attempt (Runtime HEAD stable across many
Runs, changes only at promotion)
|Mechanics (identity pin)

|`--work-item`
|Commission / maintainer review
|One per WorkItem; carries `max_autonomous_hops`, scope, authorized actions
|*Authority*

|`--profile`
|Commission / maintainer review
|Phases/roles/review structure/`finding_authority`; often reused across a
lineage
|*Authority*

|`--policy`
|Commission / maintainer review
|RepositoryPolicy: evidence commands, ceilings; repository-lifetime
|*Authority*

|`--components`
|Commission / maintainer review
|Scope declarations authorized paths resolve against; repository-lifetime
|*Authority*

|`--task`
|Commission / maintainer review
|Concrete task text; one per WorkItem
|*Authority*

|`--executable`, `--role-binding`, `--timeout-seconds`
|Maintainer (execution choice)
|Chosen per Attempt; may change between otherwise-identical Runs

|===

=== Commission mutation-scope granularity

`WorkItem.scope` and each phase's `authorized_scope` are *authority
boundaries* -- what this Commission may mutate -- not an implementation
plan predicting which files a correct implementation will touch.

The path model Harness already enforces accepts repository-relative
*directory* scopes, not only exact file paths: an authorized_scope entry
matches itself exactly or any path beginning with `<entry>/`. File-exact
scope and directory scope are the same existing prefix-match authority
check; nothing new is introduced by using one over the other. File-exact
mutation authority is therefore a Commission-author *choice*, not a
generic WFC requirement.

For ordinary implementation/correction work, the recommended default is
bounded area/directory-level authority sufficient for the semantic task,
for example:

[source,yaml]
----
authorized_scope:
  - src/workflow_coordinator
  - tests
----

or, where repository architecture provides meaningful boundaries:

[source,yaml]
----
authorized_scope:
  - src/domain
  - src/adapters
  - tests
----

A Commission may still intentionally choose narrower, file-exact scope
when that is semantically justified: a single durable review artifact; a
deliberately surgical correction whose exact carrier is already known; a
governance/document correction whose specific artifact identity is part
of the authority decision; or another genuine trust boundary where the
exact file matters.

*Least privilege means granting only the repository areas and actions
appropriate to the task -- it does not mean predicting every file a
correct implementation will touch before the implementing agent
investigates.* Treating it as the latter duplicates implementation/
discovery work into Commission authoring, often forces the Commission
author to use an LLM merely to discover the file list, makes
human-authored Commissions unnecessarily difficult, can make required
evidence impossible to satisfy when the real change touches files outside
the predicted set, and takes legitimate dependency/impact discovery away
from the worker.

This also means a coding Commission needs no generic `may_modify_tests`
boolean. Whether test maintenance is authorized is simply whether the
repository's test area is included in `authorized_scope`:

[source,yaml]
----
authorized_scope:
  - src/workflow_coordinator
  - tests
----

Omit that area, or bound it differently, when tests must remain immutable
for the task. The same generic workspace/scope mechanism authorizes
bounded mutation space identically in a non-code task, e.g.

[source,yaml]
----
authorized_scope:
  - course/current
  - exercises
----

while leaving `source_material` and `grading_policy` outside scope. The
framework models bounded mutation space, not programming-language
concepts.

The opposite extreme is equally wrong: do not make the whole repository
writable merely to avoid prediction risk. Scope should remain meaningfully
bounded by the semantic task and repository policy. Governing inputs,
authority-defining material, historical evidence, and comparable trust
surfaces remain separately protected by existing WFC rules regardless of
how an authorized_scope entry is written.

*Motivating incident:* `RUN-90c24baad80645b0958ed96ae0a2cc3f`
(`WI-WFC-PROJECTED-RESULT-CONTRACTS-P2`, Development candidate H001
`25861f2c19d438c82144d1aed742c48ea038f352`) used a deliberately file-exact
implement/correction `authorized_scope` -- exactly fifteen named
source/test paths -- while the governing RepositoryPolicy's evidence
command simultaneously required trusted full-repository
`python -m pytest -q`. H001 implemented the P2 result-family change and
its own focused validation passed, but the trusted full-suite run failed;
the contract change affected additional legacy test consumers outside
that predicted file set. The Coordinator correctly stopped
(`required_evidence_failed_without_route`) before independent review could
run -- this is fail-closed behavior working as designed (section 13), not
the Coordinator malfunctioning and not evidence checks being too strict.
The durable lesson is narrow: the Commission attempted to predict
implementation impact at individual-file granularity, and that prediction
proved incomplete. This Run was not accepted or promoted, and this section
does not reinterpret it as such; see section 19 for the general worked-
example discipline this manual applies to real Runs.

=== Review breadth and bounded rereview convergence

*Fresh context does not mean broad review.* A rereviewer can and normally
should receive `context: fresh` (no memory of prior invocations) while
still receiving a deliberately narrow falsification surface. These are
independent axes: freshness is about provider/conversation memory;
breadth is about the intended search surface. Conflating them turns every
rereview back into a full adversarial rediscovery pass merely because the
reviewer's context happens to be fresh.

Normal review progression for an `independent_review` -> `correction` ->
`rereview` loop should usually be:

[source,text]
----
initial independent review  -> establish the Finding set
correction                  -> address known Findings
rereview                    -> disposition known Findings
                                + inspect direct regressions from correction
----

The initial independent review should be broad enough for its declared
implementation/design/closure responsibility -- that is where adversarial
discovery belongs. Once the Finding set is established, a rereview should
normally narrow rather than repeatedly reopening the complete adversarial
search space. It carries stable Finding identity forward and asks: was
each blocking Finding actually corrected; is the correction mechanism
sound, not cosmetic; did the correction directly regress surrounding
behavior?

A genuinely new MATERIAL issue supported by concrete new material evidence
may still escape the bounded surface and stop/reopen the loop, exactly as
existing WFC semantics already permit -- bounding the surface narrows
*intended* search, it does not forbid a real new defect. An unrelated,
newly noticed MINOR observation should normally not reset the review
cycle; it may become a residual, observation, or separately governed
follow-up depending on current authority. "Narrow rereview" never means
telling a reviewer to ignore evidence, forcing `accept`, hiding a known
blocker, forbidding a real new MATERIAL defect, or lowering acceptance
criteria for a known Finding -- it means controlling the intended
falsification surface after an initial discovery pass has already run.

This is distinct from Correction Convergence Escape. Review narrowing
prevents moving goalposts caused by repeated broad rediscovery after every
correction. Correction Convergence Escape handles a stable problem/Finding
set that is genuinely failing to converge under ordinary correction and
may require diagnosis/reframe/strategy change. Convergence Escape is not a
substitute for bounded rereview, and bounded rereview does not make
Convergence Escape obsolete -- they address different failure shapes.

Broad rereview may still be deliberately chosen again when, for example:
the correction materially changed architecture; the prior Finding set no
longer truthfully represents the risk surface; a prerequisite/reframe
changed semantic ownership; or an explicit closure/counterexample search
is being commissioned for some other concrete reason. Such broadening
should be intentional and visible in the Commission/profile -- an
authored choice, not something that happens automatically because the
reviewer has fresh context.

A concrete wording pattern for a bounded rereview's `review.purpose`:

[source,text]
----
Fresh independent disposition of the known Findings after correction.
Re-test those Findings and direct correction regressions. Do not reopen
general discovery merely because context is fresh. Report a genuinely
new MATERIAL defect when supported by new material evidence.
----

*Precedent already in this repository's own manual-prompting practice*
(not a WFC Run -- directly prompted review/correction commits): the
Projected Result Contracts roadmap revision review sequence
`965d14d` (`docs(wfc): refine projected result contract roadmap`) ->
`c8c973` (`docs(wfc): review projected result contract roadmap revision`,
verdict `MATERIAL_REVISION_REQUIRED`) -> `f31a423` (`docs(wfc): correct
P3.5 conformance criteria`) -> `5979d75` (`docs(wfc): close projected
result contract roadmap review`, verdict `ACCEPT`). `c8c973`'s review
identified two MATERIAL findings plus one IMPORTANT and one MINOR;
`f31a423` corrected only the MATERIAL finding surfaces; `5979d75`'s
closure review used fresh reviewer context but deliberately did not
reopen a broad adversarial review -- it checked whether the two MATERIAL
findings were actually closed and whether the narrow correction
introduced direct regressions, left the known IMPORTANT sequencing
question and MINOR vocabulary issue open and non-blocking, and reached
verdict `ACCEPT` without pretending every observation in the surrounding
design had disappeared. This is the operating principle in concrete
form, not a Projected Result Contracts-specific rule.

=== Mechanism admission and design economy

An adversarial or architecture-oriented development process can keep
discovering additional conceivable edge cases, guards, authority concepts,
states, schema fields, lifecycle transitions, or other machinery. Many such
additions are locally defensible in isolation while still making the
overall system unnecessarily complex. *"Could this be modeled or guarded
more completely?" is not, by itself, sufficient justification for adding
new WFC mechanics.*

A new Coordinator mechanism -- a guard, authority concept, persisted state,
schema field or result-family concept, lifecycle transition, persistence/
history structure, reducer mechanic, routing machinery, trusted
effect/execution mechanic, or other comparable Coordinator architecture --
should normally be introduced only when it addresses at least one of:

. a concrete *observed* failure mode; or
. a concrete *imminent authorized* use case that existing mechanics cannot
  adequately support.

Before adding such mechanics, the design/Commission-authoring process
should ask:

a. What concrete observed harm or blocked authorized use drives this?
b. Why are existing mechanics insufficient?
c. Could Commission authoring, Profile/Policy configuration, bounded
   authority/scope, review purpose/breadth, evidence configuration, or
   documentation/operator convention handle this adequately instead?
d. If new mechanics are genuinely necessary, what is the smallest
   mechanism that solves the concrete problem?
e. What is the stop condition -- what evidence would make this problem
   sufficiently solved, rather than inviting indefinite further hardening?

A merely *conceivable* failure mode does not answer (a). Absent a concrete
driver, prefer a backlog entry, observation, or operator convention over
new architecture. A concrete imminent authorized use case is a valid driver
even when no production failure has occurred yet -- the operative
distinction is concrete driver versus speculative completeness for its own
sake, not present failure versus future risk.

The Commission mutation-scope and bounded-rereview rules above are
instances of the same pattern: each apparent gap was checked against
existing Commission-authoring/review mechanics before any Coordinator
change was considered, and neither turned out to need one.

This is an operating heuristic for Commission-authoring and design
judgment, not a machine-enforced WFC invariant, schema requirement,
admission gate, reviewer severity, or governance artifact type -- it is
deliberately left to human/Commission-author judgment rather than solved
by inventing mechanics that enforce it.

== 5. Attempt / OPS / STATE identity

[source,text]
----
attempt = <work-item-slug>-<date>-<counter>
          # e.g. wfc-projected-result-contracts-p1-20261007-01

OPS   = ~/wfc-ops/<attempt>
STATE = ~/wfc-state/<attempt>
----

This mapping is deterministic and holds *before STATE actually exists*: the
Attempt name alone determines where OPS will be created and where STATE will
later materialize -- no registry or database. `wfc-op`'s own
`ops_root()`/`state_root()` and the canonical `wfc-archive-run` wrapper's
`attempt_id=${state_root##*/}` derivation are the same convention, reused,
not duplicated.

== 6. Normal operator workflow

[source,text]
----
author / accept concept or task intent
    -> author Commission (WorkItem, Profile, Policy, Components, Task)
    -> commit Commission
    -> wfc-op prepare                  [deterministic Harness mechanics]
    -> inspect PREPARED / NOT LAUNCHED [maintainer decision point]
    -> wfc-op launch                   [mechanics; crosses provider boundary]
    -> wfc-op status                   [read-only, any time, any shell]
    -> terminal Run state              [WFC-owned semantic/mechanical fact]
    -> wfc-op archive                  [deterministic, delegating mechanics]
    -> semantic ledger curation        [maintainer/LLM-assisted judgment,
                                         never automated by Harness v0]
    -> Runtime promotion, separately, if accepted
    -> push, separately, if authorized
----

[cols="2,3",options="header"]
|===
|Step |Nature

|Commission authoring/commit |Semantic -- maintainer-owned, reviewed
|`prepare` |Deterministic mechanics (section 7), plus one provider-free
preflight *validation* seam that refuses rather than decides
|PREPARED / NOT LAUNCHED |Maintainer decision point: go or don't go
|`launch` |Mechanics up to starting the Run; Hops themselves are WFC-owned
semantic execution, not Harness mechanics
|`status` |Deterministic, read-only projection
|Interpreting a terminal state |Semantic -- maintainer judgment (13-14)
|`archive` |Deterministic, delegating mechanics
|Ledger curation |Semantic -- maintainer/LLM-assisted, never Harness-automated
|Runtime promotion / push |Explicit maintainer action, never automatic
|===

=== Direct-v1 Commission quickstart

`commission render` is a closed-program, *non-authoritative* projection:
it turns a maintainer-authored Direct-v1 Intent into ordinary governing
files, but neither admits a Run nor invokes a provider. From the Development
repository root, render an Intent and inspect its provenance-labelled report:

[source,shell]
----
COMMISSION=example-direct-v1-001
INTENT="governance/commissions/$COMMISSION/intent.yaml"
OUT_DIR="governance/commissions/$COMMISSION"

python3 scripts/wfc_op.py commission render \
  --intent "$INTENT" \
  --out-dir "$OUT_DIR" \
  --check
----

The render writes `work-item.yaml`, `profile.yaml`, `policy.yaml`,
`task.md`, and `render-manifest.json` below `OUT_DIR`. The manifest records
the Intent digest and the pinned program, policy-basis, component-manifest,
and selected-component source commits and digests. Review both the Intent
and those rendered governing artifacts, then commit them. A commit is
required between rendering and checking because checking admits a clean,
named Git tree:

[source,shell]
----
git add "$INTENT" "$OUT_DIR"
git commit -m "chore: add $COMMISSION Commission"
HEAD="$(git rev-parse HEAD)"

python3 scripts/wfc_op.py commission check \
  --intent "$INTENT" \
  --repository "$PWD" \
  --expected-head "$HEAD" \
  --out-dir "$OUT_DIR"
----

`commission check` re-renders from the recorded source pins, requires each
committed rendered byte to match, and then calls canonical, provider-free
operator preflight. It is therefore an admission check, not an authorization
to execute. After it succeeds, use the rendered paths with
`prepare`; inspect `PREPARED / NOT LAUNCHED`; and launch only under separate
maintainer authorization (sections 7-8).

== 7. PREPARE

`prepare` performs every deterministic preparation mechanic
`docs/run-preparation.adoc` and `docs/self-development.adoc` already
document, nothing else:

. Pins exact Development/Runtime/Evidence commit identities from the live
  checkouts, never re-typed by the maintainer.
. Requires clean Development/Evidence worktrees, and a clean, detached,
  push-disabled Runtime.
. Refuses an Attempt whose OPS or STATE already exists.
. Creates OPS; derives (but never creates) the STATE path -- STATE's absence
  is a WFC launch precondition, not a `prepare` side effect.
. Exports the exact Runtime commit via `git archive` into a fresh runtime
  venv; builds a separate development/evidence venv from the *live* pinned
  Development checkout (never an export -- exporting would strip `.git`,
  exactly the substrate mistake this tool prevents by construction).
. Writes `execution-bindings.yaml` from the explicit `--role-binding` values
  given; no automatic model/provider selection.
. Assembles the controlled `PATH` and verifies it resolves `python3` to the
  development/evidence interpreter.
. Runs provider-free preflight through one narrow, isolated seam calling the
  *pinned Runtime's own* `operator._preflight()` under its own interpreter --
  never a Harness reimplementation of admission/preflight semantics.
. Persists `preparation-pins.txt` and `harness-prepared.json` (pins, paths,
  launch-artifact digests).
. Materializes `launch.sh`; re-revalidates every pin; stops; prints:

[source,text]
----
PREPARED / NOT LAUNCHED
----

It never launches. Drift between what was pinned and what is now true is a
named refusal, never a guess.

[source,shell]
----
python3 scripts/wfc_op.py prepare \
  --attempt   wfc-<work-item-slug>-<date>-<counter> \
  --development /home/stefan/repos/spreadsheet-handling/workflow-coordinator \
  --runtime      /home/stefan/repos/spreadsheet-handling/workflow-coordinator-runtime \
  --evidence     /home/stefan/repos/spreadsheet-handling/workflow-coordinator-run-evidence \
  --work-item    governance/work-items/<work-item>.yaml \
  --profile      governance/self-development/<profile>.yaml \
  --policy       governance/self-development/<policy>.yaml \
  --components   governance/self-development/components.yaml \
  --task         governance/work-items/<task>.txt \
  --executable   /usr/local/bin/codex \
  --timeout-seconds 3600 \
  --role-binding worker=codex_cli:gpt-5.6-terra:medium \
  --role-binding independent_reviewer=codex_cli:gpt-5.6-terra:high
----

`--work-item`/`--profile`/`--policy`/`--components`/`--task` are
Development-relative paths; Harness checks only that they exist and are
repository-relative. It does not semantically validate their content -- that
is the canonical preflight seam's job, and ultimately the reducer's.

== 8. LAUNCH

[source,shell]
----
python3 scripts/wfc_op.py launch "$ATTEMPT"
----

`launch` does *not* reconstruct operator CLI inputs from scratch. It locates
OPS/STATE from the Attempt name; refuses if preparation never completed or
STATE already exists (fail closed, never silently reused); re-digests
`launch.sh`/`execution-bindings.yaml` against what `prepare` recorded,
refusing on drift; re-revalidates Development/Runtime/Evidence HEAD and
cleanliness; only then executes the already-materialized `launch.sh`
unmodified, preserving stdout/stderr/return code verbatim.

STATE is materialized at `~/wfc-state/<attempt>` only once the pinned
Runtime's own process actually starts the Run; Hops then execute until a
terminal state. `launch` may run for a long time before returning, and
prints `LAUNCH RETURN CODE: <n>` to stderr. *A non-zero return code does not
by itself mean provider or Harness failure* -- `awaiting_human` and other
legitimate terminal states can produce one too (section 13). Always inspect
persisted facts via `status`, never the return code alone.

== 9. STATUS

[source,shell]
----
python3 scripts/wfc_op.py status "$ATTEMPT"
python3 scripts/wfc_op.py status "$ATTEMPT" --json
----

Strictly read-only; never creates, mutates, retries, reconciles, or launches
anything. Safe and useful from a second shell while a Run executes in the
first. Always exits `0`: an unknown Attempt, incomplete preparation, or a
mechanical inconsistency are reportable facts, not command failures.

It projects, in priority order, whatever persisted files exist:
`preparation-pins.txt`/`harness-prepared.json` (what was prepared),
`operator-plan.json` (what was admitted), `operator-summary.json`/
per-checkout `run.json` (what happened). Where two sources each carry their
own non-empty value for a field and disagree, `status` *surfaces the
disagreement* rather than picking one -- the same discipline
`wfc-archive-run`'s `agree()` helper enforces. It never invokes the pinned
Runtime's own `wfc status` (that would be Runtime-version-coupled); reading
only persisted JSON keeps it correct across Runtime-N/Development-N+1 drift.

Fields to read: `lifecycle`, `run_id`, `work_item_id`, `checkout_id`,
`run_status`, `current_phase`, `hop_used`/`hop_limit`, `stop_reason`,
`human_question`, `final_head`, `worktree_clean`, `anomalies`/
`inconsistencies`/`corrupt_sources`.

Real example (worked attempt, section 18):

[source,text]
----
attempt: wfc-projected-result-contracts-p1-20261007-01
lifecycle: RUN_RECORDED
run_id: RUN-157080a2fa7b44de8429aa9b8fba53ab
run_status: awaiting_human
current_phase: rereview
hop_used: 4
hop_limit: 8
stop_reason: completion_blocked_by_open_blocking_findings
final_head: 84fba1653738214bc49d0eabfeefeb4deb03023f
worktree_clean: True
anomalies: []
----

== 10. ARCHIVE

[source,shell]
----
python3 scripts/wfc_op.py archive "$ATTEMPT" --dry-run
python3 scripts/wfc_op.py archive "$ATTEMPT"
----

A deterministic, delegating wrapper around the canonical
`workflow-coordinator-run-evidence/scripts/wfc-archive-run`. Harness derives
the wrapper's two positional arguments -- STATE root and Evidence repository
-- from the Attempt's own preparation facts, refusing if the two preparation
records disagree on the Evidence path. Default behavior is always
*canonical dry-run, then canonical real archive*; passing `--dry-run` to
`wfc-op archive` stops after the plan. `--semantic-json`, if given, is
forwarded verbatim. Harness implements none of the copying, hashing,
manifest, or fact-extraction logic itself.

Three layers stay conceptually separate:

[source,text]
----
STATE              live/persisted WFC execution state
mechanical archive deterministic archived evidence, committed by the
                    canonical wrapper -- a faithful copy-with-manifest
semantic ledger     curated semantic interpretation/history
                    (project_memory/run_ledger.adoc in Evidence)
----

Harness v0 performs only the mechanical archive; it never writes, updates,
or interprets the semantic ledger.

== 11. Semantic ledger curation

After a mechanical archive exists, current project convention adds a
curated entry to `workflow-coordinator-run-evidence/project_memory/
run_ledger.adoc`: Runtime version, domain exercised, what happened across
Hops, model/role bindings, related commits/BUGs, predecessor/successor
links, lessons, evidence location. This is maintainer-owned, commonly
LLM-assisted, and performed separately against the already-archived
mechanical facts -- not automated by `wfc-op archive` or designed here.

== 12. max_autonomous_hops

*This is a safety ceiling, not an estimate of expected Run length.* It is
the single most commonly misapplied piece of operator judgment here.

`max_autonomous_hops` is a WorkItem field, capped by the repository policy's
own ceiling and a hard Coordinator maximum. At Run creation it becomes
`Run.hop_limit`; `status` reports it alongside `hop_used`.

Common mistake: expecting a task to need implementation, review,
correction, and rereview -- maybe 2-4 Hops normally -- and concluding
`max_autonomous_hops` should therefore be 4. That does not follow. The same
task may legitimately need an additional review/correction cycle if a fresh
reviewer finds another real Finding; a too-tight ceiling then converts
healthy convergence into an unnecessary `awaiting_human` stop. Conversely,
an excessively high ceiling enlarges cost and autonomous blast radius if
agents genuinely fail to converge.

Choose the value as a *bounded worst-case safety ceiling* against repeated
symptom treatment, review/correction oscillation, an agent failing to
recognize a legitimate stop condition, or other genuine convergence
failures -- not as an *expected Hop count*. The probability of a convergence
defect does not shrink merely because the task seems easy; a "simple" task
does not justify an artificially tiny ceiling.

For the current bounded self-development workflow, `8` -- the value used in
section 18's worked example, which converged in 4 Hops with 4 unused -- is a
reasonable illustration of this principle, not a universal recommendation.
Set the value per WorkItem from this reasoning, not by copying `8`.

== 13. Terminal states and awaiting_human

`awaiting_human` is *not* synonymous with provider failure, implementation
failure, or failed review. It means the current Run's authority/mechanics
cannot legally continue -- the trusted reducer correctly refused rather than
fabricate or assume authority it does not have.

When a Run stops `awaiting_human`, inspect in order: `stop_reason`; any
`human_question`; open Findings and which phase, if any, holds
`finding_authority` over them; the last recorded phase/result; `anomalies`;
durable review artifacts the Run references. This is correct fail-closed
behavior, not a malfunction.

== 14. Successor Runs

Do not rewrite or "repair" historical terminal Run state. If additional
authorized work is genuinely needed:

[source,text]
----
archive the original Run truthfully
    -> curate the ledger, if convention requires it
    -> make a fresh maintainer decision
    -> create a separately authorized successor Commission / Attempt
----

A successor may reference predecessor evidence but must never fabricate a
different historical outcome for it -- the same discipline
`docs/run-recovery-and-salvage.adoc` establishes for salvage (`salvage
preserves work, not authority`). See that document for the full four-outcome
procedure when a Run or Hop does not cleanly complete at all, as opposed to
completing with an authority gap (section 13's example).

== 15. Runtime promotion

Runtime promotion is separate from WFC semantic acceptance, `archive`,
ledger curation, and push; none of those four implies or performs it.

Runtime always executes an *exact* accepted implementation commit, selected
explicitly by the maintainer -- never "latest `main`", current Development
HEAD, a `git pull`, or an implicit branch update. Review/closure commits may
legitimately exist on Development/`main` after the accepted implementation
commit; that is expected shape, not drift. Mechanically, promotion fetches
the exact target commit into the Runtime clone and checks it out detached
(full command/preconditions/postconditions:
`docs/self-development.adoc`'s Runtime promotion runbook). Runtime stays a
separate clone/object store, detached, `remote.origin.pushurl=DISABLED`,
before and after. No Harness command promotes Runtime; no generic
auto-promotion feature exists.

Development, Runtime, Evidence, OPS, and STATE are five distinct things:
Development is the evolving candidate plus Commission/implementation
history; Runtime is the pinned accepted implementation that executes Runs;
Evidence is the durable archive/ledger location; OPS is Harness's prepared
envelope; STATE is WFC's own execution state. Collapsing any two -- e.g.
assuming Development HEAD is what Runtime executes, or that OPS existing
means a Run has started -- is the most common operator misunderstanding this
manual exists to prevent.

== 16. Evidence architecture: current state vs. future direction

*Current state (implemented today).* For self-development, mechanical
archive evidence lives in the sibling `workflow-coordinator-run-evidence`
repository under `archive/<classification>/<attempt>/`, each with a
`manifest.json` of copied files and SHA-256 digests. The curated semantic
ledger lives in the same repository at `project_memory/run_ledger.adoc`.
`wfc-op archive` delegates to its `scripts/wfc-archive-run`; Harness owns
none of its copy/manifest/commit logic.

One practical limitation of the current archive, confirmed by the
link:cold_storage/backlog/pre-0.1.0b1/projected-result-contracts/wfc_p2_stagnation_audit_2026-10-09.adoc[historical P2 stagnation audit]: a trusted evidence
observation persists its exit classification, exit code, and byte-count/
SHA-256 digests of stdout and stderr, but not the full output body. A
subsequent correction Hop (section 22.4) is therefore told *that* required
evidence failed, not *which* assertions or tests failed, and may need to
re-run the relevant command itself to localize the failure. This is a known
limitation of the current evidence persistence, not something redesigned
here.

*Future direction (design intent only -- not implemented).* Evidence
archival should eventually be a WFC *product capability*, not merely a
self-development add-on: a consumer repository might configure durable
archival as disabled, repository-local, or external (a sibling/central
Evidence repository, as self-development already uses). Motivation:
long-term auditability favors curated, machine-readable records over
uncontrolled raw logs; future retrieval tooling may be as simple as
deterministic `jq`/scripts before anything more elaborate is justified.
Nothing here designs or implements this; it is recorded so a future
maintainer does not mistake today's self-development-specific arrangement
for the final product shape.

== 22. Trusted evidence, worker completion, and correction routing

*A Commission that conflates worker completion with trusted acceptance, or
that omits `failed_evidence_route` from a review gate, can turn a declared
evaluator/optimizer correction loop into a one-shot acceptance gate --
silently, because the omission is syntactically valid.* This section
documents the current mechanics precisely enough to author around that
trap. The motivating observed failure is recorded in the
link:cold_storage/backlog/pre-0.1.0b1/projected-result-contracts/wfc_p2_stagnation_audit_2026-10-09.adoc[historical P2 stagnation audit]; read this section for the
generic mechanism, that audit for one concrete case history.

=== 22.1 The trusted ordering within a Hop

Reconstructed from `vertical.py::run_one_hop` and
`reducer.py::reduce_result`. This ordering governs every Hop and is the
basis for everything else in this section:

[source,text]
----
semantic agent result
    -> CommitIntent admission
    -> Coordinator-owned trusted commit
    -> Coordinator-trusted evidence
    -> route reduction / application
----

Each stage, briefly:

* *Semantic agent result* -- the provider returns a structured result (a
  `WorkResult` for a `worker` phase, a `ReviewVerdict` for a review gate).
  It carries the agent's requested route and, optionally, a `CommitIntent`.
* *CommitIntent admission* -- a non-null `CommitIntent` is admitted only
  when the result's outcome is `completed` (or, for a gate, `changes_required`
  committing only to that phase's own durable review artifact), scope is
  unchanged, `requires_human` is false, `escalation` is null, and the phase
  grants both the `edit` and `commit` actions. The agent never runs Git
  itself; `CommitIntent` is a proposal, never proof that anything was
  committed.
* *Coordinator-owned trusted commit* -- if admitted, the Coordinator itself
  materializes one bounded local commit. This is *publication of bounded
  work, not acceptance*.
* *Coordinator-trusted evidence* -- only now does the Coordinator execute
  the phase's required evidence commands (`phase.evidence`), after the
  result and after any commit (see section 16 for a persistence
  limitation on this evidence). An agent cannot have proven this outcome at
  result-authoring time; the fact does not exist yet when the result is
  authored.
* *Route reduction* -- the reducer resolves the applied route from the
  requested route and the evidence disposition (22.3), then persists the
  checkpoint.

=== 22.2 Five concepts that must not be conflated

[cols="1,1,3",options="header"]
|===
|Concept |Owner |Meaning

|Worker completion
|agent (semantic)
|`status: completed` -- the bounded candidate for this phase is coherent
and ready for its declared next step. Gates `CommitIntent` admission;
nothing else.

|Trusted commit
|Coordinator
|One bounded local commit materialized from an admitted `CommitIntent`.
Publication, not acceptance.

|Trusted evidence
|Coordinator
|Independent, post-commit, Coordinator-executed observation of
`phase.evidence`: `pass`, clean `fail`, or `error`/`not_run`. Agent-side
test runs are never this, however diagnostic they are.

|Review acceptance
|gate phase (semantic)
|`verdict: accept` from a phase with sufficient Finding-disposition
authority over any open blocking Finding.

|Run completion
|reducer
|A `complete`-effect route actually applied, with no open blocking Finding
and required evidence not cleanly failing.
|===

All five must align for a Run to complete; no single one implies any
other. Review acceptance (a gate's own semantic verdict) and trusted
evidence (the Coordinator's independent mechanical observation) are
separate authorities over the same gate -- 22.3 explains how the reducer
combines them.

In particular, worker `completed` does *not* mean "I have already proven
every downstream Coordinator-required acceptance criterion" -- that
reading is unsatisfiable, because trusted evidence executes after the
result is parsed (22.1), so no worker can truthfully assert its outcome at
authoring time. A worker that downgrades to `blocked` to avoid asserting
that is not being honest about a red downstream gate -- it is destroying
its own trusted-commit path and leaving otherwise-good work uncommitted.
Reserve `blocked` for when the current Hop itself lacks authority, scope,
or a capability it needs -- never for a downstream gate that has not run
yet.

=== 22.3 `failed_evidence_route`

`failed_evidence_route` is a field of a phase's `review:` descriptor --
`review.failed_evidence_route` -- and only a *gate* review
(`review.authority: gate`) may declare it; a `worker` phase (`review:
null`) structurally cannot. When declared, it must name one of that phase's
own routes whose effect is `goto` or `await_human`; the loader refuses an
unknown target or every other effect. An `await_human` route uses its normal
mandatory authored `question`.

For a *new launch* (including a prepared successor), every phase with
non-empty Coordinator-required `evidence:` must be a gate and must declare
this field. Thus a `goto` target is the explicit correction disposition,
while an `await_human` target is the explicit human-disposition choice. A
worker, advisory, or other non-gate phase with required evidence is
inadmissible for a new launch; worker phases with `evidence: []` remain the
canonical shape. Agent-side diagnostic test execution is unaffected.

This is a new-launch admission rule, not a historical parsing rule. Existing
profiles, replay, and recovery remain readable without revalidation under it;
in particular, `_export_salvage()` intentionally reloads predecessor profiles
without applying this new-launch admission check.

Its effect at reduction:

[source,text]
----
required evidence: pass
    -> ordinary reduction of the agent's requested route

required evidence: clean fail, gate declares a valid failed_evidence_route
    -> that route REPLACES the agent's requested route
       (a reviewer's `accept` can be deterministically overridden)

required evidence: clean fail, no valid failed_evidence_route on this gate
    -> Run stops awaiting_human / required_evidence_failed_without_route

required evidence: error / not_run
    -> hard mechanical stop, preempting even the semantic result
----

So `failed_evidence_route` is the *only* mechanism that lets a mechanical
evidence failure be absorbed into a correction loop rather than stopping
the Run. A gate carrying required evidence but no `failed_evidence_route`
can still route a semantic `changes_required` Finding to correction -- but
a clean mechanical evidence failure at that same gate has nowhere to go.
If a Run stops this way, see the troubleshooting entry in section 17.

Do not read this as "every evidence failure should route to correction."
A Commission may deliberately choose an `await_human` route, with its
authored question, instead. The admission rule requires that the choice be
explicit rather than represented by omission.

=== 22.4 Canonical converging review topology

The current mechanics already support a genuine autonomous
evaluator/optimizer correction loop. The canonical shape:

[source,text]
----
integration / implementation [worker]
    evidence: []
    completed -> independent_review

independent_review [gate]
    evidence: [pytest or other acceptance evidence]
    review.failed_evidence_route: correction
    accept            -> complete
    changes_required  -> goto correction

correction [worker]
    evidence: []
    completed -> rereview

rereview [gate]
    evidence: [pytest or other acceptance evidence]
    review.failed_evidence_route: correction
    accept            -> complete
    changes_required  -> goto correction
----

Properties this shape gives you, all already executable under the
currently accepted mechanics, with no Core change:

* An imperfect candidate can still be committed and handed to independent
  review, because the worker phase carries no required evidence to fail.
* It remains impossible to *complete* while required evidence is red,
  because both `complete` routes sit behind gates carrying that evidence.
* A reviewer's semantic `accept` is deterministically overridden by a
  clean trusted-evidence failure, routing to `correction` instead.
* `rereview` can repeat the same gate after correction, producing a
  genuine multi-Hop autonomous loop, bounded by the ordinary Hop budget
  (section 12) rather than looping indefinitely.

Worker phases *may* still run the same evidence command themselves,
diagnostically -- `phase.evidence` governs only what the *Coordinator*
requires, never what an agent is permitted to run in its own shell. The
distinction that matters:

[source,text]
----
agent diagnostic execution  !=  Coordinator-required evidence attached to that phase
----

The first is useful input the worker can use to improve its candidate
before handing it to the gate. The second is what the reducer actually
trusts, and it belongs on the gate, not the worker.

This canonical shape composes with the existing review-breadth guidance
(section 4, "Review breadth and bounded rereview convergence"): a worker
may make a small bounded correction and still hand the *complete current
candidate* to review -- latest mutation scope and review scope are
different concepts. The first `independent_review` of a candidate should
be broad, inspecting the entire accumulated candidate rather than only the
latest diff. A subsequent `rereview` should normally narrow to the known
current-Run Findings, the corresponding correction, direct regressions,
and the gate's own trusted evidence; a genuinely new MATERIAL defect
supported by concrete new evidence may still escape that bounded surface.

=== 22.5 Commission-authoring anti-patterns

[cols="2,3,3",options="header"]
|===
|Anti-pattern |Shape |Why dangerous

|Full acceptance evidence on a worker phase
|A normal (non-gate) worker phase in a converging correction workflow
declares the full/global acceptance evidence as `phase.evidence`.
|A `worker` phase (`review: null`) structurally cannot declare
`failed_evidence_route` (22.3). A clean evidence failure there has no
absorbing route and is terminal -- the worker Hop becomes an accidental
one-shot acceptance gate.

|Gate without `failed_evidence_route`
|A review/rereview gate carries required acceptance evidence and has a
`correction` route available, but does not declare
`review.failed_evidence_route`.
|A semantic `changes_required` Finding can still route to `correction`,
but a mechanical evidence failure cannot. The profile advertises a
correction loop it cannot actually exercise from an evidence failure.

|Task prose demanding full-suite proof before `completed`
|Commission/task text tells a worker not to report `status: completed`
until the downstream full acceptance suite is green.
|Conflates worker completion with trusted acceptance (22.2). It can force
useful, commit-ready work into `blocked`, which suppresses that work's own
trusted-publication path instead of letting the gate's evidence do its
job.

|Escalating on a sandbox-only tooling gap
|An agent cannot execute a trusted evidence command in its own sandbox
(for example, a networked install its environment blocks) and escalates
for that reason alone.
|The worker should report that diagnostic limitation in its `summary` and
continue, provided its bounded work can otherwise be completed --
Coordinator execution, not the agent's shell, is the trusted authority.
Escalating here is an unjustified scope/authority claim, not a correct
refusal.

|Unsatisfiable prerequisite
|Mandate or acceptance text makes continuing, or being accepted,
conditional on a fact or confidence level that cannot be reached using
only the evidence-gathering means this Commission's own grant actually
provides -- regardless of the specific wording used to state it. Most
acute when the one decisive evidence source is explicitly withheld by
the same Commission's `withheld_authority`.
|No Worker skill resolves a deadlock the Commission itself created; the
same stop recurs identically across successor Commissions. Worked case:
`docs/backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc`,
Attempts `wfc-claude-adapter-write-permissions-001`
(`RUN-dcdf990244dd4e9cba19e40dea2d2400`), `-002`
(`RUN-878fbc45e9454cef93cccea7423475ee`), and `-003`
(`RUN-19d5cc40915d466b8790171f3308a4f4`) -- all three stopped at H001
with zero candidate on a variant of the same unresolved demand.

|Unverifiable acceptance conditions
|Acceptance or durable-artifact wording requires an artifact to
demonstrate a fact that a cited governing source (a BUG record, a design
document) already states cannot be established within the Commission's
granted authority.
|Guarantees either a stall or an artifact that overclaims. Check
acceptance wording against any cited source's own stated limitation
before committing, not only against the Commission's own prose.

|Constraint accumulation across successor Commissions
|A successor authored after a predecessor's *clean* stop
(`worktree_clean: true`, no candidate) adds new provenance narrative and
withheld-authority clauses, restating predecessor history, without
removing or restructuring the demand that produced the stop.
|Task length and apparent specificity grow every iteration while the
actual deadlock is untouched -- 16.4KB, 22.6KB, then 28.1KB across the
three Attempts above -- consuming Hop budget on historical re-reading
and creating a false impression of narrowing progress toward a
resolution that was never addressed.
|===

=== 22.6 Semantic Commission-preflight checklist

A short operator reading check before committing a Commission -- in
addition to 22.5 above and the successor-continuation runbook's
mechanical validation step. This is something an Operator applies while
reading the drafted Commission; it does not require the Commission's own
task text to contain any particular boilerplate.

. Trace every Mandate/acceptance sentence that makes continuing, or
  being accepted, conditional on a fact. Confirm the Commission's own
  granted authority actually provides a way to reach that fact, or a
  reasoned judgment about it from available evidence -- not merely that
  the sentence sounds rigorous.
. If a cited governing source states its own limitation on what can be
  established by the means this Commission grants, check the
  Commission's acceptance wording against that stated limitation.
. If this Commission succeeds a predecessor that stopped clean on an
  unresolved demand, confirm this Intent removes or restructures that
  demand rather than adding another narrowed carve-out or provenance
  paragraph on top of it.

Experimental implementation within a Commission's granted authority is
the ordinary default (`self-development.adoc`, "Commission authoring")
-- a Worker may choose, try, and record residual uncertainty about a
technical approach without that becoming a missing-authority escalation,
and task text need not restate this default. Write an explicit exception
into the task only when one genuinely applies: a fact the Commission
deliberately withholds authority to establish, or a prerequisite the
Worker must not attempt to resolve by investigation.
