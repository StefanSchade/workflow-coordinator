= WFC Level-1 operator friction log

Maturity::  working log
Authority:: informative; non-authorizing
Updated::   2026-11-25
Owns::      Dated observations of friction a Level-1 operator met while using the WFC Front Door and the Agent Skill, each with evidence, who is affected and an improvement candidate. It decides nothing and grants no authority.

The log collects friction so that it can improve the Agent Skill, the Operator
Manual and the product. An entry that becomes concrete work becomes an FTR or
a BUG in the link:../../backlog/_open.adoc[backlog] and keeps only a pointer
here. Entries describe what happened and what it cost; they do not assign
fault. Add new entries at the end of the section of their date.

== 2026-11-25 -- Beta-2 opening (docs-sync, token usage, release planning, slice R2)

[cols="1,3,2,2,2",options="header"]
|===
|# |Observation |Evidence |Affects |Improvement candidate

|1
|`simple@v1` is refused when `.wfc/config.yaml` names a role the program does
not use (`independent_reviewer`): "execution config defaults name roles the
selected program does not use". `wfc plan` refuses it first, so a consumer
that keeps a reviewer default for `robust@v1` cannot also use `simple@v1`
without a second config.
|`wfc plan` output of 2026-11-25; workaround: an in-repo config file without
the reviewer, committed in the run worktree only.
|Operator, Front Door, Skill (setup)
|Let a program ignore unused role defaults, or have the skill and quickstart
state the second-config pattern and the integration rule (do not integrate it).

|2
|A Consumer Config outside the repository is accepted by `wfc plan` but
refused after authorization: "post-commit verification failed: Consumer Config
must be an A1-normalized repository-relative path". That consumed the
checkout's single lifecycle; a fresh worktree was needed.
|`wfc run` log of the first attempt; a lifecycle is one per checkout.
|Operator, Front Door
|Refuse the same input in `wfc plan` (before authorization), or say in
`wfc plan --help` that `--config` must be repository-relative and committed.

|3
|There is no documented concurrency contract for two Runs archiving into the
same Evidence repository. The operator therefore serialized the
authorization of the second Run and treated parallel operation as preparation
only.
|`frontdoor/archive.py` narrow-cleanliness check and the bounded commit; no
statement in the Operator Manual.
|Operator, Manual (chapter 4 evidence), Skill
|State what happens when two Runs archive at once (refusal and resume, or a
safe lock) and let the skill say whether parallel Runs are supported.

|4
|Every fresh checkout needs its own venv with an editable install, the
verified offline bundle in the environment (`WFC_TEST_INPUTS`,
`WFC_TEST_PROFILE`), a scratch `TMPDIR`, and a baseline probe of about 5.5
minutes for the full suite. None of the editable-install detail is in the skill
references; a shared venv whose editable install points at another worktree
breaks that worktree's task-check.
|Attempts of 2026-11-25; Operator Manual ch03 offline inputs (partly).
|Skill (setup), Manual
|Add a short "per-checkout environment" recipe to the skill's setup reference
and the warning about a shared editable install.

|5
|`wfc report` does not accept `--repository` although `wfc status`, `plan`,
`run` do; the operator had to learn it from an error.
|`wfc report: error: unrecognized arguments: --repository`
|Operator, Front Door (CLI consistency)
|Accept `--repository` or document the `source` argument in the skill.

|6
|A stale, read-only `.git/config.lock` from the previous day blocked
`git config` writes (a failed `git worktree remove` warning pointed at it). No
git process held it. It was removed on the maintainer's instruction.
|`ls -la .git/config.lock` dated 2026-11-24; `pgrep` found no git process.
|Operator, environment
|Skill note: how to tell a stale lock from a live one before asking.

|7
|The maintainer's premise "the skills document that token usage is not
reliably available" was not true of the Agent Skill; only the quickstart said
so. The first docs-sync Commission adopted the premise into a normative
convention, and a second Commission was needed to correct it.
|`grep -rni usage src/workflow_coordinator/agent_skill/` empty; the
correction commit `62f6740`.
|Operator process
|When a task states a fact about a shipped text, verify it against the files
before writing it into the task. (Operator error, recorded as such.)

|8
|The release comparison that started the release plan was made 107 commits
before the plan was commissioned; its WFC claims were partly stale (version
surface, new skill and tutorial files).
|Plan staleness section; `git log baab49e..main`.
|Operator process
|Check a basis document's baseline commit against `main` before commissioning
from it, and state the drift in the task.

|9
|A review artifact written by the independent reviewer failed the strict
asciidoctor render (incomplete table row). The release render gate does not
cover warm storage, so nothing noticed.
|`wfc_release_streamlining_broad_review.adoc` line 362.
|Reviewer prompt, docs gates
|Ask reviewers to render their own durable artifact strictly, or include the
review directory in the render gate.

|10
|The token Commission and the planning Commission ran side by side without a
collision. Review convergence differed widely (7 Hops for the code slice, 12
for the plan; the docs-only slice R2 needed 2).
|Run results of 2026-11-25.
|Operator planning
|Use the observed Hop counts when setting later budgets; plan narrow tasks
against a controlling FTR instead of a broad corpus.
