Two further checks of the mechanism itself:

* *No per-group `labels` key exists* in the reference (`labels` is
  update-entry-level and would apply uniformly to every PR from this single
  entry), so a label genuinely cannot distinguish the two sets. Group name
  is the right mechanism, and the file says so.
* *The group name really is the identifier.* H002 could only confirm the
  branch-name half and left the PR-title half as observation `O-2`. I
  resolved it: GitHub's version-update PR-optimization page states for the
  `groups` example that the name "will be used in pull request titles and
  branch names", and shows the title form ("Bump lodash in
  monorepo-dependencies group"). The file's comment and chapter 4's sentence
  are therefore accurate as written; `O-2` is closed as a non-issue.

Behaviour in the fail-safe direction, which I checked rather than assumed: a
*major* bump of a check-only action matches `check-only-actions`' patterns
but not its `update-types`, and matches no other group, so it arrives as its
own ungrouped pull request without the eligible group's name and cannot be
swept up by a rule keyed on that name. The same holds for any action added
to the workflow later but not to a pattern list.

[[r5-h005-simplicity]]
=== Simplicity and maintainability

I looked again for a materially simpler way to the same guarantees and did
not find one worth requiring. The gate is one `needs:` entry rather than a
new job, an `if:` or a status check; the Dependabot file is a single
`updates` entry with the minimal documented key set and no mechanism that
pretends to enable auto-merge. Two `updates` entries for the same ecosystem
and directory would violate the documented no-overlap rule, and a label
cannot distinguish the sets, so two named groups is the simplest valid
construction for D3. The one piece of arguably redundant mechanism is the
second group: identification only strictly needs the eligible group's name,
and publish-path updates would be distinguishable by arriving ungrouped.
It costs three lines, carries no state and makes the partition auditable
against the workflow (I used it that way in this review), so it is not a
maintainability defect -- recorded below as an observation, not a Finding.

=== Blocking Finding (new, `finding_id: null`)

*The G9 recovery response cites a recovery-table row that prescribes the
opposite action; the recovery table itself is now incomplete for G9.*

`ch04_release_management.adoc:185-190` (new text) says, of a red
`python-compat` caused by an index-side or upstream change:

____
... the response is a re-run of the failed jobs (`<<recovery>>`'s "Failed
before any upload" row -- nothing has been uploaded yet), never a re-tag.
____

`ch04_release_management.adoc:394`, the cited row, reads in full:

____
|Failed before any upload |Fix on `main`, delete the tag, tag again.
____

Deleting the tag and tagging again *is* a re-tag. A reader who follows the
cross-reference the chapter supplies as the authority for "never a re-tag"
finds an instruction to re-tag. Two consequences, both reproduced by
reading the committed file:

. Chapter 4 contains a statement that is false -- the cited row does not
  give the stated rule -- which violates the FTR acceptance criterion
  "Chapter 4 contains no statement that is false for the integrated
  pipeline", and the Commission's review focus "G9 with its recovery
  response is consistent with the recovery table".
. The recovery table, which is the chapter's authoritative recovery source,
  now gives the wrong answer for the failure mode G9 introduces. This is
  not a pre-existing defect the change merely inherits: before G9, a
  pre-upload failure in tag mode could only be a `check` failure, and
  `check` installs from the audited offline bundle, so such a failure is
  caused by this repository and "fix on `main`, delete the tag, tag again"
  was complete. G9 is the first release-blocking pre-upload job that
  installs from the ordinary index, so it is the first pre-upload failure
  that can be purely upstream and that a bare re-run can clear. The row is
  therefore a statement the change makes *incomplete*, which the Commission
  task's chapter-4 instruction explicitly covers ("bring every statement the
  change makes false or incomplete up to date").

The premise is defective upstream of the implementer: both the FTR ("the
chapter's recovery table already says so for a failure before any upload")
and the Commission task ("the recovery table already gives that rule for a
failure before any upload, reference it") assert something the recovery
table does not say. The maintainer's own D6 record in the plan
(`beta2_release_streamlining_plan.adoc:626-631`) states only the rule
itself -- "the response is a re-run of the failed jobs, not a re-tag" -- and
makes no claim about the table. So honouring D6 does not require the false
citation, and a correction is available inside the authorized chapter-4
scope. I am not escalating this as a scope question, because a feasible fix
exists within scope.

Feasible correction (either is sufficient; the first is preferred because it
also repairs the table):

. Split the "Failed before any upload" row, or extend its action, so that it
  distinguishes the two causes -- a failure caused by this repository: fix
  on `main`, delete the tag, tag again; a transient or upstream failure with
  nothing uploaded (the G9 case): re-run the failed jobs, the tag stands,
  never re-tag -- and leave the G9 bullet's cross-reference pointing at the
  now-correct row.
. Or reword the G9 bullet so it stops attributing the rule to that row,
  stating the D6 rule on its own authority and citing `<<recovery>>` only
  for the state ("nothing has been uploaded yet").

Nothing else in the candidate depends on the outcome; both options are
confined to `docs/developer_guide/ch04_release_management.adoc` and the
verification record.
