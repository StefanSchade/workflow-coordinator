=== Non-blocking observations

`N-1` and `N-2` are new in this pass and reproduced by my own execution;
`N-3`--`N-6` are smaller, and `O-1`, `O-3`, `O-5`, `O-6` of pass H002 still
stand as written there (I re-derived `O-5` and `O-6` independently; `O-3`'s
two record imprecisions and H006's third one -- line 26 names
`atomic_write_text` where `write_usage_record` calls `atomic_write_json`, and
the measured-checks entry claims "exit code 0" for a `pytest` run that also
reports failures -- are still in the verification record).

N-1 -- the per-model breakdown is bounded only by what the provider prints::
`_claude_model_usage` keeps every well-shaped `modelUsage` entry with no cap
on the number of entries and no bound on the model-id string. Measured: a
wrapper with 50000 entries yields 50000 `per_model` entries and a *7 789 176
byte* persisted `usage.json` record from one invocation, and a model key of
5034 characters containing a newline is stored verbatim as a "model
identifier". The task authorizes storing model identifiers, and no real
wrapper behaves this way, so this is not a violation -- but the leaf the task
calls "bounded" is bounded only by provider output, which this repository's
own convention treats as untrusted (compare `_bounded(stdout, 16_384)` in
both adapters). The concrete downside is post-Run, not in-Hop: such content
is archived, and if a model id ever contained an absolute path or the
operator's private string the projection would refuse (safely, but after the
Run), turning a provider quirk into a failed `wfc audit`. A cap on the entry
count plus a length/charset bound on the id in `_claude_model_usage` would
close it in two lines without new structure.

N-2 -- the report's usage block hard-indexes its input while the rest of the
module is defensive:: `build_report` reads every other section with
`audit.get(...)` and `isinstance(..., Mapping)`, and the module defines
`ReportError` as "a refusal to build or render a report from malformed audit
input". The new block instead indexes `usage["coverage_counts"]["complete"]`,
`usage["totals"]`, `usage["by_role"]` directly. Measured on an `audit.json`
carrying `"usage": {}` (a plausible shape for a hand-edited, truncated or
future-version document): `wfc report <audit.json>` exits `1` with an
unhandled `KeyError: 'coverage_counts'` instead of the designed exit-2
refusal; the same input renders fine on the pre-change tree. `usage: null`
and `usage: []` are handled correctly. Reachable only with an audit document
this version did not produce, hence non-blocking; one `.get` chain in the
same style as its neighbours would remove the asymmetry.

N-3 -- three of the new privacy tests are not red without the
implementation:: The three added cases in `tests/unit/test_audit_privacy.py`
call the pre-existing, generic `au._guard_privacy` on hand-built
usage-shaped dicts, so they pass on the baseline tree as well; the
`_canary_attempt` extension likewise cannot fail there, because the
pre-change projection ignores `usage.json`. They are still genuine
regression guards for the new shapes, and DO item 3's requirement ("the
guards must pass for the new fields; extend their tests") is met -- but a
`project_audit`-level leak case would be the stronger guard. I ran exactly
that by injection and it refuses correctly at four distinct JSON paths, so
only the test, not the mechanism, is the weaker link.

N-4 -- a second out-of-scope developer-guide file now states something
incomplete:: Beside `ch03_engineering_conventions.adoc` (pass H002's `O-1`,
still unaddressed), `docs/developer_guide/ch02_code_navigation.adoc` lines
63--66 enumerate the audit projection's sources as `manifest.json`,

verification record states twice that a baseline comparison was made "via a
scoped `git stash`". COMMIT MECHANICS binds the Hop to "no git command that
writes (no add, mv, rm, reset, stash, commit)", and in this worktree layout

O-3 -- two inaccuracies in the verification record besides `B-1`:: The record
says `write_usage_record` uses `atomic_write_text` (it uses

O-4 -- the parsers can still raise on pathologically nested JSON:: Both
`_usage_from_wrapper_stdout` and `_usage_from_stdout` catch only
`JSONDecodeError`/`ValueError`, so a single stdout line of valid JSON nested
beyond the recursion limit raises `RecursionError` out of `execute()`
(reproduced with 200000 nested arrays). For Claude this exposure already
exists in the pre-change `_candidate_from_wrapper` on the zero-exit path, but
for Codex the stdout stream was previously never parsed, and in `slice4.py` an
exception from `execute()` ends as a charged `uncertain` Hop. No provider
plausibly emits such a line, so I do not block on it; catching
`RecursionError` (or `Exception`) around the two `json.loads` calls would
close it at no structural cost.

O-5 -- `usage.json`'s two identity guards are unreachable in production:: A
fresh Run refuses a pre-existing state root ("one-shot operator roots are
never overwritten") and continuation re-validates the Run identity, so one
checkout state root never serves two Run ids and `H{n}` is allocated from
`hop_used`, so no Hop id is written twice with different content. Both
`ReductionError` branches are therefore dead weight today, and they would turn
a usage-write anomaly into an aborted Run after the Hop was already reduced.
They are cheap and conservative; I note them only as the kind of safeguard
worth re-examining rather than growing.

O-6 -- the Run total sums `input_tokens` across incompatible cache
semantics:: `totals.input_tokens` adds Claude's cache-exclusive and Codex's
cache-inclusive figures into one number with no marker at the aggregate
level, and the report prints `input=...` beside `cache_read=...`, which a
reader may add up and double-count the Codex share. The per-invocation flag
remains readable in the same `audit.json`, the task does mandate a Run total,
and all Runs today bind one adapter, so this is honest but coarse; an
aggregate-level semantics marker (or a note in the owning documentation)
would remove the ambiguity.

O-7 -- the report's usage block is not covered for a mixed Run in the
suite:: the added report tests cover the all-complete and the partial cases;
the mixed case (some Hops with records, some without) is only covered at the
audit layer. Cheap to add alongside the `B-2` fix.
