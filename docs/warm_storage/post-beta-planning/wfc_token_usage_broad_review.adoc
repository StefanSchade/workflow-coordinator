=== Blocking Findings

B-1 -- the frozen, released release-notes section was edited:: The task
restricts `docs/release_notes/release_notes.adoc` to the "planned entry for
the next version only, never the released text", and the file's own
`Standing` says a section is "frozen to `(released)` at the matching tag and
never edited afterward". The file has exactly two sections, `== 0.1.0b2 --
planned` (line 9) and `== 0.1.0b1 -- (released)` (line 35); the candidate's
only hunk replaces the limitations bullet at lines 89--97, i.e. *inside the
released section*, and `git show 7e4fbcc` ("freeze the 0.1.0b1 release notes
for the tag") confirms that bullet was already inside the frozen section at
the freeze commit. The planned section received nothing. Beyond the
process rule this also makes the released notes untrue of the release they
describe: 0.1.0b1 genuinely does not measure token usage. The verification
record's statement "Only the planned (unreleased) section was touched; no
released section was edited" is therefore inaccurate and must be corrected
with it. Feasible fix: restore the released bullet verbatim
(`git show 206777d:docs/release_notes/release_notes.adoc`) and put the new
statement in the `0.1.0b2 -- planned` section.

B-2 -- `wfc report` no longer keeps the "no usage reported" wording, and two
guarded tutorial listings became incomplete:: DO item 4 requires that "when
no usage was reported the current wording and behavior must remain" and that
the existing report output stay stable otherwise. A record is persisted for
every dispatched Hop regardless of what the provider printed, so a Run whose
provider reports nothing now has records with coverage `none`,
`_build_usage_section` returns a section, and `render_report_text` emits
three new lines. Reproduced by execution for a single-Hop Run with one
coverage-`none` record:
+
----
usage       coverage complete=0 partial=0 none=1
usage total none reported
usage role  worker  none reported
not done    limits: no_lifecycle_facts, usage_not_reported
----
+
This is exactly the demo kit's situation: `examples/consumer-demo/rehearse.py`
binds `codex_cli` (line 135) and `examples/consumer-demo/scripted_provider.py`
writes nothing to stdout, so every rehearsal Run now reports these three
lines. The quoted "real output" listings in
`ch09_consumer_quickstart/02_first_run_example.adoc` (listing at lines
142--162) and
`03_tutorial_program_change.adoc` do not show them, so both listings are now
incomplete, and the docs-sync table's "Unchanged because still true" row for
them -- justified only by the `limits` line, not by the added lines -- does
not hold. `tests/unit/test_report.py::TestUsageReport::test_no_usage_recorded_keeps_prior_wording_and_adds_no_usage_section`
covers only the *no record at all* case, so the suite does not catch this.
Feasible fix (design is the Worker's): render the report's usage block only
when something usable was captured, for example when
`coverage_counts["complete"] + coverage_counts["partial"] > 0` (equivalently:
when the `usage_not_reported` limit is absent), which restores the previous
wording byte-for-byte for that case and leaves the two listings accurate;
`audit.json`'s section may stay as it is, since the task does require it once
a record exists. Whatever the choice, the docs-sync row and the regression
test must then state the real rule.

B-3 -- the required privacy-guard test for the new audit fields is missing:: DO
item 3 ends "The privacy guards of the projection (no path, private string,
remote) must pass for the new fields; extend their tests", and DO item 5 lists
"privacy guard" among the required audit-projection tests. No test exercises
the guard over the new fields: `tests/unit/test_audit_privacy.py` never
mentions usage and its canary fixture builds every Hop with `usage=None`, so
its own docstring claim that "every source field of the synthetic fixture
carries a known canary" no longer holds for the new source file; no new test
raises `ProjectionError` from a usage field. I verified by injection that the
mechanism itself works (see above), so this is a missing regression guard, not
a product defect. Feasible fix: one canary case in `test_audit_privacy.py`
(for example `ab.usage_record(model=ab.DEFAULT_HOME + "/m")` and a
`per_model[].model` carrying a canary) asserting the refusal and its JSON
path, plus the usage record in `_canary_attempt` so the module-wide
no-leak test actually covers the new section.

the correction Hop does not disturb them:

  unknown (`O-4` is the one exotic exception).

  synthetically and through the real archiver.
* The `wfc.audit/1` allow-lists changed additively; `_assert_keys` still
  refuses an unexpected key in every new section, and the privacy guard
  covers the new fields.
* Claude's cache-exclusive and Codex's cache-inclusive `input_tokens` are
  preserved per record via `input_includes_cache_read` and are
  distinguishable in the archive (`O-6` concerns only the aggregate view).
* Coverage and lower-bound logic is correct for mixed Runs, and the per-role

* No write surface beyond the Run's own checkout state, archived additively.

=== Non-blocking observations

O-1 -- the docs-sync check left one statement it falsified unreported::
`docs/developer_guide/ch03_engineering_conventions.adoc` (section
`frontdoor-docs-sync`, lines 54--59) still says "the consumer quickstart and
tutorial listings currently document that no token usage is reported ...
while the Agent Skill says nothing about token usage; an implementation of
token accounting would make the quickstart and tutorial statements
incomplete". After this change both clauses are false: the quickstart now
documents capture, and the skill's `references/stops-and-evidence.md` now
speaks about usage. That file is not among the owners the task enumerates and
editing it is outside the WorkItem's declared scope, so the correct move was
the one the task names -- report it as a scope question -- and it is missing
from the table entirely. I raise it here for the maintainer rather than
blocking on it: the convention's example is illustrative, not an owner of
operating information.

O-2 -- `git stash` was used although the commit mechanics forbid it:: The
verification record states twice that a baseline comparison was made "via a
scoped `git stash`". COMMIT MECHANICS binds the Hop to "no git command that
writes (no add, mv, rm, reset, stash, commit)", and in this worktree layout
the stash stack is shared with every other checkout. I found no residue
(`git stash list` holds only two older, unrelated `On main` entries; the
index and worktree are clean), so no damage is detectable, and the same
comparison is reachable without a Git write (`git archive | tar -x`, which is
what I used). Recorded for the maintainer as a process matter.

O-3 -- two inaccuracies in the verification record besides `B-1`:: The record
says `write_usage_record` uses `atomic_write_text` (it uses
`atomic_write_json`), and its `codex_adapter.py` entry first calls the missing
`json` import "pre-existing in the module before this change" and then
correctly concludes it was "this slice's own omission". The baseline module
contains no `json.` use at all, so only the second reading is true; the first
clause should go.

O-4 -- the parsers can still raise on pathologically nested JSON:: Both
`_usage_from_wrapper_stdout` and `_usage_from_stdout` catch only
`JSONDecodeError`/`ValueError`, so a single stdout line of valid JSON nested
beyond the recursion limit raises `RecursionError` out of `execute()`
(reproduced with 200000 nested arrays). For Claude this exposure already
exists in the pre-change `_candidate_from_wrapper` on the zero-exit path, but
for Codex the stdout stream was previously never parsed, and in `slice4.py` an
exception from `execute()` ends as a charged `uncertain` Hop. No provider
plausibly emits such a line, so I do not block on it; catching
`RecursionError` (or `Exception`) around the two `json.loads` calls would
close it at no structural cost.

O-5 -- `usage.json`'s two identity guards are unreachable in production:: A
fresh Run refuses a pre-existing state root ("one-shot operator roots are
never overwritten") and continuation re-validates the Run identity, so one
checkout state root never serves two Run ids and `H{n}` is allocated from
`hop_used`, so no Hop id is written twice with different content. Both
`ReductionError` branches are therefore dead weight today, and they would turn
a usage-write anomaly into an aborted Run after the Hop was already reduced.
They are cheap and conservative; I note them only as the kind of safeguard
worth re-examining rather than growing.

O-6 -- the Run total sums `input_tokens` across incompatible cache
semantics:: `totals.input_tokens` adds Claude's cache-exclusive and Codex's
cache-inclusive figures into one number with no marker at the aggregate
level, and the report prints `input=...` beside `cache_read=...`, which a
reader may add up and double-count the Codex share. The per-invocation flag
remains readable in the same `audit.json`, the task does mandate a Run total,
and all Runs today bind one adapter, so this is honest but coarse; an
aggregate-level semantics marker (or a note in the owning documentation)
would remove the ambiguity.

O-7 -- the report's usage block is not covered for a mixed Run in the
suite:: the added report tests cover the all-complete and the partial cases;
the mixed case (some Hops with records, some without) is only covered at the
audit layer. Cheap to add alongside the `B-2` fix.
