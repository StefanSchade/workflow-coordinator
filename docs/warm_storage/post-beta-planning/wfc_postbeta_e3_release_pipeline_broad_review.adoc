[[e3-h002-finding]]
=== 2. Blocking Finding `F-GH-REPO` -- the `release` job gives `gh` no repository context, so it cannot create the Release

*Invariant violated.* Task DO (1) and the acceptance: "``release``: tags only,
creates the GitHub Release from the tag attaching exactly the two artifact
files ... use the preinstalled `gh` CLI or an equally minimal mechanism", and
plan section 5, E3: "``release`` (tags only, needs ``publish-pypi``): creates
the GitHub Release from the tag, attaching the same two artifact files". The
job as written cannot create any Release.

*What the candidate does.* `.github/workflows/release.yml:217-238`. The
`release` job has exactly two steps: `actions/download-artifact@v4` into
`dist`, and a `run` step whose only environment entry is
`GH_TOKEN` (set from `+${{ github.token }}+`), executing

[source,sh]
----
gh release create "${tag}" dist/*.whl dist/*.tar.gz --title "${tag}" --notes "..."
----

There is no `actions/checkout` step in the job, no `--repo` argument, and no
`GH_REPO` environment entry.

*Why it fails.* `gh` resolves the repository a command operates on from, in
order, an explicit `--repo` argument, the `GH_REPO` environment variable, or
the Git remotes of a repository found from the current directory. I confirmed
against the published `gh help environment` manual that `GH_REPO` is the only
environment variable for repository selection and that `GITHUB_REPOSITORY` --
which GitHub Actions does set, and which the step's `--notes` value happens to
interpolate -- is not among the variables `gh` reads. A job without a checkout
step starts with an empty `$GITHUB_WORKSPACE` on an ephemeral hosted runner;
after `download-artifact` it contains only `dist/`, with no `.git` anywhere up
the path. So `gh release create` reaches none of its three resolution sources
and exits non-zero on "could not determine base repository" without creating
the Release or uploading either asset.

*Why this is blocking rather than cosmetic.* The failure is deterministic, not
a race or an environment-dependent risk, and it is positioned after the point
of no return: `release` needs `publish-pypi`, so by the time it runs, the
version has already been published to PyPI and, per the chapter's own
partial-failure rule, "a published version is never retagged". The pipeline's
terminal step is the one step that cannot succeed, and its failure is
unrecoverable by re-tagging. It is also precisely the step that cannot be
rehearsed before the first real publication, because it is tag-only and
downstream of two publish jobs.

*Feasible minimal correction.* One line, no new mechanism, no additional
permission: add `+GH_REPO: ${{ github.repository }}+` beside the existing
`GH_TOKEN` entry in that step's `env:` block (equivalently, pass
`--repo "$GITHUB_REPOSITORY"` on the `gh release create` command line, since
`GITHUB_REPOSITORY` is already a default Actions variable and is already used
by the step's `--notes` value). Adding a full `actions/checkout` to the job
would also work but is the heavier option: it needs no source for this step's
work, and keeping the job checkout-free is the better shape. Either form keeps
the job's `permissions: contents: write` and the "exactly the two artifact
files" property unchanged. The chapter's `release` bullet needs no change for
the one-line form; it already says only that the job "uses the preinstalled
`gh` CLI to create the GitHub Release from the tag".

I could not execute `gh` here: it is not installed in the agent sandbox
(`command -v gh` exits 1), so this Finding rests on reading the job against
`gh`'s documented resolution order, not on a reproduced command. The structure
it depends on -- no checkout step, no `--repo`, no `GH_REPO` -- is mechanically
asserted in <<e3-h002-structural>>.

=== 4. Non-blocking observations

None of these blocks acceptance, and none asks for new mechanism.

. *Every ordinary `main` push will show `check` red until the release notes
  are frozen -- flagged for the maintainer, not a defect.* `check` runs
  `make release-check` on both triggers, which is what plan section 5 (E3) and
  the task require. In branch mode the tool asserts the release-notes section
  for `0.1.0b1` is not marked `planned`; it currently is, deliberately, per C4.
  I reproduced the refusal against this checkout. So from the moment this
  workflow lands, every push to `main` that is not the frozen release commit
  will report a red `check` for a reason that is correct in the release context
  and noise outside it. ES-3 assumes the intended release commit, so the
  designed path is clean. I am not proposing a condition or an exemption --
  narrowing G1 is the maintainer's call, and the plan decided the criterion --
  but the maintainer should expect it rather than read it as a pipeline bug.
. *The git-lfs neutralization covers only the system scope.*
  `GIT_CONFIG_NOSYSTEM=1` suppresses `/etc/gitconfig` and nothing else. If the
  hosted image's git-lfs filter lives in the runner user's global
  `~/.gitconfig` instead, the filter remains in effect and the suite's real
  trusted-commit scenarios would meet the product's own refusal. This is
  exactly open unknown (c), "whether the runner's Git carries a git-lfs filter
  and the neutralization suffices", and the chapter keeps it open, so adding a
  second scope now would be speculative mechanism against an unmeasured
  failure. The first hosted run should answer the scope question explicitly --
  `git config --show-origin --get-regexp '^filter\.' ` in the job would settle
  it -- and the record's row (c) is the right place for the answer.
. *The Asciidoctor install is an unpinned apt package and is not mentioned in
  the chapter.* `check` runs `sudo apt-get update` and
