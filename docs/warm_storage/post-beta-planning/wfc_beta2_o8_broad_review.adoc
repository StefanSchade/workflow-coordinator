=== 2. The design, judged before the code

The record's `Design` section is dated 2026-11-27, sits in the record the
slice names (not in a review artifact), and answers every question the slice
asks with the alternative it rejects and the property it preserves. I judge
it sound, and I judge the three decisions that carry the slice to be the
right ones:

* *The effective limit stays `Run.hop_limit`.* The two alternatives are
  worse for the reasons stated: recompiling the Commission moves the digest
  and destroys the only verifiable record of what admission judged, and a
  second counter beside `hop_limit` would have to find every existing reader
  (`model.record_hop`, both reducer stop sites, `resume_after_reconcile`,
  `operator.run_serial_hops` and its hard-maximum guard at `operator.py:960`,
  the recovery predicate, status, report, audit) where a missed reader is a
  silent budget bypass or a silent stop. I checked those readers: none of
  them needed a change, which is the concrete benefit of this choice.
* *A separate `wfc extend-budget`, not a `wfc resume` option.* `wfc resume`
  is literally unchanged -- I verified its predicate, its no-op on a budget
  stop and its named refusal of a mechanically recoverable stop with no Hop
  left. Hanging a human-authority mutation on the one command an operator
  reaches for after every anomaly would have been the cheaper diff and the
  worse design.
* *The bounds are functions of facts frozen at admission*: 4 per call,
  `ceil(admitted/2)` in total recomputed from the Run on every call, never
  above the policy ceiling re-derived from the cached, *digest-verified*
  Commission, never above the hard maximum. I confirmed the ordering in
  `extend_budget_lifecycle`: the policy value comes from the cached
  commission and `_recovery_commission_identity_ok` re-verifies that cache
  against the authorized digest before any mutation, so a tampered cached
  config cannot buy a larger extension -- it can only change a refusal
  message on a call that then refuses anyway.

The honesty requirement is met without hedging: the record and the shipped
Operator Manual and skill texts all state plainly that no CLI can distinguish
a human-instructed extension from an invented one, and name the four actual
controls. The additional control the task invited -- refusing a degenerate or
gesture-only statement -- is adopted with its limits stated ("not a defence
against a deliberately fabricated sentence, and is not presented as one"),
and the three stronger-looking alternatives (TTY confirmation, signed token,
committed file) are rejected with reasons I agree with: in this operating
model each one either breaks the command or moves the secret onto the machine
the agent drives.

=== 4. Simplicity and maintainability

I looked for the shapes that cost later rather than once, and did not find a
blocking one.

* The whole decision is *one pure, total reduction* with every refusal named
  in it, and the boundary does the live-fact checks. That is the
  repository's own deterministic-core convention, and it is why I could test
  the entire refusal matrix without a filesystem.
* The new persisted record is one frozen dataclass with a closed wire schema
  and an *absent* key for an unextended Run, so no Run written before this
  slice changes by a byte. That is the cheapest possible migration story.
* `_do_continuation_launch` gained three keyword parameters whose defaults are
  the pre-O8 values, instead of a second near-duplicate launcher. Right call.
* The wire-level chain validation (~40 lines) is the one place I weighed as
  possibly redundant: the invariant it enforces is also enforced by
  construction in the reducer. I judge it worth keeping -- it converts
  `WFC-AUTO-05` from a convention into a property that survives a hand-edited
  `run.json`, which is exactly the failure mode the recovery record was
  written about, and it costs one function that no caller has to think about.
* The one duplication I would name is that `extend_budget_lifecycle` calls
  the three refusal predicates and then `extend_hop_budget` re-checks all
  three internally (observation 5). It buys named lifecycle refusals before
  the lock and a reduction that is safe standalone; it is a small, visible
  cost, not a defect.
* The gesture-token list is a closed, documented set compared only when
  *every* word of the statement is in it, so a real instruction cannot trip
  it by accident. It is the kind of safeguard that could have been a
  heuristic creeping into general text analysis, and it is not.

=== 5. The two negative tests the task names explicitly

Both exist and both actually fail if the behaviour regresses, which I
checked by reading what they assert rather than by their names:
`test_used_hops_are_never_reset_or_refunded_by_an_extension` pins
`hop_used`, the identity of every pre-stop Hop and `hop_used_at_grant`
end-to-end, and `test_an_extension_on_a_non_budget_stop_is_refused` drives a
real `awaiting_human` stop, asserts the named refusal and asserts the Run's
bytes and the journal record count unchanged. The reducer module adds the
same two properties as pure cases, including every other `RunStatus` value
by parametrisation over the enum, so a new status cannot be added without
deciding this question.

=== 6. Non-blocking observations

. *The `Design` section overstates one recording surface.* Its control list
  says the authority statement is recorded "verbatim in the Run, the journal,
  the checkpoint and the archive". The checkpoint carries only the `budget`
  block (`used`, `remaining`, `limit`, `extended_by`) -- I projected an
  extended Run and confirmed neither the statement nor its digest appears
  there. The three surfaces that matter for auditability are correct, and the
  same section describes the checkpoint accurately where it discusses it; one
  word is wrong in the summary list. Worth fixing at the next touch of the
  record.
. *A budget extension's archive destination is named `-recovery-<n>`.* The
  slice deliberately does not rename the continuation ordinal, because
  renaming would move the archive destinations of the unrelated
  mechanical-recovery path -- the right trade today, and documented in both
  the design and ch06. It does mean an extension's archive directory is not
  self-describing; a future rename belongs with O10, which touches that path
  anyway.
. *The pre-existing continuation crash gap applies here too.* If the process
  dies between the `budget_extension_granted` record and the launch (not a
  `LifecycleError`, which is rolled back and tested), the Run is `ready` with
  a raised ceiling while the checkout's latest classification still reads
  `awaiting_human_budget`. A further `extend-budget` then refuses by name
  ("the Run is not stopped on an exhausted autonomous Hop budget: ready"),
  which is fail-closed and changes nothing, but the Run needs a maintainer.
  This is the same class as the mechanical-recovery path's own gap, not a new
  one, and O10 owns it.
. *One historical narrative still says there is no in-place raise.*
  `docs/backlog/_open.adoc`'s accepted-work entry for package E0b narrates
  "No in-place Hop-budget raise exists … so the missing review ran as a new
  review-only Commission". It is an account of that Run's circumstances at
  the time, not current guidance, and the manifest's own O8 card states the
  new behaviour; a reader could still take the sentence as a rule. A dated
  qualifier at the next touch would remove the ambiguity.
. *The refusal predicates are evaluated twice* (see section 4). If a later
  slice touches this path, collapsing the lifecycle's three calls into one
  `extend_hop_budget` attempt whose `ReductionError` is mapped to
  `refused_budget_extension` -- which the code already does for the
  re-verification case -- would remove the duplication without losing a named
  refusal.
. *The semantic model's state table is now asymmetric.* Its
  `awaiting_human_budget` row is still true but says nothing about the
  in-place continuation, while the `reconcile_required` row does describe its
  `wfc resume` exposure. The semantic model is outside the docs-sync clause's
  named set and nothing in it is false, so this is a one-line improvement, not
  a correction.
. *Pre-existing, outside this slice:* `project_memory/canonical/decisions.json`
  `DEC-WFC-008` still states the Coordinator hard ceiling is "currently 20"
  while `model.COORDINATOR_HARD_MAX_AUTONOMOUS_HOPS` is 64. `DEC-WFC-007`'s
  WorkItem <= policy <= hard-ceiling relationship *is* preserved by this
  slice (the extension refuses above both upper bounds), which is why I
  looked; the stale number is unrelated drift for the maintainer to note.
