=== 3. The task's BINDING SHAPE (1)-(4)

Same inputs, same argument definitions, same request-construction path, no duplicated logic:: Holds, and the boundary is the smallest one that achieves
it. `plan.py` exposes exactly three shared seams --
`add_plan_input_arguments` (one argparse definition, called by both parsers),
`resolve_plan_inputs` returning a frozen `ResolvedPlanInputs`, and
`render_commission_preview_lines` (the common preview body, parameterized
only by its header line). `consumer_request_from_plan_inputs` is untouched
and is reached only through `resolve_plan_inputs`, so there is no second
construction path that could drift. `emit_request.py` adds no field of its
own beyond `--output`, `--force` and `--allow-inside-repository`.
Output-path refusals:: Hold. An existing destination is refused unless
`--force`; a destination that resolves inside the consumer repository's
worktree is refused unless `--allow-inside-repository`. Both are evaluated
*before* any `mkdir` or write -- I confirmed a refused run creates neither
the file nor its parent directory, and leaves an existing file's bytes
untouched. The comparison is sound: `repository_identity` returns a resolved
absolute path and `--output` is resolved too, so the check cannot be defeated
by a relative argument or a symlinked path. I checked the case the tests do
not cover, a *relative* `--output` with the current directory inside the
repository (`wfc request … --output request.yaml`, run from the repository
root): correctly refused, nothing written. The rule, both flags and the
reason ("an emitted request is not an authorization and must not dirty the
clean tree `wfc run` requires") are documented in the record's Design, the
module docstring, the help text, the skill and the manual.
The required output statements:: Hold. `wfc request` prints the identical
preview body (so the digests are right there), then the destination path,
then a `NEXT EXPLICIT ACTION` line stating that nothing was authorized -- no
project command, provider call, Commission write or Git mutation -- that the
file grants no authority because `wfc run --request` re-reads, re-parses
under the closed BP2b schema and re-digests it, and that `scope`, `program`,
`personas`, `max_autonomous_hops`, `evidence.argv` and `authority_source` are
the operator's own judgement "merely carried here -- never supplied,

=== 5. Simplicity, and the safety properties the task names

The source change is 138 new lines in `emit_request.py` (about half of them
docstring), 96 in `report.py`, 3 in `cli.py` and a net +39 in `plan.py` that
is mostly a move. I looked for a materially simpler realisation with the same
guarantees and did not find one. The three extracted seams are each used by
both commands, so none is speculative generality; `ResolvedPlanInputs` is a
frozen six-field carrier that replaces a six-value tuple return and keeps the
resolution steps in one place; `PlanInputError` exists so the shared
resolution can refuse without printing or exiting, which is what lets the two
commands keep their own message prefixes byte-for-byte. The two escape-hatch
flags are the minimum the chosen rule needs (one for each refusal) and the
repository's own commit-the-request convention actually exercises the second.
No new persisted state, no new journal field, no new classification, no new
exit code, no second request-construction path, no duplicated preview text.

The safety properties survive. `wfc plan` still performs no write of any kind
and is byte-identical in behaviour, now machine-checked from two directions.
The emitted bytes carry no authority: they are an ordinary file on an
ordinary path, and `wfc run` re-reads, re-parses under the closed schema and
re-digests before authorizing or committing -- the schema, the digest and the
drift check are byte-unchanged, and I confirmed the emitted text is a fixed
point of that schema. The default refusal to write inside the worktree keeps
the clean-tree precondition and the "an emitted request is not an
authorization" property aligned rather than merely documented. The
independent reviewer's sole Finding authority, the trusted-commit boundary,
fail-closed admission and recovery and one-Run-per-checkout are untouched:
no new code path commits, admits or classifies anything.

=== 6. Non-blocking observations

N-1 the end-to-end test stops one assertion short of the criterion's own wording:: `test_request_emitted_file_reproduces_the_previewed_digests_and_launches_through_wfc_run`
already captures the authorized `(commission_digest, envelope_digest)` pair in
`confirm_calls` but asserts only `len(confirm_calls) == 1`. Asserting that
pair against the digest derived from the previewed/emitted request would make
"the emitted request reproduces the digest the authorization path derives"
mechanically evident instead of transitively implied. I verified that
equality out-of-band (section 2b/2c), so nothing is unproven -- it is simply
not pinned by a test.
N-2 two different values are both called "the Commission digest":: `wfc plan`
and `wfc request` print `projected Commission manifest digest` (SHA-256 over
`compiled.manifest`); `wfc run` prints and authorizes `Commission digest`
(`_materials_digest` over the projected Commission texts plus the request's
raw text). The two strings never match, by construction and before this
slice. An operator who compares the preview line with the authorization line
will think something drifted. Out of scope here, but now that a command
exists whose whole purpose is "the emitted request *is* the previewed one",
naming the two values distinctly in the manual (or printing both in the
preview) would be worth a later slice.
N-3 an unusable `--output` surfaces as a traceback, not a named refusal:: with
`--output` naming an existing *directory* plus `--force`, or a path whose
parent is unwritable, `write_text`/`mkdir` raise `IsADirectoryError` /
`PermissionError` out of `main`. This matches `frontdoor/init.py`, which also
writes without wrapping `OSError`, so it is house behaviour rather than a
defect introduced here; a `try/except OSError` around the two write calls
returning the usual `wfc request: …` refusal would make the new command's
whole surface uniformly fail-closed.
N-4 `wfc report --config` is silently inert with a positional SOURCE:: it is
documented as "used only with --repository" and I confirmed it is simply
ignored there. Given that this command now refuses `SOURCE` plus
`--repository` as *ambiguous input*, refusing `SOURCE` plus an explicit
`--config` for the same reason would be more consistent; today it is a
harmless no-op.
N-5 two informative sites still describe hand-authoring only:: `docs/operator_manual/ch08_examples/03_commission_to_archive.adoc`
section 4 ("author the equivalent Consumer Request YAML … and commit it") and
`docs/operator_manual/ch10_level1_orchestration/02_worked_sequence.adoc:127`
("author the Consumer Request, then launch … exactly as in Commission 1").
Neither became false -- hand-authoring is still supported, ch08 declares
itself illustrative with "linked procedures retain ownership" and links to
the chapter 2 page that *was* updated, and the ch10 line back-references a
sequence whose own text now mentions `wfc request`. So they are incomplete,
not misleading, and I do not block on them; a clause in each is worth folding
in at integration time. Separately,
`docs/developer_guide/ch02_code_navigation.adoc` still presents
`frontdoor/init.py` and `frontdoor/plan.py` as the installed consumer-facing
commands and does not mention `frontdoor/emit_request.py`; that document is
outside the docs-sync owner list and is explicitly informative navigation,
but it is where a newcomer looks for "which module implements which command".
N-6 `--repository` on `wfc report` reaches only a single-Attempt Evidence location:: by design: more than one candidate refuses rather than guessing,
and the Design section's rejection of an mtime/journal-order guess is sound
("a wrong silent guess here is worse than a named refusal"). The consequence
is that in a mature Evidence repository the flag is permanently refused, so
friction entries 13/16 are removed for the first Run of a repository and for
rehearsals, not for steady-state operation. The shipped texts say this
plainly, which is the right behaviour for now; a later slice could keep the
refusal and add an explicit selector (`--attempt <id>`, or `--latest` as an
operator-stated choice) rather than a silent default.
N-7 `--force` has no second guard on a non-request destination:: `--force`
overwrites whatever `--output` names, including a file that has nothing to do
with WFC. The destination is always operator-typed and the refusal-by-default
is the real protection, so this is proportionate; worth remembering only if
`wfc request` ever gains a default or derived output path.
