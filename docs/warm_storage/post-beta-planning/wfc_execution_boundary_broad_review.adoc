== Blocking Findings

[[f1]]
=== F1. Slice A requires three external bind-source exceptions; the records authorize one

Blocking.

*What the records say.* Three statements disagree:

* The umbrella record's 2026-11-08 external-scratch section states that "the
  repository-only bind-source rule is superseded *only* by Slice A's one further
  designated external mount kind, the Coordinator's own result directory; a
  general loosening remains forbidden."
* The planning record's decision D4 is titled "A second designated external
  mount kind for the result channel" and decides to "add *exactly one* further
  validated external mount kind".
* Slice A's own mount model requires, outside the repository: the result
  directory; a narrow, individually bound read-only `/etc` set
  (`/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`, `/etc/ssl/certs`,
  `/etc/passwd` as the expected set); and a narrowly bound read-only provider
  authentication path. Its decomposition step 1 names all three explicitly as
  work items: "the result-channel mount kind, ... and the `/etc` and
  authentication mount kinds".

*Why it blocks.* The 2026-11-08 maintainer authorization states that it "does
not authorize ... any general loosening of the existing repository-only
bind-source rule (`validate()`'s `source.relative_to(repository)` check) beyond
this one designated exception". I verified that the rule is the single check at
`execution_boundary.py:124-127` and that it governs every caller-supplied
`Mount`, with the system view at `:166-172` generated separately inside
`build_argv`. Slice A needs at least one further *caller-designated,
per-invocation, provider-specific* external source -- the authentication path --
which cannot be a fixed generated system mount, and it does not say whether the
`/etc` entries are generated system mounts or validated mount kinds.

The result is a contract whose implementation Run is caught between its own
requirement and its own stop rule: Slice A tells it to add the `/etc` and
authentication mounts, while the umbrella tells it that only one further
exception is superseded and the stop rule tells it to stop rather than widen.
That is a reproduced inconsistency across the three records about how far an
accepted maintainer restriction is being superseded, on exactly the
security-relevant invariant that restriction fences. The acceptance criterion
requires the records to be mutually consistent and every superseded statement
to be explicitly marked; this supersession is marked for one of three cases.

*What would resolve it,* within the authorized scope and without lowering any
security claim:

. State in Slice A, per external path category, whether it is a generated
  system-view mount (like `/usr` today, outside the `Mount` validation rule) or
  a validated designated mount kind (like the external scratch root). The
  authentication path can only be the latter.
. Extend the umbrella's 2026-11-08 supersession marker to name every category
  Slice A actually requires, so the marker is accurate rather than
  understated, and keep the prohibition on a general loosening.
. Correct planning-record D4's "exactly one" to the actual set, and add the
  widening of the 2026-11-08 fence as an open maintainer decision with options
  and a recommendation -- the route the task prescribes for a requirement that
  exceeds an existing authorization, rather than silently widening it.

*What must not happen:* no blanket `/etc`, no whole provider configuration
directory, and no general relaxation of `source.relative_to(repository)`. The
Finding is about the records being honest and consistent about the exceptions,
not about granting more of them.

[[f2]]
=== F2. The reviewer-phase write prevention is overclaimed; the file-shaped overgrant removes it in the normal case

Blocking.

*The claim.* Slice A's mount-model table asserts for a reviewer phase that
"only that phase's own `durable_artifacts[artifact_key]` paths" are writable and
that "a reviewer therefore *is* mechanically prevented from writing the worker's
deliverables -- a real, honest asymmetry that follows from the existing program
data".

*Why it does not hold.* Slice A's own not-yet-existing-target rule says that for
"an authorized entry that names a not-yet-existing *file*, no empty file is
created ... Instead the nearest existing ancestor directory is mounted
writable." A durable review artifact never exists at the launch of the phase
that must create it -- that is its definition. So the normal reviewer case is
precisely the file-shaped overgrant case.

I reproduced this against this Commission's own data. The rendered profile gives
`broad_review` the single scope entry
`docs/warm_storage/post-beta-planning/wfc_execution_boundary_broad_review.adoc`
(`.wfc/governance/wfc-exec-boundary-ftr-001/profile.yaml:60-61`), which did not
exist at this Hop's start. Under Slice A's rule the boundary would bind
`docs/warm_storage/post-beta-planning/` writable -- the directory that holds the
worker's own deliverable `wfc_execution_boundary_planning_record.adoc` and the
other post-beta-planning records that the Commission's own constraints call
immutable. The reviewer would be mechanically able to write exactly the worker
deliverable the record says it is mechanically prevented from writing.

*Why it blocks rather than being a wording quibble.* This is a positive
security-property assertion in the slice's contract, and it is the one place
where Slice A claims a *phase-specific* prevention. The guarantees table
disclaims the worker-to-reviewer direction only ("a worker phase's
`authorized_scope` *is* the whole Commission scope"); residual risk 3 states the
file-shaped overgrant generically, without connecting it to the asymmetry claim
it negates. A reader of either section alone is misled, and the review focus
asks specifically whether the Commission-scope versus phase-scope relation is
stated without overclaiming. It is not.

*What would resolve it:* qualify the reviewer row and the guarantees table so
the reviewer-side prevention is stated as conditional on the artifact's parent
directory, name the directory-granularity consequence (a reviewer whose artifact
shares a directory with other records can write them), and cross-reference
residual risk 3 from the claim it limits. Optionally note the cheap mitigation
the implementation Commission could choose instead -- but do not require a new
mechanism: a correctly stated limit is sufficient here, and inventing one would
be a new requirement I have no authority to add.

[[observations]]
== Non-blocking observations

None of these blocks acceptance. They are recorded for the correction Hop and
for the implementation Commission, which may act on them or not.

. *The Claude scratch path inside the view is mandatory, not optional.* Slice
  A's provider table lists Claude `sandbox.filesystem.allowRead`/`allowWrite`
  as something that "*may* be stated in terms of the in-view paths". With
  identity-preserving mounting the repository path is unchanged, but the
  external scratch is bound at `/tmp/s`, while
  `claude_adapter.py:231-232` writes the *host* scratch path into `allowRead`
  and `allowWrite`. Inside the view that path does not exist, so the nested
  sandbox would deny scratch writes. Restating it is a precondition for L1/L2
  passing, not a permissible relaxation, and it is not in the preflight list.
. *`$HOME` is empty inside the view, not absent.* bwrap materialises the parent
  chain of every bind destination, so with identity-preserving mounting
  `/home/<user>` exists as an empty directory while `HOME` still points at it
  (`claude_adapter.py:41`, `:316-320`). The practical question Slice A does not
  raise is whether either CLI needs a *writable* state directory under `HOME`;
  if it does, that is a further writable external mount, and only the stop rule
  currently catches it. Worth naming as a live-qualification output beside L6.
. *`--new-session` appears only in the decomposition and in planning D6,* never
  in Slice A's own mount/flag discussion or its guarantees. Either include it in
  the view description or drop it from the step list.
. *Hop-budget arithmetic.* "12 as an upper limit (worker, broad review, and up
  to four correct/focused-review cycles)" adds up to 10, not 12. The number is
  an upper bound either way; the parenthetical should match it.
. *The umbrella's "one further designated external mount kind" phrasing* would
  read better as a list once F1 is resolved, so that a later reader cannot
  reconstruct the understatement from the record alone.

[[h005-f1]]
==== H005-F1. The "result directory" Slice A binds is the Run state directory; the slice would grant the agent write access to `run.json`, the dispatch marker and the audit trail

Blocking. New material, not a restatement of F001 or F002.

*What Slice A decides.* The Coordinator result directory is mounted
"read-only for Claude, read-write for Codex, bound at its own absolute path"
(`FTR-WFC-EXECUTION-BOUNDARY-DISPATCH-INTEGRATION.adoc:481-490`), as the
second designated validated external mount kind (`:555-563`). The umbrella's
supersession marker carries the same wording
(`FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc:568`), and the planning record's D4
the same again (`wfc_execution_boundary_planning_record.adoc:504-510`). All
three records treat the sensitive part as lying *above* that directory: "never
the state root above it" (`:489`), "the Coordinator state root above the
result directory ... absent" (`:499-502`), and D4's rejected option (b),
"Granting the whole state root -- it holds `run.json`, `checkpoint.json` and
the checkout association" (`wfc_execution_boundary_planning_record.adoc:538-540`).

*What the code shows.* That premise is false. The adapters' `result_directory`
*is* the Run state directory:

* `operator.py:977-980` constructs the adapter with
  `result_directory=run_root`, where
  `run_root = checkout_state_root(state_root, association)`
  (`slice4.py:135-136`: `<state_root>/checkouts/<checkout_id>`).
* That same directory holds the Coordinator's own authoritative state and
  audit records: `run.json` (`operator.py:919`, `slice4.py:319`),
  `checkpoint.json` (`operator.py:926`, `:1052`, `slice4.py:408`),
  `dispatch.json`, the dispatch marker (`slice4.py:182`, `:320`),
  `execution-evidence.json` (`operator.py:885`, `slice4.py:183`) and
  `usage.json` (`operator.py:841`).
* They are present *during* the dispatch: `slice4.py:319-325` writes the run
  snapshot and the dispatch marker and then immediately constructs the adapter
  with `run_root` as its result directory.
* They are read back as trusted Coordinator state: `frontdoor/lifecycle.py:709`
  and `:716` read `run.json` and the dispatch marker from that directory, and
  `frontdoor/archive.py:487-495` derives archive facts from
  `checkouts/<id>/run.json` and `checkpoint.json`.

Only `checkout-association.json` lives one level up (`slice4.py:100`), which is
the single file D4's rejected option (b) correctly places outside.

*Why it blocks.* Three separate consequences, each one sufficient:

. *A reproduced contradiction of Slice A's own guarantees.* The guarantees
  table asserts that writes anywhere else on the host are prevented because
  "only the repository view, the authorized writable subpaths, the private
  `/tmp`, the external scratch and the one result-channel *path* exist in the
  view" (`:85-89`), and that reads of the Coordinator's state root are
  prevented except "the one result-channel path" (`:91-97`). A directory-wide
  bind of the Run state directory is neither. The umbrella repeats the
  guarantee as "no write elsewhere on the host"
  (`FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc:65`).
. *The slice's own negative case cannot pass as specified.* N16's companion
  N11 requires asserting that a write "anywhere in the Coordinator result
  directory other than the one designated result file" is *prevented*
  (`:964-966`). Under the decided mount mode it is permitted, and
  `validate()`'s overlapping-destination rule -- which Slice A keeps unchanged
  (`:418-427`) -- rules out repairing it by nesting a narrower bind inside the
  directory bind. The implementation Commission would meet its own stop rule on
  a point the design, not reality, created.
. *It is the wrong direction for the trust boundary.* Slice A's auditability
  mechanism is a new `boundary` field in the per-Hop binding evidence and the
  audit projection (`:704-717`, L7 at `:1049-1051`); that evidence file sits in
  the directory the Codex path would get read-write. The same grant covers the
  dispatch marker, on which Slice A's own not-started/started classification
  and the existing recovery path depend (`:789-806`). An agent-writable record
  of whether the agent was isolated is not an audit trail. Today Codex's own
  `--sandbox workspace-write` is what keeps that directory out of reach; Slice
  A's premise is precisely that the provider sandbox is not the authoritative
  boundary, so the WFC boundary must not be the weaker of the two.

*What would resolve it,* within the authorized scope and without adding a
mechanism: separate the provider result *channel* from the Run state
directory, state that separation in all three records, and keep the designated
mount kind pointed only at the channel. The cheapest form is a dedicated
per-invocation channel subdirectory under the checkout state root that holds
only `structured-result.schema.json`, `result-message.json` and
`claude-closed-settings.json` -- all three are Coordinator-written before
launch (`claude_adapter.py:307-308`, `codex_adapter.py:433-434`, `:443`), so
the bind source exists, and an in-place rename by the provider still works
because the mount point is the directory. Binding the three files individually
is a second option, but it needs the implementation to confirm that the
provider does not replace the result file by rename over the bind mount. Which
form is chosen is the implementation Commission's call; what this Finding
requires is that the records stop describing the Run state directory as the
result channel, that the guarantees and N11 become consistent with whichever
form is chosen, and that M7 asks the maintainer to authorize the channel
rather than the Run state directory. The read side needs the same treatment:
with the directory bound read-only for Claude, `run.json` and every prior
Hop's evidence are readable inside the view, which the guarantees table denies.

[[h005-f2]]
==== H005-F2. The provider executable and its runtime are not inside the view, and the slice answers only with a refusal -- which leaves every qualification layer, and so every isolation claim, without a performable precondition

Blocking. New material.

*What the records say.* The system view mounts `/usr` plus the four
`/bin`-family links, "the provider binary and its interpreter must resolve
here" (`:435-438`). Preflight check 5 requires that "the provider executable
resolves to a path that exists *inside the view*", and states that a provider
installed under `$HOME` "is not reachable from a view that mounts only `/usr`
and the four `/bin`-family links, and must be refused by name before dispatch"
(`:773-777`). The planning record observes the host fact that makes this
concrete: `PATH` contains `/home/<user>/.nvm/versions/node/v22.23.2/bin` and
`/home/<user>/.local/bin`, "neither of which is mounted"
(`wfc_execution_boundary_planning_record.adoc:171-174`, E6 at `:375-379`).

*What I checked myself.* Neither provider CLI exists in a view-visible
location on this host: `ls` reports no `/usr/bin/claude`, no
`/usr/local/bin/claude`, no `/usr/bin/codex` and no `/usr/local/bin/codex`
(`/usr/bin/bwrap` and `/usr/bin/node` do exist). So on the one host the slice
designates for qualification, preflight check 5 refuses *every* isolated
invocation, for both adapters, as the design intends.

*Why it blocks.* The refusal is the correct failure direction, and I am not
asking for a mount that reaches `$HOME`. The gap is that the slice never
decides how the provider becomes reachable, and three things depend on that
decision:

. *Task requirement (c) is unanswered for this category.* The mount model is
  required to state, for what the provider CLIs need including "local child
  processes such as Node", which paths are exposed read-only, which writable
  and which hidden. For the provider's own install tree and bundled runtime --
  not `/usr/bin/node`, but the CLI bundle itself -- the records state only the
  refusal. Every other category in that row (HOME/XDG, authentication, DNS/TLS,
  `/etc`, temp) is decided.
. *Layer 2 is not performable as written.* L1 to L7 are the gate on every
  preventive-isolation claim in every document (`:993-999`, exit criteria at
  `:1062-1071`), and L1's first act is starting `claude` inside the boundary.
  With the host as observed, none of L1 to L6 can start. The record presents
  them as performable by the maintainer without naming the precondition that
  must first hold.
. *Layer 1 inherits the same question.* The deterministic cases dispatch "a
  fake provider executable" through the real path (`:896-916`), so preflight
  check 5 applies to them too; nothing states where that fake executable lives
  so that it is both reachable in the view and not a repository artifact. This
  one is cheap to answer (the mounted repository or the scratch bind), but it
  must be answered, or the implementation Run discovers it as a blocked test.

*What would resolve it:* name the precondition explicitly -- the provider
executable and everything it loads at runtime must resolve inside the view --
and decide between the two options rather than leaving the implementation Run
to invent one: (a) an operator-side prerequisite that the CLI is installed
under a view-visible path such as `/usr/local/bin` with its runtime likewise,
recorded in the enablement section and in the live layer's preconditions; or
(b) a fourth designated, individually validated read-only external mount kind
for the provider install tree, which would extend M7's enumeration and must
therefore be routed to the maintainer, not taken by the implementation
Commission. Option (a) adds no mount kind and is my recommendation; either
way the live layer needs its precondition stated, and Layer 1 needs one
sentence on where the fake provider lives.

[[h005-observations]]
=== Non-blocking observations (H005)

. *"`$HOME` is an empty directory inside the view" is not accurate under
  path-identity mounting.* The same row that states it also states the
  mechanism that refutes it: bwrap materialises the parent chain of every bind
  destination (`:504-511`), so `/home/<user>` contains the ancestor chain of
  the repository bind -- and, on this host, of the state root and the scratch
  root as well. The security substance is right and worth keeping ("no host
  content other than the designated mounts is reachable"); the words "empty"
  and "no host content under it is reachable" (`:91-97`) are not, and the
  argument that Claude's `denyRead: ["~/"]` becomes "redundant rather than
  wrong" (`:657-659`) rests on them. Today's unisolated runs already combine
  that deny rule with a repository under `$HOME`, so nothing is newly broken;
  only the wording needs care.
. *The Claude environment allowlist is four names plus an operator-set
  extension.* The seam table says "the Claude adapter's four-name allowlist"
  (`:212-216`); `claude_adapter.py:43-47` adds every name listed in
  `WFC_CLAUDE_EXTRA_ENV_NAMES`. The planning record states this correctly
  (`:223-224`), so only the FTR sentence is imprecise -- and the extension is
  one more way a token-bearing variable can reach the child, which pairs with
  residual risk 7.
. *N13's leftover-process case should name `--as-pid-1` as forbidden.* The
  "every descendant dies with it" property (`:223-228`) holds because bwrap
  installs a reaper as PID 1 of the new namespace; `--as-pid-1` would remove
  it. The option exists in the installed build, so naming it costs one clause
  and prevents a plausible implementation mistake.
