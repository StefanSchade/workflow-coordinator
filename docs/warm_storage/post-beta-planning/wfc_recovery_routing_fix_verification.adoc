== A. The recoverable-mechanical-stop predicate

`reducer.diagnose_mechanical_recovery_eligibility(run)` is the one precise,
status-agnostic predicate (`reducer.recoverable_mechanical_stop_anomaly`
collapses its two "not eligible" outcomes for a caller that only needs a
yes/no answer):

* `stop_reason` begins with `mechanical_preemption:` (the scope gate: a
  Run whose stop reason does not even carry this prefix was never a
  candidate for this predicate at all, and nothing about its behaviour
  changes);
* no `semantic_stop`;
* no `human_question`;
* no open blocking Finding;
* at least one recorded Hop;
* the anomaly text is exactly one of the five
  `vertical._durable_artifact_anomalies` strings (now named constants
  shared between `reducer.py` and `vertical.py` so the text a boundary
  observes and the text the predicate recognizes can never drift apart):
  no declared path, no CommitIntent, not named by the CommitIntent, not
  changed in the trusted commit, or absent/not a regular Git-tracked file
  at end HEAD.

Membership is checked against the exact, unjoined anomaly text. Because
`vertical.run_one_hop` only ever joins more than one anomaly with `"; "`,
a repository state with *any* other anomaly (dirty worktree, moved HEAD, a
WFC-GIT-08 subject defect, a policy anomaly, a required-evidence error)
can never equal one of the five strings verbatim -- so "worktree clean"
and "current HEAD equal to the last recorded Hop's end HEAD" are proven by
construction, not by a separate check, inside `reduce_result`.

=== WFC-GIT-08 decision (explicit, as the task requires)

Decision: *no*. `vertical._subject_anomalies` (the WFC-GIT-08 malformed
commit-subject class) is a distinct, un-reviewed authorship defect, not a
consistent, post-acceptance fact about an otherwise-accepted Hop -- it says
something is wrong about how the Hop was attributed, not merely about an
artifact bookkeeping omission. It is deliberately excluded from the
recoverable class. `test_subject_anomaly_class_stays_terminal_awaiting_human`
and `test_recovery_refuses_on_non_recoverable_anomaly_class` pin this.

=== Classification

`reduce_result`'s existing, unchanged-order mechanical-error loop now
checks, only for the `repository_anomaly` branch, whether the anomaly is a
member of the recoverable class and the other elements hold
(`_is_recoverable_mechanical_repository_anomaly`); if so it calls
`_stop_for_recoverable_mechanical`, which lands the Run in
`RunStatus.RECONCILE_REQUIRED` via `reducer.require_reconcile`'s new
`reason="mechanical_recoverable"` branch, with the Run's own
`mechanical_preemption:` stop reason and anomaly text preserved verbatim
(not the generic `reconcile_requires_explicit_resume` text the two
pre-existing reconcile reasons use). Every other mechanical stop keeps
`_stop_for_human`/terminal `awaiting_human` exactly as before.

`reducer.resume_after_reconcile` is otherwise unchanged except that its
pre-existing "anomalies must be resolved before resume" rule is skipped
for `reconcile_reason == "mechanical_recoverable"` specifically: that
anomaly text is the predicate's own historical diagnostic provenance, not
an unresolved blocker, and B preserves rather than clears it.

== B. The regular recovery path through `wfc resume`

`frontdoor.lifecycle.resume_lifecycle` now inspects the checkout's cached
`classified` journal record *before* `_advance`'s pre-existing "lifecycle
already classified (no-op)" shortcut. When that classification is
`reconcile_required` or `awaiting_human`,
`_attempt_mechanical_recovery` loads the live `run.json` and calls
`reducer.diagnose_mechanical_recovery_eligibility`:

* scope gate fails (`(None, None)`) -- returns `None`; the caller falls
  through to the unchanged no-op path. This is why every ordinary semantic
  `awaiting_human` (a real open question) and every other classification
  (`completed`, `stopped`, `interrupted`, `awaiting_human_budget`,
  non-mechanical `reconcile_required` from `interruption`/
  `prerequisite_return`, ...) is provably unaffected
  (`test_ordinary_semantic_awaiting_human_keeps_the_old_no_op_behaviour`,
  `test_completed_classification_is_unaffected`).
* a named element fails (`(None, reason)`) -- a named refusal
  (`refused_not_recoverable`), no mutation.
* eligible -- B re-verifies live facts the predicate cannot see from the
  Run record alone: exact current HEAD, a clean worktree with resolved
  submodules, at least one unused autonomous Hop remaining
  (`run.hop_used < run.hop_limit`), and unchanged Commission/execution-
  envelope identity (the same digest check `_do_commit` makes at first
  launch, read-only here). Any failure is also a named refusal with no
  mutation -- in particular, a mechanical stop recorded on the Run's last
  authorized Hop refuses by name (`"no autonomous Hop budget remains for a
  continuation"`) rather than rewriting the Run to `ready` with no Hop left
  to drive it (see <<f-c>>). On success: a
  write-ahead `mechanical_recovery_intent` journal record; the identical
  Run moved to `reconcile_required` (if it was not already, i.e. the
  already-archived `awaiting_human` case) and then to `ready` via the
  unchanged reducer functions; a `mechanical_recovery_resumed` record;
  then a genuine engine relaunch under a new, distinct journal record
  family (`mechanical_recovery_launch_intent`/`_spawned`/`_failed`, never
  the original `launch_*` kinds, so the pre-existing crash-matrix retry
  bookkeeping is untouched and unaware of it) that continues the identical
  `run_id` at its unchanged Hop budget and already-charged Hop count. The
  continuation's own terminal classification is recorded as a further
  `classified` journal record (journal records are only ever appended,
  never rewritten).

`operator.py` gained one new, narrowly scoped admission path,
`--continue-existing` (`_continue_existing_run`), reusing the unchanged
`_preflight`/`admit_parsed` pipeline (full governing-input, component,
evidence and execution-binding re-verification) at the live
`current_head`; `_preflight` only accepts a pre-existing `--state-root`
when explicitly told `allow_existing_state_root=True` (default `False`,
so every other caller's one-shot refusal is unchanged). It loads the
already-`READY` Run from the identical checkout (never `new_run`) and
drives `run_serial_hops` exactly as the fresh-Run path does.

A recovered continuation is still an ordinary Run: it still needs its own
normal accepting route from a subsequent real Hop
(`test_recovery_run_still_needs_its_own_normal_accepting_route`).
Recovery itself never touches a Finding, never touches
`semantic_stop`/`human_question`, and is reachable only from the two
listed statuses with the predicate holding.

=== Archive immutability and additive, collision-free destinations

`frontdoor.postrun.run_pending_postrun`'s "already archived, cache it"
shortcut is now scoped to facts recorded *after* the specific `classified`
record currently being processed (by journal `seq`), not "any archive
result ever for this checkout" -- otherwise a recovery continuation's
genuinely new outcome would be wrongly served the predecessor attempt's
cached result. A continuation's own archive attempt (when it is not the
first `classified` record for this checkout) uses an ordinal
`<identity>-recovery-<n>` suffix on the unchanged, Run-derived
`_attempt_identity`, so it can never collide with the predecessor's own
destination; `archive.archive_run`'s pre-existing refuse-rather-than-
overwrite rule still applies if that derived destination is itself
already (unexpectedly) occupied
(`test_recovery_refuses_a_collision_at_an_existing_destination`). The
predecessor's own archived manifest/`audit.json`/raw files/Evidence commit
are never read for writing and never rewritten
(`test_predecessor_archived_attempt_is_byte_identical_after_recovery`
hashes every file under the predecessor's destination and re-reads the
pre-recovery Evidence `HEAD` before and after). The `wfc.audit/1` schema
and its allow-list are unchanged; recovery history is visible truthfully
through the journal's further `classified`/`mechanical_recovery_*` records
and the distinct archive destination, which `wfc status`/`wfc report`
already read.

== C. Reviewer route semantics and the missing-commit trap

=== C(i)/(ii): prompt content

`prompt.assemble_prompt` gained an optional `profile: WorkflowProfile |
None` parameter (required, and only required, for a phase whose review is
a gate review -- every other phase shape, the overwhelming majority of
existing call sites, is unaffected and unchanged). For such a phase it
appends a `[review_route_semantics]` block, built only from `phase`/
`profile` facts (route effect, `goto` target phase and its role, whether
the route is this phase's `failed_evidence_route`), never a hard-coded
route name: the forward-route rule ("never a route with
`hands_back_to_worker=true`"; `is_failed_evidence_route=true` is for a
required-evidence failure or `changes_required`, never an ordinary accept
choice), and, only when `phase.durable_artifact` is `required`, the
re-review artifact obligation sentence naming the CommitIntent. Two
profiles with different, arbitrary route/phase names in
`test_review_route_semantics_prompt.py` prove nothing is hard-coded.
`vertical.run_one_hop`'s one real call site passes `profile=profile`
unconditionally.

=== C(iii): the contradiction decision

Decision: *reject outright* (the smallest option). `reduce_result` now
checks, before the pre-existing required-evidence-failure override and
only when evidence did not actually fail: gate review, `outcome ==
completed`, no open blocking Finding remains, and
`requested_route == phase.review.failed_evidence_route`. On that exact
contradiction it stops `mechanical_preemption:contradictory_route:...`
(a terminal `awaiting_human`, not the recoverable class -- it is not a
consistent post-acceptance durable-artifact fact). Rejecting was chosen
over silently normalising the route to the accept path, because this
reducer never substitutes its own route choice for the reviewer's
(exactly the authority the rest of the contract protects): normalising
would manufacture a disposition the review never made and would be a
second, quieter version of the same silent-accept risk this WorkItem
closes. A genuine `required_evidence_failed` case still legitimately
forces the `failed_evidence_route` and is unaffected
(`test_required_evidence_failure_legitimately_overrides_the_requested_route`);
so is the ordinary `changes_required` use of that same route
(`test_changes_required_requesting_the_failed_evidence_route_is_unaffected`).

=== F-A: a recovery continuation's own candidate-preservation step

`preservation.run_pending_preservation`'s "already captured, skip it"
shortcut (`_latest_fact`) consulted the latest `ext.preservation.*` record
from anywhere in the journal, the same unscoped shape `postrun.py` had
already been corrected away from. A continuation's own classified record
therefore never got its own preservation attempt: it silently re-served the
predecessor attempt's terminal fact. Fixed identically to `postrun.py`'s own
`seq > classified.seq` scoping: `_latest_fact` now takes a `min_seq` keyword
and `run_pending_preservation` passes its own `classified.seq`, so the
"already done" check only ever sees facts recorded after *this* classified
record. `postrun._preservation_fact` (which reshapes the latest preservation
fact into the archived `audit.json`'s `lifecycle.preservation`) is given the
same explicit `min_seq=classified.seq` scoping rather than relying on BP4b
having already run first in the same call — the two facts must agree by
construction, not by calling order.

Test: `test_mechanical_recovery_lifecycle.py::test_recovery_continuation_gets_its_own_preservation_and_archive_facts`.
A predecessor stops `awaiting_human` (one preservation fact, `not_needed`);
the continuation stops `awaiting_human` again (the shape in which the defect
was observable — a `completed` continuation never triggers preservation at
all, in `_TRIGGER_CLASSIFICATIONS`, before or after this fix). Asserts two
terminal `ext.preservation.*` records exist, the second has `seq` after the
continuation's own `classified` record, and the continuation's own archived

unchanged): the assertion `len(preservation_after) == 2` fails with `1`,

=== F-C: the predicate had no Hop-budget element

H005's renewed broad review found, by driving the real engine, that a
mechanical durable-artifact stop recorded on a Run's *last* authorized Hop
passed the predicate as it stood (it had no Hop-budget element) and
`resume_after_reconcile`'s pre-existing guard admits `hop_used ==
hop_limit`. Recovery then wrote `run.json` to `status=ready`,
`stop_reason=None`, and relaunched the engine, whose own
`run_serial_hops` loop opens with `if run.hop_used >= run.hop_limit:
break` (`operator.py:904`, previously unreachable because the reducer
normally stops at `AWAITING_HUMAN_BUDGET` before the budget is ever spent
with a further invocation needed) -- so the engine charged no Hop and
returned the Run still `READY`, classified `interrupted`. The honest
`reconcile_required`/`stop_reason` diagnosis was gone, and a second `wfc
resume` answered "lifecycle already classified (no-op)" with no
`semantic_stop` to let `prepare-successor` take over either: the Run was
terminally unresumable, the exact defect this WorkItem removes, newly
reachable through the fix for it.

Fixed by adding exactly one more live re-verification in
`_attempt_mechanical_recovery`, next to the HEAD/clean-worktree checks and
before the Commission-identity check: refuse by name (`"no autonomous Hop
budget remains for a continuation"`) when `run.hop_used >= run.hop_limit`,
changing nothing. `resume_after_reconcile`'s own guard, `diagnose_
mechanical_recovery_eligibility` and every other predicate element are
unchanged; a Run on its last Hop still classifies honestly as
`reconcile_required`/`awaiting_human` under A, it simply cannot be
recovered through `wfc resume` until a maintainer separately authorizes
additional Hop budget through the existing documented path (outcome 1/2 in
`docs/operator_manual/ch06_recovery/01_outcomes.adoc`). I deliberately did
not pursue the alternative of letting recovery proceed and classify
`awaiting_human_budget`: `run_serial_hops`'s `break` does not produce that
status, so making it do so would be a second, wider behaviour change to
the engine's own Hop loop for a case B's rule already covers ("if any
predicate fails it refuses with a named classification and message and
changes nothing").

Test: `test_recovery_refuses_on_no_hop_budget_remaining`
(`test_mechanical_recovery_lifecycle.py`), modeled on the other refusal
tests -- `hop_limit` reduced to the already-recorded `hop_used` (not
`hop_used` raised past the recorded Hop summaries, which
`serialization.run_from_json` rejects) so the fixture stays a valid Run;
asserts the named refusal and a byte-identical `run.json`.

== `robust@v1` left unchanged, and why

Neither the `robust@v1` nor `simple@v1` program record, route set or
catalogue digest was touched. The fix is entirely in the generic
mechanics every profile shares (`reducer.py`, `vertical.py`, `prompt.py`,
`operator.py`, `frontdoor/lifecycle.py`, `frontdoor/postrun.py`,
`frontdoor/report.py`): A/B classify and recover a mechanical stop from
facts already present on any profile's Run; C derives its prompt text
from `phase`/`profile` at dispatch time, never from a profile literal.
Verified by grepping the diff for `robust`/`simple` program identifiers
(none) and by `test_review_route_semantics_prompt.py` exercising two
profiles that are neither `robust@v1` nor `simple@v1`.

== Design notes on reuse

`RunStatus.RECONCILE_REQUIRED` and `reducer.require_reconcile`/
`resume_after_reconcile` already existed for two unrelated reconcile
reasons (`interruption`, `prerequisite_return`); `mechanical_recoverable`
is a third, additive reason, reachable only from `RUNNING` (A) or
`AWAITING_HUMAN` (B(ii), the retroactive reclassification of an
already-terminal incident-shaped Run) and never from any other status, so
a genuine human-authority stop can never be reclassified this way. The
engine relaunch reuses the unchanged `_cached_commission`/
`_pinned_envelope_text`/`_materials_digest` helpers `_do_commit` already
uses, so the live Commission-identity re-check is literally the same
check, not a parallel one that could drift.
