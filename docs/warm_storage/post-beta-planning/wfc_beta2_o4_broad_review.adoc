=== 2. The blocking Finding

[[o4-f1]]
*F-1 (blocking). `refused_path_inside_repository` does not cover the
repository's other working trees, so the command prepares into a sibling
worktree and dirties it.*

What the candidate does:: `_require_outside_repository` (`prepare_checkout.py`)
compares the target and scratch paths against `source.toplevel` and
`source.git_common_dir` only -- the single working tree named by
`--repository` and the Git common directory. A Git repository with linked
worktrees has *many* working trees sharing that one common directory, and
none of the others is checked.
How I reproduced it:: in a toy repository with a main checkout and one linked
worktree, `prepare_checkout(repository=<main>, target=<sibling>/run-checkout)`
succeeds and creates both the worktree and its `-scratch` sibling inside the
other working tree. The reverse direction (`--repository` the linked worktree,
target inside the main checkout) also succeeds. `git worktree add` itself does
not object.
Why it matters:: afterwards the host working tree reports
`?? run-checkout/` and `?? run-checkout-scratch/launch-env.sh` under
`--untracked-files=all`, `observe_repository(host).clean` is `False`, and
`git_facts.preflight_hop(host, ...)` raises
`GitPreflightError: non-ignored untracked state`. If that host worktree is
hosting a Run, its next Hop's auditable pre-Hop boundary fails, and
`lifecycle._do_probe` would refuse a launch there with "repository is not at
the clean authorized baseline". The refusal exists for precisely this reason,
and the record states it in those words: "An untracked file anywhere inside
the tree dirties it and refuses launch; a checkout inside a checkout is not a
fresh checkout." Dirtying *another* checkout is the same defect as dirtying
the given one, and in the one topology this command is written for -- one
fresh worktree per Run, fifteen sibling working trees of this repository
today -- the uncovered case is the ordinary one, not an exotic one.
Which acceptance criterion:: the task's `Acceptance`: "it refuses, by name, a
path whose checkout already has a lifecycle, an existing path, *a path inside
the repository*, a dirty base, and an unsafe hook". The command's own identity
model defines a checkout as the resolved top-level *plus* the resolved Git
common directory, i.e. the repository is the common directory and all its
working trees are trees of it; a path inside one of them is a path inside the
repository.
Feasible, simpler remedy (not a new requirement, and no new mechanism)::
resolve the repository's registered working trees once, before the first
effect, from the plumbing the module already shells out to --
`git -C <repository> worktree list --porcelain`, whose `worktree <path>` lines
list every working tree including the main one -- and refuse an overlap of
either created path with any of them under the *existing*
`refused_path_inside_repository` name. That check *subsumes* the present
`source.toplevel` comparison, so it replaces a special case rather than
adding one, and it needs one test per direction. No new refusal name, no new
state, no new flag. (If the maintainer would rather accept the gap than spend
a Hop, that is a decision for the maintainer, not something I may waive: the
criterion is explicit and the violation is reproduced.)

=== 4. The hook's trust boundary, independently probed

The design question of this slice is the hook, and this is the part I attacked
hardest. The boundary holds, and the parts that cannot be defended are stated
rather than papered over.

* The hook is *always* a blob committed at `--base-ref`, resolved through
  `commissioning._path` (so `a1_path_shape`: no absolute path, no `..`, no
  `./`, no glob, no backslash, no trailing slash), with committed mode
  `100755` required, `120000` refused by its own name, and a directory or
  submodule entry landing in `refused_hook_not_executable`. The declaration
  itself is read from the config *committed at the base ref*, which is the
  property that matters: an uncommitted edit of `.wfc/config.yaml` cannot
  redirect a command that executes code as the operator. I confirmed that a
  hook added in a later commit does not exist for an earlier base, and that a
  declaration naming an uncommitted path refuses rather than falling back to
  the working tree.
* The decide/execute gap is closed rather than assumed: the file actually run
  is re-checked in the new worktree to be a regular, non-symlinked file whose
  `git hash-object` equals the base blob, with every path component checked
  for a symlink. Both halves are tested, and a path shape that could name a
  file outside the tree is refused before the worktree exists.
* The output channel is a declaration channel and nothing else. All ten
  bounded-output parametrisations refuse: a stray diagnostic line, a
  lower-case name, an over-long value, a control character, non-UTF-8 bytes, a
  duplicate, over 64 declarations, over 65536 bytes, and `PATH`/`TMPDIR` as
  reserved names. `PATH` and `TMPDIR` are therefore always WFC's own
  composition, and `WFC_PREPARE_PATH_PREPEND` must be an absolute, existing
  directory *inside* the created checkout or scratch directory: I checked that
  a relative value, `/usr/bin`, and a symlink inside the scratch directory
  pointing at `/usr/bin` are all refused -- the last one because the value is
  `resolve()`d before the containment test, which is the right order.
* Failure is bounded and untrusted. I gave a hook 200000 lines of stderr and a
  nonzero exit: the refusal detail stays at the in-Hop evidence path's own
  `UNTRUSTED_DIAGNOSTIC_CAPTURE_LIMIT_BYTES` per stream plus a byte-count
  notice, labelled untrusted, printed only, never written to disk. A hanging
  hook times out by name. Reusing the existing limit instead of inventing a
  new one is the right call.
* The responsibility split is stated where an operator will meet it -- the
  record's Design, a `CAUTION` block in Operator Manual chapter 3, the
  quickstart, the skill text and the module docstring -- and it is the correct
  split: WFC owns the safe invocation and the invariants, the consumer owns
  the hook's content, exactly as for the declared evidence command. The "what
  this does not protect against" paragraph is honest about the part that
  cannot be defended: a committed hook runs on the operator's host, as the
  operator, outside every sandbox boundary WFC has, and anyone who can land a
  commit on the base ref of a repository whose config declares a hook can run
  code on that host at the next preparation. Not scrubbing the hook's
  environment is justified the same way (a venv build needs the host
  toolchain, and pretending to isolate it would be a safety claim the command
  cannot keep). I agree with all three judgements; inventing a sandbox here
  would be a safeguard that excludes hypothetical states while adding real
  failure modes.

=== 7. Non-blocking observations

None of these changes the verdict, and none is a new requirement. N-1 is worth
fixing in the same correction Hop as <<o4-f1,F-1>> because a Hop is being
spent anyway.

N-1 -- a non-UTF-8 committed Consumer Config crashes instead of `refused_config`:: The design's table promises `refused_config` for a config
that "exists at the base ref but cannot be parsed". `_git_raw` reads
`git show <base>:<config>` with `text=True`, so a committed config containing
non-UTF-8 bytes raises an unhandled `UnicodeDecodeError` out of
`prepare_checkout` -- a traceback and exit 1 instead of the named refusal and
exit 2. I reproduced it. Nothing is created and nothing is at risk, so this is
not an acceptance violation, but it is a deviation from the shipped design's
own table, and it is the defect class this repository has already named for
itself: `git_facts._run_git_raw`'s docstring exists because a strict text
decode of Git output "would otherwise escape … as an unhandled exception
rather than a named, journaled refusal". A `bytes` read plus one `except
UnicodeDecodeError` raising `refused_config` is the whole fix; the same
applies in principle to the other `text=True` Git reads in the module.
N-2 -- a hook that dirties the prepared tree is not detected, and the cost is the checkout's one lifecycle:: I gave a hook one line that writes an
untracked file into the checkout: the preparation *succeeds* and reports
success, and the operator discovers the problem at `wfc run`, where
`lifecycle._do_probe`'s pre-check refuses with "repository is not at the clean
authorized baseline" -- after authorization, so the checkout's single
lifecycle is spent, which is the exact cost this slice exists to remove. The
design deliberately assigns hook *content* to the consumer, WFC's own hook
puts its venv in the scratch directory, and the command already calls
`observe_repository` once, so a post-hook cleanliness check would be nearly
free. I am not asking for it: it is additional mechanism beyond the slice's
acceptance, and whether a prepared-but-dirty tree should be a refusal
(`refused_hook_dirtied_checkout`) or stay the consumer's problem is a
maintainer question. Recording it so the question is on the record.
N-3 -- "nothing outside the two created directories is written" is true of durable writes:: `observe_repository`, which the dirty-base check calls, makes
a throwaway copy of the live index with `tempfile.mkstemp` (so under
`TMPDIR`) and unlinks it in a `finally`. That is pre-existing, shared, correct
behaviour and the right way to read a tree without touching the real index,
but the record's "this is the one exception" sentence is strictly about *Git's
own* worktree administration. Half a sentence ("besides a transient index copy
under `TMPDIR` that the shared observation path removes") would make the claim
exactly true if the record is touched again.
N-4 -- the module's three private Git helpers duplicate `git_facts`':: `_git`, `_git_raw` and `_git_succeeds` reimplement what `git_facts` keeps
private, and they use plain `subprocess.run` without the `GIT_*` scrub and the
`core.hooksPath=/dev/null` policy that `git_facts._trusted_git` applies to
mutating Git. For this command that is defensible -- it runs on the operator's
host, against the operator's own repository, and it is about to run a
committed hook with full privileges, so a repository-local `post-checkout`
hook is not a new boundary -- but `git worktree add` is a *mutating* Git
operation and the reader will ask. One sentence of rationale in the module, or
a shared read-only helper in `git_facts`, would settle it.
