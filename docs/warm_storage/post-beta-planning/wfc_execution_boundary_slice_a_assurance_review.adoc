[[verdict]]
== 1. Verdict

. *Promote as a Layer-1-qualified, opt-in feature.* F1 to F5 are all really
  fixed, each by the mechanism its disposition required; I tried to forge,
  withdraw and stale the started signal on both adapters and found no route.
. The boundary itself is still sound: the generated view contains *exactly*
  the contract's mount kinds plus `--json-status-fd N` and nothing else
  (EXECUTED, token by token), and no route to unisolated execution under a
  selected `bubblewrap` mode exists.
. The unisolated `direct` path stays byte-identical in both adapters
  (`prepare_direct` reads nothing from even a fully populated grant;
  `pass_fds=()` is identical to the default; the new branch short-circuits).
. *Two things do change for every existing user of the installed Runtime,
  and neither is operator-documented:* the provider channel became
  per-invocation in `direct` mode too, changing the Run-state layout and
  `wfc archive`'s layout and content (N2); and the separate hop-timeout
  WorkItem in the same diff raised the default per-Hop cap from 900 s to
  14400 s and added a config key. Both are deliberate; only the first is
  undocumented.
. No new blocker and no new major finding. Eight minor items and four notes,
  none of which blocks an opt-in, default-off promotion.
. *Before the promotion commit:* document N2 (one paragraph), and refresh the
  contract's own `Status::`/`Type::`/`Authorized here::` header and the
  `_open.adoc` card, which still read as a pre-implementation planning record
  and mention neither the Opus review nor the rework (N8).
. *Before anyone actually selects `bubblewrap` on any host:* fix N1 (a
  reachable, nondeterministic launch refusal when the status pipe lands on
  file descriptor 9) and N3 (the unchecked, undocumented new `bwrap`
  capability prerequisite). Both are small and local.
. F6 to F15 need no action before promotion. F14 and F15 are moot; F7 and F9
  are reduced to notes by the rework; the rest stay open as the maintainer
  intended.

Two things in this table deserve to be said plainly, because a verified
absence of defects is a result. First, the F1 mechanism is a genuine
improvement in kind, not a patch: the classification input moved from "a
file inside the view" to "a descriptor that does not exist inside the view",
and the `fd 9` collision the `.git`-file masking could have caused was
noticed and guarded in the same change — I verified by execution that dash
really does clobber exactly fd 9 through that wrapper and no other number.
Second, the F5 refusal is complete in the dimension that mattered: there is
now no code path under the boundary that creates anything inside the
repository, so the "directory where a file was authorized" class is closed,
not merely narrowed.

== 5. Security re-check, test-and-claims audit, default-path impact

=== 5.1 Security: the first review's "sound" still holds

*The mount set is exactly the contract's kinds.* I built the argv for a full
Codex-shaped grant (writable repository subpath, writable channel,
authentication path, external scratch) and read all 70 tokens. In order:
`--die-with-parent`, `--json-status-fd N`, `--dev /dev`, `--proc /proc`,
`--unshare-pid`, `--new-session`, `--ro-bind /usr /usr`, the four
`/bin`-family symlinks, the five enumerated `/etc` read-only binds,
`--ro-bind <repo> <repo>`, `--tmpfs <repo>/.git` plus `--remount-ro
<repo>/.git`, `--size 268435456 --tmpfs /tmp`, `--bind <repo>/src
<repo>/src`, `--bind <channel> <channel>`, `--ro-bind <auth> <auth>`,
`--bind <scratch> /tmp/s`, `--remount-ro /`, `--chdir <repo>`, `--`,
command. EXECUTED. The only change from the pre-rework argv is the
`--json-status-fd N` pair; no fifth mount kind, no blanket home bind, no
gitdir, no Run state directory, no wholesale `/etc`, no `--as-pid-1`, and
`--remount-ro /` still appears exactly once, after every mount and before
`--chdir`.

*No route to unisolated execution.* `prepare` still dispatches on
`plan.grant.mode` alone and raises on anything that is neither `direct` nor
`bubblewrap`; `prepare_bubblewrap` now additionally refuses without a status
descriptor, which is one *more* fail-closed gate than before. Both
production call sites of `run_serial_hops` pass no adapter, so the derived
grant always reaches `_execution_adapter`. The Run-wide mode is still
checked against the Run's persisted mode as the first statement of
`run_serial_hops`, in both directions. `run_execution_configuration_from_yaml`
and `consumer_config_from_yaml` still accept only the two closed values, and
the value is frozen in the Commission envelope, so no in-Run edit of
`.wfc/config.yaml` can downgrade the current Run. The Claude adapter's
second read of the mode is still `!= "direct"` rather than `== BUBBLEWRAP`,
and is still fail-safe: a third mode takes the in-view branch, opens no
status pipe, and is then refused by `prepare` before any process starts
(TRACED). EXECUTED: a fully populated grant in `direct` mode produces a
`PreparedLaunch` identical to an empty one.

*Escape.* Nothing in the rework touches the `.git` masking, the
hardlink-alias walk, `_real_path`'s canonicality requirement, the
destination-overlap checks or the `build_argv` revalidation. The one new
host-visible object is a pipe whose write end never enters the view; the
operator measured directly that the descriptor is not open inside and that a
write to it fails with `EBADF`, and the new Layer-1 case asserts exactly
that through the real primitive. The confined process therefore has nothing
to unlink, nothing to forge and nothing to withdraw. I found no new reachable
path, and the F8 shadowing case remains the only mount-model gap.

*Provider relaxations.* Still nothing relaxes. `sandbox.enabled`,
`failIfUnavailable: true`, `allowUnsandboxedCommands: false` and
`denyRead: ["~/"]` are unchanged literals; `enableWeakerNestedSandbox`
appears nowhere; Codex's `--sandbox workspace-write` and
`--ask-for-approval never` are unchanged and not boundary-conditional. The
only boundary-conditional Claude setting is still the in-view scratch path.

*Byte-identity of the unisolated path, both adapters.* `prepare_direct`
returns `tuple(plan.argv)`, `plan.cwd`, `plan.environment` and reads nothing
from the grant (EXECUTED). In both adapters `started_signal` is `None`
whenever the mode is not `bubblewrap`, so no pipe is opened, `pass_fds=()`
is passed — which CPython treats identically to the default — `started` is
`True` by construction and the new branch cannot fire. Claude's `argv`,
`cwd`, settings and `TMPDIR` handling on the `direct` branch are untouched
by the rework; Codex's `argv` and its absent `cwd`/`env` likewise. TRACED
end to end for both; the unchanged conformance suites remain the regression
net and I could not run them here.
