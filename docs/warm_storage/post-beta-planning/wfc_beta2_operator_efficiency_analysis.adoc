== Summary: the six conclusions that matter

. *The dominant cost is not token volume; it is a refusal that arrives after
  it is expensive.* Three of the four Runs that lost a checkout in this
  session lost it to a fact the Front Door could have established earlier
  from inputs it already had: a Consumer Config path shape checked only after
  authorization (<<e2,2>>), an `--executable` never compared with the single
  adapter it must match (<<e14,14>>), and a baseline probe whose captured
  output is discarded before the refusal is printed (<<e21,21>>). Each one
  consumes the checkout's single lifecycle, so each costs a fresh worktree,
  a fresh venv and a fresh 3-6 minute baseline probe. These are the cheapest
  improvements in this analysis and they are pure ergonomics.
. *The one deterministic gate per Commission is the highest-leverage operator
  decision in the system, and nothing helps the operator choose it.* The
  evidence command is a single argv (`commissioning.py:362-364`,
  `frontdoor/lifecycle.py:415`), chosen freely at authoring time. One
  omission of lint cost ten Hops, six task-checks and two Opus Broad Reviews
  for one unused import (<<e18,18>>). The remedy that fits Beta 2 is a rule
  and a sentence in the shipped texts, not a contract change: the evidence
  command must run the repository's own gates, which here means `make check`
  (`Makefile:28`), not `python -m pytest -q`.
. *A newly established constraint bounds that remedy: the evidence timeout is
  a kernel hard cap of 900 seconds* (`model.py:27`, enforced at
  `frontdoor/request.py:81`), and the plain suite has already reached 896.96
  seconds once on this repository
  (link:../../backlog/BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[the timeout
  BUG]'s C3 diagnostic). A lint-inclusive `make check` therefore fits only
  with the verified offline input bundle in the environment (the same
  diagnostic measured 171 seconds with it). The evidence rule and the
  deterministic environment preparation are one coupled change, not two
  independent ones.
. *The answer channel the operator looked for in <<e15,15>> already exists and
  is invisible.* `wfc resume` correctly refused -- it covers only the
  mechanical durable-artifact anomaly class (`reducer.py:487-500`,
  `frontdoor/lifecycle.py:871-875`). `prepare-successor --authority-decision`
  (`operator.py:324-342`) is the productized path for exactly an
  `awaiting_human` stop carrying a frozen semantic stop, and an escalation of
  *any* kind, `operational` included, freezes one (`reducer.py:1753-1759`,
  gate at `operator.py:1688`). The Agent Skill describes neither
  `prepare-successor` nor `export-salvage`, forbids running an undescribed
  subcommand (`SKILL.md:131`) and warns that an unrecognized bare subcommand
  falls through to a legacy entry point (`SKILL.md:136-137`); the Operator
  Manual shows the command only as
  `python -m workflow_coordinator.operator prepare-successor`
  (`ch06_recovery/02_successors.adoc:130-131`). The cheapest fix in this
  whole analysis is three sentences of shipped text.
. *Of the owner's five themes, two are confirmed as stated, two are confirmed
  but already fully owned by existing records that defer them, and one is
  reshaped.* Automatic worktree management (a) is confirmed and is the
  direction
  link:../../technical_model/ch04_target_and_alternatives/03_adr_closed_versioned_workflow_programs.adoc#adr-ad5[AD-5]
  itself names as preferred; better diagnostics (e) is confirmed and one
  genuinely uncovered gap remains (the baseline-probe refusal). Continuation
  after interruption (b) and targeted successor Runs (c) are confirmed as
  gaps but are held by records whose own deferral reasons still hold.
  Simplifying large CommitIntents (d) is reshaped: its record already
  contains the question, the three alternatives, the regression inventory and
  the success criteria, so Beta 2's useful contribution is at most the
  read-only helper -- and this session found first-hand that the accepted
  mitigation it would replace is itself contaminated (<<e17,17>>).
. *The honest Beta-2 cut is small, cheap and entirely category A.* Six
  candidates are pure ergonomics and four of them are a handful of lines plus
  tests. Everything that touches a trust or authority boundary -- the
  evidence-command list, an in-place Hop-budget raise, Worker-only closure of
  a mechanical Finding, phase entry, CommitIntent enumeration, checkout reuse
  -- is recorded with options and a recommendation and is *not* proposed for
  Beta 2. No candidate in this analysis requires reversing a recorded
  maintainer decision.

== The candidate catalogue

Eight candidates survived evaluation. Each states the exact problem with its
friction-log evidence, where the fix belongs, its authority and trust impact,
risk, benefit, size as a Hop-budget estimate (upper limit about twice the
expected count, following <<e13,entry 13>>'s observed convergence) and the
qualification it needs. Four candidates the operator proposed are *rejected
or absorbed*; they are listed in <<rejected>> with the reason.

[[c1]]
=== C1 -- A program ignores role defaults it does not use

Problem:: `simple@v1` cannot be used in a repository whose committed config
carries a `robust@v1` reviewer default, so every `simple@v1` Commission needs
a second committed config file that must never be integrated. Evidence:
<<e1,1>>, <<e21,21>>. This session carries one such commit
(`chore(worktree-local): second config ...; never integrate`), which is the
recurring cost in concrete form.
Where the fix belongs:: Front Door, `frontdoor/config.py:257-262`. Six lines
plus tests.
Authority and trust impact:: Narrow but real, and it must not be waved away.
The refusal is the only mechanical signal that a role default is inert; a
consumer could read a committed `independent_reviewer` default as evidence
that review happens when the selected program performs none. Against that:
the program selection, not the config, decides whether review happens, and an
unknown role *name* is already refused when the config is parsed
(`config.py:204-206`), so the check only ever fires on a valid role the
program does not use. The asymmetry that resolves it: a
`--execution-override` is a per-Commission *intent* that cannot take effect
and should stay refused (`config.py:252-256`); a `default_execution` entry is
a standing repository *fact* that several programs share.
Risk:: Low. Mitigation: refuse config defaults no longer, keep refusing
overrides, and have `wfc plan` *print* which role defaults the selected
program ignores, so the inertness is visible rather than silent.
Benefit:: Removes a per-Commission committed artifact and the
never-integrate hazard it creates; removes <<e21,21>>'s entire failure mode.
Size:: One Commission, Hop budget 6.
Qualification:: A test that `simple@v1` resolves against the committed
repository config unchanged; a test that an unused *override* is still
refused; `tests/unit/test_self_development_consumer_config.py` green and
unchanged; `wfc plan` output asserted to name the ignored default.

[[c2]]
=== C2 -- Pre-launch refusals that are complete and early

Problem:: Three refusals around `wfc run`'s first three steps either arrive
after the lifecycle is spent or omit the fact the operator needs, and each
one costs a fresh worktree, venv and baseline probe. (a) A Consumer Config
path outside the repository is accepted by `wfc plan` and refused after
authorization as `inconsistent` (<<e2,2>>). (b) `--executable` is never
compared with the single adapter the envelope resolved to (<<e14,14>>).
(c) The baseline-probe refusal prints the exit code and discards the output
it already captured (<<e21,21>>).
Where the fix belongs:: Front Door: `frontdoor/plan.py` (a),
`frontdoor/lifecycle.py` steps 1-3 (a, b, c). No kernel change; no new
classification.
Authority and trust impact:: None for (a) and (c): (a) moves an existing
refusal earlier and widens nothing, (c) adds diagnostic output only, and the
output must be labelled untrusted exactly as the in-Hop path labels its own
(`evidence.py:243-260`). (b) *adds* a fail-closed refusal, which narrows
rather than widens -- the one case to get right is a legitimate wrapper
binary whose name matches neither adapter.
Risk:: (b) false positives. Mitigation: refuse only an unambiguous mismatch
-- the basename resolves to the *other* adapter's known binary -- and never
refuse an unrecognized name or an explicit path. (c) output volume and
secret leakage. Mitigation: reuse the existing bounded-tail limit
(`evidence.py:25`, 16384 bytes) and the same untrusted labelling; do not
persist it as evidence.
Benefit:: Removes the three cheapest lifecycle losses observed in the
session. (c) alone replaces a six-minute manual re-run of the probe command
with a line of printed output.
Size:: One Commission, Hop budget 8.
Qualification:: One test per refusal: an absolute/non-A1 `--config` refused
by `wfc plan` with no lifecycle consumed; a `claude_cli` envelope with
`--executable codex` refused by name before dispatch; a failing probe whose
refusal contains a bounded tail of the captured output and is labelled
untrusted. The existing `refused_probe`/`refused_prelaunch` classifications
must be asserted unchanged.

[[c3]]
=== C3 -- One deterministic Run-checkout preparation step

Problem:: Every Run needs a fresh checkout *at a fresh path*, its own venv
with an editable install, the verified offline bundle in the environment, a
`TMPDIR` outside the worktree and -- until <<c1,C1>> -- a second config file.
All of it is manual, none of it is a recipe in the shipped texts, and each
omission costs a refused probe or a broken gate. Evidence: <<e4,4>>,
<<e6,6>>, <<e12,12>>, <<e17,17>>, <<e20,20>>.
Where the fix belongs:: Front Door, as a new command. This is the direction
link:../../technical_model/ch04_target_and_alternatives/03_adr_closed_versioned_workflow_programs.adoc#adr-ad5[AD-5]
itself names: "The preferred way to reduce that friction later is *automated
worktree or branch creation and controlled cleanup at the Front Door*, not a
looser kernel invariant."
Authority and trust impact:: Category A *only while it honours the
one-Run-per-checkout invariant* -- that is, while it always creates a new
path and never reuses a checkout that holds a lifecycle. Reuse is
link:../../backlog/FTR-WFC-LIFECYCLE-ROTATION.adoc[FTR-WFC-LIFECYCLE-ROTATION]'s
category-B subject and is explicitly not part of this candidate. The one
genuine authority question is *cleanup*: removing a checkout is destructive,
and the Agent Skill already withholds discarding anything this session did
not itself create (`SKILL.md:50`, `:57`).
Risk:: (a) Scope creep into rotation. Mitigation: an acceptance criterion
that the command refuses any path whose checkout digest
(`frontdoor/journal.py:75-89`) already has a journal. (b) A preparation
command that writes outside the repository is a new kind of Front Door
effect. Mitigation: the prepare-only variant writes only inside the new
checkout and the scratch directory it creates. (c) Environment preparation
is consumer-specific; WFC's own offline bundle is not a generic consumer
need. Mitigation: prepare the generic part (worktree, scratch, `TMPDIR`) and
drive the consumer-specific part from a declared, committed hook rather than
hard-coding WFC's own.
Benefit:: The largest single reduction in operator mechanics in this
analysis, and the precondition for <<e18,18>>'s evidence rule being usable at
all: `make check` fits the 900-second cap only with the verified bundle in
place (171 versus 896.96 seconds, per
link:../../backlog/BUG-WFC-EVIDENCE-TIMEOUT-DIAGNOSTICS.adoc[the timeout
BUG]).
Size:: Prepare-only variant: one Commission, Hop budget 10. With controlled
cleanup: add one Commission, Hop budget 8.
Qualification:: A fresh path is created and a path with an existing lifecycle
is refused by name; the prepared checkout passes an unmodified baseline probe
that the unprepared one fails; the one-Run-per-checkout invariant is asserted
unchanged; nothing outside the created checkout and scratch directory is
written; for the cleanup variant, removal refuses anything the command did
not create.

[[c8]]
=== C8 -- The economy of continuing a stopped Run (category B, recorded and deferred)

Problem:: Two shapes cost a full successor Commission with its own review
chain for work that is mechanically trivial. (i) An exhausted Hop budget has
no in-place raise and is categorically ineligible for the productized
successor path, so a one-import lint residue costs three agent Hops
(<<e19,19>>). (ii) An `awaiting_human` operational stop can be answered only
through `prepare-successor`, which requires five newly pinned governing input
paths and a clean successor checkout at an exact baseline -- heavy for
handing over one failing node id (<<e15,15>>).
Where the fix belongs:: The product core: Hop accounting, admission and
review authority.
Authority and trust impact:: Category B on three counts. A budget raise
changes an admitted WorkItem's governing truth and collides with the recorded
rule that used Hops are never reset and resume requires explicit maintainer
authority (`FTR-WFC-ATOMIC-HOP-RECOVERY`'s `WFC-AUTO-05`). Worker-only
closure of a "purely mechanical" Finding moves Finding disposition away from
the independent reviewer -- the safeguard the repository is built on -- and
requires a machine-decidable definition of "mechanical" that does not exist.
A lighter answer channel re-opens what governing truth a continuation admits.
Risk:: The specific erosion to name: "a deterministic check failing with no
behaviour change" is not mechanically distinguishable from "a reviewer's
blocking Finding the Worker would rather close itself". Any such mechanism
must derive the class from the Coordinator's own observation, never from the
agent's claim about its own change.
Benefit:: Saves two agent Hops in the observed case. Measured against the
session: once.
Size:: Not sized as a Beta-2 slice.
Qualification:: Not applicable. The interim remedy is <<c6,C6>>'s budget
guidance plus <<e18,18>>'s gate rule, which prevents the case rather than
cheapening its repair.

[[classification]]
== The A/B classification

Category A -- pure ergonomics:: Skill and manual text, Front Door argument
handling and refusal timing, diagnostic output, scaffolding over inputs the
Front Door already parses, and deterministic preparation of a *fresh*
checkout. <<c1,C1>>, <<c2,C2>>, <<c3,C3>>, <<c4,C4>>, <<c5,C5>>, <<c6,C6>>.
Category B -- touches a trust or authority boundary:: <<c7,C7>> (the evidence
contract and, through `model.py:699`, result-contract selection), <<c8,C8>>
(Hop accounting, admission, and Finding disposition authority), and the three
themes already held by deferring records: phase entry (c), CommitIntent
enumeration (d) and checkout reuse. Each is presented with options, a
recommendation and the decision it needs. *None is presented as decided.*

Where an ergonomic change could erode a safeguard, stated plainly::
* <<c1,C1>> removes the only mechanical signal that a committed role default
  is inert. Mitigated by keeping the override refusal and printing the
  ignored defaults in `wfc plan`; the residual risk is a consumer misreading
  a config as evidence of review.
* <<c2,C2>>(c) prints provider-adjacent command output in a refusal. It must
  carry the same bounded limit and untrusted labelling the in-Hop path
  already uses; a tail printed as though it were trusted evidence would be a
  real regression of the trusted/untrusted split.
* <<c2,C2>>(b) adds a refusal. The erosion risk is the opposite of the usual
  one -- a false positive that blocks a legitimate wrapper -- which is why it
  must fire only on an unambiguous cross-adapter mismatch.
* <<c3,C3>> sits directly against the one-Run-per-checkout invariant. Its
  acceptance must assert the invariant, and its cleanup variant is
  destructive and is therefore a separate decision, not a default.
* <<c4,C4>> would, in its naive form, break `wfc plan`'s documented
  write-nothing promise. The promise is not a trust boundary, but it is a
  stated contract, so the change belongs behind an explicit flag or a
  separate subcommand and is routed as a maintainer decision.
* <<c5,C5>> would, if wired into `make check`, make the repository's own gate
  -- and therefore every baseline probe -- depend on a Ruby tool. Not
  proposed.
