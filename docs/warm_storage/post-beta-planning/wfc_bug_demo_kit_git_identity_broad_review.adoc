=== Mechanism: is it the smallest one that respects the contract?

Yes, within the stated fixed points. `wfc init --evidence-repository` already
has exactly two documented outcomes, and `ensure_evidence_repository`
(`frontdoor/init.py` lines 93-123) returns `"reused"` for an existing
directory that is a Git repository root with an `archive/` directory -- it
writes nothing into it and makes no commit. The kit now creates precisely such
a repository, with a repository-local identity set the same way
`_create_greeter_repository` already sets `greeter`'s, so the bootstrap commit
that needed a host identity never happens. Nothing in `src/`, in `wfc init`,
in the Evidence initialization or in the trusted Git execution moves, and
`rehearse.py` needs no change at all: `git -C <evidence repo>` reads that
repository's own `.git/config` regardless of `HOME`, which my rehearsal runs
confirm -- the archive commits are `WFC Demo` although `rehearsal-home` could
supply no identity.

The alternative that would avoid the duplicated ignore block -- letting `wfc
init` create the repository and handing it an identity through a `.gitconfig`
in a `HOME` the kit points the `wfc init` subprocess at -- is not available
under AC-2, which requires the Evidence repository to carry a
*repository-local* `user.name`/`user.email` as `greeter` does; and it would
make the kit manage a `HOME` for a step that currently inherits the
operator's. I see no materially simpler mechanism that keeps the fixed points
and AC-2. The one lasting cost the chosen mechanism does carry is the
duplicated constant, O-1.

=== Non-blocking observations

O-1 (maintainability; the only lasting cost I found):: `EVIDENCE_GITIGNORE_BLOCK`
in `make_workspace.py` duplicates
`frontdoor.config.evidence_gitignore_block()` with no guard, and nothing fails
if the two diverge: the demo's Evidence repository would then retain raw files
differently from a `wfc init`-created one, silently, and only in the demo. The
duplication itself is justified (the kit imports only the standard library)
and I verified the two are byte-identical at this HEAD. A one-line guard is
feasible inside the already-authorized test file -- the test file may import
`workflow_coordinator`, the stdlib-only rule binds the kit modules only -- for
example asserting the created `greeter-evidence/.gitignore` equals
`evidence_gitignore_block()`. I did exactly that assertion by hand and it
holds; adding it is a judgement call for the maintainer, not a blocking defect.

O-2 (record wording):: The `== Implementation` section says "Every commit the
kit or a rehearsal makes into `greeter-evidence` carries the repository-local
identity `WFC Demo`". That is true for host *configuration*, which is what the
sentence then argues, but not for an operator environment that carries
`GIT_AUTHOR_*`/`GIT_COMMITTER_*`: the kit's own `_git` helper does not strip
inherited `GIT_*` variables, so with them set I observed the kit's Evidence
commit (and, unchanged from before, `greeter`'s two commits) authored `Env
Person <env@example.org>` while the repository-local configuration stayed
`WFC Demo`. AC-2 asks for the configured identity and is unaffected; WFC's own
trusted commits (the `wfc init` bootstrap and every archive commit) strip
`GIT_*` and are unaffected too. This is pre-existing kit behaviour, not
introduced here; only the record's blanket sentence is wider than the fact.

O-3 (spec drift outside this scope):: `FTR-WFC-CONSUMER-DEMO-WORKSPACE.adoc`
still describes the Evidence repository as "created by `wfc init`" (its
workspace listing and its step-3 description), which the kit no longer
prints. The FTR is explicitly withheld from this WorkItem, so leaving it
untouched was correct; the `== Implementation` section does not mention the
divergence. Realigning the FTR is a maintainer decision for the next upkeep
pass.

O-4 (determinism scope, examined and not objected to):: Only the two new tests
disable Git's account-name fallback; the other 26 tests in the file still run
with it live, so a future regression of the Evidence identity would stay green
on a developer host there and show up only in the two new tests (and on a
hosted runner). Moving `_disable_git_identity_fallback` into the
`throwaway_home` fixture would make the whole file host-independent, but it
would force the two `list(throwaway_home.iterdir()) == []` containment
assertions to be rewritten -- which AC-5 forbids loosening. The per-test
placement is therefore the right call under this task's constraints; recorded
only so the trade-off is visible.
