== The YAML-collection-key observation — partly unresolved, now fixed

H002's observation was general ("YAML collection keys... stops parsing
before execution... uncaught `TypeError`"), and H003's fix
(`commissioning._construct_unique_mapping`, used by Consumer Config and
Consumer Request parsing) only covered that one loader. `serialization.py`
has its own, separately defined `_StrictLoader`/`_construct_unique_mapping`
with the identical duplicate-key logic and the identical missing
hashability guard, used by `run_execution_configuration_from_yaml`,
`work_item_from_yaml`, `workflow_profile_from_yaml`,
`repository_policy_from_yaml` and `component_manifest_from_yaml`. Direct
call confirmed the gap still live on `728f5cb`:
`run_execution_configuration_from_yaml` on a version-2
`phase_bindings: {[implement]: {...}}` fragment raised an uncaught
`TypeError: unhashable type: 'list'` — reachable at the execution-envelope
boundary (`operator._preflight`, the same boundary Finding 2 covers), not
only through Consumer Config.

Fix made in this Hop: added the same `isinstance(key, Hashable)` guard
(raising `ConstructorError`, caught by the existing `yaml.YAMLError`
handler and converted to `ValidationError`) to
`serialization._construct_unique_mapping`. Verified by direct call after
the fix: both `work_item_from_yaml` and
`run_execution_configuration_from_yaml` now refuse a list-valued key with
"found unhashable key" instead of raising `TypeError`, and the pre-existing
duplicate-key diagnostic ("found duplicate key") is unchanged for both
loaders. Added `test_unhashable_yaml_key_fails_closed_with_diagnostic` in
`tests/unit/test_serialization.py`, next to the existing
`test_duplicate_yaml_key_fails_closed`, covering both the work-item loader
and the version-2 execution envelope loader. Its two assertions mirror the
direct-call reproduction above: before this Hop's fix, the same two calls
raised an uncaught `TypeError: unhashable type: 'list'` (shown above against
`728f5cb` before editing `serialization.py`); after the fix, both raise
`ValidationError` matching `"unhashable key"`, which is what the test
asserts. `pytest` itself could not collect the test file in this sandbox
(see Environment), so the test's own pass/fail was not reproduced by
running `pytest`; its asserted behavior was reproduced by direct call
instead, against both the pre-fix and post-fix code.
