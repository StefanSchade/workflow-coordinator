[[verdict]]
== 1. Verdict, in five lines

. The mount model, the seam and the fail-closed selection logic are sound: the
  generated view contains *exactly* the contract's mount kinds and nothing
  more, `prepare_direct` is a true identity for both adapters, and no route
  to unisolated execution under a selected `bubblewrap` mode was found.
. No escape from the boundary was found or is suspected: no reachable `.git`,
  gitdir, common directory, object database, Run state, `$HOME` content or
  write outside the grant, in any code path I traced.
. Rework *is* needed, and it is narrow: the new started/not-started signal was
  placed inside the one directory the contract had just finished arguing must
  not be agent-writable, and it goes stale across Hops (F1, F2 -- both
  EXECUTED).
. Three further items block clean promotion: the one credential-bearing mount
  accepts any existing host path with no narrowing check or documented rule
  (F3, EXECUTED); the sandbox-root measurement that exit criterion 1 requires
  "recorded either way" is asserted tautologically and recorded nowhere (F4,
  TRACED); and a scope entry naming a not-yet-existing *file* is pre-created
  as a *directory*, so such a Commission cannot run under the boundary and is
  not refused by name (F5, EXECUTED).
. Recommendation: commission one small, targeted rework (five source leaves,
  five test leaves, two documents; `robust@v1`; four to six Hops) for F1 to
  F5, then promote as a Layer-1-qualified, opt-in feature. Do *not* redesign:
  the architecture the contract specified is what was built.

[[finding-detail]]
== 2a. Finding detail: what was executed

=== F1 and F2, the started marker

`prepare_bubblewrap` wraps the provider command as
`/bin/sh -c ': > "$1"; shift; exec "$@"' sh <marker> <provider argv...>`
(`execution_launcher.py:284`), and `boundary_started_marker` places `<marker>`
in the writable provider channel for a Codex-shaped grant and in the external
scratch for a Claude-shaped one (`:236-245`). Both are bound read-write into
the view, so the confined process can unlink the file. I confirmed the full
argv by building it (see <<q1>>), then drove the real `CodexCliAdapter` with a
stub standing in for `bwrap`:

* stub exits non-zero without running the wrapped command, no stale marker:
  `CodexCliError: execution boundary failed before the provider started` --
  the intended classification.
* same stub, with a marker file left in the channel beforehand: no error; the
  outcome is `returncode = 1`, `candidate = None`,
  `diagnostics = ('Codex CLI exited 1',)` -- a `bwrap` setup failure reported
  as a started provider.
* stub that runs the wrapper (so the marker is created), then deletes the
  marker and exits non-zero: `CodexCliError: execution boundary failed before
  the provider started` -- a provider that did run, classified as never
  started.

The channel is `<run_root>/provider-channel` with no invocation component
(`operator.py:1053`, `slice4.py:324`), so the second case is the ordinary
shape of every Hop after the first in a boundary-selected Codex Run. The
contract's `<<channel>>` section rejected mounting the Run state directory
precisely because it would give the agent "write access to the dispatch
marker on which this slice's own not-started/started classification depends";
the implementation then created a new classification input and put it inside
the one directory it had just made agent-writable.

=== F3, the authentication mount

I called `validate()` with each candidate as `readable_host_paths` against a
synthetic repository and printed the emitted argv:

* a home-shaped directory containing `.ssh/id_ed25519`, `.claude/credentials.json`
  and an unrelated repository: *accepted*, `--ro-bind <dir> <dir>`.
* a whole `.claude` directory: *accepted*.
* an unrelated private-key file: *accepted*.
* `/etc/shadow`: *accepted*.
* `/` : refused, but only because it overlaps the repository, which happens to
  lie under it on this host.

The checks that do exist are real and correct as far as they go: the path must
be absolute, canonical, existing, a file or directory, disjoint from the
repository, the system roots, the channel, the scratch and every other mount,
and outside the generated system view (I confirmed `/dev`, `/etc/resolv.conf`
and `/tmp` are each refused by name). What is absent is any notion of
*narrowness*, which is the one property the contract's credential rules are
about. The companion test's name,
`test_readable_host_path_cannot_substitute_an_arbitrary_host_path`, states the
property that is missing; its body only proves that a nonexistent path and a
relative path are refused.

=== F5, file-shaped scope entries

With `artifact_paths` empty, as it is for a `robust@v1` worker phase:

* `authorized_scope=("docs/warm_storage/post-beta-planning/new_review.adoc",)`
  yields `writable_repository_paths = ('docs/warm_storage/post-beta-planning/new_review.adoc',)`
  and `missing_writable_targets = (<repo>/docs/warm_storage/post-beta-planning/new_review.adoc,)`.
* the same entry declared in `artifact_paths` yields
  `('docs/warm_storage/post-beta-planning',)` with nothing to pre-create --
  the intended reviewer shape.
* an artifact whose whole parent chain is absent falls back to the artifact's
  own path, so the degenerate case is pre-created as a directory too.

The behaviour is a defensible reading of `<<mounts>>`, whose rule 1 says any
absent entry is a directory "unless the Commission says otherwise" while rule
2 says a not-yet-existing file resolves to its nearest existing ancestor; the
implementation made "the phase's declared durable artifacts" the only way a
Commission can say otherwise, and `test_derive_boundary_grant_never_overgrants_to_the_repository_root`
locks that in. The result is still a Commission shape that cannot run under
the boundary and is not refused by name, which is the part that needs a
maintainer decision rather than a silent default.

[[q1]]
== 3.1 Security

Nothing in this section is a defect; it is what I checked and found sound,
with the two integrity defects already stated as F1 to F3.

*The generated view contains exactly the contract's mount kinds.* I built the
argv for a full Codex-shaped grant (writable repository subpath, channel,
authentication path, external scratch) and read every token. In order:
`--die-with-parent`, `--dev /dev`, `--proc /proc`, `--unshare-pid`,
`--new-session`, `--ro-bind /usr /usr`, `--symlink usr/bin /bin` and the three
other `/bin`-family links, the five enumerated `/etc` read-only binds,
`--ro-bind <repo> <repo>`, `--tmpfs <repo>/.git` plus `--remount-ro
<repo>/.git`, `--size 268435456 --tmpfs /tmp`, `--bind <repo>/src <repo>/src`,
`--bind <channel> <channel>`, `--ro-bind <auth> <auth>`, `--bind <scratch>
/tmp/s`, `--remount-ro /`, `--chdir <repo>`, `--`, command. EXECUTED. There is
no fifth mount kind, no `$HOME` bind, no gitdir, no Run state directory, no
`/etc` wholesale, no `--as-pid-1`, and `--size` immediately precedes the
`/tmp` tmpfs it caps. `--remount-ro /` appears exactly once, after every mount
and before `--chdir`.

*`.git` and the Git object database.* `validate()` accepts a `.git` directory
or regular file and refuses a symlink (`execution_boundary.py:169-171`;
EXECUTED for all three shapes). The directory shape is masked with a
read-only tmpfs, the file shape with `--ro-bind-data 9 <repo>/.git` behind a
`/bin/sh` wrapper that opens FD 9 on `/dev/null` and execs into `bwrap`, so
PID, process group and session are unchanged (`:334-342`; EXECUTED for the
argv shape). A writable grant can never be `.git` or contain it: `relative`
must be non-empty and must not contain a `.git` component (`:197-200`), which
also means the repository root itself can never be writable -- I confirmed
that a scope of `"."` is refused. Neither the per-worktree gitdir nor the
common directory is ever a mount source or destination; they are unreachable
because nothing outside the repository is mounted. TRACED. The contract's
"assert that they are not inside the view" is *not* implemented as an explicit
assertion; the property holds structurally instead. I do not treat that as a
defect, because the structural guarantee is stronger than the assertion would
be, but it is a conformance difference worth recording.

*Routes to unisolated execution.* I looked for all of them.
`prepare` dispatches on `plan.grant.mode` alone and raises on anything that is
neither `direct` nor `bubblewrap` (EXECUTED). Both production call sites of
`run_serial_hops` (`operator.py:2001`, `:2158`) pass no adapter, so
`_execution_adapter` always receives the derived grant and an adapter can
never be constructed without one while `bubblewrap` is selected. The
Run-wide mode is checked against the Run's persisted mode as the first
statement of `run_serial_hops` (`:946-951`), in both mismatch directions.
`run_execution_configuration_from_yaml` and `consumer_config_from_yaml` accept
only the two closed values. An unrecognised mode on the Codex path refuses
with a not-started error and no provider process starts (EXECUTED: a stub
provider's own marker file was never created). Exception paths: every
`BoundaryConfigurationError` reaches a not-started classification, by F7's
indirect route rather than by name. Timeout and kill paths are untouched in
both adapters, and the marker check is skipped when `timed_out` is true.
Resume cannot downgrade. No environment variable or configuration key
downgrades silently; the only new environment variable,
`WFC_BOUNDARY_AUTHENTICATION_PATH`, can only *add* a read-only mount, which is
F3.

*The mode is read in two places.* `claude_adapter.py:323` tests
`self.boundary is not None and self.boundary.mode != "direct"` to choose
between host-path and in-view settings and `TMPDIR`. This is a second read of
the mode outside the seam, and it tests for inequality to `direct` rather than
equality to `bubblewrap`. It is nevertheless fail-safe: an unrecognised mode
takes the in-view branch and is then refused by `prepare` before any process
starts, so the only residue is a settings file naming in-view paths that no
process ever reads. TRACED, with the Codex equivalent EXECUTED. I would still
prefer `== BUBBLEWRAP` there, since the current form silently treats a future
third mode as isolated.

*Symlinks, path normalization, TOCTOU, `..`, bind-over-bind.* `_real_path`
requires every source to be absolute and already fully resolved, so a
non-canonical or symlinked source is refused before any access (EXECUTED
incidentally: my first probe was refused for exactly this reason). `..` in a
destination is refused; overlapping caller destinations are refused; the
channel and authentication destinations are additionally checked against each
other, against the scratch, and against the generated system view (EXECUTED).
The hardlink-alias walk runs over every writable grant, the writable channel
and the external scratch, refusing any non-directory inode with
`st_nlink != 1`, at `validate()` and again inside `build_argv`, which
revalidates from scratch. The residual TOCTOU window is the one the contract
already accepts as residual risk 1 and 2. The one gap I found in this family
is F8, the repository destination not being checked against the generated
system view.

*`/proc`, `/dev`, PID namespace, `--new-session`.* `--proc /proc` with
`--unshare-pid`, `--dev /dev`, `--new-session`, and no `--as-pid-1`, all
present and asserted by unit tests on the argv. The residual host-global
`/proc` exposure is named in the contract and not resolved here, correctly.
The N8 question (can the child create a new mount or user namespace that
re-mounts a host path) is answered only by a shallow test: it probes `mount -t
tmpfs` and a nested `bwrap --unshare-user --bind`, both inside an `if`, so the
case also passes when `mount` is simply absent from the view or when nested
namespaces are unavailable for unrelated reasons, and it never attempts the
classic `unshare -m` plus remount-read-write of the repository bind. I did not
find a reason to believe the property fails -- mounts created in bwrap's own
user namespace are locked against a nested namespace -- but it is asserted
more weakly than N8 asks. SUSPECTED; probe P4 below.

*Provider-relaxed settings.* Nothing relaxes. `sandbox.enabled`,
`failIfUnavailable` and `allowUnsandboxedCommands` are unconditional literals

== 3.3 Test quality

What is sound, and worth saying plainly: *no test is skipped and no skip
marker was introduced*. The `bwrap`-dependent files fail loudly on a host
without working user namespaces, which is the right direction and what the
Developer Guide says. The existing primitive-level suite was not weakened: the
`/repo`-to-path-identity migration kept every negative case and added the
retired `/repo` destination as a new refusal case. The relocation-driven edits
in `tests/unit/test_slice4.py` are pure path moves. The serialization tests
include a byte-identity replay of a pre-change `run.json`, which is the
strongest form of the "historical records still replay" claim.

Three real weaknesses:

. *F4*, the two tautological assertions. `test_sandbox_root_remount_ro_does_not_disturb_writable_grants`
  ends with `assert b'no_host_backing=0' in result.stdout or b'no_host_backing=1'
  in result.stdout`, and the script prints exactly one of those two strings;
  the rewritten nested-`bwrap` case ends its failure branch with `assert
  result.returncode != 0` inside `else` of `if result.returncode == 0`. Both
  are described in their own docstrings as "measuring rather than assuming",
  and neither records the measurement anywhere a reader can retrieve.
. *F9*, N11's configuration does not match production.
. *N8* is weaker than its name: both of its probes sit inside `if`
  conditions that are also false when the probed binary is absent or the
  nested namespace is unavailable for unrelated reasons.

One existing test did change meaning:
`tests/integration/test_nested_claude_bwrap_qualification.py`. Its exact
`returncode == 1` and exact-stderr assertions were replaced by "stderr is not
the old diagnostic and contains no `overflowuid`", and its
`assert not nested-marker.exists()` by a two-branch conditional whose failure
branch asserts nothing. The behaviour genuinely changed -- Slice A supplies
`/proc`, which is the whole point -- so the old assertions could not stand,
and the fixture's `--chdir /repo` had to move. The rename and the long
docstring are honest about all of that. But the replacement is materially
weaker than it needed to be: the test would now pass for almost any nonzero
exit with almost any stderr. I would not call this "weakening a test to make
a change pass" in the stop-rule sense; I would call it an incomplete
replacement, and it is the same pattern as F4.

Contract claims with no test at all, as far as I could find: the
gitdir/common-dir non-containment assertion (because it is not implemented as
an assertion); preflight check 8 (because it is not implemented); the
external-scratch half of preflight check 4 (because it is unreachable); the
cross-Hop behaviour of the channel and the marker (F2); and the
adapter-specific authentication requirement of check 6 (F6).

This is the strongest part of the candidate. Every reconciled document states
that no preventive-isolation claim is made and that Layer 2 has not been
performed, and `docs/architecture.md:82` retains the sentence the contract
required be retained verbatim. See <<claims>> for the per-claim audit. The
Layer 1 versus Layer 2 distinction is kept consistently: the integration
suite's own module docstring calls itself Layer 1, the quickstart and the Beta
limitations list say the live layer is not in the package's test suite, and

product documentation:

I found no claim of scope *enforcement* beyond prevention-for-the-filesystem,
no claim that the boundary replaces the post-Hop check, and no claim about

== 3.5 Engineering quality

Sound: the module is small, pure and exhaustively unit-testable as the
contract intended; both adapters keep their own process handling; the single
derivation function means the two construction sites cannot drift; the
`finally` bracket is correct about not suppressing an in-flight exception;
`_check_writable_aliases` and `_real_path` fail closed on `OSError` and on any
non-canonical input; `build_argv` revalidates so a hand-built
`ValidatedBoundary` cannot bypass validation; the archive extension is a
separate named allowlist rather than a widened one.

Items a maintainer may regret, beyond the findings: the unused `binding`
parameter and the unreachable scratch check in `_preflight_boundary` (F6); the
Codex adapter ignoring two of the three values the seam returns; the
`writable_host_paths` field that exists only to be refused (defensible, since
the contract names it, but it is a field no code path can ever populate); and
the preflight namespace probe not resembling the view it is meant to
pre-qualify. Duplicated logic between the adapters is minimal and of the
unavoidable kind -- the four-line marker check is textually identical in both,
which is where F1's fix should be factored. Concurrency: the boundary adds no
shared mutable state beyond the per-checkout channel directory, which is
exactly F2's problem; two Runs against the same checkout would already be
refused by the checkout association.

[[could-not-check]]
== 8. What I could not check

* *Anything requiring a real `bwrap` run.* This Hop's sandbox has no
  unprivileged user namespaces, and invoking `bwrap` was refused by the
  sandbox's own permission layer. Every in-view behavioural property --
  `--remount-ro /`, the `.git` masking as an actually empty unwritable file,
  the `/tmp` size cap, `/tmp/s` coexistence, the PID-namespace reaping, N8 --
  is therefore assessed from the generated argv and from the tests' own text,
  never from observed in-view behaviour. Probes P1 to P9 close this.
* *The test suite itself.* `pytest` and `jsonschema` are not installed here
  and there is no network, so I ran no test. The focused review records
  running 146 unit tests with a leftover virtualenv, and the Commission's
  status line records that the Coordinator's task-check passed; I could
  neither reproduce nor contradict either. In particular I cannot confirm that
  the task-check environment had working user namespaces, which is what makes
  the Layer-1 integration cases meaningful rather than failing.
* *Layer 2.* Not attempted and not attemptable here: no credentials, no
  network, and no live provider invocation is authorized for this Hop. Every
  live question -- whether either CLI starts inside the view, whether the
  nested Claude sandbox and its `AF_UNIX` bridge work, which `/etc` entries
  and which authentication path are actually necessary, whether Codex's
  `--output-last-message` write strategy works through the channel, whether
  the channel directory needs to be in Claude's own `allowRead` for it to read
  its settings file -- remains open exactly as the contract says.
* *Whether the five enumerated `/etc` entries are the necessary set.* That is
  an L6 output. The implementation binds all five when present, which is the
  contract's stated assumption, not an observation.
* *The real `claude`/`codex` install layout on the qualification host,* and
  therefore whether preflight check 5 refuses or admits it today.
* *Byte-identity of the direct path by execution.* Traced in full for both
  adapters and covered by the unchanged conformance suites, but not run here;
  the Claude adapter cannot even reach its launch path in this sandbox,
  because creating the short `/tmp` symlink fails on a read-only `/tmp`.
