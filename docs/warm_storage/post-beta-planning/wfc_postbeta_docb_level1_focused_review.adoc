=== 4 `F001` — still open (new material evidence)

The corrected block (`01_operating_pattern.adoc:250-252`) is

[source,shell]
----
while wfc status --repository . | grep -q '^CLASSIFICATION: \(not_launched\|lifecycle_active\|uncertain_launch\|engine_active\)$'; do
  sleep 30
done
----

The inversion removed the unreachable `refused_` branch, which is real
progress, but the chosen in-flight set is not the set of states a Run can
occupy while it is in flight. `not_launched` is not an in-flight value: it is
what `_evaluate` returns when an `authorized` record exists, no launch marker
exists and the ownership lock is free
(`src/workflow_coordinator/frontdoor/lifecycle.py:686-690`) — i.e. exactly the
state a checkout is left in after any refusal between authorization and launch,
because those refusals release the lock and re-raise
(`:795-797`, `:321-353`, `:390-412`, `:544`).

*Reproduced* (disposable consumer repository built the way
`tests/unit/test_lifecycle_controller.py` builds one, `XDG_STATE_HOME`
redirected into the scratch directory, the real `frontdoor.lifecycle` driven to
a refusal, then the real `wfc status` CLI path, then the chapter's own grep
pattern applied to its output):

* unresolvable provider binary (`--executable claude` with no `claude` on
  `PATH` — the very flag this correction adds): `RUN refusal classification:
  refused_prelaunch | provider executable is not resolvable on PATH: claude`,
  then `CLASSIFICATION: not_launched` / `MESSAGE: authorized; launch not yet
  reached`, and the documented pattern *matches* → the loop sleeps forever.
* dirty worktree: `RUN refusal classification: refused_prelaunch | repository
  worktree is not clean at the authorized baseline`, then the same
  `not_launched` status and the same non-terminating match.

So the failure mode `F001` named ("sleeps forever on the most likely
first-attempt outcomes — dirty tree, failed baseline probe, unresolvable
provider binary") is *not* fixed; it moved from the enumerated-terminal side to
the enumerated-in-flight side. A reader who copies the block sees the refusal
only in `run.log` (`wfc run` prints `wfc run: <reason>` on stderr and no
`CLASSIFICATION:` line on a refusal, `lifecycle.py:1041-1044`), never in the
monitor.

*Second, newly measured behaviour of the same two lines.* On a fresh worktree
nothing is journaled yet, so `wfc status` returns `no_lifecycle`
(`lifecycle.py:682-684`), which the inverted condition treats as terminal. The
loop's first poll runs immediately after the `nohup … &` line, and the status
process does strictly less work than `wfc run` does before journaling
`authorized` (same imports, then one journal read versus config read, two full
commission compilations with both digests, and three fsynced writes,
`:278-309`). Measured by spawning both as separate interpreter processes in the
documented order: the first `wfc status` finished *0.18 s* after the run was
spawned and printed `CLASSIFICATION: no_lifecycle` / `MESSAGE: no lifecycle
recorded for this checkout`; the documented pattern did *not* match, i.e. the
loop exits on its first iteration and the following `wfc status` is read as the
Run's outcome while the Run is in fact starting normally. (Repeated twice, same
result; the probe's own run later reached authorization and the pre-launch
probe before failing to launch for an agent-local reason — no installed `wfc`
console script in this shell, `lifecycle.py:94` — which does not affect the
measured first-poll window.) The pre-correction `until` loop did not have this
behaviour; `no_lifecycle` is also the *permanent* state after a refusal that
happens before authorization (`refused_unauthorized`, `refused_drift`), so the
two values cannot be separated by classification alone.

*Feasible remedy, no new mechanism.* The attempt's owner is the `wfc run`
process itself: it waits for the engine and then prints the classification or
the refusal reason. Waiting on that process instead of enumerating
classification values terminates on every outcome, needs no maintenance when a
classification is added, and cannot exit early — for example capture `$!` after
the `nohup … &` line and `wait` for it, then read `wfc status` once; where the
monitoring shell is not the launching shell (the normal Level-1 case), key the
poll on the launched process or on `run.log` having received its final
`CLASSIFICATION:`/`wfc run:` line rather than on the classification
enumeration. Any variant is acceptable that (a) terminates for every refusal
and (b) does not treat the pre-authorization window as terminal; this review
prescribes no particular shell idiom. `02_worked_sequence.adoc:123` inherits
whatever `<<level1-loop>>` states ("launch and wait exactly as in Commission
1") and needs no separate change.

For the record: `LEVEL1_PRACTICE_FACTS.txt:18-19` does describe the practice as
waiting "until the classification is no longer
lifecycle_active/engine_active/not_launched". That is the Operator's account of
practice; the Commission requires every command claim to be verified against
the implementation, and the implementation behaves as measured above. This is
an observation about the source, not a conflict that needs escalation: the
chapter is free to describe the practice and still print a loop that
terminates.
