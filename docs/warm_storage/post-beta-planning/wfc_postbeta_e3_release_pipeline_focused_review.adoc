=== 2. F001 -- resolved

F001 held that the `release` job gave `gh` no way to resolve the repository to
act on: the job has no `actions/checkout`, the command carried no `--repo`, and
the step's `env:` set only `GH_TOKEN`, so `gh release create` would exit on
"could not determine base repository" -- deterministically, as the pipeline's
terminal step, after the irreversible PyPI publication that `needs:
publish-pypi` guarantees has already happened.

The remedy applied is exactly the minimal form the Finding named, and it adds
no mechanism, no step, no permission and no dependency on a checkout:

[source,yaml]
----
      - name: Create GitHub Release
        env:
          GH_TOKEN: ${{ github.token }}
          GH_REPO: ${{ github.repository }}
----

Why that closes the Finding, re-derived here rather than taken from the
Worker's summary or from the earlier pass:

* *`GH_REPO` is the variable `gh` reads for repository selection.* I
  re-confirmed this against the published `gh help environment` manual in this
  pass: `GH_REPO` is documented as specifying "the GitHub repository in the
  `[HOST/]OWNER/REPO` format for commands that otherwise operate on a local
  repository" -- which is precisely this job's situation. `GITHUB_REPOSITORY`,
  which Actions does set and which the step's `--notes` value interpolates
  through the shell, is still not a variable `gh` reads, so the pre-correction
  job really had none of `gh`'s three resolution sources available.
* *The value has the accepted shape.* The `github.repository` context expands
  to `OWNER/REPO`. The host prefix is optional and absent, so `gh` falls back
  to its default host `github.com`, which is this project's host; no `GH_HOST`
  is needed (see observation 9 for the Enterprise case, which does not arise
  here).
* *Authentication is unchanged and still run-scoped.* `GH_TOKEN` remains
  `+${{ github.token }}+`, the ephemeral Actions token, documented as the
  variable `gh` uses for `github.com`. The job keeps `permissions: contents:
  write` and nothing was broadened.
* *The attachment contract is untouched.* The command still passes
  `dist/*.whl dist/*.tar.gz` -- exactly the two artifact files -- from the
  single downloaded `release-dist` artifact, and the job still contains no
  build step.
* *No injection surface was added.* `github.repository` is repository
  metadata, not attacker-controllable event content, and it is passed through
  an `env:` entry rather than interpolated into the `run:` body. After the
  correction the file still has zero `+${{ }}+` expressions inside any `run:`
  script.

Asserted mechanically at this HEAD (PyYAML parse of the workflow): the
`release` job has exactly one `gh release create` step; that step's `env:` is
exactly `{GH_TOKEN: ${{ github.token }}, GH_REPO: ${{ github.repository }}}`;
the job still has no checkout step, exactly one `download-artifact`, no build,
`needs: publish-pypi`, the tag-only `if`, no `environment`, and
`permissions: {contents: write}`.

*Execution limit, stated plainly:* `gh` is not installed in this sandbox
(`command -v gh` produces nothing), so I did not execute
`gh release create`. The resolution of F001 rests on the documented behaviour
of the variable the Finding itself identified as the remedy, plus the
mechanically asserted structure of the corrected step. The first hosted
tag-push run is the trusted evidence that the Release is actually created, and
nothing in this pass claims such a run happened.

=== 4. Non-blocking observations

Observations 1-7 are carried unchanged from the H002 broad review and remain
non-blocking; 8 and 9 are new in this pass. None blocks acceptance and none
asks for new mechanism.

. Every ordinary `main` push shows `check` red until the release notes are
  frozen, because `make release-check` runs on both triggers as the plan and
  task require. Correct in the release context, noise outside it; narrowing G1
  is the maintainer's call. Flagged, not waived.
. `GIT_CONFIG_NOSYSTEM=1` suppresses `/etc/gitconfig` only; a git-lfs filter
  in the runner user's `~/.gitconfig` would survive it. That is open unknown
  (c); the first hosted run should settle it (for example with `git config
  --show-origin --get-regexp '^filter\.'`), and row (c) of the hosted-run
  record is where the answer belongs.
. The Asciidoctor install is an unpinned `apt-get install -y asciidoctor`, is
  needed because the hosted image does not ship it, and is the one `check`
  step the chapter's bullet list omits.
. G5's nine-file list omits `docs/release_notes/release_notes.adoc`, which C4
  makes release-blocking content; the chapter's own G5 wording ("the assembled
  books") makes the omission defensible.
. G1 runs last in `check` rather than first, so a one-line preflight refusal
  costs a full red cycle. Ordering only.
. `python -m build` builds from the working checkout after an editable install
  and a suite run, not from a Git export; `dist-audit` and the C3 smoke bound
  the consequence.
. The chapter's partial-failure paragraph says re-running `release` alone
  "only reads the already-published tag and artifacts". With F001 fixed this
  sentence is now the one slightly optimistic line in the runbook:
  `gh release create` writes, and a re-run after a partially succeeded create
  fails on an existing release. A `--clobber`-style retry note, or one word in
  the chapter, would settle it; it changes no gate and I do not require it.
. `gh release create` depends on `gh` being present in the `ubuntu-24.04`
  runner image (the chapter says "preinstalled"). That is a runner-image fact
  I cannot verify offline, and it is of the same class as MD-5's unknowns
  (a)-(d); the first hosted tag run proves it. The alternative -- installing
  `gh` in the job -- would be mechanism against an unmeasured failure, so I do
  not propose it.
. `GH_REPO` carries no host prefix, so `gh` uses its default host. That is
  correct for this project and would only need `GH_HOST` (or a
  `HOST/OWNER/REPO` value) if the pipeline ever ran against a GitHub
  Enterprise host, which the contract does not contemplate.
