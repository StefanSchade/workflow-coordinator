=== 1. The mechanism, re-derived and made deterministic

The Worker's account is correct, and it is sharper than "racy stat luck": the
threshold is a *whole second*.

`_isolated_index_copy` (`src/workflow_coordinator/git_facts.py:899-920`) hands
`git status` a throwaway copy of the live index
(`:1015`, `:1046`). Git's racy-clean defence decides whether a cache entry's
stat may be trusted by comparing the entry's cached mtime with the *index file's
own* mtime; when the entry is racily clean Git re-reads the content instead of
believing the stat. A copy stamped with a fresh "now" mtime presents an index
file that looks newer than its own entries, so the defence switches off and a
same-size edit made in the same second as the staging commit is believed clean.

Forcing the copy's mtime instead of waiting for luck makes this deterministic.
With `scope/a.txt` committed as `v1\n` and immediately overwritten with `v2\n`,
reading `git status --porcelain=v1` through three indexes in the same trial:

[cols="3,1"]
|===
|Index the read goes through |False "clean" reads

|copy with mtime = index mtime + 2 s |*30 / 30*
|copy with mtime = index mtime (`copy2`, as committed) |0 / 30
|the live index itself |0 / 30
|===

The threshold is second-granular, not nanosecond-granular (12 trials per row,
same trial, same repository):

[cols="3,1"]
|===
|Copy mtime offset from the live index's mtime |False "clean" reads

|+0 ns |0 / 12
|+1 µs |0 / 12
|+1 ms |1 / 12
|+100 ms |4 / 12
|+999 ms |12 / 12
|+1 s |12 / 12
|+2 s |12 / 12
|===

The intermediate rows are the boundary being crossed by chance: the protection
fails exactly when the copy's mtime falls in a later whole second than the index
write. That predicts the field failure rate directly — the probability is the
elapsed time between the index write and the copy, divided by one second. I
measured that gap inside `preserve_candidate`: median *13.6 ms* over 25 trials
(mean 13.5, min 12.5, max 14.2), so ≈1.4 % for the first call and more for a
later call in the same scenario. That is the right order for every observation
in this lifecycle: the Operator's 1-of-6 single-file runs and 2-of-40 standalone
reproduction, my own 15/500 (3.0 %) for the two-call body below, and 8/300
(2.7 %) for a sibling site whose copy happens later in its own flow. The
hypothesis in the task is confirmed, with the granularity and the rate now
explained rather than assumed.

=== 2. Defect or racy fixture: (b), confirmed end to end

The Worker's answer — `preserve_candidate` itself can mis-report a real,
unpreserved change as `not_needed` — is correct, and this is not an artifact of
the test's two rapid calls. Running the exact body of
`test_repeat_capture_is_idempotent_no_second_ref`
(`tests/unit/test_candidate_preservation.py:156-168`) with the module's
`shutil.copy2` replaced by the pre-fix `shutil.copyfile`:

* 15 failures in 500 runs. Of the first five, four were
  `('preserved', 'not_needed')` and one was `('not_needed', 'not_needed')` — the
  *first* call already reporting no candidate for a file it had never preserved.
* Forcing the copy's mtime one second later makes the whole flow fail 10/10,
  with `('not_needed', 'not_needed')` every time: a single ordinary call, no
  repetition, no second observer.

So the P3 plan's Acceptance question is answered in the affirmative: the false
`not_needed` is a property of one `preserve_candidate` call over a same-size
same-second edit, not of the test's narrow pattern. A candidate worth preserving
is reported absent — the safety-relevant outcome the task names. With the
committed fix the same body ran *500 runs, 0 failures*.

=== 3. The fix: minimal, and it removes the cause

`shutil.copyfile` → `shutil.copy2` at `git_facts.py:919`. The copy now carries
the live index's own mtime, so the copy is exactly as racy-safe as the index it
stands in for and Git's own protection does the work; nothing in WFC re-implements
or second-guesses it. That is the smallest change that removes the cause, and I
could not find a materially simpler one: no new state, no retry, no sleep, no
tolerance window, no added refusal. I checked the alternatives an adversarial
reader would propose and they are all worse — an explicit `os.utime` after
`copyfile` is the same effect with two statements instead of one; `copy2` on the
real index is not an option since the whole point of the copy is that reads never
touch the registered index; forcing `git status --no-optional-locks` to re-hash
would be a performance and semantics change for every call.

Behaviour preservation, checked rather than assumed:

* No refusal, limit, error path or return shape was touched. The range's two
  deleted lines are exactly the replaced `shutil.copyfile` call and the
  one-line docstring that the longer docstring replaces; no test line was
  deleted or edited, and every `PreservationRefused` and every existing
  assertion is byte-identical.
* No retry, sleep, `skip`, `xfail` or marker was added anywhere in the range.
* `copy2` also copies the source's mode, which widens the throwaway file from
  `mkstemp`'s `0600` to the index's `0664`. I checked whether that matters for
  this function and it does not: the sibling private index in
  `_build_candidate_tree` is written by Git itself through a lock-and-rename and
  already ends up `0664` on this host, so `0600` was never a property this
  function maintained, and the copy carries only index metadata that is already
  readable to anyone who can read the checkout. Recorded in <<e0-o3,O3>>, no
  change requested.
* `copy2` follows symlinks exactly as `copyfile` did, and the worktree/`--git-path`
  resolution above it is unchanged.

=== 4. The new regression test

`test_isolated_index_copy_preserves_live_index_mtime_not_fresh_copy_time`
(`tests/unit/test_candidate_preservation.py:171-192`) asserts
`copied.stat().st_mtime_ns == live_index.stat().st_mtime_ns` and unlinks the copy
in a `finally`. Run as a body against the committed source and against the
pre-fix copy mechanism:

* as committed: *200 runs, 0 failures*
* with `copyfile` restored: *50 runs, 50 failures*

It fails before and passes after, deterministically in both directions, with no
timing dependence: it is an exact attribute equality, not a race the test hopes
to win. It is also the right guard for the future — if the copy mechanism ever
regresses, this test fails outright instead of making
`test_repeat_capture_is_idempotent_no_second_ref` flaky again
(see <<e0-o2,O2>>).
