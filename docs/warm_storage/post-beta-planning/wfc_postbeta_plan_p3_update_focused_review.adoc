=== 5. New blocking Finding — `G8`’s enforcing setting is never verified before the tag

*Invariant.* The plan states precisely what the workflow enforces by itself and
what depends on a repository setting only the maintainer can make, "and
therefore must be verified before the first tag", so that a bare tag push cannot
unintentionally bypass `G8` (task, PIPELINE REQUIREMENTS, the explicit-approval
paragraph; Acceptance: the explicit human approval gate `G8` in front of PyPI).

*Reproduced.* The plan divides the halves correctly — `G8` (464–467): "the
`pypi` environment's required-reviewer rule mechanically enforces the wait; the
rule itself is a repository setting only the maintainer can create (`ES-2`,
`ES-5`) — never inferred from a green job"; `E3` (343–346) declares
`environment: pypi` on `publish-pypi`. But every verification of that rule
happens *after* the irreversible step is entered:

* `ES-2` (207–211) creates the Environments and verifies with the sentence
  "publish-pypi visibly pauses for approval" — observable only during a tag run, i.e. after
  the tag is pushed and after `publish-testpypi` has spent the TestPyPI version.
* `ES-4` (216–218) pushes the tag and verifies only that tag-mode `check` is
  green.
* The release sequence (411–425) makes step 3 (tag) conditional on `Q1` only;
  no step and no gate requires the `pypi` rule to exist first.
* The string "before the first tag" appears nowhere in the plan; a grep for
  `before the first tag|before tagging|confirm` returns only `ES-1`’s
  trusted-publisher timing, the project-name check and `Q1`’s maintainer
  confirmation.

*Why it blocks.* `G8` is the only safeguard between a tag push and an
irreversible PyPI publication, and the plan's own rule is that approval is never
inferred from a green job. If the `pypi` Environment is absent, misnamed, or
created without the reviewer rule when the tag is pushed, `publish-pypi` runs
unattended and `0.1.0b1` is spent — the failure the task asked to foreclose by
verifying the setting *before* the tag. The same post-hoc verification style is
appropriate for `ES-1`, where a missing trusted publisher merely refuses the
upload; it is not appropriate here, where the undetected state publishes. (I did
not verify how GitHub treats a job that names an undefined environment; the gap
holds either way, because nothing in the plan checks.)

*Feasible correction (small).* Give `ES-2` a pre-tag verification the maintainer
can perform in the settings UI — Environment `pypi` exists, lists the named
required reviewer, and is the exact name `E3`’s job uses — and report that
confirmation back; make it an explicit precondition of sequence step 3 and of
`ES-4`, so the tag is not pushed until the confirmation exists. If the plan
wants to say why an absent rule would not announce itself, mark that mechanism
as unverified. One sentence in `ES-2` and a clause in step 3 cover it; no new
mechanism, register or gate is needed. While there, the `E3` bullet calls the
required-reviewers rule the enforceable half of `G8`, where `G8` calls the
workflow’s declaration the enforceable half and the rule the maintainer’s
setting — the two sentences should name the same halves.
