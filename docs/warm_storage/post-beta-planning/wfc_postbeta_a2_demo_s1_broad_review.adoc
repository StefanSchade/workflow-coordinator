=== Non-blocking observations

O-1 -- a missing parent directory produces a traceback, not a message::
`make_workspace.py <path>/ws` where `<path>` does not exist passes the
preflight (the target indeed "does not exist") and then dies in
`create_workspace`'s `workspace.mkdir(exist_ok=True)` with an uncaught
`FileNotFoundError` traceback. Nothing is created and the exit code is 1,
which is inside the FTR's code set, so no stated criterion is violated and
the kit stays safe; but the FTR's style for every other refusal is one line,
and a reader typing `make_workspace.py ~/demos/wfc-demo` before creating
`~/demos` sees a stack trace naming kit internals. The smaller of the two
one-line fixes is `mkdir(parents=True, exist_ok=True)`; the stricter one is
a preflight line requiring an existing parent. I am not asking for either in
S1 -- recording it so the choice is deliberate.

O-2 -- the new tests join the documented pytest-scratch precondition::
Every new test builds its workspace under `tmp_path`, and the kit refuses
any target inside a Git work tree. With no `TMPDIR`/`TMP`/`TEMP` set,
`tests/conftest.py` puts the pytest base at the checkout's own
`tmp/pytest`, i.e. *inside* this repository's work tree, and then the AC-1,
AC-3 and AC-8 tests fail loudly with the refusal (return code 2), not
silently. This is the class the Developer Guide already documents in
`ch01_development.adoc`'s "Pytest scratch" section, with
`test_wfc_doc_catalog.py::test_git_failure_is_reported_not_guessed` as the
named precedent and "prefer a `TMPDIR` outside the checkout entirely" as the
standing advice; the hosted `check` job sets `TMPDIR: ${runner.temp}`, so
the required suite is unaffected there. Nothing in the candidate is wrong,
and the worker had no authority over that chapter; the useful follow-up,
when a slice next touches the Developer Guide, is one sentence adding this
file to that section's named cases.

O-3 -- two refusal tests accept any reason for the refusal::
`test_preflight_refuses_a_non_empty_target` and
`test_preflight_refuses_a_target_inside_a_git_work_tree` assert only
`returncode == 2` and the absence of side effects. Under O-2's
misconfiguration the first would pass for the wrong reason. Asserting a
distinctive substring of each diagnostic (`is not empty`, `inside a Git work
tree`) costs one line each and makes the three AC-2 cases genuinely
distinct. My own harness asserted the messages and all three are distinct
today.

O-4 -- the boundary test pins the module list rather than iterating it::
`test_kit_modules_import_only_the_standard_library` begins with
`assert [path.name for path in modules] == ["make_workspace.py"]`, which
duplicates `test_slice_s2_files_do_not_exist_yet` and must be edited in S2
rather than simply covering the new modules. The task asked for "an AST
check that every kit module present imports only the standard library";
globbing and iterating, with the S1/S2 boundary left to the one test that
owns it, would be the smaller shape. No current defect, so nothing is
blocked.

O-5 -- AC-9's new assertions overlap the existing audit::
`dist_audit.audit(...) == []`, already asserted two lines above for both
archives, fails on any `examples/` entry by itself; the new `zipfile`/
`tarfile` checks restate that for AC-9 specifically. AC-9 asks for exactly
this check and the FTR itself notes the audit already covers it, so the
redundancy is the criterion's, not the candidate's. If it ever has to pay
for itself, the substring form `'examples/' in name` is also broader than
the criterion's "no path under `examples/`" -- it would also catch a
package path containing that word, which is the safe direction.

O-6 -- the FTR's own status line still says "not implemented"::
`FTR-WFC-CONSUMER-DEMO-WORKSPACE.adoc` carries `Status:: proposed /
backlog; ... not implemented` and `Not authorized here:: Any
implementation, Commission or Run`. S1 is now implemented under an accepted

=== Maintainability and simplicity

The candidate is proportionate to the slice and I found nothing to give up.
`make_workspace.py` is 266 lines of flat, sequential procedure: two
exception types that correspond exactly to the FTR's two non-zero return
codes, one small function per step, no state beyond the workspace path and
the version string, no abstraction over Git, no configuration file, no
template engine beyond a single `str.replace` of one token. The requests are
data, not code. The alternative shapes I considered are each worse here: a
copy of the Consumer Config instead of calling `wfc init` would duplicate a
format the product owns (and the FTR rules it out); a cleanup-on-failure
path would contradict SI-2 and the FTR's explicit "no automatic clean-up";
and a shared helper module between the kit and `tests/fixtures/bp9/` would
break the standard-library-only boundary both the FTR and the task fix. The
one place I looked hard for an unnecessary safeguard --
`shutil.copytree(..., dirs_exist_ok=True)`, which would overwrite if the
target were not empty -- turns out to carry no risk, because the preflight
has already established emptiness, and tightening it would add a second
guard for a state that cannot occur. The two kit tests that touch the S1/S2
boundary (O-4) are the only duplicated responsibility I found, and it is one
line.
