=== Extended: the real version-bearing surface

About 37 sites in eleven files must change at a version bump, against the four
sites in four files the basis lists. Full enumeration, with what enforces each,
is in link:../../backlog/FTR-WFC-RELEASE-PREPARATION.adoc#problem[the R1
record]. Two findings there are new and carry the economic case for W2:

. *`pyproject.toml` and `implementation_identity.VERSION` can disagree while
  the whole required suite stays green.* *[I]* No test imports both: the only
  consumers of `implementation_identity.VERSION` are
  `src/workflow_coordinator/frontdoor/skill.py`,
  `tests/architecture/test_package_boundaries.py`,
  `tests/unit/test_agent_skill_content.py` and
  `tests/unit/test_frontdoor_skill.py`, and no test module reads
  `pyproject.toml` with `tomllib` except `test_wfc_test_inputs.py` (for an
  unrelated purpose). The equality is asserted only in CI, in
  `release.yml:122` with `:139-140` and again at `:230` with `:246`. A
  half-done bump is therefore invisible locally and surfaces as a red hosted
  job.
. *`README.md` can keep links to the previous tag and `make release-check`
  passes.* *[I]* `check_readme_links` (`wfc_release_check.py:126-137`) rejects
  only targets that do not start with `http://`, `https://`, `#` or
  `mailto:`. No check compares the `blob/v<x>/` segment with the released
  version. The Agent Skill files have exactly that check
  (`test_agent_skill_content.py:237`); `README.md`, with ten such URLs, does
  not.

Both gaps are closed by W2 as adopted. Neither was stated by the basis.

[[design-decisions]]
== Design decisions of this plan, with rejected alternatives

D-A -- Four slices, not ten:: W1-W10 group by *where the recurring cost
sits*: the preparation commit (W2), the release chapter (W1 docs, W4, W8), the
pipeline's own robustness (W1 workflow, W4, W5, and W7 only as a conditional
one-line edit) and the placement of the consumer smoke (W3, W10). _Rejected:_ one slice per recommendation -- six of
the ten are one-to-three-line changes and would spend a Run each on
commissioning overhead. _Also rejected:_ one single release-streamlining
slice -- it would merge a documentation relocation, a new writing tool and a
change to the publication chain into one Run and one review, which is exactly
the merged-risk the commissioning brief warns against.

D-B -- Chapter 4 belongs to exactly one slice:: Putting the chapter in R2 only,
and having R2 state R1's and R3's work *as planned*, is what makes two
parallel lanes possible at all; otherwise all three slices serialise on one
file. _Precedent, not invention:_ this is how E1 specified E2 and E3
(`_open.adoc`'s E1 card: "planned tooling is named as planned, not as
existing").
_Rejected:_ letting each slice edit its own chapter section -- the file is the
unit of conflict, not the section.

D-C -- R2 first:: It is the only slice that corrects a defect with an
operational consequence and no behaviour change at all, and it unblocks the
other two. _Rejected:_ R1 first (the plan's own economics favour it, but it
would then own the chapter and re-serialise everything).

D-D -- R4 stays conditional:: Implementing either variant before D1 would
either reverse a recorded decision without authority or foreclose the
maintainer's choice. _Rejected:_ writing only Variant B as "the safe one" --
it pre-decides D1 by making A more expensive to choose later.

D-E -- Two economic rejections are stated as rejections:: W6 and W9 are the
two recommendations whose own recurring cost plausibly exceeds the cost they
remove. Saying so, with the arithmetic, is more useful than adopting them and
quietly never doing them. _Rejected:_ "defer with no reason", which is how a
backlog accumulates machinery.

D-F -- The scope-ceiling problem is named, not worked around:: R3 and R4 touch
`.github/workflows/release.yml`, outside `.wfc/config.yaml`'s
`work_item_scope_ceiling` (`src`, `tests`, `scripts`, `docs`, `README.md`,
`pyproject.toml`, `Makefile`, `examples/consumer-demo`). _Rejected:_ moving
the logic into a script under `scripts/` to stay inside the ceiling -- it
would put release-pipeline control flow in a second place to avoid a
configuration entry the maintainer has granted before and removed again
(`_open.adoc`'s E3 card).
