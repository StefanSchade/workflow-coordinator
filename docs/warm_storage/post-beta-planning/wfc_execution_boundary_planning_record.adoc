[[summary]]
== What this record establishes

. The Bubblewrap primitive is still wired into nothing, and in its present
  form it cannot even validate the checkout WFC self-development actually runs
  in, because that checkout is a linked Git worktree whose `.git` is a file
  *[O]*.
. The integration seam is narrow and already provider-neutral in shape: one
  `subprocess.Popen` call per adapter, plus the Coordinator-owned directory
  each adapter reads from or writes to *[I]* -- which, as H006 established, is
  the Run state directory itself and therefore has to be split before it can
  be mounted (<<d4>>).
. An effective boundary needs five things the present primitive does not have:
  a worktree-aware `.git` view, a narrow bidirectional channel to the
  Coordinator -- separated from the Run state directory, not the Run state
  directory itself -- a narrowly bound path for the provider's own
  authentication together with a small enumerated `/etc` set, a `/proc` and
  process model the provider runtimes require, and process/timeout/environment
  control that today lives in the adapters *[I]*, *[D]*. The third item widens
  the one designated bind-source exception the 2026-11-08 authorization drew,
  which is why <<m7,M7>> exists.
. The boundary also needs a *reachable provider*: the view mounts only `/usr`
  and the four `/bin`-family links, and on this host neither provider CLI
  resolves there *[O]*, so the whole qualification plan has a precondition
  that must be stated and satisfied rather than discovered (<<d9>>,
  <<m8,M8>>).
. Nothing in the present dispatch path can carry a view, a grant set or a
  boundary mode to the place that starts the provider: the port has no such
  field and the adapters are constructed with four values, none of them a
  grant *[I]*. The surface that carries them is therefore a decision this
  record has to take, and it takes it on the construction axis rather than on
  the provider-neutral port (<<d10>>), which also settles who creates and
  removes a not-yet-existing authorized target (<<d5>>).
. Provider permissiveness inside the boundary must be bound to the boundary
  actually being in force for that invocation, because the provider's own
  `failIfUnavailable: true` turns a failed nested sandbox into a refusal
  rather than a silent downgrade *[I]*, *[D]*.
. Slice A can state integrity (write prevention) honestly. It cannot state
  confidentiality or phase isolation honestly, because the scope data it would
  enforce is Commission-wide for worker phases *[I]*, because a reviewer phase
  can only be confined to the directory holding its not-yet-existing artifact
  rather than to the artifact itself (<<d5>>), and because hiding content from
  an agent requires solving the Git object database, which Slice A deliberately
  does not do.

=== What `build_argv()` actually generates

Observed verbatim for a worker-shaped grant (one writable repository subpath,
private scratch, external scratch) *[O]*:

----
bwrap --die-with-parent --dev /dev --ro-bind /usr /usr
  --symlink usr/bin /bin --symlink usr/sbin /sbin
  --symlink usr/lib /lib --symlink usr/lib64 /lib64
  --ro-bind <repository> /repo --tmpfs /repo/.git --remount-ro /repo/.git
  --bind <repository>/docs /repo/docs
  --tmpfs /tmp
  --bind <external scratch> /tmp/s
  --chdir /repo -- <command>
----

Absent from the generated argv, each verified by substring probe *[O]*:
`--proc`, any `/etc` mount, `--unshare-pid`, `--unshare-net`, `--unshare-all`,
`--clearenv`, `--setenv`, `--new-session`.

Consequences that follow directly:

* No `/proc`. The nested qualification found that this alone stops the
  Bun-based Claude CLI before it contacts anything, and that
  `--unshare-pid --proc /proc` in a throwaway harness made `claude --version`
  succeed *[D]*
  (link:../claude-adapter-and-sandbox/workflow_coordinator_nested_claude_live_qualification_2026-11-08.adoc[live
  qualification], Phase B).
* No `/etc`. `/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`,
  `/etc/passwd` and `/etc/ssl/certs` all exist on this host *[O]* and none of
  them is in the view, so name resolution, TLS trust and user lookup are
  unavailable to the child.
* No network namespace of its own: the child shares the host's network
  namespace. The primitive therefore makes no network statement at all, in
  either direction.
* No PID namespace and no `--new-session`: a child that leaves the process
  group is not contained by this primitive, and `run()` sets no timeout.
* No environment control: `run()` is `subprocess.run(build_argv(...),
  capture_output=True, check=False)` at `execution_boundary.py:185-187`, so
  the child inherits the caller's whole environment, including `HOME` and any
  token-bearing variable.
* The provider binary must be resolvable inside the view. On this host `PATH`
  contains `/home/stefan/.nvm/versions/node/v22.23.2/bin` and
  `/home/stefan/.local/bin` *[O]*, neither of which is mounted; only `/usr`
  and the four `/bin`-family symlinks are.

=== Commission scope versus phase `authorized_scope`

`commissioning.render_commission` resolves a program phase's scope slot:
`scope_slot == "S"` becomes `list(request.scope)`, the *complete* Commission
Intent scope, and any other slot becomes exactly
`request.durable_artifacts[artifact_key]`
(`commissioning.py:343-350`) *[I]*. In `robust@v1` the two worker phases
`implement` and `correct` carry `scope: S`, and the two reviewer phases carry
`scope: A` with their own `artifact_key`
(`governance/workflow-programs/robust/v1.yaml`) *[I]*.

This is exactly what
link:../../backlog/FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[the phase
write-scope record] already describes *[D]*, and it is directly observable in
this Commission: `.wfc/governance/wfc-exec-boundary-ftr-001/work-item.yaml`
has `scope: [docs/backlog, docs/warm_storage/post-beta-planning]` and names
both reviewer artifacts inside the second entry *[I]*.

Consequence for a boundary: a worker phase's writable grant, derived
faithfully from `phase.authorized_scope`, is the whole Commission scope. A
boundary built on that data prevents writes *outside the Commission*. It does
not separate worker-owned paths from reviewer-artifact paths, and must not
claim to.

`a1_path_shape` (`serialization.py:354-369`) admits any canonical relative
non-root path without globs or `..`, and nothing deduplicates nested entries.
`_admit_a1` (`operator.py:160-224`) checks A1 path shape, governance-path
overlap in both directions, the WorkItem scope ceiling and the Hop limits; it
does not normalize or deduplicate nested scope entries *[I]*. A scope list
containing both `docs` and `docs/backlog` is therefore
admissible and would produce overlapping mount destinations, which
`validate()` refuses (`execution_boundary.py:114-115`). Normalization is
Slice A's problem, not an existing bug.

[[experiments]]
== Experiments performed in this Hop

All experiments ran read-only against this checkout or inside the session
scratch directory. The helper script lived in the repository's gitignored
`/tmp/` scratch space and was removed afterwards; `git status --short -uall`
showed no change attributable to it.

E1 -- this checkout is a linked worktree::
`.git` is a regular file of 125 bytes containing
`gitdir: .../workflow-coordinator/.git/worktrees/workflow-coordinator-exec-boundary-ftr-b`;
`git rev-parse` reports a `--git-dir` and a `--git-common-dir` that both lie
outside the checkout. `validate()` refuses it: "repository must contain a real
.git directory".

E2 -- synthetic repository with a real `git worktree add`::
A fresh `git init` repository validates successfully. A linked worktree created
from it with `git worktree add` is refused with the same message, and its
`.git` file points at `<main>/.git/worktrees/linked` while its common-dir is
`<main>/.git`. Both are outside the linked checkout.

E3 -- a not-yet-existing authorized target cannot be bound::
A writable `Mount` whose source is `<repo>/docs/new` (absent) is refused with
"source does not exist". Binding the existing parent `<repo>/docs` writable
succeeds and yields destinations `['/repo/docs', '/tmp']`.

E4 -- the remaining refusals reproduced::
A writable bind of `<repo>/.git` is refused ("bind must map an existing
non-`.git` repository subpath to its matching destination"); a bind source
outside the repository is refused ("bind sources must be inside repository");
a destination that does not match the source's repository-relative path is
refused with the same message as the `.git` case; omitting the private scratch
mount is refused ("exactly one private scratch mount is required").

E5 -- generated argv::
Recorded verbatim in <<current-state>>, including the eight substring probes
for absent flags.

E6 -- host facts::
`bwrap` is `/usr/bin/bwrap`, version 0.11.0. `/etc/ssl/certs`,
`/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf` and `/etc/passwd`
exist. `PATH` contains two `$HOME`-local entries that the generated view does
not mount.

E7 -- what resolves at a view-visible path (observed at H006)::
A plain `ls` of the paths the generated view would contain shows
`/usr/bin/bwrap`, `/usr/bin/node`, `/usr/bin/env`, `/usr/bin/sh` (a symlink to
`dash`) and `/usr/bin/python3` (a symlink to `python3.13`) present, and
`/usr/bin/claude`, `/usr/local/bin/claude`, `/usr/bin/codex` and
`/usr/local/bin/codex` *absent*. `PATH` resolves provider tooling through
`$HOME`-local entries that the view does not mount (E6). No provider CLI was
invoked, read or located outside those four fixed paths, and no credential
path was touched: the observation rests on the *absence* of a name at a fixed
path. This is the evidence behind <<d9>> and <<m8,M8>>: with the host in this
state, preflight would refuse every isolated invocation and qualification
layers L1 to L6 could not start.

[[limits]]
== What could not be run, and why

No `bwrap` *sandbox* could be entered in any Hop of this Commission. The agent
executes inside its own Bubblewrap sandbox, in which
`/proc/sys/user/max_user_namespaces` reads `0` and even a minimal
`bwrap --dev /dev --ro-bind /usr /usr --tmpfs /tmp -- /bin/true` exits 1 with
"bwrap: No permissions to create new namespace, likely because the kernel does
not allow non-privileged user namespaces" *[O]*.

Narrowed at H009:: `bwrap` itself does run far enough to report about itself.
`bwrap --version` prints `bubblewrap 0.11.0` *[O]* -- closing the version
question an earlier form of this section left open -- and `bwrap --help`
documents every option the slice relies on, including `--remount-ro DEST`
("does not recursively remount"), `--size BYTES` ("only for `--tmpfs`") and
`--as-pid-1` ("do not install a reaper process with PID=1") *[O]*, which is
the evidence behind <<d11>> and behind N13's reason for forbidding
`--as-pid-1`. What remains impossible is every observation that requires
*being inside* the view.

This is an agent-local environmental limitation, not a product defect: the
same host runs `tests/integration/test_execution_boundary_bwrap.py`
successfully outside the agent sandbox, and the Coordinator's own task-check
executes the required suite there. Three consequences:

. Every claim in this record about `validate()` and `build_argv()` is from
  pure-Python execution or source reading. No claim about observed
  *in-sandbox* filesystem behaviour is made on this Hop's own evidence; those
  come from the existing tests and the two 2026-11-08 records *[D]*.
. The same restriction will apply to the implementation Commission's worker
  Hops. Its `bwrap` qualification therefore has to be carried by the required
  suite under the Coordinator's task-check and by Operator-run live
  qualification, not by agent-side experiments.
. The observation is itself evidence for the nesting problem Slice A must
  decide: an unprivileged user namespace is not always available one level
  down, and Claude's `failIfUnavailable: true` turns that into a refusal.

No provider CLI was invoked or inspected, and the operator's home directory is
not readable in this sandbox apart from two session-specific subpaths. Every
statement about what the installed Claude and Codex binaries *do* is cited
from the existing records *[D]*, never claimed as an observation here. The one
exception, added at H006, is E7: that no `claude` or `codex` name exists at the
four fixed view-visible paths, which `ls` establishes without invoking or
reading anything.

One further observation, relevant to Slice A rather than to this Hop: inside
this agent's sandbox, `git status --short -uall` reports roughly twenty
untracked repository-root paths (`.bashrc`, `.mcp.json`, `.claude/*` and
similar) that do not exist in the checkout at all. Each is a character device
`1, 3` owned by `nobody:nogroup` *[O]* -- the agent sandbox's own `/dev/null`
masks over those paths. The Coordinator, outside that sandbox, sees a clean
tree. An agent's view of Git status can therefore differ from the
Coordinator's, which is one more reason the post-Hop observation is
Coordinator-owned. Slice A's own view does not introduce such masks: it mounts
the real working tree and masks only `.git`, whose absence is both intended
and visible. `git_facts.py:227` already fails closed for special filesystem
objects Git does not report as untracked, which is the right disposition if
such a mask ever appears inside a path WFC observes.

[[decisions]]
== Design decisions, with the alternatives rejected

[[d1]]
=== D1. One provider-neutral launcher seam, not two adapter copies

Decision:: Introduce one launcher entry point that both adapters call instead
of `subprocess.Popen` directly, taking the argv, cwd and environment the
adapter builds plus a Coordinator-computed grant that carries the view (see
<<d10>>), and returning the same process handle semantics. Boundary selection
happens once, in the launcher, from the grant's mode.
Reason:: The seam is already narrow: exactly one `Popen` per adapter, and all
semantic acceptance happens afterwards in `validated_result` and the reducer
*[I]*. The same conclusion was reached independently by
link:../../research/gondolin_execution_boundary_feasibility.adoc[the Gondolin
study] *[D]*, from the opposite direction (a VM backend), which is evidence
that the seam is the right one rather than a Bubblewrap-shaped convenience.
Rejected:: (a) Wrapping inside `execution_boundary.run()` -- it has no
environment, timeout, stdin or process-group handling and would duplicate the
adapters'. (b) A boundary-aware third adapter -- it would fork the permission
and schema logic. (c) A plugin or registry -- `operator._execution_adapter`
deliberately has "no registry or fallback" *[I]*; two launchers selected by a
closed name match the existing style.
Corrected at H009 after a Finding:: An earlier form of this decision described
the launcher as taking "the read and write paths the adapter already knows".
It knows none of them: the port carries no filesystem view, grant set or
boundary mode (`adapter.py:44-69` *[I]*, and the current-state table above
says so), and the adapters are constructed with only `result_directory`,
`model`, `reasoning_effort` and `executable` *[I]*. Where those inputs come
from is now <<d10>>, and the Slice A seam section states the same decision.

[[d2]]
=== D2. Mount the repository at its own absolute path, not at `/repo`

Decision:: The repository view keeps its host-absolute canonical path inside
the boundary. `/repo` remains supported only where an existing caller asks
for it.
Reason:: Both adapters embed the resolved absolute repository path in argv
(`--cd`, `cwd=`) and the Claude settings embed it in `allowRead` and rely on
`blockReadsOutsideWorkingDirectories` *[I]*. Translating paths would mean
rewriting argv, settings, every absolute path in diagnostics, and the
scratch-symlink logic -- and silently diverging the paths an operator sees in
`audit.json` from the paths the provider saw.
Rejected:: Keeping `/repo` and translating. It creates a path-identity problem
at exactly the place where a mistake is a security mistake, and it would make
the Claude settings file describe a filesystem that does not exist inside the
view.
Cost:: `validate()`'s destination rule (`execution_boundary.py:128`) and the
tests that assert `/repo` destinations have to change. This is a deliberate,
reviewable change to the primitive, not an incidental one.

[[d3]]
=== D3. A worktree-aware, metadata-free `.git` view

Decision:: Keep the existing masking idea -- `--tmpfs` plus `--remount-ro`
over the checkout's `.git` -- and extend it to the worktree case, where `.git`
is a file: mask it with an empty read-only placeholder, and mount *neither*
the per-worktree gitdir nor the common-dir (both already known from the
checkout association, `slice4.py:78-84`) *[I]*.
Reason:: An ordinary agent needs no Git capability at all: WFC's Git writes
are Coordinator-owned (`vertical.py:400-408`) and the agent reports a
CommitIntent instead *[I]*. Exposing the object database would also hand the
agent every path the boundary hides, which is the mechanism the maintainer's
confidentiality goal explicitly names.
Open and honest:: What the provider CLIs themselves need from Git inside the
view is *not established*. Both CLIs are known to run Git-shaped tool calls
when a session asks for them, and `--tools` includes `Bash`
(`claude_adapter.py:40`) *[I]*, so Git commands will fail inside the view.
Whether either CLI needs Git for its own startup is *[A]* assumed not, on the
basis that the 2026-11-08 record saw `claude --version` succeed in a view with
no Git at all *[D]*; the live qualification must confirm it and the FTR says so.
Rejected:: (a) Binding the common-dir read-only -- defeats hiding and lets an
agent read any blob. (b) Leaving the real `.git` in place for the main-checkout
case -- the current primitive already refuses that, correctly. (c) A
synthesized minimal gitdir -- new surface, no established need.

[[d4]]
=== D4. The outside-repository sources, classified per category

Decision:: Slice A needs three categories of path outside the repository, and
each is carried by a stated mechanism rather than by a general relaxation of
`validate()`'s `source.relative_to(repository)` check
(`execution_boundary.py:124-127`) *[I]*:
+
--
. *Two further designated, individually validated external mount kinds* beyond
  today's external scratch root -- the *per-invocation provider channel
  directory* (read-only for Claude, read-write for Codex) and the provider's own
  authentication location (read-only). Each is a dedicated named parameter with
  its own checks modelled on the external-scratch rules
  (`execution_boundary.py:139-156`) *[I]*, never an arbitrary host path and
  never a shared external-mounts list. The channel directory is *not* the
  Coordinator's Run state directory: the three provider channel files move into
  a dedicated subdirectory under it, and the channel kind's own check refuses a
  source containing any Coordinator state file name, so that passing
  `run_root` by mistake cannot satisfy it.
. *A narrow, individually enumerated, read-only set of fixed `/etc` entries*
  added to the system view that `build_argv` generates
  (`execution_boundary.py:166-172`) *[I]*, in the same place and form as
  `/usr`. These are not caller-supplied `Mount` values and therefore never
  passed through the fenced rule at all.
. *Nothing else.* The generic rule for undesignated caller-supplied mounts is
  unchanged, and no configuration may add a path kind.
--
+
This corrects the earlier form of this decision twice over, and both earlier
forms are superseded rather than deleted. First (at H003): it said "exactly
one further validated external mount kind" and counted only the result
channel; the authentication path cannot be a generated system-view entry -- it
is provider- and operator-specific, varies per invocation and is a
live-qualification output -- so it must be the validated-kind form, and the
count is therefore three designated kinds rather than two. Second (at H006):
it named the *Coordinator's per-checkout result directory* as the mount, and
its rejected option (b) described the state root above that directory as the
thing being avoided. That premise was false -- the result directory *is* the
Run state directory (see the current-state rows above) -- so the mount is now
the separated per-invocation channel directory, and the rejected options
below are restated accordingly.
Reason:: Claude must read `claude-closed-settings.json`
(`claude_adapter.py:308`) and Codex must write `result-message.json`
(`codex_adapter.py:434`, `:461`) *[I]*; both live under `<run_root>` today and
under the separated channel directory in Slice A, and both are outside the
repository either way. Name resolution, TLS trust and user lookup are
unavailable in today's view, which would break provider authentication: the
generated argv mounts no `/etc` at all *[I]* (E5) while all five candidate
entries exist on the host *[O]* (E6).
And the boundary must expose the provider's own authentication to the provider
process, which is impossible without a path for it *[D]*. Without the result
channel the Codex path cannot work at all.
Rejected:: (a) Moving the channel into the repository -- forbidden by
`_require_external_state_root` (`slice4.py:87-92`) and wrong: it would put
Coordinator-written state inside the agent's write surface. (b) *Mounting the
Run state directory itself, which is what today's `result_directory` is* -- it
holds `run.json`, `checkpoint.json`, the dispatch marker, the execution
evidence and the usage record, all present during dispatch, so a read-only
mount would expose the Run snapshot and every prior Hop's evidence and the
read-write mount the Codex path needs would let the agent rewrite the dispatch
marker and the very evidence file that records whether it was isolated.
(b2) Binding the three channel files *individually* at their present paths --
equally narrow in what it exposes, and it would avoid the relocation, but a
file bind mount cannot be replaced by `rename()` (`EBUSY`), and whether the
Codex CLI writes `--output-last-message` in place or renames over it is an
unverified property of a third-party CLI; the directory-level mount does not
depend on it. (c) Passing the result on stdout for Codex too -- that is a
provider-transport change, not a boundary change. (d) A single generic
"external mounts" list with an allowlist -- it is exactly the general loosening
the 2026-11-08 authorization forbids, and it makes every future addition
invisible. (e) `--ro-bind /etc /etc` -- wholesale, and explicitly excluded.
(f) Treating the `/etc` entries as validated mount kinds -- possible, but it
would route constants through a caller-designated path for no gain.
Residual:: Codex can overwrite its own result file and schema arbitrarily
inside the channel. That is already true today and is why `validated_result`
correlates the envelope's identity against the dispatch
(`adapter.py:142-145`) *[I]*; the boundary neither improves nor worsens it.
What the separation buys is that the Run snapshot, the dispatch marker, the
usage record and the execution evidence are outside the view altogether. The
relocation also carries a non-security cost the implementation must pay: the
archive's one-level glob (`frontdoor/archive.py:377`, `:402`) must be extended
to the channel subdirectory while keeping the existing depth-one patterns for
recorded historical runs. More importantly, this widening *exceeds* the
2026-11-08 authorization's own fence of one designated exception *[D]*, which
is why it is raised as open maintainer decision <<m7,M7>> rather than taken
here, and why the umbrella record's supersession marker now names all three
categories.

[[d5]]
=== D5. Writable grants from `phase.authorized_scope`, with pre-created directories

Decision:: Derive the writable grant set from `phase.authorized_scope`,
normalized (drop any entry contained in another, then sort). For an entry that
names a directory which does not yet exist, the Coordinator creates it before
validation and removes it afterwards if it is still empty. For an entry that
names a not-yet-existing *file*, bind the nearest existing ancestor directory
writable and record the overgrant.
Who owns the lifecycle (decided at H009):: The per-Hop dispatch frame that
computes the grant -- `operator.py`'s loop body, which creates the directories
before constructing the adapter (`:978`), calls `run_real_one_hop`
(`:1007-1023`) and resumes after it returns (`:1024`) *[I]*. Not the adapter:
`execute()` returns before the Hop's post-Hop observation and candidate
acceptance (`vertical.py:400-422`) *[I]*, so an adapter-side removal would run
too early, and a transport that creates and deletes host directories is no
longer a transport. The bracket is `finally`-shaped so it also runs when the
Hop raises. Ordering is for clarity, not safety: an empty directory is
invisible to the post-Hop delta either way.
Reason:: A bind source must exist (*[O]*, E3), and an empty directory is
invisible to Git, so pre-creating one cannot disturb the clean-tree assertions
at `vertical.py:440-449` or the post-Hop delta *[I]*. Pre-creating an empty
*file* would be visible as an untracked path and is therefore not done.
This is the mechanism that would have let the
link:../../backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc[Claude
write-permission] case (`docs/developer_guide/` absent at launch) *[D]* work
preventively rather than by provider permission.
Rejected:: (a) Making the whole repository writable -- destroys the integrity
goal. (b) Requiring every scope entry to exist -- would refuse legitimate
Commissions that create a new directory, the exact case the Claude BUG
records. (c) A writable overlay over the whole repository with later
reconciliation -- a new mechanism, and the post-Hop check already reconciles.
Residual:: The file-shaped-entry case overgrants to the parent directory. The
post-Hop scope check still refuses anything outside scope, so this is a
prevention gap, not an acceptance gap. Slice A must state it -- and must state
it in the *reviewer* case specifically, because that is where it bites: a
durable review artifact never exists when its phase starts, so a reviewer
phase's grant is always a directory grant. This Commission's own
`broad_review` phase is the example: its single scope entry was the then-absent
`docs/warm_storage/post-beta-planning/wfc_execution_boundary_broad_review.adoc`
(`.wfc/governance/wfc-exec-boundary-ftr-001/profile.yaml:60-61`) *[I]*, whose
nearest existing ancestor is the directory holding this very record. A reviewer
is therefore confined to the directory containing its artifacts, not to the
artifacts, and Slice A may not claim otherwise. Narrowing it means changing the
artifact layout or the scope data, which belongs to
link:../../backlog/FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[the phase
write-scope record] and Slice B, not to Slice A.

[[d6]]
=== D6. `/proc` and the process model: minimal, and a decided default

Decision:: Add `--unshare-pid --proc /proc` to the generated view, and
`--new-session`. Do not add `--unshare-net` in Slice A.
Reason:: `/proc` is a demonstrated precondition for the Claude runtime *[D]*;
`--unshare-pid` bounds what `/proc` then shows to the sandbox's own process
branch *[D]*; `--new-session` detaches the controlling terminal, which is the
standard bubblewrap hardening for an untrusted child. Leaving the network
namespace alone keeps the boundary silent about network, which is what the
maintainer's out-of-scope decision requires: a boundary that said nothing but
quietly broke provider authentication would be worse than no boundary.
Open:: The residual `/proc` exposure (host boot parameters, parts of
`/proc/sys` and `/proc/net`) is named as unassessed by the 2026-11-08 record
*[D]* and stays an explicit open item in the FTR rather than being asserted
safe here.
Rejected:: (a) No `/proc` -- the provider does not start. (b) `--proc /proc`
without `--unshare-pid` -- exposes the host process table. (c)
`--unshare-all` -- includes the network namespace and would break provider
inference transport.

[[d7]]
=== D7. Provider permissiveness is bound to an effective boundary, per invocation

Decision:: Each adapter keeps exactly its present settings when it runs
unisolated. A more permissive provider profile is admissible only on an
invocation for which the WFC boundary was actually validated and entered, and
the boundary mode is recorded in the Hop's binding evidence and audit
projection.
Reason:: The 2026-11-16 direction already says provider configuration may
become more permissive only after a boundary is "separately integrated and
qualified" *[D]*. Mechanically, the dangerous failure is a permissive profile
on an unisolated run, so the permission must be computed from the same value
that selected the boundary, in the same call, not from configuration read
elsewhere.
Reason, second:: `sandbox.failIfUnavailable: true` (`claude_adapter.py:227`)
*[I]* means the nested provider sandbox refuses rather than degrades. Combined
with the observation that a nested user namespace may be unavailable (*[O]*,
<<limits>>), an unqualified boundary plus unchanged provider settings can
produce a hard refusal. Slice A must therefore treat "boundary on, provider
settings unchanged" as a configuration whose startup behaviour is a
qualification question, not an assumption.
Rejected:: (a) A global "permissive provider" setting -- it would apply to
unisolated runs. (b) Relaxing the provider sandbox to make the nested case
start -- that is the "no existing safeguard dropped unsecured" line the
maintainer drew. (c) Defaulting `enableWeakerNestedSandbox` -- explicitly
forbidden by the 2026-11-08 authorization *[D]*.

[[d8]]
=== D8. Opt-in in Slice A, with no silent fallback

Decision:: Slice A ships the boundary as opt-in, selected per Run through the
execution envelope, absent meaning today's behaviour. Once selected, failure
to establish it is a refusal classified as not-started; there is never a
fallback to unisolated execution.
Reason:: Default-on would change the behaviour of every existing Run, config
and test at the same moment as introducing the mechanism, and would make the
first failure mode "my Run stopped working" rather than "my Run is isolated".
The closed configuration vocabularies (`frontdoor/config.py:160-172`,
`serialization.py:1004-1037`) *[I]* accept a new *optional* key without
invalidating any existing file.
Migration:: opt-in for Slice A; a default-on decision belongs to the
maintainer after the qualification exit criteria are met, and the FTR records
it as an open decision rather than pre-deciding it.
Rejected:: (a) Default-on -- see above. (b) Per-adapter default -- makes the
security property depend on a model binding. (c) An environment variable --
not auditable in the Run's own evidence.

[[d9]]
=== D9. Provider reachability is an operator-side precondition, not a new mount

Decision:: For an invocation with the boundary selected, the provider
executable and everything it loads at runtime must resolve inside the view --
in Slice A, under `/usr` or the four `/bin`-family links. This is stated as an
operator-side prerequisite of enablement and of the live qualification layer,
with the preflight refusal naming the remedy. It adds no mount kind and no
code path beyond the refusal that <<d4>> already keeps narrow.
Reason:: The slice previously answered this category with a refusal only, and
the refusal bites universally on the host designated for qualification: this
machine has `/usr/bin/bwrap`, `/usr/bin/node`, `/usr/bin/env`, `/usr/bin/sh`
and `/usr/bin/python3`, but no `claude` or `codex` at `/usr/bin` or
`/usr/local/bin` *[O]*, and `PATH` resolves provider tooling through two
`$HOME`-local entries that are deliberately not mounted *[O]* (E6). Layers 1
and 2 gate every preventive-isolation claim in every record, and L1 to L6 all
begin by starting a real CLI inside the boundary, so without this decision the
gate had no performable precondition.
Consequence for Layer 1:: The deterministic cases dispatch a *fake* provider
through the real path, so the same rule applies to them. The fake executable
is placed inside the synthetic repository each test builds -- mounted
read-only at its own absolute path -- with a `/usr/bin/env python3` or
`/bin/sh` shebang, both view-visible *[O]*, and *committed* in that
repository's baseline commit as `PROOF.md` already is
(`tests/unit/test_slice4.py:54-63`) *[I]*, so the post-Hop observation does
not see it as an unauthorized untracked change. Today's fixtures write fake
providers into `tmp_path` outside the repository
(`tests/unit/test_slice4.py:73`) and some write side files there (`:1059`,
`:1112`) *[I]*; those stay valid for the unisolated path, while the
boundary-selected variants must move the executable into the synthetic
repository and any side file into the channel directory or the scratch, since
nothing else is writable.
Rejected:: (a) *A fourth designated read-only external mount kind for the
provider install tree.* It would make a `$HOME`-local or version-manager
install usable, which is a real operational convenience, but it extends the
enumeration the maintainer is being asked to authorize in <<m7,M7>> and binds
a directory whose contents the operator never enumerated. Not taken here; if
the maintainer prefers it, it is an addition to M7 and not a judgement call
for the implementation Commission. (b) *Binding a `$HOME`-local install onto a
path inside the view, for example `/usr/local/bin/claude`* -- that is a
caller-supplied mount with an outside-repository source, so the fenced
bind-source rule refuses it (`execution_boundary.py:124-127`) *[I]*, and
making it pass would need either option (a) or the general loosening the
2026-11-08 authorization forbids. Worth noting while rejecting it:
`validate()`'s overlapping-destination check compares caller-supplied
destinations only with one another (`:114-116`) and never with the generated
system view *[I]*, so it would *not* catch an overmount into `/usr`; Slice A
must therefore forbid system-view destinations explicitly rather than assume an
existing check covers them. (c) *Copying the CLI into the repository or the
scratch* -- it would put a provider binary into the agent's own write surface
and into candidate scope.
Residual:: An unprepared host cannot produce any isolation claim at all. The
failure direction is a refusal, so this is an availability cost rather than a
security gap, but it must be stated in the Operator Manual by the Commission's
documentation step.

[[d10]]
=== D10. The grant travels on the construction axis, not on the port

Decision:: The Coordinator computes one frozen `BoundaryGrant` per invocation
-- mode, canonical repository, normalized writable repository paths, the
readable and writable host paths, the provider channel directory and the
external scratch root -- and passes it to the CLI adapter's constructor as one
optional parameter whose `None` value means today's unisolated behaviour. The
provider-neutral port is unchanged. One Coordinator-side derivation function
produces the grant for both construction sites, and
`slice4.run_real_one_hop` gains the same optional parameter, forwarded to the
default `CodexCliAdapter` it builds when no adapter was injected.
Reason:: Four, in order of weight. (1) A grant on `AgentExecutionRequest`
would reach `FakeAdapter` and `SubprocessAdapter` (`adapter.py:100-125`)
*[I]*, which cannot act on it, so a silently ignored confinement instruction
would be expressible -- the exact shape <<d8>> forbids; on the construction
axis only an adapter that can honour a grant can be handed one. (2) Every
field of `AgentExecutionRequest` is a semantic dispatch fact the prompt or the
result contract depends on, while the execution environment is already modelled
on the construction axis (binding, result directory, executable) *[I]*. (3) The
boundary *mode* already arrives there: <<d8>> puts the closed `boundary` key on
the Run execution envelope (`model.py:180-192`, `serialization.py:1004-1043`;
its `_fields` call at `:1013` must gain `optional={"boundary"}`, since unknown
keys are rejected today, `serialization.py:217-231`) *[I]*, and
`operator.py:966-980` holds that object exactly where it resolves the binding
and constructs the adapter *[I]*. (4) Blast radius: the port is shared by both
fixture adapters, every adapter conformance test and the proof harness, and
none of them changes.
Where the inputs are:: `operator.py:957-980` already holds the profile, the
phase key (`:958`), the role (`:959`), the resolved binding (`:972`) and the
Run root (`:977`) at the construction site *[I]*;
`vertical.run_one_hop` binds `phase = profile.phases[run.phase]`
(`vertical.py:303`) *[I]*, which is why the rejected alternative was
mechanically available too.
The second construction path:: `slice4.run_real_one_hop` default-constructs a
`CodexCliAdapter` when `adapter is None` (`slice4.py:172`, `:321-326`) *[I]*,
and its one in-tree caller that relies on that default is the Codex proof
harness (`proof_harness.py:215-225`) *[I]*, which passes no grant and so stays
unisolated exactly as today. That is a non-change for a path that never
requested a boundary, not a fallback for one that did: a `bubblewrap` grant is
honoured or refused by name, never satisfied by an adapter built without one.
Auditability:: `_binding_evidence` (`operator.py:677-685`, called at `:981`)
*[I]* projects the mode from the same grant the adapter was constructed with,
so the audit field and the dispatch cannot diverge; the injected-adapter
branch (`:984-989`) *[I]* projects `direct`.
Rejected:: (a) *Boundary fields on `AgentExecutionRequest`* -- rejected for
reason (1); it is otherwise defensible and needs no adapter-constructor change.
(b) *Separate constructor arguments per path kind* -- one frozen value keeps the
derivation in one place and gives <<d5>> and Slice B a single thing to extend.
(c) *Deriving the grant inside each adapter from the request* -- it would put
authority derivation into a transport and produce two copies of the
normalization rules.
Consequence for Slice B:: Slice B requires that the profile the launcher
consumes be a Coordinator-computed value *[D]*. `BoundaryGrant` is that value:
a richer later profile changes the derivation function, not the port, the seam
or either adapter.

[[d11]]
=== D11. The sandbox root tmpfs, and what is only measurable inside a sandbox

Decision:: Intend `--remount-ro /`, appended after the mount arguments, and
make the implementation Run *measure* it (Layer 1, N12) rather than assume it.
Reason:: `build_argv` generates no root `--tmpfs` and no `--remount-ro /`
(`execution_boundary.py:166-182`) *[I]*, so the sandbox root and the parent
directories bwrap materialises to carry bind destinations belong to bwrap's own
base tmpfs and are presumably writable for the child. No host guarantee depends
on this -- a tmpfs write is not a host write -- but two claims had to be
re-phrased: a negative test asserting that an in-view write *attempt* fails can
be wrong where the path has no host backing (N11 now asserts host identity and
records the attempt's outcome separately), and the `/tmp` size cap is not the
whole answer to scratch abuse while an uncapped root tmpfs is writable (N12).
The installed build documents `--remount-ro DEST` as non-recursive *[O]*, so
appending it for `/` should leave the writable binds, the private `/tmp` and
the external scratch untouched.
Assumption, explicitly:: That it behaves so is *unverified*. No Hop of this
Commission could enter a sandbox at all (<<limits>>: namespace creation is
refused and `/proc/sys/user/max_user_namespaces` reads `0` in the agent
sandbox) *[O]*, so neither the writability nor the remedy could be observed.
If the measurement shows `--remount-ro /` is recursive or refuses, the
implementation Run reports that and the in-view-only writability stays a
stated residual; it is not a reason to lower any host guarantee or to skip the
measurement.

== Open maintainer decisions, with a recommendation

[cols="1,4,3",options="header"]
|===
|# |Decision |Recommendation

|M1
|Does Slice A stay opt-in, or become default-on once qualified?
|Opt-in now (<<d8>>); revisit default-on only after the Slice A exit criteria
are met on this host for both adapters.

|M2
|Is the residual `/proc` exposure under `--unshare-pid --proc /proc`
acceptable?
|Accept for Slice A on this single-tenant development host, and record it as a
named residual risk. It is a precondition for the provider starting at all,
and no cheaper option was found.

|M3
|May the implementation Commission change `validate()`'s `/repo` destination
convention and the tests that assert it (<<d2>>)?
|Yes. It is inside `src` and `tests`, and the alternative is worse.

|M4
|Should confining *evidence* commands be in scope anywhere?
|Not in Slice A. It is the least confined execution in WFC *[D]* and deserves
its own record; mixing it into Slice A would double the qualification surface.

|M5
|Who runs the live qualification, and with how many invocations?
|The maintainer or Level-1 operator, outside a Commission, with a stated
minimal invocation budget. Slice A's worker Hops cannot do it: they cannot
even start `bwrap` (<<limits>>).

|M6
|Does Slice A need a `.wfc/config.yaml` entry for this repository?
|Not as part of the Commission. `.wfc/` is outside the scope ceiling *[I]*;
the Commission adds the optional schema and documents it, and the maintainer
edits the file if and when they want the boundary on here.

|[[m7]]M7
|The 2026-11-08 authorization permits *one* designated exception to the
repository-only bind-source rule, today's external scratch root. Slice A needs
three designated kinds (scratch, the *per-invocation provider channel
directory* -- not the Run state directory that contains it -- and provider
authentication) plus a narrow enumerated read-only `/etc` set in the generated
system view (<<d4>>). Does the maintainer extend the fence to exactly those,
and no further?
|*Extend it to exactly those four enumerated items, and keep every other
prohibition.* The alternatives are worse: (a) refusing the provider channel makes
the Codex path unimplementable and leaves Claude unable to read its own closed
settings; (b) refusing the authentication mount makes every isolated Run an
authentication failure, which in practice means nobody turns the boundary on;
(c) a generic external-mount allowlist is the general loosening the
authorization forbids and would hide every later addition. The recommended form
keeps each addition a separately named, separately validated parameter, so a
fourth one would again be visible as a code and record change rather than
configuration. This decision is a *precondition for commissioning Slice A*,
not something the implementation Commission may take: if it is not taken, Slice
A's stop rule applies.

|[[m8]]M8
|How does the provider CLI become reachable inside the view (<<d9>>)? Either
the operator installs it and its runtime at a view-visible path, or a *fourth*
designated read-only external mount kind is added for the provider install
tree -- which would extend <<m7,M7>>'s enumeration.
|*Take the operator-side prerequisite, not a fourth mount kind.* It adds no
mount kind, no code path and nothing to the fence; the cost is operational
(the CLI must be installed outside a version manager's `$HOME` tree) and the
failure direction is a named refusal. This is also a *precondition for the
live qualification layer*, not only for commissioning: on this development
host neither CLI is at a view-visible path today *[O]*, so L1 to L6 cannot
start until the host is prepared. If the maintainer prefers the fourth mount
kind, it is decided here and implemented with the same
separate-named-parameter discipline -- never taken by the implementation
Commission on its own judgement.
