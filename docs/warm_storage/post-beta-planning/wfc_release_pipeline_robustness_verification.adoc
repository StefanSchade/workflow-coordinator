== Difference from the plan's D1 wording (reported, not silently resolved)

Maintainer decision D1 (`beta2_release_streamlining_plan.adoc#d1`) describes
Option B as printing `implementation_tree_sha256` in both runs' summaries
"and asserting equality in the tag run", and the decisions-taken summary
repeats "printed in both runs and asserted equal in the tag run". The FTR
itself (`FTR-WFC-RELEASE-PIPELINE-ROBUSTNESS.adoc`), which governs where
this task text and the FTR differ, asks only that the `check` job's summary
carry the six listed facts, including `implementation_tree_sha256`
(link:../../backlog/FTR-WFC-RELEASE-PIPELINE-ROBUSTNESS.adoc#design[its
design section]); neither that design section nor
link:../../backlog/FTR-WFC-RELEASE-PIPELINE-ROBUSTNESS.adoc#tests[its
required tests] asks for a mechanical equality-assertion step comparing the
branch-run's value to the tag-run's value, and AC-4 only requires the six
labelled lines to be present. This
slice therefore implements exactly what the FTR specifies: the `check` job
(which runs on both the branch-push and the tag-push triggers, unconditionally)
prints `implementation_tree_sha256` in its summary every time it runs, which
makes the value available for a human or an external process to compare
between the two runs, but adds no in-workflow assertion step. This is
reported as the governing difference between the task text and the FTR
per the task's own instruction; nothing beyond the FTR's text was added.

[[pipefail-correction]]
== Correction: the two `tee` pipelines needed an explicit `pipefail`

An earlier version of this record (and of the implementation) asserted that
"GitHub Actions' default shell already runs with `-o pipefail`", citing
`bash --noprofile --norc -eo pipefail {0}` as the default. That citation is
GitHub's documented shell for an explicit `shell: bash` key
(`docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax`,
`jobs.<job_id>.steps[*].shell`); neither of these two steps sets `shell:`,
so GitHub's actual default for a `run:` step on a Linux runner applies
instead: `bash -e {0}`, with no `pipefail`. Under that real default, `cmd |
tee file` reports `tee`'s exit status (always 0 here), not `cmd`'s, so a
failing `pytest` run or a `dist-audit` violation would have left the `check`
job green and, since `publish-testpypi` needs only `check`, allowed the
publication chain to proceed on a red required suite or a failed C2
audit -- unweakening neither G2 nor G3 as the FTR's W5 design and the
Commission's "no weakened or deleted test" require.

Reproduced locally:

[source,bash]
----
bash -e -c 'python3 -c "raise SystemExit(1)" | tee /dev/null'; echo "$?"
# -> 0 (GitHub Actions' real run: default; the failure is swallowed)

bash -c 'set -euo pipefail; python3 -c "raise SystemExit(1)" | tee /dev/null'; echo "$?"
# -> 1 (with set -euo pipefail, the first command's exit status wins)
----

Fix applied in this Hop, confined to `.github/workflows/release.yml`: the
"Required test suite" step's `run:` block and the "Distribution content
audit" step's `run:` block (previously a single-line `run:`, now a block)
each now start with `set -euo pipefail`, matching the convention already
used elsewhere in this same file (the C3 smoke step, the G1 preflight step,
the python-compat venv/metadata steps, the `release` job's idempotent-upload
step). No other line in either step changed; the `tee` capture mechanism
itself needed no further change. The two run-block diffs are the complete
content change in this Hop (confirmed by `diff` against the pre-correction
file: one added `set -euo pipefail` line in each of the two blocks, nothing
else).
