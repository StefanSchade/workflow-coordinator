== 2 F001 (a) — the lifecycle-consumption claim: resolved

The single bullet that asserted of all nine `refused_*` classifications that
"each still consumes this checkout's one lifecycle" is gone. The replacement
splits them into four groups, and each group is true of this tree:

* `refused_unauthorized` / `refused_drift` / `refused_journal_root` — "raised
  before authorization is recorded … the checkout's one lifecycle is *not*
  consumed". `_authorize` raises `refused_unauthorized` at
  `frontdoor/lifecycle.py:272` and `refused_drift` at `:285`, both before the
  `authorize_intent`/`authorized` records are appended at `:299-308`;
  `require_disjoint_journal_root` (`frontdoor/journal.py:100-106`) rejects a
  non-disjoint journal root before any record can be written. The lifecycle
  exists exactly when an `authorized` record exists, which is the predicate
  `_advance` tests at `:742-752`. Two tests already in the required suite
  assert the no-side-effect half directly
  (`tests/unit/test_lifecycle_controller.py:131-146`, the state home does not
  even exist afterwards, and `:148-169`, `Journal(...).read_all() == ()`); I
  re-read both and re-ran the file (section 4). H002's three-run reproduction
  on a disposable consumer repository is not repeated here — the code and the
  two tests settle the same fact and the correction follows them.
* `refused_no_lifecycle` — "`wfc resume` found nothing recorded … there was
  never a lifecycle to consume": `:745`, raised only when
  `journal.latest(("authorized",))` is `None` and no `authorize` callable was
  supplied, which is precisely `resume_lifecycle`.
* `refused_active_lifecycle` — "a lifecycle is already authorized for this
  checkout (at most one ever is, even long after an archived Run)": `:749-752`,
  and the wording matches both the refusal's own message ("use `wfc resume`")
  and `ch07_diagnostics/01_troubleshooting.adoc:48-54`.
* `refused_prelaunch` / `refused_probe` / `refused_identity_changed` /
  `refused_launch_exhausted` — "raised once a lifecycle is already authorized":
  `:326`, `:337`, `:347-353`, `:366-377`, `:390`, `:400-414`, `:544` and
  `:836-844` all sit after `_authorize` returned. This keeps the one claim the
  sources do make — the quickstart's and `references/commission.md:83`'s
  "`refused_probe` … still consumes this checkout's one lifecycle" — and the

  `ch07_diagnostics/01_troubleshooting.adoc:41-47` ("correct the input, then

== 3 F001 (b) — the completeness claim: resolved

The section headed "Every classification, and what it means" now covers all 23
keys of `frontdoor.lifecycle.EXIT_CODES`, with no extra name. Measured by
extracting the keys from the `EXIT_CODES` literal and the backticked names from

not a key: []". The three that were absent are added and each is accurate:

* `launch_failed_no_engine` — "a launch attempt never produced an engine
  process (`wfc status` reports the attempt count against the retry limit)":
  `_evaluate` returns exactly `f"no engine process was ever created (attempt
  {attempts} of {MAX_LAUNCH_ATTEMPTS})"` (`:696-701`).
* `not_launched` / `lifecycle_active` — "(`wfc status` only) authorized but
  launch has not begun, or still launching/running; `lifecycle_active` means
  another process currently holds this checkout's lock": `:686-690` chooses

  `not_launched`; the skill follows the CLI, which is the resolution the

== 6 Non-blocking observation

O6:: `refused_drift` and `refused_prelaunch` each have raise sites on *both*
sides of the authorization record, and the corrected grouping assigns each of
them to one side only. `refused_drift` also fires in `_do_commit`
(`frontdoor/lifecycle.py:511-515`) when the commission digest no longer matches
the authorized one, which is after the `authorized` record exists; the file now
places `refused_drift` in the "not consumed — `wfc run` again in the same
checkout" group. `refused_prelaunch` conversely fires at `:291` when the
checkout lock cannot be acquired, which is before this call's `authorized`
record; the file places it in the "once a lifecycle is already authorized"
group. Neither is blocking, for two measured reasons. The post-authorization
drift site is a defensive re-derivation that I could not reach without editing
WFC's own private state: `_do_commit` recompiles from the commission texts
cached in the checkout state home, the guidance text is pinned at its
`source_commit` (`commissioning.py:313`), the package components are identity-
verified (`_verify_identities_unchanged`), and an ordinary repository change in
between is caught earlier as `refused_prelaunch` (`:347-349`, `:390`). The
`:291` site, symmetrically, only fires while another controller holds this
checkout's lock, which in practice means that controller has authorized the
lifecycle, so the group text is true of it in practice. In both cases the
worst outcome of following the file is one further truthful refusal that names
the right next command, not a destructive act — the asymmetry that made F001
blocking does not apply. A cheap tightening, for S2 or a documentation pass, is
the manual's own conditional wording ("either `wfc resume` if a lifecycle was
already authorized, or a fresh checkout",
`ch07_diagnostics/01_troubleshooting.adoc:41-47`) for these two names.
