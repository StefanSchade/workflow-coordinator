=== 3. Blocking finding

==== F-C (blocking). A recovery with no remaining Hop budget erases the stop reason and leaves the Run terminally unresumable — the defect this WorkItem removes, re-created on the recovery path

The predicate has no "Hop budget remains" element, live or recorded, and
`resume_after_reconcile`'s pre-existing guard admits `hop_used == hop_limit`
(`reducer.py`: `if run.hop_used > run.hop_limit`). `run_serial_hops`,
however, cannot run a Hop in that state: its loop opens with
`if run.hop_used >= run.hop_limit: break` (`operator.py:904`), a guard the
reducer normally makes unreachable by stopping at `AWAITING_HUMAN_BUDGET`
with `stop_reason="autonomous_hop_budget_exhausted"` whenever a further
invocation is needed and the budget is spent (`reducer.py:1968`,
`reducer.py:2046`). B makes that `break` reachable for the first time.

Reproduced by execution, with the real engine, in one `wfc resume`. A
`robust@v1` Run whose mechanical durable-artifact stop falls on its last
authorized Hop (`max_autonomous_hops: 2`) satisfies the predicate exactly as
implemented:

[source,text]
----
RUN classification: reconcile_required
before resume: status=reconcile_required phase=broad_review hop_used/limit=2/2
  stop_reason='mechanical_preemption:required durable artifact has no CommitIntent'
  reconcile_reason='mechanical_recoverable'
  anomalies=('required durable artifact has no CommitIntent',)

RESUME classification: interrupted
RESUME message: mechanically recovered; classified: interrupted
after  resume: status=ready phase=broad_review hop_used/limit=2/2
  stop_reason=None
  reconcile_reason='mechanical_recoverable'
  anomalies=('required durable artifact has no CommitIntent',)

SECOND RESUME classification: interrupted
SECOND RESUME message: lifecycle already classified (no-op)
after  second: status=ready phase=broad_review hop_used/limit=2/2 stop_reason=None

classified records: ['reconcile_required', 'interrupted']
----

What the recovery did: it passed its own predicate, wrote `run.json` to
`status=ready` with `stop_reason=None`, launched the engine, which charged no
Hop and returned the Run still `READY`, and classified that as
`interrupted`. The end state is:

. *the honest diagnosis is gone.* The Run is stopped in fact but its record
  no longer says why. A's requirement is "the stop reason and anomaly text
  preserved in the Run record"; the `anomalies` tuple survives, the
  `stop_reason` does not. The reconcile classification that *did* state the
  reason has been overwritten.
. *the Run is terminally unresumable.* `_attempt_mechanical_recovery`
  returns `None` for classification `interrupted` (it is outside the
  `("reconcile_required", "awaiting_human")` gate), so `_advance` answers
  `lifecycle already classified (no-op)` — I measured exactly that on the
  second `wfc resume`. There is no semantic stop, so
  `operator._predecessor_for_successor` refuses `prepare-successor` too.
  `report.py`'s text for `interrupted` ("a human must inspect the Run and
  decide whether to resume it") now points at a resume that cannot act.
  This is the incident's own shape — mechanically stopped, consistent facts,
  no open question, no path forward — newly reachable through the fix for it.
. *the candidate's own documentation is contradicted.*
  `ch06_recovery/01_outcomes.adoc:110-116` promises that on success resume
  "moves the identical Run to `ready` ... with the stopped Hop still charged
  and the Hop budget unchanged, and continues the engine's own Hop loop to a
  further terminal classification". With no budget there is no further Hop
  and no terminal classification; the verification record (section B,
  "continues the identical `run_id` at its unchanged Hop budget") makes the
  same unqualified claim. Task B's own rule — "If any predicate fails it
  refuses with a named classification and message and changes nothing" — is
  the behaviour required here, and it is not what happens.

This is not a hypothetical state. A gate review that forgets its CommitIntent
on the Run's last authorized Hop is the ordinary case of the very mistake
C(ii) exists to prevent; the real incident Run only escapes it because it had
used 6 of 14 Hops.

Feasible, minimal fix, inside the authorized scope: add the missing element
to B's live re-verification next to the HEAD/clean-worktree/identity checks —
refuse by name (for example "no autonomous Hop budget remains for a
continuation") when `run.hop_used >= run.hop_limit`, changing nothing. That
is the smallest option, it is the only one consistent with "recovery widens
neither scope, program nor budget", and it leaves the Run's honest
`reconcile_required` record and its stop reason intact for the operator, who
can then authorize budget through the existing documented path. It needs one
refusal test in `test_mechanical_recovery_lifecycle.py` alongside the other
ten, plus the corresponding sentence in `ch06_recovery/01_outcomes.adoc` and
the verification record's predicate list. Nothing about the anomaly class,
the archive destinations, the prompt block or C(iii) needs to change.

I deliberately do not ask for the alternative (let the recovery proceed and
classify `awaiting_human_budget`): it would require the recovery to mutate a
Run it cannot continue, and `run_serial_hops`'s `break` does not produce that
status.

==== F-A (blocking). `frontdoor.preservation` was not scoped to the current classification, so a recovered continuation is never preserved

`postrun.run_pending_postrun` was correctly changed so its "already
archived, cache it" shortcut only consults `ext.archive.result` records with
`seq >` the `classified` record being processed, because B makes a *second*
`classified` record per checkout possible for the first time (before this
change `_advance` short-circuited on any `classified` record, for both
`wfc run` and `wfc resume`, so exactly one existed per journal).

The structurally identical shortcut one file over was not changed.
`preservation.run_pending_preservation` still returns
`journal.latest(("ext.preservation.result", "ext.preservation.not_needed",
"ext.preservation.refused"))` from anywhere in the journal
(`preservation.py:50`, `preservation.py:88`), and `postrun._preservation_fact`
still reads the same unscoped `journal.latest(...)` (`postrun.py:104`).

Reproduced by execution. Running
`test_recovery_run_still_needs_its_own_normal_accepting_route` (a Run that
stops mechanically, recovers, and stops again at `awaiting_human`, which is
in `preservation._TRIGGER_CLASSIFICATIONS`) and reading the journal it
leaves behind:

[source,text]
----
seq 14  ext.preservation.intent      run_id RUN-fake-engine
seq 15  ext.preservation.not_needed  run_id RUN-fake-engine
seq 16  ext.archive.intent
seq 17  ext.archive.result           archive/unclassified/consumer-repo-run-fake-engine
...
seq 23  ext.archive.intent
seq 24  ext.archive.result           archive/unclassified/consumer-repo-run-fake-engine-recovery-1
----

The continuation produced its own archive attempt, but *no*
`ext.preservation.intent` at all: `_latest_fact` found the predecessor's
terminal record and returned it as-is. Two consequences:

. A recovery continuation that stops at `interrupted`, `awaiting_human`,
  `awaiting_human_budget`, `reconcile_required` or `stopped` with its own
  new candidate work has that candidate silently *not* preserved — the one
  automatic capture step whose purpose is not losing an unaccepted
  candidate. This is a new defect introduced by B, not a pre-existing one.
. The continuation's archive carries the predecessor attempt's preservation
  fact as its own `lifecycle.preservation`, so the new Attempt's Evidence
  attests a preservation step that belongs to the earlier attempt.

That second consequence contradicts two statements this candidate itself
makes: `ch06_recovery/01_outcomes.adoc` ("`wfc status`/`wfc report` read ...
the recovery history is visible, never hidden behind the predecessor's own
facts") and the verification record's equivalent claim. The task's B
requires `wfc status`/`wfc report` to "show the recovery history
truthfully".

Feasible, minimal fix, entirely inside the Worker's authorized scope
(`src/workflow_coordinator/frontdoor` is listed in the Commission): apply
the same `seq > classified.seq` scoping the author already wrote in
`postrun.py` to `preservation.run_pending_preservation`/`_latest_fact` and
to `postrun._preservation_fact`, with a test on both sides of the seam (the
fixture already has the `awaiting_human_again` continuation mode this needs,
so the test is a few lines). Nothing about the predicate, the archive
destinations or the refusal paths needs to change.

[[f-b]]
==== F-B (blocking). Three predicate elements have no refusal test, against an explicit required-test criterion

The task's TESTS section requires a fixture-driven test that `wfc resume`
"refuses when each predicate element is violated one by one", and acceptance
requires "every single violated predicate element is refused with a named
reason". `test_mechanical_recovery_lifecycle.py` does this for six elements
(open blocking Finding, semantic stop, human question, non-recoverable
anomaly class, dirty worktree, moved HEAD) and
`test_recovery_routing_reducer.py` covers the `mechanical_preemption:` scope
gate. Three implemented refusal branches have no test at all — confirmed by
searching the whole test tree for their messages, which appear nowhere:

* `reducer.py`: `"the Run has no recorded Hop outcome"` (the predicate's
  "the Hop outcome recorded" element);
* `lifecycle.py`: `"Commission or execution envelope identity changed since
  authorization"` (B's "no changed Commission/envelope identity");
* `lifecycle.py`: `"lifecycle authorization or launch provenance is
  incomplete"` (B's "lifecycle authorization still the original one").

The first two are trust-boundary checks: the Commission-identity
re-verification is the single thing that stops a recovery from continuing
under drifted governing inputs, which is exactly the "resume widens
nothing" boundary the task asks the reviewer to check by execution. By
reading the code the branches look right (`_recovery_commission_identity_ok`
reuses `_cached_commission`/`_materials_digest`, the same digest comparison
`_do_commit` makes, and returns `False` on any exception), but I could not
execute them — and the missing test is precisely why no execution path to
them exists. Untested trust-boundary code on a new recovery path is not
something this review can accept on inspection alone.

These belong in the existing `test_mechanical_recovery_lifecycle.py` and
`test_recovery_routing_reducer.py`; no new file or production change is
needed.

=== 4. What I checked and found correct

==== A — the predicate and the classification

* The predicate (`reducer.diagnose_mechanical_recovery_eligibility`) is one
  function, pure, and status-agnostic: it reads only `stop_reason`,
  `semantic_stop`, `human_question`, `hops` and `findings`. The same
  function therefore decides a freshly stopped Run and an already-archived
  terminal one, which is what makes B(ii) work without a second predicate.
* The "worktree clean / HEAD at this Hop's own end HEAD / no other anomaly"
  elements are proven by exact-string membership rather than by separate
  checks. I verified the argument holds rather than taking it on trust:
  `vertical.run_one_hop` builds `repository_anomaly` as
  `"; ".join((*delta.anomalies, *post_acceptance_anomalies,
  *post_evidence_anomalies, trusted_commit...))` (`vertical.py:568`), and
  `git_facts` puts `"dirty tracked state"`, `"non-ignored untracked
  state"`, `"unresolved submodule identity"`, `"unexpected HEAD
  movement"`, `"divergent or rewritten ancestry"`, `"forbidden merge
  commit"`, `"commit safety-cap breach"`, out-of-scope paths and pinned
  policy mutations into `delta.anomalies`. Any of those makes the joined
  string differ from the five exact texts, so membership really does imply
  "this and nothing else".
* The five anomaly texts are now named constants imported by `vertical.py`,
  so the observed text and the recognized text cannot drift. The texts
  themselves are byte-identical to before; `_durable_artifact_anomalies` is
  not weakened — the diff is a pure constant extraction.
* The WFC-GIT-08 exclusion follows the task's default and is decided
  explicitly in the verification record, with two tests pinning it.
* `require_reconcile(reason="mechanical_recoverable")` is admitted only from
  `RUNNING` and `AWAITING_HUMAN`, so no `AWAITING_SUPERVISOR`/`SUSPENDED`/
  `COMPLETED` state can be reclassified this way, and a Run whose persisted
  status contradicts its journalled classification raises `ReductionError`,
  which `_attempt_mechanical_recovery` turns into a refusal.
* `reconcile_required` is already in `postrun._ARCHIVABLE_CLASSIFICATIONS`
  and `preservation._TRIGGER_CLASSIFICATIONS`, so A's reclassification does
  not quietly stop archiving a stop shape that used to be archived.
* Every other mechanical stop still reaches `_stop_for_human`; the
  reclassification is confined to the `repository_anomaly` branch and does
  not reorder the existing mechanical-error loop.

==== B — the recovery path

* `resume_lifecycle` only consults the recovery attempt when a `classified`
  record exists and its classification is `reconcile_required` or
  `awaiting_human`; everything else, and any `awaiting_human` whose
  `stop_reason` lacks the prefix, falls through to the unchanged no-op.
  Pinned by two tests, including the exact "lifecycle already classified
  (no-op)" message.
* A refusal returns before any mutation: the refusal branches all precede
  the first `write_run_snapshot`, and `test_recovery_refuses_on_open_blocking_finding`
  asserts `run.json` is byte-identical afterwards.
* The journal is only appended to: `mechanical_recovery_intent`,
  `_resumed`, `_launch_intent`, `_launch_spawned`, `_launch_failed`, and a
  further `classified`. The new launch record family is deliberately
  distinct from `launch_*`, so `MAX_LAUNCH_ATTEMPTS` and the crash-matrix
  bookkeeping are untouched.
* Hop charge and budget: `resume_after_reconcile` replaces only `status`,
  `stop_reason` and `human_question` — `phase`, `hop_used`, `hop_limit` and
  `findings` are carried through unchanged, and its `hop_used > hop_limit`
  guard still applies.
* No path turns a stopped Run into an accepted one. The Run lands in
  `READY` at the same phase and the engine must run that phase again and
  apply its own accepting route; `test_recovery_run_still_needs_its_own_normal_accepting_route`
  shows a continuation that stops again simply stops again. Recovery never
  touches `findings`, `semantic_stop` or `human_question`, and nothing in
  A/B/C gives the operator, the Coordinator or a resume any Finding
  operation.
* `resume` widens nothing. `operator._continue_existing_run` goes through
  the unchanged `_preflight` with the same `PRODUCTION_EVIDENCE_RUNNER`,
  never calls `new_run`, never `mkdir`s a state root, never rewrites
  `operator-plan.json`, and additionally requires `run.status is READY`,
  matching `work_item_id`/`profile_id`, and `run.current_head ==
  --expected-head`. `allow_existing_state_root` defaults to `False`, so the
  one-shot refusal is unchanged for every other caller — and it inverts
  into a positive requirement (`state_root.is_dir()`) rather than merely
  skipping a check. Scope, program and budget come from the
  digest-verified Commission and the unchanged Run record.
* `durable_artifacts=()` at the continuation's `run_serial_hops` call is
  behaviourally identical to the fresh path's `legacy_durable`, because the
  legacy tuple is only consulted when `run.hop_used == 0`
  (`operator.py:957`) and the predicate's "at least one recorded Hop"
  element guarantees `hop_used >= 1`. Correct, but see the observation in
  section 5.
* Archive immutability: the predecessor destination is untouched and the
  Evidence commit still resolves after recovery
  (`test_predecessor_archived_attempt_is_byte_identical_after_recovery`
  hashes every file under it), the continuation gets
  `<identity>-recovery-<n>`, and an occupied destination is refused with
  `ARCHIVE FAILED` and left byte-identical. I observed both destinations in
  the journal of a real run (quoted in F-A). No state outside the Run's own
  checkout state and the additive archive is written, and nothing under
  `~/.local/state` or the Evidence repository was read or written by this
  review.
* `report.py`'s new text is live, not dead: `human_question_present` is a
  real, pre-existing `wfc.audit/1` field (`audit.py:38`, `audit.py:177`).
  For an `awaiting_human` Attempt with no recorded question it now names
  `wfc resume`, which either recovers or refuses by name — both of which
  exist. The `refused_not_recoverable` entry gives that classification its
  own accurate text, and `_KNOWN_STATUSES` picks it up automatically.

==== C — route semantics, the artifact obligation, and the contradiction

* `_review_route_semantics_block` is generic: it iterates `sorted(phase.routes)`
  and reads effect, `goto` target, target-phase role and
  `phase.review.failed_evidence_route` from `phase`/`profile` only. No
  route or phase name is hard-coded anywhere in the block or the rule text,
  and two fixture profiles with unrelated route names exercise it.
* The block is added for every gate-review phase and only for those; a
  missing `profile` on such a phase raises rather than silently omitting the
  block, and the single production call site passes it.
* The route set the block lists matches `permitted_route_keys` exactly for a
  running Run, including the evaluator escape-route exclusion.
* The re-review artifact obligation is stated whenever
  `phase.durable_artifact is REQUIRED`, and it names the CommitIntent.
  `_durable_artifact_anomalies` is not weakened in any way.
* C(iii) catches the real incident shape: `robust@v1`'s `focused_review`
  declares `failed_evidence_route: correction` with routes
  `{correction, renew_broad_review}` (`commissioning.py:145`), so H004's
  "accepted, route `correction`" is exactly the combination now rejected.
  The guard is correctly narrow — it requires `not
  facts.required_evidence_failed`, `GATE` authority, `outcome ==
  completed`, and no open blocking Finding after the deltas are applied —
  and the three "legitimate" neighbours (`changes_required` on the same
  route, a genuine evidence failure, an ordinary accept route) each have a
  passing test. Rejecting rather than normalising is the right call for the
  stated reason: the reducer never substitutes its own route for the
  reviewer's.
* `robust@v1`/`simple@v1` are untouched: `commissioning.py`,
  `implementation_identity.py` and `src/workflow_coordinator/resources/**`
  are absent from the diff, as are `agent_skill/`, `governance/`, `.wfc/`,
  `.github/`, the release workflow and every version literal. No new
  dependency. The worktree is clean and no stray file was left behind.
* Docs: the predicate list in `ch06_recovery/01_outcomes.adoc` matches the
  code element for element, the `#mechanical-recovery` anchor it is linked
  to exists, the semantic-model entries for `awaiting_human` and
  `reconcile_required` are updated consistently, and the `_open.adoc` entry
  follows the surrounding form. The one inaccurate doc statement is the
  preservation claim under F-A.

=== 5. Non-blocking observations

. *C(iii) adds another terminal stop with no forward operator action.* The
  new `mechanical_preemption:contradictory_route:...` stop is a terminal
  `awaiting_human` with no `human_question` and no `semantic_stop`, so
  `prepare-successor` refuses it and `wfc resume` refuses it by name. The
  next-action text is accurate (it promises only a refusal), and the task
  admits "reject" as an option, so this is not blocking — but it is one
  more instance of the dead-end shape this WorkItem was written about. C(i)
  should make it rare; it is worth naming in the backlog rather than
  discovering it in an incident.
. *A recovered Run carries its anomaly text forever.*
  `resume_after_reconcile` deliberately preserves it for
  `mechanical_recoverable`, and nothing clears it later. If such a Run is
  afterwards interrupted, `resume_after_reconcile` with
  `reason="interruption"` will raise "reconcile anomalies must be resolved
  before resume" permanently. Not operator-reachable today (that path is
  library-only), and the preservation is intentional and documented, so
  this is a note, not a defect. `operator._summary` and
  `proof_harness` will also report the historical anomaly on an otherwise
  clean completion.
. *Duplicated route filtering.* `_review_route_semantics_block` re-derives
  the same "sorted routes minus the evaluator escape route" set that
  `permitted_route_keys` already computes. Calling the existing function
  would remove a second place to keep in step.
. *The `durable_artifacts=()` equivalence is undocumented.* It is only
  correct because the predicate guarantees `hop_used >= 1`; a comment at
  the call site naming that coupling would be cheap insurance.
. *The archive records the predecessor only through the destination name.*
  B asks for a destination "that records its predecessor attempt and the
  recovery step". `<identity>-recovery-<n>` does encode both, and
  `lifecycle_facts` is only `{classification, preservation}`, so no
  manifest field states it. Defensible as the minimal reading; an explicit
  predecessor field would be more legible if this is ever automated against.
. *The verification record's failure list is incomplete.* It names three
  pre-existing `test_lifecycle_controller` failures and a set of
  integration/architecture ones, but not the twenty
  `tests/unit/test_claude_adapter_conformance.py` failures I also measured.
  I confirmed all twenty fail identically at the base commit, so they are
  environmental and not a regression — the record is honest about its
  limits, just not exhaustive.
