=== Blocking Finding

[[docb-b4]]
==== B4 — `wfc report` is documented against an archive path the product never writes

`01_operating_pattern.adoc:262–263`, the verify step of the loop:

[source,text]
----
On `completed`, render the archived result with
`wfc report <evidence-repo>/archive/<classification>/<attempt-id>/audit.json`.
----

There is no classification segment in any archive path. The destination is
computed by `frontdoor/archive.py:746–749`:

[source,python]
----
def destination_for(evidence_repo, domain, workstream, attempt_id):
    if domain:
        return evidence_repo / "archive" / domain / workstream / attempt_id
    return evidence_repo / "archive" / "unclassified" / attempt_id
----

`domain`/`workstream` come only from `wfc archive --semantic-json`
(`archive.py:724–744`), and the automatic postrun archival that every
`wfc run --yes` performs — the only archival this chapter documents — calls
`archive.archive_run(state_root=…, evidence_repo=…, raw_retention=…,
lifecycle=…, attempt_identity=…)` with no `semantic_path`
(`frontdoor/postrun.py:221–228`), so `domain` is `None`. The classification is
stored *inside* `audit.json` as a lifecycle fact, never in the path. The
repository's own test pins this for a `completed` Run:
`tests/unit/test_postrun_lifecycle.py:221` asserts
`destination_relative == f"archive/unclassified/{_attempt_identity(repository)}"`,
and `postrun.py:154` reads the projection back from
`evidence_repo / destination_relative / "audit.json"`.

The canonical consumer quickstart — which this chapter links for the same
mechanics — already states it correctly:
`wfc report <evidence-repo>/archive/unclassified/<attempt-id>/audit.json`, plus
"`wfc run` itself prints the exact destination path to use, and every Run from
this walkthrough archives under `archive/unclassified/` since nothing here sets
a domain/workstream" (`ch09_consumer_quickstart/01_quickstart.adoc:218–227`).
The Level-1 loop sets no domain/workstream either, so the chapter contradicts
the canonical source for exactly the flow it documents. That is the
NON-GOALS' "parallel source of truth" in miniature, and the same shape as the
already-resolved `F003`: citing canonical text while stating a different rule.

Reproduced consequence: the documented command cannot resolve. `wfc report`
loads its positional `source` and refuses a missing path with
`wfc report: <message>` and exit 2 (`frontdoor/report.py:210–222`). This is a
clean refusal, not state damage — materially milder than `F001`/`F002`, and I
say so plainly — but it is a documented, real-command instruction in the
chapter's verify step that fails for every Run the chapter produces, and the
Commission's measured CHECK requires every command in the chapter to be
verified against the implementation. This one is refuted by it.

Feasible correction, one line and no new mechanism: write
`archive/unclassified/<attempt-id>/audit.json` as the quickstart does, or drop
the path shape entirely in favour of "the destination path `wfc run` printed"
and link `#quickstart-status`. Either is shorter than the present sentence.

[[docb-b1]]
==== B1 — the documented wait loop cannot terminate on eleven real classifications

`01_operating_pattern.adoc:249–251` is the chapter's monitor step:

[source,text]
----
until wfc status --repository . | grep -q '^CLASSIFICATION: \(completed\|awaiting_human\|awaiting_human_budget\|reconcile_required\|stopped\|interrupted\|refused_\|uncertain_launch\|inconsistent\)$'; do
  sleep 30
done
----

Two things are wrong with the alternation, and both are mechanical.

First, `refused_` is not a classification value. The real set is
`lifecycle.py:107–131` (`EXIT_CODES`), whose nine refusal values are
`refused_unauthorized`, `refused_drift`, `refused_prelaunch`, `refused_probe`,
`refused_identity_changed`, `refused_launch_exhausted`,
`refused_active_lifecycle`, `refused_journal_root` and `refused_no_lifecycle`.
Anchored with `$`, the branch `refused_` matches none of them.

Second, `engine_exited_before_state` — a member of `_TERMINAL_CLASSIFICATIONS`
itself (`lifecycle.py:143–146`) — and `launch_failed_no_engine`
(`lifecycle.py:696–701`) are absent from the alternation, as are the
no-lifecycle-yet facts `not_launched` and `no_lifecycle` that `wfc status`
returns after a refusal that happened before the launch marker
(`lifecycle.py:682–690`).

Measured: `printf 'CLASSIFICATION: refused_prelaunch\nCLASSIFICATION:
engine_exited_before_state\nCLASSIFICATION: completed\n' | grep -c '<the pattern
above>'` returns `1` — only `completed` matches. By inspection of the same
pattern against the full value set, the loop exits for eight values
(`completed`, `awaiting_human`, `awaiting_human_budget`, `reconcile_required`,
`stopped`, `interrupted`, `uncertain_launch`, `inconsistent`) and spins forever
for eleven (the nine `refused_*`, `launch_failed_no_engine`,
`engine_exited_before_state`), plus for the post-refusal `not_launched` /
`no_lifecycle` states.

Consequence: the single most likely first-attempt outcomes for a new Level-1
operator — a dirty tree or moved HEAD (`refused_prelaunch`), a baseline probe
that does not exit 0 (`refused_probe`), an unresolvable provider binary
(`refused_prelaunch`, see `B2`) — leave the documented loop sleeping in 30-second
increments with no output, which is exactly the "read the classification, not
the exit code" discipline the chapter is teaching, inverted into a hang.

Feasible, simpler correction: invert the condition, as the Operator's own
account in `LEVEL1_PRACTICE_FACTS.txt` already states it ("wait … until the
classification is no longer `lifecycle_active`/`engine_active`/`not_launched`").
A `while` over the four in-flight values (`no_lifecycle`, `not_launched`,
`lifecycle_active`, `engine_active`) is shorter than the present list, needs no
maintenance when a refusal value is added, and fails *open* — an unknown
classification stops the wait instead of hiding it. This is a documentation fix
only; no product change is implied.

[[docb-b2]]
==== B2 — the documented launch command silently targets the `codex` binary

`01_operating_pattern.adoc:246–247`:

[source,text]
----
nohup wfc run --repository . --request ../wfc-scratch/<package>/request.yaml \
  --yes > ../wfc-scratch/<package>/run.log 2>&1 &
----

`--executable` is omitted, and its real default is `codex`
(`lifecycle.py:72` `DEFAULT_EXECUTABLE = "codex"`, used at `lifecycle.py:960`).
The canonical quickstart states the rule the chapter is silent about:
"Pass `--executable claude` for a `claude_cli` configuration; the executable
must match the configured adapter, and a Run uses exactly one adapter
throughout" (`ch09_consumer_quickstart/01_quickstart.adoc:198–200`). The
chapter's whole subject is a Claude Code Level-1 session; the practice it
documents binds `claude_cli`; the demo configuration in `DEMO_FACTS.txt` binds
`claude_cli`/`claude-haiku-5-5`; and the chapter's *own* second leaf correctly
writes `wfc run … --executable claude --yes`
(`02_worked_sequence.adoc:89`). The generic loop a reader will copy does not,
and `--executable` is not mentioned anywhere in `01_operating_pattern.adoc`.

The cost of getting this wrong is not a retry. Authorization is journaled at
`lifecycle.py:302` *before* the executable is resolved at `lifecycle.py:333`, so
an unresolvable or mismatched binary raises `refused_prelaunch`
(`lifecycle.py:321–327`) with the lifecycle already authorized; a second
`wfc run` in that checkout then refuses with "a lifecycle already exists for
this checkout; use wfc resume"
(`lifecycle.py:751`), and `wfc resume` re-reads the same recorded
`executable_argument`. The reader therefore loses the worktree and must create a
fresh one — the exact failure mode the chapter's own prerequisites section warns
about, triggered by the chapter's own command. Combined with `B1`, the observed
symptom is a loop that never prints anything.

Correction: add `--executable claude` to the launch command (or one clause
pointing at the quickstart's executable-matches-adapter rule). One line.

==== B3 — "commit the Consumer Request YAML" contradicts the canonical chapter and the chapter's own paths

`01_operating_pattern.adoc:237–241` says to "author and commit the equivalent
Consumer Request YAML", citing `ch09_consumer_quickstart/01_quickstart.adoc#quickstart-plan`;
`02_worked_sequence.adoc:123` repeats "author and commit the Consumer Request,
then launch". The cited section says the opposite: `wfc run` "reads it from
`--request` by plain filesystem path, so it need not live inside the repository
either -- keeping it in the scratch directory keeps the tree clean"
(`01_quickstart.adoc:182–185`). Nothing in the product requires the request to
be committed; only the guidance file's commit is load-bearing
(`--guidance-commit` defaults to HEAD).

It is also internally impossible: both chapter leaves pass
`--request ../wfc-scratch/<package>/request.yaml` and
`--request ../scratch/request.yaml`, i.e. a path outside the repository, which
cannot be committed to it. A reader who follows the instruction literally either
fails or moves the request inside the repository against the chapter's own
tree-cleanliness advice four sections earlier (`:116–120`).

Correction: say "author" (and, where the guidance file is meant, say so). The
task's own NON-GOALS forbid a parallel source of truth; this is a small
instance of exactly that, pointing at the canonical text while stating a
different rule.

=== 4. Simplicity and maintainability

The chapter adds no mechanism, no governance structure and no new source of
truth; it links to eleven existing canonical anchors instead of restating them,
and its single new artifact is prose. `B1`'s correction makes the chapter
*shorter* and removes a list that would need maintenance every time a
classification value is added — I found no place where the candidate chose
mechanism over a link, and no safeguard that exists only to exclude a
hypothetical. The split into an operating leaf and a worked leaf matches
`ch06`/`ch08` practice and keeps the verified-versus-illustrative boundary on a
file edge.
