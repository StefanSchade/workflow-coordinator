=== 2. The design, judged before the code

The `Design` section is dated 2026-11-27, carries the WorkItem id, sits in the
record the slice names (not in a review artifact), and does the three things
the task asks of it: it enumerates the stop classes from the evidence, decides
each by name with a trigger, and argues *why* the shipped class is safe rather
than listing that it is. I judge the evaluation sound and the ship/no-ship
split correct, and I reached that conclusion from the product:

* *The shipped class is the one class whose proof the Coordinator can actually
  own.* Every conjunct is a fact the Coordinator wrote itself -- the dispatch
  marker it wrote before dispatching and the uncertain Hop it synthesized
  afterwards (`attribution="coordinator"`) -- and not one is read from an agent
  result. I looked for a conjunct that could be satisfied by provider-supplied
  state and found none.
* *The central argument is the right one, and it is not the one R2 needs.*
  Because the Hop stays charged and the invocation is never replayed, the
  predicate decides only that nothing useful is discarded and nothing
  unreviewed is adopted; quiescence is *not* load-bearing for safety here, as
  it would be for a discarded Hop. That distinction is what keeps this slice
  from drifting into same-Hop retry, and the record states it as an argument
  rather than as a reassurance.
* *The decision to admit an open blocking Finding is right, and it is argued.*
  It deviates from the sibling durable-artifact predicate deliberately and for
  a stated reason (the record's own Case A; preserving Run-local Findings is
  the entire value of a same-Run resume), the sibling's stricter conjunct is
  left unchanged, and I verified in code that resume reads no Finding for any
  decision and writes none -- `resume_after_reconcile` touches `status`,
  `stop_reason` and `human_question` only. The predecessor draft's stricter
  choice would have refused the record's motivating case; the candidate was
  right not to inherit it.
* *The refusals to ship are refusals of substance, not of contract.* Class 2
  is refused because there is no sound disposition of the candidate -- adopting
  it would give the trusted-commit boundary nothing to validate, discarding it
  would destroy salvage material -- and the narrower "admit a historically
  anomalous Run after a human restored the tree" form is identified, priced as
  a change to a shared pure-core invariant, and deferred with a trigger precise
  enough to act on. Class 6 is priced as a widening of O8's authority surface
  for zero recorded occurrences. Neither reason is "a contract forbids it",
  which the Beta rule would not have allowed.
* *The benefit is split honestly.* Half one (a named diagnosis for every
  post-dispatch interruption) serves both recorded occurrences; half two
  (same-Run recovery) is admitted to be of unmeasured frequency, with the
  observation that entry 14's own cause is now refused pre-dispatch by O3O2 and
  that resume does not diagnose a cause at all. A candidate that shipped on
  half two alone would have overclaimed.

=== 3. The blocking Finding

*Invariant.* A normative statement the slice writes about current behaviour
must be true of the behaviour the slice ships
(`docs/developer_guide/ch03_engineering_conventions.adoc`: names, errors and
nearby comments state current behaviour; the slice's own acceptance requires
the record's evaluation to be evidence-backed, and the binding docs-sync
clause requires editing what became inaccurate or misleading).

*What the candidate states.* In four places, that the retirement of the
already-reconciled predecessor dispatch marker is necessary for the Run to make
progress at all:

* `docs/backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc`, "The one new effect, and its
  mandatory ordering": "Without that, the continuation re-enters
  `slice4.run_real_one_hop`'s stale-marker branch (`slice4.py:201-238`),
  re-reconciles the identical already-charged uncertain Hop and *the Run can
  never progress*".
* `docs/operator_manual/ch06_recovery/01_outcomes.adoc` (Authority::
  *normative*), the new `[[quiescent-interruption]]` section: "Without that the
  engine would re-enter its stale-marker branch and re-reconcile the same
  uncertain Hop *forever*."
* `src/workflow_coordinator/frontdoor/lifecycle.py:1289-1296`, the comment on
  the retirement, in the same words.
* `tests/unit/test_quiescent_interruption_reducer.py:147-152`, whose docstring
  claims the demonstrated reducer call is "the exact call
  `slice4.run_real_one_hop`'s stale-marker branch makes on re-entry".

*What the source does.* The cited branch is guarded by the Run's schema
version: `slice4.py:201` reads
`if run.schema_version == 3 and existing.role == "uncertain_dispatch":`. The
Front Door renders every Consumer Request's profile at `schema_version: 2`
(`commissioning.py:358`) and therefore creates schema-2 Runs
(`model.py:1122`) -- which the candidate's own `Design` limit 2 states as the
reason the checkpoint projection cannot refuse here. A continuation launched
by `_continuation_engine_argv` (`frontdoor/lifecycle.py:766-793`,
`--continue-existing`) loads that same schema-2 Run. So for *every* Run that
can reach the shipped class through the Front Door the cited branch is
unreachable; re-entry takes `slice4.py:239-246` instead, which reads the
evidence file, writes a checkpoint, *unlinks the stale marker itself* and
returns the Run unchanged at `READY`, after which `operator.py:1022`'s
`while run.status is RunStatus.READY` loop dispatches the next Hop normally.
The cost of omitting the retirement is therefore one wasted engine iteration,
not a Run that can never progress.

*Why this blocks.* The statement is not a side remark: it is the entire stated
justification for the slice's one genuinely new effect, and for the rollback
machinery that restores the marker's bytes. It is asserted in a chapter marked
`Authority:: normative`, where an operator and a future slice will read it as
current behaviour, and it is the kind of claim the Commission explicitly told
this candidate's author to re-verify against the source. A later Run that
trusts it will either over-build on a liveness requirement that does not exist
for the shipped class, or fail to notice that the real motivation is a
schema-3 shape that cannot currently occur.

*What is not wrong.* The retirement itself is safe, correctly ordered and
correctly rolled back, and I am not asking for its removal. It is
information-preserving (the predicate proves no staged attempt refers to the
marker), it enables no replay (the Hop id stays in `run.hops`), it avoids the
wasted iteration, and it *is* required if a schema-3 Run ever continues
through the Front Door. The refusal of an uncorrelated or unreadable marker is
an independent and worthwhile safety gate and should stay.

*Feasible correction, bounded.* State what is true in the same four places: the
cited re-reconcile branch applies to a schema-3 Run; for the schema-2 Runs the
Front Door creates, an un-retired marker costs one engine iteration that
retires it itself (`slice4.py:239-246`) before the `READY` loop dispatches
again; the retirement is kept deliberately, to avoid that iteration and to
remain correct for a schema-3 continuation. No code change is needed, and the
test's docstring needs one clause.

=== 5. Simplicity and maintainability

The candidate chose the small complete class over a framework, and I agree
with the choice and with its stated reason: two predicates of the same shape
dispatched in one place (`_diagnose_recovery`) carry less machinery than a
registry would, and a third class is a third function and one more branch. I
checked the three places where this slice could have accreted and did not:

* *No new CLI surface.* A flag on the command that already owns the operator
  decision, as O8 decided for `wfc extend-budget --preview`. A `wfc recover`
  would have split one decision across two surfaces with its own refusal
  vocabulary.
* *No new state.* The predicate is a pure total function of the persisted Run;
  nothing is added to `Run`, the checkpoint or the journal schema beyond
  additive record fields. `reconcile_reason`/`reconcile_anchor` are
  deliberately not cleared, and I verified the safety of that: no admission,
  dispatch or reduction path reads either field (only persistence, audit,
  report and the predicate's own scope gate do), and the scope gate is the
  Run's *status*, so stale provenance can never re-admit a resumed Run.
* *No duplicated truth across the producer/consumer seam.* The six recorded
  shape constants are named once in `reducer.py` and imported by
  `persistence.py`, and the new pure-core suite drives the *real* producer into
  the predicate rather than a hand-built Run -- which is the test on both sides
  of the seam that this repository's conventions ask for, and the single most
  valuable thing in the test diff.

The one place where the shipped mechanism exceeds its stated need is the
marker retirement and its rollback, which is the Finding -- and I am asking
for the claim to be corrected, not for the mechanism to be removed, because
the mechanism is cheap, safe and correct for a schema-3 continuation.

=== 6. What I tried to break

* *Can a Run reach the predicate's admitting shape without having been
  interrupted?* No. `require_reconcile(reason="interruption")` has exactly one
  production call site (`persistence.py:202-204`, reached only from
  `slice4.py`'s three post-marker paths); `reducer.py:675` passes
  `mechanical_recoverable` and `lifecycle.py:1236` passes the same; no
  production caller passes `prerequisite_return`. Grep over `src/` is
  exhaustive.
* *Can a question or a semantic stop be stepped over?* No. `record_hop` clears
  `human_question` (`model.py:1167`) before `require_reconcile` writes its
  boilerplate, and the idempotent re-entry branch (`persistence.py:201`) calls
  no `record_hop` and so preserves it -- I executed both. Any other value, and
  any non-null `semantic_stop`, refuses by name.
* *Can an unreviewed candidate be adopted?* No. `actual_commits` empty *and*
  `base_head == end_head` *and* `end_head == current_head == reconcile_anchor`
  means nothing entered history and HEAD has not moved since the charge; the
  anomaly conjunct excludes a dirty tree by construction; and the boundary
  re-observes a clean worktree at the exact recorded HEAD before any mutation.
  Three independent gates.
* *Can the recovery loop?* No. Each resume is one human action charging
  nothing; each further interruption charges one more Hop; the budget bounds
  the count and an exhausted budget refuses by name. No new counter, which is
  the right answer.
* *Does the launch-failure rollback leave a half-recovered checkout?* Not in
  the code: the Run snapshot, the checkpoint *and* the marker bytes are
  restored, the rollback is journaled, the lock is released and the error
  re-raised. Note that every pre-mutation check -- including the new marker
  correlation and the engine resolution -- runs before the lock is taken, so
  the pre-mutation ordering the earlier `F004` correction established is
  preserved, not weakened. The one crash window the candidate admits (killed
  between `mechanical_recovery_resumed` and the continuation's own `classified`
  record) is pre-existing, shared with the sibling class, and honestly recorded.
* *Does the new `wfc report` line overclaim?* No. It fires for every
  `interruption` reconcile, including class 2, but says "run
