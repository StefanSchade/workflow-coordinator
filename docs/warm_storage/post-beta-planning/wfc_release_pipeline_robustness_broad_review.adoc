=== Blocking Finding B1 — the two new `| tee` pipelines un-gate G2 and G3

*Invariant.* A release gate enumerated in
link:../../developer_guide/ch04_release_management.adoc#release-gates[chapter 4's
gate list] is release-blocking ("Every gate is release-blocking; there is no
advisory class, *scoped to the enumerated gates G1-G8*"), and the FTR's W5
design requires that "nothing new is computed and *no step's exit status
changes*". The Commission's withheld authority adds "no weakened or deleted
test".

*What the candidate does.* `.github/workflows/release.yml`:

[source,yaml]
----
      - name: Required test suite          # :87-108, no `shell:`, no `set -o pipefail`
        run: |
          ...
          python3 scripts/wfc_test_inputs.py exec \
            ... -- python3 -m pytest -q | tee "$RUNNER_TEMP/pytest-output.txt"

      - name: Distribution content audit (C2, G3)   # :116-117, same
        run: make dist-audit | tee "$RUNNER_TEMP/dist-audit-output.txt"
----

Neither `run:` block sets `shell:` and neither contains `set -o pipefail`
(the file sets `set -euo pipefail` only at `:121`, `:166`, `:253`, `:260`
and `:400` — not in these two steps, and there is no `defaults: run: shell:`
key anywhere in the file). A pipeline's exit status is that of its *last*
command, so both steps now report `tee`'s status, which is 0 whatever
`pytest` or `make dist-audit` did.

*Reproduced locally.* Running the two shell forms GitHub documents:

[source,text]
----
bash -e -c            'python3 -c "raise SystemExit(1)" | tee /dev/null'  -> exit 0
bash --noprofile --norc -eo pipefail -c  (same pipeline)                  -> exit 1
----

`scripts/wfc_dist_audit.py:145,151` returns a non-zero status on a violation
(`raise SystemExit(main())`), so G3 was a real gate before this change, and
`make dist-audit` without the pipe failed the step under `bash -e`.

*Why the candidate's justification does not hold.* The verification record's
section "One more external assumption: GitHub Actions' default shell is
`pipefail`" states "GitHub's documented default for a `run:` step on a Linux
runner is `bash --noprofile --norc -eo pipefail {0}` -- `pipefail` already
on". That is not GitHub's documented default; it is the shell GitHub uses
when a step *explicitly* sets `shell: bash`. The documented default when
`shell:` is omitted is `bash -e {0}`, without `pipefail` (GitHub Actions
workflow-syntax reference, the `jobs.<job_id>.steps[*].shell` table; I
fetched and read that page in this Hop). The claim is therefore not merely
an unverified external assumption but a statement contradicted by the
authoritative source, and the implementation rests on it. The record's
"What changed" section repeats it ("GitHub Actions' default shell already
runs with `-o pipefail`, so this does not change either step's exit
status").

*Consequence.* On a hosted run, a failing required suite or a failing C2
audit leaves `check` green. `publish-testpypi` needs only `check`, so the
chain continues to the real TestPyPI upload and on to `publish-pypi`. Two of
the five pre-tag gates in ch04's enumeration (G2 "required suite green", G3
"both artifacts contain exactly the C2 allow-list") would no longer block,
which also makes `ch04:260` and `ch04:271-272` untrue of the pipeline as
integrated — the opposite of AC-8. This is a reproduced violation of an
explicit criterion and of the design's own "no step's exit status changes";
I do not downgrade it for the low likelihood of a red suite.

*Feasible, simpler correction* (the Worker chooses; all of these stay inside
`.github/workflows/release.yml`):

. Minimal: add `set -euo pipefail` as the first line of the "Required test
  suite" block, and turn the `dist-audit` step into a block beginning with
  the same line. One line each; matches the five other blocks in the file.
. Or drop the pipes entirely and keep the capture without a pipeline, e.g.
  redirect to the file and `cat` it, exiting with the command's own status.
. The `tee`/capture mechanism itself is sound and proportionate: W5 needs
  the suite's own summary line, and only a captured copy makes it available
  to a later step. No further mechanism is needed.

The verification record's two statements about the default shell must be
corrected in the same correction Hop; the record is the slice's evidence and
currently asserts a false fact about the platform.
