=== 4. Blocking Findings

[[b1]]
==== B-1 -- The "no in-place Hop-budget raise" statement is not marked as planned

The texts state the absolute:
`references/commission.md:119-120` -- "there is no in-place raise once a Run
stops on an exhausted budget -- a fresh Commission is required" -- and
`references/stops-and-evidence.md:84`, whose `awaiting_human_budget` row
prescribes "Prepare a successor Commission at the same scope, program and an
unwidened Hop budget" and lists "Raising the Hop budget" as needing a human.
Neither carries a planned marker, and `grep -rn -i "extend\|extension"` over
`src/workflow_coordinator/agent_skill/wfc/` returns *nothing*. The record's
implementation note has no row for it either (it mentions O7 once, at
`:243`, and O8 nowhere).

The Commission's binding updates name this statement explicitly, in the same
list as the four the candidate did mark: "no in-place Hop-budget raise (O8;
decision D7a: an explicit, journaled, maintainer-authorised extension will be
added, an agent never extends a budget on its own; D7b: no Worker-only
Finding closure)", and the Acceptance requires every binding update to be
"marked as planned where the plan says so". D7a makes the sentence a
statement that a decided slice will falsify, which is exactly the condition
the ownership rule exists for: the plan's four-row table predates D1-D7 and
is not the current specification; the task text is.

This is not cosmetic. The sentence is the operator's reason to budget
generously up front, and `awaiting_human_budget` is the stop the plan's own
friction entry 19 records as costing a discarded successor Commission. A
reader who learns the rule as an absolute will not look for the extension
that D7a admits.

*What would resolve it:* one clause on each statement, naming the planned
explicit, journaled, maintainer-authorised extension and keeping the two
properties D7a and D7b preserve -- that an agent never extends a budget on
its own, and that Finding disposition stays with the independent reviewer.
`commission.md` (153 lines) and `stops-and-evidence.md` (182 lines) both have
room under the 200-line contract limit. Add a row to the record's table with
the `path:line` of the amended statements.

[[b2]]
==== B-2 -- "A successor Run always enters at the implementation phase today" is missing

The statement appears nowhere: not in `SKILL.md`, not in any
`references/*.md`, not in the three edited manual pages, not in the record's
table. `grep -rn -i "implement"` over the skill returns only four unrelated
hits ("implementation identity", "as implemented and practised").

The Commission's binding updates require it: "a successor Run always enters
at the implementation phase today (O9 evaluates later-phase entry)". It is a
current, verifiable product fact -- `commissioning.py:369` hardcodes
`"initial_phase": "implement"` -- and it is operationally load-bearing in
exactly the way this slice is meant to capture: it is why a
verification-only or review-only successor still costs a Worker Hop at
`implement`, which is the substitute the plan's O9 entry describes ("friction
shows the substitute … works but costs a Worker Hop"). Without it an operator
sizing a successor Commission has no way to know that a review-only Run
cannot be commissioned today.

*What would resolve it:* one or two lines where the texts already discuss
preparing a successor -- `references/stops-and-evidence.md`'s
`Where a Run can continue` material is the natural home -- stating that every
Run, successor included, starts at the implementation phase today, with the
`commissioning.py:369` evidence in the record's table. Since O9 may end in a
reasoned stop rather than a change, "today" is the honest marking; it need
not be written as planned.

`stops-and-evidence.md:117-120` tells the reader "Two Runs may prepare and

*O-5 -- the Operator Manual does not carry the evidence-command gate rule.*

=== 6. Design, simplicity and what I probed and found sound

There is no mechanism to judge: the candidate adds no abstraction, no state
and no operational burden. Its complexity cost is paragraphs in a
context-loaded skill, and on that measure it is disciplined -- the four
`(Planned: …)` closes replace rather than append, the correction in `ch03`
*replaces* a wrong sentence with three right ones instead of adding a
caveat, and `SKILL.md` grew by four lines for the one thing a top-level file
had to say (that the `Never` list does not withhold `prepare-successor`).
I checked the alternative of carrying these statements in the manual alone
and reject it for the same reason the plan does: the Commission author is an
agent reading the skill.

Beyond the citations in section 2, I probed and found sound: that no `.py`
file and no test file is in the diff; that the `--config` second-file
workaround as written is actually executable (the file must be committed in
the Run's own checkout, because `verify.py:71` reads it from the tree at the
authorized HEAD and prelaunch refuses a dirty tree -- the texts say exactly
this); that `ch09`'s new `<<quickstart-evidence-location>>` xref resolves
(anchor at `:410`) and that every anchor the `AC-9` guard pins is still
present; that the two new manual links to
`FTR-WFC-RUN-CHECKOUT-PREPARATION.adoc` resolve to a real file; and that the
`wfc`-line guard in the skill content test is unaffected, because the new
`python -m workflow_coordinator.operator` invocations are inline code, not
fenced shell blocks.

One nuance I decided *not* to raise as a Finding: `SKILL.md:131-135` calls
`prepare-successor` and `export-salvage` "not a `wfc` subcommand", while
`frontdoor/cli.py:44-45` falls through unrecognized argv to `operator.main`,
so `wfc prepare-successor …` does dispatch. Neither is a registered `wfc`
subcommand with its own parser, the invocation the skill gives is correct and
matches `ch06_recovery/02_successors.adoc:131`, and the sentence's purpose --
lifting the `Never` rule for these two operations -- is served. It is a
wording nuance, not a wrong instruction.
