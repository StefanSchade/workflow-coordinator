Two things follow. First, the defect is real at both consequential sites and the
`preflight_hop` consequence is the trust-boundary one O1 called out: the gate whose

defect in the committed source — it is my probe deliberately destroying the
invariant *after* the fixed code establishes it, and it is the measurement that
proves the carried mtime is the whole mechanism. It is also the reason the
candidate's own forced test proves nothing about the fix (see <<e0b-b1,B1>>).

My natural rates (0.3–1 %) are lower than O1's 8/300 (2.7 %) for the same reason
O1 itself predicts: the failure probability is the elapsed time between the index
write and the copy divided by one second, and on this host that gap is 4–8 ms
(measured directly from the mtime deltas in the pre-fix exact-mtime runs below)
against O1's 13.6 ms. The mechanism explains both numbers; neither contradicts the
other.

`salvage_omissions`: the stat cache is *not* load-bearing. `ls-files --others
--ignored --exclude-standard` answers index *membership*, not stat freshness, so no
forced offset produced a wrong list (0/20 even with the copy 2 s in the future).
Fixing it anyway is correct and I would not have accepted leaving it: it is the
identical idiom at the identical boundary, and the task's own reasoning — "it must
not remain a trap for the next reader" — is the right standard.

=== 2. The fix: the shared helper is the simpler of the two options

One helper serving all four call sites, with the site-specific `mkstemp` prefix as
a required keyword, is the arrangement the task preferred and it is the right one
here: the four sites had byte-identical idioms, so the alternative (four
`shutil.copy2` calls) would have kept four copies of a rule that exists for one
reason. The diff removes 29 lines and adds 11 in the product file. The required
keyword (rather than a default) is a good call: it makes every site state its own
prefix, which matters because two live documents name those prefixes —
`docs/operator_manual/ch07_diagnostics/02_failure_modes.adoc:352`
(`/tmp/wfc-observe-index-*`) and the Front Door boundary plan at `:479` — and both
remain accurate. `tempfile.mkstemp` is still called without `dir=`, so the
documented "follows process temp settings, not a hard-coded `/tmp`" statement also
still holds. No documentation was owed by this change and none is stale.

Behaviour preservation, checked rather than assumed:

* The `GIT_INDEX_FILE` values are now `str(Path(...))` of the same `mkstemp` path —
  identical strings; confirmed by the 300-trial behaviour runs, which exercise all
  three sites end to end against real Git.
* No refusal, limit, error message or return shape was touched; no assertion was
  weakened; no `sleep`, retry, `skip`, `xfail` or marker was added in the product
  file. E0's test survives with its assertion byte-identical (only the new keyword)
  and passes 40/40 here.
* `_build_candidate_tree` (`:935`) is *not* a fourth copy site: its private index is
  written by Git itself (`read-tree` into a fresh `mkstemp` file), so no stat cache
  is carried over a byte copy. Independently confirmed.
* Other stat-sensitive copies in `src/`: I searched (`shutil.copyfile`,
  `shutil.copy2`, `shutil.copy`, `copytree`, and every `GIT_INDEX_FILE` use). The
  only other `copy2` is `frontdoor/archive.py:357`, which copies archive payload
  files and verifies them by SHA-256; no other index copy exists. The Worker's
  report on this point is correct.
* One behaviour *did* change, on the error path, and it was not intended: see
  <<e0b-b2,B2>>.

=== 4. Blocking Findings

[[e0b-b1]]
B1 — the forced-mechanism test is wall-clock flaky and fails against the correct product:: `tests/unit/test_index_copy_mtime.py:142`
(`test_observe_repository_reads_dirty_edit_as_clean_if_copy_mtime_is_forced_a_whole_second_later`)
asserts `facts.clean` after a same-size edit while `shutil.copy2` is patched to
stamp the copy 10 s in the future. That false clean only materializes when the
same-size edit lands in the *same whole second* as the staged entry's cached stat.
It is therefore a race the test has to win:
+
--
* Its exact body against the committed source: *6 failures in 400 runs* (1/100,
  then 5/300 — 1.5 %), each `forced-later copy did NOT produce a false clean`.
* Forcing the edit into the next whole second instead of hoping it stays inside the
  current one: *20/20 failures*. The dependence is on wall-clock alignment, not on
  anything the product does.

This violates an explicit acceptance criterion — "deterministic regression tests …
rely on no timing luck, sleep, retry, skip or xfail" and "Do not rely on wall-clock
races" — and it does so in the worst direction: an intermittent *failure* on a
correct, fixed product, i.e. a new flake added to the suite by the package whose
whole purpose is to remove one. The Worker's 40 and 60 clean file repetitions are
consistent with a 1.5 % rate (≈55 % chance of seeing nothing in 40 runs); they do
not establish determinism.

The test also carries no regression signal to weigh against that cost, as the
Worker's own docstring concedes: it patches `copy2`, which the pre-fix source at
this site never called, so it is "not itself a differentiator between the pre-fix
and fixed source". My right-hand column in section 1 is the same measurement and
shows why: once the invariant is destroyed after the fact, fixed and pre-fix
behave identically. Against the pre-fix source the test does fail — but because
the patch misses the `copyfile` call it meant to force, which is the inverse of a
regression signal: it reports "fail" for a source that does not call `copy2` at
all, whatever that source otherwise does.

Feasible, simpler correction: delete the test. The deterministic guard for this
site is the exact-mtime test (0/40 here, 20/20 pre-fix) and the behaviour guard is
`…observe_repository_reads_dirty_same_size_edit_through_the_copy` (0/300). Nothing
is lost but the flake. If the mechanism is worth stating for the next reader, the
helper docstring at `git_facts.py:882-895` already states it. A deterministic
alternative that keeps an executable demonstration is possible in principle
(pinning the worktree file's stat to the cached entry and disabling
`core.trustctime` in the fixture), but it buys a demonstration of Git's behaviour,
not of ours, and I do not request it — removal is the proportionate fix. No new
requirement is implied either way; what is required is only that no committed test
depends on winning a wall-clock race.
--

[[e0b-b2]]
B2 — the three sites lost their temp-file cleanup when the copy fails:: Before this
change, each site created the temp file and copied into it *inside* its
`try: … finally: os.unlink(...)` block, so a failing copy left nothing behind. The
shared helper is called *before* the `try`, so a copy that raises now leaks the
`mkstemp` file (empty or partially written) for the process lifetime. Reproduced by
raising `OSError(ENOSPC)` from the copy and counting leftover `wfc-*` files in a
private `TMPDIR`:
+
--
[cols="3,1,1"]
|===
|Site |pre-fix leaked |committed leaked

|`salvage_inventory` |0 |*1*
|`salvage_omissions` |0 |*1*
|`observe_repository` |0 |*1*
|`_isolated_index_copy` (E0's own, unchanged) |1 |1
|===

This is a behaviour change the task's withheld authority forbids ("no other
behavior change") and one the task's own DO (2) named explicitly: the shared helper
was to be adopted "keeping every existing behavior, prefix, cleanup and error
handling". I am not inventing a requirement — the cleanup existed at all three
sites and is gone.

It is not academic. The one recorded production failure of exactly this copy is
`ENOSPC` on a full `/tmp` at `/tmp/wfc-observe-index-*`
(`docs/operator_manual/ch07_diagnostics/02_failure_modes.adoc:352`), and
`observe_repository` runs at every Hop boundary, so repeated failures now
accumulate debris in the filesystem that is already exhausted — the regression
lands precisely where it hurts.

Feasible, simpler correction: unlink inside the helper when the copy raises
(`try: shutil.copy2(...) except BaseException: os.unlink(copied_index); raise`, or
the equivalent `try/except` that re-raises). That is three lines in *one* place and
it also closes the identical pre-existing leak at E0's `preserve_candidate` site —
strictly better than the four `finally` blocks the previous shape needed.

=== 6. Non-blocking observations

[[e0b-o1]]
O1 — the three "reads a dirty same-size edit" tests are worth keeping as they are:: They
pass deterministically after the fix because both timing branches reach the same
verdict, and before the fix they fail only at the natural rate (≈0.3–1 % here). They
are therefore weak regression detectors but zero-risk ones, and they document the
consequence in product terms rather than in `stat` terms. Keeping them alongside the
exact-mtime guards is the right arrangement; nothing to change.

[[e0b-o2]]
O2 — `_capture_copy_mtimes` records two entries per `copy2` and relies on the last one:: `shutil.copy2`
calls the module-level `copyfile` internally, so wrapping both names records the
inner data copy (fresh mtime) and then the outer corrected one. The helper's
docstring explains this and `records[-1]` is the state actually left on disk, so the
assertion is sound — but it is a CPython implementation detail. A stat of the real
copy (for instance by capturing the path the site used) would not depend on it. Not
worth a change on its own; worth knowing if the helper is ever extended.

[[e0b-o3]]
O3 — `copy2` adds a `copystat` failure mode that `copyfile` did not have:: A failing
`os.utime` on the fresh temp file would now raise `OSError` out of
`observe_repository`/`preflight_hop` where `copyfile` would have succeeded. On a
local `TMPDIR` file the process just created and owns this is not a realistic path,
and it is the same trade E0 already accepted at one site. Recorded only so that a
future move of these temporaries onto an exotic filesystem is made with open eyes.
The mode widening noted in E0's O3 (`0600` → the index's `0664`) now also applies to
the three sites; the same reasoning holds — these files carry index metadata that is
already readable to anyone who can read the checkout, and no site promised `0600`.

[[e0b-o4]]
O4 — the natural failure rate is host-dependent and the model predicts it:: 4–8 ms
index-write-to-copy gap here against 13.6 ms in E0's review, giving 0.3–1 % against
2.7 %. Anyone re-measuring these numbers on another host should expect a different
rate and the same mechanism; the exact-mtime tests are rate-independent, which is
exactly why they are the right guards.

[[e0b-o5]]
O5 — no documentation was owed:: The two live documents that name these temp prefixes
and the `mkstemp` placement
(`docs/operator_manual/ch07_diagnostics/02_failure_modes.adoc:352`, the Front Door
boundary plan `:479`) stay accurate because the prefixes and the `dir=`-less
`mkstemp` are preserved. The backlog's E0 entry
(`docs/backlog/_open.adoc:406-411`) already names E0b as the successor; recording
E0b's own outcome there is the maintainer's upkeep, not this Hop's scope.
