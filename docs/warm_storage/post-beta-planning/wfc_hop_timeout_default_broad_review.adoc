=== What I independently re-verified and found correct

  fallback in `_resolve_hop_timeout_seconds` and nowhere else duplicated.
* *Config key validation* -- `_hop_timeout_seconds` in `frontdoor/config.py`
  rejects `bool` (checked first, since `bool` is an `int` subclass in
  Python), non-`int`/`float`, non-finite (`NaN`/`inf`), and non-positive
  values, raising `CommissionError("Consumer Config.hop_timeout_seconds must
  be a positive, finite number of seconds")`, in the same message style as
  the neighbouring `boundary`/`max_autonomous_hops` keys. A config omitting
  the key yields `ConsumerConfig.hop_timeout_seconds is None`, so every
  existing construction and config is unaffected beyond the new built-in
  default -- confirmed by reading `consumer_config_from_yaml` end to end and
  by executing the new parametrized tests myself.

  config_path)` implements flag, then config key, then built-in default,
  exactly as required; `cmd_run` is the only call site, called once before
  `RunInputs` is built. The flag's argparse default became `None`, and the
  help text states the precedence and the 14400-second/4-hour default
  verbatim.

  `RunInputs` carries into `_authorize`, which journals it unchanged as

  `cmd_resume` read only the journaled record and were not touched, so `wfc
