=== Blocking Finding (proposed, `finding_id: null`)

*Invariant:* `rehearse.py` must answer an unresolvable `wfc` executable with
return code 2 and without creating anything, as the FTR's `Failure and
recovery expectations` table ("`wfc` missing or not answering `--version
--json` -> Return 2 with the command that was tried; nothing created") and
its return-code contract (1 is drift "with expected and actual printed", 2 is
usage or precondition) require.

*Reproduced*, in a freshly created workspace, for all three executable
resolutions the kit documents -- `--wfc <nonexistent path>`,
`WFC_BIN=<nonexistent path>`, and a bare `wfc` with nothing of that name on
`PATH`:

. `rehearse.py` prints the rehearsal banner,
. then dies in `subprocess.run(argv, ...)` at `rehearse.py:188` with an
  unhandled `FileNotFoundError: [Errno 2] No such file or directory: 'wfc'`
  (respectively the given path) -- a ~25-line Python traceback naming kit
  internals, and exit code *1*, the code the FTR reserves for "the rehearsal
  no longer matches this WFC version", with no expected/actual line,
. and leaves behind what step 2 already created: the worktree
  `greeter-run-t1-hello-page/` and the branch `demo/t1-hello-page` (`git
  branch --list` in `greeter/` shows `+ demo/t1-hello-page`).

The third point is what makes this more than cosmetic. The scenario's
worktree is single-use by design, so the reader who simply fixes the typo and
retries is refused: the next call prints `... already exists; a checkout holds
one lifecycle, so create a new workspace (make_workspace.py) to rehearse this
scenario again` and returns 2. One mistyped path therefore costs the whole
workspace, and the message the reader gets for it never mentions the real
cause. `make_workspace.py` preflights exactly this case (its AC-2 refusal
`could not run \`<bin>\` --version --json`, return 2, nothing created); the
new runner shares the executable resolution (`_resolve_wfc`) but not the
check.

*Feasible minimal correction*, inside the authorized scope and without new
mechanism: probe the executable in `_check_preconditions`, before
`_create_worktree`, and raise the existing `PreconditionError` -- the same
`wfc --version --json` probe `make_workspace.py` already performs (which also
covers "not answering `--version --json`"), or at least a resolvability check,
plus the same one-line treatment for `git` while that function is open
(`make_workspace.py` preflights `git` on `PATH`; `rehearse.py` would traceback
in `_create_worktree` without it). One regression test in the style of the
existing `test_preflight_refuses_when_wfc_is_not_found` -- return 2, a
distinctive substring, and `not (workspace / "greeter-run-<scenario>").exists()`
-- pins it. No behaviour of the four scenarios changes.

O-1 -- `t3-probe-refusal`'s expected classification is never compared, and cannot be::
`wfc run` prints `CLASSIFICATION:` only from `_print_result` for a classified
lifecycle; a baseline-probe refusal raises `LifecycleError` and prints
`wfc run: baseline probe failed with exit code 2; no provider ran` with exit
23 and *no* classification line (`frontdoor/lifecycle.py`: `refused_probe` is
a classification with exit code 23, but it never reaches `_print_result`).
The FTR's own `rehearse.py` rule is conditional ("*if* the output contains a
`CLASSIFICATION:` line"), so the candidate is faithful to its specification
and `expected_classification: "refused_probe"` in the scenario file is
exactly what the FTR's scenario table prescribes -- but the value is dead
data today, and AC-4's "shows the expected classification" is only reachable
for three of the four scenarios. The candidate's test replicates the same
conditional and, correctly, excludes the trailing `wfc status` output (which
prints `CLASSIFICATION: not_launched` here) from the comparison, so nothing
is asserted falsely. This is an FTR/CLI mismatch to settle at maintainer
level -- either by accepting the dead field or by having the scenario declare
an expected *message* fragment for this one case -- and not something the
slice should resolve by guessing; the task's own instruction was to report the
difference precisely rather than bend the scenario.

O-2 -- the Evidence repository's commits carry the machine's identity, not the demo identity::
SI-7 asks for "the demo identity on every commit". In the consumer
repository that holds (`WFC Demo <wfc-demo@example.invalid>`, set
repository-locally in step 2). The Evidence repository, created by `wfc
init`, gets no identity, so both its commits -- `chore: initialize WFC
Evidence repository` and the rehearsal's `evidence: archive ...` -- are
authored by whatever Git derives from the machine (here `Stefan Schade
<stefan@agent-vm.home.arpa>`, from the passwd entry and the hostname, since
the isolated `HOME` hides the user's own configuration). The reader's real
name and hostname therefore land in a workspace the kit advertises as leaving
"no trace", and a rehearsal is not identifiable from those commits. The FTR's
step list does not ask for an identity there, so I am not blocking on it and
am deliberately not adding a step of my own; the one-line close, if the
maintainer wants it, is the same `git config user.name/user.email` pair on
`greeter-evidence` in `make_workspace.py`'s step 3. Related, for S3 only: an
environment where Git cannot derive an identity at all (a container or CI
runner with an unqualified hostname) would fail that archive commit with the
isolated `HOME`; I could not reproduce that here, because WFC strips `GIT_*`
from the environment of its trusted bootstrap, so I state it as a risk to
check when AC-10 is built, not as a defect.

O-3 -- the `wfc report` inspection runs without the rehearsal environment::
Of the three inspection commands, `wfc status` is executed with the isolated
rehearsal environment (and the printed command line shows the `HOME=...`
prefix), while `wfc report` is executed with the inherited one. The
consequence is visible in the output: the report line reads `not done
limits: no_lifecycle_facts`, where the same report with
`HOME=<workspace>/rehearsal-home` would have the lifecycle facts. Nothing is
written to the real `HOME` (my throwaway `HOME` stayed empty, so SI-9
holds), and the FTR does not prescribe the environment for this command, so
this is a quality-of-demonstration point: passing the same `env` would make
the archived record the reader is pointed at as informative as the one
`wfc run` just printed.

O-4 -- WFC's `stderr` is replayed on the runner's `stdout`::
`rehearse.py` writes the captured `stdout` and then the captured `stderr` of
`wfc run` to its own `stdout`. The text is unchanged, as the FTR asks, but
the stream and the interleaving are not preserved, so a reader piping
`stdout` to a file also captures WFC's diagnostics, and a failure line can
appear after output it actually preceded. For the drift case the runner's own
one-line diagnosis does go to `stderr`. Cosmetic; the fix, if ever wanted, is
one argument (`file=sys.stderr`) on the `stderr` replay.

O-5 -- the boundary test no longer pins what it covers::
After the O-4 rewrite, `test_kit_modules_import_only_the_standard_library`
asserts only `assert modules` ("the kit ships at least one module"), so the
test would still pass if `scripted_provider.py` or `rehearse.py` disappeared
from the kit. The acceptance text speaks of "the three kit modules". A
superset assertion -- the globbed names contain `make_workspace.py`,
`rehearse.py`, `scripted_provider.py` -- keeps O-4's iteration and restores
the guarantee for one line, without reintroducing an exhaustive list that the
next slice must edit. No current defect: the scenario tests would fail loudly
if either module were missing.

=== Maintainability and simplicity

The slice is proportionate and I found nothing worth giving up.
`rehearse.py` is 225 lines of flat procedure with one exception type mapped
to one return code, no state beyond paths, and no abstraction over WFC: the
`wfc run` argument list is assembled in one function and visible at a
glance. `scripted_provider.py` is 145 lines and stays a near-literal copy of
the fixture's contract plus the containment check -- which is the right
shape here, because the FTR and the task both require an independent copy
with no shared module across the standard-library boundary; the cost is
knowing that two files implement one contract, and the scenario tests are
what will catch their divergence. The scenarios are data, not code, and the
FTR's family-neutral `disposition` key keeps each scenario ignorant of which
contract family a phase uses -- a real simplification, worth the small
renaming function. The alternatives I weighed are each worse: a shared helper
between kit and fixture breaks the boundary; a cleanup-on-failure path in the
runner contradicts SI-2 and the FTR's "no automatic clean-up"; and parsing
`wfc status` instead of the consolidated report's `archive` line to find the
Attempt would add a second output format to depend on. The one place where
less mechanism would be better is the opposite of a safeguard: the missing
executable check of the blocking Finding, which is a *reuse* of a check the
kit already owns, not a new one.
