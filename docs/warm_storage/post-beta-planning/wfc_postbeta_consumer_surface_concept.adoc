[[experience]]
== Problem and current Beta 1 user experience

A new developer reaches WFC through `README.md`, which PyPI also renders. Its "Where to start" list links six tag-pinned GitHub pages *[V]*. The content behind them is sound and unusually honest about what was verified. Four things stand between a newcomer and a first understanding.

. *The demo link lands on a page with dead references.* "Run a small demo" points at `docs/operator_manual/ch09_consumer_quickstart/02_first_run_example.adoc`. GitHub renders a leaf file on its own; that page refers to the preceding leaf with in-page anchors that exist only in the assembled manual. Rendered standalone, 8 of its 10 in-page references are dead (five anchors, among them prerequisites, install and limitations); the Level-1 worked sequence has 2 of 2 dead *[O]*. Gate G5 renders only the assembled books and cannot see this *[V]*.
. *The first Run is typed by hand.* The example builds its repository from about sixty lines of shell here-documents, then asks the reader to hand-author a Consumer Request YAML containing a commit hash *[V]*.
. *Nothing shows a Run happening.* Both example pages state that `wfc run` was not executed for them *[V]*. The reader sees the preview and then a description. The only recorded real consumer Runs are the two Q1 smokes (`robust@v1`, two Hops, about one minute each) in the release-management chapter, written as a qualification record *[V]*.
. *The interesting behaviour is invisible.* A review Finding, a correction cycle, a human-required stop and a probe refusal are described across four manual chapters. Seeing one requires a paid, non-deterministic provider Run that happens to go wrong.

What is already right and must be kept: one canonical manual, tag-pinned links enforced by the release preflight, explicit "verified / not verified" statements, and a cost paragraph that promises nothing *[V]*.

[[reference]]
== Reference-project evidence

[[ref-pages]]
=== Versioned documentation publication

The Pages repository holds only generated output: `versions/<tag>/core/`, `versions/<tag>/demo/slides/`, the moving `latest/` copies, a root `index.html`, and a vendored Reveal.js bundle that is 5.2 of its 6.0 MB *[R]*. It publishes a deliberate subset, the user guide and the release notes; developer documentation is kept out by design *[R]*.

What the mechanism needs, per the core release chapter and workflow *[R]*: a `publish-docs` job sequenced after the PyPI upload; a write deploy key stored as a repository secret, with pinned SSH host keys; a shared concurrency group and a five-attempt rebase-and-retry push, because two publishers write one branch; a PEP 440 comparison to keep `latest/` from rolling back; a root page whose version table is edited by hand per release; a helper that rewrites README links from `latest/` to `versions/<tag>/` before tagging, because PyPI freezes the README; a post-deploy structure check; and a toolchain of Asciidoctor, PlantUML, Graphviz and Java. The release runbook that carries this is 1,064 lines. The local clone holds one release (`v0.1.0b6`); the root-page source names `v0.2.2`, `v0.2.1` and `v0.1.0b6` but not `v0.2.0`. Whether the later snapshots are online is unverified.

The decisive point for WFC: that machinery is earned by three repositories publishing into one site and by PyPI pages that link to a moving `latest`. WFC has one repository and links only tag-pinned URLs.

[[ref-demo]]
=== Standalone demo repository

The demo is small and runnable: 79 tracked files, a README that is itself an eight-step first-hour tutorial, checked-in data and pipeline configurations, a launcher, and nine test modules that run the curated journeys *[R]*. Three properties matter here.

* *Its examples are qualified for free.* Every journey is a deterministic, offline `pytest` case against the installed library; CI is install, tests and a CLI smoke *[R]*. WFC's real Runs are neither deterministic nor free.
* *It drifts.* The demo pins `spreadsheet-handling==0.1.0b6` while the library is at `v0.2.2`, three releases and five months later; its last commit is from July, its `dev` branch is 13 commits ahead of `main`, and its last tag is `v0.1.0b6-demo` *[R]*. The design accepts a lag ("bumping the pin lags the PyPI publish by design"), and the lag became permanent.
* *It needs a cross-repository release sequence*: core, then demo pin and tag, then Pages as a consequence, with a helper that inspects all three checkouts *[R]*.

[[ref-tutorials]]
=== Progressive tutorials

The ACME series is two slices: a plain round trip and a cross-table round trip. The first ends by announcing a second slice about helper columns that does not exist *[R]*. The maintained first-hour path is a different example (the product business slice), and the index labels one further trail "optional, clearly secondary" *[R]*. What transfers is the shape of a slice: one goal, the source data, one command, what to inspect, why the next slice follows. What does not transfer is the number of slices.

[[ref-slides]]
=== AsciiDoc and Reveal.js walkthroughs

Each walkthrough is one AsciiDoc file with a `revealjs` backend header, so the same source is a document and a deck; every second-level section is a slide *[R]*. Rendering needs the `asciidoctor-revealjs` Ruby gem (pinned in CI) and a Reveal.js bundle, vendored into the Pages repository for publication and loaded from a CDN locally *[R]*. The decks are static: prose, code blocks and, for one journey only, five hand-captured screenshots with a capture log *[R]*. They exist online only because the Pages repository exists.

[[eval-demo]]
=== Demonstration

A static example repository suits a library, where one clone serves any number of runs. It suits WFC less: a checkout authorizes one lifecycle *[V]*, a second `wfc run` in it is refused ("a lifecycle already exists for this checkout") *[O]*, and the request must name a commit of the very repository it runs in. The WFC equivalent of a demo repository is therefore a *generator of fresh consumer repositories*, not a repository to clone.

Placing the generator in this repository instead of a sibling removes the drift observed in the reference: the kit is tagged with the product, tested by the product's suite, and has no pin to bump. The price is that a reader obtains it from the tagged source tree instead of from PyPI (D5 would remove that step at the cost of a package change).

The workspace the kit creates makes the six artefact classes physical:

[cols="3,5",options="header"]
|===
|Artefact class |Where it is in the demo workspace

|The repository being modified
|`greeter/`, a Git repository with no remote, and one worktree of it per Run

|Commission and authorized scope
|Requested in `requests/` outside the repository; committed by `wfc run` under `.wfc/governance/<commission-id>/`; bounded by the scope ceiling in `.wfc/config.yaml`

|Execution configuration and provider bindings
|`.wfc/config.yaml` and the `--execution-override` and `--executable` arguments of the Run; never part of the Commission

|Checks and review artefacts
|`checks/check.sh` (baseline probe and task-check) and `docs/reviews/*.md`, written by the reviewer role

|Trusted commits
|The Commission commit and one Coordinator commit per Hop in the worktree's Git log

|Run state and archived Evidence
|Lifecycle state under the state directory outside both repositories; `greeter-evidence/archive/...`, a second Git repository
|===

*A rehearsal is not a Run of a model.* With the released wheel and a copy of the test suite's scripted provider, this review ran, offline and in seconds *[O]*: a `robust@v1` Run of five Hops (implement, a broad review opening a blocking Finding, a correction, a focused review resolving it, a renewed broad review accepting), six trusted commits, an archived `audit.json` with the Finding's history; a Worker stop classified `awaiting_human` (exit code 10); and a baseline-probe refusal (`refused_probe`, exit code 23) with no provider at all. That demonstrates WFC's control flow, authority boundaries and evidence. It says nothing about what a model does with a task. Every rehearsal therefore binds the model name `rehearsal-no-model`, so the archived record identifies itself, and prints a banner before and after.

One practical discovery belongs in a tutorial: a check that runs Python tests writes `__pycache__` directories, and the baseline probe then refuses the Run ("baseline probe mutated the repository") unless the repository ignores them *[O]*. The existing example checks do not surface this.

[[eval-slides]]
=== Walkthrough media

A deck communicates sequence and appearance. In the reference the appearance is a workbook, which prose cannot show. A WFC Run's appearance is terminal output, a Git log and a report, which a rehearsal prints from the installed version and a document quotes as text. A deck would add a Ruby gem, a JavaScript bundle and a hosting dependency on the deferred Pages repository, and its one-slide-per-section rule would shape the tutorial source. The single thing a diagram does better, the layout of the workspace, fits one plain-text block (W3).

[[target]]
== Recommended target experience

. *Learn.* The README names three audiences in three lines. "See a Run without an account" leads to the tutorial index: a short map of the workspace, then two commands.
. *Look.* With WFC installed and this repository's tag checked out:
+
[source,shell]
----
python3 examples/consumer-demo/make_workspace.py ~/wfc-demo
python3 examples/consumer-demo/rehearse.py ~/wfc-demo t2-farewell
----
+
The second command prints a five-Hop Run with a Finding and a correction. The reader inspects `git log` in the Run's worktree and `wfc report`. Deleting `~/wfc-demo` removes every trace.
. *Try.* The same tutorial's live section gives the `wfc plan` and `wfc run` commands for a fresh worktree with the reader's own adapter and model, and says what may differ from the rehearsal.
. *Delegate.* Once the Agent Skill exists, an agent drives the same tasks in the same workspace.

[[skill]]
== Relationship to the Agent Skill workstream

The Agent Skill review and its record `FTR-WFC-AGENT-SKILL-DISTRIBUTION` are on the branch `docs/agent-skill-distribution` (`04ff81d`), not yet on `main`; this review reads them and changes nothing there.

* *Ownership stays single.* The Operator Manual owns procedures, the skill owns the agent's operating guide, the tutorials own the examples. A tutorial links to the manual and never restates a rule; the skill may link to a tutorial as "a place to practise".
* *The demo workspace serves the skill's qualification.* That record needs "an unfamiliar consumer repository", a small bounded task and "a Commission built to stop". The kit provides all three. A workspace created by one command is also reproducible between the two hosts.
* *A rehearsal is not something an agent may substitute for a Run.* The scripted provider is an executable chosen by the human on the command line. Guidance grants no authority, and nothing in the kit changes what `wfc run` authorizes.
* *The Level-1 tutorial waits.* It is the skill's first worked example and should be written against the shipped skill, as a short page reusing Tutorials 1 and 2.
* *One conflict to manage.* Both proposals touch chapter 9 (the skill adds an install step to the quickstart; this adds tutorial leaves) and both register in `docs/backlog/_open.adoc`. Neither changes the other's text.

[[maintenance]]
== Maintenance and release implications

Per release, the adopted set asks for no manual step.

* The kit carries no version literal and no pin. Its tests run against the working tree in the required suite; slice S3 of the demo record repeats the rehearsal against the built wheel.
* Three small guards replace vigilance: a standalone-render check for consumer pages, a byte comparison between the kit's files and the blocks that quote them, and the rehearsals' expected classifications.
* The release contract is untouched: neither artefact gains a file (the audit already fails on anything unlisted), README links stay tag-pinned, and G5 covers the new leaves through the assembled manual.
* What can break: the scripted provider speaks the Codex adapter's invocation shape and reads fields of WFC's Hop prompt. Both are internal. A change to either fails the kit's test in the same change, which is the reason the kit lives here.
* A live confirmation of Tutorials 1 and 2 is a maintainer activity with usage cost, recorded per adapter. It is not a recurring gate.

[[deferred]]
== Deferred options and conditions for reconsideration

P2 Pages repository:: Reconsider when a second consumer exists (MD-4), or when readers demonstrably need the assembled manual online, or when a second repository needs to publish into the same site. Start from P3.
P3 Release asset:: Reconsider on the first request for an offline or single-file manual; it needs a decision on whether the rendered file is release content.
D4 Standalone demo repository:: Reconsider when external users ask for something to clone without the source tree, when lifecycle rotation is decided (a clone would then serve more than one Run), or when the skill's qualification wants a public repository no agent has seen. If created, it must be generated from the kit by a documented command and validated by running the kit's rehearsals against the released wheel, never maintained by hand.
D5 Kit in the package:: Reconsider if obtaining the kit from the source tree proves to be the barrier. It reopens the C2 allow-list and adds a subcommand, so it belongs with the next deliberate package-surface change.
T5 Level-1 tutorial:: After the skill's command slice is implemented.
