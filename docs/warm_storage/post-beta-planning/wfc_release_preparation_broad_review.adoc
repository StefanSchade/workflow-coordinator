== Simplicity and maintainability

The design is proportionate and, in the reviewer's judgement, close to the
simplest thing that meets the authorized objectives. Three rules and one
module-level table carry the whole surface; the table is data, read by both
the tool and the tests; idempotence is obtained from the refusal list rather
than from a second mechanism; validate-then-write-all gives
all-or-nothing with one dictionary and no temporary files, no lock, no
journal and no rollback path to maintain. No new abstraction, state,
dependency or operational step was added beyond the one `make` target the
FTR asks for. The reviewer looked for a materially simpler alternative and
found none that keeps the same guarantees: dropping the `exact_one`
distinction would let a dropped literal pass silently, and a single
repository-wide version substitution -- the obvious "simpler" option -- would
corrupt the digest-pinned fixtures and the historical records enumerated
above.

The one real coupling worth naming is deliberate and fail-loud: the
`install_pin` patterns quote prose (`\bOnce <v> is\b`,
`` `==<v>` pin installs ``). Rewording that prose makes the tool *refuse*
with a named site rather than silently skip it, which is the correct failure
direction for a release tool.

== Non-blocking observations

O1 -- the runbook's prepare step says "in one commit":: `ch04:303-305` now
reads, in the present tense, that `make release-prepare VERSION=<v>` "sets
the version everywhere it is version-bearing and freezes the release-notes
heading *in one commit*". The tool runs no Git at all (an explicit FTR
non-goal: "no `add`, no `commit`, no branch ... it leaves ordinary
working-tree changes for review with `git diff`"). Read as the *shape of the
result* -- the bump arrives as one release commit instead of scattered hand
edits -- the sentence is true and matches both the FTR's own title and the
chapter's step 1 ("Push the release commit to `main`"), which is why this is
recorded as an observation and not as a blocking Finding. It is nonetheless
the one place where an operator could read a Git action into the command,
and the runbook nowhere tells them to review and commit the tool's
working-tree changes. A later chapter-4 slice could close both with one
clause, e.g. "... and freezes the release-notes heading, leaving ordinary
working-tree changes to review with `git diff` and commit as the release
commit". This slice owns the sentence but the maintainer owns the wording
question.

O2 -- lines counted as URLs:: the implementer's verification record says
README carries "ten `blob/v0.1.0b1/` URLs across lines 17-22, 34, 46, 56,
59". Those are ten *lines*; they carry *fifteen* URL occurrences (line 18
alone carries four). The FTR's `<<problem>>` table has the same conflation
("12 (10 tag-pinned URLs, 2 install/version pins)" are 12 lines). Behaviour
is unaffected -- the substitution is global per file, and the executed run
left 0 stale and 15 rewritten occurrences.

O3 -- the release-check failure count in the record:: the record says
`--tag v0.1.0b1` "fails only on the three topology facts". It reports four
(it also reports "working tree is not clean"), and with an attached HEAD it
selects *branch* mode even when `--tag` is given, so the branch-mode
assertions are the ones that fire. The substantive claim -- topology only,
no README-link failure -- is verified.

O4 -- duplicated refusal message:: the missing-file refusal prints one line
per *site* in the missing file, so deleting `references/setup.md` prints the
same `site file not found` message twice. Cosmetic.

O5 -- the relaxed tutorial regex is broader than "a WFC version"::
`\b[0-9]+\.[0-9]+\.[0-9]+[A-Za-z0-9.]*\b` would also be satisfied by a
three-component Python version, were one ever added to a "What was verified"
section. Today it matches only `0.1.0b1` in all three pages, and D4 asked
only that a version be named, so this is within the decision.

O6 -- residual of risk R-1 outside the two guards:: a *new* document
carrying a `blob/v<x>/` URL would fall outside both the surface list and
both guards (`README.md` has guard 2, the Agent Skill files have
`test_agent_skill_content.py:237`; nothing else is covered). No such file
exists today -- every live `blob/v` occurrence is accounted for in the table
above. The FTR scopes the guards deliberately, so this is noted as a
candidate for a later slice, not as a requirement withheld from this one.

O7 -- a `v`-prefixed version would be written verbatim:: `--version v0.1.0b2`
passes the PEP 440 pattern (PEP 440 permits the prefix) and would be written
as `version = "v0.1.0b2"` and `/blob/vv0.1.0b2/`. In practice the
release-notes-section requirement blocks it, since the heading would have to
have been authored with the `v` as well. Normalising the version before use
would remove the last path to it.
