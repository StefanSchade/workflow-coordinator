=== Simplicity and maintainability

This is the minimum that achieves the authorized objective: 144 moves, one
README, link targets, seven Project Memory values. Nothing else. No new script,
make target, metadata field, index, lifecycle state or per-group README; no
compatibility layer; no state; 135 of 144 documents are byte-identical and the
remaining 9 differ only in link targets. The permanent artefact count of
`docs/warm_storage/` rises by exactly one file, and what that one file buys is
the removal of a 144-file flat directory nobody could navigate. I looked
specifically for lasting complexity to object to and found almost none:

* The grouping is derivable from the filename, so no index must be maintained to
  place a file — the property that makes the ten directories cheaper than the one
  they replace. I verified this is true in practice, not just in principle, by
  re-deriving all 144 placements from the rule alone.
* Keeping every basename turns the entire package into renames, which preserves
  historical filename search and frozen Commission path strings for free. Giving
  that up (plan §9's rejected prefix-shortening) would have been the one change
  that made this expensive. It was not made.
* `operator-manual-consolidation/` holding a single file is deliberate per §4.1
  and is the right call: its later warm-to-cold retirement is one directory move
  rather than a file hunt.
* The one genuine standing cost is the README's `Files` column
  (<<d3-observations,observation 5>>), and it is an authorized criterion, not
  something the Worker added.

I found no materially simpler alternative that still meets the authorized
objectives — only alternatives that do less. I also did not ask for anything more:
in particular I did not and would not ask for a check that enforces the README
counts, which §9 already rejects.
