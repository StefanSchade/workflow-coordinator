=== 2. The design, judged before the code

The design is where the task required it -- a dated `Design` section of the
record the slice names, not a review artifact -- and it decides the five real
questions with the alternatives it rejected and the property each decision
preserves. I checked the two load-bearing constraints it rests on rather than
accepting them: `scripts/wfc_dist_audit.py`'s `WHEEL_SKILL_FILES`,
`scripts/wfc_release_prepare.py`'s `surface()`,
`docs/developer_guide/ch04_release_management.adoc` and
`tests/architecture/test_offline_distribution.py` do each enumerate exactly
the four packaged names, and `scripts/` is outside this Commission's declared
scope. SK-1 (no fifth file, redistribute inside the four) is therefore the
correct call, and recording the fifth-file option as a candidate that must
move the allow-list, the release surface and the distribution test together
is the right disposition rather than a quiet omission.

SK-2 is the decision I probed hardest, because it is the one new convention.
Reading from committed history at the base ref is the same rule the Runtime
already applies to `guidance.path` (`frontdoor/verify.py`) and to the
preparation hook (`frontdoor/prepare_checkout.py` reads both declaration and
hook at the base commit), so the convention inherits an existing invariant
instead of inventing one: a Run cannot author the notes the next Run is
operated by. The four rejected alternatives are rejected for reasons that
hold -- a config key or CLI would add a trust surface for something that
needs none, a directory needs an index and a traversal rule, a
repository-name check is excluded by the order and wrong in principle, and
`.wfc/operator-notes.md` is outside the committed ceiling (`src`, `tests`,
`scripts`, `docs`, `README.md`, `pyproject.toml`, `Makefile`,
`examples/consumer-demo`), so no ordinary Commission could write it. The
Markdown-over-AsciiDoc deviation is declared, bounded and justified by the
reader (an agent already reading the Markdown skill) and by consumers without
an AsciiDoc toolchain.

=== 4. Level 0 / Level 1 and the multi-Run correction

The separation is stated once, early, in the always-loaded file, and it is
accurate on both sides: Level 0 "executes exactly one Commission per Run …
takes no portfolio decision and orchestrates nothing -- it never chooses a
task, decomposes a goal, authors a Commission, launches itself or chains
Runs", which is what the Front Door actually does, and Level 1 is explicitly
"an external session, not a WFC component". The retired claim ("chaining
several Commissions automatically" listed as a case WFC does not fit) is
gone, and what replaces it keeps the Level-0 fact as a fact.

No authority boundary moves. Sequence is the default; a series is covered by
a delegation that already covers those packages; two Runs at once "need a
delegation that covers running them in parallel"; and the two technical
invariants are restated unchanged -- never two lifecycles in one checkout,
never two archive steps at once. The second is the real product behaviour
(`frontdoor/archive.py`'s narrowed cleanliness rule refuses the racing
attempt rather than corrupting anything), and the skill's archive paragraph
still says so.

This also removes a genuine contradiction rather than papering over one: the
skill had said two Runs may prepare and execute at the same time while
`ch10_level1_orchestration/01_operating_pattern.adoc` said unconditionally
"Launch *one Run at a time* … see the previous Run through to a terminal,
recorded state first". Both places now carry one rule, and ch10's own
`[[level1-sequences]]` section adds "Level 0 is untouched by any of this".
The correction matches the order's own wording ("only if the human's
delegation covers it, in parallel"), so it is the maintainer's boundary, not
the Worker's.

=== 5. Stack-agnosticism and the operator-notes convention

I checked the generic files for leakage beyond the parametrized token guard,

`PYTHONPATH`, `test_self_development_consumer_config`,
`wfc_prepare_checkout_env`, the four `make` gate names -- is absent from the
four files and present in `docs/operator-notes.md`.

The notes file is a real first user, not a placeholder, and I verified its
claims against this repository: the gate list matches the `Makefile` targets
(`lint`, `format-check`, `test`, `docs-render`, with `check` and
`check-docs` aggregating); the committed ceiling it quotes is exactly the
tuple `tests/unit/test_self_development_consumer_config.py:42-48` asserts;

file carries no absolute home path and no secret, its relative links resolve,
and it states its own standing, its no-authority boundary and the

The convention's five required properties all hold in the normative texts:
committed starting state (`git show <base-ref>:docs/operator-notes.md`, never

distinction: the installed Runtime is authoritative for what will happen,
this skill ships with it and describes that version, the tag-pinned manual is

=== 9. Simplicity and maintainability

The slice adds no mechanism: no CLI, no config key, no projection, no runtime
state, no new failure mode. The one new durable artifact in the product is a
plain optional file read with `git show`. That is the cheapest realisation of
the ordered capability I can construct, and it is strictly simpler than the
alternatives the design rejects. The structure stays the proven one (lean
entry file plus references followed on demand) and the packaged set stays
four files, so the distribution allow-list remains the single enumeration of
what ships. The lasting maintenance cost the slice does add is small and
named: one more file per consumer that wants notes, and the deny-list of
consumer-stack tokens, which a future generic sentence could trip -- a cheap,
clearly-diagnosed failure. I see no redundant safeguard and no abstraction to
remove.
