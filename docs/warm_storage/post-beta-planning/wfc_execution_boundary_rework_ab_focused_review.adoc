[[h004-signal]]
==== The started signal is still the only input, and still fail-closed

I drove `open_started_signal` / `close_started_signal_write_end` /
`provider_started` over seven payloads. The results match the documented
semantics exactly: nothing on the pipe, a `child-pid` document alone, and
unparseable bytes all yield `started=False`; a `child-pid` followed by an
`exit-code` document (0 or 3) and an `exit-code` document alone yield
`started=True`; a payload whose JSON stream breaks before a later
`exit-code` document yields `False`, i.e. a malformed stream fails towards
"not started" rather than towards an unproven "started". No file, directory
or agent-reachable path enters the decision: `codex_adapter.py:488-495` and
`claude_adapter.py:393-400` read `provider_started(started_signal)` and
nothing else, and the write end goes to the `bwrap` process alone
(`pass_fds=(write_fd,)`), with the Coordinator's own copy closed in a
`finally` immediately after spawn and the read end closed in an outer
`finally`. The timeout case is still deliberately excluded from the
classification (`if not timed_out and ...`), as `StartedSignal`'s docstring
states, and `provider_started` is only ever called after
`communicate()` has reaped the process, so the bounded read cannot block.

==== `operator.py`'s combined change is coherent after the removal

The dispatch frame's order is now: derive the grant (which may refuse the
scope by name, before anything exists on the host) -> create the
per-invocation channel directory, refusing a pre-existing one by name ->
`_preflight_boundary` -> `validate_grant` for a non-direct grant -> build the
adapter -> `run_real_one_hop`. Removing the bracket removed the only reason
`validate_grant` was deferred, and the corrected comment says so. There is no
double bookkeeping left between the F1/F2 channel handling and the F5
refusal: the channel directory is the only thing the frame creates, and the
F5 refusal happens strictly before it.
