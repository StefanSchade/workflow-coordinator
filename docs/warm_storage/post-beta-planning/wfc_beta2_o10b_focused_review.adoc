=== 1. F001 -- resolved

The Finding required that a normative statement about current behaviour be
true of the behaviour the slice ships: all four places that asserted the
marker retirement is *necessary* for the Run to progress -- the record's
`Design` section, the normative Operator Manual chapter, the retirement's
source comment, and a test docstring -- are false for the schema-2 Runs the
Front Door actually creates, where an un-retired marker costs one wasted
engine iteration rather than a stuck Run.

The correction restates all four, qualified by schema version, consistently:
fatal to liveness for a schema-3 Run (the cited stale-marker branch,
unreachable today), one wasted engine iteration for the schema-2 Runs the
Front Door creates (the branch below it, which retires the marker itself and
returns the Run at `READY`), kept deliberately for both reasons. I re-derived
every supporting fact from the source rather than from the correction's own
prose:

* `slice4.py:201` reads exactly
  `if run.schema_version == 3 and existing.role == "uncertain_dispatch":` --
  the branch the original four statements blamed is schema-3-gated.
* `commissioning.py:358` renders every profile at `"schema_version": 2`, and
  `model.py:1122` reads exactly `schema_version=3 if profile.schema_version
  == 3 else 2` -- so the Front Door creates schema-2 Runs, confirming the
  branch is unreachable through it today.
* `slice4.py:240` (`if run.schema_version != 3:`) through `:246`
  (`return RealHopRun(None, run, checkpoint, None)`) is the schema-2
  re-entry: it writes a checkpoint, unlinks the stale marker itself
  (`:245`) and returns the Run *unchanged* at its prior status, which is
  `READY` on this path.
* `operator.py:1022` (`while run.status is RunStatus.READY:`) is the loop
  that then dispatches the next Hop normally -- the "one wasted engine
  iteration" the correction claims, not a stuck Run.
* `lifecycle.py:1289-1304`'s retirement comment was rewritten in the same
  words as the record and the manual, and I read it at the corrected HEAD:
  it states the identical schema-3/schema-2 split.

I also grepped the diff's reach for any surviving unqualified "never
progress"/"re-reconcile … forever" phrasing and found none outside the two
places that now correctly scope it to the schema-3 case (the record's
`Design` section and the lifecycle comment, both qualified). The test
docstring (`test_quiescent_interruption_reducer.py:147-157`) now attributes
the demonstrated reducer call to "the *schema-3* stale-marker branch"
specifically and states the schema-2 cost correctly; the test body itself is
unchanged (still drives the real schema-3-shaped call), so the correction is
a docstring-accuracy fix, not a behaviour or assertion change. *Resolved.*
