== 1. Disposition

Verdict:: `accept`
Route:: `renew_broad_review`
Finding disposition:: `F001` resolved, `F002` resolved.

On the route choice: `robust@v1`'s `focused_review` declares only
`correction` (goto `correct`, a `worker` phase) and `renew_broad_review`
(goto `broad_review`, an `independent_reviewer` phase); it carries no
`{effect: complete}` route by design. A review that finds no blocking
issue must therefore take the forward route that continues toward
acceptance and must not hand converged work back to a Worker. That is
`renew_broad_review`. Choosing `correction` here with nothing to correct
would be the first step of the very incident this WorkItem fixes, and —
once this candidate is in the Runtime — would now be rejected by its own
C(iii) check. This record is updated with this Hop's verdict and named in
the CommitIntent, as C(ii) requires of every review Hop including a
no-change re-review.

== 3. `F001` — resolved

`preservation._latest_fact` now takes a `min_seq` keyword and

== 5. Boundaries, each checked by execution

*No path turns a stopped Run into an accepted one.* `resume_after_reconcile`
returns `READY`, never `COMPLETED`; acceptance in
`test_new_run_stopped_mechanical_reconcile_required_recovers_to_completion`
comes from a *fresh* Hop's own route request, not from the resume.
`test_recovery_run_still_needs_its_own_normal_accepting_route` shows a
further stop is still a stop.

*Resume widens nothing.* I called `resume_after_reconcile` directly and
measured both sides: status `reconcile_required -> ready`, phase
`review -> review` (preserved), `hop_limit` `5 -> 5` (preserved),
`hop_used` `1 -> 1` (preserved), charged hops `1 -> 1` (preserved). The
historical anomaly text is retained as provenance.

*Finding rules are untouched.* I probed the predicate with an injected
open Finding of each kind. With `blocking=True` the Run is ineligible and
refused by name (`the Run has an open blocking Finding`). With
`blocking=False` the Run is eligible, and after resume the Finding is
still `open` and still non-blocking — resume neither resolves, downgrades
nor clears it. Nothing in A/B/C gives the operator, the Coordinator or a
resume any Finding disposition.

*The previous no-op rule still holds where it should.* The pre-existing
`test_resume_after_classified_is_a_no_op_and_ext_records_are_ignored`
passes unchanged once the `wfc` console script is resolvable. A classified
Run that does not satisfy the predicate still falls through to the old
no-op path; only the eligible class behaves differently.

*Archive immutability and additivity.* Reproduced in section 3: distinct
destination, predecessor byte-identical, predecessor Evidence commit still
present, existing destination refused rather than overwritten. The
predecessor attempt and the recovery step are recorded through the
`attempt_id` itself (`<identity>-recovery-<n>`) rather than a separate
structured field — adequate, and the simpler option; noted in section 7.

*`C(i)` is generic and does not weaken the durable-artifact rule.*
`prompt._review_route_semantics_block` reads route names, target phases
and target roles from the profile only; `hands_back_to_worker` is derived
from the target phase's role and `is_failed_evidence_route` from the
phase's own review descriptor. `test_hands_back_to_worker_route_is_named_and_the_forward_rule_is_stated`
proves it with the arbitrary names `ratify`/`bounce`/`redo`, so nothing is
hard-coded. For a gate-review phase with no profile the assembly raises
rather than silently omitting the block, which is the right failure
direction. `vertical.py:315`, the single production call site, passes
`profile=profile`. `_durable_artifact_anomalies` is not weakened; the
artifact obligation sentence is added only when
`durable_artifact == required`.

*`C(iii)` is justified.* Rejecting the contradictory combination is the
smallest option that cannot create a silent-accept path: the reducer never
substitutes its own route for the reviewer's, so normalising to the accept
route would manufacture a disposition no review made. The genuine
`required_evidence_failed` override and the ordinary
`changes_required`/`failed_evidence_route` use both remain unaffected,
each with its own test, which I ran.

*Next-action texts name only existing paths.* `report.py` now overrides
the fixed table when `human_question_present is False`, promising only
`wfc resume`, "which recovers it automatically if it is eligible, or
refuses with a named reason if it is not" — accurate in both branches,
including for the new `contradictory_route` stop. `human_question_present`
is a pre-existing `audit.py` allow-list field (line 38, set at line 177)
with tests on both sides of the seam. The two existing report assertions
that were changed are a deliberate, documented replacement: the old
blanket `next_action == _NEXT_HUMAN_CHOICE[status]` could not express two
distinct `awaiting_human` shapes, and both shapes are now asserted
specifically. That is a strengthening, not a weakening.

*Scope and withheld authority.* `git diff --name-only ca1f901..HEAD`

== 7. Non-blocking observations

. *`C(iii)` adds one more terminal stop with no forward operator action.*
  The `mechanical_preemption:contradictory_route:...` stop is a terminal
  `awaiting_human` with no `human_question` and no `semantic_stop`, so
  `prepare-successor` refuses it and `wfc resume` refuses it by name. The
  `H002` reviewer recorded this and I independently reproduced its basis
  and reach the same conclusion: the next-action text is accurate (it
  promises only a conditional refusal, not a recovery), the task admits
  "reject" explicitly, and `C(i)` should make the situation rare. Worth a
  backlog line rather than an incident, but not blocking.
. *Predecessor linkage lives in the attempt identity.* The continuation's
  predecessor and recovery step are recoverable from
  `<identity>-recovery-<n>` rather than from an explicit field in
  `audit.json`/`manifest.json`. This is the simpler design and it does
  satisfy the task, but a future consumer that wants to walk the recovery
  chain programmatically will be parsing a name.
. *A recovered Run carries its anomaly text permanently.* Carried over
  from `H002` unchanged; intentional provenance, documented, and not
  operator-reachable today.
. *Hop budget preservation is asserted at the reducer seam only.* The
  lifecycle-level recovery tests do not re-assert `hop_limit`/`hop_used`.
  I verified both directly (section 5) and they hold; an assertion in
  `test_mechanical_recovery_lifecycle.py` would pin the end-to-end
  property where an operator would look for it.
