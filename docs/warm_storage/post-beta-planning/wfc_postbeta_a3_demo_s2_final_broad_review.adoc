=== Non-blocking observations

O-1 -- the `wfc` preflight accepts an executable that exits 0 without answering in JSON::
`rehearse.py`'s `_check_wfc_available()` treats exit code 0 as success and
does not parse the output, where `make_workspace.py`'s preflight additionally
requires a JSON object (I confirmed both: the same deliberately broken
executable -- `#!/bin/sh; echo not-json; exit 0` -- makes
`make_workspace.py` return 2 with "did not print a JSON object" and nothing
created, while `rehearse.py` proceeds, creates the worktree, "runs" that
executable and returns *0*, because the scenario expects exit code 0 and no
`CLASSIFICATION:` line is required). The FTR's recovery row says "`wfc`
missing *or not answering* `--version --json` -> Return 2", which can be read
as covering this case; against that, the FTR's `rehearse.py` step 1 lists
only the marker, the scenario name and the absent worktree as preconditions,
and the stopped Run's own Finding text offered "or at least a resolvability
check" as sufficient. I therefore do not block: reaching it needs an
executable that is not WFC yet exits 0 on `--version --json`, and the empty
banner sandwich makes the miss obvious on screen. The one-line close, if the
maintainer wants it, is the `json.loads` check `make_workspace.py` already
performs, reused in `_check_wfc_available()`; it would also matter more once
S3 uses these exit codes as a hosted gate.

O-2 -- `t3-probe-refusal`'s expected classification is still dead data::
A baseline-probe refusal never reaches a classified lifecycle print, so
`wfc run` emits no `CLASSIFICATION:` line and the scenario's
`expected_classification: "refused_probe"` is never compared; only the exit
code 23 is. The candidate is faithful to its specification (the FTR's rule is
conditional, and the scenario value is exactly what the FTR's table
prescribes) and its test replicates the same condition without asserting
anything false, so there is nothing to correct in the slice. It remains an
FTR/CLI mismatch for the maintainer -- accept the dead field, or let this one
scenario declare an expected message fragment -- carried over unchanged from
the earlier pass.

O-3 -- the Evidence repository's commits carry the machine identity::
`greeter/` gets the repository-local `WFC Demo <wfc-demo@example.invalid>`,
but `greeter-evidence/`, created by `wfc init`, gets none, so its
`chore: initialize ...` and `evidence: archive ...` commits are authored by
whatever Git derives from the machine (here a real name and hostname). SI-7
asks for "the demo identity on every commit". This is inherited from S1's
workspace creation, is not asked for by the FTR's step list, and does not
affect any S2 acceptance criterion; the one-line close, at the maintainer's
discretion, is the same `git config user.name/user.email` pair on
`greeter-evidence` in `make_workspace.py`'s step 3.

O-4 -- two small staleness and strength nits in the test file::
The module docstring of `tests/integration/test_consumer_demo_kit.py` still
says "slice S1" although the file now owns the S2 scenario, containment and
boundary tests; and `test_kit_modules_import_only_the_standard_library`,
after the S1 review's O-4 rewrite, asserts only `assert modules`, so it no
longer pins that all three kit modules are present (it does cover all three
today, which is what the task asked). A superset assertion over the globbed
names would restore the guarantee in one line without reintroducing a list
the next slice must edit. Neither is a defect against an acceptance
criterion: the scenario tests fail loudly if a module disappears.

=== Maintainability and simplicity

I looked for a materially simpler way to the same guarantees and did not find
one worth taking. `rehearse.py` is 239 lines of flat procedure with one
exception type mapped to one return code, no state beyond paths and no
abstraction over WFC; the correction added nine lines that *reuse* a check
the kit already owns rather than introducing a mechanism. `scripted_provider.py`
is 145 lines and stays a near-literal copy of the fixture's contract plus the
containment check -- duplication the FTR and the task deliberately chose over
a shared module that would break the `tests/`-to-`examples/` boundary; the
scenario tests are what will catch divergence. The scenarios are data, and the
family-neutral `disposition` key keeps each scenario ignorant of the contract
family of its phase for the price of one small renaming function. The
alternatives are each worse: cleanup-on-failure in the runner would
contradict SI-2 and the FTR's "no automatic clean-up"; parsing `wfc status`
instead of the consolidated report's `archive` line would add a second output
format to depend on. No redundant safeguard, no duplicated responsibility and
no recurring operational burden was introduced by this slice.
