[[dependabot-keys]]
== Dependabot keys verified against documented options

Web access was available this Hop. The documented options reference
(`docs.github.com`, Dependabot options reference) was fetched and read.
Every key used is confirmed, not an external assumption:

* `version: 2` -- required top-level key, confirmed.
* `updates` (list), `package-ecosystem: "github-actions"`, `directory: "/"`
  -- confirmed per-update keys; `github-actions` is a documented ecosystem
  value and `directory` (singular) is correct for one path.
* `schedule.interval: "weekly"` -- confirmed; one of the documented interval
  values (`daily`, `weekly`, `monthly`, `quarterly`, `semiannually`,
  `yearly`, `cron`).
* `cooldown.default-days: 7` -- confirmed; `cooldown` and its sub-key
  `default-days` are documented (cooldown delays *version* updates, not
  security updates; a 3-day default applies if omitted, so this file's
  explicit 7-day value is a deliberate, verified choice, not the default).
* `groups.<name>.patterns` and `groups.<name>.update-types` -- confirmed
  documented sub-keys of `groups` (`patterns` matches dependency names with
  `*` as wildcard; `update-types` is `minor`, `patch` or `major`). The
  reference also documents that a dependency matching more than one group
  goes into the *first* one it matches, and that `labels` is an
  update-entry-level key only -- there is no documented per-group `labels`
  key. This is why this file separates the two sets by *group name*
  (`check-only-actions` / `publish-path-actions`) rather than by label: a
  label would apply uniformly to every PR from this single `updates` entry
  and could not, by itself, distinguish the two sets.
* Two separate `updates` entries for the same `package-ecosystem` and the
  same `directory` were considered and rejected: the reference states that
  multiple blocks for one ecosystem on a target branch must have no overlap
  in the directories defined, which a second entry for `/` would violate.
  One entry with two `groups` is the structurally valid way to express the
  separation.

[[groups-derivation]]
== Automerge-eligible set re-derived from the workflow (not copied blindly)

A second scratch script parsed `.github/workflows/release.yml` with
`yaml.safe_load` and collected, per job, every `uses:` action name (the part
before `@`). Defining "check-only" as the jobs `{check, python-compat}` and
"publish-path" as `{publish-testpypi, publish-pypi, release}`:

* Actions appearing anywhere in `{check, python-compat}`:
  `actions/checkout`, `actions/setup-python`, `actions/upload-artifact`,
  `actions/download-artifact`.
* Actions appearing anywhere in `{publish-testpypi, publish-pypi, release}`:
  `actions/download-artifact`, `pypa/gh-action-pypi-publish`.
* `actions/download-artifact` is in *both* raw sets: `python-compat`
  downloads the `release-dist` artifact to run its installed-wheel checks,
  exactly as the three publish-path jobs do. The set of actions that run
  *only* in `{check, python-compat}` and *never* in a publish-path job is
  therefore `{actions/checkout, actions/setup-python,
  actions/upload-artifact}` -- matching the task's stated "today" set
  exactly, but derived, not assumed, and the derivation surfaces the reason
  `actions/download-artifact` is correctly excluded from the check-only
  group and placed only in the publish-path group (where it belongs because
  it runs in every one of `publish-testpypi`, `publish-pypi` and
  `release`). `.github/dependabot.yml`'s two `groups.*.patterns` lists were
  compared programmatically to these two derived sets: both match exactly,
  and their union covers every action the workflow pins with no overlap.

Both scratch scripts were deleted after use; `git status --short -uall`
shows only the four leaves listed above as changed or new.

== Correction (Hop H003)

The independent broad review at H002 raised a blocking finding: the
`python-compat` CI-section bullet cited <<recovery>>'s "Failed before any
upload" row as already stating the "never a re-tag" rule, but that row
prescribed "Fix on `main`, delete the tag, tag again" -- a re-tag, the
opposite of the cited rule. The row was also genuinely incomplete rather
than merely miscited: before G9, every pre-upload failure could only come
from `check` (the audited offline bundle), hence repository-caused and
correctly answered by a fix-and-re-tag; G9 is the first pre-upload,
release-blocking job that installs from the ordinary index, so its
failure can be purely upstream.

This Hop corrects both locations and nothing else in the chapter:

* The CI-section bullet's accepted-risk sentence (<<release-ci>>) now
  attributes the "re-run, never re-tag" rule to maintainer decision D6
  itself, not to the recovery table, and says explicitly that the table's
  generic pre-upload row no longer covers this case alone.
* The <<recovery>> table's "Failed before any upload" row is split in two,
  by cause: a repository-caused failure (for example `check`) keeps the
  original "fix on `main`, delete the tag, tag again" action; a failure
  not caused by this repository (`python-compat`, G9, D6's accepted risk)
  gets "re-run the failed jobs, never re-tag." The two rows are now
  mutually consistent with the CI-section bullet.

No other chapter-4 statement changed. Re-run after this edit: strict
render (`asciidoctor --safe-mode=safe -a assembled -o /dev/null
--failure-level=WARN docs/developer_guide/ch04_release_management.adoc`)
printed nothing; the doc catalog (`generate` then `check`) stayed at the
same 83 unresolved links and 4 Project Memory source_path misses. `git
status --short -uall` shows only this record and
`docs/developer_guide/ch04_release_management.adoc` changed by this Hop.
This Hop reports correction evidence only; Finding disposition is outside
this Hop's authority and is left to the reviewing phase.
