== Design decisions and reasons

Record format and location:: One new bounded checkout-scoped leaf,
`usage.json`, beside `run.json`/`checkpoint.json`/`execution-evidence.json`
under `run/checkouts/<id>/` (`src/workflow_coordinator/persistence.py:
write_usage_record`). It is a JSON object `{"schema_version": 1, "run_id":
..., "records": {<hop_id>: <record>}}`, written with the same atomic-replace
discipline as neighbouring Run records (`atomic_write_text`), append-only
and idempotent for an identical repeat, and refuses a conflicting duplicate
for an already-recorded Hop id rather than silently overwriting it
(`persistence.py::write_usage_record`). It is keyed by Hop id (one Hop is
exactly one invocation, per the task's own premise); each record additionally
carries `invocation_id`, `role` and the effective `adapter`/`model` binding
(`serialization.py::usage_record_to_data`). No prompt, output, path or
credential is ever part of it -- only numbers, enumerations and provider/
model identifiers. `frontdoor/archive.py`'s `CHECKOUT_ALLOW` gained
`"usage.json"`, additively, so it is archived exactly like its neighbours
when present and simply absent from the manifest when it is not.

Capture, where it happens:: `AgentExecutionOutcome` (`adapter.py`) gained one
new field, `usage: UsageRecord`, defaulting to the shared
`NO_USAGE_REPORTED` sentinel so every existing positional construction
(`FakeAdapter`, every inline test `Adapter`, `SubprocessAdapter`) keeps
working unchanged. `ClaudeCliAdapter.execute()` and `CodexCliAdapter.
execute()` each parse their own provider's full, un-bounded stdout (before
the existing 16 KiB diagnostic-tail bounding) into a `UsageRecord`,
independent of `candidate`/`returncode`/`timed_out`: the cost already
occurred even when the wrapper itself reports failure or the process times
out with partial output, so usage is read whenever the respective wire
format is itself parsable, never gated on acceptance. This is why capture
also covers failed, blocked and timed-out invocations whenever a parsable
provider output exists, and why a non-parsable/absent output yields
`NO_USAGE_REPORTED` (coverage `none`, every figure `None`) rather than
raising. Persistence of the parsed record then happens one layer up, in
`operator.py::run_serial_hops` (`_persist_usage_record`), using the already-
threaded `RealHopRun.outcome` -- which is populated on *both* the accepted
path and the `recover_uncertain` path in `slice4.py` (unmodified), so a
failed/timed-out/blocked invocation's usage is persisted exactly when
`slice4.py` already charges a Hop for it, with no new write surface and no
change to `slice4.py` itself (out of this WorkItem's authorized scope).

Coverage definition:: `model.usage_coverage_for(input_tokens, output_tokens)`:
`complete` when both headline figures are known, `partial` when exactly one
is, `none` when neither is -- applied uniformly to both providers, after
each individual figure has already been defensively parsed
(`model.coerce_token_count`: a non-negative `int` within
`MAX_PLAUSIBLE_TOKEN_COUNT` (1e12), `bool`/`float`/`str`/negative/too-large/
missing all yield `None`, never a guess, never zero).

Codex multi-event rule:: Codex may emit more than one `turn.completed` event
per invocation. The rule (`codex_adapter._usage_from_stdout`), applied
independently per field across every collected event: sum that field across
every event only when *every* event reports it as a well-formed non-negative
integer; if any event is missing it, has the wrong type, or the event's own
`usage` value is not even an object, that one figure becomes unknown rather
than a partial/guessed sum. A single event is the degenerate case of the
same rule. A line that is not valid JSON, or not a `turn.completed` event, is
skipped, never raised. No event at all (including fully truncated/malformed
stdout) yields `NO_USAGE_REPORTED`. Tested in
`tests/unit/test_codex_adapter_usage.py::TestMultipleEvents` against derived
fixtures built from the one real sample.

Lower-bound semantics:: `frontdoor/audit.py::_usage_figure` sums only the
known values among a group of records (a Hop's whole Run for `totals`, a
role's subset for `by_role`, a model's subset for `by_model`); the total is
`None` (never zero) when nothing in the group is known, and carries
`"lower_bound": true` whenever at least one group member did not contribute
a known value (including a Hop with no persisted record at all, which
contributes nothing to every figure) -- the sum is real but understates the
true total in that case, and this is the one and only place that marker is
set. `wfc report` renders it as a trailing `+` on the figure
(`report.py::_render_usage_metrics`).

Limit codes:: `usage_not_reported` is kept, and is set, exactly when either
(a) no Hop of the Run carries a persisted usage record at all (the old,
unconditional case -- every pre-this-change archive), or (b) records exist
but not one of them reports a usable headline figure (coverage `complete` or
`partial` is zero across the whole Run). `usage_partially_reported` (new) is
set instead when at least one Hop's coverage is `complete`/`partial` but not
every Hop reached `complete` -- i.e. real reporting exists but is honestly
incomplete; the two codes are mutually exclusive, and neither is set when
every Hop in the Run is `complete`.

Per-role/per-model source:: `by_role` is keyed by the Hop's own authoritative
`role` (from `run.json`, always present, independent of whether
`operator-plan.json`/governance is archived); `by_model` is keyed by the
persisted record's own `model` (the effective binding captured at
invocation time), and a Hop whose record carries no model (e.g. a local/fake
adapter) is excluded from `by_model` but still counted in `totals`/
`coverage_counts`. This is a deliberate asymmetry, recorded here rather than
only in code comments: role is always knowable from Run state and is the
more robust key; model is only knowable from the capture itself.

Compatibility argument (byte-identity):: A pre-this-change archive never
wrote `usage.json`, so for every Hop `usage_doc` is `None` and every hop's
projected `"usage"` stays `None` (same literal value the old hard-coded
projection produced). `_build_usage_section` returns `None` whenever no Hop
carries a non-`None` record, so the top-level `"usage"` key is omitted
entirely (not merely null) -- unconditionally true for every pre-this-change
archive -- and `usage_not_reported` is appended to `limits` by the exact
same unconditional-in-effect path the old code took. No other field this
slice touches (`run`, `governance`, `findings`, `lifecycle`, `raw`) changed
shape. `_TOP_KEYS`/`_HOP_KEYS` gained the already-reserved/allow-listed
`"usage"` key additively; `_assert_keys` only refuses an *unexpected* key, so
an allow-listed-but-absent key never fails the closed-set check. Measured in
`tests/unit/test_postrun_archive.py::UsageAdditiveArchivingTests::
test_old_style_attempt_with_no_usage_json_reprojects_without_the_usage_key`
(a real `archive_run` over a state root built the pre-this-change way) and
`tests/unit/test_audit_projection.py::TestUsageIsAlwaysNullNeverZero` (the
synthetic `bp6` fixture, likewise never carrying `usage.json`).

== Provider-semantics difference and its unverified assumptions

Verified from the two real, read-only samples
(`tests/fixtures/provider_usage_samples/`): Claude's `usage.input_tokens`
excludes both `cache_read_input_tokens` and `cache_creation_input_tokens`
(the real sample: `input_tokens: 2`, `cache_read_input_tokens: 9074`,
`cache_creation_input_tokens: 12736` -- these are clearly disjoint, additive
figures, not a subset relationship). Codex's `usage.input_tokens` *includes*
`cached_input_tokens` (the real sample: `input_tokens: 17329`,
`cached_input_tokens: 11008`, with `11008 < 17329`, consistent with
inclusion; the task text states this inclusion as a verified fact of the
real CLI, not an inference drawn here). `UsageRecord.
input_includes_cache_read` carries this fact verbatim per record (`False`
for every Claude-origin record, `True` for every Codex-origin record),
meaningful only when `input_tokens` is not `None`; no aggregation anywhere
in this slice sums a Claude figure with a Codex figure under one field
without this flag remaining readable per contributing invocation (`by_role`/
`by_model` split by role/model, which already separates adapters in every
realistic binding).

Unverified/assumed, not covered by the two real samples, and treated as
optional-and-unknown-when-absent per the task's own instruction: Claude's
`modelUsage` entries beyond the one model the real sample carries (multiple
concurrent models in one invocation is assumed possible but untested
against a real multi-model wrapper); Codex ever reporting `cache_write_
input_tokens` as non-zero (the real sample has it at `0`; the field is
parsed and stored, never asserted non-zero anywhere); a third adapter's wire
format (none exists in this product).

== Changed contracts

* `AgentExecutionOutcome` (`adapter.py`): new field `usage: UsageRecord =
  NO_USAGE_REPORTED`. Additive; every existing positional construction
  keeps working.
* `FakeAdapter` (`adapter.py`): new field `usage: UsageRecord =
  NO_USAGE_REPORTED`, threaded into its `AgentExecutionOutcome`. Additive.
* New `model.py` surface: `UsageCoverage`, `ModelUsage`, `UsageRecord`,
  `NO_USAGE_REPORTED`, `MAX_PLAUSIBLE_TOKEN_COUNT`, `coerce_token_count`,
  `usage_coverage_for`. Additive.
* New `serialization.py` function: `usage_record_to_data`. Additive.
* New `persistence.py` function: `write_usage_record`,
  `USAGE_RECORD_SCHEMA_VERSION`. Additive; one new write surface, scoped to
  the existing checkout directory.
* `frontdoor/archive.py`: `CHECKOUT_ALLOW` gained `"usage.json"`. Additive.
* `frontdoor/audit.py`: `_HOP_KEYS["usage"]` is now populated from the
  archived record instead of hard-coded `None`; `_TOP_KEYS` gained the
  conditionally-present `"usage"` key; `_build_hops_section`'s return shape
  changed (now a 3-tuple, used only inside `project_audit`, not a public
  contract); `limits`' `usage_not_reported` seeding changed from
  unconditional to conditional (see compatibility argument above, and the
  deliberately replaced assertions below); new limit code
  `usage_partially_reported`.
* `frontdoor/report.py`: `build_report`'s returned mapping gained a `"usage"`
  key (`None` when absent); `render_report_text` gained new lines, present
  only when usage was recorded.
* `operator.py::run_serial_hops`: new call to `_persist_usage_record` per
  dispatched invocation; no change to control flow, routing or any existing
  field it already wrote.
* `codex_adapter.py`: fixed a latent `NameError` (`json` was used but never
  imported) uncovered while adding usage parsing -- pre-existing in the
  module before this change, triggered only once `_usage_from_stdout` called
  `json.loads`; every `CodexCliAdapter`/`operator.py` conformance and
  integration test that exercises a real Codex-shaped subprocess now passes
  where it previously raised `NameError` inside `execute()` the moment this
  slice's own new parsing code ran (confirmed by re-running the same tests
  against the unmodified baseline via a scoped `git stash`, which reproduced
  the identical `NameError` once the single new `_usage_from_stdout` call
  was present without the import -- i.e. this is this slice's own omission,
  caught and fixed within the same change, not a pre-existing product
  defect reaching users before now).

No change to `wfc.audit/1`'s or `wfc.report/1`'s *required* fields; both
additions are optional/allow-listed and absent exactly when this slice never
ran (or ran but captured nothing to report, for `audit.json`'s `"usage"`
key specifically -- see the compatibility argument).

== H005 correction addendum

Written by `WI-WFC-TOKEN-USAGE-S1-001` H005 (Worker, correction phase)
against the independent focused review recorded at

F004 (usage parsing can raise `RecursionError` out of `execute()`):: Confirmed
by direct reproduction at the function boundary: `json.loads()` raises
`RecursionError` (not `json.JSONDecodeError`) on a pathologically deeply
nested JSON value (`"["*200_000 + "]"*200_000`), and both
`claude_adapter._usage_from_wrapper_stdout` and
`codex_adapter._usage_from_stdout` caught only `(json.JSONDecodeError,
ValueError)`, so that exception escaped uncaught. Fixed by widening both
`except` clauses to also catch `RecursionError`, which is Python's own
documented behavior for this input shape and not a provider-specific
assumption; both functions already treat any caught decode failure as
`NO_USAGE_REPORTED`/an unparsable event, so the fix changes no other
behavior. New regression tests:
`test_claude_adapter_usage.py::TestDefensiveParsing::
test_pathologically_nested_json_is_no_usage_reported_not_raised`,
`test_codex_adapter_usage.py::TestDefensiveParsing::
test_pathologically_nested_json_line_is_skipped_not_raised`, and an
end-to-end reproduction at the real adapter boundary,
`test_codex_adapter_conformance.py::
test_pathologically_nested_stdout_never_raises_out_of_execute_and_candidate_still_lands`,
which drives a fake Codex executable that writes a valid candidate result to
`--output-last-message` and also prints the pathological line to stdout,
then asserts `CodexCliAdapter.execute()` returns normally with the candidate
intact and `usage.coverage is UsageCoverage.NONE`. All three fail with
`RecursionError` against the pre-fix code (reproduced by temporarily
reverting the two adapter files in a disposable WIP stash, confirming the
failure, then restoring with `git stash apply` and dropping the entry) and
pass with the fix. The analogous `_candidate_from_wrapper` `json.loads` call
in `claude_adapter.py` was deliberately left untouched: it already only runs
on the zero-exit, non-timeout path (pre-existing, unconditional behavior
predating this WorkItem), is not usage parsing, and widening it is outside
this slice's scope and this Finding's reproduction.

F005 (docs-sync check missed two in-scope backlog owners):: Confirmed by
