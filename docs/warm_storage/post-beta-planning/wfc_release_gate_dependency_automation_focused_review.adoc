=== Why F001 is resolved

The CI-section bullet (`ch04_release_management.adoc`, the `python-compat`
entry) now reads: "nothing has been uploaded yet, but D6's own rule still
applies -- the response is a re-run of the failed jobs, never a re-tag.
This is not the generic pre-upload row of `<<recovery>>`'s table: that
table now splits the \"failed before any upload\" state by cause...". This
no longer cites the table as the source of the rule; it cites maintainer
decision D6, and accurately describes the table as having been *changed*
("now splits"), not as having already said so. The false citation H002
found is gone.

The recovery table now carries two rows in place of one:

* "Failed before any upload, caused by this repository (for example
  `check`)" -- "Fix on `main`, delete the tag, tag again." (the original
  action, correctly scoped to the only pre-G9 cause.)
* "Failed before any upload, not caused by this repository (`python-compat`,
  G9: an index-side or upstream change, the accepted risk of maintainer
  decision D6)" -- "Re-run the failed jobs. Never re-tag."

I checked this split for the overgeneralization a cause-based split invites:
could a `python-compat` failure be repository-caused (a genuine 3.10-3.12
incompatibility in WFC's own code, not an index/upstream drift)? Yes, and
such a failure belongs in the first row, not the second -- but the second
row's label is explicitly scoped to "not caused by this repository", with
`python-compat`/G9 named only as the example of *that* cause, and the
CI-section bullet mirrors the same scoping ("a `python-compat` failure of
this kind need not be [re-tagged]" -- "this kind" referring to the
index-side/upstream, D6-accepted-risk kind, not every `python-compat`
failure). Neither location claims that every `python-compat` failure is
automatically not-repository-caused. The split is honest and internally
consistent, and it repairs the substantive incompleteness H002 also raised
(before G9, every pre-upload failure in tag mode was necessarily a `check`
failure against the audited offline bundle, hence repository-caused; G9 is
the first pre-upload job that can fail for a purely upstream reason, so the
single pre-G9 row was incomplete for the integrated pipeline).
