=== 4. The slice re-derived at my own hand

I drove the real dispatcher (`frontdoor.cli.main`) in a child process
against a copy of the package placed outside the checkout, with a throwaway
`HOME` per fixture and `CLAUDE_CONFIG_DIR` controlled explicitly — the
installed-package path, not an import of the worktree's `src`. 69 assertions,
all passing. The substance:

*`show`*:: prints the packaged `SKILL.md` byte-for-byte (7 353 bytes, equal
to the tree's file) from a working directory outside the checkout; `--list`
prints the four relative paths with `sha256:` digests; an unknown name and
`show ../../etc/passwd` each exit 2 with empty stdout — `FILE` is matched
against the packaged key set, never joined onto a path.

*The five states, for `claude` and `codex`*:: `absent` → created, exit 0;
`current` → exit 0, bytes identical; `stale` (files consistent with their own
older marker) → replaced without `--force`, exit 0, and the marker written is
byte-identical to the one the first install wrote, so "equal inputs give
equal bytes" holds across runs; `modified` → `STATE: modified`,
`DIFFERING FILES:` naming `SKILL.md`, exit 3, tree byte-identical afterwards;
`foreign` (no valid marker) → same shape, exit 3, tree byte-identical;
`--force` replaces both. The marker is exactly
`{"schema": 1, "wfc_version": …, "files": {…}}` with a 64-hex digest per
relative path and no timestamp and no fourth key.

*`--dry-run`*:: on `absent` prints `WOULD INSTALL:` and creates nothing, not
even a parent (full byte-tree of the home compared before and after); on
`modified` and `foreign` returns 3 and changes nothing; it returns what the
real call would return in each case.

*Symbolic links*:: a destination that is a symlink to a victim directory is
refused with exit 2 both without and with `--force`; the link still points
where it did and the victim's own file is untouched; `status` reports
`foreign` and reads nothing through it. A packaged file replaced *inside* an
otherwise current installation by a symlink to a secret file is classified
`modified` (exit 3) with no byte of the target reaching stdout, `show` keeps
printing the packaged bytes, and `--force` then replaces the directory with
the secret file still intact.

*Staging*:: after every successful install the skills root contains exactly
`wfc` and the parent of the skills root contains no `.wfc-skill-staging-*`
leftover — the new tree is built in the parent and renamed in, never beside
the installation.

*Destinations*:: `CLAUDE_CONFIG_DIR` is honoured for `claude` user scope
(`$CLAUDE_CONFIG_DIR/skills/wfc`, and `~/.claude` is then never created) and
has no effect on `codex` (`$HOME/.agents/skills/wfc`); `--skills-dir DIR`
addresses `DIR/wfc`, reports scope `custom`, and is rejected together with
`--scope` by argparse itself (exit 2).

*Status*:: the host is required; `--scope` and `--skills-dir` each select
exactly one block; with neither flag the user installation plus the project
one inside a work tree, and the project block simply omitted outside one
(exit 0); exit 0 for all five states and for a symlinked destination;
`INSTALLED VERSION` shows the marker's `wfc_version` (`0.0.0-old` for my
fixtures) and `-` / JSON `null` where no valid marker exists; the JSON
carries exactly `host`, `packaged_version` and
`installations[{scope,path,state,installed_version}]`; no aggregate state is
printed.

*Host independence (AC-4, SI-11), both directions*:: with one host `current`,
I made the other host's installation in turn absent, stale and modified and
compared the observed host's `status` output byte-for-byte against the
baseline — identical in all six cases (three states × two directions), text
and `--json` alike, exit 0 throughout. The code reason is visible:
`resolve_destination` derives only the asked host's paths.

*Project scope (SI-5)*:: refused with exit 2 outside a Git work tree, writing
nothing into the directory; inside a seeded consumer repository the install
lands at the Git top-level, `git status --porcelain` shows exactly
`?? .agents/`, and `HEAD`, `git ls-files -s`, the reflog and
`git diff --cached` are all unchanged; no `.wfc/`, `CLAUDE.md`, `AGENTS.md`
or `.gitignore` is created anywhere. The `NEXT EXPLICIT ACTION:` line tells
the human to commit it and states that the command never commits.

*Dispatcher*:: `wfc skill`, `wfc skill nonsense`, `wfc skill install`,
`wfc skill status`, `wfc skill install mistral` each print `usage: wfc skill
…` and exit 2; `wfc skill --help` and the `--help` of all three subcommands
print usage and exit 0. `cli.py`'s diff is the three lines of one branch
placed before the legacy `operator.main` fall-through, so no existing
subcommand's dispatch or output can have moved; the candidate's own tests
assert the no-fall-through half by monkeypatching `operator.main` to raise.

F-2 (blocking, new):: *The AC-2 half of
`tests/architecture/test_offline_distribution.py` does not keep its install
inside a temporary home: it never clears `CLAUDE_CONFIG_DIR`.* The new block
(`:71-84`) builds its child environment as `host_env = os.environ.copy()`,
then sets `HOME` and pops `PYTHONPATH` and `PYTHONSAFEPATH` — and nothing
else. `claude` user scope resolves to `$CLAUDE_CONFIG_DIR/skills/wfc` *in
preference to* `$HOME/.claude/skills/wfc` whenever that variable is set
(`frontdoor/skill.py:77-81`, the FTR's own destination table at
`FTR …:407`), and neither `tests/conftest.py` nor any other conftest clears
it (the only two occurrences in the whole test tree are the deliberate ones
in `tests/unit/test_frontdoor_skill.py`). I reproduced the consequence by
replicating the test's environment construction verbatim, with
`CLAUDE_CONFIG_DIR` set in the parent to a stand-in for an operator's own
configuration directory: the `claude` install returned 0 and printed
`INSTALLED: <stand-in config>/skills/wfc`; the temporary home was left
*empty*, so the test's own next line,
`assert installed_skill_md.is_file()`, is `False`; and the stand-in
configuration directory afterwards held `skills/wfc/SKILL.md`,
`skills/wfc/.wfc-skill.json` and the three reference files. The `codex` half
is unaffected (no override exists for `$HOME/.agents`), and it passed in the
same run, which is why the defect is specific to the one host.
+
Why this blocks. The FTR's `Required tests` preamble is explicit and global:
"All automated, in the required suite; every test that installs uses a
temporary `HOME` and never the real one"; AC-2 says "`wfc skill install`
works for both hosts *into a temporary home*"; this Commission's withheld
authority says "no write to any real agent configuration or to the real
HOME". Under a documented, supported consumer configuration — the very
override this feature exists to honour, and the one the FTR itself insists
on isolating for the S3 host probes (`FTR …:746`, "under an isolated
`CLAUDE_CONFIG_DIR`") — the required suite writes the skill into the
operator's real Claude configuration directory and then fails. Both halves
matter: the unwanted write, and a suite failure whose cause points at the
environment rather than at the code.
+
Remedy, inside the declared scope: add `host_env.pop('CLAUDE_CONFIG_DIR',
None)` beside the two existing pops in
`tests/architecture/test_offline_distribution.py`. That is exactly what the
Worker already does in the unit tests
(`tests/unit/test_frontdoor_skill.py:36`,
`monkeypatch.delenv("CLAUDE_CONFIG_DIR", raising=False)`), so this is an
omission in one of two places rather than a design decision, and no other
file needs to change. Nothing in `frontdoor/skill.py` is at fault: honouring
the variable is specified behaviour, and I confirmed it works as specified
(section 4).
+
What I could not do: run that test here. Its `python -m build` step cannot
bootstrap an isolated environment offline (section 7), so the test aborts
long before the AC-2 block. I therefore reproduced the decisive mechanism
rather than the test run: the test's exact environment construction, the real
`install claude` path, and the state of both the temporary home and the
stand-in configuration directory afterwards. The unreached code path is three
statements of the same file, read directly.

=== 7. Non-blocking observations

O1 (reproduced, still non-blocking):: A filesystem failure in the install
path raises an uncaught `OSError`: the process prints a traceback and exits
1, outside the FTR's `0 / 2 / 3`. I reproduced both cases the broad review
names, with my own fixtures: a read-only `~/.claude` (the `mkdir` of the
skills root fails) → exit 1, and nothing is created; a read-only parent of
the skills root with a `stale` installation present (the `mkdtemp` staging in
the parent fails) → exit 1, the old stale installation byte-identical
afterwards, no partial installation and no staging leftover. Both fail
closed, which is why I keep it non-blocking, and I reach the broad pass's
other two reasons independently: the FTR names codes for the outcomes it
specifies rather than forbidding an exception, and the sibling module the
task names as the voice model, `frontdoor/init.py`, writes its destination
the same uncaught way. If the maintainer wants the code surface to be total,
one `except OSError` around the `_stage_and_install` call returning 2 through
the existing `SkillError` voice would do it — that is a maintainer decision,
not a defect of this slice.
O2 (reproduced):: `test_only_cli_imports_skill_module` misses one import
spelling: for a relative `ImportFrom` that names a module, `_import_targets`
returns only the module path and drops the alias names, so
`from .frontdoor import skill` in a package-root module is invisible to the
guard (section 5, mutation 6). The invariant holds today — the package
contains exactly one importer, which I measured — so this is a coverage gap
in a new guard, not a product defect. Closing it is one expression:
`{f"{full}.{alias.name}" for alias in node.names}` added to the returned set
in the relative-with-module branch, mirroring the absolute branch.
O3 (new):: Both drift guards validate `skill` only at its *top* level, and
this is new in kind: `skill` is the repository's first two-level subcommand,
while `_PARSE_ARGS` and `SUBCOMMAND_MAIN` are flat tables of one parser per
`wfc <word>`. Measured: `test_quickstart_commands._allowed_flags("skill")`
is `{-h, --help}` and `test_agent_skill_content._accepted_flags("skill")` is
`{--help}`, because `_real_parser`/`--help` capture the `wfc skill` parser,
not the `install`/`status`/`show` subparsers. The two documented quickstart
lines (`wfc skill install claude`, `wfc skill install codex`) carry no flags,
so the guard passes and its subcommand check is real; the task's requirement
("recognise the new `skill` subcommand … existing validation semantics
unchanged") is met and no existing assertion is touched. The consequences to
know: a documented `wfc skill install claude --scope project` would be
rejected as "not a real flag of the installed CLI" although it is one, and a
rename of a nested flag would not be caught. Both are fail-closed, which is
why this is an observation. If the maintainer wants depth, the cheapest shape
is one further table entry per nested subcommand
(`"skill install": SKILL._build_parser()…`) in a later slice; adding it here
would be new mechanism this slice was not asked for.
O4 (carried, confirmed):: Removing `PENDING_SUBCOMMANDS` is coverage-neutral
in substance, because the drift guard reads fenced blocks only and `SKILL.md`
names `wfc skill …` in prose. This is the S1 review's O2 and the S2 broad
pass's O3, and S2 cannot close it (the skill text is withheld). I re-checked
AC-6 by hand against the real parser instead: `wfc skill status claude`,
`wfc skill status codex`, `wfc skill show` and
`wfc skill install claude|codex` are all accepted, and the preflight's
`--skills-dir` variant likewise.
O5 (carried):: The broad pass's O4 (`--dry-run` on a `current` installation
prints the same two lines the real call prints), O5 (a symbolic link *inside*
an otherwise current destination is invisible to the state machine, because
`_hash_tree` skips link entries — I reproduced the `modified` outcome for a
*packaged file* replaced by a link, see section 4), O6 (`status` reports a
symbolic-link destination as `foreign`, which the state table defines for a
directory) and O7 (this Run's Worker Hop left no warm-storage verification
record) stand as written there. I reached the same conclusion on each where
I could re-measure it.
