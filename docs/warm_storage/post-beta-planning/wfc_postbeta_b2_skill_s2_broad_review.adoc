=== 3. The slice re-derived at my own hand

==== 3.1 The state machine, both hosts, user scope (AC-3)

For `claude` and `codex` each: `absent` → creates the directory and prints
`STATE: absent`, `INSTALLED: <path>`, `WFC VERSION: 0.1.0b1`, `INVOKE: /wfc`
or `$wfc`, `NOTHING ELSE WAS CHANGED`, and no `NEXT EXPLICIT ACTION` in user
scope; the four packaged files land byte-exact; the marker holds exactly
`schema` 1, `wfc_version` and `files` with a 64-hex digest per relative path
and no timestamp key. A second install reports `STATE: current`, writes
nothing and leaves the marker *byte*-identical, so equal inputs give equal
bytes. `stale` (files equal their own marker, differing from the package) is
replaced without `--force`. `modified` and `foreign` return 3, print
`DIFFERING FILES:` and leave every byte unchanged; `--force` replaces both.
`--dry-run` returns the real code in all five states (0, 0, 0, 3, 3), writes
nothing on `absent`, and leaves the tree identical in the others.

==== 3.2 Project scope, both hosts (AC-3, SI-5)

I ran the *whole* state machine in project scope for both hosts in a seeded
consumer repository, not only the install: absent → install, idempotent
`current`, `stale` replaced, `modified` and `foreign` refused with 3 and
unchanged, `--force` replacing, `--dry-run` unchanged, and the symbolic-link
destination refused with 2 both with and without `--force`. After the
install `git status --porcelain` is exactly `?? .claude/` (or `?? .agents/`),
`HEAD`, the index and the reflog are unchanged, no `.wfc/` exists, and no
`CLAUDE.md`, `AGENTS.md` or `.gitignore` was created; a full before/after
digest snapshot of the work tree shows every added path under the
destination, no pre-existing path changed and none removed. Run from a
sub-subdirectory the Git top-level is resolved correctly and nothing is
written beside the subdirectory. Outside a work tree both `install` and
`status --scope project` return 2 with a truthful message and write nothing.
The module's only subprocess call is a read-only
`git rev-parse --show-toplevel`; it contains no mutating Git verb at all.

==== 3.3 The symbolic-link refusal and the never-partial invariant

A symbolic-link destination returns 2 for both hosts, with and without
`--force`, in user and project scope; the link is still a link afterwards,
its target still holds its own file, and no packaged file ever appears
inside the target. `status` reports such a destination as `foreign` and
never reads through it.

I proved the staging rule by instrumentation rather than inference: a spy on
`tempfile.mkdtemp` shows exactly one staging directory per install, created
with `dir=` equal to the *parent* of the skills root, never inside it, and
afterwards the skills root contains only `wfc` and the parent holds no
`.wfc-skill-staging-*` residue. I then injected two failures. An `OSError`
at `os.rename` on a replacement leaves the old installation in place or
nothing — never a partial tree — and no staging residue. An `OSError` on the
third staged `write_bytes` leaves the *old* installation intact byte for
byte, again with no residue. A marker that is itself a symbolic link is not
trusted (`foreign`, no version). Eleven malformed marker shapes (invalid
JSON, empty, array, string, `null`, `schema` 2, missing `schema`, `files`
not a dict, non-string version, short digest, non-string digest) each
classify as `foreign`, return 3 on install, change nothing, and print no
traceback. A destination that is a regular file is `foreign`, refused
without `--force` and replaced with it. A symlinked configuration *ancestor*
(`$HOME/.claude` → elsewhere) is correctly not refused: content lands in the
target and the ancestor link is not replaced.

==== 3.4 Status semantics (AC-4, SI-11)

The host is required (`status` and `status nonsense` both return 2). Every
installation gets exactly one state; the text block is
`HOST:/SCOPE:/PATH:/STATE:/INSTALLED VERSION:` then one
`PACKAGED VERSION:` line, with no aggregate state and `INSTALLED VERSION: -`
without a valid marker. Return code is 0 in all five states for both hosts,
in text and in `--json`; the JSON object has exactly
`host`/`packaged_version`/`installations`, each installation exactly
`scope`/`path`/`state`/`installed_version`, `scope` is `user`, `project` or
`custom`, and `installed_version` is `null` without a valid marker.
`--scope` selects exactly one, `--skills-dir` selects exactly `DIR/wfc` as
`custom`, neither reports user plus project inside a work tree and user only
outside one — the omission is not an error — and `--skills-dir` with
`--scope` is rejected with 2.

Host independence I tested in both directions and byte-for-byte: with one
host `current`, I drove the other host through `absent`, `stale`,
`modified`, `foreign`, `current` and a symbolic link, confirming the other
host's real state each time, and the held host's `status` output was
byte-identical in text and in JSON in all twelve combinations, never naming
the other host or its path.

=== 6. Non-blocking observations

Corroborated by my own measurement, not carried forward on trust:: *O1* —
an unexpected filesystem failure surfaces as an uncaught exception rather
than the FTR's code 2. I reproduced two triggers: an unwritable skills root
(`PermissionError` at the rename) and `--skills-dir` pointing at a regular
file (`FileExistsError`). Both fail closed — no installation, no partial
tree, no staging residue — and the two environment errors the FTR actually
enumerates (symbolic-link destination, project scope outside a work tree)
both return 2 with a truthful message. Still an observation and not a
Finding: the FTR assigns codes to the outcomes it names rather than
forbidding an exception, `frontdoor/init.py` behaves the same way, and
adding a blanket handler is mechanism this slice was not asked for.
*O5/O8* — a symbolic link added inside an otherwise current installation
leaves the state `current` (measured); skipping link entries is the safer
trade and an extra *regular* file is caught. *O6* — `status` maps a
symbolic-link destination to `foreign`, which the state table defines for a
directory; it is the safe answer. *O9* — the committed test file exercises
project scope with two tests only; I drove the whole state machine through
project scope by hand for both hosts (3.2) and it holds. *O10* — the
destination spelling differs by scope: `--skills-dir` and project scope
print a resolved real path, user scope an unresolved `$HOME/...` path. This
cost me a false probe failure before I recognised it, which is a small
argument for making the two consistent.
O2, extended:: `test_only_cli_imports_skill_module` misses *two* import
spellings, not one. I tested seven: `from .skill import main`,
`from . import skill`, `from .frontdoor.skill import main` and both
absolute forms are rejected, but `from .frontdoor import skill` in a
package-root module *and* `from ..frontdoor import skill` in a `frontdoor`
submodule are accepted. The cause is the relative-with-module branch of
`_import_targets`, which returns the module path and drops the alias names
that the absolute branch does include. The invariant holds in fact today —
`cli.py:42` is the package's only importer, measured by AST over every
module — so this is a gap in a new guard, not a product defect, and the
remedy is one expression: add

==== 3.2 Destinations, and the five states on both hosts and both scopes

Destination table reproduced: `claude` user scope honours `CLAUDE_CONFIG_DIR`
(`$CLAUDE_CONFIG_DIR/skills/wfc`) and otherwise `$HOME/.claude/skills/wfc`;
`codex` user scope `$HOME/.agents/skills/wfc`; project scope the Git
top-level of `--repository` plus `.claude/skills/wfc` or
`.agents/skills/wfc`; `--skills-dir DIR` addresses `DIR/wfc`, reports scope
`custom`, and is mutually exclusive with `--scope` in argparse itself.

All five states, driven on the installed command:

* `absent` → creates the directory, exit 0; the marker is
  `{"files": {...}, "schema": 1, "wfc_version": "0.1.0b1"}` with a 64-hex
  digest per relative path, no timestamp.
* `current` → exit 0, nothing written.
* `stale` (files equal their own marker, differ from the package) → replaced
  without `--force`, exit 0, which is SI-6's one permitted overwrite.
* `modified` (valid marker, hand-edited file) → `STATE: modified`,
  `DIFFERING FILES:` naming `SKILL.md`, exit 3, tree byte-identical
  afterwards.
* `foreign` (no valid marker, not `current`) → same shape, exit 3, tree
  byte-identical afterwards.
* `--force` replaces `modified` and `foreign`; the destination is then equal
  to the packaged files and carries today's marker.

Idempotence and determinism: a second `install` writes nothing, and the
marker written for a fresh install and the marker written when replacing a
`stale` installation are byte-identical (`json.dumps(..., sort_keys=True)`
over content digests and `VERSION`, no clock), so "equal inputs give equal
bytes" holds across runs, not merely within one.

`--dry-run`: for `absent` it prints `WOULD INSTALL:` and creates nothing, not
even a parent; for `stale` it returns 0; for `modified` and `foreign` it
returns 3; in every case the file system is unchanged — I compared the full
byte tree before and after each of the four.

The symbolic-link refusal I attacked directly: the destination was made a
symlink to a victim directory holding a file of its own. `install` and
`install --force` both printed the refusal to stderr, returned 2, and left
the link and the victim's file untouched; `status` reported `foreign` without
reading through the link. A packaged file replaced by a symlink to
`/etc/passwd` inside an otherwise current installation is classified
`modified` (exit 3) with no content of the target reaching stdout, and
`--force` then replaced the directory with `/etc/passwd` still a regular
file: `shutil.rmtree` removes links without following them, and `_hash_tree`
walks with `followlinks=False` and skips link entries outright.

Staging: the new tree is built in a `mkdtemp` directory in the *parent* of
the skills root and renamed into place, so nothing resembling a second skill
ever exists inside the skills root; the staging directory is removed in a
`finally`. I checked the leftovers after a successful install through a
symlinked skills root as well: `~/.claude` holds only `skills`, the real
target only `wfc`. Replacement removes the old directory immediately before
the rename, so a failure leaves the old installation, the new one, or none —
the two failures I provoked (section 6, O1) left the old state and nothing
partial.

Project scope: refused with exit 2 outside a Git work tree and in a bare
repository, writing nothing. Inside a real consumer repository with a seeded
commit, `install codex --scope project` left `git status --porcelain` showing
exactly `?? .agents/`, `HEAD` and `git ls-files -s` unchanged, the reflog at
its single seed entry, and no `.wfc/` anywhere (SI-5). The
`NEXT EXPLICIT ACTION:` line tells the human to commit it and states that the
command never commits.

O4:: With `--dry-run` on a `current` installation the output reads
`STATE: current` followed by `INSTALLED: <path>`, the same lines the real
call prints for the same state. Truthful for the real call and unambiguous
with `STATE:` above it; a `NOTHING TO DO`-style second line would read better
for the planned-action phrasing of the FTR's `--dry-run` bullet.
O5:: A symbolic link *inside* an otherwise current destination is invisible to
the state machine: `_hash_tree` skips link entries, so the packaged four plus
an extra symlink is still `current` and `install` does nothing (measured). An
extra *regular* file is caught (`modified` or `foreign`). Skipping links is
the right trade — the alternative is reading through a link the installer
does not own — and the FTR's definition of `current` speaks of the installed
files; recorded so the asymmetry is a known property.
O6:: `status` reports a symbolic-link destination as `foreign`, though the
state table defines `foreign` for a directory. It is the safe answer (nothing
is read through the link) and `install` refuses it with 2 as specified; one
FTR sentence would make it an explicit rather than an inferred mapping.
