=== 3. The slice re-derived at my own hand

==== 3.1 The command interface and the dispatcher

`frontdoor/cli.py` gained exactly one branch, `args[:1] == ['skill']` at
`:41-43`, placed after the existing `status` branch and before the legacy
`operator.main` fall-through; nothing else in the file changed, so no
existing subcommand's dispatch or output can have moved. Measured against the
installed `wfc`: `wfc skill`, `wfc skill nonsense`, `wfc skill status`,
`wfc skill install`, `wfc skill install mistral` and
`wfc skill install claude --scope project --skills-dir /x` each print usage
and exit 2; `wfc skill --help` and the `--help` of all three subcommands
print usage and exit 0. None reaches the legacy entry point — the candidate's
own tests assert that by monkeypatching `operator.main` to raise, and the
exit codes above are argparse's, raised inside the `skill` branch. The
process-level contract is what the FTR states; the `SystemExit` that carries
it is the same mechanism `frontdoor/init.py` and every other argparse-based
Front Door module already uses, and the console script is `cli:main`, so the
code reaches the shell unchanged.

`show`: default `SKILL.md`, `--list` prints the four relative paths with
`sha256:` digests, an unknown name exits 2, and `show ../../etc/passwd` exits
2 without reading anything (`FILE` is matched against the packaged key set,
not joined onto a path).

==== 3.2 Destinations, and the five states on both hosts and both scopes

Destination table reproduced: `claude` user scope honours `CLAUDE_CONFIG_DIR`
(`$CLAUDE_CONFIG_DIR/skills/wfc`) and otherwise `$HOME/.claude/skills/wfc`;
`codex` user scope `$HOME/.agents/skills/wfc`; project scope the Git
top-level of `--repository` plus `.claude/skills/wfc` or
`.agents/skills/wfc`; `--skills-dir DIR` addresses `DIR/wfc`, reports scope
`custom`, and is mutually exclusive with `--scope` in argparse itself.

All five states, driven on the installed command:

* `absent` → creates the directory, exit 0; the marker is
  `{"files": {...}, "schema": 1, "wfc_version": "0.1.0b1"}` with a 64-hex
  digest per relative path, no timestamp.
* `current` → exit 0, nothing written.
* `stale` (files equal their own marker, differ from the package) → replaced
  without `--force`, exit 0, which is SI-6's one permitted overwrite.
* `modified` (valid marker, hand-edited file) → `STATE: modified`,
  `DIFFERING FILES:` naming `SKILL.md`, exit 3, tree byte-identical
  afterwards.
* `foreign` (no valid marker, not `current`) → same shape, exit 3, tree
  byte-identical afterwards.
* `--force` replaces `modified` and `foreign`; the destination is then equal
  to the packaged files and carries today's marker.

Idempotence and determinism: a second `install` writes nothing, and the
marker written for a fresh install and the marker written when replacing a
`stale` installation are byte-identical (`json.dumps(..., sort_keys=True)`
over content digests and `VERSION`, no clock), so "equal inputs give equal
bytes" holds across runs, not merely within one.

`--dry-run`: for `absent` it prints `WOULD INSTALL:` and creates nothing, not
even a parent; for `stale` it returns 0; for `modified` and `foreign` it
returns 3; in every case the file system is unchanged — I compared the full
byte tree before and after each of the four.

The symbolic-link refusal I attacked directly: the destination was made a
symlink to a victim directory holding a file of its own. `install` and
`install --force` both printed the refusal to stderr, returned 2, and left
the link and the victim's file untouched; `status` reported `foreign` without
reading through the link. A packaged file replaced by a symlink to
`/etc/passwd` inside an otherwise current installation is classified
`modified` (exit 3) with no content of the target reaching stdout, and
`--force` then replaced the directory with `/etc/passwd` still a regular
file: `shutil.rmtree` removes links without following them, and `_hash_tree`
walks with `followlinks=False` and skips link entries outright.

Staging: the new tree is built in a `mkdtemp` directory in the *parent* of
the skills root and renamed into place, so nothing resembling a second skill
ever exists inside the skills root; the staging directory is removed in a
`finally`. I checked the leftovers after a successful install through a
symlinked skills root as well: `~/.claude` holds only `skills`, the real
target only `wfc`. Replacement removes the old directory immediately before
the rename, so a failure leaves the old installation, the new one, or none —
the two failures I provoked (section 6, O1) left the old state and nothing
partial.

Project scope: refused with exit 2 outside a Git work tree and in a bare
repository, writing nothing. Inside a real consumer repository with a seeded
commit, `install codex --scope project` left `git status --porcelain` showing
exactly `?? .agents/`, `HEAD` and `git ls-files -s` unchanged, the reflog at
its single seed entry, and no `.wfc/` anywhere (SI-5). The
`NEXT EXPLICIT ACTION:` line tells the human to commit it and states that the
command never commits.

==== 3.3 Status semantics (AC-4, SI-11)

The host is a required positional (`status` without it exits 2). `--scope`
selects exactly one installation, `--skills-dir` exactly `DIR/wfc` reported
as scope `custom`, and with neither flag the user installation plus the
project one when `--repository` is inside a work tree; outside one the
project block is simply omitted, exit 0, which I confirmed both in-process
and from the clean wheel environment (whose `cwd` was not a repository).
`status` returns 0 for every one of the five states and for a symlinked
destination — I measured all six, with `INSTALLED VERSION` showing the
marker's `wfc_version` (`0.0.0-old` for my stale and modified fixtures) and
`-` / JSON `null` where no valid marker exists. No aggregate state is ever
printed.

Host independence holds in both directions and is tested in both directions:
with one host `current`, the candidate's test makes the other host's
installation absent, then stale, then modified and asserts the first host's
`status` output is byte-identical each time, and the parametrisation runs the
pair `(claude, codex)` and `(codex, claude)`. The code reason is visible:
`resolve_destination` derives only the asked host's paths, and nothing else
in `cmd_status` reads the file system.

==== 3.4 The boundaries (SI-4, SI-8, SI-10) and the simplicity question

`skill.py` imports `argparse`, `hashlib`, `json`, `os`, `shutil`,
`subprocess`, `sys`, `tempfile`, `pathlib`, `typing`,
`importlib.resources` and `from ..implementation_identity import VERSION`,
and nothing else; `grep` over the whole package confirms the only importer of
`frontdoor.skill` is `frontdoor/cli.py:42`. The module never touches `.wfc/`,
the journal or Evidence, never imports the engine, and its only subprocess is
a read-only `git rev-parse --show-toplevel`. All content comes from
`importlib.resources.files("workflow_coordinator")`, which the clean-wheel
run proves is the installed package and not a checkout.

The new AST guards are in the style of the file they join and are not
vacuous: I exercised `_import_targets` with fabricated import statements and
it resolves the repository's relative forms correctly (one spelling it misses
is O2). On simplicity I looked for the usual costs and did not find them:
one module, no new abstraction layer, no state beyond the marker the FTR
mandates, no second source of truth (the digests are computed from the
packaged bytes at every call), and the dispatcher cost is three lines. The
one place I weighed an alternative is the `SkillError` class, used for a
single condition; it is cheap, and it is the seam that would carry the
remedy in O1, so I would keep it rather than inline the one refusal.

=== 6. Non-blocking observations

O1:: A filesystem failure in the install path raises an uncaught `OSError`:
the process prints a Python traceback and exits 1, which is outside the
FTR's `0 / 2 / 3`. Reproduced twice — a non-writable destination parent
(`PermissionError` from `skills_root.mkdir`) and a writable skills root
inside a non-writable parent, where staging in the parent is what fails
(`tempfile.mkdtemp`). Both fail closed: nothing was written and no partial
installation exists, which is why this is an observation and not a Finding.
Two further reasons not to block on it: the FTR specifies codes for the
outcomes it names rather than forbidding an exception, and the sibling module
the task names as the voice model, `frontdoor/init.py`, does exactly the same
(`destination.parent.mkdir(...)`/`write_text(...)` uncaught). The remedy, if
the maintainer wants the stated code surface to be total, is one `except
OSError` around the `_stage_and_install` call returning 2 through the
existing `SkillError` voice. The second case is worth knowing in its own
right: the FTR's staging rule makes an install depend on write permission in
the parent of the skills root, not only in the root.
O2:: `test_only_cli_imports_skill_module` misses one import spelling. For a
relative `ImportFrom` that names a module, `_import_targets` returns only the
module path and drops the alias names, so `from .frontdoor import skill` in a
package-root module resolves to `workflow_coordinator.frontdoor` and the
guard does not see it; `from .skill import …`, `from . import skill`,
`from .frontdoor.skill import …` and the absolute forms are all caught, and
`cli.py`'s own `from .skill import main` is caught. The invariant holds today
(the package contains exactly one importer, measured), so this is a gap in a
new guard rather than a product defect; closing it is one expression — add
`{f"{full}.{alias.name}" for alias in node.names}` to the returned set in the
relative-with-module branch, mirroring what the absolute branch already does.
O3:: Removing `PENDING_SUBCOMMANDS` is coverage-neutral, because the drift
guard reads fenced blocks only and `SKILL.md` names `wfc skill …` in prose.
This is the S1 review's O2 and S2 cannot close it: the skill text is withheld

O4:: With `--dry-run` on a `current` installation the output reads
`STATE: current` followed by `INSTALLED: <path>`, the same lines the real
call prints for the same state. Truthful for the real call and unambiguous
with `STATE:` above it; a `NOTHING TO DO`-style second line would read better
for the planned-action phrasing of the FTR's `--dry-run` bullet.
O5:: A symbolic link *inside* an otherwise current destination is invisible to
the state machine: `_hash_tree` skips link entries, so the packaged four plus
an extra symlink is still `current` and `install` does nothing (measured). An
extra *regular* file is caught (`modified` or `foreign`). Skipping links is
the right trade — the alternative is reading through a link the installer
does not own — and the FTR's definition of `current` speaks of the installed
files; recorded so the asymmetry is a known property.
O6:: `status` reports a symbolic-link destination as `foreign`, though the
state table defines `foreign` for a directory. It is the safe answer (nothing
is read through the link) and `install` refuses it with 2 as specified; one
FTR sentence would make it an explicit rather than an inferred mapping.
