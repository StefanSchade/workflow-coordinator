=== F001 — verified resolved (by my own independent execution, not by trusting the record)

*The fix.* `git diff 900efb6..5a2ba23 -- .github/workflows/release.yml`
shows exactly two added lines, each `set -euo pipefail`, as the first line
of the "Required test suite" block (`:93`) and of the newly-blockified
"Distribution content audit" block (`:117-119`). No other character in
either step, or anywhere else in the file, differs.

*Correctness of the fix, reproduced locally in this Hop* (not merely cited
from the record):

[source,text]
----
bash -e -c 'python3 -c "raise SystemExit(1)" | tee /dev/null'; echo "$?"
# -> 0  (the real GitHub Actions run: default; F001's failure mode)

bash -c 'set -euo pipefail; python3 -c "raise SystemExit(1)" | tee /dev/null'; echo "$?"
# -> 1  (the corrected form; pytest's/dist-audit's own exit status wins and
#        -e then stops the step)
----

This confirms both halves of the correction's claim: the platform's
undecorated default swallows the failure, and the one-line fix restores it.
G2 (required suite green) and G3 (C2 allow-list audit) are gates again; a
red suite or a failed audit now fails the `check` job and
`publish-testpypi`, which needs only `check`, no longer proceeds past it.

*The record's self-correction is itself accurate.* The verification
record's prior claim — "GitHub Actions' default shell already runs with
`-o pipefail`" — was false: that invocation (`bash --noprofile --norc -eo
pipefail {0}`) is documented for an explicit `shell: bash` key, not for an
omitted one. I independently confirm GitHub's documented default for an
unspecified `run:` shell on a Linux runner is `bash -e {0}` with no
`pipefail` (`docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax`,
the `jobs.<job_id>.steps[*].shell` table), matching both the broad-review
Finding and the correction's `<<pipefail-correction>>` section in the
verification record. The record now states this correctly and the false
claim no longer appears anywhere in it.
