=== 2. Finding 1 reproduced, and the correction verified by execution

*The refinement is right, and it matters for the test design.* At the
Commission commit `0fcaf78`, `bash -n` exits `0` for
`git show <base-ref>:docs/operator-notes.md`. A literal paste makes the shell
read `<base-ref` as an input redirection and `>:docs/operator-notes.md` as an
output redirection -- a "No such file" failure or a stray file, not a syntax
error. A `bash -n` regression test alone cannot see it. The candidate states
that distinction in the convention itself and builds the primary guard on
tokens, not syntax.

*The baseline, measured with the candidate's own checker.* 51 redirection
placeholders in 11 files, which reproduces the design record's number
exactly: `SKILL.md` 1, `commission.md` 2, `stops-and-evidence.md` 2,
`docs/operator-notes.md` 2, `ch03_running/01_preparation` 9,
`ch04_evidence/02_archive` 2, `ch05_self_development/01_topology_budget` 6,
`ch06_recovery/02_successors` 2, `ch08_examples/03_commission_to_archive` 2,
`ch09_consumer_quickstart/01_quickstart` 6,
`ch10_level1_orchestration/01_operating_pattern` 17. My independent scanner
found the same 11 files. At the candidate: *0*, by both checkers.

*The two defects beyond the four forwarded locations are real, and I
reproduced both.* At `0fcaf78`, `bash -n` fails on 11 in-scope blocks --
including the three `ch09_consumer_quickstart` tutorial blocks, where the
apostrophe in `--guidance-commit <the kit's guidance commit>` opens a single
quote that never closes. That is exactly the token guard's blind spot, and it
justifies keeping `bash -n` as the weaker second line rather than dropping
it. At the candidate, 0 of 61 blocks fail `bash -n`. The usage synopses in
`ch04_evidence/02_archive` and `ch06_recovery/01_outcomes` were also
genuinely not pastable: `[--dry-run]`, `{local,commit,discard}` and a bare
`[--preview]` line are glob and brace syntax. The archive synopsis is now a
labelled `[source,text]` block; the `[--preview]` line is gone and the prose
carries the fact.

*Every block the shipped skill presents as runnable now runs as written.* I
dumped all twelve fenced blocks in the four skill files and read each one.
The nine `shell` fences contain only concrete values and `UPPER_CASE`
placeholders; the two `yaml` fences parse (the content test does this too);
the one `text` fence -- the `wfc request` fragment -- carries an explicit
lead-in naming it a fragment and telling the reader which flags to repeat.
The `wfc report` block, whose two lines are alternatives rather than a
sequence, gained a lead-in saying so ("run one of them, never both"), which
was a real hazard the forwarded finding did not mention.

*The convention's justification holds against the installed CLI.* The design
record argues for `UPPER_CASE` primarily because it is already the CLI's own
metavariable notation. I ran the real argparse: `wfc request --help` prints
`--evidence-command NAME`, `--evidence-argv TOKEN`,
`--durable-artifact PHASE=PATH`, `--execution-override ROLE.FIELD=VALUE` and
`--output PATH` -- all five claimed forms, verbatim. The choice unifies two
notations instead of adding a third, is shell-inert (no redirection, no glob,
no brace or parameter expansion), fails informatively when pasted
unsubstituted, and costs no lines, which was binding: the reference files are
capped at 200 lines by `test_agent_skill_content` and `setup.md` stood at 199
before the slice. The two rejected alternatives are recorded with reasons,
and the one place a preceding shell variable was already available
(`ch08_examples`, `--scope "docs/qualification/$COMMISSION"`) now uses it --
the strictly more executable form where it was free.

*The line the slice drew is defensible and stated.* Angle brackets remain in
the manual's prose, tables, directory trees, output transcripts and
`yaml`/`json` blocks: no redirection hazard, and `<…>` is the ordinary
typographic notation for a path or ref shape. I checked the converse case as
well -- no `[source,text]` block in the manual presents itself as a command
line to paste -- and the manual uses only `[source,shell]`, `[source,text]`,
`[source,yaml]`, `[source,markdown]` and `[source,json]`, so the guard's
block parser has no attribute form to miss today.

=== 3. Finding 2 reproduced, and the correction judged against the contracts

*The strong claim is false, and I can demonstrate it from this Run.*
`docs/operator-notes.md` sits under `docs`, inside the committed scope
ceiling; the SKC2 Commission's own `scope` list names it
(`.wfc/governance/wfc-beta2-skc2-001/work-item.yaml:15`), and this very
candidate changed it. Run A's Worker may therefore change the notes, and
after review and integration the change is part of the committed base Run B
starts from, which is what Level 1 reads for Run B. "A Run cannot write the
notes the next Run is operated by" does not hold.

*What the candidate states instead is the guarantee that actually holds.*
The notes are read from a specific committed base state
(`git show BASE_REF:docs/operator-notes.md`), never a working tree and never
a Run's candidate; that fixes *which* notes a Run is operated by, reproducibly
and beyond the reach of an uncommitted edit or a Run in flight. I checked all
four corrected locations
(`ch09_consumer_quickstart/01_quickstart.adoc`, `references/setup.md`,
`docs/operator-notes.md`, and this slice's predecessor paragraph in the
design record) and they all say this and only this.

*Reproducibility versus trustworthiness is stated, not left to inference.*
Each location says plainly that a committed file is not thereby
human-authored and not thereby individually checked by the maintainer.
`ch09/01_quickstart.adoc:316-329` carries the full distinction, including the
explicit negation of the old claim, which is the right place for it: the
consumer chapter is where a reader forms the expectation.

*Nothing was conferred and no mechanism was added.* The two additions are
labelled as operating recommendations and nothing else: let a notes change
inside a Run's scope go through that Run's ordinary independent review, and
keep the file out of Worker scopes if no Worker should edit it. The retained
boundaries are intact in all four places -- no authority, subordinate to the
skill's own rules, not the Commission's `guidance.path`, and a note the
installed CLI contradicts is stale. No runtime function, configuration
option, approval level, CLI surface, schema or authority-model change appears
anywhere in the candidate; no file under `src/` outside the skill directory
is touched.

*The residual search is clean.* Searching the repository for the phrasings
and their paraphrases ("cannot write", "must not be able to", "never
influence", "is operated by") leaves two matches outside the Commission's own
request and task text: `ch09/01_quickstart.adoc:321` and
`FTR-WFC-LEVEL1-OPERATOR-GUIDANCE.adoc:678`. Both are the corrected text
stating that the claim *does not* hold, not residue of it. The inventory and
`test_agent_skill_content` assert "never a working tree and never a Run's
candidate", which *is* the narrow guarantee and was correctly left asserting
it.

=== 4. The tests, judged as regression value rather than as coverage

The new `tests/architecture/test_runnable_shell_examples.py` is 270 lines,
has no new dependency and no framework: `shlex`, `subprocess`, `re`,
`pathlib`. Its primary guard is token-level and its quote-awareness is
load-bearing, not decorative. I confirmed the true negative the module
documents: `printf 'TMPDIR=%s\n' "${TMPDIR:-<unset>}"` in
`ch05_self_development` is correct, executable shell in which `<unset>` is a
literal fallback *value*; a text-level `<…>` search would reject it, and the
lexer does not. I also confirmed the harder true positive: the one baseline
instance inside a *quoted* `$( … )` -- `MANIFEST="$(ls …/<attempt>/…)"` --
is only reachable by descending into the substitution body, because `shlex`
treats the quoted substitution as one opaque token. My own scanner, written
without that descent, found 50 of the 51 placeholders; the candidate's finds
all 51. Fixing the checker rather than dropping the case was the right call.

The guard self-tests pin both directions, including real redirections
(`> …/run.log 2>&1`, `<<'EOF'`) and a quoted placeholder, so the checker
cannot be loosened into uselessness without a visible test change. Nothing
pins wording: the assertions are structural, and
`test_at_least_one_runnable_block_was_actually_found_in_each_surface` guards
against the silent pass a stale block parser would otherwise produce -- the
failure mode such checks usually die of.

*The two changed pinned expectations were right to change, and are declared.*
`test_agent_skill_content.py` and `test_operator_notes_convention.py` pinned
the literal `git show <base-ref>:docs/operator-notes.md` -- that is, they
pinned the defective command and would have blocked its correction. Both now
pin `git show BASE_REF:…`, each with a comment naming the WorkItem and the
reason. No test is weakened, skipped, deleted or made conditional: the
assertion count rises, the reference line cap stays at 200, the `SKILL.md`
heading-order and second-bound assertions are untouched, and
`test_the_shipped_skill_states_the_placeholder_convention` and
`test_skill_states_its_placeholder_convention_once` add the requirement that
the convention be written where the operator reads it, so the mechanical
guard cannot outlive its stated rule.

  top-level `wfc --help`" warning and "runs no `plan`/`run`" left the
  prepare-checkout paragraph to fit the 200-line cap. The first survives
  verbatim in `SKILL.md`, which is always loaded first and whose copy is
  test-pinned, so no fact is lost; the second is still implied by the
  surrounding text ("then run `wfc plan`/`wfc request`/`wfc run` in the new
  checkout"). The judgement call the Worker flagged was the right one --
  raising the cap would have been weakening a test. Worth watching: at 200 of
  200 lines, `setup.md` has no headroom at all, so the next correction there
  must compress something or change the cap deliberately.
. *The token guard exists twice.* The canonical checker lives in
  `tests/architecture/test_runnable_shell_examples.py`; a simpler copy, which
  omits the `$( … )` descent and reports unbalanced quoting itself, lives in
  `tests/unit/test_agent_skill_content.py`. The divergence is documented and
  harmless today -- the skill files contain no command substitution -- but it
  is two implementations of one rule, and `tests/support.py` already exists as
  a home for a shared helper if the rule ever grows.
. *`_shell_fence_commands` does not reset its continuation buffer between
  fences* (`tests/unit/test_agent_skill_content.py`). A block whose last line
  ends with a backslash would bleed into the next block's first command. No
  such block exists now, and the consequence would be a spurious failure, not
  a miss.
. *The guard enforces the convention over the whole Operator Manual, which
  states no notation rule of its own.* The rule is written in `SKILL.md`, in
  the design record and in the assertion message a failing author will read,
  which mitigates it well. `docs/ai_info/doc_conventions.adoc` is outside this
  slice's scope, so stating it there is a candidate for a later slice, not a
  defect here.
. *`UPPER_CASE` loses the placeholder boundary that angle brackets marked.*
  `WI-WORK-ITEM-SLUG-001` and `WORK_ITEM_SLUG_broad_review.adoc` read as one
  token where `WI-<WORK-ITEM-SLUG>-001` showed exactly which part the reader
  supplies. Under the stated convention both are still readable (the
  lower-case tail marks the boundary in the second), and this is the
  convention's one real cost rather than a mistake in applying it.
. *`ch06_recovery/01_outcomes.adoc` now names `--preview` twice in adjacent
  sentences* ("Adding `--preview` to the same command line previews the
  grant. Before any mutation -- and as the whole of `--preview` … "). Accurate
  but redundant; a later editor can fold the two.
. *Redirection placeholders remain outside this slice's scope, and I
  reproduced the list.* Three runnable blocks in
  `docs/backlog/FTR-WFC-CONSUMER-DEMO-WORKSPACE.adoc`,
  `docs/warm_storage/beta1-productization/wfc_beta1_bp5_final_assurance_001_focused_review.adoc`
  and
  `docs/warm_storage/post-beta-planning/wfc_postbeta_docb_level1_focused_review.adoc`,
  plus four in `docs/cold_storage/` and two transcripts with unbalanced
  quotes in completed `warm_storage` review artifacts. Completed review
