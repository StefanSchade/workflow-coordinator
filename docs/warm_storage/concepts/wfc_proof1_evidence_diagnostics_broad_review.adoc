== Blocking finding

*The diagnostic probe converts a typed fail-closed refusal into an unwrapped
`OSError` when a prefix-matching sibling on `PATH` cannot be `stat`-ed with
one of three hard-coded error subclasses.*

`_discoverable_path_siblings` (`src/workflow_coordinator/evidence.py:142-145`)
narrows its tolerance to

----
except (FileNotFoundError, NotADirectoryError, PermissionError, ExecutableResolutionError):
----

copied from the resolution loop at `src/workflow_coordinator/evidence.py:175`.
In the resolution loop that tuple is adequate in practice, because a candidate
that cannot be `stat`-ed is a candidate that was going to be rejected anyway.
In the probe it is not: the probe `stat`s *other* names it discovered by
listing the directory, and any `OSError` outside those three subclasses escapes
`resolve_executable` instead of being skipped. `os.stat` raises plain `OSError`
for, among others, `ELOOP` (symlink loop), `ESTALE` (stale NFS handle) and
`EIO`.

Reproduced on a `PATH` directory that contains a symlink loop named `python3`
while the authored command is `python` -- i.e. the exact scenario the BUG
record is about, with one unlucky filesystem entry:

----
case1 listdir: ['python3']
base      -> ExecutableResolutionError: executable does not resolve to an
             executable regular file: python
candidate -> OSError: [Errno 40] Too many levels of symbolic links:
             '.../python3'
----

The authored command itself is untouched in both runs; only the *diagnostic*
step differs. The same divergence appears with a two-hop mutual loop
(`python3a` -> `python3b` -> `python3a`), where neither name is the authored
command.

This is material, not cosmetic, because the escaping exception is of the wrong
class for the seam above it:

----
base      -> EvidencePreparationError | caught by admit_parsed's
             `except ValueError`: True
candidate -> OSError                  | caught by admit_parsed's
             `except ValueError`: False
----

`ExecutableResolutionError` is an `OSError` subclass
(`src/workflow_coordinator/evidence.py:36`) and `EvidencePreparationError` is a
`ValueError` (`:32`). `prepare_evidence_commands` catches only
`ExecutableResolutionError` (`:223-225`), and `operator.admit_parsed` wraps only
`ValueError` from that call into `OperatorPreflightError`
(`src/workflow_coordinator/operator.py:511-517`), which
`commissioning.verify_render_manifest` then reports as `CommissionError`. A
plain `OSError` passes through all three seams uncaught, so `commission check`
reports an unclassified `OSError` traceback instead of the operator-facing
`operator preflight refused projected bundle: evidence command task-check:
...` refusal. Preflight still refuses and nothing is executed, so the
fail-closed *outcome* is preserved, but the refusal's exception type, its
wrapping and its operator-facing message are not.

That contradicts two explicit constraints of this WorkItem -- the task's "the
raised error stays fail-closed with the same exception type and the existing
message prefix" and "never change `_preflight` refusal behavior", and the
withheld authority's "no change to preflight refusal semantics" -- and the
non-scope item in `docs/backlog/BUG-WFC-EVIDENCE-COMMAND-RESOLUTION-DIAGNOSTICS.adoc:100`,
"change `_preflight()`'s fail-closed refusal behavior itself". A purely
diagnostic probe must not be able to change the class of the refusal it is
describing.

It also falsifies two claims that currently stand in the repository and should
be corrected along with the code: the earlier revision of this artifact
asserted that the probe "introduces no new uncaught failure class: `OSError`
from `os.listdir`/`os.stat` ... are all swallowed" (true for `os.listdir`,
which is guarded by a bare `except OSError`, false for `os.stat`), and the BUG
record's implementation note at
`docs/backlog/BUG-WFC-EVIDENCE-COMMAND-RESOLUTION-DIAGNOSTICS.adoc:135-138`
states that `_preflight` fail-closed refusal is unchanged.

Correction direction (not applied here -- this review changed no implementation
file). Broadening the probe's handler to `except OSError: continue` is
sufficient and loses nothing: `FileNotFoundError`, `NotADirectoryError`,
`PermissionError` and `ExecutableResolutionError` are all `OSError` subclasses,
so every name currently skipped is still skipped. Verified on a patched copy of
the candidate under `tmp/review-h005/fix_src/`: the differential matrix drops
from one divergence to zero and the focused module still passes 10/10. A
regression test belongs with it -- the committed suite does not detect the
defect, since all ten focused tests pass unchanged both before and after the
fix. `os.symlink(target, target)` in a `tmp_path` `PATH` directory, asserting
`pytest.raises(ExecutableResolutionError)` from `resolve_executable` and
`pytest.raises(EvidencePreparationError)` from `prepare_evidence_commands`,
reproduces it in two lines and is mutation-sensitive against the narrow tuple.
Both edits stay inside
`src/workflow_coordinator/evidence.py` and
`tests/unit/test_evidence_resolution_diagnostics.py`, already in scope; no
resolution, fingerprinting, alias or canonical-identity behavior is involved.

== What the change satisfies (independently reproduced)

=== The three required message facts are present

A bare authored `python` that does not resolve on a snapshotted `PATH`
containing `python3` raises, with the pre-existing type
(`ExecutableResolutionError`) and the pre-existing message prefix intact:

----
executable does not resolve to an executable regular file: python; discoverable
PATH siblings (informational only, not selected): python3; supply a conforming
environment by prepending its prepared bin/ directory to PATH
----

So (a) the unresolved authored command is named, (b) the discoverable siblings
are listed and explicitly marked as information rather than a selection, and
(c) one sentence states how a conforming environment is supplied.
`prepare_evidence_commands` still wraps it unchanged, so the operator-facing
form additionally carries the policy-authored command name
(`evidence command task-check: ...`). With no discoverable sibling the probe
reports `no discoverable PATH siblings` rather than omitting the clause.

=== Resolution, fingerprinting and alias handling are unchanged

A 19-case differential matrix compares the structural outcome of
`resolve_executable` between the `16a3034` baseline package and the candidate:
empty directory, sibling only, exact match present alongside a sibling,
non-executable regular file, directory named like a sibling, dangling symlink,
symlink loops, twelve matching siblings, absolute `argv[0]`, slash-containing
`argv[0]`, `PATH=""`, missing `PATH` entry, repository-relative `PATH` entry,
regular file used as a `PATH` entry, multi-entry `PATH`, embedded NUL in a
`PATH` entry, mode `0o000` `PATH` directory, and unrelated prefix names.
Eighteen of nineteen are structurally identical (same resolved invocation and
canonical basename, or same exception class). The nineteenth is the blocking
finding above. Notably the pre-existing `ValueError` for an embedded NUL in
`PATH` is identical on both trees, because the resolution loop reaches
`os.stat` before the probe can run.

No alias substitution: with `python3` present and `python` authored, `python3`
resolves on its own and authored `python` is still refused
(`test_resolution_is_unchanged_for_resolvable_commands_and_no_alias_substitution`).
`_fingerprint`, the `PATH` walk and the `os.realpath` canonical-identity model
are textually untouched; `src/workflow_coordinator/operator.py` and
`src/workflow_coordinator/commissioning.py` are byte-identical across
`16a3034..378d167`, so no refusal decision moved -- the finding above is a
change in which exception reaches those unchanged seams, not a change in them.

=== The probe is bounded, read-only and quiet

* *Reached only on refusal.* The probe call sits after the candidate loop has
  been exhausted (`src/workflow_coordinator/evidence.py:182`), so a resolvable
  command never triggers a directory listing.
* *Read-only.* A sibling whose body would `touch` a marker file is listed but
  never executed; the marker does not exist after either
  `_discoverable_path_siblings` or the full `resolve_executable` refusal. The
  probe uses only `os.listdir`, `os.stat` and `os.access`.
* *Bounded.* `DISCOVERABLE_SIBLING_PROBE_LIMIT` is 5 and the limit is enforced
  across `PATH` entries, not per entry; with twelve matching executables
  exactly five names are reported and the message stays at 258 bytes.
* *Selective.* The authored name itself, unrelated names, non-executable
  regular files, directories named like a sibling and dangling symlinks are all
  excluded; names are deduplicated across `PATH` entries and the ordering is
  deterministic (`sorted`).
* *Tolerant of a broken `PATH`.* Missing directories, a regular file used as a
  `PATH` entry and a mode `0o000` directory are skipped by the bare
  `except OSError` around `os.listdir` without affecting the refusal.
* *No path disclosure.* Only basenames enter the message; neither the `PATH`
  entry nor the repository path appears.

== Non-blocking observations

* *An invalid-UTF-8 sibling name reaches the message surrogate-escaped.* A
  prefix-matching filename that is not valid UTF-8 is listed as a
  surrogate-escaped `str`, so printing the refusal to a strict stream can raise
  `UnicodeEncodeError`. The refusal type and the fail-closed outcome are
  unaffected, and the Run journal is safe because it serializes with
  `ensure_ascii=True`. Carried forward from the earlier revision.
* *The bound test derives its expectation from the constant.*
  `test_sibling_probe_is_bounded` reads `DISCOVERABLE_SIBLING_PROBE_LIMIT`, so
  raising the constant survives while removing the enforcement is killed. An
  absolute assertion alongside the existing one would pin the intended small
  value too.
* *Cross-directory de-duplication and the path-like early return are
  uncovered.* Removing `name in seen`, or the
  `os.path.isabs(...) or "/" in authored_argv0` guard, passes the committed
  suite; both are implementation niceties with equivalent observable output,
  not BUG-record obligations.
* *Prefix matching can list non-interpreter siblings.* For a different authored
  token the clause can report `git` -> `git-lfs`. The clause labels entries
  "informational only, not selected", which is what the BUG record's desired
  direction asks for.
* *`repository.resolve()` is now computed twice* on the refusal path (once in
  the probe, once in `resolve_executable`). Harmless; noted only because the
  probe duplicates the loop's `PATH`-entry rooting logic rather than sharing
  it, which is also how the `except` tuple came to be copied.
* *The `_open.adoc` card is stale and out of scope.*
  `docs/backlog/_open.adoc:398-400` still reads "investigate actionable
  missing-tool/environment messages before selecting a correction". The
  overview is the maintainer's to update and is not in this WorkItem's scope,
  so it is reported here rather than changed. Its "never silently substitute
  `python3`" constraint remains honored.
