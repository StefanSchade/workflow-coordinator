== 4. The comparison can fail (mutation sensitivity), and what it cannot see

The delivered `test_manifest_comparison_detects_a_real_difference` exercises
the real comparison predicate, not a copy of it. I probed what it actually
catches by mutating the module in memory:

* `_strip_archived_at` weakened to also drop `copied_files` → *detected*
  (test fails).
* `_assert_manifests_equivalent` replaced by a no-op → *detected*.
* The two `archived_at`-non-null assertions removed → *not* detected
  (observation 2 below).

I also tested the other disjunct of the acceptance wording ("a tampered
fixture byte … makes the comparison fail") directly: a single flipped byte in
a disposable copy of `tests/fixtures/bp7/real_run/run/
checkout-association.json`, run through the full two-archiver comparison,
*still passes*. This is not a defect in the candidate; it is structural. Both
archivers read the same relocated state root, so a tampered fixture byte
yields the same new digest on both sides and cannot break an old-vs-new
equality check. The manifest-difference branch the Worker implemented is
therefore the feasible one, and the acceptance criterion ("a tampered fixture
byte *or* a manifest difference") is met. The fixture bytes themselves are
instead pinned by `PROVENANCE.txt` plus independent re-verification, as done
in section 2 of this review; see observation 1 for the hardening that would
automate it.

== Non-blocking observations

. *Committed fixture bytes are not pinned by any automated check.* `setUp`
  hash-pins the legacy archiver and the embedded `operator-plan.json`/
  `operator-summary.json` constants, but not the eight committed
  `real_run/` files; and, as section 4 shows, a tampered byte in those files
  is invisible to the two-archiver comparison. This is inherited from the
  accepted BP5 module and is not a violation of this task (which asks to
  *keep* the existing self-checks), but adding the `PROVENANCE.txt` digests of
  each fixture's `real_run/` files to its `FixtureCase` and verifying them in
  `setUp` would make fixture tampering self-detecting instead of relying on
  reviewer re-verification.
. *The mutation test does not cover the `archived_at`-non-null assertions.*
  Removing those two statements from `_assert_manifests_equivalent` leaves the
  mutation test green. A fourth case (a manifest whose `archived_at` is
  `null`) would close that gap.
. *Two new host-local PATH entries.* `tests/fixtures/bp7/real_run/ops/
  launch.sh` records `/home/stefan/.local/bin` and
  `/home/stefan/.nvm/versions/node/v22.23.2/bin` in its frozen `PATH`, path
  shapes BP5's fixture does not contain (BP5 already commits
  `/home/stefan/.local/bin/claude` and the repository paths). They are
  verbatim archived content with no credential material, and omitting them
  would break the verbatim-copy requirement; recorded only so a future
  fixture author knows the operator's inherited `PATH` becomes committed
  fixture content.
. *`FIXTURE_CASES` growth is a module edit.* The plan's C1b wording ("accepts
  a second … fixture copy … without a code change") is satisfied in the sense
  the task prescribes — the comparison logic is untouched and a new Run is
  added as descriptor data — but adding a fixture still means editing the test
  module (one `FixtureCase`, plus two embedded constants whenever the Run
  carries the documented `operator-plan`/`operator-summary` collision). A
  data-file-driven descriptor list would be a larger design than this task
  authorizes.
. *Fixture-name ergonomics.* The generated BP7 node id is
  `…_for_bp7`, while BP5 keeps the longer historical
  `…_for_the_same_real_run`. Intentional (the BP5 node id is pinned for
  regression), but the two shapes read inconsistently in test output.
