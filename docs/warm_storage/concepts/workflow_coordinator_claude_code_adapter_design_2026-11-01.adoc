== 1. Requirements, non-goals, and MVP criterion

Claude Code is a Level-0 release prerequisite, independently of deferred P4/P5; provider-reported token evidence is a separate bounded observational MVP requirement (`docs/warm_storage/concepts/workflow_coordinator_level0_mvp_planning_decisions_2026-10-21.adoc:100-152`; `docs/backlog/_open.adoc:233-245`).  This design must not turn either into a provider framework or telemetry system.

The small MVP criterion is: an admitted role binding may explicitly name `codex_cli` or `claude_cli`; Simple, Direct, and Robust use the selected provider through the existing `AgentExecutionPort`; and a Claude result reaches the existing exact, fail-closed WFC semantic validator.  No provider registry, automatic selection/fallback, SDK, router, new result contract, agent hierarchy, generic orchestration, programme-specific branch, or Coordinator-core change is proposed.

This Commission's use of `robust@v1` remains distinct from product capability, programme revision, technical schema version, and Runtime revision, exactly as required by `docs/warm_storage/concepts/workflow_coordinator_program_capabilities_and_version_lifecycle_decisions_2026-10-31.adoc:215-244`.  It does not alter `direct@v1` or `robust@v1`.

== 2. Verified current-code analysis

=== 2.1 Provider-neutral boundary that already works

`AgentExecutionRequest` and `AgentExecutionOutcome` are frozen, provider-neutral dataclasses (`src/workflow_coordinator/adapter.py:38-74`); the request carries Invocation, prompt, repository, result contract/kind/version, timeout and routes, while the outcome carries a raw candidate and transport observations.  `AgentExecutionPort` has one `execute(request)` method (`:79-80`).  `FakeAdapter` and `SubprocessAdapter` already implement the port (`:83-107`).  Claude needs no port, model, reducer, or result-contract field.

`validated_result` is the sole semantic acceptance authority (`adapter.py:110-144`).  It parses JSON, requires the exact envelope key-set, requires the selected version, compares the entire `(run_id, hop_id, invocation_id)` triple, and calls the parser selected by result-contract kind.  This remains unchanged.  Independently, `run_one_hop` rejects a nonzero return or timeout before examining any candidate, then rejects an absent candidate before calling `validated_result` (`src/workflow_coordinator/vertical.py:326-345`).

`ExecutionBinding` already holds plain-string adapter/model/reasoning (`src/workflow_coordinator/model.py:170-184`); `StagedQualificationAttempt` records string adapter and executable provenance (`:823-851`), and its parser does the same (`src/workflow_coordinator/serialization.py:1759-1786`).  Current source inspection finds no `codex` reference in either `model.py` or `reducer.py`.

|Headless prompt and cwd
|Installed `--help` says `-p`/`--print` is noninteractive and accepts the prompt argument; the official CLI reference confirms it queries and exits (https://code.claude.com/docs/en/cli-usage[CLI reference]).  Pass `request.prompt` as the trailing, non-shell argv argument and set `cwd=request.repository`.  A fake asserts prompt/cwd; an authorized later smoke confirms observed cwd.

|Installed help and the official reference expose `--model`; installed help exposes `--effort low|medium|high|xhigh|max`.  Map explicit binding model/reasoning to `--model`/`--effort`; never use a default or `--fallback-model`. |Structured JSON
|Installed help exposes `--json-schema` and `--output-format json`. Neither inspected source specifies the exact CLI JSON wrapper for 2.1.270 or confirms every feature of WFC's present strict projection.  The decoder and exact shared schema are therefore fake-tested and release-gated by the real smoke in §7.  If the exact schema is rejected, use only a semantically equivalent Claude-compatible projection; do not weaken WFC's envelope/correlation rules or fall back to free-form `result` text.

|Exit/error/timeout
|`--print` is finite; WFC owns the timeout and process-group kill.  The exact provider error JSON is not relied on: nonzero and timeout remain untrusted transport failures, with stdout/stderr only diagnostic tails.

|Installed 2.1.270 help exposes `--restricted`, `--safe-mode`, `--tools`, `--strict-mcp-config`, `--settings`, `--permission-mode`, and `--permission-prompts none`.  `--restricted` ignores user/project/local settings, confines file tools to working directories, and removes code-running tools unless `--tools` explicitly names them; `--safe-mode` disables `CLAUDE.md`, skills, plugins, hooks, MCP, commands/agents, workflows, and memory; `--strict-mcp-config` admits only explicit MCP configuration (https://code.claude.com/docs/en/cli-usage[CLI reference]). Provider sandboxing is an inner control, not an OS boundary WFC has verified (https://code.claude.com/docs/en/sandboxing[Sandbox documentation]).

|Authentication
|No credentials were read.  Documented paths include Console, subscription, and enterprise platforms (https://docs.anthropic.com/en/docs/claude-code/getting-started[setup documentation]).  Later smoke observes only success/failure under provisioned auth and prints no credential data.

|Usage
|The Agent SDK documents input/output/cache and per-model usage, and calls cost fields local estimates (https://code.claude.com/docs/en/agent-sdk/cost-tracking[Track cost and usage]). == 4. Minimal proposed implementation

=== 4.1 Adapter and candidate transformation

Add frozen `ClaudeCliAdapter(result_directory, model, reasoning_effort, executable="claude")` in `src/workflow_coordinator/claude_adapter.py`, implementing the existing port.  It validates explicit nonempty model/reasoning, launches without a shell in `request.repository`, and performs the same request-contract checks as Codex.

[source,text]
----
<executable> -p --output-format json --json-schema <serialized WFC schema>
  --model <binding.model> --effort <binding.reasoning>
  --restricted --safe-mode --strict-mcp-config
  --tools Read,Glob,Grep,Edit,Write,Bash
  --settings <generated-closed-settings.json>
  --permission-mode acceptEdits --permission-prompts none
  --no-session-persistence <request.prompt>
----

The prompt is an argv element passed without a shell.  The adapter creates no Codex output file and passes no Codex/OpenAI flag, `--allowed-tools`, bypass-permissions flag, `--add-dir`, `--mcp-config`, plugin option, session resume/continue option, or fallback-model option.  It may retain only small generated schema/settings/diagnostic files, never raw transcripts.

`generated-closed-settings.json` is a short adapter-created file under the existing private result directory, with the repository path interpolated as data (not shell text), permissions that deny `WebFetch` and `WebSearch`, and this mandatory sandbox core:

[source,json]
----
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {"denyRead": ["~/"], "allowRead": ["<repository>"]},
    "network": {"allowedDomains": []}
  },
  "permissions": {
    "deny": ["WebFetch", "WebSearch"],
    "blockReadsOutsideWorkingDirectories": true
  }
}
----

The implementation must add no `excludedCommands`, additional directory, network-domain, credential-path, or permissive allow rule.  It sets `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` in the Claude process environment so Claude applies its documented all-subprocess environment scrubbing; the later smoke verifies that this does not break the selected authentication path.  `--restricted` plus the explicit `--tools` list makes the minimum built-in surface visible: project-local file inspection/edit/write and Bash only.  The only intended noninteractive Bash path is the CLI's sandboxed Bash behavior; `--permission-prompts none` turns an action that still asks into denial, and `allowUnsandboxedCommands: false` prevents a retry outside the sandbox.  There is no provider-side command fallback.  `acceptEdits` is retained only for the named project-local file tools.

This profile deliberately loads no user, project, or local settings; no `CLAUDE.md`, skill, hook, plugin, agent/command, workflow, memory, MCP server, custom output style, or explicit MCP configuration is admitted.  Managed settings/policy may still apply according to Claude Code's documented precedence.  They are an administrator-owned residual host-policy input, not part of the WFC execution binding or a claim of controlled source.  An installation whose managed policy forbids the profile must be rejected by a preflight compatibility check or by an observed failed process outcome; it must never silently fall back.  An installation whose managed policy adds behavior is outside the profile's reproducibility claim and must be accepted as a separately governed host prerequisite.  The adapter neither tries to inspect nor logs managed policy.

This is deliberately only an inner provider control.  Claude documents that its Bash sandbox covers shell commands and their children, while file tools, hooks, MCP, and other processes can run outside it (https://code.claude.com/docs/en/sandboxing[Sandbox documentation]); the closed startup removes the latter configurable sources, but it does not turn WFC into an OS-sandbox verifier.  `failIfUnavailable` prevents an unsandboxed fallback when support is unavailable and the settings deny default network access.  Whether that condition prevents startup or instead refuses a later command is provider behavior that the later smoke must qualify for the pinned CLI/platform; WFC does not infer an exit status from it.

After clean transport, the adapter parses the Claude JSON transport wrapper, requires its successful structured-output member, JSON-serializes that member, and returns it as `candidate_result`.  It never fills or repairs `run_id`, `hop_id`, `invocation_id`, route, kind, or version.  The complete path remains:

[source,text]
----
Claude schema-validated object -> adapter wrapper decoder -> canonical WFC JSON
-> validated_result(raw, dispatched invocation, selected kind/version) -> reducer
----

Claude schema validation is only an earlier guard.  WFC still independently rejects malformed keys, contract/version mismatch, any correlation mismatch, or kind-specific semantic invalidity.

Extract the current envelope construction from the OpenAI-named adapter to candidate `src/workflow_coordinator/structured_result_schema.py`.  The builder still takes Invocation, kind/version and permitted routes and returns the same closed WFC envelope shape.  Codex consumes it and keeps `assert_openai_strict_schema`; Claude serializes it for `--json-schema`.  This is one shared projection helper, not a new adapter architecture.

=== 4.2 Selection and unchanged WFC responsibilities

`run_execution_configuration_from_yaml` admits exactly `codex_cli` and `claude_cli`.  In `run_serial_hops`, a private two-case factory constructs Codex or Claude with the resolved binding and current executable; unknown values retain a defense-in-depth `OperatorPreflightError`.  `_binding_evidence` stays provider-neutral and persists the actual adapter/executable/model/reasoning.

Do not change `model.py`, `reducer.py`, port records, `validated_result`, prompt/result contracts, Coordinator-owned Git mutation, evidence, or Finding authority.  Provider/model selection remains a shell concern, as required by the architecture boundary.

=== 4.3 Failure mechanics

Claude copies Codex's relevant local process pattern, not its CLI dialect: `Popen(..., start_new_session=True)`, `communicate` timeout, `killpg(SIGTERM)`, three-second grace, `killpg(SIGKILL)`, and bounded stdout/stderr tails.  OSError/value failure or adapter-generated schema/settings write failure before `Popen` raises an `ExecutionNotStartedError` subtype.  The adapter classifies only process facts it observes: a nonzero exit and a timeout are transport failures, while a zero exit proceeds to wrapper decoding and WFC validation.  `failIfUnavailable` and `allowUnsandboxedCommands: false` make a sandboxed-command refusal fail closed at the provider, but a refusal or sandbox loss after `Popen` can leave Claude running; absent a pinned-CLI, documented machine-readable signal that the implementation verifies, the adapter does not promote it to a nonzero transport failure.  A started process, including one with a decoding error, returns its transport observations so existing uncertain-dispatch recovery stays conservative.  CLI-side rejection or silent ignoring of generated settings is likewise qualified by the pinned-profile smoke, not recast as an adapter-local not-started error.

=== 4.4 Mixed roles and executable provenance

Today a Claude Worker plus Codex reviewer is not safely supportable: each role could select a different adapter but both receive one scalar executable.  A dispatcher wrapper that guesses provider is hidden routing and is rejected.  The selected MVP supports homogeneous real-provider bindings per Run: Simple uses either provider for Worker, while Direct/Robust use either provider for all their roles.  Mixed bindings with one executable must fail in preflight before provider execution.

If mixed roles become a requirement, the smallest separately authorized extension is repeatable `--role-executable ROLE=PATH`, retained through `wfc_op` preparation and launch, validated against admitted roles, and used as an override to the existing scalar default.  `_binding_evidence` records the resolved per-role path.  This preserves the existing three-field `ExecutionBinding` grammar and homogeneous invocations, avoids a registry, and is explicitly out of this slice.

== 6. Security, transport failure, and trust boundaries

Claude's permission mode and closed sandbox request are not a Coordinator-verified OS boundary, just as the current Codex `--sandbox workspace-write` request is not one.  WFC independently relies on the pinned clean checkout, admitted binding/executable, post-Hop Git/scope observation, Coordinator-owned Git/evidence, semantic reduction, and Finding authority.  The Claude profile does nonetheless make provider behavior deliberately bounded: `--restricted` excludes user/project/local settings and confines file tools; `--safe-mode` disables workspace/user customizations; `--strict-mcp-config` with no `--mcp-config` excludes MCP; the explicit tools exclude web/agent surfaces; and generated settings require the Bash sandbox, prohibit unsandboxed retry, block home-directory subprocess reads, and give it no network domains.

The remaining host trust boundary is explicit.  Managed Claude policy continues to apply, and the Bash sandbox's default process environment/read surface is otherwise provider-defined.  WFC does not read configuration or credentials to prove effective policy.  Thus no claim is made that managed policy, an external process, or a provider defect is contained by the WFC binding.  The real smoke verifies the selected profile on the pinned executable/platform; deployment that requires stronger cross-process isolation must provide it outside this adapter (for example, by its managed host/container policy), not by expanding this slice.

[cols="2,3",options="header"]
|===
|Event |Required behavior

|Local schema/executable/startup failure before `Popen`
|Local not-started error; existing pre-acceptance path removes dispatch marker.  No provider invocation occurred.

|Nonzero exit, including valid-looking JSON
|Return transport facts; vertical rejects before candidate parsing.  No automatic replay.

|Timeout with partial stdout/JSON
|Terminate group, return timed-out outcome/tails, reject before parsing.  Partial output never becomes candidate.

|Zero exit but absent/malformed wrapper, absent structured output, malformed envelope, or wrong correlation
|No valid candidate reaches acceptance; never repair fields from dispatch and never retry.

|Observed permission/auth process failure
|Unanswered prompts deny rather than hang.  An observed nonzero auth, policy, or startup-sandbox failure is rejected as transport; no secret, settings body, or credential value is copied or logged.

|Post-start sandboxed-command refusal
|`failIfUnavailable` and `allowUnsandboxedCommands: false` keep the command from retrying unsandboxed, but the CLI may continue and return an ordinary wrapper.  The adapter records only its observed exit/wrapper/tails and does not invent a transport failure or a provider-independent tool-execution oracle.  The pinned-profile smoke must characterize this behavior.

|Unexpected error after dispatch
|Existing dispatch marker and uncertain-dispatch recovery conservatively stop/charge; no replay.
|===

Therefore one accepted provider invocation remains one charged Hop; provider failure cannot fabricate completion or bypass preflight, reduction, trusted Git, evidence, scope, or Finding controls.

Add deterministic `tests/unit/test_claude_adapter_conformance.py` fake-executable coverage for exact argv (no Codex, plugin, MCP, resume, fallback, bypass, or ambient-config flags), prompt/cwd, model/effort, shared schema ID/route constraints, startup failure, generated closed-settings JSON, scrubbed-subprocess environment, and successful wrapper extraction. Every negative case proves no repair or candidate acceptance.  Separately fake a zero-exit wrapper following a provider-side sandboxed-command refusal: assert only that no unsandboxed retry is requested and that the adapter does not manufacture a nonzero transport result or tool-execution oracle.

Extend serialization tests so exactly the two adapter literals are admitted and arbitrary literals rejected.  Add operator tests that patch each adapter and prove identical binding provenance/reduction plus mixed-binding/scalar-executable rejection.  Extend `test_wfc_op.py` only to preserve a `claude_cli` binding; do not authenticate or invoke Claude.  Keep Codex tests, including OpenAI strict-subset checks, passing after the shared-builder extraction.

A separately authorized real-smoke suite is release-gating, not this design's execution.  Its pinned-CLI scenarios are isolated processes, so mutually exclusive startup and post-start states are not conflated:

* one ordinary `claude -p` invocation in a disposable repository on a tiny authorized-file task confirms the exact JSON wrapper/structured-output decoder, schema enforcement, working directory, valid model/effort, an authorized in-repository edit, and a required sandboxed test command; it also plants a project customization (for example `CLAUDE.md` or a hook) and proves it is not loaded, then attempts an out-of-workspace file read and network access;
* one startup-unavailability scenario, on an authorized pinned CLI/platform configuration where the required sandbox cannot become usable, records the actual process status and any wrapper behavior; and
* one post-start refusal scenario invokes a sandboxed command that the provider refuses after a usable session has started, records the actual process status and wrapper behavior, and proves no unsandboxed retry.

Each invocation is separately authorized, disposable, and non-secret.  The two failure scenarios do not prescribe a nonzero exit or a wrapper, and the ordinary-success scenario is not treated as evidence of either failure state.  The suite records only pass/fail and non-secret provider-usage field names, never credentials, settings contents, or raw transcripts.  It is not a production Run or fallback path.

== 9. Decisions requiring maintainer approval

The implementation slice is otherwise bounded, but these maintainer decisions remain explicit:

. Is a Claude Worker plus Codex reviewer required for Level-0?  If yes, authorize the bounded `--role-executable` interface from §4.4; do not use a dispatcher executable.
. Does the intended deployment accept the stated residual trust in administrator-managed Claude policy, or must the implementation WorkItem also receive a separately specified managed-host prerequisite?  The adapter cannot prove or pin managed policy without a broader execution-environment authority.
. If the named local `Bash` surface cannot run the required tests under the fail-closed sandbox, which exact project-local command capability and sandbox filesystem/network exception is acceptable?  Approval is necessary because it widens the provider-side capability request; do not solve it with ambient allow rules, `excludedCommands`, or an unsandboxed retry.

Future token evidence must attach only provider-reported fields plus provider/version/output-location provenance, represent absence as absence, and avoid pricing, estimates, raw transcripts, policy, or routing.  This design neither blocks nor implements that separate MVP work.
