= P3.5 structural-invariant reassessment
:toc:
:sectnums:

== Commission conclusion and reader's map

This independent reassessment reaches conclusion *iii*: defer the accepted
P3.5 package for Level 0--the explicit Finding-creation declaration and its
new runtime enforcement, the proposed clean-`GOTO` guard, static
ordered-reachability validation/preflight placement, and the resulting legacy
new-launch admission and profile-migration policy. Retain the *existing*
runtime completion guard and use the bounded convention in <<d8>>. This is a
recommendation about Level-0 prioritization only; it changes no guard, Finding
rule, profile, BUG disposition, or accepted design record.

The conclusion is not that empty disposition authority is harmless. It creates
a recoverability/usability risk after an actual blocker is opened, not a route
to incorrect completion. The 43/0 result is therefore disproportionate at
Level 0 for a capability-only predictor with deliberate false positives.

== Evidence and method

This report read the required Concept, BUG, accepted design/review, Level-0
decision, backlog row, current source, and representative governance profiles.
Every engine-behavior claim below cites current source, rather than design
prose. Line numbers refer to base 079b508665bc3e3ad58a0ce74448905475f4b067.

The concrete vocabulary separates states, authorities, and routes:
FindingState includes open, resolved, residual, and superseded;
FindingAuthority includes gate and human; and RouteEffect includes complete
and await_human (src/workflow_coordinator/model.py:44-55,118-124). A
ReviewDescriptor separately holds gate authority and permitted Finding
operations (model.py:222-231).

[[d1]]
== 1. Actual failure class

P3.5 targets a structural *ordered authority-opportunity mismatch*. For an
opener-capable invocation, the accepted static rule rejects when there exists
a checkpoint-reaching continuation path on which no strictly later phase has
the required disposition authority. Equivalently, the rule demands an
authority-bearing later phase on every such path; one dangerous path suffices
for rejection. This is a capability/path-conformance property, not a claim
that every path lacks authority, or that a later authority holder will actually
emit a disposition. If the capability is exercised on an uncovered path,
completion is unavailable and current mechanisms supply no automatic authority
handoff. The S3-002 BUG is one instance.

This is not a completion-safety failure. _finding_operation maps open to
resolved/residual/superseded operations, and _may_dispose permits them only
to human authority or a gate allowed that operation
(src/workflow_coordinator/reducer.py:470-498). It is also not general
liveness: loops and never-completing profiles may fail to make progress for
unrelated reasons.

[[d2]]
== 2. Runtime completion guard and remaining risk

The guard is global and history-sensitive. _has_open_blocker is true exactly
for a persisted Finding that is both OPEN and blocking
(reducer.py:1145-1149). _apply_route permits goto, but on every COMPLETE tests
the predicate and instead stops for completion_blocked_by_open_blocking_findings
(reducer.py:1152-1174). Thus no admitted Run can complete with an actual open
blocking Finding, regardless of which phase opened it.

What remains is recoverability: the guard permits the Run to proceed until
completion is attempted, then stops it; it does not supply a disposer.
await_human stops, prerequisite authorization only changes a Run to SUSPENDED,
and reconciliation merely restores READY after checks
(reducer.py:1175-1182,1899-1988). The remaining harm is stranded work, human
intervention, and spent Hops/provider cost--not silent completion.

[[d3]]
== 3. Safety or admission-time usability

P3.5 is an admission-time usability/recoverability check, not an additional
completion-safety invariant. The proposed checker sees capabilities, paths,
and later authority opportunities; the guard sees actual `run.findings`. The
guard covers the unsafe terminal state that P3.5 might otherwise be presumed
to prevent. A rejection predicts a possible bad operational episode, not an
unsafe admitted Run. Nor does acceptance guarantee recovery: the authority
holder can emit no disposition delta, leaving the actual Finding for the guard
to stop at completion.

It has a safety-adjacent architectural benefit: it makes a per-path later
authority-opportunity promise honest before resources are spent. That may
justify it post-MVP, but does not make corpus-wide breaking admission a
Level-0 MUST-HAVE while the dynamic backstop is live.

[[d4]]
== 4. Strict-after rule: necessary cases and overreach

Strict-after is necessary for the accepted ordered *authority-opportunity*
property. Case A: review may open a blocker and has resolve, but its accept
route is complete; concurrent authority is not a later invocation opportunity.
Case B: an opener goes to a later completing phase with no disposition
authority and carries the blocker unchanged. Counting opener authority as later
authority would accept both H005/H002-falsified shapes. The reducer stops Case
B at completion as <<d2>> demonstrates.

It is not necessary in every rejection for completion safety. In Case A,
history H0 has no Finding and completes correctly; H1 opens one and stops,
rather than completing incorrectly. Strict-after is necessary only for the
stronger universal topology guarantee that every checkpoint-reaching path
encounters a later phase that *can* dispose. It does not guarantee an
autonomous later disposition in each actual opening history: that later phase
may submit no closing delta.

[[capability-history]]
== A. Capability is not history

Schema-v2 gate capability is review.authority: gate with
blocking_policy: blocking_only; the parser requires the latter and parses
finding_authority separately (serialization.py:548-598). Proposed v4
may_open_findings would also be a declaration, not a Finding. A Finding
appears only when a correlated result delta is accepted; in result v2 an open
blocking Finding additionally requires evaluator role (reducer.py:702-735).

Concrete counterexample: a one-phase gate has accept: complete, may open, and
no resolver. H0 returns accept with no Finding: the guard is false and
completion is proper. H1 returns the same route with an open blocker: it is
persisted and the guard stops completion. Static P3.5 rejects both from the
same declarations; the dynamic guard distinguishes them. Thus static checking
cannot substitute for the dynamic guard; it can only complement it by
rejecting possible H1s and necessarily rejecting harmless H0s.

[[d5]]
== 5. The 43/0 inventory, checked against YAML

Two actual schema-v2 profiles independently show the claimed predicate shape.

governance/self-development/correction-convergence-escape-implementation-s3-002-profile.yaml
defines review as a blocking-only gate with no finding_authority and
accept: {effect: complete}. It is the minimal opener-capable,
direct-completion, no-strict-after-disposer shape. Its correct/rereview cycle
cannot rescue a Finding when accept is selected.

governance/self-development/correction-convergence-escape-implementation-s1-001-profile.yaml
has the same shape: its review is a blocking-only gate,
finding_authority: [], and accept: complete; correct and rereview exist only
on the other route. Applying accepted-design sections 4.3/4.5 predicates finds
an opener candidate and no reachable strict-after disposer on its terminal
path. These are YAML facts, not reliance on design section 6.1.

The design-review-003 profile confirms breadth: its rereview has
finding_authority: [resolve] but accept: complete; concurrent authority is
insufficient under strict-after. Samples cannot establish cardinality alone;
the separately read inventory and Level-0 decision record state 43/0. They
establish the mechanism in actual members.

[[d6]]
== 6. Is a narrower sound invariant possible?

Yes, if sound means sound for actual completion safety:

____
For every application of a COMPLETE route, reject completion iff the Run's
persisted Findings contain an open blocking Finding.
____

That is exactly the existing _has_open_blocker/_apply_route invariant. It
admits all 43 and does not reintroduce the H005/H002 falsification as an
*unsafe completion*: neither an opener's concurrent authority nor an
undisposed carried Finding can cause a real open blocker to reach COMPLETED.
It deliberately re-admits the topology and its possible stopped history; this
is a reduction of the accepted pre-Run authority-opportunity property, not a
claim to preserve it.

No narrower *static capability-only* invariant can both admit these profiles
and retain the accepted stronger path guarantee that each checkpoint-reaching
path offers a strictly later disposer. H0 and H1 in <<capability-history>>
have identical topology/declarations but opposite answers under a predictor of
whether a blocker will be opened. A validator admitting H0's profile admits
H1's; rejecting H1 rejects H0. Even the accepted rule is only an opportunity
proof, not an autonomous-recovery proof. This follows from the reducer's
information boundary, not a proposal for taxonomy or liveness.

[[d7]]
== 7. Retain design plus migrate?

Retaining the design unchanged and migrating profiles is justified only if the
stronger per-path, later-disposer *opportunity* guarantee is deliberately
worth 43 potential migrations/schema-v4 adoption. Its benefit is avoiding a
class of possible post-opening stops and making a commissioning promise
pre-Run; it cannot ensure an actual later disposition. It is not avoiding
incorrect completion, already blocked by the reducer.

The known cost is revocation of new-launch admission for all 43 current
profiles followed by profile redesign. The Level-0 decision record expressly
presumes neither compatibility nor breaking change. No demonstrated safety
defect outweighs this cost at the Level-0 milestone. Retention is a coherent
post-MVP policy choice, not the recommended default.

[[d8]]
== 8. Level-0 reduction and bounded convention

Defer the accepted P3.5 package for Level 0. Specifically, defer (1) schema-v4
`may_open_findings`-style explicit creation declarations and their proposed
runtime enforcement, (2) its additive clean-`GOTO` guard, (3) static
ordered-reachability validation and any extension of operator preflight to
host it, and (4) the consequent new-launch rejection, profile migration, or
schema-v4 adoption policy for legacy profiles. This does *not* defer the
already implemented history-sensitive completion guard in <<d2>>, which
remains the Level-0 safety backstop. Until later separately authorized work,
use this bounded operating convention:

* A gate that opens a blocking Finding routes for correction or human handling,
  not successful completion.
* A Run stopped with completion_blocked_by_open_blocking_findings is not
  treated as completed or silently resumed.
* A commissioning that needs a later disposition opportunity documents a
  later authorized disposer as a review criterion, rather than using a
  universal admission validator; actual disposition remains history-dependent.

This neither claims liveness, authorizes human disposition, adds an
authority-handoff route, nor changes profiles. It leaves an accepted risk--a
Run can stop after a real blocker--bounded by fail-closed completion. Given
<<d1>>-<<d4>>, that is acceptable at Level 0 and avoids migration solely to
predict a history that may never occur.

== Current structural-validation boundary

The parser validates profile versions/required fields, review grammar, and
route shape (src/workflow_coordinator/serialization.py:548-622,667-686).
Operator preflight pins/parses inputs and checks clean head, roles, actions,
and scopes (src/workflow_coordinator/operator.py:281-367). None computes
ordered Finding-disposition reachability. This is an implementation gap, not
proof of unsafe admission: reduce_result applies correlation and mechanical
preemption before Finding/route authority (reducer.py:1520-1588), and the
terminal guard is decisive.

== Recommendation for maintainer disposition

Choose conclusion iii for Level 0: do not implement any of the accepted P3.5
proposal components listed in <<d8>> yet; retain their design/counterexamples
as a post-MVP option; retain the existing completion guard; and use <<d8>>.
Reassess if real Level-0 operations show that post-opening stops justify the
43-profile burden. This does not close the BUG: gate and disposition authority
remain independent.
