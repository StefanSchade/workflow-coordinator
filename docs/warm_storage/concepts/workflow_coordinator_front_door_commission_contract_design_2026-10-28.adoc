= Front Door Basic Commission Intent / Compiler Contract Design
:toc:
:toclevels: 3
:sectnums:

Status:: DESIGN TARGET. This record is the proposed target for independent
review in `WI-WFC-FRONT-DOOR-COMMISSION-CONTRACT-DESIGN-001`.  It authorizes
nothing: neither an implementation nor a Direct/Robust Commission.
Date:: 2026-10-28.
Scope:: The smallest shared, semantic Commission contract and deterministic
projection needed for Front Door Basic.  It selects a *closed*, versioned
reusable program and renders the governing inputs already admitted by WFC.

== 1. Decision in brief

`DEC-WFC-020` requires one structured semantic Commission behind both a human
and a machine interface, with a deterministic and authority-free projection.
`DEC-WFC-022` names Direct and Robust as the first program targets.  The
2026-10-26 Front Door plan deliberately left the binding, versioning, and safe
parameter surface open; the accepted H008 archaeology supplies the important
limit: its common F4 shape is a topology observation, *not* a semantic-family
claim.  Finding authority, required-evidence failure routing, routes, and
mandatory review are counterexamples to treating an F4 profile as a template.

This design resolves that bounded question as follows.

* A `CommissionIntent` is an above-boundary, canonical *authoring request*.
  It selects one immutable program revision and supplies only task bindings.
* A deterministic, provider-free `CommissionCompiler` renders an ordinary
  WorkItem, profile, policy, and task, selecting the existing component
  manifest unchanged.  Its output is a reviewable Git diff, not authority.
* Direct-v1 and Robust-v1 are closed programs, not user-authored graphs.  An
  Intent cannot supply phase keys, routes, actions, review descriptors,
  Finding authority, or evidence-failure routing.
* A maintainer reviews the exact rendered bundle and separately authorizes
  PREPARE/LAUNCH at its Git commit.  Level 0 continues to admit the pinned
  existing inputs, unchanged.  The Intent never becomes an input to the
  reducer or a substitute for that act.

This is intentionally one record, rather than a schema paper plus a migration
plan: the field contract, ownership, projection, two executable-shape examples,
and first proof slice are one decision boundary.

== 2. Boundary and ownership

The split is the Commissioning Service concept's sections 4--7, made concrete
for the two initial programs.  In particular, the monotonic rule remains:
above the boundary a requester may add assurance and narrow capability; trusted
derivation may also add assurance and narrow capability; neither kind of
addition is removable from above.

[cols="2,2,2,4",options="header"]
|===
|Thing |Owner and canonical form |May change it |Rule

|Reusable program semantics
|Repository-owned catalogue entry, for example
`governance/workflow-programs/robust/v1.yaml`, with an immutable
`program_id`, `revision`, and source Git object.
|A separately authorized maintainer change creating a new revision.
|Owns closed phase graph, route set, role set, review/evidence/Finding rules,
component selection, action ceiling, and program invariants.  Existing entries
are never edited in place; a correction is a new revision.

|Commission-specific task bindings
|`CommissionIntent` YAML and its rendered task/WorkItem values.
|Requester authors; compiler only validates and projects.
|Owns the task, explicit acceptance prose, scope, persona selections, artifact
destinations, requested evidence profile, and withheld authority.  These are
requests, not capability grants.

|Explicit authorization
|Maintainer review of the exact rendered Git diff, followed by a distinct
maintainer PREPARE/LAUNCH authorization at a named commit.
|Maintainer or another separately protected authority source only.
|A commit records and pins a proposal; it does not itself authorize execution.
The `authority_source` remains human-authored prose and is never boilerplate.

|Derived effective permissions
|The admitted WorkItem/profile/policy composition and Level-0's own
derivations, reported by PREPARE.
|Level 0 admits or rejects; the Intent has no write path to this result.
|`_preflight` enforces role/binding equality, policy action containment, scope
containment, artifact mapping, A1 paths and evidence disposition.  A later
trusted floor may narrow further; the compiler cannot relax either result.

|Runtime execution
|Pinned Runtime, Coordinator state, trusted evidence and execution bindings.
|Runtime/operator under the separately authorized launch.
|Owns provider invocation, actual model/binding admission, state transitions,
reconciliation, evidence and Git mechanics.  It is not a compiler service.
|===

The catalogue is consumer-repository governance, not a Runtime catalogue and
not a provider registry.  `program_id@revision` identifies an immutable
catalogue document; `program_source_commit` in the Intent pins the exact Git
object from which it was read.  The compiler copies the program ID/revision and
source commit into the rendered WorkItem's inert `profile_labels` and into its
render manifest.  The rendered profile contains the complete closed semantics,
so an old committed Commission remains inspectable and executable according to
its admitted files even after a later program revision exists.  A same-path,
silently changed catalogue entry is invalid by catalogue convention and by the
PREPARE-time projection-equivalence check in <<pinning-hand-edits-and-launch>>;
it is not a versioning mechanism.

=== 2.1 Parameter boundary

The allowed Intent parameters are deliberately few:

* identity and authority prose: Commission/work-item ID and the literal
  `authority_source` statement;
* task semantics: title, task body, acceptance semantics, withheld authority,
  and the typed default escalation instruction;
* bounded path decisions: task scope and required durable-artifact paths;
* semantic persona bindings for the program's already-fixed workflow roles;
* one program-permitted evidence-profile identifier, including its displayed
  acceptance meaning, and one program-permitted repository-policy basis; and
* a bounded hop limit no greater than the selected policy basis and program
  ceiling.

The compiler may project one such value into all places which must agree.  It
may never add a path, action, role, policy command, capability, provider,
model, or acceptance meaning to make a render fit.

The following are structurally forbidden in an Intent: arbitrary phase or
route declarations; route effects; initial-phase overrides; WorkflowRole
creation; phase actions; gate descriptors/breadth/context; `finding_authority`;
evidence command argv/timeout; `failed_evidence_route`; program components;
policy governance paths; a model/adapter/binding; and a switch which omits a
program-required review.  These are program, policy, or Runtime facts.

This boundary is specifically responsive to the archaeology's named
counterexamples: F4 topology equivalence is not semantic equivalence;
`[resolve]` versus `[]` changes Finding disposition; `FER=c` makes failed
required evidence repairable; a phase/route change can introduce a bypass; and
mandatory defensive review is an assurance floor, not a user option.  An
intent may request more assurance only through a named program-supported
monotone modifier.  Direct-v1 and Robust-v1 expose no optional weakening
modifier.  A future privileged program would derive, visibly in the rendered
profile and PREPARE report, its non-removable defensive review from trusted
policy; it is not part of this slice.

== 3. Minimal Commission Intent contract

Both Front Door Basic interfaces use this exact YAML/JSON data model.  The
human CLI is a guided producer and previewer of the fields; the machine
interface accepts the same file or equivalent flags.  Neither interface
creates a second request vocabulary or a hidden default that changes process
semantics.

[cols="2,1,3",options="header"]
|===
|Field |Origin |Meaning and validation

|`schema_version: 1`, `commission_id`, `work_item_id`
|User
|Stable identifiers.  The compiler derives filenames and a profile ID from
them; it rejects a collision rather than overwriting a Commission.

|`authority_source`
|User
|Literal, meaningful maintainer authorization rationale.  Rendered unchanged
into WorkItem; no template may replace it.

|`program: {id, revision, source_commit}`
|User selects, compiler resolves
|A closed catalogue entry and full 40-character commit.  The compiler verifies
the ID/revision/digest at that commit.  It cannot receive graph text here.

|`task: {title, body, acceptance, withheld_authority, escalation_default}`
|User
|The professional assignment and acceptance semantics.  Compiler renders the
task text; it does not infer acceptance from an evidence command.

|`scope: [repository-relative A1 paths]`
|User
|The one semantic scope decision.  Every projected WorkItem/phase/artifact
path is contained in it, and it must fit the selected policy basis ceiling.

|`personas: {worker: <prose>, independent_reviewer: <prose>}`
|User, constrained by program
|Exactly the roles fixed by the program; Direct supplies only `worker`, Robust
both.  Compiler applies existing role/persona and byte-limit validation.

|`evidence_profile`
|User selects, program constrains
|A program-allowed named acceptance/check profile.  Its acceptance meaning is
shown in the Intent and task; the immutable program/policy basis supplies the
actual existing policy command names and gate placement.  `none` is valid only
where Direct-v1 permits it.

|`policy_basis: {id, revision, source_commit}` and `max_autonomous_hops`
|User selects/narrows
|An approved immutable policy basis and a positive limit no greater than its
and the program's ceiling.  The compiler derives the policy's projected scope
ceiling from the same requested scope; no Intent supplies actions or commands.

|`durable_artifacts: {phase-key: [path, ...]}`
|User, constrained by program
|Required exactly for program-required artifact phases, absent for `none`
phases, contained by scope, and projected unchanged into WorkItem mapping.

|`components_ref: {path, source_commit}`
|User selects, compiler pins
|An existing component manifest selected by the immutable program; it is
reused unchanged.  Compiler verifies the manifest and every selected component
at the stated commit.
|===

`source_commit` fields are source provenance at render time, not a claim that
that commit authorizes a Run.  The observed clean bundle HEAD is a PREPARE and
launch pin, not a value a tracked render manifest can truthfully contain; the
PREPARE-time equivalence procedure is specified in
<<pinning-hand-edits-and-launch>>.

=== 3.1 Direct-v1 example

[source,yaml]
----
schema_version: 1
commission_id: docs-index-normalization-001
work_item_id: WI-DOCS-INDEX-NORMALIZATION-001
authority_source: >-
  Maintainer authorizes the bounded documentation normalization described in
  ISSUE-123; no implementation or metadata authority is granted.
program: {id: direct, revision: v1, source_commit: "<40-char catalogue SHA>"}
task:
  title: Normalize the documentation index
  body: Repair the specified index links and headings.
  acceptance: Links resolve and the requested document conventions hold.
  withheld_authority: No changes outside the listed documentation paths.
  escalation_default: Stop with a typed scope escalation if another path is needed.
scope: [docs/index.adoc, docs/guide]
personas:
  worker: Documentation maintainer; preserve established terminology.
evidence_profile: none
policy_basis: {id: repository-standard, revision: v1, source_commit: "<40-char policy SHA>"}
max_autonomous_hops: 1
durable_artifacts: {}
components_ref: {path: governance/components.yaml, source_commit: "<40-char manifest SHA>"}
----

Direct-v1 renders the program's fixed worker-and-verification shape.  It has no
independent LLM review and no durable review artifact.  When the Intent selects
`task-check-v1`, its required deterministic evidence is on the program's
verification *gate*, never on the worker phase; the literal record is in
<<direct-v1-literal-record>>.  Selecting `none` is allowed only for a task
whose acceptance needs no required deterministic check.  That narrower
selection proves an unreviewed, unchecked Direct task -- it does *not* claim
that a task requiring checks satisfies `DEC-WFC-022` merely because its
acceptance prose mentions them.

=== 3.2 Robust-v1 example

[source,yaml]
----
schema_version: 1
commission_id: parser-boundary-fix-001
work_item_id: WI-PARSER-BOUNDARY-FIX-001
authority_source: >-
  Maintainer authorizes the bounded parser correction in ISSUE-418 and its
  stated acceptance checks. No API redesign, dependency upgrade, or release
  action is authorized.
program: {id: robust, revision: v1, source_commit: "<40-char catalogue SHA>"}
task:
  title: Correct parser boundary handling
  body: Implement the issue's malformed-input boundary behavior.
  acceptance: The named parser cases pass and an independent broad review finds
    no blocking defect in the authorized change.
  withheld_authority: No public-API redesign or dependency update.
  escalation_default: Use semantic_authority escalation for either withheld need.
scope: [src/parser, tests/test_parser.py]
personas:
  worker: Parser maintainer; make the smallest behaviorally complete change.
  independent_reviewer: Independent adversarial parser reviewer.
evidence_profile: task-check-v1
policy_basis: {id: repository-standard, revision: v1, source_commit: "<40-char policy SHA>"}
max_autonomous_hops: 8
durable_artifacts:
  broad_review: [docs/reviews/parser-boundary-fix-001-broad.adoc]
  focused_review: [docs/reviews/parser-boundary-fix-001-focused.adoc]
components_ref: {path: governance/components.yaml, source_commit: "<40-char manifest SHA>"}
----

The compiler derives the profile's phase names, all action lists, gate
descriptors, component IDs, the `task-check` command reference, and
`failed_evidence_route: correction` from `robust@v1` and its policy basis.
The user did not get fields for those controls.  The artifact keys are checked
against the program's required keys; their values are concrete bindings.

=== 3.3 Operator visibility

`commission render --check` must print or write a compact render report before
PREPARE.  It contains the full Intent digest; program and policy ID/revision/
source commits; rendered paths and SHA-256 digests; task path and digest;
literal `authority_source`; requested scope and every effective phase scope;
effective actions, evidence commands, gate breadth/purpose/Finding authority;
required artifacts; selected component paths/digests; and the user-supplied
persona text.  The report labels each fact `user`, `program`, `policy`, or
`runtime at PREPARE`, rather than presenting a derived fact as user authority.

The maintainer reviews this report alongside `git diff` of the Intent and four
rendered files (and sees the unchanged components reference).  PREPARE later
records the actual Runtime commit and role/model/adapter bindings in its normal
execution-binding and preparation-pin material.  Thus an operator can inspect,
before launch and after execution, the task, program revision, authority
rationale, effective permissions, and actual model bindings which entered the
Run, as `DEC-WFC-020` requires.

== 4. Deterministic projection and validation

=== 4.1 Projection algorithm

Given a syntactically valid Intent, the compiler performs only these
deterministic steps:

. Resolve the exact program, policy basis, and component manifest from the
   three stated Git commits; reject absent, ambiguous, changed, or unsupported
   revisions.
. Verify the Intent's allowed roles, evidence-profile identifier, artifact
   keys, hop bound, A1-normalized paths, and requested scope against the
   selected closed program and policy basis.  Reject rather than add a
   fallback.
. Render the existing schemas: a WorkItem (including literal authority source,
   scope, profile path, personas, initial phase, hop limit, labels and artifact
   map); a WorkflowProfile that is the selected program instantiated only at
   its declared binding slots; a RepositoryPolicy with immutable basis values
   and the same-or-narrower scope ceiling; and a task file containing task and
   acceptance prose.  It references the existing component manifest unchanged.
. Emit a non-authoritative render manifest: Intent/program/policy/component
   source identities, target bundle paths, and a digest for every governing
   input and selected component.  It records render facts for inspection; it
   is neither a commit-identity container nor, by itself, a proof that the
   committed tree is the projection.

The compiler has no provider call, no model selection, no capability resolver,
and no authority decision.  Its allowed output is finite because Direct-v1 and
Robust-v1 are finite program templates, with explicitly enumerated slots.  It
may narrow an Intent (for example, reject an excessive hop limit); it may not
widen it.

=== 4.2 Existing admission remains the validator of authority

The compiler must validate the rendered bundle *using the current provider-free
admission path before any agent invocation*.  It does not reimplement that
path.  `commission render --check` is useful preview validation, but the
Commission-Intent PREPARE path itself repeats the byte-for-byte projection
equivalence check at the observed clean HEAD immediately before it delegates to
the pinned Runtime's `operator._preflight()`.  The exact order and comparison
set are specified in <<pinning-hand-edits-and-launch>>.  A failure leaves
PREPARED/LAUNCHED state absent and is corrected/re-rendered before a maintainer
may authorize launch.

The following short Robust trace states why rendering cannot weaken an existing
predicate:

[cols="2,4",options="header"]
|===
|Current check |Projection consequence

|`_preflight` requires WorkItem `profile_ref`; profile roles equal WorkItem
personas and execution-binding roles.
|Robust fixes `worker` and `independent_reviewer`; the Intent must supply
exactly those personas, and PREPARE still rejects missing/extra role bindings.

|`_preflight` checks every phase action is in policy and every phase/artifact
scope is inside WorkItem scope.
|Actions are program/policy constants; compiler projects the one requested
scope to the WorkItem and only program-declared contained phase scopes.  A
broader phase, artifact, or action is a preflight refusal, not a compiler fixup.

|`_admit_a1` checks normalized paths, governance-input containment, policy
ceiling, governance overlap, and hop limits.
|The compiler performs an earlier equivalent shape check but retains the
authoritative `_admit_a1` call.  A generated policy ceiling cannot exceed its
basis or requested scope; malformed or overlapping values still fail.

|`_admit_evidence_disposition` requires a gate plus a failed-evidence route
for every evidence-bearing phase; `_selected_evidence_names` requires policy
command definitions.
|Robust's gate evidence, command name, and correction route are program/basis
constants.  The Intent cannot remove or retarget them; undefined evidence or a
non-gate render fails before dispatch.

|Durable-artifact mapping is checked for every phase before launch.
|The fixed program says which artifact keys are required.  The Intent provides
only contained destinations, so omission or an extra destination fails.
|===

This does not replace any reducer completion guard, Finding rule, or future
P3.5 reachability rule.  It merely ensures a selected program is rendered as
that program.

[[pinning-hand-edits-and-launch]]
=== 4.3 Pinning, hand edits, and launch

The render transaction is: render to ordinary working-tree files -> inspect
report and `git diff` -> commit the Intent, manifest, and governing bundle ->
optionally run `commission render --check` at that commit -> separately
authorize PREPARE.  The following is the mandatory Commission-Intent branch of
PREPARE; it is a check, not a new authority decision:

. The wrapper obtains the normal PREPARE `expected_head` `H`, observes that the
  selected checkout is clean at exactly `H`, and reads the Intent and every
  proposed governing blob from tree `H`.  `H` is an input to the operation and
  is deliberately absent from the tracked manifest.
. From the Intent blob at `H`, it resolves the program, policy, and component
  manifest at their literal pinned source commits.  It rejects a missing,
  ambiguous, or mismatched source object before considering the rendered tree.
. It runs the deterministic projector into a fresh temporary output using only
  that Intent blob and those pinned source objects.  It byte-compares the
  projected WorkItem, profile, policy, task, and render manifest with the blobs
  at their declared paths in tree `H`.  It also byte-compares the unchanged
  component manifest and every component selected by the projected profile at
  `H` with their declared pinned source blobs.  Thus the full five inputs read
  by `_preflight` (WorkItem, profile, policy, components, task), including its
  selected component inputs, are the exact projection/bound reuse at `H`.
. Only after every comparison succeeds does it delegate to the canonical
  `_preflight` with that same `expected_head=H` and the same five paths.
  `_preflight` independently requires clean `HEAD == H`, reads those inputs by
  the tree object, and retains all current A1, role, artifact, action, evidence
  and Finding-admission predicates.

PREPARE records and materializes the normal launch artifact with the same
Development head `H`; LAUNCH revalidates its prepared identities and executes
that already materialized artifact, whose canonical invocation also carries
`--expected-head H`.  Consequently a later HEAD/input/artifact drift refuses
launch rather than turning a successful projection check for `H` into authority
for another tree.  Level 0 continues to recheck governing digests between Hops.

A hand edit after rendering -- including a hand edit that updates matching
manifest digests -- fails step 3 unless the edited tree is itself the exact
rerender from the pinned Intent and sources.  It must then be committed,
reviewed, and pass this PREPARE check at its own observed `H`.  If a maintainer
deliberately uses ordinary WFC PREPARE without this wrapper, the edited bundle
remains a hand-authored Commission subject to current admission and separate
authorization; it must not be represented as a validated projection of the
Intent.  This preserves the existing non-exclusive hand-authored path and does
not create a hidden authority gate.

== 5. Closed reusable-program compatibility

The following two records are the entire v1 program grammar.  They are literal
rendering constants, not sketches for a catalogue entry.  In the tables,
`S` is the Intent's normalized `scope`; `A(broad_review)` and
`A(focused_review)` are the corresponding required durable-artifact paths,
each required to be inside `S`; and `E` is the one policy-basis command named
`task-check`.

`direct@v1` permits exactly two evidence-profile values: `none`, which maps to
`E = []`, and `task-check-v1`, which maps to `E = [task-check]`.  The selected
immutable policy basis must define `task-check` with its exact argv and timeout;
the Intent cannot supply either.  `robust@v1` permits exactly
`task-check-v1`, hence `E = [task-check]`.  These are finite enumerations, not
a policy-command selector.  A desired evidence shape outside them requires a
new immutable program revision, not an Intent option.

Every phase has `human_gates: []`, `components.modifiers: []`, and
`components.repository_policy: []`.  The component IDs, action lists, scopes,
artifact rules, review descriptors, evidence placement, and route keys below
are exact.  The compiler has no fill-in slot for any of them.

[[direct-v1-literal-record]]
=== 5.1 Direct-v1 literal record

`direct@v1` is the bounded worker program with no independent LLM review.  Its
verification gate is a Coordinator-required deterministic-evidence gate, not
an independent semantic review; it uses the `worker` role and `[worker]`
component, never `independent_reviewer` or `[reviewer]`.  It therefore meets
the Direct target's checked form without placing required evidence on a
non-gate phase, which `_admit_evidence_disposition` rejects.

[cols="1,1,2,3,4",options="header"]
|===
|Phase |Role and components |Artifact and scope binding |Actions and evidence |Review descriptor and literal routes

|`implement`
|`worker`; `role: [worker]`
|`none`; `authorized_scope: S`
|`[edit, commit]`; `[]`
|`review: null`; `verify: {effect: goto, target: verification}`.

|`verification`
|`worker`; `role: [worker]`
|`none`; `authorized_scope: S` (read/check only because no `edit` action)
|`[review]`; `E` -- therefore `[]` for `none` and `[task-check]` for
`task-check-v1`
|`purpose: deterministic task-check disposition only; no semantic review`,
`breadth: verification`, `authority: gate`, `context: fresh`,
`blocking_policy: blocking_only`, `trigger: profile_selected`,
`exit: declared_route`, `finding_authority: []`,
`failed_evidence_route: correction`; `accept: {effect: complete}` and
`correction: {effect: goto, target: implement}`.
|===

Thus a required Direct check has exactly one legal placement and one repair
route.  With `none`, the same closed topology has no required evidence to fail;
it makes only the narrower no-required-check claim stated in section 3.1, not a
claim that unrun checks passed.

=== 5.2 Robust-v1 literal record and renewal constraint

`robust@v1` has only the following closed record:

[cols="1,1,2,3,4",options="header"]
|===
|Phase |Role and components |Artifact and scope binding |Actions and evidence |Review descriptor and literal routes

|`implement`
|`worker`; `role: [worker]`
|`none`; `authorized_scope: S`
|`[edit, commit]`; `[]`
|`review: null`; `broad_review: {effect: goto, target: broad_review}`.

|`broad_review`
|`independent_reviewer`; `role: [reviewer]`
|`durable_artifact: required`; binding `A(broad_review)`;
`authorized_scope: [A(broad_review)]`
|`[review, edit, commit]`; `E = [task-check]`
|`purpose: independent adversarial full-scope review of the rendered
Commission`, `breadth: broad`, `authority: gate`, `context: fresh`,
`blocking_policy: blocking_only`, `trigger: profile_selected`,
`exit: declared_route`, `finding_authority: [resolve]`,
`failed_evidence_route: correction`; `accept: {effect: complete}` and
`correction: {effect: goto, target: correct}`.

|`correct`
|`worker`; `role: [worker]`
|`none`; `authorized_scope: S`
|`[edit, commit]`; `[]`
|`review: null`; `focused_review: {effect: goto, target: focused_review}`.

|`focused_review`
|`independent_reviewer`; `role: [reviewer]`
|`durable_artifact: required`; binding `A(focused_review)`;
`authorized_scope: [A(focused_review)]`
|`[review, edit, commit]`; `E = [task-check]`
|`purpose: independent focused verification of correction and disposition of
the prior broad/focused Findings`, `breadth: focused`, `authority: gate`,
`context: fresh`, `blocking_policy: blocking_only`,
`trigger: profile_selected`, `exit: declared_route`,
`finding_authority: [resolve]`, `failed_evidence_route: correction`;
`correction: {effect: goto, target: correct}` and
`renew_broad_review: {effect: goto, target: broad_review}`.
|===

The exact `[resolve]` on *both* Robust gates is intentional.  A broad gate may
resolve the Findings it opens; the focused gate may resolve the Findings it
verifies before taking `renew_broad_review`.  Neither gate may residualize,
supersede, or reopen, and no Intent can alter that authority.  Failed required
evidence at either gate always takes its literal `correction` route; it cannot
complete or renew the broad review.

The missing grammar element is named the *renewed-broad-review route
constraint*.  It is a derived, non-removable program constraint: after any
transition to `correct`, a focused review may not complete; its sole successful
closed-Finding transition is `renew_broad_review: goto broad_review`, and only
the broad gate's `accept` route may reach COMPLETE.  Re-entering
`broad_review` is a fresh broad review because its descriptor has
`context: fresh`; it is not a relabelled focused check.  The route maps above
are emitted from the program, never supplied by an Intent.

This is the one additional grammar primitive needed beyond the accepted
base-pattern-plus-modifiers hypothesis: a fixed gate-to-gate renewal edge with
an all-completion-path constraint.  It is not an arbitrary edge selector, loop
language, or generalized workflow DSL.  Direct needs no new primitive.

The first implementation must prove that exact template invariant with
positive/negative tests and must reject a manifest/profile mismatch.  It need
not and must not implement P3.5's general static reachability validator.  If
implementation discovers that the existing parser/reducer cannot preserve this
closed route constraint without a general all-graph reachability analysis, that
is a flagged prerequisite for maintainer direction, not authority to design or
implement P3.5 here.

Both programs retain the decisions excluded from the grammar: a stopped Run
uses existing same-Run reconciliation; salvage preserves work but not authority
(`DEC-WFC-013`); and professional continuation is a new, separately authorized
successor Commission/Run, never resume, retry, or replay (`DEC-WFC-014`).  A
successor may cite predecessor evidence in a new Intent, but cannot inherit a
prepared state, a program pin, or authority merely by doing so.

== 6. Smallest proof path for a later Commission

This section is a commissioning map, not implementation authorization.  The
smallest vertical slice is one newly authorized `direct@v1` Commission, no
historical migration, followed only by a separately commissioned Robust slice
if Direct demonstrates the contract's measured value.

A direct future implementation Commission would need to touch only:

* a new non-authoritative parser/renderer module such as
  `src/workflow_coordinator/commissioning.py`, including
  `commission_intent_from_yaml`, `render_commission`, and
  `verify_render_manifest`; it must not be imported by the reducer or alter
  `operator._preflight` admission semantics;
* a thin explicit CLI seam, for example `scripts/wfc_op.py` subcommands
  `commission render` and `commission check`, which invokes the pinned
  existing `_preflight` during PREPARE rather than duplicating it;
* new Direct-v1 catalogue and policy-basis fixtures plus one new authorized
  Commission bundle/Intent/render manifest; and
* focused tests for that module and CLI.  No existing historical profile,
  WorkItem, policy, model, reducer, renderer, adapter, or archive design need
  change.

The minimum test set is:

* deterministic render: the same Direct Intent/source commits produces byte
  identical governing input and manifest digests;
* round trip/admission: Direct Intent -> committed rendered WorkItem/profile/
  policy/task plus unchanged components -> existing `_preflight` acceptance;
* negative counterexamples: Intent attempts to widen scope or actions, omit a
  required artifact, add a role, alter Finding authority, delete a
  failed-evidence route, or select undefined evidence; each fails before a
  provider call;
* PREPARE provenance: program/policy/component source-object mismatch, a hand
  edit after render, and a hand edit plus a matching manifest edit each fail
  the mandatory temporary rerender and byte comparison at the observed clean
  HEAD before `_preflight`; and
* literal-program rendering: Direct's `task-check-v1` places `task-check` only
  on `verification`, Direct's `none` renders no evidence, and every Direct or
  Robust phase/route/review/action/artifact value equals the section 5 record;
  an Intent cannot add a route, action, component, artifact rule, Finding
  operation, evidence placement, or failure route; and
* Robust template tests, written only in its later Commission: a clean first
  broad review may complete, but every route trace containing `correct` must
  pass `focused_review -> broad_review` before COMPLETE; no Intent field can
  add a bypass or remove the renewed broad gate.

The last Robust test is a finite assertion over the one rendered template, not
a general profile reachability validator.  It gives the future maintainer a
direct demonstration of the one promised safety property without silently
starting P3.5.

== 7. Explicit boundaries and rejected alternatives

This design does *not* authorize production code, tests, a parser, renderer,
or compiler; a Direct/Robust profile; any current-profile migration or
historical-compatibility promise; a WFC Run; P3.5 implementation; Level 1;
Front Door Advanced; a provider registry or quota scheduler; archive-storage
or Claude-adapter redesign; Runtime/Evidence/Project Memory/backlog change; or
a push/promotion.  The existing Runtime/Profile/WorkItem/Policy division and
operator mechanics remain unchanged.

Rejected alternatives:

* *A fully general workflow DSL.*  It would let the authoring request supply
  the phase/route controls which the archaeology identifies as guarantees,
  demand a broad verifier, and prebuild unobserved families.  Two closed
  immutable programs plus one named renewal constraint answer the present need.
* *Continue one profile per Commission with no compiler.*  It preserves the
  authority boundary but leaves duplicated cross-file scope and process
  material, the demonstrated source of transcription/preflight friction, and
  fails `DEC-WFC-020`'s shared semantic contract requirement.
* *Make the compiler or Intent an L0 authority mechanism.*  This would erase
  the maintained review/PREPARE authorization seam.  The rendered inputs remain
  visible, Git-pinned, and admitted exactly as today.
* *Compile model/provider choices or a registry.*  Execution bindings are
  Runtime-owned; a semantic persona does not select a provider.  This would be
  Front Door Advanced/provider-platform work, not Basic.

== 8. Remaining open questions and measurable reduction

This record reduces the open question from “what contract?” to a limited,
separately commissionable implementation choice.  It does not claim these
questions settled:

. Whether the new program catalogue and policy-basis documents should be
consumer-local paths exactly as illustrated, and their final file naming/layout.
The invariant is immutable ID/revision plus Git pin, not this illustrative path.
. The final human CLI wording and JSON schema encoding; they must preserve the
field model and no second semantic interface may emerge.
. Which eligible immutable policy basis first supplies the literal
   `task-check` command for a real consumer.  Its argv/timeout remain policy
   mechanics, while `task-check-v1` and its required placement are already
   fixed by the two v1 program records; a first Commission cannot turn task
   acceptance into opaque command selection.
. Whether future assurance modifiers are safe, and the trusted derivation of
defensive review or model eligibility.  Neither is needed by Direct/Robust-v1.
. Whether Robust can be rendered and verified as stated with a finite template
check.  If not, the exact minimal dependency on P3.5-style analysis requires
maintainer escalation; no validator is designed here.
. Program-catalogue ownership across multiple consumer repositories, mechanical
authorship provenance, Front Door Basic/Advanced versus Stage naming, archive
layout, token archival data, and historical-test reclassification.

The proposal should be judged by the Commissioning concept's measurable test,
not by its vocabulary: on the first Direct exercise it should reduce authored
duplicated scope/process declarations and provider-free preparation refusals,
while preserving explicit inspection of task, authority, program revision and
bindings.  If it does not, later renderer expansion should stop rather than be
justified as a platform build.
