== What the plan gets right

Decomposition and authoring readiness are genuinely good. Splitting BP2 into
`bp2-admission-extraction-001` and `bp2-config-compiler-001` follows the
second-pass review's own advice to commission the `_preflight` extraction
separately, and each entry carries enough module detail, excluded scope and
test content for a later orchestrator to author a Commission without
redesigning it. All nine packages are covered; no package is invented and no
new feasibility phase is introduced.

The 2026-11-18 decisions are read accurately, including the harder ones:
`simple@v1`/`robust@v1` only, guidance as a binding into the frozen
`repository_policy` slot, bindings outside the committed Commission (C1), the
non-executing `plan` with a post-authorization probe (C3), supersession of the
readiness review's C4 host/subreaper/classifier and its "mandatory BP4a
dependency", C6/RP1 as fast-follow, and -- correctly -- exactly one remaining
positive live Claude qualification with the negative criterion superseded and
provider-independent preventive isolation explicitly post Beta 1. The plan
does not invent a repeated Claude qualification, and it keeps the live Run
maintainer-owned.

Provenance of existing accepted work is handled honestly: the already-accepted
diagnostics BUGs are cited as reusable context for BP6 and explicitly not
recommissioned; the usability BUGs folded into BP4's acceptance are named
rather than silently absorbed; `FTR-WFC-ATOMIC-HOP-RECOVERY` is named as
out-of-scope rather than quietly in-scope. The preservation recommendation
under BP4 is labelled as the plan's own bounded judgment, and its seven
predicates match the readiness review's C5 list with only the quiescence
predicate substituted and relabelled `unattested` -- a legitimate bounded
recommendation, not a smuggled decision.

Batching (3/3/3/1), the critical path, the parallel work, the integration
points, and the three-milestone definition of done (implementation acceptance
≠ independent acceptance ≠ maintainer product closure) are all concrete, and
no batch claims new authority or auto-promotion. The first batch (BP1, BP8,
BP2a) is correctly identified as having no technical predecessor, and its
decision gates are correctly empty -- with the BP8 exception below.

[[blocking]]
== Blocking findings

Four material gaps. Each is a correctable defect in the plan document; none
requires new maintainer authority to fix, and B1/B2 are confined to a handful
of lines.

[[b1]]
=== B1 -- BP8 names the wrong five invariants, from the wrong test file

The plan's BP8 deliverable is "the five universal product invariants (literal
program rendering, frozen-resource tamper refusal, renewal trace, A1 path
refusal, and the compiled-bundle preflight pass -- per the second-pass
review's `test_commissioning.py` reading)".

That list is not the five universal invariants. The second-pass review's
test-debt table classifies `tests/architecture/test_self_development_governance.py`
(45 tests) and names the five by test function:
`test_work_item_mapping_cannot_enlarge_review_phase_authority`,
`test_production_preflight_rejects_consumed_isolated_state_root`,
`test_production_preflight_identifies_different_python_interpreter_identity`,
and the two `..._route_is_legal_with_empty_finding_set` cases
(`test_bootstrap_changes_required_correct_route_is_legal_with_empty_finding_set`,
`test_bootstrap_rereview_changes_required_correct_route_is_also_legal_with_empty_finding_set`).
All five exist in that file (lines 6077, 6062, 713, 6421, 6463). The four
items the plan lists instead come from the review's *separate* paragraph about
`tests/unit/test_commissioning.py` (31 tests), whose stated disposition is
entirely different: "BP2 writes their v2 equivalents against a neutral
fixture; the v1 tests stay until the v1 path is removed." The plan's fifth
item ("the compiled-bundle preflight pass") is from BP2's test list, not from
either invariant set.

Why this is material rather than cosmetic: BP8 is in the first batch, is
described as "mechanical relocation", and is the only package guarding what
must survive deletion of the historical tree at cutover. As written, its
implementer would relocate commissioning-path assertions that BP2 is supposed
to re-express, while the five actual invariants -- including the
authority-enlargement refusal and the two empty-finding-set route-legality
cases -- would remain in the file the epic expects to be reduced to a
parse-smoke test. That is exactly the loss the epic guards against ("Separate
genuine invariants from frozen scope/route assertions"; "No test is removed
merely to make the productization changes pass"). The rest of BP8 (marker,
default deselection, parse-smoke test, acceptance with
`governance/self-development/` and `governance/work-items/` absent) is correct
and consistent with the 45/5/40 split.

Also inconsistent with the corrected list: BP8's excluded scope says "no
behavior change to `commissioning.py` itself", which only makes sense under
the mistaken reading, and its "other forty historical tests" phrasing belongs
to the governance file it does not otherwise name.

[[b2]]
=== B2 -- BP5's prerequisites contradict `_open.adoc` and BP5's own acceptance

The plan's BP5 states "Prerequisites/predecessors:: `wfc-beta1-bp1-packaging-identity-001`
accepted. Runs in parallel with BP2a/BP2b and BP3", and Batch 2's internal
order has "BP2b and BP5 start together (BP5 needs only BP1); BP3 starts only
once BP2b's candidate is independently accepted".

`_open.adoc`, the sole readiness authority, states the opposite in one
sentence: "BP5 archive port can start from BP1; its commit wiring needs BP3's
primitive." The epic agrees: "Dependencies/status:: BP1 for port/tests; BP3
bounded commit primitive for write integration." The second-pass review's own
port sequence makes it concrete in step 3: "Port the wrapper's probes and
commit to Python on `bounded_path_commit`."

The plan is also internally inconsistent about it. BP5's acceptance requires
commit-level behavior -- "a retry after a kill between copy and commit
produces exactly one commit with identical content; a second archive of the
same attempt is a no-op" -- while the sequencing section says "BP3's commit
primitive is the only write path BP4's lifecycle and BP6's archive/report both
reuse", omitting BP5 from the list of its consumers. A BP5 Commission author
therefore cannot tell whether to depend on `git_facts.bounded_path_commit`
(contradicting the stated prerequisites and the stated parallelism) or to
build a second archive-commit path (contradicting "the only write path", and
re-opening precisely the "semantic change smuggled into the port" risk BP5
names).

The fix is small and does not change the batching: state the split dependency
(port and the 61 conformance tests from BP1; commit wiring on BP3's primitive),
and either order BP5 after BP3 inside Batch 2 or split BP5's acceptance so the
copy/manifest equivalence can be accepted before the commit-retry criterion.
Note that Batch 2's current internal order makes the conflict live rather than
theoretical: BP3 is sequenced *after* BP2b's acceptance, i.e. potentially
after BP5 has already been authorized and accepted.

[[b3]]
=== B3 -- Two dispositions the epic explicitly requires have disappeared

The epic's BP9 entry states: "BP7 timing, Q8 usage and public-internet
investigation must receive explicit dispositions, not disappear because R2
omitted them." The plan disposes of two of the three -- BP7 timing as DG-4 and
Q8 token usage as DG-1 -- and the public-internet item appears nowhere in the
document: not in BP9, not in the release gates, not in the explicit post-Beta
list, not in the "not open, and not reopened" list. A full-text search for
"internet" in the plan returns nothing.

This is not a theoretical omission. `_open.adoc` carries the public-internet
FTR as an unresolved gate row with an "independently accepted P1 Codex
configuration in Development", a promoted P2-002 Claude configuration, a
promoted `Bash(curl:*)` grant and two bounded agent-observed HTTPS
qualifications, and states "Beta-1-relevant even though the blueprint omitted
it". The FTR's own next action names Claude positive writes and scratch/TMPDIR
qualification. A reader of the execution plan, which claims to state the
"actual release gates" and the "explicit post-Beta items", would conclude the
subject does not exist. A one-line disposition in BP9 plus one line in the
post-Beta list is sufficient; commissioning the work is not required.

The same pattern affects BP7. The epic lists BP7's dependencies as "BP6,
maintainer Runtime promotion, Q5 preparation-contract and Q6 timing decisions"
and records that "R2 Q5 preparation-contract amendment and Q6 cutover/tag
timing remain open for BP7"; the readiness review's handoff confirms "R2's Q2,
Q3 and Q5 to Q8 are unchanged and still open". The plan's DG-4 covers Q6 only.
Q5 is the amendment of `ch03_running/01_preparation.adoc` steps 4 and 5 -- a
change to a normative document that the second-pass review explicitly says
"needs the Maintainer's assent". The plan's BP7 does list manual chapter edits
among its modules, so the work is in scope, but the maintainer decision it
requires is absent from both BP7's prerequisites and the decision-gate table
that purports to list "Decisions needing a maintainer".

[[b4]]
=== B4 -- Candidate preservation is turned into a release gate against `_open.adoc`

The plan's "What the 2026-11-18 decisions already settle" section asserts:
"*Preservation is a requirement, recovery is not:* automatic,
non-authoritative candidate preservation on a regular stop is required."
BP4's acceptance then requires "an engine-killed-mid-Hop case that ends
`interrupted` with a preserved candidate ref", and the release section lists
"BP1–BP6, BP8, BP9 as specified above" as the real gates that block `0.1.0b1`.
Preservation is therefore a tag-blocking gate in this plan.

`_open.adoc` classifies it differently: "Automatic candidate preservation on
regular stops is a Beta-1 *candidate*, with design/acceptance still open."
The epic's "Requirements and preferences" section does say "Preserve agent
work ... as automatically as practical" and "Automatic preservation of
unadopted work is a requirement, with its mechanics and limits open", so the
two authoritative records are not aligned on gate status -- and the plan names
`_open.adoc` itself as "the sole authority for priority, readiness and
ordering" in its own second paragraph.

The plan resolves that conflict silently and in the stricter direction. DG-3
does not repair it: it asks only *which quiescence signal* `preserve_candidate`
may rely on and how the limitation is worded, and both of its alternatives
build the mechanism. The maintainer is never offered the disposition
`_open.adoc` leaves open -- ship `0.1.0b1` without automatic preservation, or
accept BP4 without the preservation criterion -- even though that is the
decision with the largest effect on the tag.

The fix is a stated reconciliation: name the divergent classifications, say
which one the plan follows and why, and add gate status (gate versus
candidate/fast-follow) as an alternative under DG-3 or as its own decision
gate with a latest decision point before BP4 starts.

== Checks that passed and are explicitly not findings

* *Batch continuation conditions and stops.* "Independent broad-review
  acceptance with no open blocking Finding plus passing Coordinator
  `task-check`" is an objective, observable condition; the stops are real
  (Evidence-repository reachability for BP5, the maintainer-owned live Claude
  Run in BP9, the Runtime-promotion decision before Batch 4). No batch grants
  authority, promotes a Runtime or implies a push.
* *Decision deadlines are actionable.* DG-1/DG-2 before BP6 (Batch 3), DG-3
  before BP4 (start of Batch 3), DG-4 before BP7 (Batch 4), with DG-1/DG-2
  deliberately surfaced during Batch 1. Each gives alternatives and a
  recommendation. Subject to B3 and B4, the set is incomplete rather than
  wrong.
* *Authority separation.* The plan repeatedly separates implementation
  acceptance, independent acceptance and maintainer product closure; it keeps
  Runtime promotion and live Runs maintainer-owned; it does not treat its own
  batches as review or acceptance events. No artificial governance chain, no
  required successor chain, and no circular prerequisite was found anywhere in
  the ten entries.
* *First three executable Commissions.* BP1 and BP2a are authorable as
  written: BP1's modules, risks and acceptance match the second-pass review's
  BP1 and the offline-build caveat is correctly kept out of `task-check`;
  BP2a is correctly scoped to `operator.py` with the existing
  `test_operator.py` suite as the behavior-equivalence guard, and the
  stronger-model review note is carried over. BP8 is blocked only by B1.
* *No withheld-authority violation.* No product code, test, script, runtime,
  program, policy or adapter change; no Commission, successor, promotion,
  branch merge or push; no edit to historic reviews, the Evidence repository
  or the Operator Manual; no live provider Run; no agent Git write.

Non-blocking observations, recorded without a Finding: the second-pass review
assigns creation of the neutral fixture repository to BP2 ("BP2 creates it;
every later package uses it"), and the plan's BP2b modules do not mention it
although BP4, BP8 and BP9 all test "in a neutral fixture"; the readiness

clause; `_open.adoc` and the short-TMPDIR BUG both record a separate
promoted-Runtime Claude scratch/TMPDIR qualification as outstanding, which the
plan neither gates nor explicitly defers -- an explicit "not a Beta-1 gate"
line would close it without inventing a second Claude qualification; and
BP2a's "prerequisite: BP1 accepted" sits slightly awkwardly beside Batch 1's
"BP1 first is a convenience, not a hard dependency".

== Limits of this review

Nothing was executed beyond `asciidoctor`, read-only Git inspection, `grep`
and direct file reads. `python -m pytest` is unavailable in this review
sandbox (`No module named pytest`), so collected test counts could not be
confirmed; raw `def test_` counts are reported above instead, and the plan's

state both. The `workflow-coordinator-run-evidence` repository and the
`workflow-coordinator-runtime` checkout are outside this sandbox's readable
paths, so the archiver's own implementation and its 61 conformance tests were
verified only through the Development-side wrapper and the review's citation
of them -- the same boundary the plan states, and the reason B2 rests on
documentary rather than executed evidence. Coordinator `task-check` is a
separate, Coordinator-owned step and is not claimed here. This review disposes
no authoritative Finding; the four items above are proposed for allocation.
