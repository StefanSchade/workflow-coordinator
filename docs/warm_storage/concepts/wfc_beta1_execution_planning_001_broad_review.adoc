[[n1]]
=== N1 -- BP9 states a precondition for the Claude qualification that the controlling BUG does not impose and that the plan schedules after BP9

The plan's own basis section states the remaining Claude qualification
correctly: "exactly one targeted qualification remains open (a positive
new-directory write and WFC candidate acceptance *under the current Runtime*)"
(`beta1_execution_plan.adoc:93-96`). That matches the controlling record
exactly --
`BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc:7` ("Separately qualify
authorized new-directory creation and writing through WFC candidate acceptance
under the current Runtime") and `:16` ("under the current Runtime") -- and
`_open.adoc:183-184` ("under the promoted Runtime", i.e. the Runtime that
already carries the accepted deterministic correction).

BP9's controlling-BUG paragraph states something different:

____
"under the Runtime this plan's Commissions produce and the maintainer
promotes, a live Claude worker creates a previously nonexistent WFC-authorized
directory, writes a file in it, and WFC performs candidate acceptance and
reduction from evidence" (`:456-463`).
____

Three consequences make this material rather than editorial:

. *It contradicts the controlling BUG and the plan's own line 96.* The plan is
  informative and explicitly does not re-decide the 2026-11-18 decisions, yet
  this sentence tightens a release-gate condition the BUG and `_open.adoc`
  both tie to the *current* Runtime. The epic points the same way for BP9's
  live work: "Installed-wheel live qualification per supported adapter"
  (`beta1_productization.adoc:326`), and BP9's own acceptance says the live
  Runs happen "from an installed wheel" (`:467-471`) -- neither requires a
  Runtime promotion.
. *It inserts a Batch-4 prerequisite into a Batch-3 Commission.* "the
  maintainer promotes" names the Runtime-promotion act, which this plan
  schedules only as a Batch 4 / BP7 starting prerequisite ("a maintainer
  Runtime promotion of the BP1-BP6 implementation", `:656-658`, `:498-500`).
  BP9 sits in Batch 3, and neither BP9's prerequisites ("BP6 accepted",
  `:455`) nor Batch 3's starting prerequisites (`:634-636`) mention a
  promotion. Taken literally, BP9 cannot close where the plan puts it, and the
  critical path `... BP6 --> BP9 --> 0.1.0b1` (`:530-537`) breaks.
. *It silently moves a release gate and a maintainer stop.* The plan lists
  "the one Claude positive qualification" among the gates that block `0.1.0b1`
  (`:554-556`). If a Runtime promotion really is its precondition, that
  promotion is a maintainer decision with a latest decision point before
  Batch 3 ends -- and it appears in neither Batch 3's stop (which names only
  the live Run's maintainer ownership and provider dependence, `:648-651`) nor
  the DG-1..DG-6 table that purports to list "Decisions needing a maintainer".

A BP9 Commission author cannot determine from this plan whether the live
Claude Run uses the Runtime available today or one that does not exist until
after the batch containing BP9. Either reading is actionable once stated; the
plan must pick one. Aligning BP9's wording with its own line 96, the BUG and
the epic's installed-wheel direction is the smaller fix and changes no
batching. If the stricter reading is actually intended, then the promotion
belongs in BP9's prerequisites, in Batch 3's starting prerequisites, in the
sequencing section and in the decision-gate table with a latest decision
point.

[[n2]]
=== N2 -- BP7's manual chapter list omits the two chapters that actually document the tool BP7 retires

BP7's modules/paths field reads: "updated preparation/running/archive/
self-development/command sections of the Operator Manual's relevant chapters
(ch03, ch05, ch06)" (`:492-494`).

The prose list of *sections* is right and matches the epic's acceptance
direction verbatim ("Updated preparation/running/archive/self-development/
command guidance agrees with implemented behavior",
`beta1_productization.adoc:280-281`). The parenthetical list of *chapters*
does not match it. In the delivered manual, "archive" is
`ch04_evidence/02_archive.adoc` and "command" is the command index in
`ch08_examples`; `ch06` is `ch06_recovery`, which corresponds to no item in
the prose list. The second-pass review names the Harness-bound sections
precisely, and names four chapters, not three: "`ch03_running` (both
sections), `ch04_evidence/02_archive.adoc`, `ch05_self_development` and the
command index in `ch08_examples`"
(`wfc_beta1_product_boundary_review_second_pass.adoc:1082`).

The omitted chapters are exactly where the retired tool's commands live, which
I verified in source:

* `docs/operator_manual/ch04_evidence/02_archive.adoc:16-17` --
  `python3 scripts/wfc_op.py archive "$ATTEMPT" --dry-run` and the real
  invocation.
* `docs/operator_manual/ch08_examples/02_command_flow.adoc:22-44` -- the
  command index rows for `prepare`, `status`, `launch` and both `archive`
  forms, each a literal `python3 scripts/wfc_op.py ...` command.
* `docs/operator_manual/ch08_examples/03_commission_to_archive.adoc` -- eight
  further occurrences; the second-pass review calls this file's eleven
  transitions the specification the controller automates (`:1079`).

Why this is material and not a typo to be left: the modules/paths field is
what a later orchestrator turns into the Commission's `authorized_scope`, and
BP7's excluded scope then fences the Commission in ("No change to the manual
beyond the sections this cutover actually affects", `:495-497`). A BP7
Commission scoped to ch03/ch05/ch06 cannot update the archive chapter or the
command index, yet its own acceptance requires that "Updated manual guidance
agrees with implemented behavior" (`:513-514`) after
`scripts/wfc_op.py` is removed or stubbed. That is an unsatisfiable acceptance
condition inside the Commission's own granted scope -- the authoring
anti-pattern this project has already documented and paid for -- and the
failure mode is a tagged release whose manual still instructs the operator to
run a script that no longer exists.

The fix is one line: name ch03 (both sections), `ch04_evidence/02_archive.adoc`,
ch05, the `ch08_examples` command index, and ch06 for the recovery/preservation
reconciliation the epic separately asks BP7 to perform ("Reconcile recovery's
current manual-only boundary with the preservation design",
`beta1_productization.adoc:277-278`) -- which is the right reason to include
ch06, and is not the reason the current parenthetical implies.
