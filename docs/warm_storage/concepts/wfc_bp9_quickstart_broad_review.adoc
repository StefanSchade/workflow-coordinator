[[h002-execution]]
=== Following the quickstart literally (reproduced)

Setup exactly as the chapter prescribes: a fresh Git repository with one
committed file under `src/`, then

* `wfc init --repository . --scope-ceiling src --evidence-repository
  ../wfc-evidence` -- *works*. It printed `wrote Consumer Config:
  .wfc/config.yaml`, `NEXT EXPLICIT ACTION: ... commit it yourself -- `wfc
  init` never commits it`, `Evidence repository (created new): .../wfc-evidence
  (raw retention: local)` and `NOTHING WAS PUSHED: the Evidence repository has
  no remote configured.` This confirms three of the chapter's claims at once
  (never commits it, creates or adopts a remote-less Evidence repository,
  `local` raw retention by default).
* the `default_execution` edit from the chapter's YAML snippet, then
  `git add .wfc/config.yaml && git commit` -- *works*; `adapter`, `model` and
  `reasoning` are exactly the three required keys
  (`frontdoor/config.py:122-129`) and `codex_cli`/`claude_cli` are exactly the
  accepted adapters (`:24`, `:124-125`).
* the task document from the chapter, saved as `task.md` (the chapter shows
  the body in a `[source,text]` block and never names the file; `task.md` is
  what its own `wfc plan` line implies).
* `wfc plan task.md --repository . --scope src --commission-id ...
  --guidance-path GUIDANCE.md ...` -- *fails*, exit 2:
+
[source,text]
----
wfc plan: consumer guidance is absent or ambiguous at pinned source commit
ad0203b2a1d42e80921f7f9f924d1a34f5bdf49f: GUIDANCE.md
----
+
`--guidance-path` is a *required* flag of `wfc plan` (`frontdoor/plan.py:255`)
and `commissioning.py:313` reads it out of Git at `request.guidance.
source_commit`, which defaults to current HEAD (`plan.py:294`). So the file
must already exist *and be committed*. The chapter mentions `GUIDANCE.md`
only as a bare token inside the example's flag list: it never says what the
file is, that the consumer must author it, or that it must be committed
before `wfc plan` will run. After `printf policy > GUIDANCE.md && git add -A
&& git commit`, the identical command succeeds (exit 0) and prints the
preview. This is Finding 1.
* `wfc run --repository . --request request.yaml --execution-override ...
  --yes` with a hand-authored, schema-valid `request.yaml` in the repository
  root -- *fails*, exit 22:
+
[source,text]
----
wfc run: repository worktree is not clean at the authorized baseline
----
+
`git status --porcelain=v1 --untracked-files=all` showed `?? request.yaml` and
`?? task.md`. `GitFacts.clean` is `not tracked_changes and not
untracked_changes` (`git_facts.py:44-46`), so non-ignored *untracked* files
alone are enough, and `lifecycle.py:348` and `:389` refuse on them. The
chapter has the reader write the task document and hand-author the Consumer
Request, both implicitly inside the repository ("From your repository root"),
and never says to commit them or to keep them outside the worktree. By
contrast the accepted BP9 end-to-end test writes its request into `tmp_path`,
outside the repository, and commits the Consumer Config
(`tests/integration/test_beta_e2e_fake_provider.py:154-176`), and the existing
manual walkthrough commits the request explicitly
(`ch08_examples/03_commission_to_archive.adoc:83-97`). This is Finding 2.

So two of the chapter's six command steps refuse when the chapter is followed
exactly as written, both for reasons the chapter itself is the only plausible
place to state. Both fixes are small and stay inside the authorized file: name
and commit the guidance file as its own step, and either commit the task
document and request or place them outside the worktree.

A note on what this probe does *not* claim: no live provider ran. `wfc run`
first refused on the unresolvable `codex` executable (exit 22,
`lifecycle.py:321-326`), and I reached the clean-tree check by pointing
`--executable` at the repository's own scripted fake provider. I did not

[[h002-drift-test]]
=== The drift test is mutation-sensitive (reproduced)

`pytest` is not importable by any interpreter this sandbox can reach, the
same agent-local limitation the H005 pass on the BP9 E2E test recorded. This
is an agent-side environmental limit, not a product defect, and the
required-mode suite is Coordinator-owned evidence in any case. I therefore
ran the committed module verbatim through a 13-line stand-in supplying only
`pytest.raises`, against a *copy* of `src/` placed first on `sys.path`:

* unmutated copy: all four tests pass.
* rename `--yes` to `--confirm` in the copy's `frontdoor/lifecycle.py:962`:
  `test_every_documented_subcommand_and_flag_exists_on_the_real_cli` fails
  with "`wfc run --yes` is documented in the quickstart but is not a real flag
  of the installed CLI".
* add a new `required=True` flag to the copy's `wfc init` parser:
  `test_documented_commands_supply_every_required_flag` fails with "`wfc init`
  example is missing required flag(s): ['--brand-new-required']".

So both mutation classes the task names (a documented flag removed or renamed;
a new required flag undocumented) really are killed. The test derives its
expectations from the parsers the Front Door actually builds rather than from
a hand-maintained list, which is the right shape for a drift guard. Probe
scripts and copies were deleted afterwards.

=== Blocking Findings (H002)

[[h002-f1]]
*Finding 1 -- the documented `wfc plan` invocation cannot succeed as written.*
`docs/operator_manual/ch09_consumer_quickstart/01_quickstart.adoc:103-116`
passes `--guidance-path GUIDANCE.md`, a required flag whose target must
already be committed in the consumer repository at the pinned source commit
(`frontdoor/plan.py:255`, `:294`; `commissioning.py:313`). The chapter never
introduces the file, never says the consumer must author it, and never says
it must be committed first. Reproduced: exit 2, "consumer guidance is absent
or ambiguous at pinned source commit ...: GUIDANCE.md"; the identical command
succeeds once the file is committed. Remedy: one step or sentence in the
authorized file that names the guidance file, says what it is for, and commits
it before `wfc plan`.

[[h002-f2]]
*Finding 2 -- the documented `wfc run --yes` invocation is refused as written.*
`:82-134` has the reader author the task document and then hand-author the
Consumer Request from the repository root, and never says to commit them or
keep them outside the worktree. Non-ignored untracked files alone make the
tree unclean (`git_facts.py:44-46`), and `lifecycle.py:348`/`:389` refuse on
it. Reproduced: exit 22, "repository worktree is not clean at the authorized
baseline", with `?? request.yaml` and `?? task.md` the only unclean state.
Remedy: state where these two files live and commit them (or keep them outside
the repository, as the accepted BP9 E2E test does).

Findings 1 and 2 are one correction of the same walkthrough but two distinct
missing facts with two distinct remedies, so they are recorded separately.
Together they are a reproduced failure of the governing BP9 goal, which is
that an external user can install, configure, plan, run unattended, inspect
and archive *from this document* -- not merely that the commands exist.

[[h002-f3]]

=== Non-blocking observations (H002)

. *`archive/<classification>/` is not a real path segment.* `:154` tells the
  reader to run `wfc report <evidence-repo>/archive/<classification>/
  <attempt-id>/audit.json`. The real destination is
  `<evidence-repo>/archive/<domain>/<workstream>/<attempt-id>` when semantic
  taxonomy is supplied and `<evidence-repo>/archive/unclassified/
  <attempt-id>` otherwise (`frontdoor/archive.py:746-749`); the lifecycle
  postrun step supplies no `semantic_path`, so for *every* `wfc run` archive
  the literal segment is `unclassified`
  (`tests/integration/test_beta_e2e_fake_provider.py:213` asserts exactly
  that). A reader who substitutes the Run classification this same page
  taught them to read twelve lines earlier ("always read the printed
  classification") gets a path that does not exist. The placeholder matches
  existing manual usage (`ch04_evidence/02_archive.adoc:127`,
  `ch05_self_development/01_topology_budget.adoc:187`,
  `ch08_examples/03_commission_to_archive.adoc:222`), which is why this is not
  blocking, but inside a quickstart the collision of the two meanings of
  "classification" is actively misleading. Both `wfc run`'s consolidated
  postrun report and `wfc status`'s `ARCHIVE:` block already print the real
  `destination_relative` (`frontdoor/postrun.py:150-164`,
  `ch03_running/02_launch_status.adoc:72-78`); pointing at that is both
  shorter and correct, and it fits the same correction as Findings 1 and 2.
. *"Archiving happens automatically once the Run reaches a terminal state"
  (`:157-159`) is slightly broader than the code.* Only `completed`,
  `awaiting_human`, `awaiting_human_budget`, `reconcile_required`, `stopped`
  and `interrupted` archive (`frontdoor/postrun.py:46-49`); `uncertain_launch`
  and the `refused_*` classifications never do. Correct for the happy path the
  quickstart covers, so it is a hedge worth one clause rather than a defect.
. *The surviving-provider fact itself is not stated.* The first limitation
  covers all three sub-facts the task's parenthetical names, so the item is
  complete as specified, but the consumer-actionable half of DG-3 Variant B is
  missing: a provider process may outlive a dead controller and *can still
  write to your repository*, quiescence is recorded as `unattested`, and there
  is no `wfc stop` (`beta1_execution_plan.adoc:401-402`, `:411-412`, `:764`;
  `beta1_productization.adoc:94-97` asks for "Coordinator crashes and
  potentially surviving provider processes" to be documented). One sentence
  would close it.
. *"The same fields" understates the Consumer Request.* `:120-124` says to
  hand-author the YAML with "the same fields" as the `plan` flags.
  `evidence.timeout_seconds` and `guidance.source_commit` are *required* in
  the YAML (`frontdoor/request.py:69`, `:89`) although their `plan` flags
  (`--evidence-timeout`, `--guidance-commit`) are optional and defaulted, so a
  reader taking "the same fields" literally gets a rejected request.
. *"Prints the Commission bytes" (`:119`) is loose.* `wfc plan` prints the
  projected per-file SHA-256 digests and the manifest digest plus the resolved
  envelope and its digest, not the bytes.
. *Length.* 1221 words plus ten fenced blocks across two sections is closer
  to three printed pages than two. "About two pages" is a soft target and the
  content is all required, so this is a trim opportunity, not a defect --
  worth noting because Findings 1-3 add material.
. *Test coverage boundaries.* `tests/unit/test_quickstart_commands.py` checks
  subcommands and option tokens but not positional arguments (`wfc plan
  <task>`, `wfc report <source>`, `wfc audit <attempt-dir>`), and it treats
  the bare `wfc --version --json` form with a hardcoded allow-set
  (`:139-142`) rather than against `frontdoor/cli.py`. It also reaches into
  argparse privates (`_option_string_actions`, `_actions`) and globally
  monkeypatches `ArgumentParser.parse_args` to capture the parser. The
  monkeypatch is restored in a `finally` and the private access is the only
  practical way to introspect these parsers, so this is acceptable; it is
  recorded so a later reader knows the guard's edges.
. *`scripts/wfc_op.py` is not mentioned at all*, which satisfies "not except
  as retired", and no Harness-era instruction appears anywhere in the chapter.
