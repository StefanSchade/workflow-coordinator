== 1. Why this concept exists

`workflow-coordinator` did not begin life as a standalone product. It grew out of
internal tooling inside `spreadsheet-handling`.

That history remains visible:

* repository knowledge is spread across concepts, reviews, runbooks, Project
  Memory, backlog records, imported incubator material, source, governance, and
  Git history;
* the current Commission interface exposes many low-level mechanical invariants;
* even strong LLMs have repeatedly produced mechanically inconsistent
  Commissions that required multiple provider-free repair attempts before a Run
  could start;
* the Level-0 Run/Hop execution kernel has become substantially more coherent,
  but the repository around it still carries the sediment of rapid architectural
  discovery;
* Project Memory is valuable but not yet sufficient by itself as a complete
  fresh-agent entry point into the current project state.

The project therefore has two different consolidation needs:

. finish the current Level-0 capability line to a deliberate MVP;
. make both the consumer boundary and the repository itself legible enough that
  higher-order orchestration can build on them safely.

This concept treats those as first-class project work, not as incidental
"cleanup."

== 2. Central planning thesis

The near-term plan is:

[source,text]
----

  -> PyPI publication

========================
       LEVEL-0 MVP
========================

  -> first bounded Level-1 work
  -> dogfood from the higher layer
  -> learn where the real L1/L0 pressure points are

  -> only then add the next high-complexity L0 capabilities, e.g.
       privileged Git authority escalation

----

The important sequencing claim is:

*the Commission Front Door and repository consolidation belong before the MVP
boundary; the major kernel refactor belongs after initial Level-1 experience but
before the next cross-cutting Level-0 security/authority features.*

== 3. The MVP boundary

=== 3.1 What "Level-0 MVP" should mean

A Level-0 MVP is not merely "the Run/Hop loop works."

At the MVP boundary, a higher-level consumer should be able to use Level 0
without understanding every internal Commission invariant.

The MVP therefore has two faces.

Execution face::
Level 0 can reliably admit and execute bounded work, invoke supported providers,
perform review/correction flows, produce trusted evidence/effects, reduce Run
state, and stop fail-closed when authority or semantics are insufficient.

Consumer face::
A stable, provider-free Front Door exists that prevents consumers from directly
hand-assembling the full raw Commission protocol for ordinary use.

The second property is required before serious Level-1 work. Otherwise Level 1
would simply automate the same error-prone low-level authoring process that
humans and LLMs already find difficult.

=== 3.2 MVP publication milestone

The Level-0 MVP boundary should coincide with the first deliberate public package
publication of `workflow-coordinator` to PyPI.

PyPI publication is not merely a distribution convenience. It is a forcing
function for product boundaries:

* package metadata must be coherent;
* supported Python/runtime assumptions must be explicit;
* public entry points must be intentional;
* internal/incubator paths should not accidentally define the consumer API;
* installation and basic operator usage must be reproducible outside the
  development checkout;
* versioning and release notes must tell a comprehensible product story.

The exact version number is not decided here.

PyPI publication remains separately authorized release work.

== 4. Phase A -- finish the Level-0 MVP

=== 4.1 Complete the current capability line

The present delivery line should be completed before opening a broad new
architecture front:

. P3 -- finish Finding projection / successor completion;
. P3.5 -- authority-composition concern;
. P4 -- Coordinator-owned deterministic mechanics/effects;
. P5 -- provider-facing cleanup;
. Claude adapter.

The exact slice definitions remain governed by their existing project records.
This concept does not redefine them.

=== 4.2 Build the Commission Front Door before MVP

The reviewed Commissioning work does not justify a new trust-bearing
"Commissioning Service" between Level 1 and Level 0.

It does justify a consumer-facing inbound adapter / anti-corruption layer on the
requesting side of the existing trust boundary.

Conceptually:

[source,text]
----
Human / future Level 1
        |
        v
Commission Front Door
  - semantic authoring
  - Components resolution
  - provider-free validation
  - deterministic projection
  - no authority
        |
        v
reviewed / separately authorized governing inputs
==================================================
                trusted Level 0
  admission / execution / evidence / enforcement
----

This is a concern and adapter surface, not a new architectural level.

=== 4.3 Front Door -- smallest useful sequence

The Front Door should itself be value-first.

==== Step 1 -- use existing Components correctly

Before adding a new persona/harness catalog mechanism, make proper use of the
existing digest-pinned Components seam for reusable role/reference/prompt
material.

The recent Commissioning analysis found that reusable prompt material had been
placed into a much smaller persona field while the larger Components mechanism
was barely used.

The first simplification should exploit the mechanism already present.

==== Step 2 -- provider-free authoring validation

Add an explicit draft/authoring validation path before PREPARE.

Its purpose is to answer:

[source,text]
----
"Is this candidate Commission mechanically coherent?"
----

without:

* consuming a Run/attempt identity;
* launching a provider;
* creating execution authority;
* requiring the operator to discover deterministic authoring errors through
  repeated PREPARE attempts.

The validator should target only mechanically derivable problems, for example:

* persona/component limits;
* scope projection inconsistencies;
* invalid or stale route wiring;
* evidence-placement contradictions;
* failed-evidence-route contradictions;
* inconsistent WorkItem/Profile/Policy/Task projections;
* unsupported combinations that Level 0 can reject deterministically.

It must not become a second semantic authority engine.

==== Step 3 -- CommissionIntent / deterministic renderer, only if justified

If Steps 1-2 still leave material duplicated authoring work, introduce the
smallest useful semantic authoring model.

Current hypothesis:

[source,text]
----
CommissionIntent
  = canonical authoring source for one render transaction

deterministic renderer
  -> ordinary inspectable governing-input projection

committed + admitted governing inputs
  = canonical execution authority seen by current Level 0
----

The renderer must remain provider-free and authority-free.

A manual edit of generated governing inputs invalidates the claimed
intent/projection equivalence unless that edit is folded back into the authoring
source.

This concept does not require CommissionIntent to exist if Components plus
validation already remove most of the measured friction.

==== Step 4 -- workflow grammar only after round-trip proof

The current profile corpus shows substantial structural repetition, but the exact
grammar is not yet accepted.

Before generated topology replaces authored topology, a renderer must prove
lossless or semantically equivalent round-trip coverage of the complete current
profile corpus, including:

* non-default initial entry points;
* continuation/gate-first profiles;
* the currently observed bypass/skip edge;
* evidence and route semantics.

Until then, workflow grammar remains a simplification hypothesis.

== 5. Repository/product consolidation before MVP

Repository consolidation is not a generic "cleanup sprint."

It is productization work with concrete consumer and fresh-agent outcomes.

=== 5.1 Canonical backlog

The repository should have one discoverable current backlog view that answers:

* what work is open;
* what is next;
* what is blocked;
* which items are architecture/design work versus implementation;
* which items belong to the current MVP line;
* which items are explicitly post-MVP.

Historical backlog material may remain for provenance, but a fresh agent should
not need Git archaeology to determine the current backlog.

This concept does not prescribe the exact file/schema until the existing backlog
mechanisms are inspected.

=== 5.2 Explicit FTR index

Feature/Technical Requirement records should have a canonical index or generated
projection that answers:

* which FTRs exist;
* current status;
* owning capability/feature;
* relevant implementation and review records;
* whether the FTR is current, superseded, or historical.

The purpose is discoverability, not creation of a new governance ontology.

=== 5.3 Explicit bug / defect view

Open defects should be discoverable separately from architecture hypotheses and
feature backlog.

At minimum a fresh agent should be able to distinguish:

* known implementation bug;
* architecture debt;
* missing mechanism;
* rejected/obsolete concern;
* expected future feature.

Do not force these into one category merely to reduce file count.

=== 5.4 Concept/document taxonomy

The repository should define a clear home and intended authority class for
different records.

At minimum distinguish:

* current product/architecture decisions;
* non-authorizing concepts/hypotheses;
* independent reviews;
* runbooks/current operating procedures;
* backlog;
* historical/imported/incubator material;
* release/operator documentation;
* Project Memory.

The goal is that file placement gives a useful first approximation of status,
while status lines and authority indexes remain decisive.

=== 5.5 Repository map

A short maintained repository map should answer:

[source,text]
----
Where do I look for:
  architecture?
  current decisions?
  current backlog?
  FTRs?
  bugs?
  runbooks?
  operator usage?
  Project Memory?
  self-development governance?
  source?
  tests?
  historical/incubator material?
----

This should be concise enough to serve as the first page for a fresh human or
LLM.

=== 5.6 Project Memory as a stronger LLM entry point

Project Memory should become more useful as a compact semantic index into the
repository.

The goal is not to duplicate all architecture records.

It should help a fresh agent recover:

* implemented/current reality;
* accepted/current decisions;
* current manual practice;
* preferred but non-authorizing hypotheses;
* open/incomplete work;
* superseded/historical state;
* durable links to the records that explain each item.

A successful Project Memory experience should reduce dependence on long chat
history.

Potential future projections may include a generated "fresh-agent brief" or
bounded handoff assembled from Project Memory plus current repository facts.

No new projection format is authorized here.

=== 5.7 Fresh-agent acceptance test

Repository consolidation should be tested against a concrete operational
criterion:

[quote]
____
Can a fresh strong model, given only the repository and a short bounded task
description, identify the relevant current authority, backlog item, design
records, execution path, and next correct action without reconstructing months of
conversation history?
____

This is a stronger test than merely having complete documentation.

== 6. PyPI/productization work at the MVP boundary

Before the MVP is published, verify at least:

* installability into a clean environment;
* intentional package boundaries;
* CLI entry point(s);
* dependency declarations;
* supported Python versions;
* package/version metadata;
* license/README/release metadata as applicable;
* provider adapter optionality/dependency handling;
* no dependence on local development-only paths;
* minimal getting-started/operator documentation;
* a smoke test from installed package rather than repository checkout.

The exact release checklist should be derived from the repository and packaging
toolchain when this milestone is commissioned.

== 7. Phase B -- first Level-1 learning

After the Level-0 MVP, deliberately move upward rather than immediately adding
the next deep Level-0 security/authority capabilities.

The purpose is to gain real evidence from a higher-order consumer.

=== 7.1 First Level-1 scope should be narrow

Do not begin by building a general planner.

Likely first useful capabilities are closer to:

* choose the next authorized WorkItem from a bounded backlog;
* classify/select a known task/workflow family;
* construct/request a Commission through the Front Door;
* consume L0 Run outcome;
* interpret simple completion versus typed escalation;
* produce a bounded successor request where existing authority already decides
  the answer.

The exact first slice should be chosen from observed manual coordination work.

=== 7.2 What we want to learn

Early Level-1 dogfooding should reveal:

* which L0 details still leak through the Front Door;
* which task semantics actually matter above L0;
* which escalations recur;
* what L1 can decide deterministically;
* where human/stakeholder authority remains necessary;
* which Project Memory facts are actually useful to orchestration;
* what progress/status artifacts a stakeholder needs.

This evidence should shape the later kernel refactor.

=== 7.3 Human trajectory

Long term, routine dispatch should move away from the human.

Possible direction:

[source,text]
----
today:
  human/assistant author and authorize individual execution units

later:
  Level 1 operates inside bounded pre-authorized project envelopes

eventual:
  human behaves more like project sponsor / stakeholder
  and participates at defined checkpoints:
    major scope change
    architecture decision
    risk/authority escalation
    milestone review
    release / deployment / external effect
----

A future Level 1 may generate purpose-built stakeholder artifacts explaining:

* progress;
* decisions;
* risks;
* evidence;
* unresolved choices;
* upcoming checkpoints.

This is future direction, not current implementation scope.

== 8. Phase C -- kernel consolidation before the next complexity wave

After first Level-1 experience, but before adding the next major authority and
information-flow capabilities, perform a deliberate architecture-preserving
Level-0 kernel consolidation.

This is an explicit project gate.

=== 8.1 Why the refactor is intentionally later

Refactoring immediately after the current MVP feature line would optimize the
kernel using only bottom-up knowledge.

Waiting until a first Level-1 consumer exists gives evidence from both sides:

* internal Level-0 coupling/complexity;
* actual consumer pressure from above.

That should produce a better refactor target.

=== 8.2 Kernel Preservation Principle

[quote]
____
New Level-0 policy/derivation capabilities SHOULD live behind narrow typed
interfaces and MUST NOT require cross-cutting modification of the established
Run/Hop execution kernel unless the kernel abstraction itself is proven
insufficient.
____

The goal is that the execution kernel becomes increasingly boring and stable.

=== 8.3 Likely internal shape

[source,text]
----
Level-0 Domain
|
+-- Execution Kernel
|     Run / Hop
|     reduction
|     trusted effects
|     evidence
|     provider dispatch
|     fail-closed mechanics
|
+-- isolated Policy / Domain Services
      assurance derivation
      model capability requirements
      capability envelope derivation
      information-flow eligibility
      topology eligibility
----

Interaction should prefer:

[source,text]
----
ExecutionRequest
    -> Policy/Domain Services
    -> typed ExecutionConstraints
    -> Execution Kernel
----

rather than spreading new conditionals throughout the reducer/operator/provider
paths.

=== 8.4 Refactor acceptance test

Use at least two future requirements as architecture probes:

Privileged Git authority escalation::
Can a normal Run stop, obtain separately authorized expanded Git capability,
compile a successor envelope, and attach mandatory defensive review without
cross-cutting edits throughout the Run/Hop kernel?

Protected/corporate-secret execution::
Can a task stop before disclosure, obtain information-access authorization,
select an eligible execution boundary/model, and continue without embedding
information-flow policy throughout the kernel?

If both still require invasive edits across unrelated kernel internals, the
refactor has not created the intended boundaries.

=== 8.5 No feature piggybacking

During the kernel-consolidation slice, avoid simultaneously implementing the new
privilege/secret capabilities that motivate it.

Preserve existing behavior first.

Characterization and architecture tests should protect the current semantics
while boundaries are extracted.

== 9. Phase D -- post-refactor Level-0 expansion

Only after kernel consolidation should the project deliberately add the next
cross-cutting Level-0 concerns, likely including some subset of:

* privileged Git authority/capability escalation;
* protected/corporate-secret context;
* verified read/visibility containment;
* information-flow/provider compatibility;
* self-hosted/local model eligibility where required;
* trusted minimum model-capability/assurance policy;
* capability-derived mandatory defensive review.

These are not MVP requirements.

Their exact order should be decided from real Level-1 and organizational use
cases.

== 10. Complexity budget

The project should treat complexity as a limited architectural resource.

A new mechanism should answer:

. What repeated real problem does it remove?
. Which existing mechanism can it reuse?
. Does it introduce a second source of truth?
. Does it enlarge the execution kernel?
. Can it be isolated behind a typed port/service?
. Can a fresh agent understand its authority/status from repository records?
. Does it reduce or increase the number of concepts required to launch ordinary
  work?

Prefer:

* generated projections over duplicated hand-authorship;
* narrow deterministic services over cross-cutting conditionals;
* existing Components over new catalog systems;
* explicit open questions over premature mechanisms;
* measured friction over speculative platform design.

== 12. MVP completion questions

Before calling the Level-0 MVP complete, answer yes to questions of this form:

Execution::
Can the coordinator reliably execute the intended P3-P5-era workflow semantics
with supported provider adapters and trusted evidence?

Front Door::
Can a consumer construct ordinary valid work without directly mastering every
raw Commission invariant?

Failure mode::
Do deterministic authoring errors fail before provider execution and preferably
before PREPARE consumes operational state?

Repository::
Can a fresh human or strong model find the current backlog, FTRs, defects,
architecture status, runbooks, and next development line without chat history?

Memory::
Does Project Memory accurately distinguish implemented reality, accepted
decisions, manual practice, hypotheses, and open work?

Packaging::
Can the package be installed and smoke-tested from PyPI-style artifacts rather
than only from the repository checkout?

Authority::
Does the MVP preserve the rule that the requester/beneficiary cannot manufacture
its own authority?

Scope::
Are post-MVP privilege/information-flow capabilities explicitly deferred rather
than half-built into the MVP?

== 13. Non-goals

This concept does not authorize or require:

* a monolithic Commissioning Service;
* a new architectural Level 0.5;
* a general agent platform;
* a generic project-management engine;
* a universal workflow DSL;
* a model-scoring/router system;
* a complete corporate data-classification system;
* privileged Git escalation before kernel consolidation;
* secret-data/model-selection machinery before kernel consolidation;
* a rewrite of Level 0;
* a repository-wide cosmetic cleanup;
* migration of every historical document;
* deletion of historical/incubator provenance;
* a new Project Memory schema merely for tidiness;
* automatic PyPI publication.

== 14. Repository-consolidation principle

The repository should increasingly reflect the fact that `workflow-coordinator`
is now a project in its own right rather than an incidental helper inside
`spreadsheet-handling`.

That does not mean erasing its history.

It means making the current product legible without requiring knowledge of that
history.

A successful consolidation preserves provenance while making the current answer
to each ordinary question obvious:

[source,text]
----
What is this project?
What is current?
What is next?
Where is the authority?
Where is the backlog?
Where are the known defects?
Where are the FTRs?
Where are the architectural hypotheses?
How do I operate it?
How do I extend it?
What is intentionally deferred until after MVP?
----

== 15. Provisional conclusion

The project is approaching a useful transition.

The Level-0 execution mechanism has accumulated enough evidence and structure
that the next goal should not be unlimited feature expansion.

First finish the current P3-P5/provider line.

Then make Level 0 consumable through a deliberate Front Door, make the repository
legible as a standalone product, strengthen Project Memory as a fresh-agent
semantic index, and publish the resulting MVP to PyPI.

After that, deliberately move upward and learn from a first bounded Level-1
consumer.

Only with that higher-level evidence in hand should the project perform the
architecture-preserving kernel consolidation needed before introducing the next
cross-cutting authority, privilege, and protected-information features.

The intended trajectory is therefore:

[source,text]
----
stabilize the kernel
-> make it consumable
-> make the project legible
-> publish the MVP
-> learn from above
-> consolidate the kernel
-> then expand authority/security capability
----
