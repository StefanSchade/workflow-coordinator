== 1. Why this concept exists

`workflow-coordinator` did not begin life as a standalone product. It grew out
of internal tooling inside `spreadsheet-handling`.

That history remains visible:

* repository knowledge is spread across concepts, reviews, runbooks, Project
  Memory, backlog records, imported incubator material, source, governance, and
  Git history;
* the current Commission interface exposes many low-level mechanical
  invariants, and even strong LLMs have repeatedly produced mechanically
  inconsistent Commissions that required multiple provider-free repair
  attempts before a Run could start
  (`docs/warm_storage/concepts/workflow_coordinator_operational_friction_evidence_2026-10-11.adoc`,
  §§3-5);
* the Level-0 Run/Hop execution kernel has become substantially more coherent,
  but the repository around it still carries the sediment of rapid
  architectural discovery
  (`docs/backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc`);
* Project Memory is valuable but not yet sufficient by itself as a complete
  fresh-agent entry point into the current project state, and two of the
  repository's other authority-classified orientation surfaces
  (`docs/backlog/README.adoc`, `docs/README.adoc`) are themselves currently
  stale or incomplete (§5.1 below).

The project therefore has two different consolidation needs:

. finish the current Level-0 capability line to a deliberate product
  milestone;
. make both the consumer boundary and the repository itself legible enough
  that higher-order orchestration can build on them safely.

This concept treats those as first-class project work, not as incidental
"cleanup."

This concept amends and supersedes, at this file, the version recorded at
commit `469ebd6` after independent review
(see the Amendment note above and `docs/warm_storage/concepts/workflow_coordinator_mvp_repository_consolidation_and_level1_transition_concept_2026-10-12_review_001.adoc`).

== 2. Central planning thesis

The near-term plan is:

[source,text]
----
truth repairs in authority-classified records
  -> P3 disposition (then, only if decided, a fresh P3 Commission)
  -> P3.5
  -> friction baseline measurement
  -> Commission Front Door Steps 1-2 (Components, authoring validation)
  -> Claude adapter
  -> P4 / P5 assessed against milestone need
  -> Front Door Steps 3-4, only if the baseline shows material fall-short
  -> one real consumer-repository Run through the Front Door
  -> repository/product consolidation completion
  -> published-surface decision and release hardening

===================================
   LEVEL-0 PRODUCT MILESTONE 1
===================================

  -> PyPI publication (separately authorized release milestone)

  -> first bounded Level-1 work (pipeline-target Stage 3)
  -> dogfood from the higher layer
  -> learn where the real L1/L0 pressure points are

  -> Level-0 kernel consolidation / architecture-preserving refactor
       (shape learned from Phase B, not pre-named;
        governed by FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES)

  -> only then add the next high-complexity L0 capabilities, e.g.
       privileged Git authority escalation
       protected/corporate-secret execution
       information-flow/provider eligibility
       stronger derived assurance/model-capability policy
----

The important sequencing claim is unchanged from the original concept:

*the Commission Front Door and repository consolidation belong before the
milestone boundary; the major kernel refactor belongs after initial Level-1
experience but before the next cross-cutting Level-0 security/authority
features.*

What is new in this amendment is that the milestone boundary itself is defined
without reference to PyPI, and carries an explicit consumer-evidence
criterion (§3, §12).

The Front Door Steps (§4.4) and the first Level-1 work (§7) are not a second
stage vocabulary. They are mapped in §7.1 onto the existing maturity model in
`docs/warm_storage/concepts/workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc`
§13 (Stage 0 -- current manual reference, through Stage 3 -- bounded Level-1
orchestrator), which this concept treats as the project's one stage
vocabulary.

== 3. The Level-0 Product Milestone 1 boundary

=== 3.1 Terminology

This concept names its milestone *"Level-0 Product Milestone 1"*, not bare
"MVP". "MVP" is already used in the repository with two narrower meanings:
`docs/backlog/FTR-WFC-ROLE-PERSONA-EXECUTION-BINDING.adoc` uses it for a closed
role/persona/binding implementation choice, and
`docs/product_boundary_and_higher_order_orchestration_concept_2026-09-25.adoc`
uses "first-MVP" for a supervised-continuation deployment posture. This
concept's milestone is a different, much larger referent -- kernel
completion, Front Door, repository consolidation, and a consumer-evidence
criterion -- and a fresh agent grepping "MVP" should not get three
incompatible answers.

=== 3.2 What the milestone should mean

Level-0 Product Milestone 1 is not merely "the Run/Hop loop works."

At the milestone boundary, a higher-level consumer should be able to use
Level 0 without understanding every internal Commission invariant, *and* the
claim that Level 0 is usable by a consumer must rest on evidence from an
actual consumer, not only from WFC's own self-development.

The milestone therefore has three parts.

Execution face::
Level 0 can reliably admit and execute bounded work, invoke supported
providers, perform review/correction flows, produce trusted evidence/effects,
reduce Run state, and stop fail-closed when authority or semantics are
insufficient, *for the P3-P5-era workflow semantics actually disposed of by
then* -- see §4.2 for what "disposed of" means for each of P3, P3.5, P4, and
P5. This face does not require every one of P3-P5 to ship; it requires each
of them to have reached its own recorded resolution (finished, assessed and
deferred, or found conditionally unnecessary).

Consumer face::
Ordinary Commission authoring does not require re-deriving mechanical
invariants by hand; deterministic authoring errors are detected before
PREPARE reserves an attempt identity; the measured authoring-friction baseline
(§4.5) has materially fallen from the pre-Front-Door baseline; and a
higher-level consumer does not need to master every raw Commission invariant
for ordinary use. Hand-authored Commissions remain admissible throughout --
this criterion is about reducing friction for ordinary use, not about making
hand-authored Commissions inadmissible, which the amended Commissioning
concept rejects
(`docs/warm_storage/concepts/workflow_coordinator_commissioning_service_concept_2026-10-11.adoc`
§5.3: "admission must not depend on this one convenience authoring tool, so a
hand-authored Commission must remain admissible"). This remains a planning
criterion, not accepted architecture, and nothing here decides the concrete
authoring-model API in advance.

Consumer-evidence face::
At least one real Core-repository or Latin-repository Run, on a current
Runtime, exercised through the Front Door as applicable, with its outcome
recorded. `CONC-WFC-LEVEL0-EMPIRICAL-CONFIDENCE` is `active`/`high` and its
`next_action` is explicit: "Keep treating convergence as proven only for
routes actually exercised. ... broaden it with real Core/Latin consumer Runs
before generalizing, and do not generalize clean two-Hop self-development Runs
to arbitrary-task autonomy." The milestone must not be declared, and must not
be published (§6), on WFC-on-WFC evidence alone. The milestone statement must
say explicitly which routes it claims as exercised and which it does not. In
particular: Convergence Slice 5 ("R1A dogfood",
`docs/backlog/FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE.adoc`, product-slice list)
has not run as of this amendment; unless it runs before the milestone,
convergence-escape must be named as unexercised rather than silently implied
proven.

=== 3.3 Relationship to PyPI publication

The Level-0 Product Milestone 1 boundary does *not* coincide with publication
of `workflow-coordinator` to PyPI. Publication is reclassified as a deliberate
*release milestone immediately after* the product milestone (§6).

This corrects the original concept's §3.2, which bound the milestone
definition to "the first deliberate public package publication... to PyPI."
The review's finding (F-B1) is that, at this amendment's writing:

* the package's only console entry point, `wfc`
  (`pyproject.toml`'s `wfc = "workflow_coordinator.operator:main"`), dispatches
  `export-salvage` and `prepare-successor`, whose lineage's last independent
  rereview is *CHANGES REQUIRED* with carried requirement `R1A` open across
  three cycles
  (`docs/backlog/FTR-WFC-SCOPE-ESCALATION-CONTINUATION_implementation_review_004.adoc`;
  `CONC-WFC-ATOMIC-HOP-RECOVERY-WIRING`);
* the package declares no public API (`src/workflow_coordinator/__init__.py`
  is a single docstring describing it as "Repository-local mechanics"), so
  publication would make the current flat 15-module namespace a de-facto
  import surface;
* Phase C (§8) intends to restructure exactly that layout, so publishing it
  first would freeze a pre-refactor import surface as a public contract.

The forcing-function value PyPI offers -- coherent package metadata, explicit
entry points, no accidental incubator-path API -- is preserved by keeping the
*boundary work* (§6) inside the milestone and moving only the *publication
event* outside it. Publication itself remains separately authorized release
work, decided after the milestone, not a milestone criterion.

=== 4.3 Build the Commission Front Door before the milestone

The reviewed Commissioning work does not justify a new trust-bearing
"Commissioning Service" between Level 1 and Level 0
(`docs/warm_storage/concepts/workflow_coordinator_commissioning_service_concept_2026-10-11.adoc`,
as amended, and its
`docs/warm_storage/concepts/workflow_coordinator_commissioning_service_concept_2026-10-11_review_001.adoc`).

It does justify a consumer-facing inbound adapter / anti-corruption layer on
the requesting side of the existing trust boundary.

Conceptually:

[source,text]
----
Human / future Level 1
        |
        v
Commission Front Door
  - semantic authoring
  - Components selection / authoring
  - provider-free validation
  - deterministic projection (conditional on Step 3, see §4.4)
  - no authority
        |
        v
reviewed / separately authorized governing inputs
==================================================
                trusted Level 0
  admission / execution / evidence / enforcement
      - digest-pinned Components loading
      - digest recording
      - governing-input re-verification
----

This is a concern and adapter surface, not a new architectural level.

Two corrections to the original diagram, both bounded wording fixes (F-M4):

. The first item is named "Components *selection / authoring*", not
  "Components *resolution*". At HEAD, component content is loaded from the
  pinned revision and digest-recorded inside Level-0 admission
  (`operator.py:443`, with digest re-verification at `:475`). Digest-pinned
  component *loading*, digest *recording*, and governing-input
  re-verification remain Level-0 admission activities that the Front Door
  neither performs nor pre-empts. The Front Door's role is choosing which
  components a Commission references, which is requesting-side authoring, not
  trusted resolution.
. "Deterministic projection" is listed as *conditional* on Front Door Step 3
  (§4.4), not as definitional Front Door content, consistent with §4.4's own
  framing of Step 3 as introduced only if justified.

Package placement of the Front Door tooling is left as an open question,
bounded by the amended Commissioning concept's constraint
(`workflow_coordinator_commissioning_service_concept_2026-10-11.adoc` §5.3):
plausibly inside the WFC distribution as an explicitly non-authoritative tool,
in the relationship `scripts/wfc_op.py` and `make memory-export` already
have, and it must not link into `src/workflow_coordinator/` admission or
reducer paths as an authority-granting dependency (see §4.4 Step 2 for how
this is reconciled with reusing production validators).

=== 4.4 Front Door -- smallest useful sequence

The Front Door should itself be value-first.

==== Step 1 -- use existing Components correctly

Before adding a new persona/harness catalog mechanism, make proper use of the
existing digest-pinned Components seam for reusable role/reference/prompt
material.

Independently verified: `governance/self-development/prompts/worker.txt` is
204 bytes and `reviewer.txt` is 231 bytes, against a 65,536-byte per-component
and 196,608-byte total budget, and 248 `modifiers`/`repository_policy`
selector lines are empty across the 36 governance profiles. Reusable prompt
material has been placed into a much smaller persona field while the larger
Components mechanism is barely used. This is evidence-backed and genuinely
zero-mechanism, and is correctly placed first.

==== Step 2 -- provider-free authoring validation

Add an explicit draft/authoring validation path before PREPARE.

Its purpose is to answer:

[source,text]
----
"Is this candidate Commission mechanically coherent?"
----

without:

* consuming a Run/attempt identity;
* launching a provider;
* creating execution authority;
* requiring the operator to discover deterministic authoring errors through
  repeated PREPARE attempts.

The validator should target only mechanically derivable problems, for example:

* persona/component limits;
* scope projection inconsistencies;
* invalid or stale route wiring;
* evidence-placement contradictions;
* failed-evidence-route contradictions;
* inconsistent WorkItem/Profile/Policy/Task projections;
* unsupported combinations that Level 0 can reject deterministically;
* the phase-completion-contract ambiguity named in
  `docs/backlog/BUG-WFC-PHASE-COMPLETION-CONTRACT-OPAQUENESS.adoc`, whose
  recorded remedy is substantially this validator.

It must not become a second implementation of production admission rules.

Reuse, not duplication (resolving F-M5):: The deterministic checks this
validator needs currently live inside `operator._preflight()`, interleaved
with Git observation, state-root preconditions, and evidence-runner wiring --
they are not yet factored as a reusable pure function. The supported
direction is: the validator reuses the same deterministic check functions
*read-only*, and must not duplicate composition/admission semantics in a
second implementation. The extraction inside `operator.py` needed to make
those checks reusable is justified only as the concrete seam this feature
needs -- not as general refactoring --
consistent with
`docs/backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc`'s
own criterion that extraction is warranted when "extraction simplifies the
next concrete feature." Concretely, Front Door Step 2 consumes P3.5's
composition check (§4.2) rather than creating a parallel
Commission-conformance checker; this, not mere scheduling convenience, is why
P3.5 precedes the Front Door in §11. This reading reconciles the two
accepted-direction records that otherwise sound opposed: the friction record's
"authoring-time validation using production validators"
(`workflow_coordinator_operational_friction_evidence_2026-10-11.adoc` §9.2) and
the amended Commissioning concept's rule that the authoring tool "must not
link into `src/workflow_coordinator/` admission or reducer paths" as a
trust-bearing dependency (`workflow_coordinator_commissioning_service_concept_2026-10-11.adoc`
§5.3) -- the non-link rule targets authority coupling and projection emission,
not read-only reuse of deterministic check functions. This concept does not
design the concrete extraction API; that is A5's own work (§11).

==== Step 3 -- CommissionIntent / deterministic renderer, only if the measurement gate shows it is needed

See §4.5 for the measurement gate. If, and only if, that measurement shows
Steps 1-2 leave material duplicated authoring work by the four named metrics,
introduce the smallest useful semantic authoring model.

Current hypothesis:

[source,text]
----
CommissionIntent
  = canonical authoring source for one render transaction

deterministic renderer
  -> ordinary inspectable governing-input projection

committed + admitted governing inputs
  = canonical execution authority seen by current Level 0
----

The renderer must remain provider-free and authority-free.

A manual edit of generated governing inputs invalidates the claimed
intent/projection equivalence unless that edit is folded back into the
authoring source.

See §7.3 for the unresolved relationship between this hypothesis and the
existing `SuccessorIntent` concept -- that relationship is an open design
question, not decided here.

==== Step 4 -- workflow grammar only after round-trip proof

The current profile corpus shows substantial structural repetition, but the
exact grammar is not yet accepted.

Before generated topology replaces authored topology, and only after Step 3
is itself justified by §4.5's measurement gate, a renderer must prove lossless
or semantically equivalent round-trip coverage of the complete current profile
corpus, including:

* non-default initial entry points;
* continuation/gate-first profiles;
* the currently observed bypass/skip edge (the single bypass edge in the
  `standalone-developer-ergonomics` profile that no current grammar
  hypothesis expresses);
* evidence and route semantics.

Until then, workflow grammar remains a simplification hypothesis.

=== 4.5 Measurement gate: capture the baseline before Front Door Step 1

`CONC-WFC-OPERATIONAL-FRICTION-AI-MAINTAINABILITY`'s `next_action` is
explicit: "Capture the record's baseline metrics *before any simplification
programme*, and take the two no-new-mechanism steps first: populate the
existing digest-pinned prompt-component mechanism, and add an authoring-time
validator over the existing provider-free admission checks." The two
no-new-mechanism steps named there are this concept's Front Door Steps 1 and
2 (§4.4). The baseline must therefore be captured *before* Step 1 begins, not
interleaved between Step 1 and Step 2 -- otherwise the comparison below has
no true pre-intervention measurement to fall against.

Capture the operational-friction baseline already specified in
`docs/warm_storage/concepts/workflow_coordinator_operational_friction_evidence_2026-10-11.adoc`
§8 ("Suggested measurement before redesign") before Front Door Step 1 begins.

After Front Door Steps 1-2 are in place, compare at least the following four
metrics against that pre-Step-1 baseline, per
`CONC-WFC-OPERATIONAL-FRICTION-AI-MAINTAINABILITY`'s own judgement criteria:

* Commission lines authored per WorkItem;
* duplicated scope declarations across WorkItem/profile/policy/task;
* provider-free preflight refusals;
* consumed attempt identifiers before first successful PREPARE.

Only if the measured friction remains material against this baseline should
Front Door Step 3 (and, subsequently, Step 4) be introduced. No telemetry
subsystem is authorized by this amendment; the metrics are captured as a
bounded, one-time measurement exercise using the method the friction record
already specifies, not a new instrumentation mechanism.

=== 4.6 At least one real consumer-repository Run through the Front Door

Per §3.2's consumer-evidence face and `CONC-WFC-LEVEL0-EMPIRICAL-CONFIDENCE`,
the milestone requires at least one real Core-repository or Latin-repository
Run, executed on a current Runtime, using the Front Door as applicable (i.e.
to the extent the Front Door has been built by this point in the sequence),
with its outcome recorded in the same way prior consumer-repository evidence
has been recorded (e.g. the Latin Story-2 foreign-domain dogfood of
2026-09-29, Run `RUN-b57dcdac...`, Runtime `a390ac23`, which itself produced a
defect -- `BUG-WFC-IMMUTABLE-FINDING-ECHO` -- that remains open and is worth
revisiting as part of this Run).

The milestone statement must say explicitly which routes were exercised by
this Run and which were not, and must not imply convergence-escape is proven
unless Convergence Slice 5 has actually run by that point (§3.2).

This also supplies the Front Door's only validation against a use it was not
designed around by its own authors, which is cheap relative to its value.

== 5. Repository/product consolidation before the milestone

Repository consolidation is not a generic "cleanup sprint." It is
productization work with concrete consumer and fresh-agent outcomes, and its
primary task is *repairing* existing authority-classified surfaces that are
currently false or incomplete -- not adding new ones.

=== 5.1 Repair existing authority-classified surfaces first

Two of the repository's existing authority-classified orientation surfaces
are, at this amendment's writing, false or incomplete rather than merely
undiscoverable, and a third current-authority document carries a false
status claim:

* `docs/backlog/README.adoc` is already the canonical backlog orientation
  surface -- `docs/README.adoc` classifies it under *Current authority*,
  "The backlog index records roadmap disposition and intent" -- and it is
  stale. It was last modified 2026-09-22; its `NOW` item is the first
  WFC-on-WFC dogfood, closed in September; it mentions none of P1-P5,
  convergence, Commissioning, the Front Door, successor continuation, or
  operational friction; and it references none of the roughly two dozen
  `BUG-WFC-*`/`FTR-WFC-*` records sitting in its own directory.
* `docs/README.adoc` is already the documentation classification/taxonomy
  surface -- `README.md` calls it "the authoritative classification of
  current documentation" -- and it is incomplete: it classifies neither
  `docs/warm_storage/` (ten documents, including this concept, its review,
  and the only current successor runbook) nor the fourteen unclassified
  top-level `docs/*.adoc` files, including
  `docs/wfc_operator_manual.adoc` (current operator practice) and the
  Projected Result Contracts concept and both its reviews.
* `docs/run-recovery-and-salvage.adoc:172-176` -- also *Current authority* --
  calls `export-salvage`/`prepare-successor` "already-productized" without
  mentioning the open `R1A` carried requirement
  (`docs/backlog/FTR-WFC-SCOPE-ESCALATION-CONTINUATION_implementation_review_004.adoc`).
  `CONC-WFC-ATOMIC-HOP-RECOVERY-WIRING`'s `next_action` forbids describing
  that mechanism as accepted anywhere.

Stale truth in an authority-classified index is strictly worse than a missing
index: a fresh agent following `docs/README.adoc` to
`docs/backlog/README.adoc` gets a confident, wrong answer about what is next.
Repository consolidation therefore *begins* by repairing these three records
(§4.1's A0), not by adding a fourth, fifth, or sixth orientation surface
alongside the four that already exist (`README.md`, `docs/README.adoc`,
`docs/backlog/README.adoc`, Project Memory).

=== 5.2 FTR/bug discoverability: two axes, not one `Status::` line

Feature/Technical Requirement and bug records should have a canonical index
or *generated projection*, not a new hand-maintained registry, that answers
which records exist, their current status, and whether each is current,
superseded, or historical.

This projection cannot be derived from today's free-form `Status::` line
alone, because that line states the *record's own authority* (e.g. "proposed
/ architecture-convergence draft / implementation not authorized"), not the
*mechanism's delivery state*. At this amendment's writing, this produces
concretely wrong inferences for at least three records:

* `FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE` -- `Status:: proposed /
  architecture-convergence draft / implementation not authorized`, while its
  Slices 1-4 are implemented and independently accepted
  (`CONC-WFC-LEVEL0-EMPIRICAL-CONFIDENCE`).
* `FTR-WFC-SCOPE-ESCALATION-CONTINUATION` -- same `Status::` wording, while it
  is implemented and present in `operator.py` at HEAD, and *not*
  independently accepted (`R1A` open).
* `FTR-WFC-ROLE-PERSONA-EXECUTION-BINDING` -- `Status:: proposed MVP
  architecture / documentation only; implementation not authorized by this
  record`, while role-keyed personas and `--role-binding` are live in source
  and in `scripts/wfc_op.py`.

A projection built from `Status::` prose alone would tell a fresh agent that
implemented or partly-implemented mechanisms are unimplemented. Future
discoverability therefore needs two distinct, separately recorded axes per
record: (A) the authority/status of the record itself, and (B) the delivery
state of the mechanism or work it describes. Any generated index must derive
from these explicit reconciled fields once they exist, not infer delivery
state from today's `Status::` prose. The same two-axis need applies to the
bug/defect view (§5.3).

This is a small ontology decision, not a new governance framework. It should
reuse the repository's existing epistemic categories -- implemented/current
reality, accepted architecture, current manual practice, non-authorizing
hypothesis, open design question, open delivery item, superseded/historical --
the same categories Project Memory's `current_summary`/`posture` fields
already use successfully, rather than inventing a parallel vocabulary. Note
that Project Memory already solves this correctly in prose for the concerns it
tracks; the gap is specific to the FTR/BUG record `Status::` field.

=== 5.3 Explicit bug / defect view

Open defects should be discoverable separately from architecture hypotheses
and feature backlog, using the same two-axis distinction as §5.2: a fresh
agent should be able to distinguish known implementation bug, architecture
debt, missing mechanism, rejected/obsolete concern, and expected future
feature, without those categories being inferred from free-form status prose.

Do not force these into one category merely to reduce file count.

=== 5.4 Concept/document taxonomy

The repository should define a clear home and intended authority class for
different records, distinguishing at minimum: current product/architecture
decisions; non-authorizing concepts/hypotheses; independent reviews;
runbooks/current operating procedures; backlog; historical/imported/incubator
material; release/operator documentation; and Project Memory.

This is `docs/README.adoc`'s existing job (§5.1); the work here is repairing
its coverage, not defining a new taxonomy from scratch.

=== 5.5 Repository map

A repository map answering "where do I look for architecture / current
decisions / current backlog / FTRs / bugs / runbooks / operator usage /
Project Memory / self-development governance / source / tests /
historical-incubator material" should be `docs/README.adoc` itself, once
repaired (§5.1), or a projection mechanically generated from its canonical
declarations -- not a new, fifth or sixth, hand-maintained orientation
document. No new canonical state is created by this section.

=== 5.6 Project Memory as a bounded, stronger LLM entry point

Project Memory should become more useful as a compact semantic index into the
repository, helping a fresh agent recover implemented/current reality,
accepted/current decisions, current manual practice, preferred but
non-authorizing hypotheses, open/incomplete work, superseded/historical state,
and durable links to the records that explain each item. The goal is not to
duplicate all architecture records, and no new projection format is
authorized here.

This remains bounded by Project Memory's own design rules:
`project_memory/README.adoc` states it is "*Not a task list.* Concerns are
steering fields, not a backlog; the backlog itself remains
`docs/backlog/README.adoc`", and that its four canonical tables should gain a
fifth "only when concrete evidence shows these four cannot represent the
required memory." Project Memory therefore remains a lean steering index, not
the backlog and not execution authority; delivery state stays owned by
`docs/backlog/`, with Project Memory carrying steering-level status plus
durable links. The current four tables already demonstrate this works: every
fact this amendment cites from Project Memory above was independently
confirmable from those four tables.

One small, currently outstanding repository-truth fix belongs on this
section's list rather than being silently absorbed into general "consolidation
work": `CONC-WFC-MEMORY-PROMOTION-PROTOCOL-PROPORTIONALITY` records a false
blanket claim that no `make` invocation mode including `-j` can act on stale
output, still present at `Makefile:46-47` and in `project_memory/README.adoc`.
Its recorded `next_action` is a two-line wording narrowing, explicitly "Do not
add locking, leases, journals, promotion identity, or transaction machinery."
This concept names the fix as outstanding (§4.1) without making it here,
since it touches `Makefile` and `project_memory/README.adoc`, both outside
this file's scope.

=== 5.7 Fresh-agent acceptance test

Repository consolidation should be tested against a concrete operational
criterion, already recorded as a standing test in
`CONC-WFC-OPERATIONAL-FRICTION-AI-MAINTAINABILITY`'s notes and in
`docs/warm_storage/concepts/workflow_coordinator_operational_friction_evidence_2026-10-11.adoc`
§11 (questions 10-11):

[quote]
____
Can a fresh strong model, given only the repository and a short bounded task
description, identify the relevant current authority, backlog item, design

____

This is a stronger test than merely having complete documentation, and this

== 7. Phase B -- first Level-1 learning

After Level-0 Product Milestone 1, deliberately move upward rather than
immediately adding the next deep Level-0 security/authority capabilities. The
purpose is to gain real evidence from a higher-order consumer.

=== 7.1 Mapping onto the existing Stage 0-3 maturity model

This is not a second stage vocabulary alongside an existing one. The
`docs/warm_storage/concepts/workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc`
§13 maturity model already covers this territory:

* its *Stage 0* ("current manual reference") already lists provider-free
  validation and manual four-file Commission authoring as current -- this is
  where the repository is today, before Front Door Step 1;
* its *Stage 1* ("deterministic successor renderer": validate intent, render
  governing files, run provider-free admission, show exact diff, stop for
  explicit commit/launch authority, no LLM required) is substantially the
  same shape as this concept's Front Door Steps 2-3 (§4.4);
* its *Stage 3* ("bounded Level-1 orchestrator": authorized finite backlog ->
  select next bounded action -> prepare admitted Commission -> invoke Level 0
  -> inspect typed outcome -> archive -> bounded successor or next authorized
  item, with "start with low ceilings... do not begin with an autonomous
  'software company'") is materially the same as this concept's §7.2 first
  Level-1 scope.

Phase B's first bounded Level-1 capability (§7.2) *is* pipeline-target Stage
3, with Stage 3's own recorded prerequisite: "repeated manual/Stage-1/Stage-2
evidence demonstrates that work selection, successor classification,
archive/ledger proposal, and Commission preparation are sufficiently
repetitive and policy-bounded." This concept adopts the pipeline target's
Stage 0-3 vocabulary as the project's one staged model, rather than
maintaining Phase A-D and Stage 0-3 as two parallel, unreconciled
progressions. Phase A-D in this concept describes work *around* the Stage 0-3
progression (repository consolidation, the milestone, kernel consolidation);
it is not a second maturity model for the same thing Stage 0-3 already
measures.

=== 7.2 First Level-1 scope should be narrow

Do not begin by building a general planner.

Likely first useful capabilities are closer to:

* choose the next authorized WorkItem from a bounded backlog;
* classify/select a known task/workflow family;
* construct/request a Commission through the Front Door;
* consume L0 Run outcome;
* interpret simple completion versus typed escalation;
* produce a bounded successor request where existing authority already
  decides the answer.

The exact first slice should be chosen from observed manual coordination
work.

=== 7.3 Open design question: `CommissionIntent` versus `SuccessorIntent`

Two candidate authoring-intent identities currently exist with no
reconciliation anywhere in the repository:

* `SuccessorIntent` -- "semantic input, not a generated Commission"
  (`docs/warm_storage/concepts/workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc`
  §4), already listed among that document's own open questions (§15,
  "SuccessorIntent": "What is the smallest stable semantic schema?");
* `CommissionIntent` -- this concept's §4.4 Step 3, and the amended
  Commissioning concept's canonical-authoring-source hypothesis.

`SuccessorIntent` appears nowhere in the Commissioning concept;
`CommissionIntent` appears nowhere in the pipeline target. Neither existing
record settles whether these are one authoring type, two instances of one
type, or genuinely distinct.

This concept does not invent the answer. It is recorded here as an open
design question, to be resolved -- by whichever record first needs to build
either mechanism -- before either name silently becomes a second lifecycle
identity. Front Door Step 3 (§4.4) must not proceed by assuming an answer to
this question; if Step 3's measurement gate (§4.5) is ever triggered, this
question must be resolved as part of that work, not before it or beside it.

=== 7.4 What we want to learn

Early Level-1 dogfooding should reveal:

* which L0 details still leak through the Front Door;
* which task semantics actually matter above L0;
* which escalations recur;
* what L1 can decide deterministically;
* where human/stakeholder authority remains necessary;
* which Project Memory facts are actually useful to orchestration;
* what progress/status artifacts a stakeholder needs.

This evidence should shape the later kernel refactor (§8).

=== 7.5 Human trajectory

Long term, routine dispatch should move away from the human. This is the same
future direction already recorded, as direction only, in the amended
Commissioning concept
(`workflow_coordinator_commissioning_service_concept_2026-10-11.adoc` §5.4):

[source,text]
----
today:
  human/assistant author and authorize individual execution units

later:
  Level 1 operates inside bounded pre-authorized project envelopes

eventual:
  human behaves more like project sponsor / stakeholder
  and participates at defined checkpoints:
    major scope change
    architecture decision
    risk/authority escalation
    milestone review
    release / deployment / external effect
----

A future Level 1 may generate purpose-built stakeholder artifacts explaining
progress, decisions, risks, evidence, unresolved choices, and upcoming
checkpoints.

This is future direction, not current implementation scope. Two
preconditions the Commissioning concept already records (§5.4, §17) gate any
move along this trajectory: a caller-mediation boundary for above-L0 actors,
and a mechanical -- not merely procedural -- distinction between
maintainer-authorized and agent-produced governing input.

== 8. Phase C -- kernel consolidation before the next complexity wave

After first Level-1 experience, but before adding the next major authority
and information-flow capabilities, perform a deliberate architecture-preserving
Level-0 kernel consolidation.

This concept proposes treating this as a project gate; it is not, by this
concept alone, a governance construct that has been authorized as one.

=== 8.1 Why the refactor is intentionally later

Refactoring immediately after the current milestone's feature line would
optimize the kernel using only bottom-up knowledge. Waiting until a first
Level-1 consumer exists gives evidence from both sides: internal Level-0
coupling/complexity, and actual consumer pressure from above. That should
produce a better refactor target.

This section is independently corroborated by
`docs/backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc`,
which already directs: "exercise real consumers, and improve ergonomics only
from observed use", and explicitly declines to open a cleanup program now.
That record is this phase's governing constraint; §8.3 below states how.

=== 8.2 Kernel Preservation Principle (proposed)

This concept proposes the following principle, in its own voice -- it is this
concept's proposal, not a quotation from an accepted record:

[quote]
____
New Level-0 policy/derivation capabilities should live behind narrow typed
interfaces and should not require cross-cutting modification of the
established Run/Hop execution kernel unless the kernel abstraction itself is
proven insufficient.
____

The goal is that the execution kernel becomes increasingly boring and stable.
This is consistent with
`docs/backlog/FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW.adoc`'s refusal to
"design one workflow stage per privilege aspect."

=== 8.3 Illustration only, subordinate to the existing core/shell boundary

`FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES` already names the
boundary to preserve: a deterministic semantic core (`model.py`, `reducer.py`)
versus a controlled-effect shell spanning `operator.py`, `vertical.py`,
`slice4.py`, `adapter.py`, `codex_adapter.py`, `prompt.py`, `git_facts.py`,
`evidence.py`, `persistence.py`, and `serialization.py`. That record states
explicitly: "This directs feature work; it does not permit package
reorganization", with priority "preserve during real feature work; do not
open a cleanup program", and on `operator.py` specifically: "Breadth alone
does not authorize extraction... Do not add service classes/interfaces merely
for layering aesthetics." It also directs "Do not create a broad
architecture-test project" -- when a real feature touches a load-bearing
boundary, add the cheapest narrow guard that protects it, nothing broader.

This concept does not pre-design the kernel refactor, does not authorize
package reorganization, and does not pre-name service interfaces or classes
as the expected result. Any illustration of a possible internal shape --
for example, separating an execution kernel from isolated policy/derivation
services for assurance, model-capability, capability-envelope, or
information-flow concerns -- is exactly that: an illustration of the kind of
boundary this phase might produce, not a target architecture, not a
decomposition this concept commits to, and explicitly subordinate to the
existing core/shell boundary above. The actual shape should be learned from
Phase B pressure (§7.4), not pre-named here. Characterization work in this
phase should use the narrowest guard needed when a concrete refactor touches a
load-bearing boundary, per the record's own direction -- not a broad
characterization/architecture-test programme.

=== 8.4 Refactor acceptance probes

Use at least two future requirements as architecture probes, applied only
once a concrete refactor is actually proposed in Phase C -- these probes do
not authorize building either capability now, and neither is a Level-0
Product Milestone 1 requirement (§13):

Privileged Git authority escalation::
Can a normal Run stop, obtain separately authorized expanded Git capability,
compile a successor envelope, and attach mandatory defensive review without
cross-cutting edits throughout the Run/Hop kernel? Grounded in
`docs/backlog/FTR-WFC-ELEVATED-PRIVILEGE-DEFENSIVE-REVIEW.adoc`.

Protected/corporate-secret execution::
Can a task stop before disclosure, obtain information-access authorization,
select an eligible execution boundary/model, and continue without embedding
information-flow policy throughout the kernel? Grounded in
`docs/backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc` and
`CONC-WFC-EXECUTION-TRUST-BOUNDARY`. *Passing this probe additionally
requires* that the constrained part of the execution binding be inside the
pinned governing-input digest set before model/provider choice can govern
protected-context disclosure --
`CONC-WFC-EXECUTION-TRUST-BOUNDARY`'s recorded `next_action`: "If
information-flow or model-eligibility policy is ever built, the constrained
part of the execution binding must move inside the pinned governing-input
digest set first: the binding is currently an un-pinned file written from a
CLI flag... a premise that fails the moment a binding choice can decide
whether protected context may be disclosed." A refactor that confines
information-flow policy to an isolated service while leaving the
execution-binding gap open has not satisfied this probe. The mechanism for
closing that gap is left undesigned here, and this precondition does not move
into Phase A or the milestone.

On the model-capability side, for consistency: the amended Commissioning
concept §10.2 establishes that trusted policy may impose a *minimum*
model-capability/assurance class as a floor, with request-side preference
choosing only within the eligible set. §9's "trusted minimum
model-capability/assurance policy" is consistent with this.

If both probes still require invasive edits across unrelated kernel
internals, the refactor has not created the intended boundaries.

=== 8.5 No feature piggybacking

During the kernel-consolidation slice, avoid simultaneously implementing the
new privilege/secret capabilities that motivate it. Preserve existing
behavior first. When a real feature touches a load-bearing boundary, add the
narrowest guard that protects it, per §8.3 -- not a slice-wide
characterization or architecture-test programme.

== 9. Phase D -- post-refactor Level-0 expansion

Only after kernel consolidation should the project deliberately add the next
cross-cutting Level-0 concerns, likely including some subset of:

* privileged Git authority/capability escalation;
* protected/corporate-secret context;
* verified read/visibility containment;
* information-flow/provider compatibility;
* self-hosted/local model eligibility where required;
* trusted minimum model-capability/assurance policy;
* capability-derived mandatory defensive review.

These are not milestone requirements. Their exact order should be decided
from real Level-1 and organizational use cases. `CONC-WFC-EXECUTION-TRUST-BOUNDARY`
is `watching`/`not_now_revisit_on_concrete_need`; this section does not
change that posture.

== 10. Complexity budget

The project should treat complexity as a limited architectural resource.

A new mechanism should answer:

. What repeated real problem does it remove?
. Which existing mechanism can it reuse?
. Does it introduce a second source of truth?
. Does it enlarge the execution kernel?
. Can it be isolated behind a typed port/service?
. Can a fresh agent understand its authority/status from repository records?
. Does it reduce or increase the number of concepts required to launch
  ordinary work?

Prefer:

* generated projections over duplicated hand-authorship;
* narrow deterministic services over cross-cutting conditionals;
* existing Components over new catalog systems;
* explicit open questions over premature mechanisms;
* measured friction over speculative platform design.

== 15. Repository-consolidation principle

The repository should increasingly reflect the fact that `workflow-coordinator`
is now a project in its own right rather than an incidental helper inside
`spreadsheet-handling`.

That does not mean erasing its history. It means making the current product
legible without requiring knowledge of that history.

A successful consolidation preserves provenance while making the current
answer to each ordinary question obvious:

[source,text]
----
What is this project?
What is current?
What is next?
Where is the authority?
Where is the backlog?
Where are the known defects?
Where are the FTRs?
Where are the architectural hypotheses?
How do I operate it?
How do I extend it?
What is intentionally deferred until after the milestone?
----

Per §5.1, the practical first step is repairing the surfaces that already
claim to answer these questions, not adding new ones.

== 17. Provisional conclusion

The project is approaching a useful transition.

The Level-0 execution mechanism has accumulated enough evidence and structure
that the next goal should not be unlimited feature expansion.

First dispose the P3 stop and complete P3.5; assess P4 and P5 against actual
milestone need; build the Commission Front Door only as far as measured
friction justifies; repair the repository's existing authority-classified
surfaces rather than adding new ones; and exercise at least one real
consumer-repository Run through the Front Door before calling the result a
milestone.

Only after that evidence is in hand should PyPI publication be separately
authorized as a release milestone, and only after that should the project
deliberately move upward and learn from a first bounded Level-1 consumer --
the existing pipeline-target Stage 3.

Only with that higher-level evidence in hand should the project perform the
architecture-preserving kernel consolidation, governed by the existing
architectural-core record, needed before introducing the next cross-cutting
authority, privilege, and protected-information features.

The intended trajectory is therefore:

[source,text]
----
repair repository truth
-> dispose P3 / complete P3.5 / assess P4,P5
-> make the kernel consumable, as far as measured friction justifies
-> gather real consumer evidence
-> declare the Level-0 product milestone
-> publish to PyPI, separately, as a release milestone
-> learn from a first bounded Level-1 consumer
-> consolidate the kernel
-> then expand authority/security capability
----
