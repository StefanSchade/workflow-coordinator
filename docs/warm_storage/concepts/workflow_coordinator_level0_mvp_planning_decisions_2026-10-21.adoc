== 1. Level-0 MVP: reach a usable product soon

The maintainer's priority is a reliable, usable Level-0 product reached soon,
rather than continued infrastructure development without a milestone. This
reaffirms the MVP concept's central thesis (§2, §17) and its three-part
milestone definition (§3.2); it narrows *emphasis*, not definition: assess
real MVP necessity before commissioning substantial work (§§2-3 below), and
do not let any single slice's scope grow past what the milestone needs.

After the milestone: publish to PyPI through a separately authorized release
process (unchanged from MVP concept §3.3, §6.3 -- publication remains outside
the milestone boundary), use Level 0 in real work, and let Level-1
architecture mature through experience (unchanged from MVP concept §7).

== 2. P3.5: architecture checkpoint before implementation (pending)

The P3.5 Finding Reachability design
(link:workflow_coordinator_p35_finding_reachability_design_2026-10-18.adoc[design],
as corrected by H001, Development commit `6807d56`) was independently
accepted at H002
(link:workflow_coordinator_p35_finding_reachability_design_2026-10-18_review_003.adoc[review
003], "ACCEPT -- P35DR-002 CLOSED / ADDRESSED. DESIGN ACCEPTED."), Development
commit `b3dbbd9`.

The corrected design's own inventory is load-bearing: under the accepted
ordered-reachability rule, *all 43* currently inventoried schema-v2
self-development profiles are rejected (43 rejections / 0 acceptances;
review 003 §"Inventory, compatibility, and test contract", design
§§6.1, 6.3, 8, 10 item 1). No profile currently passes the static validator
the design specifies.

*Maintainer decision:* before any implementation Commission for this design,
explicitly reconsider the underlying profile/structural-invariant hypothesis
that produces a 43/0 split. A design being independently accepted as
internally correct does not by itself establish that rejecting every current
profile is the right MVP move.

* Do not assume that existing profiles must be migrated to satisfy the
  validator.
* Do not demand backward compatibility for its own sake either: a breaking
  change to the profile corpus is acceptable if the stricter invariant is
  judged justified once reconsidered.
* This is recorded as a *pending architecture decision*, not a resolved
  implementation strategy. No implementation Commission for this design is
  authorized by this record or by the design's acceptance alone.

== 3. P4 and P5: explicit MVP scope assessment

Before commissioning substantial work on either, critically evaluate actual
Level-0 MVP necessity and scope.

* P4 (Coordinator-owned deterministic mechanics/effects) must not
  automatically become a large architectural project merely because
  `docs/wfc_projected_result_contracts_concept_2026-10-07.adoc` §17 allows
  that it "may be a larger refactor." The MVP concept §4.2's existing
  "non-blocking, assessed against milestone need" disposition is reaffirmed,
  not loosened.
* P5 (provider-facing cleanup) remains conditional on demonstrated MVP need,
  per its own governing record and MVP concept §4.2. This record does not
  promote it.

This does not cancel either item's existing authoritative requirements or
lifecycle status (projected-result-contracts §§12-13, §17, §22; MVP concept
§4.2, §12.2-12.3). It sharpens the assessment that was already called for,
before either is commissioned at scale.

== 4. Claude Code adapter: MUST-HAVE for the MVP

The intended corporate deployment environment makes Claude Code support a
*release prerequisite*, not an optional post-MVP enhancement.

This changes the MVP concept's existing disposition. MVP concept §4.2
currently retains the Claude adapter only as "planning direction," citing
`workflow_coordinator_operational_friction_evidence_2026-10-11.adoc` §10's
explicit framing of the P3 -> P3.5 -> P4 -> P5 -> provider-neutrality/Claude
sequence as "a planning observation, not an authorization." This record
raises that from a scheduled-but-optional direction to an in-scope milestone
requirement: the milestone (MVP concept §3.2's Execution face) is not
complete while Claude Code support is missing.

Constraints unchanged from existing architecture:

* Coordinator behavior remains provider-neutral; the existing Codex adapter
  (`src/workflow_coordinator/codex_adapter.py`) is the precedent for shelling
  out rather than importing a provider SDK.
* CLI-specific detail stays inside the adapter, not in `operator.py`,
  `reducer.py`, or other kernel/shell modules named in
  `docs/backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc`.

Sequencing, design, and implementation of the adapter remain separately
authorized; this record only changes its MVP-scope priority, consistent with
the ordering already observed in the friction record and with §3's P4/P5
assessment above (the adapter is MUST-HAVE independent of whether P4/P5 are
deferred).

== 5. Token consumption evidence: observational, in-MVP

Capture available provider-reported token usage per invocation, covering
Codex and Claude, as part of the MVP. This is new scope: no current record
(`docs/wfc_projected_result_contracts_concept_2026-10-07.adoc`,
`docs/warm_storage/concepts/workflow_coordinator_operational_friction_evidence_2026-10-11.adoc`,
or the MVP concept) names token-usage capture anywhere.

Scope, explicitly bounded:

* source/provenance of each figure;
* reported input/output/cache/reasoning usage where the provider reports it;
* missing values represented honestly (absence, not a synthesized zero or
  estimate).

Explicitly out of scope for the MVP:

* no estimated values presented as measurements;
* no token-based policy engine;
* no new LLM telemetry subsystem;
* no unnecessary retention of raw provider transcripts.

This is observational evidence capture, comparable in spirit to the bounded,
one-time friction measurement the MVP concept already authorizes (§4.5) --
not a new instrumentation mechanism or architecture layer.

== 6. Front Door Stage 1: in MVP (today's workflow, documented and reproducible)

Front Door Stage 1 is substantially the workflow already used today:

[source,text]
----
human describes work
-> interactive LLM authors Commission
-> existing deterministic prepare/admission
-> human-authorized launch
-> WFC execution
-> mechanical evidence archiving
----

The MVP needs this workflow *documented and reproducible* by a fresh agent,
not re-architected. New Commission-authoring software is *not* automatically
an MVP prerequisite: existing templates, Components
(`governance/self-development/prompts/`), documentation, and the existing
provider-free preflight (`operator._preflight()`) may already suffice.

Record any small missing pieces based on evidence from actually trying to
reproduce Stage 1 end-to-end, rather than assuming that every step of the MVP
concept's Front Door Steps 1-2 (§4.4) requires new implementation. Where the
MVP concept's Step 1 (populate existing Components) and Step 2 (authoring-time
validator reusing P3.5's composition check, §4.4) are themselves found
necessary by that evidence, they remain governed by that section unchanged;
this decision does not re-author their content, only reframes Stage 1 as "make
today's workflow legible and reproducible first," consistent with MVP concept
§4.4 Step 1's own "zero mechanism" framing and §5.7's fresh-agent acceptance
test.

Note on terminology (see §10): "Stage 1" here is this record's own name for
*today's interactive workflow*. It is not necessarily the same thing as
`workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc`
§13's "Stage 1 -- deterministic successor renderer" (no LLM, by that
document's own definition), even though the MVP concept §7.1 maps its Front
Door Steps onto that same Stage 0-3 vocabulary. This naming collision is not
resolved here.

== 7. Front Door Stage 2: post-MVP direction, potentially the first Level-1 capability

Target sequence, explicitly *post-MVP*:

[source,text]
----
deterministically create a minimal bootstrap Commission
-> WFC-controlled LLM Run authors and reviews the actual Commission
-> separate authority/admission decision
-> prepare and launch the resulting Commission
-> archive all associated Runs
----

The bootstrap step must not itself require an LLM invocation -- this is the
concrete guard against recursive Commission generation (an LLM-authored
process authoring the very Commission that authorizes it).

This is a *direction*, not an approved design or implementation. The
deferral reason is informational, not merely sequencing convenience: real
Stage-1 Level-0 usage should reveal common Commission patterns, operational
friction, exceptions, and authority handoffs, enabling a better and possibly
substantially simpler Stage-2 design than one designed in advance of that
evidence. This mirrors the MVP concept's own stated rationale (§8.1) for
deferring kernel consolidation until after first Level-1 experience, applied
here one level down.

Do not prebuild `CommissionIntent`, a deterministic renderer, a workflow DSL,
or higher-order orchestration into the MVP without that evidence. This is
consistent with the MVP concept's existing non-goals (§14: "a universal
workflow DSL") and with Front Door Step 3/4's own conditionality (§4.4,
§4.5, §4.6's measurement gate), but is stated here independently of whether
that measurement gate is ever triggered: Stage 2 is post-MVP regardless.

Terminology note (see §10): this record's "Stage 2" overlaps, but is not
declared identical to,
`workflow_coordinator_successor_commission_pipeline_target_2026-10-10.adoc`
§13's "Stage 2 -- bounded LLM semantic front-end" and "Stage 3 -- bounded
Level-1 orchestrator," and to the MVP concept §7.3's open
`CommissionIntent`/`SuccessorIntent` question. Whether Front Door Stage 2 as
described here is pipeline-target Stage 2, Stage 3, or a distinct thing that
needs its own name is left as the same kind of open question §7.3 already
records, not newly resolved.

== 8. Repository-local `.wfc/` is a candidate hypothesis, not a storage contract

Consider a repository-local `.wfc/` directory inside the consumer repository
as a conventional place for WFC documentation and durable run archives, with
a separate run-evidence repository (today's actual practice, e.g.
`workflow-coordinator-run-evidence`,
per `docs/wfc_operator_manual.adoc` §"Repositories" and
`docs/run-preparation.adoc`) remaining an explicit, equally valid alternative.

This is a *design hypothesis*, nothing more:

* the active, authoritative Coordinator State must remain outside the
  agent-writable workspace -- this precondition is unchanged and is not
  weakened by considering `.wfc/`;
* archived records are not active runtime authority, whichever location
  holds them;
* a separate Run's final HEAD identity and its archive-commit identity must
  remain distinguishable, exactly as they are today (e.g. the final-HEAD /
  archive-commit pairs already recorded throughout
  `docs/backlog/BUG-WFC-SCOPE-ESCALATION-CONTINUATION-GAP.adoc`).

No new archival schema is specified here, and nothing in this section is
implemented by this record. This is recorded as a candidate for lightweight
MVP integration worth evaluating, not a decision to build it.

== 9. MVP completion

Reaffirms, without narrowing, the MVP concept's own completion questions
(§13): meaningful consumer-repository dogfooding (§3.2 consumer-evidence
face, §4.6), a documented and usable operating workflow (§5, §5.7, and §6
above for Front Door Stage 1), and release hardening and supported-provider
validation -- which now explicitly includes Claude Code (§4 above) alongside
Codex.

Level-0 product readiness (this milestone) remains distinct from the later,
separately authorized PyPI publication (MVP concept §3.3, §6.3), unchanged.
