  36-38 say the in-process scenarios drive a seam "which still launches the
  real engine as a real subprocess for every Hop". The lifecycle launches the

  one `launch_spawned` journal record for scenario (b)'s whole five-Hop Run,

  in a real separate process for every Hop of the Run, not a fake -- is true,
  and nothing fake is described as real, so this is wording, not a false
  honesty claim. "launches the real engine as a real subprocess, which then
  executes every Hop (the provider itself is launched once per Hop)" would
  be exact.

  says.* `_wfc_on_path`'s docstring (lines 104-113) explains the `PATH`

  `lifecycle._default_engine_command` first tries

  *is* installed next to the running interpreter, the inner engine is that

  permits ("the real installed or in-repository `wfc` entry point") and
  which is arguably stronger, but it means the docstring's "both via the
  in-repository entry-point shim" holds only where no such sibling exists
  (as in this sandbox, where I verified both resolutions are absent). One
  clause naming the sibling check would make the claim unconditional.

  checks `hop_used`, `anomalies`, the Finding projection and the archived
  `audit.json`, and the commits do exist (above). An assertion that each
  Hop's `actual_commits` has exactly one entry, or that the five subjects
  are in the consumer `HEAD` history, would make the "Coordinator-owned
  commits" half of task item (b) explicit in the test instead of implicit in
  the product's refusal path.

  H002's, items 1 (weak `commits` assertion, refined above), 3 (`_attempt_dir`
  ignores its `repo` argument), 4 (the docstring names only
  `run_lifecycle`/`resume_lifecycle` although (d) drives

the task asks for: byte-identical `audit.json` *and* `manifest.json`,
`git rev-list --count HEAD` unchanged, and exactly one `ext.archive.result`
fact whose outcome is `no_op`.

*Scenario (e) refuses and stops fail-closed.* The failing-evidence test
asserts the `refused_probe` classification, that the consumer `HEAD` did not
move (no Commission commit), that no attempt directory exists (no provider
ran) and that the Evidence repository still has only `wfc init`'s own
commit. The malformed-provider test is parametrized over a non-JSON payload
and a schema-violating envelope, and asserts `reconcile_required`, exit
`12`, `hops[0].outcome == "uncertain"` and `hops[0].actual_commits == []`.

*The docstring is honest about the one thing that matters most.* It states
in its first paragraph that this is not live Beta qualification, that every
provider call is answered by a scripted fixture, that no conclusion about a
real adapter may be drawn, and that the live per-adapter qualification and
the Claude record reconciliation are maintainer-owned and not attempted
here. That is exactly the "do not infer a live result from a fake provider"
requirement of both backlog sections.

*Proportion and separation.* Five groups, eight independent test functions,
one regression cannot hide another, ~11 s wall clock for the file, no sleep,
no retry loop, no network. The in-process seam is the same
`L._ENGINE_COMMAND` override `tests/unit/test_postrun_lifecycle.py` already
uses, and it is used here against the *real* engine rather than that test's
fake engine, so the candidate is strictly stronger than the pattern it
reuses.

=== Blocking Finding 1 -- scenario (a) never runs `wfc audit`, but its name and the module docstring say it does

The task's scenario (a) enumerates the commands the happy path must cover:
"`wfc init`-style config, plan preview, `run` with `--yes` (the unattended,
scripted path), `status`, `audit`, `report` and the automatic archive into a
separate disposable Evidence repository". `audit` is a real Front Door
command with its own argument parsing, its own refusal paths and its own
exit codes (`frontdoor/cli.py:27-29` dispatching `frontdoor/audit.py:565`,
which prints `AUDIT: <path>` and returns `0`, `2` or `3`).

The candidate never invokes it. Every `audit` occurrence in
`tests/integration/test_beta_e2e_fake_provider.py` is either the word in a
name or comment, or a read of the `audit.json` file the *archive* path
already wrote (lines 24, 215, 219, 224, 294-306, 387, 512, 523). The
subprocess chain actually executed is `init`, `plan`, `run --yes`, `status`,
`report`.

Two statements in the candidate assert otherwise:

* the test function name
  `test_happy_path_cli_init_plan_run_yes_status_audit_report_archives_automatically`
  (line 219) and its mutation comment "anywhere along the
  init/plan/run/status/audit/report chain" (line 224);
* the module docstring's scenario-(a) paragraph, "once as the outer CLI
  (``init``/``plan``/``run --yes``/``status``/``audit``/``report``)"
  (lines 22-24), under a heading that promises to say exactly which parts
  are real.

So this is both an uncovered item of an explicit acceptance criterion and a
false statement in a *permanent* acceptance test's own name and docstring --
the artifact a maintainer will read as the record of what BP9's automated
part proves. The task names docstring honesty as an acceptance criterion in
its own right, and `audit` is not a formality here: it is the command the
Operator Manual's recovery path uses to project an Attempt by hand.

I checked that this is a real omission and not a missing product mechanism,
because the task requires reporting a gap rather than inventing a mechanism:

* `wfc audit <attempt-dir>` on the already-archived attempt exits `2` with
  "refusing to overwrite existing audit.json with different content". That
  is correct, fail-closed product behavior: the postrun projection is
  written *with* lifecycle facts (`postrun.py:221`,
  `{"classification": ..., "preservation": ...}`) and a bare CLI call
  supplies none, so the projections legitimately differ.
* `wfc audit <attempt-dir> --lifecycle-json <facts>` with those same facts
  exits `0`, prints `AUDIT: <path>`, reproduces the archived `audit.json`
  byte for byte and leaves the Evidence repository clean. I reproduced this
  in a throwaway copy of the candidate as a four-line addition to scenario
  (a); it passed, and the rest of the file still passed.

*Correction shape (bounded, any one of these):*

. Add the real invocation to scenario (a): write the lifecycle facts to a
  file under `tmp_path`, run `wfc audit <attempt-dir> --lifecycle-json ...`
  as a subprocess, and assert exit `0`, the printed `AUDIT:` line, the
  byte-identical `audit.json` and a still-clean Evidence repository. This
  also kills a new mutation (a lifecycle-aware projection that is not
  reproducible from the placed manifest), so it strengthens the group.
. Or cover both faces: the bare call's honest `2` refusal *and* one
  successful `--lifecycle-json` projection, which additionally documents the
  manual-projection contract an operator meets in recovery.
. Or, if the maintainer prefers the scenario to stay a pure black-box
  success path, drop `audit` from the test name, the mutation comment and
  the docstring chain, and state plainly in the docstring that `wfc audit`
  is deliberately not part of this scenario and why -- but note that this
  leaves an enumerated acceptance item uncovered and is therefore a
  maintainer decision, not a Worker one.

The first shape is the one I verified end to end.

=== Non-blocking observations (H002; recorded only, no Finding proposed)

. *The happy path's "commits" assertion is weaker than it looks.* Lines
  304-306 assert only that the `commits` line of `wfc report` does not
  contain "none". With the trusted-commit boundary disabled entirely
  (mutation 8 above) scenario (a) still passes, because the line then shows
  the Commission commit. The property is covered by (b), (c) and (d), so
  nothing is lost; a direct assertion that the provider's `src/app.txt`
  change is present in the consumer `HEAD` tree, or that
  `hops[0].actual_commits` has exactly one entry with the expected subject,
  would make (a) carry its own weight and would simplify the expression.
. *The Hop-ceiling scenario is protected by two product guards.* Only
  mutating both `reducer.py` ceiling checks together makes
  `test_hop_ceiling_stop...` fail. The test is sensitive to the mechanism;
  the redundancy is in the product. Worth knowing before anyone reads a
  surviving single-guard mutation as a test defect.
. *`_attempt_dir(evidence_path, repo, run_id)` ignores its `repo`
  argument* (line 208) and relies on the `repository_name="consumer-repo"`
  default, which happens to match `_seed_repository`'s default. A second
  consumer repository name would silently compute the wrong attempt path.
  Either use `repo.name` or drop the unused parameter.
. *The docstring's (b)-(e) sentence is slightly broader than the code.*
  Scenario (d) drives `L._prepare_checkout`/`L._authorize`/`L._advance`
  before `resume_lifecycle`, and scenario (e)'s first case expects
  `LifecycleError` out of `run_lifecycle`; the docstring names only
  `run_lifecycle`/`resume_lifecycle`. One clause naming the private
  prepare/advance seam, which is what makes the interruption simulation
  possible, would complete an otherwise exemplary "what is real" section.
. *`os.environ` is mutated directly* for `WFC_BP9_SCRIPT` in the in-process
  tests (always under `try`/`finally`) rather than through `monkeypatch`.
  This matches `tests/unit/test_postrun_lifecycle.py`'s existing style, so
  it is consistent; `monkeypatch.setenv` would be leak-proof even on a hard
  interruption.
. *Scenario (c) checks classifications and exit codes but not the operator
  text.* Neither stop test looks at what `wfc status`/`wfc report` *print*.
  The reporting layer has its own honesty rules (`report.py:147-148`,
  "status is unknown -- not reported as success"), and a one-line assertion
  that the stop classification appears in a rendered report would close the
  "reported honestly" half of the requirement at the layer a user sees.
. *The quickstart document and the live/installed-wheel qualification named
  by BP9 are untouched, correctly.* The Commission scopes only the
  automated fake-provider part; the backlog's Goal/Acceptance items for the
  two-page quickstart, the per-adapter live qualification and the Claude
  record reconciliation remain open and maintainer-owned. BP9 is not closed
  by this candidate and the candidate does not claim otherwise.

=== Evidence and agent-local limitation (H002)

Agent-side verification used read-only Git inspection, source reading,
`ruff check`, whole-suite `--collect-only`, repeated execution of the
candidate file in explicit partial mode, and eight single-point product
mutations applied to a throwaway copy of the tree outside the reviewed
checkout. The reviewed worktree was never modified; `git status` is
unchanged apart from pre-existing untracked dotfiles.

The required-mode suite (`python -m pytest -q` with
`WFC_TEST_INPUTS`/`WFC_TEST_PROFILE`) could *not* be executed here: the
verified offline wheel bundle is not reachable from this sandbox, and
`conftest.py` correctly fails configuration rather than skipping or
reaching for an index. The structural precondition was therefore proved
instead -- an inert whole-suite collection selects all 8 new tests, with no
marker and no partial-mode dependency -- and the authoritative answer
remains the Coordinator's own `task-check` for this Hop. Separately,
`tests/unit/test_claude_adapter_conformance.py` fails 12 tests in this
sandbox with `OSError: [Errno 30] Read-only file system` while creating the
adapter's short `/tmp` scratch symlink; that is this sandbox's filesystem
policy, is unrelated to the candidate (which touches no adapter code) and is
not reported as a defect. `pytest` is not importable by the system
interpreter; a pre-existing virtual environment reachable from this sandbox
was used, and no dependency was downloaded. None of these limitations
affects the blocking Finding, which is reproducible by reading the candidate
and was additionally confirmed by executing the corrected shape.
