== Verdict

*changes_required.* One blocking Finding (BF-2 below).

Every behavioural property the historical BP6b Commission's fifteen
acceptance cases name was independently reproduced at this HEAD with real
Git in disposable Evidence repositories and *holds*. 356 reviewer-owned
checks passed, with zero behavioural failures. `raw_retention=None` is
byte-identical to the baseline against the real baseline code. No private
string reaches Evidence history in `local` or `discard`.

The blocking Finding is again not a behavioural defect. It is a reproduced
violation of the acceptance list's own explicit standard -- "Each case has a
mutation-sensitive test" -- on the *sibling occurrence* of exactly the guard
F001 named: the placed-`audit.json` reprojection check on the
*crash-resume* branch of `_resume_or_noop_kept_raw`. F001 named the
occurrence in the *already-committed no-op* branch, which H003 duly covered;
the resume-branch occurrence was never named and is still the only guarded
BP6b behaviour whose removal survives the entire archive/audit/report suite.
Its consequence is strictly worse than the one F001 was raised for: the
mutant does not merely mis-report "up to date", it *commits a forged
`audit.json`* as the Attempt's durable evidence record and reports
`ARCHIVED` with exit 0.

=== Method

Independent reproduction, not re-reading of the Worker's report or of the
H002/H004 artifacts. A reviewer-owned harness (deliberately *not* the
project's own test fixtures, with its own canary private strings the product
test suite has never seen) built disposable Run state roots, OPS

== Blocking Finding

=== BF-2 -- the placed-`audit.json` re-verification on the crash-resume path has no test, and its removal commits forged evidence

*Invariant.* BP6b acceptance case 9 requires a mutation-sensitive test for
the crash-resume and tamper-refusal behaviour of `local`/`commit`
retention ("crash between placement and commit resumes per mode ...; tamper
refusal in `local`/`commit`"), under the acceptance list's own standing
standard "Each case has a mutation-sensitive test". The placed-`audit.json`
reprojection re-verification on the *resume* branch of
`_resume_or_noop_kept_raw` is the guard that enforces it for the one file
every retention mode commits, and it has no test.

*The two occurrences.* `_resume_or_noop_kept_raw`
(`src/workflow_coordinator/frontdoor/archive.py`) contains the same
reprojection comparison twice:

* `archive.py:1221` (8-space indent), inside the already-committed no-op
  branch. This is the occurrence historical Finding F001 item (5) named;
  H003 covered it with
  `LocalRetentionTests::test_tampered_but_committed_audit_json_is_not_silently_treated_as_up_to_date`,
  and the mutation `noop-audit-reprojection-off` is now detected.
* `archive.py:1243` (4-space indent), on the *crash-resume* branch, reached
  when the placement exists but was never committed. *No test covers this
  one.* It was never named by F001, so the H003 correction could not have
  addressed it.

The two strings differ only in indentation, which is why a substring-based
mutation probe silently conflates them; anchoring on the newline plus exact
indentation isolates the resume-branch occurrence.

*Reproduction (r5b, then r8).* Replacing *only* the 4-space occurrence with
`if False:` on a disposable copy of `src/`, `tests/`, `scripts/` and
`pyproject.toml` leaves the entire twelve-file archive/audit/report suite
*passing*. The probe machinery is the same one `r5_mutations.py` validated at
the start of its run -- the unmutated copy of that identical preparation
passes the suite, and 28 of 29 mutations through it are detected -- so a pass
here means the mutation is genuinely unnoticed, not that the harness failed
to apply it; the exact-anchor occurrence count is asserted to be 1 before
the rewrite.

The behavioural consequence was then established directly, with the real
product and the mutant run over the identical scenario:

. archive with `--raw-retention local` (and separately `commit`), crashing
  between the atomic placement and the single commit;
. tamper *only* the placed `audit.json` -- here by rewriting `attempt_id` to
  `wfc-FORGED-ATTEMPT-ID` -- leaving `manifest.json` and every placed raw
  file byte-identical and self-consistent, so BP5's
  `_verify_resumable_placement` (which re-verifies only manifest-recorded
  `copied_files`) cannot see it;
. resume.

*The real product refuses*, in both modes: `ArchiveError`, "placed
audit.json at ... does not match a projection of its own manifest; refusing
to commit a mismatched or tampered archive", commit count still 1.

*The mutant reports `archived`*, in both modes, makes the commit, and
`git show HEAD:<dest>/audit.json` contains `attempt_id:
wfc-FORGED-ATTEMPT-ID`. In `local` mode `audit.json` is the *only* tracked
file, so the forged record becomes the Attempt's entire durable evidence.

*Why this is blocking.* It is a reproduced violation of the acceptance
list's explicit mutation-sensitivity standard, on the same function, the
same guard kind and the same acceptance case as the already-admitted and
resolved F001 -- with a strictly more severe consequence. F001's
no-op-branch mutant mis-reports "up to date" and commits nothing further;
this mutant commits forged durable evidence while reporting success, which
is the exact false-success class this Commission exists to close. The
asymmetry is also visible inside the product's own test set: the analogous
audit comparison is tested for `discard`
(`test_different_audit_is_refused_not_overwritten`) and for the
already-committed `local` branch, but not for the `local`/`commit` resume
branch. The product *behaves correctly today*; this is a test gap on a path
that carries the evidence-integrity promise, and it is the only guarded BP6b
behaviour whose removal the suite does not notice.

*Correction, already authorized and purely additive.* Add one
mutation-sensitive test per mode to `tests/unit/test_archive_retention.py`
(in scope, already extended by H003) or to the in-scope
`tests/unit/test_bp6b_final_assurance.py` leaf, reusing the crash simulation
the three passing resume tests already use (patching
`_commit_retention_archive` to raise): crash between placement and commit,
tamper only the placed `audit.json`, assert the resume exits non-zero with
the "does not match a projection of its own manifest" reason and that
`git rev-list --count HEAD` is unchanged. No product byte, no audit schema,
no lifecycle change, and no test weakened. The Commission's hop budget is 10
and this is H005, so a correction plus focused review fits.

== Non-blocking observations

Recorded here and in the Hop summary only; `finding_authority: [resolve]`
does not authorize residual transitions, so none of these is a Finding, and
none should be acted on under this Commission.

. *The legacy `None` path reports success against a retention-aware
  destination (H002 observation 1 -- reproduced).* After a successful
  `--raw-retention local` archive, `wfc archive` with *no* `--raw-retention`
  against the same Attempt exits 0 and prints `ARCHIVE ALREADY UP TO DATE`,
  while `git ls-tree -r HEAD` under that destination contains only
  `audit.json` -- the raw files the legacy path is responsible for
  committing are not in Git. Nothing is corrupted: no commit is made, no raw
  byte is committed, no private string enters history, the worktree stays
  clean. The cause is that `_path_is_tracked_clean` asks whether *anything*
  under the destination is in `HEAD`, not whether the leaves this invocation
  intends to commit are. The reverse order (legacy destination, then
  `--raw-retention local`) is correctly *refused*. This mixes the legacy path
  with a retention-aware destination, which the acceptance list never does
  and the limitations record warns against ("A production caller ... is
  expected to always supply one explicitly, never fall back to `None`"). It
  does not falsify the record's F001 claim, which this review re-confirmed.
. *`wfc init`'s bootstrap commit is not rolled back on failure (H002
  observation 3 -- now reproduced, not merely read from code).* With a
  `HOME` whose `.gitconfig` sets an empty Git identity -- the realistic way a
  first-time user hits this, since `_trusted_bootstrap_environment` strips
  every `GIT_*` variable so `GIT_AUTHOR_*` cannot supply one -- the commit
  step fails. The failure is reported as a named `CommissionError`, not a
  traceback, but `.git`, `.gitignore` and `archive/` remain, and the *next*
  `ensure_evidence_repository` adopts that commit-less repository as
  "reused". A later `wfc archive` against it then refuses cleanly (exit 1,
  no traceback), though the message is raw Git ("fatal: ambiguous argument
  'HEAD'") rather than a product-level explanation.
. *Mode switching refuses without naming the real cause.* All four switches
  exercised refuse, make no further commit and never report "up to date".
  `local` then `commit` is refused with "placed audit.json does not match a
  projection of its own manifest" -- true (the placed audit records
  `raw.retention: local`) but it names the symptom rather than the retention
  switch. Kinder messages are a BP6c concern.
. *`--dry-run` with `--raw-retention` previews the BP5 plan only.* It
  reports `DRY RUN -- NOTHING WRITTEN`, writes nothing and commits nothing,
  but neither mentions `audit.json` nor exercises the retention-specific
  pre-write refusals (`.gitignore` coverage, `audit.json` exclusion), so a
