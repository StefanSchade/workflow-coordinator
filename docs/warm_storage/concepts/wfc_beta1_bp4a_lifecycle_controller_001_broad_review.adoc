=== Method

Three kinds of evidence were produced.

. *Real-process reproductions* through `frontdoor.cli:main` in freshly spawned
  processes (non-TTY stdin and stdout), against disposable, from-scratch,
  non-WFC consumer repositories created the same way the BP4a fixtures create
  them, with the *real* engine for the happy path and the fake-engine fixture
  for pinned interruption points.
. *Mutation testing of the suite itself.* The product tree was copied to a
  scratch workspace, one guarded behaviour at a time was removed there, and
  the three BP4a test modules were run against the mutated copy (the copy's
  own `src` first on `sys.path`, so its fixtures and spawned subprocesses also
  resolve to the mutated code). A guard that no test detects is a matrix case
  the suite does not really pin. Fourteen mutations were applied; the results
  are tabulated below.
. *Source reading* of the controller, the journal, the unchanged commit
  primitive, the engine's start/persistence order and the adapters'
  process-spawning flags.

== Blocking Finding B3 (H005): a crash inside the Commission commit, after `git add` and before `git commit`, wedges `resume` permanently and commits zero times

Acceptance case (6) requires: "crash before Commission commit: `resume` commits
exactly once."

=== The window

`_do_commit` journals `commission_commit_intent` (`lifecycle.py:471`),
materialises the compiled Commission (`lifecycle.py:483`) and then calls the
unmodified `bounded_path_commit` (`lifecycle.py:486-489`). That primitive is
not atomic: it runs `git add -- <paths>` (`git_facts.py:879`) and then *three
further Git subprocesses* -- `_staged_paths`, `_staged_non_regular_paths` and
`rev-parse HEAD` (`git_facts.py:882-891`) -- before `git commit`
(`git_facts.py:893`). A process death anywhere in that window leaves the nine
Commission leaves staged in the index.

On the next `resume`, `_do_commit` is re-entered from the top. HEAD still
equals `base_head`, so the adoption branch is skipped; `_materialize_commission`
correctly tolerates its own byte-identical leftovers; and `bounded_path_commit`
then refuses at its own `if _staged_paths(identity): raise
TrustedCommitError("pre-existing staged state")` (`git_facts.py:868-869`).
`_do_commit` maps that to `LifecycleError(..., classification="refused_prelaunch")`
(`lifecycle.py:490-491`).

This window is not exotic. It is also reachable by an ordinary `Ctrl-C`:
`cmd_run`/`cmd_resume` catch only `(LifecycleError, CommissionError,
GitPreflightError, JournalError, OSError)` (`lifecycle.py:922`,
`lifecycle.py:935`), so a `KeyboardInterrupt` in the commit step unwinds the
process and leaves exactly this state.

=== Reproduced

A real, unmaskable `os._exit(137)` was injected at exactly that point -- after
the real `git add -- <paths>` that `bounded_path_commit` performs, before its
`git commit` -- in a disposable consumer repository; every subsequent command
ran as a brand-new process through `frontdoor.cli:main`:

[source,text]
----
crash process               -> exit 137, 9 paths staged
journal after the crash     -> authorize_intent, authorized, prelaunch_intent,
                               prelaunch_passed, probe_intent, probe_passed,
                               commission_commit_intent
HEAD                        -> 53d8613e... (unmoved)
commission commits          -> []

fresh-process resume 0      -> exit 22 | wfc resume: Commission commit refused:
                                         pre-existing staged state
fresh-process resume 1      -> exit 22 | (identical)
fresh-process resume 2      -> exit 22 | (identical)
fresh-process status        -> exit 0  | CLASSIFICATION: not_launched
                                         MESSAGE: authorized; launch not yet reached
fresh-process run --yes     -> exit 26 | wfc run: a lifecycle already exists for
                                         this checkout; use `wfc resume`

commission commits (final)  -> []
index (final)               -> 9 staged additions under .wfc/governance/<id>/
journal (final)             -> ... commission_commit_intent x3
----

=== Why this is blocking

* The lifecycle commits *zero* times, not once, and there is no path forward:
  `resume` refuses identically forever and `run` refuses with
  `refused_active_lifecycle`. The durable journal, whose whole purpose is to
  let the next `resume` finish the mechanics, fails at the one boundary it
  explicitly records with `commission_commit_intent`.
* The reported classification is wrong, not merely unhelpful.
  `refused_prelaunch` (exit 22) states that a pre-launch check failed; nothing
  pre-launch failed. `Deliver` item 7 asks for distinct, documented exit codes
  and the module's own contract is "a truthful, step-bounded refusal".
* `status` compounds it by reporting `not_launched` ("authorized; launch not
  yet reached"), which says nothing about the staged index the operator must
  repair by hand.
* The index is explicitly inside the acceptance model: case (1) names
  "HEAD/index/worktree" as the state that must be left unchanged.
* This is the same failure mode, at the immediately adjacent instruction, that
  was already accepted as blocking and corrected in H003. The H003 correction
  moved the wedge one call deeper rather than removing it; the candidate's new
  case-(6) regression test stops at `bounded_path_commit`'s doorstep
  (`tests/unit/test_lifecycle_crash_matrix.py:224-252` replaces the whole
  primitive), so the boundary inside it remains untested.

=== Correction sketch (no withheld authority required)

`bounded_path_commit` and `git_facts.py` must not change, and they do not need
to. The fix lives entirely inside `_do_commit`, on the re-entry path that a
journaled `commission_commit_intent` already identifies: before calling the
primitive, read `git diff --cached --name-only`; if the staged set is a subset
of this lifecycle's own intent paths, every staged entry is an addition whose
blob equals the expected text, and nothing else is staged, unstage exactly
those paths (`git restore --staged -- <paths>`) and proceed -- the primitive
then behaves exactly as on a first attempt. Anything else staged is a genuine
contradiction and should refuse as `inconsistent` (exit 18) with the staged
paths named, never as `refused_prelaunch`, and never auto-cleaned. A
crash-matrix test injected at this exact boundary (after the real `git add`,
before the real `git commit`) should accompany it.

If the maintainer prefers not to let the controller touch the index at all,
the minimum honest alternative is to detect the condition and refuse as
`inconsistent` with an actionable message -- but that still leaves acceptance
case (6) unmet for this window, so it is a maintainer decision rather than a
correction.

N9:: *The ownership lock leaks on non-`LifecycleError` exceptions.* `_advance`
releases the lock only in `except LifecycleError`. The `TrustedCommitError`
path is converted and therefore safe, but a stray `CommissionError`,
`GitPreflightError`, `OSError` or `UnicodeDecodeError` between acquisition and
launch leaves the fd open. In the one-shot CLI this is harmless (the fd dies
with the process); an in-process caller observes it as a false "active
lifecycle already running". A `finally`-based release would remove the hazard.

N10:: *Every refused re-attempt appends another `commission_commit_intent`.*
Observed three identical intent records with no completion record in the B3
reproduction. The write-ahead record is meant to mark "one intent per attempted
effect"; a reader cannot now tell three crashed attempts from three refusals.
No current decision depends on the count, so this is cosmetic today.

N11:: *The bounded relaunch path does not re-verify the execution bindings.*
On the main path `verify_commission` does check
`sha256(envelope.text) == envelope.digest` (`frontdoor/verify.py:94-95`), so a

`launch_failed_no_engine` relaunch in `_continue_after_launch` goes straight to
`_do_launch` and re-verifies only the package identity and the executable
sha256, not the cached bindings text. The state directory is inside the
operator's own trust domain (a tamperer could equally rewrite the journal), so
this is noted rather than treated as a gap.

=== Blocking Finding B1: a crash between materialising the Commission files and `bounded_path_commit` wedges `resume` permanently

Acceptance case (6) requires: "crash before Commission commit: resume commits
exactly once."

`lifecycle._do_commit` journals `commission_commit_intent`
(`lifecycle.py:451`), then materialises the compiled Commission into the
worktree with `compiled.write_to(repository, overwrite=False)`
(`lifecycle.py:463`) and writes the request leaf, and only then calls
`bounded_path_commit` (`lifecycle.py:466`). The window between those two
effects is real: nine files are written, then `bounded_path_commit` runs a
dozen Git subprocesses. A crash anywhere inside it is exactly the step
boundary the write-ahead `commission_commit_intent` record exists to mark.

On `resume`, `_do_commit` is re-entered from the top. `facts.head` still
equals `base_head`, so the adoption branch is skipped and
`compiled.write_to(..., overwrite=False)` is called again -- against files
that already exist with identical content. It raises `CommissionError`, which
is *not* a `LifecycleError`, so it escapes `_advance` uncaught and
`cmd_resume` maps it to the default `refused_prelaunch`.

Reproduced, with the crash injected strictly between the two effects and
every `resume` run as a fresh process:

[source,text]
----
journal kinds: ['authorize_intent', 'authorized', 'prelaunch_intent',
                'prelaunch_passed', 'probe_intent', 'probe_passed',
                'commission_commit_intent']

fresh-process resume 0 -> exit 22 | wfc resume: refusing to overwrite existing
                                    compiled file: .wfc/governance/bp4-probe/work-item.yaml
fresh-process resume 1 -> exit 22 | (identical)
fresh-process resume 2 -> exit 22 | (identical)
status                 -> exit 0  | CLASSIFICATION: not_launched
commission commits: []
----

A fresh `wfc run` is refused with `refused_active_lifecycle` (exit 26), so
there is no path forward at all. The lifecycle commits *zero* times, not
once; the operator is left with nine untracked `.wfc/governance/<id>/**`
leaves, a message that names an internal compiler invariant rather than a
lifecycle state, a classification (`refused_prelaunch`) that does not
describe what happened, and no journaled recovery. This is the single worst
outcome in the matrix -- a durable journal whose whole purpose is to make the
next `resume` able to finish the mechanics, failing at the one boundary it
explicitly records.

The candidate's own case-(6) test
(`test_resume_after_crash_before_commit_commits_exactly_once`) injects the
crash *before* `_do_commit` is entered at all, so it never reaches this
boundary; the task's "crash injection at every step boundary" is not met here.

The correction is narrow and needs no withheld authority. With the files
already materialised and `write_to` skipped, the existing unmodified
`bounded_path_commit` accepts them directly -- verified in that Hop:

[source,text]
----
commit succeeded on already-materialized files: caef43ffabb9
----

(`bounded_path_commit` already refuses any path that exists at `base_head`,
any unexpected dirty path and any pre-existing staged state, so re-entry is
guarded by the primitive itself.) The fix therefore lives entirely inside
`_do_commit`: make materialisation idempotent for byte-identical content, or
consult `commission_commit_intent` before re-materialising -- plus a test
that injects the crash at this exact boundary.

=== Blocking Finding B2: the legacy `wfc status --state-root=<path>` form no longer reaches the operator

Acceptance case (19) requires that legacy `wfc status --state-root` "behave as
before" and that the new status be "dispatched only without `--state-root`".

The dispatch guard is a bare token test:

[source,python]
----
if args[:1] == ['status'] and '--state-root' not in args[1:]:
----

`argparse` accepts `--state-root=<value>` as an equivalent spelling, and the
legacy operator status parser is a plain `argparse` subparser
(`operator.py:280-281`), so the equals form is a valid legacy invocation. It
contains no bare `--state-root` token, so the guard misses it and the
invocation is captured by the new lifecycle status, which has no such option.

Reproduced against a real state root produced by the fake engine, through
`frontdoor.cli:main`:

[source,text]
----
candidate (1a2fede):
  status --state-root <path>  -> exit 0, operator JSON report on stdout
  status --state-root=<path>  -> exit 2, "wfc status: error: unrecognized
                                 arguments: --state-root=<path>"

baseline (9ebd04d):
  status --state-root <path>  -> operator path
  status --state-root=<path>  -> operator path
----

So a legacy invocation that worked at the baseline now dies with an argparse
usage error instead of producing the operator's status report. The behaviour
difference is functional, not cosmetic. The candidate's legacy-status test
exercises only the space-separated form, so the suite does not catch it.

Correction: treat an argument equal to `--state-root` *or* starting with
`--state-root=` as the legacy marker, and cover both spellings in the
dispatch test.

=== Non-blocking observations (H002)

O1:: *`ext.*` is not actually reserved, and status does not report it.*
`Deliver` item 3 requires that `ext.*` records be "shown only as a count by
status". `journal.py` contains no mention of the `ext.*` namespace at all and
no schema-version marker in the record payload; the records are ignored for
decisions only incidentally, because `Journal.latest` happens to be
kind-filtered. `status` prints nothing about them -- reproduced: after
appending two `ext.*` records, `wfc status` output is unchanged. Acceptance
case (17) (opaque, ignored, accepted after `classified`) *is* satisfied; only
the count and the explicit namespace reservation are missing.

O2:: *Acceptance case (10) and `Deliver` item 5 read differently, and the
candidate follows item 5.* Case (10) says "`launch_intent` with lock held:
`engine_active`"; item 5 says a `launch_intent` without a spawned/failed
record "is `uncertain_launch`: refuse, no spawn, *regardless of lock or
state-root status*". The candidate implements item 5 -- reproduced:
`launch_intent` + lock held yields `uncertain_launch` from both `status` and
`resume`. This is recorded as an observation rather than a Finding because
the two task statements cannot both be satisfied, because the implemented
reading is the safety-conservative one (it makes no claim stronger than it
can prove and spawns nothing either way), because it matches DG-3's
"refuse honestly" stance, and because it is explicitly documented in the
limitations record. Under the alternative reading of case (10) as
"`launch_spawned` with lock held", the behaviour is implemented and tested by
the real-kill test for case (11). *The maintainer should confirm which reading
governs*; if case (10) is meant literally, this becomes a correction.

O3:: *Three matrix behaviours are correct but untested.* The prelaunch
moved-HEAD refusal (part of case 3), the unresolvable probe executable (part
of case 4) and the package-identity change (half of case 15, where only the
executable sha256 is pinned) were each driven by hand in that Hop and
produced `refused_prelaunch`, `refused_probe` and `refused_identity_changed`
respectively. The matrix preamble asks for a test per case; these lack one.
The no-TTY detection inside `_make_confirm` is likewise only covered through
the CLI end-to-end path, not by a unit test.

O4:: *The candidate adds nine `ruff` findings.* `ruff check .` reports 11
errors at `1a2fede` versus 2 at the baseline `9ebd04d`: one `F401` in
`frontdoor/journal.py` (`typing.Iterator`), one `F401` in
`tests/fixtures/bp4/fake_engine.py` (`json`), and seven `F841` unused locals
across the two new lifecycle test files. `make lint`/`make check` was already
failing at the baseline, so this is a regression of an already-red gate
rather than a newly broken one.

O5:: *A vacuous assertion.* `tests/unit/test_lifecycle_controller.py:369`
reads `assert result.classification in {...} or True`, which can never fail.
The meaningful assertion follows it, so the test is not worthless, but the
line should go.

O6:: *Exit codes are distinct but only "documented" as a dict literal.*
`Deliver` item 7 asks for "distinct, documented exit codes". The 23 values in
`lifecycle.EXIT_CODES` are indeed pairwise distinct, but neither the
limitations record nor `ch02_code_navigation.adoc` contains an exit-code
table, and `EXIT_CODES` carries no explanatory comment. Several entries
(`refused_journal_root`, `not_launched`, `lifecycle_active`, `no_lifecycle`)
are also unreachable or only reachable through `status`.

O7:: *The ownership lock leaks on non-`LifecycleError` exceptions.*
`_advance` releases the lock only in `except LifecycleError`. A
`CommissionError`, `GitPreflightError` or `OSError` raised between acquisition
and launch leaves the fd open. In the one-shot CLI this is harmless (the fd
dies with the process), but an in-process caller observes it directly: after
the B1 wedge, a second in-process `resume` reported "active lifecycle already
running for this checkout" -- a false statement -- while a fresh *process*
correctly reported the real error. A `finally`-based release would remove the
hazard. The same code path also leaves the materialised Commission files in
the worktree when `bounded_path_commit` raises `TrustedCommitError`, reported
as `refused_prelaunch`.
