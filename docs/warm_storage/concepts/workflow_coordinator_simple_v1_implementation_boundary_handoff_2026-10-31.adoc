== 1. The obstacle, independently verified

The design's §11 candidate production scope lists, among ordinary `src`/test
paths, three governance paths as new or changed:

* `governance/workflow-programs/simple/v1.yaml`
* `governance/self-development/components.yaml`
* `governance/self-development/prompts/simple-self-check.txt`

This is a real admission obstacle, not a hypothetical one. The immutable
`repository-standard@v1` policy record, read directly from
`governance/policy-bases/repository-standard-v1.yaml`, is:

[source,yaml]
----
governance_paths:
  - governance
work_item_scope_ceiling:
  - src
  - tests
  - scripts
  - docs
----

`governance` is a `governance_paths` entry and is *not* a
`work_item_scope_ceiling` entry. Two independent current-code admission
checks each separately enforce this, confirmed by direct reading at the
stated baseline:

* `src/workflow_coordinator/operator.py:138-201` (`_admit_a1`) rejects any
  WorkItem whose `scope` is not fully within `policy.work_item_scope_ceiling`
  (`:185-191`, "WorkItem.scope exceeds repository policy
  work_item_scope_ceiling") and any profile phase whose `authorized_scope`
  overlaps `policy.governance_paths` in either direction
  (`:169-184`, "profile authorized_scope overlaps repository policy
  governance_paths").
* `src/workflow_coordinator/commissioning.py:402-403` independently rejects a
  Commission Intent whose `scope` overlaps `policy.governance_paths` at
  render time, before `_admit_a1` is ever reached:
  `if any(_within(path, tuple(policy.governance_paths)) for path in intent.scope): raise CommissionError("Intent scope overlaps repository governance paths")`.

Because `governance` is outside `work_item_scope_ceiling` entirely -- not
merely outside some narrower default -- no ordinary `repository-standard@v1`
WorkItem or phase can ever legally declare write scope under `governance/`,
regardless of programme (`simple`, `direct`, or `robust`) or how the phase is
otherwise shaped. This is a general, pre-existing repository-policy
invariant that the `simple@v1` design does not propose to change and that
this note does not propose to change either.

== 2. Why this is not a design defect

The accepted design's own §9 already states the general principle this
obstacle instantiates: "The Worker never chooses evidence argv, timeout,
executable identity, policy, route map, or programme revision." Programme,
policy, and component *definitions* are maintainer-authored governing
inputs that a Commission reads and is bound by, not surfaces a Commission
writes. The design's §11 candidate scope is accordingly best read as
identifying which files must exist and in what shape for the implementation
to work, not as a claim that an ordinary agent-writable Commission may
create them. The design does not say otherwise; it simply does not resolve
the staging question, which is exactly what this note is for.

== 3. Confirmed precedent: this is how governance inputs already get created

This is not a new problem requiring a new mechanism. The existing
self-development bootstrap pattern already separates governance-input
authoring from agent-writable Commission execution:

* `governance/workflow-programs/direct/v1.yaml` and
  `governance/workflow-programs/robust/v1.yaml` (the two closed programme
  catalogue records `_load_sources` already recognizes,
  `commissioning.py:318-351`) are themselves `governance/` paths. They exist
  today only because they were authored and committed directly -- outside
  any agent-writable WFC Commission scope -- consistent with the documented
  Front Door Stage 1 workflow ("human-describes / interactive-LLM-authors /
  deterministic-prepare-admission / human-launch", `_open.adoc`'s Front Door
  Stage 1 row).
* The same pattern already recurs per self-development Commission: e.g.
  `docs/backlog/BUG-WFC-OPERATOR-DIAGNOSTIC-PROPAGATION.adoc`'s commissioned
  correction uses its own dedicated
  `governance/self-development/operator-diagnostic-propagation-fix-profile.yaml`
  and `...-policy.yaml`, which are governance inputs authored alongside the
  BUG record itself (maintainer-side, in an interactive session), *before*
  the WorkItem's own scope (confined to
  `src/workflow_coordinator/operator.py`, `slice4.py`, and their tests) is
  ever admitted.

The `simple@v1` case is the same shape at one additional layer: the new
*programme catalogue record* and its *modifier component* are themselves the
governing inputs that need pre-existing, trusted authorship before any
Commission can reference them, exactly as `direct/v1.yaml` and
`robust/v1.yaml` already do.

== 4. Recommended smallest safe staged sequence

=== Stage A -- trusted maintainer-side authoring of governance inputs (outside any agent-writable WFC scope)

Author and commit directly (ordinary maintainer git commit, with or without
interactive-LLM drafting assistance, never through an agent-writable
Commission `authorized_scope`):

* `governance/workflow-programs/simple/v1.yaml` -- the literal record
  matching design §3's YAML exactly, including `source:` provenance
  consistent with how `_direct_template`/`_robust_template`
  (`commissioning.py:268-278`, `:279-294`) already compare against their
  catalogue files.
* `governance/self-development/components.yaml` -- add the
  `simple-self-check` entry alongside the existing shared entries this
  manifest already defines; this is the same file `direct@v1`/`robust@v1`
  already share (`_load_sources`'s `required_components` check,
  `commissioning.py:350-351`), so this stage only *adds* an entry, it does
  not restructure the file.
* `governance/self-development/prompts/simple-self-check.txt` -- the closed
  text specified by design §3, instructing the Worker to self-check before
  its sole result and to report `outcome: failed`/`blocked` on a discovered
  issue, granting no evidence authority.

These three files have no runtime effect until Stage B's compiler/operator
changes exist: `_load_sources`'s `program_specs` mapping
(`commissioning.py:318-321`) and `commission_intent_from_yaml`'s
`required_personas` mapping (`commissioning.py:202-206`) are both exhaustive
and currently reject everything except `("direct","v1")` and
`("robust","v1")`. Pre-seeding these governance files is therefore safe in
the sense that it cannot be used to admit or dispatch anything -- a Commission
naming `program: {id: simple, revision: v1, ...}` is rejected by
`commission_intent_from_yaml` before `_load_sources` is even reached.

=== Stage B -- Robust-v1 implementation Commission confined to production source and tests

A subsequent `robust@v1` self-development Commission (independent reviewer,
not `simple` -- `simple` cannot bootstrap its own implementation) whose
`WorkItem.scope` and policy `work_item_scope_ceiling` match the design's §11
candidate scope *minus* the three governance paths:

* `src/workflow_coordinator/commissioning.py`
* `src/workflow_coordinator/model.py`
* `src/workflow_coordinator/operator.py`
* `src/workflow_coordinator/vertical.py`
* focused existing `tests/` for each

implements:

* the `simple@v1` entries in `program_specs` and `required_personas`
  (commissioning.py), each pinned against the Stage-A-committed catalogue
  file and component manifest exactly as `direct`/`robust` already are;
* the renderer traversal completion from design §7, tracked independently as
  `docs/backlog/BUG-WFC-COMMISSION-SELECTED-COMPONENT-PROVENANCE.adoc`;
* the shared closed-terminal-worker predicate in `model.select_result_contract`
  and the `_admit_evidence_disposition` relaxation from design §5/§7; and
* the early transport guard in `vertical.run_one_hop`, tracked independently
  as `docs/backlog/BUG-WFC-PROVIDER-TRANSPORT-CANDIDATE-ACCEPTANCE.adoc`.

This Commission's phases read the Stage-A governance files as ordinary
governing inputs -- exactly as every existing Commission already reads
`governance/workflow-programs/{direct,robust}/v1.yaml` and
`governance/self-development/components.yaml` today -- without any phase
`authorized_scope` ever naming a `governance/` path. `_admit_a1`'s
`outside_governance` check (`operator.py:161-166`) requires every *governing
input* (which includes every selected component) to be *within*
`policy.governance_paths`; that is satisfied by reading the Stage-A files
unchanged. Its separate `overlaps` check (`operator.py:169-184`) only
rejects a phase whose *write* scope overlaps `governance_paths`; Stage B's
phases write only `src`/`tests`, so no overlap exists. Neither check is
relaxed, bypassed, or reinterpreted by this staging; both apply exactly as
they do to `direct@v1`/`robust@v1` today.

=== Stage C -- real `simple@v1` dogfood

Only after Stage B is independently reviewed, accepted, and the two
prerequisite BUGs above are resolved (or explicitly waived by the
maintainer), a real `simple@v1` Commission Intent pins
`program: {id: simple, revision: v1, source_commit: <Stage-A commit>}` and
`components_ref: {..., source_commit: <Stage-A commit>}`, and is admitted and
launched as ordinary separate, later, maintainer-owned steps -- matching the
design's own §10 first-dogfood framing ("one small real maintenance change
with a bounded source/test scope and its actual task check").

== 5. No other admission or pinning dependency found

Checked and found not to introduce a further obstacle:

* `_load_sources`'s `_repository_standard_v1_record` byte-for-byte policy
  check (`commissioning.py:295-315`) and its `program_specs`/
  `required_personas` literal-template equality checks
  (`commissioning.py:318-351`) are satisfied by Stage A alone, once Stage B
  adds the matching `_simple_template()` and mapping entries; no additional
  governing file beyond the three design §3/§7 names is implied by current
  source.
* `verify_render_manifest`'s reused-input pinned-blob loop
  (`commissioning.py:514-518`) and `_clean_head`
  (`commissioning.py:481-487`) require a clean expected HEAD at the pinned
  commit for every governing input, including the new catalogue and
  component files; this is satisfied once Stage A's commit is the pinned
  `source_commit`/`expected_head` for Stage C, with no new mechanism.
* `operator.py`'s preflight component loading (`:432-446`) reads every
  `_selected_ids` entry from `args.expected_head` via `_pinned_text`
  (`:441-443`), which already tolerates any tracked path under
  `governance/self-development/...`; no change to that read path is implied.
* No other current admission predicate (`_admit_evidence_disposition`,
  Hop-ceiling enforcement, or the Front Door rendered-bundle equivalence
  check at `commissioning.py:509-512`) treats `governance/` specially beyond
  the two checks in §1 above.

This note does *not* identify a need for a fourth governance file, a new
catalogue mapping layer, or a relaxation of `_admit_a1`; Stage A/B/C as
structured above is sufficient against current source.

== 7. Architectural-boundary constraints for the Stage B implementation

Restated from
link:../../backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc[FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES]
as explicit constraints on the Stage B WorkItem, not a new architectural
decision:

* Preserve the deterministic, effect-free Reducer; no provider, Git,
  filesystem, or process access enters `reducer.py`.
* Keep workflow topology declarative; the Simple shape is admitted through
  profile/predicate data, not a phase-name branch.
* No scattered `is_simple` / `skip_review` / `allow_worker_evidence`
  switches anywhere in the shell; the one shared closed-terminal-worker
  predicate (§6 above, design §5/§7) is the single decision point both
  `select_result_contract` and `_admit_evidence_disposition` consult.
* Treat failed provider transport as a shared execution invariant in
  `vertical.run_one_hop`, not a Simple-specific branch; the transport guard
  must apply unconditionally, before any programme-specific logic runs.
* Reuse the existing evidence execution, provenance, and recovery seams
  (`vertical.py`'s post-agent/pre-reduction boundary, the existing pinned-
  blob comparison loop, `recover_uncertain`); no second orchestration
  subsystem, manifest, or pinning service.
* Preserve `direct@v1`/`robust@v1` behavior byte-for-byte except for the two
  explicitly justified shared correctness fixes (transport guard,
  provenance traversal completion) tracked as the two BUG records above.
* Add narrow architectural regression tests only at the boundaries actually
  touched (component selection, admission predicate, transport guard); no
  broad architecture-test project.
* No ABC, Strategy hierarchy, or service registry introduced merely for
  Simple's sake; `FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES`'s
  existing non-goals (no DDD layering, no interfaces-for-every-component)
  apply unchanged to this implementation.

== 8. Contradictions or additional prerequisites found against the accepted design

None found that change the design's conclusions. Two clarifications worth
recording for the Stage B authoring step, neither altering the design's
accepted disposition:

* The design's §11 file list is accurate as a *content* inventory but
  conflates authoring authority across two different actors (trusted
  maintainer vs. agent-writable Commission) for the three `governance/`
  entries; this note's Stage A/B split is the missing staging the design
  itself leaves as design section 11's "candidate file scope," not a defect
  in the design.
* The design's §2 and §8 source citations for the transport guard and
  provenance traversal were independently re-verified at the current
  Development HEAD (`a2051c5`) during this task and confirmed unchanged from
  the commit the design cites; no drift was found.

== 9. Recommendation for the subsequent Commission-authoring task

Do not author a Commission yet. When ready:

1. Have the maintainer (optionally with interactive-LLM drafting help, in a
   session like this one, never through an agent-writable WFC scope) author
   and commit Stage A's three governance files, reviewed as ordinary source
   changes.
2. Only then draft the Stage B `robust@v1` self-development WorkItem/Intent,
   scoped exactly to §6 above, with `work_item_scope_ceiling` continuing to
   exclude `governance/` (no policy change needed -- `repository-standard@v1`
   already excludes it).
3. Resolve or explicitly waive the two prerequisite BUGs before or within
   Stage B's own implementation (they are naturally in-scope for Stage B
   since they touch the same files).
4. Defer Stage C (real dogfood) until Stage B is accepted and Runtime-
   promoted per the project's ordinary review process.
