=== 1. Disposition

Verdict:: `changes_required`
Route:: `correction`
Finding disposition:: `F001` -> `resolved`; one new blocking Finding proposed
(section 4).

The H003 correction does resolve `F001`: an in-scope changed or untracked path
whose name contains a space, a quote, a backslash or a *valid UTF-8* non-ASCII
character is now read verbatim and preserved, at unit level and end to end.

The same correction, however, introduces a new blocking regression. By
switching the status read to `-z`, `preserve_candidate` now receives raw path
bytes where it previously received Git's ASCII-only C-quoted form. `_run_git`
decodes subprocess output as strict UTF-8, so a worktree path whose *name* is
not valid UTF-8 (an ordinary possibility on Linux, where a file name is a byte
string) now raises `UnicodeDecodeError` inside the capture step. That exception
is not a `PreservationRefused`, so it escapes `frontdoor.preservation` and
`frontdoor.lifecycle`, and it changes the observable BP4a exit code -- the one
thing BP4b is explicitly forbidden to touch.

The repository itself stays byte-identical in that case (no ref, no object, no
index, worktree or HEAD change), so this is a contract and availability defect,
not a mis-capture.

=== 3. `F001` -- resolved

The corrected read is

[source,python]
----
status = read_git("status", "--porcelain=v1", "-z", "--untracked-files=all", "--no-renames")
entries = status.split("\0") if status else []
if entries and entries[-1] == "":
    entries.pop()
----

`-z` suppresses `core.quotePath` entirely, so there is no quoting left to
undo, and the `" M path"` shape's significant leading space is still preserved
by the `rstrip("\n")`-only read helper.

=== 4. New blocking Finding -- an undecodable worktree path name crashes `wfc run`/`wfc resume` and changes the BP4a exit code

Severity:: *Blocking.* Reproduced violation of the frozen BP4a contract ("BP4b
adds NO new BP4a transition and changes no BP4a record, classification or exit
code"), of acceptance case (15) ("every refusal is journaled with its reason
and leaves the classification and BP4a exit code unchanged") and of `Deliver`
item 3 ("else refuse with a named reason") and item 5 (a terminal
`ext.preservation.*` record for every outcome).

*Mechanism.* `_run_git` runs Git with `text=True`, i.e. strict UTF-8 decoding
of stdout. Before H003 the porcelain status was C-quoted and therefore pure
ASCII, so it always decoded. With `-z` Git emits the path bytes verbatim, and a
worktree entry whose name is not valid UTF-8 (for example a Latin-1 `café.txt`
written by a tool, or any file extracted from an archive with a legacy
encoding) makes `subprocess.run` raise `UnicodeDecodeError` at
`git_facts.py:950`. `UnicodeDecodeError` is a `ValueError`, so:

* `run_pending_preservation` only catches `git_facts.PreservationRefused`; the
  exception passes through (the ownership lock *is* released by its `finally`);
* `cmd_run`/`cmd_resume` catch only `LifecycleError`, `CommissionError`,
  `GitPreflightError`, `JournalError` and `OSError`; the exception escapes the
  CLI entirely.

*Reproduction (end to end, real `wfc run`, delivered BP4a fake-engine/
fake-provider fixtures, request scope `["src"]`, mode `dispatch_then_crash`).*
`WFC_FAKE_ENGINE_DIRTY_FILE` is the only variable:

[cols="2,1,2,1"]
|===
|Dirty file |CLI result |Journal after the call |Preserved refs

|`src/wip.txt` (control)
|`CLASSIFICATION: interrupted`, exit *14*
|`classified`, `ext.preservation.intent`, `ext.preservation.result`
|`refs/wfc/preserved/RUN-fake-engine/1`

|`src/caf<0xE9>.txt`
|unhandled `UnicodeDecodeError`, no `CLASSIFICATION` output, process exit *1*
|`classified`, `ext.preservation.intent` (dangling, no terminal record)
|none
|===

`EXIT_CODES["interrupted"]` is 14; the operator-visible exit code becomes 1 and
the classification report is never printed, although BP4a itself classified the
Run correctly and wrote its `classified` record before preservation ran.

*It is permanent for the affected Run.* A follow-up `wfc resume` on the same
checkout raises the identical unhandled `UnicodeDecodeError` (exit 1) because
no terminal `ext.preservation.*` record was ever written, so the replay guard
never fires. `wfc status` still works (exit 0, classification reported, no
`PRESERVATION` block), confirming the damage is confined to the two write
entry points.

*It is a regression of this correction, not a pre-existing defect.* The same
end-to-end probe run against a copy of the tree with only the H003 status-parse
hunk reverted yields, for the identical repository state: `CLASSIFICATION:
interrupted`, exit *14*, and a clean terminal
`ext.preservation.refused` record. The pre-correction code refused that path
(wrongly, as `F001` describes) but refused it *honestly and within contract*.

*Not a safety hole.* After the crash, `HEAD`, the branch, the live index, the
worktree and every ref are unchanged, and `refs/wfc/preserved/` is empty.
Nothing is mis-captured; the defect is the broken BP4a exit-code contract, the
missing named refusal and the permanent loss of preservation for that Run.

*Relation to H002.* This is the concrete reproduction of H002's non-blocking
observation O6 ("a non-`PreservationRefused` exception escaping the glue would
change the BP4a exit code -- not reproduced"). H003 made it reachable from an
ordinary repository state, which is what moves it from observation to blocking
Finding.

*Correction space (non-binding, additive, no BP4a change needed).* Either
decode the status bytes tolerantly inside `preserve_candidate` (for example run
the status read through a new additive bytes-mode helper and decode with
`errors="surrogateescape"`, which also lets such a path be captured, since
Python re-encodes surrogate-escaped argv with the same convention), or -- the
minimal form -- convert the failure into a named refusal by catching
`UnicodeDecodeError` around the status read. A defensive conversion of any
unexpected exception in `run_pending_preservation` into
`ext.preservation.refused` would additionally close the whole O6 class, but
that is a design choice for the maintainer, not a review requirement. A test
pinning the behaviour needs a file name that is not valid UTF-8 (for example
`os.fsdecode(b"src/caf\xe9.txt")`).

=== 6. Non-blocking observations

Reported here and in the Hop summary only; `finding_authority: [resolve]` does
not authorize residual transitions, and none of these is a reproduced violation
of an acceptance case.

O13:: *A file named with a leading colon at repository root is refused with a
raw Git diagnostic.* With a root authorized scope (`allowed_paths=(".",)`), an
untracked `:weird.txt` is in scope but is passed to `git add -A --` as a
pathspec, where the leading `:` is pathspec magic:
`PreservationRefused: fatal: pathspec ':weird.txt' did not match any files`.
Fail-safe (repository byte-identical, no mis-capture, scope cannot be widened
this way because magic is only recognised at offset 0 of the pathspec, which
requires a root scope where everything is already in scope), but the durable
reason is a raw Git error rather than a named predicate. `--literal-pathspecs`
or `:(literal)` prefixes would close it.

O14:: *The H003 regression test does not cover the undecodable-name shape.* It
covers a space and a valid-UTF-8 non-ASCII character only, which is why the
regression in section 4 passed the delivered suite.

H002's observations O1-O12 are carried forward unchanged; this Hop did not
re-disposition them and found no evidence contradicting any of them.
