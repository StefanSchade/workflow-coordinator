== Maintainer decisions (2026-11-04)

These decisions govern sequencing and distribution for the rest of this
plan. They supersede this document's own §9.1 framing and the Batch 8 row of
the §8 table as originally written (both marked below with a dated note);
the comparative audit and consolidation design in "1. Current state" onward
are otherwise unchanged supporting analysis.

. *Immediate objective.* Restore reliable WFC-on-WFC development Runs
  through a limited period of direct Sonnet work on documentation, routing,
  and practical operator instructions. Return to WFC Runs as soon as a real
  self-development Run can be prepared, launched, and handled reliably.
  Completion of this entire documentation plan is not required first.
. *0.1.0b1 product target.* WFC must be pip-installable, including the
  Operator Harness and Front Door, and usable against unrelated consumer
  repositories without a WFC source checkout.
. *Distribution decision.* The earlier proposal to leave the Harness
  repo-local for 0.1.0b1 -- the framing behind §9.1 and part of finding F10
  -- is reversed. Its current repo-local implementation
  (`scripts/wfc_op.py`, unpackaged per `pyproject.toml`'s
  `tool.setuptools.packages.find`) remains a valid *observed* limitation --
  that part of F10 stands -- but it is not the target architecture and not
  an accepted beta constraint.
. *Documentation sequencing.* Prioritize writing conventions, AI routing,
  and the operator guidance necessary to restore self-development Runs.
  Selective header migration and less urgent documentation consolidation may
  be deferred. The full Operator Guide must ultimately describe the
  intended packaged, consumer-neutral product, while correctly documenting
  the currently supported self-development workflow in the meantime.
. *Functional Model.* Include WFC's motivation, Level 0 versus potential
  Level N, and failure modes emphasizing repository integrity against
  opportunistic or adversarial agents. Execution-environment isolation is
  primarily an external responsibility; blanket prevention of arbitrary
  secrets known to agents entering a repository is not a generic WFC kernel
  requirement. This revises Batch 7's acceptance criterion in §8.

== 2. Document metadata model

Three concepts stay distinct; only the first two are document metadata.

[cols="1,3",options="header"]
|===
|Concept |Where it lives

|*Document maturity* -- lifecycle of the document artifact
|`Maturity::` in the document header

|*Document authority* -- standing of its content
|`Authority::` in the document header

|*Feature implementation progress* -- property of a feature or defect
|The controlling `+FTR-*+`/`+BUG-*+` record, never a document header (§2.5)
|===

Neither field grants WFC runtime execution authority. That is stated once, in
`docs/README.adoc` and `doc_conventions.adoc`, and never repeated per document.

=== 2.1 Vocabulary

[cols="1,3",options="header"]
|===
|`Maturity::` |Meaning

|`draft`
|Being written or substantially incomplete; may change without notice.

|`in-review`
|Content complete and submitted for independent review; not yet dispositioned.

|`stable`
|Maintained and expected to stay current. Says nothing about whether the content
is normative.

|`superseded`
|The *document* is no longer maintained; retained as evidence. Belongs in
`cold_storage/`.
|===

[cols="1,3",options="header"]
|===
|`Authority::` |Meaning

|`historical`
|Content describes a past state, retained as provenance. Distinct from
`Maturity:: superseded`: a maintained document may contain historical content
(§2.4).

|`informative`
|Explains, navigates, or summarizes; defers to a named owner for every contract
it touches.

|`exploratory`
|Concept, hypothesis, or discussion record. Not adopted; nothing may be built on
it without separate adoption.

|`accepted-design`
|Independently reviewed and accepted as the design to implement. Acceptance is
neither implementation nor a currently applicable contract.

|`normative`
|Currently applicable: states a contract or invariant that current behavior and
current work must respect.
|===

*Relationship fields*, used only when they apply, to preserve a distinction a
single state value would destroy:

* `Supersedes::` / `Superseded-by::` -- document-level replacement.
* `Superseded-in-part-by::` -- a named decision or record overrides a specific
point while the rest stands (§2.3).
* `Governing-records::` -- already used by several WFC documents; keep it.

=== 2.2 Mechanical placement

*Observed:* the metadata block must be separated from the title (and any `:attr:`
entries) by a blank line. Without it, AsciiDoc parses the document-header
position and renders `Maturity:: stable` as the author line and `Authority` /
`: normative` as revision fields. Existing WFC documents already get this right;
earlier drafts of this plan did not.

[source,asciidoc]
----
= <Title>
:toc:

Maturity::  stable
Authority:: normative
Updated::   2026-11-03
Owns::      <the durable facts this document is canonical for, one line>
----

=== 2.3 P3.5 finding-authority reachability design

That header is stale, and an earlier draft of this plan trusted it.

*Observed:* `DEC-WFC-018` (2026-10-26) states in its own rationale that "*The

Authority::               accepted-design
Superseded-in-part-by::   DEC-WFC-018 -- predicate selection: existential

----

This is why `Superseded-in-part-by::` exists rather than a fifth maturity
value: the design's structure, motivation, and mechanism survive; one central
predicate does not.

=== 2.5 Status stays at the controlling source

Feature status and its evidence belong to the controlling `+FTR-*+`/`+BUG-*+`
record. WFC development is incremental -- slices are partially implemented,
interrupted, resumed, revised -- and the record is where slice-level
dispositions already live. *Observed:*
`FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE.adoc` (49,875 bytes) carries Slices 1-6
with distinct per-slice dispositions that `_open.adoc` summarizes in one
paragraph. `_open.adoc` stays the planning and navigation overview; its value
is that it links onward rather than restating.

Current documentation *may* state facts about implemented behavior where needed
for comprehension -- the technical model's "As-is: confirmed from current
source" is legitimate and must survive migration. What is removed is a
*redundant status declaration* in a header that duplicates a controlling record
and will silently go stale.

=== 2.6 Chapter source files

Backlog records, review artifacts, and `cold_storage/` keep their own existing
schemas; the model above applies to documentation only.

A chapter file is standalone-legible but must not inject a second metadata block
into the assembled guide. *Verified with asciidoctor:* wrap the chapter's own
header in a preprocessor conditional that the guide entry document switches off.

[source,asciidoc]
----
\ifndef::assembled[]
= WFC Operator Guide -- Run Preparation
Maturity::  stable
Authority:: normative
Updated::   2026-11-03
Owns::      Deterministic Run-preparation mechanics.
\endif::[]

== Run preparation
...
----

The entry document sets `:assembled:` before its includes. Reading the chapter
alone shows its title and metadata; reading the guide shows the guide's metadata
once. A chapter declares `Maturity`/`Authority` only where it *differs* from the
guide -- otherwise it carries just `Owns::`, naming the facts it owns.

== 3. Writing conventions for `docs/ai_info/doc_conventions.adoc`

One page. No approval requirement, no governance framework. *Observed:* neither
repository has a documentation-writing convention today; the nearest Core
statements are one line in `_ai_info.adoc` (heading level, `leveloffset`) and
the anti-duplication rule in `agent_rules.adoc`. The only existing decision to
respect is the 2026-10-15 consolidation's §3 reading path, which these extend.

. *Declare maturity and authority* using §2. Four header lines, no prose status
paragraph, and the blank-line placement rule of §2.2.
. *State the runtime-authority fact once*, in `docs/README.adoc`. No document
carries a non-authorization disclaimer.
. *One canonical home per durable fact.* State it once, in the document whose
`Owns::` line claims it. Elsewhere link and give the conclusion in one
sentence -- never restate the procedure.
. *Keep document metadata out of issue lifecycle.* Feature status, slice
dispositions, and review evidence stay in the controlling record under its own
schema.
. *Current documents stand alone.* A reader must understand current behavior
without reconstructing history. Cite an archived record for provenance only
after stating the conclusion in the document's own words.
. *Proportionate detail.* Concise and token-efficient but human-readable:
concrete commands, small YAML fragments, worked examples where they prevent a
misreading; no example that restates a procedure another document owns. No
length targets.
. *Structure for selective retrieval.* Prefer a central entry document with
chapter includes over a monolith, so one chapter can be loaded alone.
Meaningful headings; one `=` title; sections from `==`; chapter files
`==`-rooted per §2.6.
. *Mechanics.* AsciiDoc for new documents. No date in a filename unless the
document *is* a record of that date's event.
. *Apply prospectively* -- to new documents and current documents expected to
outlive the MVP. `cold_storage/` and `imported/` are not migration targets.

== 7. DMC principles to adopt

`core/.../05_domain_maintainer_contract.adoc` (704 lines, 12 sections) read in
full. *Home:* one section of roughly a page in
`developer_guide/ch03_code_conventions.adoc` -- not a separate document, and not
a second governance framework. WFC already has governance
(Commission/WorkItem/Profile/Policy); these are engineering conventions for
whoever maintains WFC's code.

*Transfer as-is:* proportionality with "not applicable" legitimate but never
hiding a touched contract (§1, §12); the explicit *"does not require"* negative
list (§1 -- the most transferable editorial device in the document); material
handoffs as first-class contracts, with the judgment test "a plausible
single-sided change on either side could silently break the other side" and its
producer/consumer/authority/ordering/atomicity/conflict-ownership checklist
(§5), which maps onto WFC's reducer -> adapter, operator -> persisted Hop audit,
Commission -> rendered bundle, and Runtime -> Evidence seams; compatibility by
migration friction rather than version number, with the five-way
preserve/simplify/migrate/deprecate/remove disposition table (§7); Reference
Readability -- permanent code and prose must state their meaning "without
requiring an FTR ID, review finding, obsolete version name, or Git history
lookup" (§11); Local Human Readability *with its explicit no-metric stance*
(§9); tests derived from the contracts actually affected, keeping existing FTR
markers because they answer "why does this test exist?" (§10 -- WFC already has
`pytest.mark.ftr` and `tests/architecture/`); and canonical ownership
distributed by document ownership rather than one reference document per scope
(§11), which independently corroborates §2.5 and §4.

*Observed live instance:* `src/workflow_coordinator/operator.py:214` raises
"Slice-5B supports at most {N} autonomous Hops" -- a historical slice label in a
user-facing refusal message, exactly what Reference Readability forbids.

*Adapt:* consumer evidence (§10) -- "if no consumer exists, do not invent
migration work" transfers, but WFC's probes are a real dogfood Run, provider-free
preflight, and the architecture guards, not spreadsheet roundtrips. State,
provenance, and reconstruction (§6) -- re-derive from WFC's five roots
(Development, Runtime, Evidence, OPS, STATE) rather than translating Core's
persisted-metadata framing. The proportional completion gate (§12) -- the idea of
a short applicability-gated checklist transfers; WFC's version should be roughly
six outcomes and should reference, not duplicate, the Profile's own phase gates,
since WFC enforces completion executably. Deliberate disposition of touched
sediment (§12.10), which bears on legacy surfaces such as the
`--durable-artifact` option already marked legacy.

*Do not copy:* Domain/Core layering, *family* as an ownership kind, Trusted
Ingress, Egress, Workbook View, and the §2 reasoning-axes apparatus; the Domain
Contracts/metadata/pipeline-step registries and `interfaces_and_gates.adoc` as a
surface; "Cycle 0" as a named procedure; the DMC's own identity as a *contract*
to comply with; and Core's separate human-readability review guide.
