= Workflow Coordinator Operational Friction Evidence -- 2026-10-11
:toc:
:toclevels: 3
:sectnums:

Status:: EMPIRICAL OBSERVATION / NON-AUTHORIZING.
Date:: 2026-10-11.
Scope:: Operational and cognitive friction observed while developing and self-dogfooding `workflow-coordinator`, with emphasis on the Projected Result Contracts and adjacent hardening lineages.
Purpose:: Preserve evidence that can later justify, bound, and evaluate a simplification effort. This record does not authorize any redesign, deletion of guardrails, schema change, Runtime promotion, provider change, or workflow change.

[IMPORTANT]
====
This record is deliberately not a proposal to weaken fail-closed behavior.

A large fraction of the evidence below shows the opposite: WFC repeatedly refused to
claim success when authority, evidence, durable artifacts, or result contracts were
not satisfied. Those safety properties are valuable.

The concern recorded here is whether the same safety semantics now require too much
human/LLM orchestration, duplicated specification, historical context, and repeated
repair work to operate and extend the system reliably.

"Reduce friction" therefore means: preserve or strengthen the invariants while
reducing the number of places, interactions, and implicit historical facts needed to
express and execute them.
====

== 1. Why this record exists

`workflow-coordinator` began as tooling around another repository and later became a
carved-out domain and repository of its own. Its architecture and repository layout
were not originally designed from first principles for long-lived AI-agent
maintenance.

The carve-out was successful enough that WFC is now able to:

* execute bounded worker/reviewer loops;
* own mechanical Git commits;
* persist Run/Hop evidence;
* fail closed on authority and contract violations;
* archive immutable evidence;
* self-develop under the same mechanism;
* project increasingly strict result contracts.

At the same time, routine work has accumulated visible orchestration cost.

The maintainer's concern is not merely that individual changes are difficult. The
stronger concern is that the *working method* is becoming expensive:

[source,text]
----
design / diagnosis
  -> curation
  -> design clarification
  -> maintainer decision
  -> durable design record
  -> Commission authoring
  -> Commission repair
  -> PREPARE
  -> preflight repair
  -> fresh attempt id
  -> PREPARE
  -> LAUNCH
  -> possible awaiting_human
  -> successor decision
  -> archive / ledger / promotion
----

Several of these stages are individually justified. The friction signal is that
their composition is increasingly difficult for both the human operator and the
interactive AI assistant to hold and execute reliably.

== 2. Evidence classes used here

This record separates three classes of evidence.

=== 2.1 Archived Run evidence

The primary historical source is the curated WFC Run Ledger in
`workflow-coordinator-run-evidence/project_memory/run_ledger.adoc`.

Run IDs, attempt IDs, commits, statuses, stop reasons, and archived evidence paths
quoted from that ledger are treated as historical evidence.

=== 2.2 Repository history and committed design/Commission artifacts

Where known, this record cites exact Development commits and named governance or
design artifacts. These establish that the observed friction was not merely terminal
scrollback or conversational memory.

=== 2.3 Maintainer/operator session observations

Some costs are interaction costs and therefore do not naturally appear in Run
evidence:

* elapsed time spent coordinating interactive assistants;
* number of conversational turns before a command is issued;
* context-switch cost while waiting for an LLM;
* the operator abandoning a short launch window and returning later;
* the interactive assistant increasingly rediscovering already-familiar CLI syntax.

These are explicitly labeled as session observations rather than Coordinator-trusted
Run facts.

== 3. 2026-10-11 P3 session: concentrated friction case

=== 3.1 Intended task

The immediate operational intention was modest:

> finish the already-curated P3 Commission and start the bounded P3 Run before going
> cycling.

The maintainer expected roughly a 30-minute window to be ample for "let us quickly
start this Run."

Instead, more than 45 minutes elapsed before the Run had even started. The maintainer
then stopped the activity and went cycling; work resumed later.

This is an operator-session observation, not a Run-timing metric.

=== 3.2 Design curation before Commission

P3 ("Finding authorship/update projection") first required a research/curation pass.

The temporary curation record identified one maintainer-level semantic question:

* whether a same-state Finding citation is an evidence-only act, or whether it should
  require `finding_authority`.

The maintainer decided:

* a same-state citation is evidence-only;
* `finding_authority` gates state-changing transitions only;
* citation and transition should therefore be structurally distinct result variants.

The temporary record was then promoted into the repository as:

`docs/warm_storage/concepts/workflow_coordinator_p3_finding_projection_design_2026-10-11.adoc`

Commit:

`e4dbf7d23502b55a730811176073e33483c6a2c9`
(`docs(wfc): record P3 finding projection design`)

The committed record is 599 lines and explicitly says it is commission-ready but
non-authorizing.

This is not itself evidence of unnecessary complexity: the design contains real
authority, replay, compatibility, and algebraic-modeling questions. It does,
however, establish the amount of durable context required before the implementation
Commission could be written.

=== 3.3 Commission size and first repair

The P3 Commission was then authored as four files:

* `governance/self-development/projected-result-contracts-p3-policy.yaml`
* `governance/self-development/projected-result-contracts-p3-profile.yaml`
* `governance/work-items/projected-result-contracts-p3-task.txt`
* `governance/work-items/projected-result-contracts-p3.yaml`

The initial Commission commit was:

`d1f3c2b3d4f7ca067282b50db14d0d75676991df`

The initial bundle added 782 lines.

The first PREPARE failed provider-free:

[source,text]
----
PREFLIGHT REFUSED:
WorkItem.personas.worker must not exceed 512 UTF-8 bytes
----

The Commission authoring pass had produced:

* worker persona: 814 UTF-8 bytes;
* independent-reviewer persona: 886 UTF-8 bytes.

Both were shortened to 337 bytes and the Commission commit was amended.

Intermediate amended commit:

`a47ab251ffe2c1b6c153ee3338e4c220ea9c6f15`

Observation:

* the semantic detail that overflowed the persona field already existed elsewhere in
  the same Commission/design material;
* the guardrail was correct and cheap to enforce;
* but it was discovered only at PREPARE, after a multi-minute LLM Commission-authoring
  cycle.

This is evidence for an *authoring-time validation gap*, not evidence against the
persona-size guardrail itself.

=== 3.4 Failed PREPARE consumed an attempt identifier

After the persona repair, PREPARE using the original attempt identifier failed:

[source,text]
----
OPS already exists; refusing to reuse an attempt id:
.../wfc-projected-result-contracts-p3-20261011-01
----

The prior provider-free refusal had already created the OPS path.

The operator therefore switched to attempt `...-02`.

This is a concrete usability cost:

* a command that failed before provider invocation nevertheless consumed a
  human-meaningful attempt identifier;
* subsequent operation required remembering that `-01` existed only as a failed
  preparation artifact.

No claim is made here that the behavior is unsafe or incorrect. It is evidence that
the PREPARE lifecycle currently exposes implementation detail to the operator.

=== 3.5 Second PREPARE exposed a stale Commission pattern

Attempt `wfc-projected-result-contracts-p3-20261011-02` failed provider-free with:

[source,text]
----
PREFLIGHT REFUSED:
profile.phases.implement has required evidence but is not a gate review
----

The P3 Commission had copied an older pattern:

[source,yaml]
----
implement:
  role: worker
  evidence: [pytest]
----

But the already-accepted Evidence-Failure-Disposition hardening requires
Coordinator-required evidence only on gate-review phases with an explicit
`failed_evidence_route`.

The Commission was repaired to:

[source,yaml]
----
implement:
  evidence: []

independent_review:
  evidence: [pytest]
  review:
    failed_evidence_route: correction

correction:
  evidence: []

rereview:
  evidence: [pytest]
  review:
    failed_evidence_route: correction
----

The final amended Commission commit became:

`d2adf082b23f41fe0ae63b6b92e2c72e98dba414`

The repair itself was small and correct.

The friction signal is historical-context related:

* the Commission authoring agent reused a formerly normal worker-evidence pattern;
* that pattern had recently become invalid under accepted hardening;
* the same repository already contained both the old precedent and the new invariant;
* the contradiction was not eliminated at Commission-authoring time;
* PREPARE became the place where the stale precedent was finally rejected.

This is a concrete example of repository/history state becoming expensive for an
agent to reconcile.

=== 3.6 Third PREPARE succeeded

Attempt:

`wfc-projected-result-contracts-p3-20261011-03`

then reached:

[source,text]
----
PREPARED / NOT LAUNCHED
----

This was the first successfully prepared P3 attempt of the session.

=== 3.7 First real P3 Hop stopped immediately

The prepared attempt was launched.

Observed operator result:

[source,text]
----
RUN STATUS: awaiting_human
HOP USED: 1
LAST RUN COMMIT: none
CURRENT HEAD: d2adf082b23f41fe0ae63b6b92e2c72e98dba414
WORKTREE CLEAN: False
NEXT EXPLICIT ACTION:
Review the recorded semantic and mechanical stop facts;
any successor preparation requires a separately authorized maintainer decision.
LAUNCH RETURN CODE: 1
----

The Run therefore:

* consumed one provider Hop;
* produced no trusted commit;
* left a dirty worktree;
* stopped `awaiting_human`;
* requires another explicit maintainer disposition before successor preparation.

This record deliberately does not diagnose that P3 stop without its detailed Run
evidence. The important friction fact is narrower:

> after substantial pre-Run curation and two provider-free PREPARE corrections, the
> first real Hop still returned control to the human immediately.

This is a stronger operational-cost signal than any single preflight error alone.

== 4. Historical evidence: the pattern predates P3

The 2026-10-11 session is not sufficient by itself to justify a broad architecture
conclusion. The Run Ledger provides earlier corroborating examples.

=== 4.1 Early self-development already required repeated attempts

The Developer-Ergonomics lineage on 2026-09-22/23/24 records:

* attempt 1: blocked on route/scope mismatch, `awaiting_human`;
* attempt 2: implementation landed but Run still ended `awaiting_human`;
* multiple follow-up review Runs;
* later discovery of the Python `python`/`python3` alias-identity gap after a review
  itself had passed.

The eventual interpreter-identity defect was fixed and independently re-reviewed.

This lineage is important because it shows the phenomenon before Projected Result
Contracts existed: WFC self-development already caused operator/review chains in
which workflow mechanics and environment identity mattered as much as the actual
feature.

=== 4.2 Finding-delta work shows both friction and successful convergence

The Immutable-Finding-Echo correction provides both sides of the evidence.

Attempt 01:

`RUN-76e153b40ef1459db4587446b18e02d5`

* useful in-scope work was produced;
* the worker correctly raised a scope escalation;
* the Run ended `awaiting_human`;
* no trusted commit landed;
* useful work required separate salvage.

Attempt 02:

`RUN-f987897544f34b9aab9f1314fdee3674`

* used four Hops;
* independent review found a real semantic defect;
* correction fixed it;
* fresh rereview accepted it;
* Run completed cleanly.

A later maintainer inspection then found a narrower internal compatibility shim,
leading to another separately commissioned Run:

`RUN-889559c681844c378c80c1ecc5975d7f`

which completed cleanly in two Hops.

Lesson:

* repeated Runs are not automatically process waste;
* reviews have found real defects;
* but decomposition, salvage, successor authorization, and post-Run residual discovery
  create substantial coordination overhead around otherwise bounded changes.

=== 4.3 Scope-escalation continuation consumed several large Runs

The Scope-Escalation-Continuation lineage is the strongest historical example of
high governance/verification cost.

Recorded implementation attempts include:

* attempt 001: 6/6 Hops, `awaiting_human_budget`;
* attempt 002: 8/8 Hops, `awaiting_human_budget`;
* attempt 003: 6/6 Hops, `awaiting_human_budget`;
* attempt 004: another separately commissioned continuation experiment.

The ledger is explicit that these were not stalled loops: each rereview found
substantive defects and each correction materially improved the candidate.

That distinction matters.

The friction concern is not that the evaluator/optimizer loop was useless. The concern
is that a single trust-boundary feature required a long chain of:

* design Run;
* separately commissioned implementation Run;
* successor Commission;
* another successor Commission;
* increasingly explicit requirement-carryover mechanisms;
* repeated human lifecycle decisions between Runs.

This is exactly the kind of accumulated process cost a later simplification effort
should measure rather than dismiss.

=== 4.4 P1 reproduced a known Commission-authoring authority defect

Projected Result Contracts P1:

`RUN-157080a2fa7b44de8429aa9b8fba53ab`

implemented and was independently judged technically acceptable after correction.

But the Run stopped `awaiting_human` because:

* H002 opened blocking Finding `F001`;
* H003 corrected the underlying issue;
* H004 independently accepted the correction;
* neither review gate held the `finding_authority` needed to transition `F001` out of
  OPEN.

The trusted reducer therefore correctly refused completion.

The ledger explicitly classifies this as a reproduction of the already-open
`BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY`, not an engine regression.

A separate Assurance Closure Run was then required.

This is direct historical evidence that Commission topology can be internally
incoherent even when:

* the implementation is sound;
* tests are green;
* independent review accepts it;
* the engine itself behaves correctly.

=== 4.5 P2 had three non-accepting Runs before the corrected topology completed in two Hops

The P2 lineage is particularly relevant to the 2026-10-11 P3 preflight failure.

The ledger records three P2 Runs that did not reach genuine independent acceptance:

* `RUN-90c24baad80645b0958ed96ae0a2cc3f`
* `RUN-d5ae5bd0eadb41dba2c10c1d085e6c4d`
* `RUN-6fa0b56e3b844896a55f147f4ee41fea`

A later stagnation audit localized the principal issue to Commission/profile topology:

* full-suite `pytest` was placed on worker phases;
* worker phases structurally could not route an evidence failure;
* review gates omitted `failed_evidence_route`;
* prompt prose encouraged the worker to treat downstream acceptance evidence as its
  own completion prerequisite.

The corrected successor topology was:

[source,text]
----
worker evidence:[]
  -> independent_review gate evidence:[pytest]
       failed_evidence_route: correction
  -> correction worker evidence:[]
  -> rereview gate evidence:[pytest]
       failed_evidence_route: correction
----

Once this topology was actually commissioned, P2 Integration Completion:

`RUN-26e233c979554260bcca8529d1b72c1f`

completed in two Hops:

* H001 integration;
* H002 independent review;
* trusted pytest PASS;
* accept;
* completed.

This is a key control observation:

> WFC can be operationally simple when the Commission accurately encodes the intended
> semantics.

Therefore the evidence does not support "multi-Hop WFC is inherently too complex."
It supports a narrower hypothesis: *authoring and maintaining coherent workflow
contracts is becoming the dominant source of friction.*

=== 4.6 Evidence-Failure-Disposition hardening itself required a three-Run lineage

The Evidence-Failure-Disposition-Hardening lineage required three fresh Commissions:

Run A:
`RUN-c661748adf434e74bcf0e15f2b05ff9f`

* implemented the core admission rule;
* trusted evidence routed to correction;
* correction reached an architecture-test/scope boundary;
* terminal `awaiting_human`;
* useful dirty work was separately salvaged.

Run B:
`RUN-98b556cacd9446539e04530406dc3a58`

* fresh successor;
* trusted evidence again routed to correction;
* later rereview returned semantic ACCEPT but omitted the required durable-artifact
  CommitIntent;
* Coordinator mechanically preempted;
* terminal `awaiting_human`.

Run C:
`RUN-65952de309aa4c4bb21a762640d64929`

* fresh narrow successor;
* closed the stale Harness fixture;
* completed in two Hops with trusted pytest PASS.

The accepted rule from this lineage is exactly the rule the 2026-10-11 P3 Commission
initially violated before its second PREPARE repair.

That temporal proximity makes the P3 failure especially useful evidence: a recently
accepted invariant was already difficult to carry consistently into the next
Commission.

=== 4.7 Durable-Artifact hardening was a clean two-Hop counterexample

The separate Durable-Artifact Completion-Handoff Hardening Run:

`RUN-b419abdd174143219ed8d9b6b42d92b5`

completed in exactly two Hops:

* H001 implementation:
  `0ab2063cc317bf12aa96eae8511f646ed1701001`
* H002 fresh independent review:
  `816f12ee89d85cf094ab3840eedc218a283a026d`
* trusted pytest PASS;
* no Findings;
* no anomalies.

This again shows that WFC's core evaluator/optimizer shape can be low-friction once
the surrounding Commission and phase obligations align.

== 5. Evidence-backed friction categories

=== 5.1 Commission-authoring knowledge is distributed

A correct Commission may need to reconcile, among other things:

* WorkItem authority;
* profile topology;
* repository policy;
* task prose;
* result-contract family/version;
* Finding lifecycle authority;
* route authority;
* evidence placement;
* failed-evidence routing;
* durable-artifact obligations;
* CommitIntent rules;
* historical replay compatibility;
* Runtime promotion state;
* previously accepted concepts and later hardenings.

Each item is individually reasonable.

The friction comes from the fact that correctness often depends on *cross-file
relationships* among them.

P1 and P2 establish that a Commission can be locally plausible yet globally unable to
complete.

=== 5.2 Semantics are repeated across multiple representations

The P3 session required the same design intent to appear in several forms:

* temporary research/curation note;
* permanent 599-line design record;
* WorkItem `authority_source`;
* 411-line task text;
* profile review-purpose prose;
* personas;
* policy/profile/work-item scope lists.

The persona overflow is a concrete symptom of this repetition.

This record does not claim that all repetition is removable. Some is defense in depth
or useful local context. It does establish that repetition is now large enough to
cause mechanical authoring failures.

=== 5.3 Guardrails are sometimes discovered too late in the authoring cycle

Both P3 provider-free refusals were deterministic and could, in principle, have been
identified before a human attempted PREPARE:

* persona >512 UTF-8 bytes;
* required evidence on a non-gate worker phase.

The second rule had been accepted immediately before P3 and was present in repository
history.

A simplification effort should investigate whether Commission authoring can consume
one canonical validator earlier, rather than relying on a later PREPARE attempt to
teach the author what current repository invariants are.

=== 5.4 Safe failure can still be operationally expensive

The system usually fails closed correctly.

Examples:

* authority escalation rather than silent scope widening;
* no trusted commit from invalid result disposition;
* open Finding blocks completion;
* missing required durable artifact causes preemption;
* invalid profile topology is rejected before provider invocation.

These are positive safety properties.

But each safe stop can require:

* human interpretation;
* salvage decision;
* new Commission;
* new attempt identifier;
* new archive/ledger entry;
* fresh review;
* Runtime promotion decision.

Safety and usability therefore cannot be evaluated independently.

=== 5.5 Human-in-the-loop interaction latency is a first-class cost

Maintainer session observation on 2026-10-11:

* Chat interaction: typically about 1--3 minutes.
* Claude task: often about 5--15 minutes.
* A planned "start the Run within ~30 minutes" window exceeded 45 minutes before any
  Run launched.
* Waiting time is not neutral: the maintainer starts reading or doing other work,
  causing another context switch before returning.
* The P3 Run then stopped `awaiting_human` after one Hop.

This means the effective cost of an extra orchestration step is not its CPU time.

A more realistic rough model is:

[source,text]
----
operational cost
  ~= LLM latency
   + human response latency
   + context-switch cost
   + state reconstruction cost
   + probability of another correction cycle
----

The system currently has no explicit metric for this cost.

=== 5.6 Interactive-assistant context saturation is a plausible additional risk

The maintainer has observed that long-lived assistant sessions tend to become less
operationally crisp over time.

Examples observed in the current interaction include:

* asking for `--help` before commands whose syntax had already been used repeatedly;
* additional verification rituals around familiar operations;
* needing an explicit reminder to use an LLM for ledger curation rather than
  dispatching many small `sed`/inspection commands;
* increased dependence on conversational history to remember which rules supersede
  older precedents.

This is not proven to be a model-context-window failure and should not be recorded as
one.

The supported conclusion is weaker:

> routine WFC operation currently benefits from a large amount of historical
> conversational context; that is itself an architectural smell for a tool intended
> to be operated and maintained by AI agents.

A desirable repository should let a fresh competent agent recover the next correct
action from bounded repository truth plus a small handoff, not from months of chat
history.

=== 5.7 Tool-to-domain carve-out may have left AI-unfriendly repository structure

WFC evolved from tool/script infrastructure into a standalone domain.

The code and governance model have matured significantly, but the repository's
information architecture still carries signs of incremental accretion:

* history-bearing concepts;
* FTRs;
* BUG records;
* WorkItems;
* task prose;
* profiles;
* policies;
* component definitions;
* run evidence;
* semantic ledger;
* Runtime clone state;
* operator state/OPS directories.

The concern is not the existence of these artifacts. It is whether the *canonical
source of each decision* is obvious enough that an agent can avoid reading and
reconciling several generations of equivalent or superseded guidance.

The maintainer additionally observes that WFC has grown to a substantial fraction of
the line count of the spreadsheet-handling repository it originally served. That LOC
comparison is not independently measured in this record and should be quantified
before being used as hard evidence.

== 6. Counterevidence: complexity is not uniformly harmful

Any simplification effort should preserve the parts that demonstrably work.

The ledger contains multiple clean bounded success cases:

* IOR-04: worker + reviewer, two-Hop acceptance.
* DMC Relation-Key Slice 2: worker + reviewer, clean first-review acceptance.
* FindingDelta compatibility-shim fix:
  `RUN-889559c681844c378c80c1ecc5975d7f`, two Hops.
* P2 Integration Completion:
  `RUN-26e233c979554260bcca8529d1b72c1f`, two Hops.
* Durable-Artifact Completion-Handoff Hardening:
  `RUN-b419abdd174143219ed8d9b6b42d92b5`, two Hops.

The worker/reviewer model has also caught real defects, including:

* datetime precision loss in DMC Relation-Key work;
* Finding immutability/echo mistakes;
* authority topology defects;
* salvage/publication and successor-provenance defects.

Therefore simplification must not mean "remove independent review" or "remove
fail-closed checks."

The more defensible target is:

> make the safe path easier to author, infer, validate, and operate.

== 7. Working hypothesis for later simplification

The current evidence supports the following hypothesis strongly enough to preserve,
but not yet strongly enough to authorize a redesign:

> WFC's dominant emerging complexity is not the basic Run/Hop evaluator-optimizer
> loop. It is the distributed specification and lifecycle machinery around that
> loop: Commission authoring, cross-artifact conformance, continuation/successor
> semantics, evidence/durable-artifact obligations, historical compatibility, and
> operator coordination.

A second hypothesis is:

> as more of these rules accumulate, the repository increasingly relies on an AI
> maintainer carrying historical context that should instead be mechanically
> derivable from a smaller set of canonical declarations.

Both hypotheses should be falsifiable by later measurement.

== 8. Suggested measurement before redesign

A future simplification effort should first establish baseline metrics.

For each bounded self-development WorkItem, record:

* wall-clock time from "maintainer decides to run" to successful PREPARE;
* wall-clock time to first provider invocation;
* number of human/assistant conversational turns before LAUNCH;
* number of separate LLM authoring/review tasks before LAUNCH;
* number of provider-free preflight refusals;
* number of consumed attempt identifiers before first launch;
* number of files in the Commission bundle;
* total Commission lines / bytes;
* duplicated scope/path declarations across WorkItem/profile/policy/task;
* number of repository documents an authoring agent had to inspect;
* number of post-Run successor Commissions caused by:
  ** product/code defects;
  ** Commission/profile topology;
  ** stale fixtures/tests;
  ** result-contract mismatch;
  ** operator/lifecycle mechanics;
* number of manual Runtime-promotion/archive/ledger steps;
* number of times useful uncommitted work required salvage;
* number of times a fresh agent/chat could not determine the next action from a
  bounded handoff.

The last metric is particularly important for AI-friendliness.

== 9. Candidate simplification principles -- non-authorizing

These are directions to investigate after current must-have capability work. They
are not accepted designs.

=== 9.1 One canonical semantic source, generated projections where practical

If the same scope, authority rule, or lifecycle fact is repeated in WorkItem,
profile, policy, task prose, and personas, investigate whether one representation can
be canonical and the others mechanically rendered or projected.

Do not remove independent policy ceilings merely to reduce duplication.

=== 9.2 Authoring-time validation using production validators

The P3 session suggests Commission authors should be able to run the same canonical
checks before committing or reserving an attempt.

Potential direction:

[source,text]
----
Commission draft
  -> canonical parse / admission / conformance validator
  -> exact diagnostics
  -> at most one targeted LLM repair
  -> valid Commission
----

This mirrors the already-considered Commission Compiler direction.

=== 9.3 Failed provider-free PREPARE should be cheap and unsurprising

Investigate whether:

* failed preflight should reserve an attempt identifier at all;
* PREPARE can be idempotent before a Run/state boundary exists;
* an explicit `validate`/`lint` operation should precede stateful preparation;
* the CLI can distinguish "invalid Commission" from "attempt lifecycle already
  consumed" more cleanly.

The correct answer is not assumed here.

=== 9.4 Bounded handoff as an architectural acceptance criterion

A useful simplification test:

> Can a fresh assistant session, given the repository plus a one-page current-state
> handoff, correctly identify the next operator action and prepare/launch a bounded
> Run without relying on earlier chat history?

If not, determine which required facts are missing, duplicated, or too difficult to
discover.

=== 9.5 Keep L0 boring

The desired steady-state operational experience remains:

[source,text]
----
select bounded WorkItem
  -> Commission already valid
  -> PREPARE
  -> LAUNCH
  -> 2--4 Hops autonomously
  -> completed or one explicit typed stop
  -> archive / semantic projection
----

The system should not require an expert human to continuously reinterpret its own
guardrails during ordinary runs.

=== 9.6 Separate safety complexity from presentation complexity

Some complexity is intrinsic:

* authority must remain explicit;
* historical evidence must remain immutable;
* replay/version identity matters;
* dirty or ambiguous Git state must fail closed;
* provider output cannot be trusted blindly.

Other complexity may be accidental:

* repeated prose restating the same rule;
* stale copied profile patterns;
* manually synchronized path lists;
* late discovery of deterministic schema/length constraints;
* lifecycle ceremony that could be mechanically derived.

Simplification should target the second class first.

== 10. Timing / sequencing observation

The maintainer's current preference is to finish the near-term must-have path before
making simplification the primary program:

[source,text]
----
P3
-> P3.5
-> P4
-> P5
-> provider-neutrality / Claude adapter dogfood
-> simplification as a primary priority
----

This is a planning observation, not an authorization for those slices and not a
requirement to postpone every local friction fix.

The purpose of preserving this evidence now is to prevent the later simplification
phase from starting from vague recollection.

== 11. Concrete questions for the later simplification review

A future review should answer at least:

. Which Commission fields are genuinely independent authority facts, and which are
  projections/restatements?
. Can invalid Commission combinations be made unrepresentable earlier?
. Can one typed Commission model render WorkItem/profile/policy/task projections?
. Which current prose exists because the agent needs it, and which exists only
  because earlier schemas were too weak?
. Can a Commission validator explain all current admission constraints without
  requiring PREPARE?
. Can failed validation avoid consuming an attempt identity?
. Can archive + semantic ledger projection be reduced to one operator action while
  keeping mechanical and semantic records distinct?
. Which Runtime-promotion decisions genuinely require a human?

== 12. Non-conclusions

This record does NOT establish:

* that WFC is over-engineered in every dimension;
* that the independent-review loop should be removed;
* that fail-closed behavior is too strict;
* that the P3 Run's current `awaiting_human` stop is itself a WFC defect;
* that long assistant context definitively causes model degradation;
* that repository LOC alone proves architectural complexity;
* that P3/P3.5/P4/P5 or the Claude adapter should be skipped;
* that a specific simplification architecture is already known.

It DOES establish enough repeated evidence to justify treating operational friction,
AI-maintainability, and specification duplication as first-class engineering
concerns rather than incidental inconvenience.
