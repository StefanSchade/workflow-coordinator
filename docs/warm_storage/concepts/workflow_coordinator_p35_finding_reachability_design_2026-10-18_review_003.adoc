=== P35DR-002 -- independent verification

==== Candidate predicate and source behavior

Design §4.3 now defines the schema-v2 candidate exactly as
`phase.review is not None and phase.review.blocking_policy == "blocking_only"`.
Neither `review.authority` nor a closing operation appears as an exclusion.
The current parser admits only `blocking_only` on a review descriptor
(`serialization.py:548-599`), so every currently parsed reviewed phase is
retained. This preserves Concept §11's reviewed-opener set without reviving
the earlier cross-version review-presence proxy: v3 remains evaluator-only,
and v4 uses its explicit declaration.

Current source independently supports that distinction. In
`reducer._finding_operation` (`reducer.py:470-486`), creating `OPEN` maps to
no disposition operation. `_apply_legacy_finding_deltas`
(`reducer.py:566-671`, especially `:588-596`) consults `_may_dispose` only
when an operation exists. Holding `resolve`, `residual`, or `supersede`
therefore does not revoke opening capability. `_may_dispose`
(`:489-498`) governs disposition separately, using the currently executing
gate's tuple selected in `reduce_result` (`:1693-1703`). Concept §11
requires a disposer strictly after the opening invocation. The design now
enforces that requirement rather than using the opening phase's closing
tuple to remove its creation event.

The documented review-less-worker under-approximation remains explicit in
§§2.5, 4.7 and 6.1; it was already assessed in the predecessor record. This
correction does not present it as full legacy-engine precision, and supplies
no new material evidence requiring that separate boundary to be reopened.

==== H005 one-phase counterexample -- rejected by the origin arm

[source,text]
----
schema v2:
p [review:gate, blocking_policy:blocking_only,
   finding_authority:[resolve]] --C-->

creates_blocking(p) = True
disposer(p) = True
checkpoint(p) = True
UnguardedEdges = {}
danger(p) = False                  # disposer absorption
----

Section 4.5 tests `creates_blocking(p) and checkpoint(p)` independently of
`danger(p)`. Both operands are true, so the profile is *REJECTED*. Its
own resolve capability cannot erase the opening checkpoint. No later
invocation exists and none is invented. Changing the tuple to empty,
residual-only, or supersede-only leaves the origin rejection intact.

This was also checked with an in-memory, structurally parsed profile and a
recorded `REVIEW_VERDICT` v1 contract identity. A new open blocking Finding
plus the completion request stopped the existing reducer at `p` with
`completion_blocked_by_open_blocking_findings`. No same-result guessed ID
or disposition was used. The runtime observation confirms the legacy
failure being caught; the rejection above follows from the written static
rule, not from crediting the runtime guard as a static solution.

==== H005 two-phase counterexample -- rejected by propagation

[source,text]
----
schema v2:
p [review:gate, blocking_policy:blocking_only,
   finding_authority:[resolve]] --G-->
finish [review:null] --C-->

creates_blocking(p) = True
checkpoint(p) = False
disposer(p) = True
creates_blocking(finish) = False
disposer(finish) = False
checkpoint(finish) = True
danger(finish) = True
UnguardedEdges = {(p, finish)}
----

Section 4.5's successor arm is true for opening phase `p`, because its
successor `finish` has `danger=True`. The profile is *REJECTED*, with
witness `p -> finish`. `danger(p)=False` does not excuse this origin:
the rule queries the later successor, not the opener's absorbed value.
The earlier authority at `p` cannot dispose a Finding carried undisposed
to `finish`.

The separately parsed two-phase reducer probe advanced from `p` to
`finish` with the new blocker still open. The next invocation, recorded
as `WORK_RESULT` v1 and proposing no Finding delta, stopped with
`completion_blocked_by_open_blocking_findings`. Empty, resolve-only,
residual-only, and supersede-only opening tuples all produced the same
two-invocation failure. The intermediate phase cannot create under the
candidate rule, but carried-Finding propagation correctly remains active.

profiles, all schema v2*. Each has a reviewed `blocking_only` phase with
a local `COMPLETE` route. Every profile therefore meets §4.5's origin arm,
establishing *43 rejections / 0 acceptances* directly, without implementing

Sections 6.1, 6.3, 8 and 10 item 1 consistently state those counts. The
eight Concept-named fixtures and eleven additional historical fixtures

evidence-admission assertions while requiring reachability to be exercised
independently. The former 19/23 sentinel inventory appears only as rejected

The new-launch consequence is now explicitly reconciled with Concept §19:
historical parsing, replay, and fixture use are preserved; the ordered
property in §11 is applied to every covered opener. The named
empty-authority shape is a required invalid instance, not an exhaustive
safe/unsafe partition that exempts a resolve-capable creating checkpoint.
The other profiles independently violate the same ordered property at
their opening checkpoints. Sections 6.1 and 6.3 consequently require their
new-launch assertions to change too; they do not promise those profiles
still pass merely because they once had closing authority. Explicit
noncreation declarations or a topology satisfying later disposition require
separately commissioned migration. No governing-policy edit or profile
migration is smuggled into this design review.

The unchanged v3 rule includes tracked evaluator creation. The standard
`profile_v3_data` fixture was freshly parsed: `evaluate` has convergence
role `EVALUATOR`, dispatches generic result v2, and has a local completion
route. It is therefore rejected by the origin arm even with closing
authority, as §8 requires. Current `_apply_v2_finding_deltas`
(`reducer.py:674-789`) restricts new blockers to evaluators and attaches
their correction obligations; ordinary Run-v3 creation is separately
rejected by `_validate_convergence_records_before_apply` (`:1285-1293`).
The earlier falsified v3 ordinary-review proxy is not reintroduced.

=== P35DR-001, P35DR-003, and P35DR-004 -- preserved closures

The correction diff and exact section comparisons confirm that §§4.4--4.6,
§§3.1.1--3.1.2, §6.2, §5.1 and all of §7 are unchanged. Their predicates
and worked outcomes were checked against the new candidate rule:

* *P35DR-001:* the opener's local checkpoint remains a separate rejection
  arm; a later revisit can still be absorbed by `disposer`. For a
  resolve-capable creator with only an unguarded self-loop, the origin
  checkpoint is false and the later successor's danger is false, so the
  loop remains accepted. Adding a local completion alternative makes the
  origin arm true and rejects it. Budgets remain irrelevant. Newly created
  supersession successors remain independent origins.
* *P35DR-003:* v4 remains the ordinary v2-derived grammar, with required
  creation booleans, no convergence block, `ConvergenceRole.NONE`, Run v2,
  and ordinary result v1. Existing `new_run` and `result_contract_version`
  (`model.py:684-702`, `:854-884`) support the stated lineage extension;
  v3 remains separate, with no implicit migration or capability override.
* *P35DR-004:* example 1 remains accepted as v4 with no creators, rejected
  as v2 by its reviewed completion gate, and accepted for its ordinary v3
  component. Examples 2, 4 and 5 retain a later absorbing disposer and
  explicitly noncreating closure phases; example 3 propagates danger from
  `complete_gate` and rejects. Example 6's guarded source is noncreating
  and disposing, so its stated preflight acceptance and two runtime
  outcomes agree. Example 7 independently checks successor creation;
  example 8 still has no checkpoint and is vacuously accepted. The
  origin-versus-propagation diagnostics in §5.1 still describe the correct
  witnesses. All default examples remain explicitly ordinary v4; none
  relies on the removed schema-v2 authority exclusion.

The necessary knock-on change is the schema-v2 inventory and associated
