[[h001-budget-stop]]
=== Blocking finding -- name the implemented budget-exhaustion state

Location:: `docs/operator_manual/ch05_self_development/01_topology_budget.adoc:82-86`, especially line 85.
Required invariant:: The normative self-development budget guidance must agree with the implemented budget mechanics and existing tests, as required by FTR05 section 5 and acceptance criteria 4-5.

The new normative section says the authorized ceiling is the number of Hops
before an unfinished Run stops `awaiting_human`. The implemented value for
exhaustion while another invocation is needed is `awaiting_human_budget`,
with `stop_reason=autonomous_hop_budget_exhausted`:

* `src/workflow_coordinator/model.py:130-131` defines `AWAITING_HUMAN` and
  `AWAITING_HUMAN_BUDGET` as distinct serialized states.
* `src/workflow_coordinator/reducer.py:1806-1819` chooses
  `AWAITING_HUMAN_BUDGET` when a goto/supervised continuation would exceed
  the budget.
* `tests/unit/test_operator.py:2488-2517`,
  `test_n2_serial_driver_uses_fresh_context_and_never_allocates_h003`,
  explicitly expects `result.status.value == "awaiting_human_budget"`
  after the second Hop and no third dispatch.

This is an operational state distinction, not a preferred phrasing:
`operator.py::_predecessor_for_successor` at lines 1460-1464 requires
`AWAITING_HUMAN` together with a frozen semantic stop, so an exhausted
budget must not be represented as that semantic-stop state or assumed to
have its continuation eligibility. The incorrect token was inherited from
the old self-development source; FTR05's mandatory code re-verification
still applies to the new normative owner.

Bounded correction: identify the budget stop accurately in the new ch05
budget subsection (the explicit state and, if useful, its stop reason),
without implying automatic continuation or successor eligibility. Preserve
the provisional recommendation, ceiling constraints, and ch02 ownership of
general mechanics. No ch01-ch04, code, test, recovery contract, or product
change is requested. Recheck that statement against the cited code/test,
then use focused rereview followed by a fresh broad review. No
implementation correction was performed by this reviewer.
