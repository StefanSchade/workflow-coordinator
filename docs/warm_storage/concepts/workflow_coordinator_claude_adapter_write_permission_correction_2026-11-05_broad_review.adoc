= Claude adapter write-permission correction: implementation handoff

== Diagnosis and evidence

The most plausible mechanism is the recorded environment-scrubbing
override of `acceptEdits`, with moderate confidence. The bug record reports
the CLI's literal warning that scrubbing forced default mode, and the adapter
sets the scrub variable while requesting `acceptEdits` and no prompts. The
installed Claude Code 2.1.270 `--help` says that `--permission-prompts none`
denies actions that would prompt. These facts fit the observed file-tool
denial; they do not prove that it caused that denial. The alternative missing
sandbox write-scope hypothesis, including directory creation behavior, is not
ruled out. Help describes `--allowed-tools` as allowing named tools, and
`--restricted` as confining file tools to working directories; it does not
establish the detailed interaction of these settings with scrubbing.

== Candidate

The generated settings add only `permissions.allow: ["Edit"]`, intended to
grant file edits without depending on `acceptEdits`. The resolved repository
is the subprocess working directory, with no additional working directories;
restricted mode supplies the provider-side file-tool boundary. The existing
read allowance also uses that resolved root. No general Bash approval or
additional sandbox write grant is added: neither is established as necessary
by the observed mode override, and a general Bash grant would be broader.
The existing sandbox, network, read-denial, scrub, and closed-profile settings
remain intact. The applicable security invariant is recorded in full in
link:../../backlog/BUG-WFC-CLAUDE-ADAPTER-WRITE-PERMISSION-MISMATCH.adoc#security-invariant-must-hold-under-any-future-correction[the bug record's Security invariant section]; the settled repository-root provider boundary and WFC's authoritative post-Hop scope check are described in `docs/architecture.md` and `docs/self-development.adoc`.

The fake-executable regression checks the generated edit grant, scrub,
restricted mode, resolved working directory and read root, and absence of an
additional working directory or filesystem write allowance, including a
symlinked repository input. It checks the transmitted configuration, not
the provider's actual enforcement or permissions semantics.

== Residual uncertainty

The explicit `Edit` rule is the smallest candidate for the observed
mode-override mechanism, but whether it also permits `Write` and creation of
missing parent directories under this exact CLI profile is unconfirmed. Bash
`mkdir` may still be denied; an independent sandbox write restriction may
also prevent the intended operation. Only the separately authorized
live-provider qualification can establish an authenticated worker's
end-to-end creation and write in an authorized missing subdirectory and the
negative case outside the phase scope, including WFC candidate acceptance.
No authenticated provider was invoked here, and this candidate does not claim
the live issue is conclusively resolved. This handoff is for deterministic
implementation review, not live-provider qualification.
