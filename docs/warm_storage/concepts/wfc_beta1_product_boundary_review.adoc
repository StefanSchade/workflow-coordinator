== Executive assessment

*The engine is already a payload-agnostic Level-0 runner. Everything a third
party would touch is not.* That is the whole finding, and it reverses the
intuitive reading of the backlog.

* *[V]* The execution engine (`src/workflow_coordinator/`, 12.6k lines) contains
  no repository name, no governance path and no test command. `operator._preflight`
  takes `--repository` plus five repository-relative governing inputs, reads
  them from Git at `--expected-head`, and admits any `evidence_commands` argv
  the consumer's policy authors. A grep of the package for self-development
  paths, `pytest`, repository names or `Path.home()` finds exactly one module
  with such constants -- `commissioning.py` -- plus one adapter scratch default.
* *[E]* This is not theoretical. In September the same engine ran against the
  `latein` content repository with governing files under
  `docs/ai_info/workflows/dogfood/latin_story02_c0/`, components `AGENTS.md`
  and a didactics document, and trusted evidence `make check-story STORY=2`,
  `make check-vocab`, `git diff --check`
  (`archive/foreign-domain-dogfood/latin-story-02/latin-story02-c0-20260929-03/run/operator-plan.json`
  and `ops/launch.sh`; ledger entries "Latin Story-2, attempt 01-03"). It also
  ran against the `core` library (ledger `dogfood` entries). *A non-Python
  consumer has already been operated.*
* *[V]* What a third party cannot use is the layer built since: the Front Door
  compiler hard-codes four `governance/...` paths and one literal policy record
  including `scope == ("workflow-coordinator",)` and
  `argv == ("python","-m","pytest","-q")`; the Operator Harness is an
  unpackaged script that demands a Runtime clone, an Evidence clone and a
  `pip install <payload>[dev]`; the workflow programs and role prompts are not
  in the wheel; the archiver lives in a sibling repository.

So WFC was *more* consumer-neutral in September -- hand-authored bundle, raw
`wfc` flags -- than its Front Door is today. The Front Door bought something
real for that: closed programs instead of hand-authored profiles, whose own
inventory later rejected all 43 (*[E]* `docs/backlog/_open.adoc`, P3.5 card).
Beta 1 has to recover neutrality *without* reopening hand-authored profiles.

*Maturity.* Trusted mechanics (admission, scope observation, `trusted_commit`,
evidence, Findings, stop routing) are mature and heavily exercised: about 100
ledger entries, 113 archived manifests. Product surface is pre-alpha: `pip install`
yields a `wfc` whose only interface is the raw engine flags; nothing can
initialize a project, compile a Commission, prepare, show status by attempt or
archive.

*Principal obstacles, in order of cost:*

. No installable Front Door: Harness and compiler entry live in
  `scripts/wfc_op.py`, outside the package (`pyproject.toml` packages only
  `workflow_coordinator*`).
. Compiler constants bind every Commission to WFC's own repository identity,
  layout and Python test command (`BUG-WFC-EVIDENCE-COMMAND-CONSUMER-NEUTRALITY`
  names one of the four; the other three are the same defect).
. Harness `prepare` encodes the Runtime-N/Development-N+1 topology and a Python
  payload as unconditional preconditions.
. Product-owned assets (programs, role prompts) and the archiver are not
  shipped with the product.
. No test anywhere exercises the Front Door against a repository that is not
  WFC itself.

*Size of the gap [R].* Four medium work packages plus a gate (§7). No engine
redesign, no new governance layer, no new authority format. The largest risk is
not technical; it is spending Beta-1 capacity on engine neutrality that already
exists, or on the Operator Manual series, which documents the self-development
path a third party will never take.

=== Product-level limits a consumer will meet (not self-development assumptions)

* *[V]* Evidence timeout hard ceiling 900 s
  (`model.COORDINATOR_HARD_MAX_EVIDENCE_TIMEOUT_SECONDS`). A consumer whose
  full suite exceeds 15 minutes cannot use it as `task-check`.
* *[V]* One adapter per Run (`operator._preflight`: "mixed execution adapters
  are incompatible with the single scalar executable"). Worker on Codex with
  reviewer on Claude is not expressible.
* *[V]* Scope operands may not be the repository root (`serialization.a1_path_shape`;
  `tests/unit/test_a1_admission.py::test_a1_rejects_repository_root_for_every_operator_operand`).
  Root-level files (`go.mod`, `package.json`, `README.md`) must be listed individually.
* *[V]* Agents have no network under the Claude adapter (`network.allowedDomains: []`,
  `WebFetch`/`WebSearch` denied); *[E]* already decided to be a gap
  (`FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY`).
* *[V]* Commits land on the checked-out branch of the working repository, with
  a Conventional-Commit subject carrying WorkItem and Hop IDs. A consumer's own
  commit convention cannot override this.
* *[V]* The working tree must be clean, including untracked files, at launch.

The one new file, `.wfc/config.yaml`, has a concrete reason: the values it
holds are today required command-line arguments of `wfc_op.py prepare`

=== The agent contract and prompt composition

`prompt.assemble_prompt` composes, in order: identity header -> contract ->
selected components (role, modifier, repository-policy) -> `[persona_guidance]`
-> `[workflow_policy]` -> `[task]` -> context/diff -> result-contract footer.

*Contract v6 is universal.* *[V]* Read clause by clause, it names no
repository, language, tool, path or phase; it states explicitly that "no
particular phase name or route is implied by this contract" and that consumer
material "may narrow them but may not widen, replace, disable, or contradict
them". Two clauses do impose on the payload and should be documented as product
behaviour rather than changed:

* the Conventional-Commit subject with WorkItem and Hop ID (enforced
  independently by `trusted_commit` via `commit_subject_error`);
* the prohibition on agent-owned mutating Git.

*The role components are mostly universal, partly self-development flavoured.*
*[V]* `governance/self-development/prompts/`:

* `worker.txt` §2 (do not end the invocation merely because work is unfinished;
  `blocked` only for a concrete obstacle) is `robust@v1` role semantics, not
  project guidance -- *[E]* it exists because of the Terra `blocked` Runs
  (ledger "Operator Manual consolidation planning 001/002").
* `worker.txt`/`reviewer.txt` offline paragraph is adapter-environment
  guidance phrased around "nested package installation or build-isolation";
  the rule is general, the example is WFC's own pip problem.
* `worker.txt` "Preserve the accepted architecture" is generic.
* `simple-self-check.txt` is universal program semantics.

None of this is payload material. Where they live (`governance/self-development/`)
is the only self-development assumption about them.

*Precedence is already correct.* Project guidance and persona enter as consumer
material below the contract; the contract says they cannot widen it; the
reducer and `trusted_commit` enforce authority regardless of prompt text.
Nothing new is needed to keep project instructions from overriding product
invariants.

=== How product-owned records reach a payload repository

The engine reads every governing input, including components, from the payload
repository's Git tree at the expected HEAD. The compiler reads program and
policy from pinned commits in the same repository and compares the program to
its in-code literal. Two ways to deliver product records follow.

Materialize (recommended for Beta 1) *[R]*:: `wfc init` writes the product's
program records and role prompts into `.wfc/` and the compiler keeps doing what
it does today: read the pinned copy, require equality with the packaged
literal. Role prompts gain the same equality check programs already have.
Intent schema v1, `render-manifest.json`, `_preflight` and governing-digest
provenance are untouched; only the four paths become configurable. Cost: `.wfc/`
holds about six product files; upgrading WFC means re-materializing them.
Benefit: the exact bytes that governed a Run stay in the payload's own history.

Resolve from the package (later):: The compiler uses packaged records directly;
Intent drops `source_commit` for program and components. Cleaner for the user,
but it changes the Intent schema, the manifest and the engine's component
resolution -- exactly the version advance
`FTR-WFC-CONTRACT-HISTORICAL-RECONSTRUCTABILITY` is waiting for.

Do not build both. This is open decision D1.

=== Project guidance

*[V]* Every phase already has a `repository_policy` component slot
(`prompt._selected_ids`); all three program records leave it empty. *[R]* Bind
it at compile time from a list of payload file paths in `.wfc/config.yaml`,
exactly as scope `S`, artifact `A` and evidence `E` are bound today. Program
semantics -- roles, routes, review descriptors, Finding authority, actions --
do not change. *[V]* A selected component is a governing input: `_admit_a1`
requires its path inside `policy.governance_paths` and forbids any phase scope
from overlapping it. A guidance file therefore cannot be edited by a Run that
uses it, and a Run scoped to its parent directory is refused -- as in the Latin
policy, which lists `AGENTS.md` as a governance path.

Whether filling a slot the literal record shows as `[]` is a
binding or a new program revision is a labelling question for the maintainer
(D1 covers it). If that is contentious, Beta 1 can ship without it: persona
strings plus task text carried the September Runs, and the catalogue record
itself says a correction is a new revision.

=== Worthwhile usability improvements (not gates)

. Capture a bounded untrusted tail when an evidence command times out, as the
  `fail` branch already does. Today the timeout branch kills, closes the pipes
  and records nothing (`ProductionEvidenceRunner.observe`). A first user whose
  test command hangs gets `timeout after 900s` and no clue.
. Actionable message when an evidence executable does not resolve
  (`BUG-WFC-EVIDENCE-COMMAND-RESOLUTION-DIAGNOSTICS`). Non-Python users will hit
  this on the first `wfc run` with a toolchain not on `PATH`.
. Non-writing preview for render (`BUG-WFC-COMMISSION-RENDER-CHECK-WRITES-BUNDLE`);
  `wfc run` needs it to show a plan before committing anything.
. Standard clause in the generated task text asking for leaf-exact
  `CommitIntent` paths, until `BUG-WFC-COMMIT-INTENT-DIRECTORY-PATH-RECONCILIATION`
  is decided. *[E]* A well-formed directory-shaped intent stopped a Run
  (ledger "Nested Claude-in-Bubblewrap Qualification").
. Known-good bindings in the quickstart. *[E]* Worker completion is
  model-dependent: Terra `blocked` 3/3, Sol 2/2 and Sonnet 1/1 completed
  (ledger external experiment 2026-11-11).
. `wfc status` without an argument resolves the latest attempt for the current
  repository by scanning preparation records; include a repository slug in
  generated attempt names so two projects cannot collide under one `$HOME`.

== Deferred capabilities

*Later -- Level 1 (convenience, recurring use)*

* Task and Intent templates; `wfc config` commands; model aliases or presets.
* Packaged-record resolution and Intent schema v2 (§3.3).
* Mixed adapters per Run (cross-provider independent review).
* Additional named evidence commands and evidence profiles; today's programs
  admit exactly one, `task-check`. A project wraps several checks in one script.
* Agent network capability (`FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY`).
* Token-consumption evidence, unless reconfirmed as a gate (D6).
* Raising or parameterizing the 900 s evidence ceiling.
* Successor-Commission ergonomics, phase-entry continuation, `direct@v1` reconciliation.
* Curated ledger tooling; archive query helpers.
* Operator Manual FTR06-10 (self-development recovery, successors, walkthrough).

*Future -- Level 2*

* Task decomposition, sequencing, difficulty evaluation, workflow and model
  selection, adaptive execution; Front Door Advanced (`DEC-WFC-021`).

*Explicit non-goals for Beta 1*

Environment provisioning or build-system detection; dynamic or phase-specific
model routing; additional reviewer roles; a workflow designer or user-defined
programs; a plugin or storage-backend system; a new governance layer; P3.5,
P4, P5; convergence-escape Slices 5/6; WFC-owned execution isolation; a general
kernel/package refactor.

*Interface boundaries worth preserving now, and nothing more:*

. the Intent file as the single machine-submittable Commission contract;
. execution bindings outside the Commission, keyed by role, each carrying its
  own `adapter` (the record is already forward-compatible with mixed adapters);
. `status --json` and process exit codes as the read interface;
. the mechanical manifest as the audit record.

== First-user walkthrough

Proposed UX, not existing behaviour. Consumer: `tidemark`, a Go command-line
tool; tests `go test ./...`; no Python in the repository. WFC needs Python
>= 3.10 on the operator's machine only.

*Install*

[source,shell]
----
pipx install workflow-coordinator==0.1.0b1     # or: uv tool install ...
wfc --version
----

*Initialize*

[source,shell]
----
cd ~/src/tidemark
wfc init
----

[source,text]
----
.wfc/
  config.yaml              defaults: bindings, executable, timeouts, PATH, archive, paths
  policy.yaml              project authority: scope ceiling, governance paths, task-check
  product/                 managed by wfc; verified against the installed version
    programs/simple/v1.yaml
    programs/robust/v1.yaml
    components.yaml
    components/worker.txt  reviewer.txt  simple-self-check.txt
----

`init` asks nothing and detects nothing. The user makes two edits in
`policy.yaml` -- the scope ceiling and the check -- and one in `config.yaml`:

[source,yaml]
----
# .wfc/policy.yaml  (existing RepositoryPolicy schema v3)
schema_version: 3
policy_id: tidemark
revision: "1"
scope: [tidemark]
governance_paths: [.wfc/config.yaml, .wfc/policy.yaml, .wfc/product, .wfc/commissions,
                   .wfc/archive, docs/ARCHITECTURE.md]
work_item_scope_ceiling: [cmd, internal, docs, README.md, go.mod, go.sum, .wfc/reviews]
max_autonomous_hops: 10
actions: [edit, commit, review]
evidence_commands:
  task-check:
    argv: [go, test, ./...]
    timeout_seconds: 600
----

[source,yaml]
----
# .wfc/config.yaml  (defaults only; grants nothing)
default_program: robust@v1
executable: claude
invocation_timeout_seconds: 1800
bindings:
  worker:               {adapter: claude_cli, model: claude-sonnet-5-5, reasoning: high}
  independent_reviewer: {adapter: claude_cli, model: claude-sonnet-5-5, reasoning: high}
personas:
  worker: "Go engineer for a small CLI; idiomatic, table-driven tests, no new dependencies."
  independent_reviewer: "Adversarial Go reviewer; verifies behaviour against the task, not the diff."
project_components: [docs/ARCHITECTURE.md]
archive: {mode: local}        # or {mode: external, repository: ../tidemark-evidence}
----

`.wfc/reviews` is deliberately not a governance path: A1 forbids any phase
scope from overlapping one, and the reviewer must be able to write its
artifact. `.wfc/archive` deliberately is one, so no phase can ever be scoped
onto it. `docs/ARCHITECTURE.md` is one because it is selected as guidance; the
consequence is that a Run scoped to all of `docs` is refused until the
guidance file moves or the scope is narrowed.

[source,shell]
----
git add .wfc && git commit -m "chore: initialize wfc"
----

*Run*

[source,shell]
----
wfc run --task ~/tasks/list-json.md --scope cmd/list --scope internal/render
----

The task file is plain Markdown; an `## Acceptance` section, if present,
becomes the Intent's acceptance text. Scope is stated per Run; there is no
implicit default to the policy ceiling. The two review-artifact paths are added
to the Intent scope by the Front Door, as today's Intents list them by hand.
`wfc run` then, deterministically:

. writes `.wfc/commissions/list-json-001/intent.yaml`, with program, policy
  and component pins at the current HEAD, and renders the bundle;
. commits exactly that directory (`commission: list-json-001`) and runs the
  admission check on the clean tree;
. prepares: pins HEAD, records the installed WFC version, resolves `go` on the
  frozen `PATH`, writes OPS;
. prints the effective Run and stops for confirmation:

[source,text]
----
PREPARED / NOT LAUNCHED   attempt tidemark-list-json-001-20261112-01
program     robust@v1      hops <= 8
scope       cmd/list, internal/render
review      .wfc/reviews/list-json-001/broad_review.md, focused_review.md
task-check  go test ./...  (/usr/local/go/bin/go, 600 s)
worker                claude_cli  claude-sonnet-5-5  high
independent_reviewer  claude_cli  claude-sonnet-5-5  high
branch      feature/list-json @ 4c1e9a2   (WFC commits here; never pushes)
Launch? [y/N]
----

`y` is the authorization. The Run executes implement -> broad review ->
(correct -> focused review -> renewed broad review) -> accept.

*Inspect*

[source,shell]
----
wfc status            # latest attempt for this repository
git log --oneline     # feat(list): WI-LIST-JSON-001 H001 ... / docs(review): ... H002 ...
cat .wfc/reviews/list-json-001/broad_review.md
----

`status` shows run status, hops used, stop reason, final HEAD, worktree
cleanliness and the trusted `task-check` observation. Trusted evidence is the
Coordinator's observation in STATE, not the agent's summary.

If the Run stops instead of completing -- `awaiting_human` with an escalation,
a failed `task-check` after the hop budget, a dirty tree after an invalid
`CommitIntent` -- `status` shows the reason. Beta 1 offers no resume: the user
keeps or discards the working-tree state and issues a new `wfc run`. This is
today's successor model (`DEC-WFC-014`) without its ergonomics.

*Archive*

[source,shell]
----
wfc archive --dry-run
wfc archive
----

Local mode copies the allow-listed Run and OPS files to
`.wfc/archive/tidemark-list-json-001-20261112-01/`, writes `manifest.json`,
and makes one commit touching only that directory. External mode does the same
in the configured repository. Nothing is pushed.

Friction this walkthrough exposes, stated plainly: three YAML edits before the
first Run; root files must be listed one by one; the agent cannot `go get`;
the tree must be completely clean, so the task file cannot sit untracked inside
the repository; a guidance file locks its own path against the Run; a stopped
Run means starting over with a new Commission.

== Critical objections

. *The engine does not need neutrality work.* The review assignment suspected
  engine-level obstacles (source resolution, pinning across repository
  boundaries, Python assumptions). They are not there. Engine work for "payload
  agnosticism" would be effort spent on a solved problem.
. *`wfc init` is not analogous to `git init`.* `git init` needs no decisions.
  WFC cannot run without a scope ceiling and a check command, and detecting
  either is the provisioning framework Beta 1 excludes. Promise "one
  command and three edits", not zero configuration.
. *`wfc run --task task.md` can hollow out the product.* WFC's value is bounded
  authority. A one-liner with a default scope equal to the whole ceiling and
  boilerplate withheld-authority text turns that into decoration; scope should
  be stated per Run. The pre-launch summary and the explicit confirmation are
  not UX polish; they are the authorization act itself. Do not add `--yes` as a default.
. *Local archive in the payload repository is riskier than it looks.* *[V]*
  Manifests and `operator-plan.json` contain absolute paths (`/home/<user>/...`),
  model bindings and role personas. Committing them to a shared or public product
  repository leaks them and adds agent bookkeeping to product history. Also,
  the Runs most worth archiving are stopped ones, whose tree is dirty, while
  the wrapper today requires a clean destination repository. Local mode needs
  destination-only staging in a dirty tree and a decision on committing at all (D3).
. *Moving the archiver trades a hardened script for a port.* Three review
  rounds went into the wrapper. The move is justified -- a product capability
  cannot live in a sibling repository -- but only if the existing tests move
  first and semantics do not change in the same step.
. *Do not turn the Runtime/Development/Evidence topology into product
  configuration.* A `runtime_repository` option in `.wfc/config.yaml` would
  export a self-development safety construct to users who have no use for it.
  It stays a specialization.
. *Personas and project guidance invite a framework.* One string per role and
  one list of file paths cover the requirement with mechanisms that exist.
  Persona libraries, inheritance or per-phase guidance are Level 1 at best.
. *Role-based binding is sufficient; note what it does not give.* Keeping one
  `independent_reviewer` role for broad and focused review is right and costs
  nothing: bindings are keyed by role. But "independent" in Beta 1 means fresh
  context, not a different model or provider -- same-model review is permitted
  (*[E]* the FTR05 correction Run bound Sol to both roles) and cross-provider
  review is not expressible. Say so in the quickstart rather than implying more.
. *The historical test file is a burden, not a blocker.* Pruning it would feel
  like progress and change nothing a third party sees. Only relocation of the
  stranded invariants and a neutral compiler fixture are on the path.
. *Redesigning evidence-failure semantics is not justified.* One unexplained
  timeout in WFC's own suite, recovered by the ordinary successor route.
. *The Operator Manual series is on the wrong path for Beta 1.* *[V]* Its
  stated audience is "a maintainer ... to operate a WFC self-development Run".
  FTR06-10 are sequenced strictly, and FTR01-05 each took at least one
  `robust@v1` Run. None
  of it helps the first external user; a two-page quickstart does.
. *Token-consumption evidence as a release gate is weakly justified.* It is
  recorded as MUST-HAVE (2026-10-21 §5) but no third party is blocked without
  it, and it has no design yet. Reconfirm or demote (D6).
. *Technically riskiest step: the Harness move while it is in use.* Self-
  development is how WFC is built. Moving `wfc_op.py` into the package while
  Runtime N still expects the old arrangement can break the loop that produces
  the fix. Keep `scripts/wfc_op.py` working throughout (D7).
. *Front Door commits are a second Git write surface.* `trusted_commit` is
  "intentionally the sole Coordinator Git write surface". The Commission commit
  in `wfc run` and the local archive commit are outside a Run and human-
  authorized, so the invariant holds as worded -- but they must be equally
  narrow: explicit path set, refuse anything staged, never push.
