= P3.5 requirements-archaeology reassessment
:toc:
:sectnums:

== Commission conclusion and reader's map

*Conclusion shape: replace or narrow the invariant.*  The record supports an
*ordered, legally selectable later disposition opportunity* for each phase
that can open (or leave carrying) an open blocking Finding.  It does not
support elevating that opportunity into the accepted design's unconditional
requirement that *every* forward checkpoint-reaching path contain a later
disposer.  The original incident is a linear absence-of-any-opportunity;
the historical order counterexample establishes ``strictly later'', but not
the additional universal branching constraint.  Existing reducer completion
protection remains a separate stateful backstop.

* Section A (<<archaeology>>) identifies `f31a423` as the earliest supported
  introduction of the unconditional every-forward-path wording and separates
  its documentary source from interpretation.
* Section B (<<fidelity>>) tests the candidate requirement against the actual
  S3-002 linear profile and worked branching, carrying, loop, and selectability
  cases.
* Section C (<<placement>>) locates a static topology check at the parsed
  profile / operator-preflight composition boundary, if the maintainer adopts
  one.
* Section D (<<previous>>) independently re-evaluates the four deferred
  components and the reported 43/43 inventory.

This is a recommendation for the still-pending P3.5 decision only.  It does
not amend the accepted design, migrate a profile, close the BUG, or prescribe
route substitution or reducer repair.

== A. Historical archaeology [[archaeology]]

=== Documentary chain

The initial Concept was introduced at `37cf58c` and P3.5 was added/refined at
`965d14d` (Git commit metadata and diffs).  At `965d14d`, Concept §11 stated:
``if a reachable workflow state can carry an open blocking Finding into a gate
whose successful route requires disposition of that Finding, some phase on
every path to that gate must possess`` the needed operation.  That is both
conditioned on a particular gate needing disposition and does not say that the
authority must occur after the opening invocation.  It is not the present
unconditional formulation.

The observed BUG is likewise narrower than a branching rule.  Its factual
trigger is the linear `review -> correct -> rereview -> accept -> complete`
topology: S3-002 opened three Findings, correction had no review authority,
and `rereview` had `finding_authority: []` and could not close them
(BUG, ``Observed behavior (S3-002 factual trigger)'').  The historical-evidence
paragraph says the same empty tuple was latent in S1/S2/S3-001 because no
Run-native blocker had previously been created.  The actual cited YAML confirms
`review` and `rereview` are gate/blocking-only phases with empty authority and
their routes are `accept: complete` and `correct: goto correct` respectively
(`governance/self-development/...-s3-002-profile.yaml`, phases `review`,
`correct`, and `rereview`).  Neither the BUG nor that YAML describes a branch
with one safe disposer route and one disposer-free completion route.  Thus it
is direct evidence for a missing later opportunity on one linear continuation,
not direct evidence for rejecting a profile merely because an alternative
continuation is uncovered.

The decisive textual change is `f31a423`, ``docs(wfc): correct P3.5
conformance criteria''.  Its full commit message attributes the Section-11
change to review_001 finding 4.2, and its diff replaces the conditional
`965d14d` property with: for every `P_open`, and *for every forward path* that
may reach a completion/accept gate while the Finding remains open, a phase
*strictly reachable after* `P_open` on that same path must dispose it.  This is
the earliest located documentary introduction of the current unconditional
all-path rule.  It was accepted as part of the corrected Concept by that
development act; later design acceptance is acceptance of the then-current
Concept, not independent original-requirement evidence.

Review_001 §4.2 supplies the stated justification.  Its counterexample is
linear: `independent_review [resolve] -> correction [none] -> rereview [none]
-> accept -> complete`.  The old membership language counted the opener's
`resolve`, even though its invocation had already executed.  The review's
smallest recommended correction says ``for every forward path'' and ``strictly
reachable after''.  The counterexample demonstrably requires the latter
ordering repair.  It does *not* distinguish a profile with no later disposer
at all from a branch where a later disposer is legally selectable on another
route: it has only one continuation.  Therefore the documentary evidence
establishes why `f31a423` used the broader words, but does not establish that
the broader quantifier was necessary to cure §4.2's false negative.  A
condition-preserving correction could instead have required a strictly later,
legally reachable disposition opportunity before a completion attempt that
would carry the blocker.

The P3.5 proposal began at `fa308c3`.  Its §4.4/§4.5 algorithm already
expressed universal checkpoint-path rejection (backward `danger` propagation)
and §4.7 claimed every statically enumerable forward path passes a later
disposer.  This is a restatement/implementation of the post-`f31a423` Concept,
not an earlier source of it.  `6075417` corrected the proposal's same-Hop
clean-checkpoint hole: it added an origin-checkpoint arm so a disposer on an
opener cannot cure a blocker newly opened by that same Hop.  `8fc44ee` refined
version-specific opener identification and diagnostics; `6807d56` changed the
v2 proxy from empty-disposition to the reviewed/blocking-only opener set and
thereby recorded the 43/0 outcome.  These diffs change precision, origin
handling, and compatibility breadth, not the Concept's already-universal
quantifier.  Design review 003 accepted the corrected design; that is a
decision accepting the design's fidelity to the current Concept, not evidence
that the earlier escalation was intended.

The prior reassessment and review are useful documentary inputs only.  Its
`P35SIR-001` correction accurately says the *accepted* rule rejects if any
checkpoint-reaching path lacks a later disposer
(`...structural_invariant_reassessment...adoc`, §1 and H003 correction
record).  It did not investigate whether `f31a423`'s change from the original
conditional text was warranted, so it cannot decide that prior question.

=== Interpretation

Two conclusions follow without relying on a recollection of intent: (1) the
original written requirement was conditional and did not contain the present
unconditional formulation; (2) `f31a423` is the earliest supported source of
the latter.  The historical review supplied a sound *order* defect, but the
record contains no incident or stated product requirement involving a safe and
unsafe branch that independently justifies the accompanying all-path
strengthening.  That makes the universal portion a requirements escalation
unless the maintainer now deliberately adopts it as a new, stronger policy.

== B. Requirements fidelity [[fidelity]]

=== What the engine and the incident require

Finding creation and disposition are different facts.  `_finding_operation`
maps creation of `OPEN` to no disposition operation, while transitions from
open to resolved/residual/superseded require named operations
(`src/workflow_coordinator/reducer.py:470-487`).  `_may_dispose` permits one
only to human authority or a gate whose current phase grants it
(`reducer.py:489-497`).  A later phase with `resolve`, `residual`, or
`supersede` is therefore an opportunity, not proof that an agent will use it.
The S3-002 path has no such later legal opportunity, so both the candidate
existential rule and the accepted universal rule correctly reject it.

The following minimal cases make the difference explicit.  `O` can create an
open blocking Finding; `D` has a suitable disposition operation; `C` has a
complete route.  Edges are routes actually declared by the profile.

[source,text]
----
1. Incident/order: O -> C                         (reject: no later D)
2. Review_001:     O[resolve] -> C                (reject: same invocation
                                                    is not later)
3. Branch:          O -> D -> C
                       \-> C
4. Loop:            O -> work -> O -> D -> C      (the second O is later)
----

Case 3 is the legitimate counterexample the candidate hypotheses leave open.
Read per phase as hypotheses 2--3 say, `D` is legally reachable from `O`, so
the existential rule accepts; the universal rule rejects the `O -> C` branch.
That result is not a proof that universal rejection is required: in the
actual reducer, an agent that opens the blocker and selects `O -> C` reaches
`_apply_route`'s complete guard, which stops for
`completion_blocked_by_open_blocking_findings` (`reducer.py:1145-1174`).  It
does not complete incorrectly, and the reducer does not choose `D` for the
agent.  An agent that needs disposition can instead select the already legal
`D` branch.  The history has no case 3: the BUG and review_001 §4.2 first
present a one-continuation topology, not this branching shape.

That does leave a real operational risk: an invocation can select the bad
branch and consume work before the fail-closed stop.  It is a reason a
maintainer might knowingly adopt universal no-dead-end admission, but it is
not the recorded original requirement and it is not completion safety.  It
must be stated as that additional policy, rather than smuggled in by a
stronger theorem.

The candidate formulation needs one precision not supplied by mere graph
membership: an opportunity must be *legally selectable in a later invocation*
under the profile's routes and authority, not just visually present in the
phase map.  An unreachable orphan `D`, an `await_human` route, or a route
that the phase cannot request is no existential repair.  Conversely, a loop
back to `O` can be a later opportunity, as the current Concept itself notes
(§11, target property); the second invocation is distinct from the opening
one.  Existing open Findings carried into a phase matter as well: the
topology must make a legal later disposition route available whenever they may
remain on exit, but it need not predict whether an agent will select it.

The operation also depends on state: `resolve`, `residual`, and `supersede`
have different legal transitions, while `reopen` alone cannot close an open
blocker.  A narrowed rule should require an operation legal for the relevant
open blocking state, and retain the profile's least-authority choices.  It
should not infer a new Finding-kind taxonomy or promise termination,
autonomous recovery, or successful LLM behavior.

=== Result

The independent fidelity result is: retain strict-after, phase/operation/state
precision, and a legally selectable disposition path; replace the universal
``every forward path'' rejection with the existential availability rule unless
the maintainer expressly chooses the stronger no-dead-end policy.  This meets
the actual linear BUG and review_001's order defect.  It openly leaves the
branching operational-risk decision to the maintainer rather than claiming
history resolved it.

== C. Architectural placement [[placement]]

If adopted, this is still a static composition property of a parsed
`WorkflowProfile`: phases, routes, review descriptors, and
`finding_authority`.  `_review` validates local closed operations and
gate/advisory coherence (`serialization.py:548-599`); `_route` validates a
route's own shape (`serialization.py:601-628`).  Neither is the right place
to decide cross-phase reachability.  `operator._preflight` already parses the
pinned profile and performs cross-document, pre-Run checks
(`operator.py:281-367`), matching Concept §11's ``where this belongs''
paragraph.  A pure parsed-profile validator called from that preflight is the
least new boundary; placing a helper module elsewhere does not change this
semantic location.

This recommendation separates where validation runs from what it validates.
The validator reports topology; the invocation chooses a requested route; and
`reduce_result` applies the actual state transition.  The reducer must retain
its stateful permission and completion checks, not invent a `D` route or
disposition.  No Commission-specific or YAML-parse-time policy is needed to
make that separation work.

== D. Reevaluate the previous reassessment [[previous]]

The prior reassessment's core observation is independently verified: the
completion guard makes the harm from an actual undisposed blocker a stopped
Run rather than incorrect completion (`reducer.py:1145-1174`).  But the
candidate existential rule changes its cost analysis materially: a profile
with an actual selectable repair route is not rejected just because another
route lacks one.

. *1. Creation declarations and runtime enforcement.*  Explicit declarations
  can improve static precision, especially for legacy creators, but they are
  not required to express the narrowed availability rule where current profile
  facts already identify a relevant opener.  Runtime enforcement is a separate
  semantic change, not justified merely by revising a static requirement.
  Defer unless a later bounded design establishes its independent value.
. *2. Clean-GOTO guard.*  The existing `COMPLETE` guard is verified.  A new
  clean-GOTO guard would prevent carrying a blocker down a selected edge; that
  is a stronger execution constraint than the existential availability
  requirement and is not evidenced by the linear BUG.  Defer as a separate
  policy decision.
. *3. Static validation/preflight.*  A narrow validator remains potentially
  valuable: it can reject S3-002's no-opportunity topology before cost is
  incurred.  Its preflight integration belongs at the boundary in section C.
  Whether Level 0 needs it depends on the maintainer's tolerance for a
  fail-closed stopped Run, but the 43/0 result cannot by itself establish that
  a narrowed validator is disproportionate.
. *4. Legacy admission/migration.*  The prior design's migration burden is a
  consequence of its reviewed-opener/all-path predicate, not an invariant fact
  of all legacy YAML.  Preserve parse/replay/fixture history independently
  from new-launch admission, as `f31a423` and Concept §§18--19 already
  distinguish.  Do not require corpus-wide migration before identifying which
  currently used profiles actually lack any legal later repair route.

The reported 43/43 (also rendered 43 rejections / 0 acceptances) is an
accepted-design inventory result, recorded in the Level-0 decision §2 and the
design's §§6.1/6.3, not a count this assessment re-derived.  This assessment
did independently inspect S3-002 YAML and confirms one rejected shape.  It
does not establish that all 43 are currently used, need new-launch admission,
or require migration.  Some may be historical fixtures whose parse/replay
compatibility remains valuable while their launch eligibility changes; some
may be active profiles requiring a targeted decision.  A future implementation
Commission must inventory those categories against actual launch usage rather
than treat either ``migrate all 43'' or ``migrate none'' as a premise.

== E. Recommendation [[recommendation]]

Replace/narrow the accepted invariant as follows:

____
For each phase that can create an open blocking Finding, and for each phase
that can leave one open, the configured profile must provide at least one
legally selectable, strictly later invocation opportunity to perform a
state-appropriate disposition before a completion attempt that would carry
the Finding.  The validator does not predict route selection or substitute a
route; the reducer remains responsible for actual authority and for refusing
completion with an open blocker.
____

This retains the original incident's required repair opportunity and
review_001's strict order correction.  It rejects orphan and linear
no-disposer configurations such as S3-002, but admits a topology with an
available correction/disposition branch even if a different branch would stop
when misselected.  If the maintainer wants to prohibit that latter branch,
they should explicitly adopt a new universal no-dead-end/usability policy and
accept its compatibility consequences; the archaeological record does not
show that policy was originally required.
