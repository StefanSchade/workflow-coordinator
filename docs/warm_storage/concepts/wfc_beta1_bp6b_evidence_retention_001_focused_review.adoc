=== 3. `F001` -- resolved

The Finding: `_path_is_tracked_clean` decided "already committed" from the
absence of a `git status --porcelain --untracked-files=all` line under the
destination, and `git status` never lists an ignored path, so an
entirely-ignored destination was read as committed -- a false
`ARCHIVE ALREADY UP TO DATE` with `commit: None` and nothing in `git ls-files`.

==== What the correction does

`_path_is_tracked_in_head` (new) asks `git ls-tree -r --name-only HEAD --
<dest_rel>`, and `_path_is_tracked_clean` now requires both status silence
*and* presence in the HEAD tree. A second new guard,
`_assert_audit_path_not_ignored`, refuses up front when the Evidence
repository's own `.gitignore` would exclude `audit.json` itself.

==== Independent reproduction of the fixed behaviour

Both reproductions from the Finding were re-run through the real
`frontdoor.cli.main` against an Evidence repository created by the product's
own `ensure_evidence_repository`:

* *Legacy `raw_retention=None` into a managed (`local`-default) Evidence
  repository.* Call 1 exits 1 with `commit failed: commit intent path has no
  worktree mutation: ...` after placing the nine raw files; calls 2 and 3 exit
  1 with the *same* message. `ARCHIVE ALREADY UP TO DATE` never appears,
  `git rev-list --count HEAD` stays at 1 (the `wfc init` bootstrap commit), and
  `git ls-files` stays `{.gitignore, archive/.gitkeep}`. The previously
  reported false success is gone and the refusal is now stable across repeats.
* *`local` retention in a repository whose `.gitignore` also covers
  `audit.json`* (managed block plus an operator-added `*.json`). Refused
  before any write: `refusing: this Evidence repository's .gitignore excludes
  archive/unclassified/<attempt>/audit.json, but every raw retention mode
  commits it; adjust the .gitignore before archiving`. Destination absent,
  `.wfc-archive-staging` absent, `git status --porcelain` empty, commit count
  unchanged -- on the first call and on two repeats. The same input is refused
  identically in `commit` and `discard` retention, which the Finding did not
  require but is the consistent outcome.

The residue the first legacy call leaves (a placed, uncommitted destination)
is afterwards refused by name in every mode -- `archive destination exists but
has no audit.json` for `local`/`commit`, `not a valid discard-retention
placement (expected only audit.json, found ['manifest.json', 'ops', 'run'])`
for `discard` -- never silently reconciled and never reported as success. The
limitations record now admits this incompatibility *and* the fact that the
previous behaviour was a false success (lines 80-90).

==== Mutation sensitivity

Reverting only the new HEAD requirement (`return
_path_is_tracked_in_head(...)` -> `return True`) in a copy of the source tree
fails
`LegacyRetentionConflictTests::test_legacy_archive_into_a_local_retention_repo_refuses_consistently_not_falsely`
and nothing else. Removing only the `_assert_audit_path_not_ignored(identity,
dest_rel)` call fails
`LocalRetentionAuditGitignoreConflictTests::test_refuses_before_any_write_when_gitignore_also_covers_audit_json`
and nothing else. Both mutants leave every BP5/BP6a/BP6b test passing
otherwise, which is the right shape: the new tests guard the new behaviour and
only it.

=== 4. `F002` -- resolved

The Finding: `_project_audit_text` called `project_audit` without
`private_strings`, so only BP6a's prefix-only absolute-path/URL heuristic
applied, and a repository-relative value that merely repeated the OS user name
reached the committed `audit.json` and the Evidence history in `local` and
`discard`.

==== What the correction does

`_attempt_private_strings` derives the four strings the task names -- `HOME`,
`getpass.getuser()` (guarded by `try/except`), the state root and the resolved
OPS directory -- once per Attempt, and they are threaded into *every*
`project_audit` call site: initial placement, the kept-raw no-op/resume
re-projection, and the `discard` ephemeral re-projection.

==== Independent reproduction of the fixed behaviour

With a repository-relative `governing_inputs` key `docs/canary-<os-user>/governance.adoc`:

[cols="1,1,1,1,1",options="header"]
|===
|Mode |Exit |stderr |Destination / staging |Commits added

|`local` |3 |`privacy guard refused projection at governance.governing_inputs.<key>` |absent / per-attempt staging absent, `git status` clean |0
|`commit` |3 |same |absent |0
|`discard` |3 |same |absent |0
|===

In all three cases `git rev-list --objects --all` contains no blob holding the
token. A control run with a benign token (`zzz-not-private-zzz`) still exits 0
and commits normally, so the guard is discriminating, not blanket. The
Finding's untested second clause of acceptance case 10 -- a guard refusal
writes nothing and commits nothing -- now has three tests and was
independently confirmed (HEAD unchanged, destination absent, per-attempt
staging directory removed, worktree clean).

Whole-history privacy was re-measured independently for a clean Attempt, with
six tokens (`HOME`, state root, OPS directory, a `USER=` canary planted in
`ops/run.log`, the real OS user name, and the scratch root): zero blob hits in
`local` and `discard`, on the first archive and after a crash-resume. `commit`
retention does carry them, which is the mode's explicit purpose.

Three independent mutations each fail all three
`PrivacyGuardEnvironmentDerivedStringsTests` tests and nothing else: dropping

=== 5. New blocking Finding

==== F-C -- the limitations record does not state that nothing is pushed

Deliverable 6 enumerates six facts the developer-facing limitations record
must state: what each retention mode keeps, where raw files live, that `local`
raw files are not backed up by Git, *that nothing is pushed*, that the default
data-home placement is a decision of this package, and that archives written
before BP6 receive no `audit.json`. Acceptance case 15 certifies that record.

Five of the six are stated. The sixth is absent:
`docs/warm_storage/concepts/wfc_beta1_bp6b_evidence_retention_001_limitations.adoc`
contains no statement that nothing is pushed and no statement that the
Evidence repository has no remote. The only occurrence of either word in the
whole 143-line record is "a Git remote URL", inside the description of the
privacy guard's heuristic. The same is true of the H001 version of the record,
so the gap has existed since the record was created.

The H002 broad review's acceptance matrix row 15 states that the record "says
... that nothing is pushed". That certification is inaccurate, which is why
the gap has not been dispositioned before now.

The *behaviour* is correct and was independently verified in this pass: after
`wfc init` and after an archive in each of the three retention modes, `git
remote -v` is empty, the local Git config holds no `remote` section, no
`.git/FETCH_HEAD` exists, the reflog holds only the local commits, `wfc init`
prints `NOTHING WAS PUSHED: the Evidence repository has no remote
configured.`, and `wfc archive` prints `push: not performed`. So this is a
documentation-only correction, confined to the limitations record; no code,
test or behaviour change is implied, and nothing else in acceptance case 15 is
in question (the record is otherwise unusually complete and honest).

Blocking because it is a reproduced, objectively verifiable omission of a
statement the task explicitly requires of a required deliverable, and because
the one artifact that should have caught it certified it instead.

=== 7. Non-blocking observations

Observations, not Findings; recorded here and in the Hop summary only. The
nine observations of the H002 broad review are not repeated.

. *A short OS user name makes every retention-aware archive refuse.* The task
  requires the OS user name to be handed to the privacy guard as a known
  private string, and `audit.py`'s guard is a plain substring test over every
  value *and every mapping key* of the projection. The projection therefore
  contains the substrings `ops` (in `run.hops_used`), `ci` (in
  `run/checkout-asso**ci**ation.json`), `run`, `op`, `id`, `a` and others. With
  `LOGNAME`/`USER` set to `ops`, `ci` or `a`, a completely benign Attempt is
  refused in every retention mode with exit 3 and a confusing location
  (`privacy guard refused projection at raw.files[3].path`). `root` happens not
  to collide. The behaviour is the specified design (substring matching plus a
  bare user name) and it errs on the safe side -- it refuses rather than
  leaking -- so it is not a Finding against this task, but a service account
  named `ci` or `ops` is plausible enough that BP6c (or a DG-2 decision) should
  settle the matching rule: a minimum length, a word/path-boundary
  requirement, or matching the user name only inside path-shaped values.
. *One private-string call site has no test.* Dropping `private_strings` from
  the kept-raw no-op/resume re-projection in `_resume_or_noop_kept_raw` (while
  leaving the initial placement correct) makes no delivered test fail. The
  threading is correct in the candidate; it is the test coverage that stops at
  the initial placement, because the resume path re-projects from an already
  guarded, already placed Attempt and so cannot be reached by a planted
  private string through the delivered fixtures. Worth a test that plants the
  string into the Run facts *after* a crash-resume placement.
. *A human-deleted destination leaves the Evidence worktree dirty.* After a
  successful `local` archive, removing the whole destination directory and
  re-archiving re-places the files and then refuses honestly at the commit
  boundary (`commit intent path already exists at base HEAD:
  <dest>/audit.json`, 0 commits), but leaves `M <dest>/audit.json` in the
  worktree. Pruning only the raw files (the plausible "save space" action the
  limitations record's own warning invites) is refused cleanly with `archive
  destination exists but has no manifest.json` and leaves nothing dirty.
  Deleting only `audit.json` is refused with `archive destination exists but
  has no audit.json`. None of these is a false success, and all are outside
  the acceptance list.
. *A NUL byte in `evidence.repository` escapes as `ValueError`.* Config
  validation enforces "single-line" by rejecting newlines, not other control
  characters, so `repository: "ev\u0000dir"` is accepted and
  `ensure_evidence_repository` then raises an uncaught `ValueError: mkdir:
  embedded null character in path` rather than a named `CommissionError`. This
  is unreachable through `wfc init` today (a NUL cannot travel in `argv`, and
  `wfc init` refuses to overwrite an existing config), so it matters only for
  the BP6c caller that will read a hand-edited config. A tab is accepted and
  works. `archive.py` already has `_reject_control_characters` for exactly
  this class of value.
. *Environmental test failures in this sandbox, unchanged by this candidate.*
  The required suite cannot run here at all: `WFC_TEST_INPUTS`/
  `WFC_TEST_PROFILE` name an offline wheel bundle that is not present, so every
  result in this record comes from `--wfc-partial` subset runs, which the
  harness itself labels "NOT the required suite or its acceptance".
  `tests/architecture/test_offline_distribution.py` and `test_bp1_identity.py`
  fail with `ERROR: No matching distribution found for setuptools>=68` (PEP 517
  build isolation without network or bundle); `tests/unit/test_wfc_op.py` runs
  a nested `pip install`; `tests/unit/test_claude_adapter_conformance.py` needs
  to create a symlink under a read-only `/tmp`. Agent-local limitation, not a
  product defect, and no substitute for the Coordinator's own full
  `task-check`.

Also noted, without product consequence: the managed block `wfc init` writes
is `archive/**/manifest.json`, `archive/**/run/**`, `archive/**/ops/**`,
whereas the task names `archive/**/run/` and `archive/**/ops/`. The effect was
measured, not assumed -- in `local` retention nothing under `run/` or `ops/`
is tracked and the worktree is clean -- so the two forms are equivalent here.
The new `_path_is_tracked_in_head` pathspec was also probed for glob magic
(`archive/unclassified/wfc-h004-probe*`, `...-0?`): `ls-tree` does not expand
it, so a glob-shaped attempt id cannot be mistaken for a committed sibling,
and an attempt whose directory name literally contains `*` archives and
commits correctly.
