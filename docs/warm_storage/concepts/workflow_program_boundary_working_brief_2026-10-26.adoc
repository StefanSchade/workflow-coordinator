== 1. What is already decided, and what is not

Already documented maintainer direction (see 2026-10-26 Front Door concept):: Prioritize Front Door and the interpreter/profile/Commission boundary ahead of P3.5. Reusable workflow programs are the target. No immediate migration, expanded DSL or kernel refactor. Maintain runtime Completion safety. P3.5's historical accepted design is not silently overwritten; future update requires review.

Discussion on 2026-10-26; record as hypotheses, NOT as an accepted FTR:: Separate permanent workflow guarantees from concrete task bindings; use standard, staged adversarial, convergence, privileged, protected-context and simple-task scenarios to test the boundary. Prefer ahead-of-time narrowed result typing where it truly constrains an LLM, and fail-closed post-Hop validation when necessary.

Not decided:: Exact program catalogue, ownership and packaging; binding contract; model-binding-by-phase; which upfront conditional schemas are supportable; guarded-route inclusion in revised P3.5; exact 'no dead end' quantification; qualified human-stop exception, if any; migration strategy (no bulk migration is currently intended). **Level 1 is explicitly unresolved**: recursive self-similar WFC orchestration, LangGraph, and other outer-loop designs remain hypotheses, not target design decisions.

== 2. Why the documentation views matter

*Functional Model:* Why we want the capability, which real workflows should exist, and the required guarantees observable by an operator.
*Semantic Model:* Exact meaning of Profile, Program, Commission, Finding, Disposition, clean state, requested/applied route, and static versus dynamic guards. Formal requirements only once agreed.
*Technical Model:* Current interpreter and YAML, proposed reusable binding seam, how schema projection/reducer/admission compose and what is already implemented.
*Backlog FTRs:* Small reviewable implementation concepts derived from an accepted functional/semantic problem -- not the canonical repository for durable product vocabulary.
*Warm storage:* Current discussion, competing proposals, evidence/counterexamples and reviews in progress.
*Cold storage:* Completed/obsolete/historical concepts and reviews, with provenance; not a hidden second active spec.

== 3. Requirements-fidelity cautions

. Do not infer that a phase is safe after review because it is named `final_review`. A full review can discover new Findings.
. Do not look only at *Finding-opening phases*. A phase can carry unresolved Findings into a new phase without opening any.
. A clean-only audit/trail/closure branch is legitimate when its *entrance* is conditioned on a provably clean post-Hop state.
. The existing `COMPLETE` guard prevents unsafe successful termination but may stop late after resources have been spent.
. The historical proposed `require_no_open_blocking_findings` is a *program route-level* guard evaluated dynamically on `GOTO`, not a Commission-specified permission. It is **not implemented**.
. A generic phase-level `requested_route` enum can be projected before dispatch today. It cannot necessarily know same-Hop Finding deltas in advance. Consider tighter result unions/guard combinations, but do not promise that strict JSON Schema alone proves semantic legality.
. Model/model-cost binding is not synonymous with WorkflowRole; UC-02 needs special attention.
. Sandbox authority and sensitive information egress must be enforced in trusted runtime/external environment, not by untrusted program prose or model claims.

== 4. Minimal counterexamples for later architecture reviews

CE-01: Review reports no blocker and requests `accept` -> `audit` -> `complete`: must be permitted.

CE-02: Review opens a blocker and requests `accept` -> `audit` -> `complete`: do not allow entry to audit; do not substitute a correction route without an accepted mechanical rule.

CE-03: Prior review opens blocker; a later phase cannot disposition and routes to audit: verify carried open state rather than just Finding opener capability.

CE-04: A phase *may* close a carried Finding in the same Hop and requests guarded audit entry; a correct design must allow the route if all required dispositions legally succeed.

CE-05: Final adversarial reviewer opens a brand new blocker; require another repair path rather than presuming finality based on name.

CE-06: Privileged code modification occurs; every legally successful continuation must pass independent defensive review even if no Finding was opened.

CE-07: A model is permitted to work with protected data; ensure no prompt, Git diff, log, test output or artifact crosses an unauthorized egress boundary.

CE-08: Repeated narrow fixes address individual exploit examples without closing underlying invariant; trigger root-cause escape without inventing arbitrary transitions.

== 5. 2026-10-27 governance/deployment/override discussion

Maintainer concern:: When workflows are used to *ensure* review, evidence or defensive security obligations, allowing every Commission to invent its own flow makes those governance guarantees optional in practice. However, permanently banning special-purpose workflows would undermine existing flexibility and potentially future higher-level callers.

Preferred direction to preserve, not an accepted implementation design:: Keep a stable trusted interpreter; allow reusable reviewed programs; allow typed *declared* variation points; permit separately authored and independently admitted custom program revisions when authorized. A Commission binds/selects and must not silently rewrite program semantics. A future deployment could install/enable different approved program catalogues (for example, a regulated-development pack), but mere installation neither grants task authorization nor starts a Run.

Risk trade-offs:: (1) Distinct per-Commission graphs impede comparative traceability, unless fully pinned and auditable; (2) repeated bespoke workflows make cost, staffing/model capacity and review planning harder; (3) each distinct graph explores new reducer/gate combinations and can surface novel semantic defects. Counterpoint: the interpreter must still reject structurally illegal programs and uphold global safety independently of catalogue standardization. Restricting authoring should not paper over a defective interpreter.

Vocabulary caution:: "Locked", "Configurable", "Custom" are possible authoring/admission classes, **not** supported WFC runtime modes. A typed override of a review model/budget default may be safe if guaranteed constraints are preserved. An override that removes mandatory defensive review is not the same kind of operation and must not be represented as an ordinary parameter.

Packaging caution:: A workflow pack initially means declarative profile definitions plus identities/guarantees/approvals. It is **not** permission for consumer Python to enter the trusted WFC process. Ownership of workflow programs may reside with WFC, a consumer, or a separately approved specialty package; ownership itself must not imply authority to execute.

Level-1 disposition:: Unsolved research problem. Earlier recursive reducer self-similarity hypothesis (review loop nested in backlog-selection and larger planning loops) remains one possible concept. Outer-loop orchestration may differ substantially and could use LangGraph. No choice is made, and neither hypothesis is an MVP dependency. Future callers must honor the same immutable program/admission/Run-authority boundary.

Related evidence/source gaps:: The repo-level functional/semantic/technical information architecture is a proposed complement to `docs/README.adoc`, not a replacement. The profile census still needs to distinguish truly new workflow programs from duplicated Commission bindings and trace historical final-review variability.
