== Independently reproduced: what the implementation actually does

All probes below ran against from-scratch, disposable Git repositories created
by `git init` with no `governance/` directory, no `pyproject.toml`, no `*.py`
file, and an executable `checks/check.sh`. Probe transcripts were produced in
this Hop by driving the production entry points directly.

=== Admission is reused, not duplicated, and its caller obligations are met

`frontdoor/verify.py:42-137` is the only consumer-path caller of
`operator.admit_parsed`, and it establishes each obligation that function's
docstring (`operator.py:363-376`) assigns to the caller, in this order:

* repository top-level identity via the same `git_facts.repository_identity`
  the unchanged `_preflight` uses, and a `is_dir()` check;
* a 40-hex lowercase `expected_head` equal to the observed HEAD, and a clean
  worktree with resolved submodules via the same `observe_repository`;
* a resolved state root that cannot pre-exist, since it is a fresh name inside
  a newly created `TemporaryDirectory`;
* strict parse of the corresponding objects through the unchanged
  `work_item_from_yaml` / `workflow_profile_from_yaml` /
  `repository_policy_from_yaml` / `component_manifest_from_yaml` /
  `run_execution_configuration_from_yaml`;
* normalized input paths through operator's own `_relative_path`, and governing
  texts read with operator's own `_pinned_text` at `expected_head` -- so the
  "texts were read from those paths at that revision" obligation is discharged
  by the same helper `_preflight` uses, not by a parallel reimplementation;
* binding-source provenance: the envelope text is written to a file, read back,
  parsed, and its `digest` is re-derived from its own text and refused on
  mismatch (`verify.py:94-95`);
* operating-contract validity via the unchanged `load_agent_operating_contract`.

Critically, `verify.py:82-85` compares *every* compiled byte against the tree at
`expected_head`, not only the five named governing files. The materialized
`components/*.txt` are covered, so admission cannot be handed an unverified
committed copy of a frozen role text. The consumer `repository_policy`
component is the one compiled path that is not a generated file; it is covered
separately at `verify.py:87-92`, where the blob observed at `expected_head`
must equal the blob at the request's pinned `guidance.source_commit`.

=== Commission identity is separate from execution identity

Verified directly. With the Request and Config held fixed and only the
`resolve_execution` override changed, the compiled `texts` mapping is identical
and the envelope digests differ, which the committed test
`test_consumer_simple_end_to_end_admits_with_differing_execution_digests`
also asserts after a real `verify_commission`/`admit_parsed` round trip
(`result[16]` differs between the two bindings while
`compiled_a.texts == compiled_b.texts`).

The task directs this reviewer to judge whether execution-default changes
affect immutable Commission identity. Reproduced result: changing only
`default_execution.model` in the Consumer Config changes exactly one compiled
file, `commission-manifest.json`, because the manifest records
`config.sha256` over the whole pinned Config text. Every admission-governing
byte -- `work-item.yaml`, `profile.yaml`, `policy.yaml`, `task.md`,
`components.yaml` and every materialized `components/*.txt` -- is byte-identical.
This is not a material breach: the task itself specifies the resolver as
`resolve_execution(config, overrides, roles)`, so the Config legitimately
carries execution defaults, and the task separately requires "traceable origin
and digests" for the pinned inputs. The manifest digest is provenance of a
legitimate pinned input, not an admission-governing or authority-bearing byte,
and the stated acceptance (same Request/Config, differing permitted bindings ->
byte-identical Commission artifacts, differing envelope digests) holds. Recorded
below as a non-blocking observation, not a finding.

Request-level rejection of execution fields is structural rather than a
deny-list: `commissioning._mapping` refuses any unexpected key, so
`bindings:`, or a `provider:` nested inside `evidence:`, is refused as a
forbidden field. `_SUPPORTED_PROGRAMS` is closed to `simple@v1` and
`robust@v1`; `direct@v1` is refused at parse time and again in
`_consumer_program_template`. No new Workflow Program, revision or program
record is introduced -- the consumer templates are the same
`_simple_template()` / `_robust_template()` literals with the already-declared
`repository_policy` slot filled.

=== Profile equivalence to v1

The committed tests pin the full compiled `phases` mapping for both programs
field-for-field against the accepted `simple@v1` and `robust@v1` literals. The
only differences are the deliberate ones: `components.repository_policy` is
`["repository_policy"]` in every phase instead of empty, the `scope`/`artifact_key`
slots are resolved into concrete `authorized_scope`, and the `evidence` slot is
resolved to `["task-check"]`. Routes, roles, `authorized_actions`,
`human_gates`, `durable_artifact`, review `breadth`/`authority`/`context`/
`blocking_policy`/`trigger`/`exit`/`finding_authority`/`failed_evidence_route`
are preserved exactly. Those differences are documented in
`docs/backlog/beta1_productization.adoc`.

Guidance cannot widen anything: it enters only as the text of one prompt
component bound into the existing `repository_policy` slot. No request or config
field can reach `authorized_actions`, `routes`, `review.finding_authority` or
`policy.actions`; those come from the closed package-owned literals.

== Non-blocking observations

These are recorded for the maintainer; none is a Finding and none blocks this
gate.

. `commission-manifest.json` digests the whole Consumer Config text, which
  includes `default_execution`, so an execution-default change perturbs that one
  provenance file. Analysed above; no admission-governing byte is affected.
. `verify_commission` writes the execution bindings into a `TemporaryDirectory`
  that is removed before it returns, so the returned tuple's `binding_source`
  names a path that no longer exists. Harmless for this verify-and-admit entry
  point, but a future BP3 launch path must not treat that returned value as
  live provenance.
. `resolve_execution` copies only `adapter`/`model`/`reasoning` out of an
  override mapping; an unexpected key in a programmatic override is ignored
  rather than refused, unlike the parsed-text schemas which refuse unknown
  fields.
. `compile_commission`'s governance/scope overlap check is one-directional,
  so the guidance-inside-scope case compiles and is caught only later by
  `operator._admit_a1`'s bidirectional check. Fail-closed at the real boundary,
  but the message surfaces at admission rather than at compile time.
. `test_consumer_compile_rejects_tampered_package_resource` inverts the
  comparison by monkeypatching the expected digest instead of mutating the
  resource bytes. Equivalent in effect; a genuine on-disk mutation was confirmed
  refused during this review, and the pre-existing required test
  `test_bp1_identity.py::test_installed_identity_and_real_preflight` (lines
  51-54) mutates the real installed `resources/roles/worker.txt` bytes and
  requires `wfc --version` to exit 2 with `digest mismatch`.
. The BUG record paragraph attributes the consumer-neutral evidence change to
  `WI-WFC-BETA1-BP2-CONFIG-COMPILER-001` rather than the delivering `-002`
  WorkItem. The record correctly stays open for the self-development path and
  claims no closure.

== Disposition

Accept. No blocking Findings. The BP2b deliverable is present and real for both
`simple@v1` and `robust@v1` against a genuine non-Python, non-WFC repository
with a real shell check; admission is reused rather than duplicated and every
documented caller obligation is established before the call; Commission identity
and execution identity are separate; frozen product resources and pinned
consumer guidance reach the engine authority boundary and their tampering is
refused there; the v1 render and self-development route and the legacy exact
Python policy identity check are unchanged; and no excluded surface was
modified.

This is implementation-level independent review acceptance only. It is not
product qualification, not BP2 closure, and not acceptance of the controlling
BUG record, all of which remain outstanding. Coordinator task-check is separate
and authoritative.
