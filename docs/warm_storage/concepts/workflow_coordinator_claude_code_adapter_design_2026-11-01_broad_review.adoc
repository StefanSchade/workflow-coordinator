== 1. Disposition

Outcome:: `changes_required`
Route:: `correction`

The design is small and mostly respects the existing execution port.  It keeps
the exact WFC envelope correlation and semantic validator unchanged, rejects
failed transport before candidate trust, avoids a provider registry, and
identifies the single-executable restriction honestly.  Its proposed Claude
invocation is not yet safe or reproducible enough to implement, however.  It
selects ordinary Claude Code startup with ambient configuration and no
provider-side filesystem/command containment, then cites the Coordinator's
post-Hoc Git and scope observations as if they covered that larger surface.
They do not.

One blocking Finding is therefore open.  The defect can be corrected entirely
inside the design document; no production, test, governance, schema, Runtime,
Evidence, or programme change is required in this Hop.

== 3. Blocking Finding

=== CCADR-001 -- ambient Claude configuration and an unbounded tool surface bypass the controlled invocation

Severity:: *BLOCKING.*
Disposition:: *OPEN; correction required.*

Invariant:: A noninteractive provider adapter must explicitly bound all
provider inputs that shape a Hop and the provider-requested tool/filesystem
surface.  User/project instructions, settings, hooks, plugins, MCP servers,
permission rules, or an unsandboxed command retry must not silently widen the
Coordinator-admitted prompt, source, scope, or executable provenance.  Any
provider-side sandbox request must still be described as a requested inner
control, not as a Coordinator-verified OS boundary.

==== 3.1 Counterexample

The proposed argv uses `-p`, `--permission-mode acceptEdits`, and
`--permission-prompts none`, but it uses neither `--restricted` nor
`--safe-mode`, supplies no closed tool list, and supplies no explicit sandbox
settings (design lines 92--93 and 106--116).  Section 6 then says WFC relies on
the pinned checkout, scope/Git observation, and Coordinator-owned authorities,
while explicitly deferring `--restricted` as future hardening (lines 177--204).

That composition is not controlled:

. Claude Code's ordinary local startup reads user, shared-project, and local
  settings.  Those sources can contribute permission rules, hooks, plugins,
  environment values, and MCP configuration.  `--permission-prompts none`
  denies only actions that still require a prompt; it does not cancel an
  already matching allow rule, an automatically approved `acceptEdits` file
  operation, or startup hooks.
. Ordinary startup can also load `CLAUDE.md`, skills, commands, agents, plugins,
  MCP servers, and auto-memory.  These are prompt- or behavior-shaping inputs
  outside the rendered WFC component set.  In print mode the workspace trust
  dialog is skipped, so an unattended invocation cannot rely on that dialog to
  admit them.
. Claude's Bash sandbox is off by default.  The design neither enables it nor
  sets the documented fail-closed controls.  A repository/user setting can
  therefore allow a command or hook whose reads, writes, process effects, or
  network effects are invisible to WFC's repository diff and authorized-path
  check.  Post-Hoc Git observation can reject an in-repository write; it cannot
  retract an external read, hook effect, MCP call, or network disclosure.

The counterexample needs no malicious model.  A checkout containing a normal
`.claude/settings.json` hook or permission allow-rule, or a maintainer account
with a user-level rule, changes what the same pinned adapter argv does without
changing the WFC execution binding.  The design therefore does not yet preserve
the task's controlled-source/scope requirement, and its claimed homogeneous
Simple/Direct/Robust compatibility depends on unspecified host state.

==== 3.2 Verified available controls

The installed 2.1.270 help and the official CLI reference expose controls
specifically relevant to this adapter:

* `--restricted` is documented for evaluation harnesses on shared machines.  It
  loads only managed settings plus explicit `--settings`, confines built-in
  file tools to working directories, removes command/code tools and WebFetch
  unless explicitly named, refuses bypass-permission mode, and refuses cloud
  sessions.
* `--safe-mode` disables `CLAUDE.md`, skills, plugins, hooks, MCP servers,
  custom commands/agents, workflows, LSP, and auto-memory while leaving
  authentication, model selection, built-in tools, and permissions available.
* an explicit `--tools` value can close the built-in tool set, and
  `--strict-mcp-config` can prevent ambient MCP configuration from being used;
  and
* explicit `--settings` can request `sandbox.enabled: true`,
  `sandbox.failIfUnavailable: true`, and
  `sandbox.allowUnsandboxedCommands: false`.  Official sandbox documentation
  also warns that the Bash sandbox covers command processes, while file tools,
  hooks, and MCP servers run outside it, and that its default read surface is
  broader than the working directory.

These facts do not prove a particular combination is sufficient.  They do
prove that the current design's ordinary-startup assumption is neither the
smallest controlled choice nor a missing-CLI limitation.

==== 3.3 Required correction

Correct sections 3, 4, 6, 7, 8, and 9 as needed to define one implementable,
fail-closed Claude invocation profile:

. Select and justify the exact startup-isolation flags.  Prefer the installed
  `--restricted` harness mode unless a verified incompatibility requires a
  different closed combination.  State exactly whether user/project/local
  settings, `CLAUDE.md`, skills, hooks, plugins, MCP servers, memory, and
  managed settings can load; do not leave any category implicit.
. Specify an explicit minimum tool/permission surface sufficient for the WFC
  roles in scope.  Explain how noninteractive Bash/test commands work without
  inheriting ambient allow rules or enabling provider fallback/bypass.
. Decide the provider-side command sandbox request and its fail-closed
  settings, including availability failure, unsandboxed retry, filesystem read
  and write reach, network reach, and credential exposure.  Preserve the
  design's correct statement that this remains a provider-requested inner
  control rather than a WFC-verified OS security boundary.
. Add fake-CLI argv assertions for the closed startup/tool/settings shape and
  negative tests proving forbidden ambient configuration cannot be selected.
  Extend the separately authorized real smoke to test the effective working
  directory, an authorized edit and required test command, attempted
  out-of-workspace access, a deliberately planted project customization, and
  fail-closed sandbox unavailability without logging secrets.
. If managed policy remains intentionally loadable, name it as residual host
  policy and avoid claiming it is pinned by WFC execution-binding evidence.

Correction must remain a design change.  It need not add an outer sandbox,
execution-environment port, telemetry schema, provider registry, or production
implementation to this WorkItem.
