== P35DR-001 -- Opening-phase checkpoints escape the ordered property

Severity:: MATERIAL
State:: OPEN
Design locations:: §§1.4, 4.2--4.7, 7 example 7, 8; especially §4.5, lines 530--549.
Governing evidence:: Projected-result-contracts concept §11 requires a disposer strictly after the opening invocation on each relevant forward path; it does not exempt a completion attempt made by that invocation.

=== Minimal false acceptance

One phase suffices, using the design's own notation:

[source,text]
----
p [review:gate, finding_authority:[]] --C-->
----

This is a legacy schema-v2 shape. The corresponding proposed-v4 annotation
is `may_open_findings:true`. Here `creates_blocking(p)=True`,
`checkpoint(p)=True`, `disposer(p)=False`, and `danger(p)=True`, but there
are no `UnguardedEdges`. Section 4.5 therefore ACCEPTS. A Hop at `p` can
open a blocker and request completion; there is no later disposing phase
at all. Existing `reduce_result` stops it with
`completion_blocked_by_open_blocking_findings` and leaves the blocker open
(`reducer.py:1145-1168`, `:1713-1725`, `:1835`). A local invocation of the
unmodified reducer confirmed exactly that stop.

The draft acknowledges this acceptance, but its justification reverses the
ordered requirement: excluding the opening invocation as a *disposer* does
not exclude its outgoing completion route as a *checkpoint*. A runtime
backstop and a one-Hop cost do not establish the promised static property.
The motivating multi-Hop failure is also protected by the same backstop;
using that protection to waive this case weakens the claimed invariant.

There is an analogous guarded case:

[source,text]
----
p [may_open_findings:true, review:gate, finding_authority:[]]
  --G(guard:true)--> q [may_open_findings:false] --C-->
----

`p` is a checkpoint, but its sole outgoing edge is excluded. The rule
again ACCEPTS, although a newly opened blocker cannot pass that checkpoint
and has no legal disposal path. Section 4.6's protection of carried
Findings does not cover this newly opened Finding at the guard's source.

=== Supersession is a further instance, not an undecidability result

[source,text]
----
p [may_open_findings:true, review:gate, finding_authority:[]]
  --G--> s [may_open_findings:true, review:gate,
             finding_authority:[supersede]] --C-->
----

The rule accepts: `danger(s)=False`, and `s` has no unguarded successor.
If `s` supersedes the earlier Finding with a fresh open blocking successor,
completion stops. What the future agent will actually author is unknown,
but the *possibility* of a new blocker at `s` is explicitly declared and
the absence of a later disposer is statically decidable. If instead
`s.may_open_findings=False`, §5.3 must reject creating that successor.
Supersession itself is a legal disposition of the original Finding; the
fresh successor is a separate opening obligation. The static rule must
consider each eligible opening phase, including a disposing phase that
can also create Findings. This needs no Finding-kind taxonomy and no
general liveness analysis.

Even without fixing the origin-checkpoint hole, a third phase `q` with no
authority and a completion route after `s` makes the draft's *existing*
rule reject from `s`, provided `s` is declared capable of opening Findings.
Thus the categorical assertion in §7 example 7 that no profile fact can
address the successor risk is already contradicted by the rule itself.
Unknown actual execution is not static undecidability of capability
composition.

=== Minimal required correction

Correct the rule and its strength statement so the opening invocation's
own clean checkpoint is considered without crediting that invocation's
disposition authority for its newly opened Finding. Retain credit for an
actual later revisit of the phase. Do not simply query `danger(p)`, because
its disposer-absorption would still erase an origin that is also a
disposer. Correct the supersession discussion and add explicit origin
completion, origin guarded-route, and successor-creation cases to the test
contract. State and reconcile the compatibility consequences under
P35DR-002; do not silently weaken the governing ordered property or presume
an unimplemented result/route restriction.

The proxy can over-approximate as well as under-approximate creation.
Current schema-v3 ordinary phases cannot create an open blocking Finding,
even if they have a review descriptor (`reducer.py:1285-1293`). A concrete

[source,text]

over-flagged by the proxy, not an observed schema-v3 self-development

== P35DR-003 -- Schema-v4 inheritance has an unresolved semantic branch

Severity:: MATERIAL
State:: OPEN
Design locations:: §§3.1.1--3.1.2, 5.3, 6.2, 7, 8, 10 item 3.
Evidence:: `serialization.py:667-709`, `:724-746`, `:837-976`; `model.py:684-702`, `:853-885`; `reducer.py:450-454`, `:717-721`, `:1266-1294`.

Section 3.1.1 says v4 carries *every* v3 structural rule, including full
convergence cross-validation. Those rules require a `convergence` block,
per-phase convergence roles, and all five of corrector, evaluator,
diagnosis, reframe, and strategy gate. They impose specific topology and
authority requirements. They are not optional orthogonal checks on an
otherwise ordinary profile.

Consequently a v2 ordinary review/correction profile cannot migrate merely
by declaring `may_open_findings` per phase as §6.2 suggests. Nor can the
ordinary small v4 graphs in §7 satisfy the stated inherited rules. They
would need unrelated convergence machinery. This is a semantic migration
decision, not a field-name or next-integer choice.

The draft also leaves the associated execution lineage unspecified:

* `new_run` selects Run schema 3 only for profile schema exactly 3; otherwise
  it selects Run schema 2 (`model.py:869`).
* `result_contract_version` selects the ordinary typed result version 3
  only for profile schema exactly 3; other ordinary profiles use version 1
  (`model.py:684-702`).
* `_profile_phase` currently admits only profile versions 2/3 and couples
  v3 to Run v3 (`reducer.py:450-454`).
* Convergence phases and ordinary phases have different creation
  restrictions and bookkeeping. Granting `may_open_findings:true` does not
  by itself remove these restrictions; treating it as an override would
  change existing convergence semantics, contrary to the stated boundary.

Simply adding 4 to a parser's version set does not choose between the
ordinary legacy lineage and the convergence lineage. Replacing all
`== 3` tests with `>= 3` would force the latter and retain evaluator-only
blocking creation, contradicting the claimed general migration of plain
Finding-creating worker phases. Keeping those predicates unchanged while
inheriting v3 parsing would instead pair convergence declarations with the
wrong Run/result semantics. Either implementation could be inferred from
the present text.

=== Minimal required correction

Specify a coherent v4 structural and execution contract: whether and how an
ordinary v2 profile can opt into explicit creation declarations without
adopting convergence; when existing convergence constraints apply; the
profile-to-Run/result-version mapping using existing result families; and
the intersection of `may_open_findings` with existing role/lineage creation
restrictions. Make every proposed-v4 worked example state all required
capability flags and its relevant mode. Preserve old version semantics and
P1-P3 transport/selection architecture; do not introduce new result
families, rewrite convergence, or require unrelated topology as an
unstated migration cost. These choices are prerequisites for an
implementable design, even though the final field spelling and numeric
version assignment can remain implementation details.

== P35DR-004 -- Worked explanations do not follow the predicates

Severity:: IMPORTANT
State:: OPEN
Design locations:: §§4.6, 5.1, 7 examples 1--3 and 6, 8.

Concrete discrepancies:

* Example 3 says `checkpoint(rereview)=True` because an unguarded `GOTO`
  leads to `complete_gate`. Section 4.3 defines that predicate locally;
  this makes `danger(rereview)=True` by propagation, not
  `checkpoint(rereview)=True`.
* Example 6 says the guarded route contributes
  `checkpoint(post_review_wrapup)` conditionally on safe arrival. It
  contributes `checkpoint(rereview)`, unconditionally, at the source.
  `post_review_wrapup` has only an unguarded `GOTO`, so is not a checkpoint.
* Example 1 says no candidate exists despite its `complete_gate` having a
  review descriptor under the legacy proxy. It is a candidate, merely one
  with no successor checked by §4.5. Example 2 likewise needs an explicit
  v4 noncreating annotation on `rereview` if its unguarded successor is a
  nondisposing completion phase; under the legacy proxy that rereview is
  another origin and the rule rejects from it.
* Section 5.1's required diagnostic names the immediate dangerous successor
  and its local predicates. In example 3 that successor is `correct`, not
  the later `rereview` named by the example. A nondisposing intermediary
  with a further dangerous successor need not itself be a checkpoint or
  the phase to which disposition authority should be granted.

Excluding guarded edges is a faithful way to model carrying an *undisposed*
Finding. However §4.6's stronger claim that retaining those edges must
over-reject example 6 is not demonstrated. Its disposer absorbs danger
regardless of the guard. More generally, adding guarded edges to the
fixpoint does not change `danger`: every nondisposing guarded source is
already a checkpoint seed, and every disposing source is already
absorbing. The special first-edge decision can differ, but that is exactly
the origin-checkpoint hole in P35DR-001, not proof that a carried Finding
requires a different dangerous-node set. The current asymmetry is sound
for carried Findings; the claimed necessity proof and its supporting
example are not.

Minimal correction:: Recompute the examples from the actual local predicates, distinguish candidate/absorption/propagation/origin checks, make diagnostics deterministic with a consistent witness location or path, and replace the unsupported necessity assertion with the exact modeling argument. This can be addressed alongside the MATERIAL corrections without redesigning the algorithm.

== Other required review assessments

=== Graph fixpoint, cycles, and human stops

For its stated induced graph and predicates, the backward least-fixpoint
is finite, monotone, and computable in `O(phases + routes)` with adjacency
lists. Disposer absorption correctly excludes `reopen`; gate status and
one of resolve/residual/supersede are necessary under the current
disposition rules. This is a capability-path check, not proof that the
agent will exercise its authority.

The ordered *revisit* case works:

[source,text]
----
p [may_open_findings:true, review:gate, finding_authority:[resolve]]
  --G(again)--> p
----

`p` may additionally have a completion route, but the path being assessed
here is the one through a later invocation. The successor is `p`, now a
later visit; `danger(p)=False` properly credits its resolve capability for
the *earlier* Finding. A local existing-reducer diagnostic opened a
Finding on a self-loop, then resolved it and completed on the next
invocation. The invalid direct-completion alternative is separately
P35DR-001; it does not justify rejecting all revisits or counting budgets.

Example 8's no-checkpoint boundary is deliberate and appropriate. A graph
whose only forward exits are `AWAIT_HUMAN`, prerequisite suspension, or
`STOP` has no completion-path obligation of the bounded kind under review.
The draft truthfully gives it vacuous acceptance, not verified human
disposition. `confirm_supervisor_route` performs no Finding mutation
(`reducer.py:1872-1896`); prerequisite authorization/reconciliation/resume
do not dispose Findings (`:1899-1979`). No production caller grants
`FindingAuthority.HUMAN` to `apply_finding_deltas`. A stronger general
termination/usefulness check is not required here. This boundary differs
from P35DR-001, which has an actual declared clean checkpoint.

=== Authority independence, defaults, and enforcement

Creation and disposition are independent today for the ordinary legacy
path. `_finding_operation(None, OPEN)` returns no disposition operation;
`_apply_legacy_finding_deltas` consequently permits a new open Finding even
for an unreviewed worker. `_may_dispose` independently enforces the gate's
operation tuple. Advisory review cannot declare disposition authority
(`serialization.py:568-579`). Result-v2 and result-v3 convergence paths
impose additional restrictions; the independence claim must be read with
those restrictions, not as a universal capability override.

Requiring an explicit declaration at a new profile schema is a defensible
authoring decision. Default false would revoke existing legacy opening
behavior, including the motivating review gates. Default true would retain
that behavior for legacy phases, but would not establish that every author
affirmatively intended every phase to create Findings. Correction phases
commissioned for bounded artifact edits and empty-Finding design-review
loops illustrate the difference between engine permission and intended
use. The source cannot prove an omitted boolean's authorial intent; the
draft should describe mandatory explicit authorship as a governance choice,
not prove that default true changes the legacy engine's behavior. Nor would
default true override current v3 restrictions if the change is additive.
The new schema's existence is reasonable; its unresolved semantics are
P35DR-003.

Section 5.3's proposed rejection is fail-closed *for the Finding
transaction* if all deltas are screened before publication. The current
helpers return immutable replacement Runs and errors are caught against
the pretransaction Run, yielding
`mechanical_preemption:invalid_finding_delta:*` (`reducer.py:1713-1725`).
Preserve atomicity even with a legal existing-Finding delta preceding a
forbidden creation, and cover all existing result variants. The stop is
truthful; no silent dropping or blocking downgrade is proposed.

Two source/explanation qualifications do not require engine fixes here:

* Several design line numbers are stale (for example the model's
  ExistingFindingDelta and NewFindingDelta declarations are now at
  `model.py:304` and `:361`), but the named disposition,
  parsing, routing and preflight functions generally support the cited
  mechanisms. The existing ordinary phase dispatch uses typed
  `WORK_RESULT`/`REVIEW_VERDICT` v1 as well as the legacy reduction path;
  referring to that path as a generic contract everywhere is imprecise.
* Section 4.5's blanket assertion that the reducer cannot reference a newly
  allocated Finding within the same result is true of the later
  validate-before-allocation paths, but not of legacy sequential
  application: a synthetic new delta followed by an existing delta naming
  the guessed `F001` resolved in a local direct helper diagnostic. Such
  guessing violates the projected invocation identity contract and is not
  a legitimate disposing path. Narrow the source claim rather than treating
  this reducer accident as authorized behavior or changing source here.

Section 5.4's literal assertion of no persisted side effect on reducer
failure also overstates the convention: the invocation/Hop has already
occurred and a stop is recorded. The useful guarantee is no publication of
the rejected Finding transaction and no route advance; preflight failure,
unlike reducer preemption, occurs before a Run/provider exists.

=== P35DR-001 -- verified correction

Design §§4.5--4.7 now distinguish the opening invocation's checkpoint from
the backward `danger` value, which deliberately absorbs at disposers.
For the one-phase `p --COMPLETE-->` case, `creates_blocking(p)` and
`checkpoint(p)` are true, so the first arm rejects even if `p` also has
resolve authority. The guarded `p --G(guard:true)--> q` counterexample is
rejected by the same arm. Neither case needs an unguarded successor.

For a genuine later revisit, `p[creator,resolve] --G--> p` with no local
checkpoint has a false first arm and an absorbed successor
`danger(p)=False`, so it remains accepted. If `p` additionally has a direct
completion alternative, that alternative now correctly invalidates the
profile; the existence of a safe loop does not cure the unsafe alternative.
Budgets are still irrelevant to the static property.

Section 4.7 and example 7 now correctly treat a freshly created blocking
supersession successor as another creation event. A creating closure gate
with a local checkpoint is rejected independently of its ability to
supersede the earlier Finding. The claimed static undecidability exemption
has been removed. Section 8 explicitly requires the direct-origin,
guarded-origin, successor-creation and revisit cases. Section 4.5 no longer
claims that every legacy transaction already prevents guessed same-result
IDs; it requires rejection rather than relying on that accident as legal
disposition. These changes address the underlying ordered-property defect.

==== New v3 adapter does not name a coherent existing predicate

Section 4.3 now requests the "existing result-v3 legality predicate for an
untracked open blocker (the applicable convergence evaluator path...)".
Those are different paths, not one existing predicate:

* Ordinary v3 phases dispatch typed result v3 and cannot open an untracked
  blocker (`model.result_contract_version`; reducer
  `_validate_convergence_records_before_apply`, lines 1285--1293).
* A convergence evaluator dispatches generic result *v2*, not result v3
  (`model.py:684--702`). Its new open blocker is allocated with a
  `CorrectionObligation`, hence is *tracked*
  (`_apply_v2_finding_deltas`, lines 772--789).
* Correctors cannot create a new open blocker; diagnosis, reframe and
  strategy-gate paths cannot mutate Findings. The existing tests confirm
  evaluator tracking and atomic non-evaluator rejection.

The standard parsed `tests/unit/test_serialization.py::profile_v3_data`
fixture has an evaluator with resolve/residual/supersede and a `COMPLETE`
route. Treating its tracked creation as a candidate rejects it via the
origin arm. Searching only for legal *untracked* creation yields no
candidate and accepts it. The difference is concrete, not merely helper
naming. Section 2.1 currently calls the tracked mechanism out of scope;
§4.3 must distinguish leaving its *mechanics* untouched from including or
excluding its existing creation capability in this static check.

=== P35DR-004 -- explanatory corrections remain incomplete

The source-side checkpoint in example 6, propagated danger in example 3,
and guard-edge modeling explanation in §4.6 are corrected. Example 2 now
explicitly marks its rereview noncreating. Remaining concrete defects:

* Example 1 still says no candidate exists and that its v2 variant is
  accepted. Its reviewed `complete_gate` is a v2 candidate and a local
  checkpoint, so the corrected rule *rejects*. Under v4 that phase lacks
  the required `may_open_findings` declaration. Declaring it false would
  make the stated v4 positive example valid; it cannot establish the
  stated v2 verdict.
* The examples still lack complete capability/mode annotations, including
  `complete_gate` in example 2 and the additional gate in example 4.
  Example 5's `evaluator` is not identified as an ordinary v4 phase name
  versus a v3 convergence role. Example 2's assertion that this is the
  P1-Assurance-Closure shape also obscures that the real legacy profile
  completes at its reviewed gate and now fails the origin arm. Section 8
  cannot mechanically use incompletely specified v4 fixtures with the
  promised accept/reject assertions.
* Section 5.1 still requires a diagnostic to name the specific dangerous
  *successor* and that successor's predicates. The corrected one-phase
  origin violation has no successor at all. Section 8 permits an origin
  witness, but §5.1 has not been reconciled. For propagated violations,
  the immediate successor still need not be the checkpoint or the phase
  that should receive authority. A witness path is useful; prescribing an
  authority grant at that immediate successor is not entailed by the rule.

Minimal remaining correction:: Finish the existing requirement: explicitly annotate every example's version/mode and required booleans, recompute its verdict under the corrected predicates, and define an origin diagnostic as well as a consistent successor/path diagnostic.
