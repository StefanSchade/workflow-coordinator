== Verdict

R2's architecture holds. Seven points need correction or extension before implementation; none reopens the package structure.

[cols="1,3,4",options="header"]
|===
|# |R2 position |Disposition

|C1
|Role bindings are a field of the committed Commission; a different model is a different Commission (Q4: yes).
|*Reversed.* The engine already receives bindings as a separate file, freezes them before the first dispatch and records them per Hop. The Commission stays binding-free; the Front Door freezes an execution envelope beside it. One authorization names both digests (<<c1>>).

|C2
|`--yes` is first-class; Q1 left "one confirmation or none" open.
|*Confirmed and closed* by Maintainer decision. Three residual points where an unattended lifecycle could still stall or fail late are closed (<<c2>>).

|C3
|The pre-authorization half is "pure" and includes the baseline probe; `wfc plan` is that half.
|*Corrected.* `plan` executes no project command. The probe runs after authorization and before the Commission commit, and additionally asserts that the check leaves the tree clean (<<c3>>).

|C4
|Engine detached, `flock` held for the engine's lifetime; a surviving provider is reported as a risk.
|*Extended.* A lock cannot attest that providers have stopped. A small supervising host process makes quiescence an observed fact in every case but its own abnormal death, which is classified as unknown (<<c4>>).

|C5
|No preservation: after a stop the user discards or keeps the working-tree changes.
|*Added.* Automatic, non-authoritative preservation of the uncommitted candidate under `refs/wfc/candidates/`, by Git plumbing on a private index, with a classified fallback (<<c5>>).

|C6
|"No outcome triggers a successor ... simply the next `wfc run`."
|*Extended.* Beta 1 records lineage and the assurance baseline for a successor started with `--continues`; `wfc continue` follows as package RP1 (<<c6>>, <<disposition>>).

|C7
|`wfc.audit/1` with `lifecycle_outcome`; an interrupted Run is archived as it stands.
|*Extended* by five blocks, added before the schema first ships, that keep observed facts apart from the controller's classification (<<c7>>).
|===

Recommended disposition *[R]*: alternative B of the assignment. Beta 1 ships supervision, truthful classification, automatic preservation and the lineage record. `wfc continue` ships shortly afterwards as RP1. The critical path keeps its shape and grows by roughly one small-to-medium unit of work.

== Focused findings

[[c1]]
=== C1 -- The Commission and the execution bindings are separate artifacts

[horizontal]
Second pass:: `commission.json` carries `execution.roles`; the request accepts a per-request `roles` override; `CompiledCommission` has a `bindings_text` member; Q4 recommends "yes", with the consequence that "a different model is a different Commission".
Evidence:: G1 to G5. The boundary the Maintainer asks for is the one the engine implements and three earlier records state: the 2026-10-28 contract design, `DEC-WFC-016` (the Harness writes bindings from explicit inputs) and R1's own list of interfaces worth preserving ("execution bindings outside the Commission, keyed by role"). *[E]* `DEC-WFC-020` requires that the operator can *see*, before and after execution, which bindings entered it. That is a visibility requirement and says nothing about co-location. *[V]* Functional Model UC-02 calls model choices "illustrative commercial bindings, not the definition of the workflow program".
Corrected design:: Five things in four places, below. The Commission names roles; it never names an adapter, model, reasoning level or executable.
Why it matters:: A caller that commissions work, whether a person or a later orchestrator, supplies task, scope and program and nothing about providers. One committed Commission can be executed more than once under different envelopes from the same baseline, which is how a controlled model comparison has to work. *[E]* The Maintainer has already run one by hand (`experiments/operator-manual-h001-model-replays-20261111` in the Evidence repository). R2's attempt identifiers end in an attempt counter, which already presumes several attempts per Commission.
Remaining uncertainty:: Where project-level binding defaults live. A user-level default (models are an account and machine fact as much as a repository fact) is plausible later; it is additive because the envelope, not the configuration, is what gets recorded.

[cols="2,3,3",options="header"]
|===
|Responsibility |Artifact |Owner and lifetime

|Commissioned work: task, scope, program, roles, personas, evidence, actions
|`.wfc/commissions/<id>/` in payload Git; digest of `commission.json`
|Whoever commissions. Immutable once committed.

|Execution configuration: the inputs to selection
|`execution.bindings` in `.wfc/config.yaml` as project default; `--bind ROLE=ADAPTER:MODEL:REASONING` per invocation (the Harness grammar, G4)
|The Front Door reads it. It is not part of any Commission.

|Frozen Run execution envelope
|`OPS/<attempt>/execution-bindings.yaml` (schema 1, unchanged) and the `envelope` block of the lifecycle journal
|The Front Door, at authorization. One per attempt.

|The Coordinator's actual bindings
|`--execution-bindings <file>`, parsed once (G1, G2)
|The engine. Unchanged.

|Audit record of what executed
|`operator-plan.json` `role_bindings`; per-attempt rows in `execution-evidence.json`; `audit.json`
|The engine writes; the archiver projects.
|===

Consequences for R2's contracts:

* `commission.json` loses `execution`. It gains nothing: the role set is already implied by the program and present in the rendered profile.
* The request (`schema: 2`) loses `roles`. A binding override is an option of the invocation, beside the request and never inside it.
* `compile_commission` does not receive bindings and `CompiledCommission` has no `bindings_text`. A separate `resolve_execution(config, overrides, roles)` produces the envelope. `admit_parsed` takes the parsed bundle and the parsed bindings as two arguments, mirroring `_preflight`.
* The authorization record names two digests, `commission_sha256` and `envelope_sha256`. One confirmation, or one `--yes`, covers both. Nothing here adds an approval: selection is a Front-Door responsibility, and the requirement is only that the selected identities are frozen and recorded before dispatch. G3 shows the engine already does this for its own record.
* In `.wfc/config.yaml`, personas (commissioned content, rendered into the WorkItem) and bindings (execution configuration) sit under separate keys so that the two responsibilities are not interleaved in one `roles` block.

Effect on the properties the assignment lists:

[cols="2,5",options="header"]
|===
|Property |With the corrected boundary

|Commission schema and compilation
|Smaller. Compilation is independent of provider availability, so `wfc commission verify` can re-compile without knowing any model.

|Run identity and provenance
|Commission to attempt is one to many. An attempt is identified by its own identifier, Run ID, Commission digest and envelope digest.

|One-command use
|Unchanged. `wfc run task.md --scope ...` resolves both and shows both in one summary.

|Repeated execution, model comparison
|Same Commission commit, different envelope, separate attempt. Because Hop commits land on the checked-out branch, a second attempt from the same baseline needs its own worktree or branch. Beta 1 provides the boundary and no command for this.

|Historical reconstructability
|Commission bytes from payload Git; executed bindings from `operator-plan.json` and `audit.json` (R2 already lists adapter, model and reasoning per Hop there).

|Admission and execution contracts
|Unchanged (G1).

|BP2 and BP4
|See <<packages>>.
|===

[[c2]]
=== C2 -- Unattended execution is the normal case

[horizontal]
Second pass:: One confirmation on a terminal; `--yes` first-class and required without a terminal; no further prompt through the archive. Q1 offered "no prompt at all" as an alternative.
Evidence:: *[V]* Both adapters already run providers without interaction (`--ask-for-approval never`; `--permission-prompts none`). Nothing in the engine reads standard input.
Corrected design:: Q1 is closed by Maintainer decision: an interactive invocation confirms once, `wfc run ... --yes` runs the complete authorized mechanical lifecycle. Three additions make that hold in practice.
Why it matters:: A script or an outer agent sees exactly one command and one exit code. A lifecycle that can only finish after a human looks at it is not unattended.
Remaining uncertainty:: None architectural.

. *No terminal and no `--yes` is a refusal, not a wait.* Exit 2, before anything is written. `wfc init` takes every answer as a flag and never asks when standard input is not a terminal.
. *Everything knowable is checked before authorization.* R2 validates the Evidence repository only when the archive is written. An unattended Run would then spend its whole budget and end unfinished (exit 3) for a reason that was visible beforehand. The destination is checked provider-free in the read-only half (exists or can be created, is a Git repository, nothing staged) and checked again when written.
. *Every post-launch step is prompt-free and has a deterministic outcome.* This includes the two steps this review adds, quiescence and preservation (<<c4>>, <<c5>>). A step that cannot complete ends the command with exit 3 and a single named remedy.

A need for more authority never widens anything silently. It surfaces as one of three mechanical outcomes: a refusal before launch (exit 2; for example a changed provider binary between authorization and launch), a Run that stops with a human question (exit 1, archived, reported), or a Continuation that is refused for lack of a required input (<<c6>>). The exit codes of R2 stand; `report --json` carries the distinctions an orchestrator needs.

Interrupting the foreground command does not stop the Run: the engine is detached. The command says so and names `wfc stop` and `wfc resume`. `wfc stop <attempt>` is the one command this review adds to the Beta-1 surface (<<c4>>).

[[c3]]
=== C3 -- `plan` executes nothing; the probe follows authorization

[horizontal]
Second pass:: The flow labels resolve, compile, admit, *probe*, summarize as "PURE (nothing written, nothing persisted)" and defines `wfc plan` as "that half of the pipeline on its own". A failing baseline "refuses in the pure half".
Evidence:: *[V]* An evidence command is an arbitrary consumer-authored argv run with `shell=False` at the repository root in the inherited environment, with no containment (`ProductionEvidenceRunner.observe`). It may write files, contact services and run for up to 900 seconds; on timeout only its direct child is killed (G10). *[V]* The engine requires a tree clean of non-ignored untracked files before every Hop (G11).
Corrected design:: Two operations with different natures, kept apart by the authorization line.
Why it matters:: A command documented as an inspection must not run project code. The corrected placement also gives the probe a second job that the first placement could not do: catching a check that dirties the tree.
Remaining uncertainty:: The probe runs on the baseline before the Commission bundle is committed, so a check that scans every file in the tree does not see `.wfc/commissions/<id>/`. Stated as a limitation; see the alternatives below.

[cols="2,4",options="header"]
|===
|Operation |Definition

|Read-only planning (`wfc plan`, and the first half of `wfc run`)
|Reads Git, configuration, package resources and file metadata. Resolves evidence and provider executables and records their fingerprints. Executes no project command and no provider. Writes nothing (`--out DIR` outside the repository excepted).

|Baseline probe (inside `wfc run`, after authorization)
|Executes `task-check` once through `ProductionEvidenceRunner`, in the frozen environment, on the clean baseline. A project command; covered by the same single authorization, whose summary states that it will run and for how long at most.
|===

Sequence after authorization: journal, *probe*, Commission commit, committed admission, launch. The probe passes only if the check passes *and* the repository is afterwards at the same HEAD with a clean tree and nothing staged.

[horizontal]
Failure scenario for the cleanliness assertion:: A check writes a non-ignored file (a coverage database, an updated snapshot, a generated source). In a Run this surfaces after the first gate review as `inter_hop_git_validation_failed` or as a dirty tree at the end, after the provider spend. *[V]* `preflight_hop`.
Cost:: One `observe_repository` call.

Failure reporting, all exit 2 with nothing committed and no provider invoked:

* Check fails or times out: status, exit code and the bounded output tail; the log and exit code are written to `OPS/<attempt>/baseline-task-check.log` and `.exitcode` (names the archive allow-list already admits, G16).
* Check passes but leaves the tree dirty: the offending paths are listed. WFC does not remove them; they are the project command's output.
* Either way the journal is closed with outcome `not_launched` and the reason, and the active-lifecycle pointer is cleared. R2 did not define how a lifecycle that was authorized but never launched ends; this is that definition, and it also covers a failed committed admission (there the Commission commit remains and is reported).

Alternatives considered:

* *Probe after the Commission commit.* Exactly the launch state, but every probe failure leaves an inert Commission commit, and probe failures are the common first-use failure. Rejected.
* *No probe.* Simplest. Loses the protection R2 justified with recorded evidence, and the new cleanliness check. Rejected; `environment.baseline_check: false` remains for a project whose baseline is intentionally red.
* *A probing `plan` mode.* Unnecessary. `wfc run ... --until probed` is the same controller stopped early, in the style of R2's `--until committed`; it needs the same authorization because it executes project code.

The probe is skipped, and recorded as skipped, when a successor starts from an adopted unaccepted candidate, which may legitimately be red (<<c6>>).

[[c4]]
=== C4 -- Process supervision and quiescence

[horizontal]
Second pass:: The controller takes an exclusive `flock`, passes the descriptor to a detached engine and closes its copy; "the lock lasts exactly as long as the engine process". Monitoring rule: lock free with a summary is terminal, lock free without one is `interrupted`. A surviving provider is noted as an unresolved risk.
Evidence:: G6 to G11. By G7 the lock is released when the engine dies whatever the provider is doing, so "lock free" proves nothing about providers. By G6 no record identifies the provider process afterwards. By G9 "summary present" does not prove an engine-terminal status.
Corrected design:: A supervising host process between controller and engine, with a completion record. The engine and both adapters stay unchanged.
Why it matters:: Three later steps depend on knowing that nothing is still writing: preservation would otherwise capture a half-written candidate, the archive could be overtaken (*[V]* Codex writes its last message into STATE through `--output-last-message`), and a successor launched in the same checkout would have a predecessor's provider writing into its Hop, to be committed under the successor's identity if the paths are in scope.
Remaining uncertainty:: Operating-system and provider behaviour not exercised here; see the experiments.

==== Mechanism

[source,text]
----
wfc run (controller, foreground)
  +- host   own session; stdin null; output to OPS/run.log; holds engine.lock
       +- engine   python -m workflow_coordinator.operator ...   (inherits the lock descriptor)
            +- provider   own session per invocation (G6); does not hold the lock (G7)
            +- evidence command   engine's session (G10)
----

The host does five things and nothing else:

. Marks itself a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER)`), so every descendant orphaned by the engine's death is re-parented to the host instead of leaving the tree, whatever session it is in. *[V]* The package already calls Linux-only primitives through `ctypes` and refuses where they are missing (`operator._rename_no_replace`).
. Writes `host.json` (its own and the engine's process identifier and start time, and the boot identifier), starts the engine, waits for it.
. After the engine exits, terminates whatever descendants remain: `SIGTERM` to each remaining child's process group, a short grace period, `SIGKILL`, repeated until it has no children. A provider that outlives its engine cannot have its result admitted, so letting it run only costs money and mutates the tree.
. Writes `host-exit.json`: the engine's exit code or signal, how many descendants remained, which were signalled, and `quiescent: true`.
. On `SIGTERM` (sent by `wfc stop`) it terminates the engine and proceeds with steps 3 and 4.

The lock is held by host and engine together, so "lock held" means one of them is alive. The engine's behaviour on signals (G8) is left as it is; a stopped Run is classified by the controller, not by the engine.

==== The six cases

[cols="3,3,3",options="header"]
|===
|Case |Observed facts |Result

|1. Controller interrupted, engine alive
|Lock held; `host.json` processes alive.
|Running. `wfc resume` re-attaches by waiting on the lock. Nothing is reclassified.

|2. Engine terminated after a completed Hop
|Lock free; `host-exit.json` present; no engine-terminal summary; no `dispatch.json`, or its Hop is recorded in `run.json`; HEAD equals the Run's current HEAD; tree clean.
|`interrupted`, class `at_hop_boundary`. No provider outcome is pending and nothing needs preserving: every completed Hop is a commit.

|3. Engine crash between Hops
|As 2. If the crash fell between the trusted commit and the `run.json` write (G11): `dispatch.json` present, Hop not recorded, HEAD one or more commits past the marker's `base_head`.
|As 2; or class `during_hop` with `head_moved`. The commits are listed as facts. The controller does not decide whether the Hop "counted".

|4. Engine crash during a provider invocation
|Lock free; `host-exit.json` shows descendants terminated; `dispatch.json` present, Hop not recorded; HEAD equals `base_head`; tree possibly dirty.
|`interrupted`, class `during_hop`; provider outcome `unknown`; candidate preservation applies (<<c5>>).

|5. Provider alive after engine termination
|As 4 while the host is working: lock still held by the host.
|Not yet terminal. The host ends it and the case becomes 4.

|6. Uncertain dispatch, partial persistence
|Engine-written `reconcile_required` with an `uncertain_dispatch` Hop (the engine's own conservative path); or a failure summary (G9) with `operator_status: failed`.
|The first is an engine status and is reported as such. The second is `interrupted`, class `engine_error`, with the error text as a fact, and is then read by the marker rows above.
|===

An engine that never reached its first dispatch (STATE holds a plan and no `run.json`) is `interrupted`, class `before_first_dispatch`. In every row the launch is not repeated: *[V]* the engine refuses an existing state root, and the controller never removes one.

==== What the host cannot attest

If the host itself is killed, no completion record exists.

[cols="3,4",options="header"]
|===
|Observation |Quiescence

|`host-exit.json` present with `quiescent: true`
|`attested`: the host observed that it had no descendants left.

|No `host-exit.json`; boot identifier differs from `host.json`
|`reboot`: no process of that boot exists.

|No `host-exit.json`; lock held; host process gone
|Engine running unsupervised. Reported as such. `wfc stop` signals the engine directly.

|No `host-exit.json`; lock free; same boot; engine wrote a terminal summary
|`not_attested`: the engine waited for every provider it started (G6), but nothing observed their descendants.

|No `host-exit.json`; lock free; same boot; no terminal summary
|`unknown`.
|===

With `not_attested` or `unknown`, preservation and archive do not run and a new launch in that checkout is refused; the command ends with exit 3. The remedies are a probe, if the experiments show one to be reliable, or `wfc resume --assume-quiescent`, which records `asserted` with the operator as the source. This is the honest floor for a rare case (a `SIGKILL` aimed at one small process); it is deliberately not disguised as a detection.

==== Experiments and tests

The experiments need a real provider or a real kernel behaviour and precede the design freeze of BP4a. None is authorized by this review.

|===
|# |Question |Decides

|X1
|When the engine dies mid-invocation, does `claude -p` or `codex exec` stop by itself once its output pipes have no reader, and how long does it keep writing the worktree?

Deterministic tests, all with a scripted fake provider in the neutral fixture and no real provider:

* Kill the controller during a Hop; `resume` re-attaches; one launch.
* Kill the engine at each point of G11 (before the marker, during the invocation, after the commit, after `run.json`, before marker removal). Assert the classification row, that `host-exit.json` exists, and that no relaunch occurs.
* A fake provider that ignores `SIGTERM` and starts a detached writer: the host kills both; no write to the tree occurs after `host-exit.json`.
* The provider process does not hold the lock descriptor.
* Kill the host during an invocation: status reports an unsupervised engine; after the engine is killed, quiescence is `unknown`, no candidate ref is created and `wfc run` refuses.
* `SIGINT` to the engine leaves `dispatch.json` and no summary. This pins G8 so that a later engine change is noticed.
* The classifier as a pure function over fixture STATE directories and Git facts, table-driven from the rows above, including G9.
* `wfc stop` yields `interrupted` with a `stop_requested` fact.

[[c5]]
=== C5 -- Automatic candidate preservation

[horizontal]
Second pass:: None. After an interruption the report "states that the working tree may be dirty"; the user "discards or keeps the working-tree changes".
Evidence:: G11, G13, G15, G16. *[E]* The normative recovery section defines four maintainer-chosen outcomes and an exact manual procedure whose invariant is "salvage commit delta == frozen dirty candidate delta". *[V]* The existing `export-salvage` serves a different purpose (prompt context for a successor), refuses the whole export on one out-of-scope path and is limited to one stop kind (G13).
Corrected design:: A lifecycle step, `preserve`, between quiescence and archive. It creates a commit object from the dirty tree with a private index and publishes it under `refs/wfc/candidates/<run-id>/<hop-id>`. It touches neither the working tree, nor the real index, nor any branch.
Why it matters:: `GOAL-WFC-001`. The next `wfc run` refuses a dirty tree, and the quickest way for a user to get past that refusal destroys the work the Run paid for.
Remaining uncertainty:: Line-ending and attribute normalization on unusual repositories (the implementation choice below); size caps.

==== What can be known about the dirty tree

The engine supplies one strong fact and WFC must not claim more than it. By G11 the tree was clean at the Hop's `base_head` when the Hop was dispatched. Therefore every non-ignored difference between `base_head` and the tree arose during or after that Hop's execution window. That window contains the provider, its descendants, the trusted check if it ran, and anything a person did in the same checkout meanwhile. WFC cannot tell these apart by content.

Consequences:

* Changes that existed before the Run cannot be present: launch requires a clean tree.
* "Produced by the agent" is never recorded. What is recorded is `origin: hop_window` plus whether the capture happened inside the supervised lifecycle (quiescence `attested`, capture immediately after) or after an unsupervised interval (`reboot`, `asserted`).
* Ignored files are outside the candidate, as they are outside every trusted commit.

==== Candidate predicates

All are observations. If all hold, the result is class `candidate`.

. Quiescence is `attested`, `reboot` or `asserted` (<<c4>>).
. The repository is the registered checkout, and HEAD equals the Run's current HEAD as persisted in `run.json` (for an interrupted Hop this equals the marker's `base_head`, G11).
. The real index equals HEAD; no merge, rebase or cherry-pick is in progress; submodules are resolved.
. Every changed path (the enumeration `trusted_commit` uses: differences from HEAD plus non-ignored untracked files) lies inside the stopped Hop's phase scope, read from the profile at the Run's baseline as `_export_salvage` does, and is a regular file or a deletion.
. No clean or process filter is configured (the `trusted_commit` rule, G16).
. The change set is within a size cap.
. The tree computed from the working tree is identical in two consecutive passes.

Predicate 7 is the normative exactness check and a minimal stability check at once: two equal tree identifiers show that the preserved tree is the working tree and that it did not change during capture.

==== Creation

[source,text]
----
private index  <-  read-tree <HEAD>
private index  <-  add/remove exactly the enumerated paths
tree           =   write-tree                       (twice; identifiers must match)
commit         =   commit-tree <tree> -p <HEAD>     (fixed identity; subject wip(wfc): ...; trailers below)
ref            =   update-ref refs/wfc/candidates/<run-id>/<hop-id> <commit>   (create-only)
----

* Every command runs through the `_trusted_git` policy (G16) with the private index named explicitly. This matters for more than commit hooks: a ref update can trigger a `reference-transaction` hook, and staging can run configured filters.
* Staging uses the same semantics as `trusted_commit`, so the preserved tree is byte for byte what a trusted commit of the same paths would have contained. Hashing raw bytes without Git's normalization would bypass filters by construction but can make an adopted candidate appear modified on repositories with line-ending attributes. This is a local implementation choice with that constraint.
* Trailers: `WFC-Attempt`, `WFC-Run`, `WFC-Hop`, `WFC-Base`, `WFC-Status: unaccepted-candidate`. The subject follows the two existing precedents (G15) and deliberately does not satisfy the Hop-commit subject rule.
* The same change as a binary-safe patch (`git diff --binary <HEAD> <commit>`) is written to `OPS/<attempt>/H<nnn>-worker-dirty.patch`, with the status listing beside it. Both names are already on the archive allow-list (G16), so the raw archive holds a copy that does not depend on the payload repository.

Idempotent by observation: ref present, its tree equal to the working tree and its parent equal to HEAD means done. Ref present and tree clean means done (the user adopted or discarded since). Ref present and the working tree different and dirty means `changed_after_preservation`: the ref is never moved, and the state is reported.

==== Fallback

If predicate 1 fails, the step is deferred (<<c4>>). If any of 2 to 7 fails, no commit and no ref are created. The result is class `forensic`: the status listing and `git diff --binary HEAD` are written to OPS under the same names, untracked files are listed with size and SHA-256, the failed predicates are recorded, and the report states that the working tree holds the only complete copy. This is the existing outcome 3 ("forensic preservation only ... a patch is appropriate"), reached mechanically. A `forensic` result is never offered to a Continuation as a starting point.

==== What preservation is not

It decides nothing about value, review or acceptance. It does not clean, reset or stash. It does not put anything on a branch. It is the third bounded Front-Door Git write after the Commission commit and the archive commit, and the only one that turns agent-written bytes into a Git object without a `CommitIntent`, which is why it is confined to a ref namespace no ordinary push or checkout uses.

It does contradict one sentence of a normative document and one Project Memory note (G15): WFC "does not automatically ... create salvage commits". The Maintainer has stated the desired behaviour; amending that section is the act of adoption (M1). The rest of that section stands and is what this design implements: salvage preserves work, not authority.

One related fact belongs in the quickstart, not in a new mechanism. Hop commits of a Run that does not complete are already on the checked-out branch (R1, product limits). "Unaccepted work" therefore has two forms: commits in the range baseline to final HEAD, recorded by reference, and the uncommitted remainder, which this step preserves.

[[c6]]
=== C6 -- Continuation semantics

[horizontal]
Second pass:: Continuation is "simply the next" invocation of `wfc run`; resuming an interrupted Run is "not open" (`DEC-WFC-014`, F1).
Evidence:: G12 to G14. *[E]* `DEC-WFC-014`: a successor is a fresh, separately authorized Run. *[E]* The recovery section: "execution starting point != assurance baseline"; "the fresh reviewer evaluates the complete resulting product against the real assurance baseline, including salvaged ancestry". *[V]* The engine gives a reviewer only the prior Hop range of its own Run (`operator._reconstructed_context`), so a successor's reviewer is not told about earlier work unless the task says so.
Corrected design:: Six operations, kept distinct; one lineage record; one product-owned clause.
Why it matters:: Without the lineage record, related Runs cannot be found again. Without the assurance-baseline clause, a successor's review silently covers only the successor's own changes, which is the one way preserved work could gain credit it has not earned.
Remaining uncertainty:: X5; the composition of the successor task has never been automated.

==== Lineage and the assurance clause (Beta 1)

`wfc run ... --continues <attempt>` resolves the predecessor from its lifecycle journal, or from its `audit.json` when OPS is gone, checks that it belongs to the same repository, and records a `lineage` block in `commission.json` (<<contracts>>). Two values in it are observed, not chosen:

* `starts_from` is `candidate` if the successor's baseline equals the predecessor's candidate commit, `predecessor_head` if it equals the predecessor's final HEAD, else `other`.
* `assurance_baseline` is the predecessor's own assurance baseline, or its Run baseline if it had none, so the value is constant along a chain.

When a lineage is present the compiler adds one product-owned clause to the task: the commits in the range from the assurance baseline to the successor's baseline are unaccepted work of the named Run; every line is unverified and may be kept, changed or removed; review covers the whole range; earlier review artifacts are informative only. No engine change is involved.

==== `wfc continue` (RP1)

`wfc continue <attempt>` is a convenience over `--continues`. It builds the successor request from the predecessor's committed `request.yaml`, the same program, the same scope unless `--scope` is given, a product-owned continuation block (stop reason, the human question verbatim and labelled, candidate and review-artifact references) and an optional additional task file. It then shows the ordinary plan and runs the ordinary lifecycle. Three questions need decisions.

*How the successor receives the preserved work.*

[cols="2,4,2",options="header"]
|===
|Way |Mechanics |Assessment

|Adopt as starting point
|If the working tree still equals the candidate tree: advance the checked-out branch to the candidate commit by compare-and-swap and refresh the real index. No file changes; the tree becomes clean. The successor's baseline is the candidate commit.
|*Recommended* (M4). It is the canonical manual procedure with the manual step removed. The summary names the commit the branch will advance to.

|Reference only
|The successor starts at the predecessor's HEAD on a tree the user has cleaned; the task names the candidate ref, and the worker reads it with read-only Git and re-applies it. *[E]* Done once by hand (`wfc-claude-code-adapter-implementation-continuation-001`).
|Works in Beta 1 with no mechanism. Costs a re-implementation Hop.

|Untrusted context
|The existing descriptor path (G13).
|Not used by the Front Door: one stop kind, 65,536 bytes, text only, dependent on predecessor STATE and absolute paths, and not independently accepted.
|===

Adoption does not make the candidate trusted. Its commit keeps the `unaccepted-candidate` trailer, lies inside the assurance range and is reviewed like every other line.

*Where the successor enters.* `implement` by default. For `robust@v1`, `broad_review` when the predecessor stopped in a review phase with a clean tree, which is the motivating case of `FTR-WFC-FRONT-DOOR-PHASE-ENTRY-CONTINUATION`. Never `correct` or `focused_review`: *[E]* Findings are local to a Run and do not transfer, so those phases would start without the state they exist to dispose of. Entering at broad review cannot skip a review, so the program's guarantee holds. The entry phase is derived by the Front Door from predecessor facts and a per-program constant; it does not become a free request field. This lifts, for one case, the 2026-10-28 rule against initial-phase selection (M5).

*What an unattended Continuation requires.* `wfc continue --yes` never widens scope. If the predecessor stopped with a semantic question, an answer must be supplied (`--answer`), or the command is refused with exit 2: a successor to a question that nobody answered would stop at the same place after the same spend. The answer enters the task under its own label.

The Front Door records lineage in the Commission, for every stop kind, and does not use the engine's descriptor (G12, G13). Reconciling the two, by widening the descriptor's eligibility or retiring it, can wait (M6).

=== Governance economy

Added by this review, each a mechanical step or refusal with the failure it prevents stated in place: the tree-cleanliness assertion after the probe (<<c3>>); the quiescence requirement before preservation, archive and a new launch (<<c4>>); the answer requirement for an unattended Continuation after a question (<<c6>>). One operator override exists, `--assume-quiescent`, for one rare state.

Removed relative to R2: bindings from the Commission and the request; the idea that changing a model requires a new Commission; project code from the planning path.

Deliberately not added: an approval for model selection; a policy for which models a role may use; a second ref namespace; a state machine for recovery; a series or ledger record; any change to the reducer, to persistence or to the result contract.

== Limits of this review

* Nothing was executed. Every statement about signals, sessions, subreaping and descriptor inheritance beyond what G6 to G10 read from source is *[I]* until X1 to X4 and the tests of <<c4>> run.
* Provider CLIs were read only through the adapters' argv. Their process trees and sandbox helpers were not inspected.
* The `export-salvage` and `prepare-successor` code was read for eligibility, binding and limits (G13), not reviewed for correctness; its open requirement R1A was not examined.
* `git_facts` staging semantics on repositories with line-ending attributes, sparse checkouts, submodules or large files were not analysed beyond the refusals named in <<c5>>.
* The Findings and convergence structures remain as unexamined as R2 left them.
* macOS and Windows were not assessed.
