== Verdict

The first review's diagnosis stands: the Level-0 engine is payload-agnostic, and everything a third party touches is not. Its remedy does not stand. It chose the path of least change to existing source resolution, and three of its nine decisions follow from that choice rather than from the product.

. *Product resources should be owned by the package and frozen by the compiler, not copied by `wfc init` and not resolved by the engine.* *[V]* The engine reads every governing input, including prompt components, from the payload repository's Git tree at the expected HEAD (`operator._preflight`, `_pinned_text`), and re-reads them between Hops (`_governing_inputs_unchanged`). The compiler can therefore write the effective role texts into the Commission directory it already creates. The engine is untouched, nothing is duplicated per repository, an upgrade changes nothing already committed, and the exact bytes that governed a Run are in the payload's own history. The first review's two options (materialize at `init`, or change engine resolution) missed this third one. It is the central design choice of this document (<<resources>>).
. *One command is achievable with existing mechanics, but only the controller can be made restartable, not the Run.* *[V]* `operator.main` always calls `_preflight`, which refuses an existing state root. The dispatch marker and `recover_uncertain_dispatch` exist, but no production entry point re-enters a Run after its process dies. *[E]* The backlog says the same (`FTR-WFC-ATOMIC-HOP-RECOVERY`: "no production operator entry point"). The end-to-end controller therefore has exactly one non-repeatable step, the launch; every other step can be made idempotent by observing Git, STATE and the Evidence repository. An interrupted Run is a terminal outcome to archive, never something to relaunch (<<lifecycle>>).
. *A separate Evidence repository is the right default, and the audit projection is what makes it shareable.* *[V]* In the archived Run sampled, eight of twelve files contain absolute home-directory paths, and the archive also holds the full frozen `PATH`, role personas and the agent's result message. The archive wrapper is also not retry-safe: a failure between copy and commit leaves a destination that the next attempt refuses twice over. Port first, project second (<<evidence>>).
. *The user-facing surface shrinks to one file and one command.* `.wfc/config.yaml` carries the authority ceiling, the check command, role bindings and optional guidance. The RepositoryPolicy record, the three 40-character source pins, the component manifest, the review-artifact paths and the withheld-authority boilerplate become compiler output (<<config>>).
. *Self-development becomes an ordinary consumer plus one rule.* The three-repository topology is replaced, for the product, by a recorded package identity and a refusal to operate on the repository the running package is imported from. The Runtime clone remains a Maintainer practice for producing that installation (<<preparation>>).

Where this review disagrees with the Maintainer's revised direction:

* "Package-owned resource resolution" is right as ownership and wrong as a Coordinator feature. Resolution belongs in the compiler; the Coordinator should keep reading only pinned Git blobs.
* "Restartable" must be stated narrowly. A design that implies an interrupted agent invocation can be continued would contradict `DEC-WFC-014` and the engine as built.
* Dropping the exported-baseline evidence environment removes a step the normative preparation contract lists. *[V]* The only current implementation already does not perform it (`prepare_development_environment`: "installed from the LIVE Development checkout (never an export)"), and the contract's own Harness subsection says so. The generic contract should state what the product actually guarantees (<<preparation>>).
* The separate Evidence repository reverses the stated preference of `DEC-WFC-023` (repository-local `.wfc/archive/`). That is a decision to record, not a detail (Q3).

Size of the work *[R]*: nine packages, of which six are on the critical path (<<packages>>). No reducer, persistence, adapter or result-contract change. Two small additive engine changes: an extracted admission function and an implementation identity in `operator-plan.json`.

=== Data and control flow

[source,text]
----
wfc run task.md --scope cmd/list --scope internal/render
  |
  |  PURE (nothing written, nothing persisted)
  v
resolve     config@HEAD + request + package resources + machine facts
compile     -> Commission bundle in memory (engine inputs + frozen role texts + commission.json)
admit       schema, A1, role/binding coherence, evidence executables resolved
probe       optional: run task-check once on the clean baseline
summarize   effective scope, actions, program, bindings, check, branch
  |
  |  AUTHORIZATION (once): confirm on a terminal, or --yes
  v
journal     OPS/<attempt>/lifecycle.json + the exact bundle bytes     <- first persisted state
commit      bounded commit of .wfc/commissions/<id>/ only
admit       engine _preflight against the committed bundle at HEAD
launch      engine subprocess, same interpreter, frozen environment   <- the one non-repeatable step
monitor     wait; project progress from STATE read-only
terminal    completed | awaiting_human | stopped | reconcile_required | interrupted
archive     raw copy + manifest + audit.json -> Evidence repository, one commit
report      consolidated result, exit code
----

Everything above the authorization line is a pure function of committed configuration, the request, the installed package and the machine environment. Nothing needs cleaning up if the user declines, and `wfc plan` is that half of the pipeline on its own. Everything below it runs without returning control, and each step is recorded in a journal so that `wfc resume` can finish it.

=== Room for later capabilities

The boundary that keeps later features cheap is already in the flow: the Front Door *resolves*, the Commission *records resolved values*, the Coordinator *executes what is recorded*. A task class that selects models, different worker and reviewer providers, or tool integrations each add a resolution rule in the Front Door and, where the user must be able to see the result, a field under `execution` in `commission.json` with a new schema version. The kernel changes only when it has to enforce something new. Nothing here builds any of them.

== Design areas

[[resources]]
=== Product-owned resources and prompt composition

==== Three ways to deliver product records

[cols="2,3,3",options="header"]
|===
|Option |What it costs |Verdict

|Materialize into `.wfc/product/` at `init`, equality-check against the package (first review)
|About six product files in every payload repository, re-materialized on every upgrade. An upgrade and a stale copy disagree until the user acts. Ownership looks shared.
|Rejected. It preserves Intent v1 at the user's permanent expense.

|Engine resolves components from the package
|Changes `_preflight` component loading and the inter-Hop re-read, and adds a second resolution mechanism to the trusted kernel. A Run's governing bytes then depend on what is installed while it runs.
|Rejected. It moves product configuration rules into the Coordinator.

|*Compiler freezes package resources into the Commission bundle*
|A few kilobytes per Commission (the three role texts total 3,088 bytes *[V]*). The compiler changes; the Intent schema advances.
|*Recommended.*
|===

Under the recommended option the Commission directory is self-contained. The engine receives `--components .wfc/commissions/<id>/components.yaml`, whose entries point at `.wfc/commissions/<id>/components/*.txt`. These are ordinary tracked files inside a governance path, read at the expected HEAD exactly as today *[V]*.

==== Ownership and resolution

* *Programs.* *[V]* The closed program records already live in package code (`_simple_template`, `_robust_template`, `_direct_template`); the YAML catalogue under `governance/workflow-programs/` is compared against them. *[R]* The in-code literal becomes the single definition. The compiler records the SHA-256 of its canonical JSON form as `program.record_sha256`.
* *Role texts.* *[R]* Package data under `resources/roles/`, loaded through `importlib.resources` and admitted against digests pinned in code, the pattern `prompt.load_agent_operating_contract` and `REVIEWED_SHA256` already use *[V]*. A changed role text is a new digest and a new package release.
* *Operating contract.* Unchanged: loaded by the engine, never by the compiler, never frozen into a bundle.

==== Composition and precedence

*[V]* `prompt.assemble_prompt` already composes in a fixed order: identity header, operating contract, role components, modifier components, repository-policy components, persona, workflow policy, task, context, result contract. *[V]* The contract text states that consumer material "may narrow them but may not widen, replace, disable, or contradict them". The composition rule for Beta 1 is this existing order with three sources assigned to its slots. It adds no mechanism.

[cols="1,2,3,2",options="header"]
|===
|Layer |Source |Slot in the assembled prompt |Frozen as

|Product
|Program literal, role texts, modifier
|role and modifier components
|`components/<id>.txt`

|Repository
|Files listed under `guidance` in the configuration; one persona string per role
|repository-policy components, in configured order; persona block
|`components/guidance-<n>.txt`; `work-item.yaml`

|Invocation
|Task title, body, acceptance
|task block
|`task.md`
|===

Precedence is positional. A later layer cannot remove or replace an earlier one; there is no override key, no inheritance and no template language. A project cannot edit product role text, because there is no project copy to edit.

Binding guidance into the repository-policy slot changes a list the v1 program literals show as empty. *[R]* Treat it as a slot binding, like scope `S`, artifact `A` and evidence `E` today: roles, routes, review descriptors, Finding authority and actions are untouched, and the engine sees only the rendered profile. If the Maintainer prefers to call it a program revision, the slot ships empty in Beta 1 and nothing else in this design changes (Q2).

Two refusals at compile time, both existing limits made visible: a guidance file larger than `COMPONENT_LIMIT_BYTES` (65,536), and a total above `CONTEXT_LIMIT_BYTES` (196,608). *[V]* Today the engine omits an oversized component and records the omission; a silently omitted project rule is the worse failure.

==== Composition cannot extend authority

No new rule is needed. Scope, actions, routes and Finding authority come from the rendered profile and policy. *[V]* `trusted_commit` and the post-Hop observation enforce them regardless of prompt text. The compiler writes guidance only into component files; it has no path from a guidance file to `authorized_scope` or `authorized_actions`.

Freezing a copy also removes a friction the first review documented. *[V]* A selected component is a governing input, so A1 refuses any phase scope that contains it or lies inside it. With the original file selected, a Run scoped to `docs` is refused when `docs/ARCHITECTURE.md` is guidance. With a frozen copy selected, the original is an ordinary file again and can be in scope; the Run is governed by the bytes as they were when it was authorized.

==== Freezing, digests and audit after an upgrade

`commission.json` (<<contract-commission>>) lists every frozen resource with its layer, origin, digest and frozen path, plus the identity of the package that compiled it. After a package upgrade:

* A committed Commission is unaffected. Its governing bytes are Git blobs.
* `wfc commission verify` re-checks internal consistency (listed digests against blobs) with any version, and byte-exact re-compilation only when the installed identity equals `compiled_by`. A different identity is reported as such, not as a mismatch.
* A lifecycle resumed after an upgrade is refused before launch (<<lifecycle>>).

==== Compatibility with the existing programs

`simple@v1` and `robust@v1` are compiled from the same literals; the acceptance test for the new compiler is that the rendered profile equals the v1 rendering field for field, apart from the guidance slot and the component paths (BP2). *[V]* The verification gate of `direct@v1` has `finding_authority: []`; *[E]* its acceptance is unreconciled in the active-work manifest. It stays out of the Beta-1 set (R1-D5 unchanged).

One opportunity falls out of the compiler deriving review-artifact paths itself. If the worker phases receive only the requested scope and the reviewer phases only the artifact paths, worker and reviewer write scopes become disjoint with no engine change. *[E]* `FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION` reserves that for a future program version. This review only notes that the new compiler makes it a two-line decision; it is not part of the plan.

[[frontdoor]]
=== One-command Front Door and authorization

==== What the user authorizes

A `wfc run` invocation authorizes one Commission: this task, this scope, this program, these role bindings, this check, on this branch. Each of those is either typed in the invocation or read from configuration the user committed. Three properties keep that honest without a sequence of approvals:

. *No authority-bearing value is defaulted silently.* Scope is required per request and never defaults to the ceiling. Role bindings have no built-in default; `init` asks for them once.
. *The ceiling moves only by a human commit.* `.wfc/config.yaml` is a governance path. *[V]* A1 forbids any phase scope overlapping one, so no Run can widen the ceiling. `wfc run` never edits it.
. *Authorization binds to the effective contract.* The summary shows the compiled Commission, and the journal records the SHA-256 of `commission.json` together with how authorization was given.

*[R]* On a terminal, `wfc run` prints the summary and asks once. `--yes` skips the question and is a first-class flag, required when standard input is not a terminal. After that point there is no further prompt, including for the archive. This differs from the first review in two ways. It called `--yes` something not to offer by default; an outer agent or a script has no other way to use the product. And it committed the Commission *before* asking, which leaves a commit behind when the user declines; here nothing is written until authorization.

The alternative, no prompt at all, is defensible: nothing `wfc run` does is pushed, and every effect is a local commit or provider spend. It is Q1.

The shell-approval behaviour of an outer Codex or Claude session is unrelated. That session approves the single `wfc run --yes ...` command; WFC's own authorization is the recorded act above.

==== Commands

[cols="2,4",options="header"]
|===
|Command |Behaviour

|`wfc init`
|Write a `.wfc/config.yaml` skeleton and `.wfc/.gitignore`; create or adopt the Evidence repository. Asks only for what cannot be defaulted.

|`wfc plan <task> --scope ...`
|The pure half: resolve, compile, admit, summarize. Writes nothing. `--out DIR` writes the bundle outside the repository for inspection.

|`wfc run <task> --scope ...`
|The whole lifecycle. `--until committed`, `--until prepared` stop after that step for stepwise operation; `--request FILE` takes a complete request (the machine interface of `DEC-WFC-020`).

|`wfc resume [attempt]`
|Continue an unfinished lifecycle from its journal.

|`wfc status [attempt]`
|Read-only projection, as `wfc_op.py status` today; without an argument, the repository's latest attempt.

|`wfc archive <attempt>`, `wfc report <attempt>`
|The last two steps on their own; both idempotent.

|`wfc commission verify <id>`
|Check a committed Commission's listed digests against its files, and re-compile byte for byte when the installed identity matches.

|`wfc --repository ... --state-root ...`

|===

The segmented path is the same controller stopped early, not a second implementation.

[[lifecycle]]
=== Durable lifecycle

==== What can and cannot be restarted

[cols="2,2,4",options="header"]
|===
|Step |Repeatable? |How completion is decided on resume

|Compile, admit, probe, summarize
|Yes (pure)
|Not resumed at all. Nothing is persisted before authorization; a crash here is as if the command had not run.

|Commission commit
|Yes, by observation
|HEAD equals the recorded baseline and the tree is clean: write the stored bundle and commit. HEAD is one commit ahead, its parent is the baseline and its tree adds exactly the stored bundle bytes: adopt it. Anything else: refuse; the repository changed after authorization.

|Committed admission
|Yes (provider-free)
|Re-run.

|*Launch*
|*No*
|STATE absent and engine lock free: launch. STATE present: it was launched, whatever the journal says. *[V]* The engine itself refuses an existing state root, so a double launch cannot produce a second Run.

|Monitor
|Yes
|Engine lock held: wait. Lock free and `operator-summary.json` present: terminal. Lock free and no summary: `interrupted`.

|Archive
|Yes, by observation
|Destination tracked in the Evidence repository with the same Run ID: done. Staging directory present: delete and redo. Destination present but untracked: re-verify digests against STATE, then commit.

|Report
|Yes (pure)
|Recompute.
|===

This is what distinguishes a restartable process from a script that works while everything succeeds: each step's completion is read from the world (Git, STATE, the Evidence repository), and the journal contributes only the frozen inputs and the intent. A journal that says "launched" is never trusted over an absent state root, and the reverse.

==== The smallest persistent mechanism

One JSON file per attempt, `lifecycle.json` in the existing OPS directory, written with the existing `atomic_write_json`, plus the bundle bytes stored beside it at authorization (<<contract-lifecycle>>). Three supporting facts:

* *Engine lock.* The controller opens `engine.lock` in OPS, takes an exclusive `flock`, passes the descriptor to the engine child and closes its own copy. The lock lasts exactly as long as the engine process. A later `wfc resume` probes it without blocking. No PID guessing.
* *Detached engine.* The engine child starts in its own session with output to `run.log` in OPS. It survives the controller and the terminal. `wfc resume` attaches by waiting on the lock.
* *One active lifecycle per checkout.* A pointer file keyed by the repository's canonical path names the unfinished attempt. A second `wfc run` in that checkout refuses and prints the `resume` command. Justification: two lifecycles on one worktree would interleave commits on one branch and make every Hop's HEAD check fail (*[V]* `preflight_hop`); the pointer turns a confusing mid-Run stop into a refusal before any spend.

==== The five failure modes the assignment names

[cols="2,4",options="header"]
|===
|Failure |Prevention

|Duplicate Commission from a retried command
|An unfinished lifecycle blocks a new `wfc run`. Resume reuses the stored bundle and adopts an already-made commit.

|Duplicate provider dispatch
|Launch is never repeated once STATE exists. An interrupted Run is terminal. *[V]* Inside the engine, the dispatch marker already prevents re-dispatch of an uncertain Hop.

|Double archive or duplicate archive commit
|Deterministic destination keyed by attempt; tracked-destination check before any write; staging directory renamed into place only after verification.

|Reinterpreting an authorized Commission under changed configuration
|Resume never re-reads configuration or re-compiles. It writes the bytes stored at authorization, whose digest the authorization record names.

|Silently continuing with different execution identities
|Package identity, provider executable fingerprint and the frozen environment digest are recorded at authorization and compared before launch. A difference refuses the launch. After launch the engine process already holds its code; a changed package is recorded in the report as an anomaly and cannot be acted on.
|===

==== Terminal outcomes

`completed`, `awaiting_human`, `stopped` and `reconcile_required` are the engine's own statuses and are archived as they are. `interrupted` is the controller's classification of a Run whose engine process ended without a summary. It is archived too (F3), with `dispatch.json` noted when present, because the provider's outcome is then unknown. The report states that the working tree may be dirty and that a provider child process may still be running (<<risks>>).

No outcome triggers a successor. *[E]* `DEC-WFC-014`: continuation is a fresh, separately authorized Run. In this product that is simply the next `wfc run`.

Semantic ledger curation, Runtime promotion and push stay outside the controller. The mechanical archive commit is inside it.

[[evidence]]
=== Evidence storage and audit projection

==== Three layers, unchanged

Transient operational state (OPS, STATE, scratch) stays where it is. Durable mechanical evidence goes to an Evidence repository. Semantic interpretation stays a Maintainer practice with no product support. The home-directory layout gains one override (`WFC_HOME`) and a project slug in attempt names; it is not redesigned.

==== Destination

*[R]* A Git repository separate from the payload, created by `wfc init`.

* Default location: `<WFC_HOME>/evidence/<project>`, so a first user configures nothing and never sees a second repository unless they look.
* Override: `evidence.repository` in the configuration, relative to the payload root or absolute. Self-development sets `../workflow-coordinator-run-evidence`.
* Layout: `archive/<prefix...>/<attempt>/`, the existing shape. The prefix defaults to the project name; self-development keeps `unclassified` or domain and workstream from `--semantic-json`.

Repository-local storage remains an alternative, not the default. The arguments against it as a default are concrete: archive commits would land on the feature branch the Run is working on; *[I]* the Runs most worth archiving are stopped ones, whose tree is dirty; and (F5) today's files would put a user's home directory and provider binary path into shared history. The audit projection removes the third objection only.

==== What is committed

[cols="1,3,3",options="header"]
|===
|Setting `evidence.raw` |Committed to the Evidence repository |Raw files

|`local` (default)
|`audit.json` only
|Kept beside it on disk, excluded by the repository's `.gitignore`.

|`commit`
|`audit.json`, `manifest.json`, `run/`, `ops/`
|Versioned, as self-development does today.

|`discard`
|`audit.json` only

|===

The default makes the durable, shareable record the sanitized one, while keeping the raw files in a stable place for debugging. A user who later pushes the Evidence repository shares no local path, persona or provider output unless they chose `commit`.

==== Audit projection

`audit.json` (<<contract-audit>>) is derived from the raw archive after the copy is verified. Rules:

* *Portable.* Absolute paths are replaced by symbolic roots (`<repository>`, `<state>`, `<ops>`, `<home>`) or dropped. Executables appear as authored name plus fingerprint digest, not as a path.
* *No provider prose.* No result message, persona text, diagnostic tail or Finding text. Findings appear as identifier, status and blocking flag.
* *Original digests preserved.* The projection lists every raw file with its SHA-256 and size exactly as the raw manifest recorded them. Raw files are never rewritten to sanitize them.
* *Versioned.* `"schema": "wfc.audit/1"`. A later schema adds a new version; old records are not migrated.

==== What stays verifiable without the raw files

[cols="2,3",options="header"]
|===
|Fact |Verifiable from

|The Commission that governed the Run, byte for byte
|Payload Git: the bundle at the Commission commit, against the digests in `audit.json`.

|Every Hop's commit, subject and changed paths
|Payload Git.

|Review artifacts
|Payload Git.

|Which product role texts and program were used
|Bundle digests against the published package of the recorded version and tree digest.

|That the audit record was not altered after archiving
|The Evidence repository's own commit.

|Trusted evidence outcomes (exit classification, output digests)
|Not independently re-verifiable. They are the Coordinator's attested observation; *[V]* the output bodies were never stored.

|Content of a raw file
|Only by producing the file and matching its listed digest.
|===

==== Commit ownership, idempotency and integrity

* The controller is the only writer of archive commits. One commit touches one attempt directory, made with the same bounded commit function as the Commission commit. Never a push.
* The copy goes to a staging directory inside the Evidence repository and is renamed into place only after the existing verification (manifest parses, every listed file present, counts agree). A partial copy is never at the destination, which closes F4.
* The clean-repository requirement narrows to: nothing staged, and nothing dirty outside the attempt's own destination and staging directory.
* All existing self-consistency refusals are kept: state root against the plan's own `state_root`, agreement of Run ID, WorkItem ID, checkout ID and repository across sources, OPS coherence, destination isolation.

==== Reuse and sequencing

*[V]* `archive_run.py` derives its archive root from `__file__`; the wrapper locates OPS at `$HOME/wfc-ops/<attempt>` and is 517 lines of shell around an embedded Python probe. *[E]* Two of its three reviews concerned the shell and TSV protocol. *[R]* Two packages, deliberately separate:

. *BP5, port.* `archive_run.py` into the package with the root and OPS directory as parameters; wrapper logic in Python; manifest byte-compatible apart from `archived_at`. The 61 Evidence tests (21 helper, 40 wrapper) are ported first and serve as the specification. Adds staging and idempotent retry, nothing else.
. *BP6, projection.* `audit.json`, the `raw` setting, the report.

The existing 119 manifests are not rewritten and receive no `audit.json`. An archive directory without one is, by that fact, a pre-projection archive; <<identity>> gives the reading rule.

[[preparation]]
=== Generic preparation and runtime identity

==== What preparation becomes

*[V]* Today's `prepare` does seven things that are not about the payload: pin a Runtime clone, pin an Evidence clone, export and pip-install the Runtime per attempt, build a venv, pip-install the payload with `[dev]`, require `python3` to resolve into that venv, and run the Runtime's preflight under its own interpreter. For the product, all seven go:

* The installed package is the executing implementation. Its identity is recorded instead of a Runtime HEAD.
* The Evidence repository is validated at archive time, when it is used.
* No environment is built.

What remains is small: resolve the provider executable, freeze the environment, write the execution bindings, create the scratch directory, run admission.

==== The evidence environment contract

*[V]* The engine runs each evidence command with `shell=False`, working directory at the repository root, and the environment snapshot taken at admission (`coordinator-inherited-environment-v1`). The contract for Beta 1 states that and adds two things.

. *The user provides the environment; WFC records it.* The frozen `PATH` is the configured `path_prepend` entries followed by the ambient `PATH` at authorization. Its digest, the resolved executable and its stat fingerprint are already in `operator-plan.json` *[V]*.
. *A baseline probe demonstrates suitability.* Before authorization, WFC runs `task-check` once on the clean baseline, in the frozen environment, through the existing `ProductionEvidenceRunner`. A non-passing baseline refuses the run and shows the output tail.

The probe answers the assignment's point that an executable on `PATH` proves nothing about its dependencies. Its justification under the governance-economy rule:

[horizontal]
Failure scenario:: The check cannot pass in this environment, for reasons unrelated to the task. The Run discovers that only after paying for an implementation Hop. *[E]* This has happened repeatedly: a 900-second timeout in FTR05, and whole Hop budgets lost to the same gate ("Claude Adapter Environment Allowlist", "TMPDIR Scratch Provisioning" in the ledger).
Goal at risk:: `GOAL-WFC-001`: wasted provider spend and a stop the user must diagnose.
Why existing controls are insufficient:: Admission resolves the executable but does not run it.
Cost:: One execution of the check, at most its timeout. No human step. `environment.baseline_check: false` turns it off for a project whose baseline is intentionally red.

*[V]* The Evidence allow-list already names `baseline-*.log` and `baseline-*.exitcode`: a baseline run was an established manual practice before the Harness. This mechanizes it.

WFC provisions nothing. A project that needs a virtual environment, a toolchain or a container prepares it and puts it on `PATH`.

==== The normative preparation contract

*[V]* The canonical sequence in `ch03_running/01_preparation.adoc` includes "Export the exact target baseline and build the separate evidence environment", illustrated with `pip install "$OPS/target-src[dev]"`. The same file's Harness subsection states that the only current implementation does not do this and installs from the live checkout. *[E]* The September Latin Run did neither. *[R]* When BP7 lands, steps 4 and 5 of that sequence are amended to what the product guarantees: a recorded implementation identity, and a user-provided environment whose identity is recorded and whose suitability is probed. This is a change to a normative document and needs the Maintainer's assent (Q5); it is one section, not a reopening of the manual.

==== Self-development without the topology

The purpose of Runtime N and Development N+1 (`DEC-WFC-001`) is that the code executing a Run is not the code the Run is changing. One consumer-neutral rule preserves exactly that:

*WFC refuses to operate on a repository that contains the package it is running from.*

[horizontal]
Failure scenario:: An editable install from the payload checkout. A worker Hop edits `reducer.py`; the next Hop's evidence subprocess, or a re-import, runs the edited code inside the Run that is supposed to judge it.
Goal at risk:: Integrity of WFC's own orchestration and trusted operations (Functional Model 3.1).
Why existing controls are insufficient:: Today the protection is the three-repository check, which the product path drops.
Cost:: One path comparison at resolve time. It affects only people developing WFC itself.

With that rule, self-development is an ordinary consumer: the Maintainer installs WFC N from the Runtime clone into a dedicated environment and runs it against the Development checkout, whose `.wfc/config.yaml` names the check, a maintained development environment on `path_prepend`, and the existing Evidence repository. Detached HEAD and disabled push URL remain checks of the *promotion* procedure, where they belong, instead of preconditions of every Run. *[E]* The per-attempt `pip install` they replace is the source of `BUG-WFC-NESTED-PREPARE-OFFLINE-BUILD-ISOLATION`.

[[identity]]
=== Identity and historical reconstructability

==== A minimal identity model

link:../../backlog/FTR-WFC-CONTRACT-HISTORICAL-RECONSTRUCTABILITY.adoc[`FTR-WFC-CONTRACT-HISTORICAL-RECONSTRUCTABILITY`] waits for the first advance of a governance `schema_version`. The request schema proposed here is that advance, so this design meets its activation criterion and must answer it. Five facts, each recorded where it is cheapest to keep true:

[cols="2,3,3",options="header"]
|===
|Dimension |Value |Recorded in

|Product release
|Distribution name and version (`workflow-coordinator 0.1.0b1`)
|`commission.json` (`compiled_by`), journal, `operator-plan.json`, `audit.json`

|Exact implementation
|`package_tree_sha256`: SHA-256 over the sorted list of (relative path, file SHA-256) for every file of the installed `workflow_coordinator` package, bytecode caches excluded; plus the source commit when known
|same four places

|Contract revisions
|The `schema` or `schema_version` each emitted artifact already carries; program `id@revision` and record digest; operating-contract version and digest
|`commission.json`

|Effective resources
|Layer, origin, digest and frozen path of every role text and guidance file
|`commission.json`; the bytes themselves in the bundle

|Documentation applicability
|An `Applies-to::` line naming the release series
|The consumer quickstart and any agent skill, nowhere else
|===

A PyPI version does not establish bytes: the same version string can come from a wheel, an sdist build, a local checkout or an editable install. The tree digest does, for about twenty files, in milliseconds, independent of the installer.

The source commit needs no build system: a package resource containing `$Format:%H$` and an `export-subst` attribute make `git archive` write the commit into it. *[V]* The Harness already installs the Runtime from a `git archive` export. A build from a plain checkout leaves the placeholder, and the identity then reports the commit as unknown, which is the truth.

This is a record, not a framework: no compatibility matrix, no migration, no version negotiation.

==== Reading historical evidence

Three eras, distinguishable from the artifacts alone and never rewritten:

[cols="1,3,3",options="header"]
|===
|Era |Recognizable by |Implementation identity

|Hand-authored profiles
|`governance/self-development/*-profile.yaml`; no `intent.yaml`
|Runtime commit in the archive's pin file, where one exists

|Intent v1
|`intent.yaml` with `schema_version: 1` and `render-manifest.json` with source commits
|`runtime_head` in `preparation-pins.txt`

|Request v2
|`commission.json` with `"schema": "wfc.commission/2"`; `audit.json` in the archive

|===

One short table of this kind, kept in the Evidence repository's README, is the whole "historical interpretation" mechanism. Old Commissions stay intelligible as evidence. They do not need to compile or launch under a later release, and (F9) most already do not.

==== Automatically rendered provenance in documentation

*[R]* Lower priority, with one exception. The concrete mismatch to prevent is an agent skill or runbook that tells a fresh agent to run `python3 scripts/wfc_op.py ...` after the Front Door has replaced it. *[V]* The Operator Manual's entry document and its running, evidence and example chapters do that today. The remedy is small: `wfc --version --json` prints the identity above, and the quickstart and skill carry an `Applies-to::` line that one test compares with the package version. Rendering provenance into every manual chapter is hygiene with no failure behind it.

=== Major examples of redundant governance

Named so they can be weighed, not a cleanup plan.

. *Disclaimers the conventions already abolished.* link:../../ai_info/doc_conventions.adoc[The writing conventions] say the runtime-authority fact is stated once and "no other document carries a non-authorization disclaimer". *[V]* A phrase search finds one in 43 of the 142 documents outside `cold_storage/`.
. *A status manifest that cannot keep up.* *[V]* `docs/backlog/_open.adoc` still lists the Operator Manual series as "planned / NOT commissioned", and `docs/README.adoc` still describes the additional failure-mode breadth and the successful walkthrough as separately planned, at a HEAD where all ten packages are accepted and recorded in the project history. Status is kept in the manifest, the FTR records, the history chapter and the ledger; the sole "active-work manifest" is the copy that went stale.
. *Tests as per-Commission review records* (F9, F10). Forty tests froze the scope tuples and routes of forty hand-authored Commissions. The practice stopped once the compiler made the check structural. The tests remain and now assert a refusal.
. *Ceremony per unit of work.* *[V]* Each of FTR06 to FTR10 completed cleanly in two Hops (`git log a1648bb..f6824f7`: one Commission commit and two Hop commits each). *[E]* Each also produced an archive commit and a ledger entry, and the sampled Commission (FTR10) carries a task body of several dozen lines. The Run itself was the cheap part.
. *Delegation guarded by string scans.* *[V]* `test_harness_implements_no_archive_mechanics` forbids the words `shutil.copy`, `manifest.json` and `sha256_of` in the Harness source to protect "one implementation", which it does by freezing where that implementation lives.

=== Document authority and the adoption of product direction

*[V]* The Functional Model is indexed as `draft` and `exploratory`, and still carries a pre-convention `Status::` line. The conventions define `exploratory` as "nothing may be built on it without separate adoption", then state that no approval workflow exists. This assignment had to declare three of its sections accepted by instruction. So the classification says the product goals are unadopted, the Maintainer says they are adopted, and no described act connects the two.

*[R]* Minimal clarification, no new framework:

* One sentence in the conventions: *adoption is the Maintainer's commit that changes a document's or section's `Authority::` value.* That is already how every other header changes.
* Apply it once: give Sections 1 to 3 of the Functional Model a section-level `Authority:: normative` using the existing mixed-document rule (conventions 1.4), and replace its `Status::` line with the four-line header. The use cases keep the document default.

Beta 1:: Required.
Decision:: None.

== Migration strategy

=== Constraint

Every package below is built by WFC operating on itself with today's tools: `scripts/wfc_op.py`, Runtime `6c88e476`, Intent v1, `repository-standard@v1`, and a `task-check` that is the whole test suite within 900 seconds. Nothing may break that path until its replacement has run.

=== Bridges

[cols="3,2,3",options="header"]
|===
|Bridge |Kind |Ends when

|`scripts/wfc_op.py` unchanged; v1 functions and constants in `commissioning.py` unchanged; the new compile path added beside them
|Temporary
|Cutover (BP7)

|Role texts exist twice: `governance/self-development/prompts/` and `resources/roles/`; one test asserts byte equality
|Temporary
|Cutover. The governance copies then stay as frozen history; they are inputs of past Commissions.

|`wfc` with today's bare flags passes through to `operator.main`
|Temporary
|One Runtime promotion after cutover, when no prepared `launch.sh` of the old shape can remain

|Evidence `scripts/wfc-archive-run` unchanged and in use
|Temporary
|Cutover. It then becomes a shim or is frozen.

|Existing Evidence layout `archive/<prefix>/<attempt>/` and manifest shape
|Permanent
|--

|Engine input schemas (WorkItem 2, Profile 2, Policy 3, manifest 1, bindings 1)
|Permanent
|--

|`governance/` tree, historical Commissions, 119 archive manifests
|Permanent as evidence, never as compiler input
|--
|===

=== Cutover

. BP1 to BP6 are implemented and accepted through the current path.
. The Maintainer promotes a Runtime that contains them and installs it into a dedicated environment. From then on that installed `wfc` is "Runtime N".
. Development gains `.wfc/config.yaml`: ceiling `src`, `tests`, `scripts`, `docs`; check `python -m pytest -q`; a maintained development environment on `path_prepend`; `evidence.repository: ../workflow-coordinator-run-evidence` with `raw: commit`.
. One self-hosted `wfc run` on a small real task, archived into the existing Evidence repository. Its raw files must match what the old wrapper would have produced for the same STATE (BP5's equivalence test, repeated live).
. After that Run and one more: retire `scripts/wfc_op.py`, remove the v1 compile path and the literal policy check, delete the quarantined test file, update the Harness-bound manual sections and the preparation contract.

If step 4 fails, nothing is lost: the old path is intact and the failure is a finding against a package.

=== What is not a compatibility constraint

Historical Commissions do not need to compile under the new compiler. Historical archives do not get projections. Intent v1 is not accepted by `wfc run`. *[E]* This follows the recorded lifecycle principle of 2026-10-31: provenance and intelligibility are required, indefinite executable compatibility is not.

Acceptance:: The scenario of <<acceptance>> up to the terminal state passes in the neutral fixture, including the two interruption cases. No `pip` invocation occurs anywhere in the path.

Delegable:: Steps 1, 5, 6 yes. The crash matrix (which boundaries, which predicates) should be specified by a stronger model before a cheaper one implements it.

== Beta-1 acceptance scenario

Proposed behaviour, not existing behaviour. Payload: `tidemark`, a Go command-line tool with `go test ./...`, no Python in the repository. The operator's machine has Python 3.10 or later, Git, Go and an authenticated provider CLI.

=== Install and initialize

[source,shell]
----
pipx install workflow-coordinator==0.1.0b1
wfc --version --json

cd ~/src/tidemark
wfc init --adapter claude_cli --model claude-sonnet-5-5 --reasoning high
$EDITOR .wfc/config.yaml        # two edits: scope_ceiling, checks.task-check.argv
git add .wfc && git commit -m "chore: add wfc configuration"
----

`init` writes the skeleton, `.wfc/.gitignore` and an empty Evidence repository under `WFC_HOME`. It detects nothing. The real setup is therefore: install, one command, two edits, one commit.

Friction that remains and belongs on the quickstart's limitations list, each *[V]* in current source: the working tree must be completely clean at launch; root-level files (`go.mod`, `README.md`) must be listed in the ceiling one by one, because a scope path may not be the repository root; agents have no network under the Claude adapter, so dependencies must be present before the Run; commits land on the checked-out branch with a Conventional-Commit subject carrying WorkItem and Hop identifiers; one adapter per Run; a check may take at most 900 seconds; a stopped Run is continued only by a new `wfc run`.

=== Inspect, then run

[source,shell]
----
wfc plan ~/tasks/list-json.md --scope cmd/list --scope internal/render

[[risks]]
=== Unresolved risks and limits of this review

* *Process supervision is designed, not tested.* The lock, the detached engine and attachment by `resume` rest on ordinary POSIX behaviour. *[V]* The adapters start provider processes in their own sessions. *[I]* If the engine dies, a provider process may survive it and keep writing to the working tree. The report says so; nothing in this design stops it. BP4 should establish the facts by experiment before fixing the design.
* *Agents have no network.* *[V]* Claude adapter settings; *[E]* `FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY` calls it a gap under `GOAL-WFC-004`. A first user in an ecosystem that fetches dependencies during work will meet it in their first Run. It is outside this blueprint and inside Beta-1 risk.
* *One adapter per Run.* "Independent" review means fresh context, not a different provider. The configuration is shaped for mixed adapters; the engine's single `--executable` is not.
* *Audit schema without a consumer.* The Findings and convergence structures in `run.json` and `checkpoint.json` were sampled from one clean Run with no Findings. The Findings part of `wfc.audit/1` is the least grounded field list here.
* *Platforms.* Everything inspected assumes POSIX and was exercised on Linux. macOS and Windows were not assessed.
* *The same-repository refusal covers the obvious case only.* It detects a package imported from inside the payload. It does not detect an environment that some other process rebuilds from the payload mid-Run.
* *`interrupted` leaves STATE as the engine left it.* `run.json` then says `ready` with a dispatch marker. The audit record carries the controller's classification; whether the engine should gain a way to close such a Run itself is `FTR-WFC-ATOMIC-HOP-RECOVERY`, deliberately not pulled in.
* *Not examined:* individual archived Runs beyond one recent sample and the first review's Latin citation; `docs/cold_storage/`; the reducer, serialization and adapters beyond what admission and dispatch required; token-usage availability in either provider CLI. No test suite was run.
