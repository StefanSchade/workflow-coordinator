== 1. Motivation

The Workflow Coordinator (WFC) is intentionally authority-bounded. A worker or
correction agent receives a finite authorized scope and may not silently expand
that authority merely because a broader repository check exposes a failure
outside that scope.

That constraint can feel operationally expensive when an otherwise coherent
candidate reaches an adjacent test or document which appears to need a small
update. The evidence-failure-disposition hardening dogfood Run described below
shows why the constraint is valuable.

A normal correction agent is optimized to converge a candidate toward green
evidence. When a failing artifact is an architecture test, however, changing
the artifact may itself be an architecture decision. The locally attractive
repair

[source,text]
----
test is red
-> edit test until candidate is green
----

can become a Procrustean correction: the implementation is preserved by
silently weakening or rewriting the architecture contract that was supposed to
judge it.

The central hypothesis of this note is therefore:

[quote]
____
Level 0 should execute an already-authorized Commission. It should not acquire
architecture-policy authority merely because convergence crosses an
architecture boundary.

When ordinary Level-0 authority is insufficient, the system should stop with
durable facts. A higher orchestration level may then decide whether the next
authorized action is ordinary scope continuation, architecture disposition,
ADR/design work, or human judgment.
____

== 2. Empirical trigger: Run `RUN-c661748adf434e74bcf0e15f2b05ff9f`

This concept was prompted by the evidence-failure-disposition hardening
dogfood Run:

Run ID:: `RUN-c661748adf434e74bcf0e15f2b05ff9f`
Attempt:: `wfc-evidence-failure-disposition-hardening-20261009-01`
Baseline:: `fbe663832cf475daa265479164a0d7827dfae9cb`
Hop limit:: `8`

The relevant sequence was:

[source,text]
----

  -> WorkResult / completed
  -> trusted commit f274db058ecb92c607de086c374c2050dc87c821

H002 independent_review
  -> ReviewVerdict / accept
  -> review commit dbfdea7262e1ecd72fea2f65c8fbefdd5e241f40

This is important for two separate reasons.

First, it demonstrated that the promoted P2 projected result contracts were

acceptance did not complete the Run when Coordinator-owned evidence failed.
The declared evidence-failure route moved execution into correction.

The later H003 stop is the design trigger for this paper.

== 3. Why the H003 stop is useful rather than merely inconvenient

The H003 correction agent identified an architecture-test failure outside its
authorized scope. The immediate repository-local temptation would be to widen
the worker scope and permit the agent to edit the failing test.

That may sometimes be the right final action, but it is not automatically the
right *authority decision*.

An architecture-test conflict can mean at least three materially different
things:

. *Candidate defect.* The implementation violates the intended architecture.
  The correct action is to change production code or the ordinary candidate,
  not the architecture test.
. *Stale architecture test.* The accepted architecture changed legitimately,
  and the test still encodes the previous contract. The test may need a bounded
  update.
. *Architecture decision required.* Candidate and existing test each represent
  plausible requirements or design goals. The correct next step is architecture
  analysis, perhaps an ADR/design process, and potentially human approval.

An ordinary correction worker is not the right authority to collapse these
three cases into "make pytest green".

The current narrow-authority stop therefore exposed a useful separation of
duties:

[source,text]
----
ordinary worker/correction authority
        !=
authority to reinterpret or replace architecture constraints
----

== 4. Level-0 boundary hypothesis

For this concept, *Level 0* means the bounded WFC execution kernel operating an
already-authorized Commission.

Its responsibility is approximately:

[source,text]
----
authorized WorkItem
-> execute bounded phase
-> trusted Git mechanics
-> trusted evidence
-> review/correction routing
-> typed/durable completion or stop
----

Level 0 may contain multiple worker/reviewer Hops and may converge within the
authority granted by its Commission.

Level 0 should *not*, merely because it encounters an obstacle:

* widen its own WorkItem scope;
* manufacture a stronger role with broader authority;
* reinterpret architecture tests as ordinary fixtures;
* create or approve an ADR;
* decide that a previously governing architecture constraint is obsolete;
* silently turn a scope stop into authority to mutate adjacent architecture
  surfaces.

A pre-authorized Commission may of course contain specialized roles and routes.
The important boundary is that the running system does not grant itself new
authority dynamically.

== 5. Level-1 boundary hypothesis

For this concept, *Level 1* means a future outer WorkItem orchestrator above the
WFC execution kernel.

Its broader responsibility may eventually include:

[source,text]
----
bounded backlog / explicit work source
-> select next WorkItem
-> generate or obtain Commission
-> deterministic Commission admission
-> invoke Level 0
-> classify completed/stopped result
-> archive / ledger mechanics
-> choose or prepare authorized successor process
-> next WorkItem
----

Architecture disposition is a candidate Level-1 concern because it answers a
different question from Level-0 correction.

Level 0 asks:

[quote]
____
Can this already-authorized work be completed within the authority and
mechanics granted by this Commission?
____

Level 1 may ask:

[quote]
____
Given this durable stop and its evidence, what *kind of authorized work* should
happen next?
____

This distinction prevents Level 0 from gradually becoming a complete autonomous
software organization.

== 6. Candidate architecture-disposition flow

The following is illustrative only:

[source,text]
----
Level-0 Run
    |
    | scope / semantic-authority stop
    v
Level-1 classification
    |
    +-- ordinary bounded scope miss
    |       |
    |       -> ordinary successor Commission
    |
    +-- architecture-sensitive conflict
    |       |
    |       -> architecture-disposition work
    |             |
    |             +-- candidate is wrong
    |             |      -> correction successor
    |             |
    |             +-- architecture test is stale
    |             |      -> bounded architecture-test update successor
    |             |
    |             +-- architecture itself needs reconsideration
    |                    -> ADR/design process
    |                          |
    |                          +-- bounded decision possible
    |                          |      -> successor Commission(s)
    |                          |
    |                          +-- new material authority / trade-off
    |                                 -> human
    |
    +-- insufficient or ambiguous evidence
            |
            -> human
----

The outer classifier need not initially be a new Level-0 schema concept.

For example, the current Level-0 stop may remain a generic `scope` or
`semantic_authority` stop carrying:

* failing path;
* current phase and role;
* authorized scope;
* trusted evidence failure;
* candidate/review state;
* explicit escalation question.

Level 1 can combine those facts and classify the continuation as
"architecture-disposition-needed".

Only repeated evidence that this distinction must be represented inside Level 0
would justify introducing a new stop kind or route.

== 7. Architecture disposition is not "architect can edit everything"

If future evidence justifies an architecture-disposition role or process, its
authority should remain purpose-specific.

A plausible separation is:

Architecture-disposition reader authority::
Broad read access to the relevant candidate, architecture tests, accepted design
records, ADRs, and governing documentation.

Architecture-analysis authority::
Determine whether the conflict is best characterized as candidate defect, stale
architecture test, architecture ambiguity, or missing governing decision.

Architecture-test write authority::
Potentially permitted only in a bounded successor whose explicit purpose is to
update the stale architecture contract after that disposition is made.

Production-code write authority::
Not implied merely by being an architecture reviewer.

ADR approval authority::
Not implied. Drafting an ADR and accepting an ADR are distinct acts.

The design goal is semantic authority separation, not a privileged
"super-agent".

== 8. ADR / design escalation

Some conflicts cannot be reduced safely to "test stale" versus "candidate
wrong".

For example:

[source,text]
----
new invariant
    vs.
historical behavior
    vs.
compatibility objective
----

may expose a legitimate design trade-off.

At that point a normal correction loop is overextended.

A future Level-1 path may instead create a bounded architecture-analysis or ADR
process:

[source,text]
----
architecture-sensitive stop
-> gather governing evidence
-> analyze alternatives
-> record trade-offs
-> produce ADR/design draft
-> approval according to project policy
-> new Commission(s)
-> Level-0 execution
----

The analysis step could be agent-assisted without granting implementation or
approval authority. Human approval may remain appropriate when the result
creates new material architecture authority, changes a public/trust boundary,
or chooses among genuine trade-offs not already settled by governing records.

== 9. Human escalation is a policy boundary, not necessarily the normal case

The current Run escalated to the maintainer because no higher automated
orchestration level presently exists and the Commission did not authorize the
architecture test.

That does not imply that every future architecture-sensitive conflict must
reach a human.

A future Level 1 may be able to resolve mechanically or through a narrowly
authorized LLM-assisted analysis when:

* the governing architecture decision is already explicit;
* the candidate/test mismatch is unambiguous;
* the necessary successor authority is pre-authorized by project policy;
* no new architectural choice is being made.

Human involvement becomes necessary when the system would otherwise have to
invent new authority or choose a genuinely new architecture policy.

A useful long-term principle is:

[quote]
____
Escalate upward until an existing authority can decide. Do not manufacture that
authority at the lower level.
____

== 10. Relation to Commission generation

This concept is compatible with a future simple Commission-generation pipeline:

[source,text]
----
ticket / successor intent
-> one LLM CommissionDraft
-> deterministic admission
-> optional single bounded repair using validator diagnostics
-> admitted Commission
-> Level 0
----

Architecture disposition should not turn that pipeline into another large
Evaluator-Optimizer system.

If Level 1 concludes that architecture work is required, it should generate a
*different bounded work type / Commission* rather than silently widening the
failed Level-0 Run.

This preserves the desired property that Commission generation remains simple
and fail-closed.

== 11. Relation to the future stateless facade

Internally, Level 0 remains stateful, Git-bound, auditable, and replay-aware.

Externally, Level 1 should eventually be able to consume it approximately as:

[source,text]
----
execute(admitted_commission)
    -> Completed
     | Stopped(durable facts)
----

The outer orchestrator should not need to know the internal number of Hops in
order to classify the result.

Architecture disposition therefore belongs naturally near the consumer side of
that facade:

[source,text]
----
Level 0 reports what happened under granted authority.
Level 1 decides what authorized work should happen next.
----

This separation is compatible with eventually using a general orchestration
framework such as LangGraph above the WFC, without delegating WFC trust/Git
semantics to that framework.

== 12. Mechanism-admission rule

This concept deliberately does *not* propose immediate implementation.

The observed Run is one strong example, not yet evidence for a new generic WFC
mechanism.

Before adding any new Level-0 route, stop kind, role, or persisted field, ask
whether the need can be met by:

. existing scope and semantic-authority stops;
. existing Commission/profile/policy vocabulary;
. Level-1 classification;
. a bounded successor Commission;
. existing review/evidence artifacts;
. ordinary design/ADR governance.

Only repeated observed failures or a concrete imminent requirement should
justify moving architecture-disposition semantics into Level 0.

This follows the project's existing mechanism-admission principle:

[quote]
____
Add mechanism only for observed failure or concrete imminent need; first ask
whether Commission, profile, policy, scope, review, evidence, documentation, or
convention already suffice.
____

== 13. Non-goals / explicitly not authorized

This concept does not authorize:

* a new `architect` WorkflowRole;
* a new `architecture_conflict` stop kind;
* a new `architecture_review` phase;
* automatic write access to `tests/architecture`;
* dynamic scope widening;
* dynamic authority escalation inside a Run;
* autonomous ADR acceptance;
* a general architecture ontology;
* a policy engine;
* LangGraph integration;
* Level-1 implementation;
* changing or resuming `RUN-c661748adf434e74bcf0e15f2b05ff9f`;
* salvaging or committing its dirty H003 state;
* modifying the currently failing architecture test;
* Runtime promotion;
* Evidence or ledger mutation.

All of those remain separate future decisions.

== 14. Questions to answer before implementation

. Is architecture disposition common enough to justify a reusable Level-1
  classification, or should early cases remain explicit maintainer decisions?
. Which existing Level-0 stop facts are sufficient for a higher-level
  classifier without creating a new stop schema?
. What facts distinguish a stale architecture test from a candidate violating
  architecture?
. Which governing documents are authoritative enough for an automated
  architecture disposition, and which require human judgment?
. Should an architecture-analysis agent ever have write authority, or should it
  produce only a decision artifact consumed by a separate successor?
. What exact authority boundary separates "update stale architecture test" from
  "change architecture"?
. When is an ADR required, optional, or inappropriate?
. Which Level-1 decisions can be deterministic, which may use a bounded LLM
  call, and which always require a human?
. What empirical threshold would justify promoting a repeated Level-1 pattern
  into a first-class Level-0 route?
. How should provenance link a successor/ADR process back to the stopped Run
  without treating the predecessor's dirty state as correctness authority?

== 16. Provisional conclusion

The evidence-failure-disposition hardening Run illustrates a useful property of
narrow authority: it prevents a correction agent from turning an
architecture-sensitive repository failure into an ordinary local repair merely
to restore green evidence.

The current stop should therefore not be read simply as friction to eliminate.

It suggests a layered model:

[source,text]
----
Level 0:
  execute already-authorized work faithfully and fail closed at authority edges

Level 1:
  classify durable outcomes/stops and decide what kind of authorized work comes next

Architecture / ADR governance:
  resolve genuine architecture-policy questions

Human:
  grant new material authority or choose unresolved trade-offs
----

This is a hypothesis for future orchestration design, not a request to expand
the current WFC. The immediate value of the note is to preserve the distinction
before a future optimization accidentally converts "make the suite green" into
"allow the worker to rewrite the architecture that judged it".
