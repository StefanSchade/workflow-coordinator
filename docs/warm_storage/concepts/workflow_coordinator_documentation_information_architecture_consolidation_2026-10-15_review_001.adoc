=== D001 -- Current backlog truth must be reconciled and card-complete

Underlying invariant:: A fresh maintainer or agent must be able to learn current
truth and next work from the accepted design and its future active projection,
without reconciling stale headers, implementation reviews, Project Memory, and
later planning concepts.  If the design prescribes six facts for every active
card, it must settle those facts for the specifically commissioned P3.5/P4/P5
family rather than delegate their discovery to Run B.

Evidence::

* Design section 1 says only that P1 is complete/promoted and that P2/P3
  "precede" the remaining entries.  Current canonical Project Memory instead
  records posture
  `p1_p2_p3_delivered_and_promoted_to_runtime_later_slices_unauthorized` and
  identifies `39acb595...` as Runtime's accepted P3 identity
  (`project_memory/canonical/concerns.json`,
  `CONC-WFC-RESULT-CONTRACT-PROJECTION-DELIVERY`).
* `docs/backlog/FTR-WFC-PROJECTED-RESULT-CONTRACTS_implementation_review_008.adoc`
  independently accepts the P3 implementation, and commit `583d732` records
  its later maintainer-owned Runtime promotion.  Calling the P3 design the
  notable live accepted-direction material without also classifying its now-
  implemented lifecycle is therefore not a current-state answer.
* Design section 4 requires every `_open.adoc` card to state status, problem,
  controlling source, next concrete action, prerequisite, and explicit
  boundary.  Its P3.5/P4/P5 table supplies meaning, coarse status, and boundary,
  but not that complete set.
* The amended, reviewed
  `workflow_coordinator_mvp_repository_consolidation_and_level1_transition_concept_2026-10-12.adoc`
  section 4.2 records material dispositions the candidate omits: P3.5 is
  retained as required before the stated milestone and is a prerequisite of
  the authoring-time composition check; P4 is non-blocking and to be assessed
  against milestone need; P5 is conditional and assessed only if a need remains
  after preceding work.  Current Project Memory further says documentation
  consolidation comes before selection of the next product slice and that none
  of P3.5/P4/P5 is authorized.

Risk:: Run B cannot populate the prescribed active card from this plan alone.
It must decide which later planning record qualifies the older controlling
concept, reconcile the already-delivered P3 lifecycle, and invent the missing
next-action/prerequisite text.  That recreates the exact archaeology and
requirement-inflation risk the design is intended to remove.  It can also cause
a fresh reader to infer that P2 or P3 is still pending, or that P4/P5 are an
ordered unconditional queue.

Smallest sufficient correction:: Reconcile the record to current repository
state and provide the actual projection-ready P3.5/P4/P5 family-card content:
for each slice, state its current meaning, why it remains open, current
disposition, controlling source(s) and precedence where their dates/status
lines differ, prerequisite, next concrete action (including when the next
action is maintainer selection or assessment rather than implementation), and
explicit non-authorization.  State plainly that P1-P3 are implemented,
accepted, and promoted, while P3.5/P4/P5 remain unimplemented and unauthorized.
This is status/navigation correction only; it must not redesign or implement
any slice, Front Door, provider, or code architecture.

Disposition:: *OPEN.*

=== D002 -- The plan must contain the semantic migration classification

Underlying invariant:: Run B may perform a read-only inventory to prove
coverage, resolve mechanical links, and execute moves.  It must not need a new
planning exercise to determine which meaningful current records are active
truth and which are history.  Heterogeneous directories require an explicit
path/family disposition or an exhaustive, decision-complete rule plus named
exceptions; "classify later" is not a migration decision.

Evidence::

* In design section 6, `docs/warm_storage/concepts/*.adoc` receives the
  treatment "Classify: retain live warm / archive historical / leave current
  accepted direction discoverable."  This directory actually mixes active
  empirical evidence, accepted but now implemented P3 design/reviews,
  corrected planning hypotheses, non-normative target drafts, and this Run-A
  design/review family.  The row does not say which family goes where.
* The root dated `docs/*.adoc` row likewise says "Classify individually" and
  gives Run B the decision whether each record is a current controlling source
  or archive material.  The candidate itself identifies that mixed root as one
  cause of the present navigation failure.
* For `docs/backlog/`, the plan gives lifecycle rules but no decision-complete
  active set or family mapping from which `_open.adoc` can be seeded.  Existing
  `README.adoc` is acknowledged as stale, and filenames alone do not
  distinguish live BUG/FTR owners from accepted reviews and historical stop
  records.
* Ordered step 1 directs Run B to resolve ambiguous statuses from the authority
  index, record status, and accepted review.  That is appropriate verification
  after Run A has made the semantic plan, but it is not a substitute for the
  missing plan decisions.  The later instruction to stop on genuinely
  conflicting current sources is sound and should remain.

Risk:: A directly commissioned Run B would have to repeat the full warm/root/
backlog archaeology, choose which source is controlling, and author its own
classification output before it could safely move anything.  Different
implementers could produce materially different active manifests while each
claiming to follow this plan.  The result would be another planning layer, and
the accepted design would not actually define the accepted target information
architecture at file/directory level.

Smallest sufficient correction:: Add a compact, explicit migration manifest
covering every heterogeneous current file family that needs a semantic choice.
It may group paths only where treatment is uniform, but must name exceptions.
At minimum it must:

* identify the source records/cards retained on the active backlog path and
  the backlog families moved to `done`, `wont_do`, or `history`;
* give each existing warm concept/review family a retain-warm or exact
  cold-storage disposition, including the P3 design/reviews and this Run-A
  design/review lifecycle; and
* give each top-level dated concept/evidence/review family an explicit retain
  or archive destination.

The manifest need not enumerate generated link edits or Git commands.  Run B's
inventory remains useful as a coverage and conflict check, and a genuine
current-source conflict may still stop for maintainer disposition.  The
correction must not migrate files now.

Disposition:: *OPEN.*

== 4. Non-blocking conclusions

The following parts survived adversarial review and need no independent
redesign to address `D001` or `D002`:

* The authority index / task router distinction is coherent and avoids making
  `ai_info` a second authority source.
* The normal path of current references, active manifest, and at most one live
  warm owner is a compact mental model.
* Cold storage remains available provenance while being excluded from ordinary
  context; the deletion and tombstone rules are appropriately conservative.
* The requirement-inflation guard correctly keeps reviews evidentiary unless a
  current owner explicitly absorbs a requirement.
* WFC's preparation, self-development, recovery, operator, and successor-
  continuation procedures remain first-class operational guidance.  The
  comparison is genuinely bidirectional: WFC adopts Core's lean routing/archive
  ideas while retaining the stronger WFC runbook pattern and flagging it only
  as a possible later Core candidate.
* The design describes the flat `src/workflow_coordinator/*.py` topology only
  as current state and names no future package design.
* The ten-minute fresh-context test has concrete questions, a bounded starting
  context, and a recordable result.
