== 1. Disposition

Outcome:: `changes_required`
Route:: `correction`

The central evidence choice is sound: reuse the current post-provider,
post-commit, pre-reduction evidence seam and narrowly admit a review-less
terminal Worker phase.  This gives Simple one agent dispatch while retaining
Coordinator-owned evidence commands and the existing evidence-failure stop.
The one-phase/no-`goto` programme, hop limit one, completion blocker, scope and
trusted-commit boundaries, and Front Door literal-record approach are all
directionally correct.

Three blocking gaps prevent acceptance.  The chosen `WORK_RESULT` v1 contract
cannot express the design's required Worker-reported `failed` outcome; a valid
candidate can currently complete despite a nonzero or timed-out provider
transport; and the proposed programme has no mechanism that actually projects
the mandatory same-invocation self-check instruction to its Worker.  The
candidate's assertion that only commissioning and evidence-admission code must
change is therefore false.

Review-local blocking identifiers:: `SBR-001`, `SBR-002`, `SBR-003`.
Open blocking identifiers:: all three.

These review-local labels are durable cross-Hop references, not preallocated
Coordinator Finding IDs.  The structured H002 result proposes three new
Current-Run Findings with `finding_id: null`; the Coordinator owns their
authoritative identifiers.

== 2. Review method

The review challenged the committed design against the maintainer decision,
the active backlog, the Front Door contract and compiled Robust-v1 precedent,
the FD-08 BUG record, the deferred P3.5 design, both closed programme records,
and current source at the reviewed baseline.  It independently walked:

* Intent parsing, literal source loading, rendering and equivalence checking in
  `commissioning.py`;
* preflight, evidence admission/preparation, the serial dispatch loop, and
  executable/evidence provenance in `operator.py`;
* result-family selection and hop accounting in `model.py`;
* strict result projection/parsing in `codex_adapter.py`, `adapter.py`, and
  `serialization.py`;
* the provider/commit/evidence/reduction order and interruption boundary in
  `vertical.py` and `slice4.py`; and
* Finding creation/disposition, evidence-failure routing, completion blocking,
  and hop-budget enforcement in `reducer.py`.

The falsification questions were whether any success or failure needs H002;
whether evidence is Coordinator-owned and runs after the sole Worker; whether
every stated outcome is encodable by the selected result family; whether
transport failure remains controlling even when a candidate file exists;
whether a review-less Worker can open an undisposable blocker; whether the
self-check is actually part of the dispatched contract; and whether scope,
Git, source, executable, and existing-programme invariants remain intact.

== 3. Blocking findings

=== SBR-001 -- Worker-reported failure is not representable

Invariant:: Simple must distinguish a Worker-reported task failure from
success, blockage/escalation, mechanical failure, evidence failure, and
provider interruption, using a result contract that the current parser and
reducer can enforce.

The design fixes Simple to a review-less Worker and `WORK_RESULT` v1
(candidate lines 102-115, 175-176, and 210-223), then maps Worker `failed` to
the reducer's `result_failed` stop (lines 131-137).  Current source does not
permit that result:

* `model.py:145-148` defines `WorkStatus` as only `completed` and `blocked`;
* `model.py:654-681` selects `WORK_RESULT` for this exact Worker/no-review
  shape;
* `codex_adapter.py:294-300` exposes only `completed` and `blocked` in the
  strict provider schema; and
* `serialization.py:1289-1317` rejects any other `status` before reduction.

`reducer.py:1660-1663` does contain a generic `Outcome.FAILED` stop, but a
Simple `WorkResult` cannot reach it.  Treating task failure as `blocked` would
erase the distinction the task explicitly requires; emitting `failed` would
produce an invalid candidate and uncertain-dispatch reconciliation rather
than the claimed semantic failure stop.

Correction requirement:: choose and document one minimal, version-honest way
to represent Worker-reported failure.  Account for every affected model,
strict-schema, parser, prompt, reducer/replay, and test seam and update the
bounded implementation scope.  Do not silently widen immutable result v1 or
claim no technical-schema/model change without explaining why that is a
compatible contract evolution.

=== SBR-002 -- provider transport failure can currently fabricate completion

Invariant:: Nonzero provider exit or timeout must be controlling failure
truth and must never reach `COMPLETE`, even if the provider left a
syntactically valid, correlated candidate result.

The design says infrastructure interruption must fail closed (lines 30-34),
claims the existing uncertain-dispatch path is sufficient (lines 138-143),
and excludes any vertical/reducer change (lines 208-225).  That source
assessment is incomplete:

* `vertical.py:324-341` validates any present candidate without first
  rejecting `AgentExecutionOutcome.returncode != 0` or `timed_out`;
* trusted commit and evidence then execute normally, and
  `vertical.py:547-563` supplies no transport-failure mechanical fact to the
  reducer;
* `vertical.py:499-500` records return code and timeout only in staged
  execution evidence; and
* `slice4.py:390-399` enters uncertain recovery for absent/invalid results or
  exceptions, not for a valid candidate paired with a failed transport.

Consequently a process that writes a valid `completed`/`accept` candidate and
then exits nonzero, or is timed out after writing it, can still reduce to
`COMPLETE`.  The proposed negative test covers only a missing result or
unspecified interruption (lines 268-271), so it would not expose this case.

Correction requirement:: place a fail-closed transport check at the existing
execution boundary, define its persisted/recovery result without a second
agent invocation, add the affected production path(s) to the implementation
scope, and require explicit nonzero-with-valid-candidate and
timeout-with-valid-candidate tests.  Preserve the established dispatch marker
and no-replay behavior.

=== SBR-003 -- the mandatory self-check is asserted but not projected

Invariant:: Every Simple Worker must be instructed to perform its self-check
inside the one dispatched invocation; this behavior cannot depend on each
Commission author remembering to restate the programme contract.

The candidate says the Worker performs the self-check (lines 21-28), but later
only says it _may_ self-check (lines 123-129).  Its literal programme selects
the existing generic `worker` role component and no modifier (lines 95-110).
That component, `governance/self-development/prompts/worker.txt:1-3`, instructs
bounded task performance but contains no self-check requirement.  No proposed
compiler, component, or fixed prompt change supplies the missing instruction.

This is not a request for a second reviewer or for Coordinator trust in the
self-check.  The self-check remains agent-attributed and non-authoritative;
the gap is simply that the selected closed programme does not tell the sole
Worker to perform its defining behavior.

Correction requirement:: specify the smallest closed, provenance-preserving
projection of the Simple-only self-check instruction, classify it as
programme-declared behavior rather than maintainer-authored task text, and
include the corresponding compiler/component/source-digest and test scope.
Do not modify the shared Worker component in a way that silently changes
`direct@v1` or `robust@v1`.

== 5. Additional terminal and recovery precision

The correction should also make the terminal table explicit about a
pre-dispatch admission refusal: `_preflight` errors occur before `new_run` in
`operator.main` (`operator.py:1710-1735`), so they do not produce an
`AWAITING_HUMAN` Simple Run.  Post-dispatch commit/scope/evidence faults do
produce a charged Hop and a fail-closed Run state.  Conflating those two
boundaries in candidate lines 138-140 makes operational diagnosis ambiguous,
although it does not itself create a second invocation.

Required-evidence `fail` correctly becomes
`required_evidence_failed_without_route`; evidence `error`/`not_run` is a
mechanical preemption.  In either case a trusted commit already created before
evidence remains observable at the stopped Run's HEAD; the correction should
state this recovery fact rather than imply rollback.

== 6. Acceptance boundary

Acceptance after correction requires all three review-local blockers to be
verified and dispositioned by a later authorized gate.  The focused rereview
should inspect the actual selected result family, transport-failure mechanics,
and dispatched prompt, not rely only on prose changes.

This review does not authorize implementation, a new programme catalogue
entry, a schema change, a Runtime promotion, P3.5, modification of
`direct@v1`/`robust@v1`, or a nested WFC invocation.  Coordinator-owned
`task-check` remains the trusted route evidence; source inspection performed
for this artifact is reviewer-side diagnostic evidence only.
