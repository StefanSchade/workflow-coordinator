This is recorded as a new, independent manifestation of the defect class
`BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY` already names, added to
that record's evidence
(see link:../../backlog/BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY.adoc[the

The distinguishing fact from every prior case in that BUG: the prior cases
(S1/S2/S3-series) were *hand-authored* self-development profiles, each a
bespoke YAML file. FD-08's `verification` phase instead comes from

(`governance/workflow-programs/direct/v1.yaml`, closed per the

dispose it -- survived the move from hand-authored per-Commission profiles
to a reusable, versioned, independently reviewed program. This shows the
defect class is not an artifact of ad hoc profile authoring; it can recur in
a deliberately designed, closed, reusable programme definition.

The reducer's fail-closed stop at H004 is correct, exactly as it was at
S3-002's H003: no engine change is implicated.

== 2. The P3.5 lesson, preserved without promoting its priority

=== 2.1 What the accepted design already addresses

The accepted P3.5 design already separates Finding-*creation* capability
(proposed `may_open_findings`) from Finding-*disposition* authority
(`review.finding_authority`), and states precisely why a gate with
disposition-bearing purpose and `finding_authority: []` is invalid once its
review may enter the authoritative Run Finding ledger. This record does not
claim the original design overlooked authority; it did not. FD-08 is new
*empirical* evidence for an already-identified defect shape, observed for
the first time in a reusable program rather than a hand-authored profile.

=== 2.2 Future conformance/regression fixture (recorded, not authorized)

Record, as a target for a future, separately authorized P3.5 implementation
Commission: a conformance/regression fixture demonstrating that the
`direct@v1` `implement -> verification` authority composition -- a
`blocking_only` gate phase with `finding_authority: []` and no later
disposer -- is rejected by the applicable P3.5 predicate *before any
provider dispatch*, mirroring the already-rejected S3-002 shape. This is
recorded as a requirement for the eventual implementation's test strategy;
no test, profile, or implementation is added by this record.

This fixture must be evaluated against whichever predicate the maintainer
has actually selected -- the existential authority/state-aware reachability
predicate of `DEC-WFC-018`, not the originally accepted universal-path
predicate -- since `direct@v1`'s `implement -> verification` topology has
only one continuation (no branch offering an alternative disposer route) and
is therefore rejected under either predicate. This record does not reopen
that choice; it is restated here only so the future fixture is not
mistakenly built against a predicate the maintainer has since superseded.

== 3. New MVP decision: a `simple` workflow (2026-10-31)

*Maintainer Level-0 MVP scope decision, dated 2026-10-31:* a genuinely
single-agent-invocation `simple` workflow is a Level-0 MVP requirement.

Intent:

* One bounded Worker assignment.
* Self-check/self-review within the *same* agent invocation.
* No mandatory second agent invocation.
* No independent semantic reviewer.
* No correction/review loop disguised as a supposedly simple execution.
* Coordinator-owned mechanical validation, provenance, and fail-closed trust
  boundaries remain mandatory.
* A failed task or failed mandatory evidence must not be silently accepted.
* Implementation must not introduce a second agent invocation merely to
  satisfy the existing evidence-gate design.

The precise mechanism for applying optional/required trusted evidence and
handling failures in a single-invocation program remains an open design
question. The current profile schema is not assumed to already support it
correctly.

In particular: the current runtime may allow Run-native Finding creation by
an agent even without a review phase at all (§2.1 of the governing BUG;
`_apply_legacy_finding_deltas` dispatches a creation with no `review`
descriptor present, per the accepted P3.5 design §2.1). A future Simple
design must define and enforce compatible Finding/terminal semantics for
this case rather than assume the problem away.

This decision is *MVP scope authority only*. It is not authorization to
implement the `simple` program, alter the kernel, or generate a new
Commission. A minimal implementation consistent with the existing Front
Door programme compiler is preferred; no new generic orchestration system is
authorized.

== 4. Programme capability taxonomy

[cols="1,4",options="header"]
|===
|Capability |Description

|`simple`
|Single worker invocation, internal self-check, Coordinator mechanical
checks, no separate semantic review. Newly approved for MVP scope (§3);
*not yet implemented*.

|`direct`
|Worker execution followed by lightweight agentic verification with fresh
context; no independent reviewer persona or mandatory durable review
artifact. `direct@v1` exists and has been dogfooded (FD-08, §1; the earlier
Direct-v1 quickstart and successor Runs). It has a demonstrated
Finding-authority composition problem (§1) and must not be described as
fully successful on the basis of the FD-08 Run alone.

|`robust`
|Worker plus independent reviewer, explicit review/Finding lifecycle,
correction and renewed review where required. `robust@v1` exists and has
been dogfooded (first end-to-end Robust-v1 dogfood,
`workflow-coordinator-run-evidence` Run Ledger).
|===

Do not rename, silently replace, or modify `direct@v1` or `robust@v1` by
virtue of this record. The continuing product value and long-term support
commitment for `direct` as a third offering remain subject to explicit later
review; this record does not decide that question, positively or negatively.
Separate product names (`simple`/`direct`/`robust`) do not automatically
require separate runtimes -- all three execute on the same
`src/workflow_coordinator/` interpreter; what differs is the reusable
workflow-programme definition each one selects.

== 5. Capability, revision, schema, and Runtime are distinct dimensions

*Durable architectural/lifecycle principle:* workflow capability identity,
workflow-programme revision, technical schema version, and Runtime revision
are four distinct dimensions. Conflating any two of them misdescribes either
the product or the implementation.

[cols="1,3",options="header"]
|===
|Dimension |Example

|Programme capability
|`simple`, `direct`, `robust` -- what the workflow is for, as a product
offering.

|Programme revision
|`direct@v1`, and a possible future `direct@v2` -- a specific, closed,
versioned definition of one capability.

|Profile/Run/Result schema
|Independent representation and compatibility formats (e.g. profile
`schema_version: 2` vs. `3`; result-schema v1/v2/v3) -- how a programme
revision's phases/routes/Findings are represented and reduced.

|Runtime Git revision
|The executable implementation (`src/workflow_coordinator/` at a given
Development commit) actually used to execute a Run.
|===

A technical schema version must not become the name of an advertised
product capability.

=== 5.1 Convergence Escape does not generalize across the fleet

`direct@v1` and `robust@v1`'s rendered profiles use profile
`schema_version: 2` (see `governance/commissions/wfc-fd08-scratch-investigation-001/profile.yaml`
and the robust-v1 implementation profiles). Correction-Convergence-Escape
mechanics (Slices 1-4, `FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE`) are already
implemented, but under the separate schema-v3 convergence lineage, which
Front Door's currently rendered ordinary profiles do not use. Do not
describe convergence as globally unimplemented -- it is implemented and
independently accepted through Slice 4 -- and do not describe every
programme as necessarily having that capability: it is schema-v3-lineage
scoped, not a property every `direct`/`robust`/future `simple` programme
revision automatically inherits.

=== 5.2 General design requirement (recorded, not implemented)

Record the general requirement that a future capability/compatibility
declaration mechanism must be able to express these four dimensions
independently -- naming a capability, a specific programme revision, the
schema family that revision's rendered artifacts use, and the Runtime
revision that executed it -- without conflating any pair of them. No
capability registry is designed or authorized by this record; this is
restated as a design constraint for whichever future record takes up the
Runtime/Profile/Commission boundary work
(link:workflow_coordinator_front_door_priority_and_profile_commission_boundary_plan_2026-10-26.adoc[priority
plan] §3.4, §6 Workstream 3).

=== 5.3 Historical contract lifecycle

*Maintainer principle:* historical provenance and intelligibility are
required; indefinite executable backward compatibility is not.

Distinguish:

. Retained historical governing inputs, immutable identifiers, commits, and
  evidence.
. Inspection and faithful explanation of historical Runs.
. Runtime parsing/replay compatibility, where explicitly supported.
. Admission and execution of *new* Runs under actively supported programme
  revisions.

These are different obligations. An old revision may become retired for new
Runs without weakening (1)-(3) for Runs already completed under it. An
in-flight *pinned* Run needs an explicit migration/retirement decision
rather than silent reinterpretation.

The exact support-window policy, migration mechanics, compatibility-test
policy, active-revision selector, and historical-replay requirements remain
future design decisions, explicitly not decided here. This record does not
authorize deleting any compatibility code or weakening any current
replay/admission guarantee; it is a lifecycle direction, not a source-code
refactor authorization. This parallels, and does not alter, the already
distinct treatment of parse/replay/fixture preservation versus new-launch
admission in the accepted P3.5 design §6.3.

* How `simple` enforces compatible Finding/terminal semantics for an agent

* Ownership, versioning, binding, and compatibility-declaration format for
  reusable workflow programmes generally (§5.2; left to the priority plan's
  §6 Workstream 3).
* The exact support-window/migration/retirement policy for a retired
  programme revision (§5.3).
* Whether, and how, `direct` continues as a long-term supported third
  offering alongside `simple` and `robust` (§4) -- explicitly reserved for
  later review, not decided here.
* The eventual field name(s), schema version number, and diagnostic shape
  for any future P3.5 implementation remain as recorded in the accepted
  design's own §10 -- unchanged by this record.
