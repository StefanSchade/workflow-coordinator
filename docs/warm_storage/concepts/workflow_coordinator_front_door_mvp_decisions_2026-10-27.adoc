== 2. New maintainer decisions

=== 2.1 Front Door Basic is the MVP target

Front Door *Basic* -- not Advanced (§2.3) -- is the Level-0 MVP target. A
human may continue to prepare the professional task interactively with an
LLM, exactly as today. Front Door's purpose is to make the *mechanical* steps
-- Commission creation, preparation, admission, execution, and archiving --
as simple and legible as possible.

The professional effort of writing the task description, scope, and
acceptance criteria is explicitly *not* part of the mechanical effort this
milestone minimizes. This narrows emphasis within the existing MVP concept
thesis (§2, §17) and the 2026-10-21 record's Stage 1 framing ("document and
verify, not re-architect"); it does not redefine either.

=== 2.2 Two operating interfaces, one shared Commission contract

Front Door Basic supports two interfaces:

* a comprehensible human CLI, with a guided TUI as a later prospect;
* a stable machine CLI/file interface for automation and, later, Level 1.

Both must produce the same structured, validatable semantic Commission. A
deterministic Commission projection derives the required governing inputs
from it without making its own professional or authority-granting decisions
-- the same authority-free, provider-free projection role the Commissioning
concept already assigns to a `CommissionCompiler` above the trust boundary
(`workflow_coordinator_commissioning_service_concept_2026-10-11.adoc` §5,
§12). The concrete schema shape and implementation decomposition are *not*
designed here (§4).

Usability specifically requires that the operator can see, before and after
execution, which task, which program revision, which authority, and which
model bindings actually entered execution -- not only that a Commission was
accepted.

=== 2.3 Front Door Advanced is optional, deferred, and not the Level-1/Level-0 interface

Front Door *Advanced* -- a later, optional LLM-assisted producer of semantic
Commissions -- remains explicitly post-MVP and unauthorized, consistent with
the 2026-10-21 record's deferral of what it called "Front Door Stage 2"
(§6-7). This record adds one explicit constraint that 2026-10-21 did not
state: Advanced is *not* the interface between Level 1 and Level 0.

Level 1 must be able to submit already-planned, already-authorized work
directly through the shared Commission contract of §2.2. A mandatory
LLM-commissioning hop between Level 1 and Level 0 execution must not become
required for this. Whether Advanced is useful as an optional convenience at
all remains open.

This narrows the 2026-10-21 record's "Front Door Stage 2" direction, which
described a WFC-controlled LLM Run authoring the real Commission as a
plausible first Level-1 capability (§7). That remains a legitimate future
*convenience* hypothesis; it is no longer available as the *required* path
between Level 1 and Level 0. See §3 for the resulting reconciliation and the
still-unresolved Stage-naming question this does not settle.

=== 2.4 Reusable programs: first target candidates, Direct and Robust

First reusable-program design targets, as target *requirements* for a future
design, not already-implemented or accepted programs:

Direct:: A bounded worker task with no independent LLM review, but with
whatever deterministic checks the task actually needs. Approximately the
"simple task" scenario already recorded as a design constraint, not a
shipped program
(`workflow_coordinator_front_door_priority_and_profile_commission_boundary_plan_2026-10-26.adoc`
§4.4).

Robust:: Implementation -> Broad Review; on a Finding, Correction and Focused
Review; once Findings are closed, a *renewed* Broad Review before Complete.
In the clean case, Robust needs only Implementation and Broad Review. After
any correction, no successful Completion may occur without that renewed
full-breadth review -- a fresh broad pass, not merely a stronger final check.

This loop is stricter than, and not yet expressible by, the base-pattern
grammar hypothesis the 2026-10-26 plan records (its §9): that grammar's
twice-occurring `WORK -> GATE -> WORK -> GATE` cycle does not yet name a
gate-to-gate edge that re-enters a *broad* review after a focused
correction-check closes its Findings. This is recorded as a gap the eventual
grammar must cover, not resolved here.

Convergence Escape (per `FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE`, amended by
its Design Revision 001, status `NEXT` pending independent review of that
amendment) is an extension worth investigating for Robust once repeated
correction/review cycles fail to converge. It is explicitly *not* designed
into Robust by this record.

Both programs must preserve, unchanged:

* professional continuation across successor Runs, per
  `DEC-WFC-014` (successor continuation is a fresh, separately authorized
  Run, never resume/retry/replay);
* existing same-Run reconciliation, per the operator manual's terminal-state
  handling (§13-14);
* the separation of salvage, authority, and continuation already canonical
  under `DEC-WFC-013` (salvage preserves work, not authority).

=== 2.5 Archiving as a regular Front Door completion step

Archiving becomes a normal, regular part of a completed Front Door run, not
a separate maintainer chore.

*Location.* The normal long-term archive location moves to a configurable
root inside the consumer repository, preferably `.wfc/archive/`. This
confirms and sharpens the 2026-10-21 record's "candidate hypothesis, nothing
more" framing (§8) into a stated direction: the existing separate
`workflow-coordinator-run-evidence` repository, and the existing mechanical
archiver it already owns
(`../workflow-coordinator-run-evidence/scripts/archive_run.py`,
delegated to by `scripts/wfc_op.py archive` per the operator manual §10),
remain a fully supported alternative operating mode, not a legacy path to be
retired. The archive root must be configurable either way. No new archival
schema, directory layout, or migration is designed or authorized here.

*Audit-trail content.* The target is a deterministic, minimal audit trail
carrying, for each Run: Run/Attempt/Hop/Invocation identities and Git
provenance; the model, adapter, and effective permission bindings; review,
Finding, routing, and evidence outcomes; reported token-consumption data
where available (per the 2026-10-21 record §5's already-decided observational
scope); and a traceable association between WFC-generated commits and the
executions that produced them. `archive_run.py`'s existing `manifest.json`
extraction (run/work-item/policy/profile identities, per-Hop
role/outcome/adapter/model/reasoning facts) is current implementation
evidence of most of this shape; it does not yet carry token-consumption
fields, which remain separately scheduled MVP scope.

*Separation and idempotency.* Run completion and the archive commit must
remain separate acts, exactly as today. The archive must not establish
active runtime authority, must not carry secrets or unnecessary raw
transcripts, and must not be writable by the agent during execution outside
the archiver's own protected path. `archive_run.py` already refuses to
overwrite an existing destination file, which is evidence toward safe
repeated-archive-attempt behavior, not a demonstrated complete idempotency
design; archiving a stopped Run and tolerating a repeated archive attempt
must both work correctly, and the precise placement, protection, and
idempotency mechanics remain design work (§4).

*`run_ledger.adoc` is optional dogfooding, not a Beta-MVP requirement.* The
curated semantic ledger (operator manual §11; today
`workflow-coordinator-run-evidence/project_memory/run_ledger.adoc`) remains a
useful dogfooding practice. It is explicitly *not* a mandatory part of
regular Beta-MVP operation. After the MVP, only the mechanical evidence
archive is required as the general audit trail; a project may continue to
keep an optional curated report on top of it.

=== 2.6 MVP and architecture discipline

Reaffirmed, not newly decided:

* The Claude Code adapter remains MVP-mandatory alongside the Codex CLI
  adapter (2026-10-21 record §4; `DEC-WFC-017` does not touch this).
* Observable token-consumption evidence remains MVP-mandatory (2026-10-21
  record §5; §2.5 above restates its scope for the archive specifically).
* Minimally usable documentation, consumer dogfooding with DMC-refactoring
  evidence, and a separately authorized PyPI beta release remain the
  targeted product-readiness markers (MVP concept §13, §3.3, §6.3).
* Model presets, provider/phase/difficulty lookup, capacity management, and
  Level-1 escalation propagation remain later extensions, not MVP scope.
* No general kernel/package/module refactor before the MVP without a
  concrete need, per `FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES`
  and its unchanged "revisit only during real feature work" disposition.

Newly stated here:

* The historical Commission-specific test load
  (`tests/architecture/test_self_development_governance.py`, per the
  2026-10-25 test-burden finding already tracked in the active-work manifest)
  must be reviewed. Permanent executability of every historical Commission is
  not automatically a product promise. Historical auditability and current
  launch-compatibility are separate requirements, and the eventual review
  must treat them separately rather than assuming one implies the other.
* The accepted 2026-10-27 profile archaeology
  (`workflow_program_profile_archaeology_2026-10-27.adoc`,
  accepted H008) is evidence for exactly one claim: that reusable process
  guarantees (topology, Finding authority, evidence/failure routing,
  mandatory review) are separable from per-Commission bindings (scope,
  persona, evidence profile, artifact paths). It is not, by its own accepted
  status, implementation authority for Front Door, P3.5, Direct, or Robust;
  §2.4 above treats it exactly that way.

== 4. Open design questions

None of the following is resolved by this record:

* The concrete schema of the shared semantic Commission contract, and the
  implementation decomposition of its deterministic projection into governing
  inputs (§2.2).
* Whether the Front Door Basic/Advanced naming introduced here should replace,
  map onto, or coexist with the existing "Front Door Stage 1/Stage 2" naming
  (2026-10-21 §6-7) and the pipeline-target concept's "Stage 0-3" naming
  (already flagged as an unresolved collision by the 2026-10-21 record itself,
  §6 note); this record adds a third naming surface rather than resolving the
  collision.
* The exact workflow grammar edge(s) needed to express Robust's
  renewed-broad-review-after-correction loop, and whether that edge composes
  safely with the monotonicity rule the Commissioning concept's grammar
  hypothesis already requires (§9 there).
* Ownership, ordering, and triggering of Convergence Escape inside Robust, if
  it is ever adopted there.
* The precise `.wfc/archive/` layout, write-protection, and idempotency
  mechanics for repeated or stopped-Run archiving, and how a configurable
  archive root is selected, validated, and recorded.
* How observable token-consumption data (already MVP-mandatory per
  2026-10-21 §5) is threaded into the archive's manifest alongside the
  existing `archive_run.py` fact extraction.
* Whether, and how, the historical Commission-specific test corpus should be
  reclassified between permanent regression guarantees and one-time
  Commissioning validation evidence (§2.6; this is the same question already
  open at the active-work manifest's test-burden-finding row).

== 5. Project Memory

The following decisions are recorded in
`project_memory/canonical/decisions.json`:

* `DEC-WFC-019` -- Front Door Basic, not Advanced, is the Level-0 MVP target;
  mechanical effort minimization excludes professional task/scope/acceptance
  authoring.
* `DEC-WFC-020` -- Front Door Basic's human and machine interfaces share one
  structured, validatable semantic Commission contract with a deterministic,
  authority-free projection to governing inputs.
* `DEC-WFC-021` -- Front Door Advanced is optional, deferred, and explicitly
  not the required interface between Level 1 and Level 0.
* `DEC-WFC-022` -- Direct and Robust are the first reusable-program design
  targets, with Robust's renewed-broad-review-before-Complete invariant.
* `DEC-WFC-023` -- Archiving is a regular Front Door completion step, with a
  configurable archive root preferring repository-local `.wfc/archive/`, the
  separate Evidence repository remaining a supported alternative, and
  `run_ledger.adoc` curation staying optional dogfooding rather than a
  Beta-MVP requirement.
