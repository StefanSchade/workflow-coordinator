=== New blocking Finding: the documented `wfc run --yes` still refuses

Invariant:: The documented unattended `wfc run --yes` invocation must succeed
when the chapter is followed as written by a reader of an unrelated
repository, because the governing BP9 goal is that such a reader can run
unattended *from* this document.

What the chapter says:: The `wfc plan` block passes
`--evidence-argv sh --evidence-argv checks/check.sh`
(`01_quickstart.adoc:134`) and the request paragraph carries the same values
into `evidence:` (`:144-146`). `checks/check.sh` is written as a literal
path; every genuine placeholder on the page uses angle brackets
(`<your model>`, `<model>`, `<evidence-repo>`, `<classification>`,
`<attempt-id>`). The page never says that this is the consumer's *own*
check command, never says it must exist, be committed, exit 0 or leave the
tree unchanged, and never mentions the baseline probe at all. The
Prerequisites section lists Git, a clean tree, Python and a provider CLI --
not a check command (`:19-27`). The limitations list says only that "a
Commission declares exactly one trusted `task-check` command, with a timeout
of at most 900 seconds" (`:226-228`), which tells the reader there is one
such command but not that they must supply it or what it must satisfy.

What the product does:: `wfc run`'s lifecycle order includes a mandatory
one-shot baseline probe between the pre-launch checks and the Commission
commit (`lifecycle.py:782-784`; it is not optional and has no skip flag).
The probe runs the request's own evidence argv with the consumer repository
as the working directory (`lifecycle.py:393-397`) and then refuses the Run
on a non-zero exit -- "baseline probe failed with exit code N; no provider
ran", classification `refused_probe` (`:405-409`), exit code 23
(`:123`) -- and refuses equally if the command mutated the tree or moved HEAD
(`:410-415`). A repository that does not contain `checks/check.sh` therefore
cannot get past this step: executed in this worktree, which has no such file,
`subprocess.run(["sh", "checks/check.sh"])` returns 2, so the reader's
`wfc run --yes` ends at `refused_probe`. Because the `authorized` journal
record is written before the probe (step 1 of the same sequence), that first
refusal also consumes the checkout's single lifecycle: a second `wfc run` on
the same checkout is refused with "a lifecycle already exists for this
checkout; use `wfc resume`" (`:751`, exit 26). And the chapter's own advice
for a non-zero exit -- "*A non-zero exit code does not by itself mean
failure*" (`:170-172`) -- actively points the reader away from the real
cause.

Why it is blocking, not an observation:: It defeats the governing goal in the
same way `F001` and `F002` did, in the last remaining step of the six-step
walkthrough, and the requirement is already owned elsewhere in the manual --
`ch03_running/01_preparation.adoc:123-127` makes "the evidence command's
interpreter resolvable" an explicit preparation precondition. The chapter is
the only plausible place to state it for a reader who has not read ch03, which
is exactly this chapter's audience. It is also not hypothetical for the
author's own trace: a trace that silently seeds a working `checks/check.sh`
passes the probe and hides the gap, which is why neither H001/H003's traces
nor the H002 probe (which refused earlier, at the clean-tree gate) surfaced it.

Correction direction (inside the already-authorized file):: name
`--evidence-argv` for what it is -- the consumer's own single check command --
and state its contract where the reader meets it: it must already exist and
be committed in the repository, be runnable from the repository root, exit 0
on the clean baseline, and leave the tree and HEAD unchanged, because
`wfc run` executes it as a pre-launch baseline probe and refuses the Run
(`refused_probe`, exit 23) otherwise. A one-line `checks/check.sh` in the
example repository plus one sentence is enough; the limitations list needs no
new item.

=== Limitations list: independently re-derived

All nine named items are present, and every claim I checked is true at
`e1c8913`. I re-derived each from source rather than from the prior review:

. *Crash and surviving provider.* `lifecycle.py:14-24` states DG-3 Variant B
  verbatim, including "an unresolved `launch_intent` is always
  `uncertain_launch` and is never launched past"; the classification is real
  (`:116`, exit 17) and raised at `:693` and `:762`. "`resume` ... only
  continues an already-authorized controller from journal and filesystem
  facts" matches `:16-24`. No supervision code path exists.
. *One adapter per Run.* `operator.py:408-411` refuses outright: "mixed
  execution adapters are incompatible with the single scalar executable".
  `config.py:125` closes the adapter vocabulary to `codex_cli`/`claude_cli`,
  as the chapter says at `:68`.
. *One evidence command, ceiling 900 s.* `model.py:26`
  `COORDINATOR_HARD_MAX_EVIDENCE_TIMEOUT_SECONDS = 900`, enforced as
  `1..900` in `frontdoor/request.py:81-84`. The Consumer Request grammar has
  exactly one `evidence` mapping (`request.py:58`, `:110-117`): there is no
  per-phase or per-Hop evidence command.
. *Clean-tree and scope-ceiling rules.* Clean tree as in <<h004-f002>>.
  "Covers only itself and its own descendants; a root-level file must be
  listed individually" is literally `commissioning.py:126-127`
  (`path == root or path.startswith(root.rstrip("/") + "/")`), applied to the
  config ceiling at `:302`.
. *Incomplete recovery conveniences.* `frontdoor/cli.py:18-42` has no
  `continue` branch, so there is no `wfc continue`.
  `frontdoor/preservation.py:1-10` says in its own words that preservation
  "is never adoption, acceptance, scope widening or Finding transfer and
  gives no credit toward review; it does not replace the manual
  salvage/successor procedure" -- which is what the chapter states.
. *One lifecycle per checkout.* `lifecycle.py:748-752` refuses a second
  `wfc run` on a checkout that already recorded an `authorized` lifecycle
  (`refused_active_lifecycle`, exit 26 at `:126`), with no terminal-state
  exception, and `FTR-WFC-LIFECYCLE-ROTATION.adoc:4` is still
  "proposed / backlog; not part of Beta-1", its own interim guidance being
  one fresh checkout per Run (`:50`). The chapter's "What next" and this
  bullet agree.
. *No token usage reported.* `audit.py:466` seeds every projection's
  `limits` with `usage_not_reported` unconditionally, and `:312` writes
  `"usage": None` for every Hop entry. The DG-1 decision is recorded at
  `beta1_execution_plan.adoc:737-742`: option (b), fast-follow, "BP6
  reserves a nullable `usage` field; a value the provider does not report
  stays unknown, never zero". The chapter's wording matches the decision and
  does not overclaim.
. *Qualified platform, only as far as the repository records it.*
  `pyproject.toml:10` is `requires-python = ">=3.10"`, and
  `docs/developer_guide/ch01_development.adoc:11-17` is the record: "The
  current required-suite bundle profile is CPython 3.13 on Linux x86-64 ...
  Host OS, CPU and provider-adapter support require separate qualification.
  ARM64 is an intended target, not a qualified development profile here."
  The chapter restates exactly that and nothing more.
. *WFC never pushes.* No `push` invocation exists anywhere in `src/`, and the
  product says so itself at `wfc init` time ("NOTHING WAS PUSHED"), which I
  observed.

The closing paragraph (`:257-261`) states plainly that live qualification of
each supported provider adapter from an installed wheel is the maintainer's,
is not claimed by the document, and is not substituted for by the
fake-provider test. That satisfies the task's explicit requirement and
nothing on the page contradicts it.

=== The drift test

`tests/unit/test_quickstart_commands.py` builds each real parser by
intercepting `ArgumentParser.parse_args` and reading
`parser._option_string_actions`, so the allowed-flag set comes from `src/`
and not from a hand-maintained list. All four test functions pass at
`e1c8913`. Against simulated `src/` mutations it is genuinely sensitive --
each of these produced a failing assertion with a diagnostic naming the flag:

* renaming `plan`'s `--guidance-path` to `--repository-policy-path`;
* removing `run`'s `--yes`;
* removing `init`'s `--scope-ceiling`;
* renaming `init`'s `--evidence-repository`;
* adding a new *required* flag to `wfc run`
  (caught by `test_documented_commands_supply_every_required_flag`).

That is the acceptance criterion ("fails when a documented flag is removed or
renamed") met with margin. One inaccuracy worth a later word: the comment at
`:128-132` also claims the test kills "a mutation that changes the dispatch
contract so a documented subcommand no longer exists". It does not -- the
module never imports `frontdoor.cli`, and `_PARSE_ARGS` is the test's own
name-to-parser table, so deleting the `run` branch at `cli.py:33` would not
fail this test. The claim overstates the guard; the guard itself is sound.

=== Non-blocking observations

. *The example `default_execution` block cannot simply be appended.*
  `wfc init` already writes `default_execution: {}` (`init.py:189`), and the
  config loader refuses duplicate keys by design
  (`commissioning.py:42-57`). I verified both branches in process: appending
  the chapter's block verbatim (`:59-66`) fails with "invalid Consumer Config
  YAML: ... duplicate key: default_execution", while filling in the existing
  empty mapping parses. The chapter never shows what `wfc init` wrote, so one
  clause -- "replace the empty `default_execution: {}` that `wfc init`
  wrote" -- would remove the trap. Not blocking: the reader opens the file to
  edit it and sees the existing key, and the refusal is explicit. Worth
  folding into the same correction.
. *The hand-authored Consumer Request has no complete example and no link.*
  `:143-152` compresses a closed-schema document into one sentence and omits
  `commission_id`, `work_item_id`, `authority_source`, `program` and
  `evidence.timeout_seconds` by name; `wfc plan` prints a human-readable
  preview (`plan.py:173-222`), not a copyable request. Every omission fails
  closed with a message naming the missing field, so the reader can converge,
  but a pointer to the existing complete example in
  `ch08_examples/03_commission_to_archive.adoc` would cost one link.
. *`<classification>` in the documented `wfc report` path is misleading.* The
  automatic postrun archive files the Attempt under `archive/unclassified/`
  (`archive.py:732`), so a reader substituting their Run's classification
  (`completed`) will not find the directory. `wfc status` prints
  `destination_relative` (`lifecycle.py:1014-1018`), which is the reliable
  way to it.
. *`--guidance-path` vs `--guidance-commit`.* `:141-143` attributes the
  HEAD default to `--guidance-path`; the default belongs to
  `--guidance-commit` (`plan.py:256-257`, `:294`). The behavior described is
  right, the flag named is not.
. *"never touches Git"* (`:139-140`) means never *mutates* Git; `wfc plan`
  does read Git (`repository_identity`, `repository_head`, `_git_text`) --
  as the same page says three paragraphs earlier. The CLI's own help says
  "no ... Git mutation", which is the precise form.
. *Length.* 1,398 words plus six code blocks, nearer three printed pages than
  two. "About two pages" is soft and the content earns its space; the prior
  pass reached the same conclusion.
