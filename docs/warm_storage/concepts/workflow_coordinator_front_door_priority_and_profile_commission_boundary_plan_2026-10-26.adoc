== 1. The priority decision

*Maintainer decision (2026-10-26):* Front Door, including the
Runtime/Profile/Commission architecture refactoring, is prioritized ahead of
further P3.5 implementation.

Reason: P3.5 static validation should target a coherent, stable
workflow-program model. Implementing it now against commission-specific
duplicated profiles risks cementing precisely the structure that needs to
change -- the accepted design's own 43/0 inventory result is partly a symptom
of that duplication, not only of the validator's strictness (see §3).

This decision:

* does not revoke current runtime safety guards, accepted evidence, or the
  underlying `BUG-WFC-SELF-DEVELOPMENT-GATE-FINDING-AUTHORITY`;
* does not amend the accepted P3.5 design or implement anything;
* pairs with the separate maintainer selection of the existential
  authority/state-aware reachability predicate as the intended future P3.5
  requirements direction, recorded in
  `workflow_coordinator_p35_semantic_requirement_escalation_case_2026-10-25.adoc`
  and in the Project Memory decisions this record's own §7 anchors;
* is independently corroborated by the `workflow-coordinator-run-evidence`
  Run Ledger's P3.5 Requirements-Archaeology Reassessment entry (2026-10-26),
  which records the same prioritization as "supplied planning context... not
  a Run outcome."

== 3. Runtime / Profile / Commission: current architecture, target, and gap

=== 3.1 Current architecture decision and source model (unchanged)

`DEC-WFC-003` already defines the core division, and this record does not
replace it:

* Policy determines authority.
* Profile determines flow.
* WorkItem bounds the task and scope.
* Coordinator executes deterministically.
* Agent performs bounded semantic work.

`docs/architecture.md` currently states, and this remains accurate: "consumers
own task inputs, repository policy, workflow profiles, and authorization."
There is no Runtime-owned reusable profile catalogue in the current source
model, and this record does not claim one already exists. Profile files are
authored per Commission under `governance/self-development/`, reviewed and
admitted the same way any other governing input is.

=== 3.2 Maintainer's clarified intended target

*Runtime interpreter (Python):* implements phase execution, routing
semantics, Findings, state transitions, trusted evidence, and enforceable
authority boundaries. This is already true of `src/workflow_coordinator/`
and is not itself a change.

*Reusable workflow programs (YAML profiles):* intended to define stable,
versioned, reviewable workflow structures and mandatory guarantees, reused
across different Commissions rather than recreated per assignment. This *is*
a change from current practice, described in §3.3 below.

*Commission / WorkItem:* defines a concrete professional assignment, selects
an appropriate workflow program, and supplies bounded task-specific
parameters and authorization. Today's WorkItem/Profile pairing already does
this in substance (a Commission already "selects" its one bespoke profile);
the target changes *which* profiles exist to select from, not the
WorkItem/Profile relationship itself.

This target is the maintainer's stated direction. It is not yet designed in
binding/ownership/versioning detail (§3.4), and no implementation is
authorized by stating it here.

=== 3.3 Observed profile/Commission coupling (evidence, not a migration mandate)

Current observations, independently sourced from repository inspection
(`workflow_coordinator_commissioning_service_concept_2026-10-11.adoc` §2.6
and direct counts in this record):

* 45 `*-profile.yaml` files currently exist under
  `governance/self-development/`; 43 existed at the P3.5 design's snapshot
  commit `6807d56`, with two added since for the two P3.5 reassessment
  Commissions.
* Independently reproduced over the 36-profile commissioning-concept
  amendment baseline: 124 phases, 12 distinct phase-*name* sets, but only
  five raw WORK/GATE signatures, which a position/route-target-relative
  normalization reduces further to *one logical cycle* occurring once (9
  profiles, including gate-first continuation truncations) or twice (27
  profiles) -- 36 of 36 profiles accounted for, 35 of 36 exactly, and the
  remaining one (`standalone-developer-ergonomics`) adding exactly one extra
  bypass edge the current reduction does not yet name.
* Phase definitions bundle graph-shape-irrelevant content -- scope,
  authorized actions, evidence commands, review purpose prose, persona text,
  and `finding_authority` -- together with the phase's position in that
  shared logical cycle. Authoring a new ordinary WorkItem today means
  cloning an entire profile file, not instantiating a shared graph with
  per-Commission parameters.
* `tests/architecture/test_self_development_governance.py` has grown to
  7,731 lines / 44 tests (39 Commission-specific) with 42
  `_materialize_bundle()` calls (>=252 Git subprocesses per run), re-executed
  on every trusted-review evidence gate across the whole repository, per the
  2026-10-25 test-burden finding.

These observations strongly motivate a separation refactor. *They do not
establish how many genuinely distinct workflows exist.* No complete
profile-topology census has been performed; the reduction above covers the
36-profile amendment baseline, not all 45 current profiles, and
"effectively one cycle, twice or once" is a structural-position finding, not
yet a verified claim that all content differences (persona, scope, evidence
commands, review purpose) are safely parameterizable. Do not assert that all
43 (or 45) historical profiles are identical or require migration; §6
Workstream 1 is the read-only census this record defers to.

=== 3.4 What the target composition must preserve, and what remains undesigned

Least privilege, restated for this specific composition, not newly invented:

* A reusable profile may specify capabilities and mandatory safety
  obligations (e.g., a mandatory defensive-review gate for a privileged
  phase, see §4).
* A Commission supplies bounded concrete authorization within what the
  profile allows.
* Policy and the Runtime interpreter enforce the effective limits --
  exactly as `DEC-WFC-003` and the Commissioning concept's binding
  invariants (§2.8) already require: the effective execution envelope is
  derived inside trusted Level 0, fail-closed, and a caller may request
  capabilities but never select the concrete mechanism.
* Selecting a phase or supplying a parameter never grants authority by
  itself -- authority comes only from admitted Policy/Profile/WorkItem
  composition, as today.
* A Commission must not weaken a profile's mandatory security requirements
  (for example, it must not be able to parameterize away a profile-mandated
  defensive-review gate).

Left explicitly undesigned by this record, for investigation under §6:

* Where a reusable profile is owned, versioned, and stored relative to
  per-Commission parameters (a single repository-owned catalogue? a
  profile-plus-overlay pair? something else?).
* How a Commission binds to a specific profile *version* so that an
  in-flight or historical Commission's semantics do not silently shift
  under it.
* Backward/forward compatibility expectations when a reusable profile
  changes -- including how historical-inspection/replay fixtures (the 19
  bypassed profiles named in the P3.5 design and in the semantic
  requirement-escalation case record) are preserved independently of new-
  launch admissibility.
* Whether parameterization is expressed as profile-level template slots,
  a layered overlay, or another mechanism -- no mechanism is selected here.

== 4. Genuinely different workflow use cases (design constraints, not today's work)

These are assessment scenarios the target architecture must remain able to
express. None is authorized for implementation by this record.

=== 4.1 Default workflow

Approximately: task/implementation -> independent review -> correction ->
rereview -> completion, with possible repeated correction/review cycles --
matching the one-or-twice-occurring logical cycle in §3.3.

*Open historical question, not a settled standard:* whether a separate final
review phase is present or absent has varied across historical profiles.
This record does not establish when, why, or how often; it is recorded as a
question for the read-only topology census (§6 Workstream 1 and Workstream
2), not resolved here.

=== 4.2 Convergence failure escape

After repeated correction/review cycles without meaningful progress, a
bounded escape path changes perspective toward diagnosis, root cause, or
strategy revision. Per recorded Project Memory evidence
(`SIG-ACT-WFC-CONVERGENCE-ESCAPE-SLICES-1-4`, 2026-10-02 to 2026-10-06),
Slices 1-4 of this machinery are implemented and independently accepted
in the Correction-Convergence-Escape lineage. The controlling record,
`FTR-WFC-CORRECTION-CONVERGENCE-ESCAPE`, remains status NEXT at the active-
work manifest, pending independent review of its Design Revision 001
amendment before any further implementation Commission -- this record does
not classify that work as fully closed, only as partially implemented and
independently accepted through Slice 4.

=== 4.3 Privileged worker and mandatory defensive review

An ordinary worker should not necessarily be allowed to write privilege-
escalation-sensitive surfaces such as Git hooks, CI/CD definitions, or
security-critical tests. A separately authorized elevated worker might be
allowed to modify such surfaces, followed by obligatory defensive review
before successful completion. YAML profile text alone cannot enforce actual
OS/sandbox restrictions or grant elevated authority -- that remains Policy
and Coordinator-derived, per `CONC-WFC-EXECUTION-TRUST-BOUNDARY` and the
Commissioning concept §10.5's capability/information-escalation timing
distinction. Unlike the existential P3.5 repair-availability requirement
(§1), mandatory post-privilege defensive review could legitimately require a
*universal* all-completion-path guarantee -- every path to completion after
a privileged write must pass the mandatory review gate. This is a design
constraint on the target grammar (§3.4), not a decision to build this
workflow now.

=== 4.4 Simple task

A lightweight workflow executing a bounded task without independent review
may be valuable once WFC acts as a standard controlled interface to LLM
execution generally, not only self-development. Recorded as a scenario the
target grammar should remain able to express; not scheduled.

=== 4.5 Level 1

Future orchestration (per `CONC-WFC-LEVEL1-BOUNDARY-DEFINITION`) may create
additional workflow requirements. This record does not prebuild a
generalized platform for speculative Level-1 needs; the existing preference
for "let the hypothesis mature through further observed cases rather than a
platform build" stands.

== 6. Staged workstreams

Prefer incremental, evidence-led delivery. No bulk migration, generic new
platform, or big-bang refactor.

. *Read-only topology and configuration inventory.* Extend §3.3's partial
  reduction to all 45 current profiles (not only the 36-profile amendment
  baseline), separating true graph differences (phase count, route
  topology, gate-first entry points, the one known bypass edge) from
  task-specific bindings (authorized scope, evidence commands, persona/role
  text, review purpose prose, `finding_authority` grants). Read-only; no
  profile is edited by this workstream.
. *Reconstruct the final-review history (§4.1).* Determine, from the actual
  profile corpus and Run Ledger, when and why a separate final review phase
  has been present or absent, as a historical/evidence question -- not as a
  prerequisite for defining today's grammar, but as input to it.
. *Target architecture for reusable profiles and safe Commission
  parameterization.* Design the ownership/versioning/binding/compatibility
  questions left open in §3.4, using Workstream 1's census as evidence for
  how much parameterization surface is actually needed. Front Door Step 2's
  existing provider-free authoring validator (MVP concept §4.4) is the
  natural integration point once this exists.
. *Incremental refactor, exercised first on one real future Commission.* No
  bulk migration. Prove the reusable-profile mechanism on one concrete,
  currently-needed Commission before considering any retrofit of historical
  profiles, consistent with §5's kernel-boundary constraint and with
  `FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES`'s "exercise real
  consumers first" direction.
. *Reduce repeated YAML, per-Commission permanent tests, and operator
  preparation burden.* Builds directly on the 2026-10-25 test-burden finding
  (§2) and on FD-02/FD-03 (§7): classify which of the 39 Commission-specific
  tests are reusable regressions versus one-time Commissioning validation,
  and provide reusable, cheaply validated AsciiDoc Finding-table scaffolds
  before asking authors to hand-write more of them.
. *Operator diagnostics and explicit, safe recovery.* See §7's diagnostic
  concern; FD-04/FD-05/FD-06/FD-07.
. *Reconsider P3.5 after the profile architecture has stabilized.* Only once
  Workstreams 3-4 give P3.5's composition check a stable, non-duplicated
  profile model to validate against. This record does not re-authorize P3.5
  implementation; it names the condition under which reconsidering it next
  becomes coherent.

== 8. Operational diagnostic concern: the unexplained 2026-10-26 provider failure

The requirements-archaeology reassessment's first attempt,
`wfc-p35-requirements-archaeology-reassessment-001-2026-10-26-01`, ended
`reconcile_required` after H001:

* Provider (`codex`) invocation `INV-9e55b2d0931943c69e84fa710a24e091` returned
  `returncode=1`.
* `timed_out=false` -- not a timeout.
* No structured result (`candidate_result_present=false`; `result-message.json`
  empty).
* No trusted commit; HEAD unchanged throughout; worktree clean.
* The actual provider failure cause was not established by that Run's own
  evidence.

The separate second attempt (`...-02`) completed successfully against the
identical Commission and baseline. *That does not retrospectively explain
the first failure* -- it only shows the Commission itself was not the cause.

=== 8.1 What the code actually does today (do not assume capturing is absent)

Inspected directly: `src/workflow_coordinator/codex_adapter.py`'s
`CodexCliAdapter.execute()` already captures both `stdout` and `stderr` from
the provider subprocess (`subprocess.Popen(..., stdout=subprocess.PIPE,
stderr=subprocess.PIPE, ...)`, `codex_adapter.py:387-389`), already bounds
them to the last 16,384 characters via `_bounded()`
(`codex_adapter.py:101`), and already returns them as fields on
`AgentExecutionOutcome` (`codex_adapter.py:408`) alongside `returncode` and
`timed_out`. Capturing itself is not the gap.

The gap is propagation. `src/workflow_coordinator/operator.py` constructs the
audit/invocation record that becomes the operator-visible and persisted
account of a Hop at three call sites (`operator.py:654-656`, `:906-907`,
`:948-949`); each pulls only `outcome.returncode`, `outcome.timed_out`, and
`outcome.candidate_result_present` -- `outcome.stdout` and `outcome.stderr`
are discarded at exactly this boundary and never reach persisted state or
`status` output. The separate smoke/proof-harness tooling
(`codex_adapter_smoke.py:171-172`, `proof_harness.py:251-252`) *does* carry
`stdout_tail`/`stderr_tail` into its own summary -- confirming the capture-
and-bound mechanism is reusable -- but that tooling is a distinct smoke-test
path (FD-06), not the normal operator Hop-audit path a maintainer consults
after a real launched Run fails.

=== 8.2 Candidate requirement

Record, as a bounded candidate for a future design: propagate a bounded,
already-captured stdout/stderr tail (the existing `_bounded()` mechanism) from
`AgentExecutionOutcome` into the same operator-visible audit record that
already carries `returncode`/`timed_out`/`candidate_result_present`, at the
same three `operator.py` sites, for the `returncode != 0` / `timed_out` case
specifically.

This must distinguish, and a future design must state explicitly:

* *Safe operational telemetry* (a bounded, possibly-redacted diagnostic tail
  for operator triage) versus *trusted evidence* (the existing Coordinator-
  owned evidence/review/Finding mechanics, per `DEC-WFC-006`) -- the former
  must never be described or treated as the latter.
* No indiscriminate long-term storage of full provider output or secrets;
  the existing 16,384-character bound and the existing distinction between
  Development-local operator records and the separate Evidence repository
  are starting points, not a designed retention policy.
* This is explicitly not authorization to change `codex_adapter.py` or
  `operator.py` now; it is evidence and a bounded problem statement for a
  separately authorized design Commission (feeding Workstream 6, §6).

== 9. FD-08 scratch-space management and the Commission-Intent/Compiler contract

=== 9.1 Motivating incident

The 2026-10-28/29 `/tmp` tmpfs-exhaustion incident
(link:../incidents/2026-10-28_tmpfs_exhaustion.adoc[incident report]) found
`/tmp` completely full (a 5.7 GiB tmpfs, while `/` itself had over 400 GB
free) during the Front Door Direct-v1 successor Run
(`RUN-c358b544417c4a33a0d040a0d8c38656`,
`WI-WFC-FRONT-DOOR-DIRECT-V1-IMPLEMENTATION-002`): after five productive Hops
reached trusted commit `b70481a`, H006's structured `accept` review result
could not be durably processed because `observe_repository()`
(`src/workflow_coordinator/git_facts.py:477`) copies `.git/index` to a
`tempfile.mkstemp(prefix="wfc-observe-index-")` path -- which resolves under
the ambient system `/tmp` by Python default -- and that copy failed with
`ENOSPC`. The Run stopped `reconcile_required`, not `completed`; see the
incident report and the Run Ledger for the full facts. This section records
FD-08 as the resulting candidate requirement and assesses its contract
boundary; it does not reopen or re-litigate the incident's own open
questions.

=== 9.2 FD-08 requirement

A configurable scratch-space root, defaulting to a location under `$HOME`
rather than the ambient system `/tmp`, that:

* is established, and resolved to one effective path, before the first
  temporary-file operation any operator, agent sandbox, or Evidence-side
  process performs -- not discovered lazily after one has already attempted
  to write;
* is used consistently by Harness/operator-owned temporary operations (for
  example `git_facts.py`'s index-observation copy), by agent-side sandboxes,
  and by the separate Evidence repository's own temporary needs, rather than
  each independently defaulting to the ambient system temp directory;
* remains portable across plain Linux, WSL2, and differing host mount
  configurations, where the ambient `/tmp` may be a small fixed-size tmpfs
  distinct from a much larger root/data filesystem -- exactly the asymmetry
  the incident exposed; and
* keeps the resolved effective path, and the resource backing it, legible to
  an operator inspecting a Run or Attempt afterward -- consistent with this
  plan's existing legibility direction (FD-07), not a new silent default.

This is distinct from FD-01 (§7): FD-01 targets an operator's own repeated
manual environment/path/venv/model-binding rediscovery around the
already-mechanized PREPARE/LAUNCH sequence; FD-08 targets where ordinary
temporary files are written during execution, which FD-01 does not address
and which PREPARE/LAUNCH mechanization does not currently control.

=== 9.3 Explicit contract-boundary assessment

FD-08 does *not* change the accepted Commission-Intent/Compiler contract
(`workflow_coordinator_front_door_commission_contract_design_2026-10-28.adoc`).
That design's boundary (its §2) assigns reusable-program semantics,
Commission-specific task bindings, explicit authorization, and derived
effective permissions to the compiler/Intent side, and assigns "Runtime
execution" -- provider invocation, state transitions, and Git mechanics,
explicitly "not a compiler service" -- to "Runtime/operator under the
separately authorized launch." Scratch/temp-file location is not an Intent
field anywhere in that design's §3 field contract, is not a program or
policy input, and is not a value the compiler projects into any rendered
WorkItem, profile, or policy. Where a Harness process, the Runtime's own code
(`git_facts.py`'s `observe_repository()`), an agent sandbox, or the Evidence
repository stage a transient file is squarely "how the Runtime executes," not
"what a Commission may do" -- the latter being the Commission-Intent
design's entire subject matter.

Concretely, FD-08 is scoped to:

* Harness/operator launcher and preparation mechanics, where a scratch root
  would be resolved and exported, alongside today's PREPARE-time
  environment/path/venv/model-binding discovery;
* the Runtime's own temporary-file call sites, starting with the one
  concretely implicated in this incident; and
* the separate Evidence repository's own temporary-file needs during
  archiving.

FD-08 does not propose, and must not be read as proposing: a Direct/Robust
program change, a new Commission Intent field, a change to
`operator._preflight()`'s admission predicates, or any
`model.py`/`reducer.py` or kernel/shell-boundary change. It is
launcher/operational integration, not program design -- the same distinction
`FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES` already draws
between CLI/operational detail and architectural core.

=== 9.4 Staging

Consistent with this plan's own non-goals (§10) and with FD-01 through FD-07,
FD-08 is recorded here only as a candidate requirement; nothing in this
section authorizes its implementation. If and when scheduled, it is a
separate, small Front Door follow-up step -- sized like the existing Stage
1/Stage 2 items in
`workflow_coordinator_level0_mvp_planning_decisions_2026-10-21.adoc`
§§6-7 -- not an immediate redesign mandate, and not a precondition for
Direct-v1 itself, whose Run already reached H005 successfully before the
unrelated Hop-6 observation-copy failure. No Commission is authorized by
this section.
