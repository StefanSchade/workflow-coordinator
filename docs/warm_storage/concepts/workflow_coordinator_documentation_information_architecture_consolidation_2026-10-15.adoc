== 1. Problem and observed state

WFC already has good current material, but it is not arranged so a reader can
reliably find it without first knowing the repository's history.  The
standalone authority index (`docs/README.adoc`) correctly classifies the root
documents, governance, provenance, imported history, and backlog.  The current
architecture (`docs/architecture.md`), explicit operator contracts
(`docs/run-preparation.adoc`, `docs/self-development.adoc`, and
`docs/run-recovery-and-salvage.adoc`), and operator manual are real current
truth.  The canonical JSON Project Memory is separately and correctly bounded
by `docs/project_memory.adoc` and `project_memory/README.adoc`.

However, `docs/backlog/` mixes open BUG/FTR records with accepted reviews,
implementation reviews, dogfood stop records, bootstrap history, and dated
planning records.  The root `docs/` likewise mixes current reference with
superseded or non-authorizing concepts.  `docs/warm_storage/concepts/` contains
both genuinely live planning/evidence material and delivered-design/review
provenance.  Thus a status line in an individual file is often discoverable
only after archaeology, and a review can look like a second specification.

`docs/wfc_projected_result_contracts_concept_2026-10-07.adoc` §§11--13, 17,

accepted, and promoted to Runtime.  For delivery facts, the accepted P2/P3

the projected-result-contracts concept control; for milestone disposition,

== 2. Empirical comparison and decision

Core's `docs/ai_info/_ai_info.adoc` is a useful task-index: it says "load only
what is relevant", routes review work first, and links small context,
architecture, boundary, workflow, and Project Memory guides.  Core also makes
its active backlog explicit in `docs/backlog/_ftrs_open.adoc` and puts completed
or rejected backlog material in `docs/cold_storage/`; its agent and Git guides
state that cold material is archaeology rather than the normal path.  Those
are answers to navigation and active-versus-history problems, not merely a
directory preference, and WFC should adopt their *smallest useful form*.

WFC is stronger where it has short, explicit operational contracts: generic
preparation, self-development Runtime/Development topology, recovery/salvage,
and the operator manual distinguish authority, deterministic mechanics,
provider entry, recovery, and Runtime promotion unusually clearly.  Preserve
those as first-class current operational documents, surfaced by the new task
index; do not fold them into a generic developer guide or bury them in warm
storage.  This is worth flagging to Core as a possible later adoption
candidate, but this plan makes no Core change.

The deliberate difference is proportionality.  Core has a larger technical
model chapter hierarchy and a mature cold-storage implementation.  WFC should
adopt the two operational ideas (a lean `ai_info` router and a cold archive),
but retain its compact root current-reference set rather than create Core's
many chapter categories, a registry, a second backlog taxonomy, or an
alternative authority system.  WFC's existing `docs/README.adoc` remains the
single authority-class index; `docs/ai_info/_ai_info.adoc` is a task router
which links to authority, never a competing authority index.

Run B creates `docs/ai_info/_ai_info.adoc` as a short table, modeled on Core:
project context/authority, architecture, operations, backlog, Project Memory,
and a review route.  Its entries must name the minimal starting file and the

where a link target would otherwise be ambiguous; it must not paraphrase the

The normal reading path is only current root references, `ai_info`, active
backlog, and the live warm record named by one of them.  A current document
may cite an archived item for provenance, but must give the current conclusion
in its own text and label the historical link non-authorizing.  A review never
becomes current truth merely by being retained.

== 4. Active work, provenance, and the inflation guard

`docs/backlog/_open.adoc` is the sole active-work manifest.  It has a short
intro saying it grants no execution authority, then one card per active item
or tightly coupled roadmap family, with exactly:

* identifier/title;
* status (`NOW`, `NEXT`, `LATER`, or `WATCH` -- existing WFC vocabulary);
* problem and desired outcome in one or two sentences;
* controlling current source (one FTR/BUG or exact concept section);
* next concrete decision/action and known prerequisite; and
* explicit boundary/not-authorized statement.

The P3.5/P4/P5 card is one roadmap-family card, with the three subsection
links and the current meanings/statuses in section 1.  It is not three new
backlog FTRs and does not choose their eventual implementation order beyond
the controlling §17 sequence.  A source record is still where full design and
acceptance conditions live.  A WorkItem/Profile/Policy remains the only
execution authority, exactly as the current authority index says.

`docs/backlog/README.adoc` becomes a concise explanation of that manifest,
status vocabulary, record lifecycle, and the distinction between backlog
intent and a Commission.  It lists neither every review nor a competing
roadmap.  Active BUG/FTR source records stay directly under `docs/backlog/`;
each begins with an unambiguous status and contains a `Current controlling
source`/`Next action`/`Not authorized here` block if it lacks those facts.

Run B moves closed, superseded, rejected, and historical backlog *records and
their review/implementation-review companions together* to
`docs/cold_storage/backlog/{done,wont_do,history}/` as appropriate, preserving
filenames and relative provenance where feasible.  It adds a small
`docs/cold_storage/README.adoc` that says archive material is available
evidence, never current authority, and must be loaded only from a current
pointer or a bounded archaeology need.  A move must leave a current pointer or
small tombstone only when an existing current document needs stable reader
navigation; do not duplicate the archived content.

This enforces a requirement-inflation guard:

1. A problem's controlling source is declared in the active manifest; a
review tests it but does not enlarge it by implication.
2. A review-discovered requirement becomes active only when an accepted
current FTR/BUG/concept explicitly absorbs it, names its owner, and states the
new or amended boundary.  Otherwise it remains evidence in the review.
3. A successor or correction links to the exact open requirement it addresses;
it does not treat historical review IDs, recommendations, or context prose as
an unbounded requirements ledger.
4. When a current source is replaced, the replacement declares supersession
and the predecessor moves to cold storage with provenance retained.  The
active manifest has one preferred pointer for each problem.

This is the DMC-style anti-sediment rule applied to documentation: one owner
for the current statement; join/link rather than mirror; add a category only
when it changes reader decisions.

== 5. Operations, Project Memory, and code boundary

Operational instructions remain deliberately separate from architecture and
backlog.  The Operations route in `ai_info` chooses among:

* `wfc_operator_manual.adoc` for a maintained end-to-end operator overview;
* `run-preparation.adoc` for deterministic preparation and the provider
boundary;
* `self-development.adoc` for the WFC Runtime-N/Development-N+1 specialization
and promotion rules;
* `run-recovery-and-salvage.adoc` after an unclean Run/Hop; and
* `warm_storage/runbooks/successor_continuation_runbook_2026-10-10.adoc` only
when its stated current operational scope applies.

This preserves the real WFC advantage while preventing a fresh reader from
mistaking a concept for a runbook.  Project Memory stays unchanged and outside
the new taxonomy: `docs/project_memory.adoc` is its documentation pointer and
`project_memory/README.adoc` its data-navigation entry; neither backlogs nor
cold documents override canonical JSON.

`docs/architecture.md` retains only observed implemented responsibilities,
authority boundaries, and the deliberately temporary description of today's
flat module layout.  It may have responsibility-oriented links stable across
a future package reorganization, but must not assert future package names,
module groups, or refactor plans.  Run B must record a link to a separately
tracked “Code Architecture Assessment” concern in the active manifest only if
such a current source already exists; it must not invent a proposal or make
this documentation plan one.

== 7. Rejected alternatives

* *Leave the current layout and add a bigger README.*  This leaves active and
historical records co-located and requires a fresh agent to infer status from
many files; a prose index cannot enforce active-only backlog reading.
* *Mirror Core's entire technical-model/chapter and registry structure.*  It
would import taxonomy without a demonstrated WFC reader decision.  The lean
router, active manifest, and cold/archive separation solve the identified
problem.
* *Put all concepts in cold storage.*  This hides accepted but unimplemented
direction, including P3.5/P4/P5 and their controlling concept.  Warm is for
live direction; cold is for completed/superseded evidence.  Delivered P3
design and review material is instead cold provenance under §6.1.
* *Make reviews a requirements source.*  This is precisely the inflation path.
Reviews retain falsification evidence; a current owner must explicitly adopt a
requirement before it controls later work.
* *Use this consolidation to design the code refactor.*  Documentation should
describe observed current responsibility seams and preserve task navigation;
it has no authority to choose future Python topology.
