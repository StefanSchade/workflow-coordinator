== Falsification results

* `_observe_hop` explicitly disables rename detection for the base-to-end range.
  Committed renames and delete-plus-similar-add pairs expose both source and
  destination under `diff.renames=true`, `false` and `copies`. An out-of-scope
  source produces its own scope anomaly; an entirely in-scope move has no scope
  anomaly. Existing pinned-path observation also sees the deleted source.
* Salvage's tracked names, binary classification and patch diffs all use
  `--no-renames`. A staged out-to-in move is refused with the source named.
  When both leaves are authorized, the captured patch contains separate deletion
  and addition records. Existing isolated-index and special-file checks remain.
* Operator prior-Hop context, per-Hop summary and whole-Run summary expose both
  leaves, including an out-of-scope source, across the three configurations.
* The fallback observation in `run_one_hop` supplies `max_commits=0`. One or two
  agent-created commits stop in worker and gate-review Hops, with empty or
  populated scope, empty/review/edit-plus-commit actions, and omitted or correct
  claims. A clean zero-commit Hop still completes in those combinations.
  Returning an intent alongside an agent-created commit cannot legitimize it:
  trusted admission refuses HEAD movement and fallback observation detects the
  commit-cap breach. Recovery observation still parks uncertain dispatches for
  reconciliation; it does not provide an alternative successful Hop path.
* Valid Coordinator-owned edits, additions and deletions still produce exactly
  one clean commit, the exact intended changed-path set, no observation anomaly
  and no claim mismatch under all three configurations. Existing tests retain
  repository/HEAD, path, action, subject, hook, environment and filter protections.
* `_staged_paths`, `_changed_worktree_paths`, trusted admission and result schemas
  have no implementation changes. Under rename detection, naming both leaves of
  a worktree rename still fails with `staged paths differ from commit intent`;
  naming only the destination still fails with `unexpected dirty path` for the
  source. With detection disabled, the existing both-leaf behavior remains
  configuration dependent; this candidate does not add rename-intent support.
* The historical subject-postcondition test changes only the formerly accepted
  agent-commit outcome and adds the new cap assertion. Its invalid-subject,
  identity-collision, Hop charging and checkpoint coverage remains. No legacy
  fields or mechanisms are removed. The separate legacy-debt item is unchanged.
  Operator/Technical Model explanations match the enforced boundary; the bug
  record labels the implementation a candidate and leaves later gates pending.
