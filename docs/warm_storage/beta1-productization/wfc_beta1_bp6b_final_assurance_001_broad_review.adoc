== Verdict

*accept.* No blocking Finding.

All fifteen acceptance cases of the historical BP6b Commission
(`governance/commissions/wfc-beta1-bp6b-evidence-retention-001/intent.yaml`)

== Acceptance case reproduction

=== Case 1 -- configuration (reproduced, holds)

`resolve_evidence` defaults to raw `local` and
`<XDG_DATA_HOME>/wfc/evidence/<repository_name>`; an absent *or empty*
`XDG_DATA_HOME` falls back to `<HOME>/.local/share/...`; neither set is
refused with "HOME is not set" rather than guessed. A relative `repository`
resolves against the payload root (including `../side-evidence`); an absolute
one is used verbatim. All three `raw` values parse; `evidence: {}` defaults
`raw` to `local`.

Refused with a named reason: an unknown key, an invalid `raw` string, a
non-string `raw`, an empty `repository`, a multi-line `repository`,
`evidence` as a list, `evidence` as a scalar.

Existing behaviour is untouched: a config without the block parses, has
`evidence is None`, preserves `raw_text` verbatim, and still requires all six
original keys (each one removed individually is still refused). Adding an
`evidence` block -- with `raw`, or with `repository` *and* `raw` -- leaves
`resolve_execution(...).digest` bit-for-bit identical, so the execution
envelope digest is unaffected by the new vocabulary.

=== Case 2 -- `wfc init` Evidence repository (reproduced, holds)

A new Evidence repository gets `archive/`, a root `.gitignore` carrying the
managed block (both markers, all three patterns), *exactly one* commit, and
`git ls-files` == `['.gitignore', 'archive/.gitkeep']` with a clean worktree.
`git remote` is empty and `git config --get-regexp '^remote\.'` exits
non-zero: no remote, not even an unused one.

A valid existing repository is *reused untouched*: outcome `reused`, HEAD
unchanged, every tracked file byte-identical, still no remote. An existing
*empty* directory is adopted and initialized. A path that is a file is
refused ("not a directory").

A foreign non-empty directory is refused *before anything is written*: the
message names the reason and says "nothing was written", and afterwards there
is no `.git`, no `archive/`, no `.gitignore`, and every byte of the
pre-existing content (including a nested file) is unchanged.

Payload containment, through the real `wfc init` CLI: exit 0, the output
names the Evidence location and prints "NOTHING WAS PUSHED ... has no remote
configured"; `git status --porcelain` in the payload repository lists `.wfc/`
and nothing else; HEAD there is unchanged (`wfc init` still never commits);
an unrelated tracked file is untouched; the written config carries the
requested `evidence` block and re-parses. `--no-evidence-repository` writes
the config only and says nothing about an Evidence repository, and a
default-only init writes *no* `evidence` block at all. `wfc init` pointed at
a foreign Evidence directory exits non-zero and leaves it untouched.

=== Cases 3, 4, 5, 7, 8, 10, 13 -- per-mode retention and privacy (reproduced, holds)

For each mode, a fresh archive exits 0 and reports `ARCHIVED`.

`local`:: `git ls-files` is *exactly*
`['.gitignore', 'archive/.gitkeep', 'archive/unclassified/<attempt>/audit.json']`.
`manifest.json`, `run/` and `ops/` exist on disk. `git status` is clean.
`commit`:: `manifest.json`, `audit.json`, `run/**` and `ops/**` are all
tracked, and the set of tracked Attempt paths equals the set the single
commit touched -- nothing arrived by a second route.
`discard`:: the destination directory contains *only* `audit.json`; the
tracked set matches `local`'s.

One commit per Attempt in every mode (`rev-list --count` delta == 1), each
commit touching only paths under `archive/unclassified/<attempt>/` and each
containing `audit.json`. With two different Attempts in one repository:
exactly two commits, and each commit touches exactly one Attempt.

Privacy, in `local` and `discard`: every blob in the *complete object
database* was decoded and scanned for the fixture's `HOME`, state root and
OPS directory, a canary `USER=` string planted in `run.log`, the real OS user
name, and the real `$HOME`. None appears in any blob -- on the fresh archive,
after a crash and resume, and with two Attempts. In `commit` mode the raw
bytes are present by design, as the recorded decision states.

Idempotency: a re-archive exits 0, reports `ARCHIVE ALREADY UP TO DATE`,
makes *no* second commit, leaves `audit.json` and `manifest.json`
byte-identical, keeps the worktree clean and the tracked set unchanged.

No push, no remote: `git remote` empty, no `remote.*` config key, and no
reflog entry mentioning a push, in every mode.

=== Case 6 -- `raw_retention=None` against the real baseline (reproduced, holds)

The legacy path was not merely asserted against today's tests; it was run
side by side with the code it is supposed to preserve. The `9ebb6d5` tree was
extracted read-only, and the *same* fixture was built twice at the *same
absolute path* -- once with the baseline `src` on `sys.path`, once with
HEAD's -- each run printing the loaded `archive.py` path to prove the two
runs really loaded different modules.

Identical between baseline and HEAD: exit code, stdout (normalized only for
the commit sha, which cannot repeat), stderr, the sha256 of every placed file
other than `manifest.json`, `manifest.json`'s key order, the sha256 of
`manifest.json` normalized for `archived_at`, the parsed manifest with
`archived_at` removed, the absence of `audit.json`, the commit count, the
commit subject, `git ls-files -- archive`, the set of paths the commit
touched, `git status --porcelain`, and the remote list.

The *only* byte difference anywhere is `manifest.json`'s `archived_at` -- a
wall-clock timestamp that cannot be equal across two runs. So: legacy
behaviour writes no `audit.json`, keeps BP5's manifest bytes and commit
shape, tracks the raw files, and configures no remote, exactly as the
baseline does.

One behavioural divergence does exist on this path, on an input the baseline
could never receive. It is reproduced against both implementations and
discussed as <<_obs_1_the_legacy_path_no_longer_reports_a_false_success,
observation 1>>.

=== Case 9 -- crash resume, tamper refusal, different content (reproduced, holds)

The crash was simulated the way the product's own tests do it, by making the
single commit step raise after the atomic placement, so the process dies
between placement and commit.

In *all three* modes: the crashed run fails; it made no commit; `audit.json`
is on disk; nothing of the Attempt is tracked. The resume then exits 0 and
reports `ARCHIVED` -- never a false `ALREADY UP TO DATE` -- for a total of
*exactly one* commit; the commit contains `audit.json`; in `commit` mode it
carries the *full* raw set (`manifest.json`, `run/**`, `ops/**`), in `local`
and `discard` only `audit.json`; the worktree is clean; `local`/`discard`
history is still free of private strings; and a third archive afterwards is a
no-op with no further commit.

Tamper refusal in `local` *and* `commit`: crash, then rewrite *only* the
placed `audit.json` (`attempt_id` -> `wfc-H008-FORGED-ATTEMPT-ID`), leaving
`manifest.json` and every raw file byte-identical so the BP5 placement
re-verification cannot see it. Both modes refuse with
"does not match a projection of its own manifest", commit nothing, track
nothing, and the forged id reaches no blob in the object database. The BP5
tamper class still refuses too: altering a placed raw file after the crash is
refused in both modes with nothing committed.

`discard` different audit: a rewritten placed `audit.json` is refused as
"already exists with different content", nothing is committed, and the file
on disk is *not overwritten*. A destination carrying an unexpected extra
entry is refused as "not a valid discard-retention placement" rather than
resumed.

A placed `local`/`commit` destination whose `audit.json` has been removed is
refused ("has no audit.json") with nothing committed.

a crash on a plausible input.

[#_obs_1_the_legacy_path_no_longer_reports_a_false_success]
=== Observation 1 -- the legacy path no longer reports a false success (flagged for the maintainer)

This is the only reproduced behavioural divergence of `raw_retention=None`
from the baseline, and the only observation this review considered promoting
to blocking. It is recorded in full because the maintainer may want to
confirm the judgement.

`_path_is_tracked_clean`, which the *legacy* path shares, gained a
requirement: the destination must actually appear in the `HEAD` tree, not
merely be absent from `git status`. The scenario was run against *both*
implementations with an identical fixture -- a legacy `raw_retention=None`
archive pointed at an Evidence repository carrying BP6b's managed
`.gitignore`, three times in a row:

[cols="1,2,2"]
|===
|Attempt |baseline `9ebb6d5` |HEAD `67fbbf1`

|first |exit 1, 0 commits, "commit intent path has no worktree mutation"
|exit 1, 0 commits, *identical* message
|second |*exit 0*, 0 commits, `ARCHIVE ALREADY UP TO DATE`
|exit 1, 0 commits, same honest message
|third |*exit 0*, 0 commits, `ARCHIVE ALREADY UP TO DATE`
|exit 1, 0 commits, same honest message
|===

Neither implementation ever tracks a raw file here. So the divergence is
exactly this: the baseline reports a *false success* from the second attempt
onward for an archive it never committed; HEAD refuses consistently.

Not treated as blocking, for four reasons that together are decisive:

. *It cannot occur on the baseline's own input domain.* The scenario requires
  a `.gitignore` that excludes `archive/**/manifest.json`, `archive/**/run/**`
  and `archive/**/ops/**` -- a file only BP6b's `wfc init` writes. Against
  every Evidence repository the legacy path could have been pointed at before
  BP6b existed, behaviour is byte-identical, as case 6 above establishes
  against the real baseline code.
. *No byte differs.* Nothing placed, committed, or printed on any succeeding
  path changes; the divergence is a refusal replacing a false `exit 0`.
. *The acceptance list's own operational test passes.* Case 14 requires
  "BP4/BP5/BP6a tests and the existing suite pass unchanged", and BP5's
  entire archive suite is unmodified on disk and green.
. *Reading case 6 the other way makes the Commission self-contradictory.* It
  would protect, as "legacy behavior", a reproducible report of
  `ARCHIVE ALREADY UP TO DATE` for an Attempt with zero commits -- the exact
  false-success class this Commission exists to close, and a direct conflict
  with the hard rule that a refusal writes nothing and commits nothing.

The change was raised as a blocking Finding inside the historical BP6b Run,
corrected within the authorized scope, and its consequence is stated
explicitly in the limitations record (the section
"`raw_retention=None` remains the unmodified BP5 path, not a fourth mode",
which names `_path_is_tracked_clean` and the false-`ARCHIVE ALREADY UP TO
DATE` it removes). The BP6b Commission's own `escalation_default`
anticipated this tension -- "inability to meet the matrix without changing
BP5 archive semantics for `raw_retention=None`" -- and the historical Run
resolved it by correcting the false success and recording it rather than by
escalating. That recorded, reviewed and documented resolution is what this
review is measuring, and it holds.

[#_obs_2_the_library_level_raw_retention_revalidation_is_unreachable_from_the_cli]
=== Observation 2 -- the library-level `raw_retention` re-validation is unreachable from the CLI

The one surviving mutation: replacing `archive_run`'s
`if raw_retention is not None and raw_retention not in EVIDENCE_RAW_CHOICES`
with `if False:` leaves the whole suite green. The reason is benign --
`wfc archive`'s `argparse` parser declares
`--raw-retention choices=EVIDENCE_RAW_CHOICES`, so an invalid value is
rejected before `archive_run` is entered, and no test calls `archive_run`
with a bad value directly. The guard is defence in depth for library callers,
and no acceptance case names it.

The behaviour itself was verified directly rather than left to inference: a
direct `archive_run(raw_retention=...)` call with each of `'LOCAL'`,
`'everything'`, `''`, `'Local'`, `'local '`, `'none'` and `'0'` is refused
with "must be one of", and none of those refusals placed or committed
anything. Through the CLI, an invalid and an empty `--raw-retention` are both
refused cleanly with no traceback. So this is a test-coverage gap on a
redundant check, not a behavioural one.

=== Observation 3 -- `wfc report <attempt-dir>` reprojects without the derived private strings

`wfc archive` supplies this Attempt's `HOME`, OS user name, state root and
OPS directory to the privacy guard. `report.py:190` calls
`project_audit(path)` with no `private_strings`, so when `wfc report` is
pointed at an attempt *directory* it reprojects using only the built-in
absolute-path/remote-URL heuristics. A projected value that merely *contains*
a private string without itself looking like an absolute path or a remote URL
is therefore printed verbatim by `wfc report`, though `wfc archive` would
have refused to commit it.

Non-blocking: case 10's privacy property is scoped to the Evidence *history*
("the Evidence history (all blobs) contains none of the known ... strings"),
and that holds -- such a value never reaches a commit, because the archive
refuses first. `wfc report` renders to a terminal, writes nothing and commits
nothing. The limitations record already documents that `wfc archive` supplies
a fixed set and that `wfc audit --private-string` exists for anything else.
Case 12 asks only that a guard refusal exit 3, which it does (five variants
verified). Widening `wfc report`'s guard inputs would be a design change, not
a defect correction, and is outside this Commission.

=== Observation 4 -- mode mixing is refused, but by two different guards

Re-archiving one Attempt under a different mode is always refused cleanly
with no second commit and nothing mis-stated (the placed `audit.json` keeps
recording the mode that actually placed it). The refusing guard differs by
direction: `local`->`commit` is caught by the `audit.json` reprojection
("does not match a projection of its own manifest"), while `commit`->`local`
is caught by the `.gitignore` coverage check, because `commit` mode's own
per-Attempt negation `.gitignore` re-includes the raw paths that `local`
requires to be excluded. Both are correct and both are documented in the
limitations record as a structural mismatch; the asymmetry is noted only
because the second message talks about `.gitignore` coverage rather than
about mode mixing, which could read as confusing to an operator. No
acceptance case covers mode mixing.

== Limitations of this review

* Agent-side test results here are exploratory and were run with
  `--wfc-partial`. They are *not* Coordinator-trusted evidence. The
  mandatory full `task-check` is the Coordinator's, and neither this artifact
  nor any accepting verdict in it establishes Run acceptance.
* Four test modules could not be executed in this sandbox for the
  environmental reasons quoted under case 14. All four are untouched by the
  BP6b diff, but this review therefore did not observe them green here.
* The reproductions use synthetic Attempt fixtures. They exercise the real
  `frontdoor.cli` dispatch, the real `frontdoor.init` repository
  construction and real `git`, but not a Run produced by the live engine --
  BP6b has no lifecycle wiring, so no such Run exists to archive.
* `raw_retention=None` equivalence was established against the baseline
  *source tree* extracted from `9ebb6d5` and run in-process, not against a
  separately installed baseline distribution; packaging equivalence was not
  re-derived here.
* Privacy scanning decodes every blob as UTF-8 with replacement. A private
  string split across a binary encoding boundary would not be found; all
  archived content in these fixtures is text.
* `scripts/wfc_doc_catalog.py check` reports "catalog drifted". This is
  *pre-existing and not caused by this Hop*: the same run lists the BP5
  final-assurance artifacts (which predate this Run entirely) as `added`,
  and all 78 unresolved links are in `docs/cold_storage/project_history/`.
  The projection is documented as local and non-authoritative, no test
  enforces its freshness (`tests/unit/test_wfc_doc_catalog.py` -- 18 passed),
  and the catalog file is not in this Commission's scope, so this review did
  not regenerate it.
