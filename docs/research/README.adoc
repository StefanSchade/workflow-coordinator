= Technical research for future WFC capabilities
:toc:
:toclevels: 2

Maturity:: in-review
Authority:: exploratory
Updated:: 2026-11-14
Owns:: Open technical questions and investigation triggers for future product capabilities, without an implementation mandate.

Research explores what could serve a concrete future capability and what is
still unknown. It is not a second active backlog, a set of decided FTRs or a
schedule of implementation epics. Current product work and ordering live only
in link:../backlog/_open.adoc[the backlog overview]; existing technical records
remain in place. A topic's trigger is a reason to investigate, not a decision
to implement its suggested mechanism.

The maintainer's topic direction is recorded in the
link:../../governance/commissions/wfc-backlog-consolidation-001/task.md[consolidation task].
Questions below are deliberately open. No new protocol, process or governance
layer is specified here.

[[r1]]
== R1 — Gondolin and micro-VM controlled agent execution

Motivation:: Explore an execution environment that could provide useful agent
capability with controlled filesystem and networking when a concrete workload
needs more than current provider controls.
Open questions:: What does Gondolin actually offer for this use? What isolation,
startup/resource costs, host prerequisites and nested-provider constraints
would a micro-VM introduce? How would workspace/scratch mounts, Git access,
network access and export of results work? Is credential mediation useful in
such a deployment, and what would it have to protect beyond provider-owned
credential protection? How would this compare with Bubblewrap on the same
workload?
Existing sources:: link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[Execution trust boundaries],
its November-9 product-scope decision, and
link:../functional_model/workflow_program_use_cases.adoc[Functional Model]
§§1.2, 3, UC-05. Gondolin is a maintainer-named investigation lead; no verified
WFC evaluation or micro-VM feasibility result is established by these sources.
Trigger:: A reproducible workload with a concrete isolation/capability gap
that permits comparison of mechanisms. No decision for micro-VMs or against
Bubblewrap has been made; no WFC-owned credential broker is a general requirement.

[[r2]]
== R2 — Linux process lifetime, orphaned agents and crash recovery

Motivation:: Understand when an interrupted Coordinator leaves provider or
check descendants running, spending resources or writing after the apparent stop.
Open questions:: How do process hierarchies, sessions/process groups, Linux
subreaper adoption and cgroups/systemd scopes behave for both provider CLIs?
Which detached/double-forked helpers survive signals or Coordinator death?
What changes after terminal loss, host-process death or reboot? Which liveness
facts are observable reliably, and what recovery information is actually useful?
Existing sources:: link:../warm_storage/beta1-productization/wfc_beta1_implementation_readiness_review.adoc#c4[Third review C4 and X1–X4],
link:../backlog/FTR-WFC-ATOMIC-HOP-RECOVERY.adoc[atomic-Hop recovery],
link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[execution boundaries]
and link:../backlog/FTR-WFC-SELF-DEVELOPMENT-EXECUTION-INTEGRATION-DEBT.adoc[integration debt].
The third review performed source inspection, not those experiments. Its stronger
supervision recommendation is superseded for Beta 1 by the maintainer's narrower
planning basis; the questions remain useful.
Trigger:: Observed orphaned writers, resource loss or recurring crash-recovery
cost justifies a bounded experiment. No Beta-1 subreaper or comprehensive
supervision mandate. Initially document Coordinator crashes and possibly
surviving providers as known limitations; do not predesign refusal protocols.

[[r3]]
== R3 — Provider-independent execution and context boundary

Motivation:: Explore a consistent execution/filesystem view across providers,
then later selective context visibility, including hiding irrelevant historical
artifacts without losing needed provenance.
Open questions:: How should an outer execution boundary compose with each
provider's sandbox, `/proc`, scratch and IPC needs? Can one filesystem view
supply the necessary tools and bounded writable paths across providers? What
should later context control hide, including Git objects/history and derived
outputs, rather than merely hiding a directory name? How would necessary
historical evidence remain retrievable without routine exposure to all history?
Existing sources:: link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[Execution trust boundaries]
(narrow November-6/8 slices and broader deferred questions),
link:../backlog/FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[phase write separation],
link:../cold_storage/sources/pre-0.1.0b1/claude_code_adapter_architecture.adoc[adapter snapshot],
link:../cold_storage/architecture/pre-0.1.0b1/workflow_coordinator_claude_adapter_development_retrospective_2026-11-08.adoc[Claude/Bubblewrap retrospective]
and link:../architecture.md[current architecture]. The Bubblewrap filesystem
primitive and external-scratch mount are implemented; live provider dispatch
integration, unified filesystem/context control and historical-artifact hiding
are not established by them. A stopped WFC qualification and separate maintainer
live observations must not be conflated with accepted integration.
Trigger:: A concrete protected-context, provider portability or context-quality
need that the existing primitives do not satisfy. Explore composition first;
no blanket containment claim or replacement of current provider controls follows.

For a focused exploration of Commission-specific information views and the
knowledge lifecycle, see link:context_sculpting_and_knowledge_lifecycle.adoc[Context sculpting and the knowledge lifecycle].

[[r4]]
== R4 — Controlled internet through proxy, firewall or sandbox

Motivation:: Preserve normal development-agent internet capability while
learning how specific deployments could restrict egress where needed.
Open questions:: Which provider controls already provide ordinary internet
access? When would a proxy, firewall, sandbox networking or domain policy add
value? How would DNS, TLS, dependency downloads, documentation lookup and
credential-bearing requests work? Could controls remain usable and avoid
turning every ordinary request into manual approval? Is an own firewall worth
its cost compared with existing facilities?
Existing sources:: link:../backlog/FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY.adoc[Public-internet capability],
link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[network/egress questions]
and link:../functional_model/workflow_program_use_cases.adoc[Functional Model]
GOAL-WFC-004 / §3.1. The Claude adapter's empty allowed-domain list and denied
web tools are a concrete current capability gap, tracked in the backlog.
Trigger:: A concrete controlled-egress need or evidence that existing controls
cannot provide the required capability. Improving normal network access is
separate current backlog work, sequenced after Claude completion; research
into an own firewall is not its prerequisite or a new Beta gate.

[[r5]]
== R5 — MCP, agent-to-agent and other integrations

Motivation:: Investigate useful external tools/callers without coupling the
Level-0 engine to one integration mechanism or letting callers invent authority.
Open questions:: What real caller/tool workflow needs MCP, agent-to-agent
communication or another interface? What belongs outside Level 0 versus in an
adapter? How would task submission, results, cancellation, credentials and
bounded authority compose? What exactly does the maintainer mean by “ASE
integration”? That term's identity, expansion and API are unverified; no match
to another protocol or project is assumed.
Existing sources:: link:../functional_model/workflow_program_use_cases.adoc[Functional Model]
§§8–9, link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[authority and delegation boundaries],
link:../cold_storage/sources/pre-0.1.0b1/core-incubator/agent_workflow_coordinator_composable_product_and_nested_loop_concept_2026-09-18.adoc[historical integration concept]
and link:../functional_model/workflow_program_use_cases.adoc#_9_level_1_deliberately_unresolved[unresolved Level-1 direction].
The link:../cold_storage/backlog/pre-0.1.0b1/documentation-information-architecture/wfc_documentation_consolidation_plan.adoc[November audit]
is dated provenance; its ASE mention supplies no selected integration.
Trigger:: An identified integration partner and concrete workflow; clarify the
ASE reference before treating it as a technical dependency. No integration
protocol or product API is selected by this topic.

[[r6]]
== R6 — Later Front Door intelligence and orchestration

Motivation:: Reduce task/binding preparation effort after ordinary bounded
execution works, choosing models and roles based on demonstrated task needs.
Open questions:: How can task difficulty be estimated and validated? When do
model routing, provider/role optimization or sidecars improve quality/cost?
Which orchestration belongs outside the deterministic Level-0 loop? What usage,
quality and failure evidence would justify dynamic choices rather than explicit
bindings? How can a caller select within granted authority without weakening
program guarantees?
Existing sources:: link:../functional_model/workflow_program_use_cases.adoc[Functional Model]
UC-02 and §9, link:../backlog/FTR-WFC-ARCHITECTURAL-CORE-AND-CONSOLIDATION-BOUNDARIES.adoc[core/effect separation],
link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[delegation boundary],
link:../warm_storage/beta1-productization/wfc_beta1_product_boundary_review_second_pass.adoc#architecture[later resolution seam]
and link:../warm_storage/beta1-productization/wfc_beta1_implementation_readiness_review.adoc#c1[binding-free Commission].
These reviews describe possible seams, not delivered intelligence.
Trigger:: Repeated task/binding decisions and outcome/cost evidence show a
concrete optimization opportunity. Beta-1 compilation should remain bounded
and deterministic; do not anticipatorily model a full router, sidecar framework
or Level-1 orchestrator there.
