= Context sculpting and the knowledge lifecycle
:toc:
:toclevels: 2

Authority:: Exploratory research; not a current execution contract or implementation mandate.

This report connects the information an agent sees with how project knowledge
is maintained. It extends link:README.adoc#r3[research R3] on execution and
context boundaries and relates to link:README.adoc#r5[R5] on integrations and
link:README.adoc#r6[R6] on later Front Door intelligence. These are questions
for future work, not another backlog or a design decision.

== Motivation and distinction

Execution isolation can constrain the filesystem, writes, Git surfaces,
processes and execution capabilities available to an agent. Context sculpting
has a complementary purpose: deliberately construct the information
environment useful to a particular Commission. Making relevant information
available while excluding distractions and inappropriate material was an
important original motivation for this direction, not merely an incidental
benefit of isolation. The two purposes can share mechanisms, but neither
implies that the other has been achieved.

The established link:../backlog/FTR-WFC-EXECUTION-TRUST-BOUNDARIES.adoc[execution trust record]
distinguishes visibility/read, mutation/write and execution authority. Seeing a
file does not grant authority to change it or run it; a write scope does not
itself establish a read boundary. Prompt instructions alone are not technical
containment. A Commission may request context or capabilities, but cannot
independently grant them: effective authority must remain within trusted policy
and independently admitted authority. The record also addresses information
flow and indirect execution; this report does not replace those concerns.

== Commission-specific information environment

An envisioned environment could expose selected repository paths read-only or
read-write, hide `.git` and sensitive or inappropriate paths, and leave inactive
documentation out of ordinary view. It might also offer read-only external
references, for example an ASE checkout, where authorized and useful. A usable
environment would still need suitable binaries and libraries and writable
temporary space. Different Commissions, or potentially different phases,
could need different views. These are conceptual intentions, not claims that
WFC currently provides such views or grants these capabilities.

A view for a documentation task, for example, might emphasize current models
and relevant working concepts; a bounded archaeology task might need a
specific archived source. Relevance does not itself confer authority on a
source, and access to a reference does not authorize copying protected content
into an incompatible output. Selection must respect the existing trust record.
This discussion specifies no schema, mount compiler or permission framework.

== Knowledge through its lifecycle

Current models and operational documentation contain distilled durable
knowledge needed to understand, develop and operate WFC. Their stated standing
and the link:../README.adoc[authority index] still matter: a current model can
be a draft rather than an execution authority. Warm storage contains working
investigation and development knowledge, including concepts and reviews
awaiting distillation or retirement. Cold storage holds inactive knowledge
outside normal working context, including provenance and reasoning. Cold does
not mean obsolete, invalid or merely historical: a valid idea can become cold
because it is not currently relevant.

When a concept is implemented, its durable functional, semantic, technical and
operational conclusions can be distilled into the appropriate current documents.
Reasoning, rejected alternatives, development history and provenance can be
preserved in cold storage, and working concepts no longer needed for active
work can leave the normal active context. Distillation is not deletion. The
existing link:../ai_info/doc_conventions.adoc[writing conventions] and
link:../cold_storage/README.adoc[cold storage orientation] describe the
present documentation practice; this report proposes no migration or new
mandatory metadata.

An archived idea may be retrieved selectively and reconsidered when relevant.
Retrieval for one task is different from a deliberate decision to reactivate
knowledge in warm or current documentation. Neither opening nor retrieving an
archive automatically gives it current authority. A useful conclusion must be
assessed against current sources before it is treated as current guidance.

== Possible mediated retrieval

A longer-term possibility is to exclude cold storage from an agent's normal
filesystem view while making selected material available on demand through a
controlled separate retrieval service, potentially via MCP. Metadata,
full-text search, semantic search, embeddings and retrieval-augmented generation
(RAG) are possible discovery approaches. None is selected here, and no service
or interface design follows from this possibility. Results would need to be
understood in their provenance and standing, subject to the applicable trusted
information boundary.

The archived link:../cold_storage/sources/pre-0.1.0b1/core-incubator/agent_workflow_coordinator_proposed_architecture_2026-08-25.adoc[proposed architecture]
already discussed bounded retrieval and kept indexing and embeddings outside
the Coordinator. The archived link:../cold_storage/sources/pre-0.1.0b1/core-incubator/agent_workflow_coordinator_composable_product_and_nested_loop_concept_2026-09-18.adoc[capability composition concept]
considered retrieval services and MCP as possible integrations, with installed
services not automatically available as Run capabilities. These are historical
ideas, not current requirements. The separate archived
link:../cold_storage/architecture/pre-0.1.0b1/workflow_coordinator_level1_architecture_disposition_concept_2026-10-10.adoc[Level-1 disposition concept]
provides broader outer-loop context, not authority for a retrieval service.

A retrieval MCP interface might overlap with other capabilities such as Front
Door; whether it should is deferred. The current CLI Front Door direction
suffices for foreseeable needs. Retrieving information and performing
authoritative operations have different trust implications, so an interface
similarity would not settle their relationship. No MCP server or Front Door
redesign is proposed here.

== Implementation and ownership anchors

*Established:* the execution trust record owns the broader visibility,
mutation, execution and information-flow concerns. The
link:../backlog/FTR-WFC-PHASE-WRITE-SCOPE-ARTIFACT-ISOLATION.adoc[phase write-scope record]
tracks a distinct phase artifact-boundary question. The
link:../backlog/FTR-WFC-AGENT-PUBLIC-INTERNET-CAPABILITY.adoc[public internet record]
owns the ordinary agent internet capability gap; its possible network sidecar
is not a knowledge-retrieval service. R3, R5 and R6 retain their existing
research questions and triggers.

*Prepared but unintegrated:* link:../../src/workflow_coordinator/execution_boundary.py[the Bubblewrap primitive]
provides a bounded subprocess facility, including a read-only repository view,
masked `.git`, selected mounts and private temporary space, with a dedicated
external scratch option. It expects already-authorized grants and is not an
authority resolver. The execution trust record describes its narrow authorized
slices and separate nested-provider investigation. Filesystem isolation is not
fully integrated into WFC provider execution: this primitive does not establish
a current provider-wide context boundary. Its repository-wide read-only view
is not selective hiding of inactive documentation or general external references.

*Envisioned:* Commission- or phase-specific selective visibility and mediated
cold retrieval remain open. Repository searches across source, backlog,
research and archived material found historical retrieval ideas and existing
MCP/integration research, but no dedicated active knowledge-retrieval sidecar
record. This observation is for later Maintainer disposition; it does not create
an FTR or duplicate an existing backlog owner.

== Open questions and deferred concerns

* What concrete workload benefits enough from a tailored information view to
  justify an investigation, and which current sources are actually needed?
* How can useful archived evidence be discovered and interpreted without
  confusing task-specific retrieval with promotion to current knowledge?
* How would a future boundary address Git objects and history, symlinks,
  alternate paths and external repositories, rather than only hiding a pathname?
* What tooling, libraries and temporary space are needed for a useful agent
  environment, and how would any phase variation compose with provider controls?
* When would a separate retrieval capability be justified, and what trust
  implications would its interface have alongside authoritative operations?

These are deferred technical and product questions, not commitments. In
particular, this report makes no choice of search technique, service boundary,
filesystem enforcement, network mechanism or Front Door integration.
