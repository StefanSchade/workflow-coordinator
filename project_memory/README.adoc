= Standalone Workflow Coordinator Project Memory
:toc:

== Purpose

This is orientation and steering memory for the standalone Workflow
Coordinator repository, modeled on the flat-JSON canonical-truth principle
used by `spreadsheet-handling/core`'s `project_memory`. It grants no Run
authority and does not override architecture, governance, or backlog.

== Canonical truth

The four files under `canonical/` are the curated source of Project Memory
truth:

* `concerns.json` -- long-lived steering concerns. A concern is broad enough
  to survive multiple implementation slices and explains why an area is
  active or watched. It is not a task and not an individual bug.
* `concern_events.json` -- coarse, dated historical/evidence events. An event
  is deliberately coarser than a commit, finding, or review document.
  `commit_refs` are anchors, not a complete provenance model; a `core:`/`wfc:`
  prefix disambiguates which repository a referenced commit belongs to where
  it matters.
* `concern_event_xrefs.json` -- the flat many-to-many relation between events
  and concerns, each row carrying an `event_role` (`driver`, `trigger`,
  `evidence`, `historical_context`, `watch_item`, `mitigation`,
  `implementation_evidence`, `regression_evidence`). One event can affect
  several concerns differently; do not add list-valued concern references to
  `concern_events.json` itself.
* `decisions.json` -- lightweight, ADR-like anchors for stable decisions that
  future work must remember. A decision is not created merely because
  something happened historically; use `concern_events` for history.

This is intentionally a lean subset of Core's model. It has no `findings`,
`reviews`, `review_sets`, `ftrs`, `ftr_dependencies`, or `releases` tables, no
`extracted/`/`derived/`/`plugins/`/`templates/` directories, no generated
context report, no candidate or commit-signal extraction, no health report, no
Jinja2 rendering, and no JSON Schema. Add another canonical table only when
concrete evidence shows these four cannot represent the required memory.

== Spreadsheet round trip

The four tables can be inspected and edited as an ODS workbook. The flow is
deliberately one-directional in authority terms:

[source,text]
----
project_memory/canonical/*.json      (authoritative)
    -> make memory-export            -> project_memory.ods
    -> edit the workbook
    -> make memory-preview           -> project_memory/staging/*.json + proposed delta
    -> read the delta
    -> make memory-promote           -> approve exactly that proposal
----

Three separate questions, three separate targets. Conflating them is what makes
a review boundary decorative, so the vocabulary keeps them apart:

`make memory-roundtrip-check`:: *Transformation invariant.* Reimports the
workbook into a throwaway directory and requires the result to equal canonical
JSON exactly. Run it on an *unedited* workbook: a non-empty delta there means
the JSON -> ODS -> JSON transformation lost something, which is a defect. It
never reads or writes staging, so it is not, and cannot be used as, the approval
gate for an intentional content edit.
`make memory-preview`:: *Proposal preview.* Imports the edited workbook into a
fresh temporary directory, asserts the exact expected table set
(`concerns.json`, `concern_events.json`, `concern_event_xrefs.json`,
`decisions.json`) and that every imported table parses, and only then replaces
the staging proposal. It then prints the canonical-vs-staging delta as *review
information* and exits 0 -- a non-empty delta is the normal, expected result of
an intentional edit, not a failure. A failed or incomplete import refuses
without touching the previous proposal.
`make memory-promote`:: *Operator approval.* The distinct action meaning "I
approve exactly the proposal I just reviewed". It refuses unless staging is
complete, staging still carries the fingerprint that was previewed, and
canonical still carries the baseline fingerprint the proposal was reviewed
against. After a successful promotion the proposal is consumed, so a stale
approval cannot be replayed.

The binding is `reviewed canonical baseline` + `reviewed staging content` ->
`promoted canonical content`. `memory-preview` records both fingerprints under
`project_memory/.proposal/` (untracked) and prints them; that record identifies
which proposal was previewed and is *not* authority and *not* approval. The
workbook deliberately stays outside the binding: it is an editing source, so
re-exporting or further editing it after a preview does not invalidate the
proposal that was already materialised and reviewed. Any change to canonical or
to staging does, and then a fresh `make memory-preview` is required.

Each target is a single process that sequences import, comparison, and mutation
internally. No correctness property depends on Make prerequisite ordering, so
`make -j` cannot diff before importing, replace a proposal between its review
and its promotion, promote a staging state that was never displayed, or promote
against a canonical baseline that has moved. Preview and promotion are separate
invocations by design: asking one parallel invocation for both
(`make -j memory-preview memory-promote`) still cannot promote an undisplayed
proposal -- the promotion either refuses or approves an outstanding previously
previewed one -- but it removes the reading step the protocol exists to create.

`make memory-setup` installs the pinned `sheets-run` tooling from
`requirements/spreadsheet-handling.txt`. That pin is maintainer tooling only --
no `workflow_coordinator` source imports it -- and `SHEETS_RUN=<path>` overrides
the executable if it is already available elsewhere. `project_memory.ods`, the
contents of `project_memory/staging/`, `project_memory/.proposal/`, and any
generated `_meta.yaml` (workbook column presentation, not memory data) are
generated artifacts and stay untracked.

== What this is not

* Not an authorization source. A concern, event, or decision here grants no
  Run, push, or promotion authority.
* Not a replacement for detailed evidence. `docs/backlog/BUG-WFC-*.adoc`,
  `docs/backlog/FTR-WFC-*.adoc`, review artifacts, and Git history remain the
  detailed provenance layer; canonical memory is intentionally lossy relative
  to that history and links back to it via `commit_refs` and `source_path`.
* Not automatically generated or promoted. Nothing extracts memory content from
  commits, reviews, or documents in this lean version. The only mechanical path
  into these files is the previewed and separately approved workbook promotion
  described under <<Spreadsheet round trip>>; otherwise the four files are
  curated and updated by hand.
* Not a task list. Concerns are steering fields, not a backlog; the backlog
  itself remains `docs/backlog/README.adoc`.

== Updating this memory

Edit the JSON files directly, or edit the workbook and promote it as described
above. Keep `id` values unique per table, keep `concern_event_xrefs` entries
pointing at existing `concern_events`/`concerns` rows, and keep new concerns few
and broad rather than one per bug or commit. `docs/project_memory.adoc` is a
short pointer into this directory, not a second copy of this data.
