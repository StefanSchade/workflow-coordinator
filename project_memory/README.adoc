= Standalone Workflow Coordinator Project Memory
:toc:

== Purpose

This is orientation and steering memory for the standalone Workflow
Coordinator repository, modeled on the flat-JSON canonical-truth principle
used by `spreadsheet-handling/core`'s `project_memory`. It grants no Run
authority and does not override architecture, governance, or backlog.

== Canonical truth

The four files under `canonical/` are the curated source of Project Memory
truth:

* `concerns.json` -- long-lived steering concerns. A concern is broad enough
  to survive multiple implementation slices and explains why an area is
  active or watched. It is not a task and not an individual bug.
* `concern_events.json` -- coarse, dated historical/evidence events. An event
  is deliberately coarser than a commit, finding, or review document.
  `commit_refs` are anchors, not a complete provenance model; a `core:`/`wfc:`
  prefix disambiguates which repository a referenced commit belongs to where
  it matters.
* `concern_event_xrefs.json` -- the flat many-to-many relation between events
  and concerns, each row carrying an `event_role` (`driver`, `trigger`,
  `evidence`, `historical_context`, `watch_item`, `mitigation`,
  `implementation_evidence`, `regression_evidence`). One event can affect
  several concerns differently; do not add list-valued concern references to
  `concern_events.json` itself.
* `decisions.json` -- lightweight, ADR-like anchors for stable decisions that
  future work must remember. A decision is not created merely because
  something happened historically; use `concern_events` for history.

This is intentionally a lean subset of Core's model. It has no `findings`,
`reviews`, `review_sets`, `ftrs`, `ftr_dependencies`, or `releases` tables, no
`extracted/`/`derived/`/`plugins/`/`templates/` directories, no generated
context report, no candidate or commit-signal extraction, no health report, no
Jinja2 rendering, and no JSON Schema. Add another canonical table only when
concrete evidence shows these four cannot represent the required memory.

== Spreadsheet round trip

The four tables can be inspected and edited as an ODS workbook. There are
exactly two persistent representations -- canonical JSON and the workbook --
and Git is the review, acceptance, and rollback boundary:

[source,text]
----
project_memory/canonical/*.json      (authoritative)
    -> make memory-export            -> project_memory.ods
    -> edit the workbook
    -> make memory-import            -> canonical JSON, as working-tree changes
    -> git diff                      -> read the change
    -> git commit                    (accept)   or   git restore  (reject)
----

`make memory-export`:: Renders canonical JSON into `project_memory.ods`.
`make memory-import`:: Converts the edited workbook into a fresh temporary
directory outside the repository, requires the conversion to succeed and to
produce exactly the expected table set (`concerns.json`, `concern_events.json`,
`concern_event_xrefs.json`, `decisions.json`) with every table parsing as JSON,
and only then replaces the canonical files. A failed, partial, or malformed
conversion therefore leaves canonical Project Memory exactly as Git recorded
it. The temporary directory is defensive implementation machinery with no
identity: it is not a proposal, it is not awaiting approval, and it is
discarded when the process ends.
`make memory-roundtrip-check`:: *Transformation invariant.* Renders canonical
JSON to a temporary workbook, reimports that into a temporary directory, and
requires the result to equal canonical JSON exactly. A non-empty delta means
the JSON -> ODS -> JSON transformation lost something, which is a defect. It
writes neither canonical JSON nor the maintainer's `project_memory.ods`.

Import refuses to start when `project_memory/canonical/` already carries
uncommitted changes, so it can never silently overwrite a canonical edit made
by hand; commit or discard that edit first. Row deletions and other content
edits inside a valid workbook are ordinary data editing, but a missing table in
the converted result is an incomplete import and is rejected rather than
treated as a request to delete a canonical table. The importer also refuses a
`project_memory/canonical/` that a symbolic link redirects outside the
repository, and replaces each table by renaming onto its canonical name, so no
write can escape the repository-owned directory.

The four canonical files are replaced individually after the complete result
has been validated. No cross-file transactional or crash-atomic guarantee is
claimed: a process, machine, or filesystem failure during the replacement could
leave a mixed canonical state, which `git status` and `git restore` recover.
There is deliberately no journal, lock, or recovery protocol.

No memory target is a prerequisite of another, and each is one self-contained
process, so no `make` invocation mode -- `-j` included -- can act on stale
output. The stronger staged-proposal/fingerprint promotion protocol that
preceded this design, together with its reviews, remains available in Git
history (`aa219a6`, `56f4a04`, `d201af5`, `773ea97`); see `DEC-WFC-010` for why
it was not carried forward.

`make memory-setup` installs the pinned `sheets-run` tooling from
`requirements/spreadsheet-handling.txt`. That pin is maintainer tooling only --
no `workflow_coordinator` source imports it -- and `SHEETS_RUN=<path>` overrides
the executable if it is already available elsewhere. `project_memory.ods` is a
generated artifact and stays untracked.

== What this is not

* Not an authorization source. A concern, event, or decision here grants no
  Run or push authority.
* Not a replacement for detailed evidence. `docs/backlog/BUG-WFC-*.adoc`,
  `docs/backlog/FTR-WFC-*.adoc`, review artifacts, and Git history remain the
  detailed provenance layer; canonical memory is intentionally lossy relative
  to that history and links back to it via `commit_refs` and `source_path`.
* Not automatically generated. Nothing extracts memory content from commits,
  reviews, or documents in this lean version, and nothing commits on the
  maintainer's behalf. The only mechanical path into these files is the
  validated workbook import described under <<Spreadsheet round trip>>, whose
  result is an ordinary reviewable working-tree change; otherwise the four
  files are curated and updated by hand.
* Not a task list. Concerns are steering fields, not a backlog; the backlog
  itself remains `docs/backlog/README.adoc`.

== Updating this memory

Edit the JSON files directly, or edit the workbook and import it as described
above, then review the result with `git diff` and commit it. Keep `id` values
unique per table, keep `concern_event_xrefs` entries pointing at existing
`concern_events`/`concerns` rows, and keep new concerns few and broad rather
than one per bug or commit. `docs/project_memory.adoc` is a
short pointer into this directory, not a second copy of this data.
